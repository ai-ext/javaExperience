# R03 MySQL 8.4 공식 근거 조사

**확인일:** 2026-10-20 (Asia/Seoul) · **범위:** R03 원문, 원본 `schema.sql`·`seed.sql`, Oracle MySQL 8.4 공식 문서/다운로드 페이지. 본문은 문서 근거 정리이며 SQL을 실행한 실측 결과가 아니다.

| `VARCHAR(n)`의 n은 문자 수 한도이며 실제 payload는 문자셋과 값에 따른 바이트 수다. `utf8mb4` 문자는 최대 4바이트이므로 255문자 최악 payload는 1,020바이트. 길이 접두사는 최대 가능 바이트가 255 이하일 때 1바이트, 초과 가능하면 2바이트. | [CHAR/VARCHAR](https://dev.mysql.com/doc/refman/8.4/en/char.html) §13.3.2 문단 228 및 231; [저장 요구량](https://dev.mysql.com/doc/refman/8.4/en/storage-requirements.html) §13.7 문단 319–330; [utf8mb4](https://dev.mysql.com/doc/refman/8.4/en/charset-unicode-utf8mb4.html) | 선언 길이·charset에 의존. `CHAR_LENGTH()`/`OCTET_LENGTH()`는 각각 문자 길이/바이트 길이를 확인할 때 쓰는 함수. | payload와 접두사는 실제 행의 전체 physical row/page/disk 사용량을 뜻하지 않는다. 행 헤더, InnoDB 레코드 포맷, off-page 저장 등과 별개. 문서가 관습적 `255`의 단일 역사적 원인을 확정하지 않는다. |
| `CHAR`는 지정 길이로 우측 공백 패딩해 저장하고 기본 검색 시 후행 공백을 제거한다. 문자열 비교의 후행 공백 취급은 collation의 `PAD SPACE`/`NO PAD` 속성을 따른다. | [CHAR/VARCHAR](https://dev.mysql.com/doc/refman/8.4/en/char.html) §13.3.2 문단 226–229, 260–265 | `PAD_CHAR_TO_FULL_LENGTH` SQL mode가 CHAR 반환 시 공백 제거 동작에 영향. | 특정 비교 결과는 해당 열 collation에 좌우된다. |
| strict mode는 transactional table의 잘못된/누락 값을 변경하는 문장에서 오류 후 문장 롤백을 낸다. `DECIMAL` 등 exact-value와 `FLOAT`/`DOUBLE` approximate-value는 구별한다. | [SQL modes](https://dev.mysql.com/doc/refman/8.4/en/sql-mode.html) §7.1.11 문단 637–646; [precision math](https://dev.mysql.com/doc/refman/8.4/en/precision-math.html) §14.24; [FLOAT/DOUBLE](https://dev.mysql.com/doc/refman/8.4/en/floating-point-types.html) §13.1.4 | `STRICT_TRANS_TABLES` 활성 여부 및 storage engine/statement 조건에 의존. | 길이초과와 숫자범위초과의 정확한 오류·영향은 데이터 변경문, 엔진, IGNORE 및 설정에 좌우된다. `CAST(0.1 AS DOUBLE)+CAST(0.2 AS DOUBLE)=CAST(0.3 AS DOUBLE)` 문법이나 출력은 이 조사에서 실행·실측하지 않았다. |
| `CHECK`는 결과 `FALSE`를 거부하고 `TRUE` 또는 `UNKNOWN`(NULL 포함)은 통과하므로 `NOT NULL`은 별도다. `BOOLEAN`/`BOOL`은 `TINYINT(1)` 별칭이며 0/1 전용 도메인이 아니므로 필요하면 `CHECK (x IN (0,1))`로 닫는다. MySQL이 CHECK를 실제 enforcement한 것은 8.0.16부터다. | [CHECK](https://dev.mysql.com/doc/refman/8.4/en/create-table-check-constraints.html) §15.1.20.6 문단 589–598; [BOOL/BOOLEAN](https://dev.mysql.com/doc/refman/8.4/en/numeric-type-syntax.html) §13.1.1; [8.0.16 릴리스 노트](https://dev.mysql.com/doc/relnotes/mysql/8.0/en/news-8-0-16.html) | 8.4에서는 기본 `ENFORCED`; 명시 `NOT ENFORCED`는 검사하지 않음. | 해당 구버전 바이너리 실행은 하지 않았다. |
| `UNIQUE` 인덱스는 NULL을 포함하는 여러 행을 허용할 수 있어 필수 유일값에는 `NOT NULL UNIQUE`를 함께 둔다. | [CREATE INDEX](https://dev.mysql.com/doc/refman/8.4/en/create-index.html) §15.1.15 “Unique Indexes”; [PRIMARY KEY/UNIQUE](https://dev.mysql.com/doc/refman/8.4/en/constraint-primary-key.html) §1.7.3.1 | MySQL 8.4 | 복합 UNIQUE의 NULL 조합은 모든 키부분과 collation 조건을 고려해야 한다. |
| FK의 정수 대응 열은 크기와 signedness가 일치해야 한다. 기본 참조 동작은 `NO ACTION`; InnoDB에서 이는 즉시 `RESTRICT`와 같다. 부모 참조 행이 있으면 삭제를 거부한다. | [FK](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html) §15.1.20.5 문단 643, 673–679 | InnoDB, 지원 엔진; FK 검사 활성 조건 | 잘못된 FK의 오류는 정의/상태에 따라 달라진다. 매뉴얼은 일부 경우 errno 150을 예로 들지만 단일 고정 오류번호로 일반화하지 않는다. `CREATE TABLE ... LIKE`는 컬럼 속성과 인덱스를 복제한다고 기술하며, FK 복제 여부는 별도 §15.1.20.3을 직접 확인하지 못해 단정하지 않는다. |
| InnoDB DYNAMIC/COMPRESSED의 인덱스 키 한도는 16KiB page에서 3,072바이트, page 8KiB에서 1,536바이트, 4KiB에서 768바이트다. utf8mb4 최대 바이트를 전제로 단일 문자열 키 768문자가 3,072바이트에 이른다. | [InnoDB limits](https://dev.mysql.com/doc/refman/8.4/en/innodb-limits.html) §17.21 문단 377–383; [저장 요구량](https://dev.mysql.com/doc/refman/8.4/en/storage-requirements.html) §13.7 | row format·인스턴스 `innodb_page_size`에 의존. | `VARCHAR(768)` 선언 한도와 실제 값 길이를 구분한다. 769문자 인덱스 가능성은 UNIQUE/nonunique, prefix 지정, 복합키 총 바이트를 포함해 별도 DDL 검증이 필요하며 실측하지 않았다. |
| `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE` 등 대부분의 DDL은 활성 트랜잭션을 암묵적으로 먼저 커밋한다. InnoDB atomic DDL은 사용자 `ROLLBACK`으로 DDL을 취소할 수 있다는 뜻이 아니다. | [implicit commit](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html) §15.3.3 문단 589–597 | 개별 DDL/임시 테이블 예외 존재 | 기존 DML이 DDL 전에 같은 세션에서 미커밋 상태였다면 그 DML도 선행 암묵 커밋 대상이다. |
| `DATE`, `DATETIME`, `TIMESTAMP`의 범위와 의미가 다르다. TIMESTAMP는 세션 시간대에서 UTC로 변환 저장하고 조회 때 세션 시간대로 변환한다. | [날짜·시간](https://dev.mysql.com/doc/refman/8.4/en/datetime.html) §13.2.2 문단 227–235 | 8.4; TIMESTAMP 범위 UTC 1970-01-01 00:00:01–2038-01-19 03:14:07 | timezone 설정·fractional precision에 따라 결과 해석이 달라진다. |
| 내부 임시 테이블의 TempTable은 VARCHAR를 길이·포인터가 있는 셀과 연속 메모리로 표현하며 패딩하지 않는다. MEMORY는 고정 길이 행에서 선언 최대 길이까지 패딩한다. | [internal temporary tables](https://dev.mysql.com/doc/refman/8.4/en/internal-temporary-tables.html) §10.4.4 문단 499–503 | 내부 임시 테이블 선택 엔진에 따라 다름 | 모든 임시 테이블이나 일반 디스크 행의 물리 사용량으로 일반화하지 않는다. |

## 대상 원문 대조

기존 R03의 핵심 설명은 대체로 위 공식 문서와 일치한다. 특히 utf8mb4 최대 payload와 접두사, DDL 위험, 시간대 차이를 강조한 방향은 유지 가능하다. 다만 원문의 `CREATE TABLE LIKE` 연습은 FK 포함 여부를 전제로 하지 말고 8.4 §15.1.20.3을 보완 확인해야 한다. 원본 스키마는 `ENGINE=InnoDB`, `DEFAULT CHARSET=utf8mb4`, `utf8mb4_0900_ai_ci`, CHECK, FK, UNIQUE, DECIMAL 및 DATETIME을 실제 선언한다. Seed는 `SET NAMES utf8mb4`를 사용한다. 이 파일들은 읽기만 했으며 실행·적재하지 않았다.

`CHAR_LENGTH()`는 문자 단위, `OCTET_LENGTH()`는 바이트 단위 표현을 확인하는 SQL 함수다. 함수 참조는 [string functions](https://dev.mysql.com/doc/refman/8.4/en/string-functions.html)를 참조한다.

## 실행 경로 판단

공식 목록상 portable tarball은 존재한다. 사용자 영역에 푼 바이너리를 사용해 독립 datadir과 private socket을 지정하고, 초기화 및 서버 시작 때 `--no-defaults`, `--skip-networking`, X Plugin 비활성화를 명시하는 계획은 공식 옵션 문서와 부합한다. 따라서 원리상 격리 경로는 성립한다. 다만 직접 다운로드 URL·실물 검증은 미확인이고, 초기화/기동을 실행하지 않았으므로 현재 환경에서 작동한다고 확정하지 않는다. 상세 경로·옵션은 [RUNTIME-OPTIONS.md](RUNTIME-OPTIONS.md)를 참조한다.
