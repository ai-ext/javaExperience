# S08 트랜잭션 시각화 공식 근거 조사

확인일: 2026-10-20 (KST). 조사 경로는 Codex CLI `gpt-6-luna` / `openai`이며 LiteLLM 미사용이다. 공식 문서 본문은 웹 도구로 직접 열어 확인했다. 참고 기준선은 Spring Framework 7.0.9, Spring Boot 4.1.1 managed dependencies다. Spring Reference의 버전 경로 및 `current` Javadoc은 조회 시점에 최신판을 가리킬 수 있어 표에서 API/버전을 따로 표시한다.

|---|---|---|---|
| BOM으로 Framework 7.0.9 및 Boot 4.1.1 의존성을 선택한 별도 standalone `AnnotationConfigApplicationContext` 실험은 JDBC 선언적 트랜잭션 범위를 재현할 수 있다. `@EnableTransactionManagement`는 기본 proxy 모드다. 대상 클래스에 인터페이스가 없고 `proxyTargetClass=true`이면 CGLIB 하위 클래스 프록시를 사용한다. 같은 패키지의 비공개 클래스는 CGLIB 프록시될 수 있고 package-private `importOne`도 클래스 기반 프록시에서 가로챌 수 있다. `public transfer`도 외부 빈이 주입된 프록시를 통해 호출해야 한다. | [Spring AOP proxying](https://docs.spring.io/spring-framework/reference/core/aop/proxying.html) “Proxying Mechanisms”; [Using `@Transactional`](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html) “Method visibility”; [Boot managed coordinates](https://docs.spring.io/spring-boot/appendix/dependency-versions/coordinates.html) | Framework 7.0.9 문서/API, Boot 4.1.1 좌표; 2026-10-20 | 패키지 비공개 클래스라도 final이면 프록시 불가. `private` 메서드는 override할 수 없어 advice 불가. self-invocation은 프록시를 우회하고 직접 `new` 객체도 컨테이너 프록시가 아니며, 외부에서 주입된 별도 빈을 호출해야 interception된다. 설정·실험은 수행하지 않음. `DataSourceTransactionManager` + `JdbcTemplate` + H2를 조합하면 해당 실험에서 JDBC 자원을 관찰하되, 이는 H2 결과만 뜻한다. |
| 기본 규칙은 `RuntimeException` 및 `Error` rollback, checked exception commit이다. `rollbackFor`/`noRollbackFor`는 예외 타입 및 상위 타입 매칭을 사용하고, 충돌하면 가장 구체적인(strongest) 매치가 이긴다. checked 예외를 트랜잭션 메서드 안에서 catch하고 정상 반환하면 예외 기반 rollback 규칙은 작동하지 않는다. rollback-only를 설정했을 때만 최종 rollback된다. | [Rolling back](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html) “default configuration”, “Rollback rules”; [`TransactionExecution.setRollbackOnly`](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/TransactionExecution.html) | Framework 7.0.9 reference/API 확인; 2026-10-20. `ALL_EXCEPTIONS`는 6.2부터 제공 | 타입 기반 규칙은 class-name 부분 문자열 규칙보다 안전하다. checked 예외를 실제로 던져 커밋/롤백 실측하지 않음. `@EnableTransactionManagement(rollbackOn=ALL_EXCEPTIONS)`는 6.2+ 별도 정책이며 현재 실험에 적용하거나 실행하지 않았다. 반환 시점 이미 exceptionally completed인 `Future`/`CompletableFuture`만 특수 처리된다(6.1+); 나중의 완료 실패까지 기다리는 의미가 아니다. Reactive 경계는 Reactor Context 기반으로 별도이며 실험하지 않았다. |
| `REQUIRED` 안쪽에서 RuntimeException이 나고 바깥이 이를 catch해도 참여 범위에서 rollback-only가 설정되면 바깥 commit 시 `UnexpectedRollbackException`으로 실제 롤백을 알린다. `REQUIRES_NEW`는 outer 자원을 보류하고 새 독립 물리 트랜잭션/추가 연결을 확보한다. `NESTED`는 일반적으로 JDBC savepoint를 이용해 한 물리 트랜잭션 일부만 되돌린다. | [Transaction propagation](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html) `REQUIRED`, `REQUIRES_NEW`, `NESTED`; [Abstract manager API](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/support/AbstractPlatformTransactionManager.html) nested/validation | Framework 7.0.9 reference/API 확인; 2026-10-20 | `REQUIRES_NEW`는 pool 고갈/대기 가능성이 있고 독립 커밋은 outer rollback에 되돌려지지 않는다. `NESTED`는 savepoint 지원이 있는 JDBC 리소스 중심이며 manager/driver마다 제약이 있어 모든 manager 일반화 금지. `SUPPORTS`는 기존 물리 transaction에 참가하거나 없을 때 비트랜잭션 실행하되 synchronization 범위가 생길 수도 있다. `MANDATORY`는 없으면 예외, `NOT_SUPPORTED`는 기존 것을 보류하고 비트랜잭션 실행, `NEVER`는 활성 transaction이 있으면 예외다. active transaction과 synchronization은 구분해야 한다. 해당 조합은 미실행. |
| `DataSourceTransactionManager`의 readOnly는 기본적으로 `Connection.setReadOnly(true)` JDBC 힌트다. `enforceReadOnly` 기본은 false이며 true로 선택하면 트랜잭션 직후 `SET TRANSACTION READ ONLY`를 실행한다. 이미 존재하는 트랜잭션 참여 시 바깥 특성이 우선하므로 내부 선언 isolation/timeout/readOnly는 새 물리 경계를 만들지 않는다. `validateExistingTransaction`은 호환되지 않는 isolation/readOnly를 거부하도록 선택할 수 있다. timeout 3초는 새 물리 트랜잭션의 timeout 요청이며, 모든 쿼리/DB에 보편적 강제 중단을 보장하지 않는다. | [`DataSourceTransactionManager`](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/jdbc/datasource/DataSourceTransactionManager.html) `setEnforceReadOnly`, `prepareTransactionalConnection`; [`AbstractPlatformTransactionManager`](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/support/AbstractPlatformTransactionManager.html) `setValidateExistingTransaction`; [Propagation](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html) | Framework 7.0.9 API/reference; 2026-10-20 | `SET TRANSACTION READ ONLY` 인식 예로 Oracle/MySQL/Postgres가 제시되지만 모든 DB에 동일 적용된다는 뜻은 아니다. `readOnly=true`를 모든 DB의 쓰기 금지로 설명하지 않는다. timeout 효과는 manager/resource/JDBC 실행 경로에 의존한다. 실행하지 않음. |
| `TransactionTemplate` callback이 `setRollbackOnly()` 후 정상 반환하면 `execute` 결과는 정상 반환일 수 있지만 자원은 rollback된다. 따라서 정상 반환 또는 boolean `false` 자체는 commit 증거가 아니다. 원문 `ImportService`의 별도 repository가 이미 수행한 중간 INSERT도 같은 DataSource/transaction-bound connection을 쓰고 그 트랜잭션이 rollback-only로 최종화되면 rollback 대상이다. | [`TransactionTemplate`](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/support/TransactionTemplate.html) `execute`; [`TransactionExecution`](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/TransactionExecution.html) `setRollbackOnly`; [Spring programmatic transactions](https://docs.spring.io/spring-framework/reference/data-access/transaction/programmatic.html) | Framework 7.0.9 API/reference; 2026-10-20 | `false`는 업무 반환값일 뿐이다. 중간 INSERT 롤백 관찰에는 같은 Spring 관리 `DataSource`, 동일 transaction manager/thread, `JdbcTemplate` 또는 `DataSourceUtils` 경로가 필요하며 새 연결/비관리 접근이면 결론이 달라질 수 있다. H2에 원문을 실행하지 않음. |
| `@TransactionalEventListener` 의미는 기존 공식 Spring 자료에서 기본 `AFTER_COMMIT`, `AFTER_ROLLBACK`, 무트랜잭션 기본 skip 및 `fallbackExecution=true` 예외를 설명한다. 커밋 이후 리스너 예외는 완료된 DB commit을 되돌릴 수 없고, 프로세스 내 listener는 durable broker 전달을 뜻하지 않는다. Outbox는 업무 row와 이벤트 row를 한 DB 트랜잭션에 기록한 뒤 relay/CDC가 발행하는 별도 패턴이다. | [Transaction-bound events](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html) 최신 URL 열기 실패; 검색 확인된 [Spring 5.1 Reference PDF](https://docs.spring.io/spring-framework/docs/5.1.x/spring-framework-reference/pdf/data-access.pdf) “Transaction-bound Events”; [Transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) | Spring 5.1 공식 PDF에서 이벤트 단계 확인, 최신 Reference 세부 본문은 미확인; AWS 가이드; 2026-10-20 | Spring 5.1 근거는 과거 버전이다. 최신 API/예외 경계의 세부 문구는 이번 조회로 확정하지 못했으므로 본문 설명을 버전불변 API 근거로 단정하지 않는다. 원문의 outbox DDL은 별도 H2에서만 시험하는 범위로 한정한다. 실제 broker, CDC, 프로세스 kill, 재시도/중복 전달은 실행하지 않음. |
| 격리 현상 표는 SQL 표준이 정의한 최소 보장과 DB 구현을 나눠야 한다. PostgreSQL 18은 `READ UNCOMMITTED`를 `READ COMMITTED`처럼 구현하고 `REPEATABLE READ`에서 phantom을 허용하지 않는 더 강한 동작이 있다. MySQL 공식 문서는 InnoDB 격리 수준을 별도로 규정한다. | [PostgreSQL 18 §13.2](https://www.postgresql.org/docs/18/transaction-iso.html); [MySQL 8.4 §17.7.2.1](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html); [H2 Advanced](https://h2database.com/html/advanced.html) | PostgreSQL 18, MySQL 8.4, H2 공식 사이트; 2026-10-20 | 표준을 특정 DB 동작으로 일반화하지 않는다. 별도 standalone H2 실험을 MySQL 실측이라 부르지 않는다. 격리 동시성 실험은 실행하지 않음. |

실험 범위는 조사 설계 기준이다. 이번 작업에서는 Spring 애플리케이션, SQL, H2, 브로커/CDC를 실행하지 않았다. `REPORT.md`의 URL은 공식 1차 출처이며 실제 열람 여부와 미확인 URL은 `_data/source-notes.md`에 기록했다.
