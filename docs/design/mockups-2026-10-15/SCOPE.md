# javaExperience 시안 범위와 1차 제작 계획

기준: 2026-10-15, PR #7의 `0914f6d681663666460760433b53a51b7307b5eb`. 현재 원문·생성 HTML 목록을 집계한 계획이며, 전체 콘텐츠의 의미별 장면 배정을 끝냈다는 뜻은 아니다.

## 목표와 시안 단위

3~6년차 전공 개발자에게 기대하는 설명·예측·진단·설계 선택·구현·검증 역량까지 다루되, 처음 읽는 사람이 짧은 이야기와 시각적 변화로 이해하게 한다. 핵심 개념뿐 아니라 기존 토글 안의 산문, 표, 예외 설명까지 새 읽기 구조로 옮긴다.

- **화면 구성 시안:** 한 페이지에서 무엇을 어떤 순서로 읽고 조작하는지 정하는 보드. 긴 문서는 전체 읽기 순서를 설계하되 모든 내용을 한 이미지에 작은 글자로 넣지 않는다.
- **개념·장면 시안:** 한 가지 이해 목표를 가르치는 보드. 필요하면 주요 상태 2~4컷을 함께 담는다. MVC의 뜻과 Controller·Service·Repository의 책임은 별도 이해 목표다.
- **표현 방식:** 여러 개념에서 재사용할 수 있는 문법. 같은 문법을 사용해도 개념별 데이터·비교 조건·실패 분기·문구는 따로 설계한다.
- 이미지에 문장을 모두 구워 넣는 것이 최종 구현은 아니다. 시안이 확정되면 읽을 수 있는 HTML 텍스트와 조작 가능한 시각화로 구현한다.

현재 검사 목록의 42,644개는 원문과 생성 UI의 중복을 포함한 검사 단위다. 시안 수나 서로 다른 개념 수로 계산하지 않는다.

## 표현 방식 10종

1. **역할 분해:** 하나의 실제 장면을 확대해 각 요소의 책임을 연결한다. MVC, 프로세스 구성.
2. **데이터 변환:** 같은 값이 JSON·DTO·Entity·행으로 바뀌는 모양을 나란히 잇는다.
3. **연속 장면:** 행동 → 요청 → 처리 → 결과를 짧은 설명과 함께 따라간다.
4. **상태 비교:** 같은 시점의 여러 위치와 같은 위치의 전후 값을 비교한다. JPA, 캐시.
5. **분기와 조건:** 정상·실패·권한에 따라 갈라지는 실행 경로를 보여 준다.
6. **시간선과 경합:** 둘 이상의 작업이 겹치는 순서와 대기를 보여 준다. 동시성, 이벤트.
7. **대기열과 자원:** 들어온 요청, 점유된 자리, 반납, 밀리는 줄을 보여 준다. 스레드·커넥션 풀.
8. **관계와 탐색:** 객체 관계·테이블 연결·트리·탐색 범위를 실제 값으로 보여 준다.
9. **구조·비용 비교:** 같은 작업을 서로 다른 구조로 처리할 때 차이를 비교한다. 메모리·SSD, 동기·비동기. 시간 수치는 실측 또는 명확한 예시 조건을 붙인다.
10. **증거로 진단:** 증상·로그·지표를 놓고 가설을 고르고 확인한다. 장애 대응, 쿼리 튜닝.

HDD·SSD처럼 물리 구조가 중요한 개념은 동작 구조와 접근 과정을 비교하는 표현을 쓴다. 이벤트 아키텍처는 생산·전달·처리의 시간과 실패 경계를 표현한다. 모든 개념을 동일한 상자·화살표로 만들지 않는다. 이번 HDD 비교 자체의 새 기술 콘텐츠는 작성하지 않았으며, 다음 비교 시안은 기존 W23의 메모리·SSD 내용을 먼저 근거로 삼는다.

## 산문을 실제로 이관하는 방법

각 원문 블록에 다음 표를 채운 뒤 시안을 만든다.

| 필드 | 기록할 내용 |
|---|---|
| 원문 ID | 기존 visual-inventory.jsonl의 식별자 |
| 전달할 사실 | 문장이 설명하던 정의·조건·원인·예외 |
| 학습자의 질문 | 이 문장을 읽기 전에 생기는 질문 하나 |
| 시각적 증거 | 볼 대상, 값, 시간, 차이, 관계 |
| 새 문구 | 장면 옆에 필요한 짧은 설명 |
| 심화 연결 | 다음 조건·반례·선택 비용 |
| 확인 과제 | 결과 예측, 직접 조작, 구현·테스트 |
| 보존 근거 | 원문 코드·SQL·공식 근거·실측 여부 |
| 시안과 상태 | 이미지 경로, 검토 결과, 구현·검증 범위 |

아무 장면에도 배정되지 않은 산문이 있으면 이관 미완료다. 공통 템플릿에 넣었다는 이유로 완료 처리하지 않는다. 정의는 정의대로 독립 장면이 필요하고, 배경·선택 이유·예외도 개념과 맞는 표현을 따로 고른다.

예: P02의 “Controller는 경로·HTTP 메서드를 매핑하고 요청 DTO를 받아 Service를 호출한다”는 문장을 통째로 접는 대신, 요청의 경로 강조 → 담당 메서드 선택 → 입력 객체 확인 → 업무 호출 장면으로 나눈다. MVC의 Model·View·Controller와 이 계층 흐름이 같은 분류라는 오해가 없게 01번 장면으로 연결한다.

본문은 1~3문장 설명과 시각 자료가 교대로 이어지게 한다. 모든 산문을 없애려 하지 않는다. 개념·인과관계·중요 조건은 기본 노출한다. 길이가 긴 전체 코드, 원시 로그, 출처 원문, 정답은 필요할 때 펼치되 핵심 설명을 다시 접기 속에 숨기지 않는다.

## 깊이를 지키는 검토 기준

- 초급: 무엇이 무엇인지 설명할 수 있다.
- 중간: 조건을 바꾸면 어떤 값과 경로가 달라지는지 예측한다.
- 실무: 반례와 실패 원인을 증거로 좁히고 대안의 비용을 비교한다.
- 구현: 새 상황의 코드를 작성하고 테스트·로그·데이터로 검증한다.

보기 좋은 그림과 학습 성취를 구분한다. 시안을 보았다는 사실만으로 이해도 검증을 완료했다고 하지 않는다. 첫 설명 장면, 조작 장면, 실패 장면, 근거 확인까지 연결한다. 애니메이션은 재생·정지·한 단계 이동이 가능하게 설계하고 색만으로 의미를 구별하지 않는다. 모바일에서는 한 장면씩 세로로 읽으며 동일한 깊이의 내용에 접근할 수 있게 한다.

## 이번 이미지의 출처와 경계

이미지는 built-in image_gen으로 생성한다. 전체 프롬프트는 `mockup-prompts.json`에 저장했다. 현재 장면의 기술 근거는 다음과 같다.

- P02, 시나리오 1-1 원문: MVC 역할, JSON 변환, DB 미저장 단계.
- [Spring DispatcherServlet](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-servlet.html): 요청 처리의 위임 구조.
- [Spring @ResponseBody](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-methods/responsebody.html): HttpMessageConverter를 통한 본문 직렬화.
- S09 원문과 [Jakarta Persistence EntityManager](https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/EntityManager.html): 관리 객체 변경과 flush.
- 시나리오 4-2 원문: 갱신 손실, 원자 UPDATE, 중복·트랜잭션·교착 재시도 구분.

예시의 제목과 초기 좋아요 5는 설명용이다. 4-2 실제 채점용 글 16의 초기값은 0이므로 실제 실습 데이터로 오해하지 않게 구현 시 분리한다. JPA 시안은 기존 행의 UPDATE, 일반적인 격리 수준, 별도 연결의 새 autocommit SELECT를 가정하며 열린 기존 트랜잭션의 스냅샷과 구별한다. 요청 시안의 JSON은 전체 계약이 아닌 일부 필드다. 이미지의 장식용 숫자·이름·날짜는 API 계약이나 실제 관측값이 아니다.

이번 범위는 시안 수 산정과 대표 이미지 제작이다. 시안의 버튼은 동작하지 않으며 HTML 이관·모바일 구현·실서버 계측·학습자 이해도 검증은 후속 단계다.

## P02 한 문서를 끝까지 옮길 때의 예시 분해

MVC 문서 하나도 상단 그림 한 장으로 끝내지 않는다. 화면 전체의 읽기 순서 보드 1장과 다음 설명 보드 5장을 우선 가정한다.

| 보드 | 다룰 원문 | 새 구성 |
|---|---|---|
| A. MVC의 의미와 응답 | 1절, 2.1~2.3, Q1·Q2 | 하나의 게시글에서 역할을 분해 → HTML·JSON 비교 → MVC와 계층 관점 구분. 이번 01번 시안의 범위 |
| B. 책임과 의존 | 2.4~2.6, 2.9~2.10, 6절, Q3·Q5~Q7 | 규칙이 바뀔 때 고칠 위치 → 저장소 교체 → 패키지 배치 → 작을 때 과도한 계층을 만들지 않는 판단 |
| C. 데이터 계약 | 2.7~2.8, Q4 | 요청에서 허용할 필드 선택 → 내부 객체 → 응답 공개 필드 → record의 장점과 한계 |
| D. 실제 앱 만들기 | 3.1~3.6, 4절 관련 행 | 환경 준비 → 같은 데이터로 코드 파일·요청·응답 연결 → HTML 렌더링 비교. 전체 코드는 별도 탐색기로 보존 |
| E. 오류를 찾아 설명하기 | 5절, 나머지 치트시트 | 잘못된 요청·빈·템플릿·포트 사례 → 실행이 멈춘 위치 → 확인할 증거 → 예측 과제 |
| 근거·심화 연결 | 8절과 각 절의 참조 | 각 장면에서 근거로 이동, 하단에 출처 목록 유지 |

이 표는 섹션 수준의 이관 설계이며 아직 모든 원문 블록 ID를 의미별로 배정한 결과는 아니다. 산문을 재작성할 때 원문 자체의 기술적 단순화도 확인해야 한다. 예를 들어 요청 URL과 HTTP 메서드 불일치를 항상 같은 상태 코드로 설명하지 않고, 실제 매핑과 변환 단계에 맞춰 구분한다.
