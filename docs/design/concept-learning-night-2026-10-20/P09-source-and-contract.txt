# gpt-image-prompt — 제품에 얹을 이미지 에셋 프롬프트

## 학습 화면·실습 시안 — 두 표현 방식, 하나의 스킬

아래 §0~8의 고해상도·재질·조명·세트 일관성 기준은 그대로 유지한다. 정보가 적게 보이는 화면도 싼 아이콘·평면 카드로 만들지 않는다. 표현 방식은 과제에 맞춰 고른다.

- **전체 참조 장면:** 이미 배운 흐름을 되짚거나 두 기술을 비교할 때 쓴다. 요청→Java/SQL→DB→응답의 관계와 실제 값을 풍부하고 정확하게 보여 준다. 이미지를 원문·실행 결과로 검수한다.
- **지금 할 일 화면:** 직접 구현을 시작하거나 결과를 확인할 때 쓴다. **한 화면에 한 작업·한 파일 또는 한 요청·하나의 확인 결과**만 기본 노출한다. 다음 작업은 별도 화면으로 이어 준다. 설명·정답·예외를 첫 화면에 쌓지 않고 이름이 분명한 심화 영역에서 찾게 한다. 원본의 재질·미세 디테일은 유지하되, 현재 보이는 정보량은 크게 줄인다.

시작 화면에서 학습자가 2초 안에 `무슨 파일/SQL을 바꾸지?`, `어떤 요청을 보내지?`, `무슨 값을 확인하지?`에 답할 수 있어야 한다. 모든 과제가 세 화면일 필요는 없다. DTO 작성, Controller 작성, HTTP 실행, DB 행 관찰처럼 **실제로 하는 일**을 기준으로 화면을 나눈다. 하나의 긴 페이지나 고정 탭·지하철식 지도에 정보를 몰아넣지 않는다. 실무 깊이는 전체 시나리오에 유지하고, 현재 행동은 쉽게 말한다.

시나리오 **첫 장면**은 더 좁힌다. 사용자 상황을 자연스러운 한 문장으로 말하고, **만들 것·보낼 것**만 기본 노출한다. 에이전트 프롬프트가 정말 필요할 때만 그 목적과 함께 덧붙인다. 기대 응답·DB 증거·오류·채점·개념 설명은 해당 구현/실행/관찰 장면에 둔다. 첫 장면의 장식적 밀도를 높여도 정보량을 늘리지 않는다. 단계가 길면 장표와 이미지 수를 늘린다.

MVC, JPA, MyBatis, 영속성 컨텍스트, 트랜잭션처럼 처음 접하는 개념은 **이미지 시안을 먼저 만들고**, 실행 상태가 변하는 하나의 시각 컴포넌트로 구현한다. [서버 모니터링 분석 가이드](https://kciter.so/posts/server-monitoring-analysis-guide/)의 ‘현상을 보여 주고 의미를 읽게 하는’ 방식을 참고한다. 정지된 화살표 지도 대신 한 시점의 객체·SQL·행 값을 강조하고, 다음 시점은 조작으로 넘긴다. `flush`와 `commit`, JPA와 Hibernate, MyBatis의 `#{}`와 `${}` 같은 경계는 상태 전후와 대조해 드러낸다. 원문의 깊은 설명은 잃지 않되 첫 장면에 모두 싣지 않는다. 개념 문서는 제목·소제목으로 검색할 수 있게 연결한다.

전수조사는 DOM 블록 수를 이미지 수로 오해하지 않는다. 원문을 **독립적으로 이해·조작해야 하는 의미 장면**으로 분할하고, 장면마다 시안·정확성 검토·구현·모바일/데스크톱 캡처·동작 확인을 기록한다. 하나의 일괄 템플릿을 100개 페이지에 적용한 것만으로 시안 일치를 선언하지 않는다.

원문·코드·요청/응답 계약을 먼저 읽는다. 이미지 안의 API·SQL·테이블·상태·코드를 반드시 대조하며 예상 흐름을 실측처럼 표시하지 않는다. 전체 학습 UI 시안에는 핵심 라벨과 값이 읽혀야 하므로 아래 독립 에셋용 `No caption`과 무자막 원칙을 적용하지 않는다. 작은 코드가 깨졌으면 교정하고, 실제 구현에서는 정확한 원문 텍스트를 DOM으로 넣는다. 각 distinct 화면은 실제 `imagegen`을 호출해 만든다.

기술 경계는 [학습 계약](references/learning-contract.md), 화면·크기·동작 검수는 [검수 기준](references/verification.md)을 따른다. 프로젝트의 AGENTS.md, 상태 목록, 시안 대조 체계가 있으면 그 위치에 증거를 기록한다. 아직 UI만 만들었다면 학습자의 서버·DB 결과나 이해도를 검증했다고 표시하지 않는다.

## 왜 이게 따로 있나

이미지 모델은 잘 그린다. 실패는 대부분 **프롬프트가 잘못된 등급을 지시해서** 난다.
특히 "작게 표시되니까 단순하게"라는 직관이 결과를 통째로 망가뜨린다.

이 스킬은 studymate `/invest` 카드 에셋 작업(2026-09)에서 **7번 실패하고 9번째에 성공한**
실물 기록에서 뽑았다. 실패한 7번과 성공한 9장의 차이가 아래에 다 들어 있다.

---

## 0. 가장 중요한 것 — 작다고 단순화하지 마라

> **"작은 썸네일에 들어간다고 원본의 세부를 없애지 않는다."**

16px·32px에 들어갈 이미지라도 **원본은 사진급 디테일로 만든다.** 이유:

- 단순화한 에셋은 축소해도 **싸구려 아이콘**으로 남는다
- 디테일이 살아 있는 이미지는 축소되면 **질감 있는 덩어리**가 된다
- 32px에서 "사진"으로 읽히는 게 "픽토그램"으로 읽히는 것보다 낫다

❌ 실패한 지시: `요소 2~3개로 극단적으로 단순하게`, `굵은 선과 큰 면으로`, `주요 요소 7개 이내`
✅ 성공한 지시: `exquisitely detailed`, `minute carefully rendered surface detail`, `photorealistic CGI`

표시 크기는 **요소를 깎는 근거가 아니라, 주제가 그 크기에서 읽히는지 판정하는 기준**이다.

## 1. 프롬프트 골격 (7블록)

영어로 쓴다. 블록 순서를 지킨다.

```
① 등급 선언   Create ONE exquisitely detailed <square|landscape 3:2> editorial image
              for a premium <도메인> service.
② 부정 정의   This is a fully developed <product-visualization|architectural> scene,
              NOT an icon, pictogram, emoji, simplified symbol or flat vector illustration.
③ 재질·조명   High-end photorealistic CGI, physically believable materials, minute carefully
              rendered surface detail, sophisticated soft lighting, <배경 팔레트>,
              restrained warm accents.
④ 구도 원칙   Art-directed composition with a clear subject, substantial depth and
              atmospheric realism.
⑤ 금지       No caption, branding or watermark. <+ 이 주제의 흔한 오답들>
⑥ 출력       Output one <square|landscape> opaque PNG.
⑦ Scene:     <장면을 한 문단으로 통짜 서술. 불릿 금지.>
```

①~⑥은 세트 전체에서 **같은 문자열로 재사용**한다. 장별로 바뀌는 건 ⑦ `Scene:` 뿐이다.

---

## 2. 기법 5개

### ① 부정 정의로 등급을 잠근다

원하는 것만 적으면 부족하다. **빠질 함정을 이름으로 막아야** 한다.

```
NOT an icon, pictogram, emoji, simplified symbol or flat vector illustration
```

"소프트 3D 렌더" 같은 긍정 지시만 주면 모델이 일러스트 쪽으로 해석할 여지가 남는다.

### ② 금지는 속성이 아니라 오답 오브젝트 이름으로

```
❌ 글로우 금지                    → 모델이 "림라이트"로 우회한다
✅ No map pins, chart symbols or platform pedestal
✅ not chunky 3D bars or a stylized upward arrow
✅ No oversized checkmark badge, giant fold, logo
✅ No giant cubes, servers, chain-link hardware, stacks, orbit hoops, lasers or broad fog
```

그 주제에서 AI가 흔히 뱉는 클리셰를 **물건 이름으로** 나열한다.

### ③ 물성어를 구체적으로 명명

```
❌ 유광 플라스틱 또는 클레이 재질
✅ brushed-metal, pale limestone cladding joints, glass balustrades, reeded edges,
   milled grooves, paper fibers, window mullions, satin platinum facets
```

이름이 구체적일수록 렌더가 구체적으로 나온다.

### ④ 조명은 세팅 지시가 아니라 장면 언어로

```
❌ 위쪽 부드러운 광원 1개 + 약한 반사광     → 조립을 부른다
✅ blue hour, warm ivory interior lighting, controlled warm desk lighting,
   soft directional light against cool surroundings
```

### ⑤ 요소를 나열하지 말고 장면을 서술한다

```
❌ - 중앙: 코인 1개
   - 그 뒤: 블록 4개
   - 블록 위: 지그재그 1줄        → 부품 목록이라 부품처럼 나온다

✅ Scene: an intimate, angled close-up of an exceptionally crisp professional
   stock-analysis display in a dim sophisticated workspace. Most of the composition is
   the dark navy glass screen, showing many finely drawn candlesticks... A sliver of
   finely machined dark monitor bezel and a softly blurred metal keyboard in the
   foreground establish real material and depth.
```

## 2-B. 퀄리티를 올리는 레버 — 주제에 따라 경로가 다르다

"정교하게"는 한 가지가 아니다. **물성이 있는 주제**와 **없는 주제**의 경로가 다르다.

### 물성이 있는 주제 (제품·건축·인물·자연)

금속 결·유리 반사·석재 이음매·종이 섬유가 실재한다. 그걸 이름으로 불러주면 된다.

```
물성   brushed metal, reeded edges, limestone cladding joints, paper fibers, satin facets
빛     directional key + soft fill, contact shadows, physically plausible reflectance
깊이   shallow depth of field, atmospheric recession, layered foreground/background
```

### 물성이 없는 주제 (차트·다이어그램·UI·추상)

같은 방식이 안 통한다. 금속도 그림자도 없다. 대신 다섯 축으로 올린다.

| 레버 | 지시 방법 |
|---|---|
| **정보 층위** | 층을 늘린다. 차트면 가격 + 거래량 + 볼륨 프로파일 + 보조지표 1개. 층이 없으면 빈약해 보인다 |
| **정렬 정밀도** | `Every pane shares one vertical grid; elements line up exactly on each position` |
| **선 굵기 위계** | `Line weight and brightness step down in strict order: A, then B, then C, then grid` |
| **표면 물성** | 완전 플랫 대신 `fine matte glass plate, imperceptible directional sheen, very soft inner shadow, extremely fine micro-grain`. 기기 없이도 "물체"가 된다 |
| **색 절제** | 2~3색으로 제한하고 나머지 위계는 명도로. 색이 늘면 정보가 아니라 소음이다 |

기준 문장으로 등급을 못 박으면 효과가 크다:
`The craftsmanship standard is a high-DPI institutional trading terminal captured at full
resolution: absolute alignment, disciplined line hierarchy and dense but calm information.`

### ⚠ 글자는 모델의 약점이다

작은 글자·숫자를 정확히 못 쓴다. 라벨을 많이 요구하면 **깨진 글자가 박힌다.**
읽혀야 하는 텍스트는 이미지에 넣지 말고 UI로 얹는다. 이미지 안에 필요하면 이렇게:

```
rendered at a size where they read as precise typographic texture rather than legible values
```

## 3. 작업 전 — 표시 치수를 실측한다

**계산하지 말고 DOM에서 재라.** 컨테이너·사이드바·패딩을 빠뜨리면 40%씩 틀린다.

```js
// 브라우저 콘솔 또는 Playwright
[...document.querySelectorAll("img")].map(i => {
  const r = i.getBoundingClientRect();
  return [i.currentSrc.split("/").pop(), Math.round(r.width) + "x" + Math.round(r.height)];
});
```

같이 확인할 것:
- **불투명도가 곱해지는가** (`opacity-*` 클래스). 60%가 걸려 있으면 에셋 밝기 요구가 달라진다
- **`object-fit`이 contain인가 cover인가**. 불투명 사진은 cover, 투명 일러스트는 contain
- 배경색 hex (에셋이 그 위에 떠야 한다)

## 4. 세트로 만들 때 — 기준 장 먼저

여러 장이 한 화면에 나란히 놓이면 **재질·조명·채도가 어긋나는 순간 세트가 깨진다.**
색만 다른 게 아니라 다른 스타일의 에셋처럼 보인다.

```
1. 가장 중요한 한 장을 먼저 만들어 확정한다 (= 기준 장)
2. 나머지는 기준 장을 참고 이미지로 반드시 첨부하고 이렇게 덧붙인다:
   "첨부 이미지와 같은 재질·조명 방향·그림자 세기·채도로, 색조만 다르게."
3. 전부 나란히 놓고 봤을 때 한 장이라도 재질이 달라 보이면 그 장을 다시 만든다
```

"먼저 만든 장이 **있으면** 첨부하고" 같은 조건절로 쓰면 안 지켜진다. **필수로** 쓴다.

---

## 5. 변형을 볼 때 — 한 번에 한 축만

버전을 밀어붙이지 말고 축을 분리한다. 여러 축을 같이 바꾸면 결과가 나빠도
**어느 축 때문인지 분리가 안 돼** 수렴하지 않는다.

```
세 안을 만들되 한 축만 바꾼다. 예: 정면 / 약한 사선 / 근접 — 재질·조명은 고정.
각 안은 독립 실행 가능한 완성 프롬프트로 쓴다 (공통 조건 전부 포함).
마지막에 차이를 표로 비교하고, 선택된 안만 생성한다.
한 장에 여러 안을 합치지 않는다.
```

## 6. 받은 뒤 — 눈으로 보지 말고 잰다

전체 크기로 보면 다 괜찮아 보인다. **실패는 축소 후에만 드러난다.**
실제 사례: 알파 bbox가 캔버스의 39%뿐이라 화면에서 묻혔는데 **테스트는 통과했다.**

### 6-1. 기계 검사

```bash
file 받은파일.png    # RGBA인가 RGB인가 — 투명 에셋인데 RGB면 배경이 칠해진 것
```

```python
# 알파 bbox · 평균휘도 · 평균채도 — PNG 순수 파이썬 디코드 (의존성 없음)
# 판정 기준
#   알파 bbox      캔버스의 85% 이상 (투명 에셋인 경우)
#   배경 대비      (평균휘도 × 불투명도 + 배경휘도 × (1-불투명도)) / 배경휘도 ≥ 2.5배
#   세트 내 채도   최대-최소 차 0.15 이내
#   세트 내 휘도   최대/최소 2배 이내
```

### 6-2. 실제 크기 합성 — 이 단계를 건너뛰지 마라

에셋을 **실측 표시 크기로 축소**하고 **실제 배경색 위에 실제 불투명도로** 얹어서 본다.
여러 장이면 나란히 놓는다. 세트 불일치는 나란히 놓는 순간에만 보인다.

## 7. 안티패턴 (전부 실제로 저지른 것)

| 하지 말 것 | 왜 |
|---|---|
| "작게 보이니 요소를 줄여라" | 싸구려 아이콘이 된다. §0 |
| 요소 수 상한을 1원칙으로 | 밀도가 아니라 톤·등급이 문제인 경우가 훨씬 많다 |
| 프레임워크 버전·폰트를 프롬프트에 | 이미지 모델이 Next 버전 보고 그림을 바꾸지 않는다 |
| 표시 크기를 레이아웃으로 계산 | 사이드바·셸 패딩을 빠뜨려 40% 틀렸다. DOM에서 재라 |
| 속성 단위 금지("글로우 금지") | 다른 이름으로 우회한다. 오브젝트 이름으로 막아라 |
| 한 버전에서 여러 축 동시 변경 | 원인 분리가 안 돼 수렴하지 않는다 |
| 전체 크기로 보고 통과 | 축소·불투명도 적용 후에만 드러나는 실패가 있다 |
| 없는 제약을 스스로 만들기 | "청록 계열만"을 규약인 양 넣었는데 내가 지어낸 것이었다 |

## 8. 배치할 때

- 서비스용은 **표시 크기의 2~3배**로 축소해 넣는다. 원본은 따로 보관한다
  (표시 240px → 768px 소스면 충분)

===== 학습 계약 =====
# 깊이를 보존하는 학습 계약

## 학습 시나리오

사용자가 익힐 역량을 연차가 아니라 관찰 가능한 행동으로 적는다. 예: 명세로 구현, 선택 이유 설명, 조건 변경에 응용, 실패 재현·진단, 테스트로 회귀 방지. 실습 수료만으로 특정 연차의 실력을 보장하지 않는다.

장면을 만들기 전에 다음을 기록한다.

| 항목 | 기록할 것 |
|---|---|
| 출처 | 원문/코드/계약의 파일·절·줄, 필요시 공식 근거 |
| 시작 | 사용자가 하려는 일, 선행 개념·준비 상태 |
| 만들 것 | 수정할 파일/쿼리와 첫 행동, 기존 기능의 확장 여부 |
| 데이터 | 계속 따라갈 실제 값이나 명시된 예시 값 |
| 처리 | 입력→변환→판단→저장/조회→응답의 해당 구간 |
| 결과 | HTTP·행·로그·테스트 등 관찰 가능한 기대값 |
| 경계 | 이번 구현, 관찰만 할 오류, 다음 단계의 범위 |
| 응용 | 같은 원리를 다른 조건에 적용할 과제와 판단 근거 |

첫 API를 정규식으로 잡아 핵심 과제로 단정하지 않는다. 준비용 요청, 관찰용 오류, SQL 과제, 단위 테스트, 운영 명령을 구별한다. 기존 요구사항·채점 기준·학습자의 미완성 코드를 보존한다. 진행 기록은 실제 파일과 대조한다.

## 백엔드 화면의 정확성

- 같은 요청의 URL·JSON 필드·DTO·Service·Repository/Mapper·SQL·행을 출처대로 연결한다. 모든 계층이 등장해야 한다고 강제하지 않는다.
- Entity 메모리 값과 DB 행을 구별한다. EntityManager/영속성 컨텍스트/구현체를 같은 물건으로 표현하지 않는다.
- flush의 SQL 실행과 commit의 확정, rollback 분기, 별도 연결에서 조회하는 시점을 구별한다. DB 클라이언트는 앱 처리 경로 밖의 관찰 도구다.
- 토큰 검증과 업무 데이터 조회를 구별한다. 예컨대 JWT 서명 검증에 DB가 필요 없다는 말은 `/users/me` 구현도 DB를 읽지 않는다는 뜻이 아니다. 로그인·재요청·실패 흐름을 실제 코드에서 확인한다.
- 실습용 인증 구성과 실무 권장 구성을 같은 것으로 단정하지 않는다. 세션/JWT·인증/인가의 차이를 객체 모양만으로 가르치지 말고 생성·전달·검증·만료·폐기 위치를 표시한다.
- 성능·동시성·재시도는 기대 경로와 측정 결과를 분리한다. 실제로 실행하지 않은 쿼리 수·ms·EXPLAIN 결과를 성공값으로 꾸미지 않는다.
- 성능 실험은 기존 정답 데이터를 보존하는 별도 실험 데이터에서 한다. 명령의 실행 효과와 복구 방법은 프로젝트 규칙을 따른다.

## 조사와 근거

로컬 내용 대조와 새로운 이론/웹 리서치를 구별한다. 리서치가 필요하면 사용자의 상시 위임·도구·보관 규칙을 따른다. 원문과 이미지가 충돌하면 이미지를 사실 근거로 삼지 않는다. 원문 자체의 오류도 기록하고, 요청 범위 안에서 고친다.

## 전달

한 데이터의 여정을 시작부터 끝까지 따라가게 한다. 설명 수준은 쉬워도 판단의 이유·실패 조건·경계는 삭제하지 않는다. 풍부한 화면의 근거를 순서·강조·확대 장면으로 이어준다. 필요한 상세 패널은 정밀한 내용을 보존하며, 핵심 설명을 전부 접힌 영역에 숨기지 않는다.

시나리오 첫 장면에는 사용자 상황, 만들 것, 보낼 것만 둔다. 확인 방법은 실제 요청·DB 관찰 장면에서, 개념은 독립된 학습 장면에서 제공한다. 한 장면이 길어지면 글씨를 줄이거나 토글을 쌓는 대신 장면을 나눈다. 개념 장면은 사용자의 조작에 따라 한 값이나 한 상태가 바뀌어 의미를 보여 주며, 설명용 값과 실측을 시각적으로 구분한다.

# 시안과 구현 검수

## 이미지 검수

1. **사실:** API·필드·타입·코드·표명·상태·값·단계 이름을 원문과 대조한다. 사이드바·작은 보조 패널도 검사한다. 화살표의 순서·분기·관찰 위치를 확인한다.
2. **제작 등급:** 재질·빛·깊이·미세 디테일·타이포가 주 장면과 작은 카드에서 일관적인지 확인한다. 한 번 더 단순화하면 좋아질 것이라는 가정으로 검사를 끝내지 않는다.
3. **정보 위계:** 먼저 할 행동, 따라갈 데이터, 결과를 찾을 수 있는지 본다. 풍부함을 유지하면서 크기·대비·공간·강조·연결을 조정한다.
4. **실제 표시 크기:** 원본을 보고, 기존 DOM의 실측 크기 또는 명시된 설계 크기로도 본다. crop·object-fit·opacity·배경을 적용한 상태에서 핵심이 잘리는지 확인한다. 세트는 나란히 비교한다.
5. **파일:** 크기·비율·포맷·알파를 확인한다. 특정 출력 픽셀 수를 요청했어도 실제 결과가 같은지 읽어서 확인한다.

평균 휘도 비율, 알파 bbox 85%, 채도 차 0.15 같은 특정 에셋의 경험값을 보편적 합격 기준으로 쓰지 않는다. 피사체 점유율·투명 여백·휘도·채도는 실제 배치와 목적에 맞춰 판단한다. 이 수치들은 텍스트 대비나 교육 정확성의 대체 증거가 아니다.

## 구현 검수

이미지 시안의 실제 크기와 같은 뷰포트에서 구현을 캡처하고 모바일(기본 360px, 프로젝트 지정값 우선)도 확인한다. 배치·밀도·재질·타이포·줄바꿈·선·그림자·상태를 나란히 대조한다. 단순한 카드로 대체하고 '시안 반영'이라 부르지 않는다. 의도적으로 다른 부분은 구체적으로 남긴다.

버튼·키보드·포커스·토글·링크·모바일 넘침을 실제 브라우저에서 확인한다. 원문과 긴 코드, 상세 값, 평가 기준이 보존됐는지 확인한다. light/dark가 있으면 각각 실제 계산 대비와 캡처를 본다. 그라디언트·반투명·이미지 배경의 자동 대비 수치는 실제 배경을 잘못 해석할 수 있으므로 캡처와 대조한다. 일반 텍스트 4.5:1, 큰 텍스트 3:1을 실무 검사 목표로 삼되 평균 이미지 휘도와 혼동하지 않는다.

## 증거 기록

프로젝트에 inventory/parity가 있으면 그 스키마를 따른다. 없으면 작은 manifest에 다음을 기록한다.

```json
{
  "id": "page-state",
  "source": ["source-file:section-or-line"],
  "mockup": "selected-image.png",
  "prompt": "final-prompt.txt",
  "canvas": {"width": 1536, "height": 1024},
  "corrections": [],
  "status": "mockup_ready",
  "desktopCapture": null,
  "mobileCapture": null,
  "visualDiff": "",
  "technicalCheck": "source contract checked; runtime not executed",
  "interactionCheck": "",
  "learnerValidation": "not conducted"

```

`canvas`는 예시이며 실제 파일 크기로 교체한다. 상태의 의미는 draft=검토 중, mockup_ready=시안 검수 완료, implemented=구현했으나 검증 남음, verified=해당 단위의 기술·시각·조작 증거가 충족됨이다. 사용자 이해도 검증은 별도다. 시안 하나나 공통 컴포넌트 하나를 만들었다고 다른 화면·토글·내부 블록 전체에 verified를 전파하지 않는다.

핵심 오류가 남은 이미지는 draft로 유지한다. 이미지 생성, 정적 원문 대조, 브라우저 동작, 실제 API·DB 실행을 각각 구별해 결과를 말한다.


===== P09 원문 전체 =====
# P09. Java 문법 기초 — 클래스·필드·메서드·생성자를 선언하고 호출하기

> 클래스는 상태(필드)와 동작(메서드)을 한 이름 아래 선언하고, 객체는 그 클래스로부터 만들어진다.
> 필드는 객체 상태로 감싸고 메서드로 읽고 바꾸며, 호출자는 메서드의 입력과 반환값으로 객체와 협력한다.
> 인자는 항상 값으로 전달된다. 객체 인자는 참조값의 복사본이므로 객체 내부 변경은 보이지만 매개변수 재할당은 호출자에게 보이지 않는다.

## 1. 한 줄로 말하면

Java 클래스는 필드, 생성자, 메서드 같은 멤버를 선언하는 타입이고, `new`로 만든 객체는 각자 인스턴스 필드 값을 가진다. 메서드는 이름·매개변수·반환 타입·본문을 선언해 입력을 처리하고 결과를 돌려주며, `static` 멤버는 특정 객체가 아니라 클래스에 속한다. 이 문법을 읽고 고쳐야 Spring의 Controller, Service, DTO가 어떤 상태를 들고 어떤 호출을 하는지 파악할 수 있다.

## 2. 당장 알아야 할 것

### 1) 소스 파일·패키지·import

`package` 선언, 필요한 `import`, 클래스 순으로 둔다. 소스 루트 아래 경로는 패키지와 맞춘다.

```java
package com.example.billing;
import java.math.BigDecimal;
public class Invoice { private BigDecimal total; }
```

예: `src/main/java/com/example/billing/Invoice.java`. 파일 기반 `javac`에서는 공개 최상위 타입과 파일 basename을 맞춘다(JLS §7.6). 이름 없는 패키지는 작은 실습용이다.

### 2) 클래스 구성과 생성자

상수·필드, 생성자, 공개 메서드, private 보조 메서드 순은 관례다. 생성자는 클래스명과 같고 반환 타입 없이 새 객체를 초기화한다.

```java
public class Invoice {
    private final String number;
    public Invoice(String number) { this.number = number; }
}
```

직접 생성자를 선언하지 않았을 때만 기본 no-arg 생성자가 제공된다. 생성자·Builder 설계는 → P04 참조.

### 3) 변수 종류·스코프·기본값

인스턴스 필드는 객체별, `static` 필드는 클래스별 하나다. 지역 변수는 선언 블록 안에서만 유효하며 사용 전 직접 초기화한다. 기본값은 필드와 배열 원소에 적용된다.

| 종류 | 위치·범위 | 초기화 |
|---|---|---|
| 지역 변수 | 메서드·블록 안 | 읽기 전에 직접 대입 |
| 인스턴스 필드 | 객체마다 | 숫자 `0`, `boolean false`, 참조 `null` 등 |
| `static` 필드 | 클래스당 공유 | 타입별 기본값 또는 초기값 |
| 매개변수 | 메서드 호출마다 | 인자값 |

```java
private int retryCount; // 기본값 0
private static int issuedCount;
public void send() { int attempt = retryCount + 1; }
```

요청별 상태를 공유되는 `static` 필드에 두지 않는다.

### 4) 메서드 선언 해부

```java
public BigDecimal totalWithTax(BigDecimal rate) throws ArithmeticException {
    return total.multiply(BigDecimal.ONE.add(rate));
}
```

`public`은 접근, `BigDecimal`은 반환 타입, `totalWithTax`는 이름, 괄호 안은 타입·이름의 매개변수, `throws`는 선언 예외, 중괄호 안은 본문이다. 반환값이 없으면 `void`; `static`은 `public static int parse(...)`처럼 쓴다. static 문맥에는 `this`가 없다.

### 5) 호출·`this`·`return`

인스턴스 메서드는 `invoice.total()`, static 메서드는 `Invoice.parse(...)`로 호출한다. 인스턴스 안의 `recalculate()`는 `this.recalculate()`와 같다. `this.number = number`는 필드와 동명 매개변수를 구분한다. 비void 메서드는 정상 종료 경로마다 반환값이 필요하며, `void`에서는 `return;`으로 일찍 끝낼 수 있다.

```java
public boolean overdue(LocalDate due) { return due.isBefore(LocalDate.now()); }
public void markPaid() { if (paid) return; paid = true; }
```

### 6) 접근 제어자

접근은 멤버 사용 경계, 스코프는 이름의 유효 범위다.

| 선언 | 같은 클래스 | 같은 패키지 | 타 패키지 하위 클래스 | 그 밖 |
|---|---:|---:|---:|---:|
| `private` | O | X | X | X |
| 생략(package-private) | O | O | X | X |
| `protected` | O | O | O* | X |
| `public` | O | O | O | O |

`*` 타 패키지에서는 하위 클래스 문맥에서 상속 관계에 맞게 접근한다. 최상위 클래스는 `public` 또는 생략만 가능하다. 실무 기본값은 필드 `private`, 메서드는 필요한 호출자에게만 공개하는 것이다.

### 7) 캡슐화·getter/setter·`final`

필드를 감추고 유효성 검사를 메서드에 모은다. getter는 읽기, setter는 허용된 변경 경로다. 모든 필드에 setter를 만들 필요는 없다.

```java
private int quantity;
public int getQuantity() { return quantity; }
public void setQuantity(int quantity) {
    if (quantity < 0) throw new IllegalArgumentException();
    this.quantity = quantity;
}
```

`final` 변수는 재대입, `final` 메서드는 재정의, `final` 클래스는 상속을 막는다. 참조 변수의 `final`은 대상 객체의 가변성까지 없애지 않는다.

### 8) 오버로딩·가변 인자

같은 이름이라도 매개변수 목록(개수·타입·순서)이 달라야 오버로딩된다. 반환 타입만 바꾸면 오류다.

```java
String find(long id) { ... }
String find(String code) { ... }
```

마지막 매개변수에만 `...`을 붙이는 varargs는 본문에서 배열처럼 다룬다.

```java
static int sum(int... values) {
    int total = 0;
    for (int value : values) total += value;
    return total;
}
```

배열 하나 또는 개별 값을 넘길 수 있다. 오버로드에 varargs가 겹치면 선택되는 시그니처를 확인한다.

### 9) Java는 항상 값 전달

기본 타입은 값이 복사된다. 참조 타입도 객체가 아니라 참조값 복사본을 받는다. 따라서 같은 객체의 필드 변경은 보이지만 매개변수에 새 참조를 대입해도 호출자 변수는 그대로다. 3절 예제를 실행해 확인한다.

### 10) `main`

```java
public static void main(String[] args) { ... }
```

Java 실행 시작점이다. `args`는 명령행 인자이며 Spring Boot도 여기서 `SpringApplication.run(...)`을 호출한다.

### 연산자 표와 식 읽기 (보강)

연산자는 피연산자에 계산이나 비교를 적용해 값을 만든다. 아래 표는 일상적인 코드에서 자주 만나는 산술·비교·논리 연산자를 모았다. 식은 결과의 타입도 함께 생각한다. 산술식은 보통 숫자를, 비교식과 논리식은 `boolean`을 만든다.

| 구분 | 연산자 | 의미·예 |
|---|---|---|
| 산술 | `+`, `-`, `*`, `/`, `%` | 더하기, 빼기, 곱하기, 나누기, 나머지: `7 % 3`은 `1` |
| 부호·증감 | `+x`, `-x`, `++x`, `x++`, `--x`, `x--` | 부호를 붙이거나 값을 1 증감. 전위형은 증감한 값, 후위형은 증감 전 값을 식의 결과로 사용 |
| 크기 비교 | `<`, `<=`, `>`, `>=` | 숫자 등의 대소 비교: `age >= 19` |
| 동등 비교 | `==`, `!=` | 기본형 값 또는 참조의 동일성 비교: `count != 0` |
| 논리 | `!`, `&&`, `||` | 부정, AND, OR: `ready && !closed` |
| 비트/boolean | `&`, `|`, `^` | 정수에서는 비트 연산, boolean에서는 AND·OR·XOR. boolean `&`, `|`는 양쪽을 모두 평가 |

비교와 논리 연산의 결과는 `true` 또는 `false`다. Java는 숫자를 참·거짓으로 자동 변환하지 않으므로 `if (count)`는 컴파일되지 않고 `if (count > 0)`처럼 조건을 써야 한다. `==`는 두 객체의 내용이 같은지 검사하지 않고 참조가 같은 객체를 가리키는지 검사한다. 문자열 내용 비교는 `name.equals("Ada")`처럼 `equals`를 사용한다. `==`는 두 기본형 값이 같은지 비교할 때 알맞다.

정수 나눗셈은 소수 부분을 버린다. 따라서 `7 / 3`은 `2`이고, 나머지는 `7 % 3`으로 얻는다. 0으로 정수를 나누면 `ArithmeticException`이 난다. `int` 계산 결과가 표현 범위를 넘으면 예외 대신 값이 순환해 보이는 오버플로가 발생할 수 있다. 금액 계산에 `double`을 무심코 쓰면 이진 부동소수점의 근삿값이 드러날 수 있으므로, 실제 금액 모델에서는 보통 `BigDecimal`을 사용한다.

연산자 우선순위는 괄호가 없는 식을 어떤 묶음으로 해석할지 정한다. 자주 쓰는 순서는 높은 것부터 낮은 것으로 다음과 같다. 같은 묶음 안에서 결합 방향이 다를 수 있으므로, 복잡해지면 괄호를 써서 의도를 드러낸다.

| 우선순위 | 연산자 묶음 |
|---|---|
| 높음 | 후위 `x++`, `x--` → 단항 `++x`, `--x`, `!`, `+`, `-` |
|  | 곱셈·나눗셈·나머지 `*`, `/`, `%` → 덧셈·뺄셈 `+`, `-` |
|  | 관계 `<`, `<=`, `>`, `>=` → 동등 `==`, `!=` |
|  | 비트 AND `&` → XOR `^` → OR `|` |
|  | 논리 AND `&&` → 논리 OR `||` |
| 낮음 | 삼항 `?:` → 대입 `=`, `+=` 등 |

예를 들어 `2 + 3 * 4`는 곱셈을 먼저 해 `14`가 된다. `10 + 6 / 2 * 3`은 곱셈·나눗셈이 덧셈보다 먼저이고, 같은 우선순위의 이항 산술 연산이 왼쪽부터 결합하므로 `10 + ((6 / 2) * 3)`, 즉 `19`다. `a || b && c`는 `a || (b && c)`로 묶인다.

반면 수학 기호처럼 `0 < age < 100`이라고 연쇄 비교할 수 없다. 첫 비교의 결과가 boolean이기 때문에 `age > 0 && age < 100`으로 써야 한다. 우선순위에 익숙해져도 조건이 길면 괄호나 중간 boolean 변수를 써서 읽는 사람이 계산을 머릿속으로 추적하지 않게 한다.

`&&`와 `||`는 단락 평가(short-circuit)를 한다. `&&`의 왼쪽이 `false`면 전체 결과가 이미 `false`라 오른쪽을 실행하지 않는다. `||`의 왼쪽이 `true`면 전체 결과가 이미 `true`라 오른쪽을 건너뛴다.

그래서 `denominator != 0 && total / denominator > 3`은 분모가 0일 때 나눗셈을 피한다. `user != null && user.isActive()`도 null 객체의 메서드 호출을 막는 전형적인 가드다. 다만 오른쪽 식을 건너뛸 수 있으므로, 그 안에 필수 대입이나 부수 효과를 넣으면 조건에 따라 동작이 달라진다.

`&`와 `|`는 boolean 두 값을 받을 수 있지만 양쪽을 모두 평가한다. 정수에 쓰면 비트 연산이 되므로 논리 조건에는 보통 `&&`, `||`를 쓴다.

다음 순수 Java 예제는 산술·비교·논리식과 우선순위, 단락 평가를 한 번에 보여 준다.

```java
public class OperatorsDemo {
    public static void main(String[] args) {
        int quantity = 3;
        int unitPrice = 1200;
        int subtotal = quantity * unitPrice;
        int discounted = subtotal - subtotal / 10;
        int precedence = 2 + 3 * 4;
        int leftToRight = 10 + 6 / 2 * 3;
        boolean eligible = quantity >= 3 && discounted >= 3000;
        int divisor = 0;
        boolean safe = divisor != 0 && 24 / divisor > 3;
        int calls = 0;
        boolean skippedAnd = false && (++calls > 0);
        boolean skippedOr = true || (++calls > 0);
        boolean evaluatedBitwise = false & (++calls > 0);

        System.out.println("subtotal=" + subtotal + ", discounted=" + discounted);
        System.out.println("precedence=" + precedence + ", leftToRight=" + leftToRight);
        System.out.println("eligible=" + eligible + ", safe=" + safe);
        System.out.println("shortCircuit=" + skippedAnd + ", " + skippedOr
                + ", bitwise=" + evaluatedBitwise + ", calls=" + calls);
    }
}
```

JDK 21 실행 결과:

```text
subtotal=3600, discounted=3240
precedence=14, leftToRight=19
eligible=true, safe=false
shortCircuit=false, true, bitwise=false, calls=1
```

마지막 줄에서 `&&`와 `||`의 오른쪽에 둔 `++calls`는 실행되지 않았지만, boolean `&` 오른쪽은 실행되어 `calls`가 1이 됐다. 이처럼 증감 연산자를 조건식 안에 넣으면 값 계산과 상태 변경이 뒤섞여 읽기 어렵다. 가능하면 증감은 별도 줄로 옮기고, `x++`와 `++x`가 식 안에서 다른 결과를 만든다는 점도 기억한다. 배열 인덱스나 반환식에 후위형을 쓸 때는 특히 전후 어느 값이 사용되는지 확인한다.

참고: Operators (The Java™ Tutorials) — https://docs.oracle.com/javase/tutorial/java/nutsandbolts/operators.html
참고: Chapter 15. Expressions, §15.23 Conditional-And Operator — https://docs.oracle.com/javase/specs/jls/se25/html/jls-15.html#jls-15.23

```java
public class MethodsDemo {
    private final String prefix;
    private static int created;
    public MethodsDemo(String prefix) { this.prefix = prefix; created++; }
    public String format(String name) { return prefix + name; }
    public String format(String name, int count) { return format(name).repeat(count); }
    public void printAll(String... messages) {
        for (String message : messages) System.out.println(message);
    }
    public static int createdCount() { return created; }
    public static void main(String[] args) {
        MethodsDemo demo = new MethodsDemo("Hello, ");
        System.out.println(demo.format("Ada"));
        System.out.println(demo.format("Hi! ", 2));
        demo.printAll("one", "two");
        System.out.println("created=" + MethodsDemo.createdCount());
    }
}
```

```text
Hello, Ada
Hello, Hi! Hello, Hi! 
one
two
created=1
```

첫 두 메서드는 인자 목록이 달라 오버로드다. `printAll`은 0개 이상 문자열을 받을 수 있고 본문에서는 배열처럼 반복한다. `createdCount()`는 타입으로 부르는 static 메서드다. JDK 21 실행 출력이며 이 예제 문법은 Java 25에서도 같다.

## 4. 치트시트
| 이름 | 용도 | 예시 | 주의 |
|---|---|---|---|
| `package` / `import` | 타입 위치·이름 | `package com.app;` | 파일 경로와 패키지를 맞춤 |
| 클래스 | 필드·메서드 묶음 | `public class Order {}` | 공개 타입 파일명 일치 |
| 필드 / 지역 변수 | 상태 / 임시값 | `private long id;` | 지역 변수는 직접 초기화 |
| `static` | 클래스 소속 멤버 | `Order.nextId()` | 인스턴스 `this` 없음 |
| 생성자 | 객체 초기화 | `new Order(7L)` | 반환 타입 없음 |
| 반환 메서드 / `void` | 결과 / 작업 | `int size()` / `void cancel()` | 반환 메서드는 `return` 필요 |
| 접근 제어 | 사용 경계 | `private`, 생략, `protected`, `public` | 필드는 보통 private |
| 오버로딩 | 입력별 같은 이름 | `find(long)`, `find(String)` | 반환 타입만 다르면 오류 |
| varargs | 여러 입력 수용 | `log(String... values)` | 마지막 매개변수만 가능 |
| `this` / `final` | 현재 객체 / 재대입 방지 | `this.code = code;` | 참조 final은 객체 불변과 다름 |
| `main` | 실행 시작점 | `public static void main(String[] args)` | 런처가 args 전달 |

## 5. 자주 나는 에러와 해결

1. **`class Invoice is public, should be declared in a file named Invoice.java` →** 공개 클래스 이름과 파일명이 다르다 → 파일을 `Invoice.java`로 바꾸고 패키지 디렉터리도 `package`와 맞춘다.
2. **`cannot find symbol` →** 이름 오타, import 누락, package 경로 불일치, 메서드 인자 타입 불일치 중 하나다 → 컴파일 오류가 가리킨 줄에서 선언 이름·import·매개변수 시그니처를 차례로 확인한다.
3. **`non-static variable ... cannot be referenced from a static context` →** `main`이나 static 메서드에서 인스턴스 필드/메서드를 객체 없이 사용했다 → 객체가 필요한 동작이면 `obj.method()`로 호출하고, 실제로 인스턴스 상태가 필요 없는 기능만 static으로 만든다.
4. **`missing return statement` 또는 `incompatible types` →** 비void 메서드의 일부 경로가 반환하지 않거나 반환값의 타입이 선언과 다르다 → 모든 분기에서 선언 타입에 맞는 값을 반환한다. 반환할 의미가 없는 작업이면 `void`인지 다시 판단한다.
5. **`variable x might not have been initialized` →** 지역 변수를 기본값이 있을 것으로 착각했다 → 선언할 때 초기화하거나, 읽기 전 모든 분기에서 대입한다. 필드의 초기화 규칙을 지역 변수에 적용할 수 없다.
7. **필드 변경이 호출 뒤 사라짐 →** 매개변수 변수 자체에 새 값을 대입해 호출자의 변수가 바뀔 거라 기대했다 → 공유할 객체를 전달했다면 그 객체를 수정하고, 호출자가 새 객체를 받게 하려면 결과를 반환해 `x = method(x)`처럼 대입한다.

## 6. 한 단계 더

선언을 읽을 때는 먼저 패키지와 타입 이름, 다음에 필드의 소유자(객체 또는 클래스), 메서드의 접근 범위·매개변수·반환 타입을 본다. 호출 시 컴파일러는 이름과 인자 목록으로 접근 가능한 메서드를 선택하고, 인자 값을 매개변수 변수에 전달한다. 인스턴스 메서드는 대상 객체의 `this`를 기준으로 필드에 접근하지만 static 메서드는 객체 상태에 기대지 않는다.

필드 접근 제한은 변경 규칙을 한곳에 모아 실수 가능한 경로를 줄인다. 객체의 동등성 계약과 상속 설계는 → J02 참조. 레코드와 모던 문법은 → J05, 제네릭은 → J03 참조.

## 7. 자가점검 Q&A (면접 대비)

### Q1. 필드와 지역 변수의 초기화 규칙은 왜 다른가?

필드는 객체 또는 클래스가 만들어질 때 타입별 기본값으로 초기화된다. 지역 변수는 실행 흐름마다 초기화 여부가 달라질 수 있어, 컴파일러가 읽기 전에 대입했는지 확인한다. 지역 변수의 자동 기본값을 가정하면 특정 분기에서 의미 없는 값이 사용될 수 있다.

**꼬리질문: 참조 필드의 기본값은?** `null`이다. 업무상 필수 참조 필드는 생성자에서 유효한 값으로 설정해 null 상태를 줄인다.

### Q2. 객체를 메서드에 넘겼는데 필드 변경은 보이고 재할당은 안 보이는 이유는?

Java는 참조에 의한 전달이 아니라 값 전달이다. 객체를 가리키는 참조값이 복사되므로 매개변수와 호출자의 변수가 같은 객체를 가리킬 수 있다. 그 객체의 필드를 바꾸는 것은 관찰되지만 매개변수 변수에 다른 참조를 대입해도 호출자 변수는 바뀌지 않는다.

**꼬리질문: 호출자에게 새 객체를 돌려주려면?** 메서드의 결과를 반환하고 호출자가 대입한다. 예: `profile = normalize(profile);`.

### Q3. 반환 타입만 바꿔 오버로딩할 수 없는 이유는?

메서드를 호출할 때 컴파일러는 이름과 인자 목록을 보고 후보를 고른다. 반환 타입만 다르면 같은 호출식이 어느 메서드를 뜻하는지 정할 수 없다. 의미가 다른 작업이면 이름을 나누고, 입력 형식만 달라 같은 작업이면 매개변수를 오버로드한다.

**꼬리질문: 매개변수 이름만 바꾸면?** 시그니처가 같으므로 중복 선언 오류다. 매개변수 이름은 호출 선택 기준이 아니다.

### Q4. `static` 메서드에서 `this`를 쓸 수 없는 이유는?

static 메서드는 클래스에 속하며 특정 인스턴스를 대상으로 하지 않고 호출된다. 어느 객체의 인스턴스 필드를 가리켜야 할지 정해진 `this`가 없다. 필요한 객체 상태를 인자로 받거나 인스턴스 메서드로 만들어 대상 객체에서 호출한다.

**꼬리질문: static 메서드에서 인스턴스 메서드를 호출하려면?** 해당 클래스 객체를 받아 `obj.instanceMethod()`처럼 호출한다.

### Q5. `private` 필드에 getter와 setter를 모두 만들면 캡슐화가 되는가?

접근 문법만 감췄다고 캡슐화가 끝나지 않는다. setter가 검증 없이 어떤 값이든 허용하면 필드 공개와 실질적으로 다르지 않다. 도메인 규칙에 맞춰 허용된 동작만 노출하고 변경할 필요가 없는 값에는 setter를 제공하지 않는다.

**꼬리질문: 조회 전용 필드는 어떻게 두나?** 필드를 `private`으로 두고 getter만 제공하거나 필요한 조회 메서드만 노출한다.

### Q7. varargs를 선언하면 메서드 본문에서 여러 인자는 어떻게 보이는가?

마지막 매개변수에만 `Type... values`로 선언한다. 호출자는 값을 0개 이상 전달하거나 해당 타입 배열 하나를 전달할 수 있고, 메서드 안에서는 배열처럼 인덱싱·반복한다. varargs와 다른 오버로드가 겹치면 실제 선택된 메서드 시그니처를 확인한다.

**꼬리질문: varargs 매개변수를 두 개 선언할 수 있나?** 불가능하다. 가변 길이 입력은 마지막 매개변수 하나에만 둘 수 있다.
