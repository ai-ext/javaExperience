# javaExperience 시각 학습 개편 계획과 작업 기록

> 대상: 공개 `javaExperience` 저장소. StudyMate는 이번 단계에서 수정하지 않는다. 구현은 범위가 작은 작업으로 나눠 서브에이전트에 맡기고, 메인 담당자가 기술 내용·화면·원문 보존을 검증한다.

## 현황과 완료 판단

`node tools/site/inventory-visual-work.mjs`가 원문과 생성 HTML이 함께 있는 **323개 화면**을 [화면별 체크리스트](VISUAL-PAGES.md)에 나열한다. 원문의 절·산문·표·코드·목록과 생성 HTML의 토글, 화면 JSON의 위젯·흐름을 [개별 항목 목록](visual-inventory.jsonl)에 기록한다. 첫 목록 생성 시 **42,631개 항목**이었고, 생성 화면이 바뀌면 수가 변한다. 이는 같은 콘텐츠의 원문 블록과 생성 UI를 모두 포함한 검사 단위 수이지, 서로 다른 개념 수가 아니다. [집계](visual-inventory-summary.json)에 현재 상태를 남긴다.

한 항목의 상태는 `unreviewed → mockup_ready → implemented → verified` 순서로만 올린다. 시안을 만들었어도 실제 화면에 반영하지 않았으면 `mockup_ready`에 둔다. 공통 컴포넌트가 적용돼도 개별 화면의 콘텐츠·모바일·상호작용을 확인하지 않았으면 해당 페이지 체크박스를 완료로 바꾸지 않는다. `--mark <id> <상태> <근거>`로 상태를 바꾸고, 목록 재생성은 기존 상태를 보존한다.

## 화면 설계의 검증 질문

- 첫 화면에서 사용자 행동과 API 경로, 화면 변화가 보이는가? 핵심이 닫힌 토글 속에만 있지 않은가?
- 한 데이터의 **메모리 객체 값 / 컨텍스트 스냅샷 / SQL / MySQL 행 값**을 각 순간에 비교할 수 있는가?
- JPA 표준, Hibernate 구현, Spring Data Repository, `EntityManager`, Entity, DTO의 역할을 바꿔 말하지 않는가?
- `flush`와 `commit`의 결과를 구분하는가? `rollback`은 commit 다음 단계가 아니라 분기인가? DBeaver의 별도 연결에서 보이는 값은 올바른가?
- 원문 코드·채점값·링크·앵커가 그대로 남고, 360px에서 가로 넘침과 숨은 조작이 없는가?
- 흐름 애니메이션을 학습용 예상 경로로 표시하고, 실제 서버 요청 결과만 실측으로 표시하는가?

### 1. JPA 세로 사례: 실제 DB 값까지 따라가기

출처: `docs/knowledge/S09-jpa-hibernate.md`, `P20-jpa-entity-mapping.md`, `lessons/E3-what-is-jpa.md`, `E7-jpa-update-delete.md`. 구현 후보: `tools/site/knowledge-page-visual.mjs`, 별도 `tools/site/jpa-journey.{css,js}`. 전체 문장을 한 장에 밀어 넣지 않고 첫 장면을 누르면 상세 레인이 열리게 한다.

기술 동작은 [Jakarta Persistence 3.2 명세](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2)와 [EntityManager API](https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/entitymanager)의 `find`·`flush` 설명에 대조한다. 별도 연결의 관찰은 실습 MySQL의 트랜잭션 격리와 조회 시작 시점을 함께 적는다.

- [x] 실제 `imagegen`으로 [JPA 데이터 여정 시안](jpa-entity-db-journey-v1.png)을 생성한다. 예제는 게시글 `id=42`, 제목 `첫 글 → 수정된 글`이다.
- [x] 시안의 오해 가능성 식별: commit/rollback은 순차 3·4단계가 아니라 **동일한 flush 뒤 갈림길**이다. 이미지 속 SQL/문구는 기술 근거가 아니다.
- [x] S09에 조회 전 DB 행, `find()` 이후 Entity 인스턴스와 스냅샷, setter 이후 메모리 값, flush 뒤 트랜잭션 내부 행을 단계 선택으로 구현한다. commit/rollback 뒤 결과는 같은 flush의 두 분기 카드로 둔다.
- [x] S09에서 `EntityManager`를 컨텍스트 조작 창구로, Hibernate를 SQL 생성·실행 구현체로 표시한다. Entity와 DB 행의 `id | title`을 별도 표로 비교한다.
- [ ] SELECT가 생략되는 같은 컨텍스트의 재조회, IDENTITY 식별자 때문에 INSERT가 앞당겨질 수 있는 예외, 트랜잭션 경계가 없는 경우는 기본 경로 아래 확장편으로 둔다.
- [x] S09의 별도 DBeaver 관찰 레인을 앱 요청 경로 밖에 두고, 새 autocommit SELECT 기준 commit 전·후 값과 rollback 결과를 표시한다. 열린 REPEATABLE READ 스냅샷의 예외도 명시한다.
- [ ] S09와 P20의 실제 문장·코드·근거 링크를 보존하고, `npm run build`와 개념 상태 검사 및 데스크톱·360px 브라우저로 확인한다.
- [x] S09의 원문 ASCII 흐름 항목을 시안 → 구현 → 검증으로 차례로 기록한다. 이는 S09 전체 문서 완료를 뜻하지 않는다.

### 1-1. P20 엔티티 필드에서 실제 DB 열까지

- [x] 실제 P20 코드가 `Post`가 아니라 `Order`·`OrderLine`인 것을 대조한 뒤, 별도 `imagegen` [P20 Order 시안](p20-order-entity-mapping-v1.png)을 만든다.
- [x] `Order.id`, `ordererName`, `lines`와 `orders.id`, `orderer_name`, `order_lines.order_id`의 대응을 예시 행으로 보여 준다. 예시 키는 실제 DB 결과로 표기하지 않는다.
- [x] `Order.create` → `addLine` → `EntityManager.persist` → 트랜잭션 안의 SQL → commit 뒤 별도 DB 조회를 원문 코드 기반으로 단계별 보여 준다. IDENTITY의 INSERT 시점과 실제 SQL의 차이는 설명한다.
- [x] 실제 이미지 시안과 P20의 데스크톱·360px 화면을 비교했다. 필드와 열 강조, 2·3·4단계의 값 변화, 원문 앵커, 360px 가로 넘침 없음을 브라우저에서 확인했다. 시안의 밝은 전체 셸·모바일 세부 배치는 아직 동일하게 재현되지 않았다.
- [x] P20의 매핑 화면과 저장 단계 항목에 시안·구현·검증 근거를 기록했다. P20 전체 문서의 모든 항목이 검증된 것은 아니므로 화면 체크박스는 미완료다.

### 2. 산문·표·토글 정보 구조

- [x] 전체 토글 종류와 JPA/학습 자료의 긴 산문·코드 현황을 읽기 전용으로 조사한다.
- [ ] 절 첫머리에는 한 문장 핵심, 실제 값이 움직이는 이미지/인터랙션, 읽을 순서를 노출한다. `knowledge-chapter`와 `knowledge-topic`의 2중 접기 속에 핵심이 숨는 화면을 페이지별로 표시한다.
- [ ] 짧은 개념 설명은 기본 노출하고, 증거 로그·긴 정답 코드·Postman 설정·원문 표는 접기 또는 파일 탭으로 둔다. 정답을 먼저 보여 주면 안 되는 문제형 레슨은 정답 토글을 유지한다.
- [ ] 각 유형의 imagegen 시안에서 데스크톱과 모바일의 제목·주요 시각·설명·깊이 정보 배치를 정한 뒤 공통 컴포넌트에 반영한다. 시안 하나로 여러 화면을 처리해도 각 화면의 표현과 사실은 목록에서 따로 확인한다.
- [ ] 토글의 제목이 `보기`/`코드`처럼 모호한 항목, 본문 안 2중 접기, 접은 상태에서 핵심을 볼 수 없는 항목을 재검사한다.

### 3. 화면별 적용 순서

DB 조회·쿼리 실습은 [DB 시나리오 확장 계획](DB-SCENARIO-PLAN.md)의 DB-01~13을 기존 M1~M10·8장·9장·L12~L14에 연결한다. 현재는 기획 단계다. [첫 DB 화면 시안](db-api-query-journey-draft-v1.png)은 배치 초안으로만 기록했고, 잘못 생성된 SQL·스키마·파라미터·측정값을 확인해 구현 근거에서 제외했다.

- [ ] **시나리오 101단계:** `1-2` 첫 INSERT → `1-4` 컬럼·DDL·실DB → `2-1` 조회 → `2-4` N+1 → `10-12` JPA/MyBatis flush부터 값 변화를 시각화한다. 이후 [101개 화면 목록](VISUAL-PAGES.md)의 각 항목을 순서대로 확인한다.
- [ ] **공부자료 134개:** S09·P20·P19·S10부터 데이터/실행 흐름을 완성한다. 나머지는 상태 변화, 비교·선택, 절차·시간, 장애·운영 유형으로 나눠 각 문서의 고유 내용을 이미지 시안과 대조한다.
- [ ] **레슨 50개·티켓 30개:** 문제·정답의 공개 순서를 지키며, 실행 로그와 DB 전후 차이를 별도 시각으로 읽게 한다.
- [ ] **홈·시나리오 목차·미션·랩·오류 화면:** 시작 지점, API 묶음, 데이터 연결, 수동 확인 경로를 화면별로 검토한다.

### 4. 각 작업의 반복 절차

1. [ ] 목록에서 페이지와 하위 항목 ID를 고르고 실제 `.md`, 생성 `.html`, 정답·SQL 출처를 읽는다.
2. [ ] 실제 `imagegen` 시안을 만들고 파일·프롬프트 요약·사실 검토 결과를 `docs/design/`에 기록한다.
3. [ ] 서브에이전트가 좁은 범위의 UI를 구현한다. 메인 담당자는 시안 대 실제 화면을 대조한다.
4. [ ] `npm run build`, 관련 자동 검사, 브라우저 조작, 360px 확인을 마친다. 원문과 생성 코드의 일치를 확인한다.
5. [ ] 항목별 상태와 [화면별 체크리스트](VISUAL-PAGES.md)를 갱신한다. 묶음 검증 후에만 PR을 갱신한다.

## 이번 반복의 사실 관계

이전 imagegen 시안 두 장은 **부분 적용**이다. S09 버전 표는 카드와 원문 표 접기로, 코드 시안은 역할별 탐색기로 구현됐다. 세 번째 JPA 시안의 첫 세로 사례는 S09 상단의 인터랙티브 값 비교로 적용했다. 시안 전체가 동일하게 재현됐거나 P20·나머지 화면까지 개별 검토를 받은 상태는 아니다. 상태 목록은 이를 그대로 나타낸다.

## 2026-10-15 · 새 브랜치 첫 화면 이관
