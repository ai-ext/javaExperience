## 목표·선수 지식·학습자 작업

DB 기반 BLOCK/MASK 금칙어를 post create/copy/replace/patch/publish/restore와 comment create/edit에 적용한다. BLOCK은 모든 Unicode whitespace를 제거해 비교하고 MASK는 연속 일치 문자열을 가린다. 선수는 입력 정규화와 공통 write policy.

## 확장 개발 명세

### 입력 정규화 경계와 규칙 cache 무효화 후속

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

baseline은 literal normalization과 즉시 DB 최신성을 정한다. scale 시 cache를 추가하더라도 삭제한 금칙어가 오래 stale되지 않아야 한다.

**시작 상태**

격리 DB에 BLOCK “바카라”, MASK “바보”를 넣고 한 앱, 그 뒤 두 app instance/cache 실험 환경을 준비한다.

**학습자가 할 일**

- 공백 삽입, punctuation 분리, fullwidth/confusable 변형을 요청해 현재 어떤 입력이 match하는지 기록한다.
- 관리 API로 word를 add/delete하고 선택한 cache invalidation 방식에서 각 app이 언제 변경을 보는지 확인한다.
- BLOCK 복수 필드 오류와 MASK 저장이 post/comment write path마다 유지되는지 확인한다.

**정상 사례**

- 공백으로 분리된 차단 문구는 match하고 연속 MASK는 가려진다. 삭제 rule은 문서화한 한도 안에 모든 instance에 반영된다.

**실패·경계 사례**

- cache stale로 삭제한 금칙어가 허용 시간보다 오래 남지 않는다. rule reload failure는 관측되며 차단 문구가 조용히 저장되지 않는다.

**동시성·성능**

격리 DB에서 rule 1/100/1000개일 때 cache 적용/미적용의 query 수·필터 지연·다중 인스턴스 반영 시간을 비교한다.

**DB 관찰**

**합격 기준**

정규화 범위가 문서화되고 cache add/delete propagation bound 및 모든 write path 공유 정책을 테스트한다.

**기존 과제와 중복·연결**
