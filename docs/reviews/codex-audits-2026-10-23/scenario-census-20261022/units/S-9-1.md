## 판정

기존 schema 기준선 설정과 빈 Testcontainers migration 경로의 설정은 존재한다. 기존 데이터 보존과 BASELINE history 증거는 수동 D1/D2 확인으로 남으며 blank DB 테스트 통과와 구분한다.

## 목표·선수 지식·학습자 작업

기존 스키마를 Flyway migration 이력의 기준선으로 바꿔 이후 변경을 추적한다. 선수 단계와 DB 구분은 scenario/README.md 기준으로 확인한다.

baseline과 migration 도입 경로가 있다. 이미 존재하는 DB/빈 DB의 서로 다른 시작 상태, checksum/실패 복구, migration 자동 적용 설정 및 schema drift를 분리해서 검토한다.

## 요구·구현·검사 대조

### 1. 기존에 데이터가 있는 practice/community schema에 Flyway를 도입한다. history가 없고 테이블이 있으면 V1을 실행하지 않고 version1 기준선을 기록한다. 빈 DB의 V1은 데이터가 아닌 schema만 만들고 JPA ddl-auto는 validate로 유지한다.

구현 대조: 실제 snapshot의 application.yml은 baseline-on-migrate=true, baseline-version=1, ddl-auto=validate다. V1은 schema DDL을 담고 빈 Testcontainers 설정은 V1 다음 V1_1 test seed를 실행한다. test seed는 운영 migration 디렉터리와 분리돼 있다.

검사 대조: 수동 합격 항목 D1은 BASELINE version/type/success, D2는 post 수 145 이상을 확인한다. T1 Gradle 테스트는 빈 Testcontainers DB에서 V1/V1_1을 실행한다. 기존 practice DB baseline을 단언하는 테스트는 확인되지 않았다.

공백 또는 한계: 기존 schema 기준선 경로는 수동 명령과 DB 확인에 의존한다. Testcontainers는 빈 DB만 다룬다. 적용 migration checksum 불변성도 자동 검사는 아니다.

## 쿼리·DB 깊이와 다음 단계

baseline-on-migrate는 기존 테이블 schema와 빈 DB를 다르게 처리한다. 운영용 migration과 테스트 seed migration 분리도 요구에 부합한다. community/practice 기준선을 코드 존재만으로 실행했다고 추정하지 않는다. V1은 schema만 만들고 기존 데이터에 재실행되지 않는지 확인한다.

- 현재 난이도: 고급(해당 단계 기준)
- 판정 이유: 기존 스키마를 Flyway migration 이력의 기준선으로 바꿔 이후 변경을 추적한다.
- 다음 단계: 9-2~9-5에서 index/backfill/new table/expand-contract로 이어진다. 이 단계에는 운영 DB backup/restore 절차가 직접 누락될 수 있으나 전 과정 위험 승인/사전 백업 설명을 따져 과도한 필수 요구로 두지 않는다.

## 확장 개발 명세

### 기존 DB 기준선과 빈 테스트 DB 경로를 분리 확인

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

기존 테이블이 있는 DB에서는 V1을 다시 실행하지 않고 기준선을 기록해야 하며, 빈 테스트 DB에서는 V1과 테스트 seed migration을 실제 실행해야 한다.

**시작 상태**

A: post 145개 이상이 있는 practice schema이며 flyway_schema_history는 없다. B: 비어 있는 MySQL 8.4 Testcontainers DB다. 공유 volume은 초기화하지 말고 A는 disposable 복사본에서 확인한다.

**학습자가 할 일**

- A의 disposable schema에 앱을 실행하고 history 첫 행의 version=1,type=BASELINE,success=1인지 확인한다.
- 실행 전후 post 수가 145개 이상 그대로인지, 대표 ID/열 값이 바뀌지 않았는지 비교한다.
- 빈 DB Testcontainers 설정 위치를 확인하고 테스트를 실행해 V1 테이블 생성 뒤 V1_1 seed가 들어오는지 확인한다.
- ddl-auto=validate인지 확인하고 spring.sql.init 또는 ddl-auto update가 별도 schema 생성 경로로 작동하지 않는지 확인한다.
- 적용 migration 파일은 수정하지 않고 변경은 V2 이후 새 파일로 추가하는 규칙과 checksum 검증을 확인한다.

**정상 사례**

- 기존 비어 있지 않은 schema에는 BASELINE 기록만 생기고 V1 CREATE TABLE은 실행되지 않는다.
- 빈 테스트 DB에서는 V1 및 별도 위치의 V1_1이 실행된다.

**실패·경계 사례**

- 잘못된 baseline version이면 기존 테이블에 과거 migration이 다시 적용될 수 있다.
- V1에 seed나 데이터 의존 auto_increment를 넣으면 기존 schema의 기준선 재현성이 깨질 수 있다.
- 적용한 V1을 수정하면 checksum 검증이 실패한다.

**동시성·성능**

부하 측정 범위가 아니다. 이 단위는 startup/history 경로를 확인한다. backup/restore는 R07 연결 주제이며 여기서 실행했다고 간주하지 않는다.

**DB 관찰**

- flyway_schema_history version/type/success와 post 행 수.
- 기준선 전후 대표 행 ID/값, 빈 DB에서 V1/V1_1 실행 결과.

**합격 기준**

- 기존 DB는 BASELINE version1을 기록하고 145개 이상 데이터가 보존된다.
- 빈 container 테스트는 V1과 V1_1 경로를 통과한다.
- Flyway 외 스키마 자동 변경 경로 없이 ddl-auto validate가 적용된다.

**기존 과제와 중복·연결**

S9-3/5는 기준선 이후 schema 변경을 다루고 S9-1은 Flyway 이력 소유권과 시작점을 설정한다.

**우선순위**

medium
