## 확장 개발 명세

### Q03 구체 데이터 결과와 경계 검사

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

게시판 slug=dev로 필터하고 PUBLISHED/not-deleted/not-hidden/PUBLIC 상태를 지킨다.

**시작 상태**

L12 practice profile. Request P creates dev/PUBLISHED/PUBLIC post `[쿼리연습] JPA 연결` with content `본문 JPA 검색` by member5. Use dynamic id/author from P response.

**학습자가 할 일**

- 명시된 boardSlug=dev query parameter로 요청하고 같은 공개 조건의 직접 SQL 결과와 비교한다.
- P가 조건을 만족하면 P.body.id가 포함되는지 확인하고 모든 행의 공개 조건/게시판 slug를 검증한다.
- 동일 입력으로 JPA/MyBatis 결과를 비교한다.
- 잘못된 slug 또는 빈 결과 경계를 별도 호출한다.

**정상 사례**

- boardSlug=dev이며 PUBLISHED, 미삭제, 미숨김, PUBLIC인 글만 남는다.

**실패·경계 사례**

- P는 dev에 생성되므로 맞는 조건이면 결과에 있어야 한다. C3는 200과 items 배열 type만 보고 ID나 total을 단언하지 않는다.

**동시성·성능**

L12 query 정확성만 다룬다. plan/성능 측정은 DB-08~14에서 수행한다.

**DB 관찰**

- 실제 응답 ID/total/status와 실행 SQL을 기록한다. items type만 확인하지 않는다.
- 동적 P로 seed count가 달라질 수 있으므로 reset하거나 직접 SQL과 대조한다.

**합격 기준**

- 조건을 만족하는 동적 P ID가 응답에 있고 모든 행의 공개 조건이 맞는다.
- 같은 입력의 직접 SQL/JPA/MyBatis ID 결과가 일치한다.

**기존 과제와 중복·연결**

Q02는 hidden/deleted 조건, DB-01은 field mapping, DB-07은 query 방식 비교를 다룬다.

medium
