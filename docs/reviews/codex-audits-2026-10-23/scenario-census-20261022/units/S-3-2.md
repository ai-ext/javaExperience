## 판정

## 목표·선수 지식·학습자 작업

삭제 버튼은 post row/관계 row를 지우지 않고 deleted_at/updated_at만 채우는 soft delete를 한다. 일반 조회에서는 작성자/운영자 포함 누구도 볼 수 없으며 운영팀·휴지통 경로는 원 행 및 like/comment/tag 관계가 남아 있음을 활용한다. 2-3 access policy와 1-6 auth가 선수다.

DELETE /api/posts/{id}를 만들고 토큰 사용자·운영자 삭제 권한을 서비스에서 검사한다. 살아 있고 볼 수 있는 post에 soft-delete timestamp를 주며 204 no-body를 반환한다. 조회/목록/PATCH 후속 경로는 삭제 행을 감춰야 한다.

## 쿼리·DB 깊이와 다음 단계

- content: DELETE request becomes UPDATE post.deleted_at/updated_at. Foreign-keyed post_like/comment/post_tag relations are not deleted. Shared access policy and list WHERE exclude deleted rows; future trash/restore must use a separate read path.
- current_scope: soft delete state transition, authorization, 204 응답, 숨겨진 row 및 관계 보존.
- missing_scope: purge/archive/retention/backup/restore는 여기 정의되지 않으며 11-5 trash/restore로 이어진다.
- existing_links: 2-3 access policy가 deletedAt 기준 404, 3-1 PATCH가 canView 재사용, 11-5가 restore, scheduler 후속이 batch purge를 다룬다.

- 현재 난이도: 중급
- 판정 이유: 삭제 요청을 실제 row 삭제가 아닌 timestamp 상태 변경으로 표현하고 FK 관계는 보존한다. 접근권한과 목록 노출을 따로 검증한다.
- 다음 단계: - S-2-3: deleted rows are never visible
  - S-3-1: PATCH only accessible non-deleted records
  - S-11-5: trash/restore
  - S-15-4: purge in batches
