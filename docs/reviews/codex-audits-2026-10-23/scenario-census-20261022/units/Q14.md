## 판정

실제 코드가 요청된 Query clause를 구현한다. 자동 검사는 Querydsl/JPA가 size=3으로 반환한 items를 비교하며, 본문 size=5 예시와는 다른 유효 입력이다. 자동 검사가 5개 응답을 그대로 검사한다고 볼 수 없고, 결과 ID·동률 순서·이 요청의 total은 고정 assertion이 없다.

## 목표·선수 지식·학습자 작업

정렬 허용값/보조 tie key 및 content/count query 조건의 일치를 확인한다. 공통 준비 및 앞 단계 L12/L13/L14의 누적 SQL 실습을 선수로 한다.

원문은 단계별 코드 제공/미완성 구간을 구별해 적고, 학습자는 해당 쿼리 요구와 경계 케이스를 실행 결과로 확인한다. 정렬 허용값/보조 tie key 및 content/count query 조건의 일치를 확인한다.

## 요구·구현·검사 대조

### 1. likeCount DESC, id DESC sort와 content/total count 동일 필터.

구현 대조: JPA SearchFilter는 sort=latest/likes를 허용한다. likes는 like_count DESC,id DESC로 정렬하고 @Query countQuery에도 동일 FILTER를 쓴다. MyBatis choose와 별도 count도 같은 정렬/조건을 쓴다.

검사 대조: L13 요청 I/J는 각각 sort=likes,page=0,size=3이며 C6은 두 items 배열만 비교한다. 본문 size=5 입력도 유효한 별도 예시이나 checker는 이를 보내지 않는다. Q14 요청의 total, 정확한 ID 순서, 동률 정렬을 단언하지 않는다. C2 count 비교는 앞선 board 필터 요청에 적용된다.

공백 또는 한계: 검사기는 size=3 요청의 두 엔진 items 동등성만 확인한다. size=5 요청 및 Q14 해당 요청의 total, 알려진 정렬 ID, like_count 동률의 id tie-break 결과는 별도 검증 대상으로 남는다. size가 3과 5로 다르다는 것 자체는 결함이 아니다.

## 확장 개발 명세

### 좋아요 정렬 동률과 total 일치

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

좋아요 수가 같은 행은 ID DESC로 고정하고 같은 필터에 대한 content와 total count가 맞아야 한다.

**시작 상태**

L13 practice profile에서 기존 seed와 자동 요청 P 이후의 DB 상태를 사용한다. 문서 요청 크기 5와 자동 check 크기 3이 달라졌으므로 실제 테스트는 자동 check의 size3을 재현하고 차이를 기록한다.

**학습자가 할 일**

- QueryDSL/MyBatis 각각 sort=likes,page=0,size=3으로 실행하고 id/likeCount 정렬을 확인한다.
- 정렬상 동률인 like_count=22 글의 id tie order를 seed에서 확인한다. P는 좋아요 0이라 top3에 들어가지 않는다.
- 같은 query filter로 total count도 읽고 두 엔진 값과 직접 SQL count를 대조한다.
- 문서 size5와 request panel size3 중 의도된 완료 입력을 명세/검사에서 일치시킨다.

**정상 사례**

- 현재 public PUBLISHED not-deleted seed에서 첫 세 기대 IDs `[131,103,55]`이며 세 글 모두 like_count=22, 동률은 id DESC. P의 like_count=0.
- QueryDSL와 MyBatis content 순서와 total이 동일.

**실패·경계 사례**

- 실제 요청이 size3인데 source contract size5를 그대로 통과로 가정하지 않는다.
- 보조 id DESC가 빠지면 동점 22개 사이 순서가 불안정할 수 있다.
- Count query에 동일 filter가 빠지면 items는 같아도 total이 달라진다.

**동시성·성능**

이 단위는 query contract를 검증하며, 실행계획·성능 측정은 DB-08~14로 연결한다.

**DB 관찰**

- actual IDs, likeCount, total, query params; total과 직접 count 결과.

**합격 기준**

- 실행 크기를 명시(문서 5/자동 3 차이 해결 전엔 run size3으로 check 근거).
- size3 first IDs [131,103,55], tie id DESC.
- QueryDSL/MyBatis items와 total 동일 및 SQL count agreement.

**기존 과제와 중복·연결**

Q18은 pagination/count를 QueryDSL 동적 필터로 다루고 Q14는 L13 @Query/MyBatis 정렬 방식이다.

**우선순위**

medium
