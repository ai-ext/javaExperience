## 확장 개발 명세

### 동일 first-page 계약으로 다섯 query 방식을 분리 호출

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

각 query 경로는 대안 구현이다. 동일 기준 요청으로 결과를 비교하고 운영 요청 하나에서 모든 방법을 동시에 호출하지 않는다.

**시작 상태**

M1 practice seed, boardSlug=dev, 익명 viewer, 첫 페이지 size20, 빈 cursor를 기준으로 한다. overlay API가 다르면 동일 파라미터로 각 repository 함수를 호출한다.

**학습자가 할 일**

- 다섯 구현을 각각 dev/PUBLISHED/not-deleted/PUBLIC 조건 및 publishedAt DESC,id DESC 정렬로 실행한다.
- 반환 ID, 응답 7개 필드, 행 수, SQL 로그와 parameter binding을 기록한다.
- 선택된 page ID를 이용한 별도 batch query로 tag를 붙이고 결과 배열/count를 비교한다.
- native SQL alias/provider 동작과 Page count query가 각 실행 경로에 미치는 차이를 적는다.
- opaque cursor 계약은 별도로 본다. PageRequest.of(0,20)은 첫 페이지 근사일 뿐이다.

**정상 사례**

- 다섯 구현은 같은 7개 field와 ID 순서, content 비포함 결과를 반환한다. tag array는 두 번째 page ID query로 연결한다.

**실패·경계 사례**

- id tie-breaker가 없으면 publishedAt 동률의 순서가 달라질 수 있다.
- page query에서 tag를 JOIN하면 게시글이 중복돼 LIMIT/count가 틀어질 수 있다.
- JPQL Page는 추가 count query를 실행할 수 있다. MyBatis XML은 #{slug} 바인딩을 사용하고 문자열 치환을 사용하지 않는다.
- Derived Top20/Pageable은 M1의 전체 opaque cursor/size 계약을 대신하지 않는다.

**동시성·성능**

SQL 로그만으로 속도를 주장하지 않는다. plan을 확인하려면 동일 data/parameter로 DB-08 이후 EXPLAIN을 수행한다. query syntax 비교에는 필수가 아니다.

**DB 관찰**

- 독립 구현 간 ID/정렬 필드/행 수 동등성.
- 실제 SQL과 placeholder 값, query 수 및 두 번째 tag query.

**합격 기준**

- 모든 방법이 같은 filter/order/size 및 응답 필드를 반환한다.
- tag hydration은 모든 tag를 붙이되 게시글 행을 중복시키지 않는다.
- method별 SQL 로그와 차이/한계를 기록한다.

**기존 과제와 중복·연결**

Q01~08은 L12, Q09~14는 L13, Q15~18은 L14 query 방식을 구현한다. DB-07은 한 M1 SQL/API 계약으로 비교한다.

**우선순위**

high
