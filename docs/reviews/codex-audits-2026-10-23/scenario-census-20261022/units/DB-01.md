## 확장 개발 명세

### 응답 필드에서 두 읽기 SQL 유도

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

M1 목록 API는 DTO 열 출처, 비로그인 공개조건, page selection, 태그 batch hydration을 연결한다.

**시작 상태**

practice seed; GET `/api/boards/dev/posts?size=20&cursor=` 첫 페이지 계약. API 구현은 아직 없는 checkout이므로 HTTP 응답을 실측했다고 말하지 않는다.

**학습자가 할 일**

- id/title/authorNickname/likeCount/commentCount/publishedAt의 DB 원천과 FK를 line별로 그린다.
- WHERE와 order/limit을 직접 작성하고 query에서 빠져야 할 content를 설명한다.
- 목록 SQL에서 나온 최대20 post id로 second tags SQL을 작성한다.
- CloudBeaver에서 두 SELECT를 직접 실행하고 M1 기대값과 대조한다.

**정상 사례**

- 전체 dev 목록 50개; 첫 다섯 ids [145,144,143,140,138].
- post145=스프링 트랜잭션 전파 삽질기, author 밤샘개발자, like20,comment1,published_at 2026-10-03 10:10:08; 태그 java.

**실패·경계 사례**

- visibility PUBLIC 누락 시 private post가 결과에 들어올 수 있다.
- status/deleted filter 하나를 빼면 M1의 50개/첫 IDs와 달라진다.
- 태그를 첫 쿼리에 직접 JOIN하면 multi-tag 글이 페이지 행을 늘릴 수 있고 글별 SELECT면 N+1.

**동시성·성능**

현재 scope는 query shape; N+1 query-count 관찰은 M1/M10-1로 연결하고 실행 계획은 후속 DB 단계.

**DB 관찰**

- 첫 SQL 최대20행과 second SQL별 post/tag 쌍.
- 요청에 없는 content가 첫 projection에 없는지.

**합격 기준**

- 첫 SELECT ID order `[145,144,143,140,138]`, 전체 count 50.
- 145 row fields와 tag `java` 일치.
- 두 번째 query는 page ids로 한 번에 찾고 SQL 횟수와 실제 결과를 기록.

**기존 과제와 중복·연결**

M1과 중복되는 데이터 계약이고 DB-02는 같은 API의 cursor를 확장한다.

**우선순위**

medium
