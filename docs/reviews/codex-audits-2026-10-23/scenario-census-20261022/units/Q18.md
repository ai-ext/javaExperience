## 판정

page content와 total count가 동일한 동적 필터를 사용하고 tie·빈 페이지를 확인한다. 공통 준비 및 앞 단계 L12/L13/L14의 누적 SQL 실습을 선수로 한다.

문서에서 제공된 코드와 미완성 구간을 구별하고, 동적 필터·정렬·페이지·count 요구를 실행 결과로 확인한다. 자동 요청은 sort=likes,page=0,size=3이며 별도로 문서 예시인 size=5도 호출해 각각의 반환 크기와 total을 기록한다.

## 확장 개발 명세

### QueryDSL page/count와 정렬 tie key 검증

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

sort=likes는 likeCount DESC,id DESC이고 page content 및 total count는 같은 predicate로 계산되어야 한다.

**시작 상태**

L14 practice overlay에 seed를 적재한다. 비교 대상 G/H는 sort=likes,page=0,size=3이며 본문은 size=5 요청도 예시로 든다. 좋아요 수 동률 게시글 쌍이 있으면 반환 순서와 ID를 기록한다.

**학습자가 할 일**

- 같은 필터·정렬·페이지 파라미터로 Querydsl G와 MyBatis H를 호출해 status, items ID 순서, total을 기록한다.
- 자동 검사 입력 size=3과 본문 예시 입력 size=5를 각각 실행해 응답 최대 개수와 total을 기록한다. 각각의 유효 입력을 따로 확인하고 둘이 다른 값이라는 이유로 결함 판정하지 않는다.
- 좋아요 수 동률이 있는 게시글 쌍에서 sort=likes가 likeCount DESC,id DESC를 따르는지 SQL/코드와 ID 순서로 확인한다.
- 결과가 없는 필터를 호출해 items=[]와 total=0인지 확인하고 다음 페이지 경계에서 items=[]여도 total은 같은 predicate의 전체 수로 남는지 본다.
- 필터 하나를 바꿨을 때 목록 조건과 count 조건이 함께 바뀌는지 대조한다.

**정상 사례**

- size=3 요청은 최대 3개, size=5 요청은 최대 5개를 반환하며 양쪽 total은 해당 필터의 전체 건수다.
- 동률은 likeCount 내림차순 뒤 id 내림차순으로 안정화된다.

**실패·경계 사례**

- 목록은 필터됐는데 total은 필터 전 건수면 count predicate 불일치다.
- 같은 요청에서 두 엔진의 ID 순서가 다르면 정렬·동률 처리 차이를 조사한다.
- 존재하지 않는 조건에서 items가 비었는데 total>0이면 목록/count 조건 차이다.

**동시성·성능**

이 단위는 query contract를 검증하며, 실행계획·성능 측정은 DB-08~14로 연결한다.

**DB 관찰**

- page0/page1 ID, likeCount, total, sort parameter와 count WHERE 조건을 기록한다.

**합격 기준**

- G/H의 동일 size=3 요청은 status=200, items 최대 3개, total 일치 및 ID 배열 일치를 보인다.
- size=5 문서 예시는 최대 5개 반환과 total을 별도로 확인한다.
- 동률은 likeCount DESC,id DESC 순서이고 빈 조건은 items=[],total=0이다.

**기존 과제와 중복·연결**

Q14는 L13의 Page/count와 유사하고 Q18은 L14 QueryDSL 동적 query 방식이다.
