## 확장 개발 명세

### M1 정책 접근과 cursor 계약을 각각 확인

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

MISSION의 HTTP·데이터 기대값과 참조 snapshot에 없는 cursor 목록을 별도로 확인한다.

**시작 상태**

practice seed와 공통 R1~R5 규칙을 사용하고 초기 DB 상태를 읽기 전용으로 기록한다. 2-3 snapshot은 비교 자료일 뿐 M1 구현 정답으로 간주하지 않는다.

**학습자가 할 일**

- 익명으로 GET dev size20 첫 페이지를 요청해 ID와 total을 기록하고 X-Member-Id 7로 다시 요청한다.
- 상세 ID 7,36,42,15를 작성자·관리자·팔로워·비팔로워 조건에서 요청해 정책별 결과를 비교한다.
- P 생성 및 상세 응답 필드와 좋아요/북마크 상태를 확인하고 작성자/비작성자 조회 전후 view_count를 기록한다.
- cursor가 published_at,id 두 키를 사용하는지 확인한다. offset PageRequest만으로는 M1 cursor 계약을 충족하지 않는다.

**정상 사례**

- 익명 첫 페이지와 X-Member-Id 7 요청의 결과를 각각 MISSION 기대 ID/total과 비교한다.
- 상세 정책 판정은 요청자 역할과 post ID 조합별 응답 상태/본문으로 기록한다.

**실패·경계 사례**

- offset 기반 PageRequest만 사용하면 opaque cursor 및 다음 페이지 중복·누락 검증을 통과한 것으로 볼 수 없다.
- 조회 횟수 전후 차이를 기록하지 않으면 view_count 불변/증가 규칙을 확인하지 못한다.

**동시성·성능**

커서 정확성 실습이며 지연 시간 목표는 없다.

**DB 관찰**

- 첫 페이지/전체 페이지 ID, total, nextCursor와 각 Post의 접근 상태.
- 요청 전후 view_count, like/bookmark 상태와 DB 관계 행.

**합격 기준**

- 익명과 member7의 첫 페이지 값·상세 접근 정책을 각각 계약에 맞게 확인한다.
- 전체 cursor traversal에 ID 누락/중복이 없고 view_count 증감 주체가 기대와 일치한다.

**기존 과제와 중복·연결**

2-3은 상세 접근 정책의 비교 자료다. DB-02는 두 키 cursor를, M1은 API 접근 규칙과 cursor 계약을 다룬다.

high
