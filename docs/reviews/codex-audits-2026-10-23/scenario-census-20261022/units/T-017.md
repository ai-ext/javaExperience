## 판정

요구가 정량적인 동시 재현을 포함하고 선택 테스트까지 제안한다. 자동 회귀가 선택임과 barrier 미세조건 부족이 주요 gap이며 구현 snapshot 미제공은 결함이 아니다.

## 목표·선수 지식·학습자 작업

조회수 동시 증가와 좋아요 수 갱신손실 문제를 재현하고 원자적 DB 증가·응답 재조회로 고친다. 선수는 JPA dirty checking, UPDATE column set, database atomic update, lost update, persistence context staleness.

상세 GET에서 read-modify-write를 atomic `view_count = view_count + 1`로 바꾸고 API가 요청별 반영된 수를 반환하게 한다. like_count를 덮지 말고 concurrent request 30개와 after state query를 비교한다.

## 요구·구현·검사 대조

### 1. 30 concurrent GET 모두 200; 응답 30개의 viewCount가 각기 다르고 마지막 A/B 비교에서 +31; like_count는 post_like row count와 계속 같다. 기술 설명은 Hibernate update가 다른 column을 stale entity value로 써서 손실 유발 가능.

구현 대조: 정답 snapshot은 지정되지 않았다. 이 독립 과제의 요구로 확인했으며 미제공 정답을 구현 결함으로 판정하지 않는다.

검사 대조: C1~C4는 동시 요청·누적 차이·응답 값 유일성·likes 유지, D1은 view_count와 like_count/cache row 비교. T1 concurrency test는 optional로 표기되어 실제 자동 regression은 완료 필수 아니다. R1-R3는 원인, atomic increment/locking/version 대안, persistence context 응답 갱신을 다룬다.
