## 확장 개발 명세

### M10 네 실패 실험의 재현·수정·근거

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

학습 목표는 실패 원인 진단이다. 수정된 코드 테스트만으로는 실패를 재현했는지 확인할 수 없다.

**시작 상태**

올바른 snapshot을 기록한 후 격리 worktree/Testcontainers 또는 disposable profile에서 실험하고 매번 코드/설정을 복구한다. 공유 practice seed는 변경하지 않는다.

**학습자가 할 일**

- M10-1: M1 첫 페이지 size5/20의 SQL 호출 수를 기록하고 N+1 방식과 작성자 JOIN+페이지 ID 태그 일괄 조회를 비교한다. 응답 ID/필드는 같아야 한다.
- M10-2: 격리 branch에서 원자적 증가를 현재값 읽기 후 +1 저장으로 바꾸고 동기화 동시 요청을 실행해 lost update를 기록한다. 이후 원자적 SQL 증가와 unique insert를 복원해 다시 실행한다.
- M10-3: 격리 설정에서 hikari maximum-pool-size=2, transaction 안의 sleep3000 시험 hook을 넣고 요청 5개를 동시에 보내 pool timeout 및 active/idle/pending 값을 기록한 뒤 설정과 hook을 제거한다.
- M10-4: PostQueryService.getDetail부터 PostAccessPolicy.canView까지 draft/hide/follow/block/delete 사례를 따라가 첫 반환 분기와 결과를 기록한다.

**정상 사례**

- 현재 PostListQueryCountTest는 free 게시판 size5/20에서 쿼리 수가 같고 5 이하인지 검사한다. M10은 cursor 구현 뒤 같은 기준을 M1 목록에서 확인해야 한다.
- 수정된 LikeService 검사는 동시 회원 20명 뒤 관계 행과 counter 일치를 확인한다. 이는 실패 버전을 재현하는 과제와 다르다.

**실패·경계 사례**

- read+1 변형에서 lost update를 먼저 관찰하고 diff 및 테스트 근거를 보존한다.
- pool2와 트랜잭션 내 sleep 조건에서만 timeout 포화를 기대한다. 포화되지 않은 상태에서 timeout이 없다는 결과는 재현 실패 판정이 아니다.
- 일반 실행 전에 모든 시험 hook/설정을 복원한다.

**동시성·성능**

시작 latch와 고정 요청 수를 쓰고 active/idle/pending/error를 기록한다. 단일 실행 결과를 보편적 pool 용량으로 일반화하지 않는다.

**DB 관찰**

- M2 성공 요청 수, 관계 행 수와 like_count 증가량.
- pool active/idle/pending, timeout 시간 및 오류.

**합격 기준**

- 4개 실험 각각 변경 전·실패 관찰·수정 또는 원인 설명 증거가 있다.
- M2 실패 변형은 counter/행 불일치를 재현하고 수정판은 정합성을 회복한다.
- M3 timeout은 격리 pool2+3초 실험에서 재현한 뒤 hook을 제거한다.
- M1 쿼리 감소 후 응답은 같고 정책 분기 설명에 실제 코드 행과 결과가 포함된다.

**기존 과제와 중복·연결**

PostListQueryCountTest와 LikeConcurrencyTest는 정상 상태 검사다. M10은 고장 변형 대비가 핵심이며 P18/W06/R08은 동시성/pool 원리를 설명한다.
