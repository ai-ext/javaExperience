## 판정

폴더 service는 실제로 잠금→count→unique insert를 수행하고 삭제는 관계 bulk 이동과 폴더 삭제를 원자 트랜잭션으로 묶는다. 합격기준의 동시 상한/이름 경합은 실행 JUnit이 없으므로 그 부분만 검증 gap이다.

## 목표·선수 지식·학습자 작업

회원별 폴더 상한·중복 이름·이동/삭제 원자성을 다루며, 동시 생성의 정확한 보장은 folder service 구현에서 확인해야 한다. 선행 6-0에서 기본 관계를 만들고 이어 6-3 목록, 6-4 부분수정, 6-5 조합 조회로 연결한다.

요청/응답과 service/repository/DDL의 회원 소유권·멱등성·실패 계약을 원문 C/D/R 항목 및 정답 코드와 대조한다.

## 요구·구현·검사 대조

### 1. 회원별 폴더 상한·중복 이름·이동/삭제 원자성을 다루며, 동시 생성의 정확한 보장은 folder service 구현에서 확인해야 한다.

구현 대조: 실제 BookmarkFolderService에서 create는 Transactional 안에서 폴더명 normalize→member 행 `findByIdForUpdate` 잠금→현재 count 확인→중복 조회→saveAndFlush 순으로 동작한다(35-48). DB unique(member_id,name) 경합은 DataIntegrityViolationException을 DuplicateBookmarkFolderNameException으로 매핑한다(76-83). 삭제는 소유자 확인 뒤 bookmark를 기본 폴더로 bulk UPDATE하고 폴더를 삭제하며 한 트랜잭션이다(63-69).

검사 대조: HTTP checker C1-C12 및 D1-D3는 cap/중복/owner/type/delete 이동을 점검한다. 관련 JUnit BookmarkConcurrentSetTest는 북마크 set 경합이며 폴더 10개 동시생성 테스트는 없다.

공백 또는 한계: R1/R2의 두 핵심 경합(같은 이름, 한 회원의 10개 초과 생성)을 자동 동시요청 JUnit으로 잠그지 않는다. 구현은 DB unique와 회원 행 잠금으로 처리하도록 돼 있으나 검사는 수동·정적이다.

## 쿼리·DB 깊이와 다음 단계

folder 생성은 회원 행을 비관적 잠금하고 잠금 아래 count해 cap 경쟁을 직렬화한다. 이름은 `(member_id,name)` unique가 최종 방어선이다. 삭제 시 소유 폴더의 bookmark를 한 번의 bulk UPDATE로 기본 폴더로 이동 후 delete한다. JPA bulk update 후 persistence context stale 여부/flush-clear는 service가 관리하는지 repository 구현에서 확인할 필요가 있다.

**이유**

**시작 상태**

격리 DB 회원 4가 폴더 9개를 가진 상태; test method 시작 전 해당 회원 폴더 fixture를 초기화한다.

**학습자가 할 일**

- 동일 회원으로 barrier 이후 3개 폴더 POST를 동시에 보낸다.
- 모든 응답이 허용된 성공/409 경로인지 확인하고 DB count를 읽는다.
- 같은 이름 요청 경쟁도 별도 시험해 unique 처리 결과를 검사한다.

**정상 사례**

- 폴더 9개에서 1개 생성은 성공하여 총 10개.

**실패·경계 사례**

- 동시 3개 중 상한을 넘는 요청은 400으로 종료되고 DB 폴더 수는 10을 넘지 않는다.
- 동시 이름 중복은 한 이름만 남고 나머지는 409.

**동시성·성능**

동일 member row lock이 create 요청을 직렬화하며 동시 실행 뒤 count<=10을 단언한다.

**DB 관찰**

- bookmark_folder rows by member_id=4
- 각 생성 응답 status와 generated ids

**합격 기준**

- 병렬 재현을 10회 반복해 항상 cap<=10
- 고유 이름 행은 하나만 보존, 충돌 응답 409

**기존 과제와 중복·연결**

문서 R1/R2의 요구를 자동 테스트로 고정; 신규 비즈니스 기능은 추가하지 않는다.
