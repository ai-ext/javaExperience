## 요구·구현·검사 대조

### 1. GET /api/me/likes?size=20&cursor= 는 R1에서 현재 보이는 좋아요 글만 반환하고 post_like.created_at DESC,id DESC 및 (likedAt,likeId) cursor를 쓴다. member12 예상 total=26, 첫 5 post ID=[145,143,140,139,142]이며 제외 기대 ID 59/67/105를 확인한다.

검사 대조: snapshot에는 좋아요 쓰기와 marked-post 테스트는 있으나 GET /api/me/likes 전용 테스트는 확인되지 않았다. member12 total=26, 첫 5개 ID, 59/67/105 제외를 직접 확인하는 assertion도 없다.

## 확장 개발 명세

### member12 좋아요 목록과 복합 cursor 경계 확인

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

M3는 좋아요 생성시각 기준 정렬, 현재 공개 조건, (likedAt,likeId) cursor를 요구하며 post 시각이나 offset과 다르다.

**시작 상태**

고정 Clock의 practice seed에서 인증 회원12, size20으로 시작한다. 첫 페이지 및 전체 기대값은 MISSION에서 확인한다.

**학습자가 할 일**

- 첫 페이지를 요청해 첫 5개 ID, 전체 cursor 순회 수, nextCursor를 기록한다.
- nextCursor를 끝까지 따라가 모든 ID를 모으고 likedAt/id 쌍 중복이나 누락이 없는지 확인한다.
- 제외 기대 ID 59,67,105의 visibility/block 관련 DB 행을 각각 대조한다.
- 격리 데이터에 likedAt이 같은 두 행을 준비하거나 선택해 likeId DESC 동률 처리를 확인한다.

**정상 사례**

- 첫 페이지 size20 뒤 cursor가 있으면 다음 페이지로 이동하고 마지막 페이지에서 더 이상 ID가 반환되지 않는다.
- 전체 순회 ID 수는 MISSION total 26이며 기대 첫 5개는 [145,143,140,139,142]다.

**실패·경계 사례**

- timestamp만 cursor에 넣으면 같은 created_at 행에서 중복 또는 누락이 생길 수 있다.
- visibility를 LIMIT 적용 뒤 필터링하면 짧은 페이지와 hasNext 오판이 생길 수 있다.

**동시성·성능**

읽기 cursor 정확성만 다루며 쿼리 지연 목표는 없다.

**DB 관찰**

- post_like created_at/id tuple, 응답 postId 순서, nextCursor 및 hasNext.
- post 59/67/105의 제외 사유와 전체 traversal count.

**합격 기준**

- 모든 페이지에 누락/중복이 없고 합계 26개다.
- 정렬은 (created_at,id) 두 키이고 첫 5개 ID가 기대값과 일치한다.

**기존 과제와 중복·연결**

DB-02는 두 키 keyset 원리를 설명하고 DB-12는 JOIN/EXISTS를 비교한다. MISSION은 고정 좋아요 데이터 결과를 제시한다.

**우선순위**

high
