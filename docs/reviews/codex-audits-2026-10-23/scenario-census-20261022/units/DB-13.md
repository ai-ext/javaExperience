## 확장 개발 명세

### 두 size 요청에서 SQL 수와 응답을 실제 계측

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

N+1은 쿼리 모양에서 찾고 실제 개선은 SQL 로그/계측으로 확인해야 한다.

**시작 상태**

M1 API 구현 또는 목적에 맞춘 practice overlay를 사용한다. practice seed와 dev 익명 요청을 유지하고 size5 및 size20, 빈 cursor를 각각 측정한다.

**학습자가 할 일**

- 한 요청의 Controller→Service→Repository 호출 순서를 기록한다.
- 수정 전 SQL statement 수를 모으고 count/content/author/tag query를 역할별로 분리한다.
- size5와 size20을 비교하되 batch fetch/cache/중복 작성자 때문에 무조건 1+N+N이라고 가정하지 않는다.
- 작성자 projection JOIN 또는 페이지 ID 기준 tag batch query를 적용한 뒤 같은 요청을 재실행해 ID/순서/7 fields/tags를 비교한다.
- Hibernate SQL/Statistics 또는 datasource 계측을 사용한다. 마지막 page에서 Page count query가 생략될 수 있음을 기록한다.

**정상 사례**

- M1 공개 dev 첫 페이지 계약과 tags 결과가 수정 전후 보존된다.
- 수정된 방식에서 작성자/tag 조회가 게시글마다 반복되지 않는다.

**실패·경계 사례**

- collection fetch join으로 tags를 한 query에 모으면 row fanout이 생겨 LIMIT이 깨질 수 있다.
- 작성자 join 없는 projection은 lazy author query를 남길 수 있다.
- SQL 실행 로그 없이 statement만 세면 DB round trip을 놓칠 수 있다.

**동시성·성능**

statement count만 측정하며 latency 주장은 하지 않는다. cache 상태와 framework 설정을 기록한다.

**DB 관찰**

- size5/size20별 statement 수와 SQL 역할, 응답 ID/필드/tag 동일성.

**합격 기준**

- 전후 실제 log를 저장하고 각 count가 요청 size 및 환경과 연결되어 있다.
- 수정 뒤 작성자/tag 조회가 항목마다 반복되지 않는다.

**기존 과제와 중복·연결**

M1/M10-1은 기능과 query 수, 2-4는 선행 N+1 연습, DB-01은 응답 필드와 SQL 연결을 다룬다.

**우선순위**

high
