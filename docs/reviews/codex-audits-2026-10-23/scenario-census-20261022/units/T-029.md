## 판정

expand/dual write/backfill/read switch/contract와 옛 컬럼 prefix 조건이 자세하다. live edit 경쟁과 실제 rollback 단계 리허설을 추가하면 무중단 절차 검증이 완성된다.

## 목표·선수 지식·학습자 작업

댓글 본문을 1000자에서 20000자로 확장하되 rolling deploy 동안 구/신 앱이 함께 작동하게 한다. expand/dual write/backfill/read switch/contract와 batch restart가 핵심이다.

새 nullable MEDIUMTEXT body를 추가하고 새/수정 write는 기존 content 1000자 prefix와 새 body에 같이 기록한다. admin batch API로 100개씩 backfill, 완료 확인 후 읽기 전환, 다음 배포에서 옛 컬럼 제거를 설계한다. 이모지/문자 길이/bytes를 구분한다.

## 요구·구현·검사 대조

### 1. 새 body는 20,000 characters까지 저장하고 구 content는 앞 1000자 prefix를 유지한다. dual-write 동안 모든 write는 두 컬럼을 채운다. backfill은 100 이하·반복 가능·remaining 0까지 진행한다. 1200자 댓글은 API/목록에서 손실 없이 읽혀야 한다.

구현 대조: 정답 snapshot이 제공되지 않은 독립 과제다. 구현 상태를 미제공 정답 부재만으로 결함 처리하지 않는다.

검사 대조: C1-C5는 백필 진행/권한, 1200자 create/list, 기존 emoji를 확인한다. D1 null body 0, D2 old prefix equality, D3 CHAR_LENGTH, D4 schema, D5 Flyway. T1 반복 backfill은 선택 사항. R1-R3 byte/char·롤백·batch scan을 설명한다.

공백 또는 한계: backfill과 live edit 동시성 및 read switch 전 배포/rollback sequence는 개념적으로 설명하지만 경쟁 update가 stale copy로 덮이지 않는 확인이 없다. 100개 경계에서 마지막 호출이 0건을 반환하는 응답 계약은 더 고정할 수 있다.

**이유**

**학습자가 할 일**

- backfill이 legacy content를 읽은 직후 같은 댓글을 1000자 초과로 수정해 두 컬럼 dual-write를 하고, backfill update가 새 body를 덮지 않는지 barrier로 확인한다. 컬럼 추가, dual write, 절반 backfill, 읽기 전환 각 단계에서 구버전으로 되돌려 비교한다. batch 중간 실패 후 재요청 결과와 100개 경계를 기록한다.

**정상 사례**

- 원문의 정상 C/D/T acceptance를 만족한다.

**실패·경계 사례**

- 원문에서 명시한 오류·경합·롤백·배포/운영 실패조건을 재현하고 DB 관측값을 기록한다.

**동시성·성능**

해당 문제의 동시 요청/SQL 수/계획/백필 진행에 맞게 barrier나 계측을 선택하고 버전·행 수·시간을 기록한다.

**DB 관찰**

body NULL 개수, legacy content=LEFT(body,1000), 둘의 CHAR_LENGTH, batch별 updated/remaining, live edit timestamp를 비교한다. utf8mb4 문자와 byte 용량을 별도로 계산한다.

**합격 기준**

동시 edit 결과가 보존되고 재시작 가능한 backfill이 중복/누락 없이 완료된다. rollout 단계별로 구버전 read/write가 안전하고 D1/D2 조건이 계속 참이어야 한다.
