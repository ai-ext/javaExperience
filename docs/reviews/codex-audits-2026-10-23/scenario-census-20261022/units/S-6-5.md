## 판정

두 관계의 교집합/합집합을 DB EXISTS로 페이지 전에 평가하고 countQuery를 동일 조건으로 복제한다. page 이후 상태는 두 bulk lookup으로 채워 N+1을 피한다. 주 gap은 복제 predicate 유지/scale 검증이며 결과 정확성 contract는 checker·JUnit에 있다.

## 목표·선수 지식·학습자 작업

좋아요/북마크 조건을 AND/OR 필터로 조합해 내 표시 글을 페이지화한다. 관계 JOIN 중복 없이 한 글씩 반환하고 별도 count와 data query를 일치시킨다.

좋아요/북마크/교집합 필터, page/size/default/빈 필터, count, 중복 제거, 인증 흐름을 확인한다. cursor 방식은 4-3/6-3과 분리한다.

## 요구·구현·검사 대조

### 1. JUnit은 각 조건/관계 조합을 확인한다. count query 기능은 응답의 totalElements로 확인하지만 대량 관계 행 실행 계획/성능 제한은 측정하지 않는다.

구현 대조: Repository는 PUBLISHED/PUBLIC/not-deleted와 양방향 block NOT EXISTS를 적용하고, liked/bookmarked=true이면 해당 EXISTS가 추가되며 전체 결과는 두 관계 중 하나 이상을 가져야 한다. 별도 countQuery가 같은 조건을 반복한다. Service는 id DESC Page로 조회하고 페이지 ID에 대해서만 like/bookmark 관계를 각각 한번씩 읽어 item 상태를 채운다. `(long)page*size > Integer.MAX_VALUE`면 조회 범위 예외 대신 빈 목록+전체 count를 반환한다.

검사 대조: C1-C13은 관계 OR/AND, 상태 DTO, 인증, size/page/filter format, 매우 큰 유효 page, empty result와 count를 검사하고 D1은 SQL 관계 ID로 중복 여부를 직접 확인하도록 요구한다. MarkedPostControllerTest는 snapshot에 있다. Stage test execution은 부모 89개 총통과 결과와 별개로 개별 test count를 claim하지 않는다.

공백 또는 한계: countQuery가 본문 query와 같은 조건을 복제하므로 향후 한쪽만 수정하면 페이지 건수가 어긋날 위험이 있다. 현재 snapshot에서는 두 식이 일치하며 별도 자동 assertion은 통합 응답의 totalElements에 의존한다.

**정상 사례**

- EXPLAIN 조건 계획

- 각 flag 조합 결과·count 일치
