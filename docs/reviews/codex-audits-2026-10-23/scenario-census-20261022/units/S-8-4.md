## 목표·선수 지식·학습자 작업

여러 선택 조건을 조합해 검색하는 동적 SQL에서 조건 누락·파라미터·정렬·페이징 계약을 다룬다. 선수 단계와 DB 구분은 scenario/README.md 기준으로 확인한다.

복수 조건/검색어/기간 등을 조합하는 JPQL/native 동적 쿼리와 수동 확인이 있다. 파라미터화 및 문자열 결합 금지, 빈값·공백·NULL 구분, 동적 정렬 화이트리스트, 조건 조합 테스트/총건수 일치 여부를 채점과 실제 repository 대조한다.

## 요구·구현·검사 대조

### 1. `GET /api/posts/search`는 값이 있는 board/tag/author/from/to/q만 추가하고, 기존 2-3 visible 조건 및 published_at DESC,id DESC를 유지한다. 태그는 EXISTS로 중복 방지. 날짜는 from/to 포함일이며 to 다음 날 00:00 미만으로 구현한다. 페이지 count는 별도 조회하고 큰 offset이 앞 결과를 재노출하지 않아야 한다.

구현 대조: 실제 PostSearchRepository는 들어온 조건만 predicate로 추가하고 공통 viewable()을 게시판/검색이 공유한다. 태그 EXISTS, title LIKE escape, 날짜 상한은 to.plusDays(1) exclusive, max DB date는 upper 생략. count 먼저 조회해 long offset의 int truncation으로 앞 페이지가 다시 보이는 것을 막는다.

검사 대조: Z1~Z16 자동 HTTP 검사에서 구체 ID·건수·상태를 확인한다. tag=jpa total13 ID [123,118,98,87,79], qna+spring total12 ID [139,130,111,106,104], author2+Sep total1 ID112, N+1 total9, 기본 검색 total111, 없는 tag는 빈 결과다. member7 차단 결과 및 잘못된 날짜/큰 page도 검사한다.

공백 또는 한계: HTTP 검사는 여러 조건 조합, 차단, 잘못된 날짜와 매우 큰 page를 다루지만 생성 SQL statement 개수는 직접 분리하지 않는다. R2~R4의 count·동적 계획 기준은 코드/SQL 로그 근거가 추가로 필요하다.

## 쿼리·DB 깊이와 다음 단계

실제 검색기는 공통 열람 가능 predicate와 값이 주어진 조건만 결합한다. tag는 EXISTS를 써 다중 태그 관계가 결과를 중복시키지 않는다. 날짜 종료값은 그날 다음 날 00:00 미만으로 처리하고 최대 날짜에서는 상한을 생략한다. count를 먼저 조회해 큰 offset을 int로 잘라 앞 페이지가 다시 나오지 않게 막는다.

- 현재 난이도: 고급(해당 단계 기준)
- 판정 이유: 여러 선택 조건을 조합해 검색하는 동적 SQL에서 조건 누락·파라미터·정렬·페이징 계약을 다룬다.
- 다음 단계: DB-02 커서/정렬, DB-14 느린 쿼리로 이행. 조건별 인덱스·선택도와 계획 검증은 뒤 단계에 둔다.

## 확장 개발 명세

### 조합 조건 결과와 SQL 호출 수 측정

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

하나의 재사용 Criteria 조립으로 필터 조합 결과를 유지하면서 count 1회와 content 1회만 호출되는지 확인한다.

**시작 상태**

Practice seed, 기본은 로그아웃 상태다. 차단 사례는 viewer7을 사용하고 Z1~Z16 요청/기대값을 따른다.

**학습자가 할 일**

- Z1/Z2/Z3/Z4 각 조건을 단독으로 요청한 뒤 조건을 결합해 응답 ID와 total을 비교한다.
- 결과가 있는 페이지와 빈 페이지의 Hibernate SQL 로그를 남기고 count/content statement 및 tag/author 추가 조회 수를 센다.
- Z7에서 Authorization: tok-p07로 author2 차단 결과를 확인하고 익명 결과와 비교한다.
- tag=no-such-tag, 공백 tag, from>to, 최대 날짜 경계를 각각 호출한다.

**정상 사례**

- Z1 tag jpa: total13, first IDs [123,118,98,87,79].
- Z5 all public visible: total111, first IDs [145,144,143,141,140].
- Z13 whitespace tag omits condition: same total111/IDs [145,144,143,141,140].

**실패·경계 사례**

- Z9 from>to는 400이어야 한다. Z16은 없는 board로 인해 빈 결과가 되기 전에 잘못된 날짜를 검사해 400이어야 한다.
- Z10 page=85899346,size=50 및 Z11 INT_MAX 요청은 total111, items=[],hasNext=false를 반환한다.

**동시성·성능**

SQL 호출 수는 측정하되 요청 지연시간 합격선을 요구하지 않는다. 계획·인덱스 실측은 DB-14/9-2에서 다룬다.

**DB 관찰**

- 응답 JSON의 total/items/hasNext와 생성 SQL statement 수.
- LIKE %q% 형태는 보통 B-tree left-prefix 탐색에 맞지 않는다. R4는 대안 논의이며 현재 index가 검색을 가속한다고 주장하지 않는다.

**합격 기준**

- R2/R3 코드에서 predicate 재사용, tag EXISTS, 별도 count 구조를 확인한다.
- SQL 로그에 tag별 또는 필터 수에 비례한 추가 조회가 없다.
- 결과 및 상태 값이 각 Z 요청의 명시 기대와 맞는다.

**기존 과제와 중복·연결**

2-2/2-3/2-4는 목록 정책·재사용 visibility·N+1을 다룬다. 8-4는 그 조건들을 동적 필터 하나로 결합한다.
