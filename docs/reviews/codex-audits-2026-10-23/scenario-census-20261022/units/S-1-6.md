## 판정

토큰으로 author를 결정하고 만료/폐기/정지, 권한, body보다 인증 우선, preflight, sensitive SQL bind logging까지 함께 다룬 강한 인증 관문이다. 인터셉터와 주입 경계는 코드와 맞으며 11개의 HTTP cases와 DB SELECT 확인이 있다. API token의 정확한 문자 비교는 MySQL case-insensitive table collation 때문에 모호하고, HTTP auth-scheme casing은 RFC보다 좁게 검사한다. 실제 런타임 비교/브라우저 preflight는 재현하지 않았다.

## 목표·선수 지식·학습자 작업

로그인/토큰 발급은 구현하지 않고 기존 api_token row를 검증해 작성자를 클라이언트 body가 아니라 인증된 회원으로 정한다. 만료·폐기·정지 상태, 401/403, 인증 우선순위 및 브라우저 OPTIONS preflight 예외를 확인하는 중급 인증 관문이다. 1-5까지의 게시글 저장/권한/ProblemDetail 경로가 선수다.

토큰 조회 Entity/Repository, AuthInterceptor, Clock, AuthenticatedMember, @LoginMember ArgumentResolver, 예외 처리와 설정을 추가한다. 서비스 create는 authenticated member id를 받으며 body authorId를 사용하지 않는다. 배포형 token issuance/lifecycle은 이번 범위에서 구현하지 않는다.

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

**시작 상태**

seed token tok-lee, api_token.token 열의 collation, JPQL token 비교 및 AuthInterceptor의 인증 prefix 처리를 대조한다.

**학습자가 할 일**

격리 Testcontainers에서 `tok-lee`와 `TOK-LEE` 결과를 비교해 실제 DB collation을 고정하고, `Bearer`/`bearer` scheme 이름을 parser가 허용해야 하는지 HTTP contract와 대조한다.

**정상 사례**

- 정확한 토큰 + canonical Bearer로 user 3 인증
- header가 없는 protected POST는 401 + WWW-Authenticate

**실패·경계 사례**

- 철자/대소문자 변경된 credential은 같은 발급 token으로 오인되지 않도록 case-sensitive comparison
- 만료·폐기 token 401
- valid but suspended user 403

**동시성·성능**

**합격 기준**

테스트가 token string case semantics를 명시하고, case-sensitive header scheme handling은 RFC 9110과 상호운용하며 fixture AUTH cases를 유지한다.

**기존 과제와 중복·연결**
