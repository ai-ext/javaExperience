## 요구·구현·검사 대조

### 1. Post 2의 태그 행 spring(tag2),jpa(tag3)를 찾는다. `WHERE tag.name IN spring,jpa` JOIN은 post2를 두 번 낸다. DISTINCT는 selected columns 모두 같을 때 글 ID를 하나로 줄이고, 목록 API에서 글 행만 필요한 경우 correlated EXISTS는 글 단위 1행을 유지한다. 페이지 LIMIT는 multiplicative join 전에 두면 안 된다.

구현 대조: 이 문서는 SQL 개념 실습이며 앱 API 구현이나 DB 실측을 제공하지 않는다. seed post2에 post_tag (2,2)/(2,3)와 tag2=spring/tag3=jpa가 있다. 원문은 duplicate JOIN rows, DISTINCT projection tradeoff, EXISTS one post row 및 API의 tag loading 분리를 설명한다.

검사 대조: test-db04-focused-journey.mjs는 seed의 post2 및 두 tag 매핑 문자열, SQL 두 블록 보존, 7-panel 설명과 LIMIT 주의문을 확인한다. JOIN을 실행해 중복 결과를 세지 않는다.

공백 또는 한계: 자동 검사는 seed mapping과 문자열 보존까지다. 실제 row cardinality 및 LIMIT 전후 fanout은 learner DB 관측으로 확인한다. API에서 게시글 하나와 tag array를 반환하는 것은 M1/DB-01 연결 범위다.

## 확장 개발 명세

### post2 JOIN 중복과 EXISTS 행 단위 비교

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

실제 post2에 두 matching tag가 있어 join cardinality는 직접 확인 가능하다.

**시작 상태**

community seed 01-community.sql에서 post2 제목은 JPA 연관관계 매핑 정리다. post_tag는 (2,2),(2,3), tag 이름은 spring/jpa다.

**학습자가 할 일**

- 두 tag 이름으로 post_tag/tag를 JOIN해 post_id/title/tag name을 출력한다.
- post id/title/published_at만 선택한 SELECT DISTINCT와 EXISTS 결과를 비교한다.
- LIMIT 1 page query 뒤 tag JOIN을 해 게시글 집합과 tag 조합이 불완전해지는 사례를 확인한다. 필터 grain과 tag hydration grain을 구분한다.
- 기대 API 응답은 게시글 한 건과 tags 배열이지 게시글 응답 두 건이 아님을 명시한다.

**정상 사례**

- post-only DISTINCT 및 EXISTS는 post ID 2를 한 번 반환한다.

**실패·경계 사례**

- DISTINCT projection에 tag name을 추가하면 선택 행이 달라 두 행이 남는다.
- 두 tag JOIN 뒤 LIMIT 1을 적용하면 tag 배열이 일부만 나올 수 있다.
- SQL ID는 유일해도 게시글마다 tag query를 실행하면 M1 batch 요구를 만족하지 않는다.

**동시성·성능**

시간 benchmark는 없다. DB-12는 동등 query plan을 비교하고 DB-04는 결과 grain을 확인한다.

**DB 관찰**

- 원 JOIN 행 수=2, 고유 post 수=1, EXISTS 결과=post2 한 행.
- post-tag 결과 이름은 spring/jpa 두 개.

**합격 기준**

- 관측 행이 seed의 관계 tuple 두 개와 맞는다.
- 두 tag를 가져오면서 API 게시글 행은 중복되지 않는다.

**기존 과제와 중복·연결**

DB-01/M1은 page tags[]와 batch fetch를 요구한다. DB-04는 관계 cardinality, DB-12는 계획 비교를 다룬다.

**우선순위**

medium
