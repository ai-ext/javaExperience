## 목표·선수 지식·학습자 작업

새 검색창 GET /api/search/posts를 기존 8-4 조합 검색과 분리해 만든다. 요구는 공개 조건을 통과하는 글에서 단어마다 지정 범위의 제목/본문/작성자 닉네임 중 하나에 부분일치(AND of OR), LIKE wildcard literal 처리, 공개 규칙·안정 정렬·페이징을 한 결과/COUNT 쿼리에 반영하는 것이다. 선수는 2-3 viewability, 8-4 criteria 조립과 기존 pagination이다.

직접 작성: q normalization/길이/단어수, in/page/size의 다중 오류 수집, scope별 criteria predicate 생성, wildcard escaping과 바인딩, 목록과 COUNT의 같은 조건 및 안정 정렬, response mapping. 기존 8-4 endpoint와 schema는 바꾸지 않는다.

## 확장 개발 명세

### backslash literal 및 검색 가시성 자동 회귀

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

요구된 escaping 3종 중 backslash test와 privacy predicate 경계가 현재 checker에서 분리되지 않는다.

**시작 상태**

fixture에 PUBLIC 글 A(title=`100%_\dev`), FOLLOWERS 글 B(작성자 3), HIDDEN 글 C, deleted 글 D, 차단 관계를 가진 글 E를 만들고, 토큰 없는 사용자·팔로워·비팔로워/차단 사용자 조건을 준비한다.

**학습자가 할 일**

- `GET /api/search/posts?q=%25`와 `q=_`와 `q=\` 각각에서 문자 그대로 일치하는 A만 찾는지 검증한다.
- 같은 q를 in=title/content/author로 교차해 scope 밖 필드에서 나온 행이 포함되지 않는지 확인한다.
- 비로그인·팔로워·비팔로워가 각각 같은 query를 실행하고 status/deleted/follow/block 조건을 비교한다.

**정상 사례**

- literal wildcard/backslash query는 일치하는 공개 글만 반환한다.
- 두 단어 검색은 각 단어가 다른 허용 칸에 있어도 모두 충족할 때만 결과에 남는다.

**실패·경계 사례**

- escape가 빠지면 `%`/`_`가 과다 매칭하고, scope의 OR 괄호가 빠지면 hidden 또는 private 결과가 새는 반례를 보여야 한다.
- page/size/q/in을 동시에 잘못 보낸 경우 errors에 네 field가 모두 있고 DB query가 실행되지 않아야 한다.

**동시성·성능**

동일 입력의 COUNT와 content query 의미를 맞춘다. 실제 쿼리 성능 주장은 하지 않고 DB-14에서 별도 fixture/EXPLAIN으로 측정한다.

**DB 관찰**

C1/D1처럼 공개 대상 결과의 count와 API totalElements를 비교하고, 제외 상태의 row는 search와 count 모두에서 빠져야 한다.

**합격 기준**

정확한 id set·totalElements·status/error fields가 expected와 일치; invalid request는 400/DB 결과 변화 없음; 8-4 endpoint 응답은 회귀 없이 동일.

**기존 과제와 중복·연결**

L12 Q05는 단일 제목 LIKE 연습, DB-14는 실제 plan 관찰. 이 expansion은 별도 사용자 검색 endpoint의 literal escaping/viewability regression만 보강한다.

**우선순위**

low
