## 확장 개발 명세

### 실제 DDL부터 결과 동등성 및 인덱스 정리

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

학습자가 먼저 DB schema를 확인해 요구를 SQL에 옮기고, query/plan를 측정한 뒤 same rows를 보존하며 index lifecycle을 완료한다.

**시작 상태**

tools/db-perf-fixture.sh up/status만 사용해 disposable javaexperience_perf port13319를 확인한다. practice/community/app DB에 DDL을 실행하지 않는다. fixture 기본은 board/member/post와 좋아요 500,000행이다.

**학습자가 할 일**

- SELECT DATABASE(), VERSION(), SHOW TABLES, SHOW CREATE TABLE board/member/post 및 information_schema의 columns/statistics/FK를 기록한다.
- board-03과 실제 ID를 찾는다. PUBLISHED/deleted-null 조건 및 board/member JOIN을 유도하고 visibility는 이 query 범위 밖임을 적는다.
- 기준 query의 행/ID와 index 전 EXPLAIN 및 EXPLAIN ANALYZE를 기록한다.
- 현재 index를 확인한다. 후보가 없을 때만 복합 index를 만들고 ANALYZE TABLE 뒤 열 순서를 확인한다.
- 동일 tuple query와 계획을 다시 실행하고 전후 결과 행/순서가 같은지 비교한다.
- 실험용으로 만든 후보 index만 DROP/ANALYZE TABLE하고 SHOW INDEX 및 query로 baseline 복구를 확인한다.

**정상 사례**

- 설정된 fixture에서 board-03은 board id3이다. 기본 20,000 post 생성은 20개 board에 분배되어 필터 전 후보가 1,000건이다.
- 과거 한 번의 기록에서 첫 5 ID는 전/후 모두 [19983,19963,19943,19923,19903]이었다. 이는 참고 관측이지 현재 실행의 고정 합격값은 아니다.

**실패·경계 사례**

- schema가 다르거나 table이 없으면 임의 DB에 migration하지 말고 fixture 버전을 확인한다.
- 후보 index 이름이 이미 있으면 중복 생성하지 않는다.
- index 변경 뒤 결과 행/순서가 바뀌면 query/data 계약 변경 원인을 확인하고 최적화 성공으로 간주하지 않는다.

**동시성·성능**

EXPLAIN estimates와 EXPLAIN ANALYZE actual rows/loops/time을 분리한다. 벽시계 합격 기준은 없다. 12.4/.44ms는 이전 단일 실행 값이다.

**DB 관찰**

- 실제 schema metadata, board ID, FK/index 정의.
- 동일 query의 전후 결과 tuple/ID/hash, 계획 추정값 및 실제 iterator 관측.

**합격 기준**

- 전후 SQL 결과가 동일하며 실험 후보 index 외 baseline index가 그대로다.
- 복구 뒤 index 목록/query를 다시 확인하고 작업 후 disposable fixture를 중단한다.

**기존 과제와 중복·연결**

DB-01/03은 응답/schema/JOIN, DB-08/09는 plan, DB-10은 좋아요 index, DB-14는 live schema 조사와 board 목록 index를 다룬다.

**우선순위**

high
