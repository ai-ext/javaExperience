## 목표·선수 지식·학습자 작업

목록 조건에 정렬·limit·offset/cursor 경계를 더하고 tie를 안정화한다. 기초: published_at DESC,id DESC 및 size+1/두 키 커서를 예시로 둔다. offset 삽입 변화는 가상 비교.

## 요구·구현·검사 대조

### 1. DB-01 목록 조건을 유지하고 size=2 다음 페이지를 `(published_at,id)` 복합 커서 뒤로 이어 읽는다. order는 DESC,DESC이므로 strict `<` lexicographic condition; 다음 cursor는 이전 응답의 마지막 id144의 `(2026-10-02 21:57:53,144)`. hasNext 위해 LIMIT size+1=3, 응답에서 세 번째 제거.

## 확장 개발 명세

### 두 키 cursor와 size+1 결과 확인

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

published_at만 cursor로 쓰면 같은 시각 행을 건너뛰거나 반복할 수 있다.

**시작 상태**

DB-01 seed의 page size2는 [145,144]다. 다음 요청 cursor 경계는 마지막 반환 행 post144의 published_at=2026-10-02 21:57:53이다.

**학습자가 할 일**

- 두 key cursor 조건을 쓴다: published_at < post144 시각 OR 같은 시각 AND id < 144.
- 첫 페이지 [145,144], 다음 페이지, size+1 probe 행을 각각 실행하고 응답 순서를 기록한다.
- published_at이 같은 두 행을 격리 fixture에 두고 페이지를 나눠 ID 누락/중복을 확인한다.
- 페이지 경계 앞에 새 행을 넣어 offset 방식과 cursor 결과를 비교한다.

**정상 사례**

- 세 번째 probe는 hasNext 여부만 결정하고 응답 items에는 들어가지 않는다.

**실패·경계 사례**

- cursor가 없으면 첫 페이지를 반환하고 NULL 비교를 하지 않는다.
- ORDER BY나 cursor predicate에서 id를 빼면 timestamp 동률에서 행을 건너뛰거나 반복한다.
- 첫 페이지 마지막 반환 ID 144 대신 ID145를 cursor로 쓰면 잘못된 다음 경계가 된다.

**동시성·성능**

앞쪽에 새 행이 생길 때 cursor 경계가 유지되는지 확인한다. lock/isolation 성능 실험은 요구하지 않는다.

**DB 관찰**

- 첫 페이지/다음 페이지/probe의 실제 ID, 정렬 key와 hasNext.
- 경계 앞 삽입 뒤 offset과 cursor의 결과 ID.

**합격 기준**

- 두 번째 페이지가 [143,140]이고 probe 행은 응답 body에서 빠진다.
- 동일 timestamp fixture에서 모든 행이 페이지마다 한 번씩만 나온다.

**기존 과제와 중복·연결**

DB-01은 첫 페이지 mapping, M1은 전체 API cursor 계약, DB-10은 이후 index 측정이다.

**우선순위**

medium
