## 확장 개발 명세

### 격리 fixture 전후 결과·계획 증거 기록

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

이 실습의 합격은 ID 순서가 같다는 정확성 gate 뒤에 계획 및 actual work 차이가 실제로 관찰됐는지 기록하는 것이다.

**시작 상태**

`tools/db-perf-fixture.sh up`은 이미 실행 중인 전용 컨테이너를 재생성하지 않으므로 먼저 status와 `SHOW INDEX FROM post_like`를 본다. 목적 DB는 `127.0.0.1:13319/javaexperience_perf`; 기존 practice/community DB를 사용하지 않는다. 기본은 500,000 rows, 자료의 과거 확인 사례는 별도 100,000 rows다.

**학습자가 할 일**

- 회원 12 row count와 최초 11개 `id,post_id,created_at`를 기록한다.
- 원문 WHERE member_id=12, ORDER BY created_at DESC,id DESC,LIMIT 11에 대해 EXPLAIN의 key/rows/Extra와 EXPLAIN ANALYZE의 actual rows/loops/time을 기록한다.
- 없을 때만 `ix_post_like_member_created(member_id,created_at,id)`를 만들고 ANALYZE TABLE 후 같은 두 명령을 반복한다.
- 전후 ID 배열을 정렬 변경 없이 비교하고, plan 변화가 없으면 변화 없음으로 기록한다.
- 마지막에 인덱스를 원래 상태로 복원하거나 전용 컨테이너 reset/down으로 제거한다.

**정상 사례**

- fixture 기본 500,000행에서 member 12는 2%=10,000 좋아요다(대상 행 수 500,000으로 생성한 경우). ID 순서 비교는 실제 select 결과에서 한다.
- 문서의 100,000행 observation은 member 12=2,000, 선행 key `uq_post_like_member_post`와 filesort, 생성 후 복합 index backward scan 및 첫 5 `(post_id,created_at)` 순서 동일이다. 이를 현재 실행의 기대 정답으로 복사하지 않는다.

**실패·경계 사례**

- 같은 이름 복합 인덱스가 이미 있으면 CREATE를 반복하지 않고 현재 상태를 먼저 기록한다.
- ID 순서가 바뀌면 성능 향상으로 간주하지 말고 조건/정렬/fixture 상태 오류로 조사한다.
- EXPLAIN ANALYZE는 SELECT를 실제 실행하므로 이 읽기 쿼리만 전용 fixture에서 실행한다.

**동시성·성능**

실제 member 12 cardinality·plan·actual rows/loops와 같은 실행 조건을 기록한다. wall-clock 1회만으로 통과 처리하지 않는다. 500k 기본/100k 과거 사례를 분리한다.

**DB 관찰**

- row count는 fixture 초기화 출력과 SELECT COUNT(*)가 같은지 확인한다.
- 전후 ID와 순서, key, rows, Extra, TREE actual rows/loops/time를 기록한다.
- practice DB와 앱 전체 join API가 측정 범위가 아님을 표시한다.

**합격 기준**

- 전후 SQL이 동일하고 두 결과의 11개 ID 순서가 완전히 같다.
- 전후 plan과 actual TREE 기록이 있으며 관측 차이가 없으면 없음으로 명시한다.
- fixture만 수정했고 종료 후 전용 인덱스/컨테이너 상태를 복원했다.

**기존 과제와 중복·연결**

DB-08은 가설/추정, DB-09는 EXPLAIN ANALYZE, DB-11은 invisible/restore/drop을 담당한다. DB-10에서 해당 lifecycle 전부를 강제하지 않는다.

**우선순위**
