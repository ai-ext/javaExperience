## 판정

정적 대조에서 run 기록/본문 트랜잭션 분리, 최신 FAILED 날짜 선정, GET_LOCK 재시도 선점, referenceAt/runId 보존, 권한/검증은 설계와 일치한다. 다만 crash로 남은 RUNNING의 복구가 없고, named-lock connection을 작업 동안 점유하는 구조는 pool 용량에 좌우되므로 운영 stress 검증이 필요하다.

## 목표·선수 지식·학습자 작업

모든 앞선 batch의 실행/실패 기록과 operator retry를 공통 runner로 통합한다. 기록 저장은 본문 트랜잭션과 분리해 FAILED가 롤백되지 않게 하고, job/date별 마지막 상태가 FAILED인 날만 재시도하며, 실행 사이 idempotency와 referenceAt 보존을 보장한다. 선수는 15-1~15-5 배치별 실패/중복 의미, MySQL 트랜잭션, 관리자 권한, connection-level lock이다.

V65 job_run schema와 practice 실패 seed를 준비하고 JobCatalog→JobLauncher→JobRunner를 통해 수동/예약/retry 경로를 하나로 묶는다. RUNNING→SUCCESS(processed)/FAILED(error) 기록을 본문 transaction 밖에서 저장하고 입력 검증을 기록 전 실행한다. 빈 scheduled run은 생략하고 실패일 재실행은 GET_LOCK 및 마지막 상태 재조회로 선점한다. 목록 필터/재시도 API 권한, 각 retry의 referenceAt/runId, 이후 실제 본문 idempotency를 확인한다.

## 부족한 점

## 확장 개발 명세

### 중복 retry·RUNNING orphan·pool 고갈과 실패 복구 운영 검증

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

원문의 named-lock과 실행기 상태가 프로세스/connection pool 실제 조건에서 안전한지 재현하고 복구 규칙을 결정한다.

**시작 상태**

격리 MySQL과 명시적으로 작은 Hikari pool(예: maximumPoolSize=2)에 실패한 job/date row를 두고, 테스트 batch는 별도 repository connection을 요구하게 구성한다. 다른 job/date도 준비한다.

**학습자가 할 일**

- 동일 job/date retry 두 요청을 barrier로 겹치고 하나만 batch 본문에 들어가는지, loser 응답이 빈 목록인지 검사
- lock connection 점유 후 본문 DB connection 확보가 가능한 최소 pool 경계를 찾아 timeout/대기 상황을 관찰
- JVM 강제 종료/RUNNING 중단을 재현해 orphan row가 retry 대상이 되지 않는 현 상태를 확인하고 lease/heartbeat/운영자 stale 판정 정책을 설계
- 본문 transaction rollback 뒤 FAILED row가 남는지, 다음 날짜 retry는 계속되는지 검증
- 0건이 아닌 지속 실패가 1시간/1일 유지될 때 job_run growth/error redaction/retention 기준 설정

**정상 사례**

- 한 날짜만 하나의 runner가 실행하고 자신의 runId 상태를 반환한다.
- 마지막 상태가 SUCCESS인 날짜는 이전 FAILED가 있어도 건너뛴다.
- 재시도는 scheduled-publish의 원래 referenceAt을 그대로 전달한다.

**실패·경계 사례**

- batch RuntimeException은 본문 변경 rollback + FAILED row commit + 다음 날짜 계속 실행을 만족한다.
- 실행 중 프로세스 종료 시 stale RUNNING을 식별하고 중복 실행 위험을 검토한 후 명시적 recovery path가 복구한다.
- small pool에서 retry가 lock connection을 점유해 batch가 무한대기하지 않거나, 제한 시간 내 명확한 실패/해제 경로로 종료한다.

**동시성·성능**

same job/date와 다른 date/job을 각각 겹쳐 lock key 범위를 측정한다. Hikari active/idle/pending, GET_LOCK 결과, transaction connection 수, 대기 및 retry 지연을 기록한다.

**DB 관찰**

job_run의 id/status/trigger/reference_at/processed/error/시간, active named lock, 본문 테이블 rollback/commit을 관찰한다. 운영 오류 내용은 민감값을 마스킹한다.

**합격 기준**

중복 본문 실행 0, 성공 복구 날짜 재시도 0, 실패 기록 지속, 정상 pool에서 교착 없음, orphan RUNNING의 식별/복구 책임자·기준이 문서화되고 자동 검사된다.

**기존 과제와 중복·연결**

C1~C9/D1~D4/R1~R5를 이 통합 재현에 확장한다. 15-1~15-5 business idempotency를 대체하지 않고 전제조건으로 검사한다.
