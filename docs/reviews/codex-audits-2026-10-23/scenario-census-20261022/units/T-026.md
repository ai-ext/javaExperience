## 판정

입력 재전송, payload mismatch, 동시 요청, 회원 scope, 제약과 RR 함정이 구체적이다. retention/body replay는 열린 제품 결정을 정답 요구로 오판하지 않고 명시해야 한다.

## 목표·선수 지식·학습자 작업

요청 timeout 뒤 client retry가 같은 회원·같은 idempotency key라면 기존 글 결과를 재사용하고 중복 글을 만들지 않는다. 첫 요청 동시 경합과 MySQL REPEATABLE READ 읽기 시점이 핵심이다.

Idempotency-Key와 `(member_id,key)` UNIQUE, request payload hash 및 생성 글/응답 참조를 설계한다. 같은 payload replay, 다른 payload 422, 동시 첫 요청, 회원 간 key scope, key/post atomicity와 보존기간을 결정한다.

## 이번 실행 근거

이번 단위 전체를 별도 실행하지 않았다. 문서의 기존 실행 예시·코드·검사 정의를 대조한 결과와 다른 단계의 실행 증거를 구분한다.

## 쿼리·DB 깊이와 다음 단계

- content: 회원+key 복합 UNIQUE가 중복 생성의 권위 있는 제약이다. 키 row와 post는 한 transaction으로 묶어 실패하면 둘 다 rollback해야 한다. REPEATABLE READ 재조회는 locking/current read 또는 새 transaction이 필요할 수 있다.
- current_scope: 티켓 원문 전체의 시작조건, 직접 구현 업무, 채점·실험 방법을 대조했다. 정답 코드 snapshot 없음.
- missing_scope: 키 보존 기간, 어떤 실패 응답에 key를 남기는지, 원 응답 body 전체 replay 또는 post id 재조회 방식이 결정되어 있지 않다. 동시 loser가 처음 transaction commit 후 값을 어떤 read로 보게 할지도 구현 선택에 남는다.
- existing_connections: 선수/후속/겹치는 영역: S08 transaction isolation; T-018 unique insert race; S06 idempotency/network retries. 기존 단위와 겹치면 신규 기능을 발명하지 않고 reuse/regression으로 연결한다.

- 현재 난이도: 상+ — 사용자별 범위, payload 충돌, 요청 직렬화, transaction 원자성, 응답 재생과 키 보존 문제를 함께 다룬다.
- 판정 이유: HTTP 재전송만 막는 것이 아니라 성공 요청인지 payload conflict인지 저장소가 판정하고 concurrent first-use에서 한 결과만 노출해야 한다.

  - T-018 unique insert race
  - S06 idempotency/network retries
