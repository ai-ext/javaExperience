## 판정

정적 구현은 TTL과 키·불변 snapshot, commit 후 세대 무효화 및 주요 status 경로를 명세와 맞춘다. 단일 JVM 동시 GET 재채움 위험을 generation으로 처리하고 multi-node 한계도 원문에 명시돼 있다. 실제 barrier·multi-node·heap 검증은 미실행이다.

## 목표·선수 지식·학습자 작업

8-2 인기글 점수/조회 쿼리를 days·limit별 60초 cache로 재사용하되 게시글 공개 상태가 바뀌면 즉시 숨겨진 글을 다시 노출하지 않는다. 선수는 Cacheable/immutable 결과, TTL, AFTER_COMMIT, transaction synchronization, 다중 JVM cache consistency다. 다음 16-4 외부 링크 HTTP/timeout은 캐시와 별도 부수효과다.

Caffeine maximumSize 100/expireAfterWrite 60s, immutable snapshot and logical key (days,limit,generation)으로 인기 응답을 캐시한다. HIT/MISS X-Cache·CORS expose를 구현한다. 공개 여부에 영향 주는 수정/삭제/숨김/복구/예약 발행 성공에서 commit 뒤 generation을 올리고 cache를 비운다. 점수만 바뀌는 좋아요·댓글과 0건/rollback은 TTL을 유지한다. GET/수정 경합과 multi-node 한계를 설명한다.

## 확장 개발 명세

### 지연 GET·상태변경 race와 다중 서버 일관성 실험

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

generation이 옛 결과 재삽입을 막는지 barrier로 입증하고 로컬 cache/version의 수평 확장 한계를 실제 stale window로 설명한다.

**시작 상태**

테스트용 cache manager에 인기글을 채우고 글 A를 PUBLIC으로 둔다. PostRepository query를 latch로 지연시켜 GET이 old generation key 계산 뒤 DB 결과를 읽는 중이 되게 한다.

**학습자가 할 일**

- GET을 중지시킨 동안 moderation hide/delete를 commit하고 generation/cache clear 후 GET을 풀어준다
- 다음 GET의 X-Cache/응답에 A가 없고 이전 generation key만 남는지 확인
- 서버 인스턴스 두 개에 별도 PopularCacheVersion/CacheManager를 두고 한 곳의 hide 후 다른 곳의 stale 응답 기간 측정
- direct SQL mutation이 무효화 callback을 통과하지 않는 조건과 Caffeine TTL 종료 후 회복을 비교
- 100개 max size를 초과하는 cache key와 동시 cold miss를 만들어 eviction/query stampede/heap을 측정

**정상 사례**

- 수정된 세대에서 숨김/삭제 글은 즉시 사라지고 다음 동일 요청은 HIT한다.
- 실패한 patch·rollback·예약 0건은 generation을 증가시키지 않는다.

**실패·경계 사례**

- 지연 old GET이 커밋 이후 완료돼도 최신 key에서 예전 공개 글이 재사용되지 않는다.
- 두 노드에서 invalidation 전파가 없으면 다른 노드가 TTL 내 stale 결과를 보이는 조건이 재현된다.

**동시성·성능**

single JVM barrier 테스트와 두 JVM/공유 Redis pub-sub 대안을 비교한다. mutation 후 각 node stale duration, cache hit/query count, eviction, p95를 기록한다.

**DB 관찰**

DB의 status/visibility/deleted_at, cache generation 값, key별 응답 item, query execute 여부, X-Cache를 비교한다.

**합격 기준**

단일 JVM은 commit 이후 이후 요청에서 stale item 0이며, multi-node는 공유 invalidation/TTL/일관성 정책을 명시하고 검증한다. 성능 tradeoff는 데이터·인스턴스·TTL과 함께 측정한다.

**기존 과제와 중복·연결**

C1~C7/R1~R4를 race·multi-node 조건으로 확장한다. 새 인기 점수/인덱스를 임의로 바꾸지 않는다.

**우선순위**
