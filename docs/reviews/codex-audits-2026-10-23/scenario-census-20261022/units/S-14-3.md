## 확장 개발 명세

### 서로 다른 pin 동시 요청에서 board별 hard cap 유지

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

count-then-insert는 원문이 밝힌 경쟁에서 최대치를 보장하지 않는다. 세 개가 반드시 상한인지 제품 요구를 확인한다.

**시작 상태**

board 4에 pin 2개가 있고 두 admin이 서로 다른 공개 게시글을 동시에 pin하려 한다.

**학습자가 할 일**

- 두 PUT을 barrier로 동시에 보내 응답/최종 DB row/list count를 확인한다.
- board row lock 또는 3개 quota slot 모델을 설계해 기존 count-then-insert와 비교한다.
- 같은 post를 두 번 요청해 기존 멱등 성공은 유지한다.

**정상 사례**

- 순차 세 번째 pin 성공, 동일 글 반복은 row 하나, 순차 네 번째는 400.

**실패·경계 사례**

- hard cap 정책 선택 시 서로 다른 동시 요청으로도 3개 초과가 없고 loser 요청의 partial row가 없다.
- 숨김/삭제된 pinned 글은 출력에서 제외되나 명시 unpin 전까지 slot을 차지한다.

**동시성·성능**

독립 admin 두 transaction을 겹쳐 lock wait와 최종 count를 측정한다.

**DB 관찰**

SELECT board_id,post_id,created_at and count before/after; verify uniqueness and cap.

**합격 기준**

hard cap을 택하면 경합 후에도 최대 3, 같은 글 중복은 멱등이다.

**기존 과제와 중복·연결**

C11은 same-post unique race만 증명한다. 이 확장은 명시된 different-post count race만 다루며 목록/visibility 기능을 바꾸지 않는다.
