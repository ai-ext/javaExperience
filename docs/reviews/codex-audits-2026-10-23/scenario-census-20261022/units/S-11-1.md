## 확장 개발 명세

### 동시 publish와 상태 단일 전이 회귀 검사

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

서비스가 row lock으로 동시 호출을 직렬화한다고 설명하지만 채점 기준은 순차 호출만 한다. 구현 선택의 효력을 실제 동시 실행으로 확인한다.

**시작 상태**

clean community fixture에서 `tok-kimjava`가 자유 게시판에 `status=DRAFT` 글 1개를 만들고 id를 기록한다. 기존 DRAFT를 준비 API로 만들 수 없으면 POST /api/posts 요청으로 준비한다.

**학습자가 할 일**

- 두 worker가 동일 id에 `POST /api/posts/{id}/publish`를 barrier로 동시에 보낸다.
- 각 응답 상태·본문 status/publishedAt을 기록하고, 요청 시작/완료 시각을 함께 남긴다.
- SELECT id,status,published_at,updated_at FROM post WHERE id=:id로 한 행의 최종 상태를 확인한다.

**정상 사례**

- 동시 요청 2개에서 한 요청은 200 PUBLISHED, 대기 요청은 commit 이후 409를 받는다.
- 그 후 GET /api/posts/{id}는 PUBLISHED 상세를 반환하고, GET /api/me/drafts에서 id는 빠진다.

**실패·경계 사례**

- 같은 id를 다른 회원이 발행하면 404로 존재를 감추고, 조회 가능한 타인 공개 글이면 403, 이미 발행된 글이면 409여야 한다.
- 첫 요청이 rollback되도록 테스트 전용 실패 지점을 두면 후속 요청은 DRAFT에서 발행 가능해야 하며 중간 상태가 남지 않아야 한다.

**동시성·성능**

동시 2요청을 barrier로 재현하고 2xx가 두 번 나오는지 확인한다. 잠금이 걸린 요청의 순서를 로그로 확인하되 처리 시간 성능 주장은 하지 않는다.

**DB 관찰**

최종 행은 하나, status=PUBLISHED이며 published_at/updated_at이 채워진다. PUBLISHED 전환 외 컬럼이 바뀌지 않는지 업데이트 전후를 비교한다.

**합격 기준**

응답 집합이 정확히 {200,409}; 최종 상태 PUBLISHED; draft 목록에서 제거; 게시글 행은 한 개; 오류/rollback 경우 DRAFT 원상태.

**기존 과제와 중복·연결**

T-017/T-023/T-025는 별도 동시 업데이트 결함이며 이 publish 상태 경합과 중복으로 세지 않는다. S-15-3은 예약 발행의 batch 경쟁을 후속 비교한다.

**우선순위**

medium
