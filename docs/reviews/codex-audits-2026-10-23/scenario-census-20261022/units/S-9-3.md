## 판정

Migration·Entity·조회 경로가 excerpt 규칙에 맞는다. 요청 checker는 101자/null/공백 변경을 검사하지만 기존 전체 seed backfill과 schema 값은 수동 acceptance이며 대형 backfill batching은 확장 검토다.

## 목표·선수 지식·학습자 작업

운영 중인 테이블에 새 컬럼을 추가하고 기존 행을 backfill해 새 응답/코드에 연결한다. 선수 단계와 DB 구분은 scenario/README.md 기준으로 확인한다.

nullable/additive migration, 채움, 이후 제약 강화를 따라간다. 배치 크기/재실행/중간 실패, dual-read/write 호환 기간, 미완료 행 탐지가 체크 기준에 포함되는지 확인한다.

## 요구·구현·검사 대조

### 1. V3는 excerpt VARCHAR(120) NULL을 추가하고 기존 글에 LEFT(content,100)을 backfill한 뒤 NOT NULL로 바꾼다. 새 글/수정 글도 첫 100 Unicode code point로 excerpt를 유지하며 목록/검색은 content 대신 excerpt를 반환한다.

구현 대조: Migration은 nullable 추가→전체 행 backfill→NOT NULL 변경 순서다. Entity excerptOf는 Unicode code point 기준으로 자르고 생성/changeContent에서 호출된다. 검색 DTO는 excerpt를 선택하고 content는 제외한다.

검사 대조: 요청 checker는 A1 세 게시글 excerpt 길이<=100, A2 생성, B1 101자 PATCH 후 B2 앞 100자, A3 짧은 수정, V1 null 유지 200, V2 공백 400, V3 짧은 excerpt 보존을 검사한다. 수동 D1~D3는 schema와 기존 행 backfill을 확인한다.

공백 또는 한계: 자동 요청 검사는 새 글/수정 경계를 다루지만 기존 행 전체 backfill과 NOT NULL schema는 수동 D1~D3에 남는다. 대형 테이블 batching/resume은 이 145행 실습 구현 범위가 아니다.

## 확장 개발 명세

### excerpt nullable 추가·backfill·NOT NULL 및 쓰기 경계 확인

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

배포 전후 migration 순서와 애플리케이션의 입력 경로 모두 동일한 excerpt 규칙을 지켜야 한다.

**시작 상태**

V2 practice schema의 게시글 145개와 긴 본문 post124를 사용한다. V3는 migration 이력이 있는 disposable 또는 지정 learner DB에만 적용한다.

**학습자가 할 일**

- V3 순서가 nullable 열 추가→LEFT(content,100) 전체 행 backfill→NOT NULL 변경인지 확인한다.
- D1에서 excerpt가 VARCHAR(120) NOT NULL인지, D2에서 LEFT(content,100)과 다른 행 수가 0인지 확인한다.
- post124 본문과 excerpt를 비교하고 150자 본문 생성, 101자 PATCH 뒤 목록 100자 excerpt를 확인한다. 짧은 본문, null, 공백 PATCH도 실행한다.
- 각 변경 전후 excerpt를 대조하고 목록 SELECT에는 excerpt만 있고 긴 content는 없는지 확인한다.
- 수백만 행 환경에서 필요한 batching/checkpoint, 재시작, 구버전과 동시 실행 시 write 호환성을 설명하되 이번 145행 실습에서 측정한 값과 혼동하지 않는다.

**정상 사례**

- 짧은 PATCH는 excerpt를 갱신하고 null PATCH는 기존 본문/excerpt를 유지하며 공백은 400으로 거절된다.

**실패·경계 사례**

- backfill 전에 NOT NULL을 적용하면 기존 NULL 행에서 실패한다.
- null PATCH가 excerpt를 NULL로 만들거나 서버 오류 500을 반환하면 안 된다.
- 문자열 자르기가 Unicode code point 중간을 분리하면 실패다.

**동시성·성능**

현재 fixture는 145행이며 한 번의 집합 UPDATE다. 수백만 행의 lock/duration, PK 범위 batching, 진행률·재시작, expand-contract 호환성은 별도 설계·측정 대상이며 이 단위는 성능 결과를 주장하지 않는다.

**DB 관찰**

- 전체 행 수와 excerpt 불일치 수, post124 값.
- 생성/PATCH/null/공백 각 요청의 status 및 본문/excerpt 전후 값.
- 목록 SELECT의 투영 열 목록과 긴 content 비포함 여부.

**합격 기준**

- D1 schema 및 D2 불일치 0을 확인한다.
- 생성/101자 PATCH/짧은 PATCH/null/공백의 응답과 excerpt가 계약에 맞는다.
- 목록 응답에는 excerpt가 포함되고 긴 content가 빠진다.
- 소규모 one-shot UPDATE와 대규모 대안 설계를 구분한다.

**기존 과제와 중복·연결**

S9-1은 기준선, S9-5는 expand-contract를 다룬다. MISSION/API 쓰기 검증 규칙과 연결한다.

**우선순위**

medium
