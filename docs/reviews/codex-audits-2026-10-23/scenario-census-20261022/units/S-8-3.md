### 관계 결과와 양방향 차단 인덱스 근거 확인

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

정답 행은 seed 기대값과 자동 check가 구체적이다. 심화 가치는 각 쿼리의 반대 방향 인덱스 접근과 recommendation rank가 데이터에서 도출되는지 직접 설명하는 데 있다.

**시작 상태**

8-3 snapshot의 community seed; 회원 2 mutual/follow-back, 회원 7 recommendation fixture.

**학습자가 할 일**

- F1/F2/F3/F4/F6/F7 결과를 각 명세된 ID 배열/튜플, status와 대조한다.
- F3 각 후보를 만든 f1→f2 경로 수가 mutualCount 3/3/2/1/1인 이유를 follow 행과 대조한다.
- 회원 7과 후보 3,10,11,13,17의 차단 방향 양쪽, ACTIVE status, 이미 팔로우 여부를 검사한다.
- EXPLAIN으로 follow 방향 `(follower_id,followee_id)` 및 역방향 `(followee_id,follower_id)` key를 보고 실제 선택을 기록한다.

**정상 사례**

- 회원 2 mutuals [3,4], 회원4 mutuals [2,5,19].
- 회원2 follow-back [8,9,11,12,15,16,20,21,22,24,27]; suspended 28/withdrawn 29 제외.
- 회원7 suggestions limit=5 ID [3,10,11,13,17], mutualCount [3,3,2,1,1].

**실패·경계 사례**

- 요청 없이 follow-back/suggestions는 status 401.
- `limit=` 빈 값, 0, 21, `abc`는 400. 생략은 5, 1과 20은 허용.

**동시성·성능**

이 read-only 관계 쿼리에서 동시성 요구 없음. 기존 행 수와 동일 DB에서 EXPLAIN만 검토한다.

**DB 관찰**

- 세 쿼리의 index/key 및 rows 추정값. 예상/실제 비용을 혼동하지 않는다.

**합격 기준**

- C1-C6의 원문 결과 모두 일치.
- 회원7 recommendation 경로 count와 동률 id ordering 설명.
