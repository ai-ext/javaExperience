## 판정

정적 구현은 이름 있는 전용 pool, AFTER_COMMIT async fanout, sender 밖의 짧은 DB transaction, 회원별 결과와 계속 진행을 구현한다. 정상 지연/실패 채점도 구체적이다. 그러나 외부 전송 성공과 SENT 저장 실패의 경계, pool 포화 CallerRuns, 종료 후 NULL 복구가 중요한 운영 한계라 조건부 고위험으로 후속 재현이 필요하다.

## 목표·선수 지식·학습자 작업

16-1의 커밋 후 팔로워 알림 생성에 실제 느린/실패하는 외부 전송을 붙여 글쓰기 요청의 응답 지연·커넥션 점유·회원별 실패 격리를 측정한다. 선수는 AFTER_COMMIT/REQUIRES_NEW, ThreadPoolExecutor 포화·거절 정책, 트랜잭션과 외부 부수효과 구분이다. 다음 16-3 인기글 cache는 조회 경로의 캐시 일관성을 다룬다.

V71 notification.push_status NULL/SENT/FAILED를 두고 notificationExecutor core 2/max 4/queue 100/CallerRunsPolicy 및 종료 대기를 설정한다. async AFTER_COMMIT listener에서 수신자 id를 얻은 뒤 느린 FakePushSender를 transaction 밖에서 호출하고 각각의 결과는 짧은 REQUIRES_NEW로 기록한다. delay/fail input과 풀 saturation, API Server-Timing, DB status 진행 및 shutdown 유실을 관찰한다.

## 요구·구현·검사 대조

### 1. 새 글 AFTER_COMMIT listener는 notificationExecutor에서 실행하여 POST 응답이 회원별 느린 push를 기다리지 않게 한다. 전용 pool은 크기·큐·거절 정책·thread name·shutdown wait를 명시한다.

구현 대조: 구현 일치: @Async(notificationExecutor)+AFTER_COMMIT, executor core 2/max 4/queue 100/CallerRunsPolicy/notify- prefix/10초 종료 대기. 큐 포화 시 CallerRuns 때문에 요청 스레드에서 느려질 수 있다는 tradeoff를 원문이 밝힌다.

검사 대조: C3은 15명×150ms에도 응답 Server-Timing 1000ms 미만, D1은 2초 안 NULL status가 섞이는 관찰 기준, C5는 동기/비동기 시간 비교를 요구한다. D1은 늦게 실행하면 사라질 수 있다고 선택 항목으로 제한한다.

공백 또는 한계: 정상 큐 상황은 구체적 검사가 있다. 포화 상태에서는 CallerRuns가 요청 응답을 block하는 조건이 의도되어 있어 항상 빠르다는 주장으로 확대할 수 없다.

## 확장 개발 명세

### 풀 포화·전송 성공/상태 저장 실패·shutdown 복구 실험

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

응답 지연, worker 용량, DB status와 외부 전송 결과가 갈라지는 조건을 재현해 운영/전달 보장 선택을 명시한다.

**시작 상태**

통합 테스트에서 follower 150명, delay 500ms, fail 1명, notificationExecutor 큐를 빠르게 포화시키는 동시 publish 요청을 구성한다. push sender와 repository mark update에 독립적인 fault injection을 둔다.

**학습자가 할 일**

- 정상 15명과 150명에서 app Server-Timing, executor active/queue/rejected, DB active connection을 수집
- queue를 100 초과시키 CallerRuns 동작 때 응답 스레드가 직접 처리하는지 확인
- sender 성공 후 markPush(SENT) 실패를 주입하고 실제 external send count와 DB status를 비교
- FAILED 기록 DB도 실패시키고 다음 follower가 계속 처리되는지 확인
- SIGTERM 10초 대기와 강제 kill을 각각 수행해 남은 NULL row 및 재시작 시 재처리 정책을 확인
- durable 전달이 필요하면 outbox 상태 NEW/IN_PROGRESS/SENT/FAILED, lease expiry, retry attempt, idempotency key를 설계

**정상 사례**

- 정상 큐에서는 글 POST가 1초 미만으로 끝나고 worker가 각 결과를 기록한다.
- 한 사용자 sender 실패는 FAILED로 기록되고 다른 사용자에게 계속 전송한다.

**실패·경계 사례**

- mark SENT 실패는 sender 전송 실패와 다른 상태/metric으로 식별된다.
- process kill 후 미처리 job은 손실/중복 여부가 정책으로 정의되고 lease timeout 후 회복된다.
- 큐가 포화되었을 때 호출 스레드 지연 또는 rejection 결과가 명시적인 관측으로 드러난다.

**동시성·성능**

스레드 2/4, 큐 100, 동시 요청 수 1/10/50을 조합해 p50/p95, task completion, pool/DB wait를 측정하고 과부하 시 backpressure를 평가한다.

**DB 관찰**

push_status별 NULL/SENT/FAILED, 각 member_id/post_id, 시작/완료 시각, executor queue·DB connection·sender 실제 횟수를 맞춘다.

**합격 기준**

각 수신자마다 외부 발송 결과와 DB 상태의 불일치가 식별 가능하고, 실패가 다음 수신자 진행을 막지 않으며, shutdown/restart 복구 정책의 중복·유실 기준이 테스트된다.

**기존 과제와 중복·연결**

C1~C5/D1~D4/R1~R4를 계측/fault injection으로 확장한다. 내구성이 요구되면 current in-memory executor 범위를 outbox/queue로 전환하는 별도 결정을 기록한다.

**우선순위**

높음
