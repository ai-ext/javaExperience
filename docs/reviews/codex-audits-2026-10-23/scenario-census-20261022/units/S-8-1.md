## 목표·선수 지식·학습자 작업

요약 지표 네 종류를 member 기준으로 분리 집계하고 JOIN fanout이 수치를 부풀리는 반례를 피한다. 선수 단계와 DB 구분은 scenario/README.md 기준으로 확인한다.

상관 COUNT 서브쿼리와 미리 집계 후 LEFT JOIN을 제공한다. 원문은 활동 없는 회원, 삭제 글/댓글, 원글 삭제, 좋아요 원본행을 계약으로 구체화하고 합계·상위 5·0건 회원의 확인을 요구한다. EXISTS·인덱스 선택과 실행계획 측정은 학습자 과제로는 약하다.

## 요구·구현·검사 대조

### 1. GET `/api/stats/member-activity`는 member 30행을 모두 반환하고 likesReceived DESC,memberId ASC 정렬한다. 각 수치는: posts=PUBLISHED·미삭제, comments=삭제되지 않은 댓글+원글 미삭제, received=삭제되지 않은 내 글에 달린 post_like 행 수, given=member의 post_like 행 수.

구현 대조: 실제 SQL 파일과 StatsRepository 모두 member에서 시작해 각 값별 correlated COUNT를 수행한다. comments는 comment/post deleted_at, received likes는 post_like 원본행·글 deleted_at을 조건화하며 비정규화 like_count를 더하지 않는다. StatsService는 한 번 조회해 DTO로 매핑한다.

검사 대조: HTTP check A는 200 및 길이30, 첫 다섯 회원 exact tuple, member30=(0,0,0,0), member26=(0,9,0,23), withdrawn member29=(3,10,13,14), member12=(6,12,10,29)를 검사한다. R2 fanout=182 및 R3 요청 1~2회/120회를 코드 리뷰 기준으로 두며 자동 assertion은 없다.

공백 또는 한계: 정적 check는 API 계약값을 구체적으로 검사한다. R2의 잘못된 JOIN 재현과 R3의 SQL statement count는 자동 검사값이 아니라 학습자가 코드/계측으로 설명해야 한다.
