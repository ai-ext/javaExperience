## 판정

정적 Service/query/header와 checker는 명시된 best-effort quota와 일치한다. 동시 overshoot와 삭제 후 우회는 원문이 밝힌 제한이며 현재 숨은 결함이 아니다. index 실제 선택은 runtime 검증이 별도다.

## 목표·선수 지식·학습자 작업

POST/copy에 member별 rolling 60초 창에서 미삭제 글 5개 제한을 적용하고 6번째는 Retry-After/Problem Details 429로 거부한다. validation/BLOCK 오류는 quota를 소비하지 않는다.

V45 author/created_at 인덱스, 최근 5건 query, DB datetime 초 단위에 맞춘 now, Retry-After 상한·ceil, 429/CORS header, copy 경로 공유 limiter를 구현한다. soft delete 후 다시 쓰기가 quota를 비우는 정책 및 best-effort 동시 경쟁을 이해한다.

## 확장 개발 명세

### Strict per-member quota under concurrent creates

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

문서가 동시 초과 가능성을 인정한다. 제품이 절대 5개 제한을 원하면 quota 확인/글 생성을 직렬화해야 한다.

**시작 상태**

member 12에게 최근 60초 이내의 미삭제 글 4개를 두고 해당 구간에 다른 write는 하지 않는다.

**학습자가 할 일**

- 두 POST create와 두 POST copy를 같은 member에서 barrier로 동시에 보낸다.
- best-effort 현 동작과 member row lock/atomic quota bucket 대안을 비교한다.
- invalid validation/BLOCK 요청은 quota reserve하지 않는지 확인한다.

**정상 사례**

- hard cap 정책이라면 동시 두 요청 중 하나만 다섯 번째로 성공하고 다른 요청은 429다.
- 다른 회원 요청은 영향받지 않고 bad input은 400이며 slot을 소비하지 않는다.

**실패·경계 사례**

- lock timeout/rollback은 slot을 소비하지 않아야 한다. duplicate retry는 T-026 idempotency와 별개로 다룬다.
- best-effort 유지 시 최대로 넘을 수 있는 수와 이를 허용하는 이유를 명시한다.

**동시성·성능**

서로 다른 transaction 두 개를 barrier로 겹쳐 허용 수와 lock wait를 기록한다. 조회 plan/카디널리티는 별도 측정한다.

**DB 관찰**

SELECT author_id,created_at,deleted_at for accepted rows; verify max strict count if selected design claims hard cap.

**합격 기준**

선택한 정책이 명확하며 strict면 동시 상황에서도 5 초과 없음, best-effort면 관측 가능한 overshoot 한계가 문서화된다.

**기존 과제와 중복·연결**

T-026은 요청 재시도 중복 방지이고 burst quota와 다른 문제다. R4가 member-row lock/Redis INCR를 더 강한 대안으로 언급한다.

**우선순위**

중간

### Index range plan and precise window boundary

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

R2는 최근 범위 query의 인덱스 확인을 요구하지만 index 생성만으로 optimizer 선택은 증명되지 않는다.

**시작 상태**

삭제/미삭제 및 정확한 cutoff 시각을 포함한 회원별 post 이력을 가진 별도 DB를 준비한다.

**학습자가 할 일**

- 바인딩된 파라미터로 findRecentCreatedAt EXPLAIN을 실행해 key/rows를 확인한다.
- 초 단위 clock 기준으로 60초 경계의 다섯 번째 post/여섯 번째 post와 Retry-After를 확인한다.
- 삭제 행 포함 여부와 창 만료 후 재시도 시간 변화를 비교한다.

**정상 사례**

- 가장 최근 미삭제 글 다섯 건만 세고 오래된 것이 창을 벗어나면 Retry-After가 1~60 범위로 감소한다.

**실패·경계 사례**

- DATETIME 초 절삭 경계에서 Retry-After 61이 나오지 않으며 경계 포함 규칙은 source 계약과 일치한다.

**동시성·성능**

행 수, 실행계획, DB version, index, 쿼리 시간을 기록한다. 작은 fixture만으로 일반 성능을 추론하지 않는다.

**DB 관찰**

Inspect ix_post_author_created usage and timestamps in SELECT.

**합격 기준**

명시 환경에서 적절한 range/index가 선택되고 Retry-After가 1~60초이며 strict greater-than 정책과 경계가 일치한다.

**기존 과제와 중복·연결**

R05 index 학습과 연결한다. V45가 요구하는 기존 index를 중복 추가하지 않고 그 사용을 측정한다.

**우선순위**
