## 요구·구현·검사 대조

### 1. QueryDSL tag=spring 검색은 해당 게시글마다 행을 하나만 반환한다. 관계 존재 필터가 게시글 결과 grain을 늘리면 안 된다.

구현 대조: QueryDSL은 where 절에서 p.tags.any().name.eq(filter.tag())를 쓰고 JPQL/MyBatis는 상관 EXISTS를 쓴다. post-tag 관계는 같은 tag 이름 중복을 제한하지만 현재 단일 tag 요청만으로 다중 매칭 fanout을 검증하지는 않는다.

검사 대조: E/F는 tag=spring으로 요청하고 C3는 QueryDSL/JPA items 배열을 비교한다. P.id 포함이나 게시글 ID 중복 제거를 assertion하지 않으며 MyBatis HTTP 요청도 없다.

## 확장 개발 명세

### 태그 spring에서 글 단위 한 행 확인

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

QueryDSL tag predicate는 관계 존재를 판정하며 응답의 단위는 post row다.

**시작 상태**

L14 practice overlay에서 P는 tag=spring인 공개 dev 글이다. 기존 tags와 post_tag는 tag 이름 및 연결 쌍 unique 제약을 갖는다.

**학습자가 할 일**

- QueryDSL과 JPA에 tag=spring을 요청하고 ID와 total을 기록한다.
- 각 결과에 동적 P.id가 포함되고 post ID가 한 번씩만 나타나는지 확인한다.
- 생성 SQL의 QPost.tags.any 조건을 살펴 L13 JPQL/MyBatis 상관 EXISTS와 비교한다.
- 여러 tag 매칭 fanout을 실험할 때만 disposable 테스트 relation을 추가한다. 현재 요청은 정확한 단일 tag다.

**정상 사례**

- 단일 tag에서 tag 이름 unique 및 post-tag 쌍 unique 제약은 게시글마다 한 개 매칭만 허용한다.

**실패·경계 사례**

- 향후 여러 tag 조건을 JOIN/OR로 추가하면 두 tag 행에 걸린 게시글이 중복될 수 있다. 현재 Q17 요청은 그 사례를 만들지 않는다.
- 두 엔진이 같은 잘못된 빈 결과를 줄 수 있으므로 P 포함을 별도로 단언한다.

**동시성·성능**

이 단위는 query contract를 검증하며, 실행계획·성능 측정은 DB-08~14로 연결한다.

**DB 관찰**

- P의 post_tag/tag 행, 반환 ID, 중복 수와 total.

**합격 기준**

- P.id가 한 번만 나오며 반환 ID는 spring tag 존재 조건을 만족한다.
- QueryDSL/JPA 배열과 total이 일치한다. MyBatis 비교는 현재 panel 요청이 아니라 확장 검사다.

**기존 과제와 중복·연결**

DB-04는 다중 tag JOIN fanout, DB-12는 JOIN/EXISTS 계획 비교를 다룬다. Q17은 QueryDSL 단일 tag 요청이다.

**우선순위**

medium
