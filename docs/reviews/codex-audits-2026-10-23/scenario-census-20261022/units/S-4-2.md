## 판정

DB 원자 갱신·unique 기반 멱등성·fresh transaction 재시도와 동기화된 Testcontainers 동시 테스트까지 흐름을 구성한다. 다만 test fixture가 post 16을 공유해 두 번째 race 검증을 무력화할 수 있고, 동시 DELETE 경로는 JUnit으로 덮지 않는다. 성능이나 deadlock 발생률 수치는 재측정 전까지 사례 설명으로 한정한다.

## 목표·선수 지식·학습자 작업

4-0·4-1의 순차 트랜잭션은 정상이나, 동시에 같은 수를 읽고 Java에서 더해 저장하면 갱신을 잃을 수 있다. 같은 회원의 동시 INSERT도 사전 exists 확인만으로 막히지 않는다. 이 단계는 원자 SQL·unique key·새 트랜잭션 재시도와 barrier 동시 테스트를 과제로 둔다.

각 시도마다 새 트랜잭션을 시작하는 TransactionTemplate, INSERT IGNORE와 unique key, 행 변경 수에 따른 like_count 원자 증가·감소를 구현한다. 20명 동시 PUT, 동일 회원 5회 동시 PUT, 동시 DELETE를 실행하고 relation 수와 counter를 비교한다.

## 확장 개발 명세

### 경합 테스트마다 독립 fixture로 초기화하고 PUT/DELETE를 모두 검증

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

각 경합 테스트가 동일한 시작 행 상태를 가져야 하며, 현재 공유 seed post는 동일회원 최초 INSERT 경쟁을 무력화할 수 있다.

**시작 상태**

Testcontainers community fixture에서 post 16과 동시성 테스트 2개가 같은 row를 공유하는 현재 상태.

**학습자가 할 일**

- 각 테스트가 독립 disposable post를 만들거나 relation을 초기 상태로 되돌리고 worker에 걸친 단일 외부 트랜잭션은 사용하지 않는다.
- 20명 동시 like, 동일회원 첫 unlike-free like 5회, 20명 concurrent unlike를 각각 실행한다.
- 각 테스트 시작과 끝의 relation/count baseline을 SQL로 assertion한다.

**정상 사례**

- 20 unique member inserts -> 20 rows and count +20
- 5 same-member simultaneous PUTs -> one row/count +1
- 20 simultaneous DELETEs -> zero target rows/count zero

**실패·경계 사례**

- 재시도 뒤 모든 future가 완료되고 중복·deadlock 예외가 응답으로 노출되지 않는다.
- 테스트 시작 전에 같은 회원 relation이 있으면 최초 삽입 경합 시나리오로 인정하지 않는다.

**동시성·성능**

CountDownLatch로 시작을 동기화하고 timeout/future 완료를 검사한다. 대규모 성능 benchmark와 구분한다.

**DB 관찰**

테스트 DB에서 post별 relation 수와 like_count를 요청 전후 SELECT한다. 공유 community DB나 volume reset은 사용하지 않는다.

**합격 기준**

- 각 테스트가 기대한 baseline에서 시작함을 확인한다.
- 동시 PUT/DELETE 전후 모두 post_like row 수와 like_count가 일치하고 실행 순서에 독립적이다.

**기존 과제와 중복·연결**

README의 Testcontainers 설정과 4-1 순차 동작, T-017의 counter 테스트 설계를 활용하되 like race 전용 assertion을 추가한다.

**우선순위**

high
