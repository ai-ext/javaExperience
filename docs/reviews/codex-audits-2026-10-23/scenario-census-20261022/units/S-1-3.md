## 판정

관계 저장을 여러 SQL과 실제 행으로 따라가며 Service 경계의 이유를 단일 실패 전후 관찰로 체득하게 한다. 정상 중복 방지, 관계 행, rollback 확인이 좋고 구현·계약이 맞는다. 가장 큰 결함은 실패 실험의 복구가 모든 DB 볼륨 삭제를 권한다는 점이다. SQL 행 확인은 수동이며 자동 test는 snapshot에 없다.

## 목표·선수 지식·학습자 작업

1-2의 Controller 직접 저장을 Controller→Service→Repository로 나누고 태그 생성/중복 제거/post_tag 관계 행까지 한 트랜잭션에 넣는다. 1-2의 게시판 저장/201 계약과 E1/JPA 개념이 선수다.

Tag/TagRepository, Post의 ManyToMany join table, 서비스와 @Transactional, 응답 tags 변환을 추가한다. 입력 검증은 아직 없으며, 요청 내 동일 tag 제거와 이미 저장된 tag 재사용을 구현한다.

## 쿼리·DB 깊이와 다음 단계

- content: 서비스가 board 1회, 각 distinct tag별 SELECT/필요 시 INSERT, post INSERT 및 post_tag 관계 INSERT를 한 JDBC transaction으로 실행한다. id/unique/check/FK/길이 제약과 rollback을 다룬다.
- current_scope: 태그 entity lookup/create, 중복 제거, join-table persistence, 단일 요청 원자성
- missing_scope: 동시 신규 tag의 lookup-then-insert race 및 retry/unique 충돌은 다루지 않는다. 해당 과제는 요청 내 중복 처리와 정상 단건 저장에 초점을 두므로 별도 심화로 남긴다.
- existing_links: S-1-4는 스키마 제약을 entity와 맞춤, S-1-5는 요청 전 검증, S-7-3은 Testcontainers integration; 고급 동시성은 별도 연결이 명시된지 추가 확인 필요.
