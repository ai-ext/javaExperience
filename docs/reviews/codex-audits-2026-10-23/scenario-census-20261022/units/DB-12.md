## 확장 개발 명세

### 먼저 결과 ID/순서 일치, 뒤이어 네 계획 비교

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

JOIN/EXISTS 문법 모양보다 동일한 결과를 주는 비교가 우선이다.

**시작 상태**

practice DB read-only. Likes sample member12 size20 plus hasNext probe LIMIT21; tag sample board dev/tag spring. 예시는 public 조건만 다루며 full M3 access policy는 범위 밖이다.

**학습자가 할 일**

- 동일 filter/order/limit으로 좋아요 JOIN 및 EXISTS를 실행하고 like_id,post_id,liked_at tuple을 기록한다.
- tuple 순서가 같은 것을 확인한 뒤 두 query의 EXPLAIN을 비교한다.
- board/status/deleted/visibility/tag/order가 같은 tag JOIN 및 EXISTS를 실행해 post ID 순서와 중복을 비교한다.
- 나머지 두 query의 EXPLAIN을 기록하고 대표적인 읽기 전용 tag EXISTS 하나에만 EXPLAIN ANALYZE를 실행한다.
- 작은 practice 데이터에서 계획 차이가 없으면 그 사실을 기록하고 중단한다. DB-10은 별도 fixture 실험이다.

**정상 사례**

- 좋아요 쌍의 projection 및 순서가 같고 둘 다 LIMIT21이다.
- tag 쌍의 ID 결과가 같고 단일 spring tag에서 게시글은 한 번씩만 나온다.

**실패·경계 사례**

- tag JOIN에서 게시글 ID가 중복되면 tag 한 개 조건인지 여러 값인지 확인한다.
- 한쪽 query에만 R1 follower/block 조건을 넣지 않는다.
- 데이터·필터·parameter가 다르면 timing 비교를 하지 않는다.

**동시성·성능**

고정 plan/속도 합격 기준이 없다. EXPLAIN ANALYZE는 SELECT를 실행하므로 읽기 전용 query로 제한한다.

**DB 관찰**

- 네 query의 동일 SQL parameter/filter/order/limit.
- 각 EXPLAIN의 type/key/rows/Extra 및 대표 EXPLAIN ANALYZE TREE의 actual rows/loops/time을 기록한다.

**합격 기준**

- 계획을 비교하기 전에 좋아요 결과 및 tag 결과 두 gate가 각각 통과한다.
- 모든 query에서 회원/filter/order/limit 조건이 같다.
- 예시가 full API R1 예외를 포함하지 않는다고 기록한다.

**기존 과제와 중복·연결**

DB-03/04/06은 JOIN/EXISTS와 tag cardinality, DB-08/09는 estimate/actual, DB-10은 격리 좋아요 index를 다룬다.

**우선순위**

medium
