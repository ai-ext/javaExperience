## 요구·구현·검사 대조

### 1. Flyway V2는 post_like에 `(member_id,created_at,id)` 복합 인덱스를 online DDL로 추가하고 ANALYZE TABLE을 실행한다. 같은 member12 요청의 첫 5 postId `[145,143,140,139,142]`는 변경 전후 유지한다. 추정 EXPLAIN·실행하는 EXPLAIN ANALYZE·통계 갱신 ANALYZE TABLE을 구분한다.

구현 대조: snapshot migration은 ALGORITHM=INPLACE, LOCK=NONE으로 복합 인덱스를 만들고 ANALYZE TABLE을 수행한다. 기존 FK 인덱스 제거는 분리 변경으로 남긴다. PostLikeRepository와 LikeService는 member별 likedAt/id 커서와 API 응답을 구현한다.

검사 대조: API check C1은 status 200과 postId 순서 `[145,143,140,139,142]`를 검사한다. D1 인덱스 열 순서와 D3 Flyway V2 성공 여부는 수동 SQL 확인, D2 핵심 SELECT의 EXPLAIN과 D4 실제 JOIN 계획도 수동 기록이다. 데이터·통계·버전에 따라 달라질 실행 계획을 고정값으로 단정하지 않는다.

공백 또는 한계: 자동 check는 API 결과만 검증하고 새 key가 선택됐는지, rows·sort·actual work가 줄었는지는 검사하지 않는다. 이는 문서가 요구하는 학습자 직접 계획 관찰 항목이다.

## 쿼리·DB 깊이와 다음 단계

V2는 API에 쓰는 같은 ordered index를 migration으로 만든다. 실제 좋아요 조회는 visibility/access-policy JOIN과 member block/follow 조건을 포함하므로 단일 post_like EXPLAIN만으로 API 쿼리 결론을 대신할 수 없다. 문서는 핵심 SELECT와 실제 JOIN EXPLAIN을 따로 기록하고 응답 ID 순서를 유지하라고 한다.

- 현재 난이도: 고급(해당 단계 기준)
- 판정 이유: 인덱스 설계와 실행계획을 게시글/좋아요 쿼리에서 연결한다.
- 다음 단계: DB-08/09/10/11이 가설·실측·복합 인덱스·가시성 lifecycle을 상세 담당한다. 같은 고급 주제를 이 단위 누락으로 중복 계산하지 않는다.

## 확장 개발 명세

### V2 전후 API 동일성과 핵심/실제 계획 비교

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

작은 핵심 SELECT와 전체 API JOIN은 실행 계획이 다를 수 있다. API 응답 동등성을 먼저 확인한 뒤 두 계획을 별도 분석한다.

**시작 상태**

practice DB, 회원12(tok-p12), V2 전후 schema. 데이터가 있는 DB에서 baseline/history 상태를 확인한다.

**학습자가 할 일**

- V2 전 먼저 SHOW INDEX와 GET /api/me/likes?size=5를 저장한다.
- 핵심 단일 테이블 SELECT의 EXPLAIN 및 EXPLAIN ANALYZE를 기록한다.
- Flyway V2가 성공했는지 schema_history에서 조회하고 인덱스 열 순서를 확인한다.
- 같은 API를 재요청하여 전후 ID 순서/응답 필드를 비교한다.
- 복합 인덱스가 보이는 상태에서 실제 JOIN SQL EXPLAIN을 실행하고 각 테이블 접근 경로를 기록한다.

**정상 사례**

- C1 IDs [145,143,140,139,142].
- D1 ordered columns exactly member_id,created_at,id.
- D3 version 2 success=1.

**실패·경계 사례**

- 실행계획 key가 달라지지 않아도 즉시 오류가 아니다. stats/cardinality, join order를 조사한다.
- API SQL은 FORCE INDEX를 사용하므로 index INVISIBLE 상태에서 요청하지 않는다. visibility/drop 복구는 DB-11.
- 이미 적용한 Flyway migration 파일을 수정해 재적용하지 않는다.

**동시성·성능**

온라인 DDL 옵션은 사용하지만 이 단계는 lock duration 측정을 합격으로 요구하지 않는다. 대량 데이터 성능 비교는 DB-10 격리 fixture.

**DB 관찰**

- D1 index ordered columns.
- D3 migration success.
- D2 핵심 EXPLAIN key/rows/Extra.
- D4 JOIN EXPLAIN join order와 각 테이블 key/access/estimated rows.
- API IDs before/after.

**합격 기준**

- C1 응답 ID 순서 전후 동일.
- D1 member_id,created_at,id.
- D3 V2 success.
- D2/D4 출력은 실제 현재 DB에 맞게 기록하고 환경 독립 정답값으로 쓰지 않는다.

**기존 과제와 중복·연결**

DB-08/09 explain/actual, DB-10 대량 분리 fixture, DB-11 invisible/restore/drop. 9-2는 API와 Flyway migration 결합을 담당한다.

**우선순위**

medium
