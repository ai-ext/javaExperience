## 판정

이 단계는 N+1 기준선을 관찰한 뒤 singular fetch join, collection batch fetch와 명시 COUNT를 선택하고 같은 결과를 보존한다. 쿼리 수 assertion이 존재하지만 이번 감사를 통해 실행했다고 주장하지 않는다.

## 목표·선수 지식·학습자 작업

2-2/2-3 목록은 결과가 맞지만 응답 DTO 변환 때 author/tag lazy relation을 글마다 조회한다. 같은 응답 JSON/접근정책을 유지하면서 SQL 수를 page size에 비례하지 않게 낮추고, Hibernate Statistics 기반 테스트로 회귀 방지한다.

목록 쿼리에 단건 작성자는 fetch join하고, 태그 컬렉션은 default_batch_fetch_size=100 또는 동등한 batch fetch로 한 번에 불러온다. `Page` count 생략 최적화가 5/20 size 비교를 흔들지 않도록 SELECT와 count를 분리해 항상 실행한다. PostListQueryCountTest를 작성한다.

## 요구·구현·검사 대조

### 1. size 5와 size 20 목록 호출의 Hibernate SQL statement count가 같고 둘 다 5 이하이며 0보다 커야 한다.

구현 대조: 구현됨: author fetch join, tag batch fetch 설정, 명시 count 쿼리, List와 PageImpl 응답.

검사 대조: PostListQueryCountTest가 actual prepareStatementCount를 clear/measure하고 equality, <=5, >0을 assert

공백 또는 한계: 테스트는 size가 달라도 쿼리 증가량이 제한됨을 확인하지만 SELECT별 SQL 모양은 고정하지 않는다. 문자열 SQL assertion을 피한 선택이다.

## 쿼리·DB 깊이와 다음 단계

- content: 최적화 전에는 page SELECT 뒤 각 글마다 author/tag 조회가 추가될 수 있다. 이후 author fetch join, tag IN 일괄 조회와 명시 COUNT로 같은 DTO를 만든다. Tag collection을 페이징 query에서 join fetch하지 않아 page row가 증폭되지 않는다.
- current_scope: 응답/filter/order 의미를 유지하며 fetch 전략을 바꾸고 실제 Testcontainers DB에서 SQL 문장 수를 센다.
- missing_scope: 작은 seed에서 문장 수를 재는 검증이지 대규모 cardinality, EXPLAIN, 실행 시간/row estimate는 아니다. DB-08+와 disposable performance fixture가 그 다음 경로다.
- existing_links: 2-2는 row별 관계 조회를 만든다. DB-13은 API N+1, 9-2와 별도 성능 fixture는 인덱스/EXPLAIN을 다룬다.

- 현재 난이도: 고급
- 판정 이유: Repository 호출 수와 실제 SQL 수를 구별하고 테스트 DB에서 page size별 실행을 측정하면서 pagination/count 의미를 지켜야 한다.
