## 판정

JPA 저장을 선언적 Entity/Repository 코드와 실제 SQL·생성 id·201/Location·응답 DTO·DB 행으로 연결하는 완성도 높은 첫 저장 단위다. Service/검증/태그/인증을 이후로 보류한 이유가 명확하고 진행 경로가 있다. 다만 manual O2가 community DB에 잘못된 row를 남기고, datasource/CLI 안내가 실제 Compose 값과 불일치한다. 게시판 writeRole 경계는 다음 인증 단계와 함께 닫히는지 추가 확인이 필요하다.

## 목표·선수 지식·학습자 작업

1-1의 수신-only endpoint를 community DB 저장으로 키운다. 게시판 slug 조회, Post Entity/JpaRepository save, 생성 키를 응답 id와 Location으로 전달한다. 1-3에서 Service/태그/트랜잭션, 1-4에서 전체 스키마 정합성, 1-5에서 입력 정책, 1-6에서 인증 주인을 단계적으로 추가한다.

Post와 Board Entity/Repository, Controller 저장 경로, 응답 전용 DTO 및 201/Location을 구현한다. 작성자는 임시로 member id 2, 태그 저장은 아직 없고 검증도 수행하지 않는다. SQL·DB 행은 D1 수동 확인으로 읽는다.

## 확장 개발 명세

### 관찰용 실패 입력을 별도 DB에서 실행

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

하나의 의도된 관찰(O2)이 커뮤니티 시드 DB에 잘못된 행을 남긴다.

**시작 상태**

ID 1~21 seed를 가진 community DB, POST 저장 API, O1~O5 관찰 요청

**학습자가 할 일**

O1~O5를 disposable profile/database 또는 롤백되는 격리 테스트에서 실행하고 정상 A 요청 및 D1 확인은 별도의 보존 가능한 흐름으로 둔다. 격리 환경을 만들 수 없으면 O2는 요청 payload 검토만 하고 community에는 전송하지 않는다.

**정상 사례**

- 정상 게시글은 201, Location과 body id가 같음
- D1 행의 id/board/author/title/visibility가 응답과 일치

**실패·경계 사례**

- null title·긴 title·check 위반은 현재 DB 거부 500 관찰
- 공백 title/빈 body는 현재 성공 저장해 invalid row를 만든다는 점 표시
- 없는 board는 현재 500 이후 1-5 404로 개선

**동시성·성능**

해당 없음: 이 단계는 단건 저장과 키 생성

**DB 관찰**

검사 후 seed baseline이 그대로이고 테스트 행이 남지 않았는지 disposable DB에서 확인

**합격 기준**

공유 community DB에 O2가 쓰이지 않고, 실패 계약과 정상 저장/응답 일치는 재현 가능한 격리 상태에서 검증된다.

**기존 과제와 중복·연결**

S-7-3의 Testcontainers와 기본 DB 분리를 사용할 수 있음. 테스트 실행과 격리 복원은 메인 감사 담당.
