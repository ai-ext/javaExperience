## 판정

한 줄 요약이 아니라 실제 build.gradle/yml을 읽고 설정 변화가 코드·응답에 반영되는지 확인한다. 여러 실패 유형을 원인 계층별로 구분하며 실제 snapshot은 문서의 포트/URL 및 설정값과 일치한다. 성공 checker는 단일 응답뿐이라 반복된 고장 실험은 수동 학습이다.

## 목표·선수 지식·학습자 작업

Gradle dependency scopes, JDBC driver, datasource/JPA startup behavior, YAML nesting, @Value 생성자 주입을 실제 현재 파일과 비교하며 익힌다. 문서의 완료 예시는 덮어쓰기 템플릿이 아니라 비교 자료다. 0-1의 DB 시작 문제와 0-5의 로그 읽기가 연결된다.

실제 build.gradle/application.yml을 확인하고 필요한 start.greeting/max-items 설정을 추가한다. ConfigController에서 앱 이름과 두 설정값을 읽어 응답한다. 설정 오류를 일부러 만들어 컴파일/기동 실패와 datasource 연결 실패를 구분한다.

## 확장 개발 명세

### 기동 전 환경 진단 기록

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

datasource가 필요한 이유는 충분히 설명하지만 로컬 구성값이 다르면 첫 API까지 진행이 차단될 수 있다.

**시작 상태**

현재 application.yml의 datasource URL localhost:13308, Compose host publish port, 활성 Spring profile을 대조한다.

**학습자가 할 일**

현재 활성 설정과 compose 공개 포트를 직접 확인하고 JDBC URL, DB health, driver presence, 실행 profile을 짧은 진단 표로 기록한다.

**정상 사례**

- MySQL healthy와 URL 포트 일치 후 config endpoint 200
- start.greeting 변경 후 restart 시 새 응답

**실패·경계 사례**

- DB 미기동/포트 거부
- driver 제거
- placeholder 오타
- YAML 중복 키·들여쓰기 오류

**동시성·성능**

실행환경 작업이므로 동시성/성능은 없음

**DB 관찰**

시작 연결과 실제 SELECT/쓰기 동작을 구분; DB 볼륨 초기화는 이 실습의 일부가 아니라고 안내

**합격 기준**

학습자가 앱 코드 문제와 datasource/driver/profile/YAML 문제를 구분하고 공유 데이터를 지우지 않고 복구 절차를 선택한다.

**기존 과제와 중복·연결**

S-0-5가 로그 판독, S-1-2가 repository 연결을 맡으므로 여기서는 환경 진단만 남긴다.
