## 확장 개발 명세

### 회원12 핵심 SELECT의 EXPLAIN 가설

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

학습 결과는 EXPLAIN 화면이나 근거 없는 속도 주장이 아니라 현재 추정값에 근거한 가설이다.

**시작 상태**

DB-10 전용 fixture만 사용한다. 기본 PERF_ROW_COUNT=500000이며 값을 바꿨으면 실제 행 수를 기록한다. member12 비율은 2%, query는 LIMIT 11이다. tools/db-perf-fixture.sh status/up을 확인한다.

**학습자가 할 일**

- 먼저 정확한 SELECT를 실행해 결과 ID 순서를 기록한 뒤 같은 query에 EXPLAIN을 실행한다.
- type, possible_keys, 선택된 key, estimated rows, Extra를 기록한다.
- 관측 사실+의심 원인+다음 비교 실험을 한 문장으로 쓴다. Using filesort만으로 디스크 I/O나 endpoint latency를 단정하지 않는다.

**정상 사례**

- SELECT l.id,l.post_id,l.created_at FROM post_like AS l WHERE l.member_id=12 ORDER BY l.created_at DESC,l.id DESC LIMIT 11 을 기준 query로 쓴다.
- plan 정답 숫자를 고정하지 않는다. 현재 fixture에서 나온 estimates를 기록한다.

**실패·경계 사례**

- practice/community DB나 API 전체 join에 연결하면 이 fixture 실험 범위가 아니다.
- EXPLAIN ANALYZE는 SELECT를 실행한다. 이 작업은 DB-09이며 읽기 비용을 확인해야 한다.
- 기준 plan을 남기기 전에 index를 추가하면 DB-08의 비교 기준이 사라진다.

**동시성·성능**

실제 실행 rows/시간은 재지 않는다. 이 단계는 optimizer 추정 계획만 기록한다.

**DB 관찰**

- DB/schema, fixture 행 수, index 목록, SQL 전문과 EXPLAIN 열.
- 가설에 관측 필드와 다음 DB-09/10 실험이 포함되어야 한다.

**합격 기준**

- 현재 fixture의 EXPLAIN 결과를 저장한다.
- 가설은 관측한 key/estimated rows/Extra를 인용하고 동일 조건의 후속 실험을 제안한다.

**기존 과제와 중복·연결**

DB-09는 actual rows/loops/time, DB-10은 index 추가, S-9-2는 application migration과 explain을 다룬다.

**우선순위**

medium
