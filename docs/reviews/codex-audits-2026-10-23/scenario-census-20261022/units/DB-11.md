## 확장 개발 명세

### 같은 EXPLAIN으로 visibility 단계 비교 및 복구

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

Invisible index는 정의를 유지한 채 optimizer의 후보에서 제외해 계획을 비교하게 한다. 종료 전 VISIBLE 복구가 필수이며 DROP은 별도 선택이다.

**시작 상태**

DB-10에서 사용한 MySQL 8.4 javaexperience_perf fixture를 쓴다. index가 이미 있을 수 있으므로 status/SELECT DATABASE/SHOW INDEX를 먼저 확인한다. practice DB나 전체 API FORCE INDEX query는 쓰지 않는다.

**학습자가 할 일**

- 복합 index가 없을 때만 생성하고 ANALYZE TABLE을 실행한다.
- VISIBLE에서 member12 LIMIT11 동일 query EXPLAIN의 key/rows/Extra를 기록한다.
- index를 INVISIBLE로 바꾸고 SHOW INDEX visibility와 같은 EXPLAIN을 기록한다.
- 즉시 VISIBLE로 복구한 뒤 SHOW INDEX 및 같은 EXPLAIN을 확인한다.
- fixture를 원상 복구할 때만 이 실험용 index를 VISIBLE 상태에서 DROP하고 ANALYZE TABLE한 뒤 확인한다. FK/UNIQUE index는 제거하지 않는다.

**정상 사례**

- 모든 단계에서 member12, created_at DESC/id DESC, LIMIT11 query를 동일하게 사용한다.
- plan은 바뀌거나 유지될 수 있다. 예상 key를 정답으로 강제하지 않고 실제 값을 기록한다.

**실패·경계 사례**

- PRIMARY index를 INVISIBLE로 만들거나 숨긴 상태에서 9-2 FORCE INDEX API를 실행하지 않는다.
- 중단으로 INVISIBLE이 남으면 종료 전에 VISIBLE로 복구한다.
- 다음 단계에서 공유하는 기존 index라면 DROP하지 않는다. 기본은 유지 선택이다.

**동시성·성능**

시간 합격선은 없다. key/rows/Extra 계획만 비교하며 actual 실행은 DB-09다.

**DB 관찰**

- 세 상태의 SHOW INDEX visibility와 계획 key/rows/Extra.
- optional DROP 뒤 ix_post_like_member_created만 사라지고 baseline index가 남는지 확인한다.

**합격 기준**

- VISIBLE→INVISIBLE→VISIBLE의 동일 계획 기록이 세 개 이상이다.
- 마지막 SHOW INDEX가 VISIBLE이거나 cleanup 선택 시 실험 index만 제거됐음을 확인한다.

**기존 과제와 중복·연결**

DB-10은 복합 index 설계, DB-09는 EXPLAIN ANALYZE, S-9-2는 앱 migration index를 다룬다. DB-11은 disposable fixture의 visibility 상태만 바꾼다.

**우선순위**

medium
