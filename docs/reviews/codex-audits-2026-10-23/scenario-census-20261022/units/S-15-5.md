## 확장 개발 명세

### 두 배치 runner 및 notification 실패 원자성/외부 전달 분리

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

동일 단계의 UNIQUE gate가 DB 알림 중복을 막는지 검증하고, DB commit 후 외부 전송 실패를 같은 트랜잭션으로 착각하지 않도록 전달 계약을 나눈다.

**시작 상태**

격리 MySQL에 좋아요 9·49·99개 글과 각 문턱을 넘는 실제 좋아요 행, 작성자 notification inbox를 만들고 milestone 기록을 비운다.

**학습자가 할 일**

- 두 scheduler worker가 barrier 이후 같은 candidate 목록을 처리하게 해 milestone INSERT 영향행과 notification 수를 비교
- notification insert를 실패시키고 marker도 rollback되는지 확인한 뒤 재실행
- DB commit 이후 fake push gateway가 timeout/재시도/중복 응답을 주는 조건을 추가하고 outbox event id/상태 저장 여부 설계
- poll 주기 사이 threshold가 10→9로 변한 사례에서 사업 규칙상 축하 대상인지 명시적으로 결정

**정상 사례**

- 각 post/stage 조합당 marker와 notification이 각각 최대 하나다.
- 같은 stage 경쟁의 loser는 added가 비고, 저장 성공 한 번만 notification 한 건이 존재한다.

**실패·경계 사례**

- DB notification 저장 실패 시 milestone도 없다.
- 외부 gateway timeout은 DB notification을 rollback하지 않으며 재시도 시 동일 event key로 중복 발송하지 않는다.
- actor null 알림은 기존 LIKE/COMMENT 목록을 깨뜨리지 않는다.

**동시성·성능**

동일 12개/수천개 candidate를 두 worker로 실행해 unique conflict, transaction duration 및 배치 크기를 기록한다.

**DB 관찰**

like_milestone unique count와 notification(post_id,type,milestone) 조인 수, rollback 결과, outbox delivery 상태를 확인한다.

**합격 기준**

각 단계 DB 기록/알림 1:1, 동시 중복 0, DB 실패 rollback, 외부 재시도는 idempotent하고 기존 알림 조회 계약도 유지된다. threshold 의미는 명시한 결정과 테스트가 일치한다.
