## 판정

## 목표·선수 지식·학습자 작업

1-2 글 작성 흐름에서 먼저 multipart로 파일을 업로드하고 나중 요청에서 imageIds로 글에 붙인다. 업로드 응답 201과 post_image의 post_id=NULL, 글 저장 후 FK 연결, GET 본문 다운로드를 한 파일 흐름으로 구현한다. 기반은 Spring multipart 제한, 기존 member/post 관계와 `app.upload-dir` 설정이다.

직접 구현: V20 테이블, multipart Controller, 내용 바이트 기반 타입 판정, 임의 저장 이름/디스크 저장, 이미지 메타데이터와 `post_id NULL` 저장, 첨부 시 본인·미연결 검사 및 원자적 연결, 조회/다운로드, 오류 변환. 제공 기반: Spring multipart 파서와 공통 인증, 파일 저장 디렉터리 설정 틀. 로컬 파일과 DB의 단일 트랜잭션은 성립하지 않는다는 운영 한계를 설명한다.

## 확장 개발 명세

### 같은 이미지 선점 경합과 글 생성 원자성

상태: **제안·미구현**. 이 문서 작성만으로 학습 실습이 구현됐다고 표시하지 않는다.

**이유**

repository pessimistic lock으로 중복 첨부를 막는 코드가 있지만, acceptance는 이미 붙은 이미지를 순차 재사용할 때만 확인한다.

**시작 상태**

김자바가 POST /api/images로 GIF 1개를 업로드해 imgId를 얻는다. 디스크 파일과 post_image 행(post_id IS NULL)을 확인한다.

**학습자가 할 일**

- 두 독립 HTTP worker가 동시에 POST /api/posts를 보내며 둘 다 같은 imageIds=[imgId]와 서로 다른 제목을 사용한다.
- HTTP status와 응답 id를 기록하고, 두 요청 완료 후 post_image.post_id 및 post 행을 조회한다.
- 첫 요청의 post insert 뒤 attach가 실패하도록 테스트 주입 가능한 오류를 두어 post와 관계 row rollback 여부를 따로 확인한다.

**정상 사례**

- 병렬 요청 중 하나만 201로 글을 만들고 이미지가 해당 글 id에 연결된다.
- 다른 요청은 400 imageIds이며 그 요청의 제목에 해당하는 post 행은 0개다.

**실패·경계 사례**

- 없는 id/다른 회원의 id/이미 연결된 id/11개/소수 id는 400이고 글은 저장되지 않는다.
- DB rollback이 난 업로드에서는 행과 디스크 파일 cleanup 시도를 확인하되, 프로세스 종료면 별도 cleanup이 필요함을 분리 기록한다.

**동시성·성능**

barrier로 동시 2개 attach를 발생시킨다. 응답은 1 success/1 validation failure. 잠금 대기는 기록하며 처리량 향상 주장은 하지 않는다.

**DB 관찰**
