## 시작 상태

L16의 동일 계약을 구현하는 두 구현체와 별도 Spring context를 사용한다. 요청자 A/B를 구분하고 context의 정상 종료를 제어한다.

## 학습자가 할 일

1. 생성자, 의존성 주입 후 초기화, 첫 사용, context 종료 이벤트를 순서대로 기록한다.
2. 의존성 후보가 0개·2개·정상 1개인 경우의 기동 결과를 구분한다.
3. 현재 회원 ID를 singleton 필드에 둔 실패판에서 A/B 요청을 barrier로 겹치게 한다. 이후 요청 값을 메서드 인자로만 전달하도록 바꾼다.

## 정상 입력과 기대 결과

- 컨테이너 내 동일 빈이 여러 호출자에게 공유됨을 확인한다.
- A 응답에는 A의 데이터, B 응답에는 B의 데이터만 담긴다.

## 실패·경계·반례

- 후보 0개·2개가 예상한 기동 오류로 검출된다.
- 강제 종료에도 정상 destroy callback이 보장된다고 가정하지 않는다.
- 가변 필드 실패판에서 교차 요청의 상태 오염을 결정적으로 재현한다.

## 동시성·측정·DB 관찰과 정리

반복 횟수에 의존하는 확률적 재현 대신 두 요청의 읽기·쓰기 순서를 barrier로 제어한다. 정상 종료 시 자신이 연 자원을 정리한다.

## 합격 기준

생명주기 순서와 상태 오염의 수정 전후를 자동 검증하고, singleton이면 자동으로 thread-safe하다는 오답을 구별해야 한다.

## 제작 완료 판정

위 계약을 실행할 fixture/시작 코드/검사기를 작성하고, 정상 구현 통과와 대표 오답 실패를 둘 다 확인한 뒤에만 학습 화면에 완료 상태로 공개한다. 실행 로그·버전·원문 링크·복구 결과를 함께 보존한다.
