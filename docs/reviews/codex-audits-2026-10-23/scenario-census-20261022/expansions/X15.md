# X15. 커밋 후 종료·중복 전달을 견디는 outbox

상태: **개발 명세 — 미구현·미실행**. 우선순위: P1. 확인일: 2026-10-22. 기존 학습자 코드와 시나리오 원문에 자동 반영하지 않았다.

## 현재 근거와 확장 이유

커밋후이벤트/비동기 발송과 프로세스 종료 시 유실 한계는 이미 명시돼 있다. outbox는 대안으로 소개되지만 강제 종료 후 재개까지 완결하는 실험을 보강한다.

## 시작 상태

업무 글 P와 outbox(event_id,status,attempts,next_retry_at), 처리한 event_id의 유니크 제약을 가진 소비자를 준비한다. broker 또는 별도 HTTP 수신 대역을 고정한다.

## 학습자가 할 일

1. 업무와 outbox를 같은 transaction에 저장한다.
2. 저장 전·commit 직후·전송 후 상태 기록 전의 세 지점에서 relay를 종료한다.
3. 같은 event_id를 두 번 전달하고 소비자의 업무 효과가 한 번인지 확인한다.
4. 지속 실패를 retry 한도·실패 보관·수동 재처리로 연결한다.

## 정상 입력과 기대 결과

- 업무 commit 1건마다 event가 보존되고 재시작 후 처리된다.
- 중복 전달에도 알림이나 금액 증가는 정확히 한 번 적용된다.

## 실패·경계·반례

- rollback된 업무의 event는 남지 않는다.
- 전송 성공 후 relay가 종료돼 재전달해도 중복 효과가 없다.
- 독성 메시지가 뒤의 정상 메시지를 영구히 막지 않는다.

## 동시성·측정·DB 관찰과 정리

두 relay의 경합·작업 선점·재시도 지연을 기록한다. 전달 자체가 exactly-once라고 주장하지 않고 중복 전달 허용과 업무 효과의 멱등성을 구분한다.

## 합격 기준

각 실패 창에서 유실 0건·중복 업무 효과 0건을 DB와 수신 로그로 확인해야 한다.

## 제작 완료 판정

위 계약을 실행할 fixture/시작 코드/검사기를 작성하고, 정상 구현 통과와 대표 오답 실패를 둘 다 확인한 뒤에만 학습 화면에 완료 상태로 공개한다. 실행 로그·버전·원문 링크·복구 결과를 함께 보존한다.
