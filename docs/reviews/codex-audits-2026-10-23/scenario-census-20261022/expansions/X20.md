# X20. DB 타입·문자 비교·시간·금액의 업무 계약

상태: **개발 명세 — 미구현·미실행**. 우선순위: P1. 확인일: 2026-10-22. 기존 학습자 코드와 시나리오 원문에 자동 반영하지 않았다.

## 현재 근거와 확장 이유

NOT NULL·기본값·FK·enum 실습은 이미 있다. 이번 실행에서 교육용 api_token의 대소문자 변형이 같은 회원으로 인증됨을 확인했다. 현재 동작을 먼저 재현한 뒤, 식별자별 문자 비교 정책을 명세로 정하고 DB·애플리케이션을 함께 바꾸는 과제다.

## 시작 상태

현재 utf8mb4_0900_ai_ci token 열을 복제한 격리 fixture에서 시작한다. tok-p05/TOK-P05가 같게 조회되는 현 상태를 확인한다. 목표 정책은 token 값의 대소문자 구분이며, 닉네임 정규화·금액 DECIMAL·시각의 시간대 계약은 별도로 정한다.

## 학습자가 할 일

1. token 값의 원문·대소문자 변형과 인증 scheme 표기 변형을 각각 검사한다.
2. 목표 token 정책에 맞게 collation 또는 애플리케이션 비교를 변경하고 기존 데이터의 중복·호환성을 확인한다.
3. 닉네임의 대소문자·악센트·공백·Unicode 형태와 UNIQUE 판정을 대조한다.
4. 소수 수량·금액 반올림·DATETIME 정밀도·UTC/지역시각 경계를 API→객체→DB→응답으로 추적한다.

## 정상 입력과 기대 결과

- 변경 전에는 기존 재현과 같고, 변경 후에는 정한 token 비교 정책만 허용된다.
- 금액·시각이 명세대로 round-trip되며 허용하지 않은 정밀도는 거부된다.

## 실패·경계·반례

- 수량 2.7이 의도 없이 2로 저장되거나 변경 후에도 잘못된 token이 인증되면 실패한다.
- DB collation과 애플리케이션의 동등성 판정 차이를 검출한다.

## 동시성·측정·DB 관찰과 정리

UNIQUE나 collation 변경 전에 기존 중복과 이행 방식을 검토한다. 현재 교육용 token 모델과 10장 JWT 검증을 같은 문제로 취급하지 않는다.

## 합격 기준

변경 전후 경계 입력의 HTTP 상태·회원 ID·정확한 저장 값·제약 오류가 각각의 독립 기대값과 일치해야 한다.

## 제작 완료 판정

위 계약을 실행할 fixture/시작 코드/검사기를 작성하고, 정상 구현 통과와 대표 오답 실패를 둘 다 확인한 뒤에만 학습 화면에 완료 상태로 공개한다. 실행 로그·버전·원문 링크·복구 결과를 함께 보존한다.
