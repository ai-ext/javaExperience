# 부족한 내용을 채울 때의 추가 순서와 합격 조건

이 파일은 감사 결과에 따른 보완 명세다. 아래 기능이나 학습 화면을 구현 완료했다고 주장하지 않는다. 문서 수를 늘리기보다 이미 있는 근거를 연결하고 제공 코드를 점진적으로 줄인다.

## 모든 과제에 공통으로 필요한 다섯 파일

각 학습 단위의 산출물을 다음처럼 나눌 수 있다. 실제 적용할 위치와 UI는 후속 구현에서 정한다.

1. `요구사항`: 누가 무엇을 요청하며 허용·거절되는 조건이 무엇인지.
2. `설계판단`: 입력 출처, 필요한 행, 업무 불변식, 메서드/계층, 트랜잭션 경계.
3. `실행관찰`: 요청, Java 객체값, SQL, 같은 tx와 별도 연결의 DB 전후값.
4. `실패실험`: 잘못된 입력·권한·후행 실패·중복·경쟁 중 해당하는 사례.
5. `검증결과`: 실행 명령, 환경/fixture, 실제 관측, 아직 확인하지 않은 범위.

- P20 생성자 치트시트, DTO 컴파일 경로, E1 순환 의존 설명, 4-2 tx/thread/DELETE 설명을 먼저 정리한다.
- 저장소에 없는 `practice/starter` 명령은 재현 가능한 프로젝트 경로/패키지로 연결한다.

**합격:** 새 checkout에서 정답을 읽기 전에 실행할 수 있고, 원문 코드를 복사할 때 별도 연구 폴더가 없어도 필요한 파일을 얻는다. 생성자·tx 기본값·동시 테스트 설명이 공식 계약과 모순되지 않는다.

## 1. 내 객체로 IoC·DI·Bean 확인

- 현재 Controller/Service/Repository 의존 그래프를 그린다.
- 같은 Service를 컨트롤러 두 곳이 받는지, new한 Entity는 왜 Bean과 다른지 직접 관찰한다.
- Service를 순수 Java로 만들 때 fake Repository를 넣어 업무 규칙만 시험한다.
- 같은 인터페이스 구현2개와 후보 누락을 각각 만들고 실제 bean 생성 오류를 분류한다.
- 요청별 회원 ID를 singleton 필드에 저장했을 때 교차 요청이 섞이는 실패와 메서드 인자 방식의 차이를 확인한다.

**합격:** 어노테이션 이름이 아니라 생성·주입·수명·요청상태의 소유자를 설명한다. 실제 순환 그래프와 단순 계층 역방향 참조를 구별한다.

관련: C01~C06, C26.

## 2. 최소 게시글 Service를 스스로 설계

처음에는 태그와 이미지 없이 진행한다.

- 요청의 `boardSlug`는 기존 게시판 조회, 작성자는 인증 정보, 제목/본문은 요청, ID/시각은 서버·DB 값으로 나눈다.
- Service 시그니처를 정하고 `조회 → 권한/상태 확인 → 객체 생성 → 저장 → DTO` 의사코드를 쓴다.
- Entity 메서드는 유효 상태를 유지하고 Controller는 HTTP 계약을 다룬다.
- 정상 작성, 없는 게시판, 권한 없음, 잘못된 제목의 쓰기 전후를 비교한다.

**합격:** 새 게시글1개/응답ID 일치, 거절 시 쓰기0개. 완성 코드를 보지 않고 새로운 “댓글 생성” 의사코드를 동일 방식으로 작성한다.

관련: C07/C12/C25, I01/I03/I13/I14.

## 3. 댓글로 관계 1:N을 처음부터 구현

공유 태그보다 생명주기가 분명한 게시글-댓글을 먼저 다룬다.

- `comment.post_id` FK와 필수/선택 관계를 정하고 Java 필드를 유도한다.
- 단방향 `ManyToOne`만으로 해결되는 조회와 부모 컬렉션이 필요한 경우를 비교한다.
- 양방향이면 FK 주인과 편의 메서드를 설계하고 inverse-only 실패를 확인한다.
- DTO가 Entity를 그대로 노출하지 않게 하고, 삭제/soft delete/cascade/orphan 정책을 행으로 설명한다.

**합격:** 글1·댓글2, 다른 글의 댓글이 섞이지 않음, 없는 부모 거절, 양쪽 객체/FK 일치, 삭제가 공유 회원 등 무관한 행에 전파되지 않음.

관련: C17/C18/C24, I10/I11/I07.

## 4. 현재 태그 구현에서 공유 태그로 이동

- `tag.title`과 제공된 `tag.name`의 차이를 실제 DDL로 확인한다.
- “글에 종속된 태그”와 “이름이 공유되는 태그”를 각각 표로 그린 뒤 이번 시나리오의 요구를 선택한다.
- 기존 태그 재사용과 새 태그 생성, 입력 중복 제거, `post_tag` 연결을 구현한다.
- 요청마다 전부 새 태그를 만드는 방식과 공유 Entity를 cascade remove하는 방식의 문제를 실패 과제로 둔다.
- ID/유일 제약/FK/NOT NULL을 Entity와 DDL 양쪽에서 확인한다.

**합격:** 같은 태그를 두 글이 공유해도 tag1·연결2이며 한 글의 연결을 제거해도 다른 글/공유태그가 살아 있다. 후행 실패에는 글·새 태그·연결의 원자성 계약에 맞는 원복이 확인된다.

관련: C07/C18/C20, I03/I12/I16.

## 5. EntityManager와 트랜잭션을 실제 요청에 연결

- 같은 데이터로 new → persist/find → managed 변경 → flush → commit/rollback → 새 연결 조회를 기록한다.
- Spring이 주입한 EM 프록시와 실제 tx별 컨텍스트를 구분한다. 실제 EM을 여러 worker에 공유하지 않는다.
- `save`와 `merge`, Entity ID와 실제 DB 행 존재를 분리한다.
- Spring/Jakarta 두 Transactional import를 비교한다.
- RuntimeException, checked exception, catch 정상 반환, inner rollback-only, self invocation을 나눠 시험한다.
- readOnly에서는 조회 뒤 변경, 신규 INSERT, native/JDBC DML, 바깥 REQUIRED 참여를 현재 DB/driver/JPA 환경별로 비교한다.

**합격:** “실행 SQL이 보였다=commit”이라고 답하지 않는다. rollback 후 객체값과 DB값을 구별한다. 서로 다른 readOnly 실험의 결과를 하나로 일반화하지 않는다.

관련: C09~C16, C20/C22, I02.

## 6. 좋아요를 관계·멱등·동시성으로 구현

- Boolean이 아니라 회원-글 관계 행으로 상태를 표현한다.
- `PUT`은 원하는 상태를 설정하고 `DELETE`는 해제한다. 반전 toggle과 구분한다.
- 동일회원 중복, 다른회원 동시 증가, 동시 취소, PUT/DELETE 혼합을 각각 시험한다.
- DB unique 제약, 관계 변경 여부, 카운터 변경, rollback, retry 경계를 별도로 설명한다.
- 영향을 받은 행 수와 파생 delete 반환값을 구별한다. 재시도는 운영 코드의 호출 전제와 tx 경계까지 확인한다.

**합격:** 순차 중복 호출에서 관계행1/0, 다른 회원의 상태 보존, 동시작업 종료 후 count=관계행수, 음수없음, 업무 거절 시 두 테이블 불변. 모든 worker 예외/Future를 회수한다.

이번 감사에서 원문 PUT2시험 및 동시 DELETE100호출은 통과했다. 따라서 기존 동시성 코드를 무조건 새로 쓰기보다 빠진 계약/회귀테스트를 보강한다.

관련: I08/I09/I15, C15/C16.

## 7. 조회·수정·오류를 마무리

- Service 내부 DTO 조립과 LAZY 로딩 경계를 정하고 OSIV를 껐을 때도 계약을 지킨다.
- 목록에서 쿼리 수뿐 아니라 정렬 동률·페이지 경계·중복/누락을 검사한다.
- 컬렉션 fetch join과 페이지 조합은 안전한 대안(ID 페이지 후 상세조회/DTO projection 등)과 실제 결과를 비교한다.
- PATCH 생략/null/빈목록을 구분하고 변경 후 검증 실패에 원복을 확인한다.
- 형식오류400, 인증401, 권한403, 없는 리소스404, 충돌409 등은 프로젝트의 API 계약을 명시해 일관되게 적용한다. 모든 IllegalArgumentException을404로 묶지 않는다.

**합격:** 요청 밖 DTO 사용에서도 필요한 데이터가 준비돼 있고, 잘못된 입력과 업무 거절이 문서의 HTTP 계약에 맞으며, 변경 실패 후 DB 상태가 그대로다.

관련: C19/C20/C25, I04~I07/I13/I14.

## 8. 정답 없는 전이 평가

기존에 정답으로 본 좋아요와 다른 기능인 “북마크 폴더 한도·중복 이름·소유권·이동” 또는 댓글 정책 변경을 준다.

학습자는 다음 결과를 직접 제출한다.

- 요구사항에서 도출한 불변식·관계·DB 제약.
- Controller/DTO/Service/Repository/Entity의 책임과 메서드 계약.
- 정상·실패·경쟁 사례별 기대 응답과 DB 전후 상태.
- 단위/슬라이스/실제 DB 테스트 중 선택한 범위와 선택 이유.
- 실행 결과와 미검증 범위, 느린 쿼리나 풀 대기의 근거.

**합격:** 복사한 코드의 동작을 설명하는 데서 끝나지 않고, 새 요구에 맞는 설계를 만들고 실패를 재현해 원인을 설명한다. 이 과제를 통과해야 목표 역량이 실제로 습득됐다는 판단을 할 수 있다.

이벤트/outbox, 대규모 캐시·메시징·운영 아키텍처는 위 기본 경로의 선수조건으로 끼워 넣지 않는다. 외부 부작용/신뢰성 요구가 생긴 다음 I17의 심화로 연결한다.
