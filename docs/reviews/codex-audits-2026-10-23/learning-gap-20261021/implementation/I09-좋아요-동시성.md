# I09 좋아요 동시성: UNIQUE, 조건부 증감, 실제 삭제 행수, 재시도

우선순위: **P0** / 판정: **설명 정확성·기존 회귀테스트 공백 · 이번 동시 DELETE 실험은 통과**

검토일: 2026-10-21 KST. 읽기 전용 정적 감사이며 이 담당자는 원본 수정·빌드·테스트·DB 실행을 하지 않았다. 현재 작업 중인 worktree의 파일을 읽었으므로 아래 SHA256 manifest 시점의 판단이다. 기존 문서의 실행 성공 기록은 과거 기록이며 이번 실행으로 표시하지 않는다. 학습자 미구현은 의도된 실습 상태다. 아래 기존 학습자 상태는 main 및 기존 두 worktree의 확보 시점 기준이다. 감사 중 별도로 발견한 common-learning-foundation의 새 학습자 소스는 해당 항목의 추가 확인 단락으로 구분한다.

## 학습 계약

동일회원 PUT 경쟁과 다른회원 카운트 경쟁을 따로 해결한다. 실제 관계 변경이 일어난 요청만 count를 갱신하고 실패 시 두 쓰기가 함께 rollback된다. DELETE도 같은 수준으로 검증한다.

## 실제 학습자 코드·정답·문서·UI의 상태

4-2 정답은 INSERT IGNORE 반환값>0 때 원자 increment, DELETE 반환값>0 때 decrement, TransactionTemplate 바깥 ConcurrencyFailureException 재시도와 최종 숫자 SELECT를 구현한다. 테스트에는 20회원 PUT 및 동일회원5 PUT이 있다. 댓글5-3은 명시적 조건부 softDeleteIfLive 영향행수1만 감산하는 안전한 대조 사례다. 메인 담당자가 정답 4-2를 별도 폴더로 복원한 Boot4.1.1/Hibernate7.4.5/MySQL8.4.11 환경에서 기존 PUT 테스트2개가 통과했다. 추가로 동일회원5동시 DELETE×20라운드(100호출)는 모두 예외 없이 종료했고 매 라운드 관계0/count0이었다. 동시 DELETE 데이터손상은 이번에 재현되지 않았다.

## 빠진 설명·직접 연습·합격 판정

좋아요 Repository의 deleteByPost_IdAndMember_Id는 @Query DELETE가 없는 파생 delete다. Service는 그 반환값을 실제 삭제영향행수처럼 사용하므로 동일회원 동시 DELETE에서 반환값·flush·stale row 오류를 반환 의미를 바로잡아야 한다. 이번 MySQL 동시 DELETE 결과는 성공이며, 이를 기존 교육 회귀테스트에 편입하는 보완이 필요하다. 현재 LikeConcurrencyTest에 DELETE·PUT/DELETE 혼합·초기오염 reset 검증이 없다. 동일회원 PUT 테스트는 해당회원행1만 단언하고 전체 counter 정합성은 따로 단언하지 않는다. 두 테스트가 동일 post16을 공유하고 시작 초기화가 없어 메서드 실행순서와 잔존 상태가 실험에 영향을 줄 수 있다.

## 보완할 과제: 입력·전후 상태·SQL·실패

격리 fixture를 매 테스트 명시 초기화한다. (A) 20회원 PUT (B) 없는관계에 같은회원5 PUT (C) 있는관계에 같은회원5 DELETE (D) 같은회원 PUT/DELETE 동시 (E) INSERT 성공 뒤 count UPDATE 강제실패. SQL 각 호출의 영향행수·최종행집합·count·오류를 수집한다. 혼합의 최종 상태는 성공한 직렬화 순서 중 하나로 해석하고 특정 순서를 강제하지 않는다.

## 관찰 가능한 합격 기준

모든 작업 종료/예외를 수집하고 count=COUNT(post_like) 및 음수없음을 각 케이스 단언한다. 동일회원 DELETE가 모두200이라는 계약과 실제 ORM 동작을 대조한다. 재시도 전에 실패 tx가 끝났고 새 tx에서 전체 업무가 다시 실행되는지 확인한다.

## 한계와 정확성 확인

공식 Spring Data JPA 4.1.1 DeleteExecution 코드는 대상 목록 SELECT 후 em.remove를 호출하고 숫자 반환에는 resultList.size()를 쓴다. 따라서 이 파생delete 반환값은 native DELETE의 SQL 영향 행수가 아니다. 이것만으로 최종 숫자 손상을 단정할 수 없고 이번 20라운드는 정합성을 지켰다. TransactionTemplate 기본 REQUIRED는 기존 tx에 참여한다. 메인 담당자의 바깥 tx에서 like 후 예외를 던진 실험은 최종 rows0/count0으로 둘 다 rollback돼, 항상 독립 새 tx라는 표현이 틀렸음을 실측했다. INSERT IGNORE는 중복 외 일부 오류도 warning으로 낮출 수 있어 반환0을 중복의 유일 증거로 가르치면 안 된다. 실행과 공식 근거를 함께 확인한 설명 수정 사항이지 기존 Controller 경로의 기능 실패 판정은 아니다.
