# I04 상세 조회: Optional, 가시성, DTO, 조회수 쓰기

우선순위: **P1** / 판정: **계약·화면 있음 · 자기 코드로 옮기는 연결 필요**

검토일: 2026-10-21 KST. 읽기 전용 정적 감사이며 이 담당자는 원본 수정·빌드·테스트·DB 실행을 하지 않았다. 현재 작업 중인 worktree의 파일을 읽었으므로 아래 SHA256 manifest 시점의 판단이다. 기존 문서의 실행 성공 기록은 과거 기록이며 이번 실행으로 표시하지 않는다. 학습자 미구현은 의도된 실습 상태다. 아래 기존 학습자 상태는 main 및 기존 두 worktree의 확보 시점 기준이다. 감사 중 별도로 발견한 common-learning-foundation의 새 학습자 소스는 해당 항목의 추가 확인 단락으로 구분한다.

## 학습 계약

ID를 받아 존재 없음과 볼 수 없음을 구분해 같은 404로 숨기고, 허용된 조회만 조회수를 바꾼다. 연관 필드를 DTO로 바꾸는 시점과 트랜잭션 종료 시점을 이해한다.

## 실제 학습자 코드·정답·문서·UI의 상태

학습자 Controller는 단건 TODO다. 2-1과 2-3 정답에는 findById→정책→조회수→DTO가 있으며 functional 상세는 4개 상태와 읽기처럼 보이는 쓰기 tx를 제시한다. 현재 상세 정본의 동시 GET 갱신손실 한계도 caveat로 적혀 있다.

## 빠진 설명·직접 연습·합격 판정

Optional.orElseThrow와 “존재하지만 비공개”의 별도 판단을 직접 만드는 짧은 발판이 필요하다. 최신 functional은 정책과 DTO helper를 제공하므로 lazy 접근 예외와 응답 필드를 스스로 선택하는 연습은 별도다. practice M1의 작성자 본인 조회수 제외와 본편 “호출마다+1”도 서로 다른 계약임을 명확히 연결해야 한다.

## 보완할 과제: 입력·전후 상태·SQL·실패

입력: 앞 생성 응답 id, 익명/작성자/차단회원. 전: view_count=v. 후: 허용 200은 v+1, 404는 v. SELECT post 후 author/tag 읽기와 UPDATE 시점을 기록한다. DTO를 tx 밖에서 만든 변형은 실제 OSIV 설정을 먼저 확인한다. 누락id와 abc, 비공개 글을 비교한다.

## 관찰 가능한 합격 기준

404 요청 뒤 DB 숫자 불변, 200의 필드와 v+1 일치, 연속 2회 v+2, updated_at 불변을 검증한다. 단일요청 합격을 동시성+N 보장으로 확대하지 않는다.

## 한계와 정확성 확인

학습자 application.yml은 OSIV=false가 활성 설정에 없는 반면 정답은 false다. 예외 재현 결과를 설정 확인 없이 일반화하지 않는다.

## 추가 common worktree 확인

 common의 getPosts 반환 Entity를 HTTP 요청 밖에서 PostResponseDto로 바꾸는 추가 실험은 tags 접근에서 LazyInitializationException이 났다. 같은 코드의 MockMvc HTTP 목록은 성공했으므로 OSIV 요청 경계와 Service 반환경계를 구분하는 실제 전이 과제로 사용할 수 있다.
