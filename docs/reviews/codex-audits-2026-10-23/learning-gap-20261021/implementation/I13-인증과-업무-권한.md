검토일: 2026-10-21 KST. 읽기 전용 정적 감사이며 이 담당자는 원본 수정·빌드·테스트·DB 실행을 하지 않았다. 현재 작업 중인 worktree의 파일을 읽었으므로 아래 SHA256 manifest 시점의 판단이다. 기존 문서의 실행 성공 기록은 과거 기록이며 이번 실행으로 표시하지 않는다. 학습자 미구현은 의도된 실습 상태다. 아래 기존 학습자 상태는 main 및 기존 두 worktree의 확보 시점 기준이다. 감사 중 별도로 발견한 common-learning-foundation의 새 학습자 소스는 해당 항목의 추가 확인 단락으로 구분한다.

## 학습 계약

신원확인과 객체접근권한, 작성권한을 분리한다. 누락토큰·잘못된토큰·비활성회원·비가시객체의 오류를 구분하고 목록과 상세가 일관된 규칙을 따른다.

## 실제 학습자 코드·정답·문서·UI의 상태

1-6 토큰, 2-3 상세/목록 가시성, functional의 권한 선행순서가 있다. PostAccessPolicy는 삭제·status·FOLLOWERS·양방향차단·알수없는visibility를 검사한다. 수정은 작성자만, 삭제는 canView를 통과한 작성자/ADMIN이며 ADMIN 무조건우회가 아니다.

## 빠진 설명·직접 연습·합격 판정

functional이 정책 자체를 제공하므로 호출문을 채워도 정책을 설계하지는 않는다. 상세 자바와 목록 JPQL의 조건은 의도적으로 두 곳에 있으며 수정 시 동등성을 검증하는 테스트 행렬을 학습자가 만들 필요가 있다. “같은 규칙”이라는 말만으로 드리프트를 막을 수 없다. practice R1과 본편의 세부조건은 별도계약으로 대조해야 한다.

## 보완할 과제: 입력·전후 상태·SQL·실패

행렬: viewer 익명/본인/팔로워/비팔로워/차단/ADMIN × post PUBLISHED PUBLIC/FOLLOWERS/DRAFT/HIDDEN/deleted. 먼저 상세 기대코드와 목록포함 여부를 채운다. 이후 대표값만 Policy 순수테스트와 Repository DB테스트로 옮긴다. 수정/삭제/좋아요가 같은 canView 결과 뒤 어떤 별도권한을 더하는지 적는다.
