# I16 스키마 제약과 마이그레이션: 업무규칙의 최종 경계

우선순위: **P1** / 판정: **DDL·Flyway 심화 있음 · 첫 관계설계와 연결 부족**

검토일: 2026-10-21 KST. 읽기 전용 정적 감사이며 이 담당자는 원본 수정·빌드·테스트·DB 실행을 하지 않았다. 현재 작업 중인 worktree의 파일을 읽었으므로 아래 SHA256 manifest 시점의 판단이다. 기존 문서의 실행 성공 기록은 과거 기록이며 이번 실행으로 표시하지 않는다. 학습자 미구현은 의도된 실습 상태다. 아래 기존 학습자 상태는 main 및 기존 두 worktree의 확보 시점 기준이다. 감사 중 별도로 발견한 common-learning-foundation의 새 학습자 소스는 해당 항목의 추가 확인 단락으로 구분한다.

## 학습 계약

PK/FK/UNIQUE/CHECK가 각각 어떤 나쁜 상태를 막는지 알고, Service의 사전검사와 DB 최종 보장의 역할을 구분한다. 현재 DB와 설정이 어느 실습계약인지 식별한다.

## 실제 학습자 코드·정답·문서·UI의 상태

community DDL에는 좋아요유니크·각FK·카운터음수금지, tag이름유니크가 있다. 9-1은 기존DB baseline vs 빈DB V1, ddl-auto validate를 제시하고 9-5는 dualwrite/backfill/read전환/drop 순서를 가르친다. 학습자 활성설정은 mysql localhost3306 및 ddl-auto update로 정답13308/validate와 다르다.

## 빠진 설명·직접 연습·합격 판정

초기 학습자는 @Entity만 붙이면 요구된 스키마가 생긴다고 생각하기 쉽다. post_txt와 기존 post의 차이, community/practice/project, dump초기화와 Flyway변경을 자기 코드 시작점에서 먼저 대조해야 한다. 좋아요·댓글·태그를 만들기 전에 해당 제약을 읽는 mini과제가 필요하다. 모든 고급 마이그레이션을 선행 학습시킬 필요는 없다.

## 보완할 과제: 입력·전후 상태·SQL·실패

각관계 기능에 DDL1장 작성: post_like FK2개+UNIQUE2열, comment parent FK와 Service깊이검사, post_tag 복합키. 격리DB에서 중복관계/없는부모/음수카운터를 넣어 DB가 막는것과 다른글부모/2단계초과처럼 Service가 막아야 할 것을 비교한다. 변경 실습은 기존DB를 백업하고 새 migration을 적용하는 별도선택과제로 둔다.

## 관찰 가능한 합격 기준

현재 접속 DB/포트/스키마를 확인하고 학습자 post_txt와 과제 post를 혼동하지 않는다. 사전exists 검사만으로 UNIQUE를 대신하지 않는다. 기존행 보존 및 새제약 검증결과를 기록한다. Flyway baseline은 스키마동등성 검증 자체가 아님을 설명한다.

## 한계와 정확성 확인

활성3306설정이 사용자의 다른MySQL과 맞는지 이 감사에서는 접속하지 않았으므로 “잘못된 포트”로 단정하지 않는다. 운영마이그레이션 적용이나 데이터리셋은 실행하지 않는다.
