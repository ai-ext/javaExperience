# I03 게시글 생성: 문자열 입력을 기존 엔티티와 새 엔티티로 해석

우선순위: **P0** / 판정: **완성 경로 있음 · 최소 관계형 생성 발판 부족**

검토일: 2026-10-21 KST. 읽기 전용 정적 감사이며 이 담당자는 원본 수정·빌드·테스트·DB 실행을 하지 않았다. 현재 작업 중인 worktree의 파일을 읽었으므로 아래 SHA256 manifest 시점의 판단이다. 기존 문서의 실행 성공 기록은 과거 기록이며 이번 실행으로 표시하지 않는다. 학습자 미구현은 의도된 실습 상태다. 아래 기존 학습자 상태는 main 및 기존 두 worktree의 확보 시점 기준이다. 감사 중 별도로 발견한 common-learning-foundation의 새 학습자 소스는 해당 항목의 추가 확인 단락으로 구분한다.

## 학습 계약

boardSlug를 board_id로, 인증회원 id를 author_id로, 태그 이름을 tag/post_tag로 해석한다. 데이터베이스 기본값과 Java 생성자 기본값의 책임을 구분하고 생성 id를 다음 요청에 전달한다.

## 실제 학습자 코드·정답·문서·UI의 상태

1-3→1-4 정답은 Board·Member @ManyToOne, Tag @ManyToMany와 생성자 카운터0을 갖는다. functional create는 board 존재·쓰기역할·작성자 출처·PUBLIC 기본값·201 Location·같은 id 재사용을 모두 명시한다. 최신 자료에 작성 흐름이 없다고 할 수 없다.

## 빠진 설명·직접 연습·합격 판정

학습자는 post_txt에 boardSlug와 tags를 직접 저장한다. 이 단계에서 Entity 필드와 DTO 필드가 달라도 되는 이유, 본문 authorId를 신뢰하지 않는 이유, 기존 참조와 새 저장을 고르는 판단을 직접 손으로 바꾸는 최소 과제가 없다. 완성 정답은 여러 규칙을 한 번에 도입한다.

## 보완할 과제: 입력·전후 상태·SQL·실패

태그 없는 글 생성부터 시작한다. 입력은 boardSlug=dev, title/content, 토큰회원2. 전: board와 member만 존재. 후: post(board_id=dev의 실제id,author_id=2)1행. 다음 단계에서 tag 한 개만 추가한다. SELECT board WHERE slug, 참조회원 확인, INSERT post, INSERT post_tag를 DB 실제 열에 적어 본다. 존재하지 않는 board·본문 authorId 위조·비관리자 notice 요청을 실패케이스로 둔다.

## 관찰 가능한 합격 기준

201 body.id와 Location 및 DB PK가 일치하고, HTTP 본문 작성자 위조가 DB author_id에 영향을 주지 않는다. 카운터와 시각을 생성 직후 검산한다. FK 대상이 존재하지 않으면 부분 저장이 남지 않는다.

## 한계와 정확성 확인

List<String>의 @Column 매핑이 무조건 오류라고 단정하지 않는다. 여기서 확실한 차이는 태그 관계 테이블 계약과 현재 post_txt 저장 모델이 다르다는 점이다. 메인 담당자의 격리 MySQL 실행에서는 tags 두 개가 JSON 저장·조회 왕복에 성공했다. 따라서 저장 자체는 동작하며 관계 테이블 설계로 전환할 이유를 요구사항에서 배워야 한다.

## 추가 common worktree 확인

common에서는 별도 TagsEntity를 만들고 태그 저장 후 글 저장하는 구현이 있다. 관계 생성 자체가 전혀 없다는 판정은 폐기해야 한다. 다만 boardSlug 문자열, 인증 작성자 연결 부재, 기존 tag 재사용 없이 매번 새 태그 생성이라는 정답 계약과의 차이가 남는다. 메인 담당자의 일회용 MySQL/선언된 community seed 실행에서 tags=[]는 POST 뒤 목록 GET까지 성공했다. 비어 있지 않은 tags는 tag.name 필수열과 TagsEntity.title 매핑 차이로 DataIntegrityViolationException이 재현됐고 tag/post_txt는 추가되지 않았다. 사용자의 별도 개발 DB 스키마 전체에서 같은 결과가 난다고 일반화하지 않는다.
