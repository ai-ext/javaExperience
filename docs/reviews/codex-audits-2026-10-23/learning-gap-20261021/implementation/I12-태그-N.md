# I12 태그 N:M: 중복 제거와 공유 엔티티의 생명주기

우선순위: **P0** / 판정: **매핑·연결교체 자료 있음 · 최신 학습자 seed/매핑 충돌 재현**

검토일: 2026-10-21 KST. 읽기 전용 정적 감사이며 이 담당자는 원본 수정·빌드·테스트·DB 실행을 하지 않았다. 현재 작업 중인 worktree의 파일을 읽었으므로 아래 SHA256 manifest 시점의 판단이다. 기존 문서의 실행 성공 기록은 과거 기록이며 이번 실행으로 표시하지 않는다. 학습자 미구현은 의도된 실습 상태다. 아래 기존 학습자 상태는 main 및 기존 두 worktree의 확보 시점 기준이다. 감사 중 별도로 발견한 common-learning-foundation의 새 학습자 소스는 해당 항목의 추가 확인 단락으로 구분한다.

## 학습 계약

문자열목록을 tag 고유행과 post_tag 연결행으로 분리하고 요청중복·DB이름 동등성·동시 생성 충돌을 각각 구분한다. 연결삭제가 공유 tag삭제를 의미하지 않음을 이해한다.

## 실제 학습자 코드·정답·문서·UI의 상태

1-3은 이름 중복제거·기존태그재사용·없는태그생성·@ManyToMany를 제공한다. MyBatis 설명은 DB가 대소문자를 같게 볼 수 있어 태그ID로도 중복제거한다고 명시한다. functional PATCH의 []는 연결만 해제한다. DDL에는 tag.name UNIQUE와 post_tag 복합PK/FK가 있다.

## 빠진 설명·직접 연습·합격 판정

현재 학습자 List<String>에서 두 테이블로 나누는 이유를 한 글이 아니라 두 글이 같은 spring을 쓰는 상태로 확인해야 한다. 한 요청 LinkedHashSet 중복 제거는 동시에 두 글이 새 이름을 만드는 경쟁을 해결하지 않는다. 정답 findByName.orElseGet(save)는 해당 동시성 경계를 별도 실습으로 고정하지 않는다.

## 보완할 과제: 입력·전후 상태·SQL·실패

글A tags=[spring,spring,새태그], 글B tags=[spring]. 전 spring tag1행. 후 tag새태그1행, A연결2/B연결1. A PATCH tags=[] 후 tag행2 및 B연결1 보존. SQL JOIN으로 글별태그를 확인한다. 대소문자/앞뒤공백은 DB collation 및 정규화 정책을 확인한 뒤 기대를 정한다. 선택심화: 두 tx가 같은 새 이름을 생성하고 UNIQUE 예외 시 전체업무 또는 별도 조회를 어떻게 처리하는지 결정한다.

## 관찰 가능한 합격 기준

요청중복 제거와 DB고유성 보장을 별개로 설명하고 공유태그가 남는다. 부모글 삭제에 tag cascade remove를 넣지 않는다. 동시 생성 충돌을 검증하지 않았다면 “태그생성 동시성안전”을 주장하지 않는다.

## 한계와 정확성 확인

기본 @ManyToMany로 충분한 현재 태그에 무조건 연결Entity 리팩터링을 요구하지 않는다. 연결에 createdAt/순서/작성자 같은 속성이 생길 때 별도 Entity를 선택하는 후속 비교가 적절하다.

## 추가 common worktree 확인

common의 태그는 @OneToMany로 한 글에 소유되는 TagsEntity이며 매 요청마다 모든 태그를 새로 만든다. 본편의 동일 이름 tag를 여러 글이 공유하는 N:M과 다른 모델이다. TagsEntity는 tag.title을 쓰지만 본편 DDL은 tag.name NOT NULL/UNIQUE이므로 같은 테이블 이름이 같은 계약을 뜻하지 않는다. 공통 seed와의 충돌은 별도 실행 결과와 대조해야 한다. 메인 담당자가 선언된 community seed로 띄운 일회용 MySQL에서 비어 있지 않은 tags 생성은 DataIntegrityViolationException을 재현했다. TagsEntity.title 저장과 기존 tag.name NOT NULL의 불일치이며 트랜잭션 뒤 tag 행수는 원래대로, 새 post_txt는0이었다. tags=[]의 HTTP 생성·목록은 성공했다. 따라서 단순 문자열 태그→엔티티 분리만으로 기존 스키마 및 공유 규칙까지 충족하는 것은 아니라는 직접 근거가 생겼다.

## 구분해서 읽기

학습자 src는 본인이 구현 중인 프로젝트다. snapshot manifest와 blobs는 단계별 완성 참조 코드다. functional 화면은 제공된 공통 부분과 Service 구현 빈칸을 조합한 별도 과제다. 개념 worktree의 supplemental은 별도 모델/환경의 실험 기록이므로 게시판 API가 구현됐다는 증거가 아니다. HTML은 정적 내용과 참조 연결만 확인했으며 이 담당자는 브라우저에서 실행하지 않았다.
