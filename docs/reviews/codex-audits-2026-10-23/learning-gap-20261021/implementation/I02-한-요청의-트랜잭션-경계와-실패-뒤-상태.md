# I02 한 요청의 트랜잭션 경계와 실패 뒤 상태

우선순위: **P0** / 판정: **설명·실험 있음 · 게시판 실패 설계 전이 부족**

검토일: 2026-10-21 KST. 읽기 전용 정적 감사이며 이 담당자는 원본 수정·빌드·테스트·DB 실행을 하지 않았다. 현재 작업 중인 worktree의 파일을 읽었으므로 아래 SHA256 manifest 시점의 판단이다. 기존 문서의 실행 성공 기록은 과거 기록이며 이번 실행으로 표시하지 않는다. 학습자 미구현은 의도된 실습 상태다. 아래 기존 학습자 상태는 main 및 기존 두 worktree의 확보 시점 기준이다. 감사 중 별도로 발견한 common-learning-foundation의 새 학습자 소스는 해당 항목의 추가 확인 단락으로 구분한다.

## 학습 계약

글·태그·연결을 하나의 업무 단위로 묶고 flush와 commit, DB rollback과 Java 객체 값의 차이를 설명한다. 예외 종류·프록시 호출 경로가 rollback에 미치는 영향도 단계적으로 확인한다.

## 실제 학습자 코드·정답·문서·UI의 상태

1-3에 태그 저장 후 글 실패를 통한 rollback 실습이 있다. functional create/patch에는 별도 observer, IDENTITY, rollback 분기가 명시되어 있다. 개념 S08은 checked/runtime/catch/self-invocation/REQUIRED/REQUIRES_NEW, W11은 저장소별 경계와 서비스 경계의 차이를 이미 다룬다.

## 빠진 설명·직접 연습·합격 판정

초급 문장 “예외가 밖으로 나가면 rollback”은 예외 종류·설정·실제 프록시 경계가 생략된 요약이다. 주문/계좌 실험을 읽은 뒤 자기 게시판에서 실패 지점을 정하고 증명하는 과제가 명시 연결되어 있지 않다. 동일 트랜잭션 재시도와 독립 트랜잭션 재시도의 차이도 좋아요와 연결해야 한다.

## 보완할 과제: 입력·전후 상태·SQL·실패

입력: 신규 태그 이름을 가진 글. 격리 fixture에서 태그 INSERT 뒤 post INSERT가 실패하도록 만든다. 전/후 tag·post·post_tag 행수를 다른 연결의 새 SELECT로 비교한다. 별도 변형으로 RuntimeException, checked exception, catch 후 정상반환을 비교한다. 아직 커밋되지 않은 id와 객체 값이 남아도 DB 행이 0인지 기록한다.

## 관찰 가능한 합격 기준

실패 이전 쓰기를 실제 실행한 증거, rollback 후 세 테이블 상태, HTTP 오류, 예외 위치를 함께 제시한다. 입력 검증 단계에서 막힌 400을 “DB rollback 검증”으로 채점하지 않는다. 관계 저장 실패 실험에는 DB FK/UNIQUE 발생 시점도 구분한다.

## 한계와 정확성 확인

W11/S08 supplemental의 과거 실행 결과는 이 감사에서 재실행하지 않았다. 모든 예외가 자동 rollback된다는 일반화를 피하고 공식 자료 확인을 병행해야 한다.
