# I15 테스트 작성: HTTP 성공에서 업무 불변식 증명으로

우선순위: **P0** / 판정: **정답테스트·개념실험 있음 · 학습자 기능테스트는 아직 없음**

검토일: 2026-10-21 KST. 읽기 전용 정적 감사이며 이 담당자는 원본 수정·빌드·테스트·DB 실행을 하지 않았다. 현재 작업 중인 worktree의 파일을 읽었으므로 아래 SHA256 manifest 시점의 판단이다. 기존 문서의 실행 성공 기록은 과거 기록이며 이번 실행으로 표시하지 않는다. 학습자 미구현은 의도된 실습 상태다. 아래 기존 학습자 상태는 main 및 기존 두 worktree의 확보 시점 기준이다. 감사 중 별도로 발견한 common-learning-foundation의 새 학습자 소스는 해당 항목의 추가 확인 단락으로 구분한다.

## 학습 계약

순수업무 분기 unit, Repository SQL/제약 integration, HTTP 계약, 실제 commit/rollback 및 동시성 검증의 역할을 구분하고 필요한 검사를 직접 작성한다.

## 실제 학습자 코드·정답·문서·UI의 상태

학습자 테스트는 HelloControllerTest 한 개다. 정답snapshot은 4-2 동시성테스트와 2-4 SQL수테스트를 제공한다. V04 supplemental은 mock repository unit이 DB/프록시를 검증하지 않는다는 범위, flush없이rollback의 거짓양성, HTTP server tx와 동기MockMvc/testtx의 차이를 상세히 다룬다. 따라서 테스트 교육자료 자체 부재는 아니다.

## 빠진 설명·직접 연습·합격 판정

“AI에 채점 프롬프트를 붙여넣기”와 학습자가 자신의 실패케이스를 테스트코드로 쓰는 능력은 분리되어야 한다. functional의 화면 검사 스크립트는 교육UI/정본을 검증하는 도구이지 학습자 Service 완성 증거가 아니다. starter 완료 시 자신의 테스트를 추가하는 점진 과제가 필요하다.

## 보완할 과제: 입력·전후 상태·SQL·실패

첫 과제는 공개권한Policy 3케이스 unit, 다음 댓글 INSERT+count 정합 DB테스트, 다음 MockMvc201/400, 마지막 실제commit후 별도연결조회다. 테스트 데이터는 suite마다 격리하며 부모→자식 생성, 자식→부모 정리. 실패 주입으로 한쪽쓰기만 남으면 반드시 실패하는 테스트를 만든다. 병렬테스트는 ready/start/done과 Future/예외를 모은다.

## 관찰 가능한 합격 기준

정답 코드를 일부러 망가뜨려 테스트가 실제로 실패한 뒤 복구해 통과해야 한다. HTTP만 보는 테스트에 DB보장 표시 금지. SQL 실행전 rollback으로 제약이 확인되지 않는 거짓양성을 막는다. 기존 로그를 이번 실행성공으로 표시하지 않는다.

## 한계와 정확성 확인

4-2 snapshot 주석은 테스트@Transactional이 다른 스레드에 자동 공유되는 듯 쓰여 있으나 실제 스레드바인딩 확인이 필요하다. 또한 테스트 초기화/독립성 문제는 I09에서 다룬다. 이번 메인 담당자는 원본을 격리 복사해 기존1개+감사6개를 실행했다. 감사의 통과조건에는 NPE 등 문제행동의 재현도 포함되어 7개통과가 기능정상을 뜻하지 않는다.

## 추가 common worktree 확인

common은 학습자 소스가 다른 새 비교대상이며 main 실행 7개 결과를 그대로 적용할 수 없다. 새 관계매핑과 예외처리에 대한 별도 메인 실행의 결과를 함께 참조한다. 메인 담당자의 common 별도 관찰4개는 실패0이었다. 정상 빈태그 생성·목록뿐 아니라 비어 있지 않은 태그의 DB제약 예외와 요청 밖 DTO의 lazy 예외가 재현되는 것도 테스트 통과조건이다. 이 결과를 전체기능정상으로 읽지 않는다.
