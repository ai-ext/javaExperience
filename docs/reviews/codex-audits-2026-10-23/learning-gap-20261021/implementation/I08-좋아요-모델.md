# I08 좋아요 모델: Boolean에서 회원-글 관계와 멱등으로

우선순위: **P0** / 판정: **내용 있음 · 학습자 모델에서 넘어가는 핵심 발판 부족**

검토일: 2026-10-21 KST. 읽기 전용 정적 감사이며 이 담당자는 원본 수정·빌드·테스트·DB 실행을 하지 않았다. 현재 작업 중인 worktree의 파일을 읽었으므로 아래 SHA256 manifest 시점의 판단이다. 기존 문서의 실행 성공 기록은 과거 기록이며 이번 실행으로 표시하지 않는다. 학습자 미구현은 의도된 실습 상태다. 아래 기존 학습자 상태는 main 및 기존 두 worktree의 확보 시점 기준이다. 감사 중 별도로 발견한 common-learning-foundation의 새 학습자 소스는 해당 항목의 추가 확인 단락으로 구분한다.

## 학습 계약

likedByMe는 특정 회원과 글 사이 관계의 존재이고 likeCount는 모든 관계행의 합계임을 구분한다. PUT/DELETE를 원하는 상태로 만드는 연산으로 설계한다.

## 실제 학습자 코드·정답·문서·UI의 상태

학습자 PostEntity에는 Boolean heart 하나가 있다. 4-0은 PUT만 단계적으로 만들고 4-1은 취소·반복요청·본인글·인증·가시성 계약을 제공한다. UNIQUE(post_id,member_id)도 실제 DDL에 있다. 10-10 토글과 10-11 멱등은 별도 프로젝트 실습이다. 이번 메인 담당자 실행에서는 nullable heart를 boolean getter로 읽어 DTO를 만드는 경로의 NPE가 재현됐다. 이는 Boolean 기본값/응답 계약 문제이며 회원별 관계를 표현하지 못하는 모델 문제와 따로 구분한다.

## 빠진 설명·직접 연습·합격 판정

Boolean 하나로는 회원2와 회원3의 서로 다른 좋아요 여부를 저장할 수 없다는 반례를 직접 DB 행으로 만드는 과제가 필요하다. 4-0의 설명은 좋은 발판이지만 최신 functional 5개에는 좋아요 task가 없어 CRUD 완료 후 동일한 빈칸 방식이 이어지지 않는다. 토글이라는 파일명과 멱등 API 내용의 차이도 혼동 지점이다.

## 보완할 과제: 입력·전후 상태·SQL·실패

전: post3 like_count=0, 관계 없음. 회원2 PUT→(3,2)1행/count1, 회원2 PUT 반복→그대로, 회원3 PUT→(3,3)추가/count2, 회원2 DELETE→(3,3)만/count1, 반복 DELETE→그대로. 요청마다 토큰회원·관계집합·count·likedByMe를 직접 표로 쓴다. SELECT COUNT WHERE post_id와 WHERE post_id AND member_id를 따로 작성한다.

## 관찰 가능한 합격 기준

반복 PUT/DELETE마다 행수와 count가 일치하며 본인글400·비활성403·비가시404·무인증401에 쓰기없음. 입력 본문의 memberId/likeCount를 믿지 않는다. 정확한 count는 요청횟수가 아니라 실제 관계 변경 횟수로 계산한다.

## 한계와 정확성 확인

4-0/4-1의 순차 구현은 교육용이고 동시성 안전 보장은 4-2의 별도 과제다. 기존 내용이 없다는 평가보다 현재 학습자 모델과의 비교 과제를 최우선으로 추가한다.

## 추가 common worktree 확인

common에서는 heart가 primitive boolean이라 앞선 nullable Boolean 자동언박싱 NPE 원인은 제거되어 있다. 하지만 Boolean 한 필드로 회원별 좋아요 관계를 표현하지 못하는 모델링 문제는 그대로다. main NPE 실행 결과를 common 결함으로 확대하지 않는다. common의 태그 없는 HTTP 생성→목록 흐름은 이번 실험에서200/200, like=false였다. primitive heart 변경이 기존 NPE 원인을 제거했다는 범위까지 확인됐으며 회원별 좋아요 관계를 구현했다는 뜻은 아니다.
