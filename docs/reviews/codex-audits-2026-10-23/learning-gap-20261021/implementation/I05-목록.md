## 학습 계약

응답 필드에서 필요한 JOIN과 WHERE를 도출하고, 정렬 동률과 페이지 경계를 만든다. 목록 필터와 COUNT 조건을 맞추며 쿼리 수와 반환 의미를 함께 검증한다.

## 실제 학습자 코드·정답·문서·UI의 상태

2-2는 OFFSET 및 입력 범위, 2-3은 가시성을 DB에서 필터, 2-4는 쿼리 수 상한과 size 비교, 2-5는 SQL→JPQL 연습을 제공한다. functional 목록은 Service 빈칸이나 JPQL·정책은 제공된다. concept W09의 projection과 W15의 cursor/Page/Slice 실험도 이미 있다.

## 빠진 설명·직접 연습·합격 판정

학습자의 findAll 기반 목록에서 게시판 필터 한 개→정렬→limit→author JOIN→tags IN으로 증가하는 구현 경로가 산재한다. 완성된 findViewableByBoard 호출만 채우면 SELECT를 스스로 설계할 수 있는지 드러나지 않는다. OFFSET 본편과 cursor practice, 다른 정렬키의 내좋아요 목록을 섞으면 경계가 달라진다.

## 보완할 과제: 입력·전후 상태·SQL·실패

입력: 같은 published_at의 글 3개, page0 size2와 page1 size2. 전/후 데이터는 불변. SQL은 게시판 확인·조건있는 목록·동일조건 COUNT·태그 IN을 각각 작성한다. 익명/팔로워/차단으로 기대 id 집합을 먼저 적고 조회한다. size5/20의 실제 SQL 수를 비교한다. content를 DTO에서 제거하는 것과 DB에서 그 열을 읽지 않는 projection도 비교한다.

## 관찰 가능한 합격 기준

동률 중복/누락 없음, 목록과 total 일관, content 미노출, 2-4의 실제 문장수 기준 충족 및 응답 불변. collection fetch join에 페이지를 붙인 경우 프레임워크 버전·경고·반환행을 실제로 확인한다.

## 한계와 정확성 확인

개념 S09에는 Hibernate7.4.5에서 API max와 HQL limit의 세부 차이 실험까지 있다. “fetch join이면 항상 같은 경고/동작”으로 고정하지 않는다. 이번 감사는 기록을 읽었고 성능 측정은 하지 않았다.

## 추가 common worktree 확인
