## 개발 순서

1. **P0: 실행과 판정부터 안정화한다.** 오래된 접속 안내·독립 시작점·단계별 검사·쿼리의 독립 기대값을 먼저 고친다(X01/X02). 정답이 맞아도 학습자가 실행하거나 실패를 구별하지 못하면 새 시나리오를 추가해도 효과가 작다.
2. **P1: 서버·DB의 상태와 실패를 깊게 다룬다.** X03~06, X08~16, X20. 기존 본편·티켓의 정상 구현을 출발점으로 삼고 새로운 실패 창과 복구를 붙인다.
3. **P2: 선택 심화와 종합 과제로 전이한다.** 고급 SQL(X07), 두 노드 캐시/외부 호출(X17/X18), 모듈형 모놀리스와 서비스 분리 판단(X19). MSA 구현 자체를 필수 정답으로 삼지 않는다.

## 찾아가는 경로의 완료 조건

- 증상으로 시작할 수 있어야 한다: “목록이 느림”→N+1/실행계획→인덱스 실험, “중복 저장”→UNIQUE/경합→멱등, “200인데 DB 그대로”→트랜잭션/영속상태.
- 각 화면에는 필요한 선행 단계, 실행할 시작 코드/DB, 지금 해야 할 일, 비교할 결과, 막혔을 때 볼 자료, 다음 과제가 직접 연결되어야 한다.
- 이름만 적힌 “노하우 랩 L2/L3/L5…”은 실행 링크를 확인하기 전까지 학습 경로가 갖춰졌다고 세지 않는다. 현재 저장소의 `scenario/labs`에는 L12~L16이 있다. 외부 서비스에 해당 랩이 존재하는지는 이번 저장소 감사에서 확인하지 않았다.
- 원문 링크의 존재, 화면 진입, 서버 실행, DB 결과, 고급 실패 복구는 서로 다른 검증이다. 한 가지 성공을 다른 단계의 완료로 올리지 않는다.

## 공식 기준의 용도

심화 설계는 Luna의 공식 자료 조사와 메인의 원문 확인을 사용했다. 예를 들어 DDL은 다른 세션의 미완료 트랜잭션이 가진 metadata lock 때문에 대기할 수 있으므로, 무중단 과제에 실제 대기와 회복을 넣는다. [MySQL 8.4 Metadata Locking](https://dev.mysql.com/doc/refman/8.4/en/metadata-locking.html)

인덱스 과제는 추정 계획과 실제 실행을 구분한다. `EXPLAIN ANALYZE`의 시간은 해당 반복자와 실행 환경의 관측이므로 실제 API 전체 지연의 증거로 대체하지 않는다. [MySQL 8.4 EXPLAIN](https://dev.mysql.com/doc/refman/8.4/en/explain.html)

빈 실습은 컨테이너·빈 정의별 singleton 공유 범위에서 출발한다. 이는 요청별 가변 상태를 안전하게 만들어 주는 계약이 아니므로 교차 요청 실험을 별도로 둔다. [Spring Framework Bean Scopes](https://docs.spring.io/spring-framework/reference/core/beans/factory-scopes.html)

기존 개념 문서의 실습도 누락 여부를 대조하는 보조 근거로 사용했다. 특히 R07의 기본 복원 절차를 없다고 세지 않았으며, 집합 연산 사용 예시와 독립 SQL 과제를 구분했다: [/Users/ds/code/javaExperience/.worktrees/concept-census-20261021/docs/knowledge/R07-backup-restore.md](/Users/ds/code/javaExperience/.worktrees/concept-census-20261021/docs/knowledge/R07-backup-restore.md).
