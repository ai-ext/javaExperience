## 배포·release·환경

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 기술적으로 artifact를 배포하는 일과 사용자에게 기능을 공개하는 release는 다르다. 같은 artifact를 local/dev/stg/prod 환경으로 승격할 수 있다.

**언제 사용하는가:** 산출물·배포·사용자 공개 시점을 구분해 계획할 때 사용한다.

**대안과 경계:** deployment는 실행 환경에 전달하는 기술 작업이고 release/launch는 사용자에게 기능을 제공하는 결정이다.

**예시·실행 근거:** 한 번 만든 동일 JAR를 여러 환경에서 실행하고 배포와 기능 공개의 시점을 비교한다.

**선수개념:** artifact; 환경 설정

**관련 표기·별칭:** Deploy, release and environment

**보완·검증 필요 사항:**

- 추가 실험은 로컬 profile을 관찰했을 뿐 운영 환경 배포는 하지 않았다.

**초보자가 시작할 질문:**

- JAR를 배포했는데 사용자는 왜 새 기능을 보지 못할 수 있나?

## rolling·blue-green·canary·feature flag 전략

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** rolling, blue-green, canary는 traffic을 새 버전으로 옮기는 방식이고 feature flag는 배포된 기능을 노출할지 제어한다.

**언제 사용하는가:** 서버 교체와 사용자 대상 기능 공개를 분리할 때 사용한다.

**대안과 경계:** 어떤 전략도 단독으로 무중단을 보장하지 않는다. capacity, 호환성, health check와 fallback이 필요하다.

**예시·실행 근거:** 서버 집합 전환과 일부 traffic만 새 버전으로 보내는 순서를 비교한다.

**선수개념:** 배포 artifact; health check

**관련 표기·별칭:** rolling·blue-green·canary·feature flag; Rolling, blue-green, canary, flags

**보완·검증 필요 사항:**

- 본문 개념은 설명 중심이며 실제 Kubernetes rollout은 실행하지 않았다.

**초보자가 시작할 질문:**

- 배포는 끝났는데 특정 사용자에게만 기능을 공개하려면?

## rollback과 schema 호환성

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** expand-contract migration은 이전/새 애플리케이션 버전이 함께 작동하도록 DB schema를 단계적으로 바꾼다.

**언제 사용하는가:** 앱 rollback 가능성을 유지한 채 DB schema를 변경할 때 사용한다.

**대안과 경계:** 앱 artifact를 되돌려도 이미 적용된 DB 변경은 자동으로 되돌아가지 않는다.

**예시·실행 근거:** 구/신규 컬럼을 함께 지원한 뒤 이전 버전 의존을 제거하는 단계와 rollback window를 비교한다.

**선수개념:** DB migration; 배포 버전

**관련 표기·별칭:** Rollback and schema compatibility

**보완·검증 필요 사항:**

- 실제 운영 migration과 복구를 실행하지 않았다.

**초보자가 시작할 질문:**

- 새 schema를 적용한 뒤 앱 버전을 이전으로 바꾸면 DB는 어떻게 되나?
