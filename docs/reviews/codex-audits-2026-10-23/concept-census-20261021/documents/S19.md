## Boot 실행 가능 JAR

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Boot loader와 앱·의존성을 담은 JAR가 manifest의 launcher를 통해 nested JAR를 읽어 Start-Class를 실행한다.

**언제 사용하는가:** `java -jar` 배포 단위를 만들고 JAR 내부 의존성을 포함한 재현 가능한 실행을 원할 때 쓴다.

**대안과 경계:** 일반 `java -cp app.jar Main`은 nested JAR를 classpath로 풀지 않는다.

**예시·실행 근거:** manifest·BOOT-INF 구조와 Dockerfile 추출 예제가 있으나 미실행이다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- Boot 실행 JAR를 `java -cp app.jar Main`으로 실행했더니 라이브러리 클래스를 못 찾는다면 의존성은 어디에 들어 있나요?
- manifest의 Main-Class와 Start-Class가 다른 역할을 하는 이유는 무엇인가요?

## Layered JAR와 이미지 cache

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** JAR 내용을 의존성·loader·앱 코드 등 변경 빈도별 층으로 나누어 각 Docker image layer에 복사한다.

**언제 사용하는가:** 앱 코드가 자주 바뀌고 의존성이 안정적일 때 의존성 layer 재사용으로 배포 전송량을 줄인다.

**대안과 경계:** JAR layer와 Docker image layer는 다르며 계층별 COPY가 없으면 cache 효과가 없다.

**예시·실행 근거:** jarmode=tools extract와 multi-stage Dockerfile을 보여 준다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- 앱 코드만 수정했는데 이미지의 의존성까지 모두 다시 복사된다면 JAR 내부 계층을 어떻게 이미지에 나눠야 하나요?
- JAR에 layer index가 있는데 Dockerfile에서 한 번에 COPY하면 cache 이익이 없는 까닭은 무엇인가요?

## Buildpacks·Dockerfile·Native Image

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Buildpacks는 builder/buildpack으로 OCI 이미지를 만들고 Dockerfile은 각 단계를 명시한다. Native Image는 정적 분석으로 대상 플랫폼 바이너리를 빌드한다.

**언제 사용하는가:** 표준 이미지 단순화에는 Buildpacks, OS·사용자·복사 통제가 필요하면 Dockerfile, 시작/유휴 메모리 목표가 분명하면 Native Image를 평가한다.

**대안과 경계:** Native Image 동적 reflection/resource에는 힌트가 필요하며 JVM CDS/AOT cache와 결과물이 다르다.

**예시·실행 근거:** 도구별 선택표와 native build 명령이 있지만 미실행이다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- Native Image에서 reflection serializer가 빠지거나 시작되지 않는다면 분석 힌트와 JVM AOT cache 중 무엇을 확인해야 하나요?
- 팀이 Dockerfile 운영 부담은 줄이고 표준 Spring 이미지가 필요하면 어떤 builder 경로를 고려하나요?

## probe와 트래픽 수명주기

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** startup은 초기화 허용 시간, readiness는 트래픽 수용, liveness는 재시작 필요 상태를 probe에 전달한다.

**언제 사용하는가:** 느린 초기화는 startup, 필수 서비스 준비는 readiness, 복구 불가능 내부 정지에는 liveness를 사용한다.

**대안과 경계:** 외부 DB를 liveness에 연결하면 장애 때 재시작 폭주가 날 수 있다.

**예시·실행 근거:** Kubernetes YAML에 세 probe와 자원 설정을 보여 주지만 실제 cluster는 미검증이다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- 느린 초기화 중 liveness가 먼저 실패해 Pod가 재시작된다면 어떤 probe가 먼저 성공해야 하나요?
- DB 장애로 readiness가 실패할 때 트래픽 제외와 프로세스 재시작 중 어떤 결과가 의도인가요?

## graceful shutdown·종료 유예

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Boot 서버는 새 요청을 멈추고 진행 요청에 제한 시간을 주며 Kubernetes termination grace가 강제 종료까지의 바깥 시간을 정한다.

**언제 사용하는가:** 애플리케이션 종료 단계, worker/consumer 종료, Kubernetes 유예 시간 순서를 맞춘다.

**대안과 경계:** HTTP graceful shutdown이 모든 background 작업을 완료시킨다고 보장하지 않는다. K8s grace는 Boot timeout보다 길어야 한다.

**예시·실행 근거:** Spring timeout 25초와 Pod grace 40초 예시를 제공한다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- 배포 중 진행 요청이 25초보다 오래 걸리는데 Kubernetes가 40초 뒤 종료한다면 두 시간 제한을 어떻게 맞춰야 하나요?
- 앱이 HTTP 요청을 graceful하게 끝내도 메시지 consumer가 중단될 수 있는 이유는 무엇인가요?
