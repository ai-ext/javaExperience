## cgroup limit·heap/native 예산

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** Linux cgroup은 heap뿐 아니라 native, thread stack, metaspace, code cache, direct buffer 등을 포함한 프로세스 메모리를 제한합니다. HotSpot은 컨테이너 한도를 읽어 기본값을 정할 수 있습니다.

**언제 사용하는가:** 컨테이너 메모리 종료를 조사할 때 `-Xmx`, RSS, cgroup peak를 함께 봅니다.

**대안과 경계:** 컨테이너 limit을 그대로 `-Xmx`로 쓰면 비-heap 공간이 부족할 수 있습니다. 계산 예시는 안전한 여유 공간을 입증하지 않습니다.

**예시·실행 근거:** 1GiB 가상 한도에서 heap을 빼는 예제를 보여 주되 남은 공간이 안전하다는 결론은 내리지 않습니다.

**선수개념:** cgroup; process RSS

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Linux container trace/runtime not captured.

**초보자가 시작할 질문:**

- heap이 640MiB이고 container limit이 1GiB일 때 남은 384MiB가 안전 여유라고 말할 수 없는 이유는?
- Java OOME 없이 OOMKilled가 되는 실행 경로는 어떻게 다른가요?

## CPU quota·ActiveProcessorCount

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** CPU quota는 커널이 허용하는 실행 시간을 제한하고, `-XX:ActiveProcessorCount`는 JVM 내부 pool 산정에 쓰는 CPU 수를 지정합니다.

**언제 사용하는가:** JVM의 감지 값과 실제 quota가 다르고 thread pool 산정이 문제가 될 때만 설정을 검토합니다.

**대안과 경계:** 이 옵션은 cgroup quota나 애플리케이션 thread 수를 바꾸지 않습니다.

**예시·실행 근거:** JDK 21에서 ActiveProcessorCount=2를 명시한 ContainerProbe 실행을 기록합니다.

**선수개념:** container CPU; ForkJoinPool

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Host macOS run does not verify Linux cgroup detection.

**초보자가 시작할 질문:**

- ActiveProcessorCount를 2로 바꾸면 Docker CPU quota도 2로 바뀌나요?
- quota를 잘못 감지하면 GC/common pool 크기에 어떤 영향이 생기나요?

**근거:**

## RSS와 NMT·OOM 분류

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** NMT는 HotSpot 내부 메모리 일부를 추적하고 RSS는 OS에서 실제 상주하는 페이지를 뜻합니다. OOMKilled는 커널 종료일 수 있으며 Java OOME 예외와 다릅니다.

**언제 사용하는가:** Pod 종료 이벤트·cgroup 최고치·RSS·NMT 요약과 차이를 함께 비교합니다.

**대안과 경계:** NMT는 모든 native 사용량을 포함하지 않고 committed와 RSS도 같지 않습니다. 종료 코드 137만으로 OOM 원인을 확정할 수 없습니다.

**예시·실행 근거:** jcmd VM.native_memory 명령과 실패 원인 구분표를 제시합니다.

**선수개념:** native memory; Kubernetes status

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 실제 container incident logs not present.

**초보자가 시작할 질문:**

- exit 137만 보고 OOM이 확실하다고 할 수 없는 이유는 무엇인가요?
- NMT 값과 RSS가 다르면 어느 쪽이 틀렸다고 결론낼 수 있나요?

**근거:**

## CDS/AOT cache·CRaC·Native Image

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** CDS/AOT cache는 HotSpot에서 클래스·링크·프로파일 자료를 재사용하고, CRaC는 JVM checkpoint 복원, Native Image는 별도 native 실행 파일 생성 방식입니다.

**언제 사용하는가:** 시작 시간과 실제 부하 특성에 맞춰 동일한 시나리오로 비교 측정합니다.

**대안과 경계:** AOT cache도 HotSpot을 사용합니다. CRaC에는 자원 재연결 처리가 필요할 수 있고 Native Image는 reachability metadata와 다른 런타임 특성을 갖습니다.

**예시·실행 근거:** JDK 25 AOT 명령과 CRaC·Native Image 차이를 비교합니다.

**선수개념:** class loading; runtime resource lifecycle

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- No AOT/CRaC/native image execution proof.

**초보자가 시작할 질문:**

- AOT cache와 Native Image가 둘 다 ahead-of-time인데 결과 실행 환경은 어떻게 다른가요?
- CRaC restore 뒤 DB socket을 다시 연결해야 하는 이유는?

## JDK flags in actual container

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** 컨테이너 안에서 `os+container` 로그, PrintFlagsFinal, cgroup 수치를 읽어 실제 JVM 인식 값을 확인합니다.

**언제 사용하는가:** 배포 대상과 동일한 Linux 이미지·제약에서 JVM 옵션을 검증합니다.

**대안과 경계:** macOS 호스트에서 측정한 값은 Linux 컨테이너의 cgroup 인식을 증명하지 않습니다.

**예시·실행 근거:** 문서의 명령 예와 Java 21 probe의 실제 출력 기록을 구분합니다.

**선수개념:** JDK options; Linux cgroup

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Container runtime command not run.

**초보자가 시작할 질문:**

- `java -XX:+PrintFlagsFinal`을 호스트에서 실행한 값으로 container limit 적용을 증명할 수 있나요?
