## 요구 불확실성을 줄이는 API 작업 순서

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** 요구의 주체·성공·실패 의미를 먼저 구체화하고 HTTP 계약·저장 불변식을 정한 뒤, 한 API를 DB부터 응답까지 작게 연결해 가정을 조기에 검증하는 작업 전략.

**언제 사용하는가:** 신규 API, 프론트/백엔드 병렬 작업, 요청·인증·DB 정책이 서로 얽힌 기능에서 사용. 레거시에서는 이미 배포된 스키마·제약을 먼저 읽고 계약과 차이를 조정한다.

**대안과 경계:** Controller 우선은 라우팅·직렬화 시연을 빠르게, DB 우선은 기존 schema·제약·쿼리 위험을 빠르게 드러낸다. 계약/마이그레이션 승인 등 위험이 어느 경계에 있는지에 따라 착수 순서를 바꾸되, 결국 작은 end-to-end slice로 이어 붙이는 원칙은 유지한다.

**예시·실행 근거:** 좋아요 기능에서 “누가 누르는가, 중복 요청을 성공으로 볼 것인가, 작성자가 눌러도 되는가, 삭제 글은 어떻게 하는가”를 계약 사례로 정하고, `(post_id, member_id)` 유일키를 둔 뒤 PUT 한 요청을 Repository→Service→Controller→응답까지 연결한다.

**선수개념:** 유스케이스와 경계 사례를 문장으로 표현; HTTP 메서드·요청자 인증·상태 코드; DB 제약과 트랜잭션의 역할 구분

**관련 표기·별칭:** 계약 우선; 명세 우선; 수직 슬라이스; vertical slice

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 문서는 순서를 설계 프레임으로 설명하지만 합격기준을 자동으로 측정할 테스트 코드는 생략한다. 직접 실행 여부는 예제가 명시적으로 미실행이다.
- 문서의 upsert SQL은 PostgreSQL `ON CONFLICT` 예시다. 저장소 빌드는 MySQL 8.4 계열이므로 그대로 실행 가능한 코드가 아니며, dialect별 대안을 학습자가 직접 찾아야 한다.
- 작은 서비스와 레거시에 대한 적응을 설명하지만, 사용자/팀이 기존 작업 흐름을 바꿀 때 어떤 artifact(ADR, API spec, migration)를 필수로 남길지 세부 계약은 없다.

**초보자가 시작할 질문:**

- API를 만들 때 DB, Controller, Service 중 실제로 무엇을 먼저 정해야 하나?

## API 계약과 API/영속 모델 경계

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** 클라이언트와 서버가 합의하는 URL, HTTP method, 인증 주체, 요청/응답 schema, 상태 코드와 반복 요청 의미. API 응답 DTO는 storage entity를 그대로 외부 계약으로 노출하지 않도록 분리한다.

**언제 사용하는가:** 프론트엔드·모바일·외부 파트너와 병렬 개발하거나, 인증/오류/중복 요청에 여러 해석이 가능한 API에서 구현 전에 합의한다.

**대안과 경계:** Entity 직접 응답은 빠르지만 schema 변경이 외부 contract로 전파된다. 별도 DTO는 변환 비용이 있지만 persistence 모델을 독립적으로 바꿀 수 있다. `PUT`/`DELETE`는 원하는 상태 설정·해제 semantics를 선택하고 실제 API contract와 맞춘다.

**예시·실행 근거:** `PUT /api/posts/{postId}/likes/me`는 로그인된 principal에서 member ID를 받고, 성공 시 204를 반환한다. body는 받지 않아 다른 회원 ID를 조작하지 못하게 한다.

**선수개념:** REST/HTTP 요청·응답; 인증 principal과 body의 차이; Entity/DTO 책임

**관련 표기·별칭:** HTTP contract; API contract; DTO와 Entity 분리; API-first

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- OpenAPI YAML은 204/401/404를 제시하지만 실제 구현·contract test가 없다.
- 본문이 없는 상태에서 중복 `PUT`의 “항상 204” 정책은 중복 관계·없는 글·비공개 글에 대한 오류 의미와 테스트로 확정해야 한다.
- 보안 문장이 있지만 actual Spring Security configuration, role/ownership policy와 threat test는 구현되지 않았다.

**초보자가 시작할 질문:**

- 클라이언트는 엔티티가 아니라 무엇에 의존해야 하나?
- 같은 엔드포인트의 반복 PUT은 어떤 결과를 보장해야 하나?
- 사용자 ID를 request body에서 받으면 어떤 위험이 있나?

## 데이터 불변식과 동시 요청 idempotency

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** 한 회원-게시글 조합을 최대 한 행으로 제한하는 invariant를 DB unique constraint가 최종 보장하고, 애플리케이션은 충돌을 idempotent API의 정책에 맞게 처리한다. 조회 후 저장만으로는 검사-쓰기 경합을 닫지 못한다.

**언제 사용하는가:** 좋아요, 회원가입 중복, idempotency key처럼 동시 요청이 같은 logical row를 만들 수 있는 모든 경로에서 사용.

**대안과 경계:** 단순 `exists`→`save`는 비동기 경쟁을 막지 못한다. DB unique key는 경쟁에도 최종 중복을 막지만 어떤 HTTP 응답을 돌려줄지 정하지 않는다. Atomic upsert는 DB별 문법과 update count를 확인해야 한다.

**예시·실행 근거:** PostgreSQL 예제의 `UNIQUE(post_id, member_id)` + `INSERT ... ON CONFLICT (...) DO NOTHING`; 프로젝트 MySQL에서는 MySQL dialect에 맞는 별도 전략과 통합 테스트 필요.

**선수개념:** PK/FK/unique constraint; 경쟁 조건과 linearization point; HTTP idempotency semantics

**관련 표기·별칭:** unique constraint; 복합 유일키; atomic upsert; 중복 요청 안전성

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 문서에서 “unique constraint + upsert가 PUT을 안전하게”라고 간략화하지만 API response, counter 업데이트, retry를 하나의 invariant로 검증하는 테스트는 생략한다.
- 예제가 PostgreSQL임을 명시하지만 문서의 저장소 기본 DB가 MySQL이므로 별도 MySQL 실행 예시가 있어야 학습 전이가 명확하다.

**초보자가 시작할 질문:**

- exists 검사와 INSERT 사이에 두 요청이 동시에 오면 어떤 일이 생기나?
- 유일 제약은 애플리케이션 오류 처리까지 해결하나?
- 다른 DB에서 upsert SQL을 그대로 쓸 수 있나?

## Controller/Service/Repository의 실행 경계

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** Controller가 HTTP 바인딩·검증·응답 표현을, Service가 하나의 유스케이스 규칙·작업 순서·트랜잭션을, Repository가 persistence query/write를 맡는 책임 분리. 단순 위임에는 Service가 필수는 아니다.

**언제 사용하는가:** 업무 규칙·여러 저장소 조율·다른 호출 진입점·원자적으로 묶어야 하는 쓰기가 생길 때 Service 경계를 명확히 둔다.

**대안과 경계:** Controller→Repository 직접 호출은 단순 조회/CRUD에서 적절할 수 있다. 모든 요청에 빈 forwarding Service를 추가하는 것은 layering이 아니라 boilerplate다. Hexagonal/ports-and-adapters는 외부 기술로부터 use case를 보호하는 목적이 강하며 계층형 구조와 상호 배타적이지 않다.

**예시·실행 근거:** Controller는 authenticated principal에서 member ID를 전달하고, Service가 접근 가능 게시글/좋아요 policy와 transaction을 조정하며, Repository가 DB unique/insert/delete 작업을 수행한다.

**선수개념:** HTTP adapter와 application/domain use case의 차이; DI 의존 방향; Repository와 transaction basics

**관련 표기·별칭:** 계층 책임; 3-tier layering; 유스케이스 경계

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 설명은 역할 위치와 선택 조건을 제공하지만, 실제 project의 같은 API에 적용된 DTO, exception advice, authentication path, repository implementation을 함께 실행한 증거는 없다.
- Service가 `ResponseStatusException`을 직접 던지는 예제는 웹 프레임워크 결합을 단순화로 인정한다. 규모가 커질 때 domain exception→HTTP mapping을 실제로 분리하는 비교가 더 필요하다.
- 국내 “실무에서 흔한가” 수치가 없다고 여러 행에서 명시한 점은 과장 방지에 적절하다.

## 수직 슬라이스/테스트 전략과 저장 무결성 증거

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** 한 유스케이스가 DB constraint부터 HTTP response까지 올바르게 연결되는지 계층별로 작은 기능을 통합하고, 목적에 맞는 test boundary로 계약·규칙·DB behavior를 분리 검증한다.

**언제 사용하는가:** 계층 인터페이스만 만들어진 채 통합을 미루지 말고, contract, persistence invariant, concurrency behavior가 필요한 때 earliest slice를 구축한다.

**대안과 경계:** Unit test는 business branching을 빠르게 검증한다. Spring MVC test는 HTTP bind/status를 검증한다. 실제 DB integration test는 FK/unique/upsert/lock 동작을 확인한다. H2가 MySQL 동작을 증명하지 않는다.

**예시·실행 근거:** 정상 like/unlike, unauthenticated, missing post, duplicate concurrent PUT를 실제 API 경로에서 호출하고 DB row count와 API response를 비교한다.

**선수개념:** JUnit/MockMvc; 트랜잭션 test thread-locality; Testcontainers/DB isolation

**관련 표기·별칭:** vertical slice; thin slice; 계층 통합 테스트

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 문서가 동시 중복과 실제 DB 제약 테스트를 권고하지만 테스트 전체 코드 및 pass evidence는 제공하지 않는다.
- 요청에서 code snippets are marked 미실행; 학습 화면에서 test result and SQL/HTTP evidence are not established.
- DB 전용 SQL을 사용하는 경우 H2-only test로 green이 나도 MySQL-specific upsert/IGNORE/lock semantics를 별도로 검증해야 한다.

## 시각 구조와 보완 장면

**기존 표현**

**정적 구조의 한계**

- 코드 블록과 흐름도는 설명을 돕지만 실제 DB·HTTP·스레드 동작을 증명하지 않는다.
- 화면 첫 노출과 모바일 가독성은 아래 실제 캡처 판독에서 별도로 기록했다.

**추가할 의미 장면**

- 좋아요 기능에서 “누가 누르는가, 중복 요청을 성공으로 볼 것인가, 작성자가 눌러도 되는가, 삭제 글은 어떻게 하는가”를 계약 사례로 정하고, `(post_id, member_id)` 유일키를 둔 뒤 PUT 한 요청을 Repository→Service→Controller→응답까지 연결한다.
- `PUT /api/posts/{postId}/likes/me`는 로그인된 principal에서 member ID를 받고, 성공 시 204를 반환한다. body는 받지 않아 다른 회원 ID를 조작하지 못하게 한다.
- PostgreSQL 예제의 `UNIQUE(post_id, member_id)` + `INSERT ... ON CONFLICT (...) DO NOTHING`; 프로젝트 MySQL에서는 MySQL dialect에 맞는 별도 전략과 통합 테스트 필요.
- Controller는 authenticated principal에서 member ID를 전달하고, Service가 접근 가능 게시글/좋아요 policy와 transaction을 조정하며, Repository가 DB unique/insert/delete 작업을 수행한다.
