## QueryDSL·JPQL 비교

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** APT가 생성한 경로 타입을 Java compiler가 확인하는 쿼리 도구

**언제 사용하는가:** 조건이 선택적인 검색/타입 검사가 필요한 JPA 쿼리

**대안과 경계:** 문자열 JPQL은 단순하지만 오타 조기 검출 약함; QueryDSL은 SQL plan 보장 아님

**예시·실행 근거:** name 또는 status 조건을 선택해 predicate를 만들고 검색 결과가 어떻게 달라지는지 비교한다.

**선수개념:** Java 제네릭; JPQL

**관련 표기·별칭:** Q type; typed query

**보완·검증 필요 사항:**

- 실행 SQL/실행계획 비교 없음.

**초보자가 시작할 질문:**

- 조건 검색의 필드 오타를 언제 잡나?

## APT와 Q 생성

현재 판정: **미검증** / 우선순위: high

**정의와 실제 역할:** 컴파일 시 APT가 entity metadata에서 generated source를 생성

**언제 사용하는가:** Java 빌드에서 타입 안전 경로를 쓸 때

**대안과 경계:** annotationProcessor 설정이 있어야 컴파일 과정에서 processor가 실행된다. 구현 라이브러리 의존성만 추가해도 Q 타입이 자동 생성되는 것은 아니다.

**예시·실행 근거:** clean compile 후 build/generated의 QMember 확인

**선수개념:** annotation processing 설정; Jakarta API

**관련 표기·별칭:** annotationProcessor; Jakarta classifier

**보완·검증 필요 사항:**

- Spring 전체 예제 미실행; 버전 릴리스 주장 공식 확인 필요.

## 동적 predicate 선택

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 조건을 Java 메서드로 만들고 query where에 조합

**언제 사용하는가:** 선택 입력이 있는 검색 조건이나 여러 OR 조건을 Java 코드로 조합할 때 사용한다.

**대안과 경계:** 고정된 검색에는 null을 반환하는 BooleanExpression을 쓰기 쉽고, 조건을 반복 누적하거나 OR로 묶을 때는 BooleanBuilder가 편리하다. 간단한 검색은 JPQL도 대안이다.

**예시·실행 근거:** nameContains/statusEq와 where(null-aware)

**선수개념:** 입력값이 비어 있을 때의 처리; Predicate 조건식

**관련 표기·별칭:** BooleanExpression; BooleanBuilder

**보완·검증 필요 사항:**

- 복잡도 기준은 있으나 사용자가 직접 값 변화에 따른 SQL 비교하는 장면은 없음.

**초보자가 시작할 질문:**

- 검색어/상태가 비어 있을 때 조건은 어떻게 빠지나?

## 커스텀 repo·DTO·페이지/content/count

현재 판정: **미검증** / 우선순위: high

**정의와 실제 역할:** Spring Data custom fragment에서 DTO select 및 page/count 구현

**언제 사용하는가:** 검색 API에 제한 페이지와 total이 필요할 때

**대안과 경계:** 전체 fetch는 모든 결과를 메모리에 올린다. 페이지의 content 조회와 전체 개수 count는 별도 SQL일 수 있다.

**예시·실행 근거:** members query에서 content와 totalElements 1 확인

**선수개념:** JPA 조회; pagination(페이지 처리); 응답 DTO

**관련 표기·별칭:** repository fragment; projection; PageableExecutionUtils

**보완·검증 필요 사항:**

- API 미실행; count/query log 확인은 지시만 있다.

## fetch join·쿼리 계획 경계

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 연관 데이터 SQL을 가져오되 collection row 증폭/page 제한 문제를 함께 고려

**언제 사용하는가:** 필요한 연관 조회와 페이지 분리 설계 시

**대안과 경계:** 타입 안정성이 실행계획 최적성 보장은 아님; ID page + IN query 대안

**예시·실행 근거:** Q&A가 ID paging 대안 설명

**선수개념:** SQL; N+1

**관련 표기·별칭:** pagination; EXPLAIN

**보완·검증 필요 사항:**

- 실제 EXPLAIN/측정 예가 없다.

**초보자가 시작할 질문:**

- fetch join이면 항상 N+1이 끝나나?

## 시각 구조와 보완 장면

**기존 표현**

- 표, Gradle 설정, 쿼리 코드, 실행 명령과 예상 curl 결과를 제공한다.

**정적 구조의 한계**

- 캡처된 API 실행 결과는 없으며 컴파일 검증과 Spring 애플리케이션 실행 검증을 구분해야 한다.

**추가할 의미 장면**

- Q 타입 파일 생성과 컴파일 오류, 선택 필터별 SQL 변화, content 조회와 count 조회를 나란히 보여준다.

## 실제 캡처 관찰

- desktop의 주제 요약은 Q 타입·APT·SQL/count를 소개한다. mobile은 2열 주제 카드와 제목 줄바꿈이 보이고 가로 넘침은 없다. core 2.x 앵커의 카드 5개가 닫혀 JPQL 오타, Q 타입 생성, null predicate, count 질문이 첫 화면에서 보이지 않는다. 기술 용어와 의존성 버전이 요약에 밀집되어 있다. 필터 입력→Q 표현식→SQL/결과 경로를 추가하고 컴파일만 검증된 부분과 미실행 부분을 구별할 필요가 있다.
