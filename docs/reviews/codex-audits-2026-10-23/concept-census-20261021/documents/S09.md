## JPA entity state·persistence context·flush/merge

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** JPA는 Jakarta Persistence 표준, Hibernate는 구현체다. Persistence context는 관리 객체 identity와 dirty state를 추적한다. flush는 SQL 동기화이지 commit이 아니다. merge는 detached 상태를 managed 인스턴스로 복사하고 새 관리 객체를 반환할 수 있다.

**언제 사용하는가:** 새 entity는 persist, managed entity는 짧은 tx에서 변경, 응답 DTO는 tx 안에서 구성한다.

**대안과 경계:** 1차 캐시는 컨텍스트 단위, 애플리케이션 공유 cache와 다르다. SQL은 query/commit 전 flush 될 수 있고 merge 원본은 계속 detached다.

**예시·실행 근거:** managed Order를 변경하고 flush; detached order merge 반환값으로 후속 변경한다.

**선수개념:** JPA entity; transaction boundary; identity map

**관련 표기·별칭:** EntityManager; persistence context; managed; detached; flush; merge

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 예제 미실행; Hibernate7/MySQL SQL 동작을 직접 관찰하지 않았다.

**초보자가 시작할 질문:**

- flush하면 commit된 건가?
- merge는 원본을 관리 객체로 바꾸나?
- SQL 오류가 왜 메서드 종료에서 날 수 있나?

## 관계 주인·fetch/N+1·cascade·OSIV·락

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** Owning association은 실제 FK를 저장하고 mappedBy는 inverse 관계다. LAZY는 조회를 늦추며 요청별 fetch plan이 필요하다. cascade/orphanRemoval은 생명주기 전파, @Version은 낙관적 충돌 검출이다.

**언제 사용하는가:** 양방향 helper로 양측을 갱신; LAZY 유지; use case에 fetch join/entity graph/batch/DTO 사용. OSIV false와 tx 내 DTO 변환을 시작점으로 한다.

**대안과 경계:** EAGER 일괄은 overfetch, LAZY 반복 접근은 N+1. collection fetch join은 SQL row 증폭/페이지 문제. Cascade REMOVE 공유 객체에 위험. 비관적 락은 대기와 교착 비용.

**예시·실행 근거:** OrderLine.order FK owner; PurchaseOrder.addLine 양쪽 갱신; @Version; nonpaged detail fetch join.

**선수개념:** foreign key; SQL join cardinality; ORM proxy

**관련 표기·별칭:** mappedBy; orphanRemoval; LAZY; EAGER; OSIV; @Version

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- SQL query counts, OSIV runtime, lock race, MySQL roundtrip을 실행하지 않았다.

**초보자가 시작할 질문:**

- 어느 쪽이 FK를 바꾸나?
- LAZY인데 N+1이 왜 생기나?
- collection fetch join과 Page가 충돌하는 이유?
- @Version은 충돌을 언제 찾나?

## 실제 캡처 관찰

- 공개 base는 Spring Data JPA→JPA→Hibernate의 역할 층을 구분하는 장면을 보여준다.
- progress는 assigned ID→persist→flush→commit 뒤 조회→새 컨텍스트 find→같은 컨텍스트 identity의 6단계 상태를 보여준다.
- 모바일 progress에서는 환경 고지, 시나리오 선택과 장면 이동 버튼이 보이며 큰 테이블형 시각이 아래에서 폭을 차지한다.
- 실험은 별도 native Hibernate7.4.5+H2 2.4.240+JDK21과 추가 ProbePost42 테스트다. 수동 ID 보유 객체가 새 상태이고 persist로 관리, flush에서 INSERT, commit 뒤 새 컨텍스트 find 성공, 동일 컨텍스트 identity를 관찰했다.
- 원문 PurchaseOrder/OrderLine을 추가로 바꾸지 않았으며 Spring Boot/JPA proxy/HTTP/MySQL/OSIV/JDK25 결과로 확대하지 않는다.
- core 캡처는 anchor가 연 외부 detail 범위로 판정하며 모든 nested section/조작을 검증했다는 뜻은 아니다.
