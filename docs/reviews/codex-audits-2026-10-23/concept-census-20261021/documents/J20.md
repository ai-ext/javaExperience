## InputStream/Reader/Charset

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** InputStream은 바이트를, Reader는 문자를 읽으며, 문자를 바이트로 바꾸는 경계에는 Charset이 필요합니다. 버퍼링은 작은 읽기를 묶지만 전체 파일을 반드시 메모리에 올리지는 않습니다.

**언제 사용하는가:** 텍스트 파일의 인코딩을 명시하고, 큰 입력은 스트리밍으로 처리해 메모리 사용을 제한합니다.

**대안과 경계:** read 한 번이 요청한 바이트를 모두 채운다고 보장되지 않습니다. available은 전체 길이가 아니며 문자 단위는 surrogate pair 중간을 나눌 수 있습니다.

**예시·실행 근거:** UTF-8로 한글 파일을 쓰고 다시 읽는 왕복 예제를 실행합니다.

**선수개념:** bytes/chars; charset

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- No malformed decoder REPORT sample.

**초보자가 시작할 질문:**

- UTF-8 byte stream을 default Charset으로 디코딩하면 다른 서버에서 한글이 깨질 수 있는 이유는?
- `read(byte[])`가 배열을 다 채웠다고 가정하면 어떤 데이터가 유실될까요?

## Path/Files and resource lifecycle

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Path는 위치를 표현하고 Files는 파일 시스템 작업을 수행합니다. Files.lines는 지연 처리되는 closeable stream입니다.

**언제 사용하는가:** 대용량 파일은 스트리밍 API로 읽고, 파일·stream 등 자원은 try-with-resources로 닫습니다.

**대안과 경계:** exists 확인 후 open 사이에 파일이 바뀔 수 있습니다(TOCTOU). 원자적 이동은 파일 시스템 제공자에 따라 지원 여부가 다릅니다.

**예시·실행 근거:** 임시 파일을 만들고 기록·읽기·삭제하는 왕복 예제가 있습니다.

**선수개념:** Path; TWR

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Filesystem provider behavior can differ.

**초보자가 시작할 질문:**

- Path가 File descriptor를 열고 계속 소유하는 객체가 아닌 이유는?
- Files.lines를 사용하고 닫지 않으면 어떤 리소스가 남을 수 있나요?

## Buffer/Channel/Selector mechanics

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Buffer는 position·limit·capacity를 관리하고, Channel은 일부만 읽거나 쓸 수 있습니다. Selector는 논블로킹 채널의 준비 상태를 모읍니다.

**언제 사용하는가:** 많은 연결이 각자 대기하는 비용이 병목일 때 논블로킹 I/O를 검토하고, 연결별 상태를 따로 보존합니다.

**대안과 경계:** select는 준비 상태가 올 때까지 대기합니다. OP_WRITE를 계속 등록하면 반복 회전할 수 있고, 파일 채널은 항상 Selector 대상이 되는 것이 아닙니다.

**예시·실행 근거:** ByteBuffer 예제가 flip과 compact 뒤 position·limit 변화를 출력합니다.

**선수개념:** network socket; buffer state

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- No actual selector event loop server.

**초보자가 시작할 질문:**

- `flip`이 position과 limit을 바꾸지 않으면 방금 쓴 바이트를 왜 읽지 못하나요?
- write가 일부만 보냈는데 다음 이벤트 전까지 어떤 상태를 보관해야 하나요?

## HttpClient lifecycle and body handling

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 재사용하는 HttpClient가 동기 또는 비동기 요청을 보내고, BodyHandler가 응답을 어떤 형태로 소비할지 정합니다.

**언제 사용하는가:** 연결·요청 제한 시간을 설정하고, 응답이 큰 경우 전체 본문 문자열 대신 스트림 처리를 선택합니다.

**대안과 경계:** 비동기 Future가 자원 사용을 없애지는 않습니다. 연결 제한 시간과 응답 제한 시간은 서로 다른 구간을 다룹니다.

**예시·실행 근거:** loopback HttpServer에 HttpClient.sendAsync로 요청해 200 응답을 확인합니다.

**선수개념:** HTTP request; CompletableFuture

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- No external service/auth failure test.

**초보자가 시작할 질문:**

- `sendAsync()`이어도 원격이 응답 안 하면 어떤 timeout 자원이 필요할까요?

## JDBC PreparedStatement and pool sizing

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** DataSource는 Connection을 빌려 주고, PreparedStatement는 SQL 문장과 값을 분리하며, 풀에 연결된 Connection을 닫으면 대개 풀에 반환됩니다.

**언제 사용하는가:** 사용자 입력은 바인딩하고 Connection·Statement·ResultSet을 닫습니다. 풀 크기는 DB 연결 예산과 실제 부하를 기준으로 정합니다.

**대안과 경계:** 테이블명 같은 식별자는 값 파라미터로 바인딩할 수 없습니다. 커넥션 풀은 대기열이므로 크기를 늘리면 DB 포화가 악화될 수도 있습니다.

**예시·실행 근거:** JDBC 자원 수명과 연결 반환 흐름을 설명하며 실제 DB 접속 실행은 하지 않았습니다.

**선수개념:** SQL; connection lifecycle

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Hikari timings/BOM value vary by version.

**초보자가 시작할 질문:**

- SQL column name을 `?`에 넣어 바인딩할 수 없는 이유는?
- getConnection 대기가 긴 상황에 pool size만 늘리면 DB가 더 느려질 수 있는 이유는?
