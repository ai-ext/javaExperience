## 계층을 나누는 기준은 변경 이유와 실행 경계

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** 계층은 파일 수가 아니라 다른 변경 이유와 실행 경계가 만나는 곳에서 나눈다.

**언제 사용하는가:** Controller는 HTTP 입출력, Service는 업무 흐름, Repository는 저장 접근을 담당하도록 책임이 실제로 달라질 때 분리한다.

**대안과 경계:** 단순 CRUD를 무조건 3개로 나눌 필요는 없지만 여러 저장소·정책을 조정하면 서비스 경계가 유용하다.

**예시·실행 근거:** 단일 조회 흐름과 주문·재고 동시 변경을 비교한다.

**선수개념:** HTTP request; database persistence

**관련 표기·별칭:** Controller-Service-Repository; 3-tier architecture; layered architecture

**판정 이유:** 핵심 개념은 설명하지만 대상 환경 실행·학습자 수행 근거가 충분하지 않아 부분 판정.

**보완·검증 필요 사항:**

- 예제 코드는 미실행이며 패키지/파일 수 자체가 품질 지표는 아니다.

## Service as application use case; when direct Repository access is enough

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** Service는 유스케이스와 규칙을 소유한다. 단순 조회·저장만 연결하는 API라면 직접 Repository 호출도 가능하다.

**언제 사용하는가:** 여러 저장소·권한·상태 전이·트랜잭션을 함께 조율할 때 서비스 경계를 둔다.

**대안과 경계:** Repository 직접 호출은 얇지만 업무 규칙이 여러 진입점에 복제될 수 있다.

**예시·실행 근거:** GET 단순 조회와 주문·재고 처리의 계층을 나란히 비교한다.

**선수개념:** Controller; Repository; use case

**관련 표기·별칭:** Service Layer; application service; thin service

**판정 이유:** 핵심 개념은 설명하지만 대상 환경 실행·학습자 수행 근거가 충분하지 않아 부분 판정.

**보완·검증 필요 사항:**

- 국내 조직별 계층 관행은 정량 자료가 없다.

## 트랜잭션 경계와 proxy 기반 적용

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** 선언형 트랜잭션은 프록시를 지난 외부 메서드 호출에서 경계를 적용한다.

**언제 사용하는가:** 같은 업무 요청이 여러 DB 변경을 함께 성공/실패해야 할 때 서비스 진입점에 둔다.

**대안과 경계:** Repository 각자 커밋하면 부분 성공이 남을 수 있으며 self-invocation은 프록시를 우회한다.

**예시·실행 근거:** 주문 INSERT와 재고 차감을 한 트랜잭션에 포함하는 예.

**선수개념:** AOP proxy; PlatformTransactionManager

**관련 표기·별칭:** @Transactional proxy; transaction boundary; self invocation

**판정 이유:** 핵심 개념은 설명하지만 대상 환경 실행·학습자 수행 근거가 충분하지 않아 부분 판정.

**보완·검증 필요 사항:**

- 실행 환경에 연결한 트랜잭션 테스트가 없다.

## 인터페이스와 구현 분리의 선택 기준

**언제 사용하는가:** 외부 API·복수 전략·모듈 교체 이유가 있을 때 인터페이스를 둔다.

**대안과 경계:** 구현이 하나여도 경계가 실제로 바뀌면 유용하고 이름만 숨기는 인터페이스는 비용일 수 있다.

**선수개념:** constructor injection; abstraction boundary

**관련 표기·별칭:** Service interface; ServiceImpl; JDK proxy; CGLIB proxy

**판정 이유:** 핵심 개념은 설명하지만 대상 환경 실행·학습자 수행 근거가 충분하지 않아 부분 판정.

**보완·검증 필요 사항:**

- 예제/Mockito는 미실행이며 실제 프록시 유형도 확인하지 않았다.

## Layered architecture and Hexagonal architecture distinction

현재 판정: **부분** / 우선순위: P2

**정의와 실제 역할:** Layered는 기술별 의존 흐름을 정리하고 Hexagonal은 도메인 안팎의 포트·어댑터 경계를 강조한다.

**언제 사용하는가:** 유스케이스와 외부 시스템을 분리해야 할 때 포트·어댑터를 검토한다.

**대안과 경계:** Layered와 Hexagonal은 서로 배타적이지 않으며 과한 포트 추출은 복잡도를 늘린다.

**예시·실행 근거:** Service가 인터페이스를 통해 결제 API를 호출하고 adapter가 HTTP를 처리한다.

**선수개념:** dependency direction; port/adapter

**관련 표기·별칭:** Hexagonal architecture; Ports and Adapters; architecture style

**판정 이유:** 핵심 개념은 설명하지만 대상 환경 실행·학습자 수행 근거가 충분하지 않아 부분 판정.

**보완·검증 필요 사항:**

- 구조도만으로 모듈 경계의 실제 독립성이 증명되지는 않는다.

## 외부 계층에서 규칙을 재사용하고 테스트 경계를 분리하기

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** 외부 계층은 안쪽 업무 규칙을 재사용하되 자신이 맡은 입출력 변환만 수행한다.

**언제 사용하는가:** 웹/배치/메시지가 같은 유스케이스를 실행하거나 테스트 경계를 나눌 때 재사용한다.

**대안과 경계:** Controller가 업무 규칙을 소유하면 다른 진입점에서 복제되고, 서비스가 HTTP 타입을 직접 쓰면 웹에 결합될 수 있다.

**예시·실행 근거:** Controller는 DTO를 받아 Service를 호출하고 Repository 결과를 HTTP 응답으로 변환한다.

**선수개념:** DTO; service use case; persistence

**관련 표기·별칭:** unit testing service; MockMvc; repository integration test

**판정 이유:** 핵심 개념은 설명하지만 대상 환경 실행·학습자 수행 근거가 충분하지 않아 부분 판정.

**보완·검증 필요 사항:**

- 테스트 구성은 예시 수준이며 실제 adapter test는 없다.
