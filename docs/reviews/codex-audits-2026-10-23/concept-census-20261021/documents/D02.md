## DNS와 URL 이름 해석

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** URL은 scheme·host·port·path·query·fragment로 구성되고 DNS는 domain 이름을 address record로 해석한다. DNS 응답만으로 앱의 정상 동작을 입증하지 않는다.

**언제 사용하는가:** 도메인 이름, URL target, resolver 응답을 분리해 확인할 때 사용한다.

**대안과 경계:** recursive resolver는 조회를 대신하고 authoritative DNS는 해당 zone의 원본 답을 제공한다. 주소 응답은 HTTP health와 다르다.

**예시·실행 근거:** URL parse, `dig` 결과와 HTTP 요청을 단계별로 비교한다.

**선수개념:** URL 구성; IP address

**관련 표기·별칭:** DNS and URL resolution

**보완·검증 필요 사항:**

- 외부 DNS를 실제로 조회하는 증거는 별도이며 TLS 최신 인용은 RFC 9846으로 갱신한다.

## TCP·QUIC·NAT·방화벽·listener

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** network route가 packet을 전달하고 NAT·firewall 규칙과 server socket listener가 연결 가능 여부를 결정한다.

**언제 사용하는가:** port 도달 실패, localhost/container 주소 오류, 연결 거부를 구분할 때 사용한다.

**대안과 경계:** TCP는 연결 지향 byte stream이다. QUIC은 UDP 위에서 전송/연결 기능을 제공한다. ICMP ping 성공은 HTTP 성공을 뜻하지 않는다.

**예시·실행 근거:** localhost와 0.0.0.0 bind, port mapping, TCP/QUIC 경로를 명령으로 비교한다.

**선수개념:** IP address; port와 socket

**관련 표기·별칭:** TCP/QUIC, NAT, firewall and listener

**보완·검증 필요 사항:**

- 외부 firewall·NAT·QUIC 경로를 직접 실행한 것은 아니므로 실제 환경 관측과 문서 설명을 구분한다.

**초보자가 시작할 질문:**

## TLS와 proxy routing

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** TLS handshake가 암호화 연결과 인증서를 확인한 뒤 load balancer/reverse proxy를 통해 app으로 요청을 전달한다.

**언제 사용하는가:** 인증서 검증 실패, proxy routing, HTTP status 오류 위치를 좁힐 때 사용한다.

**대안과 경계:** TLS 보호는 앱 권한이나 HTTP 처리 성공을 보장하지 않는다. proxy와 app은 다른 장애 지점이다.

**예시·실행 근거:** curl·openssl·ss 결과를 DNS, TCP, TLS, proxy, app 단계에 대응시킨다.

**선수개념:** DNS; TCP; 인증서

**관련 표기·별칭:** TLS and proxy routing

**보완·검증 필요 사항:**

- 실습은 loopback TLS 관찰에 한정될 수 있다. TLS 1.3 최신 RFC는 RFC 9846이며 RFC 8446은 대체됐다.
