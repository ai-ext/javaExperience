## WebFlux·Reactive Streams·event loop

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** Mono/Flux는 publisher 결과 신호 모델이고 Reactive Streams demand/cancel은 흐름 제어 규약이다. WebFlux는 논블로킹 I/O 경로에서 유리하지만 event loop의 JDBC blocking이 다른 요청을 막을 수 있다.

**언제 사용하는가:** 실제 reactive client/data access 또는 긴 스트리밍이 필요하면 WebFlux; JDBC/JPA·동기 라이브러리가 중심이면 MVC를 우선 검토한다.

**대안과 경계:** Reactive 타입이 스레드 이동이나 논블로킹 source를 보장하지 않는다. Backpressure는 요청 수요를 표현하되 DB 연결·버퍼·외부 rate를 자동 제한하지 않는다.

**예시·실행 근거:** WebClient 결과는 Mono로 반환; 불가피한 JDBC는 fromCallable+boundedElastic에 격리하지만 DB 호출은 여전히 blocking이다.

**선수개념:** HTTP I/O; threading; publisher/subscriber

**관련 표기·별칭:** Mono; Flux; backpressure; event loop; Scheduler

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 코드 미실행; 이벤트 루프 부하 테스트 없음.

## Virtual Threads와 executor 적용 범위

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** 가상 스레드는 blocking 코드의 대기 스레드 비용을 낮춘다. CPU나 DB 연결 수를 늘리지 않으며 Boot task executor/scheduler 설정과 Tomcat connector executor는 다를 수 있다.

**언제 사용하는가:** MVC/JDBC 시스템에서 VT를 부하 조건으로 검증하고 HTTP 요청 executor가 실제 VT를 쓰는지 확인한다. end-to-end reactive 경로에는 WebFlux를 고려한다.

**대안과 경계:** VT는 imperative 흐름을 유지하고 reactive는 publisher/demand 모델을 쓴다. 둘 다 CPU·DB pool·외부 API 한계가 남는다.

**예시·실행 근거:** spring.threads.virtual.enabled는 Boot managed executor에 영향을 준다. Tomcat 요청 VT는 connector executor를 별도 구성한다.

**선수개념:** Java 21 threads; Boot task execution; DB pools

**관련 표기·별칭:** Virtual Threads; TaskExecutor; Tomcat executor; boundedElastic

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 동일 workload 비교 성능실험과 Tomcat 연결 검증은 없다.

**초보자가 시작할 질문:**

- VT가 DB 연결을 늘리나?
- WebFlux가 더 복잡해도 선택할 상황은?

## 찾아가는 경로

**들어오는 경로**

- W14 async/blocking
- W25 multi-threading
- J12 virtual threads

**다음 경로**

- DB limits
- scheduler fixed-delay
- reactive cancellation
