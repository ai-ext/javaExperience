## 람다의 대상형과 함수형 메서드

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 람다는 독립 함수 타입이 아니라 문맥이 제공하는 SAM 대상형을 구현합니다. `@FunctionalInterface`는 그 의도를 컴파일 시 검사합니다.

**언제 사용하는가:** Function/Predicate/Consumer/Supplier처럼 역할에 맞는 인터페이스를 선택하고 domain 계약은 이름 있는 함수형 타입으로 둡니다.

**대안과 경계:** default/static 메서드는 SAM 하나의 조건을 깨지 않습니다.

**예시·실행 근거:** Function parse/andThen과 Predicate 연산이 실제 출력됩니다.

**선수개념:** interface; generic type inference

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 오버로드된 lambda 대상형은 모호할 수 있습니다.

**초보자가 시작할 질문:**

- `var f = x -> x + 1`에서 컴파일러가 변수 타입을 정할 수 없는 이유는 무엇인가요?
- 함수형 인터페이스에 default 메서드를 하나 추가해도 람다가 유지되는 이유는?

## 메서드 참조·캡처·수신 객체 평가

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 정적/바인딩/언바인딩/생성자 참조의 매개변수 대응이 다릅니다. 캡처 지역변수는 final 또는 effectively final이어야 합니다.

**언제 사용하는가:** 동작이 그대로 맞으면 method reference, 수신 객체를 지연 조회하거나 변환이 있으면 lambda를 씁니다.

**대안과 경계:** 바인딩 참조는 receiver expression을 만들 때 평가하며, 참조가 가리키는 mutable 객체는 변경 가능/동기화 별도입니다.

**예시·실행 근거:** MethodReferenceCaptureDemo 4종의 참조와 StringBuilder capture를 실행합니다.

**선수개념:** SAM; 변수/참조

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 프록시/비동기 context propagation은 별도 도구 문제입니다.

**초보자가 시작할 질문:**

- `supplier.get()::send`를 만들 때 get()은 지금 실행되나요, 나중에 실행되나요?
- effectively final인 StringBuilder의 내용은 람다 안에서 바뀔 수 있는데 무엇이 고정인가요?

## invokedynamic와 lambda runtime

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** javac는 target/SAM을 검사하고 일반 HotSpot 경로는 invokedynamic bootstrap/LambdaMetafactory로 callsite를 연결할 수 있습니다.

**언제 사용하는가:** 런타임 구현 설명을 읽을 때 언어 계약과 VM 최적화를 분리합니다.

**대안과 경계:** lambda 객체 class 이름, 매번 새 객체인지, `==` 동일성은 API 보장이 아닙니다.

**예시·실행 근거:** 문서의 linkage diagram과 JDK21 runnable examples.

**선수개념:** class file/invokedynamic

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- J08에서는 lambda bytecode를 javap로 직접 덤프하지 않았습니다.

**초보자가 시작할 질문:**

- 같은 lambda 표현식을 두 번 평가하면 같은 객체일 거라고 가정할 수 없는 이유는 무엇인가요?
- invokedynamic을 매 호출마다 reflection lookup하는 것으로 설명하면 왜 틀리나요?

## Optional·합성과 기본값 평가

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** map은 값 변환, flatMap은 Optional 한 겹 평탄화, andThen=f→g, compose=g→f, orElse는 eager / orElseGet은 lazy입니다.

**언제 사용하는가:** 부재가 정상 결과인 반환 경계에 Optional을 쓰고 기본 생성이 비싸면 orElseGet을 택합니다.

**대안과 경계:** 권한/validation 실패를 Optional.empty로 숨기지 않으며 Optional 자체를 null로 두지 않습니다.

**예시·실행 근거:** OptionalUsageDemo에서 eager 기본 함수만 출력됩니다.

**선수개념:** Optional; 순수 함수 composition

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 중첩 Optional은 flatMap으로 정리할 수 있습니다.

**초보자가 시작할 질문:**

- 값이 이미 있어도 `orElse(expensiveDefault())`가 로그를 찍는 이유는 무엇인가요?
- f.compose(g)와 f.andThen(g) 중 입력을 먼저 g에 주는 것은 어느 쪽인가요?

## 캡처 상태와 스레드 안전성

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** effectively-final은 지역 참조 재대입을 제한하며 그 대상 객체의 변경을 막지 않습니다.

**언제 사용하는가:** 공유 람다 state가 있으면 immutable 전달이나 명시적 synchronization을 씁니다.

**대안과 경계:** 캡처 가능하다는 것은 visibility/race-free를 뜻하지 않습니다.

**예시·실행 근거:** mutableHolder가 람다 실행 뒤 같은 StringBuilder 상태를 출력합니다.

**선수개념:** 참조 alias; JMM

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 멀티스레드 경합은 이 문서에서 직접 재현하지 않습니다.

**초보자가 시작할 질문:**

- 람다에서 builder.append가 허용되는데도 여러 스레드 공유는 안전하지 않을 수 있는 이유는?
- 캡처한 local `count++`가 컴파일 오류인 것과 객체 필드 수정은 왜 다른가요?

## 실제 캡처 관찰

- desktop/mobile 첫 화면은 target type, effectively final 캡처, 런타임 구현에 관한 동일한 3줄 요약을 보여 준다. 모바일도 가로 넘침 없이 줄바꿈된다.
- core에는 함수형 interface 용어표와 java.util.function, method reference, Optional의 접힌 소주제가 보인다. 정적 정의는 제공하지만 평가 순서 애니메이션은 없다.
- 시각 개요는 reference identity가 보장되지 않는다고 언급하지만 core 캡처에는 lambda identity나 출력 비교 시연이 없다.

**관찰 범위:** 이 캡처들에서 보이는 부분만 평가했다. Optional.orElse와 orElseGet, bound method reference 시간 차이 예제를 실행하지 않았다.
