## 검증 신뢰 경계: client, server, database

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** 브라우저·서버·DB 검증은 서로 다른 신뢰 경계다.

**언제 사용하는가:** 브라우저는 빠른 입력 안내, 서버는 조작 요청을 포함한 최종 업무 판정, DB는 모든 writer 공통의 저장 불변식을 맡는다.

**대안과 경계:** 같은 형식 규칙을 중복해도 목적이 다르다; 권한·현재 재고·중복은 서버/DB에서 검증한다.

**예시·실행 근거:** HTML min 검증만으로 서버 요청을 막지 못하며 DB UNIQUE가 동시 중복의 마지막 보장이다.

**선수개념:** client/server trust boundary; database constraint

**관련 표기·별칭:** frontend validation; server validation; database constraints; defense in depth

**판정 이유:** 개념 정의와 적용 기준은 확인되나 실제 실행/학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- DDL SQL은 PostgreSQL 문법으로 명시돼 있어 MySQL 실행 예로 복사하면 안 된다.

**초보자가 시작할 질문:**

- DB에서 중복을 최종 차단하는 이유?

## Bean Validation DTO constraints and groups

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** Bean Validation으로 DTO 모양과 입력 제약 검사

**언제 사용하는가:** @NotBlank/@Email/@Size 같은 제약이 요청 객체에 바인딩된 값의 형식/길이를 검증한다.

**대안과 경계:** 요청 DTO의 필수값·형식·범위를 컨트롤러 경계에서 확인한다.

**선수개념:** Bean Validation; DTO

**관련 표기·별칭:** @NotBlank; @Email; @Size; @Valid; Validation group

**판정 이유:** 개념 정의와 적용 기준은 확인되나 실제 실행/학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- Jakarta Validation

## Database constraints and check-then-act race

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** DB 제약과 check-then-act race

**언제 사용하는가:** 애플리케이션에서 조회 뒤 insert/update는 동시 요청 사이 경쟁 구간이 있다. UNIQUE/NOT NULL/CHECK와 원자적 update가 최종 상태를 보호한다.

**대안과 경계:** 중복 키는 unique constraint, stock은 조건부 update+transaction으로 보장한다.

**예시·실행 근거:** existsByEmail 사전 검사만으로 두 동시 요청의 중복 insert를 막지 못한다. 추가 예: UPDATE inventory SET stock=stock-1 WHERE id=? AND stock>0; 영향 행 0이면 품절.

**선수개념:** unique constraint; atomic update; transaction

**관련 표기·별칭:** UNIQUE; NOT NULL; FOREIGN KEY; CHECK; existsBy

**판정 이유:** 개념 정의와 적용 기준은 확인되나 실제 실행/학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- SQL constraint
- transaction isolation

**초보자가 시작할 질문:**

- 이메일 중복을 먼저 조회했는데도 중복 insert가 가능한 이유?
- 재고를 읽은 뒤 차감할 때 어떤 동시성 문제가 생기나?

## Contract rule sharing and drift control

현재 판정: **부분** / 우선순위: P2

**정의와 실제 역할:** 계약 규칙 공유와 드리프트 관리

**언제 사용하는가:** 프론트/서버에 같은 규칙을 두더라도 한쪽은 UX, 다른 쪽은 trust enforcement를 담당한다.

**대안과 경계:** 규칙 변경을 양쪽과 DB migration/문서에 전파하고 경계별 테스트로 차이를 찾는다.

**예시·실행 근거:** DTO 그룹/중복 코드 공유가 모든 계층을 자동 동기화하지 않는다. DB가 최종 불변식, client는 안내다. 추가 예: invalid email, duplicate account, out-of-stock을 browser/server/DB 경로별로 테스트한다.

**선수개념:** validation test; schema migration

**관련 표기·별칭:** OpenAPI; JSON Schema; generated validation

**판정 이유:** 개념 정의와 적용 기준은 확인되나 실제 실행/학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- contract tests
- schema migration

**초보자가 시작할 질문:**

- 프론트와 서버에 같은 형식 검사가 있는데 각각 왜 필요한가?
