## Gradle lifecycle과 task graph

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Gradle은 initialization, configuration 단계에서 task graph를 만들고 선택된 task를 실행한다. build는 compile보다 넓은 절차다.

**언제 사용하는가:** 빌드 중 어떤 task가 실행되고 처음 실패한 지점을 조사할 때 사용한다.

**대안과 경계:** task graph는 dependency 관계를 나타내며 설명상 고정된 일렬 실행 순서와 다르다. build에는 test·package 등도 포함될 수 있다.

**예시·실행 근거:** `./gradlew build`의 task graph와 첫 실패 task를 확인한다.

**선수개념:** Gradle task; dependency

**관련 표기·별칭:** Gradle lifecycle/task graph

**보완·검증 필요 사항:**

- 추가 실험의 graph는 해당 fixture 선택에 한정되며 모든 project 실행 순서를 보장하지 않는다.

**초보자가 시작할 질문:**

- build가 실패했을 때 compile, test, package 중 어디부터 실패했는지 어떻게 찾나?

## 의존성 선택과 빌드 재현성

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Wrapper·toolchain·lockfile·cache는 서로 다른 역할로 Gradle 실행과 의존성 선택에 영향을 준다.

**언제 사용하는가:** 개발자와 CI 간 JDK/의존성 차이로 결과가 달라지는 원인을 줄일 때 사용한다.

**대안과 경계:** build cache는 재현성 자체가 아니며 Gradle Wrapper는 JDK를 고정하지 않는다. lockfile도 toolchain을 대신 고정하지 않는다.

**예시·실행 근거:** Wrapper 버전, toolchain JDK와 lock된 dependency graph를 CI/로컬에서 비교한다.

**선수개념:** Gradle Wrapper; JDK; dependency

**관련 표기·별칭:** Dependency resolution and reproducibility

**보완·검증 필요 사항:**

- 원문은 관계를 설명하지만 모든 환경을 실제로 재현한 증거는 없다.

**초보자가 시작할 질문:**

- Wrapper를 썼는데 CI와 로컬 결과가 다른 이유는 무엇인가?

## artifact·image 생성과 게시

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** JAR package, 선택적인 container image 생성, registry push는 build 결과를 배포 가능한 위치로 전달하는 별도 단계다.

**언제 사용하는가:** 빌드 성공 후 artifact/image publish 또는 registry 인증 오류를 추적할 때 사용한다.

**대안과 경계:** JAR 생성, image build, registry push는 각각 다른 산출물과 실패 경계다.

**예시·실행 근거:** 첫 실패 task가 dependency, compile, test, package 또는 push 중 무엇인지 찾는다.

**선수개념:** JAR; container image; registry

**관련 표기·별칭:** Artifact and image publishing

**보완·검증 필요 사항:**

- 정적 흐름은 있지만 실행된 publish 결과가 없다.

**초보자가 시작할 질문:**

- JAR가 만들어졌는데 배포 pipeline이 실패하면 다음으로 무엇을 확인하나?
