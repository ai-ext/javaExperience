## 생성자와 객체 불변식

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 생성자는 객체가 쓸 필수 값을 초기화하고 검증합니다. 다른 생성자를 하나라도 선언하면 기본 무인자 생성자는 자동 제공되지 않습니다.

**언제 사용하는가:** 필수값이 적으면 생성자, 공통 초기화는 `this(...)`로 한 경로에 모읍니다.

**대안과 경계:** 생성 중 override 가능한 메서드를 부르면 자식 필드 초기화 전 코드가 실행될 수 있습니다. `final` 참조도 내부 객체를 깊게 고정하지 않습니다.

**예시·실행 근거:** 순수 Java 예제로 부모/자식 초기화 순서, record compact constructor 검증과 출력 결과를 제시합니다. Spring Boot 예제는 미실행입니다.

**선수개념:** 클래스·필드·생성자; 상속과 초기화 순서

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Final reference is not deep immutability; generated no-arg force can violate invariants; Java25 flexible constructor body noted.

**초보자가 시작할 질문:**

- `new Child()` 한 번에서 부모 필드, 부모 생성자, 자식 필드는 어느 순서로 실행될까요?
- `final List`를 생성자에 넣고 그대로 보관하면 호출자가 나중에 무엇을 바꿀 수 있나요?

## 정적 팩토리와 Builder

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 정적 팩토리는 생성 의도에 이름을 붙이고 구현 선택을 숨길 수 있습니다. Builder는 여러 선택값을 단계별로 구성하고 `build()`에서 필수값을 검증합니다.

**언제 사용하는가:** 생성 경로가 여러 의미를 가지면 factory, 선택값이 많아 인자 순서가 불분명하면 Builder를 검토합니다.

**대안과 경계:** 필수값이 적으면 Builder보다 생성자가 단순합니다. 일반 Builder는 컴파일 시 필수값을 보장하지 않아 build 검증이 필요합니다.

**예시·실행 근거:** `Order.of`와 `Order.builder()`로 같은 타입을 만들고 출력 값을 비교합니다.

**선수개념:** 생성자·static method; 선택값·불변성

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Builder의 deep copy/미완성 상태 설계는 프레임워크가 대신 보장하지 않습니다.

**초보자가 시작할 질문:**

- `Order.of(id, quantity)`와 `Order.builder()`는 각각 어떤 생성 의도를 드러내나요?
- Builder에서 필수 id를 빼고 `build()`하면 어떤 검증이 있어야 하나요?

## 불변 참조와 방어 복사

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** `final`은 필드 참조 재대입을 막고 `List.copyOf`는 리스트 구조를 복사해 변경 불가로 돌려줍니다.

**언제 사용하는가:** 값 객체 안에 외부 컬렉션을 저장할 때 입력 참조를 격리하고, 변경 가능한 원소가 있는지도 확인합니다.

**대안과 경계:** `final`만으로 대상 컬렉션이 불변이 되지 않으며 `List.copyOf`도 원소 객체까지 깊게 복사하지 않습니다.

**예시·실행 근거:** Order 생성자에서 tags를 `List.copyOf`하고 Builder를 수정해도 이미 생성한 Order가 유지되는 추가 증거를 제시합니다.

**선수개념:** 참조 타입; List/컬렉션

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 가변 요소 내부 상태는 별도 복사/불변 모델이 필요합니다.

**초보자가 시작할 질문:**

- Builder의 tags에 새 값을 추가한 뒤 이미 만든 Order의 tags가 바뀌어야 할까요?
- `List.copyOf` 뒤에도 원소 객체 자체를 바꿀 수 있는 이유는 무엇인가요?

## Lombok 생성자와 Spring 주입

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** `@RequiredArgsConstructor`는 초기화되지 않은 final/@NonNull 필드 중심 생성자를 컴파일 중 만듭니다. Spring은 유일한 생성자로 협력 객체를 넣습니다.

**언제 사용하는가:** Spring Bean의 필수 의존성을 `private final`로 선언하고 명시적 생성자 또는 Lombok을 사용합니다.

**대안과 경계:** `@NoArgsConstructor(force=true)`는 final을 기본값에 두어 유효 상태 보장을 우회할 수 있습니다. JPA Entity는 DTO와 다른 생성 규칙이 있습니다.

**예시·실행 근거:** PaymentService 생성자 주입과 Lombok 문법을 함께 보여줍니다. 실제 Spring 실행은 미실행입니다.

**선수개념:** Spring Bean; compile-time processor; JPA Entity

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Lombok IDE와 build processor 설정이 일치하는지 확인해야 합니다.

**초보자가 시작할 질문:**

- 필드를 하나 추가했을 때 `@RequiredArgsConstructor`가 생성자 인자로 고르는 기준은 무엇인가요?
- `@NoArgsConstructor(force=true)` 뒤 Entity가 유효하지 않은 상태일 수 있는 이유는 무엇인가요?

## DTO와 JPA Entity 생성 규칙

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 요청/응답 DTO는 외부 값 전달 계약이며 record로 간결하게 표현할 수 있습니다. JPA Entity는 provider 접근을 위한 무인자 생성자와 통제된 상태 변경이 필요합니다.

**언제 사용하는가:** DTO는 입력·응답 목적에 맞춰 만들고, Entity는 도메인 검증과 ORM 생성 조건에 맞게 설계합니다.

**대안과 경계:** 요청 DTO와 Entity는 이름/필드가 같아도 같은 역할이 아닙니다. 외부 JSON을 Entity에 직접 연결하지 않습니다.

**예시·실행 근거:** OrderRequest compact constructor와 Entity protected no-arg 요구를 대비합니다. DTO→Entity 저장은 이 문서에서 끝까지 추적하지 않습니다.

**선수개념:** record; JPA persistence

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- DTO→Entity mapping/save sequence not shown; JPA constructor constraint cited but no runtime provider reproduction.
