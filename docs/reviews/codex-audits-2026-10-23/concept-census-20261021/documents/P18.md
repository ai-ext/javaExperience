## Lost update와 원자 조건부 UPDATE

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** 두 요청이 같은 재고를 읽고 각자 계산한 뒤 저장하면 나중 쓰기가 앞선 차감을 덮어쓸 수 있습니다. 조건 확인과 차감을 한 UPDATE로 묶고 영향 행 수를 성공 여부로 사용합니다.

**언제 사용하는가:** 한 행의 재고 감소는 `stock > 0` 조건부 UPDATE를 우선 검토합니다.

**대안과 경계:** synchronized나 AtomicInteger는 한 JVM 안의 상태만 다루므로 여러 서버와 DB commit을 보호하지 않습니다.

**예시·실행 근거:** 순수 Java 경합 출력은 한 번 관찰한 결과이며 SQL 예시는 Spring에서 실행하지 않았습니다.

**선수개념:** 공유 상태·DB transaction

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- No concurrent MySQL reproduction

**초보자가 시작할 질문:**

- 초기 stock=1일 때 두 요청이 먼저 SELECT 1을 읽고 각각 0을 저장하면 어떤 업데이트가 사라지나요?
- 조건부 UPDATE의 affected rows 0은 이 업무에서 무엇을 뜻하나요?

## 비관적·낙관적 DB 락

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** 비관적 락은 판단 중 행을 잠그고, @Version 낙관적 락은 읽은 뒤 값이 바뀐 stale update를 감지해 충돌을 알립니다.

**언제 사용하는가:** 경합 빈도와 잠금 대기 허용, 판단이 여러 단계인지에 따라 두 방식을 고릅니다.

**대안과 경계:** 둘 다 트랜잭션 경계와 timeout 설정이 중요합니다. 낙관적 충돌 재시도는 실패한 영속성 컨텍스트가 아니라 새 트랜잭션에서 해야 합니다.

**예시·실행 근거:** PESSIMISTIC_WRITE와 @Version 구조를 제시하지만 Spring 예제는 실행하지 않았습니다.

**선수개념:** 공유 상태·DB transaction

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- No lock timing/deadlock measurement

**초보자가 시작할 질문:**

- 잔여 재고 확인과 여러 테이블 변경을 읽은 뒤 결정해야 하면 원자 UPDATE 외에 어떤 선택이 있나요?
- OptimisticLockException을 같은 영속성 컨텍스트에서 바로 재시도하지 말아야 하는 이유는 무엇인가요?

## JVM lock·Redis lease·queue 범위

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** JVM lock은 한 프로세스, Redis SET NX PX는 만료되는 lease, queue는 키별 처리 순서를 다룹니다.

**언제 사용하는가:** 한 JVM 내부의 중복 계산을 줄이거나 순서가 필요한 작업에 쓰되 DB 제약과 원자 UPDATE로 최종 정합성을 보장합니다.

**대안과 경계:** Redis TTL 만료는 오래된 소유자의 작업을 중단시키지 않습니다. Queue도 중복 전달이나 DB 트랜잭션을 대신하지 않습니다.

**예시·실행 근거:** token을 비교해 해제하는 Lua와 상품별 queue 설계를 설명하며 실제 런타임 검증은 하지 않았습니다.

**선수개념:** 공유 상태·DB transaction

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- No Redis/Kafka runtime example

**초보자가 시작할 질문:**

- 서버 두 대가 서로 다른 synchronized 객체를 잠그면 공유 DB 재고를 막을 수 없는 이유는 무엇인가요?
- Redis 락 TTL 뒤 이전 작업이 다시 DB를 쓰지 못하게 보장하는가?

## 멱등키·좌석 unique 제약

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** lock은 동시에 처리되는 구간, idempotency key는 같은 요청의 재전송, unique 제약은 좌석 같은 중복 데이터의 최종 판정을 막습니다.

**언제 사용하는가:** 결제·예약 요청 키와 처리 결과를 unique하게 저장하고 같은 요청 재시도에는 처음 저장한 결과를 반환합니다.

**대안과 경계:** lock만으로 순차 중복 요청을 막을 수 없고, 사전 exists 조회는 조회와 저장 사이 경쟁을 막지 못합니다.

**예시·실행 근거:** `unique(show_id, seat_no)`와 `(user_id, key)` 제약 예시로 최종 중복 차단을 보입니다.

**선수개념:** unique index; request identity; transactions

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- No full idempotency schema/transaction implementation.

**초보자가 시작할 질문:**

- 사용자가 결제 버튼을 연속 클릭해 요청이 순차로 도착해도 왜 락만으론 중복 청구를 막지 못하나요?
- 좌석 exists 조회 두 번이 동시에 false일 때 최종적으로 무엇이 하나만 저장되게 하나요?

## Redis lease and queues

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** Redis SET NX PX 방식은 만료 가능한 lease이고, partition queue는 같은 키의 처리를 직렬화하는 대신 지연·재시도·중복 제거 문제를 더합니다.

**언제 사용하는가:** 정합성보다 중복 작업 감소가 목적이면 Redis lock을 고려하고, 순서가 요구될 때 queue를 선택하되 DB 제약을 함께 둡니다.

**대안과 경계:** TTL 만료 뒤 오래된 소유자가 계속 동작할 수 있습니다. queue 소비도 중복될 수 있어 소비자가 멱등해야 합니다.

**예시·실행 근거:** token 확인 후 해제하는 Lua와 productId 기준 partition을 설명합니다.

**선수개념:** Distributed systems.

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Redis Redlock debated; no implementation or runtime test.

## 실제 캡처 관찰

- 데스크톱 요약은 조건부 UPDATE 권장을 명확히 하고 DB lock과 idempotency를 구분하지만 보이는 화면은 글 중심이다.
- 모바일 제목과 요약은 좁은 화면에 가로 넘침 없이 들어온다. 본문은 줄바꿈되며 읽을 수 있다.
- core에는 조건부 UPDATE, pessimistic/optimistic lock, Redis, idempotency, unique 제약을 포함한 동시성 소주제 9개가 접혀 있다. 경쟁 요청이나 재고 값 변화 그림은 없다.

**관찰 범위:** 캡처는 동시 요청을 실행하거나 재고 counter 전후를 시각화하지 않는다. 캡처된 범위에서는 DB 보장 선택을 글로만 설명한다.
