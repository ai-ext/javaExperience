## RPO·RTO와 복원 시험

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** RPO는 사고에서 허용할 수 있는 데이터 손실 범위, RTO는 서비스 복구 완료까지 허용하는 시간이다.

**언제 사용하는가:** backup 주기와 복원 순서를 정하고 재해 복구 목표를 검증할 때 사용한다.

**대안과 경계:** backup 파일이 존재하는 것만으로 RPO/RTO 달성을 입증하지 못한다. 복구 drill에서 실제 시간을 측정해야 한다.

**예시·실행 근거:** RPO 15분/RTO 2시간은 설명용 숫자이며 실제 복구 결과가 아니다.

**선수개념:** backup; incident response

**관련 표기·별칭:** RPO/RTO and recovery tests; Recovery Point Objective; Recovery Time Objective

**보완·검증 필요 사항:**

- 업무별 실제 목표와 담당 책임은 조직에서 정해야 한다.

**초보자가 시작할 질문:**

- backup 간격이 RPO를 만족하나? 복원 테스트는 실제 몇 분 걸리나?

## DB·VM·애플리케이션 백업 범위

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** DB 행·log, VM disk/OS, 애플리케이션 artifact·파일·secret은 각각 다른 백업 범위다.

**언제 사용하는가:** 전체 서비스를 복구할 때 데이터베이스 이외의 자산도 포함해 설계한다.

**대안과 경계:** DB dump 하나가 JAR, upload 파일, secret과 VM 설정을 대신 백업하지 않는다. snapshot도 transaction-consistent하다고 자동 가정할 수 없다.

**예시·실행 근거:** DB·VM·app asset을 각기 복원해 완전한 service를 구성하는 그림을 따른다.

**선수개념:** server; DB; artifact

**관련 표기·별칭:** DB, VM and app asset backup scope; logical backup; physical snapshot; artifacts

**보완·검증 필요 사항:**

- vendor snapshot의 consistency와 restore 의미는 제품별로 다르다.

**초보자가 시작할 질문:**

- DB dump만 있으면 JAR와 고객 upload 파일도 복구되나?

**근거:**

## 백업 일관성과 시점 복구

현재 판정: **미검증** / 우선순위: high

**정의와 실제 역할:** full backup을 복구한 뒤 continuous binlog/WAL 기록을 재생해 원하는 시각까지 되돌리는 방식을 point-in-time recovery라 한다.

**언제 사용하는가:** 허용 데이터 손실 구간을 줄이고 사고 직전 상태를 복구할 때 사용한다.

**대안과 경계:** MySQL mysqldump의 --single-transaction 일관성은 InnoDB에 한정되며 동시 DDL 등 주의점이 있다. 다른 엔진/제품에 일반화하지 않는다.

**예시·실행 근거:** 분리된 복구 DB에 full backup을 restore하고 지정된 stop time까지 log를 재생한다.

**선수개념:** transaction log; full backup

**관련 표기·별칭:** consistency and PITR; binlog; WAL; PITR

**보완·검증 필요 사항:**

- 복원 절차는 이번 감사에서 실행되지 않았다. MySQL 공식 백업·PITR 범위는 sources에 기록했다.

**초보자가 시작할 질문:**

- full dump를 뜨는 것과 사고 시점 복구는 어떻게 다른가?

## 복원 검증과 백업 보안

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** checksum은 byte 변화 여부를 찾고 업무 query/관계 검사는 복원된 데이터가 쓸 수 있는지 검증한다.

**언제 사용하는가:** 재해 복구 준비와 백업 파일의 무결성·기능성을 확인할 때 사용한다.

**대안과 경계:** hash 일치는 업무 row, 관계, 앱 호환성 또는 service readiness를 증명하지 않는다. backup은 삭제/랜섬웨어로부터 격리하고 실제 restore해야 한다.

**예시·실행 근거:** 원문 149–161행은 source/restored table의 행 수를 UNION ALL query로 비교한다. UNION ALL의 등장 자체는 있지만 UNION/UNION ALL의 독립 정의나 중복 제거 차이 설명은 없다.

**선수개념:** hash; SQL

**관련 표기·별칭:** verify restore/security; 3-2-1; checksum; restore drill

**보완·검증 필요 사항:**

- 실행/캡처 결과는 없고 query 예시는 기대 검증 절차다. R07에서 UNION ALL은 사용되므로 “문자열/코드가 없다”고 하지 않는다. SQL UNION 의미 교육은 여전히 독립적으로 필요하다.

**초보자가 시작할 질문:**

- 파일 hash가 맞으면 서비스 복구도 성공했다고 볼 수 있나?
