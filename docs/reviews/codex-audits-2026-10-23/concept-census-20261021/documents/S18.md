## MockMvc·WebTestClient·실서버

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** MockMvc는 서버 포트 없이 servlet 처리 체인을 호출한다. WebTestClient는 mock binding 또는 실서버에 연결할 수 있다.

**언제 사용하는가:** 네트워크·포트·서버 스레드 검증이 목적일 때만 RANDOM_PORT를 사용한다.

**대안과 경계:** 도구 이름만으로 실제 서버 실행 여부를 판단하지 말고 binding·webEnvironment를 확인한다.

**예시·실행 근거:** MOCK/RANDOM_PORT와 서버 트랜잭션 차이를 설명한다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:**

## Spring TestContext 캐시 키

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 같은 설정 키의 컨텍스트를 JVM 정적 캐시에서 재사용하며 profile·properties·mock customizer 차이는 캐시를 분리한다.

**언제 사용하는가:** CI context 시작이 반복될 때 fork·DirtiesContext·profiles·mock 이름을 비교해 cache miss를 찾는다.

**대안과 경계:** 프로세스 fork는 캐시를 공유하지 않고 DirtiesContext는 컨텍스트 재생성 비용을 만든다.

**예시·실행 근거:** 캐시 hit/miss 구성 예시와 제한을 서술하지만 측정 실행은 없다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

**초보자가 시작할 질문:**

## Testcontainers·ServiceConnection

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Testcontainers는 실제 DB/브로커 컨테이너를 테스트 자원으로 시작하고 ServiceConnection은 연결 세부 정보를 Boot 자동 설정에 연결한다.

**언제 사용하는가:** 운영 엔진별 SQL·제약·잠금 호환성이 중요한 소수 테스트에서 사용한다.

**대안과 경계:** select 1 성공은 schema/migration 전체 호환성을 보장하지 않는다. Docker 환경이 필요하다.

**예시·실행 근거:** PostgreSQLContainer와 @ServiceConnection 예제는 제시되지만 미실행이다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- H2에서 통과한 SQL이 PostgreSQL에서만 실패한다면 어떤 엔진 차이를 Testcontainers로 확인해야 하나요?
- `select 1`이 성공했다는 결과만으로 운영 migration과 제약 조건을 검증했다고 볼 수 있나요?

## 테스트 트랜잭션·fixture 격리

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 테스트 메서드 트랜잭션 rollback은 같은 트랜잭션 자원만 되돌리며 서버 스레드·비동기·REQUIRES_NEW 부수 효과는 따로 정리해야 한다.

**언제 사용하는가:** 테스트별 고유 key/schema와 소유 자원만 cleanup하고 시계·난수 seed를 주입한다.

**대안과 경계:** @ResourceLock은 같은 JUnit 실행 내부만 조정하며 별도 JVM/CI worker/DB를 잠그지 않는다.

**예시·실행 근거:** 문서는 fixture·Clock·Random·병렬성의 실행 예를 포함하나 보강 코드 미실행이다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- 실제 서버 thread에서 만든 행이 테스트 종료 뒤 남았다면 어떤 고유 key나 schema로 fixture를 격리하나요?
- 테스트 순서를 섞을 때만 실패하면 Clock·Random·공유 DB 중 어떤 상태를 기록하고 재현해야 하나요?
