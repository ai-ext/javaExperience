## Instant, LocalDateTime, OffsetDateTime, ZonedDateTime model distinct meanings

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** Instant는 타임라인의 한 순간, LocalDateTime은 zone 없는 벽시계, OffsetDateTime은 고정 offset, ZonedDateTime은 지역 ZoneId 규칙을 담는다.

**언제 사용하는가:** 과거 사건/로그/만료는 Instant, 날짜만이면 LocalDate, 미래 지역 약속은 LocalDateTime+ZoneId와 gap/overlap 정책을 보존한다.

**대안과 경계:** Offset +09:00은 Asia/Seoul의 미래 규칙을 보존하지 않는다. DST gap은 유효 시각 없음, overlap은 두 Instant가 가능하다.

**예시·실행 근거:** 이벤트 Instant를 UTC 저장 후 사용자 ZoneId로 표시; DST 예약은 ZoneRules valid offsets를 확인한다.

**선수개념:** ISO-8601; UTC instant; IANA zone rules; DB/JDBC mapping

**관련 표기·별칭:** wall-clock; ZoneId; ZoneOffset; DST gap/overlap

**판정 이유:** 정의와 선택 기준은 설명하지만 대상 실행 환경의 동작 검증 또는 학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 순수 Java 예제는 원문에 실행됐다고 하지만 이 감사에서 재실행하지 않았다.

**초보자가 시작할 질문:**

- +09:00은 Asia/Seoul과 같은 뜻인가?

## Database/API precision, time zone settings, and Clock-based tests

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** MySQL DATETIME은 timezone 변환 없는 필드, TIMESTAMP는 연결 timezone을 통해 UTC 변환한다. Clock 주입은 현재 시각 경계 테스트를 가능하게 한다.

**언제 사용하는가:** UTC/컬럼 타입/세션 시간대와 정밀도를 맞춰 저장하고 만료는 Clock.fixed로 검증한다. 지역 하루 범위는 zone의 시작부터 다음 시작까지 반열림 구간으로 둔다.

**대안과 경계:** hibernate.jdbc.time_zone 하나가 MySQL session time_zone을 설정하지 않는다. Instant nanos는 컬럼 microsecond precision에서 줄어들 수 있다.

**예시·실행 근거:** Clock.systemUTC를 주입하고 test에서 fixed clock; MySQL read/write roundtrip과 @@session.time_zone 검사.

**선수개념:** JPA temporal types; JDBC Calendar; MySQL session zone; precision; deterministic testing

**관련 표기·별칭:** MySQL DATETIME/TIMESTAMP; hibernate.jdbc.time_zone; Clock.fixed; half-open range

**판정 이유:** 정의와 선택 기준은 설명하지만 대상 실행 환경의 동작 검증 또는 학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- MySQL round-trip·Hibernate binding 예제는 실행하지 않았다.

**초보자가 시작할 질문:**

- MySQL DATETIME과 TIMESTAMP는 시간대 변환이 어떻게 다른가?
- JVM을 UTC로 맞추면 DB 저장 변환까지 고정되나?
- DST 날짜 범위가 항상 24시간인가?
- 만료 경계 시간을 테스트에서 어떻게 고정하나?
