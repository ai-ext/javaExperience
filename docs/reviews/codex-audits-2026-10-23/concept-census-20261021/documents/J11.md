## ThreadPoolExecutor 큐·성장·거절

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** worker가 core보다 적을 때 먼저 늘리고, core가 차면 큐에 넣으며, 큐가 거부하면 max까지 늘립니다. worker도 max면 rejection policy가 실행됩니다.

**언제 사용하는가:** 유입률이 처리율보다 높은 서비스에서 유한 큐·명시 거절 정책을 둡니다.

**대안과 경계:** unbounded queue는 maxPoolSize를 사실상 사용하지 않고 메모리/대기 폭증으로 바뀔 수 있습니다.

**예시·실행 근거:** PoolDemo에서 두 worker+한 대기+AbortPolicy rejection을 latch로 재현합니다.

**선수개념:** ThreadPoolExecutor; bounded queue

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 지속 부하 stress test나 결과 부하 지표는 없습니다.

**초보자가 시작할 질문:**

- 고정 스레드 풀에서 maxPoolSize를 늘려도 worker가 늘지 않을 수 있는 이유는 무엇인가요?
- Future를 기다리는 submit 작업을 DiscardPolicy가 버리면 호출자는 어떤 상태에 빠지나요?

## Future·CompletableFuture 실행 위치와 실패

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** Future.get은 block하고, CompletableFuture의 non-async stage는 완료 thread에서 실행될 수 있으며 thenCompose는 다음 async 결과를 평탄화합니다.

**언제 사용하는가:** async chain의 각 stage 실행 위치와 실패 변환을 명시하고 blocking I/O는 전용 executor로 분리합니다.

**대안과 경계:** Async는 매번 새 thread 보장이 아니며 cancel(true)는 interrupt 요청이지 강제 종료가 아닙니다.

**예시·실행 근거:** FutureDemo가 21→42와 실패 원인 회복을 출력합니다.

**선수개념:** Future; Executor

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Java25 기본 async pool 변경은 JDK21 실행 결과와 분리해야 합니다.

**초보자가 시작할 질문:**

- thenApply 함수가 Future를 반환하면 중첩 타입을 피하기 위해 무엇을 쓰나요?
- Future.cancel(true)를 호출해도 작업이 계속될 수 있는 이유는 무엇인가요?

## Lock·CAS·AtomicLong/LongAdder

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** CAS는 예상한 현재값에 한해 교체합니다. Lock은 timeout/interruption/Condition을 제공하고 LongAdder는 통계 업데이트 경합을 분산합니다.

**언제 사용하는가:** 여러 필드 불변식은 Lock으로, 정확한 단일 값은 AtomicLong, 경합 큰 통계는 LongAdder를 고릅니다.

**대안과 경계:** LongAdder.sum은 원자 스냅샷이 아니며 ReadWriteLock 승격/StampedLock 재진입은 지원하지 않는 경계가 있습니다.

**예시·실행 근거:** 잠금·CAS·카운터 비교표.

**선수개념:** shared state; JMM

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 경합 성능 측정은 하지 않았습니다.

**초보자가 시작할 질문:**

- 잔액을 확인한 뒤 차감하는 두 동작을 LongAdder로 각각 수행하면 왜 업무 불변식이 깨질 수 있나요?
- WriteLock이 필요해질 때 read lock에서 바로 upgrade할 수 있나요?

## ConcurrentHashMap·BlockingQueue·coordination tools

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** ConcurrentHashMap의 key 단위 API는 합성 갱신을 원자화하고 BlockingQueue/latch/semaphore/barrier는 대기·완료·자원 수·단계 합류를 각각 조절합니다.

**언제 사용하는가:** 짧은 key update에 compute/merge, 병렬자원 수에 Semaphore, 완료 gate에 CountDownLatch를 씁니다.

**대안과 경계:** size/iteration은 일관된 전체 스냅샷이 아닐 수 있고 compute function 안의 느린 I/O는 피합니다.

**예시·실행 근거:** 인터페이스 및 선택 기준 표.

**선수개념:** Map; queue; lifecycle

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 컨테이너/DB 동시성 실행 검증은 없습니다.

**초보자가 시작할 질문:**

- containsKey 확인 후 put이 원자적이지 않은 이유는 무엇인가요?
- DB/HTTP 자원을 동시에 3개까지만 쓰려면 latch와 semaphore 중 무엇을 쓰나요?

## ForkJoinPool·common pool·Java25

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** ForkJoinPool은 CPU 작업 분할과 work-stealing을 위한 풀입니다. JDK25에서 schedule API와 CF 기본 async 실행 규칙이 달라졌습니다.

**언제 사용하는가:** 분할 가능한 CPU 작업에는 fork/join을, blocking I/O는 별도 제한 executor를 검토합니다.

**대안과 경계:** blocking은 worker를 소진할 수 있고 common pool은 공유 자원입니다.

**예시·실행 근거:** 문서 흐름도와 JDK25 change table.

**선수개념:** parallel algorithm; CompletableFuture

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Java25 변경 코드는 JDK21에서 실행하지 않았습니다.

**초보자가 시작할 질문:**

- work-stealing이 JDBC 대기 때문에 정체된 풀을 자동으로 해결하지 못하는 이유는 무엇인가요?
- 여러 비동기 함수가 common pool을 쓰면 어떤 작업과 경쟁할 수 있나요?
