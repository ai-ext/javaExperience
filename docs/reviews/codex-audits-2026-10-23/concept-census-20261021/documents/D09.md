## SLI·SLO·SLA와 error budget

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** SLI는 사용자 중심 service 수준 지표, SLO는 내부 목표, SLA는 대외 약속이다. error budget은 목표 대비 허용 실패분을 나타낸다.

**언제 사용하는가:** 서비스의 성공 기준과 배포 위험을 정할 때 사용한다.

**대안과 경계:** HTTP 200만으로 업무 성공을 판정할 수 없고 SLA는 SLO와 동일한 내부 목표가 아니다.

**예시·실행 근거:** 최근 기간 정상 결제 비율로 SLI/SLO/error budget을 계산하는 예를 든다.

**선수개념:** 업무 성공 조건; 요청/기간

**관련 표기·별칭:** SLI·SLO·SLA·error budget; SLI/SLO/SLA/error budget

**보완·검증 필요 사항:**

- 원문 모델은 설명 사례이며 실제 서비스 SLO 측정치는 아니다.

**초보자가 시작할 질문:**

- HTTP 200 응답인데 주문이 실패했으면 가용성 지표는 어떻게 계산하나?

## log·metric·trace·alert 신호

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** log는 사건 문맥, metric은 시간에 따른 집계, trace는 요청 흐름과 span을 보여준다. alert는 즉시 대응 신호다.

**언제 사용하는가:** 서비스 이상 위치와 사용자 영향을 찾아 경보 기준을 만들 때 사용한다.

**대안과 경계:** metric label의 cardinality가 지나치게 크면 비용/저장 문제가 생길 수 있고 alert가 많다고 관측성이 좋은 것은 아니다.

**예시·실행 근거:** 같은 requestId/traceId로 주문부터 결제까지 연결하고 오류율 metric/alert를 비교한다.

**선수개념:** 요청 ID; SLI

**관련 표기·별칭:** log·metric·trace·alert; Logs, metrics, traces and alerts

**보완·검증 필요 사항:**

- 실제 운영 signal은 구성하지 않았고 설명/예시 수준이다.

**초보자가 시작할 질문:**

- 요청 한 건의 실패 원인은 log·metric·trace 중 어디서 가장 잘 보이나?

## 장애 대응·capacity·disaster recovery

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** incident 중에는 원인 분석과 병행해 영향을 낮추는 mitigation을 먼저 하고 postmortem으로 개선한다. RPO/RTO, autoscale, backup은 복구/수용량 선택과 관계된다.

**언제 사용하는가:** 사용자 영향이 있는 장애를 완화하고 다음 복구 목표와 여유 capacity를 정할 때 사용한다.

**대안과 경계:** mitigation은 근본 원인 해결과 다르다. backup은 restore test, autoscale은 실제 병목과 scaling 경계를 따로 검증해야 한다.

**예시·실행 근거:** incident 영향 축소→RPO/RTO에 맞춘 restore test→capacity 조정 흐름을 비교한다.

**선수개념:** SLO; backup; 용량 관측

**관련 표기·별칭:** incident·capacity·disaster recovery; Incident, capacity and DR

**보완·검증 필요 사항:**

- 실제 장애·복구 훈련, autoscale 성능 측정은 없다.

**초보자가 시작할 질문:**

- DB를 복구하는 데 1시간이 걸리면 데이터 손실 허용량과 어떻게 구분하나?
