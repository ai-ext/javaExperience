## 디버깅 도구 선택은 실행 위치·재현성·중단 영향에 따른다

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** 디버깅 도구는 실행 위치·재현성·중단 영향으로 고른다.

**언제 사용하는가:** 로컬에서 재현되는 조건은 IDE breakpoint, 간헐 운영 문제는 로그·metrics·trace를 우선한다.

**대안과 경계:** breakpoint는 실행 중단과 local state, telemetry는 중단 없이 사전 기록된 사건을 보여준다.

**예시·실행 근거:** 브라우저 Network와 server trace ID를 함께 보고, 운영 JVM을 임의로 중단하지 않는다.

**선수개념:** browser DevTools; server JVM

**관련 표기·별칭:** browser DevTools; IDE debugger; operational debugging

**판정 이유:** 개념 정의와 적용 기준은 확인되나 실제 실행/학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 문서 예제는 Java25 참조가 있으나 저장소 toolchain Java21이며 실행 검증 안 됨.

## Breakpoint, Logpoint, logger and JDWP semantic difference

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** Breakpoint/Logpoint와 JDWP 원격 디버깅

**언제 사용하는가:** Breakpoint는 thread를 멈추고 state/stack을 본다. JDWP는 JVM inspection/control 통로, 로그/metrics/trace는 선택해 남긴 관측 데이터다.

**대안과 경계:** 로컬 deterministic bug에 breakpoint, 운영에서 끝난/간헐 요청은 correlation ID 기반 telemetry를 쓴다.

**예시·실행 근거:** JDWP는 원격 통제 권한이므로 공개 bind는 위험하고 운영 관측성 대체가 아니다. console println은 레벨/문맥/수집 정책이 없다. 추가 예: 로컬 loopback에서 breakpoint; 운영은 제한 네트워크의 로그/trace와 thread dump.

**선수개념:** JVM subclass proxy; JDWP network access

**관련 표기·별칭:** suspended thread; JDWP; postmortem observability

**판정 이유:** 개념 정의와 적용 기준은 확인되나 실제 실행/학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- JVM process
- JDWP security
- debugger stack

**초보자가 시작할 질문:**

- 실제 IDE/원격 JDWP는 실행하지 않았다.

## 로그와 관측성 신호의 역할

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** 로그·metrics·trace의 역할

**언제 사용하는가:** 로그는 사건 기록, metrics는 집계 수치, trace는 요청 경로와 span 지연을 연결한다.

**대안과 경계:** 재현 어려운 장애와 분산 호출 지연에서 요청 ID와 안전한 필드를 미리 기록한다.

**예시·실행 근거:** 로그만으로 세부 변수 상태를 재구성할 수 없고 trace는 임의 local state를 자동 수집하지 않는다. 민감 필드도 수집기에서 자동 안전화되지 않는다. 추가 예: 요청 ID를 MDC에 넣고 비동기 문맥 전달/정리를 설정한다.

**선수개념:** logging; metrics; distributed tracing

**관련 표기·별칭:** log; metric; trace; trace ID; APM

**판정 이유:** 개념 정의와 적용 기준은 확인되나 실제 실행/학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- SLF4J
- MDC
- tracing

**초보자가 시작할 질문:**

- 실제 collector/MDC async propagation은 미검증.
