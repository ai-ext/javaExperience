## workload·SLO·capacity 모델

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** RPS, p95 latency, concurrency와 Little’s Law를 workload 및 측정된 처리량과 연결한다. 수치 예제는 설명용이다.

**언제 사용하는가:** 서비스 목표와 load test 결과를 이용해 안정 수용량을 추정할 때 사용한다.

**대안과 경계:** 평균 RPS만으로 peak나 tail latency를 설명할 수 없다. Little’s Law 입력은 동일한 시스템 경계의 측정값이어야 한다.

**예시·실행 근거:** 현실적인 요청 mix에서 p95, 동시 요청과 error를 측정해 capacity를 산정한다.

**선수개념:** 요청 분포; SLO; load test

**관련 표기·별칭:** Workload/SLO/capacity model

**보완·검증 필요 사항:**

- 예시 수치는 실제 API benchmark 결과가 아니다.

**초보자가 시작할 질문:**

- 응답시간 목표와 동시 요청을 바탕으로 인스턴스 수를 어떻게 정하나?

## 애플리케이션과 DB 자원

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** JVM heap/native memory와 DB working set/buffer pool/storage IOPS·throughput은 서로 다른 자원이다.

**언제 사용하는가:** 성능 병목이 app인지 DB인지 자원 지표로 나눌 때 사용한다.

**대안과 경계:** app CPU나 heap 증설은 DB I/O·lock 대기 병목을 해결하지 않을 수 있다.

**예시·실행 근거:** app heap/GC와 DB buffer/IOPS/wait를 같은 workload에서 비교한다.

**선수개념:** JVM memory; DB cache; storage

**관련 표기·별칭:** App vs database resources

**보완·검증 필요 사항:**

- 실제 서비스 자원 지표는 실행/측정하지 않았다.

**초보자가 시작할 질문:**

- 앱 메모리를 늘렸는데 요청이 계속 느리면 DB의 어느 지표를 확인하나?

## 인스턴스 수와 cloud sizing

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 인스턴스 수는 측정한 healthy 처리량과 목표 여유, 장애 시 남길 용량으로 산정한다. N+1은 한 대 장애를 감당하는 여유를 포함한다.

**언제 사용하는가:** peak load와 인스턴스 장애를 견딜 수 있는 수량을 추정할 때 사용한다.

**대안과 경계:** health endpoint만 때리는 k6 측정은 실제 업무 API의 DB/외부 호출 workload를 대표하지 않는다.

**예시·실행 근거:** 실제 요청 mix를 부하 테스트하고 p95·오류·resource를 기준으로 N+1 수량을 계산한다.

**선수개념:** 용량 측정; autoscaling

**관련 표기·별칭:** Instance count/cloud sizing

**보완·검증 필요 사항:**

- 원문 k6 예제는 health endpoint만 시험해 업무 API capacity를 검증하지 않는다.

**초보자가 시작할 질문:**

- health check가 초당 수천 번 응답하면 실제 주문 API도 그만큼 처리한다는 뜻인가?
