## OFFSET, Page/Slice와 깊은 페이지 비용

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** OFFSET은 정렬 결과 앞의 위치를 숫자로 지정해 건너뛰므로 깊어질수록 선행 엔트리 처리 비용이 증가할 수 있다. Page는 total metadata, Slice는 다음 창 여부에 초점.

**언제 사용하는가:** 번호 이동과 전체 건수가 요구되는 얕은 검색 목록은 제한된 Page; 무한 스크롤이나 순차 소비는 keyset 고려.

**대안과 경계:** 인덱스는 필터·정렬 비용 개선 가능하지만 OFFSET skip 의미는 남는다. 정확한 count 쿼리는 추가 비용이다.

**예시·실행 근거:** LIMIT 50 OFFSET 500000와 같은 필터/ORDER BY cursor query를 EXPLAIN ANALYZE로 비교; 실제 성능은 계획 측정해야 한다.

**선수개념:** SQL ordering/index; Spring Data Pageable; count semantics

**관련 표기·별칭:** LIMIT/OFFSET; Page; Slice; count query

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- SQL 계획 예제는 측정 안내이며 이 감사가 DB 실행하지 않았다.
- JPA Window/keyset API example is marked unexecuted; actual version compilation needed.
- EXPLAIN ANALYZE는 쿼리를 실제 실행하므로 운영 영향 경고가 있다.

## 키셋 커서와 deterministic composite ordering

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** 키셋은 전체 결정적 정렬 tuple을 커서로 전달해 WHERE seek 경계를 구성한다. 순차 읽기의 삽입 밀림을 줄이지만 다중 요청을 하나의 snapshot으로 묶지 않는다.

**언제 사용하는가:** 깊은 피드/무한 scroll, 대량 결과 순차 처리 및 안정 tie-breaker가 있을 때.

**대안과 경계:** 정렬 tuple이 유일/비NULL/가능하면 불변이어야 한다. 혼합 ASC/DESC는 각 조건 방향이 달라진다. 커서 서명은 무결성이지 접근 권한이 아니다.

**예시·실행 근거:** ORDER BY created_at DESC, id DESC에 맞춰 두 키를 cursor로 보내고 사전식 조건으로 다음 창을 읽는다. Base64 토큰은 서명 없이는 위조를 막지 못한다.

**선수개념:** lexicographic ordering; composite index; SQL null logic; pagination API contract

**관련 표기·별칭:** keyset pagination; ScrollPosition; cursor token; tie-breaker

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 예제 코드/API/Spring Data 4.1 API는 미실행.
- Cursor filtering and index needs must be measured on MySQL 8.4 workload; no actual explain plan supplied.
- Snapshot/watermark guarantees need separate product/DB transaction design.

**초보자가 시작할 질문:**

- created_at 동률일 때 중복/누락이 왜 생기나?
- 커서가 같은 DB snapshot을 보장하나?
