## 인덱스 구조와 유지 비용

현재 판정: **충분** / 우선순위: high

**정의와 실제 역할:** InnoDB clustered index leaf에는 행이 저장되고 secondary index leaf에는 보조 키와 PK가 기록된다.

**언제 사용하는가:** 다른 열 조건으로 행을 찾거나 정렬 계획을 개선할 가능성을 검토할 때 사용한다.

**대안과 경계:** 인덱스는 읽기 비용을 줄일 수 있지만 저장공간과 INSERT/UPDATE/DELETE 유지 비용을 늘린다.

**예시·실행 근거:** secondary index에서 후보를 찾은 뒤 PK로 행을 조회하는 과정을 따라간다.

**선수개념:** index page; Primary Key

**관련 표기·별칭:** index structure and cost; B-tree; clustered index; secondary index

**보완·검증 필요 사항:**

- 공개 화면에서 특정 데이터의 실행계획/실행시간 변화는 측정하지 않았다. 인덱스가 항상 빨라진다는 결론은 원문이 말하는 범위가 아니다.

## 복합 인덱스의 선두 열과 범위 탐색

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 복합 인덱스는 열 순서대로 정렬되어 선두 열부터 이어지는 조건을 범위 탐색에 활용한다.

**언제 사용하는가:** 여러 WHERE와 ORDER BY 조건에 맞춰 인덱스 열 순서를 설계할 때 사용한다.

**대안과 경계:** 선두 등가 조건 뒤 첫 range 이후의 열은 탐색 범위를 더 줄이지 못할 수 있지만 필터나 covering에 쓰일 수 있다.

**예시·실행 근거:** (member_id, ordered_at)에 member_id 등가 조건과 ordered_at 날짜 범위를 적용한다.

**선수개념:** WHERE; 정렬된 복합 키; 실행계획

**관련 표기·별칭:** composite leftmost prefix and ranges; composite index; leftmost prefix; range scan

**보완·검증 필요 사항:**

- 공개 원문은 선두 prefix와 range 조건을 설명하지만 두 번째 열 단독 조건의 실제 작업량은 보여주지 않는다. 부모 probe의 전체 index scan 결과는 별도 근거다.

**초보자가 시작할 질문:**

- 복합 인덱스에서 두 번째 열만 조건에 쓰면 어떤 탐색이 가능하고 어떤 작업이 늘어나나?

## 커버링 인덱스

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 조회에 필요한 값이 index에서 모두 나와 테이블 행을 다시 읽지 않는 계획을 covering이라 한다.

**언제 사용하는가:** 자주 실행되는 조회에서 이득과 인덱스 폭 비용을 실제 계획으로 확인할 때 고려한다.

**대안과 경계:** 인덱스에 열을 넣으면 조회를 덮을 수 있지만 저장과 쓰기 갱신 비용이 증가한다.

**예시·실행 근거:** 필요한 id와 ordered_at이 `(member_id, ordered_at)` 인덱스에서 제공되는 예를 본다. 부모 probe는 별도 실행 근거다.

**선수개념:** EXPLAIN key/Extra; secondary index와 PK

**관련 표기·별칭:** covering index; Using index; index-only scan

**보완·검증 필요 사항:**

- 공개 원문 설명에는 실제 실행계획이 없다. 부모 probe로 확인한 Using index·Using index condition·전체 index scan 대비를 공개 화면에 추가하지 않았다.

**초보자가 시작할 질문:**

## 실행계획 추정치와 실제 관측값

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** EXPLAIN은 선택된 계획과 추정을 보여주고 EXPLAIN ANALYZE는 query를 실행해 actual rows와 loops 등을 관측한다.

**언제 사용하는가:** 추정치와 실제 작업량 차이나 인덱스 선택 이유를 조사할 때 사용한다.

**대안과 경계:** rows 추정값은 시간 단위가 아니다. 데이터가 작거나 선택도가 낮으면 table scan이 합리적일 수 있다.

**예시·실행 근거:** optimizer 예상 rows와 ANALYZE actual rows/loops를 나란히 본다.

**선수개념:** optimizer statistics; query 조건과 data 규모

**관련 표기·별칭:** optimizer plan and actual metrics; EXPLAIN; EXPLAIN ANALYZE; actual rows; loops

**보완·검증 필요 사항:**

- EXPLAIN/ANALYZE 비교 절차는 있으나 원문에 실행 output과 실제 metric은 없다. 부모 probe는 독립 fixture 결과이며 benchmark가 아니다.

## 인덱스 범위 탐색에 맞는 조건식

현재 판정: **충분** / 우선순위: high

**정의와 실제 역할:** 인덱스 열에 함수를 적용하면 정렬된 키 범위로 바로 찾기 어려워질 수 있다.

**언제 사용하는가:** 날짜 범위와 접두어 검색 조건을 인덱스 가능한 범위식으로 표현할 때 사용한다.

**대안과 경계:** 포함 문자열 검색은 B-tree 접두어 범위와 달라 full-text 등 다른 방법이 필요할 수 있다.

**예시·실행 근거:** DATE(column)=day 대신 당일 시작 포함, 다음날 시작 제외의 반개구간 조건을 쓴다.

**선수개념:** SQL 조건; 인덱스 정렬 순서

**관련 표기·별칭:** sargability and B-tree range; function on column; leading wildcard

**보완·검증 필요 사항:**

- 원문은 함수/leading wildcard 예와 대안을 설명한다. 자료별 실행계획 및 결과 비교는 보여주지 않는다.

## 공개본과 진행 중 보강의 차이

**추가된 내용:** 보강 HTML은 공개 HTML과 다르다. progress 캡처에서 SQL 실행 결과와 상태 비교가 추가된 점을 확인했으나 소스 원문은 동일하다. 공개된 학습 화면에 포함된 것으로 계산하지 않는다. 부모 측 MySQL 8.4.11 probe에서 복합 인덱스의 covering 조회는 range 10행 및 Using index, 비포함 열 추가 시 Using index condition, 두 번째 열만 조회하면 type=index·약 9532행의 전체 커버링 인덱스 스캔으로 관측됐다. 이 결과는 효율적인 key lookup과 전체 index scan을 구별하며, 본 에이전트의 실행으로 표시하지 않는다.

**공개본과의 차이:** B-tree의 root→internal→leaf 경로, 복합 키 정렬 순서와 leftmost prefix, EXPLAIN 추정치와 실행 관측치의 대응이 공개 화면에서 보이지 않는다. 공개 화면에서는 covering index, Index Condition Pushdown, 두 번째 열만 쓸 때 전체 인덱스 스캔을 실제 결과로 구분하지 않는다.
