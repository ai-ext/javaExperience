## HotSpot interpreter·C1/C2·Tiered

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** HotSpot은 인터프리터 실행과 profile 수집 뒤 hot code를 단계 컴파일할 수 있습니다. C1/C2는 HotSpot implementation 이름입니다.

**언제 사용하는가:** 기동/워밍업과 정상상태를 분리하고 JIT log를 성능 가설 확인에 씁니다.

**대안과 경계:** 컴파일 레벨·threshold는 VM 계약이 아니고 모든 메서드가 C2되는 것도 아닙니다.

**예시·실행 근거:** JitWorkload에서 level 3 관찰. C2/JIT speedup 결론은 내리지 않았습니다.

**선수개념:** JVM bytecode; profile

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 한 번의 compile log로 성능 우위를 확정할 수 없습니다.

## Inlining·escape analysis·deoptimization

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Inlining은 호출 코드 접합, escape analysis는 참조가 경계를 넘는지 보고 scalar replacement/lock elimination 근거를 줄 수 있습니다. Deoptimization은 compile 가정이 깨졌을 때 실행 상태를 복구합니다.

**언제 사용하는가:** allocation/CPU evidence가 있을 때 optimization 로그와 profile을 연결합니다.

**대안과 경계:** 객체가 자동으로 stack에 배치되는 사양이 아니며 deoptimization 1회는 정상일 수 있습니다.

**예시·실행 근거:** 프로파일링 가정이 맞지 않을 때 deoptimization이 일어날 수 있음을 설명합니다. allocation 제거 효과를 입증한 실행은 아닙니다.

**선수개념:** JIT profile; object escape

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Optimization result varies with JIT/profile and is not reproduced here.

**초보자가 시작할 질문:**

- 지역 `new Point()` 객체가 런타임에 존재하지 않을 수도 있다는 말은 stack allocation 보장과 같은 뜻인가요?
- 런타임 실제 타입이 달라지면 JIT 가정에 어떤 복구가 일어날 수 있나요?

## JMH benchmark design

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** JMH는 warmup/measurement/fork를 분리해 small operation을 통제된 조건에서 비교합니다.

**언제 사용하는가:** 동일 입력/옵션에서 결과를 소비하고 단위/error/confidence, JVM/hardware 등을 기록합니다.

**대안과 경계:** System.nanoTime single run은 JIT/프로세스 상태가 섞이고 운영 tail latency를 대신하지 않습니다.

**예시·실행 근거:** SumBenchmark는 JMH 구조를 설명하는 예시이며 JMH 설정·실행은 하지 않았습니다.

**선수개념:** JIT warmup; statistical comparison

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 숫자 benchmark result는 없음.

## JFR·async-profiler·진단 선택

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** JFR은 이벤트와 시간 흐름, async-profiler는 CPU/allocation/lock stack sample을 보여줍니다. CPU sample과 wait time sample은 다른 질문입니다.

**언제 사용하는가:** CPU 높으면 hot stack, CPU 낮은 latency는 wait/lock/db pool/thread dump를 함께 봅니다.

**대안과 경계:** flame graph 비율은 sample 추정치이며 heap dump는 pause/disk/privacy 영향이 큽니다.

**예시·실행 근거:** JFR custom event 실제 count=1, operational command examples.

**선수개념:** JVM events; thread states

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- No live production incident captured.

## Operational diagnostic selection

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 지연 시간과 CPU 사용 상태에 따라 JFR, thread dump, heap histogram/dump, compiler log처럼 다른 관찰 자료를 선택합니다. dump에는 성능 영향과 민감 정보 노출 가능성이 있습니다.

**언제 사용하는가:** 먼저 증상을 분류하고 필요한 최소 자료를 수집하며, heap dump나 상세 로그는 영향·보관·접근 통제를 검토합니다.

**대안과 경계:** CPU sample은 실행 중인 연산을 보여 주고 대기 thread dump는 잠금·I/O 대기를 보여 줍니다. 서로 대신할 수 없습니다.

**예시·실행 근거:** 지연·CPU 상태에 따라 JFR, thread dump, heap histogram/dump, compiler log 중 조사 도구를 고르는 절차입니다.

**선수개념:** JVM/OS process basics
