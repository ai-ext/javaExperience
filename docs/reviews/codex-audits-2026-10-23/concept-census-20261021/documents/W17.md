## Cache layer choice and HTTP freshness/validator

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** 브라우저/CDN은 HTTP 표현을, Caffeine은 JVM별 조회 결과를, Redis는 공유 키/값을 보관한다. DB buffer pool은 DB 내부 최적화다.

**언제 사용하는가:** 공개 정적·변경 드문 응답은 HTTP cache부터 적용하고, 반복 조회가 병목으로 확인되면 로컬 캐시나 공유 캐시를 고려한다.

**대안과 경계:** ETag 재검증은 서버 요청이 간다. no-cache는 재사용 전 검증, no-store는 저장 금지다. Redis에는 네트워크/직렬화/운영 비용이 있다.

**예시·실행 근거:** 공개 카테고리는 revision 기반 ETag, 한 JVM 반복 조회는 bounded Caffeine, 공유가 필요하면 Redis CacheManager를 쓴다.

**선수개념:** HTTP cache directives; Spring Cache proxy; key design; distributed invalidation

**관련 표기·별칭:** browser cache; CDN; Caffeine; Redis; ETag; Cache-Control

**판정 이유:** 정의와 선택 기준은 설명하지만 대상 실행 환경의 동작 검증 또는 학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 예제 미실행; CDN/browser hit 지표와 실제 cache-manager 설정을 확인하지 않았다.

## Cache key, invalidation, stale consistency and stampede controls

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** 캐시는 허용 가능한 오래된 값의 사본이며 결과를 바꾸는 모든 입력을 키로 구분해야 한다. DB commit과 캐시 무효화는 자동으로 원자화되지 않는다.

**언제 사용하는가:** 데이터별 stale 허용 시간을 정하고 commit 뒤 무효화한다. 반드시 전달돼야 할 invalidation은 outbox와 재시도를 고려한다.

**대안과 경계:** TTL은 즉시 일관성이 아니다. commit 전 삭제는 구버전 DB 값을 재적재할 수 있다. tenant/user/locale 누락은 다른 사용자의 값 반환 위험이다.

**예시·실행 근거:** 키에 tenant+locale 포함, commit 후 evict/outbox, miss burst에는 single-flight와 DB 보호 제한을 둔다.

**선수개념:** transaction commit order; key normalization; HTTP shared/private cache; consistency/failure modes

**관련 표기·별칭:** cache key; TTL; @CacheEvict; cache stampede; cache penetration; cache avalanche

**판정 이유:** 정의와 선택 기준은 설명하지만 대상 실행 환경의 동작 검증 또는 학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- fault injection·DB/cache race·CDN key 검증은 실행하지 않았다.

**초보자가 시작할 질문:**

- TTL이 수정 직후 새 값을 보장하나?
- DB commit 전에 cache를 지우면 어떤 race가 있나?
- 키에서 tenant/locale/permission을 빼면?
- 캐시 장애 fallback으로 DB가 어떻게 과부하되나?
