## 서비스 트랜잭션 경계와 propagation REQUIRED

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** 서비스 유스케이스 진입점이 함께 성공/실패해야 할 여러 DB 변경을 하나의 트랜잭션으로 묶는다. Spring proxy가 외부 호출을 가로채고 REQUIRED는 기존 트랜잭션에 참여하거나 없을 때 시작한다.

**언제 사용하는가:** 주문·재고처럼 여러 저장 작업이 한 업무 불변식을 구성할 때. Controller/배치/메시지 등 진입 채널과 독립적인 경계가 필요할 때 서비스 진입점을 둔다.

**대안과 경계:** Controller는 HTTP 수명, Repository는 저장 단위, 서비스는 업무 경계다. 각 Repository 단독 커밋은 앞선 커밋을 나중 예외로 되돌릴 수 없다. `TransactionTemplate`은 코드 구간을 좁히는 대안이다.

**예시·실행 근거:** 주문 insert와 재고 조건부 차감을 서비스 `@Transactional`로 감싸고 실패 시 rollback; 저장소 호출은 REQUIRED로 참여한다.

**선수개념:** Spring proxy/AOP; 트랜잭션 매니저; JDBC 자원 동기화; rollback 규칙

**관련 표기·별칭:** 유스케이스 트랜잭션; Unit of Work; PROPAGATION_REQUIRED

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 예제는 미실행. Bootstrap은 Boot4.1/Framework7 기준, 파일은 Java25라 프로젝트 Java21과 구분 필요.
- 업무 서비스라는 계층은 이름보다 유스케이스 소유권으로 정의해야 한다.
- 외부 API·다른 DB·브로커까지 같은 @Transactional로 원자화된다고 오해하지 않도록 Outbox/Saga 후속 학습 필요.
- Controller 메서드 경계, JSON 직렬화 및 OSIV는 별개로 실환경 검증 필요.

**초보자가 시작할 질문:**

- 왜 저장소마다 @Transactional이 있어도 부분 커밋이 가능한가?
- REQUIRED는 언제 새 트랜잭션을 만들고 언제 참여하나?
- Controller 반환 뒤 JSON 직렬화도 트랜잭션 안인가?

## 프록시 경계·예외 rollback·커밋 후 이벤트의 한계

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** 선언형 트랜잭션은 Spring proxy 호출 시 적용되며 기본 rollback은 RuntimeException/Error다. AFTER_COMMIT은 실행 시점이지 영속 이벤트 저장·재전달 보장이 아니다.

**언제 사용하는가:** 호출 경로, 예외 유형, 외부 시스템 필수 후처리의 신뢰성 요구를 설계할 때.

**대안과 경계:** 같은 객체 내부 호출은 proxy 우회. DB rollback은 HTTP 결제/메일을 취소하지 않는다. 커밋 후 이벤트는 best effort; 내구 전달은 Outbox/보상 흐름 고려.

**예시·실행 근거:** 외부 진입 가능한 유스케이스 메서드에서 단일 tx; 이벤트는 커밋 뒤 알림, 반드시 전달되어야 하면 outbox row를 같은 DB transaction에 기록한다.

**선수개념:** Spring AOP proxy; Java exception hierarchy; 트랜잭션 자원 범위

**관련 표기·별칭:** self-invocation; rollbackFor; AFTER_COMMIT; Outbox

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 예제는 실행하지 않았다.
- 공식 문서 기준의 transaction manager/annotation 설정 및 실제 application proxy 확인 필요.

**초보자가 시작할 질문:**

- 같은 객체의 this 호출이 왜 @Transactional을 건너뛸 수 있나?
- checked exception 또는 잡힌 예외에서 데이터는 어떻게 되나?
- AFTER_COMMIT 리스너는 유실을 막아 주나?

## 공개본과 진행 중 보강의 차이

**추가된 내용:** 원문 A/B/C/D 코드는 그대로 두고 별도 Spring Framework 7.0.9 CGLIB + H2 2.4.240 + JDK21 테스트 harness와 A/B 명시적 동명 대안, transaction/connection/table seed, 독립 JDBC observer 결과를 붙였다. Repository별 REQUIRED 경계에서 첫 주문 commit 뒤 재고 실패시 부분 주문이 남는 경우, 상위 서비스 transaction에서 함께 rollback 되는 경우, 별도 실행에서 두 transaction commit 성공을 보여준다. 실행 범위는 직접 JVM 호출·H2·Spring transaction manager; Boot 웹서버/실제 HTTP·MVC 201·응답 직렬화·외부 알림/broker는 미실행.

**공개본과의 차이:** 진행중 보강이 공개 기준에서 확인되지 않는 경우 공개 화면 기능으로 산입하지 않는다.
