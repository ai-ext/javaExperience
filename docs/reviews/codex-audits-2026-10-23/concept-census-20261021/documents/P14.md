## 이미지·컨테이너·레지스트리

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 이미지는 컨테이너 파일시스템/실행 템플릿, 컨테이너는 격리 실행 프로세스, registry는 이미지를 배포합니다.

**언제 사용하는가:** 로컬 DB/Redis 버전 재현에 태그가 명확한 이미지와 Compose를 사용합니다.

**대안과 경계:** 컨테이너의 writable layer와 volume 수명은 다릅니다. 컨테이너 삭제가 DB volume 삭제를 뜻하지 않습니다.

**예시·실행 근거:** docker pull/run/ps/logs/exec/stop/rm 명령이 제시됩니다.

**선수개념:** 프로세스·파일·네트워크 기초; Docker/Compose 실행 위치

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- macOS/Windows VM/engine 세부는 환경별 확인

**초보자가 시작할 질문:**

- 컨테이너만 삭제했는데 DB 데이터가 남을 수 있는 이유는 무엇인가요?
- 이미지 태그를 명시하면 로컬 재현에서 어떤 불확실성을 줄이나요?

## 네트워크·포트와 실행 위치

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 호스트 포트 매핑은 외부/호스트 앱을 컨테이너 포트에 전달하고 Compose 내부는 service DNS 이름을 사용합니다.

**언제 사용하는가:** 호스트 실행은 127.0.0.1:published port, container 실행은 `mysql:3306`으로 연결합니다.

**대안과 경계:** localhost는 호출을 실행하는 현재 network namespace입니다. 컨테이너 간 통신엔 ports가 불필요할 수 있습니다.

**예시·실행 근거:** 호스트 JDBC `127.0.0.1:3307`, 컨테이너 `mysql:3306`.

**선수개념:** 프로세스·파일·네트워크 기초; Docker/Compose 실행 위치

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 실제 compose network 실행은 예제에서 확인하도록 안내

**초보자가 시작할 질문:**

- Spring 앱이 호스트에서 실행될 때와 Compose 안에서 실행될 때 DB URL이 달라지는 이유는 무엇인가요?
- 서비스 간 통신에 host port를 공개하지 않아도 되는 상황은 무엇인가요?

**근거:**

## 볼륨·초기 SQL·migration

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Named volume은 컨테이너와 별개로 데이터 디렉터리를 보존합니다. MySQL init 스크립트는 빈 데이터 디렉터리에서 초기화 때 실행됩니다.

**언제 사용하는가:** 개발 DB 보존은 volume, 반복 가능한 schema 변경은 migration 도구로 처리합니다.

**대안과 경계:** down과 down -v는 데이터 영향이 다르며, 이미 초기화된 volume은 새 init script를 다시 읽지 않습니다.

**예시·실행 근거:** `down -v`를 명시적 reset으로 구분하고 init.sql 재실행 조건을 설명합니다.

**선수개념:** 프로세스·파일·네트워크 기초; Docker/Compose 실행 위치

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- DB 백업/복구 정책은 별도

**초보자가 시작할 질문:**

- init SQL을 고쳤는데 기존 DB 테이블이 바뀌지 않는 이유는 무엇인가요?
- `docker compose down -v` 전에 어떤 데이터 영향부터 확인해야 하나요?

**근거:**

## depends_on·healthcheck readiness

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** depends_on은 서비스 시작 순서를 정하고 healthcheck/service_healthy는 초기 readiness 조건을 표현합니다.

**언제 사용하는가:** 앱 연결 전에 DB가 실제 요청을 받을 준비가 됐는지 확인합니다.

**대안과 경계:** running과 ready는 같지 않으며 healthcheck도 이후 런타임 장애를 제거하지 않습니다.

**예시·실행 근거:** GET /hello 요청 예와 컨테이너 실행·DB·Git 확인 창의 역할을 연결합니다.

**선수개념:** 프로세스·파일·네트워크 기초; Docker/Compose 실행 위치

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 재시도/backoff는 애플리케이션 운영 쪽에서 별도 필요

**초보자가 시작할 질문:**

- DB 컨테이너가 running인데 첫 JDBC 연결이 실패할 수 있는 이유는 무엇인가요?
- healthcheck가 프로세스 존재 대신 무엇을 확인해야 하나요?

## 개발 Compose 지원과 Testcontainers

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Boot Docker Compose 지원은 개발 실행의 서비스를 감지하고 Testcontainers는 테스트 lifecycle에 맞춰 격리 컨테이너를 실행합니다.

**언제 사용하는가:** 공유 로컬 DB는 Compose, 테스트별 재현성은 Testcontainers를 검토합니다.

**대안과 경계:** 자동 ConnectionDetails가 설정값을 앞설 수 있어 자동/수동 URL 전략을 명확히 합니다.

**예시·실행 근거:** Boot `developmentOnly` 의존성과 integration test context-managed containers.

**선수개념:** 프로세스·파일·네트워크 기초; Docker/Compose 실행 위치

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Boot 4.1 minimum Compose version/current provider details are time-sensitive

**초보자가 시작할 질문:**
