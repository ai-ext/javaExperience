## JPA and MyBatis persistence-state mental models

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** JPA entity state와 MyBatis SQL mapping은 상태 추적 방식이 다르다.

**언제 사용하는가:** 객체 도메인 lifecycle 중심은 JPA, SQL/result mapping 중심은 MyBatis를 고른다.

**대안과 경계:** JPA는 persistence context가 변경 감지, MyBatis는 명시 SQL 결과를 반환하며 엔티티 변경을 자동 추적하지 않는다.

**예시·실행 근거:** 동일 변경을 JPA managed entity와 MyBatis update로 나란히 비교한다.

**선수개념:** JPA entity state; MyBatis SQL mapping

**관련 표기·별칭:** managed/detached entity; dirty checking; write-behind; explicit SQL mapping

**판정 이유:** 개념 정의와 적용 기준은 확인되나 실제 실행/학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 예제는 미실행; 쿼리 로그 비교 없음.

**초보자가 시작할 질문:**

- 필드 setter 뒤 두 도구는 저장 SQL을 어떻게 만들까?

## 새 entity 판정과 persist/merge return identity

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** 새 entity 판단과 persist/merge 반환 동일성

**언제 사용하는가:** persist는 새 객체를 관리 상태로 등록하고 merge는 detached 상태를 복사해 managed 객체를 반환한다.

**대안과 경계:** 새 entity 저장 시 persist/repository save 정책, detached 객체를 병합할 때 반환 객체를 사용한다.

**예시·실행 근거:** id가 있다고 DB 행 존재나 managed 상태를 뜻하지 않는다. merge 원본은 계속 detached일 수 있다. 추가 예: detached = em.merge(input); 이후 managed 변수로 상태를 조회/수정한다.

**선수개념:** persist/merge; entity id; Spring Data save

**관련 표기·별칭:** Spring Data save; persist; merge; assigned ID

**판정 이유:** 개념 정의와 적용 기준은 확인되나 실제 실행/학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- EntityManager lifecycle
- Spring Data new detection

**초보자가 시작할 질문:**

- Boot4 Hibernate/MySQL 예제 미실행; 새 상태 판정은 실제 @Version/id 설정에 의존.

## MyBatis SQL as a DB-focused read model

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** MyBatis SQL 중심 읽기 모델

**언제 사용하는가:** 복잡 읽기·집계는 직접 SQL과 DTO projection으로 결과를 명시한다.

**대안과 경계:** 화면용 목록/통계에서 join/group SQL 모양이 도메인 object graph보다 중요할 때.

**예시·실행 근거:** JPA는 entity state 변경에 적합, MyBatis는 mapper SQL 제어에 적합; query 성능은 실제 계획을 측정한다. 추가 예: 복잡한 주문 요약을 DTO 행으로 SQL 한 번에 반환한다.

**선수개념:** SQL projection; read model

**관련 표기·별칭:** explicit SQL; result map; DTO projection; report query

**판정 이유:** 개념 정의와 적용 기준은 확인되나 실제 실행/학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- read model
- DTO mapping

**초보자가 시작할 질문:**

- 예제 SQL/DB plan은 미실행.

## JPA/MyBatis same transaction but separate cache and state

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** 같은 DB transaction 안의 별도 persistence cache

**언제 사용하는가:** JPA와 MyBatis가 같은 DataSource transaction에 참여할 수 있으나 MyBatis는 JPA 1차 cache와 상태를 공유하지 않는다.

**대안과 경계:** 두 접근 기술을 함께 쓰는 기존 시스템에서 변경 순서와 읽기 일관성을 관리할 때.

**예시·실행 근거:** JPA 변경이 아직 flush되지 않거나, 이미 관리 중인 엔티티가 있어 MyBatis DB 행과 JPA 상태가 어긋날 수 있다. 추가 예: JPA update 후 MyBatis query 전에 flush; 외부 SQL 뒤 관리 entity refresh/clear를 고려한다.

**선수개념:** transaction manager; persistence context; MyBatis session

**관련 표기·별칭:** shared transaction; flush before mapper; stale persistence context; single write owner

**판정 이유:** 개념 정의와 적용 기준은 확인되나 실제 실행/학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- transaction resource
- EntityManager first-level cache

**초보자가 시작할 질문:**

- 혼용 stale/cache behavior를 실제 실행하지 않았다.

## readOnly transaction semantics in JPA/provider

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** readOnly transaction의 provider 의미

**언제 사용하는가:** Spring readOnly는 최적화 힌트이며 Hibernate/JDBC manager가 flush/connection 처리에 활용할 수 있다.

**대안과 경계:** 읽기 전용 서비스 경계에서 의미를 표시하고 query만 실행할 때.

**예시·실행 근거:** DB가 쓰기를 반드시 거부하는 보안 장치는 아니며 실제 효과는 manager/provider/DB에 따라 다르다. 추가 예: readOnly=true와 flush mode/DB read-only option을 분리해 실제 SQL/write behavior 확인.

**선수개념:** readOnly transaction; Hibernate flush

**관련 표기·별칭:** @Transactional(readOnly=true); flush mode; read-only hint

**판정 이유:** 개념 정의와 적용 기준은 확인되나 실제 실행/학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- Spring transaction
- Hibernate flush mode

**초보자가 시작할 질문:**

- 설정별 효과를 Boot4/Hibernate7/MySQL에서 실행 확인하지 않았다.
