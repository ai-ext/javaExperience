## Nullness contracts: Optional, JSpecify and empty collections

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** Optional은 정상적인 단건 부재를 반환 경계에서 표현하고 JSpecify는 기본 non-null/예외 nullable 계약을 정적 도구에 알린다. 다건 0건은 빈 컬렉션이 자연스럽다.

**언제 사용하는가:** 단건 조회의 empty, 필수 인자의 즉시 검증, nullable entity 필드의 @Nullable, package 기본 @NullMarked를 각각 쓴다.

**대안과 경계:** JSpecify는 runtime 검사 장치가 아니며 analyzer가 읽어야 효과가 난다. Optional 자체가 null이면 상태가 더 늘어난다. DB row 없음과 컬럼 null은 다르다.

**예시·실행 근거:** findUser→Optional, nickname→@Nullable, 입력 경계→requireNonNull; 목록은 빈 List.

**선수개념:** Java reference/null behavior; repository semantics; static analysis; API contract

**관련 표기·별칭:** Optional<T>; @NullMarked; @Nullable; @NullUnmarked

**판정 이유:** 정의와 선택 기준은 설명하지만 대상 실행 환경의 동작 검증 또는 학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- NullAway/IDE 설정을 프로젝트에서 실행하지 않았다.

**초보자가 시작할 질문:**

- 조회 부재는 Optional.empty인가 exception인가?
- @NullMarked면 runtime null check 되나?
- Optional<List<T>>가 필요한가?

## SQL NULL three-valued logic and JSON PATCH tri-state

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** SQL NULL 비교는 UNKNOWN이며 IS NULL로 확인한다. JSON PATCH에서는 key 누락(유지)·explicit null(삭제)·값 설정을 구분할 수 있다.

**언제 사용하는가:** DB nullable/NOT NULL을 업무 규칙에 맞추고 API PATCH가 차이를 요구하면 tri-state를 보존한다.

**대안과 경계:** 행 미존재는 Optional.empty, 행은 존재하지만 속성 null은 entity field nullable이다. COUNT(*)는 행, COUNT(column)은 non-null 값만 센다.

**예시·실행 근거:** PATCH parser는 UNCHANGED/CLEAR/SET로 상태를 분리하고 DB unique/NOT NULL 제약은 저장 최종 경계로 둔다.

**선수개념:** SQL 3-valued logic; JDBC NULL mapping; JSON/Jackson semantics; patch protocol

**관련 표기·별칭:** UNKNOWN; IS NULL; COUNT(*); missing vs explicit null; UNCHANGED/CLEAR/SET

**판정 이유:** 정의와 선택 기준은 설명하지만 대상 실행 환경의 동작 검증 또는 학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- Jackson3 binding/response settings 예제는 실행하지 않았다.

**초보자가 시작할 질문:**

- 행 없음과 컬럼 NULL은 어떻게 구별?
- x = NULL이 왜 결과를 안 주나?
- PATCH {}와 {field:null}은 어떤 의미인가?
- COUNT(column)이 row count와 다르나?
