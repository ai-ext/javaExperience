## Persistence lifecycle: process memory, file, embedded DB, server DB

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** JVM 메모리는 process와 함께 사라지고 file은 남지만 query/index/atomic update/repair를 앱이 설계한다. DB는 공유 질의·제약·트랜잭션·복구 기능을 제공한다.

**언제 사용하는가:** 재시작 이후에도 남고 여러 요청/노드가 공유하며 무결성이 필요한 회원/주문은 관계형 DB가 정본이다. 파일/메모리는 요구가 단순한 산출물·임시값에 적합하다.

**대안과 경계:** Embedded DB와 server DB는 SQL 기능보다 배포/공유 토폴로지가 다르다. Cache는 정본을 대체하지 않고, 이미지 원본 바이트는 object/file storage 후보.

**예시·실행 근거:** member email UNIQUE, order+items transaction; JSONL 파일은 검색/동시 쓰기/복구를 별도 구현해야 한다.

**선수개념:** durability; SQL constraints; multi-request concurrency

**관련 표기·별칭:** JVM heap; JSONL; SQLite; relational DB; object storage

**판정 이유:** 핵심 설명과 선택 기준은 있으나 실행/학습 과제 근거가 부분적이므로 부분 판정.

**보완·검증 필요 사항:**

- Spring JDBC/DB 예제는 미실행. 파일 경합 코드는 source가 실행했다지만 audit에서는 재실행 안함.

## ACID, constraints, transaction limits and backup responsibility

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** ACID는 DB 트랜잭션의 원자성·일관성·격리성·지속성이다. DB 제약은 선언한 불변식을 모든 writer에 적용하지만 외부 시스템이나 backup 복구까지 자동 포함하지 않는다.

**언제 사용하는가:** 여러 DB 변경은 같은 transaction으로 묶고 UNIQUE/NOT NULL/FK를 선언한다. 외부 결제/메시지는 멱등/outbox/보상과 백업 복원 훈련을 따로 둔다.

**대안과 경계:** ConcurrentHashMap의 개별 연산 안전성은 다단계 read-modify-write 원자성과 다르다. DB도 deadlock/lost update/pool exhaustion 문제는 남는다.

**예시·실행 근거:** 동시 이메일 등록은 사전 exists 체크에 의존하지 않고 DB UNIQUE를 최종 수문장으로 둔다. order+items 실패는 같은 트랜잭션 rollback.

**선수개념:** SQL transaction; unique constraint; backup/restore

**관련 표기·별칭:** Atomicity; Consistency; Isolation; Durability; lost update; outbox

**판정 이유:** 핵심 설명과 선택 기준은 있으나 실행/학습 과제 근거가 부분적이므로 부분 판정.

**보완·검증 필요 사항:**

- PostgreSQL/H2 대체 예제는 명시된 방언이며 MySQL 실행 근거가 아니다. 복구/backup은 실행 안함.

**초보자가 시작할 질문:**

- 동시 요청 두 개가 exists=false를 보면?
- transaction이 외부 결제를 취소하나?
- commit이 되면 backup이 필요 없나?
