## REST, GraphQL, gRPC는 서로 다른 API 계약 위치를 선택한다

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** REST는 HTTP 자원/메서드 의미, GraphQL은 schema selection/resolver, gRPC는 proto 원격 메서드와 generated stub을 API 계약으로 삼는다.

**언제 사용하는가:** 브라우저 공개 CRUD는 REST를 기본으로 둔다. 여러 화면의 조합 부담이면 GraphQL BFF, 다언어 typed RPC/streaming이면 내부 gRPC를 검토한다.

**대안과 경계:** GraphQL은 over-fetching을 줄일 수 있지만 resolver N+1·권한·비용을 해결하지 않는다. gRPC는 바이너리여도 자동으로 빠르거나 browser native 호출이 되지 않는다.

**예시·실행 근거:** 외부 REST→BFF GraphQL→내부 gRPC처럼 소비자 경계별로 조합한다.

**선수개념:** HTTP semantics; schema/resolver; protobuf/stub deployment

**관련 표기·별칭:** HTTP/JSON; GraphQL schema/resolver; protobuf RPC

**판정 이유:** 정의와 선택 기준은 설명하지만 대상 실행 환경의 동작 검증 또는 학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 예제 미실행; latency/payload/DB query 비교 측정이 없다.

**초보자가 시작할 질문:**

- GraphQL 한 요청이면 DB도 한 번만 조회하나?
- gRPC는 브라우저 fetch가 가능한가?
- REST와 JSON은 동의어인가?

## API contract compatibility, caching, authorization and failure controls

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** API 계약은 호환성·캐시·인가·실패 정책도 포함한다. OpenAPI/proto/schema는 형식 계약을 돕지만 데이터 행 접근 권한은 자동 보장하지 않는다.

**언제 사용하는가:** 버전 호환·resolver 비용·proto 변경·deadline·재시도 정책을 빌드/게이트웨이에 포함한다.

**대안과 경계:** GET URI는 HTTP 캐시에 유리하고 GraphQL body cache는 별도 설계, gRPC에는 앱 cache가 필요할 수 있다. proto field number는 wire 계약이라 삭제 번호를 재사용하지 않는다.

**예시·실행 근거:** GraphQL 객체 단위 권한과 batching, proto reserved field, RPC deadline/취소 전달을 검증한다.

**선수개념:** HTTP cache semantics; access control; wire compatibility; retry semantics

**관련 표기·별칭:** OpenAPI; GraphQL depth/cost/DataLoader; proto reserved/deadline; idempotency

**판정 이유:** 정의와 선택 기준은 설명하지만 대상 실행 환경의 동작 검증 또는 학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 배포 호환/게이트웨이/API 테스트를 실행하지 않았다.

**초보자가 시작할 질문:**

- proto field number를 삭제 후 재사용해도 되나?
- GraphQL schema는 row 접근권한을 보장하나?
- gRPC deadline/retry는 왜 업무 의미와 관련있나?
