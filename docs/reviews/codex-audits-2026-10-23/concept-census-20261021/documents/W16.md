## ID generator placement and JPA batching

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** IDENTITY는 DB INSERT 뒤에 값이 생기지만 SEQUENCE나 앱 생성 ID는 INSERT 전에 값을 알 수 있어 Hibernate JDBC batching에 유리할 수 있다. JPA GenerationType.UUID는 UUID 버전을 지정하지 않는다.

**언제 사용하는가:** 단일 MySQL CRUD는 BIGINT AUTO_INCREMENT로 시작한다. DB 쓰기 전 ID나 다중 노드 독립 생성이 필요할 때 SEQUENCE/UUID/Snowflake를 검토한다.

**대안과 경계:** 배치 여부는 트랜잭션·드라이버·SQL·설정에 달렸다. ID 생성 순서가 commit 순서인 것은 아니다.

**예시·실행 근거:** IDENTITY/SEQUENCE/UUID entity를 비교하고 SQL batching과 실제 DB 컬럼 형식을 확인한다.

**선수개념:** ORM entity lifecycle; DB generator semantics; JDBC batch; schema types

**관련 표기·별칭:** IDENTITY; SEQUENCE; GenerationType.UUID; JDBC batching

**판정 이유:** 정의와 선택 기준은 설명하지만 대상 실행 환경의 동작 검증 또는 학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- Spring/JPA 코드 미실행. 프로젝트 MySQL에서 sequence 방식은 그대로 적용할 수 없다.
- Hibernate의 UUID binary mapping과 인덱스 효과를 확인하지 않았다.

## Distributed identifier shape, storage cost, and security separation

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** UUIDv4는 난수형, UUIDv7/ULID는 시간 필드를 포함하며 Snowflake는 시간·노드·sequence를 조합한다. InnoDB PK는 clustered index이고 보조 인덱스에도 PK가 포함된다.

**언제 사용하는가:** DB 전에 ID가 필요하거나 여러 쓰기 노드가 독립 생성해야 할 때, 또는 내부 PK와 외부 공개 ID를 분리할 때 목적에 맞는 전략을 택한다.

**대안과 경계:** UUIDv7은 시간 순서에 가까울 뿐 전역 단조/commit 순서를 보장하지 않는다. UUID는 인가 수단이 아니다. Snowflake는 노드 ID·시계 운영이 필요하다.

**예시·실행 근거:** 내부 BIGINT PK와 public UUID UNIQUE를 함께 두고 모든 API에서 소유권 권한을 확인한다.

**선수개념:** RFC UUID layout; entropy; InnoDB clustered/secondary indexes; clock synchronization

**관련 표기·별칭:** UUIDv4; UUIDv7; ULID; Snowflake; public_id

**판정 이유:** 정의와 선택 기준은 설명하지만 대상 실행 환경의 동작 검증 또는 학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 상대 성능은 이 문서에서 측정하지 않았다.
- Snowflake 예제는 분산 worker 배정 안전성을 증명하지 않는다.

**초보자가 시작할 질문:**

- 외부 ID를 UUID로 바꾸면 접근 권한도 해결되나?
- PK 크기가 보조 인덱스에 미치는 영향은?
