## Actuator access와 exposure

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Actuator endpoint access는 허용 작업이고 exposure는 HTTP/JMX로 공개할 통로다.

**언제 사용하는가:** 운영 상태·Prometheus scrape만 필요한 경우 endpoint를 최소 공개하고 인증·네트워크 경계와 맞춘다.

**대안과 경계:** access와 exposure가 모두 허용되어야 사용할 수 있다. health만 기본 노출이며 민감 정보 endpoint 공개는 별도 위험이다.

**예시·실행 근거:** YAML 예제에서 endpoint access·exposure·역할 인증을 분리하지만 미실행이다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- Prometheus registry를 추가했는데 scrape 주소가 404라면 공개 경로와 권한 중 무엇을 확인하나요?
- /actuator/env가 외부에서 조회될 때 어떤 endpoint 설정과 경계를 좁혀야 하나요?

## liveness·readiness와 Kubernetes

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** liveness는 재시작 필요 여부, readiness는 트래픽 수용 가능 여부를 드러낸다.

**언제 사용하는가:** 외부 의존성이 잠시 실패해도 프로세스가 살아 있으면 liveness는 통과시키고 서비스 정책상 필요한 readiness만 실패시킨다.

**대안과 경계:** DB 장애를 liveness에 넣으면 재시작 폭주가 날 수 있다. 모든 readiness 지표 포함은 전체 Pod 제외를 만들 수 있다.

**예시·실행 근거:** health group/probe path와 상황별 선택을 설명하며 실제 cluster 동작은 미검증이다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- DB가 잠깐 느려져 전체 Pod가 재시작되기 시작했다면 health 검사가 어떤 역할을 잘못 맡았나요?
- 새 Pod가 트래픽을 받기엔 준비되지 않았는데 process 자체는 살아 있다면 어떤 probe를 실패시켜야 하나요?

## Meter와 cardinality

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Meter는 이름과 tag 조합으로 구별되며 Counter·Gauge·Timer 등 종류마다 값 의미가 다르다.

**언제 사용하는가:** 누적 사건은 Counter, 현재량은 Gauge, 지연 분포는 Timer로 계측하고 태그 값 종류를 제한한다.

**대안과 경계:** request ID·user ID·원본 URL처럼 고유값 태그는 meter·시계열 수를 폭증시킨다. Gauge는 참조 대상 생명주기 관리가 필요하다.

**예시·실행 근거:** Counter와 bean 필드 AtomicInteger Gauge 예제가 있으나 Spring context 실행은 미실행이다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- 메트릭에 userId를 tag로 넣은 뒤 저장소 비용이 급증하면 어떤 값 조합이 시계열을 늘렸나요?
- Gauge로 queue 길이를 봤는데 meter가 사라졌다면 참조 대상의 수명에서 무엇을 살펴야 하나요?

## Observation·Span·로그 문맥

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Observation은 관측 구간이고 handler가 이를 Meter나 Span으로 변환한다. MDC는 로그 이벤트에 붙는 문맥 map이다.

**언제 사용하는가:** 업무 경계를 한 번 계측해 지표·trace를 연결하고 로그에는 trace ID를 함께 둔다.

**대안과 경계:** 고카디널리티 값을 metric tag로 쓰지 않으며 async/Reactor 경계에서 ThreadLocal/MDC가 자동 전파된다고 가정하지 않는다.

**예시·실행 근거:** Observation과 MDC 코드 예제는 실행 handler 및 Boot context가 필요해 미실행이다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- 한 요청을 로그·metric·trace에서 연결하려는데 각각 문맥이 끊긴다면 어떤 전파 경계를 확인하나요?
- userId가 매번 다른 metric tag와 trace attribute 중 어느 쪽에서 cardinality 폭발을 막아야 하나요?

## sampling·client propagation

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** trace sampling은 저장할 trace 비율을 결정하고 Boot builder로 만든 HTTP client는 문맥 전파 설정을 받을 수 있다.

**언제 사용하는가:** 원격 호출 흐름을 확인하고 async trace 누락을 조사할 때 client builder와 executor propagation 설정을 확인한다.

**대안과 경계:** 샘플링되지 않은 요청도 메트릭·로그에는 남을 수 있으며 직접 만든 client는 전파가 빠질 수 있다.

**예시·실행 근거:** sampling 0.1 및 RestClient/WebClient builder 차이를 설명하나 collector 실행은 없다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- 비동기 작업 로그에 traceId가 없는데 동기 요청 로그에는 있다면 어떤 executor 설정을 비교하나요?
- 일부 요청의 trace가 저장되지 않았는데 metric에는 남아 있다면 sampling 설정이 어떻게 작동했나요?
