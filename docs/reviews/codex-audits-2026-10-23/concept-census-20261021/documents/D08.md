## PR review와 merge gate

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** PR merge에는 사람의 승인과 CI status check가 각각 필요할 수 있다. commit SHA가 바뀌면 이전 CI 결과만으로 새 변경을 승인할 수 없다.

**언제 사용하는가:** 변경 이력을 검토하고 branch 보호 조건을 확인할 때 사용한다.

**대안과 경계:** 사람의 review와 CI 자동 검사는 서로 다른 gate다. 마지막 green check 이후 파일이 바뀌었는지 확인한다.

**예시·실행 근거:** 새 commit 뒤 기존 PR check가 유효한지 SHA 기준으로 확인한다.

**선수개념:** Git branch; commit SHA

**관련 표기·별칭:** PR, review and status gates

**보완·검증 필요 사항:**

- 진행 중 화면의 Git fixture는 로컬 실험이며 원격 PR 승인/CI를 실행하지 않았다.

**초보자가 시작할 질문:**

- CI가 통과한 뒤 파일을 추가로 고쳤다면 기존 green check를 믿어도 되나?

## CI/CD 단계와 artifact

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** CI는 checkout·build·test·analysis·publish 단계를 자동화할 수 있고 delivery와 deployment는 배포 준비/실제 운영 반영을 구분한다.

**언제 사용하는가:** 코드 merge부터 artifact 생성 및 배포까지 자동화 흐름을 이해할 때 사용한다.

**대안과 경계:** build cache는 성능을 위해 재사용하는 자료이고 artifact는 전달할 산출물이다.

**예시·실행 근거:** pipeline 단계에서 artifact가 만들어지고 저장소/registry로 전달되는 경로를 추적한다.

**선수개념:** Git; build; test

**관련 표기·별칭:** CI/CD stages and artifacts

**보완·검증 필요 사항:**

- 원격 CI pipeline 실행 근거는 없다.

**초보자가 시작할 질문:**

- CI가 green인데 실제 prod에는 왜 새 버전이 올라가지 않을 수 있나?

## GitOps 상태 동기화

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** CI는 선언형 저장소를 갱신하고 Argo CD 같은 controller는 desired state와 실제 cluster state를 비교한다.

**언제 사용하는가:** 배포 상태를 선언형 저장소에서 관리할 때 사용한다.

**대안과 경계:** auto sync만으로 삭제된 리소스 prune 또는 drift self-heal이 항상 켜지는 것은 아니다.

**예시·실행 근거:** 저장소 변경 후 desired/actual 상태 비교와 sync 흐름을 따른다.

**선수개념:** Kubernetes resource; Git commit

**관련 표기·별칭:** GitOps reconciliation; GitOps reconciliation

**보완·검증 필요 사항:**

- Argo 또는 실제 cluster는 실행하지 않았다.

**초보자가 시작할 질문:**

- Git에는 새 image가 있는데 cluster는 왜 이전 버전을 유지할 수 있나?
