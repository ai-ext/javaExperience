## OAuth2·OIDC·JWT 역할 및 검증

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** OAuth2는 리소스 접근 위임, OIDC는 표준 인증 결과/ID token을 추가한다. JWT는 claim 컨테이너로 signed일 수 있지만 자동 암호화되지 않는다. Resource Server는 signature·issuer·audience·expiry·scope 검증.

**언제 사용하는가:** browser session, public-client Authorization Code+PKCE, service-to-service Client Credentials를 소비자 경계에 맞춰 선택하고 API는 access token 권한을 확인한다.

**대안과 경계:** ID token은 client 대상으로 API access token과 다름. Signature만 유효해도 올바른 audience를 뜻하지 않는다. Stateless JWT는 상태 조회 없이 즉시 폐기하기 어렵다.

**예시·실행 근거:** iss, API aud, exp/nbf, algorithm allowlist, scopes 검증; 외부 신원키는 (iss,sub), email 단독 linking 피함.

**선수개념:** authorization vs authentication; cryptographic signatures; redirect flow

**관련 표기·별칭:** OAuth2; OIDC; JWT; JWKS; issuer; audience

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- IdP/JWKS/token test를 실행하지 않았다.

**초보자가 시작할 질문:**

- 서명이 맞으면 모든 API에서 받아도 되나?
- JWT logout이 즉시 폐기하나?

## PKCE·refresh rotation·state/nonce·키 rollover

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** PKCE는 일회성 authorization code를 verifier/challenge로 결속한다. state는 callback 상관관계, OIDC nonce는 ID token replay 방지. Refresh token 회전/재사용 탐지는 탈취 위험을 낮추며 JWKS key는 토큰 수명 동안 겹쳐 둔다.

**언제 사용하는가:** 공개 client는 S256 PKCE, exact redirect URI, refresh rotation; signing key 변경은 최대 issued token lifetime과 overlap 고려.

**대안과 경계:** Browser에 client secret 보관 불가. Access token은 RS, refresh token은 AS token endpoint 전용. Client Credentials는 user login 없는 서비스 주체.

**예시·실행 근거:** 인가 요청은 S256 challenge와 state를 보내고 callback에서는 state를 비교한다. token 교환에는 원래 verifier를 보내며 refresh token 재사용은 family 폐기 정책으로 다룬다.

**선수개념:** HTTP redirect; secret storage; key rotation

**관련 표기·별칭:** PKCE; state; nonce; refresh token; JWKS rotation

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 실제 provider redirect/token renewal은 실행하지 않았다.

**초보자가 시작할 질문:**

- PKCE가 client secret인가?
- state와 nonce를 왜 따로 두나?
- 예전 JWKS key는 언제 제거하나?
