## properties migrator와 OpenRewrite

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** migrator는 옛 설정을 기동 중 진단·임시 변환하고 OpenRewrite는 소스·빌드·프로퍼티를 recipe로 변환한다.

**언제 사용하는가:** 변경이 반복되는 앱은 자동 변환을 dry-run한 후 diff·테스트로 점검하고 실제 설정 파일을 수정한다.

**대안과 경계:** migrator를 영구 의존성으로 두면 옛 설정 문제를 숨긴다. recipe도 업무 의미나 reflection을 보장하지 않는다.

**예시·실행 근거:** migration dependency 및 property 치환 예제가 있으며 순수 Java 모델은 실행 기록이 있다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

## JSpecify null-safety

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Framework 7의 JSpecify annotation은 nullability 계약을 도구에 알리며 IDE/NullAway 등이 정적 분석에 사용할 수 있다.

**언제 사용하는가:** public library 경계에서 기본 non-null과 실제 nullable 입력을 명시해 호출자가 계약을 검사하게 한다.

**대안과 경계:** annotation만으로 Java 런타임 NPE가 사라지지 않으며 컴파일러가 null을 강제하지 않는다.

**예시·실행 근거:** null 계약의 타입 범위와 checker 역할을 설명한다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- IDE에서 annotation이 non-null이라고 보여도 실제 Java 실행에서 NPE가 난다면 JSpecify가 보장한 범위는 어디까지인가요?
- nullable 반환을 호출자가 놓치지 않게 하려면 어떤 정적 checker가 계약을 읽어야 하나요?

## HttpHeaders·HTTP Service Client

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Framework 7 HttpHeaders는 일반 MultiValueMap 상속 계약을 제거했고 @HttpExchange interface는 client proxy로 요청을 기술한다.

**언제 사용하는가:** 헤더 조작은 전용 API로 이동하고 반복 client 구성은 Boot HTTP Service Client 설정을 검토한다.

**대안과 경계:** header는 대소문자 비구분·다중 값이 가능하다. 선언형 client가 timeout/retry/security/resilience를 자동 해결하지 않는다.

**예시·실행 근거:** interface 예제와 헤더 설계 차이를 설명하지만 애플리케이션 미실행이다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- `HttpHeaders`를 MultiValueMap으로 cast하던 코드가 Framework 7에서 깨지면 어떤 헤더 전용 API로 옮겨야 하나요?
- 선언형 HTTP interface를 만들었는데 호출이 무한 대기한다면 proxy 외에 어떤 timeout 설정이 필요한가요?

## API version resolver·parser·deprecation

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** API versioning은 요청에서 버전 위치를 읽고 문자열 해석과 폐기 정책을 각기 다른 책임으로 둔다.

**언제 사용하는가:** header/query/media type 등 전달 위치와 지원·폐기 정책을 먼저 정하고 MVC/WebFlux를 각각 검증한다.

**대안과 경계:** 자동 설정은 business representation이나 모든 controller 분기를 자동 생성하지 않는다.

**예시·실행 근거:** MVC 설정 예제와 resolver/parser 역할을 제공하지만 설정 미실행이다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**
