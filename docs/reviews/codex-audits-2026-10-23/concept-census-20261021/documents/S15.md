## @Async와 실행기 큐

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** @Async는 프록시가 호출을 실행기에 제출하는 경계이며 실행기가 동기/스레드풀/거부 등 과부하 동작을 정한다.

**언제 사용하는가:** 짧은 작업을 요청 흐름에서 분리할 때 쓰되 유실되어도 되는지와 완료 결과 관찰 방식을 먼저 정한다.

**대안과 경계:** 애노테이션은 내구성 큐를 만들지 않는다. self-invocation은 프록시를 우회하고 ThreadLocal·트랜잭션도 자동 전달되지 않는다.

**예시·실행 근거:** 유한 큐·거부 정책을 둔 ThreadPoolTaskExecutor 예시가 있으나 Spring 코드는 미실행이다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- 요청 API는 성공했는데 서버 재시작 뒤 작업이 사라졌다면 실행기 설정에서 무엇이 보존되지 않았나요?
- 스레드 풀이 꽉 찼을 때 새 작업을 쌓을지 거절할지 누가 결정하나요?

## @Scheduled와 분산 중복

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** @Scheduled는 각 애플리케이션 프로세스의 시계에 등록되는 로컬 작업이다.

**언제 사용하는가:** 복제본마다 실행돼도 되는 작업에 사용하며 여러 노드 중 한 번만 실행하려면 공유 잠금·분산 스케줄러를 검토한다.

**대안과 경계:** ShedLock은 잠금 실패 호출을 대기열에 넣지 않고 건너뛴다. `lockAtMostFor`가 짧으면 기존 실행과 겹칠 수 있다.

**예시·실행 근거:** cron zone·fixed rate/delay와 ShedLock 경계 및 다중 노드 위험을 설명한다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:**

## fixed rate와 fixed delay

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** fixed rate는 예정된 시작 간격이고 fixed delay는 앞 작업 완료 뒤 쉬는 간격이다.

**언제 사용하는가:** 일정한 시작 주기 목표는 rate, 완료 후 휴지 시간을 보장해야 하면 delay를 선택한다.

**대안과 경계:** 주기가 작업보다 짧아도 JDK 실행기는 같은 주기 작업을 겹쳐 실행하지 않으며 밀릴 수 있다.

**예시·실행 근거:** 80ms 작업에서 50ms 주기 두 방식의 JDK 21 실제 출력을 비교한다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- 정기 작업 시작 간격이 실행 시간보다 짧아지면 같은 작업이 동시에 겹쳐 실행되나요?

## JobInstance·JobExecution·JobRepository

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** JobInstance는 Job과 식별 JobParameters로 정한 논리 작업이고 JobExecution은 한 번의 실행 시도다. Repository/ExecutionContext가 실행 메타데이터와 체크포인트를 보관한다.

**언제 사용하는가:** 대량 작업 실패 뒤 동일 논리 입력을 이어 실행해야 할 때 사용한다. 재시도 때 식별 매개변수를 유지한다.

**대안과 경계:** Repository만으로 재시작 안전성이 완성되지 않는다. Reader 상태와 외부 부수효과 멱등성도 필요하다.

**예시·실행 근거:** chunk(2) 예제는 항목 묶음 commit을 보여 주지만 ListItemReader는 운영 재시작 checkpoint가 아니다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- 실패한 영업일 정산을 다시 실행하는데 매번 UUID를 새로 주면 왜 이전 진행 위치를 못 찾나요?
- Job 상태는 저장됐는데 재시작 후 파일 입력 위치가 처음으로 돌아간다면 Reader에 무엇이 빠졌나요?

## chunk·외부 효과·멱등성

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** chunk는 정한 항목 수를 읽고 처리·기록한 뒤 트랜잭션을 commit하는 경계다.

**언제 사용하는가:** DB 중심 대량 입력의 처리량과 재시작을 관리하되 크기는 rollback·commit 비용을 측정해 조정한다.

**대안과 경계:** DB rollback은 이미 성공한 HTTP·파일·메일을 되돌리지 않는다. 큰 chunk는 rollback 범위를 넓히고 작은 chunk는 metadata 비용을 늘린다.

**예시·실행 근거:** 예제와 Q&A에서 외부 효과와 checkpoint를 구분하며 Spring 코드는 미실행이다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- 청크 DB 변경은 rollback됐지만 이메일은 이미 발송됐다면 재시작 때 이메일 중복을 어떻게 막나요?
- chunk 크기를 크게 했더니 실패 복구가 오래 걸릴 때 어떤 비용이 같이 커졌나요?
