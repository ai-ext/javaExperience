## IoC·DI·Container·Bean의 관계

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** IoC는 객체 생성·연결 제어를 바깥 조립자에 맡기는 원칙이고 DI는 생성자 인자 등으로 협력 객체를 전달하는 방법입니다. Spring ApplicationContext가 조립하고 관리 객체가 Bean입니다.

**언제 사용하는가:** 협력 객체가 늘거나 구현 교체/테스트 대역이 필요할 때 container 조립을 사용합니다.

**대안과 경계:** IoC가 DI보다 넓은 개념이고 Service Locator는 조회를 객체 내부에 숨길 수 있습니다.

**예시·실행 근거:** OrderService가 Repository와 PaymentClient를 직접 new하는 코드와 생성자 주입 버전을 비교합니다.

**선수개념:** Java constructor; interface

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- ApplicationRunner Spring 예제는 미실행입니다.

**초보자가 시작할 질문:**

- OrderService가 구현을 직접 new하면 테스트에서 무엇을 바꾸기 어려운가요?
- IoC와 DI를 같은 뜻이라고 할 수 없는 이유는 무엇인가요?

## 생성자 주입·인터페이스·가짜 구현

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 필수 협력 객체를 역할 타입으로 선언하고 생성자에서 받아 구현 선택은 조립 지점에 둡니다.

**언제 사용하는가:** 필수값은 생성자, 테스트는 fake를 전달해 Spring 없이 객체 동작을 확인합니다.

**대안과 경계:** 인터페이스는 교체 경계가 있을 때 유용하지만 모든 클래스에 기계적으로 만들 필요는 없습니다. setter는 선택 의존성에 적합합니다.

**예시·실행 근거:** ConstructorOrderService는 FakeRepository/FakePaymentClient로 테스트되고 main에서 수동 조립됩니다.

**선수개념:** 생성자; interface; test double

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 외부 DB/API 구현은 없는 순수 Java 예제입니다.

**초보자가 시작할 질문:**

- 테스트에서 운영 저장소 대신 FakeOrderRepository를 전달하려면 서비스에 어떤 생성 경로가 필요할까요?
- 필수 결제 클라이언트를 setter로만 받으면 객체 생성 직후 어떤 불완전 상태가 생기나요?

## Spring 스캔·자동 조립

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** @Service/@Repository/@Component가 Bean 후보를 표시하고, Boot 메인 패키지 이하를 스캔해 타입에 맞는 생성자 인자를 연결합니다.

**언제 사용하는가:** 객체 수가 늘어 수동 조립이 커질 때 container wiring을 사용합니다.

**대안과 경계:** 애노테이션이 붙어도 직접 new한 객체가 컨테이너 Bean이 되는 것은 아닙니다.

**예시·실행 근거:** ApplicationRunner가 OrderService를 주입받아 예시 주문을 넣는 흐름. 출력은 예상값이며 Spring 미실행.

**선수개념:** 컴포넌트 scan; Bean

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 예제 밖의 프레임워크 설정이나 운영 환경 차이는 별도 실행으로 확인해야 합니다.

**초보자가 시작할 질문:**

- @Service 클래스가 있는데 `new OrderService()`도 같은 Bean이 되는 건가요?
- 메인 클래스의 package를 최상위로 두는 이유는 무엇인가요?

## 싱글턴 scope와 proxy 적용 경계

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 기본 singleton은 Bean 정의 하나당 컨테이너 안의 인스턴스 하나입니다. proxy 기능은 관리 객체를 거치는 호출에 적용됩니다.

**언제 사용하는가:** 무상태 서비스 Bean을 공유하고 요청별 데이터는 메서드 지역값으로 둡니다.

**대안과 경계:** 프로세스 전체 하나가 아니며 컨테이너마다 별도일 수 있습니다. 직접 new 객체에는 transaction proxy가 적용되지 않습니다.

**예시·실행 근거:** 두 수동 생성 서비스가 같은 Repository 인스턴스를 참조하는 예를 출력합니다.

**선수개념:** Spring scope; AOP proxy

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 생명주기와 proxy 호출 내부는 S01/S02 링크로 넘깁니다.

**초보자가 시작할 질문:**

- transaction annotation 메서드를 직접 만든 객체에서 호출할 때 왜 proxy를 통과하지 않나요?

## 수동 조립과 Spring 테스트의 역할

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 생성자 주입은 어떤 collaborator를 넣는지 호출부에 드러내며, pure unit test와 Spring context wiring test를 분리합니다.

**언제 사용하는가:** 업무 로직은 fake로 빠르게, 컨테이너 등록/설정은 별도 통합 테스트로 검증합니다.

**대안과 경계:** DI 방식만으로 DB가 자동으로 가짜가 되지 않습니다. 테스트가 fake 선택을 해야 합니다.

**예시·실행 근거:** IocStages 실제 출력은 fake 호출을 보이고 Spring 프로젝트 부분은 미실행입니다.

**선수개념:** 생성자 주입; JUnit

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- JUnit 실행 예제가 직접 포함되지는 않습니다.

**초보자가 시작할 질문:**

- 생성자 주입을 써도 DB 통합 테스트가 되는 이유는 무엇인가요?
- 실제 컨테이너 Bean 등록 오류는 어떤 테스트로 검증해야 하나요?
