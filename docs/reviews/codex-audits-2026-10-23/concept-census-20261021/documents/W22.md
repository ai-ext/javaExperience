## Environment fingerprinting and differential diagnosis

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** 같은 코드는 설정·JVM·OS·경로·권한·네트워크·DB 데이터·동시성·자원 조건이 다르면 다른 결과를 낼 수 있다. 실패 요청 조건을 고정하고 차이를 하나씩 제거한다.

**언제 사용하는가:** 빌드/요청 ID, profile, 안전한 runtime fingerprint와 프로세스 위치를 비교하고 DNS→TCP→TLS→인증을 단계별 확인한다. 비밀값은 출력하지 않는다.

**대안과 경계:** Docker는 userspace/JDK 편차를 줄이지만 DNS·secret·실데이터·kernel·resource limit을 복제하지 않는다. DNS 성공은 TCP/인증 성공을 뜻하지 않는다.

**예시·실행 근거:** JVM·OS·charset·zone·locale의 안전한 지문과 이미지 digest 비교; 설정은 단일 키의 출처 확인.

**선수개념:** process vs IDE launch; networking/DNS; Unix path permissions; containers; observability

**관련 표기·별칭:** works on my machine; runtime fingerprint; one-factor-at-a-time

**판정 이유:** 정의와 선택 기준은 설명하지만 대상 실행 환경의 동작 검증 또는 학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 실제 운영 장애나 서버에 접속하지 않았다.

**초보자가 시작할 질문:**

- 로컬 성공인데 서버 timeout이면 무엇부터 비교?
- 시스템 기본값/경로/실행 사용자 차이를 어떻게 좁히나?
- 환경 변수 전체를 로그에 남겨도 되나?

## Configuration precedence, container networking and representative verification

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** Boot는 여러 PropertySource를 우선순위로 병합한다. 컨테이너 내 localhost는 자기 자신이며 Compose 서비스명은 컨테이너 네트워크 주소다.

**언제 사용하는가:** Property origin, 실행 사용자, 실제 DB 버전, migration, 리소스 한도를 같은 배포 위치에서 확인하고 concurrency도 재현한다.

**대안과 경계:** H2 단일 요청 성공은 MySQL 제약·락·동시성 증거가 아니다. 같은 image도 네트워크/비밀/데이터/CPU 제한이 다를 수 있다.

**예시·실행 근거:** 앱 컨테이너 내 jdbc 주소는 db:port; 호스트 앱은 published localhost port; CI는 대상 DB 버전으로 테스트한다.

**선수개념:** Boot config precedence; container networking; cgroups; database isolation and concurrency tests

**관련 표기·별칭:** PropertySource; profile; localhost; Docker Compose; DB parity; resource limits

**판정 이유:** 정의와 선택 기준은 설명하지만 대상 실행 환경의 동작 검증 또는 학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 예시 compose는 PostgreSQL이라 프로젝트 MySQL의 직접 검증이 아니다.

**초보자가 시작할 질문:**

- app container localhost는 어떤 호스트?
- Spring yaml 값이 env/CLI에 덮였는지?
- H2 통과는 운영 DB 증거인가?
- Docker면 운영과 똑같나?
