## Spring singleton scope and request-thread concurrency

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** Spring singleton은 컨테이너와 BeanDefinition당 객체 하나다. 여러 Servlet worker가 같은 singleton 메서드를 동시에 호출할 수 있어 요청별 mutable field는 값 섞임을 일으킨다.

**언제 사용하는가:** 서비스는 stateless singleton과 immutable 의존성, 요청별 인자/지역변수로 둔다. 상태가 필요하면 명시된 요청 범위나 외부 저장소를 사용한다.

**대안과 경계:** final은 참조 재할당만 막고 내부 thread safety를 보장하지 않는다. request scope는 비동기 thread/동일 요청 병렬성을 자동 보장하지 않는다.

**예시·실행 근거:** 공유 currentName field 대신 greet(name) 인자와 지역 변수로 계산한다.

**선수개념:** JVM heap/stack; thread safety; Spring bean scopes

**관련 표기·별칭:** singleton bean; request scope; stateless service; Tomcat worker

**판정 이유:** 핵심 설명과 선택 기준은 있으나 실행/학습 과제 근거가 부분적이므로 부분 판정.

**보완·검증 필요 사항:**

- 문서의 Boot/Tomcat 12-request 실측은 원문 기록이며 이 감사에서 재현 안함.

## ThreadLocal context, worker pools and resource pool sizing

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** ThreadLocal은 thread별 값이며 요청 스코프 저장소 자체가 아니다. Tomcat worker는 재사용되고 async 작업은 별도 executor일 수 있다. Tomcat worker, Hikari connection, scheduler는 서로 다른 pool이다.

**언제 사용하는가:** transaction/security/MDC 같은 인프라 문맥은 관리 경계를 쓰고 직접 넣은 ThreadLocal은 finally에서 제거한다. pool 대기 스택/지표로 실제 병목을 찾는다.

**대안과 경계:** worker max 증가는 DB 동시 연결 수를 늘리지 않고 기다리는 요청을 늘릴 수 있다. @Async는 transaction/auth 문맥을 자동 전파하지 않는다.

**예시·실행 근거:** thread dump와 Hikari active/pending을 같은 시각 비교하고 async 경계에서 새 transaction/명시 문맥 전달을 정한다.

**선수개념:** ThreadLocal lifecycle; executor pools; JDBC connection pool

**관련 표기·별칭:** ThreadLocal; TransactionSynchronizationManager; SecurityContextHolder; HikariCP; @Async; Tomcat max threads

**판정 이유:** 핵심 설명과 선택 기준은 있으나 실행/학습 과제 근거가 부분적이므로 부분 판정.

**보완·검증 필요 사항:**

- Tomcat max 200은 version-specific documented default이며 이 audit에서 현장 설정 확인은 하지 않았다.

- Tomcat worker와 DB connection 수는 같은가?
- @Async가 기존 transaction을 이어받나?
