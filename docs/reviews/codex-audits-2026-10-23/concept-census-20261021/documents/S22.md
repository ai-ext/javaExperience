## 레이어드 구조의 책임

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Controller-Service-Repository 구조는 요청·유스케이스·저장소 경계를 나누지만 규칙이 서비스와 ORM 모델에 퍼질 수 있다.

**언제 사용하는가:** 단순 CRUD나 작은 팀은 레이어드로 시작하고 함께 참이어야 하는 복잡한 규칙은 소유 객체를 명확히 한다.

**대안과 경계:** 레이어 수를 늘리는 것만으로 의존 방향·규칙 소유 문제는 해결되지 않는다.

**예시·실행 근거:** 레이어 비대화 흐름과 Controller→Service→Repository 대비를 설명한다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:**

## 포트·어댑터와 의존 방향

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 포트는 안쪽 유스케이스가 필요로 하는 외부 계약이며 어댑터는 HTTP·JPA·Kafka 같은 기술 구현이다.

**언제 사용하는가:** 기술 교체, 독립 테스트, 외부 변화 분리가 실익 있는 경계에만 포트를 둔다.

**대안과 경계:** 모든 클래스에 인터페이스를 만들면 추상화 비용만 늘 수 있다. 안쪽 모듈이 기술 세부사항을 import하지 않는 것이 핵심이다.

**예시·실행 근거:** PlaceOrder 입력 포트와 OrderRepository 출력 포트 구조 예시가 있으나 앱 전체는 미실행이다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:**

## 애그리거트 루트와 불변식

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 애그리거트는 한 트랜잭션에서 함께 지킬 불변식의 범위이고 루트는 외부 변경의 단일 진입점이다.

**언제 사용하는가:** 확정 후 수정 금지·수량 한도처럼 함께 참이어야 하는 규칙을 루트 명령 메서드로 둔다.

**대안과 경계:** 테이블 관계나 객체 그래프 크기로 경계를 정하지 않으며 모든 자식을 항상 하나로 묶지 않는다.

**예시·실행 근거:** 순수 Java Order/Money 예제가 한도·상태 전이·이벤트를 실행 결과와 함께 보여 준다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

## Entity·Value Object·도메인/애플리케이션 서비스

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Entity는 식별성·생명주기, Value Object는 값과 제약에 따른 동일성을 가진다. 애플리케이션 서비스는 흐름·트랜잭션을 조정한다.

**언제 사용하는가:** Money·Address처럼 값 규칙이 있거나 Order 상태 전이가 복잡할 때 객체에 행위를 둔다. 여러 모듈/포트를 엮으면 애플리케이션 서비스를 둔다.

**대안과 경계:** 도메인 서비스는 한 객체에 자연히 속하지 않는 업무 규칙이다. 모든 CRUD에 풍부한 모델을 강제하지 않는다.

**예시·실행 근거:** Money·ProductId record와 Order.confirm 예제 및 빈약/풍부한 모델 비교를 제시한다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- Money 1000원과 Money 1000원이 같은 값을 뜻하지만 id가 없다면 동일성을 어떤 기준으로 판단하나요?

## 바운디드 컨텍스트·모듈러 모놀리스

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 바운디드 컨텍스트는 언어·모델이 유효한 범위이며 모듈러 모놀리스는 한 배포 안에서 업무 모듈 API와 의존 규칙을 검증한다.

**언제 사용하는가:** 같은 단어의 의미가 팀/업무마다 다르거나 내부 접근·순환이 늘 때 컨텍스트/모듈 경계를 세운다.

**대안과 경계:** 패키지 이름만 나눈 것으로 경계가 되지 않는다. 공개 API, 내부 은닉, 자동 verify가 필요하다.

**예시·실행 근거:** Spring Modulith verify 예시가 순환·내부 접근을 검사하나 Boot 4.1 호환 조합은 미확인으로 표시한다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**
