## In-memory, cache, source of truth are different roles

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** 인메모리는 RAM에서 처리한다는 뜻이고, 캐시는 원본을 대체하지 않는 파생 사본이다. H2는 SQL 데이터베이스, Caffeine은 JVM 로컬 캐시, Redis는 외부 공유 저장소다.

**언제 사용하는가:** 반복 조회가 많고 원본이 비싸며 정해진 stale을 허용할 때 캐시를 검토한다. 단일 JVM은 Caffeine, 여러 노드 공유는 Redis 후보.

**대안과 경계:** Map은 기본 만료·용량 제한·노드 공유가 없다. Redis는 network/운영 부담과 설정에 따른 영속성, DB buffer pool은 DB 내부 최적화다.

**예시·실행 근거:** DB를 기준 데이터로 두고 제한된 CacheManager를 조회 경로에 적용한다. H2는 캐시 provider가 아니다.

**선수개념:** JVM/프로세스 수명; DB vs cache; network topology

**관련 표기·별칭:** cache; in-memory; cache hit/miss; Caffeine; Redis; H2

**판정 이유:** 핵심 설명과 선택 기준은 있으나 실행/학습 과제 근거가 부분적이므로 부분 판정.

**보완·검증 필요 사항:**

- latency 숫자는 2012년 전후의 교육용 근사치이며 현재 보장값이 아니다.
- Map timing example을 이 감사에서 재실행하지 않았다.

## Cache economics, lifecycle, eviction and concurrent loading

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** 캐시 hit는 원본 조회를 건너뛰고 miss는 원본을 읽어 사본을 채운다. 결과를 바꾸는 키 차원과 갱신·퇴거 정책이 일관성을 정한다.

**언제 사용하는가:** hit/miss, origin 부하/지연, 캐시 지연/퇴거/메모리와 p95/p99를 계측한 뒤 데이터별 size/TTL을 정한다.

**대안과 경계:** ConcurrentHashMap은 일부 concurrent map 작업을 지원해도 expire/bound/distributed invalidation은 제공하지 않는다. TTL은 오래된 값 최대 체류 시간이지 즉시 최신 보장이 아니다.

**예시·실행 근거:** Cache loss 시 origin burst를 대비해 immutable value, bounded Caffeine, 동일 키 요청 합치기를 설계한다.

**선수개념:** heap/GC; cache key; mutable object ownership

**관련 표기·별칭:** hit rate; max size; expireAfterWrite; cache miss stampede; immutability

**판정 이유:** 핵심 설명과 선택 기준은 있으나 실행/학습 과제 근거가 부분적이므로 부분 판정.

**보완·검증 필요 사항:**

- 동시 miss와 장애 fallback은 실험하지 않았다.

**초보자가 시작할 질문:**

- ConcurrentHashMap이 만료도 관리하나?
- 캐시된 객체를 호출자가 바꾸면?

## 실제 캡처 관찰

- 첫 화면에는 시뮬레이션 컨트롤(키 선택·같은 키 요청·초기화)과 APP cache/DB 원본의 별도 상태 및 조회 횟수가 보여 miss→hit의 핵심을 조작으로 전달한다.
- 390px에서 컨트롤과 APP cache 카드가 세로 배치되어 입력과 상태가 판독 가능하며 두 번째 카드/설명은 스크롤 아래에 있다.
- 시뮬레이터에 실제 Caffeine/DB를 호출하지 않는 설명용 상태임을 화면에 표시한다.
- core는 지정 anchor 화면일 수 있으므로 모든 nested details/조작 상태를 확인했다는 뜻은 아니다.
- 이미지의 키 선택/같은 키 요청/초기화 UI와 당시 cache miss 표시를 시각적으로 확인했다. 직접 클릭 전후 action/DOM 캡처는 남기지 않았으므로 클릭 동작 시험으로 간주하지 않는다.
