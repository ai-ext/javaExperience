## multipart 바인딩과 요청 크기

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** multipart/form-data는 파일과 폼 데이터를 여러 파트로 묶고 Spring은 각 파일을 MultipartFile로 받습니다. 파일 하나의 크기 제한과 요청 전체 크기 제한은 별개입니다.

**언제 사용하는가:** 파트 이름과 Content-Type을 맞추고 애플리케이션과 프록시의 크기 제한을 함께 설정합니다.

**대안과 경계:** MultipartFile은 요청 처리 중 임시 자원이며 영구 저장소가 아닙니다.

**예시·실행 근거:** @RequestPart("file") 바인딩과 파일별·요청별 제한 설정을 보여 줍니다. Spring Boot 예제는 실행되지 않았습니다.

**선수개념:** HTTP multipart·파일 경로·권한

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Spring sample marked unexecuted

## 서버 생성 storage key와 메타데이터

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** 사용자가 보낸 파일명과 MIME 값은 신뢰하지 않고, 서버가 UUID 등 예측하기 어려운 저장 key를 만듭니다. 실제 파일 형식은 signature나 decoder로 확인할 수 있습니다.

**언제 사용하는가:** 경로 조작·덮어쓰기·위장 MIME을 막고 DB에는 소유자, key, 크기, 상태 같은 메타데이터를 저장합니다.

**대안과 경계:** 확장자나 Content-Type 검사만으로 악성 파일이나 내용 위장을 막을 수 없습니다.

**예시·실행 근거:** 저장 경로를 normalize한 뒤 허용 root 안에 있는지 확인하고, 난수 key와 메타데이터를 기록합니다.

**선수개념:** HTTP multipart·파일 경로·권한

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Virus scan/auth/DB schema fully not implemented in tutorial.

## 다운로드 권한과 Resource

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** 다운로드는 먼저 소유·공유 권한을 확인한 뒤 Resource 또는 stream과 Content-Disposition으로 응답합니다.

**언제 사용하는가:** 큰 파일은 byte 배열 전체 적재 대신 stream이나 객체 저장소의 제한된 direct URL을 검토합니다.

**대안과 경계:** InputStreamResource 종료는 응답 writer의 수명과 맞춰야 합니다. 원본 파일명을 헤더에 그대로 넣으면 인젝션·인코딩 문제가 생길 수 있습니다.

**예시·실행 근거:** attachment 응답과 UTF-8 파일명을 구성하는 ContentDisposition 예제를 제시합니다.

**선수개념:** HTTP response; resource stream; authorization

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

## Presigned URL 업로드 상태

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** API가 PENDING 상태와 서버 생성 key를 만든 후 제한된 URL을 반환합니다. 클라이언트가 저장소로 업로드하고, 서버가 HEAD와 내용 검증을 마친 뒤 AVAILABLE로 전이합니다.

**언제 사용하는가:** 애플리케이션 서버가 대용량 파일 본문을 중계하는 비용을 줄일 때 사용하며 만료 URL과 고아 파일 정리 절차를 둡니다.

**대안과 경계:** URL은 만료 전까지 권한을 가진 bearer 값입니다. 같은 key를 덮어쓸 수 있고 클라이언트 완료 통지만으로 업로드 성공을 확정하면 안 됩니다.

**예시·실행 근거:** presign 요청→저장소 PUT→완료 요청→서버 HEAD 검증 순서를 설명합니다.

**선수개념:** S3 auth; state machine; idempotent completion

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- AWS integration not executed; provider configuration omitted.

**초보자가 시작할 질문:**

- PUT URL이 200으로 끝나도 서버가 S3 HEAD를 다시 확인해야 하는 이유는 무엇인가요?
- 업로드 요청 뒤 완료 호출이 안 온 파일 metadata는 어떤 상태로 정리하나요?

## File/DB atomicity and operations

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** 파일 바이트와 DB 메타데이터는 서로 다른 저장소에 있어 실패·원자성 경계가 다릅니다.

**언제 사용하는가:** 상태 전이와 정리 작업을 설계하고 로컬 디스크는 내구성·공유 서버 계획이 명확할 때만 선택합니다.

**대안과 경계:** DB rollback이 객체 저장소 쓰기를 취소하지 않으며 컨테이너 재시작도 외부 파일을 자동 정리하지 않습니다.

**예시·실행 근거:** PENDING→AVAILABLE 전이와 orphan 정리, 로컬 디스크 재시작 손실 가능성을 짚습니다.

**선수개념:** Transactions and lifecycle.

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- No saga/compensation concrete implementation.

## 실제 캡처 관찰

- 데스크톱 요약은 multipart, metadata, 신뢰할 수 없는 filename/MIME, object storage를 간결히 설명하며 문서 섹션은 접혀 있다.
- 모바일 캡처에서는 페이지 전체가 눈에 띄게 작은 글자로 렌더링된다. 요약과 섹션 행은 보이지만 캡처 크기에서는 읽기 어렵다.
- core 캡처에는 파트, 임시 MultipartFile, 제한, key, disposition/권한, 대용량 업로드의 소주제 6개가 접혀 보인다. 업로드 상태 전이는 펼쳐지지 않았다.

**관찰 범위:** 캡처는 파일 upload/download나 presigned URL 실행을 보여 주지 않는다. 저장소·보안 동작은 캡처 화면 아래 본문에서 글로 설명한다.
