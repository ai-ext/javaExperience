## IoC/DI와 BeanDefinition·ApplicationContext

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** IoC는 객체 생성·의존 연결·생명주기 통제를 컨테이너로 옮기는 원칙이고, DI는 필요한 협력 객체를 전달하는 방법이다. BeanDefinition은 인스턴스 생성 전 메타데이터, ApplicationContext는 빈 관리와 이벤트/리소스 등 애플리케이션 기능을 제공한다.

**언제 사용하는가:** 애플리케이션 서비스는 생성자 주입, 외부 라이브러리·조건부 객체는 @Bean 등록을 사용하고 ApplicationContext를 기본 컨테이너로 둔다.

**대안과 경계:** 빈 등록·객체 생성·초기화는 다른 단계다. 컴포넌트 스캔은 앱 패키지에서 후보를 찾고 자동 구성은 별도 imports 경로를 쓴다.

**예시·실행 근거:** CheckoutService 생성자에 PaymentGateway 계약을 주입하고 구현이 여러 개면 qualifier로 선택한다.

**선수개념:** Java 객체/생성자; 타입 후보 탐색

**관련 표기·별칭:** Inversion of Control; Dependency Injection; BeanFactory; ApplicationContext; @Component; @Bean

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 예제는 Boot4.1/Framework7 기준이며 컨텍스트 실행은 하지 않았다.

## Bean 생명주기, scope, extension point, 이벤트 한계

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** 컨테이너는 정의 메타데이터를 처리한 뒤 의존성을 구성하고 초기화 콜백과 후처리를 실행한다. singleton은 정의별 컨테이너당 하나, prototype은 요청마다 새 인스턴스, request scope는 웹 요청 범위다.

**언제 사용하는가:** 작은 setup/cleanup은 lifecycle 콜백, 관리형 소비자 시작/정지는 SmartLifecycle, singleton이 매번 prototype이 필요하면 ObjectProvider/factory, 앱 내부 loose coupling엔 ApplicationEvent를 쓴다.

**대안과 경계:** BeanFactoryPostProcessor는 인스턴스 이전 정의를 수정하고 BeanPostProcessor는 인스턴스를 래핑/처리한다. prototype destruction은 자동 관리되지 않고 request proxy는 활성 요청 밖에서 실패한다. ApplicationEvent는 재시도/내구성/외부 원자성을 주지 않는다.

**예시·실행 근거:** @PostConstruct로 작은 메모리 상태 준비, @PreDestroy는 정상 종료 정리; 필수 이벤트 전달은 outbox/broker로 설계한다.

**선수개념:** S01 Bean registration; Spring proxy

**관련 표기·별칭:** singleton; prototype; request scope; @PostConstruct; BeanFactoryPostProcessor; BeanPostProcessor; SmartLifecycle; ApplicationEvent

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 정확한 callback sequence는 버전·extension에 따라 검증 필요; 런타임 실행하지 않았다.
