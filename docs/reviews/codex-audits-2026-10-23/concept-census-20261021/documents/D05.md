## 문제 재현과 가설 검증

현재 판정: **충분** / 우선순위: high

**정의와 실제 역할:** 디버깅은 조건을 고정하고 최소 재현을 만든 뒤 반증 가능한 가설 하나를 검증하는 과정이다.

**언제 사용하는가:** 간헐적 오류나 회귀 문제에서 원인 후보를 줄일 때 사용한다.

**대안과 경계:** 비슷해 보이는 환경에서 한 번 성공했다고 문제가 해결된 것은 아니다. 재현과 회귀 검증이 필요하다.

**예시·실행 근거:** 조건 기록→최소 입력→가설→실험→회귀 test 순으로 진행한다.

**선수개념:** 오류 증상; 재현 입력

**관련 표기·별칭:** Reproduction and hypothesis

**보완·검증 필요 사항:**

- 실제 프로젝트 전반에 적용한 debug run은 아니며 방법론과 예제를 구분한다.

## 예외·로그·debugger 증거

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** exception cause chain, 첫 애플리케이션 stack frame, log, browser, SQL과 debugger는 서로 다른 관찰 근거다.

**언제 사용하는가:** 어느 계층에서 실패했는지 판단하고 다음 증거 수집 방법을 고를 때 사용한다.

**대안과 경계:** error message 한 줄이나 stack 최상단만으로 최초 원인을 확정할 수 없다. log는 시점·request correlation, debugger는 실행 상태를 보여준다.

**예시·실행 근거:** 최초 application frame과 cause를 읽고 requestId, SQL binding 및 response를 함께 확인한다.

**선수개념:** exception; stack trace; log

**관련 표기·별칭:** Exceptions, logs and debugger

**보완·검증 필요 사항:**

- 일부 runtime 예시는 특정 환경 fixture에 한정된다.

**초보자가 시작할 질문:**

- 500 응답을 받았을 때 원인 stack을 어디에서부터 읽나?

## 운영 장애 조사와 commit 범위 축소

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** metrics/log/trace 확인 후 필요하면 thread/heap dump를 수집하고 git bisect로 문제 commit 범위를 좁힌다.

**언제 사용하는가:** 운영 장애가 코드·자원·요청 경로 중 어디에 있는지 추가 조사할 때 사용한다.

**대안과 경계:** dump는 부하와 개인정보 위험을 만들 수 있다. 수집 목적·권한·보관 정책을 먼저 고려한다.

**예시·실행 근거:** 최근 정상/실패 revision과 관측된 오류를 사용해 bisect를 수행한다.

**선수개념:** metrics; log; trace; Git

**관련 표기·별칭:** Production escalation and bisect

**보완·검증 필요 사항:**

- 무거운 운영 증거 수집의 비용과 자료보호 절차를 실습으로 검증하지 않았다.

**초보자가 시작할 질문:**

- 문제가 난 commit을 모를 때 어떤 순서로 범위를 좁히나?

## 시각 구조와 보완 장면

**기존 표현**

- debug loop, exception chain과 운영 증거 수집 순서를 제공한다.

**정적 구조의 한계**

- core 앵커는 용어 표가 길고 뒤에 있는 Mermaid debug 흐름은 첫 진입에서 보이지 않는다.

**추가할 의미 장면**

- 최상위 예외→cause→첫 application frame을 찾고 최소 재현→가설→회귀 test로 되돌아가는 흐름을 보여준다.
