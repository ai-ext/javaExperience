## Virtual Thread·carrier·unmount

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** Virtual Thread는 JDK가 관리하는 경량 Thread이고 실행 시 platform carrier에 mount됩니다. 지원 블로킹 중 unmount하여 다른 작업이 carrier를 쓸 수 있습니다.

**언제 사용하는가:** I/O 대기 비중이 큰 요청당 동기 코드 서버에서 높은 동시성 모델로 검토합니다.

**대안과 경계:** OS thread가 없어지는 것도 CPU가 늘어나는 것도 아닙니다.

**예시·실행 근거:** VirtualThreadFanOut에서 JDK21 8개 작업이 virtual=true로 실행됩니다.

**선수개념:** Thread lifecycle; blocking I/O

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 서비스 부하에서 throughput/latency 비교는 없습니다.

**초보자가 시작할 질문:**

- 가상 스레드가 I/O 중 멈췄을 때 같은 OS thread를 계속 점유하지 않아도 되는 이유는 무엇인가요?
- CPU-bound 계산이 8코어보다 빨라지는 효과를 가상 스레드가 주나요?

## Pinning과 외부 자원 제한

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** unmount할 수 없는 native/foreign 경계에서 carrier가 작업과 함께 묶일 수 있습니다. Java24는 monitor pinning 대부분을 제거했습니다.

**언제 사용하는가:** JFR로 남은 pinning을 관찰하고 DB·remote API는 connection pool/permit/rate limit으로 별도 제어합니다.

**대안과 경계:** Virtual thread 수가 DB 동시성 한도는 아니며 synchronized를 무조건 ReentrantLock으로 바꿀 이유도 아닙니다.

**예시·실행 근거:** SemaphoreLimit은 12 VT 중 downstream active를 3으로 제한합니다.

**선수개념:** JMM; Semaphore; JFR

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 실제 DB/API 포화는 미실행.

**초보자가 시작할 질문:**

- 가상 스레드 1000개가 DB 커넥션 1000개를 만들어도 되는 이유가 되지 않는 것은 왜일까요?
- JEP491 이후에도 pinning을 계속 조사해야 하는 native 경계는 무엇인가요?

## ThreadLocal과 ScopedValue

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** ThreadLocal은 Thread별 저장이고 ScopedValue는 동적 호출 범위에 값 binding을 제공합니다. Scoped Values는 Java25에서 정식화됐습니다.

**언제 사용하는가:** 불변 request context를 하위 호출에 전달할 때 scoped binding을 고려합니다.

**대안과 경계:** ThreadLocal은 금지/폐기되지 않고 ScopedValue도 가리키는 mutable 객체를 immutable하게 만들지 않습니다.

**예시·실행 근거:** Java25 ScopedValue 코드; JDK21 미실행.

**선수개념:** ThreadLocal; immutable value

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 운영 프레임워크에서 실제 전파 경로는 별도 확인 필요.

**초보자가 시작할 질문:**

- 요청 종료 후 요청 ID가 사라지는 범위 제한을 어떤 API가 직접 표현하나요?
- ScopedValue에 mutable HashMap을 넣으면 그 Map 변경도 막히나요?

## Structured Concurrency preview와 task scope

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** 관련 하위 작업을 부모 scope 수명 안에 묶어 join/failure/cancel 정책을 다루는 API입니다.

**언제 사용하는가:** HTTP 요청의 병렬 fan-out/fan-in처럼 자식 작업이 부모 완료에 종속될 때 검토합니다.

**대안과 경계:** Java27까지 preview라 시그니처가 변할 수 있고 close는 interrupt 무시 작업을 강제 종료하지 못합니다.

**예시·실행 근거:** Java25 JEP505 예제는 미실행, parent/child 생명주기 diagram.

**선수개념:** ExecutorService; interrupt

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 최신 preview 버전별 코드를 실제 컴파일하지 않음.

**초보자가 시작할 질문:**

- 부모 요청이 끝난 뒤 자식 작업이 계속 남을 수 있는 기존 Future 패턴은 어떤 운영 문제를 만들까요?
- StructuredTaskScope.close가 느린 자식을 OS에서 강제 종료해 주나요?

## 스레드별 모델 관측과 버전

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** JFR VT start/end/pinned/submit-failed와 JSON thread dump로 JDK 동시성을 관측할 수 있습니다.

**언제 사용하는가:** JFR recording range, request ID, thread dump를 같은 시간대로 모아 병목을 설명합니다.

**대안과 경계:** 녹화 이벤트가 없다고 pinning이 전혀 없다고 단정하려면 설정/필터 확인이 필요합니다.

**예시·실행 근거:** 문자열을 값으로 전달하는 예와 mutable 객체를 전달하는 예에서 호출 뒤 변수·객체 상태를 비교합니다.

**선수개념:** JFR; jcmd

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 실제 JFR output 미수집.

**초보자가 시작할 질문:**

- `jdk.VirtualThreadPinned` 이벤트가 녹화되지 않았을 때 즉시 pinning 없음이라고 결론 내릴 수 있나요?
