## Thread lifecycle·JVM 상태

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** Thread.start()가 새 실행을 시작하고 run() 직접 호출은 현재 thread에서 일반 메서드처럼 돕니다. JVM State는 여섯 상태의 순간 진단값입니다.

**언제 사용하는가:** join/lock 등 명세된 synchronization point로 진행을 조정합니다.

**대안과 경계:** RUNNABLE은 CPU 실행 중만 뜻하지 않으며 getState()는 synchronization 아님.

**예시·실행 근거:** WaitNotifyDemo는 WAITING을 관찰하지만 상태 polling 자체는 설명 예시입니다.

**선수개념:** Java method call; Thread API

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 스케줄러의 실제 OS state와 JVM state는 1:1이 아닙니다.

**초보자가 시작할 질문:**

- `thread.run()`을 호출한 뒤 새 thread id가 생기나요?
- `getState()==WAITING`을 확인한 코드가 다른 메모리 쓰기를 보장하지 않는 이유는?

## monitor·wait/notify condition

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** synchronized는 reentrant monitor를 획득/해제합니다. wait은 monitor를 놓고 대기한 뒤 다시 잡고 반환합니다.

**언제 사용하는가:** 조건 상태·검사·wait/notify를 한 monitor 안에 두고 while로 재검사합니다.

**대안과 경계:** notify는 특정 올바른 waiter를 고르지 않고, sleep은 monitor를 해제하지 않습니다.

**예시·실행 근거:** 동일한 입력을 배열과 컬렉션에 넣고 순회·조회 결과를 출력합니다.

**선수개념:** monitor; ThreadState

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 조건 경쟁과 spurious wakeup은 if로 바꾸면 발생할 수 있습니다.

**초보자가 시작할 질문:**

- wait() 후 깨어났다고 바로 큐를 꺼내면 어떤 조건 변화 때문에 오류가 날 수 있나요?
- 모니터를 가진 채 sleep하는 코드가 다른 스레드를 막는 이유는?

## JMM·data race·happens-before

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** JMM은 실행 결과에서 어떤 공유값을 허용하는지 정의하는 명세 모델이며 HB는 program order/synchronizes-with/transitivity 관계입니다.

**언제 사용하는가:** 쓰기를 읽기에 연결하는 synchronization edge가 있는지 추적합니다.

**대안과 경계:** “메모리를 비운다”는 구현 비유가 아니며 data race에서는 source order만으로 읽은 값을 추론할 수 없습니다.

**예시·실행 근거:** 정렬 기준을 바꾸어 정렬 결과가 어떻게 달라지는지 확인합니다.

**선수개념:** shared variable; monitor/volatile

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 한 번의 실행값은 모든 실행 보장 증명은 아닙니다.

**초보자가 시작할 질문:**

- writer가 payload를 쓴 뒤 ready=true를 volatile에 쓰면 reader가 어떤 순서로 읽을 때 payload가 보장되나요?
- happens-before가 물리적으로 CPU 명령 실행 시각을 고정하지 않는 이유는?

**근거:**

## volatile/final/publication

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** 같은 volatile 변수의 write/read는 가시성·순서를 연결하지만 복합 연산은 원자화하지 않습니다. final은 완성 생성자와 this escape 없음 조건에서 초기화 값을 보호합니다.

**언제 사용하는가:** 독립 종료 플래그는 volatile, 여러 필드 불변식은 lock, 객체는 안전한 공개를 씁니다.

**대안과 경계:** volatile count++는 읽기/계산/쓰기로 나뉘고 final 참조 대상은 깊은 불변이 아닙니다.

**예시·실행 근거:** 비교 기준이 0인 두 객체를 TreeSet에 넣어 중복 취급 결과를 관찰합니다.

**선수개념:** volatile variable; constructor

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- J11 atomic types are separate.

**초보자가 시작할 질문:**

- volatile int count++에서 두 스레드가 값을 잃을 수 있는 실행 순서는 어떤가요?
- 생성 중 this를 노출하면 final field guarantee가 기대대로 적용되지 않을 수 있는 이유는?

## deadlock·livelock·starvation

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** Deadlock은 circular wait, livelock은 계속 반응하지만 완료 못 함, starvation은 특정 thread가 자원을 못 얻는 진행 문제입니다.

**언제 사용하는가:** 여러 lock이 필요하면 전역 획득 순서를 정의하고 timeout/fairness 요구를 따로 둡니다.

**대안과 경계:** synchronized는 fair queue나 자동 deadlock detector를 보장하지 않습니다.

**예시·실행 근거:** 동일 JLS/concurrency discussion.

**선수개념:** lock/resource

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 동시성 도구·진단은 J11에서 상세화.

**초보자가 시작할 질문:**

- A가 x를 가진 채 y를 기다리고 B가 y를 가진 채 x를 기다리면 어떤 교착 조건이 되나요?
- 잠금은 계속 풀리고 재획득도 하지만 두 작업이 서로 양보만 한다면 deadlock과 무엇이 다른가요?
