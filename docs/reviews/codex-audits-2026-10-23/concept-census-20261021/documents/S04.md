## PropertySource 우선순위와 Config Data

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** Environment는 여러 PropertySource를 우선순위로 합친다. 환경변수/CLI/test sources가 application config를 덮을 수 있고 Config Data 내부 classpath/external/profile 순서도 있다.

**언제 사용하는가:** 실행 값이 다르면 특정 키의 최종 value/origin을 제한적으로 확인한다. 공통값은 base, deploy-specific는 외부 설정/secret provider로 둔다.

**대안과 경계:** @PropertySource는 refresh 때 추가되어 early read 속성에 늦을 수 있다. profile-specific config는 여러 sources 중 한 층이다. List는 항목별 merge가 아니라 교체될 수 있다.

**예시·실행 근거:** YAML URL보다 SPRING_DATASOURCE_URL이 높은 우선순위면 실제 접속은 env값; 값 전부 덤프하지 말고 단일 키 origin 확인.

**선수개념:** Boot config loading; externalized environment

**관련 표기·별칭:** Environment; PropertySource; Config Data; application.yml; @PropertySource; SPRING_APPLICATION_JSON

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 우선순위는 버전별 공식 문서에서 확인해야 하며 실행 예제 미실행.

## Profiles·typed binding·validation·configtree

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** Profiles는 환경별 문서/빈 조건을 구성하고 groups는 alias를 여러 profile에 매핑한다. @ConfigurationProperties는 prefix 속성을 타입 객체로 바인딩하고 validation으로 startup fail을 만들 수 있다.

**언제 사용하는가:** 관련 설정 여러 개는 record+ConfigurationProperties+검증, 단일 값은 @Value, mounted key-per-file secret은 configtree. optional은 정말 선택적 파일에만 사용한다.

**대안과 경계:** active profile은 무엇을 켤지, on-profile은 어느 문서를 적용할지, @Profile은 빈 registration을 나눈다. Config metadata는 IDE 도움이지 runtime validation 아님; list는 통째로 replace.

**예시·실행 근거:** production profile group이 proddb/prodmq를 함께 켜고 configtree는 마운트된 파일명에서 payment.api-key 속성을 만든다.

**선수개념:** Boot Binder; Jakarta Validation; Kubernetes secret mount

**관련 표기·별칭:** spring.profiles.active; on-profile; profile group; @ConfigurationProperties; @Value; configtree; configuration metadata

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- Configtree/secret volume 및 binding sample 미실행.

- group과 include 차이?
- environment variable spelling?
- metadata가 검증하나?
- 필수 secret에 optional 쓸까?

- desktop 화면은 application.yml 들여쓰기와 점으로 바뀌는 property key 관계를 직접 대응시킨다.
