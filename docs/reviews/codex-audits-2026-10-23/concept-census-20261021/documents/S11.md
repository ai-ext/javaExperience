## Spring Cache/provider/cache-aside/TTL

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** Spring Cache는 추상화이지 저장소가 아니다. Caffeine은 JVM 로컬, Redis는 원격 공유 캐시다. Cache-aside는 miss 시 원본을 읽어 채운다.

**언제 사용하는가:** 반복 조회 비용이 측정될 때; 로컬 최신성 차이를 감당하면 Caffeine, 여러 인스턴스 공유가 필요하면 Redis. 크기/TTL 한도 둔다.

**대안과 경계:** TTL은 stale 최대 수명이지 즉시 정합성 보장 아님. sync=true는 구현체가 같은 키 로딩을 조정하는 기능이지 분산락이 아니다.

**예시·실행 근거:** Cacheable product; Redis CacheManager에 key prefix/TTL; DB 커밋 뒤 캐시 키 제거.

**선수개념:** Spring proxy; DB commit; cache key

**관련 표기·별칭:** CacheManager; Caffeine; Redis; cache-aside; sync

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 예제 미실행; managed Spring Data Redis와 cluster 동작 확인 못함.

**초보자가 시작할 질문:**

- Spring Cache가 Redis를 제공하나?
- TTL이 업데이트 직후 반영을 보장하나?
- sync=true는 cluster lock인가?

## 캐시 키·스탬피드·expand-contract 마이그레이션

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** 캐시 키는 결과를 바꾸는 모든 조건을 표현해야 한다. DB write와 invalidation은 원자적이지 않으며 outbox/TTL이 복구를 돕는다. 스키마 확장은 구/신 버전 호환 기간을 거쳐 backfill·read switch·삭제 단계로 나눈다.

**언제 사용하는가:** tenant/user/locale에 따라 결과가 다르면 키에 반영; 꼭 전달할 invalidation은 outbox; rolling deploy 동안 additive schema 먼저 추가.

**대안과 경계:** 키에 tenant를 빼면 데이터 노출 위험. concurrent miss는 stampede. Redis 전체 clear는 keyspace/driver에 따라 비용 큼. Flyway 적용 migration은 수정 대신 새 파일.

**예시·실행 근거:** catalog:v1 키 접두어와 cache별 TTL을 두고 Expand/Contract에서는 컬럼 추가→구/신 버전 호환→backfill→읽기 전환→구 컬럼 제거 순으로 배포한다.

**선수개념:** tenant isolation; rolling deployment; DB DDL

**관련 표기·별칭:** write-through; stampede; outbox; expand/contract; Flyway; Liquibase

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 스키마 예제가 PostgreSQL인 점은 원문 명시; MySQL 그대로 실행 금지.

**초보자가 시작할 질문:**

- DB commit 후 invalidation 전에 process가 죽으면?
- old instance가 살아 있는 중 column drop이 가능한가?
