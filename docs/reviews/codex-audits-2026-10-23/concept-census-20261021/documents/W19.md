## Lombok annotation processor and build/IDE compiler boundary

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** Lombok은 주로 컴파일 시 compiler AST에 멤버를 추가하고 결과 bytecode는 일반 메서드가 된다. IDE 지원과 build annotation processor는 별도다.

**언제 사용하는가:** 팀이 JDK/compiler/IDE를 정렬하고 보일러플레이트 절감이 코드 가독성보다 이득일 때 허용 목록을 두어 사용한다.

**대안과 경계:** Record는 언어 내장 데이터 carrier, IDE 생성은 결과가 소스에 보임, Lombok은 숨김. processor가 compiler 내부에 의존해 JDK별 호환 비용이 생긴다.

**예시·실행 근거:** compileOnly+annotationProcessor를 고정하고 IDE가 아닌 clean CLI/CI build에서 생성 코드가 확인되는지 검증한다.

**선수개념:** Java compilation phases; Gradle configurations; IDE vs build classpath

**관련 표기·별칭:** AST transformation; annotationProcessor; delombok; javac/Eclipse

**판정 이유:** 정의와 선택 기준은 설명하지만 대상 실행 환경의 동작 검증 또는 학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- Lombok/Java21 컴파일과 delombok은 직접 확인하지 않았다.

**초보자가 시작할 질문:**

- Lombok은 런타임 reflection 도구인가?
- IDE가 getter를 보여주는데 CI는 왜 실패하나?
- Java upgrade가 Lombok을 깨뜨릴 수 있나?

## Record, @Data and entity equality/builder tradeoffs

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** record는 얕은 불변 데이터 타입이다. @Data는 getter/setter, equals/hashCode, toString, 생성자 등을 묶어 만들며 엔티티의 가변 상태·프록시와 충돌할 수 있다.

**언제 사용하는가:** DTO/event는 record 우선, 일반 클래스는 필요한 Lombok 기능만 사용한다. JPA 엔티티는 접근자/동등성/문자열 포함 필드를 따로 정한다.

**대안과 경계:** record 안 List 값은 깊게 불변이 아니다. @Data 엔티티는 lazy 관계 로딩·순환 toString·민감값 로그·가변 hash 문제를 일으킬 수 있다. Builder 기본값은 명시적 처리 필요.

**예시·실행 근거:** 응답 record, entity @Getter+protected 생성자+domain method; 엔티티 전역 @Data는 피한다.

**선수개념:** records; ORM proxies/lazy loading; hash collections; generated API contract

**관련 표기·별칭:** record; @Data; @Builder.Default; @ToString; equals/hashCode

**판정 이유:** 정의와 선택 기준은 설명하지만 대상 실행 환경의 동작 검증 또는 학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- JPA entity equality/proxy runtime 테스트 없음.

**초보자가 시작할 질문:**

- record collection is deeply immutable?
- 왜 @Data toString on entity 위험?
- builder가 field initializer를 자동으로 쓰나?
- all-args same-type args order risk?
