## MVC의 Model·View·Controller

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Model은 View에 전달할 데이터, View는 HTML 표현, Controller는 요청 연결을 맡는다.

**언제 사용하는가:** HTTP 매핑과 서버 렌더링/JSON 응답 경로를 구분할 때 쓴다.

**대안과 경계:** MVC는 웹 표현 분류, Controller·Service·Repository는 애플리케이션 책임 계층이다. JSON은 DTO를 변환기로 본문에 쓰며 HTML View를 렌더링하지 않는다.

**예시·실행 근거:** @Controller의 return "hello"는 뷰 이름, @RestController 객체는 응답 본문.

**선수개념:** HTTP; JSON/HTML

**관련 표기·별칭:** Spring MVC

**보완·검증 필요 사항:**

- DispatcherServlet 내부 순서는 S05로 넘긴다.

## Controller·Service·Repository 책임 계층

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Controller는 HTTP 입출력, Service는 유스케이스·정책, Repository는 저장 조회 계약을 맡고 기본 흐름은 Controller→Service→Repository다.

**언제 사용하는가:** HTTP 경계·업무 결정·저장 방식의 변경 이유를 분리하고 규칙을 여러 진입점에서 재사용할 때 적용한다. 기계적 계층 추가는 강제하지 않는다.

**대안과 경계:** Repository는 저장 쿼리를 맡지만 업무 허용 여부는 Service가 판단한다.

**예시·실행 근거:** MemoController.create → MemoService.create → repository.save → MemoResponse 변환.

**선수개념:** 메서드 호출; 인터페이스; HTTP

**관련 표기·별칭:** layered architecture

**보완·검증 필요 사항:**

- 현재 Service 예제는 단순 저장+DTO 변환이며 트랜잭션·복수 정책을 구현하지 않는다.

**초보자가 시작할 질문:**

- 규칙은 어디에 두나?
- 한 줄 Service도 늘 만들어야 하나?

## 요청 DTO·도메인 객체·응답 DTO와 Entity 경계

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** 요청 DTO는 입력 허용 필드, 도메인/Entity는 내부 상태, 응답 DTO는 공개 필드를 표현한다. Memo는 JPA Entity가 아닌 메모리 도메인 record다.

**언제 사용하는가:** 외부 입력 허용 범위를 제한하고 공개 계약과 저장 모델의 변경 이유가 다를 때 분리한다.

**대안과 경계:** 요청에서 Entity를 받으면 대량 할당 위험, 응답 Entity는 내부 필드·연관관계·지연로딩이 계약에 노출될 수 있다.

**예시·실행 근거:** MemoCreateRequest(title,content)→save(title,content)→Memo(id,title,content)→MemoResponse. JPA Entity 매핑 예제는 없다.

**선수개념:** record; 객체 생성; JSON

**관련 표기·별칭:** DTO; Entity; mass assignment

**보완·검증 필요 사항:**

- DTO→JPA Entity 생성/수정/저장 미설명. Value Object의 동일성·불변값과 Entity 생명주기 별도 학습 필요. 직렬화 순환·Lazy 오류는 위험만 서술.

**초보자가 시작할 질문:**

- Value Object·DTO·Entity는 무엇이고 언제 쓰나?
- DTO에서 Entity로 바꿔 DB에 어떻게 저장하나?
- Entity를 응답하지 않는 이유는?

## Repository 계약·메모리 저장 구현

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Repository 인터페이스는 저장·조회 계약, 구현 Bean은 저장 방식을 수행한다. 예시는 AtomicLong과 ConcurrentHashMap으로 메모리에 저장한다.

**언제 사용하는가:** 업무 계층에서 저장 기술 세부를 감추고 계약으로 조회·저장할 때 쓴다.

**대안과 경계:** 재시작 후 보존되지 않으며 SQL/JPA/트랜잭션을 보여주는 예제가 아니다.

**예시·실행 근거:** save가 id를 만들고 Memo를 Map에 저장, findAll은 id 순 List로 반환.

**선수개념:** interface; Map/List; Bean

**관련 표기·별칭:** repository interface; in-memory repository

**보완·검증 필요 사항:**

- DB·SQL·트랜잭션·제약조건은 후속 학습이다.

**초보자가 시작할 질문:**

- 인터페이스를 주입하면 구현은 누가 제공하나?
- Map 저장은 DB에 남나?

## 생성자 주입·의존 방향

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Spring은 등록된 구현 Bean을 생성자 인수 인터페이스 타입에 연결한다. Controller→Service→Repository 방향으로 의존한다.

**언제 사용하는가:** 필수 의존성을 드러내고 교체와 격리를 쉽게 하며 객체 관리를 컨테이너에 맡긴다.

**대안과 경계:** 구현체 직접 new는 교체·테스트 격리를 어렵게 한다. 순환 의존은 책임을 흐린다.

**예시·실행 근거:** MemoService 생성자에 MemoRepository 인터페이스를 전달하고 InMemoryMemoRepository가 이를 구현하는 예입니다.

**선수개념:** 생성자; interface; Spring Bean

**관련 표기·별칭:** constructor injection

**보완·검증 필요 사항:**

- 복수 구현 @Primary/@Qualifier 선택은 언급만 있고 실행 확인은 없다.

**초보자가 시작할 질문:**

## record 값 전달 타입

## 시각 구조와 보완 장면

**기존 표현**

**정적 구조의 한계**

- 역할 예시일 뿐 실제 계약/DB 결과가 아니라고 밝히며 실행도 미실행이다. JPA DTO→Entity 저장, 모바일 렌더링은 확인 불가.

**추가할 의미 장면**

- 요청 DTO→Entity 생성→저장→DB 행→응답 DTO 실제 값 이동

## 실제 캡처 관찰

- 데스크톱에는 이름을 입력하는 밝은 MVC 장면과 Controller→Model→View 값 흐름이 보인다. DB 결과가 아닌 설명 예시라고 표시하고 예상 GET /hello 응답을 보여 준다.
- 모바일은 같은 카드를 세로로 쌓고 가로 넘침은 보이지 않는다. 캡처는 응답 카드와 CTA 앞에서 끝나므로 화면 아래 배치는 확인하지 못했다.
- core 캡처는 문서의 두 번째 섹션 대신 데스크톱과 같은 MVC 시작 장면을 반복한다. 이 캡처에는 더 깊은 개념 내용이 보이지 않는다.

**관찰 범위:** 보이는 정적 MVC 장면만 확인했다. 이름 입력란과 CTA는 보이지만 조작하지 않았다. 별도의 요청 DTO/Entity/DB 학습 흐름을 검증한 것은 아니다.
