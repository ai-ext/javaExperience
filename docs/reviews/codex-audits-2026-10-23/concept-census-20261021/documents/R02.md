## 저장 모델과 조회 패턴

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 관계형 DB는 table·constraint·transaction을 제공하고, NoSQL 제품은 각자 특정 query/access pattern에 맞춘 model을 제공한다.

**언제 사용하는가:** 요구되는 조회, 무결성, 규모와 durability를 확인한 뒤 저장소를 선택할 때 사용한다.

**대안과 경계:** NoSQL이 schema가 없거나 자동으로 더 확장 가능한 것은 아니다.

**예시·실행 근거:** 관계형/문서/키-값 저장소의 조회 조건과 요구 특성을 비교한 표를 확인한다.

**선수개념:** table과 query

**관련 표기·별칭:** models and query patterns; RDB; document; key-value; wide-column; graph; search

**보완·검증 필요 사항:**

- 성능과 비용 tradeoff를 실제 workload로 측정한 결과는 없다.

## 원본 데이터와 파생 저장소

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** RDB를 주문·결제의 원본으로 두고 cache와 검색용 document는 원본에서 파생된 자료로 다룬다.

**언제 사용하는가:** 읽기 모델이나 cache를 추가할 근거가 있고 원본과 동기화 정책을 세울 때 사용한다.

**대안과 경계:** 여러 DB·Redis에 걸친 쓰기는 하나의 원자 transaction이 아니다. cache 무효화 또는 outbox/retry가 필요하다.

**예시·실행 근거:** 주문 RDB 변경 후 outbox event로 Mongo projection을 갱신하는 흐름을 비교한다.

**선수개념:** transaction; cache

**관련 표기·별칭:** source of truth and derived stores; authoritative data; projection; outbox

**보완·검증 필요 사항:**

- 전체 event retry와 idempotency 구현은 설명 참조에 그친다.

## 문서의 내장과 참조 선택

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 함께 읽고 값의 snapshot을 유지할 bounded field는 embed하고 독립 변경되거나 커지는 자료는 reference로 둘 수 있다.

**언제 사용하는가:** 문서형 read model이 실제 query 경계에 맞을 때 사용한다.

**대안과 경계:** MongoDB는 multi-document ACID transaction을 지원하지만 데이터 모델 선택이 RDB와 같아지는 것은 아니다.

**예시·실행 근거:** 주문 당시 상품 이름과 가격을 주문 document에 보관하는 이유를 살핀다.

**선수개념:** JSON document

**관련 표기·별칭:** document embedding/reference; embedding; reference; MongoDB

**보완·검증 필요 사항:**

- 예제는 미실행이다. 크기 제한과 versioned schema 주장은 공식 근거가 필요하다.

## Redis와 Cassandra의 조회 모델

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Redis는 key와 자료구조/TTL 중심이고 Cassandra는 partition key로 정한 query table 중심이다.

**언제 사용하는가:** cache/session이나 partition 기반 대량 조회가 요구될 때 각각을 고려한다.

**대안과 경계:** RDB를 원본으로 유지할 수 있다. Cassandra schema는 조회 방식에 맞춰 설계하며 hot partition은 측정해야 한다.

**예시·실행 근거:** Cache-aside와 member/month partition query를 비교한다.

**선수개념:** key-value; partitioning

**관련 표기·별칭:** Redis and Cassandra access model; TTL; partition key; cache-aside

**보완·검증 필요 사항:**

- 코드는 실행되지 않았고 성능은 측정되지 않았다.

## ACID와 CAP에서 말하는 일관성

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** ACID consistency는 transaction 전후 업무 불변식이 유지되는 성질이고 CAP의 consistency는 network partition 중 replica가 응답하는 분산 동작과 관련된다.

**언제 사용하는가:** 분산 환경에서 partition 발생 시 가용성과 최신성의 동작을 설명할 때 사용한다.

**대안과 경계:** CAP를 정상 상황에서 제품이 속성 하나만 제공한다는 뜻으로 단순화하지 않는다.

**예시·실행 근거:** transaction constraint와 네트워크 분할 중 replica 응답 상황을 구분해 설명한다.

**선수개념:** transaction; network

**관련 표기·별칭:** ACID vs CAP consistency; atomicity; availability; partition tolerance

**보완·검증 필요 사항:**

- 제품별 실제 일관성 설정은 검토하지 않았다.

**초보자가 시작할 질문:**

- CAP의 consistency와 transaction의 consistency는 같은 뜻인가?
