## JUnit Platform·Jupiter·lifecycle

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** JUnit Platform은 엔진을 찾고 실행하며, Jupiter는 테스트·확장 모델을 제공하고, Vintage는 구형 엔진을 연결합니다. PER_METHOD는 테스트마다 새 인스턴스를 만듭니다.

**언제 사용하는가:** 테스트 상태가 서로 섞이지 않도록 기본 생명주기를 유지하고, 입력 경계는 매개변수화 테스트로 반복 검증합니다.

**대안과 경계:** PER_CLASS는 필드를 공유하므로 상태 초기화가 필요합니다. Vintage는 이전 테스트 이관에 쓰며 새 테스트의 기본 선택은 아닙니다.

**예시·실행 근거:** PricePolicy의 경계값과 음수 입력을 검증하는 parameterized test가 실제 빌드에서 통과했습니다.

**선수개념:** JUnit basics; test lifecycle

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Full Spring context/Slice coverage belongs S18.

**초보자가 시작할 질문:**

- 동일 테스트 클래스의 mutable field가 테스트마다 초기화되지 않는 설정은 무엇이고 어떤 side effect가 나나요?
- JUnit Platform과 Jupiter 중 어느 쪽이 test method annotation을 제공하나요?

## stub·mock·spy·fake·dummy roles

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Stub은 준비한 값을 돌려주고, mock은 상호작용을 검증하며, spy는 실제 객체에 위임하고, fake는 단순한 대체 동작을 수행합니다. dummy는 호출 인자를 채우기만 합니다.

**언제 사용하는가:** 외부 협력자의 결과를 통제하거나 호출 여부가 요구사항일 때 테스트 관찰 목적에 맞춰 선택합니다.

**대안과 경계:** spy의 when 호출은 실제 메서드를 실행할 수 있습니다. fake는 실제 DB 엔진의 제약이나 SQL 동작까지 증명하지 않습니다.

**예시·실행 근거:** 결제 테스트에서 mock과 captor로 전달 금액을 확인하고, 재고 테스트는 InMemoryStock fake로 수량 변화를 확인합니다.

**선수개념:** Java interface; external dependency

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Mock overuse/internal call verification can be brittle.

**초보자가 시작할 질문:**

- 검증 결과가 틀리면 외부 발송을 확인할 필요 없이 state assertion으로 볼 수 있는 경우는?
- spy에 when(spy.load())을 쓰면 stubbing 중 왜 실제 load가 실행될 수 있나요?

## assertions and coverage

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** JaCoCo는 클래스 바이트코드를 계측해 실행된 명령·줄·분기 비율을 계산합니다. 이 값은 테스트가 코드를 지나간 범위를 나타냅니다.

**언제 사용하는가:** 미실행 분기를 찾아 추가 테스트 후보를 정할 때 사용하고, 요구사항 충족 여부는 명시적 assertion으로 확인합니다.

**대안과 경계:** 커버리지 수치가 높아도 결과를 검증하지 않으면 실패를 발견하지 못합니다. 예외 발생은 JaCoCo 분기와 동일하지 않습니다.

**예시·실행 근거:** 문서는 JaCoCo의 줄·명령·분기 지표와 임계값 사용의 한계를 설명합니다.

**선수개념:** assertion; bytecode

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- No mutation testing run.

**초보자가 시작할 질문:**

- 100% line coverage인데 잘못된 결과를 못 잡는 테스트를 어떻게 만들 수 있나요?
- JaCoCo branch coverage에서 exception handler 경로가 누락되는 이유는?

## Flaky tests and isolation

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 공유 static 값, 테스트 순서, 시간·난수, DB 데이터가 실행 간에 남으면 간헐 실패가 생깁니다.

**언제 사용하는가:** 실패한 seed와 순서를 기록하고 단일 테스트, 클래스, 전체 묶음 순으로 범위를 넓혀 재현합니다. 테스트가 소유한 데이터만 정리합니다.

**대안과 경계:** @ResourceLock은 같은 테스트 실행기 안의 경쟁을 조정할 뿐 다른 프로세스나 DB 작업을 잠그지 않습니다.

**예시·실행 근거:** 시간·난수·DB·병렬 실행별 원인과 재현·격리 방법을 문서의 문제 해결 표에서 다룹니다.

**선수개념:** test lifecycle; shared resources

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Some integration mechanisms require real DB/test container.

**초보자가 시작할 질문:**

- 단독 실행 통과·전체 실행 실패를 재현할 때 어떤 순서로 범위를 넓히나요?
- @ResourceLock 하나로 두 CI worker가 같은 DB row를 쓰는 문제가 해결되나요?

## Red-Green-Refactor and test boundary

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Red-Green-Refactor는 요구 동작 실패를 먼저 확인하고 최소 구현으로 통과시킨 뒤 구조를 정리하는 순환입니다.

**언제 사용하는가:** 가격·배송비처럼 입력 경계와 결과가 명확한 정책을 바꿀 때 동작 테스트를 먼저 작성합니다.

**대안과 경계:** 컴파일 실패와 assertion 실패는 서로 다른 신호입니다. 내부 메서드 호출 순서에 과하게 묶인 테스트는 리팩터링을 방해합니다.

**예시·실행 근거:** 배송비 30,000원 기준과 바로 아래 29,999원 입력의 결과를 검증합니다.

**선수개념:** Junit test; business rule

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Section example not accompanied by captured command output.

**초보자가 시작할 질문:**

- 무료 배송 threshold 바로 아래와 임계값의 두 입력을 함께 두면 어떤 경계 오류를 잡나요?
- Refactor 뒤 테스트가 private method 순서를 보게 되면 어떤 변화에 취약해지나요?
