## 개발 생명주기·산출물·운영 피드백

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 요구사항을 구현·검증해 배포 artifact로 만들고 운영 관측과 후속 작업으로 되돌리는 개발 생명주기다.

**언제 사용하는가:** 기능 요청이 실제 운영에 도달하는 전체 경로를 이해하거나 작업 누락 지점을 찾을 때 사용한다.

**대안과 경계:** 빌드 artifact 생성은 운영 배포와 다르고, 배포 완료도 사용자 출시나 성공적인 운영을 보장하지 않는다.

**예시·실행 근거:** 한 ticket이 code commit→review/CI→동일 artifact→환경 배포→관측·후속 ticket으로 이어지는 예를 따라간다.

**선수개념:** 요구사항; Git commit; build/test

**관련 표기·별칭:** Lifecycle, artifacts and feedback

**보완·검증 필요 사항:**

- 원문은 전체 흐름을 제시하지만 특정 제품/조직의 배포 절차를 검증하지 않는다.

**초보자가 시작할 질문:**

- 코드를 작성한 뒤 사용자가 실제 기능을 쓰기까지 어떤 단계를 거치나?

## 환경별 검증 책임

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** local·dev·stg·prod는 실행 위치와 검증 목적이 다르며 설정·자원·데이터 경계가 달라질 수 있다.

**언제 사용하는가:** 환경별 configuration과 테스트 책임을 나누고 싶을 때 사용한다.

**대안과 경계:** 환경 이름만 같다고 검증 범위나 운영 데이터가 같은 것은 아니다. 각 팀의 환경 정의가 필요하다.

**예시·실행 근거:** local 개발, dev 통합, stg 리허설, prod 실제 사용자 경계를 목적과 데이터 기준으로 비교한다.

**선수개념:** 환경 변수; 배포 artifact

**관련 표기·별칭:** Environment responsibility

**보완·검증 필요 사항:**

- 환경별로 어떤 결함을 검증하는지 조직별 구체 기준은 충분히 고정하지 않는다.

**초보자가 시작할 질문:**

- stg에서 통과했는데 prod에서만 실패하는 이유는 무엇인가?

## 장애 복구와 운영 피드백

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 운영 장애에 rollback·hotfix 등으로 영향도를 낮추고 사후 회고/개선으로 연결한다.

**언제 사용하는가:** 배포 후 지표나 사용자 영향이 악화될 때 복구 단계를 선택한다.

**대안과 경계:** 애플리케이션 버전 rollback이 DB schema/data 변경까지 되돌린다는 뜻은 아니다.

**예시·실행 근거:** 문제가 된 release를 되돌리고 이전 artifact와 schema 호환성을 확인한 뒤 후속 ticket을 만든다.

**선수개념:** 배포와 DB migration; 운영 관측

**관련 표기·별칭:** Incident recovery

**보완·검증 필요 사항:**

- 데이터 변경과 앱 rollback의 독립성을 구체적인 migration 상태 전후로 보여주지 않는다.

**초보자가 시작할 질문:**

- 앱을 이전 버전으로 되돌리면 DB 변경도 같이 돌아가나?

## 공개본과 진행 중 보강의 차이

**추가된 내용:** progress 화면에서 티켓의 완료 조건과 추가 로컬 Java fixture를 선택형 질문으로 연결한다. 같은 입력을 반복해 count=1인지 확인하는 예를 추가했으나 API·DB·CI·배포는 모형으로 명시되어 있다. 모바일은 단계 선택 UI가 접혀 보이고 아래 그림은 스크롤해야 한다. core는 용어표라 작업 티켓→실제 CI/배포 흐름은 실행하지 않는다.
