## enum과 저장 식별자

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** enum은 유한한 타입 값이며 각 상수는 객체입니다. EnumMap/EnumSet은 상태 테이블·플래그에 특화합니다.

**언제 사용하는가:** 닫힌 상태/권한 집합에 쓰고 DB·외부 저장값은 명시 코드를 택합니다.

**대안과 경계:** ordinal은 선언 순서 인덱스라 재정렬 후 의미가 바뀌며 외부 식별자가 아닙니다.

**예시·실행 근거:** 상태 전이를 EnumMap/EnumSet으로 제한한 실행 결과.

**선수개념:** enum 타입/Map/Set

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 실제 JPA enum mapping과 DB migration은 S09 경계입니다.

**초보자가 시작할 질문:**

- enum 상수 순서를 바꾸면 ordinal로 저장한 기존 주문 상태는 어떻게 되나요?
- EnumMap이 키를 다른 타입으로 잘못 섞지 않게 하는 방식은 무엇인가요?

## 애노테이션 보존 정책

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** `@Retention`은 SOURCE/CLASS/RUNTIME 중 누가 정보를 볼 수 있는지, @Target은 적용 위치를 제한합니다.

**언제 사용하는가:** 컴파일 도구는 필요한 보존, reflection 소비자는 RUNTIME을 명시합니다.

**대안과 경계:** 기본 retention은 CLASS라 `.class`에는 남아도 `getAnnotation`에는 보이지 않을 수 있습니다.

**예시·실행 근거:** Audited RUNTIME은 조회되고 BytecodeOnly CLASS는 null 결과입니다.

**선수개념:** @Retention/Java reflection

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- @Inherited는 타입 계층 한정이며 method/field에 자동 전파되지 않습니다.

**초보자가 시작할 질문:**

- 클래스 파일에는 애노테이션이 있는데 `getAnnotation()`이 null인 이유는 무엇인가요?
- @Inherited가 @Override된 method annotation에도 적용되나요?

## annotation processor와 runtime reflection

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** processor는 javac 처리 라운드에서 type model을 보고 소스/리소스를 생성하고 reflection은 실행 중 멤버를 조회/호출합니다.

**언제 사용하는가:** MapStruct/Lombok 등 compile-time generated code면 processor; 실행 중 동적 탐색이면 reflection을 씁니다.

**대안과 경계:** 두 도구는 시점과 비용/권한 경계가 다릅니다.

**예시·실행 근거:** processor round, Filer, Messager와 generated mapper 설명.

**선수개념:** annotation metadata; javac compile phase

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- IDE/CI processor 설정이 다르면 결과 코드가 달라 보일 수 있습니다.

**초보자가 시작할 질문:**

- MapStruct 구현체가 앱 실행 전에 만들어지면 어떤 단계가 애노테이션을 읽나요?
- reflection으로 메서드를 문자열로 찾는 방식과 정적 호출은 무엇이 다른가요?

## Reflection·MethodHandle·VarHandle·Proxy

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Method는 메타데이터 기반 호출, MethodHandle은 명시적 MethodType 호출 경로, VarHandle은 변수의 volatile/CAS access mode, JDK Proxy는 인터페이스 호출을 handler로 보냅니다.

**언제 사용하는가:** 일반 경로는 정적 호출, 동적 요구가 있는 프레임워크 경계에서 적합한 도구를 씁니다.

**대안과 경계:** setAccessible은 JPMS를 무조건 우회하지 않으며 Method.invoke 예외는 target cause를 감쌉니다.

**예시·실행 근거:** Greeter JDK Proxy와 MethodHandle/VarHandle 예제 실행 결과.

**선수개념:** reflection; JMM; interface

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 실제 성능비교는 하지 않았고 호출 모드/메모리 의미는 JDK에 따릅니다.

**초보자가 시작할 질문:**

- Proxy handler에서 equals를 같은 proxy에 다시 위임하면 어떤 일이 생기나요?
- VarHandle.get과 getVolatile을 어떤 메모리 약속으로 구분하나요?
