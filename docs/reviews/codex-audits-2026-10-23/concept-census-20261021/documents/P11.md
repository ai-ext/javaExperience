## 빈 등록과 역할 stereotype

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** ApplicationContext가 Bean 정의를 읽어 객체를 만들고 의존성을 연결합니다. 직접 만든 클래스는 `@Component` 계열로, 외부 라이브러리 객체는 `@Configuration`의 `@Bean`으로 등록합니다.

**언제 사용하는가:** 클래스 스캔과 외부 객체 생성 경로를 구분할 때 사용합니다.

**대안과 경계:** `@Service`는 트랜잭션을 자동 선언하지 않고 `@Repository`도 DB 연결을 만들지는 않습니다.

**예시·실행 근거:** InMemoryGreetingRepository는 @Repository, JDK Clock은 @Bean으로 제공합니다.

**선수개념:** Spring Bean; component scan

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Spring 실행 예제는 문서에 미실행으로 표시됩니다.

**초보자가 시작할 질문:**

- JDK Clock에 @Component를 붙일 수 없다면 Spring에 어떻게 전달하나요?
- @Service를 붙였는데도 빈을 찾지 못하면 어떤 두 경계를 먼저 보나요?

## 생성자 주입과 같은 타입 후보 선택

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 필수 의존성은 생성자로 받고 final로 보관합니다. 같은 타입 후보는 @Primary/@Qualifier, 모두 필요하면 List/Map 주입으로 선택합니다.

**언제 사용하는가:** 필수 의존성 기본값은 생성자, 선택 의존성은 setter/ObjectProvider를 검토합니다.

**대안과 경계:** @Primary는 단일 주입 기본 후보를 고르지 컬렉션에서 다른 후보를 지우지 않습니다.

**예시·실행 근거:** GreetingService가 Repository·Properties·Clock을 `@RequiredArgsConstructor`로 받습니다.

**선수개념:** Java constructor; Lombok; interface

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Lombok processor와 IDE 설정 차이, 여러 구현체의 qualifier 선택은 실제 실행하지 않았습니다.

**초보자가 시작할 질문:**

- Repository 구현이 두 개 생기면 타입만으로 빈이 골라지지 않는 이유는 무엇인가요?
- 서비스에서 두 구현을 모두 써야 하면 생성자 인자를 어떻게 표현하나요?

**근거:**

## 패키지 검색과 설정 바인딩

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 기본 component scan은 @SpringBootApplication 클래스 패키지의 하위입니다. @Value는 단일 값, @ConfigurationProperties는 설정 묶음을 바인딩합니다.

**언제 사용하는가:** 메인 클래스를 상위 패키지에 두고, 관련 설정을 타입으로 모아 등록합니다.

**대안과 경계:** 형제 패키지는 기본 검색되지 않으며 설정 타입도 scan/enable 없이는 Bean이 아닐 수 있습니다.

**예시·실행 근거:** GreetingProperties record와 @ConfigurationPropertiesScan, `/actuator/beans` 예시.

**선수개념:** Java package; Spring config

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Actuator bean endpoint는 로컬 진단용이며 실제 런타임은 미실행입니다.

**초보자가 시작할 질문:**

- `com.example.catalog` 아래 `greeting`은 검색되는데 형제 패키지가 빠지는 이유는 무엇인가요?
- 속성 여러 개를 @Value로 각각 받지 않고 묶으면 어떤 이점이 있나요?

## Spring 컨텍스트 테스트와 순수 단위 테스트

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** @SpringBootTest는 Spring 배선·설정을 올리고, 직접 생성한 서비스 테스트는 container 없이 로직을 확인합니다.

**언제 사용하는가:** 테스트가 Spring 연결 자체를 검증하는지 로직만 보는지에 따라 선택합니다.

**대안과 경계:** 직접 `new`한 @Service는 Bean이 아니므로 proxy와 주입이 적용되지 않습니다.

**예시·실행 근거:** 고정 Clock/가짜 Repository를 넣는 단위 테스트와 MockitoBean 컨텍스트 테스트를 제시합니다.

**선수개념:** JUnit; Mockito; Bean lifecycle

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 예제 테스트 코드는 미실행입니다.

**초보자가 시작할 질문:**

- Clock이 고정된 순수 단위 테스트는 왜 Spring을 띄울 필요가 없나요?
- `new GreetingService`를 했는데 @Transactional이 자동 적용되지 않는 이유는 무엇인가요?

## Bean 관찰과 순환 의존 오류

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** getBeanDefinitionNames와 Actuator beans로 등록 상태를 볼 수 있고, 중복·누락·순환 의존은 서로 다른 원인입니다.

**언제 사용하는가:** 시작 실패 시 가장 안쪽 원인과 scan/profile/조건을 구분합니다.

**대안과 경계:** 등록된 Bean 목록은 실행 권한 제한이 필요하며 순환 참조를 lazy 주입으로 감추기보다 구조를 바로잡습니다.

**예시·실행 근거:** NoSuchBeanDefinitionException, NoUniqueBeanDefinitionException, BeanCurrentlyInCreationException 원인을 비교합니다.

**선수개념:** Exception cause; Spring scan

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 실제 컨테이너 오류 재현은 없습니다.

**초보자가 시작할 질문:**

- 빈이 없다는 오류와 같은 타입 Bean이 둘이라는 오류는 어떻게 다른가요?
- A가 B를 필요로 하고 B가 다시 A를 요구하면 왜 생성자 조립에서 멈출까요?
