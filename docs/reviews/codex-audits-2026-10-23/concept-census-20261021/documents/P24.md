## Broker address와 advertised.listeners

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** bootstrap 주소로 메타데이터를 받은 뒤, 브로커가 광고하는 실제 접속 주소를 다시 사용한다.

**언제 사용하는가:** Docker 컨테이너와 호스트에서 Kafka client가 실행될 때 각 환경에서 도달 가능한 주소를 확인한다.

**대안과 경계:** client가 bootstrap 주소에 접속할 수 있어도 브로커가 광고한 주소에 도달하지 못하면 통신이 실패한다.

**예시·실행 근거:** localhost:9092에서 broker metadata와 advertised address를 확인한다.

**선수개념:** Docker network; Kafka broker

**관련 표기·별칭:** bootstrap.servers; advertised.listeners

**보완·검증 필요 사항:**

- 주소를 반환받은 뒤 실제 client가 연결을 시도하는 단계까지는 원문 예제가 실행되지 않았다.

**초보자가 시작할 질문:**

- Docker에서 Kafka를 실행했는데 client가 왜 broker에 다시 접속하지 못할까?

## topic·partition·key·consumer group 관계

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Topic은 record를 모으는 논리 이름이고 partition은 저장·병렬 처리 및 순서 보장의 단위다. 같은 consumer group은 partition을 나눠 읽고 다른 group은 독립적으로 읽는다.

**언제 사용하는가:** 이벤트의 순서 보장 범위와 consumer 병렬성을 설계할 때 사용한다.

**대안과 경계:** 같은 key는 같은 partition으로 가므로 그 partition 안에서만 상대 순서를 기대할 수 있다. partition 하나는 전역 순서를 제공하지만 병렬성이 제한된다.

**예시·실행 근거:** orderId를 key로 보내고 CLI와 consumer의 partition 배정을 확인한다.

**선수개념:** 이벤트 record; partition과 consumer group

**관련 표기·별칭:** Topic·partition·key·consumer group; Topic·partition·key·group; topic; partition; key; group.id

**보완·검증 필요 사항:**

- partition 수를 늘릴 때 key와 partition의 매핑이 바뀌는 영향은 FAQ에서 간단히 언급할 뿐이다.

**초보자가 시작할 질문:**

- 주문 이벤트 순서를 어느 범위까지 보장할 수 있나?
- consumer를 늘리면 메시지는 어떻게 나뉘나?

## 전송·offset·ACK·멱등성

현재 판정: **미검증** / 우선순위: high

**정의와 실제 역할:** producer 전송 future의 완료, broker가 기록한 metadata, consumer 처리, offset commit은 서로 다른 단계다.

**언제 사용하는가:** 전송 성공의 의미와 재전달 때 중복 처리를 어떻게 할지 정할 때 사용한다.

**대안과 경계:** 새 consumer group의 earliest 시작과 이미 commit한 offset은 구분해야 한다. DB 반영 뒤 offset commit 전에 장애가 나면 메시지가 재전달될 수 있다.

**예시·실행 근거:** topic·partition·offset 결과와 같은 메시지 재전달 상황을 확인한다.

**선수개념:** 비동기 future; transaction

**관련 표기·별칭:** offset·send·ACK·idempotency; offset; SendResult; AckMode

**보완·검증 필요 사항:**

- Spring 코드와 예제는 실행되지 않았다.

**초보자가 시작할 질문:**

- producer가 보냈다는 응답을 받으면 DB 처리까지 끝난 건가?
- 처리 직후 장애가 나면 왜 같은 메시지를 다시 받나?

## 재시도·DLT

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 재시도 가능한 실패를 정해진 간격과 횟수만큼 처리한 뒤, 계속 실패하는 record를 DLT로 보낼 수 있다.

**언제 사용하는가:** 일시 장애와 반복 실패하는 독성 메시지를 구분해 처리할 때 사용한다.

**대안과 경계:** 무한 재시도는 partition의 다른 메시지를 막을 수 있다. DLT를 두더라도 조사·수정·재처리 절차가 필요하다.

**예시·실행 근거:** 실패 메시지를 정해진 횟수만큼 재시도한 뒤 DLT에서 확인한다.

**선수개념:** consumer group; offset

**관련 표기·별칭:** DefaultErrorHandler; DeadLetterPublishingRecoverer

**보완·검증 필요 사항:**

- 단일 노드 KRaft 설정은 고가용성이나 replication 동작을 입증하지 않는다.

**초보자가 시작할 질문:**

- 계속 실패하는 메시지가 다른 메시지까지 막으면 어떻게 분리하나?
