## 빌드 도구·Wrapper·플러그인

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Gradle/Maven은 의존성을 해결하고 컴파일·테스트·패키징을 수행합니다. Wrapper는 저장소가 지정한 빌드 도구 버전을 실행합니다.

**언제 사용하는가:** 저장소의 build.gradle.kts/pom.xml과 Wrapper부터 읽고 CI에서도 동일한 Wrapper를 씁니다.

**대안과 경계:** Wrapper는 JDK·저장소 자격증명까지 고정하지 않습니다. plugin은 task/lifecycle 기능을 추가합니다.

**예시·실행 근거:** `./gradlew bootRun`, `./mvnw package`; 명령 예제 미실행.

**선수개념:** 컴파일과 빌드 산출물; shell

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 예제 실행은 미실행으로 표시되어 있어 코드를 동작 근거로 단정할 수 없습니다.

**초보자가 시작할 질문:**

- 전역 Gradle 대신 `./gradlew`를 써야 팀과 CI에서 어떤 값이 같아지나요?
- Wrapper가 있어도 따로 맞춰야 하는 Java 실행 버전은 무엇인가요?

## 의존성 좌표·저장소·scope

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** GAV 좌표와 repository가 라이브러리를 찾고, implementation/runtimeOnly/testImplementation/annotationProcessor가 필요한 classpath를 정합니다.

**언제 사용하는가:** 코드에 import하면 compile classpath, DB driver처럼 실행만 필요하면 runtimeOnly를 씁니다.

**대안과 경계:** Maven scope와 Gradle configuration은 완전히 동일하지 않고 plugin repository와 library repository도 분리됩니다.

**예시·실행 근거:** Lombok compileOnly+annotationProcessor, JDBC runtimeOnly 예시.

**선수개념:** 컴파일·실행 구분; 전이 의존성

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 예제 실행은 미실행으로 표시되어 있어 코드를 동작 근거로 단정할 수 없습니다.

**초보자가 시작할 질문:**

- runtimeOnly의 JDBC driver를 Java 코드에서 import하면 어떤 단계에서 실패하나요?

## BOM과 의존성 충돌

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Spring Boot BOM은 관리 대상 라이브러리의 호환 버전을 제공하고 실제 선택은 의존성 그래프에서 결정됩니다.

**언제 사용하는가:** Boot 관리 버전을 우선 쓰고 NoSuchMethodError에서 dependencyInsight/tree로 요청 경로를 봅니다.

**대안과 경계:** Boot plugin만 적용했다고 모든 프로젝트에서 의존성 버전 관리가 자동으로 구성되는 것은 아닙니다.

**예시·실행 근거:** native `platform(spring-boot-dependencies)`와 Maven parent 비교.

**선수개념:** Java classpath와 빌드 task

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- NoSuchMethodError 원인 재현은 없음

**초보자가 시작할 질문:**

- Boot BOM 없이 Spring library 하나만 수동 올리면 어떤 종류의 충돌이 날 수 있나요?
- requested version과 selected version을 확인하는 명령은 무엇인가요?

## 빌드·테스트 오류 분류

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 네트워크/GAV, JDK/toolchain, 테스트 실패, IDE 모델 stale은 서로 다른 오류입니다.

**언제 사용하는가:** 가장 먼저 에러와 Wrapper version/JDK를 확인하고 한 원인씩 분리합니다.

**대안과 경계:** clean은 의존성 cache를 지우지 않고 test skip은 검사 통과가 아닙니다.

**예시·실행 근거:** `dependencyInsight`, `-version`, `--refresh-dependencies` 예시.

**선수개념:** Java classpath와 빌드 task

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 오류는 guide에서 미실행/가정으로 분류

**초보자가 시작할 질문:**

- `clean` 뒤에도 잘못된 artifact가 cache에서 보일 수 있는 이유는 무엇인가요?
- 테스트 실패를 일시 우회한 결과를 완료로 보고하면 안 되는 이유는 무엇인가요?

## Build failure triage

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 저장소 접속·좌표·JDK toolchain·테스트 실패·IDE 모델 stale은 서로 다른 빌드 장애 범주입니다.

**언제 사용하는가:** 오류가 발생한 단계의 로그를 보고 dependencyInsight, `java -version`, dependency refresh 등 해당 진단을 선택합니다.

**대안과 경계:** 의존성 해석 실패를 소스 컴파일 오류로, IDE 모델 문제를 명령행 빌드 실패로 뭉뚱그리지 않습니다.

**예시·실행 근거:** 잘못된 source release, Could not resolve, NoSuchMethodError를 각각 JDK·저장소·실행 의존성 문제의 사례로 둡니다.

**선수개념:** Compiler and classpath.

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- No observed failures recorded; remedy is textbook guidance.

**초보자가 시작할 질문:**

- Build failure triage이란 무엇이며 언제 필요한가?

## 실제 캡처 관찰

- 데스크톱 첫 화면은 build.gradle의 dependency 선택과 application.yml 런타임 값을 두 열로 나누어 보여 준다. 차이를 설명하는 문장과 번호형 slide 탐색이 함께 있다.
- 모바일 첫 화면은 같은 두 개념 카드를 세로로 쌓는다. 첫 카드는 읽을 수 있지만 두 번째 카드는 화면 아래로 이어진다. slide selector는 가로 방향이며 다음 tab 일부만 보여 전체 목록이 한 번에 드러나지 않는다.
- core 캡처에서는 두 번째 섹션이 초록색 focus 테두리와 함께 접혀 있고 긴 본문 섹션도 닫혀 있다. 섹션 제목과 짧은 요약만 보인다.

**관찰 범위:** 캡처된 concept slide는 설명 장면이며 실제 dependency resolution/configuration 실행이 아니다. 내비게이션 클릭이나 다음 slide 동작은 시험하지 않았다.
