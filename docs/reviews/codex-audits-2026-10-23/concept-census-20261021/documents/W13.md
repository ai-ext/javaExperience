## 브라우저 신뢰경계와 서버 검증·인가

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** 브라우저 코드·DOM·저장값·요청은 사용자가 변조할 수 있다. 서버는 인증된 주체를 바탕으로 권한/소유권과 현재 업무 규칙을 판정하고, 재고 등 동시성 민감 상태는 원자적 DB 조건으로 바꾼다.

**언제 사용하는가:** 금액·권한·소유권·재고·상태 변화 및 민감정보가 관련된 모든 API에서 서버 검증을 강제한다. 클라이언트는 빠른 UX 안내를 중복 제공한다.

**대안과 경계:** HTML required/disabled는 UX. CORS는 브라우저 응답 공개 정책이지 인증/방화벽이 아니다. ID 난수화는 권한 검사 대체가 아니다. SSR도 API 권한을 대신하지 않는다.

**예시·실행 근거:** 요청에 productId/quantity만 받고 principal에서 buyer를 얻어 server catalog 가격으로 total 계산; 재고는 조건부 UPDATE와 주문 저장을 묶는다.

**선수개념:** HTTP/브라우저 실행 모델; 인증/인가; 데이터 무결성; 동시성/트랜잭션

**관련 표기·별칭:** client trust boundary; IDOR; TOCTOU; business validation

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 코드 예제는 미실행이고 애플리케이션 security config/DB adapter 구현이 생략됐다.
- 초안의 CORS 예제는 credential 허용시 구체 origin을 쓰지만 실제 Spring Security filter ordering은 검증 필요.
- 재고 조회 후 저장의 TOCTOU는 조건부 update/locking으로 별도 확인해야 한다.

## CSR·SSR·BFF·세션과 렌더링/토큰 경계

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** CSR/SSR은 HTML 렌더 위치 선택이다. BFF는 브라우저와 백엔드 사이 토큰/API 중개, 세션 쿠키는 서버 측 인증 상태를 참조하는 방식이다. 렌더링 방식이 authorization boundary를 바꾸지 않는다.

**언제 사용하는가:** 첫 HTML/SEO·상호작용성·토큰 보관·API 조합이 실제 요구일 때 구성요소를 선택한다.

**대안과 경계:** CSR+API direct는 서버 hop이 적으나 browser token 다룸. BFF는 token을 JS에서 가릴 수 있지만 CSRF·운영 부담을 더한다. HttpOnly 쿠키는 읽기를 제한하나 XSS가 사용자 대신 요청하는 걸 막지 못한다.

**예시·실행 근거:** 공개 상품은 SSR/정적 캐시, 개인 주문은 API; BFF가 세션 쿠키를 받고 API 권한은 대상 서비스도 확인.

**선수개념:** same-origin/CORS; cookie attributes; OAuth/session; cache semantics

**관련 표기·별칭:** CSR; SSR; BFF; HttpOnly; SameSite; CSRF

**판정 이유:** 개념 정의와 선택 기준은 다루지만 실습/실행이나 학습 과제의 검증 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- 외부 브라우저/HTTP 동작 예는 문서 작성자의 실제 조작 evidence가 없고 감사자는 재현하지 않았다.
- BFF 실제 선택의 국내 보편성 통계는 제공되지 않았다.
- 쿠키 기반 인증에는 CSRF threat model 및 캐시 격리 필요.

**초보자가 시작할 질문:**

- SSR이면 API 권한 검사를 줄여도 되나?
- HttpOnly는 XSS를 막나?
- BFF는 SPA에 항상 필요한가?

**발견 문제**

- 외부 MDN/OWASP/Auth0 링크는 문서에 제시되어 있으나 각 문헌 재검토/실제 브라우저 재현은 본 건에서 수행하지 않음.
- CORS와 인증을 혼동하지 않도록 핵심 표/흐름을 처음 화면에서 보이는지 캡처 검사 필요.

## 시각 구조와 보완 장면

**기존 표현**

- 공개 기준 HTML 정적 구조: 접기 영역 26개, 코드/pre 블록 4개, 표 1개, Mermaid 표현 1개. 이는 렌더 결과와 조작 검증이 아니라 구조 목록이다.

**정적 구조의 한계**

- 코드 블록과 흐름도는 설명을 돕지만 실제 DB·HTTP·스레드 동작을 증명하지 않는다.
- 화면 첫 노출과 모바일 가독성은 아래 실제 캡처 판독에서 별도로 기록했다.

## 실제 캡처 관찰

- desktop/mobile에서 첫 화면에는 9개 목차와 trust-boundary 요약만 노출되며 인증·인가·CORS·SSR/BFF의 예시는 접혀 있다.
- 모바일 summary가 여러 줄로 읽히지만 대표 판단 기준/예시가 화면에 없어 구체 이해에는 탐색이 필요하다.
- core는 원리 section만 열린 화면; 안쪽 코드/하위 접힘까지 확인한 증거가 아니다.
- core 캡처는 기존 DOM의 짧은 답/원리 외부 details anchor로 이동한 결과일 수 있어, 모든 nested details·조작 흐름·응답 동작까지 검증했다는 뜻은 아니다.
