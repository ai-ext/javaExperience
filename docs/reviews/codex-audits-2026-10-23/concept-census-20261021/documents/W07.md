## SLF4J facade vs logging provider

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** SLF4J facade와 logging provider

**언제 사용하는가:** SLF4J는 호출 API, Logback/Log4j2 등 provider가 필터·형식·appender 출력을 수행한다.

**대안과 경계:** Spring Boot application code는 facade 사용, provider 변경은 운영/성능 이유가 명확할 때 한다.

**예시·실행 근거:** println은 구조/레벨이 없는 출력이다. provider conflict/missing은 dependency graph에 좌우된다. 추가 예: SLF4J LoggerFactory에서 log.info/error; Boot logging level 설정.

**선수개념:** logging facade; provider; appender

**관련 표기·별칭:** SLF4J; Logback; Log4j2; JUL; provider/binding

**판정 이유:** 개념 정의와 적용 기준은 확인되나 실제 실행/학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- logging API vs provider
- dependency graph

**초보자가 시작할 질문:**

- Boot4 기본 provider 의존성은 실제 Gradle graph로 확인하지 않았다.

## Logger levels and lazy parameter evaluation

현재 판정: **부분** / 우선순위: P1

**정의와 실제 역할:** 로그 레벨과 비용 지연 평가

**언제 사용하는가:** 레벨은 사건 심각도/운영 필요 정보를 고른다. 파라미터 placeholder는 문자열 구성량을 줄이나 인자 계산은 호출 전에 일어날 수 있다.

**대안과 경계:** INFO/WARN은 운영 요약, DEBUG/TRACE는 조사 때 제한적으로 켜고 비용 큰 인자 계산은 guard/lazy supplier를 쓴다.

**예시·실행 근거:** 레벨 비활성화가 임의의 메서드 계산을 항상 막는 것은 아니다. 동적 level 변경과 수집기 필터도 별도다. 추가 예: 비싼 serialize()는 isDebugEnabled 또는 logger supplier 형태로 조건부 실행.

**선수개념:** log levels; lazy evaluation

**관련 표기·별칭:** ERROR/WARN/INFO/DEBUG/TRACE; placeholder; guarded logging

**판정 이유:** 개념 정의와 적용 기준은 확인되나 실제 실행/학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- SLF4J parameterization
- lazy computation

**초보자가 시작할 질문:**

- 성능 code example 실행/벤치마크 없음.

## Exception logging, MDC context and structured logs

현재 판정: **부분** / 우선순위: P0

**정의와 실제 역할:** 예외·MDC·구조화 로그

**언제 사용하는가:** 예외는 마지막 인자로 전달해야 stack trace가 보존된다. MDC는 요청별 context 값을 로깅 이벤트에 붙인다.

**대안과 경계:** 기술 실패를 한 경계에서 stack trace와 correlation ID로 남기고 비동기/요청 종료 시 context를 정리한다.

**예시·실행 근거:** 예외를 여러 계층에서 중복 로깅하면 같은 사건이 반복되고, MDC ThreadLocal은 다른 worker로 자동 전파되지 않는다. JSON format은 수집만 구조화하고 비밀을 자동 제거하지 않는다. 추가 예: catch 후 의미를 추가하거나 재던질 때 한 번 기록; requestId를 MDC에 넣고 finally에서 제거.

**선수개념:** exception stack; MDC; structured log privacy

**관련 표기·별칭:** stack trace; MDC; requestId; JSON logs

**판정 이유:** 개념 정의와 적용 기준은 확인되나 실제 실행/학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- exception propagation
- thread local
- JSON logs

**초보자가 시작할 질문:**

- MDC async propagation 및 redaction 설정을 테스트하지 않았다.

## Synchronous vs asynchronous logging choice

현재 판정: **부분** / 우선순위: P2

**정의와 실제 역할:** 동기·비동기 로깅 선택

**언제 사용하는가:** 동기 appender는 요청 스레드가 출력 완료를 기다릴 수 있고 async appender는 queue/worker로 출력을 분리한다.

**대안과 경계:** 로그 I/O가 실제 요청 병목일 때 비동기 출력을 검토하되 유실/queue overflow/종료 flush 요구를 정의한다.

**예시·실행 근거:** 비동기는 출력 지연을 겹칠 수 있지만 장애 시 데이터 유실 가능성과 순서/문맥 비용이 있다. 추가 예: 요청 latency와 appender queue를 측정하고 필수 감사 이벤트는 별도 저장 경로로 분리한다.

**선수개념:** async appender; queue failure policy

**관련 표기·별칭:** AsyncAppender; async logger; queue saturation

**판정 이유:** 개념 정의와 적용 기준은 확인되나 실제 실행/학습자 수행 근거가 부족해 부분 판정.

**보완·검증 필요 사항:**

- logging appender
- queue backpressure

**초보자가 시작할 질문:**

- 실제 Logback async config/성능은 미실행.
