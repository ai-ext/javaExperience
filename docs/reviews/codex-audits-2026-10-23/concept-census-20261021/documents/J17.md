## Feature release·LTS·vendor support

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** Java feature release는 6개월 주기로 나오며, LTS 표시는 각 공급자의 장기 지원 정책입니다. 지원 종료일과 패치 제공 조건은 배포판마다 다릅니다.

**언제 사용하는가:** 목표 JDK를 고를 때 필요한 기능, 공급자의 보안 패치 기간, 애플리케이션 호환성, 팀의 업그레이드 여력을 함께 비교합니다.

**대안과 경계:** LTS는 별도의 언어 명세 종류가 아닙니다. Oracle·Corretto·Temurin 등은 지원 기한과 SLA가 서로 다를 수 있습니다.

**예시·실행 근거:** 2026-10-21 기준 주요 배포판의 릴리스 및 지원 일정을 문서에서 비교합니다.

**선수개념:** JDK distribution; support contract

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Support calendars drift and must be refreshed on next release decision.

**초보자가 시작할 질문:**

## GA·Preview·Incubator lifecycle

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** GA는 정식 릴리스 기능이며 Preview와 Incubator는 확정 계약이 아닙니다. Preview 기능은 보통 실행·컴파일에 버전별 flag가 필요합니다.

**언제 사용하는가:** 제품의 안정 API에는 GA 기능을 우선 사용합니다. Preview를 채택한다면 업그레이드와 flag 정책을 함께 정합니다.

**대안과 경계:** 특정 버전의 Preview flag와 동작이 다음 JDK에서도 유지된다고 가정할 수 없습니다. Incubator도 정식 API와 호환성 약속이 다릅니다.

**예시·실행 근거:** 버전별 API 예제와 JEP 상태표에서 기능의 출시 단계를 대조합니다.

**선수개념:** JEP/versioning

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Some latest JEP refs are secondary bibliography, and support can drift.

**초보자가 시작할 질문:**

- Preview를 쓰면 왜 컴파일 JDK와 실행 JDK를 모두 같은 feature release에 맞춰야 하나요?
- Preview를 final API처럼 public library signature에 넣는 위험은?

## Source/API/classfile/runtime compatibility

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** javac --release는 언어 수준·공개 API·classfile 대상을 함께 제한하지만, reflection·JNI·ServiceLoader·실행환경 호환성을 증명하지는 않습니다.

**언제 사용하는가:** 목표 버전으로 컴파일한 뒤 의존성·테스트를 대상 런타임 컨테이너에서 실행해 확인합니다. jdeps와 jdeprscan은 추가 진단에 씁니다.

**대안과 경계:** 오래된 JVM이 이전 classfile을 읽을 수 있다는 사실만으로 새 API, 라이브러리, 환경 의존성까지 호환된다고 볼 수 없습니다.

**예시·실행 근거:** `javac --release 21`, `jdeps`, `jdeprscan`의 사용 예를 제시합니다.

**선수개념:** compiler toolchain; class file version

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Scans miss dynamic class names/config.

**초보자가 시작할 질문:**

- `-target 21`만 설정해도 Java25-only API 호출이 없는 것을 보장하는 이유는 왜 부족한가요?
- jdeps가 0건이어도 reflection 문자열 때문에 깨질 수 있는 사례는?

## Java vendor and migration workflow

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** JDK 배포판 선택에는 바이너리·라이선스·패치 전달·지원 계약이 포함됩니다. 이관에는 네이티브 라이브러리와 에이전트의 호환성도 걸립니다.

**언제 사용하는가:** 지원 기간이 명확한 배포판 하나를 정하고, 스테이징과 카나리에서 관측한 뒤 확대합니다.

**대안과 경계:** 다운로드가 무료여도 보안 패치나 지원 SLA가 무료라는 뜻은 아닙니다. 컴파일 성공만으로 운영 호환성이 입증되지 않습니다.

**예시·실행 근거:** 목표 배포판 선정부터 스테이징·카나리까지 순서대로 확인할 절차를 기록합니다.

**선수개념:** dependency management; CI/CD

**언제 사용하는가:** 운영과 비슷한 이미지에서 테스트한 후 관측·롤백 기준을 두고 단계적으로 전환합니다.

**대안과 경계:** 컴파일은 소스와 API 일부의 적합성만 확인합니다. 운영에서의 메모리·성능·에이전트·환경 차이는 별도 검증이 필요합니다.

**예시·실행 근거:** 버전 목표 설정, 의존성 조사, 테스트, 스테이징, 카나리, 롤백을 포함한 이관 순서를 제시합니다.
