## 소스·중간/최종 연산·지연

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** Stream은 원소를 저장하지 않는 1회성 계산 파이프라인이며 terminal operation까지 source를 읽지 않습니다.

**언제 사용하는가:** 컬렉션 변환/집계를 순차 stream으로 먼저 기술하고 필요할 때만 단락 연산을 씁니다.

**대안과 경계:** 중간 map/filter 부수 효과가 결과에 필요하면 구현이 단계를 생략할 수 있어 보장되지 않습니다.

**예시·실행 근거:** LazyShortCircuitDemo는 두 짝수를 위해 source 4개만 생성합니다.

**선수개념:** Iterable/Collection; lambda

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- peek은 로직 실행 계약이 아니라 진단 보조입니다.

**초보자가 시작할 질문:**

- `map(...);`까지만 적고 결과를 사용하지 않으면 왜 source 원소를 안 읽을 수 있나요?
- count() 결과가 이미 소스 크기로 정해지면 map lambda가 실행되지 않을 수 있는 이유는?

## map/flatMap과 collector 선택

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** map은 1→1, flatMap은 1→0..n을 평탄화합니다. groupingBy, partitioningBy, toMap은 결과 구조와 중복 키 정책이 다릅니다.

**언제 사용하는가:** 그룹 집계는 downstream groupingBy, 두 분할은 partitioningBy, key→value는 merge policy 포함 toMap을 씁니다.

**대안과 경계:** toMap duplicate key 기본값은 예외이고 flatMap은 하위 Stream을 잇습니다.

**예시·실행 근거:** CollectorCompositionDemo가 카테고리/SKU별 합계와 flat list를 출력합니다.

**선수개념:** Map/List; Collector

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 순서가 중요하면 collector map/result order를 명시해야 합니다.

**초보자가 시작할 질문:**

- 같은 SKU가 두 행에 나타나면 `toMap`은 어떤 규칙을 써야 하나요?
- `List<List<String>>`를 한 줄 목록으로 바꾸려면 map과 flatMap 중 무엇인가요?

## reduce/collect/primitive stream

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** reduce는 결합 가능한 값 누적, collect는 supplier/accumulator/combiner가 있는 결과 컨테이너 수집입니다. Int/Long/DoubleStream은 기본형 값 흐름입니다.

**언제 사용하는가:** 가변 컬렉션은 collect; 숫자 집계는 mapToInt/sum 등 원시 스트림을 우선 검토합니다.

**대안과 경계:** 병렬 reduce는 associativity 필요; 공유 ArrayList를 reduce에서 mutate하지 않습니다.

**예시·실행 근거:** 기본형 API와 mutable reduction 설명.

**선수개념:** monoid/identity notion; generics

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- float 합계 순서 결과는 병렬 결합 순서에 달라질 수 있습니다.

**초보자가 시작할 질문:**

- 병렬 처리 중 부분 결과 List를 하나로 합치려면 reduce 대신 어떤 terminal operation을 쓰나요?
- 0.1+0.2 같은 실수 합계가 병렬 순서에 영향을 받는 이유는?

## parallel stream 분할과 blocking

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** Spliterator가 입력을 나누고 worker 결과를 combine합니다. 일반 HotSpot Stream은 공용 ForkJoinPool을 활용할 수 있습니다.

**언제 사용하는가:** 큰 CPU 작업이고 source가 잘 분할되며 결합이 순서에 무관할 때 workload로 측정합니다.

**대안과 경계:** blocking JDBC/HTTP를 공용 풀에 넣으면 worker를 고갈시킬 수 있고 ThreadLocal/transaction 전파를 가정하면 안 됩니다.

**예시·실행 근거:** 문서에 분할→처리→combine 그림과 실행 모델 선택표.

**선수개념:** J11 Executor; J12 virtual thread

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 벤치마크를 실행한 결과는 없습니다.

**초보자가 시작할 질문:**

- `.parallel()` 추가가 DB 연결수나 CPU core 수를 늘려 주지 않는 이유는 무엇인가요?
- CPU가 낮은데 요청이 느리면 CPU flame graph 외에 어떤 대기 지표를 봐야 하나요?

## Gatherer와 Collector

현재 판정: **부분** / 우선순위: critical

**정의와 실제 역할:** Gatherer는 Java24+ 사용자 정의 intermediate transformation, Collector는 terminal accumulation입니다.

**언제 사용하는가:** 윈도/scan/연속 중복 제거가 built-in 연산으로 어색할 때 Gatherer를 검토합니다.

**대안과 경계:** parallel combiner가 순차와 동일 의미를 보장해야 하며, sliding window는 메모리를 씁니다.

**예시·실행 근거:** windowFixed 예시는 예상 출력으로 명시되고 JDK21 host에서는 미실행입니다.

**선수개념:** Stream pipeline; Java24 API version

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- API는 Java24+; Java21 실행 증거는 없습니다.

**초보자가 시작할 질문:**

- `gather()`는 pipeline에서 값을 바꾸는 중간 단계인가 결과를 모으는 최종 단계인가요?
- 사용자 Gatherer를 parallel로 만들 때 어떤 결합 법칙이 필요할까요?
