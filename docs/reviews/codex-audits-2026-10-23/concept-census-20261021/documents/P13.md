## 작업 디렉터리·index·HEAD

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 작업 변경은 index에 stage되고 commit은 객체로 저장되며 HEAD/branch가 현재 지점을 가리킵니다.

**언제 사용하는가:** status와 diff/diff --cached로 서로 다른 변경 층을 확인합니다.

**대안과 경계:** `git diff`는 worktree-index, `--cached`는 index-HEAD 차이를 보여줍니다.

**예시·실행 근거:** git add -p 뒤 staged diff를 검토하는 절차.

**선수개념:** Git commit/ref

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- Spring 프로젝트가 아니라 임시 Git 레포 실습입니다.

**초보자가 시작할 질문:**

- 파일을 수정했는데 `git diff --cached`가 비어 있다면 변경은 어느 단계에 있나요?
- add -p를 쓰면 한 파일에서 어떤 변경을 나눠 올릴 수 있나요?

## 브랜치·원격·fetch/pull

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 브랜치는 commit을 가리키는 이름입니다. fetch는 원격 추적 ref만 갱신하고 pull은 fetch 뒤 현재 브랜치 통합까지 합니다.

**언제 사용하는가:** 기반 상태를 확인한 뒤 feature branch를 만들고 fetch 후 차이를 검토합니다.

**대안과 경계:** detached HEAD는 branch 이름이 없고 pull의 통합 방식은 설정에 따라 다를 수 있습니다.

**예시·실행 근거:** switch -c, fetch, log HEAD..origin/main, ff-only 예시.

**선수개념:** Git ref model

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 예제 밖의 프레임워크 설정이나 운영 환경 차이는 별도 실행으로 확인해야 합니다.

**초보자가 시작할 질문:**

- fetch 후 작업 파일이 즉시 바뀌지 않는 이유는 무엇인가요?
- detached HEAD에서 만든 commit을 잃지 않으려면 무엇을 해야 하나요?

## 충돌·restore/reset/revert/stash

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 충돌은 최종 내용 선택이 필요한 상태입니다. restore는 파일/index, reset은 ref/index/worktree, revert는 역변경 commit, stash는 임시 보관입니다.

**언제 사용하는가:** 공유 commit 수정은 보통 revert, 비공유 개인 작업은 검증 후 reset을 선택합니다.

**대안과 경계:** reset --hard는 tracked 변경을 버릴 수 있고 stash 기본은 untracked 제외; reflog는 미커밋 변경을 복구하지 못합니다.

**예시·실행 근거:** 임시 repo에서 충돌 마커 제거·stash -u·soft reset·reflog 확인 출력.

**선수개념:** Git status/diff

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 예제 밖의 프레임워크 설정이나 운영 환경 차이는 별도 실행으로 확인해야 합니다.

**초보자가 시작할 질문:**

- 공유된 commit을 reset으로 지우면 동료 clone에서 어떤 문제가 생길까요?
- 새 untracked 파일까지 임시 보관하려면 stash 명령에 무엇을 붙이나요?

## merge/rebase/cherry-pick과 이력

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** merge는 두 parent를 보존하고 rebase는 커밋을 재생성해 id를 바꾸며 cherry-pick은 특정 commit을 적용합니다.

**언제 사용하는가:** 개인 branch 정리와 공유 branch의 통합 방식을 팀 규칙에 맞춥니다.

**대안과 경계:** 공유 branch 재작성 뒤 force push는 다른 사람이 본 기반을 흔들 수 있습니다.

**예시·실행 근거:** rebase --continue/abort와 push --force-with-lease 예시.

**선수개념:** commit graph; remote tracking

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 예제 밖의 프레임워크 설정이나 운영 환경 차이는 별도 실행으로 확인해야 합니다.

**초보자가 시작할 질문:**

- rebase 뒤 commit id가 달라지는 이유는 무엇인가요?
- force-with-lease가 일반 force보다 무엇을 확인하나요?

## 비밀값과 ignore

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** gitignore는 아직 추적하지 않은 경로를 건너뛰며 과거 commit을 지우지 않습니다.

**언제 사용하는가:** 토큰은 올리기 전에 분리하고 이미 노출되면 credential을 먼저 교체합니다.

**대안과 경계:** git rm --cached는 이후 추적만 멈추며 히스토리 purge와 키 회수는 별도입니다.

**예시·실행 근거:** .env ignore, local config stop tracking 안내.

**선수개념:** Git index/history

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 예제 밖의 프레임워크 설정이나 운영 환경 차이는 별도 실행으로 확인해야 합니다.

**초보자가 시작할 질문:**

- .gitignore에 추가했는데 과거 commit의 비밀번호가 남는 이유는 무엇인가요?
- 원격에 API key가 올라간 뒤 가장 먼저 해야 할 조치는 무엇인가요?

## 실제 캡처 관찰

- 데스크톱 개요는 worktree/index/repository 차이와 공유 commit 되돌리기를 분명히 설명하고 섹션을 접힌 행으로 나열한다.
- 모바일 제목과 요약은 가로 넘침 없이 줄바꿈된다. 명령 예시는 캡처된 첫 화면 아래에 있다.
- core 캡처에는 HEAD, branch, fetch/pull, conflict, revert, stash, merge/rebase, ignore의 Git 소주제 8개가 접힌 상태로 보인다. 실제 graph/conflict 전이는 없다.

**관찰 범위:** 브라우저 캡처에서 Git 명령을 실행하지 않았다. 보이는 화면은 탐색 목록이며 실제 repository 실습이 아니다.
