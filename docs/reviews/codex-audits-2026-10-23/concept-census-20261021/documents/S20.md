## Discovery·LoadBalancer·Gateway

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Discovery는 서비스 이름의 인스턴스 후보를 찾고 LoadBalancer는 후보 중 요청 대상을 고른다. Gateway는 외부 진입 라우팅·정책을 맡는다.

**언제 사용하는가:** Kubernetes DNS로 충분하면 기본 Service를 쓰고 다중 플랫폼 또는 공통 외부 정책이 필요할 때 Cloud 기능을 보탠다.

**대안과 경계:** Gateway는 내부 권한 검증을 대신하지 않으며 Discovery 결과도 죽은 인스턴스를 잠시 포함할 수 있다.

**예시·실행 근거:** 요청 경로 그림과 Kubernetes Service YAML이 있으나 실행 미검증이다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- Discovery가 살아 있는 Pod 목록을 반환했는데 선택한 Pod가 응답하지 않는다면 추가로 필요한 호출 경계는 무엇인가요?
- Kubernetes Service DNS가 이미 있는데 Cloud Discovery를 더해야 할 요구는 무엇인가요?

## Config Server·ConfigMap

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Config Server는 중앙 설정 배포, ConfigMap은 Kubernetes Pod에 비기밀 설정을 공급한다.

**언제 사용하는가:** Git 승인·여러 런타임 중앙 설정이 필요하면 Config Server, Kubernetes 내 기본 설정은 ConfigMap부터 고려한다.

**대안과 경계:** 환경 변수 변경은 실행 중 프로세스에 자동 반영되지 않으며 ConfigMap은 secret 저장소가 아니다.

**예시·실행 근거:** Config 공급 흐름과 ConfigMap volume 설정을 제공한다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

## CircuitBreaker·Retry·timeout

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** CircuitBreaker는 결과 창의 실패 기준 초과 후 호출을 거절하고 retry는 다시 실행하며 timeout은 호출 지속 시간을 제한한다.

**언제 사용하는가:** 명시적 deadline을 우선 정하고 멱등 호출의 제한 재시도를 한 계층에 두며, 지속 실패 차단과 resource 보호를 추가한다.

**대안과 경계:** Breaker는 이미 진행 중인 요청을 취소하지 않는다. 여러 계층 retry는 호출 수가 곱으로 증가할 수 있다.

**예시·실행 근거:** breaker 상태도·설정 예제가 있지만 RestClient 연동은 미실행이며 호환 조합 미확인이다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- 재고 API가 느려졌는데 breaker가 OPEN이어도 기존 호출이 계속 대기한다면 어떤 제한이 빠졌나요?
- 주문 코드와 HTTP client가 각각 3회 retry하면 원격 호출이 몇 배까지 늘 수 있나요?

## Bulkhead·RateLimiter·멱등성

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Bulkhead는 동시 진행 작업을 제한하고 RateLimiter는 시간당 허용 호출 수를 제한하며 멱등성은 반복 요청의 효과를 같게 한다.

**언제 사용하는가:** 동시 연결 격리, 외부 quota, 재전송 안전이라는 서로 다른 문제에 각각 적용한다.

**대안과 경계:** HTTP 메서드명만으로 멱등성을 보장할 수 없고 두 제한기 종류도 서로 대체되지 않는다.

**예시·실행 근거:** Resilience4j 비교표와 주문/결제 판단을 제공한다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- 외부 API quota를 초과하는 문제와 느린 API 동시 연결이 쌓이는 문제는 어떤 서로 다른 제한 장치가 맡나요?
