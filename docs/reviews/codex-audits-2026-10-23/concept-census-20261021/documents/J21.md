## SOLID 원칙과 변경 이유

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** SRP/OCP/LSP/ISP/DIP는 책임 분리, 확장 경계, 치환 가능성, 작은 계약, 의존 방향을 확인하는 설계 기준입니다.

**언제 사용하는가:** 변경 요구가 어떤 파일/정책에 전파되는지 설명할 때 사용합니다.

**대안과 경계:** SOLID는 인터페이스나 패턴을 무조건 늘리는 규칙이 아닙니다.

**예시·실행 근거:** OrderService가 Store/Notifier 추상화에 의존하는 코드 예시.

**선수개념:** Java class/interface; change reason

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 자동 architecture test는 없습니다.

**초보자가 시작할 질문:**

- 메일 형식만 바뀌는데 SQL 테스트까지 바뀐다면 어느 책임이 한데 섞였을까요?
- 하위 타입이 부모 계약의 입력을 더 제한하면 치환 가능한가요?

## Strategy·Factory·Template/Callback

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Strategy는 교체 알고리즘, Factory는 생성 경계, Template/Callback은 공통 흐름과 변하는 작업을 나눕니다.

**언제 사용하는가:** 실제 반복되는 변동 정책 또는 자원 boilerplate가 확인될 때 패턴을 둡니다.

**대안과 경계:** 한 번의 두 분기에 Strategy 클래스를 여러 개 만들면 탐색 비용이 더 클 수 있습니다.

**예시·실행 근거:** Payment Strategy map, JdbcTemplate RowMapper 설명. Spring 예제 일부 미실행.

**선수개념:** interface; Spring bean wiring

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 패턴 용어 소개가 실행 evidence를 대신하지는 않습니다.

**초보자가 시작할 질문:**

- 새 결제 방식마다 기존 if를 수정하지 않으려면 어떤 계약을 둘 수 있을까요?
- RowMapper만 넘기고 Connection/ResultSet close를 Template에 맡기면 반복 코드 무엇이 줄까요?

## Proxy·Decorator·Adapter·Observer·Facade·Composite

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Proxy는 호출 앞뒤를 감싸고, Decorator는 같은 계약을 확장하고, Adapter는 인터페이스를 연결하며, Observer는 알림, Facade는 하위 단계 조정, Composite는 부분/전체 동일 처리를 뜻합니다.

**언제 사용하는가:** 각 패턴의 실제 변화 역할이 반복되는지 확인한 뒤 선택합니다.

**대안과 경계:** `@Transactional`은 프록시 경계를 지나야 하고 기본 Spring event는 listener 시간이 요청에 포함될 수 있습니다.

**예시·실행 근거:** InputStream decorator, MVC HandlerAdapter와 event references.

**선수개념:** interface; AOP proxy

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 런타임 proxy 내부는 S02, lifecycle/event는 S01에서 더 확인 필요.

**초보자가 시작할 질문:**

- this.save() 호출이 외부 프록시 advice를 건너뛰는 이유는 무엇인가요?
- Composite에서 leaf와 group 연산 의미가 다르면 같은 interface로 억지 통합해야 하나요?

## Spring singleton scope와 무상태 빈

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Spring singleton은 컨테이너별 같은 Bean instance를 공유합니다. JVM 전체 단 하나를 뜻하지 않으며 스레드 안전성을 보장하지 않습니다.

**언제 사용하는가:** 일반 service에 요청별 mutable field를 저장하지 않습니다.

**대안과 경계:** 다중 ApplicationContext 또는 여러 JVM에서는 별도 instance가 생길 수 있습니다.

**예시·실행 근거:** Q&A와 상태 누출 경고.

**선수개념:** Bean scope; thread concurrency

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 다중 context 실행 demo는 없습니다.

**초보자가 시작할 질문:**

- 두 Spring 컨테이너에 등록된 singleton Bean이 같은 객체를 공유할까요?
- 요청 id를 singleton service 필드에 두면 동시 요청에서 어떤 문제가 생길까요?

## 과잉/부족 추상화의 선택

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 작은 인터페이스·constructor injection·composition/lambda를 시작점으로 하고 변화 지점이 확인될 때 pattern을 추가합니다.

**언제 사용하는가:** 두 번째 구현/변경 요구와 책임 분리가 실제로 나타난 뒤 추상화합니다.

**대안과 경계:** 패턴 없는 코드는 미숙, 패턴이 많은 코드는 우수라는 기준은 성립하지 않습니다.

**예시·실행 근거:** SolidPatternDemo 실행 출력은 JDK21; Spring sections은 미실행입니다.

**선수개념:** SOLID; test boundary

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 서비스 도메인별 acceptance test가 아닌 개념 example.

**초보자가 시작할 질문:**

- 두 번째 구현이 아직 없는데 인터페이스·factory·strategy를 모두 만들면 어떤 비용이 생기나요?
- God class를 나눌 때 우선 어느 변경 이유를 분리해야 하나요?
