## process·thread·스케줄링

현재 판정: **충분** / 우선순위: high

**정의와 실제 역할:** process는 독립 주소 공간, thread는 process 내부 실행 흐름이다. platform/virtual thread, context switch, concurrency와 parallelism은 다른 개념이다.

**언제 사용하는가:** 동시 요청·thread 대기·process 격리를 이해할 때 사용한다.

**대안과 경계:** 동시성은 여러 작업이 겹쳐 진행되는 구조고 병렬성은 여러 CPU에서 실제 동시에 실행되는 것이다. virtual thread는 OS thread와 같은 개념이 아니다.

**예시·실행 근거:** 요청 작업이 thread를 대기/전환하는 모습과 virtual/platform thread를 비교한다.

**선수개념:** CPU; process와 thread

**관련 표기·별칭:** Process/thread/scheduling

**보완·검증 필요 사항:**

- 원문은 개념 설명 중심이며 JVM/OS 동작을 실제 trace하지 않았다.

## 메모리·page·RSS·OOM

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** virtual memory는 process 주소 공간이고 page fault는 메모리 page 접근 사건이다. JVM heap, process RSS와 cgroup memory limit은 서로 다르다.

**언제 사용하는가:** heap은 충분한데 container가 OOM kill되거나 page fault가 늘 때 원인을 나눠 볼 때 사용한다.

**대안과 경계:** heap 사용량이 낮아도 native memory와 다른 process 영역 때문에 RSS/cgroup 한도를 넘을 수 있다. OOM killer는 Java exception과 다를 수 있다.

**예시·실행 근거:** heap, RSS와 cgroup limit 지표를 같은 시간축에서 비교한다.

**선수개념:** JVM heap; OS page; container limit

**관련 표기·별칭:** Memory/page/RSS/OOM

**보완·검증 필요 사항:**

- 원문 설명은 있으나 실제 OOM/cgroup 지표를 실행해 관찰하지 않았다.

**초보자가 시작할 질문:**

- heap이 남아 있는데 container가 종료되는 이유는 무엇인가?

## 파일 descriptor·I/O·event loop

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** file descriptor는 process가 연 socket/file 같은 자원을 가리킨다. epoll과 event loop는 readiness를 기다려 I/O를 처리한다.

**언제 사용하는가:** socket 누적·I/O 대기 또는 WebFlux event loop blocking 문제를 조사할 때 사용한다.

**대안과 경계:** edge-triggered event loop는 준비된 데이터를 다 읽을 때까지 drain해야 할 수 있다. WebFlux event loop를 blocking하면 다른 요청도 막힐 수 있다.

**예시·실행 근거:** 요청→socket FD→readiness event→thread 처리 흐름을 따라간다.

**선수개념:** system call; socket; I/O

**관련 표기·별칭:** file descriptor·I/O·event loop; FD·I/O·event loop; FD and I/O/event loop

**보완·검증 필요 사항:**

- 실제 epoll trace나 WebFlux blocking thread dump는 측정하지 않았다.

**초보자가 시작할 질문:**

- WebFlux에서 blocking 호출 하나가 왜 다른 요청까지 늦추나?
