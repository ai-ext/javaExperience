## Kafka 로그와 RabbitMQ 큐

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** Kafka는 파티션 로그와 그룹별 offset을 보존해 재생하고, RabbitMQ는 exchange가 binding 규칙으로 queue에 라우팅한다.

**언제 사용하는가:** 새 구독자가 과거 이벤트를 재생하거나 독립 그룹들이 같은 로그를 읽으면 Kafka를, 라우팅 키·개별 ack를 가진 작업 큐가 필요하면 RabbitMQ를 검토한다.

**대안과 경계:** Kafka는 보존·재생, RabbitMQ는 전달과 routing이 중심이다. 파티션 안 순서와 여러 consumer의 완료 순서도 구분한다.

**예시·실행 근거:** 문서의 Kafka 파티션/그룹 설명과 RabbitMQ exchange·binding 코드가 대응한다. Spring 예제는 미실행이다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

## at-most-once·at-least-once·exactly-once

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 전달 위치를 업무 전/후 언제 확정하는지에 따라 유실과 중복 가능성이 달라지는 처리 보장 범위다.

**언제 사용하는가:** 중복보다 유실이 허용될 때 at-most-once, 재전달을 감수하고 멱등 처리할 때 at-least-once를 설계한다.

**대안과 경계:** Kafka의 exactly-once 범위는 Kafka 입력 offset·출력 흐름이며 외부 DB나 결제 API까지 자동 확장되지 않는다.

**예시·실행 근거:** 문서에서 DB commit 전후 offset 확정의 실패 창을 설명하고, 전송 보장 선택을 비교한다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

**초보자가 시작할 질문:**

## ack·offset commit·publisher confirm

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** RabbitMQ ack는 전달 처리 결과, Kafka offset commit은 재시작 위치, publisher confirm은 브로커의 발행 확인이다.

**언제 사용하는가:** 브로커 발행 성공과 업무 처리 성공을 각각 관측해야 하는 생산·소비 경계에서 쓴다.

**대안과 경계:** 세 확인은 서로 다른 방향/단계의 신호이며 DB 트랜잭션과 자동 원자화되지 않는다.

**예시·실행 근거:** RabbitTemplate confirm·return 예제와 listener ack 설명을 제공한다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

## 멱등 소비자와 Outbox

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 멱등 소비자는 같은 event ID의 업무 반영을 막고 Outbox는 업무 변경과 발행 기록을 한 DB 트랜잭션에 저장한다.

**언제 사용하는가:** DB 업데이트에 따른 이벤트 유실 창을 닫아야 하면 outbox와 relay/CDC를 둔다.

**대안과 경계:** relay는 broker 발행 확인 뒤 진행 저장 전에 죽어 중복 발행할 수 있어 outbox만으로 중복이 없어지지 않는다.

**예시·실행 근거:** `processed_message` 고유키와 outbox 저장 코드가 있으나 broker 통합은 미실행이다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

- 문서의 핵심 선택과 실패 경계는 정리되어 있으나 제시된 Spring/infra 예제의 실제 실행은 별도 검증하지 않았다.

**초보자가 시작할 질문:**

- 주문 DB는 저장됐는데 이벤트 발행은 실패했다면 누락을 복구할 기록은 어디에 남겨야 하나요?
- outbox relay가 broker 전송 뒤 종료되면 같은 event ID가 다시 올 수 있는데 소비자는 무엇을 확인해야 하나요?

## 재시도·DLT/DLQ와 순서

현재 판정: **부분** / 우선순위: high

**정의와 실제 역할:** 재시도는 실패 작업을 다시 처리하고 DLT/DLQ는 반복 실패 메시지를 격리해 조사·복구하게 한다.

**언제 사용하는가:** 한시적 오류는 제한 횟수와 backoff, 격리 메시지는 원인별 재처리 절차와 경보를 설계한다.

**대안과 경계:** blocking 재시도는 파티션 진행을 막을 수 있고 지연 토픽은 순서를 바꿀 수 있다.

**예시·실행 근거:** 실패 처리기·재시도 토픽의 코드/운영 제한을 기술하지만 실행은 하지 않았다.

**선수개념:** Java/Spring 기본 실행 흐름; HTTP·DB·프로세스 중 해당 개념의 접점

**관련 표기·별칭:** 

**보완·검증 필요 사항:**

**초보자가 시작할 질문:**
