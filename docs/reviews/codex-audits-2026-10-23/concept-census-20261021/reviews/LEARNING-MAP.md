# 개념 이름을 모르는 학습자의 진입 경로

이 파일은 기존 자료를 어떤 질문에서 찾아가게 해야 하는지에 대한 감사 결과다. 아래 경로를 현재 UI에 구현했다는 뜻은 아니다.

## 먼저 서로 다른 종류의 개념을 구분해야 한다

| 학습자가 결정할 문제 | 개념의 종류 | 대표 개념 | 혼동하면 생기는 문제 |
|---|---|---|---|
| 요청을 어떻게 받아 응답하나 | 웹 요청 처리와 표현 | HTTP, MVC, Controller, 직렬화 | MVC의 Model을 Repository로 오인 |
| 프로그램 안에서 누가 무엇을 책임지나 | 내부 책임·의존성 | Layered, Service, Repository, Port/Adapter | 파일 세 개를 만들면 업무 설계가 끝났다고 오인 |
| 실행·배포를 어디서 나누나 | 시스템 경계 | Monolith, 모듈러 모놀리스, MSA | 계층형과 모놀리스/MSA를 서로 배타적인 선택지로 오인 |
| 객체를 누가 만들고 연결하나 | 실행시 조립·수명 | Bean, IoC, DI, scope, lifecycle | 모든 Java 객체와 JPA Entity를 Spring Bean으로 오인 |
| 이 값은 어떤 의미와 경계를 가지나 | 모델·데이터 계약 | Entity, Value Object, DTO, Command | 필드가 같으면 같은 역할이라고 오인 |
| DB와 어떻게 통신하고 매핑하나 | 데이터 접근 기술 | JDBC, MyBatis, JPA, Hibernate, Spring Data | JPA와 Hibernate/Repository/EntityManager를 같은 것으로 오인 |
| 데이터가 서로 어떻게 연결되나 | 관계·정합성 | PK, FK, N:1, 1:N, N:N, UNIQUE | 객체 컬렉션과 관계 테이블을 동일한 구조로 오인 |
| 관련 데이터를 언제 얼마나 읽나 | 조회 범위·시점 | LAZY, EAGER, fetch join, projection, N+1 | Entity에 값이 있거나 SQL이 실행됐다고 영속화/commit까지 됐다고 오인 |
| DB가 어떤 후보를 어떤 구조로 찾나 | 접근 경로·비용 | B-Tree, 복합/커버링 인덱스, 실행 계획 | 인덱스를 썼으면 항상 효율적이라고 오인 |

따라서 하나의 긴 기술명 목록만으로는 충분하지 않다. 각 개념이 위 질문 중 어디에 속하는지부터 안내해야 한다.

## 실제 요구에서 시작하는 경로

| 시작 질문 | 먼저 읽을 개념 | 이어 볼 기존 자료 | 중간에 직접 확인할 결과 |
|---|---|---|---|
| Controller 뒤에 무슨 코드를 써야 하나? | 입력 출처·업무 규칙·Service 책임 | W01/W02/P02 → W10/W11 → 생성 시나리오 | 조회/거절/변경/반환 의사코드와 실패 시 쓰기0건 |
| 객체를 직접 new하지 않았는데 어디서 생겼나? | 객체/참조 → 컨테이너 조립 → Bean/DI | P09/P04 → P12/P11 → S01 | 생성자 호출, 후보 선택 오류, 요청별 상태의 위치 |
| DB에 저장하려는데 JPA와 MyBatis 중 무엇을 쓰나? | SQL·행·JDBC → 매핑 방식/통제 범위 | R01/R03/R04 → W03 → W04 또는 P19/S09 | 같은 SELECT/INSERT를 각 방식으로 호출하고 SQL/결과 비교 |
| 글 하나에 댓글 여러 개를 붙이고 싶다 | PK/FK → N:1 → 양방향 선택 | R03 → E4/P20 → 댓글 시나리오 | 메모리 연결과 실제 FK의 값 일치 |
| 같은 태그를 여러 글에서 쓰고 싶다 | 공유 수명 → N:N 연결 엔티티 | R03/P20 → 태그 시나리오 | 태그1개/연결2개, 한 연결 제거 뒤 다른 글 보존 |
| 요청으로 받은 필드를 전부 저장해도 되나? | 허용 입력·인증값·업무 불변식 → DTO/Entity/VO | W09/W10/S22 → 생성·수정 시나리오 | 클라이언트가 작성자/권한을 임의 변경하지 못함 |
| 저장했는데 다른 DB 창에서 안 보인다 | 관리 상태 → flush → commit/rollback → 격리 | S09/W11/S08 → R04/R08 | 같은 tx와 새 연결 관찰을 분리 |
| 조회 중 SQL이 왜 계속 나가나? | LAZY/fetch → 직렬화 → N+1 | P20/S09/W09 → S10/W15 | 실제 SQL 수와 필요한 필드 비교 |
| 검색이 느려졌는데 어느 인덱스를 만들까? | WHERE/정렬/선택열 → 키 순서 → 계획/측정 | R04 → R05 → DB 실행계획 시나리오/S17 | 후보별 계획·실제 행 수·쓰기 비용 |
| 두 SELECT 결과를 한 목록으로 합치고 싶다 | UNION/UNION ALL → 중복 행·호환 컬럼 | 현재 SQL 입문 공백 후보 → R04 확장 위치 | 2행/3행 차이와 JOIN/Union-Find와의 구별 |
| 숫자가 가끔 틀어지거나 중복 저장된다 | 원자성 → UNIQUE → 경쟁 → 재시도 | P18/W25/S08 → 동시성 과제 | 모든 worker 결과와 count=관계행수 |
| 서버 하나로 만들지 나눌지 모르겠다 | 내부 모듈 경계 → 배포/데이터 소유권 | P02/W02 → S22 → S20 | 같은 업무를 나눴을 때 생기는 네트워크/트랜잭션/운영 비용 |

위 E4는 개념 레슨이다. 자료가 현재 공개 화면에서 어떤 경로로 연결되는지는 각 문서의 discovery 평가와 실제 검색 로그를 따른다. 문서 ID를 아는 사람이 이 표로 읽을 수 있다는 사실과, UI가 이미 이 경로를 안내한다는 주장을 구분한다.

## 각 개념에 필요한 최소 안내

1. 처음 드는 질문 한 개: 기술명을 포함하지 않아도 찾을 수 있어야 한다.
2. 이 개념이 해결하는 문제와 지금 알아야 하는 이유.
3. 먼저 이해할 두세 개념과 바로 갈 수 있는 링크.
4. 동일한 데이터로 볼 수 있는 상태 전후 또는 비교 장면.
5. 한 가지 직접 해볼 과제와 관측 가능한 합격 조건.
6. 헷갈리는 인접 개념과 적용하지 않을 조건.
7. 완료 뒤 이어갈 다음 질문.

모든 사람이 Java 문법·알고리즘 전체를 끝낸 뒤에만 API를 만들도록 고정하지 않는다. 지금 만드는 기능에 필요한 짧은 필수 경로를 제공하고, 깊은 내용은 명시적인 심화 경로로 이어야 한다.

## 전수 목록을 읽는 방법

기존134문서 각각의 JSON에는 의미 단위 개념, 선수개념, 발견 질문, 근거, 시각 제안이 있다. 같은 개념이 여러 문서에서 다뤄질 수 있으므로 개념 항목 수를 고유 개념 수로 부르지 않는다. 추가 needed 목록도 담당 영역 밖에서 이미 다룬 내용인지 교차 대조한 뒤 최종 누락과 연결 부족을 나눈다.
