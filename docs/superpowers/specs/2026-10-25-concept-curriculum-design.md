134개 문서를 나열하는 현재 목록에는 Spring Boot 입문자가 당장 배울 핵심, 선수 개념, 깊이, 실제 개발과의 연결이 드러나지 않는다. 기본 분류에 Spring 자체가 없고 IoC·DI도 요청·응답으로 묶였다. P11/P12/S01은 원문이 있지만 개별 화면 보강은 미착수다. 첫 추천 경로는 객체·생성자·JSON·DTO까지만 안내한다.

목표는 학습자가 '지금 무엇을 왜 배워야 하나, 어디에 쓰나, 무엇을 직접 확인했나'를 목록과 상세에서 알아보게 하는 것이다.

## 분류 기준

우선순위와 깊이는 다른 속성이다.

| 축 | 값 | 판정 기준 |
|---|---|---|
| 우선순위 | 필수 | 이 저장소에서 기본 API·서버 코드를 읽고 구현·검증하는 데 필요한 개념 |
| 우선순위 | 선택 | 특정 기능·성능 문제·환경에서 필요해지는 개념 |
| 깊이 | 기초 | 선언·용어·기본 사용과 정상 동작을 직접 설명하고 확인 |
| 깊이 | 응용 | 실제 기능 구현, 실패 진단, 경계 조건과 설계 선택에 적용 |
| 깊이 | 심화 | 프레임워크 확장 지점, 내부 구현, 특수 성능·운영 조건 |

분류는 사용 빈도 통계를 추정해 정하지 않는다. 실제 저장소 과제와 선수 관계를 근거로 남긴다. 하나의 문서에 여러 깊이가 있으면 문서 전체를 하나로 판정하지 않고 절 단위 학습 단원으로 연결한다. 예를 들어 S01의 생성자 주입과 BeanFactoryPostProcessor 내부를 같은 기초 학습으로 강제하지 않는다.

첫 화면은 우선순위=필수, 깊이=기초를 기본값으로 한다. 우선순위 필터(필수/선택/전체)와 깊이 필터(기초/응용/심화/전체)는 독립적으로 선택한다. 필수·응용, 필수·심화, 선택·기초도 누락 없이 탐색할 수 있다. '실무 응용' 같은 추천 바로가기는 명시적인 필터 조합의 별칭일 뿐 분류 값을 합치지 않는다. 분야는 Java, Spring·Boot, HTTP·API, DB·JPA, 테스트, 운영으로 구분하는 안을 사용한다. Spring 자료를 요청·응답 안에 숨기지 않는다.

## 리서치·검증 표시 기준

'리서치 완료'라는 단일 표시는 사용하지 않는다. 다음 사실을 별도로 기록한다.

- 자료 상태: 초안/내용 검토 필요/검토됨. 누가 어떤 주장을 검토했는지 범위를 남긴다.
- 출처 대조: 공식 문서 URL, 실제 읽은 절, 확인일, 대상 버전, 지지하는 주장, 접근 실패·상충 내용. HTTP 200과 링크 개수만으로 대조 완료라고 하지 않는다.
- 코드 실행: 미실행/일부 실행/실행 확인/실패. 예제별 실행 명령·환경·입력·실제 결과·assertion·원문 SHA를 기록한다. 예상 출력과 실제 출력을 분리한다.
- 화면 확인: 미확인/확인 범위. 실제 PC 다크 흐름·캡처·동작 근거를 기술 사실 검증과 구분한다.
- 기록 상충·불명확: 미실행 표시와 성공 서술이 함께 있으면 두 문구와 위치를 보존하고 원시 로그·대상 예제·SHA를 대조하기 전에는 현재 성공으로 이관하지 않는다. P27의 미실행 표기와 '컴파일 성공은 확인되지만' 같은 표현도 이 규칙으로 확인한다. 이것만으로 과거 주장을 거짓이라고 단정하지 않는다.

컴파일, 프로그램 실행, Spring 컨텍스트 기동, HTTP 요청, DB 결과는 각각 확인한 범위를 기록한다. 한 단계 성공으로 뒤 단계까지 검증됐다고 표시하지 않는다.

예: W19에 명시적 Java 예제 실행 기록이 있어도 그 문서의 Lombok 예제가 미실행이면 해당 예제를 'Lombok 실행 확인'으로 표시하지 않는다. 한편 P11의 227행에는 실제 delombok 출력이라는 별도 기록이 있다. 이 사실도 범위를 보존하며, 새로 재실행한 것으로 표시하거나 전체 Spring 앱의 실행 성공으로 확대하지 않는다. 원문 SHA나 실행 환경이 달라지면 이전 영수증은 역사 기록으로 유지하고 현재 적용 여부를 다시 판정한다. 버전·사용 빈도·실무 관행을 확인 없이 일반화하지 않는다.

웹·문헌 추가 조사는 사용자의 상시 지시대로 Codex CLI gpt-6-luna를 직접 사용하고 LiteLLM을 쓰지 않는다. 메인은 출처와 실행 결과를 대조한다. 현재 작업의 로컬 파일 조사는 새 웹 조사로 부르지 않는다.

3. 목록의 경로·필터·표시를 구현 → 기본 진입에서 Spring 핵심과 다음 단계가 보이고 검색·뒤로가기·원문 접근이 유지됨.

5. PC 다크 화면과 사실 관계를 검증 → 메인 설계·검증, 단순 구현 Luna high, 독립 검수 Sol high, 관련 하네스·빌드·필수 감사 통과 후 상태 갱신.

main과 기존 worktree는 그대로 보존한다. 구현 승인을 받으면 최신 main에서 별도 worktree로 진행하며 승인 없는 push/PR/main merge는 수행하지 않는다. 이 설계 검토 단계에서는 제품 파일을 수정하지 않았다.
