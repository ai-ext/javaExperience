# 14. javaExperience 시나리오 개편 설계 (2026-10-22, 승인)

근거 문서: 04(현 시나리오 평가), 05(3~6년차 기준선), 06(Spring 기본기·결함 지도), 07(DB 사건), 08(장애·브라운필드), 09(참고 코드베이스·Entity 관례), 10(커넥션 풀·외부 연동·Redis), 13(넷마블).

## 1. 의도

지금 시나리오는 "기능 만들기" 101개다. 좋아요·북마크·투표를 하나씩 만들지만, 끝낸 사람에게 업무 토의에서 "이렇게 하면 이렇게 된다"고 말할 거리가 잘 남지 않는다. 분량의 대부분은 정답 코드다(14장 기준 62%). 페이지를 끝까지 내려야 해서, 무엇을 어떤 순서로 개발하는지도 보이지 않는다.

개편 방향은 **기능이 아니라 역량을 축으로** 삼는 것이다.
- 먼저 익힐 역량을 정하고, 그 역량을 써야만 풀리는 상황을 기능과 티켓으로 만든다.
- 학습자는 빈 프로젝트에서 서버 하나를 직접 만든다.
- 이어서 남이 만든 어수선한 서버를 넘겨받아 고친다.
- 이와 별도로 매일 짧은 Java 실습으로 Java에 익숙해진다.

## 2. 목표 · 비목표 · 반목표

**목표**

2~3주 압축 과정을 끝낸 사람이 다음 두 가지를 할 수 있어야 한다.
1. **만들기**: Spring Boot + JPA/MyBatis + MySQL + Redis로 서버를 처음부터 규칙에 맞게 만든다. 서버에는 인증, CRUD, 복잡 조회, 동시성이 걸린 상점, 외부 결제 연동, 관리자 기능이 있다.
2. **말하기**: 각 결정을 자기 경험으로 설명한다. 순서는 문제 상황, 원인, 선택, 결과다. 신입과 3~6년차의 차이가 바로 이것이다(05 참고).

함께 지켜야 할 조건이 두 가지 있다.
- 어느 날이든 페이지를 열면 **오늘 무엇을 어떤 순서로 만드는지가 맨 위에** 보인다.
- Java 문법(클래스, 제네릭, 컬렉션, 선언 타입과 실제 타입, stream 등)을 매일 반복해서 다룬다.

**비목표**
- Kafka, MSA, 쿠버네티스. Redis는 캐시·카운터·랭킹·횟수 제한 수준까지만 다루고 클러스터 운영은 제외한다.
- SI 특화 관례.
- 게임 운영 도메인. 대신 같은 종류의 문제(쿠폰, 결제, 운영툴)를 게임 지식 없이 겪게 한다.
- 학습 운영 설계(리뷰어 배치, 합격 판정). 이번 범위는 시나리오와 화면을 만드는 데까지다.

**반목표** (기술적으로 돌아가도 실패로 본다)
- 페이지를 끝까지 내려야 오늘 할 일이 보이는 구성.
- 기능 수를 늘려 분량으로 보이는 것.
- "3주 만에 3~6년차"를 약속하는 문구. 현실적인 약속은 **"3~6년차가 쓰는 말과 판단을 직접 겪어 본 상태"**다.

## 3. 제약

- **기간**: 2~3주. 15일안을 기본으로 하고 10일 압축안을 함께 둔다.
- **학습자**: 개발 경험이 거의 없다. 첫 사흘은 친절하게 진행하고, 그 뒤로는 밀도를 빠르게 올린다.
- **스택**: Java 21, Spring Boot 4.1, Spring Security, JPA(Hibernate 7), MyBatis, MySQL 8.4, Redis(Spring Data Redis·Lettuce), Testcontainers. 외부 연동은 WireMock(+Toxiproxy)으로 재현한다.
- **로컬 환경**: Colima. Docker Desktop을 전제로 한 문구는 쓰지 않는다. 정답 snapshot 테스트가 Colima에서 통과하는 것은 확인했다.
- **공개 범위**: 저장소는 public이다. 정답도 public이며, 순서 칸마다 접어서 둔다.
- **기존 자산**: 버리지 않고 재료로 쓴다. 대상은 시드 데이터와 함정 설계, C/D/T/R 채점, AI 채점 프롬프트, 티켓 30개, 에러 도감, 공부자료 134개다.

### 5-1. 일자 페이지 구성 (모든 날 공통)

이번 개편의 핵심이다. **로드맵이 먼저 보이고, 정답은 각 순서 칸 안에만 둔다.**

```
[오늘 순서]  ① 엔티티 만들기 → ② 저장 API → ③ 요청으로 확인 → ④ 함정 겪기 → ⑤ 말하기 카드     (체크 표시로 진도)
[오늘의 Java] J4 열기 (30분)
─────────────────────────────
① 엔티티 만들기
   만들 파일 · 규칙 · 완료 조건
   ▸ 막히면: 힌트 1줄
   ▸ 정답 보기 (이 순서의 코드만)
② ...
─────────────────────────────
말하기 카드 3~5개 · 채점 프롬프트 · 내일 미리보기(오늘 결과 중 무엇을 내일 쓰는지)
```

- 한 순서 칸에서 만드는 파일은 1~3개다.
- 정답 전체를 접기 하나에 몰아넣지 않는다. 각 순서에 그 순서의 코드만 둔다.
- 참고 자료(기존 단계 문서, 공부자료)는 맨 아래 접기 하나에 모은다.

### 5-3. Spring 트랙 2단계 (D11 ~ D14)

도메인은 1단계와 같지만, **다른 사람이 짠 코드**를 받는다.
- 출발점은 1단계 정답이다. 여기에 결함을 심고, 티켓에 필요한 기능을 덧붙이고, 비대한 서비스를 일부러 만든다.
- 규모는 하루 안에 읽을 수 있는 파일 100~150개로 맞춘다.
- 16-4 snapshot은 쓰지 않는다. 443파일에 인터셉터 인증이고 MyBatis가 없어서 1단계와 구조가 다르기 때문이다.
- 반면교사 모델은 eladmin과 06 §17 결함 지도다.

| 일 | 할 일 |
|---|---|
| D11 | 인수인계: 코드 읽기, 특성화 테스트로 동작 고정, 구조·컨벤션 리뷰 메모, ArchUnit 규칙 1개 |
| D12~D13 | 티켓 처리(하루 2~3건). 티켓에는 **증상만** 쓰고, 일부에는 오진을 부르는 단서를 섞는다 |
| D14 | 기능 고도화 1건과 모의 장애 훈련(장애 주입 스크립트 → 대응 → 회고 문서) |

- "내가 겪은 문제 5개" 회고 문서를 쓴다.

### 5-5. Java 트랙 (J1 ~ J15)

- Spring 없이 순수 Java와 JUnit만 쓴다. **학습 테스트** 형식이다. 실패하는 테스트를 통과시키는 방식으로, 우테코 java-jdbc·mvc·http에서 쓰는 방법이다.
- 도메인 객체는 Spring 트랙과 같다(Post, Member, Coupon, Point). 그래서 같은 날 Spring 트랙에서 같은 모양의 코드를 다시 보게 된다.
- 하루 30~60분 분량이다. `./gradlew :java-track:test --tests J05*`로 실행한다.
- **날마다 다른 과제**를 주고 **뒤로 갈수록 어렵게** 한다. 기간이 짧으므로 변수·조건문 같은 너무 쉬운 연습은 넣지 않는다. 대신 한 과제 안에 개념 2~3개를 묶는다.
  - J1~J3은 기본기를 묶은 과제다.
  - J4~J7은 설계와 컬렉션이다.
  - J8~J10은 함수형, 시간, 프록시를 직접 구현한다.
  - J11~J14는 실전 리팩터링이다.
  - J15는 종합 미니 과제다.
- J 페이지 한 장의 구성은 다음과 같다.

```
[상황] 2~3줄 — 오늘 Spring 트랙의 어떤 장면에서 이 코드가 필요해지는가
[빠른 연상] 그림 또는 비교 한 장 — 이미 아는 것(JS/TS, 일상 비유)에 붙이고, 흔한 착각 1개를 짚는다
[만들 것]  ▸ 펼치면: 채울 클래스·메서드 목록, 빈칸이 있는 뼈대 코드, 통과시킬 테스트 이름
[확인]     ./gradlew :java-track:test --tests J05*
[정답]     ▸ 펼치면: 정답 코드 + "왜 이렇게 쓰나" 3줄
[오늘 Spring에서 다시 만나는 곳] D5 ② 목록 DTO 변환
```

**J0 워밍업 (선택, D1 전 반나절~1일)**

시간이 있으면 Spring에 들어가기 전에 한다. 없으면 건너뛰고 바로 D1으로 간다. 아래 기본기는 J1~J15에서도 매일 다시 쓰도록 과제를 짠다(기본기 반복 칸).

- 메서드 만들기(매개변수, 반환 타입, `return`), 필드 선언과 초기화, `for`·향상된 for
- **값 전달 방식**. Java는 항상 값을 복사해서 넘긴다.
  - 기본형(`int` 등)은 값 자체가 복사된다.
  - 객체는 **참조(주소)가 복사**된다. 깊은 복사가 아니다. 그래서 메서드 안에서 객체의 필드를 바꾸면 호출한 쪽에서도 바뀐다.
  - 반면 메서드 안에서 매개변수에 새 객체를 대입하면 호출한 쪽은 그대로다.
  - 학습자가 흔히 하는 착각이라 테스트 3개로 직접 확인시킨다.
- 컬렉션에 담고 꺼내기, 제네릭 타입 읽기(`List<Post>`), 반복문을 stream으로 옮기기

**매일 과제의 기본기 반복 칸**: J1~J15는 그날 주제 과제 외에 "기본기 반복" 문제를 1~2개 둔다. 위 기본기(메서드, 필드, 반복문, 값 전달, return, 제네릭, stream)를 그날 도메인으로 다시 쓰게 하고, 날이 갈수록 조건을 늘린다. 예시는 다음과 같다.
- J2: 단순 합계
- J5: 그룹별 합계(`groupingBy`)
- J8: 실패 건을 모아 예외로 반환

**매일 "타입 한 컷" 칸**

J 페이지마다 타입 하나를 짧게 다룬다. 구성은 비교표 1개, 함정 1개, 확인 테스트 1개다. 그날 Spring 코드에서 그 타입이 왜 그렇게 쓰였는지와 연결한다.

| J | 타입 한 컷 | 그날 연결 |
|---|---|---|
| J1 | `int` vs `Integer`: 기본형과 래퍼. null 가능 여부, 기본값(0과 null) | 요청 DTO에서 "값 없음"과 "0"을 구분해야 하는 이유 |
| J2 | `long` vs `Long`: 엔티티 id는 왜 `Long`인가(null이면 아직 저장 전) | BaseEntity, JPA 신규·기존 판단 |
| J3 | **오토박싱·언박싱 NPE**(`Long` → `long`): 장애가 나는 세 가지 패턴을 직접 터뜨려 본다. ① 집계 결과가 없을 때 `SUM`이 null을 돌려준다(MyBatis `resultType="long"`, JPA `Long` 반환을 `long`으로 받음) ② `Map.get()`이 null을 돌려준다 ③ 아직 저장 전인 엔티티의 id가 null이다 | 포인트 합계 조회, 캐시 조회, 저장 직후 id 사용 |
| J4 | `==` vs `equals`: `Integer` 캐시(-128~127) 때문에 작은 수는 `==`도 맞아 보인다 | id 비교 버그 |
| J5 | 제네릭에는 왜 래퍼만 쓰나(`List<int>` 불가), `IntStream`·`mapToLong` | 합계 stream |
| J6 | **`Optional`**: `orElse`와 `orElseGet`의 차이(`orElse`는 값이 있어도 인자를 먼저 실행한다), `orElseThrow`, 반환 타입에는 쓰고 필드·매개변수에는 쓰지 않는 이유 | 단건 조회 404 처리, 쿠폰 조회 |
| J7 | `boolean` vs `Boolean`, `is` 접두어와 JSON 직렬화 | 응답 필드 이름이 바뀌는 문제 |
| J8 | `String` 불변, `+` 결합과 `StringBuilder`, `String.format` | 로그 메시지, 외부 API URL 조립 |
| J9 | `LocalDate`·`LocalDateTime`·`Instant`·`ZonedDateTime`의 차이 | 출석 자정 경계, 토큰 만료 |
| J10 | `final`·`var`·`static final` 상수 | 설정 상수, 불변 필드 |
| J11~J15 | 배열 vs `List`, `enum` 확장, `record`, (선택) `double` vs `BigDecimal`, 정리 퀴즈 | 리팩터링 과제 |

**실무 습관 칸** (사용자 확정 5개, 해당 J의 주제 과제에 붙인다)

| 항목 | 다루는 것 | 자리 |
|---|---|---|
| 불변 컬렉션과 방어적 복사 | `List.of()`에 `add`하면 예외가 난다. getter가 내부 리스트를 그대로 내주면 밖에서 엔티티가 바뀐다. 참조 복사의 실전판 | J1(값 전달 다음) |
| null 다루는 습관 | `Objects.requireNonNull`, `Objects.equals`, 컬렉션은 null 대신 빈 리스트를 반환 | J3(NPE와 묶음) |
| Map 실무 API와 `toMap` 함정 | `getOrDefault`·`computeIfAbsent`·`merge`, `toMap` 중복 키 예외, `HashMap`은 순서를 보장하지 않음 | J5·J7 |
| Lombok이 만드는 코드 | `@Getter`·`@RequiredArgsConstructor`·`@Builder`가 생성하는 코드를 직접 확인한다. 엔티티에서 `@AllArgsConstructor`·`@Setter`를 피하는 이유 | J2 |
| 예외 원인 연결과 삼키기 | `new XxxException(msg, e)`로 원인을 남긴다. 빈 catch가 장애 때 무엇을 숨기는지 확인한다 | J8 |

문자열 처리(`split`·`isBlank`·`strip`·`String.join`)는 따로 칸을 두지 않고 J2~J6의 기본기 반복 문제 입력값으로 섞는다(태그 문자열 파싱, 공백 제목 거절 등).

선택(J11~J15): ThreadLocal(Spring 트랜잭션·SecurityContext·MDC의 원리), 정규식 기초, 최신 문법(switch 식, record 패턴, text block), JVM 메모리 기초(힙·스택·GC·OOM).

| J | 날 | 다루는 Java | 예시 과제 |
|---|---|---|---|
| J1 | D1 | 클래스, 생성자, 필드, 접근제어자, record, 값 전달(객체 참조 복사) | `Member` 만들기, 생성자에서 잘못된 값 거절, 메서드에 넘긴 `Member`를 바꾸면 원본이 바뀌는지 테스트로 확인 |
| J2 | D2 | static과 인스턴스, 상속, 예외 계층, 제네릭 클래스 | `Result<T>`, `BusinessException` 계층 |
| J3 | D3 | enum, 불변 객체, `equals`/`hashCode` | `Role` enum과 권한 판정 메서드 |
| J4 | D4 | 인터페이스와 구현, **선언 타입과 실제 타입**, 추상 클래스와 인터페이스 비교 | `DiscountPolicy policy = new RateDiscountPolicy()`일 때 어떤 메서드가 불리는가 |
| J5 | D5 | `List`/`ArrayList`, `new`로 만들어 담기, for에서 stream(`map`·`filter`·`collect`)으로, `Optional` | 엔티티 목록을 DTO 목록으로 바꾸기, 사용 가능한 쿠폰만 거르기 |
| J6 | D6 | 제네릭 메서드·와일드카드, `Comparator` 정렬 | `CursorPage<T>`, 커서 비교기 |
| J7 | D7 | `Map`·`Set`, 스레드와 공유 상태, `AtomicInteger`, `synchronized` | 잔액 갱신 손실을 순수 Java로 재현하고 고치기 |
| J8 | D8 | 체크 예외와 언체크 예외, try-with-resources, 람다와 함수형 인터페이스 | 재시도 함수 `retry(Supplier<T>, int)` |
| J9 | D9 | `LocalDateTime`·`ZonedDateTime`·`Clock`, `Duration` | TTL 계산, 자정 경계 테스트 |
| J10 | D10 | 어노테이션과 리플렉션, JDK 동적 프록시 | 어노테이션이 붙은 메서드만 실행 시간을 로깅하는 프록시를 직접 만들기(AOP의 원리). 같은 객체 안에서 호출하면 프록시를 거치지 않는 것을 테스트로 확인 |
| J11~J14 | D11~D14 | 리팩터링 | 긴 메서드 나누기, 조건문을 전략으로 바꾸기, null 처리, 특성화 테스트 쓰기 |
| J15 | D15 | 종합 | 작은 쿠폰 할인 계산기를 처음부터 만들기(인터페이스, 제네릭, stream, 예외, 테스트를 모두 사용) |

**사용자가 정한 것**
