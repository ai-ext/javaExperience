작성일 2026-10-22. 이 문서는 웹 리서치 결과를 근거로 한 기준선 초안이다. 근거 등급은 아래 세 가지로 구분한다.

- **[공고]** 채용 공고 원문에서 확인한 내용 (아래 §1의 공고 번호로 표기)
- **[면접]** 공개 면접 질문 자료에서 확인한 주제 (§2의 자료 번호로 표기)
- **[설계]** 위 근거를 바탕으로 이 문서가 제안하는 기준. 대표 문장 예시와 "할 수 있어야 하는 것"의 구체 작업은 대부분 여기에 해당하며 출처가 직접 말한 문장이 아니다.

## 0. 먼저 알아야 할 한계

1. 공고 25건의 자격요건은 **"경험 서술형"** ("~을 설계·운영해 본 경험")이다. CS 개념 질문 형태가 아니다. 반면 공개 면접 질문 모음 4종은 모두 **신입 대상이거나 연차 미표기**의 개념 열거형이다. 3~6년차 대상으로 정리된 공개 질문 목록은 찾지 못했다 (§확인 불가).
2. 공고의 연차 하한은 3~5년이 많지만 상한은 8~15년으로 넓다. "3~6년차"만 따로 쓴 공고는 거의 없다. 기준표는 공고 25건의 공통분모를 3~6년차 하한선으로 보는 가정을 둔다.
3. 빈도는 "해당 키워드가 자격요건·우대·주요업무·기술스택에 한 번이라도 등장한 공고 수"이며, 25건 중 몇 건인지로 적었다. 분모 25는 중복(동일 공고의 복수 게재)을 합치고 리더급·비Java·2018년 공고를 뺀 수다. 키워드 분류는 사람이 읽고 센 것이라 ±1 오차가 있을 수 있다.

## 3. 역량 기준표 (3~6년차)

빈도 열은 §1-A 25건 중 해당 키워드가 나온 공고 수다. 면접 열은 §2 개념 질문 자료 5종 중 몇 종에 나오는지다.

### 3-1. Spring 핵심 (DI·빈·AOP·트랜잭션)

- **말할 수 있어야 하는 것**
  - "@Transactional은 프록시 기반이라 같은 클래스 안에서 this로 호출하면 트랜잭션이 안 걸립니다. 그래서 이 로직은 별도 빈으로 뺐습니다." [설계]
  - "Checked 예외는 기본 롤백이 안 돼서 rollbackFor를 지정했고, REQUIRES_NEW로 분리한 로그 저장은 본 트랜잭션이 롤백돼도 남습니다." [설계]
- **할 수 있어야 하는 것**: 생성자 주입 기반 빈 구성, 프록시(JDK/CGLIB) 때문에 생기는 함정 재현·해결, 전파/격리/readOnly 선택, 커스텀 AOP(로깅·재시도 등) 작성, 트랜잭션 경계 안에서 외부 호출을 빼는 구조 설계. [설계]
- **근거**: 공고에서 "Spring 원리(빈, DI, AOP, MVC) 이해"는 P20 1건에만 명시. 나머지는 "Spring 기반 서비스 개발 경험" 수준이라 24/25 (P1은 업무 설명에만). 면접은 DI/IoC/Bean 5/5, 트랜잭션 5/5, AOP 3/5. 공고는 경험을, 면접은 개념을 요구해 **개념+동작 원리+장애 사례**를 한 묶음으로 설계해야 한다.

### 3-2. 웹/API 설계

- **말할 수 있어야 하는 것**
  - "응답 코드는 4xx/5xx를 구분하고, 재시도 안전한 API는 멱등 키를 받도록 했습니다. 목록은 offset 대신 커서로 바꿔 깊은 페이지 성능을 지켰습니다." [설계]
- **할 수 있어야 하는 것**: 요구사항에서 리소스·API·데이터 모델을 설계(P2), 에러 응답 포맷 표준화, 검증, 페이징, 버전·호환성 유지(P1 "변경이 소비 팀에 미치는 영향을 호환성·버전·단계적 이전으로 관리"). [공고+설계]
- **근거**: REST/API 설계·MVC 경험 명시 8/25 (P2, P8, P10, P16, P20, P21, P22, P24). 면접 RESTful·HTTP 메서드는 I5, Filter/Interceptor·DispatcherServlet은 I1~I3·I5 다수.

### 3-3. 인증·인가 (Spring Security)

- **말할 수 있어야 하는 것**
  - "인증은 필터 체인에서 JWT를 검증해 SecurityContext에 올리고, 인가는 메서드 레벨에서 역할과 소유권을 같이 봅니다. Refresh 토큰은 회전시키고 폐기 목록을 둡니다." [설계]
- **할 수 있어야 하는 것**: SecurityFilterChain 구성, JWT/세션 중 선택 근거 설명, CORS·CSRF 설정, 소유권 검사(IDOR) 방지 테스트. [설계]
- **근거**: **공고 자격요건에는 Spring Security 명시가 0/25.** 업무로는 P1(인증/인가, JWT/JWKS 발급)과 P22(회원 인증) 2건. 면접 자료는 2/5 (I4, I5). 공고가 직접 요구하지 않는 영역이라 우선순위는 중간으로 두되, 사내 서비스에는 필요하므로 포함한다 [설계].

### 3-4. 데이터 / JPA / 쿼리

- **말할 수 있어야 하는 것**
  - "목록 API에서 연관 엔티티를 지연 로딩으로 돌려 N+1이 났습니다. 컬렉션은 fetch join이 페이징과 같이 못 가서 batch size로 풀었고, 쿼리 수를 테스트로 고정했습니다." [설계]
  - "dirty checking 덕에 save를 안 불러도 UPDATE가 나가는데, 벌크 연산은 영속성 컨텍스트를 우회하므로 clear가 필요합니다." [설계]
- **할 수 있어야 하는 것**: 엔티티 연관관계 설계, 실행 쿼리 확인·튜닝, QueryDSL 또는 JPQL로 조회 작성, DTO 프로젝션, 대량 처리 시 JDBC batch/벌크. [공고+설계]
- **근거**: JPA/ORM 10/25 (요건·우대 8 + 기술스택 표기 2: P4, P22). RDBMS 설계·모델링·SQL 16/25. 야놀자(P21)는 JPA와 QueryDSL을 함께 요구. 면접 N+1은 3/5, 영속성 컨텍스트·지연 로딩은 I1·I3·I5.

### 3-5. DB 운영 (인덱스·스키마 변경)

- **말할 수 있어야 하는 것**

## 4. 신입(0~2년)과 3~6년차 차이

신입 기준은 공고(하한 2년 공고: 야놀자 파트너 P20, 네이버지도 참고 공고)와 I1·I2·I4 신입 대상 질문 목록에서 읽은 것이다. 아래 표의 "신입" 열은 [면접] 근거, "3~6년차" 열은 [공고]+[설계]를 합친 것이다.

| 영역 | 신입(0~2년) | 3~6년차 | 차이의 핵심 |
|---|---|---|---|
| Spring 핵심 | DI/IoC/Bean 정의, DispatcherServlet 흐름, @Bean vs @Component를 설명 | 프록시·트랜잭션 경계 함정을 재현하고 고침 | 정의 → 동작 원리와 함정 |
| 웹/API | REST 개념, HTTP 메서드, CRUD API 구현 | 요구사항에서 API·모델을 설계, 호환성·멱등 고려 | 구현 → 설계와 변경 관리 |
| 인증·인가 | JWT/OAuth 개념 설명 | 필터 체인 구성, 토큰 수명·소유권 검사 설계 | 개념 → 구성과 위협 대응 |
| JPA/쿼리 | N+1 정의와 fetch join, 영속성 컨텍스트 이점 | 쿼리 수 측정, 페이징·대량 처리 문제 해결 | 용어 → 측정하고 고침 |
| DB 운영 | 인덱스 장단점, 정규화, JOIN | 실행계획으로 튜닝, 무중단 스키마 변경 | 개념 → 운영 영향 판단 |
| 동시성 | 프로세스/스레드, 뮤텍스/세마포어, 데드락 (OS 수준) | 낙관/비관 락, 분산 환경 중복·정합성 방어 | OS 이론 → 서비스 정합성 |
| 캐시 | Redis 소개, Redis vs Memcached | 무효화·정합성·스탬피드를 설계 | 도구 소개 → 일관성 설계 |
| 비동기·메시징 | (공개 신입 자료에 거의 없음) | 멱등 컨슈머, 재시도·DLQ, 아웃박스 | 경험 없음 → 필수 운영 경험 |
| 외부 연동·장애 내성 | (거의 없음) | 타임아웃·재시도·서킷, 부분 실패 처리, 장애 분석 | 없음 → 핵심 평가 항목 |
| 테스트 | TDD 알고 있는가 | 단위·통합 분리, 실제 DB 테스트, 회귀 테스트 | 인지 → 습관 |
| 관측성 | (없음) | 로그·메트릭·트레이싱으로 원인 좁힘 | 없음 → 운영 필수 |
| 배포·운영 | Maven vs Gradle, WAS vs 웹서버 | CI/CD 수정, 롤링 배포 호환성, 기본 운영 | 도구 이해 → 운영 책임 |
| 설계 | 싱글톤·인터페이스 vs 추상 클래스 등 언어 개념 | 책임 분리, 레이어·패키지, 레거시 개선 | 문법 → 구조 |
| 협업 | 협업 방식 소개 | 리뷰, API 계약 조율, 타 직군과 일정·우선순위 조율 | 참여 → 주도 |

한 줄 요약: 신입은 "개념을 정확히 말한다", 3~6년차는 "문제가 났던 상황·원인·선택·결과를 말하고 같은 일을 직접 한다". 토스 공고 P2~P5가 "문제 정의·시도·결과를 적어 달라"고 이력서 요건에 넣은 것이 이 차이를 가장 직접 보여 준다.

## 5. 이 표를 온보딩 설계에 쓸 때의 우선순위 제안 (이 문서의 의견)

1. 공고 빈도가 높고 공개 면접 자료에서 빠진 영역(비동기·메시징 11/25, 장애 대응 9/25, 관측성 7/25, 동시성·정합성)은 **직접 구현·장애 재현 과제**로 채운다. 개념 읽기로는 부족하다.
2. 공고 빈도가 낮지만 사고가 잦은 영역(무중단 스키마 변경 0/25, 캐시 무효화 0/25, 서킷브레이커 0/25, Spring Security 0/25)은 공고가 아니라 **사내 사고 사례**를 근거로 삽입 여부를 정한다.
3. 공고 문구 중 "경험을 서술하라"는 요구(P2~P5)에 맞춰, 각 과제 끝에 "문제·시도·결과" 3줄 회고를 쓰게 하면 "해 본 사람처럼 말하기" 훈련이 된다.
