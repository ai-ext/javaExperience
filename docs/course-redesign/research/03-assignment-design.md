# 03. javaExperience로 과제를 주는 방법 (제안)

## 가정 (확인 필요)

- 대상: 백엔드 신입 또는 프론트→백엔드 전환자. Java 경험 유무는 사람마다 다름.
- 기간: 4주 내외. 하루의 절반 정도를 과제에 쓴다.
- 리뷰어: 사수 1명이 여러 명을 본다 → 사람 리뷰 시간이 병목.

가정이 다르면(기간 1~2주, 경력 전환자 등) 아래 경로의 길이만 바꾼다.

## 핵심 판단

1. **101단계 전부는 주지 않는다.** 시나리오 md가 8.9만 줄이다. 필수 경로 20단계를 고르고 나머지는 선택으로 둔다.
2. **"따라 만들기 → 티켓 → 명세서 프로젝트" 3단으로 형식을 바꿔 가며 준다.** 외부 사례의 세 패턴(단계 확장 / 레거시+변경 / 명세만 주기)이 이 레포에 이미 다 들어 있다.
3. **채점은 AI가 1차(C·D·T), 사람은 R 항목과 설명만 본다.** 리뷰어 병목을 이렇게 푼다.

## 운영 방식

- **브랜치**: 학습자는 fork 또는 `<이름>/chN` 브랜치(README 규칙). main 직접 push 금지.
- **PR 템플릿**(새로 추가 권장): 단계 ID · AI 채점표 붙여넣기 · R 항목 자기 답변 · 막혔던 점.
- **AI 채점**: 단계 HTML의 "결과 테스트 프롬프트"를 Claude Code/Codex에 붙여 넣기. 프롬프트가 "코드 수정 금지·SELECT만"을 강제한다.
- **사람 리뷰**: R 항목만 질문한다. "왜 원자 UPDATE를 골랐나, 비관적 락이면 뭐가 달라지나" 처럼 설명을 요구하고, 정답 코드를 주지 않는다.
- **정답 열람 규칙**: 힌트·접기는 30분 막힌 뒤에만. PR에 "정답 접기를 열었는지" 체크박스.

## 과제를 주기 전에 해야 할 일 (준비 작업)

| # | 할 일 | 왜 |

## 정해 주셔야 할 것

1. 대상과 기간 — 신입/전환자, 몇 주인지.
2. 사수 리뷰를 어디까지 할지 — 장 단위 PR 리뷰를 사람이 볼 여력이 있는지.
3. 이 레포를 그대로 쓸지, 사내 fork(회사 조직)로 가져가 위 준비 작업을 할지. 공개 레포라 원작자 협의가 필요할 수 있다.
