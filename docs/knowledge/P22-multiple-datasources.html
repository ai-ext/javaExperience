여러 DB는 DataSource·EntityManagerFactory·트랜잭션 매니저의 경계를 명시해야 한다. 읽기/쓰기 라우팅은 AbstractRoutingDataSource, 커넥션 지연은 LazyConnectionDataSourceProxy가 맡는다. 기본 추천은 primary 하나로 정확성을 검증한 뒤 읽기 부하가 확인되면 replica를 추가하는 것이다.

011. 한 줄로 말하면열기 ↓

여러 데이터소스는 레거시 DB·도메인별 DB처럼 서로 다른 데이터베이스에 연결하는 구성이다. 읽기 복제본 라우팅은 쓰기는 primary, @Transactional(readOnly = true) 읽기는 replica로 보낼 프록시를 하나의 DataSource처럼 노출한다. 두 DB를 한 요청에서 갱신하면 로컬 트랜잭션 두 개일 뿐 자동 원자 커밋은 아니다.

012.1 Boot 자동 구성과 @Primary↘

Spring Boot는 spring.datasource.*와 starter를 보고 보통 DataSource 하나, JPA EntityManagerFactory 하나, 트랜잭션 매니저 하나를 연결한다. 후보가 여러 개면 기본 대상이 모호하므로 명시 구성이 필요하다. @Primary는 주입 기본값이지 분산 커밋 기능이 아니다. 나머지는 @Qualifier("ordersDataSource")로 고른다.

DataSource는 JDBC 커넥션 입구, EntityManagerFactory는 JPA 단위, PlatformTransactionManager는 해당 자원의 커밋 경계다. AbstractRoutingDataSource는 target 풀을 선택하고 LazyConnectionDataSourceProxy는 물리 연결을 지연한다. source/primary는 쓰기 원본이며 replica는 비동기 복제 대상이다.

022.2 두 DB와 primary/replica는 다르다↘

users DB와 orders DB 분리는 DataSource·EMF·매니저 2세트와 repository 패키지 분리가 필요하다. 같은 스키마의 primary/replica는 두 물리 DS를 routing 하나로 감싸고 EMF 하나를 쓴다. repository 스캔 범위가 겹치면 persistence unit이 깨지므로 basePackages와 EMF의 .packages(...)를 같은 도메인 묶음으로 맞춘다.

032.3 DataSourceProperties와 url/jdbc-url↘

Boot 4.1의 DataSourceProperties는 url을 받고 initializeDataSourceBuilder()로 풀을 만든다. Hikari 타입에 곧바로 설정을 바인딩하면 Hikari가 기대하는 jdbcUrl과 url이 달라 다음 오류가 난다.

java.lang.IllegalArgumentException: jdbcUrl is required with driverClassName.

DataSourceProperties가 url을 풀의 jdbcUrl로 변환하게 맡긴다.

042.4 read-only를 routing key로 사용하기↘

라우터는 TransactionSynchronizationManager.isCurrentTransactionReadOnly()를 기준으로 key를 얻는다. 직접 만든 ThreadLocal은 finally 누락과 비동기 전파 위험이 있다.

052.5 replica 최신성↘

MySQL 8.4의 기본 replication은 비동기다. 쓰기 직후 replica가 이전 값을 반환하는 read-after-write 문제가 발생한다. 결제 상태와 재고처럼 최신성이 필요한 읽기는 primary로 보내고 일반 목록만 replica로 보낸다. readOnly=true는 라우팅 힌트이지 쓰기 금지 권한이 아니다.

package com.example.config;

import jakarta.persistence.EntityManagerFactory;
import javax.sql.DataSource;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.boot.jdbc.autoconfigure.DataSourceProperties;
import org.springframework.boot.orm.jpa.EntityManagerFactoryBuilder;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Primary;
import org.springframework.data.jpa.repository.config.EnableJpaRepositories;
import org.springframework.orm.jpa.JpaTransactionManager;
import org.springframework.orm.jpa.LocalContainerEntityManagerFactoryBean;
import org.springframework.transaction.PlatformTransactionManager;

@Configuration(proxyBeanMethods = false)
@EnableJpaRepositories(basePackages = "com.example.users.repo",
    entityManagerFactoryRef = "usersEntityManagerFactory",
    transactionManagerRef = "usersTransactionManager")
public class UsersDbConfig {
    @Bean @Primary @ConfigurationProperties("app.datasource.users")
    DataSourceProperties usersProperties() { return new DataSourceProperties(); }

    @Bean @Primary
    DataSource usersDataSource(@Qualifier("usersProperties") DataSourceProperties p) {
        return p.initializeDataSourceBuilder().build();
    }

    @Bean @Primary
    LocalContainerEntityManagerFactoryBean usersEntityManagerFactory(
            EntityManagerFactoryBuilder b, @Qualifier("usersDataSource") DataSource ds) {
        return b.dataSource(ds).packages("com.example.users.entity")
                .persistenceUnit("users").build();
    }

    @Bean @Primary
    PlatformTransactionManager usersTransactionManager(
            @Qualifier("usersEntityManagerFactory") EntityManagerFactory emf) {
        return new JpaTransactionManager(emf);
    }
}

033.3 방식 ② 읽기/쓰기 라우팅 전체 코드↘

src/main/java/com/example/config/RoutingDataSourceConfig.java

package com.example.config;

import com.zaxxer.hikari.HikariDataSource;
import java.util.Map;
import javax.sql.DataSource;
import jakarta.persistence.EntityManagerFactory;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.boot.jdbc.autoconfigure.DataSourceProperties;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Primary;
import org.springframework.jdbc.datasource.LazyConnectionDataSourceProxy;
import org.springframework.jdbc.datasource.lookup.AbstractRoutingDataSource;
import org.springframework.orm.jpa.JpaTransactionManager;
import org.springframework.transaction.PlatformTransactionManager;
import org.springframework.transaction.support.TransactionSynchronizationManager;

@Configuration(proxyBeanMethods = false)
public class RoutingDataSourceConfig {
    enum Role { WRITE, READ }

    @Bean @ConfigurationProperties("app.datasource.write")
    DataSourceProperties writeProperties() { return new DataSourceProperties(); }
    @Bean @ConfigurationProperties("app.datasource.read")
    DataSourceProperties readProperties() { return new DataSourceProperties(); }

    @Bean HikariDataSource writeDataSource(
            @Qualifier("writeProperties") DataSourceProperties p) {
        return p.initializeDataSourceBuilder().type(HikariDataSource.class).build();
    }
    @Bean HikariDataSource readDataSource(
            @Qualifier("readProperties") DataSourceProperties p) {
        return p.initializeDataSourceBuilder().type(HikariDataSource.class).build();
    }

    @Bean DataSource routingTargetDataSource(
            @Qualifier("writeDataSource") DataSource write,
            @Qualifier("readDataSource") DataSource read) {
        AbstractRoutingDataSource r = new AbstractRoutingDataSource() {
            @Override protected Object determineCurrentLookupKey() {
                return TransactionSynchronizationManager.isCurrentTransactionReadOnly()
                        ? Role.READ : Role.WRITE;
            }
        };
        r.setTargetDataSources(Map.of(Role.WRITE, write, Role.READ, read));
        r.setDefaultTargetDataSource(write);
        r.setLenientFallback(false);
        r.afterPropertiesSet();
        return r;
    }

    @Bean @Primary
    DataSource dataSource(DataSource routingTargetDataSource) {
        return new LazyConnectionDataSourceProxy(routingTargetDataSource);
    }

    @Bean @Primary
    PlatformTransactionManager transactionManager(EntityManagerFactory emf) {
        return new JpaTransactionManager(emf);
    }
}

라우팅 방식은 JPA EMF 하나가 @Primary DataSource를 사용하므로 방식 ①의 두 EMF 설정을 동시에 켜지 않는다. 서비스는 다음과 같다.

@Service
public class NoteService {
    private final NoteRepository repository;
    public NoteService(NoteRepository repository) { this.repository = repository; }

    @Transactional(readOnly = true)
    public Note find(long id) { return repository.findById(id).orElseThrow(); }

    @Transactional
    public Note save(Note note) { return repository.save(note); }
}

확인 방법: 두 서버에 구분 값을 넣고 GET/POST를 호출한다. SQL 로그에서 GET은 read pool, POST는 write pool이어야 한다.

Spring 예제는 이 문서에서 실행하지 않았으므로 (미실행)이다. lazy proxy 없이 JPA가 먼저 커넥션을 얻으면 기본 WRITE key를 볼 수 있다. Spring 예제는 (미실행)이다. 서로 다른 JpaTransactionManager는 한쪽만 커밋할 수 있으므로 업무 상태와 outbox를 한 DB 트랜잭션에 저장하고 publisher가 멱등 전달한다.

055. 자주 나는 에러와 해결No qualifying bean of type 'jakarta.persistence.EntityManagerFactory' · Not a managed type: class ...Order · jdbcUrl is required with driverClassName · 읽기가 계속 primary로 간다열기 ↓
01No qualifying bean of type 'jakarta.persistence.EntityManagerFactory'↘

EMF를 만들지 않았거나 entityManagerFactoryRef와 bean 이름이 다르다. DB별 EMF·repository ref·transaction manager 이름을 맞추고, 라우팅 방식이면 EMF 하나를 primary DataSource에 연결한다.

02Not a managed type: class ...Order↘

orders repository가 users persistence unit을 보거나 EMF packages에 엔티티가 빠졌다. basePackages와 .packages를 맞추고 jakarta.persistence.Entity를 사용한다.

03jdbcUrl is required with driverClassName↘

Hikari에 url을 직접 바인딩한 것이다. DataSourceProperties에 url을 바인딩하고 initializeDataSourceBuilder()로 만든다.

04읽기가 계속 primary로 간다↘

커넥션을 너무 일찍 얻었거나 @Transactional이 프록시를 거치지 않았다. lazy proxy를 라우터 바깥에 두고 풀 이름을 로그로 검증한다.

05쓰기 직후 GET이 이전 값을 반환한다↘

replica lag이다. 최신성 경로는 primary로 보내고 lag metric을 관찰한다.

06두 저장 중 한쪽만 커밋됐다↘

두 로컬 매니저가 독립 커밋했다. outbox를 업무 DB와 같은 트랜잭션에 넣고 멱등 키와 보상 작업을 둔다.

066. 한 단계 더열기 ↓

트랜잭션 매니저는 자원을 현재 스레드에 묶고 routing은 새 커넥션의 풀만 정한다. 전파는 → S08, JPA는 → S09, 단일 연결은 → P19 참조.

077. 자가점검 Q&A (면접 대비)Q1. @Primary란? · Q2. lazy proxy가 필요한 이유는? · Q3. 두 DB를 트랜잭션 하나로 묶을 수 있나? · Q4. readOnly면 쓰기가 절대 불가능한가?열기 ↓
01Q1. @Primary란?↘

여러 후보 중 자동 주입 기본값이다. 모든 DB를 묶거나 분산 커밋하지 않는다. 나머지는 Qualifier로 선택한다.

꼬리질문: 두 개에 붙이면? 답: 기본 후보가 둘이라 모호성 오류가 난다.

02Q2. lazy proxy가 필요한 이유는?↘

read-only 속성보다 커넥션을 먼저 얻으면 라우터는 기본 WRITE를 선택한다. 첫 Statement까지 지연해 속성이 정해진 뒤 READ/WRITE를 선택한다.

꼬리질문: 열린 커넥션을 바꿀 수 있나? 답: 없다. 새 연결/트랜잭션이 필요하다.

03Q3. 두 DB를 트랜잭션 하나로 묶을 수 있나?↘

일반 JPA 매니저 두 개는 로컬 트랜잭션만 관리한다. 한쪽 커밋 뒤 다른 쪽 실패를 자동 취소하지 않는다. XA/JTA는 비용을 검토할 때만 선택하고 보통 outbox를 쓴다.

꼬리질문: outbox 원자성은? 답: 업무 상태와 outbox 행을 같은 DB 로컬 트랜잭션으로 커밋한다.

04Q4. readOnly면 쓰기가 절대 불가능한가?↘

아니다. 라우팅 힌트다. replica 계정 권한을 읽기 전용으로 하고 쓰기 메서드는 기본 트랜잭션으로 명시한다.

꼬리질문: 최신 읽기는? 답: primary로 보낸다.

05Q5. repository 패키지를 나누는 이유는?↘

repository는 특정 EMF에 등록된다. 범위가 겹치면 다른 persistence unit을 보아 Not a managed type이 난다. package와 EMF ref를 1:1로 맞춘다.

꼬리질문: 같은 엔티티를 두 DB에서 읽으면? 답: persistence unit별 이름을 분리한다.

06Q6. primary/replica 불일치를 라우팅 버그로 단정할 수 있나?↘

먼저 비동기 복제 지연을 확인한다. 실제 접속 주소, 풀 이름, replica 적용 상태를 함께 관찰하고 최신성 요구에 따라 경로를 정한다.

꼬리질문: 장애 때 무조건 primary fallback? 답: 포화와 장애 은폐를 막도록 정책을 둔다.
