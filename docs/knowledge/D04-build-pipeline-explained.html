# D04. 빌드란 무엇인가 — 소스 코드가 실행 파일·이미지가 되기까지

> 빌드는 코드를 컴파일하는 한 단계가 아니라, 선언된 입력을 검증하고 실행·배포 가능한 산출물로 바꾸는 자동화 과정이다.
> Gradle은 먼저 프로젝트와 태스크 그래프를 준비한 다음 필요한 태스크를 의존성 순서대로 실행한다.
> 로컬과 CI의 차이는 대개 JDK·의존성·환경변수·커밋 상태·캐시 입력이 서로 다른 데서 시작한다.

## 1. 큰 그림

```mermaid
flowchart LR
    S["소스 코드 .java"] --> G["Gradle Wrapper와 빌드 설정"]
    G --> D["의존성 그래프 해석과 파일 확보"]
    D --> C["Java 컴파일 .class"]
    C --> R["리소스 처리"]
    R --> T["테스트 실행"]
    T --> J["JAR 패키징"]
    J --> I["선택: 컨테이너 이미지 생성"]
    I --> P["선택: 레지스트리에 업로드"]
    J --> X["서버에서 실행 또는 전달"]
    P --> X
```

`gradlew`와 빌드 설정이 태스크를 결정하고, Gradle은 라이브러리를 해결해 Java를 `.class`로 컴파일하고 리소스를 복사한다. 테스트 통과 뒤 클래스와 리소스를 JAR로 묶는다. 서버는 JAR을 직접 실행하거나, JAR을 넣은 컨테이너 이미지를 레지스트리에서 가져올 수 있다.

“빌드 성공”이 `compileJava`, 테스트, JAR, 이미지 중 어디까지를 뜻하는지 확인한다. 이미지 생성·업로드는 선택 단계다.

Gradle은 초기화로 프로젝트를 찾고, 구성으로 태스크 그래프를 만든 뒤, 실행 단계에서 선택 태스크를 처리한다.

이 문서는 전체 개발 과정(D01 참조) 가운데 소스가 검증된 산출물로 바뀌는 빌드 구간을 다룬다.

## 2. 용어 사전

| 용어 | 한 줄 정의 | 실무 예시 | 헷갈리는 것과 차이 |
|---|---|---|---|
| 빌드(build) | 소스·설정·의존성을 처리해 검증된 산출물을 만드는 전체 절차 | `./gradlew clean build` | 컴파일보다 범위가 크며 테스트·패키징도 포함할 수 있다. |
| 컴파일(compile) | 소스 문법과 타입을 검사해 다른 표현의 코드로 변환 | `compileJava`가 `.java`를 `.class`로 변환 | Java 컴파일은 JAR 포장이 아니며, `.class`는 보통 JVM에서 실행된다. |
| 태스크(task) | Gradle의 실행 단위 | `test`, `bootJar` | `build`도 태스크이며 명령 옵션과 다르다. |
| 태스크 그래프(task graph) | 선택 태스크와 선행 조건을 방향으로 연결한 실행 계획 | `build`가 `check`, `assemble`을 끌어옴 | 텍스트로 적은 순서 목록보다 의존성에 의해 결정되는 그래프다. |
| 의존성(dependency) | 컴파일·테스트·실행에 필요한 외부 또는 다른 모듈 | Spring Boot starter | 소스의 `import`와 실제 JAR 파일을 함께 가리킬 수 있다. |
| 전이 의존성(transitive dependency) | 직접 고른 라이브러리가 다시 요구하는 라이브러리 | starter가 로깅·웹 관련 모듈을 가져옴 | 직접 선언과 달리 빌드 파일에 일일이 적지 않아도 그래프에 들어온다. |
| 의존성 해석(resolution) | 선언과 메타데이터에서 모듈 그래프·변형·파일을 결정 | 저장소에서 버전·플랫폼 선택 | 그래프 결정과 실제 아티팩트 파일 확보는 구분되는 단계다. |
| 저장소(repository) | 플러그인·라이브러리 메타데이터를 제공하는 위치 | Maven Central, 사내 Maven 저장소 | Git 소스 저장소와 다르다. |
| 아티팩트(artifact) | 이름·버전으로 교환하는 파일 | `demo-1.0.0.jar` | 빌드 산출물과 의존성 JAR이 모두 해당한다. |
| 리소스(resource) | 컴파일하지 않고 실행 때 클래스패스에 두는 파일 | `application.properties` | `processResources`가 결과 위치로 복사한다. |
| 패키징(packaging) | 클래스·리소스·필요 메타데이터를 전달 가능한 단위로 묶음 | `jar`, Spring Boot `bootJar` | 컴파일 뒤 단계다. 컨테이너 이미지 생성과도 별도다. |
| JAR | JVM 클래스·리소스를 묶는 아카이브 | `build/libs/`의 애플리케이션 파일 | 모두 실행 가능한 것은 아니다. 구조는 P05 참조. |
| 컨테이너 이미지(image) | 컨테이너를 만들 때 사용할 파일시스템·설정의 패키지 | 앱 JAR과 런타임을 포함한 이미지 | 실행 중인 컨테이너 인스턴스와 이미지 파일은 다르다. |
| 레지스트리(registry) | 컨테이너 이미지를 보관하고 배포하는 서비스 | 팀 레지스트리에 `team/api:1.2.0` 업로드 | Gradle 의존성 저장소와 목적·형식이 다르다. |
| 태그(tag) | 이미지 또는 버전을 찾기 위한 레이블 | `api:1.2.0`, `api:latest` | `latest`는 최신이라는 보증이 아니라 태그 이름이다. |
| 스냅샷(snapshot) | 최종 전의 변경 가능 버전 관례 | `1.2.0-SNAPSHOT` | Gradle 태스크가 아니며 저장소 동작을 확인한다. |
| 릴리스(release) | 외부 사용을 위해 버전·내용을 확정해 공개한 결과 | `1.2.0` | 배포(deploy)는 환경에 올리는 행위도 뜻하므로 같은 단어가 아니다. |
| 시맨틱 버저닝(SemVer) | 호환성을 MAJOR.MINOR.PATCH로 표현하는 규칙 | 호환 깨짐은 major 증가 | Gradle 버전 선택 정책과는 별개다. |
| Wrapper | 프로젝트 지정 Gradle을 실행하는 스크립트·설정 | `./gradlew` | 전역 `gradle`과 달리 버전을 맞추지만 JDK는 별도다. |
| 빌드 캐시(build cache) | 입력이 같으면 태스크 출력을 재사용하는 저장소 | 공유 캐시의 컴파일 결과 | 현재 작업공간의 증분 빌드와 다르다. |
| 증분 빌드(incremental build) | 바뀐 입력에 영향을 받는 작업만 다시 실행 | 한 파일 수정 후 일부 클래스 재컴파일 | 원격 캐시에서 다른 빌드 출력을 가져오는 것과 다르다. |
| 재현 가능한 빌드(reproducible build) | 같은 입력에서 같은 결과를 얻도록 통제한 빌드 | 고정 JDK·Gradle·의존성 | 캐시 적중과 다르며 캐시는 재현성을 보장하지 않는다. |
| CI 빌드 | 커밋을 자동으로 가져와 격리 실행하는 빌드 | PR마다 `./gradlew build` | 로컬과 환경 차이를 드러낸다. |

SemVer는 공개 API 호환성에 의미를 부여하고, Gradle은 설정과 저장소 메타데이터로 실제 모듈 파일을 선택한다. 이미지 태그와 의존성 버전도 별개다.

## 3. 단계별로 보기

### 3.1 프로젝트 준비와 그래프 구성

무엇이 일어나나: `./gradlew`가 지정 Gradle을 실행한다. 초기화 때 프로젝트를 찾고 구성 때 빌드 파일·플러그인을 평가해 태스크와 선행 관계를 등록한다. 요청 태스크에서 필요한 그래프를 고른다.

누가·도구: 개발자 또는 CI, Wrapper, Gradle 플러그인, `settings.gradle(.kts)`, `build.gradle(.kts)`.

입력·산출물: 커밋된 빌드 설정으로 그래프를 만든다. 이 단계에는 앱 JAR이 없다.

실패 신호: 배포판 다운로드 오류는 네트워크·프록시·URL을, 플러그인 미발견이나 설정 오류는 플러그인 ID·버전·저장소를 확인한다. 이는 컴파일 실패가 아니다.

초기화·구성 후 그래프가 정해진다. 실행은 선행 관계를 따르며 독립 태스크는 병렬일 수 있다.

```mermaid
    B --> C["요청 태스크와 선행 관계 분석"]

```

### 3.2 의존성 해석과 확보

무엇이 일어나나: 선언·버전 제약·메타데이터에서 모듈 그래프를 해석하고 필요한 변형과 파일을 저장소 또는 로컬 캐시에서 가져온다. 전이 의존성도 포함된다. 테스트 의존성은 테스트 태스크가 필요할 때 해결될 수 있다.

누가·도구: Gradle 의존성 엔진, `repositories`, 인증 정보, 로컬 의존성 캐시.

입력·산출물: 의존성 선언과 저장소 메타데이터에서 모듈 버전·변형·JAR을 고른다. 잠금 파일은 해석 버전을 기록해 선택 변화를 줄이지만 파일 무결성이나 저장소 가용성은 보장하지 않는다.

실패 신호: `Could not resolve/find`, `401/403`, `PKIX`, `No matching variant`를 본다. 좌표·저장소, 네트워크·인증, 인증서, 플랫폼 변형을 점검하고 컴파일 전에 실패했는지 확인한다.

### 3.3 컴파일과 리소스 처리

무엇이 일어나나: `compileJava`가 `javac`로 소스·타입을 검사해 `.class`를 만든다. 클래스패스 라이브러리는 심볼 확인에 쓰인다. Toolchain과 소스 호환성 설정이 어긋나면 JDK별 API·바이트코드 문제가 생긴다. `processResources`는 설정·템플릿을 출력 디렉터리에 복사한다.

누가·도구: Gradle Java 플러그인, Java Toolchain, JDK.

입력·산출물: 기본 경로는 프로덕션 클래스 `build/classes/java/main`, 리소스 `build/resources/main`, 테스트 클래스 `build/classes/java/test`, 테스트 리소스 `build/resources/test`다. source set 설정으로 바뀔 수 있다.

실패 신호: `cannot find symbol`, `incompatible types`, `invalid source release`와 파일·줄을 확인한다. `compileJava`/`compileTestJava`를 구분하고 JDK·클래스패스를 본다. 리소스 오류는 파일 충돌·권한·필터 설정을 본다.

### 3.4 테스트와 패키징

무엇이 일어나나: 테스트 코드를 컴파일한 뒤 `test`가 프레임워크를 실행한다. 실패하면 `build`가 중단될 수 있고, 통과하면 `jar` 또는 Boot 플러그인의 실행 JAR 태스크가 패키징한다.

누가·도구: Gradle `test`, `check`, `jar`, Boot `bootJar`, 테스트 엔진. `build`는 검증과 조립을 모은다.

입력·산출물: 보고서는 `build/reports/tests/test/`, JAR은 설정에 따라 `build/libs/`에 놓인다. 실행 JAR 파일명은 디렉터리에서 확인한다.

실패 신호: 실패 테스트명과 assertion을 찾고 HTML 보고서의 예외를 본다. `compileTestJava` 실패와 실행 중 `test` 실패를 구분한다.

대표 관계는 다음과 같다. 플러그인과 프로젝트 설정에 따라 실제 그래프는 다르다. `--dry-run`은 계획을 보여주지만 태스크를 실행하지 않는다.

```mermaid
flowchart LR
    CJ["compileJava"] --> CL["classes"]
    PR["processResources"] --> CL
    CL --> JAR["jar 또는 bootJar"]
    CL --> CTJ["compileTestJava"]
    PTR["processTestResources"] --> TC["testClasses"]
    CTJ --> TC
    TC --> TEST["test"]
    TEST --> CHECK["check"]
    JAR --> ASM["assemble"]
    CHECK --> BUILD["build"]
    ASM --> BUILD
```


### 3.5 컨테이너 이미지와 레지스트리

무엇이 일어나나: 선택 단계다. Docker 빌더가 컨텍스트·Dockerfile을 처리해 이미지를 만들고, `push`는 태그를 붙인 이미지를 레지스트리에 올린다.

누가·도구: Docker CLI/BuildKit, Dockerfile, `.dockerignore`, 이미지 레지스트리. 앱 빌드 성공이 이미지 생성 성공을 뜻하지는 않는다.

입력·산출물: JAR·Dockerfile·기반 이미지가 로컬 이미지를 만든다. 업로드할 때 대상 레지스트리·태그·권한을 확인한다.

실패 신호: `failed to solve`는 이미지 빌드 단계, `unauthorized`/`denied`는 레지스트리 연결·인증·쓰기 권한을 확인한다.

로컬과 CI의 코드 처리 경로는 다음과 같다.

```mermaid
sequenceDiagram

    participant CI as "CI 작업자"

    participant Reg as "이미지 레지스트리"
    Dev->>Dev: "Wrapper와 JDK로 로컬 빌드"
    Dev->>Git: "변경사항 커밋과 push"
    Git->>CI: "동일 커밋 checkout"
    CI->>Repo: "플러그인·의존성 해석"
    Repo-->>CI: "선택된 파일 반환"
    CI->>CI: "컴파일, 테스트, JAR 생성"
    CI->>Reg: "선택: 이미지 업로드"
    Reg-->>CI: "업로드 결과와 이미지 참조"
```

### 3.6 실패 종류와 로그를 읽는 순서

최초 실패 태스크와 그 원인을 기준으로 분류한다. `BUILD FAILED`만 보지 않는다.

| 분류 | 눈에 띄는 첫 신호 | 먼저 확인할 것 |
|---|---|---|
| 설정·플러그인 | settings 평가 오류, 플러그인 미발견 | Wrapper, 플러그인 ID·버전, 저장소, 설정 파일의 구문 |
| 의존성 해석 | `Could not resolve/find`, HTTP 상태코드 | 좌표·버전·저장소 URL·네트워크·자격 증명·변형 속성 |
| 컴파일 | `compileJava` 또는 `compileTestJava`, javac 오류 줄 번호 | 최초 진단 줄, JDK/toolchain, 컴파일 클래스패스, 생성 코드 |
| 테스트 | `:test` 실패, 실패 테스트 이름·assertion | 최초 실패와 원인 예외, 보고서, CI에서만 다른 설정·시간·외부 서비스 |
| 패키징 | `jar`/`bootJar` 실패, 파일 충돌·권한 | 입력 디렉터리, 중복 리소스, 출력 파일 경로·권한 |
| 메모리 | `Java heap space`, `GC overhead`, daemon/worker 종료 | 어느 JVM(Gradle daemon·컴파일러·테스트)이 메모리를 쓰는지, CI 메모리 한도와 로그 앞부분 |
| 이미지·업로드 | Docker 단계 실패, `unauthorized`/`denied` | 이미지 빌더와 Dockerfile, 빌드 컨텍스트, 태그, 레지스트리 인증·권한 |

선행 `compileJava` 오류로 후속 태스크가 실패했다면 독립 오류 하나로 센다. `--info`는 단서를 늘리지만 로그 공유 전 민감한 환경값을 확인한다.

## 4. 직접 해보기

프로젝트 이름을 `demo`로 한 Spring Boot 4.1.1, Java 25, Gradle Wrapper 프로젝트에서 실습한다. 아래는 Boot 플러그인과 Java Toolchain 설정의 핵심이다. 의존성 버전은 Gradle BOM 지원 또는 의존성 관리 플러그인으로 맞춘다.

```kotlin
plugins {
    java
    id("org.springframework.boot") version "4.1.1"
}

group = "com.example"
version = "0.0.1-SNAPSHOT"

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(25)
    }
}
```

명령은 프로젝트 루트에서 실행한다. macOS/Linux 기준이며 Windows는 `gradlew.bat`를 사용한다.

```bash
java -version
./gradlew --version
./gradlew tasks --all
./gradlew clean build --dry-run
```

첫 명령들로 Java·Gradle 버전과 등록된 태스크를 확인한다. `--dry-run`은 `clean build`의 실행 계획만 출력하므로 산출물을 만들지는 않는다.

이제 전체 흐름을 실제로 돈다.

```bash
./gradlew clean build --info
find build/classes build/resources build/libs build/reports/tests -type f -print
```

`clean`은 이전 출력을 지운다. 성공 뒤 클래스·리소스·JAR·테스트 보고서를 확인한다. 경로는 프로젝트 설정에 따라 달라질 수 있다. 실패하면 `--info`에서 첫 실패 태스크를 찾아 3.6절 기준으로 분류한다. `build/`은 다시 만들 수 있는 출력이다.

이 설정대로 `demo` 프로젝트를 만들면 Boot 실행 JAR을 다음처럼 실행한다. 다른 이름이나 버전을 택했다면 `build/libs/`에서 파일명을 확인한다.

```bash
java -jar build/libs/demo-0.0.1-SNAPSHOT.jar
```

별도 Dockerfile이 준비되어 있다면 이미지 생성과 태깅은 다음처럼 시험한다. `registry.example.com/team/demo`는 예시 주소이므로 실제 업로드에는 팀이 승인한 레지스트리와 로그인 정보가 필요하다.

```bash
docker build -t registry.example.com/team/demo:1.0.0 .
docker image ls registry.example.com/team/demo
docker push registry.example.com/team/demo:1.0.0
```

`docker build`는 로컬 이미지 생성, `docker push`는 레지스트리 업로드다. 커밋과 릴리스 태그를 기록한다. 업로드는 선택 실습이다.

이 실습에서 가장 재현성 높은 기본 선택은 커밋된 Wrapper(`./gradlew`)와 Java 25 Toolchain, 고정된 릴리스 버전 의존성을 사용하고 PR CI에서 `clean build`를 실행하는 것이다. Wrapper는 Gradle 버전을 맞추지만 JDK 선택, 의존성 그래프, 환경변수, 운영체제 차이까지 자동으로 고정하지는 않는다. 동적 버전을 쓰면 의존성 잠금을 검토하고, 빌드 캐시는 성능을 위한 옵션으로 취급한다.

Gradle/Maven 빌드 파일 작성 실무 → P08 참조. JAR 내부 구조 → P05 참조. 이미지 모범 사례·패키징 배포 → S19 참조.

## 5. 자주 하는 오해와 실수

1. **“컴파일되면 빌드도 끝났다” →** `.class`는 중간 산출물일 뿐이다. 테스트와 패키징은 아직 실패할 수 있다. 배포 기준이 `build` 통과인지 이미지 게시까지인지 CI 파이프라인 이름과 태스크를 확인한다.

2. **“`build`는 한 개의 명령 태스크만 돈다” →** 생명주기 태스크가 플러그인에서 추가한 검증·조립 태스크를 그래프로 끌어온다. `./gradlew build --dry-run`으로 실제 프로젝트의 선택 흐름을 확인한다.

3. **“내 PC에서 성공했으니 CI도 성공한다” →** 로컬 미커밋 파일, 다른 JDK, 환경변수, OS 파일명 대소문자, 캐시가 성공을 가릴 수 있다. Wrapper와 Toolchain을 사용하고 깨끗한 checkout의 CI 결과를 기준으로 삼는다.

4. **“버전 문자열을 적었으니 의존성도 늘 같다” →** 동적 버전, 저장소 메타데이터 변경, 전이 의존성 선택은 다른 시점에 달라질 수 있다. 릴리스용 버전을 고정하고 필요한 경우 lock 파일을 커밋한다.

5. **“캐시를 끄면 재현 가능한 빌드가 된다” →** 캐시는 동일 입력으로 태스크 출력을 재사용하는 최적화다. 입력이 흔들리거나 시스템 시각·환경변수에 결과가 의존하면 캐시와 무관하게 결과가 달라질 수 있다. 입력을 명시하고 버전·환경부터 통제한다.

6. **“CI에서 테스트 실패는 컴파일 오류다” →** 컴파일 성공 후 테스트 assertion이나 통합 환경 문제로 실패할 수 있다. 실패 태스크가 `compileTestJava`인지 `test`인지 확인하고 테스트 보고서를 본다.

7. **“JAR과 컨테이너 이미지가 같은 배포물이다” →** JAR은 JVM 애플리케이션 아카이브이고, 이미지에는 실행 기반 환경과 이미지 설정도 들어간다. 어느 산출물을 운영에 전달하는지 배포 계약과 태그를 확인한다.

## 7. 자가점검 Q&A (면접 대비)

### Q1. 컴파일과 빌드는 어떻게 다른가?

컴파일은 소스 코드를 `.class` 같은 형식으로 바꾸는 한 작업이다. 빌드는 의존성 준비, 컴파일, 리소스 처리, 테스트, 패키징처럼 더 넓은 절차를 포함한다. 그래서 `compileJava`가 성공해도 테스트나 `bootJar`는 실패할 수 있다.

**꼬리질문: 컴파일 성공 후 배포 파일이 없으면 어디를 볼까?**

`test`, `jar` 또는 `bootJar`가 실행됐는지와 최초 실패 태스크를 확인한다. 클래스 파일만 생긴 것은 JAR 생성 여부를 보장하지 않는다.

### Q2. Gradle에서 `build`를 실행할 때 내부적으로 어떤 순서가 있는가?

먼저 프로젝트를 초기화하고 빌드 파일을 구성해 태스크 그래프를 결정한다. 선택된 태스크는 선행 관계에 맞춰 실행되고, 독립적인 작업은 병렬일 수 있다. 실제 순서는 그래프와 플러그인에 따라 달라진다.

**꼬리질문: `build` 전에 `test`를 명령줄에 먼저 쓰면 항상 테스트가 먼저일까?**

그렇지 않다. 선택된 태스크들의 의존 관계가 순서를 결정하므로 `--dry-run` 출력으로 해당 프로젝트의 계획을 본다.

### Q3. 전이 의존성은 무엇이며 왜 문제가 되나?

직접 선택한 모듈이 필요로 해 함께 선택되는 라이브러리다. 선언을 줄여주지만 직접 보이지 않는 버전 충돌이나 갑작스러운 그래프 변화의 원인이 될 수 있다. 의존성 보고와 잠금 파일로 실제 선택 결과를 확인한다.

**꼬리질문: 저장소에 JAR이 있는데도 의존성 해석이 실패할 수 있나?**

가능하다. 메타데이터·버전·변형이 요청과 맞지 않거나 인증·저장소 설정이 잘못됐을 수 있다. Gradle은 단순 파일 검색 외에 그래프와 변형도 해석한다.

### Q4. “로컬에서는 되는데 CI에서는 실패”할 때 무엇을 비교할까?

같은 커밋을 빌드하는지부터 확인한다. 이어 Wrapper, JDK/toolchain, 잠금 의존성, OS, 환경변수, 시크릿, 네트워크·저장소 설정을 비교한다. 로컬 캐시나 미커밋 파일 때문에 숨겨진 차이도 찾는다.

**꼬리질문: Wrapper만 커밋하면 재현성이 확보되나?**

아니다. Wrapper는 Gradle 배포판을 통일하지만 JDK와 의존성 선택은 별도 관리가 필요하다. 입력을 더 고정하고 깨끗한 CI 결과를 확인해야 한다.

### Q5. 빌드 캐시와 증분 빌드가 같은 말인가?

아니다. 증분 빌드는 현재 작업공간에서 바뀐 입력의 영향 범위만 다시 처리하는 최적화다. 빌드 캐시는 이전 실행 출력과 현재 입력을 비교해 로컬 또는 원격 저장소에서 태스크 결과를 재사용한다. 둘 다 시간을 줄이지만 정확한 입력 정의가 전제다.

**꼬리질문: 캐시를 비우면 비결정적인 빌드가 해결되나?**

아니다. 시각·환경값·동적 의존성 같은 입력 자체가 달라지는 원인을 고쳐야 한다. 캐시 삭제는 원인 진단 수단일 뿐 재현성 보장은 아니다.

### Q6. JAR과 컨테이너 이미지는 어떤 관계인가?

JAR은 애플리케이션 클래스와 리소스를 담은 아카이브다. 컨테이너 이미지 빌드에서는 JAR을 파일시스템에 넣고 런타임·시작 설정과 결합할 수 있다. 따라서 이미지 생성과 레지스트리 업로드는 JAR 패키징 이후의 별도 선택 단계다.

**꼬리질문: 이미지 생성은 성공하고 업로드는 실패했다면 코드 결함일까?**

대개 레지스트리 연결, 인증, 권한, 태그 주소 문제다. 이미지가 로컬에 존재하는지와 push 로그의 첫 실패를 분리해 본다.

D04. 빌드란 무엇인가

#D04. 빌드란 무엇인가 — 소스 코드가 실행 파일·이미지가 되기까지

원문 전체 · 코드·버전별 변화·실무 가이드·참고문헌

빌드는 코드를 컴파일하는 한 단계가 아니라, 선언된 입력을 검증하고 실행·배포 가능한 산출물로 바꾸는 자동화 과정이다. Gradle은 먼저 프로젝트와 태스크 그래프를 준비한 다음 필요한 태스크를 의존성 순서대로 실행한다. 로컬과 CI의 차이는 대개 JDK·의존성·환경변수·커밋 상태·캐시 입력이 서로 다른 데서 시작한다.

gradlew와 빌드 설정이 태스크를 결정하고, Gradle은 라이브러리를 해결해 Java를 .class로 컴파일하고 리소스를 복사한다. 테스트 통과 뒤 클래스와 리소스를 JAR로 묶는다. 서버는 JAR을 직접 실행하거나, JAR을 넣은 컨테이너 이미지를 레지스트리에서 가져올 수 있다.

“빌드 성공”이 compileJava, 테스트, JAR, 이미지 중 어디까지를 뜻하는지 확인한다. 이미지 생성·업로드는 선택 단계다.

Gradle은 초기화로 프로젝트를 찾고, 구성으로 태스크 그래프를 만든 뒤, 실행 단계에서 선택 태스크를 처리한다.

이 문서는 전체 개발 과정(D01 참조) 가운데 소스가 검증된 산출물로 바뀌는 빌드 구간을 다룬다.

022. 용어 사전열기 ↓
용어 한 줄 정의 실무 예시 헷갈리는 것과 차이
빌드(build) 소스·설정·의존성을 처리해 검증된 산출물을 만드는 전체 절차 ./gradlew clean build 컴파일보다 범위가 크며 테스트·패키징도 포함할 수 있다.
컴파일(compile) 소스 문법과 타입을 검사해 다른 표현의 코드로 변환 compileJava가 .java를 .class로 변환 Java 컴파일은 JAR 포장이 아니며, .class는 보통 JVM에서 실행된다.
태스크(task) Gradle의 실행 단위 test, bootJar build도 태스크이며 명령 옵션과 다르다.
태스크 그래프(task graph) 선택 태스크와 선행 조건을 방향으로 연결한 실행 계획 build가 check, assemble을 끌어옴 텍스트로 적은 순서 목록보다 의존성에 의해 결정되는 그래프다.
의존성(dependency) 컴파일·테스트·실행에 필요한 외부 또는 다른 모듈 Spring Boot starter 소스의 import와 실제 JAR 파일을 함께 가리킬 수 있다.
전이 의존성(transitive dependency) 직접 고른 라이브러리가 다시 요구하는 라이브러리 starter가 로깅·웹 관련 모듈을 가져옴 직접 선언과 달리 빌드 파일에 일일이 적지 않아도 그래프에 들어온다.
의존성 해석(resolution) 선언과 메타데이터에서 모듈 그래프·변형·파일을 결정 저장소에서 버전·플랫폼 선택 그래프 결정과 실제 아티팩트 파일 확보는 구분되는 단계다.
저장소(repository) 플러그인·라이브러리 메타데이터를 제공하는 위치 Maven Central, 사내 Maven 저장소 Git 소스 저장소와 다르다.
아티팩트(artifact) 이름·버전으로 교환하는 파일 demo-1.0.0.jar 빌드 산출물과 의존성 JAR이 모두 해당한다.
리소스(resource) 컴파일하지 않고 실행 때 클래스패스에 두는 파일 application.properties processResources가 결과 위치로 복사한다.
패키징(packaging) 클래스·리소스·필요 메타데이터를 전달 가능한 단위로 묶음 jar, Spring Boot bootJar 컴파일 뒤 단계다. 컨테이너 이미지 생성과도 별도다.
JAR JVM 클래스·리소스를 묶는 아카이브 build/libs/의 애플리케이션 파일 모두 실행 가능한 것은 아니다. 구조는 P05 참조.
컨테이너 이미지(image) 컨테이너를 만들 때 사용할 파일시스템·설정의 패키지 앱 JAR과 런타임을 포함한 이미지 실행 중인 컨테이너 인스턴스와 이미지 파일은 다르다.
레지스트리(registry) 컨테이너 이미지를 보관하고 배포하는 서비스 팀 레지스트리에 team/api:1.2.0 업로드 Gradle 의존성 저장소와 목적·형식이 다르다.
태그(tag) 이미지 또는 버전을 찾기 위한 레이블 api:1.2.0, api:latest latest는 최신이라는 보증이 아니라 태그 이름이다.
스냅샷(snapshot) 최종 전의 변경 가능 버전 관례 1.2.0-SNAPSHOT Gradle 태스크가 아니며 저장소 동작을 확인한다.
릴리스(release) 외부 사용을 위해 버전·내용을 확정해 공개한 결과 1.2.0 배포(deploy)는 환경에 올리는 행위도 뜻하므로 같은 단어가 아니다.
시맨틱 버저닝(SemVer) 호환성을 MAJOR.MINOR.PATCH로 표현하는 규칙 호환 깨짐은 major 증가 Gradle 버전 선택 정책과는 별개다.
Wrapper 프로젝트 지정 Gradle을 실행하는 스크립트·설정 ./gradlew 전역 gradle과 달리 버전을 맞추지만 JDK는 별도다.
빌드 캐시(build cache) 입력이 같으면 태스크 출력을 재사용하는 저장소 공유 캐시의 컴파일 결과 현재 작업공간의 증분 빌드와 다르다.
증분 빌드(incremental build) 바뀐 입력에 영향을 받는 작업만 다시 실행 한 파일 수정 후 일부 클래스 재컴파일 원격 캐시에서 다른 빌드 출력을 가져오는 것과 다르다.
재현 가능한 빌드(reproducible build) 같은 입력에서 같은 결과를 얻도록 통제한 빌드 고정 JDK·Gradle·의존성 캐시 적중과 다르며 캐시는 재현성을 보장하지 않는다.
CI 빌드 커밋을 자동으로 가져와 격리 실행하는 빌드 PR마다 ./gradlew build 로컬과 환경 차이를 드러낸다.

SemVer는 공개 API 호환성에 의미를 부여하고, Gradle은 설정과 저장소 메타데이터로 실제 모듈 파일을 선택한다. 이미지 태그와 의존성 버전도 별개다.

013.1 프로젝트 준비와 그래프 구성↘

무엇이 일어나나: ./gradlew가 지정 Gradle을 실행한다. 초기화 때 프로젝트를 찾고 구성 때 빌드 파일·플러그인을 평가해 태스크와 선행 관계를 등록한다. 요청 태스크에서 필요한 그래프를 고른다.

누가·도구: 개발자 또는 CI, Wrapper, Gradle 플러그인, settings.gradle(.kts), build.gradle(.kts).

입력·산출물: 커밋된 빌드 설정으로 그래프를 만든다. 이 단계에는 앱 JAR이 없다.

실패 신호: 배포판 다운로드 오류는 네트워크·프록시·URL을, 플러그인 미발견이나 설정 오류는 플러그인 ID·버전·저장소를 확인한다. 이는 컴파일 실패가 아니다.

초기화·구성 후 그래프가 정해진다. 실행은 선행 관계를 따르며 독립 태스크는 병렬일 수 있다.

    E --> F
023.2 의존성 해석과 확보↘

무엇이 일어나나: 선언·버전 제약·메타데이터에서 모듈 그래프를 해석하고 필요한 변형과 파일을 저장소 또는 로컬 캐시에서 가져온다. 전이 의존성도 포함된다. 테스트 의존성은 테스트 태스크가 필요할 때 해결될 수 있다.

누가·도구: Gradle 의존성 엔진, repositories, 인증 정보, 로컬 의존성 캐시.

입력·산출물: 의존성 선언과 저장소 메타데이터에서 모듈 버전·변형·JAR을 고른다. 잠금 파일은 해석 버전을 기록해 선택 변화를 줄이지만 파일 무결성이나 저장소 가용성은 보장하지 않는다.

실패 신호: Could not resolve/find, 401/403, PKIX, No matching variant를 본다. 좌표·저장소, 네트워크·인증, 인증서, 플랫폼 변형을 점검하고 컴파일 전에 실패했는지 확인한다.

033.3 컴파일과 리소스 처리↘

무엇이 일어나나: compileJava가 javac로 소스·타입을 검사해 .class를 만든다. 클래스패스 라이브러리는 심볼 확인에 쓰인다. Toolchain과 소스 호환성 설정이 어긋나면 JDK별 API·바이트코드 문제가 생긴다. processResources는 설정·템플릿을 출력 디렉터리에 복사한다.

누가·도구: Gradle Java 플러그인, Java Toolchain, JDK.

입력·산출물: 기본 경로는 프로덕션 클래스 build/classes/java/main, 리소스 build/resources/main, 테스트 클래스 build/classes/java/test, 테스트 리소스 build/resources/test다. source set 설정으로 바뀔 수 있다.

실패 신호: cannot find symbol, incompatible types, invalid source release와 파일·줄을 확인한다. compileJava/compileTestJava를 구분하고 JDK·클래스패스를 본다. 리소스 오류는 파일 충돌·권한·필터 설정을 본다.

043.4 테스트와 패키징↘

무엇이 일어나나: 테스트 코드를 컴파일한 뒤 test가 프레임워크를 실행한다. 실패하면 build가 중단될 수 있고, 통과하면 jar 또는 Boot 플러그인의 실행 JAR 태스크가 패키징한다.

누가·도구: Gradle test, check, jar, Boot bootJar, 테스트 엔진. build는 검증과 조립을 모은다.

입력·산출물: 보고서는 build/reports/tests/test/, JAR은 설정에 따라 build/libs/에 놓인다. 실행 JAR 파일명은 디렉터리에서 확인한다.

실패 신호: 실패 테스트명과 assertion을 찾고 HTML 보고서의 예외를 본다. compileTestJava 실패와 실행 중 test 실패를 구분한다.

대표 관계는 다음과 같다. 플러그인과 프로젝트 설정에 따라 실제 그래프는 다르다. --dry-run은 계획을 보여주지만 태스크를 실행하지 않는다.

flowchart LR
    CJ["compileJava"] --> CL["classes"]
    PR["processResources"] --> CL
    CL --> JAR["jar 또는 bootJar"]
    CL --> CTJ["compileTestJava"]
    PTR["processTestResources"] --> TC["testClasses"]
    CTJ --> TC
    TC --> TEST["test"]
    TEST --> CHECK["check"]
    JAR --> ASM["assemble"]
    CHECK --> BUILD["build"]
    ASM --> BUILD
053.5 컨테이너 이미지와 레지스트리↘

무엇이 일어나나: 선택 단계다. Docker 빌더가 컨텍스트·Dockerfile을 처리해 이미지를 만들고, push는 태그를 붙인 이미지를 레지스트리에 올린다.

누가·도구: Docker CLI/BuildKit, Dockerfile, .dockerignore, 이미지 레지스트리. 앱 빌드 성공이 이미지 생성 성공을 뜻하지는 않는다.

입력·산출물: JAR·Dockerfile·기반 이미지가 로컬 이미지를 만든다. 업로드할 때 대상 레지스트리·태그·권한을 확인한다.

실패 신호: failed to solve는 이미지 빌드 단계, unauthorized/denied는 레지스트리 연결·인증·쓰기 권한을 확인한다.

044. 직접 해보기5개 코드 · 열기 ↓

프로젝트 이름을 demo로 한 Spring Boot 4.1.1, Java 25, Gradle Wrapper 프로젝트에서 실습한다. 아래는 Boot 플러그인과 Java Toolchain 설정의 핵심이다. 의존성 버전은 Gradle BOM 지원 또는 의존성 관리 플러그인으로 맞춘다.

plugins {
    java
    id("org.springframework.boot") version "4.1.1"
}

group = "com.example"
version = "0.0.1-SNAPSHOT"

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(25)
    }
}

명령은 프로젝트 루트에서 실행한다. macOS/Linux 기준이며 Windows는 gradlew.bat를 사용한다.

java -version
./gradlew --version
./gradlew tasks --all
./gradlew clean build --dry-run

첫 명령들로 Java·Gradle 버전과 등록된 태스크를 확인한다. --dry-run은 clean build의 실행 계획만 출력하므로 산출물을 만들지는 않는다.

이제 전체 흐름을 실제로 돈다.

./gradlew clean build --info
find build/classes build/resources build/libs build/reports/tests -type f -print

clean은 이전 출력을 지운다. 성공 뒤 클래스·리소스·JAR·테스트 보고서를 확인한다. 경로는 프로젝트 설정에 따라 달라질 수 있다. 실패하면 --info에서 첫 실패 태스크를 찾아 3.6절 기준으로 분류한다. build/은 다시 만들 수 있는 출력이다.

이 설정대로 demo 프로젝트를 만들면 Boot 실행 JAR을 다음처럼 실행한다. 다른 이름이나 버전을 택했다면 build/libs/에서 파일명을 확인한다.

java -jar build/libs/demo-0.0.1-SNAPSHOT.jar

별도 Dockerfile이 준비되어 있다면 이미지 생성과 태깅은 다음처럼 시험한다. registry.example.com/team/demo는 예시 주소이므로 실제 업로드에는 팀이 승인한 레지스트리와 로그인 정보가 필요하다.

docker build -t registry.example.com/team/demo:1.0.0 .
docker image ls registry.example.com/team/demo
docker push registry.example.com/team/demo:1.0.0

docker build는 로컬 이미지 생성, docker push는 레지스트리 업로드다. 커밋과 릴리스 태그를 기록한다. 업로드는 선택 실습이다.

이 실습에서 가장 재현성 높은 기본 선택은 커밋된 Wrapper(./gradlew)와 Java 25 Toolchain, 고정된 릴리스 버전 의존성을 사용하고 PR CI에서 clean build를 실행하는 것이다. Wrapper는 Gradle 버전을 맞추지만 JDK 선택, 의존성 그래프, 환경변수, 운영체제 차이까지 자동으로 고정하지는 않는다. 동적 버전을 쓰면 의존성 잠금을 검토하고, 빌드 캐시는 성능을 위한 옵션으로 취급한다.

Gradle/Maven 빌드 파일 작성 실무 → P08 참조. JAR 내부 구조 → P05 참조. 이미지 모범 사례·패키징 배포 → S19 참조.

055. 자주 하는 오해와 실수열기 ↓

  1. “컴파일되면 빌드도 끝났다” → .class는 중간 산출물일 뿐이다. 테스트와 패키징은 아직 실패할 수 있다. 배포 기준이 build 통과인지 이미지 게시까지인지 CI 파이프라인 이름과 태스크를 확인한다.

  2. “build는 한 개의 명령 태스크만 돈다” → 생명주기 태스크가 플러그인에서 추가한 검증·조립 태스크를 그래프로 끌어온다. ./gradlew build --dry-run으로 실제 프로젝트의 선택 흐름을 확인한다.

  3. “내 PC에서 성공했으니 CI도 성공한다” → 로컬 미커밋 파일, 다른 JDK, 환경변수, OS 파일명 대소문자, 캐시가 성공을 가릴 수 있다. Wrapper와 Toolchain을 사용하고 깨끗한 checkout의 CI 결과를 기준으로 삼는다.

  4. “버전 문자열을 적었으니 의존성도 늘 같다” → 동적 버전, 저장소 메타데이터 변경, 전이 의존성 선택은 다른 시점에 달라질 수 있다. 릴리스용 버전을 고정하고 필요한 경우 lock 파일을 커밋한다.

  5. “캐시를 끄면 재현 가능한 빌드가 된다” → 캐시는 동일 입력으로 태스크 출력을 재사용하는 최적화다. 입력이 흔들리거나 시스템 시각·환경변수에 결과가 의존하면 캐시와 무관하게 결과가 달라질 수 있다. 입력을 명시하고 버전·환경부터 통제한다.

  6. “CI에서 테스트 실패는 컴파일 오류다” → 컴파일 성공 후 테스트 assertion이나 통합 환경 문제로 실패할 수 있다. 실패 태스크가 compileTestJava인지 test인지 확인하고 테스트 보고서를 본다.

  7. “JAR과 컨테이너 이미지가 같은 배포물이다” → JAR은 JVM 애플리케이션 아카이브이고, 이미지에는 실행 기반 환경과 이미지 설정도 들어간다. 어느 산출물을 운영에 전달하는지 배포 계약과 태그를 확인한다.

01Q1. 컴파일과 빌드는 어떻게 다른가?↘

컴파일은 소스 코드를 .class 같은 형식으로 바꾸는 한 작업이다. 빌드는 의존성 준비, 컴파일, 리소스 처리, 테스트, 패키징처럼 더 넓은 절차를 포함한다. 그래서 compileJava가 성공해도 테스트나 bootJar는 실패할 수 있다.

꼬리질문: 컴파일 성공 후 배포 파일이 없으면 어디를 볼까?

test, jar 또는 bootJar가 실행됐는지와 최초 실패 태스크를 확인한다. 클래스 파일만 생긴 것은 JAR 생성 여부를 보장하지 않는다.

02Q2. Gradle에서 build를 실행할 때 내부적으로 어떤 순서가 있는가?↘

먼저 프로젝트를 초기화하고 빌드 파일을 구성해 태스크 그래프를 결정한다. 선택된 태스크는 선행 관계에 맞춰 실행되고, 독립적인 작업은 병렬일 수 있다. 실제 순서는 그래프와 플러그인에 따라 달라진다.

꼬리질문: build 전에 test를 명령줄에 먼저 쓰면 항상 테스트가 먼저일까?

그렇지 않다. 선택된 태스크들의 의존 관계가 순서를 결정하므로 --dry-run 출력으로 해당 프로젝트의 계획을 본다.

03Q3. 전이 의존성은 무엇이며 왜 문제가 되나?↘

직접 선택한 모듈이 필요로 해 함께 선택되는 라이브러리다. 선언을 줄여주지만 직접 보이지 않는 버전 충돌이나 갑작스러운 그래프 변화의 원인이 될 수 있다. 의존성 보고와 잠금 파일로 실제 선택 결과를 확인한다.

꼬리질문: 저장소에 JAR이 있는데도 의존성 해석이 실패할 수 있나?

가능하다. 메타데이터·버전·변형이 요청과 맞지 않거나 인증·저장소 설정이 잘못됐을 수 있다. Gradle은 단순 파일 검색 외에 그래프와 변형도 해석한다.

04Q4. “로컬에서는 되는데 CI에서는 실패”할 때 무엇을 비교할까?↘

같은 커밋을 빌드하는지부터 확인한다. 이어 Wrapper, JDK/toolchain, 잠금 의존성, OS, 환경변수, 시크릿, 네트워크·저장소 설정을 비교한다. 로컬 캐시나 미커밋 파일 때문에 숨겨진 차이도 찾는다.

꼬리질문: Wrapper만 커밋하면 재현성이 확보되나?

아니다. Wrapper는 Gradle 배포판을 통일하지만 JDK와 의존성 선택은 별도 관리가 필요하다. 입력을 더 고정하고 깨끗한 CI 결과를 확인해야 한다.

05Q5. 빌드 캐시와 증분 빌드가 같은 말인가?↘

아니다. 증분 빌드는 현재 작업공간에서 바뀐 입력의 영향 범위만 다시 처리하는 최적화다. 빌드 캐시는 이전 실행 출력과 현재 입력을 비교해 로컬 또는 원격 저장소에서 태스크 결과를 재사용한다. 둘 다 시간을 줄이지만 정확한 입력 정의가 전제다.

꼬리질문: 캐시를 비우면 비결정적인 빌드가 해결되나?

아니다. 시각·환경값·동적 의존성 같은 입력 자체가 달라지는 원인을 고쳐야 한다. 캐시 삭제는 원인 진단 수단일 뿐 재현성 보장은 아니다.

06Q6. JAR과 컨테이너 이미지는 어떤 관계인가?↘

JAR은 애플리케이션 클래스와 리소스를 담은 아카이브다. 컨테이너 이미지 빌드에서는 JAR을 파일시스템에 넣고 런타임·시작 설정과 결합할 수 있다. 따라서 이미지 생성과 레지스트리 업로드는 JAR 패키징 이후의 별도 선택 단계다.

꼬리질문: 이미지 생성은 성공하고 업로드는 실패했다면 코드 결함일까?

대개 레지스트리 연결, 인증, 권한, 태그 주소 문제다. 이미지가 로컬에 존재하는지와 push 로그의 첫 실패를 분리해 본다.
