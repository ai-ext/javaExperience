P20. JPA 엔티티·연관관계 매핑 따라 하기

#P20. JPA 엔티티·연관관계 매핑 따라 하기

원문 전체 · 긴 코드·심화·자가점검·참고문헌

엔티티는 자바 객체와 테이블 사이의 상태·식별자·관계를 선언한다. 연관관계에서는 FK를 쓰는 @ManyToOne 쪽을 주인으로 둔다. 기본 추천은 LAZY, 명시적 제약, DTO 응답, 제한된 범위의 cascade다.

011. 한 줄로 말하면열기 ↓

JPA 엔티티는 @Entity가 붙은 non-final 클래스이며, public/protected 무인자 생성자, @Id, persistent 필드를 가진다. 연관관계는 객체 참조를 외래 키로 매핑하는 선언이다. 엔티티를 API 응답으로 직접 반환하면 지연 로딩, 순환 JSON, 내부 필드 노출이 생기므로 DTO로 경계를 둔다.

022. 당장 알아야 할 것2.1 최소 엔티티 · 2.2 ID와 기본 타입 · 2.3 감사 필드 · 2.4 연관관계의 주인2개 코드 · 열기 ↓
012.1 최소 엔티티↘

JPA 3.2의 엔티티 조건은 non-final 클래스, public/protected 무인자 생성자, final이 아닌 persistent 필드/메서드다. 필드에 매핑 애노테이션을 두는 field access를 예제로 사용한다.

@Table을 생략하면 naming strategy의 영향을 받는다. 운영 스키마와 이름을 계약해야 하면 이름을 직접 적는다. nullable=false는 DB에도 실제 NOT NULL이 생겼는지 DDL로 확인한다.

022.2 ID와 기본 타입↘
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "order_seq")
@SequenceGenerator(name = "order_seq", sequenceName = "orders_seq", allocationSize = 50)
private Long sequenceId;

@Column(nullable = false, precision = 19, scale = 2)
private BigDecimal amount;                 // 금액에 double을 쓰지 않는다
private LocalDate deliveryDate;
private LocalDateTime createdAt;

@Enumerated(EnumType.STRING)
@Column(nullable = false, length = 20)
private OrderStatus status;

@Lob
private String memo;

IDENTITY는 INSERT 때 DB가 키를 만든다. SEQUENCE는 DB 시퀀스에서 키를 먼저 얻는다. AUTO는 구현체에 맡기므로 운영 DDL을 명확히 해야 하면 전략을 적는다.

Enum의 기본값은 ORDINAL이므로 반드시 STRING을 쓴다. 상수 순서를 바꾸면 과거 숫자의 의미가 바뀐다. JSON은 이식성이 우선이면 문자열+검증, Hibernate 7 JSON 연산이 필요하면 @JdbcTypeCode(SqlTypes.JSON)을 검토한다.

032.3 감사 필드↘

설정 클래스에 @EnableJpaAuditing(auditorAwareRef = "auditorAware")를 붙이고 AuditorAware<String>이 현재 사용자를 Optional로 반환하게 한다. 날짜만 기록하면 AuditorAware는 필요 없다. Spring Data 공식 문서는 날짜 애노테이션과 사용자 SPI를 분리한다.

042.4 연관관계의 주인↘

FK가 order_line.order_id라면 그 값을 바꾸는 것은 child의 OrderLine.order다.

@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "order_id", nullable = false)
private Order order;

@OneToMany(mappedBy = "order",
           cascade = CascadeType.ALL,
           orphanRemoval = true)
private List<OrderLine> lines = new ArrayList<>();

public void addLine(OrderLine line) {
    lines.add(line);
    line.order = this;
}
public void removeLine(OrderLine line) {
    lines.remove(line);
    line.order = null;
}

mappedBy는 자바 필드명이다. 편의 메서드가 없으면 owning side가 null인 채 flush될 수 있다. 컬렉션 setter 대신 도메인 메서드를 쓴다.

052.5 cascade, orphanRemoval, 다대다↘

cascade는 JPA 상태 전파이고 DB FK cascade가 아니다. orphanRemoval=true는 부모 컬렉션에서 빠진 자식을 삭제한다. 주문항목처럼 생명주기가 종속된 경우에만 함께 쓴다.

@ManyToMany는 수량·가격·생성일을 담기 어려우므로 중간 엔티티를 만든다.\n\n### 2.6 LAZY와 객체 계약

JPA 기본 fetch는 @ManyToOne·@OneToOne가 EAGER, 컬렉션이 LAZY다. 기본값은 모든 연관에 LAZY를 명시하고 필요한 관계만 가져오는 것이다.

Lombok @Data는 쓰지 않는다. equals/hashCode/toString이 연관관계를 순회해 순환·지연 로딩·프록시 문제를 만든다. generated ID가 null일 때도 안전한 팀 표준을 정한다.

엔티티를 JSON으로 직접 반환하지 않는다. 양방향 순환과 세션 밖 LAZY 접근을 막기 위해 DTO로 복사한다.

package example.shop.domain;
import java.math.BigDecimal;
import jakarta.persistence.*;

@Entity @Table(name="order_lines")
public class OrderLine {
  @Id @GeneratedValue(strategy=GenerationType.IDENTITY) private Long id;
  @Column(nullable=false, length=120) private String productName;
  @Column(nullable=false, precision=19, scale=2) private BigDecimal price;
  @Column(nullable=false) private int quantity;
  @Enumerated(EnumType.STRING) @Column(nullable=false, length=20)
  private LineStatus status = LineStatus.PENDING;
  @ManyToOne(fetch=FetchType.LAZY, optional=false)
  @JoinColumn(name="order_id", nullable=false) private Order order;
  protected OrderLine() {}
  public OrderLine(String n, BigDecimal p, int q) {
    if (q < 1) throw new IllegalArgumentException("quantity must be positive");
    productName=n; price=p; quantity=q;
  }
  void attach(Order o) { order=o; } void detach() { order=null; }
  public Long getId() { return id; } public String getProductName() { return productName; }
  public BigDecimal getPrice() { return price; } public int getQuantity() { return quantity; }
  public LineStatus getStatus() { return status; }
}
enum LineStatus { PENDING, PAID, CANCELLED }

055. 자주 나는 에러와 해결열기 ↓
  1. org.hibernate.LazyInitializationException: failed to lazily initialize a collection of role: ... no Session → 트랜잭션 뒤 컬렉션을 직렬화했다. → 트랜잭션 안에서 DTO로 변환한다.
  2. could not initialize proxy [example.shop.domain.Order#1] - no Session → detached 프록시 getter 접근이다. → 트랜잭션 안에서 필요한 관계를 가져온다(S09·S10).
  3. org.hibernate.PersistentObjectException: detached entity passed to persist → detached 객체를 새 객체처럼 persist했다. → 기존 aggregate를 로드해 변경한다.
  4. org.hibernate.TransientPropertyValueException: object references an unsaved transient instance → 저장되지 않은 parent를 참조한다. → owning side와 생명주기에 맞는 cascade를 확인한다.
  5. JsonMappingException: Infinite recursion (StackOverflowError) → 양방향 그래프를 Jackson이 순회했다. → DTO에서 단방향·필요 필드만 노출한다.
  6. DataIntegrityViolationException 또는 Column 'order_id' cannot be null → FK 주인이 null이다. → add 메서드와 INSERT의 order_id를 확인한다.
066. 한 단계 더열기 ↓

객체 그래프와 관계형 FK는 다르다. JPA는 owning field와 inverse collection을 나눈다. mappedBy 컬렉션만 수정하면 FK는 바뀌지 않는다. flush SQL과 DDL을 확인하고, 큰 목록은 child의 @ManyToOne과 페이지 조회를 기본으로 둔다. 영속성 컨텍스트·N+1은 → S09, 쿼리는 → S10, 연결은 → P19 참조.

077. 자가점검 Q&A (면접 대비)Q1. mappedBy는 무엇인가? · Q2. 왜 @ManyToOne(fetch=LAZY)를 명시하나? · Q3. cascade와 orphanRemoval의 차이는? · Q4. Enum ORDINAL의 문제는?열기 ↓
01Q1. mappedBy는 무엇인가?↘

FK를 관리하는 필드의 반대편이다. OrderLine.order가 order_id를 쓰며 컬렉션은 읽는 쪽이다. 값은 컬럼명이 아닌 필드명이다. 꼬리질문: 컬렉션만 add하면? → FK가 저장되지 않는다.

02Q2. 왜 @ManyToOne(fetch=LAZY)를 명시하나?↘

기본 EAGER는 불필요한 연관까지 즉시 준비한다. LAZY와 유스케이스별 조회로 범위를 통제한다. 단, 세션 밖 접근은 예외이므로 트랜잭션 안에서 DTO를 만든다. 꼬리질문: LAZY면 SQL 한 번인가? → 추가 SQL이 나올 수 있다.

03Q3. cascade와 orphanRemoval의 차이는?↘

cascade는 persist/remove 상태 전파이고 orphanRemoval은 컬렉션에서 빠진 자식 삭제다. 종속 생명주기에서만 함께 쓴다. 꼬리질문: DB cascade와 같은가? → 별개 규칙이다.

04Q4. Enum ORDINAL의 문제는?↘

상수 순서가 숫자의 의미가 된다. 중간 삽입으로 과거 데이터가 다른 상태로 해석된다. @Enumerated(EnumType.STRING)을 명시한다. 꼬리질문: 이름을 바꾸면? → 마이그레이션이 필요하다.

05Q5. 왜 @Data를 피하나?↘

equals/hashCode/toString이 연관관계를 순회해 순환·지연 로딩·프록시 문제를 만든다. 필요한 메서드만 작성한다. 꼬리질문: generated ID equals는? → null·hash 안정성을 고려한다.

06Q6. Entity를 직접 반환하지 않는 이유는?↘

API가 영속 모델에 종속되고 순환 그래프와 세션 밖 LAZY가 실패한다. DTO에서 필요한 필드만 복사해 계약과 조회 범위를 분리한다. 꼬리질문: JsonIgnore면? → 장기 경계는 DTO가 낫다.

07Q7. 언제 @OneToMany 대신 @ManyToOne만 두나?↘

자식 수가 크거나 검색·페이지네이션이 필요할 때다. child를 조건 조회하는 편이 부모 컬렉션보다 안정적이다. 꼬리질문: 양방향이 항상 좋은가? → 아니다.
