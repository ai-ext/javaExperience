3줄 요약 — SQL 값은 #{}로 바인딩하고, 문법 조각은 검증된 값만 ${}로 치환한다. 조건·조인·관계 매핑에는 XML이 리뷰하기 쉽다. 기본은 Boot 4.1, Starter 4.1.0, Mapper XML, 서비스 @Transactional이다.

011. 질문열기 ↓
  1. Mapper 메서드에 구현이 없다. XML의 namespace와 id가 Java 인터페이스와 어떻게 연결되는가?

  3. ORDER BY의 컬럼은 왜 값처럼 바인딩할 수 없을까? 문자열 치환은 어떤 검증 뒤에 허용해야 하는가?
022. 짧은 답열기 ↓
  • SQL 값은 #{}가 기본이다. SQL 문법 요소만 동적 선택하고 허용 목록으로 제한한다.
  • 단순 SQL은 annotation, 조건·조인·재사용 조각이 커지면 XML을 기본으로 한다.
  • 단순 행은 resultType, 관계 매핑은 resultMap이다.
  • 한 DB는 LIMIT/OFFSET, 다중 방언이나 팀 표준이면 PageHelper를 검토한다.
  • Boot 4.1 호환 Starter는 4.1.0이며 Mapper는 @MybatisTest로 검증한다.

01Mapper 메서드와 XML의 연결↘

Starter는 DataSource를 감지해 SqlSessionFactory와 SqlSessionTemplate을 만들고 Mapper 인터페이스를 Spring 빈으로 등록한다. 기본 스캔은 @Mapper를 찾고 직접 범위를 정하면 @MapperScan을 쓴다. Mapper 프록시가 메서드 호출을 MyBatis statement 실행으로 연결한다.

일반적인 statement 키는 인터페이스의 완전한 이름 + 메서드 id다. com.example.book.BookMapper.findById라면 XML의 namespace는 com.example.book.BookMapper, id는 findById여야 한다. XML 파일은 mapper-locations에 포함해야 한다.

flowchart LR
  A["서비스 호출"] --> B["Mapper 프록시"]
  B --> C["namespace + id 탐색"]
  C --> D["XML 동적 SQL 구성"]
  D --> E["#{값} 바인딩"]
  E --> F["JDBC 드라이버와 DB"]
  F --> G["resultType 또는 resultMap"]

XML은 SQL 중심 리뷰가 쉽지만 경로·이름 규칙이 추가된다. annotation은 단순 SQL을 찾기 쉽지만 복잡한 <script>는 읽기 어렵다. 양쪽은 같은 statement 엔진을 쓰므로 근거 없이 속도 차이를 단정하지 않는다.

02#{}와 ${}는 안전성 모델이 다르다↘

#{status}는 값을 SQL 문자열에 이어 붙이지 않는다. MyBatis는 PreparedStatement의 ? 표식을 만들고 JDBC 드라이버에 실제 값을 별도로 전달한다. DB는 값과 SQL 문법을 구분하므로 입력이 따옴표를 닫거나 OR 1=1을 실행하지 못한다. 값 비교·검색어·삽입·수정 값에는 #{}를 쓴다.

${column}은 문자열을 SQL에 그대로 삽입한다. 파라미터 자리는 값에만 쓸 수 있어 ORDER BY ?에 컬럼명을 넣어도 식별자로 동작하지 않는다. 동적 식별자가 필요한 때만 문자열 치환이 필요하다. 입력 안전성은 MyBatis가 보장하지 않는다. name; DROP TABLE ...처럼 SQL 텍스트 자체를 바꿀 수 있다. 이스케이프·금칙어 차단 대신 enum이나 고정 Map으로 허용 이름을 열거한다.

03동적 태그가 줄이는 것과 줄이지 않는 것↘

OGNL로 조건, 분기, 의 WHERE·선행 AND/OR, 의 SET·끝 쉼표, 접두·접미, 목록(IN) 생성을 제어한다.

태그는 SQL 모양을 정리할 뿐 업무 안전 조건을 강제하지 않는다. 검색 조건이 모두 빠지면 WHERE가 없어져 전체 조회가 될 수 있다. 빈 ID 목록도 결과 없음인지 필터 없음인지 호출 정책이 필요하다. 삭제·수정은 서비스에서 필수 조건과 빈 목록을 검사한다.

04결과 집합을 객체 관계로 바꾸기↘

resultType은 행의 자동 매핑이다. map-underscore-to-camel-case=true면 book_title과 bookTitle을 연결하며 MyBatis 기본값은 false다.

조인 결과에서 부모 행이 자식 수만큼 반복되면 resultType은 그 행을 객체 그래프로 접지 않는다. resultMap으로 컬럼과 프로퍼티를 연결한다. 은 단일 객체, 은 목록이다. 부모·자식 를 지정하면 반복 행에서 동일 객체를 식별한다. 컬럼 alias로 id/name 충돌을 구분한다.

05Spring 트랜잭션이 Mapper를 감싸는 이유↘

SqlSessionTemplate은 Spring 트랜잭션에 참여한다. 원자적 Mapper 호출은 서비스의 @Transactional 경계에 둔다. self-invocation은 AOP 프록시를 거치지 않아 적용되지 않을 수 있다.

044. 선택지 비교열기 ↓
선택지 어떻게 동작 장점 단점 언제 쓰나 국내 실무에서 흔한가(근거 있으면)
Mapper XML 메서드와 namespace/id statement 연결 동적 SQL·조인·resultMap을 SQL 중심으로 리뷰 경로 오타가 런타임 오류가 될 수 있음 검색, 복합 조인, 공통 SQL 국내 통계 미확인
Mapper annotation @Select 등으로 인터페이스에 SQL 작성 단순 문장과 메서드가 가까움 복잡 <script>는 문자열 안에서 읽기 어려움 작은 CRUD, 고정 조건 국내 통계 미확인
#{} 바인딩 PreparedStatement 값 파라미터 데이터와 SQL 문법 분리 식별자 변경 불가 거의 모든 입력값 공식 기본 방식
${} 치환 문자열을 SQL 텍스트에 삽입 동적 컬럼·테이블 지원 외부 입력은 인젝션 위험 허용 목록 정렬 키 사용률 미확인
resultType/resultMap 자동 이름 매핑/선언형 관계 매핑 간결/복합 관계가 명확 resultMap 작성량과 오타 가능성 단순 행/조인 그래프 국내 통계 미확인
LIMIT/OFFSET/PageHelper 직접 DB 구문/방언 플러그인 SQL 투명/DB 방언 공통화 DB 종속/플러그인 설정 필요 한 DB/다중 방언 표준 국내 통계 미확인

기본값 추천: 신규 Boot 4.1 모듈은 Mapper 인터페이스 + XML, 값은 #{}, 단일 테이블은 resultType, 조인 그래프는 resultMap, 한 DB 페이징은 LIMIT/OFFSET으로 시작한다. 팀에 통일된 annotation이나 PageHelper 규칙이 있으면 따른다. 같은 SQL을 XML과 annotation에 중복 정의하지 않는다.

025.2 같은 검색: XML 동적 SQL과 annotation (미실행)↘

두 방식은 상태·최소 ID로 최근순 조회를 한다. 한 방식만 둔다. text block은 Java 15에 정식화됐다(JEP 378).

package com.example.book.mapper;
import com.example.book.domain.Book;
import java.util.List;
import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Param;
import org.apache.ibatis.annotations.Select;
@Mapper
public interface BookXmlSearchMapper {
    List<Book> search(@Param("status") String status,
                      @Param("minId") Long minId,
                      @Param("limit") int limit,
                      @Param("offset") int offset);
    @Select("""
        SELECT id, title FROM book
        ORDER BY ${sortColumn} ${direction}
        LIMIT #{limit} OFFSET #{offset}
        """)
    List<Book> page(@Param("sortColumn") String sortColumn,
                    @Param("direction") String direction,
                    @Param("limit") int limit,
                    @Param("offset") int offset);
}
<mapper namespace="com.example.book.mapper.BookXmlSearchMapper">
<select id="search" resultType="Book">
  SELECT id, title FROM book
  <where>
    <if test="status != null and status != ''">
      AND status = #{status}
    </if>
    <if test="minId != null">
      AND id &gt;= #{minId}
    </if>
  </where>
  ORDER BY id DESC
  LIMIT #{limit} OFFSET #{offset}
</select>
</mapper>

빈 조건의 의미를 정하고 limit 상한과 offset 음수·overflow를 검사한다. 문법은 MySQL 호환이다.

package com.example.book.mapper;
import com.example.book.domain.Book;
import java.util.List;
import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Param;

@Mapper
public interface BookSearchMapper {
    @Select("""
        <script>
        SELECT id, title FROM book
        <where>
          <if test='status != null and status != ""'>
            AND status = #{status}
          </if>
          <if test='minId != null'>
            AND id &gt;= #{minId}
          </if>
        </where>
        ORDER BY id DESC
        LIMIT #{limit} OFFSET #{offset}

                      @Param("limit") int limit,
                      @Param("offset") int offset);

정렬 컬럼 선택: (앞의 Mapper page 메서드, 미실행)

컬럼은 바인딩 값이 아니므로 enum의 고정 이름만 전달한다. 앞의 Mapper에 있는 page 메서드를 쓰고 서비스에서 원문 입력을 제한한다.

package com.example.book.service;
import com.example.book.domain.Book;
import com.example.book.mapper.BookXmlSearchMapper;
import java.util.List;
import org.springframework.stereotype.Service;
@Service
public class BookSortService {
    enum SortKey {
        NEWEST("created_at"), TITLE("title");
        final String column;
        SortKey(String column) { this.column = column; }
    }
    enum Direction { ASC, DESC }
    private final BookXmlSearchMapper mapper;
    public BookSortService(BookXmlSearchMapper mapper) { this.mapper = mapper; }
    public List<Book> page(String sort, String direction, int limit, int offset) {
        SortKey key = SortKey.valueOf(sort.toUpperCase());
        Direction dir = Direction.valueOf(direction.toUpperCase());
        return mapper.page(key.column, dir.name(),
                Math.min(100, Math.max(1, limit)), Math.max(0, offset));
    }
}

valueOf 실패는 입력 오류로 처리한다. DB에 없는 컬럼은 목록에 넣지 않고 방향도 ASC/DESC로 제한한다.

035.3 조인 결과를 resultMap으로 만들기 (미실행)↘

책 한 권에 저자가 한 명, 리뷰가 여러 개다. 조인 행이 반복되므로 alias와 부모·자식 ID를 구분한다.

package com.example.book.mapper;
import java.util.Map;
import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Param;
@Mapper
public interface BookDetailMapper {
    Map<String, Object> findDetail(@Param("id") long id);
}
<mapper namespace="com.example.book.mapper.BookDetailMapper">
<resultMap id="bookDetailMap" type="map">
  <id property="id" column="book_id"/>
  <result property="title" column="book_title"/>
  <association property="author" javaType="map">
    <id property="id" column="author_id"/>
    <result property="name" column="author_name"/>
  </association>
  <collection property="reviews" ofType="map">
    <id property="id" column="review_id"/>
    <result property="body" column="review_body"/>
  </collection>
</resultMap>
<select id="findDetail" resultMap="bookDetailMap">
  SELECT b.id AS book_id, b.title AS book_title,
         a.id AS author_id, a.name AS author_name,
         r.id AS review_id, r.body AS review_body
  FROM book b JOIN author a ON a.id = b.author_id
  LEFT JOIN review r ON r.book_id = b.id
  WHERE b.id = #{id}
</select>
</mapper>

예제는 Map을 썼다. 도메인 DTO를 쓰면 resultMap의 type/javaType/ofType과 getter/setter를 맞춘다. 리뷰가 없으면 review_id는 NULL이다. 중복은 alias와 를 확인한다. 여러 1:N 조인은 행 수가 곱으로 늘 수 있다.

    @Test
    void insertReturnsGeneratedIdAndCanBeRead() {
        Book book = new Book();
        book.setTitle("MyBatis XML");
        assertThat(mapper.insert(book)).isEqualTo(1);
        assertThat(book.getId()).isNotNull();
        assertThat(mapper.findById(book.getId()).getTitle())
                .isEqualTo("MyBatis XML");
    }
}

H2와 운영 DB는 페이징, 타입 변환, 예약어, 생성 키가 다를 수 있다. 기본 매핑은 slice에서, DB 고유 SQL은 운영 엔진 통합 테스트에서 확인한다. 개발 프로필에서 Mapper namespace DEBUG 로그로 SQL을 본다. 바인딩 값에 개인정보·토큰이 있을 수 있어 운영 로그의 권한과 보존 기간을 제한하고 마스킹한다. STDOUT_LOGGING은 일시 디버깅에만 쓴다.

066. 실무에서는 실제로열기 ↓
  • 신규 서비스: Starter 4.1.0과 Mapper XML을 기본으로 정하고 경로·namespace 규칙을 고정한다.
  • 작은 도구: 단순 SQL은 annotation, 조건·조인이 늘면 XML로 옮긴다.
  • 레거시: 기존 형식과 별칭 규칙을 유지하고 새 쿼리부터 기준을 적용한다.
  • SI·금융: 복잡 SQL에는 XML과 resultMap이 유리할 수 있다. 업종별 통계는 확인하지 못했으므로 변경 빈도와 리뷰 체계로 정한다.
  • 스타트업: 단순 CRUD는 annotation, 복잡 SQL은 XML. /는 공통 조각에만 쓴다.
  • 한 DB면 LIMIT/OFFSET, 다중 방언이나 팀 표준이면 PageHelper.
  • 접근 비교 → W03, JPA 혼용 → W05 참조.
077. 흔한 오해와 실수열기 ↓
  1. 메서드 SQL은 자동 연결된다 → namespace/id를 못 찾으면 Invalid bound statement (not found). → 완전한 인터페이스 이름, XML 경로/id, 빌드 산출물을 확인한다.
  2. 인자 이름은 늘 XML에서 보인다 → 이름 불일치면 BindingException: Parameter 'status' not found. → 여러 인자에 @Param을 명시한다.
  3. #{}는 식별자에도 쓸 수 있다 → ORDER BY #{column}은 컬럼 정렬이 아니다. → 고정 컬럼이나 허용 목록 값만 ${}로 전달한다.
  4. 가 빈 검색을 막는다 → WHERE가 생략되어 전체 조회가 될 수 있다. → 정책·최소 조건·페이지 상한을 서비스에서 정한다.
  5. 빈 도 안전하다 → IN 조건이 사라지면 전체 변경 위험이 있다. → 빈 목록을 변경 쿼리에서 거부한다.
  6. resultMap 관계가 null/중복 → resultType은 행 단위이고 alias/property 오타가 원인일 수 있다. → //을 확인한다.
  7. 단일 반환형이면 결과도 한 행이다 → 여러 행이면 TooManyResultsException. → 유일 조건을 확인하고 복수 결과는 List로 반환한다.
088. 자가점검 Q&A (면접 대비)Q1. #{}와 ${}의 차이는? · Q2. Invalid bound statement (not found)는 어떻게 찾나? · Q3. resultType과 resultMap은 어떻게 고르나? · Q4. 가 해결하는 것과 못 하는 것은?열기 ↓
01Q1. #{}와 ${}의 차이는?↘

#{}는 PreparedStatement 값으로 전달되어 데이터와 SQL 문법을 구분한다. ${}는 문자열을 직접 치환해 식별자에만 제한한다. 일반 입력은 #{}가 기본이다.

꼬리질문: 정렬 컬럼은? → enum 허용 목록만 치환한다.

02Q2. Invalid bound statement (not found)는 어떻게 찾나?↘

Mapper 메서드와 XML id, 완전한 이름과 namespace를 대조한다. mapper-locations와 빌드 리소스 포함 여부, 중복 statement와 오타를 살핀다.

꼬리질문: 기동 때 항상 못 잡는 이유는? → statement 탐색이 호출 때 이뤄질 수 있다.

03Q3. resultType과 resultMap은 어떻게 고르나?↘

단일 행 이름 매핑은 resultType이 짧다. 조인 행을 부모·자식 그래프로 묶으려면 resultMap을 명시한다. 한 statement에서 둘을 동시에 쓰지 않는다.

꼬리질문: collection이 중복이면? → ID와 alias를 확인한다.

04Q4. 가 해결하는 것과 못 하는 것은?↘

조건이 있을 때 WHERE와 AND/OR를 정리해 문법 실수를 줄인다. 조건이 없을 때 조회 범위는 제한하지 않는다. 정책은 서비스가 정한다.

꼬리질문: 한 분기만 적용하려면? → //를 쓴다.

05Q5. 조인한 1:N을 매핑하려면?↘

부모·자식 ID와 alias를 구분한다. resultMap의 과 자식 로 행을 부모 목록에 모은다. 단일 연관은 이다.

꼬리질문: ID를 빼면? → 반복 행의 동일 객체를 판별하기 어려워 중복될 수 있다.

06Q6. @Transactional은 어디에 두나?↘

여러 Mapper 호출이 한 업무 단위라면 서비스 경계에 둔다. Spring 프록시와 SqlSessionTemplate이 같은 DataSource 트랜잭션을 사용한다.

꼬리질문: 같은 클래스 내부 호출은? → self-invocation은 프록시를 건너뛴다.
