Azure HNS의 directory semantics/atomic operations를 모든 POSIX 보장으로 확대하지 않습니다. 제품 비교표는 유사 기능 예이며 완전 API/SKU/책임 호환·요금 인증이 아닙니다. 7R은 조직마다 평가할 선택지이며 모든 조직의 필수 순서가 아닙니다. Relocate는 같은 platform/app 구조를 보존한 환경·region·account 이전 범위로 읽고 OS/runtime 변경을 섞지 않습니다. # D07. 온프레미스 vs 클라우드 — 서버는 어디에 있고 누가 관리하나

> 온프레미스는 장비와 시설부터 애플리케이션까지 조직이 직접 소유·운영하는 방식이고, 클라우드는 필요한 컴퓨팅 자원을 네트워크로 빌려 쓰는 방식이다.
> 클라우드로 옮긴다고 책임이 사라지는 것은 아니다. 서비스 모델이 IaaS에서 PaaS·SaaS로 갈수록 제공자가 관리하는 층이 늘고, 데이터·계정·설정 책임은 대체로 고객에게 남는다.
> 선택의 기준은 “클라우드가 더 현대적인가”가 아니라 규제, 변동성, 장애 허용도, 팀의 운영 역량, 총비용과 전환 위험의 조합이다.

## 1. 큰 그림

NIST는 클라우드를 “공유된 설정 가능 컴퓨팅 자원 풀에 네트워크로 편리하게, 필요할 때 접근하고 빠르게 할당·해제하는 모델”로 정의한다. 핵심은 서버가 반드시 남의 건물에 있다는 뜻이 아니라, 물리 자원을 추상화하고 사용량에 따라 공급받는 운영 모델이라는 점이다.

```mermaid
flowchart LR
    A["요구사항: 규제·트래픽·가용성·예산"] --> B{"배치 선택"}
    B --> C["온프레미스 / IDC"]
    B --> D["퍼블릭 클라우드"]
    B --> E["프라이빗 클라우드"]
    B --> F["하이브리드 / 멀티클라우드"]
    C --> C1["조직이 시설·서버·네트워크·OS·앱 관리"]
    D --> D1["제공자 인프라 + 고객 설정·데이터·앱"]
    E --> E1["전용 환경의 통제 + 클라우드식 자동화"]
    F --> F1["연결·데이터 이동·책임 경계 관리"]
    C1 --> G["배포 가능한 Spring Boot 애플리케이션"]
    D1 --> G
    E1 --> G
    F1 --> G
```

그림의 왼쪽에서 오른쪽으로 갈수록 “서버를 어디에 둘까”와 “누가 무엇을 운영할까”가 분리된다. 온프레미스라면 고장 난 디스크 교체, 전원·냉각, 하이퍼바이저, OS 패치까지 같은 조직의 책임이다.

퍼블릭 클라우드에서는 물리 시설과 호스트는 제공자가 맡지만, EC2 VM의 게스트 OS와 보안 그룹은 고객이 맡는다. 관리형 DB나 PaaS로 가면 OS 운영 부담은 줄지만 스키마, 계정, 백업 정책, 애플리케이션의 잘못된 쿼리까지 제공자가 대신 책임지지는 않는다.

이 문서는 전체 개발 과정(D01)에서 “코드가 어떤 실행 환경에 배치되고 운영 주체가 누구인지”를 다루는 단계다. 배포 절차는 D06, 네트워크 기초는 D02를 참조한다.

| 레지스트리 | 컨테이너 이미지와 메타데이터를 보관하는 저장소 | ECR, ACR, Artifact Registry | 실행 서비스가 아니라 이미지 공급·권한·스캔을 담당 |
| 온디맨드 | 장기 약정 없이 사용량만큼 지불 | EC2 On-Demand | 유연하지만 지속 사용에는 할인 옵션보다 비쌀 수 있음 |
| 예약·약정 | 일정 사용량·기간을 약속하고 단가를 낮추는 방식 | Savings Plans, 예약 인스턴스 | 수요 예측이 빗나가면 유연성이 줄어듦 |
| 스팟 | 사업자의 유휴 용량을 큰 할인으로 쓰는 방식 | 중단 가능한 배치 작업 | 중단·회수에 견디는 작업에만 적합 |
| 이그레스(egress) | 클라우드 밖으로 데이터를 전송하는 트래픽 | 리전 밖 백업·인터넷 응답 | 저장 비용만 계산하면 놓치기 쉬운 비용 항목 |

## 3. 단계별로 보기

### 3.1 서버 위치와 책임 경계

온프레미스에서는 다음 스택을 한 조직이 모두 계획한다: 건물/전원 → 물리 서버 → 스토리지·스위치 → 하이퍼바이저 → VM·OS → 런타임 → 애플리케이션·데이터. 코로케이션은 건물과 전력을 외부에 맡기지만 서버·OS 책임은 남을 수 있다.

클라우드에서는 “서비스를 선택하는 순간 경계가 정해진다.” AWS의 표현으로 물리 시설·호스트·가상화는 Security of the Cloud, 고객의 OS·애플리케이션·보안 그룹·데이터는 Security in the Cloud다. 다만 S3처럼 추상화된 서비스에서는 고객이 OS를 만지지 않고 데이터 암호화와 IAM 권한을 관리한다.

| 층 | 온프레미스 | IaaS | PaaS | SaaS |
|---|---|---|---|---|
| 데이터·분류·보존 | 고객 | 고객 | 고객 | 고객 |
| 계정·IAM·MFA | 고객 | 고객 | 고객 | 고객 |
| 애플리케이션 코드·설정 | 고객 | 고객 | 고객과 제공자 공유 | 고객과 제공자 공유 |
| 네트워크 제어 | 고객 | 고객 | 공유 | 대부분 제공자 |
| OS·런타임 | 고객 | 고객 | 제공자 | 제공자 |
| 물리 호스트·네트워크·시설 | 고객 | 제공자 | 제공자 | 제공자 |

이 표는 “관리형”을 “안전 보장”으로 읽지 않게 해준다. PaaS가 OS 패치를 해도 취약한 코드, 과도하게 열린 애플리케이션 권한, 실수로 공개한 객체 버킷은 고객의 문제다. 계정·데이터·설정은 서비스 모델과 관계없이 고객이 지속해서 책임진다는 Azure의 표도 같은 결론을 보여준다.

### 3.2 가상화와 컨테이너

```mermaid
flowchart TB
    H["물리 서버"] --> V["하이퍼바이저"]
    V --> VM1["VM 1: 게스트 OS + JVM + 앱"]
    V --> VM2["VM 2: 게스트 OS + DB"]
    H --> K["호스트 OS 커널"]
    K --> R["컨테이너 런타임"]
    R --> C1["컨테이너: JVM + Spring Boot 앱"]
    R --> C2["컨테이너: 다른 서비스"]
```

VM은 커널과 드라이버를 포함한 운영체제 전체를 가상화하므로 격리 경계가 크고 서로 다른 OS를 함께 실행하기 쉽다. 컨테이너는 프로세스와 파일 시스템을 격리하고 호스트 커널을 공유하므로 빠르게 시작하고 같은 호스트에 더 많이 배치할 수 있다. 따라서 클라우드의 VM 안에서 여러 컨테이너를 돌리는 구성도 흔하다. 컨테이너가 VM을 대체한다기보다 서로 다른 층의 기술이다.

### 3.3 리전·AZ·트래픽 흐름

```mermaid
sequenceDiagram
    participant U as "사용자"
    participant DNS as "DNS"
    participant LB as "로드밸런서"
    participant AZ1 as "AZ-a의 Spring Boot"
    participant AZ2 as "AZ-b의 Spring Boot"
    participant DB as "관리형 DB / 복제본"
    U->>DNS: "api.example.com 조회"
    DNS-->>U: "로드밸런서 주소"
    U->>LB: "HTTPS 요청"
    LB->>AZ1: "헬스체크 정상 대상에 전달"
    LB->>AZ2: "장애 시 다른 AZ로 전달"
    AZ1->>DB: "쿼리·트랜잭션"
    DB-->>AZ1: "결과"
    AZ1-->>U: "응답"
```

리전은 지리적·법적 경계이고 AZ는 한 리전 안의 장애 격리 단위다. 한 AZ의 문제가 전체 서비스가 되지 않게 하려면 앱·로드밸런서·데이터 계층을 여러 AZ에 배치하고 상태를 외부화해야 한다. AWS 문서도 리전마다 적어도 세 AZ를 두어 고가용성 설계를 돕는다고 설명하지만, AZ가 여러 개라는 사실만으로 복제·재시도·데이터 일관성이 해결되지는 않는다.

### 3.4 서비스 선택과 실제 대응

| 필요 | AWS | Azure | Google Cloud | Spring Boot 배치 관점 |
|---|---|---|---|---|
| VM 컴퓨트 | EC2 | Azure Virtual Machines | Compute Engine | JAR를 VM에 직접 실행하거나 Docker 런타임 설치 |
| 관리형 Kubernetes | EKS | AKS | GKE | 컨테이너·Deployment·Service 운영, 클러스터 책임 일부 위임 |
| 관리형 애플리케이션 플랫폼 | Elastic Beanstalk 등 | App Service | Cloud Run | 이미지/JAR 배포, OS 패치 부담 감소 |
| 관리형 관계형 DB | RDS | Azure Database | Cloud SQL | JDBC 연결·마이그레이션·쿼리와 권한은 애플리케이션 팀 책임 |
| 오브젝트 스토리지 | S3 | Blob Storage | Cloud Storage | 업로드 파일·백업·정적 자산 저장, URL 권한 설계 필요 |
| 로드밸런서 | Elastic Load Balancing | Azure Load Balancer / Application Gateway | Cloud Load Balancing | TLS 종료, 헬스체크, 다중 인스턴스 진입점 |
| DNS | Route 53 | Azure DNS | Cloud DNS | 도메인 이름을 LB·서비스 주소에 연결 |
| 이미지 레지스트리 | ECR | ACR | Artifact Registry | 빌드 이미지 push, 배포 주체가 pull |

Google의 대응표는 제품명이 같다는 뜻이 아니라 기능상 비교 가능한 선택지를 보여주는 표다. 예를 들어 ECR은 이미지를 저장·push·pull·스캔하는 관리형 레지스트리이지 Kubernetes 실행 서비스가 아니다. S3는 파일 서버의 디렉터리와 같은 저장소가 아니라 객체 키와 권한·수명주기 중심의 저장소다.

### 3.5 비용과 전환

온프레미스 비용은 서버 구매, 감가상각, 전력·상면, 회선, 예비 장비, 운영 인건비를 먼저 부담하고 낮은 사용률에도 계속 발생하는 경향이 있다. 클라우드는 초기 구매가 줄지만 컴퓨트 시간, 디스크, 요청 수, 데이터 전송, 관리형 서비스, 로그와 이그레스가 누적된다. EC2는 온디맨드·약정형 Savings Plans·중단 가능한 Spot 같은 구매 옵션이 있고, S3는 저장·요청·검색·데이터 전송·복제 등이 비용 항목이다.

전환은 “서버를 옮긴다”가 아니라 의존성과 운영 책임을 옮기는 일이다. AWS의 7R은 Retire, Retain, Rehost, Relocate, Repurchase, Replatform, Refactor/re-architect다. 빠른 리프트 앤 시프트인 Rehost는 변경 위험이 작지만 클라우드의 탄력성과 관리형 기능을 충분히 쓰지 못할 수 있다.

Replatform은 DB·런타임을 관리형으로 바꾸고, Refactor는 애플리케이션 구조까지 바꾼다. 큰 마이그레이션에서 Refactor를 한꺼번에 하면 복잡도가 폭증하므로, 먼저 옮긴 뒤 현대화하는 순서가 합리적인 경우가 많다.

## 4. 직접 해보기

아래 실습은 비용 없는 로컬 경로를 기본으로 한다. Docker Desktop과 JDK 25, Gradle이 설치되어 있다고 가정한다. 클라우드 계정으로 ECR·EC2 등을 만드는 단계는 선택이며, 실행하면 비용과 권한이 발생할 수 있다.

### 4.1 Spring Boot 애플리케이션을 로컬 프로세스로 실행

Spring Initializr에서 Spring Web을 포함한 Gradle 프로젝트를 만들고, 기준 버전인 Spring Boot 4.1 / Java 25를 선택한다. 핵심 컨트롤러는 다음처럼 둔다.

```java
package com.example.demo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}

@RestController
class HealthController {
    @GetMapping("/health")
    String health() {
        return "ok";
    }
}
```

실행과 확인:

```bash
./gradlew bootRun
curl -i http://localhost:8080/health
# HTTP/1.1 200
# ok
```

이 상태는 “내 노트북이 서버”인 가장 작은 온프레미스 실습이다. 프로세스 종료, 포트 충돌, 로컬 디스크 고장은 직접 해결해야 한다. (Spring 예제 미실행)

### 4.2 같은 애플리케이션을 컨테이너로 패키징

프로젝트 루트의 `Dockerfile`:

```dockerfile
FROM eclipse-temurin:25-jre
WORKDIR /app
COPY build/libs/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

```bash
./gradlew clean bootJar
docker build -t d07-demo:local .

```

이미지는 앱과 JVM 런타임을 묶어 “어디서 실행할지”와 “무엇을 실행할지”를 분리한다. 그러나 호스트 커널, 런타임, 포트, 비밀과 로그 수집은 여전히 실행 환경의 책임이다. (Spring 예제 미실행)

### 4.3 실행 위치를 세 가지로 그려 보기

```mermaid
flowchart LR
    A["소스 코드"] --> B["Gradle bootJar"]
    B --> C["로컬 JVM: 온프레미스식 직접 실행"]
    B --> D["Docker 이미지: 레지스트리 push"]
    D --> E["단일 VM의 컨테이너"]
    D --> F["관리형 Kubernetes"]
    B --> G["관리형 PaaS에 JAR 또는 이미지 배포"]
    E --> H["팀이 OS·런타임·앱 관리"]
    F --> I["팀이 워크로드, 제공자가 일부 컨트롤 플레인 관리"]
    G --> J["팀이 앱·설정·데이터, 제공자가 플랫폼 관리"]
```

선택 실습으로 클라우드 레지스트리에 로그인해 이미지를 push할 수 있다. 예를 들면 AWS에서는 ECR 리포지터리를 만들고 권한을 부여한 뒤 `docker push`를 수행한다. 다음 단계로 EC2에서 이미지를 pull해 실행하면 Rehost에 가까운 구성이 된다.

실제 명령은 리전·계정·IAM 정책에 따라 달라지므로 계정 정보를 문서에 하드코딩하지 않는다. 운영에서는 이미지 태그를 `latest` 하나로 덮어쓰지 말고 커밋 SHA나 릴리스 버전과 스캔 결과를 연결한다.

## 5. 자주 하는 오해와 실수

1. **“클라우드면 서버가 없다” →** 서버는 존재하고, 고객이 물리 장비를 직접 관리하지 않을 뿐이다. **대처:** 서비스별 책임표에서 OS·런타임·데이터·IAM 담당자를 명시한다.
2. **“AWS가 보안을 모두 책임진다” →** AWS는 인프라를 보호하지만 EC2 패치, 보안 그룹, 애플리케이션 취약점, S3 권한은 고객 책임이다. **대처:** 자산별 패치·권한·백업 소유자를 체크리스트로 둔다.
3. **“여러 AZ면 무조건 무중단이다” →** 단일 DB, 세션의 로컬 메모리, 잘못된 헬스체크가 병목·장애를 만든다. **대처:** 상태 외부화, 다중 AZ 데이터 경로, 장애 주입과 복구 연습을 검증한다.
4. **“컨테이너는 VM보다 안전하다” →** 컨테이너는 격리 프로세스이고 커널을 공유한다. 취약한 이미지, root 실행, 과도한 권한은 위험하다. **대처:** 최소 이미지·비root 사용자·이미지 스캔·런타임 권한 제한을 적용한다.
5. **“클라우드는 사용한 만큼만 내면 되니 항상 싸다” →** 유휴 VM, 로그 보관, NAT·리전 간 전송·이그레스가 청구서를 키운다. **대처:** 서비스별 비용 알람과 태그, 예산, 비정상 이그레스 모니터링을 둔다.
6. **“멀티클라우드는 장애와 종속성을 모두 없앤다” →** API·IAM·네트워크·데이터 포맷이 달라 운영 복잡도와 동기화 비용이 늘어난다. **대처:** 정말 필요한 독립 장애 도메인인지, 단일 클라우드의 다중 리전으로 충분한지 먼저 비교한다.
7. **“Replatform과 Refactor는 같은 말이다” →** Replatform은 코드를 크게 바꾸지 않고 관리형 플랫폼으로 옮기는 쪽이고, Refactor는 구조·운영 모델을 다시 설계한다. **대처:** 전환 목표와 변경 범위를 별도 승인하고 단계별 성공 기준을 둔다.

## 6. 시각화 설계 메모

## 7. 자가점검 Q&A (면접 대비)

### Q1. 온프레미스와 퍼블릭 클라우드의 본질적 차이는 무엇인가?

온프레미스는 조직이 물리·가상·소프트웨어 스택의 대부분을 직접 소유하고 용량을 선투자한다. 퍼블릭 클라우드는 사업자의 공유 인프라를 API로 프로비저닝하고 일부 책임을 위임한다. 따라서 위치보다 조달 방식, 탄력성, 운영 책임의 경계가 핵심이다.

꼬리질문: IDC에 서버를 두면 클라우드인가? → 아니다. 상면을 임대하는 코로케이션일 수 있으며, 셀프서비스·탄력적 자원 풀·책임 분담 여부를 함께 봐야 한다.

### Q2. IaaS에서 고객이 반드시 관리해야 하는 것은?

게스트 OS 업데이트와 보안 패치, 설치한 애플리케이션, 네트워크 보안 그룹, 계정·권한, 데이터 보호가 대표적이다. 제공자가 물리 호스트와 가상화 계층을 관리해도 VM 내부의 잘못된 설정은 자동으로 고쳐지지 않는다.

꼬리질문: PaaS로 가면 데이터 보안도 제공자 책임인가? → 아니다. 플랫폼의 물리·OS 운영은 위임되지만 분류, 암호화 선택, 애플리케이션 권한과 계정은 고객이 관리한다.

### Q3. 리전과 AZ를 어떻게 선택하는가?

리전은 데이터 주권, 법적 요구, 사용자와의 지연시간, 필요한 서비스의 제공 여부로 선택한다. AZ는 한 리전 안에서 장애를 분리하기 위해 여러 개를 사용한다. 다만 앱·DB·세션·백업까지 장애 경계를 넘겨야 실제 복원력이 생긴다.

꼬리질문: 다른 리전 하나를 추가하면 무조건 재해복구가 되는가? → 아니다. 복제 지연, DNS 전환, 비밀·키, 데이터 일관성, 복구 절차를 시험해야 한다.

### Q4. VM과 컨테이너를 비교해 보라.

VM은 게스트 OS와 커널을 포함해 격리와 OS 독립성이 큰 대신 이미지와 시작 비용이 크다. 컨테이너는 격리된 프로세스로 호스트 커널을 공유해 빠르고 밀도가 높지만 커널·런타임·이미지 보안에 의존한다. 실제 클라우드에서는 VM 위에 컨테이너를 실행하는 조합이 흔하다.

꼬리질문: 컨테이너를 쓰면 운영체제 패치가 사라지는가? → 아니다. 이미지의 사용자 공간을 재빌드해야 하고 호스트 커널과 런타임 패치는 운영 주체가 계속 수행한다.

### Q5. 관리형 Kubernetes를 쓰면 무엇이 편해지고 무엇이 남는가?

제공자가 컨트롤 플레인 일부의 가용성과 패치를 맡아 클러스터 운영 부담을 줄인다. 고객은 컨테이너 이미지, 워크로드 리소스, 서비스 노출, IAM/RBAC, 시크릿, 로그와 비용을 여전히 관리한다. 관리형이라는 말은 애플리케이션 운영을 대신한다는 뜻이 아니다.

꼬리질문: 작은 Spring Boot 하나에도 Kubernetes를 써야 하는가? → 운영 표준·확장·팀 역량이 필요할 때 선택하고, 그렇지 않으면 단일 VM이나 PaaS가 더 단순한 기본값이다.

### Q6. 클라우드 비용을 온프레미스와 비교할 때 무엇을 포함해야 하는가?

클라우드의 VM·스토리지 가격만 보지 말고 요청, 관리형 DB, 로그, 백업, 리전 간 전송과 인터넷 이그레스까지 합산한다. 온프레미스도 장비 감가, 전력·상면, 회선, 예비 부품, 장애 대응 인건비를 포함해야 공정하다. 실제 트래픽 패턴과 1~3년 총소유비용으로 비교한다.

꼬리질문: Spot이 가장 싸니 웹 서버에 쓰면 되는가? → 중단을 견디는 무상태·배치에 적합하다. 중단 시 요청과 세션을 잃는 핵심 단일 서버에는 온디맨드나 약정형과 조합한다.

### Q7. Rehost, Replatform, Refactor를 언제 선택하는가?

Rehost는 빠른 이전과 코드 변경 최소화가 우선일 때, Replatform은 관리형 DB·실행 플랫폼으로 운영 부담을 줄일 때 쓴다. Refactor는 구조적 확장성·탄력성 개선이 목표지만 테스트와 설계 변경 비용이 크다. 규제·의존성·서비스 수명까지 평가해 애플리케이션마다 다르게 선택한다.

꼬리질문: 전환 프로젝트 전체를 Refactor로 시작하면 좋은가? → 대규모 이전에서는 위험하다. 먼저 Retain/Retire와 저위험 Rehost·Replatform을 분류하고, 검증된 서비스부터 현대화한다.

#D07. 온프레미스 vs 클라우드 — 서버는 어디에 있고 누가 관리하나

원문 전체 · 코드·버전별 변화·실무 가이드·참고문헌

온프레미스는 장비와 시설부터 애플리케이션까지 조직이 직접 소유·운영하는 방식이고, 클라우드는 필요한 컴퓨팅 자원을 네트워크로 빌려 쓰는 방식이다. 클라우드로 옮긴다고 책임이 사라지는 것은 아니다. 서비스 모델이 IaaS에서 PaaS·SaaS로 갈수록 제공자가 관리하는 층이 늘고, 데이터·계정·설정 책임은 대체로 고객에게 남는다. 선택의 기준은 “클라우드가 더 현대적인가”가 아니라 규제, 변동성, 장애 허용도, 팀의 운영 역량, 총비용과 전환 위험의 조합이다.

    F --> F1["연결·데이터 이동·책임 경계 관리"]
    C1 --> G["배포 가능한 Spring Boot 애플리케이션"]
    D1 --> G
    E1 --> G
    F1 --> G

그림의 왼쪽에서 오른쪽으로 갈수록 “서버를 어디에 둘까”와 “누가 무엇을 운영할까”가 분리된다. 온프레미스라면 고장 난 디스크 교체, 전원·냉각, 하이퍼바이저, OS 패치까지 같은 조직의 책임이다.

퍼블릭 클라우드에서는 물리 시설과 호스트는 제공자가 맡지만, EC2 VM의 게스트 OS와 보안 그룹은 고객이 맡는다. 관리형 DB나 PaaS로 가면 OS 운영 부담은 줄지만 스키마, 계정, 백업 정책, 애플리케이션의 잘못된 쿼리까지 제공자가 대신 책임지지는 않는다.

이 문서는 전체 개발 과정(D01)에서 “코드가 어떤 실행 환경에 배치되고 운영 주체가 누구인지”를 다루는 단계다. 배포 절차는 D06, 네트워크 기초는 D02를 참조한다.

013.1 서버 위치와 책임 경계↘

온프레미스에서는 다음 스택을 한 조직이 모두 계획한다: 건물/전원 → 물리 서버 → 스토리지·스위치 → 하이퍼바이저 → VM·OS → 런타임 → 애플리케이션·데이터. 코로케이션은 건물과 전력을 외부에 맡기지만 서버·OS 책임은 남을 수 있다.

클라우드에서는 “서비스를 선택하는 순간 경계가 정해진다.” AWS의 표현으로 물리 시설·호스트·가상화는 Security of the Cloud, 고객의 OS·애플리케이션·보안 그룹·데이터는 Security in the Cloud다. 다만 S3처럼 추상화된 서비스에서는 고객이 OS를 만지지 않고 데이터 암호화와 IAM 권한을 관리한다.

네트워크 제어 고객 고객 공유 대부분 제공자

이 표는 “관리형”을 “안전 보장”으로 읽지 않게 해준다. PaaS가 OS 패치를 해도 취약한 코드, 과도하게 열린 애플리케이션 권한, 실수로 공개한 객체 버킷은 고객의 문제다. 계정·데이터·설정은 서비스 모델과 관계없이 고객이 지속해서 책임진다는 Azure의 표도 같은 결론을 보여준다.

VM은 커널과 드라이버를 포함한 운영체제 전체를 가상화하므로 격리 경계가 크고 서로 다른 OS를 함께 실행하기 쉽다. 컨테이너는 프로세스와 파일 시스템을 격리하고 호스트 커널을 공유하므로 빠르게 시작하고 같은 호스트에 더 많이 배치할 수 있다. 따라서 클라우드의 VM 안에서 여러 컨테이너를 돌리는 구성도 흔하다. 컨테이너가 VM을 대체한다기보다 서로 다른 층의 기술이다.

리전은 지리적·법적 경계이고 AZ는 한 리전 안의 장애 격리 단위다. 한 AZ의 문제가 전체 서비스가 되지 않게 하려면 앱·로드밸런서·데이터 계층을 여러 AZ에 배치하고 상태를 외부화해야 한다. AWS 문서도 리전마다 적어도 세 AZ를 두어 고가용성 설계를 돕는다고 설명하지만, AZ가 여러 개라는 사실만으로 복제·재시도·데이터 일관성이 해결되지는 않는다.

053.5 비용과 전환↘

온프레미스 비용은 서버 구매, 감가상각, 전력·상면, 회선, 예비 장비, 운영 인건비를 먼저 부담하고 낮은 사용률에도 계속 발생하는 경향이 있다. 클라우드는 초기 구매가 줄지만 컴퓨트 시간, 디스크, 요청 수, 데이터 전송, 관리형 서비스, 로그와 이그레스가 누적된다. EC2는 온디맨드·약정형 Savings Plans·중단 가능한 Spot 같은 구매 옵션이 있고, S3는 저장·요청·검색·데이터 전송·복제 등이 비용 항목이다.

전환은 “서버를 옮긴다”가 아니라 의존성과 운영 책임을 옮기는 일이다. AWS의 7R은 Retire, Retain, Rehost, Relocate, Repurchase, Replatform, Refactor/re-architect다. 빠른 리프트 앤 시프트인 Rehost는 변경 위험이 작지만 클라우드의 탄력성과 관리형 기능을 충분히 쓰지 못할 수 있다.

Replatform은 DB·런타임을 관리형으로 바꾸고, Refactor는 애플리케이션 구조까지 바꾼다. 큰 마이그레이션에서 Refactor를 한꺼번에 하면 복잡도가 폭증하므로, 먼저 옮긴 뒤 현대화하는 순서가 합리적인 경우가 많다.

055. 자주 하는 오해와 실수열기 ↓
  1. “클라우드면 서버가 없다” → 서버는 존재하고, 고객이 물리 장비를 직접 관리하지 않을 뿐이다. 대처: 서비스별 책임표에서 OS·런타임·데이터·IAM 담당자를 명시한다.
  2. “AWS가 보안을 모두 책임진다” → AWS는 인프라를 보호하지만 EC2 패치, 보안 그룹, 애플리케이션 취약점, S3 권한은 고객 책임이다. 대처: 자산별 패치·권한·백업 소유자를 체크리스트로 둔다.
  3. “여러 AZ면 무조건 무중단이다” → 단일 DB, 세션의 로컬 메모리, 잘못된 헬스체크가 병목·장애를 만든다. 대처: 상태 외부화, 다중 AZ 데이터 경로, 장애 주입과 복구 연습을 검증한다.
  4. “컨테이너는 VM보다 안전하다” → 컨테이너는 격리 프로세스이고 커널을 공유한다. 취약한 이미지, root 실행, 과도한 권한은 위험하다. 대처: 최소 이미지·비root 사용자·이미지 스캔·런타임 권한 제한을 적용한다.
  5. “클라우드는 사용한 만큼만 내면 되니 항상 싸다” → 유휴 VM, 로그 보관, NAT·리전 간 전송·이그레스가 청구서를 키운다. 대처: 서비스별 비용 알람과 태그, 예산, 비정상 이그레스 모니터링을 둔다.
  6. “멀티클라우드는 장애와 종속성을 모두 없앤다” → API·IAM·네트워크·데이터 포맷이 달라 운영 복잡도와 동기화 비용이 늘어난다. 대처: 정말 필요한 독립 장애 도메인인지, 단일 클라우드의 다중 리전으로 충분한지 먼저 비교한다.
  7. “Replatform과 Refactor는 같은 말이다” → Replatform은 코드를 크게 바꾸지 않고 관리형 플랫폼으로 옮기는 쪽이고, Refactor는 구조·운영 모델을 다시 설계한다. 대처: 전환 목표와 변경 범위를 별도 승인하고 단계별 성공 기준을 둔다.

01Q1. 온프레미스와 퍼블릭 클라우드의 본질적 차이는 무엇인가?↘

온프레미스는 조직이 물리·가상·소프트웨어 스택의 대부분을 직접 소유하고 용량을 선투자한다. 퍼블릭 클라우드는 사업자의 공유 인프라를 API로 프로비저닝하고 일부 책임을 위임한다. 따라서 위치보다 조달 방식, 탄력성, 운영 책임의 경계가 핵심이다.

꼬리질문: IDC에 서버를 두면 클라우드인가? → 아니다. 상면을 임대하는 코로케이션일 수 있으며, 셀프서비스·탄력적 자원 풀·책임 분담 여부를 함께 봐야 한다.

02Q2. IaaS에서 고객이 반드시 관리해야 하는 것은?↘

게스트 OS 업데이트와 보안 패치, 설치한 애플리케이션, 네트워크 보안 그룹, 계정·권한, 데이터 보호가 대표적이다. 제공자가 물리 호스트와 가상화 계층을 관리해도 VM 내부의 잘못된 설정은 자동으로 고쳐지지 않는다.

꼬리질문: PaaS로 가면 데이터 보안도 제공자 책임인가? → 아니다. 플랫폼의 물리·OS 운영은 위임되지만 분류, 암호화 선택, 애플리케이션 권한과 계정은 고객이 관리한다.

03Q3. 리전과 AZ를 어떻게 선택하는가?↘

리전은 데이터 주권, 법적 요구, 사용자와의 지연시간, 필요한 서비스의 제공 여부로 선택한다. AZ는 한 리전 안에서 장애를 분리하기 위해 여러 개를 사용한다. 다만 앱·DB·세션·백업까지 장애 경계를 넘겨야 실제 복원력이 생긴다.

꼬리질문: 다른 리전 하나를 추가하면 무조건 재해복구가 되는가? → 아니다. 복제 지연, DNS 전환, 비밀·키, 데이터 일관성, 복구 절차를 시험해야 한다.

04Q4. VM과 컨테이너를 비교해 보라.↘

VM은 게스트 OS와 커널을 포함해 격리와 OS 독립성이 큰 대신 이미지와 시작 비용이 크다. 컨테이너는 격리된 프로세스로 호스트 커널을 공유해 빠르고 밀도가 높지만 커널·런타임·이미지 보안에 의존한다. 실제 클라우드에서는 VM 위에 컨테이너를 실행하는 조합이 흔하다.

꼬리질문: 컨테이너를 쓰면 운영체제 패치가 사라지는가? → 아니다. 이미지의 사용자 공간을 재빌드해야 하고 호스트 커널과 런타임 패치는 운영 주체가 계속 수행한다.

05Q5. 관리형 Kubernetes를 쓰면 무엇이 편해지고 무엇이 남는가?↘

제공자가 컨트롤 플레인 일부의 가용성과 패치를 맡아 클러스터 운영 부담을 줄인다. 고객은 컨테이너 이미지, 워크로드 리소스, 서비스 노출, IAM/RBAC, 시크릿, 로그와 비용을 여전히 관리한다. 관리형이라는 말은 애플리케이션 운영을 대신한다는 뜻이 아니다.

꼬리질문: 작은 Spring Boot 하나에도 Kubernetes를 써야 하는가? → 운영 표준·확장·팀 역량이 필요할 때 선택하고, 그렇지 않으면 단일 VM이나 PaaS가 더 단순한 기본값이다.

06Q6. 클라우드 비용을 온프레미스와 비교할 때 무엇을 포함해야 하는가?↘

클라우드의 VM·스토리지 가격만 보지 말고 요청, 관리형 DB, 로그, 백업, 리전 간 전송과 인터넷 이그레스까지 합산한다. 온프레미스도 장비 감가, 전력·상면, 회선, 예비 부품, 장애 대응 인건비를 포함해야 공정하다. 실제 트래픽 패턴과 1~3년 총소유비용으로 비교한다.

꼬리질문: Spot이 가장 싸니 웹 서버에 쓰면 되는가? → 중단을 견디는 무상태·배치에 적합하다. 중단 시 요청과 세션을 잃는 핵심 단일 서버에는 온디맨드나 약정형과 조합한다.

07Q7. Rehost, Replatform, Refactor를 언제 선택하는가?↘

Rehost는 빠른 이전과 코드 변경 최소화가 우선일 때, Replatform은 관리형 DB·실행 플랫폼으로 운영 부담을 줄일 때 쓴다. Refactor는 구조적 확장성·탄력성 개선이 목표지만 테스트와 설계 변경 비용이 크다. 규제·의존성·서비스 수명까지 평가해 애플리케이션마다 다르게 선택한다.

꼬리질문: 전환 프로젝트 전체를 Refactor로 시작하면 좋은가? → 대규모 이전에서는 위험하다. 먼저 Retain/Retire와 저위험 Rehost·Replatform을 분류하고, 검증된 서비스부터 현대화한다.
