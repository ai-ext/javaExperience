J15. JIT·성능 분석·프로파일링

#J15. JIT·성능 분석·프로파일링

3줄 요약 — HotSpot은 인터프리터로 시작해 실행 프로파일을 모으고, 자주 실행되는 코드를 C1·C2로 단계적으로 컴파일한다. JIT 최적화는 관측된 실행 형태를 전제로 하므로, 워밍업·인라이닝·탈출분석·deoptimization을 이해해야 벤치마크와 운영 프로파일을 바르게 해석한다. 성능 분석은 재현 가능한 JMH 측정, JFR 사건 기록, async-profiler 샘플링, jcmd 스레드·힙 진단을 문제에 맞게 조합한다.

011. 왜 알아야 하나열기 ↓

API p99가 30ms에서 800ms로 튀었는데 CPU는 15%라면 뜨거운 루프 최적화로 해결되지 않는다. DB 대기, 락 경합, 스레드 풀 고갈, GC 정지 중 무엇인지 구분해야 한다. CPU가 100%일 때 평균 응답시간만 보고 고치면 JSON 직렬화·정규식·압축 등 실제 소비 지점을 놓친다.

노트북에서 System.nanoTime()으로 한 번 재도 운영 성능을 알 수 없다. 첫 호출에는 로딩·인터프리터가, 반복 호출에는 JIT·인라이닝이 섞인다. 결과를 쓰지 않으면 계산이 제거될 수 있고, 반복문을 벤치마크 안에 몰면 최적화 양상이 달라진다. JMH가 독립 프로젝트와 생성 하네스를 권하는 이유다.[4][5]

이 문서는 JVM이 코드를 최적화하는 방식부터 측정·수집·진단까지 이어지는 절차를 다룬다. GC 튜닝은 J14, 시작시간 최적화(CDS/AOT)는 J16을 참조한다.

022. 핵심 개념열기 ↓
용어 뜻 실무에서 보는 흔적
인터프리터 바이트코드를 메서드 단위로 해석 실행하며 호출·분기 같은 프로파일을 수집하는 시작 경로 첫 요청 지연, -Xlog:jit+compilation
C1 빠르게 컴파일하고 실행 프로파일을 보강하는 클라이언트 컴파일러 tiered compilation의 중간 컴파일 단계
C2 더 많은 분석 비용을 들여 뜨거운 코드를 최적화하는 서버 컴파일러 인라이닝·루프 최적화가 반영된 코드
Tiered compilation 인터프리터 프로파일과 C1/C2를 결합해 실행 상태에 따라 컴파일 수준을 올리는 HotSpot 방식 로그에 나타나는 compilation level. 숫자와 임계치는 VM 구현 세부사항
인라이닝 호출 대상 메서드의 본문을 호출 지점에 합치는 최적화 간접 호출·분기 비용 감소, 상위 호출자의 추가 최적화 가능
탈출분석 객체 참조가 메서드·스레드 경계를 벗어나는지를 분석하는 최적화 기법 안전한 경우 스칼라 치환·락 제거의 근거
deoptimization 컴파일 코드의 가정이 깨졌을 때 최적화된 프레임을 복원해 덜 최적화된 실행 경로로 되돌리는 것 컴파일 로그의 재컴파일·무효화 흔적, 일시적 지연
워밍업 프로파일을 쌓고 컴파일이 진행되어 정상 운영에 가까운 코드 상태를 만드는 기간 시작 구간과 정상 구간을 분리한 측정
샘플링 프로파일러 짧은 간격으로 스레드의 실행 위치를 표본화해 CPU·대기 스택 비중을 추정 flame graph, 표본 수와 이벤트 설정
JFR JVM·JDK·애플리케이션 이벤트를 시간 정보와 함께 기록하는 Flight Recorder .jfr 파일, JMC의 타임라인·이벤트 분석

C1은 빠른 컴파일·프로파일 수집을, C2는 뜨거운 코드의 추가 최적화를 맡는다. Tiered compilation은 둘 중 하나를 고르는 스위치가 아니라 단계적 경로다. 레벨·임계치·인라이닝 한도는 빌드·플랫폼·플래그에 따라 달라지므로 고정 계약으로 다루지 않는다.[1][2]

혼동하기 쉬운 쌍 구분
지연시간 vs 처리량 지연시간은 한 요청의 완료시간 분포(p50/p95/p99), 처리량은 단위 시간당 처리량이다. 처리량 개선이 p99 개선을 뜻하지 않는다.
JMH vs 운영 프로파일러 JMH는 작은 연산의 통제된 비교 측정에 쓰고, JFR·async-profiler는 실제 애플리케이션의 사건·스택을 관찰한다.
JFR vs CPU flame graph JFR은 여러 종류의 시간 기록 이벤트를 남기고, CPU flame graph는 표본화된 스택으로 CPU 소비 비중을 보여준다.
힙 덤프 vs 힙 사용량 힙 덤프는 객체 그래프를 보관하는 파일이다. GC.heap_info·GC.class_histogram 요약과 달리 객체 값이 포함될 수 있고 수집 비용도 크다.
CPU 샘플 vs 벽시계 지연 CPU 샘플은 실행 중인 스택을, wall-clock 샘플은 실행·대기 시간을 포착한다. CPU가 낮은 느린 요청은 대기 구간을 봐야 한다.

JIT는 프로그램 전체를 한 번에 기계어로 바꾸지 않는다. HotSpot은 실행 빈도와 프로파일을 보고 가치가 있는 메서드부터 컴파일한다. Tiered compilation에서는 C1이 비교적 빠르게 코드를 만들면서 타입·분기 정보를 보강하고, 더 뜨거운 메서드는 C2의 분석 대상이 된다.

이 방식은 인터프리터만 쓰는 경우보다 긴 실행의 성능을 얻으면서도, C2 컴파일이 모든 메서드에 드는 비용을 줄인다. 계층 컴파일은 Java 7부터 HotSpot에 들어왔다.[1]

인라이닝은 호출 비용을 줄일 뿐 아니라 호출자와 피호출자의 상수 전파·죽은 코드 제거를 열어준다. 호출 타입이 안정적이면 컴파일러가 인라인과 가드를 선택할 수 있고, 타입이 다양하거나 코드가 커지면 보류한다. private/final 여부만으로 결정되지 않는다.

탈출분석은 객체 참조가 분석 범위를 벗어나는지 본다. 안전하고 코드 형태가 허용되면 객체를 필드 값으로 스칼라 치환해 힙 할당을 피하거나 락을 제거할 수 있다. “객체가 무조건 스택에 할당된다”는 보장은 아니다. JVM 최적화 결과이므로 실제 할당은 프로파일러로 확인한다.[1]

C2는 관측된 수신 타입이 하나라는 이유로 가상 호출을 직접 호출로 바꾸는 식의 추측을 할 수 있다. 실행 도중 예상하지 못한 타입이 들어오면 가드를 통과하지 못하거나 의존 관계가 무효화되어 deoptimization할 수 있다. 런타임은 최적화 프레임의 값을 복원할 수 있도록 상태 정보를 남기므로 자바 의미와 예외·부수효과는 유지된다.

deoptimization 한 번은 정상적인 적응 동작이다. 같은 메서드가 반복적으로 무효화·재컴파일되면 입력 타입이 흔들리는지, 코드 캐시·컴파일 큐가 압박받는지 확인한다.

02측정과 관측은 서로 다른 질문에 답한다↘
  • JMH는 “이 연산 A와 B의 차이가 이 JVM·CPU·입력 조건에서 반복 측정해도 유지되는가?”를 묻는다. 포크별 실행 프로세스와 워밍업·측정 반복을 분리해, 같은 프로세스에서 누적된 JIT 상태가 한 후보만 유리하게 만드는 일을 줄인다.
  • JFR은 “운영의 특정 60초 동안 CPU 표본, 할당, 락, 스레드, GC 등의 이벤트가 어떤 순서·빈도로 발생했나?”를 기록한다. JEP 328은 JFR을 HotSpot/JVM 문제 해결용 저오버헤드 이벤트 수집기로 JDK 11에 제공했고, 이벤트 설정·필터링·파일 기록을 설계 목표로 삼았다. JEP의 성능 목표 수치는 특정 벤치마크에서의 목표이지 모든 서비스의 무오버헤드 보장이 아니다.[6]
  • [9] async-profiler는 “CPU 또는 할당 표본의 스택 비중은 어디에 모이는가?”를 본다. 전통적인 safepoint 표본화의 편향을 피하려는 설계이고, Java 외의 GC/JIT 스레드 및 네이티브 프레임도 관찰할 수 있다. 샘플은 통계 추정치다. 짧은 실행이나 표본 수가 적은 결과의 작은 비율 차이를 확정적 병목으로 읽지 않는다.[9]

01예제 1 — 실제 컴파일 활동 확인↘

메서드의 컴파일 여부는 출력된 프로그램 결과와 별도로 로그에서 확인한다. 로그의 레벨·타임스탬프는 JVM과 실행 조건에 따라 바뀐다. 아래 예제는 컴파일 로그에서 hot 메서드가 관측되는지를 보는 입력이다. 특정 메서드가 반드시 C2까지 올라간다는 실험 규약은 아니다.

public class JitWorkload {
    @FunctionalInterface
    interface Op { int apply(int x); }

    static int hot(Op op, int n) {
        int sum = 0;
        for (int i = 0; i < n; i++) sum += op.apply(i);
        return sum;
    }

    public static void main(String[] args) {
        Op stable = x -> x * 31 + 7;
        int checksum = 0;
        for (int batch = 0; batch < 5; batch++) checksum += hot(stable, 100_000);
        System.out.println("batches=5, checksum=" + checksum);
    }
}

실행 (Corretto JDK 21에서 실제 실행; unified logging은 JDK 9+):

<JDK21>/bin/java -Xlog:jit+compilation=debug _scratch/J15/JitWorkload.java

실행 결과 중 JitWorkload 행과 프로그램 출력:

[0.201s][debug][jit,compilation] 1376       3       JitWorkload$$Lambda/0x000000b0011443e8::apply (5 bytes)
[0.201s][debug][jit,compilation] 1377       3       JitWorkload::lambda$main$0 (8 bytes)
[0.202s][debug][jit,compilation] 1379 %     3       JitWorkload::hot @ 4 (27 bytes)
[0.202s][debug][jit,compilation] 1380       3       JitWorkload::hot (27 bytes)
batches=5, checksum=1901636720

실제 JVM 출력은 주소·컴파일 ID·시각이 실행마다 다르다. 이 실행에서는 컴파일 레벨 3 로그가 보였다. 한 번의 로그만으로 C2 승격, 인라이닝 성공, 또는 다른 하드웨어에서의 성능 향상을 결론내리지 않는다. 컴파일 로그는 가설을 확인하는 자료이고, 성능 비교는 JMH로 한다.

02예제 2 — JMH로 결과가 살아 있는 벤치마크 만들기↘

JMH README는 독립 Maven 프로젝트와 processor 생성 하네스를 권한다. 아키타입 프로젝트에 다음 클래스를 넣는다. 의존성·프로세서 구성 후 실행 가능하며, 여기서는 JMH를 구성하지 않아 미실행이다.[4][5]

package bench;

import java.util.concurrent.TimeUnit;
import org.openjdk.jmh.annotations.Benchmark;
import org.openjdk.jmh.annotations.BenchmarkMode;
import org.openjdk.jmh.annotations.Mode;
import org.openjdk.jmh.annotations.OutputTimeUnit;
import org.openjdk.jmh.annotations.Scope;
import org.openjdk.jmh.annotations.State;

@State(Scope.Thread)
@BenchmarkMode(Mode.Throughput)
@OutputTimeUnit(TimeUnit.SECONDS)
public class SumBenchmark {
    private final int[] values = {1, 2, 3, 4, 5, 6, 7, 8};

    @Benchmark
    public long sum() {
        long total = 0;
        for (int value : values) total += value;
        return total; // 반환값을 하네스가 소비하므로 계산 결과가 관측 가능하다.
    }
}

아키타입이 만든 프로젝트 루트에서 mvn clean verify로 벤치마크 JAR를 만들고, java -jar target/benchmarks.jar SumBenchmark -wi 5 -i 8 -f 2처럼 실행한다. 여기서 워밍업 5회·측정 8회·포크 2개는 예시 설정이지 보편적인 정답이 아니다.

실제 연산량, 실행 시간, JVM 옵션을 맞추고 입력 자료형도 대표적으로 구성한다. 보고서에는 score 단위, error 또는 confidence interval, 워밍업·측정 횟수, 포크 수, JDK·CPU·OS, GC 설정, 입력 크기를 함께 적는다.

큰 반복문은 호출 단위 분포를 가리거나 루프 최적화를 유발할 수 있다. 결과를 무시하면 dead-code elimination, 상수 입력은 constant folding 대상이 된다. JMH 하네스를 따르고 반환하기 어려운 값만 Blackhole로 소비한다.[5]

03예제 3 — JFR 사용자 이벤트를 파일로 남기기↘

Recording은 기록을 설정·시작·종료하고 파일로 덤프하는 JDK API다. 아래 코드는 요청을 흉내 내는 사용자 이벤트를 하나 기록한 뒤 파일을 다시 열어 해당 이벤트 수를 확인한다. API는 Java 9부터 제공되며, Corretto JDK 21에서 실제 실행했다.[7]

import java.nio.file.Files;
import java.nio.file.Path;
import jdk.jfr.Event;
import jdk.jfr.Label;
import jdk.jfr.Name;
import jdk.jfr.Recording;
import jdk.jfr.consumer.RecordedEvent;
import jdk.jfr.consumer.RecordingFile;

public class JfrRecordingDemo {
    public static void main(String[] args) throws Exception {
        Path file = Path.of("_scratch/J15/request.jfr");
        try (Recording recording = new Recording()) {
            recording.enable(ProfileRequest.class);
            recording.start();
            ProfileRequest event = new ProfileRequest();
            event.route = "/orders";
            event.begin();
            event.end();
            event.commit();
            recording.stop();
            recording.dump(file);
        }
        long count = 0;
        for (RecordedEvent event : RecordingFile.readAllEvents(file)) {
            if (event.getEventType().getName().equals("demo.ProfileRequest")) count++;
        }
        Files.deleteIfExists(file);
        System.out.println("demo.ProfileRequest events=" + count);
    }
}

@Name("demo.ProfileRequest")
@Label("Profile request")
class ProfileRequest extends Event {
    @Label("Route") String route;
}

실행 결과:

demo.ProfileRequest events=1

실서비스에서는 요청마다 고카디널리티 문자열·개인정보를 이벤트에 무심코 넣지 않는다. 이벤트 비용과 파일 크기를 제한하고, 필요한 필드만 기록하며, 운영 JFR 설정은 대상 JDK의 이벤트 설정을 확인해 고른다.

055. 버전별 변화 — 왜 바뀌었나열기 ↓
  • Java 7 — Tiered compilation 도입. 서버 컴파일만 기다리면 시작 구간의 프로파일 수집이 느리고 인터프리터만으로는 정상 상태 처리량이 낮았다. C1으로 빠르게 실행하면서 프로파일을 모으고 이후 더 최적화된 코드로 나아가는 계층을 넣었다. 근거: Oracle HotSpot 성능 가이드.[1]
  • Java 9 — Compiler Control(JEP 165). 전역 컴파일 플래그만으로는 특정 메서드·문맥을 실험하거나 컴파일러 버그의 범위를 격리하기 어려워, 런타임에 메서드별 compiler directive를 적용·변경하는 제어를 추가했다.[3]
  • Java 11 — JDK Flight Recorder(JEP 328). 문제 재현만으로는 부족한 운영 환경의 시계열 JVM·OS·애플리케이션 이벤트를 수집할 수 있도록 JFR을 JDK 기능으로 제공했다. 기록·필터링 API와 파일 형식이 들어왔으며 시각화 자체는 JEP의 목표가 아니어서 JMC 등 분석 도구가 별도 역할을 맡는다.[6]
  • JDK 25 기준 — JFR API 및 HotSpot 컴파일 진단이 계속 제공된다. jdk.jfr.Recording으로 제어·덤프할 수 있고, java 실행 옵션 문서는 컴파일 활동과 code cache 관련 옵션을 설명한다. 진단 플래그는 사용 전에 해당 JDK의 java -X/명령 매뉴얼을 확인한다.[2][7]
  • JMH — Java 언어 기능이 아닌 별도 벤치마크 프로젝트. 단순 시간 재기에서 생기는 워밍업·결과 제거·포크 문제를 하네스로 제어하기 위해 만들어졌다. 프로젝트의 권장 방식은 annotation processor가 생성한 하네스를 포함한 독립 Maven 프로젝트다.[4][5]
066. 실무 가이드열기 ↓

기본값 추천: 회귀 비교는 독립 JMH 프로젝트에서 목표에 맞는 Mode.AverageTime 또는 Mode.Throughput 하나를 고르고, 반복·2개 이상 포크와 동일한 머신·JDK·입력을 유지한다. 운영 탐색은 JFR부터 시작하고 CPU 스택 원인이 필요할 때 async-profiler를 추가한다.[5][6][9]

  • 연산 하나의 변경 전후를 비교한다면, JMH @Benchmark로 한 연산만 재고 반환값을 소비시킨다. 후보별 실행 순서·포크를 분리하고 결과와 환경을 함께 보관한다.
  • API 지연이 나쁘고 CPU가 낮다면 JFR 실행/대기 이벤트와 요청 타임라인을 본다. CPU 표본은 대기 시간을 설명하지 못한다. 운영 기록은 jcmd <pid> JFR.start name=incident settings=profile duration=60s filename=/secure/path/incident.jfr로 제한하고 jfr summary /secure/path/incident.jfr 또는 JMC로 분석한다.[8]
  • CPU가 포화되면 asprof -d 30 -f cpu.html <pid>로 부하 중 30초 샘플을 모아 넓은 프레임과 호출 경로를 본다. 가장 깊은 프레임보다 누적 비중을 기준으로 우선순위를 정한다.[9]
  • 할당이 문제면, JFR allocation 이벤트 또는 async-profiler의 alloc 모드로 상위 할당 경로를 확인한다. 임시 객체 제거가 실제로 할당량을 줄이는지 같은 부하에서 다시 확인한다. GC 원인과 튜닝은 J14 참조.
  • 락 대기가 의심되면, JFR의 모니터/락 이벤트와 여러 시점의 thread dump를 함께 본다. BLOCKED 스레드가 같은 소유자에 반복해서 묶이는지, 잠금 구역에서 I/O나 큰 계산을 하는지 찾는다.
  • JVM 상태는 같은 사용자 권한으로 jcmd -l, jcmd <pid> help, jcmd <pid> Thread.print -l, jcmd <pid> GC.heap_info 순으로 확인한다. jstack -l <pid>는 락 정보를 더하고 세 시점 덤프를 비교할 때 유용하다. JDK 25 문서는 jstack·jmap을 실험적·비지원으로 표시하므로 가능한 작업은 jcmd를 우선한다.[8][10][11]
  • 힙 그래프가 꼭 필요할 때만 jcmd <pid> GC.heap_dump /secure/path/heap.hprof나 jmap -dump:live,format=b,file=/secure/path/heap.hprof <pid>를 계획한다. 덤프는 서비스 정지·디스크 사용·개인정보 유출 위험을 감수해야 하는 사고 자료다. jmap -histo:live <pid>도 live 객체 집계 과정의 비용을 고려한다.[10]
  • 컴파일 정체나 code cache 부족이 의심되면 -Xlog:jit+compilation=debug와 jcmd <pid> Compiler.codecache를 확인한다. 진단 플래그를 상시 켜두기보다 같은 시점의 CPU·지연·컴파일 로그를 제한된 시간 동안 수집한다.
  • 코드 변경 전후 운영 검증은 같은 트래픽 형상으로 단계 배포하고 p50/p95/p99, 처리량, CPU, 할당률, 오류율을 비교한다. 마이크로벤치마크의 몇 퍼센트 차이가 서비스 개선으로 이어졌는지 별도로 확인한다.
077. 함정·안티패턴열기 ↓
  1. 워밍업 없이 첫 실행만 측정 → 클래스 로딩, 인터프리터, 초기화, JIT 컴파일 비용이 섞인다 → JMH 워밍업과 측정 반복을 분리하고 초기 요청 지연 자체가 요구사항이면 콜드 스타트 별도 측정으로 정의한다.
  2. 연산 결과를 버리는 수제 마이크로벤치마크 → dead-code elimination·상수 접기·루프 최적화가 실제 작업을 제거하거나 변형한다 → 결과를 반환하거나 JMH Blackhole을 사용하고 실제 입력 범위를 넣는다.
  3. 벤치마크 메서드 안에 큰 반복문 → 반복문이 하나의 최적화 단위가 되어 호출·분기·분포가 실제 경로와 달라진다 → JMH 샘플처럼 연산 단위를 벤치마크하고 루프를 넣어야 할 이유가 있는지 먼저 검증한다.
  4. 한 번의 평균 수치로 승자를 선언 → OS 스케줄링·주파수 조정·백그라운드 작업·JIT 상태가 차이를 가린다 → 포크·반복·오차범위를 보고, 기대 효과보다 오차가 크면 동등으로 판단한다.
  5. CPU flame graph만 보고 I/O 대기 원인을 찾음 → CPU 프로파일에는 스레드가 잠든 시간이 충분히 나타나지 않는다 → wall-clock/JFR 대기 이벤트, thread dump, DB·외부 호출 지표를 함께 본다.
  6. flame graph의 가장 위쪽 프레임만 최적화 → 그래프 폭은 샘플 비중을 나타내며 한 번의 긴 호출이나 전체 요청 지연을 뜻하지 않는다 → 넓은 경로와 호출자를 확인하고 표본 수·수집 이벤트·부하 재현성을 확인한다.
  7. 힙 덤프를 무심코 운영 서버에서 생성 → Full GC급 정지·큰 파일·메모리 압박이 생길 수 있고 객체 내용에 개인정보가 남는다 → 우선 GC.heap_info/class histogram, JFR로 좁힌 뒤 승인된 창구·보안 저장소·용량을 준비한다.
  8. deoptimization을 곧바로 JIT 버그라고 판단 → 프로파일 가정이 깨진 뒤 복구하는 정상 동작일 수 있다 → 반복 빈도와 대상 메서드, 타입 다양성, 입력 패턴을 함께 보고 지속적인 재컴파일·지연으로 이어지는지 확인한다.
088. 자가점검 Q&A (면접 대비)Q1. 인터프리터가 있는데도 JIT 컴파일을 하는 이유는? · Q2. C1과 C2의 역할을 간단히 설명하라. · Q3. 인라이닝은 왜 성능을 높이고, 왜 항상 하지 않는가? · Q4. 탈출분석과 스칼라 치환을 설명하라.열기 ↓
01Q1. 인터프리터가 있는데도 JIT 컴파일을 하는 이유는?↘

인터프리터는 시작이 빠르고 프로파일을 모으지만 반복 실행마다 바이트코드를 해석한다. JIT는 뜨거운 경로를 기계어로 바꾸고 런타임 정보를 최적화에 쓴다. 컴파일 비용이 있으므로 실행 빈도로 대상을 고른다.

꼬리질문 — 모든 메서드가 C2까지 컴파일되는가? 아니다. 호출량·복잡도·컴파일 비용 등으로 일부 메서드는 인터프리터나 낮은 레벨에 남을 수 있다. 로그의 숫자를 고정 계약으로 보지 않는다.

02Q2. C1과 C2의 역할을 간단히 설명하라.↘

C1은 빠른 컴파일과 프로파일 수집을 맡고, C2는 추가 최적화를 수행한다. 개별로 켜기보다 tiered compilation의 코드 상태를 로그로 확인한다.

꼬리질문 — C2가 항상 더 좋은가? 뜨겁지 않은 메서드는 컴파일 비용이 이득보다 클 수 있다. 짧은 실행이나 빠른 시작이 중요한 프로그램은 정상상태 처리량만으로 결론내리지 않는다.

03Q3. 인라이닝은 왜 성능을 높이고, 왜 항상 하지 않는가?↘

호출·디스패치 비용을 줄이며 호출자와 피호출자 본문을 함께 최적화할 기회를 만든다. 하지만 큰 메서드를 계속 인라인하면 코드 크기와 instruction cache 압박이 커지고 컴파일 시간도 늘어난다. 호출 대상이 안정적인지와 인라인 예산을 함께 따진다.

꼬리질문 — final을 붙이면 반드시 인라인되는가? 아니다. final은 동적 오버라이드 가능성을 줄이는 정보일 뿐이고, 코드 크기·호출 빈도 등 다른 판단은 남는다.

04Q4. 탈출분석과 스칼라 치환을 설명하라.↘

탈출분석은 객체 참조가 분석 범위를 벗어나는지 알아내는 기법이다. 안전하다고 판단하면 구현이 허용하는 경우 객체를 필드별 값으로 풀어 힙 할당을 없애거나 잠금을 제거할 수 있다. 모든 지역 객체가 스택에 배치된다는 뜻도, 소스에서 new를 지우면 항상 할당이 사라진다는 뜻도 아니다.

꼬리질문 — 지역 변수로 만든 객체는 힙에 있는가? 자바 언어는 이를 보장하지 않는다. JIT 최적화로 물리적 객체 할당이 사라질 수 있으므로 allocation profiler로 관측하고 판단한다.

05Q5. deoptimization은 언제 발생하고 왜 필요한가?↘

JIT가 프로파일을 바탕으로 가정한 타입·클래스 계층 등이 실제 실행에서 깨질 때 발생한다. 런타임은 최적화 프레임을 복구해 올바른 실행을 이어가고 이후 다시 컴파일할 수 있다. 추측 최적화의 성능 이득과 자바 의미의 정확성을 함께 유지하는 장치다.

꼬리질문 — 한 번 발생하면 장애인가? 아니다. 일회성은 정상일 수 있다. 반복적인 무효화·재컴파일과 지연 상승이 함께 나타날 때 원인을 조사한다.

06Q6. JMH에서 워밍업·포크·결과 소비가 필요한 이유는?↘

워밍업은 측정 구간 전에 JIT가 대표 코드 상태에 도달하게 한다. 포크는 JVM 프로세스를 분리해 이전 벤치마크가 만든 컴파일·프로파일 상태가 다음 결과를 오염시키는 일을 줄인다. 반환값이나 Blackhole은 계산이 dead code가 되는 일을 막는다.

꼬리질문 — 워밍업을 길게 하면 언제나 정확한가? 아니다. 워밍업 길이는 코드의 컴파일 안정화와 실제 운용 구간에 맞춰야 한다. 무한히 길게 돌리면 콜드 구간이나 짧은 작업의 특성을 지워버릴 수 있다.

07Q7. JFR과 async-profiler를 어떻게 선택하는가?↘

여러 종류의 JVM·애플리케이션 사건을 시간 순서로 보고 싶으면 JFR을 먼저 쓴다. CPU 소비 스택의 비중, 할당 경로, 락 경합을 flame graph로 좁히고 싶으면 async-profiler가 적합하다. 두 도구는 경쟁 관계가 아니라 문제를 좁히고 검증하는 상호 보완 도구다.

꼬리질문 — JFR이 저오버헤드이면 무조건 상시 무제한 기록해도 되는가? 설정·이벤트 양·보존 시간에 따라 비용과 디스크 사용이 달라진다. 저장량을 제한하고 데이터 접근·보존 정책을 적용한다.

08Q8. CPU는 낮은데 응답시간이 높은 서비스에서 무엇을 볼 것인가?↘

CPU flame graph보다 먼저 여러 시점의 thread dump와 JFR의 스레드·대기·모니터 이벤트를 본다. BLOCKED는 모니터 획득 대기, WAITING은 신호나 조건 대기, RUNNABLE은 CPU에서 실행 중일 수도 있고 네이티브 호출 중일 수도 있다. DB 커넥션 풀·외부 호출의 대기시간과 큐 적체도 같이 확인한다.

꼬리질문 — thread dump 한 장으로 데드락을 확정할 수 있는가? 덤프가 데드락 정보를 보고할 수는 있지만, 순간 상태만으로 진행성 저하의 추세를 판단하기는 어렵다. 일정 간격 덤프를 비교하고 락 소유자와 스택을 연결한다.
