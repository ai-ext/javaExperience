P02 · 사용자 시안 05·06 / 두 응답 경로

같은 Spring MVC인데 왜 HTML과 JSON이 다를까요?

요청과 Controller의 반환 방식을 골라 두 경로를 비교하세요.

HTML 화면Model → Thymeleaf → HTML

@Controller가 name을 Model에 넣고 뷰 이름 hello를 돌려줍니다. hello.html이 문장을 만듭니다.

JSON 데이터MemoResponse → HttpMessageConverter → JSON

@RestController가 DTO를 반환합니다. 메시지 변환기가 응답 본문으로 직렬화하며 서버의 HTML View를 렌더링하지 않습니다.

GET /hello는 hello.html을 렌더링해 HTML을 응답합니다.

JSON 응답에도 hello.html이 쓰일까요?

아니요. GET /api/memos는 응답 DTO를 JSON으로 직렬화합니다. 이 비교는 같은 예제 앱의 두 경로를 설명하며, 실제 서버 요청 결과는 아닙니다.

이 화면의 GET /api/memos는 목록 조회 예시입니다. 다음 장면에서 직접 보내는 POST /api/memos는 새 메모를 만드는 별도 요청입니다.

P02 · 시안 10 / 인메모리 저장소

P02 · 시안 13 / record와 Entity

이 실습의 Memo record는 JPA Entity가 아닙니다

값을 전달하는 타입과 DB 영속 상태를 관리하는 타입을 한 예제의 같은 객체로 합치지 않습니다.

현재 P02 코드MemoResponse · 불변 값 전달
public record MemoResponse(long id, String title, String content) {}

record 구성 요소는 생성 뒤 다시 대입할 수 없습니다. 이 실습은 인메모리 저장소를 사용합니다.

JPA Entity는 다른 DB 실습에서 영속성 컨텍스트와 상태 변경을 배웁니다. 시안 속 MemoEntity는 별도 설명 예시이며 이 프로젝트의 P02 코드에 만들지 않습니다.

P02 · 시안 14 / 생성자 주입

Spring은 시작할 때 구현 객체를 만들고 생성자로 연결합니다

Service는 MemoRepository 인터페이스에 의존하고 Spring은 등록된 구현체를 넣습니다. 요청마다 새로 조립하지 않습니다.

@RepositoryInMemoryMemoRepositoryimplements MemoRepository
→
@ServiceMemoServiceMemoService(MemoRepository repository)
→
@RestControllerMemoControllerMemoController(MemoService service)
HTTP 요청 → MemoController.create → MemoService.create → MemoRepository.save

앱 시작 시 Spring이 구현체·Service·Controller를 만들고 생성자 의존성을 연결합니다.

인터페이스 자체의 객체를 만드는 것이 아닙니다. 등록된 구현 객체를 인터페이스 타입 매개변수에 주입합니다.

MVC는 HTTP 요청과 응답을 다루는 표현 계층의 방식이다.

011. 한 줄로 말하면열기 ↓

Spring MVC는 Servlet 기반 웹 프레임워크에서 HTTP 요청을 Controller에 연결해 HTML 뷰를 렌더링하거나 응답 본문을 만드는 구조다. MVC의 Model·View·Controller와 애플리케이션의 Controller·Service·Repository는 서로 다른 분류다. Controller·Service·Repository는 기능을 나누는 계층형 구조이며, 웹 요청이 업무 로직과 저장소 코드에 뒤섞이지 않도록 경계를 둔다.

이 경계를 놓치면 파라미터 검증, 업무 규칙, DB 코드가 Controller 하나에 몰린다. 같은 규칙을 다른 API에서 복사하다 동작이 달라지고, JSON에 DB Entity를 그대로 노출해 내부 필드가 계약에 새거나 순환 참조·지연 로딩 오류가 생긴다. 작은 기능을 만들 때부터 각 계층에 한 가지 책임을 두면 변경할 위치가 분명해진다.

012.1 MVC란↘

Model은 View에 전달할 데이터, View는 HTML 등의 표현, Controller는 요청 처리 연결을 맡는다. MVC의 Model은 Repository를 뜻하지 않는다. Spring MVC는 화면과 JSON API 모두 처리한다.

022.2 화면과 REST 응답↘

@Controller의 return "hello"는 뷰 이름이고, @RestController에서 반환한 객체는 HTTP 본문으로 변환된다. Thymeleaf 화면은 Model에 데이터를 담고, REST는 응답 DTO를 반환한다.

032.3 MVC와 계층형 구조↘

Spring MVC는 웹 처리 프레임워크다. Controller·Service·Repository는 책임을 나누는 계층이므로 REST API도 이 구조를 쓸 수 있다. 기본 호출 방향은 Controller → Service → Repository다.

042.4 Controller↘

2.4 · 요청을 받는 경계

POST /api/memos의 JSON은 MemoCreateRequest로 변환되어 Controller에 도착합니다. Controller는 Service를 호출하고 201 Created와 응답 DTO를 돌려줍니다.

Controller의 역할

  • 경로와 HTTP 메서드를 매핑합니다.
  • 요청 DTO를 받아 Service에 전달합니다.
  • 상태 코드와 응답 DTO를 정합니다.
  • 업무 규칙과 SQL은 여기에 두지 않습니다.

@PostMapping
public ResponseEntity<MemoResponse> create(

    return ResponseEntity.status(HttpStatus.CREATED).body(created);
}
052.5 Service↘

2.5 · 요청 하나를 유스케이스로 처리

현재 예제의 create는 요청 값을 저장소에 전달하고, 저장된 Memo를 MemoResponse로 바꿉니다. 공통 업무 규칙이 필요해지면 그 판단을 Service에 추가합니다.

01 · 요청 받기MemoCreateRequesttitle · contentController가 전달
→
02 · 저장 요청repository.save(...)request.title(), request.content()Repository 계약 호출
→

실제 코드 · MemoService.create

public MemoResponse create(MemoCreateRequest request) {
    Memo saved = repository.save(request.title(), request.content());
    return toResponse(saved);
}
private MemoResponse toResponse(Memo memo) {
    return new MemoResponse(memo.id(), memo.title(), memo.content());
}
현재 예제의 범위지금 구현은 간단한 저장과 DTO 변환입니다. 유효성·중복 검사처럼 여러 진입점에서 함께 적용할 업무 판단은 필요해질 때 Service에 둘 수 있습니다. 현재 코드에 해당 규칙이나 스케줄러, DB는 구현되어 있지 않습니다.
062.6 Repository↘

Repository는 저장·조회 계약을 제공하고 구현을 감춥니다. 이 예제는 DB 쿼리 대신 ConcurrentHashMap에 보관하므로 앱을 다시 시작하면 데이터가 사라집니다.

072.7 DTO와 Entity↘

2.7 · 경계마다 필요한 필드만 전달

요청 DTO는 입력을 제한하고 응답 DTO는 공개할 값을 고릅니다. 이 실습의 Memo는 JPA Entity가 아니라 메모리 저장소에서 쓰는 도메인 record입니다.

요청 DTO · 입력 허용MemoCreateRequest
title입력 허용content입력 허용
record MemoCreateRequest( String title, String content) {}
→
내부 도메인 객체 · InMemoryMemo
id저장 시 생성title내부 값content내부 값
record Memo(long id, String title, String content) {}
→
응답 DTO · 공개 필드MemoResponse
id응답에 포함title응답에 포함content응답에 포함
record MemoResponse(long id, String title, String content) {}
request.title(), request.content()→repository.save(...)→new MemoResponse(id, title, content)

이 예제는 Service에서 변환하며, 반복되는 변환은 Mapper로 분리할 수 있습니다.

외부 Entity 직접 노출을 피하는 이유내부 필드가 API 응답에 섞이면 공개 계약이 의도치 않게 바뀔 수 있습니다. 요청에서 Entity를 그대로 받으면 허용하지 않은 필드까지 수정되는 대량 할당 위험이 생깁니다.
082.8 DTO에 record↘

2.8 · DTO를 선언하는 두 방식

record는 값 전달용 타입을 짧게 선언하는 방법이며 Java 16에서 정식화됐습니다(JEP 395). 컴포넌트 참조는 재할당할 수 없지만, 그 안에 든 객체까지 자동으로 깊은 불변이 되는 것은 아닙니다.

일반 클래스 · 별도 파일필드·생성자·접근자를 직접 선언
// MemoResponse.java
public class MemoResponse {
    private final long id;
    private final String title;
    public MemoResponse(long id, String title) {
        this.id = id;
        this.title = title;
    }
    public long id() { return id; }
    public String title() { return title; }
}
record · 별도 파일같은 두 값을 간결하게 선언
// MemoResponse.java
public record MemoResponse(long id, String title) {}
  • 생성자·접근자와 equals·hashCode·toString을 제공합니다.
  • 컴포넌트 값은 생성 뒤 다시 대입할 수 없습니다.
  • 값 전달 DTO를 간결하게 표현하기 좋습니다.

상태 변경이 필요하면 일반 클래스로 가변 상태를 직접 설계할 수 있습니다. 비교용 클래스 예시는 같은 값들을 final 필드로 담았습니다.

Jackson 직렬화 개념 예시new MemoResponse(1, "첫 메모")→{ "id": 1, "title": "첫 메모" }개념 예시이며, 현재 P02 실습의 MemoResponse는 id · title · content 세 필드를 가집니다.

102.10 의존 방향↘

2.10 · 한 방향으로 의존하고 생성자로 주입

요청 처리 의존성은 Controller → Service → Repository로 흐릅니다. Spring이 등록된 구현체를 생성자에 전달해 각 클래스의 의존 관계를 드러냅니다.

@RestControllerMemoControllerMemoController(MemoService service)Service를 생성자 주입 받음
→
@ServiceMemoServiceMemoService(MemoRepository repository)Repository 인터페이스에 의존
→
@Repository · 구현체InMemoryMemoRepositoryimplements MemoRepositoryMap 기반 저장소 구현
Spring 컨테이너가 연결합니다MemoRepository 인터페이스 자체를 만드는 것이 아닙니다. 등록된 InMemoryMemoRepository 구현 객체를 생성자 매개변수의 인터페이스 타입에 주입합니다.

실제 생성자 · Controller / Service

public MemoController(MemoService service) {
    this.service = service;
}
public MemoService(MemoRepository repository) {
    this.repository = repository;
}

실제 저장소 구현

@Repository
public class InMemoryMemoRepository
        implements MemoRepository {
    private final ConcurrentHashMap<Long, Memo> memos
            = new ConcurrentHashMap<>();
}

package com.example.memo.repository;

import com.example.memo.domain.Memo;
import java.util.List;

public interface MemoRepository {
    Memo save(String title, String content);
    List<Memo> findAll();
}

src/main/java/com/example/memo/repository/InMemoryMemoRepository.java:

package com.example.memo.repository;

import com.example.memo.domain.Memo;
import java.util.Comparator;
import java.util.List;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicLong;
import org.springframework.stereotype.Repository;

@Repository
public class InMemoryMemoRepository implements MemoRepository {
    private final AtomicLong sequence = new AtomicLong();
    private final ConcurrentHashMap<Long, Memo> memos = new ConcurrentHashMap<>();

    @Override
    public Memo save(String title, String content) {
        long id = sequence.incrementAndGet();
        Memo memo = new Memo(id, title, content);
        memos.put(id, memo);
        return memo;
    }

    @Override
    public List<Memo> findAll() {
        return memos.values().stream()
                .sorted(Comparator.comparingLong(Memo::id))
                .toList();
    }
}

src/main/java/com/example/memo/application/MemoService.java:

package com.example.memo.application;

import com.example.memo.api.MemoCreateRequest;
import com.example.memo.api.MemoResponse;
import com.example.memo.domain.Memo;
import com.example.memo.repository.MemoRepository;
import java.util.List;
import org.springframework.stereotype.Service;

@Service
public class MemoService {
    private final MemoRepository repository;

    public MemoService(MemoRepository repository) {
        this.repository = repository;
    }

    public MemoResponse create(MemoCreateRequest request) {
        Memo saved = repository.save(request.title(), request.content());
        return toResponse(saved);
    }

    public List<MemoResponse> findAll() {
        return repository.findAll().stream().map(this::toResponse).toList();
    }

    private MemoResponse toResponse(Memo memo) {
        return new MemoResponse(memo.id(), memo.title(), memo.content());
    }
}

간결성을 위해 Service가 DTO 변환을 맡았다. 커지면 별도 Command/Query나 Mapper로 분리하되 Entity를 HTTP 응답으로 직접 노출하지 않는다.

확인: 구현에 @Repository, Service에 @Service가 있고 생성자에서 Repository를 받는지 본다. (미실행)

043.4 Controller에서 HTTP 입출력을 연결하기↘

src/main/java/com/example/memo/api/MemoController.java:

package com.example.memo.api;

import com.example.memo.application.MemoService;
import java.util.List;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/memos")
public class MemoController {
    private final MemoService service;

    public MemoController(MemoService service) {
        this.service = service;
    }

    @PostMapping
    public ResponseEntity<MemoResponse> create(@RequestBody MemoCreateRequest request) {
        MemoResponse created = service.create(request);
        return ResponseEntity.status(HttpStatus.CREATED).body(created);
    }

    @GetMapping
    public List<MemoResponse> findAll() {
        return service.findAll();
    }
}

@RequestMapping과 메서드 애노테이션을 조합해 두 URL을 처리한다. JSON POST 요청은 Content-Type: application/json으로 보낸다.

확인: ./gradlew bootRun 또는 ./mvnw spring-boot:run 후 로그의 기동 메시지와 8080 포트를 확인한다. (미실행)

055. 자주 나는 에러와 해결열기 ↓
  1. 404 Not Found → URL·HTTP 메서드가 매핑과 다르다. @RequestMapping과 요청 주소를 대조한다.
  2. 415 Unsupported Media Type → 요청 형식을 표시하지 않았다. JSON 본문에 Content-Type: application/json을 보낸다.
  3. No qualifying bean of type 'MemoRepository' available → 구현 빈이 없거나 스캔 범위 밖이다. 구현에 @Repository를 붙이고 시작 클래스를 루트 패키지에 둔다.
  4. TemplateInputException: Error resolving template [hello] → Thymeleaf 의존성·템플릿 위치·뷰 이름 중 하나가 안 맞는다. templates/hello.html과 return "hello"를 확인한다.
  5. @Controller가 문자열을 뷰로 찾음 → 문자열을 응답 본문으로 생각했다. 본문이면 @ResponseBody나 @RestController를 쓴다.
  6. JSON 요청에 400 응답 → JSON 문법이나 DTO 필드 타입·이름이 맞지 않는다. 요청 본문과 record 선언을 비교하고 변환 오류 로그를 확인한다.
  7. Port 8080 was already in use → 포트를 다른 프로세스가 사용한다. 기존 프로세스를 종료하거나 server.port를 바꾼다.
066. 한 단계 더열기 ↓

요청 매핑과 메시지 변환의 내부 순서는 → S05 참조. REST 자원·상태 코드 설계는 → S06, 여러 DB 변경을 원자 처리하는 방법은 → S08 참조. 여기서는 HTTP 경계를 Controller, 업무 판단을 Service, 데이터 접근을 Repository에 두고 도메인 객체를 HTTP 계약에 직접 노출하지 않는 원칙을 익힌다. 복잡한 도메인 의존이 생기면 포트·어댑터를 검토한다.

077. 자가점검 Q&A (면접 대비)Q1. MVC의 Model은 Repository와 같은 뜻인가? · Q2. @Controller와 @RestController의 반환값 차이는? · Q3. 업무 규칙을 Controller에 넣으면 왜 문제가 되나? · Q4. DTO와 Entity를 왜 분리하는가?열기 ↓
01Q1. MVC의 Model은 Repository와 같은 뜻인가?↘

아니다. Model은 View가 렌더링할 데이터이고 Repository는 저장소 접근 계층이다. JSON 응답 DTO가 Model의 일부 역할을 해도 Repository는 아니다.

꼬리질문: REST에 View가 없어도 Spring MVC인가?
답: 그렇다. 요청 매핑은 Spring MVC가 처리하고 JSON은 메시지 변환기로 본문에 쓴다.

02Q2. @Controller와 @RestController의 반환값 차이는?↘

@Controller의 문자열은 보통 뷰 이름이다. 응답 본문 어노테이션이 적용되면 값을 본문으로 기록하며 @RestController는 이 동작을 기본 적용한다.

꼬리질문: @Controller에서 JSON을 반환하려면?
답: 메서드에 @ResponseBody를 붙이거나 @RestController를 쓴다.

03Q3. 업무 규칙을 Controller에 넣으면 왜 문제가 되나?↘

HTTP 진입점에 규칙이 묶여 다른 진입 방식에서 재사용하기 어렵고 중복 규칙이 달라질 수 있다. 유스케이스 판단은 Service에 둔다.

꼬리질문: 한 줄짜리 Service도 항상 만들어야 하나?
답: 기계적으로 늘릴 필요는 없다. 규칙·재사용 책임이 생기는 시점에 경계를 둔다.

04Q4. DTO와 Entity를 왜 분리하는가?↘

Entity를 요청으로 받으면 내부 필드를 외부에서 변경하는 대량 할당 위험이 있다. 응답으로 내보내면 내부 구조가 API 계약이 된다. DTO로 입출력 필드를 명시한다.

꼬리질문: 필드가 같아도 분리하는가?
답: 공개 계약과 내부 모델의 변경 이유가 다르면 분리한다. 단순 매핑 비용과 독립성의 균형을 팀 기준으로 정한다.

05Q5. Repository에 업무 규칙을 두면 안 되는가?↘

Repository는 조회·저장 방식과 쿼리 책임을 갖고, 업무상 허용 여부는 Service가 판단한다. 저장소 제약은 데이터 무결성의 최종 방어로 함께 쓸 수 있다.

꼬리질문: 이메일 중복 가입을 막는다면?
답: 중복 조회는 Repository, 가입 거절 결정은 Service, 동시 요청 보장은 DB unique 제약으로 처리한다.

06Q6. 계층별과 기능별 패키지 중 무엇을 선택할까?↘

작은 앱에선 계층별이 간단하지만 기능이 많아지면 한 기능의 코드가 흩어진다. 기능별 최상위 패키지 아래 역할을 나누는 구성을 기본값으로 삼는다.

꼬리질문: 기능 내부 계층은 항상 나눠야 하나?
답: 작으면 생략할 수 있다. 책임이 섞이고 클래스가 늘 때 하위 패키지를 만든다.

07Q7. Repository 인터페이스를 Service 생성자로 받는 이유는?↘

Service를 저장소 구현에서 분리해 교체할 수 있고 생성자 주입이 의존성을 드러낸다. 구현 빈이 여러 개면 @Primary나 @Qualifier 등으로 선택을 명시한다.

꼬리질문: 구현을 직접 new 하면 어떤 비용이 있나?
답: 구현 교체와 테스트 격리가 어려워지고 객체 생명주기를 컨테이너에 맡길 수 없다.
