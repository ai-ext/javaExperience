# D06. 배포란 무엇인가 — 환경·방식·무중단 배포·롤백

> 배포는 실행 가능한 변경을 특정 환경에 적용하는 일이고, 릴리스는 그 기능을 사용자에게 사용할 수 있게 하는 결정이다.
> 무중단은 배포 도구 이름이 아니라 용량·트래픽 전환·헬스 확인·종료·DB 호환성이 함께 맞아야 얻는 결과다.
> 장애 때 이전 버전으로 돌아갈 수 있도록 애플리케이션과 데이터 변경을 나누어 계획하고, 지표를 보고 단계적으로 넓혀라.

## 1. 큰 그림

```mermaid
flowchart LR
    A["코드 변경·커밋"] --> B["빌드·테스트"]
    B --> C["버전이 붙은 산출물"]
    C --> D["dev 환경에 배포"]
    D --> E["QA 검증"]
    E --> F["stg 리허설·승인"]
    F --> G["prod에 배포"]
    G --> H["헬스·오류율·지연 관찰"]
    H --> I["사용자 공개·점진 확대"]
    H --> J["중단·롤백 또는 핫픽스"]
    J --> H
```

코드는 저장소에 있다고 서비스에 반영된 것이 아니다. 빌드 단계가 코드와 의존성을 실행 가능한 산출물(JAR 또는 컨테이너 이미지)로 만들고, 테스트·검토를 거친 같은 산출물을 환경별 실행 설정과 함께 배치한다. dev와 QA에서 발견한 문제를 고친 뒤 운영과 비슷한 stg에서 배포 절차와 주요 시나리오를 확인하고 prod로 간다. 조직에 따라 QA가 사람·팀·검증 단계 이름이기도 하므로 정확한 의미는 팀의 운영 문서에서 확인한다.

prod 배포 후에도 완료 버튼을 누르면 끝나는 게 아니다. 새 프로세스가 요청을 받을 준비가 됐는지 확인하고, 오류율·지연·로그·업무 지표를 살핀다. 문제가 없으면 전체 트래픽 또는 기능 공개 범위를 넓힌다. 이상이 보이면 확대를 멈추고 이전 산출물로 복귀하거나 수정본을 배포한다. DB 구조를 바꿨다면 앱만 되돌려도 예전 앱이 새 스키마에서 동작하는지 별도로 판단해야 한다.

이 문서는 전체 개발 과정(D01)에서 검증된 변경을 실행 환경에 옮겨 사용자에게 제공하는 구간을 다룬다. 파이프라인 구성은 D08, 이미지 빌드·Kubernetes 매니페스트·probe 설정은 S19, 인프라 형태는 D07 참조.

| 배포 승인 | 지정된 책임자가 변경 범위·시각·검증·복구 계획을 확인하는 통제 | 당직자가 변경 티켓 승인 | 코드 리뷰나 테스트 성공과 다른 책임·운영 판단 |
| 배포 동결(Freeze) | 특정 기간 운영 변경을 제한해 위험을 줄이는 조직 정책 | 대규모 행사 전 변경 동결 | 기술적으로 배포가 불가능한 상태가 아님; 예외·긴급 절차를 둠 |
| 스모크 테스트 | 핵심 경로가 크게 깨지지 않았는지 빠르게 확인하는 최소 검사 | 로그인 후 주문 조회 | 전체 회귀 테스트를 대체하지 않음 |
| expand-contract | 스키마 변경을 호환 가능한 확장·전환·정리로 나누는 패턴 | 새 컬럼으로 이전 후 옛 컬럼 제거 | 한 번의 파괴적 DDL이나 앱 롤백과 다름 |
| 컨테이너 | 앱 실행환경을 이미지로 묶어 같은 단위로 시작하는 방식 | 같은 이미지 digest를 stg·prod에 배치 | VM 전체를 이미지화하는 것과 다름; 설정·영속 데이터는 보통 외부에 둠 |
| PaaS | 플랫폼이 앱 실행·스케일·상태 관리 일부를 제공하는 서비스 모델 | Git에 push하거나 이미지 지정해 배포 | 배포 책임이 사라지는 것이 아니라 운영 경계가 플랫폼과 나뉨 |

## 3. 단계별로 보기

### 3.1 환경과 설정을 맞춘다

환경은 앱 버전, 의존 서비스, 네트워크, 권한, 설정이 묶인 실행 조건이다. local은 개인 확인, dev는 통합, QA는 계획된 검증, stg는 운영 리허설, prod는 실제 서비스가 목적이다. 조직에 따라 QA는 환경 또는 검증 조직을 뜻한다.

가능하면 같은 JAR 또는 이미지 digest를 환경 간 승격한다. 코드까지 다시 빌드하면 검증한 산출물과 prod 실행물의 동일성을 확인하기 어렵다. DB URL·외부 API 주소는 외부 설정으로, 비밀번호·토큰은 시크릿 저장소로 분리한다. Spring Boot는 properties/YAML, 환경 변수, 시스템 속성, 명령행 인자의 우선순위를 정의한다.

### 3.2 산출물을 실행 환경에 옮기는 방식

| 방식과 절차 | 장점 | 한계·실패 신호 | 맞는 상황 |
|---|---|---|---|
| JAR 복사 + `nohup` | 빌드 JAR를 서버에 복사하고 `nohup java -jar ... &`로 즉시 실행 | 셸 스크립트마다 PID·로그·재시작·부팅 등록 방식이 달라짐. SSH 종료 후 프로세스가 사라지거나 두 버전이 같은 포트를 잡는 일이 생김 | 개인 VM 실습, 단일 서버의 임시 확인; 장기 운영 기본값으로 삼지 않음 |
| JAR + systemd 서비스 | 서비스 단위에 사용자·실행 명령·재시작 정책을 두고 서비스 매니저가 시작·종료·상태를 관리 | 단일 서버 중심이라 여러 대의 용량·배포 순서를 직접 관리해야 함. 재시작 반복은 근본 장애를 숨길 수 있음 | 소수 Linux VM, 컨테이너 플랫폼 도입 전 단순 서비스 |
| Docker 컨테이너 | 앱 실행 단위를 이미지로 고정해 레지스트리에서 가져와 실행 | 컨테이너 하나만으로 자동 배포·무중단·스케일링이 생기지 않음. 외부 설정, 시크릿, 상태 데이터, 프로세스 종료는 별도 설계 | 개발·검증·운영의 실행 단위를 통일하고 싶은 경우 |
| Kubernetes·PaaS | 원하는 개수·버전을 선언하거나 플랫폼 절차로 배포하고, 플랫폼이 인스턴스 수명·교체를 조정 | 플랫폼 설정·비용·권한·관찰이 추가됨. 설정 오류, 이미지 pull 실패, 준비 실패가 rollout을 막을 수 있음 | 여러 서비스·인스턴스를 반복 운영하거나 자동 복구·스케일 요구가 뚜렷한 경우 |

운영 방식은 순서대로 대체되지 않는다. JAR + systemd, VM의 Docker, PaaS가 함께 쓰이며 선택은 배포 빈도·서비스 수·당직 역량·비용에 달렸다. 이미지와 Kubernetes 설정은 S19 참조.

### 3.3 prod로 전환하고 상태를 판단한다

새 버전을 실행했다고 곧바로 트래픽을 보내지 않는다. 앱이 초기화되고 의존성 연결을 마쳤는지 확인한 뒤 준비된 인스턴스만 요청을 받게 한다. 교체될 구 버전에는 종료 신호를 보내고, 새 연결을 거절하면서 진행 중 요청이 끝날 시간을 준다.

Spring Boot의 내장 웹 서버는 graceful shutdown을 지원하고, `spring.lifecycle.timeout-per-shutdown-phase`로 종료 단계 제한 시간을 지정할 수 있다. 바깥의 플랫폼·서비스 관리자도 종료 대기 시간을 허용해야 앱 내부 대기 전에 프로세스를 강제 종료하지 않는다.

무중단을 기대하려면 한 인스턴스가 교체될 동안 나머지가 트래픽을 처리할 여유가 있어야 한다. readiness 확인 없이 새 인스턴스로 바로 보내면 초기화 중 오류가 난다. 반대로 readiness가 영원히 실패하면 배포가 멈춘다. liveness가 일시적인 DB 장애까지 앱 재시작으로 해결하려 하면 재시작 폭풍이 날 수 있다. 인스턴스 건강 신호는 배포 제어의 입력이지, 외부 사용자의 핵심 경로까지 모두 검증했다는 증명은 아니다.

### 3.4 무중단·점진 배포 전략

| 전략 | 트래픽 전환 방식 | 강점 | 비용·주의점 |
|---|---|---|---|
| Rolling | 구 버전을 조금 줄이고 새 버전을 조금 늘리는 과정을 반복 | 추가 환경을 통째로 유지하지 않고 교체 가능 | 버전이 잠시 공존하므로 API·DB 호환성이 필요; 여유 용량과 준비 확인이 없으면 오류·용량 부족 |
| Blue-green | green을 별도 준비·검증한 다음 라우터나 서비스 경로를 한 번 전환 | 전환이 빠르고 경로만 되돌려 복구하기 쉬움 | 두 환경의 컴퓨트·연결 비용, 세션·공유 자원, DB 변경은 여전히 고려해야 함 |
| Canary | 소수 인스턴스 또는 사용자 비율만 새 버전에 보내고 지표를 본 뒤 확대 | 전체 영향 전에 운영 데이터로 위험을 관찰 | 라우팅·세그먼트·지표 임계값이 필요; 표본이 작거나 사용자가 편향되면 문제를 못 찾음 |
| Feature flag | 코드는 배포하되 사용자·조직별 기능 사용을 켜고 끔 | 배포와 기능 공개를 분리하고 공개를 빠르게 중단 가능 | 오래된 플래그는 코드 경로와 테스트 조합을 늘림; 데이터 형식·API 변화까지 되돌리는 스위치는 아님 |

Blue-green은 “두 벌 배포 후 경로 전환”, canary는 “작은 범위에서 새 버전을 경험시킨 뒤 확대”가 핵심이다. 카나리의 범위는 서버일 수도 사용자일 수도 있고 둘을 조합할 수도 있다. 기능 플래그는 배포된 코드의 행동을 제어한다. 카나리를 구현할 때 플래그를 쓸 수 있지만 네 전략은 같은 층위의 동의어가 아니다. 네 방식 어느 것도 백그라운드 작업, 세션, 이벤트 포맷, DB 스키마를 자동 호환해 주지 않는다.

Blue-green의 단순화된 전환 순서:

```mermaid
sequenceDiagram
    participant Op as 운영자
    participant G as Green 새 환경
    participant R as 라우터
    participant U as 사용자
    participant B as Blue 현재 환경
    Op->>G: 새 산출물 배포
    Op->>G: 헬스·스모크 검사
    R->>B: 현재 요청 전달
    Op->>R: 활성 경로를 Green으로 전환
    U->>R: 사용자 요청
    R->>G: 새 요청 전달
    Op->>G: 오류율·지연 관찰
    alt 지표 정상
        Op->>R: Green을 활성 상태로 유지
    else 지표 악화
        Op->>R: 경로를 Blue로 복귀
    end
```

Rolling 중에는 구·신 버전이 공존한다. 새 앱의 컬럼 제거·이벤트 포맷 변경은 구 앱을 깨뜨릴 수 있어 호환을 지켜야 한다. 카나리는 앱 오류율과 로그인·결제 성공률, 큐 적체를 보고 사전 정의한 기준으로 확대하거나 중단한다.

### 3.5 실패 판정, 복구, DB 변경

배포 후 지표가 나빠지면 먼저 추가 확대를 멈춘다. 문제가 새 버전 코드에 국한되고 DB·메시지 포맷이 옛 버전과 호환되면 트래픽을 이전 버전으로 보내거나 이전 산출물을 다시 실행한다. 같은 산출물 digest, 직전 버전, 배포 시간, 변경 커밋을 기록해 두면 재현과 복구가 빠르다. 반면 데이터가 잘못 수정되거나 이미 외부 결제가 발생했다면 앱만 되돌려도 원상복구되지 않는다. 데이터 복구·보상 처리는 별도 판단이다.

DB 변경은 expand-contract로 구버전과 신버전의 공존 시간을 안전하게 만든다.

```mermaid
flowchart LR
    A["현재: 앱이 옛 컬럼 사용"] --> B["Expand: 새 컬럼·테이블 추가"]
    B --> C["호환 앱 배포: 옛·새 형식 함께 처리"]
    C --> D["데이터 이관·검증"]
    D --> E["앱 읽기 기준을 새 형식으로 전환"]
    E --> F["Contract: 옛 형식 사용 중단 확인"]
    F --> G["옛 컬럼 제거는 후속 변경"]
    C --> H["문제 시 호환 앱으로 롤백"]
    D --> H
```

예를 들어 `full_name`을 `given_name`·`family_name`으로 나눈다고 하자. 첫 배포에서 새 컬럼을 추가하고 예전 앱도 새 스키마에서 계속 동작하게 한다. 다음 버전은 필요 기간 동안 새 값을 기록하면서 읽기 전환·데이터 backfill을 검증한다.

모든 앱과 배치가 옛 컬럼을 더 이상 쓰지 않는 걸 확인한 뒤, 나중 배포에서 컬럼을 제거한다. 중간 버전에서 오류가 나도 이전 앱이 스키마를 읽을 수 있으므로 복귀 경로가 남는다.

컬럼 삭제와 이름 변경을 앱 릴리스와 한 번에 묶으면 “앱 롤백은 성공했는데 DB 때문에 구버전이 시작되지 않음”이 발생할 수 있다. 대용량 테이블의 backfill은 트랜잭션 잠금·부하·재시작 가능성을 따져 작은 배치로 처리한다. 마이그레이션 스크립트가 한 번 실행되면 되돌리는 SQL이 존재해도 데이터를 원래대로 복원한다는 보장은 없다. 자동화 파이프라인 안에 마이그레이션을 넣는 절차는 D08에서 다룬다.

## 4. 직접 해보기

클라우드 계정 없이 로컬에서 “외부 설정 → 산출물 실행 → 헬스 확인 → 종료”를 관찰한다. 기준은 Java 25, Spring Boot 4.1.x, Gradle 프로젝트다. 아래 실습은 문서 작성 중 미실행이며, 이미 생성된 Boot 앱을 전제로 한다. 이미지·probe 매니페스트는 S19 참조.

1. Actuator 의존성이 없다면 `build.gradle`의 `dependencies`에 추가한다.

```groovy
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-actuator")
}
```

2. `src/main/resources/application.yaml`에 종료 대기 시간을 둔다. 이 예는 Boot의 기본 graceful shutdown 흐름에 종료 단계 제한을 명시한다.

```yaml
spring:
  lifecycle:
    timeout-per-shutdown-phase: 20s
```

3. wrapper가 사용하는 JDK가 기준과 맞는지 확인하고 패키징한다.

```bash
java -version
./gradlew clean bootJar
ls -l build/libs
```

4. 산출물 이름을 `ls` 결과에 맞춰 실행한다. 환경 변수는 환경별 주소·비밀값을 외부에서 주입하는 형태를 보여준다. 실제 DB가 없으면 앱에 연결된 테스트용 설정을 사용한다.

```bash
SPRING_PROFILES_ACTIVE=local SERVER_PORT=8080 java -jar build/libs/실제파일명.jar
```

5. 다른 터미널에서 Actuator health를 확인한다. `spring-boot-starter-actuator`가 있고 해당 endpoint가 HTTP로 노출된 경우 기본 URL은 `/actuator/health`다.

```bash
curl -i http://localhost:8080/actuator/health
```

응답이 `UP`이면 앱이 보고하는 상태가 정상인 것이다. 이것만으로 인증·주문·DB 쓰기 등 모든 기능이 정상임을 증명하지는 않는다. 이어서 실행 중인 터미널에서 `Ctrl-C`로 정상 종료를 요청하고, 진행 중 요청이 어떻게 마무리되는지 관찰한다. IDE의 정지 버튼은 `SIGTERM`을 보내지 않을 수 있으므로 graceful shutdown 관찰에는 터미널에서의 종료 신호를 사용한다.

환경별로는 같은 JAR를 다시 빌드하지 말고 `SPRING_PROFILES_ACTIVE=stg`처럼 프로파일과 외부 설정을 바꿔 실행해 본다. DB 주소나 키를 `application-prod.yaml`에 평문으로 커밋하지 않는다.

배포 방식 실습을 확장하려면 이 앱을 서비스 매니저 단위로 등록하거나 컨테이너 런타임·PaaS에 올릴 수 있지만, 이는 선택 과제이며 실제 계정·리소스 비용이 발생할 수 있다. 서비스 단위·이미지 빌드·클러스터 배포 설정은 각각 운영체제 및 플랫폼 문서를 확인한다.

## 5. 자주 하는 오해와 실수

1. **“배포했으니 고객도 새 기능을 본다” →** 서버 반영과 공개는 다를 수 있다. 기능 플래그·라우팅·권한에 따라 코드는 실행 중이어도 사용자에게 감춰져 있다. 배포 완료와 기능 공개 이벤트를 별도로 기록한다.
2. **“Rolling이면 무중단이다” →** 교체 구간의 여유 용량, 준비 상태, 기존 요청 종료, 앱·DB 호환이 맞지 않으면 오류가 난다. 단일 인스턴스라면 교체 중 받을 서버가 없을 수도 있으니 용량·헬스·의존성 전환을 점검한다.
3. **“stg 통과는 prod 성공 보증” →** 운영 데이터량, 트래픽 패턴, 권한, 외부 서비스, 네트워크가 다를 수 있다. 차이를 목록화하고 prod 초기 지표를 직접 관찰한다.
4. **“버전만 이전으로 바꾸면 rollback 끝” →** 새 앱이 DB를 파괴적으로 바꿨거나 메시지를 새 형식으로 보냈다면 이전 앱이 실패한다. expand-contract와 데이터 복구 시나리오까지 배포 전에 정한다.
5. **“health가 UP이면 사용자 경로도 정상” →** health는 설정된 구성요소를 요약할 뿐 핵심 업무 흐름을 모두 실행하지 않을 수 있다. 스모크와 업무 지표를 함께 본다.
6. **“기능 플래그를 추가하면 위험 없이 배포 가능” →** 오래된 토글은 조건·테스트 경우의 수를 늘리고 플래그가 켜진 경로도 DB 호환 문제를 가질 수 있다. 담당자·만료 시점·제거 티켓을 함께 둔다.
7. **“긴급 핫픽스는 승인·테스트 생략” →** 장애 중 검증되지 않은 수정은 추가 장애를 만든다. 범위를 최소화하되 핵심 회귀 검사, 배포 담당자, 복구 계획, 사후 기록을 유지한다.

운영 배포 전 체크리스트:

- [ ] 산출물 버전·커밋·digest와 대상 환경이 맞는가?
- [ ] 설정·시크릿·DB 연결 대상이 의도한 환경인가?
- [ ] 승인자, 배포 시간, 동결 예외 여부, 담당 당직자가 정해졌는가?
- [ ] 앱·스키마 변경 순서가 구버전과 호환되며 복구 경로가 있는가?
- [ ] 용량, 헬스 확인, graceful 종료 대기 시간이 충분한가?
- [ ] 오류율·지연·핵심 업무 지표의 기준과 관찰 시간이 정해졌는가?

## 6. 시각화 설계 메모

1. **개발에서 prod까지 승격 흐름** | 목적: 개발 과정에서 배포 위치를 보여준다 | 요소: 커밋, artifact, dev·QA·stg·prod, 승인, 복구 | 관계: 동일 artifact가 환경을 승격하고 실패 시 복구로 분기 | 애니메이션: 검증→승격→관찰 | 오해: QA·stg 통과가 운영 보증은 아니다. 1절 Mermaid 대응.
2. **배포 방식의 실행 단위 비교** | 목적: nohup, systemd, Docker, Kubernetes·PaaS의 책임 경계를 그린다 | 요소: 프로세스, 서비스 관리자, 이미지, 오케스트레이터 | 관계: 관리 범위가 프로세스에서 여러 인스턴스로 확대 | 애니메이션: JAR→서비스 관리→이미지→rollout | 오해: 컨테이너가 배포·복구를 자동화하지는 않는다.
3. **전략별 트래픽 전환 타임라인** | 목적: rolling·blue-green·canary·flag의 차이를 보여준다 | 요소: 구/신 버전, 라우터, 사용자, 기능 스위치, 지표 | 관계: 교체·경로 전환·표본 확대·행동 제어 | 애니메이션: 요청 범위와 활성 기능 변화 | 오해: canary와 feature flag는 조합 가능하지만 같은 전략은 아니다. 3절 sequence diagram 대응.
4. **DB expand-contract와 롤백 창** | 목적: 스키마 변경을 릴리스로 나누는 이유를 보여준다 | 요소: 앱 버전, 컬럼, 이관, 삭제 | 관계: 구·신 버전 호환 뒤 구형식 제거 | 애니메이션: 추가→이관→전환→삭제 | 오해: 앱 롤백과 데이터 복구는 별개. 3절 흐름도 대응.

## 7. 자가점검 Q&A (면접 대비)

### Q1. 배포와 릴리스는 어떻게 다른가?
배포는 산출물을 특정 환경에서 실행하는 행위다. 릴리스는 버전을 확정하거나 사용자가 기능을 쓸 수 있게 공개하는 의미로 쓰이며 조직마다 범위가 다르다. 코드는 배포됐어도 기능 플래그가 꺼져 있으면 고객 공개는 하지 않은 상태일 수 있다.

**꼬리질문: 기능 플래그가 장애 복구를 대신하나?** 코드 경로만 끌 수 있다. DB 변경·잘못 처리된 데이터·외부 부작용은 별도 복구가 필요하다.

### Q2. stg에서 성공했는데 prod에 장애가 날 수 있는 이유는?
stg와 prod의 데이터량, 부하, 권한, 네트워크 경로, 외부 연동이 다를 수 있다. stg 테스트가 prod의 모든 조건을 재현한다고 가정하지 않는다. 환경 차이를 확인하고 prod에서는 작은 범위로 배포해 지표를 관찰한다.

**꼬리질문: 그럼 stg를 왜 운영과 비슷하게 유지하나?** 배포 절차와 통합 동작의 차이를 줄여, 운영 전에 발견 가능한 실패를 앞당긴다.

### Q3. rolling과 blue-green의 복구 특성을 비교하라.
Rolling은 인스턴스를 점차 교체해 별도 전체 환경 비용을 줄이는 대신 여러 버전이 공존한다. Blue-green은 별도 환경 검증 후 라우팅을 전환하므로 경로 복귀가 단순하지만 컴퓨트와 공유 상태 비용을 감당해야 한다. 양쪽 모두 DB·메시지 호환 문제는 별도로 해결해야 한다.

**꼬리질문: 둘 중 하나가 언제나 무중단인가?** 아니다. 준비 상태, 용량, 연결 전환, 종료 유예, 호환 설계가 함께 있어야 중단을 줄인다.

### Q4. 카나리 배포에서 무엇을 관찰해야 하나?
새 버전이 받는 작은 트래픽 범위의 오류율·지연뿐 아니라 업무 성공률을 본다. 비교할 기준선, 최소 관찰 시간, 중단 임계치를 사전에 정한다. 지표가 나쁘면 확대를 멈추고 원인을 조사한 뒤 이전 버전으로 돌린다.

**꼬리질문: 1% 카나리면 충분히 안전한가?** 요청량과 사용자 편향에 달렸다. 소수 비율은 영향을 줄이지만 드문 경로·특정 고객 문제를 놓칠 수 있다.

### Q5. 롤백을 어렵게 만드는 대표적인 DB 변경은?
구버전이 기대하는 컬럼을 바로 삭제·이름 변경하거나, 되돌릴 수 없는 데이터 변환을 한 배포에 함께 넣는 경우다. 먼저 스키마를 확장해 양쪽 앱이 동작하게 하고 데이터를 옮긴 뒤, 구버전이 완전히 사라진 후 옛 형식을 정리한다. 데이터 변경의 복구·보상 절차도 계획한다.

**꼬리질문: 마이그레이션에 down 스크립트가 있으면 롤백 가능한가?** 실행 가능하다는 것과 데이터가 손실 없이 원상 복구된다는 건 다르다. 실제 변환과 데이터 보존 조건을 확인해야 한다.

### Q6. Spring Boot graceful shutdown이 배포에 기여하는 점은?
종료 단계에서 새 요청을 거절하고 이미 처리 중인 요청이 끝날 유예 시간을 준다. 덕분에 버전 교체 중 응답이 끊길 위험을 줄인다. 단, 플랫폼 종료 시간이 앱 제한 시간보다 짧거나 요청이 유예 시간을 넘으면 강제 종료될 수 있다.

**꼬리질문: 그러면 무중단이 보장되는가?** 보장되지 않는다. 새 인스턴스 readiness, 남은 용량, 라우터의 연결 해제, 종료 신호 전달도 함께 맞아야 한다.

배포는 실행 가능한 변경을 특정 환경에 적용하는 일이고, 릴리스는 그 기능을 사용자에게 사용할 수 있게 하는 결정이다. 무중단은 배포 도구 이름이 아니라 용량·트래픽 전환·헬스 확인·종료·DB 호환성이 함께 맞아야 얻는 결과다. 장애 때 이전 버전으로 돌아갈 수 있도록 애플리케이션과 데이터 변경을 나누어 계획하고, 지표를 보고 단계적으로 넓혀라.

코드는 저장소에 있다고 서비스에 반영된 것이 아니다. 빌드 단계가 코드와 의존성을 실행 가능한 산출물(JAR 또는 컨테이너 이미지)로 만들고, 테스트·검토를 거친 같은 산출물을 환경별 실행 설정과 함께 배치한다. dev와 QA에서 발견한 문제를 고친 뒤 운영과 비슷한 stg에서 배포 절차와 주요 시나리오를 확인하고 prod로 간다. 조직에 따라 QA가 사람·팀·검증 단계 이름이기도 하므로 정확한 의미는 팀의 운영 문서에서 확인한다.

prod 배포 후에도 완료 버튼을 누르면 끝나는 게 아니다. 새 프로세스가 요청을 받을 준비가 됐는지 확인하고, 오류율·지연·로그·업무 지표를 살핀다. 문제가 없으면 전체 트래픽 또는 기능 공개 범위를 넓힌다. 이상이 보이면 확대를 멈추고 이전 산출물로 복귀하거나 수정본을 배포한다. DB 구조를 바꿨다면 앱만 되돌려도 예전 앱이 새 스키마에서 동작하는지 별도로 판단해야 한다.

이 문서는 전체 개발 과정(D01)에서 검증된 변경을 실행 환경에 옮겨 사용자에게 제공하는 구간을 다룬다. 파이프라인 구성은 D08, 이미지 빌드·Kubernetes 매니페스트·probe 설정은 S19, 인프라 형태는 D07 참조.

022. 용어 사전열기 ↓
용어 한 줄 정의 실무 예시 헷갈리는 것과 차이
배포(Deploy, 디플로이) 산출물을 목표 환경에 놓고 실행 상태로 만드는 작업 “오늘 3시에 prod 배포합니다” 릴리스·출시와 겹쳐 쓰기도 하지만, 기술적으로는 환경 반영 행위
릴리스(Release) 특정 버전을 사용 가능하다고 선언하는 일; 조직에 따라 산출물 확정 또는 사용자 공개를 뜻함 “2.4.0 릴리스 노트를 발행” 배포와 동의어로 쓰이는 팀도 있어 회의에서 범위를 확인
출시(Launch) 고객에게 기능·제품을 공개하는 사업·제품 관점의 시점 “금요일 결제 기능 출시” 기능이 이미 배포되어 있어도 플래그가 꺼져 있으면 출시는 전일 수 있음
산출물(Artifact) 빌드된 버전이 식별되는 배포 단위 app-2.4.0.jar, 이미지 digest 소스 코드와 다름; 같은 산출물을 테스트하고 운영에 올리는 게 추적에 유리
환경(Environment) 앱과 연동 자원, 설정을 합쳐 특정 목적에 쓰는 실행 공간 stg DB에 붙은 앱 인스턴스 브랜치나 AWS 계정 하나와 반드시 일치하는 개념은 아님
local 개발자 컴퓨터에서 빠르게 확인하는 환경 로컬 DB 또는 테스트 컨테이너로 API 확인 공유 dev와 다름; 개인별 상태·주소·비밀값이 다를 수 있음
dev 통합한 변경을 개발 중 확인하는 공유 환경 프론트·백엔드 연동 개인 local이나 운영 전 최종 리허설인 stg와 목적이 다름
QA 기능·회귀·탐색 테스트를 수행하는 검증 단계 또는 담당 조직 주문 취소 시 재고 복구 확인 환경 이름으로도 쓰임; 모든 조직에서 고정된 약어는 아님
stg·stage 운영과 유사한 설정·경로로 릴리스 리허설하는 환경 운영 배포 전 로그인·결제 스모크 테스트 “운영과 같다”는 보장은 아님. 데이터량·외부 연동·권한이 다를 수 있음
prod·production 실제 사용자 트래픽과 업무 데이터를 처리하는 운영 환경 고객 요청을 받는 API stg와 설정을 공유하지 말고 비밀값·자원 경계를 분리
환경별 설정 같은 앱 산출물의 동작을 환경에 따라 바꾸는 값 DB 주소, 포트, 로그 수준 환경별로 따로 빌드한 바이너리와 다름; Boot는 외부 설정을 지원
롤링 업데이트(Rolling) 기존 인스턴스를 조금씩 새 버전으로 교체 새 Pod를 올리고 구 Pod를 줄임 전체를 한 번에 전환하는 blue-green과 차이; 용량 확보가 필요

카나리(Canary) 작은 사용자·서버 비율부터 새 버전 영향을 확인하고 확대 1% 요청으로 오류율 비교 점진 확대 전략; 작은 표본은 문제를 놓칠 수 있음
기능 플래그(Feature flag) 배포된 코드 안의 기능을 설정으로 켜고 끄는 스위치 내부 직원에게만 새 검색 노출 배포·릴리스 분리 도구; 카나리처럼 비율 제어에 쓸 수 있지만 같은 개념은 아님
헬스체크(Health check) 프로세스·앱이 요청 받을 상태인지 확인하는 검사 /actuator/health 확인 프로세스가 살아 있음과 업무 기능이 정상임은 같지 않음
readiness 새 인스턴스가 트래픽을 받아도 되는지 나타내는 준비 상태 초기화 중이면 라우터에서 제외 liveness는 재시작 판단에 쓰는 생존 신호; 구체적 probe 설정은 S19 참조
graceful shutdown 종료 신호를 받은 앱이 새 요청을 받지 않고 진행 중 요청을 마무리하는 종료 프로세스 교체 중 응답 절단을 줄임 무한 대기나 모든 비동기 작업 완료를 보장하지 않음; 제한 시간이 있음
롤백(Rollback) 실패한 변경을 이전 동작 또는 산출물로 되돌리는 복구 직전 안정 이미지로 트래픽 복귀 원상복구가 불가능하면 수정 배포(roll-forward)가 더 안전할 수 있음
롤포워드(Roll-forward) 현재 상태를 유지하면서 수정 버전을 추가 배포해 복구 핫픽스로 오류 경로 수정 롤백과 반대편 선택지; 이미 처리된 데이터까지 저절로 복구하진 않음
핫픽스(Hotfix) 긴급 장애·보안 문제를 우선 해결하는 작은 수정 릴리스 인증 오류 수정본을 긴급 배포 긴급하다고 검증·승인·기록을 생략한다는 뜻은 아님
배포 승인 지정된 책임자가 변경 범위·시각·검증·복구 계획을 확인하는 통제 당직자가 변경 티켓 승인 코드 리뷰나 테스트 성공과 다른 책임·운영 판단
배포 동결(Freeze) 특정 기간 운영 변경을 제한해 위험을 줄이는 조직 정책 대규모 행사 전 변경 동결 기술적으로 배포가 불가능한 상태가 아님; 예외·긴급 절차를 둠
스모크 테스트 핵심 경로가 크게 깨지지 않았는지 빠르게 확인하는 최소 검사 로그인 후 주문 조회 전체 회귀 테스트를 대체하지 않음
expand-contract 스키마 변경을 호환 가능한 확장·전환·정리로 나누는 패턴 새 컬럼으로 이전 후 옛 컬럼 제거 한 번의 파괴적 DDL이나 앱 롤백과 다름
컨테이너 앱 실행환경을 이미지로 묶어 같은 단위로 시작하는 방식 같은 이미지 digest를 stg·prod에 배치 VM 전체를 이미지화하는 것과 다름; 설정·영속 데이터는 보통 외부에 둠
PaaS 플랫폼이 앱 실행·스케일·상태 관리 일부를 제공하는 서비스 모델 Git에 push하거나 이미지 지정해 배포 배포 책임이 사라지는 것이 아니라 운영 경계가 플랫폼과 나뉨

013.1 환경과 설정을 맞춘다↘

환경은 앱 버전, 의존 서비스, 네트워크, 권한, 설정이 묶인 실행 조건이다. local은 개인 확인, dev는 통합, QA는 계획된 검증, stg는 운영 리허설, prod는 실제 서비스가 목적이다. 조직에 따라 QA는 환경 또는 검증 조직을 뜻한다.

가능하면 같은 JAR 또는 이미지 digest를 환경 간 승격한다. 코드까지 다시 빌드하면 검증한 산출물과 prod 실행물의 동일성을 확인하기 어렵다. DB URL·외부 API 주소는 외부 설정으로, 비밀번호·토큰은 시크릿 저장소로 분리한다. Spring Boot는 properties/YAML, 환경 변수, 시스템 속성, 명령행 인자의 우선순위를 정의한다.

023.2 산출물을 실행 환경에 옮기는 방식↘
방식과 절차 장점 한계·실패 신호 맞는 상황
JAR 복사 + nohup 빌드 JAR를 서버에 복사하고 nohup java -jar ... &로 즉시 실행 셸 스크립트마다 PID·로그·재시작·부팅 등록 방식이 달라짐. SSH 종료 후 프로세스가 사라지거나 두 버전이 같은 포트를 잡는 일이 생김 개인 VM 실습, 단일 서버의 임시 확인; 장기 운영 기본값으로 삼지 않음
JAR + systemd 서비스 서비스 단위에 사용자·실행 명령·재시작 정책을 두고 서비스 매니저가 시작·종료·상태를 관리 단일 서버 중심이라 여러 대의 용량·배포 순서를 직접 관리해야 함. 재시작 반복은 근본 장애를 숨길 수 있음 소수 Linux VM, 컨테이너 플랫폼 도입 전 단순 서비스
Docker 컨테이너 앱 실행 단위를 이미지로 고정해 레지스트리에서 가져와 실행 컨테이너 하나만으로 자동 배포·무중단·스케일링이 생기지 않음. 외부 설정, 시크릿, 상태 데이터, 프로세스 종료는 별도 설계 개발·검증·운영의 실행 단위를 통일하고 싶은 경우
Kubernetes·PaaS 원하는 개수·버전을 선언하거나 플랫폼 절차로 배포하고, 플랫폼이 인스턴스 수명·교체를 조정 플랫폼 설정·비용·권한·관찰이 추가됨. 설정 오류, 이미지 pull 실패, 준비 실패가 rollout을 막을 수 있음 여러 서비스·인스턴스를 반복 운영하거나 자동 복구·스케일 요구가 뚜렷한 경우

운영 방식은 순서대로 대체되지 않는다. JAR + systemd, VM의 Docker, PaaS가 함께 쓰이며 선택은 배포 빈도·서비스 수·당직 역량·비용에 달렸다. 이미지와 Kubernetes 설정은 S19 참조.

033.3 prod로 전환하고 상태를 판단한다↘

새 버전을 실행했다고 곧바로 트래픽을 보내지 않는다. 앱이 초기화되고 의존성 연결을 마쳤는지 확인한 뒤 준비된 인스턴스만 요청을 받게 한다. 교체될 구 버전에는 종료 신호를 보내고, 새 연결을 거절하면서 진행 중 요청이 끝날 시간을 준다.

Spring Boot의 내장 웹 서버는 graceful shutdown을 지원하고, spring.lifecycle.timeout-per-shutdown-phase로 종료 단계 제한 시간을 지정할 수 있다. 바깥의 플랫폼·서비스 관리자도 종료 대기 시간을 허용해야 앱 내부 대기 전에 프로세스를 강제 종료하지 않는다.

무중단을 기대하려면 한 인스턴스가 교체될 동안 나머지가 트래픽을 처리할 여유가 있어야 한다. readiness 확인 없이 새 인스턴스로 바로 보내면 초기화 중 오류가 난다. 반대로 readiness가 영원히 실패하면 배포가 멈춘다. liveness가 일시적인 DB 장애까지 앱 재시작으로 해결하려 하면 재시작 폭풍이 날 수 있다. 인스턴스 건강 신호는 배포 제어의 입력이지, 외부 사용자의 핵심 경로까지 모두 검증했다는 증명은 아니다.

043.4 무중단·점진 배포 전략↘
전략 트래픽 전환 방식 강점 비용·주의점
Rolling 구 버전을 조금 줄이고 새 버전을 조금 늘리는 과정을 반복 추가 환경을 통째로 유지하지 않고 교체 가능 버전이 잠시 공존하므로 API·DB 호환성이 필요; 여유 용량과 준비 확인이 없으면 오류·용량 부족
Blue-green green을 별도 준비·검증한 다음 라우터나 서비스 경로를 한 번 전환 전환이 빠르고 경로만 되돌려 복구하기 쉬움 두 환경의 컴퓨트·연결 비용, 세션·공유 자원, DB 변경은 여전히 고려해야 함
Canary 소수 인스턴스 또는 사용자 비율만 새 버전에 보내고 지표를 본 뒤 확대 전체 영향 전에 운영 데이터로 위험을 관찰 라우팅·세그먼트·지표 임계값이 필요; 표본이 작거나 사용자가 편향되면 문제를 못 찾음
Feature flag 코드는 배포하되 사용자·조직별 기능 사용을 켜고 끔 배포와 기능 공개를 분리하고 공개를 빠르게 중단 가능 오래된 플래그는 코드 경로와 테스트 조합을 늘림; 데이터 형식·API 변화까지 되돌리는 스위치는 아님

Blue-green은 “두 벌 배포 후 경로 전환”, canary는 “작은 범위에서 새 버전을 경험시킨 뒤 확대”가 핵심이다. 카나리의 범위는 서버일 수도 사용자일 수도 있고 둘을 조합할 수도 있다. 기능 플래그는 배포된 코드의 행동을 제어한다. 카나리를 구현할 때 플래그를 쓸 수 있지만 네 전략은 같은 층위의 동의어가 아니다. 네 방식 어느 것도 백그라운드 작업, 세션, 이벤트 포맷, DB 스키마를 자동 호환해 주지 않는다.

Blue-green의 단순화된 전환 순서:

sequenceDiagram
    participant Op as 운영자
    participant G as Green 새 환경
    participant R as 라우터
    participant U as 사용자
    participant B as Blue 현재 환경
    Op->>G: 새 산출물 배포
    Op->>G: 헬스·스모크 검사
    R->>B: 현재 요청 전달
    Op->>R: 활성 경로를 Green으로 전환
    U->>R: 사용자 요청
    R->>G: 새 요청 전달
    Op->>G: 오류율·지연 관찰
    alt 지표 정상
        Op->>R: Green을 활성 상태로 유지
    else 지표 악화
        Op->>R: 경로를 Blue로 복귀
    end

Rolling 중에는 구·신 버전이 공존한다. 새 앱의 컬럼 제거·이벤트 포맷 변경은 구 앱을 깨뜨릴 수 있어 호환을 지켜야 한다. 카나리는 앱 오류율과 로그인·결제 성공률, 큐 적체를 보고 사전 정의한 기준으로 확대하거나 중단한다.

053.5 실패 판정, 복구, DB 변경↘

배포 후 지표가 나빠지면 먼저 추가 확대를 멈춘다. 문제가 새 버전 코드에 국한되고 DB·메시지 포맷이 옛 버전과 호환되면 트래픽을 이전 버전으로 보내거나 이전 산출물을 다시 실행한다. 같은 산출물 digest, 직전 버전, 배포 시간, 변경 커밋을 기록해 두면 재현과 복구가 빠르다. 반면 데이터가 잘못 수정되거나 이미 외부 결제가 발생했다면 앱만 되돌려도 원상복구되지 않는다. 데이터 복구·보상 처리는 별도 판단이다.

DB 변경은 expand-contract로 구버전과 신버전의 공존 시간을 안전하게 만든다.

flowchart LR
    A["현재: 앱이 옛 컬럼 사용"] --> B["Expand: 새 컬럼·테이블 추가"]
    B --> C["호환 앱 배포: 옛·새 형식 함께 처리"]
    C --> D["데이터 이관·검증"]
    D --> E["앱 읽기 기준을 새 형식으로 전환"]
    E --> F["Contract: 옛 형식 사용 중단 확인"]
    F --> G["옛 컬럼 제거는 후속 변경"]
    C --> H["문제 시 호환 앱으로 롤백"]
    D --> H

예를 들어 full_name을 given_name·family_name으로 나눈다고 하자. 첫 배포에서 새 컬럼을 추가하고 예전 앱도 새 스키마에서 계속 동작하게 한다. 다음 버전은 필요 기간 동안 새 값을 기록하면서 읽기 전환·데이터 backfill을 검증한다.

모든 앱과 배치가 옛 컬럼을 더 이상 쓰지 않는 걸 확인한 뒤, 나중 배포에서 컬럼을 제거한다. 중간 버전에서 오류가 나도 이전 앱이 스키마를 읽을 수 있으므로 복귀 경로가 남는다.

컬럼 삭제와 이름 변경을 앱 릴리스와 한 번에 묶으면 “앱 롤백은 성공했는데 DB 때문에 구버전이 시작되지 않음”이 발생할 수 있다. 대용량 테이블의 backfill은 트랜잭션 잠금·부하·재시작 가능성을 따져 작은 배치로 처리한다. 마이그레이션 스크립트가 한 번 실행되면 되돌리는 SQL이 존재해도 데이터를 원래대로 복원한다는 보장은 없다. 자동화 파이프라인 안에 마이그레이션을 넣는 절차는 D08에서 다룬다.

044. 직접 해보기5개 코드 · 열기 ↓

클라우드 계정 없이 로컬에서 “외부 설정 → 산출물 실행 → 헬스 확인 → 종료”를 관찰한다. 기준은 Java 25, Spring Boot 4.1.x, Gradle 프로젝트다. 아래 실습은 문서 작성 중 미실행이며, 이미 생성된 Boot 앱을 전제로 한다. 이미지·probe 매니페스트는 S19 참조.

  1. Actuator 의존성이 없다면 build.gradle의 dependencies에 추가한다.
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-actuator")
}
  1. src/main/resources/application.yaml에 종료 대기 시간을 둔다. 이 예는 Boot의 기본 graceful shutdown 흐름에 종료 단계 제한을 명시한다.
spring:
  lifecycle:
    timeout-per-shutdown-phase: 20s
  1. wrapper가 사용하는 JDK가 기준과 맞는지 확인하고 패키징한다.
java -version
./gradlew clean bootJar
ls -l build/libs
  1. 산출물 이름을 ls 결과에 맞춰 실행한다. 환경 변수는 환경별 주소·비밀값을 외부에서 주입하는 형태를 보여준다. 실제 DB가 없으면 앱에 연결된 테스트용 설정을 사용한다.
SPRING_PROFILES_ACTIVE=local SERVER_PORT=8080 java -jar build/libs/실제파일명.jar
  1. 다른 터미널에서 Actuator health를 확인한다. spring-boot-starter-actuator가 있고 해당 endpoint가 HTTP로 노출된 경우 기본 URL은 /actuator/health다.
curl -i http://localhost:8080/actuator/health

응답이 UP이면 앱이 보고하는 상태가 정상인 것이다. 이것만으로 인증·주문·DB 쓰기 등 모든 기능이 정상임을 증명하지는 않는다. 이어서 실행 중인 터미널에서 Ctrl-C로 정상 종료를 요청하고, 진행 중 요청이 어떻게 마무리되는지 관찰한다. IDE의 정지 버튼은 SIGTERM을 보내지 않을 수 있으므로 graceful shutdown 관찰에는 터미널에서의 종료 신호를 사용한다.

환경별로는 같은 JAR를 다시 빌드하지 말고 SPRING_PROFILES_ACTIVE=stg처럼 프로파일과 외부 설정을 바꿔 실행해 본다. DB 주소나 키를 application-prod.yaml에 평문으로 커밋하지 않는다.

배포 방식 실습을 확장하려면 이 앱을 서비스 매니저 단위로 등록하거나 컨테이너 런타임·PaaS에 올릴 수 있지만, 이는 선택 과제이며 실제 계정·리소스 비용이 발생할 수 있다. 서비스 단위·이미지 빌드·클러스터 배포 설정은 각각 운영체제 및 플랫폼 문서를 확인한다.

055. 자주 하는 오해와 실수열기 ↓
  1. “배포했으니 고객도 새 기능을 본다” → 서버 반영과 공개는 다를 수 있다. 기능 플래그·라우팅·권한에 따라 코드는 실행 중이어도 사용자에게 감춰져 있다. 배포 완료와 기능 공개 이벤트를 별도로 기록한다.
  2. “Rolling이면 무중단이다” → 교체 구간의 여유 용량, 준비 상태, 기존 요청 종료, 앱·DB 호환이 맞지 않으면 오류가 난다. 단일 인스턴스라면 교체 중 받을 서버가 없을 수도 있으니 용량·헬스·의존성 전환을 점검한다.
  3. “stg 통과는 prod 성공 보증” → 운영 데이터량, 트래픽 패턴, 권한, 외부 서비스, 네트워크가 다를 수 있다. 차이를 목록화하고 prod 초기 지표를 직접 관찰한다.
  4. “버전만 이전으로 바꾸면 rollback 끝” → 새 앱이 DB를 파괴적으로 바꿨거나 메시지를 새 형식으로 보냈다면 이전 앱이 실패한다. expand-contract와 데이터 복구 시나리오까지 배포 전에 정한다.
  5. “health가 UP이면 사용자 경로도 정상” → health는 설정된 구성요소를 요약할 뿐 핵심 업무 흐름을 모두 실행하지 않을 수 있다. 스모크와 업무 지표를 함께 본다.
  6. “기능 플래그를 추가하면 위험 없이 배포 가능” → 오래된 토글은 조건·테스트 경우의 수를 늘리고 플래그가 켜진 경로도 DB 호환 문제를 가질 수 있다. 담당자·만료 시점·제거 티켓을 함께 둔다.
  7. “긴급 핫픽스는 승인·테스트 생략” → 장애 중 검증되지 않은 수정은 추가 장애를 만든다. 범위를 최소화하되 핵심 회귀 검사, 배포 담당자, 복구 계획, 사후 기록을 유지한다.

운영 배포 전 체크리스트:

  • 산출물 버전·커밋·digest와 대상 환경이 맞는가?
  • 설정·시크릿·DB 연결 대상이 의도한 환경인가?
  • 승인자, 배포 시간, 동결 예외 여부, 담당 당직자가 정해졌는가?
  • 앱·스키마 변경 순서가 구버전과 호환되며 복구 경로가 있는가?
  • 용량, 헬스 확인, graceful 종료 대기 시간이 충분한가?
  • 오류율·지연·핵심 업무 지표의 기준과 관찰 시간이 정해졌는가?
  • 롤백 또는 롤포워드 담당자와 중단 기준이 명확한가?
  • 결과와 사용자 영향, 후속 조치를 변경 기록에 남겼는가?

01Q1. 배포와 릴리스는 어떻게 다른가?↘

배포는 산출물을 특정 환경에서 실행하는 행위다. 릴리스는 버전을 확정하거나 사용자가 기능을 쓸 수 있게 공개하는 의미로 쓰이며 조직마다 범위가 다르다. 코드는 배포됐어도 기능 플래그가 꺼져 있으면 고객 공개는 하지 않은 상태일 수 있다.

꼬리질문: 기능 플래그가 장애 복구를 대신하나? 코드 경로만 끌 수 있다. DB 변경·잘못 처리된 데이터·외부 부작용은 별도 복구가 필요하다.

02Q2. stg에서 성공했는데 prod에 장애가 날 수 있는 이유는?↘

stg와 prod의 데이터량, 부하, 권한, 네트워크 경로, 외부 연동이 다를 수 있다. stg 테스트가 prod의 모든 조건을 재현한다고 가정하지 않는다. 환경 차이를 확인하고 prod에서는 작은 범위로 배포해 지표를 관찰한다.

꼬리질문: 그럼 stg를 왜 운영과 비슷하게 유지하나? 배포 절차와 통합 동작의 차이를 줄여, 운영 전에 발견 가능한 실패를 앞당긴다.

03Q3. rolling과 blue-green의 복구 특성을 비교하라.↘

Rolling은 인스턴스를 점차 교체해 별도 전체 환경 비용을 줄이는 대신 여러 버전이 공존한다. Blue-green은 별도 환경 검증 후 라우팅을 전환하므로 경로 복귀가 단순하지만 컴퓨트와 공유 상태 비용을 감당해야 한다. 양쪽 모두 DB·메시지 호환 문제는 별도로 해결해야 한다.

꼬리질문: 둘 중 하나가 언제나 무중단인가? 아니다. 준비 상태, 용량, 연결 전환, 종료 유예, 호환 설계가 함께 있어야 중단을 줄인다.

04Q4. 카나리 배포에서 무엇을 관찰해야 하나?↘

새 버전이 받는 작은 트래픽 범위의 오류율·지연뿐 아니라 업무 성공률을 본다. 비교할 기준선, 최소 관찰 시간, 중단 임계치를 사전에 정한다. 지표가 나쁘면 확대를 멈추고 원인을 조사한 뒤 이전 버전으로 돌린다.

꼬리질문: 1% 카나리면 충분히 안전한가? 요청량과 사용자 편향에 달렸다. 소수 비율은 영향을 줄이지만 드문 경로·특정 고객 문제를 놓칠 수 있다.

05Q5. 롤백을 어렵게 만드는 대표적인 DB 변경은?↘

구버전이 기대하는 컬럼을 바로 삭제·이름 변경하거나, 되돌릴 수 없는 데이터 변환을 한 배포에 함께 넣는 경우다. 먼저 스키마를 확장해 양쪽 앱이 동작하게 하고 데이터를 옮긴 뒤, 구버전이 완전히 사라진 후 옛 형식을 정리한다. 데이터 변경의 복구·보상 절차도 계획한다.

꼬리질문: 마이그레이션에 down 스크립트가 있으면 롤백 가능한가? 실행 가능하다는 것과 데이터가 손실 없이 원상 복구된다는 건 다르다. 실제 변환과 데이터 보존 조건을 확인해야 한다.

06Q6. Spring Boot graceful shutdown이 배포에 기여하는 점은?↘

종료 단계에서 새 요청을 거절하고 이미 처리 중인 요청이 끝날 유예 시간을 준다. 덕분에 버전 교체 중 응답이 끊길 위험을 줄인다. 단, 플랫폼 종료 시간이 앱 제한 시간보다 짧거나 요청이 유예 시간을 넘으면 강제 종료될 수 있다.

꼬리질문: 그러면 무중단이 보장되는가? 보장되지 않는다. 새 인스턴스 readiness, 남은 용량, 라우터의 연결 해제, 종료 신호 전달도 함께 맞아야 한다.
