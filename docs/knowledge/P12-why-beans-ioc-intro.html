  • 서비스가 의존 객체를 직접 new 하면 구현이 고정되어 교체와 단위 테스트가 번거롭다.
  • 생성자로 필요한 객체를 받으면 호출자가 구현을 선택할 수 있고, Spring은 그 연결 작업을 컨테이너에서 대신한다.
  • Spring이 만든 객체를 빈(bean)이라고 부른다. @Service 같은 표시와 생성자 주입으로 시작하면 된다.
011. 한 줄로 말하면2개 코드 · 열기 ↓

먼저 두 코드를 비교하자.

class OrderService {
    private final OrderRepository repository = new SqlOrderRepository();
}

이 코드는 OrderService가 SqlOrderRepository를 직접 선택한다. 테스트에서 가짜 저장소를 쓰려 해도 전달할 곳이 없고, 저장소 구현을 바꾸려면 이 서비스 파일을 고쳐야 한다. 반면 아래 코드는 필요한 역할만 선언하고 구현 선택을 바깥으로 넘긴다.

class OrderService {
    private final OrderRepository repository;

    OrderService(OrderRepository repository) {
        this.repository = repository;
    }
}

**IoC(Inversion of Control, 제어의 역전)**는 객체가 자기 의존 객체를 만들거나 찾아다니는 대신, 객체 생성과 연결을 바깥의 조립자에게 맡기는 설계 원칙이다. **DI(Dependency Injection, 의존성 주입)**는 그 원칙을 구현하는 방법 중 하나로, 생성자 인자나 설정자 등을 통해 필요한 객체를 전달한다. Spring에서는 컨테이너가 객체를 만들고 연결하며, 컨테이너가 관리하는 객체 하나를 **빈(bean)**이라고 부른다.

용어 이 문서에서의 뜻 OrderService 예
의존 객체 서비스가 일을 맡기는 협력 객체 OrderRepository, PaymentClient
DI 필요한 객체를 외부에서 전달하는 방식 new OrderService(repo, payment)
IoC 컨테이너 객체 생성·연결을 관리하는 Spring의 조립자 Boot 앱의 ApplicationContext
빈 컨테이너가 생성하고 관리하는 객체 @Service가 붙은 OrderService
컴포넌트 스캔 지정한 패키지에서 Spring 등록 표시가 붙은 클래스를 찾는 일 @SpringBootApplication이 기본 패키지를 스캔
022. 당장 알아야 할 것3개 코드 · 열기 ↓

  1. 필수 협력 객체는 생성자로 받는다. 생성자 시점에 필요한 값이 모두 정해져야 객체가 유효해진다. private final로 보관하면 이후 다른 값으로 덮어쓰지 못한다.

    public OrderService(OrderRepository repository, PaymentClient paymentClient) {
    this.repository = repository;
    this.paymentClient = paymentClient;
}

  2. OrderRepository 같은 역할(인터페이스)을 의존하고 구체 구현은 교체한다. 서비스가 SqlOrderRepository에 직접 묶이면 인메모리 구현이나 다른 저장소 구현으로 바꿀 때 서비스 코드도 바뀐다. 인터페이스를 사용하면 운영 조립에서는 실제 구현을, 단위 테스트에서는 가짜 구현을 넣을 수 있다.

  3. Spring에 맡길 클래스에 등록 표시를 붙이고, 그 클래스들을 스캔 범위 안에 둔다. @Service, @Repository, @Component 등은 객체 후보를 표시한다. @SpringBootApplication이 있는 애플리케이션 클래스를 최상위 패키지에 두면 그 하위 패키지의 컴포넌트를 기본 스캔한다.

    com.example.orders
├── OrdersApplication.java  (@SpringBootApplication)
├── OrderService.java       (@Service)
└── adapter
    ├── InMemoryOrderRepository.java (@Repository)
    └── ConsolePaymentClient.java    (@Component)

  4. 필드가 아니라 생성자에 주입한다. 생성자에 필수 의존성이 드러나고, final로 만들 수 있으며, Spring 없이도 테스트에서 가짜를 넣을 수 있다. Spring Boot 문서도 일반적으로 생성자 주입을 권장한다.

  5. 생성자가 하나면 보통 @Autowired를 쓰지 않는다. Spring은 그 유일한 생성자를 선택한다. 생성자가 여럿이면 사용할 생성자를 표시하거나 설계를 다시 단순하게 한다. 상세한 선택·모호성 해결은 → P11.

  6. 기본 구현이 둘 이상이면 타입만으로 고를 수 없다. 예를 들어 PaymentClient 구현을 카드사별로 둘 만들면 어느 것을 전달할지 추가 선택 기준이 필요하다. 등록 상세와 @Qualifier는 → P11.

  7. new로 직접 만든 객체에는 Spring이 개입하지 않는다. 클래스에 @Service가 붙어 있어도 new OrderService(...)로 만든 그 인스턴스를 컨테이너가 만든 건 아니다. 컨테이너의 의존성 주입, 초기화·종료 관리, 프록시 기반 기능은 그 객체에 자동으로 적용되지 않는다.

  8. Spring이 없는 곳에서는 계속 new를 쓴다. 순수 단위 테스트는 new OrderService(fakeRepository, fakePayment)처럼 필요한 가짜를 직접 전달하면 된다. Spring을 띄우지 않아 빠르고 어떤 협력 객체를 쓸지 코드에서 분명하다.

  9. Spring 기본 빈 범위는 컨테이너당 싱글턴이다. 같은 빈을 주입받는 곳은 기본적으로 컨테이너가 관리하는 같은 인스턴스를 공유한다. 싱글턴은 “프로세스 전체에 딱 하나”라는 뜻이 아니라 Spring IoC 컨테이너 하나에 하나라는 뜻이다. 공유되는 서비스 필드에 요청별 가변 상태를 저장하지 않는다. 범위·생명주기는 → S01.

  10. Lombok 표기는 생성자 작성의 축약이다. @RequiredArgsConstructor는 초기화되지 않은 final 필드마다 인자 하나를 받는 생성자를 생성한다. 이 생성자는 직접 적은 생성자와 의미가 같다. 빌드에 Lombok을 추가하고 애노테이션 프로세싱을 켜야 한다.

@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderRepository repository;
    private final PaymentClient paymentClient;
}
방식 뜻·장점 주의점
직접 생성자 + private final 의존성과 대입이 코드에 명시됨 필드 추가 시 생성자도 함께 수정
@RequiredArgsConstructor 위 생성자를 Lombok이 생성 IDE·빌드에 Lombok 설정 필요, 직접 생성자와 중복 작성하지 않음
필드 @Autowired Spring이 필드에 값을 넣음 필수 의존성이 클래스 선언부에 안 보이고 final 불가, 컨테이너 없이 테스트하기 불편해 비권장
setter 주입 생성 후 선택적으로 변경 가능한 값 전달 필수 의존성이 빠진 불완전 객체가 생길 수 있어 필수 협력 객체에는 부적합

01① 서비스 안에서 직접 new 하면 교체 지점이 서비스에 박힌다↘

아래 프로그램은 한 파일로 바로 실행한다. 저장소와 결제 어댑터는 외부 DB·HTTP를 호출하지 않고 예제 출력을 남긴다. 첫 방식은 내부에서 주 구현을 직접 고른다. 테스트용 가짜로 바꿀 생성자가 없으므로 이 코드를 테스트하기 어렵고, 구현 변경도 서비스 수정으로 이어진다.

02② 생성자로 받으면 테스트에서 가짜를 넣을 수 있다↘

ConstructorOrderService는 인터페이스만 알고 인스턴스는 생성자 호출자가 정한다. 이 단계에서는 프로그램의 main이 직접 연결하므로 아직 조립 책임이 호출자에게 남아 있다.

03③ main에 조립을 모아도 객체 수가 늘면 조립 코드가 커진다↘

한곳에서 연결하면 역할은 분리되지만 객체가 50개면 생성·연결 코드를 계속 관리해야 한다. 여러 서비스가 같은 저장소를 쓰려면 같은 인스턴스를 직접 넘겨야 한다. 출력의 true는 그 수동 공유를 확인한다.

// _scratch/P12/IocStages.java — 전체 실행 코드
public class IocStages {
    interface OrderService { void place(String id); }
    interface OrderRepository { void save(String id); }
    interface PaymentClient { void charge(String id); }

    static class DirectNewOrderService implements OrderService {
        private final OrderRepository repository = new PrimaryOrderRepository();
        private final PaymentClient payment = new StripePaymentClient();
        public void place(String id) { repository.save(id); payment.charge(id); }
    }
    static class ConstructorOrderService implements OrderService {
        private final OrderRepository repository;
        private final PaymentClient payment;
        ConstructorOrderService(OrderRepository r, PaymentClient p) { repository = r; payment = p; }
        public void place(String id) { repository.save(id); payment.charge(id); }
    }
    static class PrimaryOrderRepository implements OrderRepository {
        public void save(String id) { System.out.println("[main repository] saved " + id); }
    }
    static class FakeOrderRepository implements OrderRepository {
        public void save(String id) { System.out.println("[test fake repository] captured " + id); }
    }
    static class StripePaymentClient implements PaymentClient {
        public void charge(String id) { System.out.println("[payment adapter] requested charge for " + id); }
    }
    static class FakePaymentClient implements PaymentClient {
        public void charge(String id) { System.out.println("[test fake payment] accepted " + id); }
    }

    public static void main(String[] args) {
        System.out.println("== 1. Service가 직접 new ==");
        new DirectNewOrderService().place("order-101");
        System.out.println("== 2. 생성자로 의존 객체 받기 ==");
        new ConstructorOrderService(new FakeOrderRepository(), new FakePaymentClient()).place("order-202");
        System.out.println("== 3. main에서 조립 ==");
        OrderRepository repo = new PrimaryOrderRepository();
        PaymentClient pay = new StripePaymentClient();
        ConstructorOrderService first = new ConstructorOrderService(repo, pay);
        ConstructorOrderService second = new ConstructorOrderService(repo, pay);
        System.out.println("두 서비스가 저장소 인스턴스를 공유: " + (first.repository == second.repository));
        first.place("order-303");
        second.place("order-304");
    }
}

04④ Spring Boot가 조립을 맡기↘

Spring에게 “이 타입의 객체를 찾아서 여기 넣어 달라”고 맡긴다. 패키지와 파일을 아래처럼 만든다. Boot 4.1.1 Gradle 플러그인과 의존성 BOM을 쓰며, Java 툴체인은 기준 버전 25로 지정했다.

src/main/java/com/example/orders/OrderPorts.java

package com.example.orders;

import org.springframework.stereotype.Component;
import org.springframework.stereotype.Repository;

interface OrderRepository { void save(String orderId); }
interface PaymentClient { void charge(String orderId); }

@Repository
class InMemoryOrderRepository implements OrderRepository {
    @Override public void save(String orderId) {
        System.out.println("[repository] saved " + orderId);
    }
}

@Component
class ConsolePaymentClient implements PaymentClient {
    @Override public void charge(String orderId) {
        System.out.println("[payment] request charge " + orderId);
    }
}

src/main/java/com/example/orders/OrderService.java

package com.example.orders;

import org.springframework.stereotype.Service;

@Service
public class OrderService {
    private final OrderRepository repository;
    private final PaymentClient paymentClient;

    public OrderService(OrderRepository repository, PaymentClient paymentClient) {
        this.repository = repository;
        this.paymentClient = paymentClient;
    }

    public void place(String orderId) {
        repository.save(orderId);
        paymentClient.charge(orderId);
    }
}

src/main/java/com/example/orders/OrdersApplication.java

package com.example.orders;

import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
public class OrdersApplication {
    public static void main(String[] args) {
        SpringApplication.run(OrdersApplication.class, args);
    }

    @Bean
    ApplicationRunner placeExampleOrder(OrderService orderService) {
        return args -> orderService.place("order-501");
    }
}

여기서 @Service, @Repository, @Component가 등록 후보를 표시한다. 애플리케이션 클래스가 하위 패키지까지 스캔해 컨테이너에 보관하고, OrderService의 유일한 생성자 인자 타입과 일치하는 빈을 찾아 전달한다.

따라서 OrderService 코드는 InMemoryOrderRepository나 ConsolePaymentClient를 직접 만들지 않는다. 실무에서는 저장소·결제 API와 연동하는 구현을 선택하되, 서비스 코드는 같은 생성자 구조를 유지한다.

확인 방법: 프로젝트 루트에서 gradle wrapper를 한 번 실행해 wrapper를 만들고 ./gradlew bootRun으로 시작한다. (Spring 예제 미실행.) 정상 구성이라면 시작 로그 뒤에 다음 두 동작이 출력되어야 한다.

[repository] saved order-501
[payment] request charge order-501

Maven 프로젝트라면 pom.xml에서 spring-boot-starter-parent를 4.1.1로 지정하고 java.version을 25로 둔 뒤 org.springframework.boot:spring-boot-starter와 spring-boot-maven-plugin을 사용한다. BOM이 관리하므로 starter에 별도 버전을 적지 않는다. 실행은 mvn spring-boot:run이다.

Spring 밖의 단위 테스트는 직접 생성한다. Spring 예제의 타입과 같은 테스트 대역을 준비했다면 다음처럼 구성한다.

OrderService unit = new OrderService(
        new InMemoryOrderRepository(), new ConsolePaymentClient());
unit.place("order-test");

이 인스턴스는 @Service 애노테이션이 붙은 클래스의 인스턴스일 뿐, 컨테이너의 빈은 아니다. 예를 들어 나중에 OrderService의 메서드에 @Transactional을 붙여도 컨테이너가 생성한 프록시를 거치지 않으므로 이 new 인스턴스 호출에 트랜잭션 처리가 자동으로 붙지 않는다. 위 코드는 주입 없이 생성자가 동작한다는 것만 확인하는 예다.

044. 치트시트열기 ↓
이름 용도 예시 주의
@Component 일반 Spring 관리 객체 등록 @Component class ConsolePaymentClient 스캔 범위 안이어야 함
@Service 서비스 역할 등록 @Service class OrderService 기능상 컴포넌트이며 역할을 드러내는 이름
@Repository 저장소 역할 등록 @Repository class InMemoryOrderRepository DB 연결 자체를 만들어 주지는 않음
생성자 주입 필수 협력 객체 전달 OrderService(repo, payment) 생성자가 하나면 보통 @Autowired 생략
private final 주입받은 참조를 고정 private final PaymentClient client; 생성자에서 빠짐없이 대입
@RequiredArgsConstructor 필수 필드 생성자 생성 private final Repo repo; Lombok 설정과 빌드 지원 필요
@SpringBootApplication Boot 설정 + 자동 구성 + 컴포넌트 스캔 시작점 OrdersApplication 애플리케이션 패키지를 최상위에 둠
직접 new Spring 밖에서 객체 생성 new OrderService(fakeRepo, fakePay) 컨테이너 기능은 자동 적용되지 않음
ApplicationContext 컨테이너 API SpringApplication.run(...) 반환값 입문 단계에서는 직접 조회보다 주입을 사용
055. 자주 나는 에러와 해결열기 ↓

  1. Parameter 0 of constructor in ... required a bean of type '...OrderRepository' that could not be found. → 구현 객체를 등록하지 않았거나 애플리케이션 스캔 범위 밖이다. 구현에 @Repository/@Component를 붙이고 OrdersApplication의 패키지가 구현 패키지의 상위인지 확인한다.

  2. No qualifying bean of type '...PaymentClient' available: expected single matching bean but found 2 → 같은 타입의 구현이 둘 이상인데 하나를 선택할 기준이 없다. 필요에 맞게 구현 하나만 남기거나 명시적으로 선택한다. 상세는 → P11.

  3. The dependencies of some of the beans in the application context form a cycle → A 생성자에 B가 필요하고 B 생성자에 다시 A가 필요한 구조다. 생성자 주입은 이 순환을 숨기지 않고 시작 시 실패시킨다. 책임을 분리하거나 의존 방향을 한쪽으로 정리한다.

  4. 필드 선언에 final을 붙였더니 variable repository might not have been initialized → 생성자에서 해당 필드에 값을 대입하지 않았다. 모든 필수 필드를 생성자 인자로 받고 this.repository = repository;처럼 초기화한다.

  5. Cannot resolve symbol 'RequiredArgsConstructor' 또는 생성자 인자가 없다는 컴파일 오류 → Lombok 의존성·IDE 인식·애노테이션 프로세싱 설정이 빠졌거나 생성된 생성자를 직접 쓴 것으로 오해했다. 빌드에 Lombok 설정을 추가하거나 우선 명시적 생성자를 작성한다.

  6. @Service가 있는데도 직접 만든 객체에서 Spring 기능이 동작하지 않는다. → 애노테이션은 new를 가로채지 않는다. Spring이 관리해야 하는 앱 객체는 컨테이너가 생성하도록 등록·주입하고, 단위 테스트 객체는 Spring 동작 없이 사용한다.

066. 한 단계 더열기 ↓

서비스 안에서 의존 객체를 찾거나 만들던 책임을 생성자 호출자에게 옮기면 구현 교체와 단위 테스트가 쉬워진다. 생성자 주입은 필수 의존성을 완성한 뒤 객체를 사용할 수 있게 한다. Spring Boot에서는 등록 애노테이션과 컴포넌트 스캔으로 객체를 빈으로 만들고, 생성자의 타입 정보를 이용해 연결한다.

기본 범위는 컨테이너별 싱글턴이지만 공유 상태를 무심코 저장하지 않는다. 수동 객체 생성은 Spring 프록시·생명주기 관리와 별개다.

다음 실무 단계인 등록 방식, 다중 구현 선택, 주입 오류는 → P11(빈 등록과 의존성 주입 따라 하기). 컨테이너 내부와 생명주기는 → S01, 생성자 문법은 → P09/P04.

077. 자가점검 Q&A (면접 대비)Q1. OrderService가 저장소를 직접 new 하지 않고 주입받으면 뭐가 달라지나? · Q2. IoC와 DI는 같은 말인가? · Q3. 생성자 주입과 필드 주입 중 생성자를 기본으로 권하는 이유는? · Q4. 생성자가 하나뿐이어도 @Autowired를 붙여야 하나?열기 ↓
01Q1. OrderService가 저장소를 직접 new 하지 않고 주입받으면 뭐가 달라지나?↘

OrderService가 구체 구현 선택과 생성 책임을 내려놓는다. 같은 서비스에 운영용 저장소나 테스트 가짜를 전달할 수 있다. 따라서 교체 시 서비스 코드를 수정할 가능성이 줄고, 테스트가 외부 DB에 덜 묶인다.

  • 꼬리질문: 구현 교체를 위해 인터페이스가 꼭 필요한가?
  • 답: 항상 필요한 것은 아니다. 다만 여러 구현을 바꿔 끼우거나 테스트 대역을 만들 때 인터페이스 경계가 구체 클래스 결합을 줄여 준다.
02Q2. IoC와 DI는 같은 말인가?↘

IoC는 생성·선택·흐름 제어를 객체 바깥에 맡기는 넓은 원칙이다. DI는 필요한 객체를 인자로 전달해 연결하는 구체적 방법이다. Spring은 DI를 통해 IoC 컨테이너가 객체를 조립하게 한다.

  • 꼬리질문: Service Locator도 IoC 구현인가?
  • 답: 객체가 중앙 조회자에게 의존 객체를 직접 요청하는 방식이다. DI는 필요한 의존성이 생성자에 드러나지만, Service Locator는 조회가 내부에 숨을 수 있다.
03Q3. 생성자 주입과 필드 주입 중 생성자를 기본으로 권하는 이유는?↘

생성자 인자만 보면 객체가 꼭 필요로 하는 의존성을 알 수 있다. final로 참조를 고정하고, Spring 없는 단위 테스트에서 가짜를 전달할 수도 있다. 필드 주입은 객체 생성 뒤 값이 들어가므로 컨테이너 없이 테스트하기 어렵다.

  • 꼬리질문: setter 주입은 언제 고려하나?
  • 답: 필수가 아니고 생성 후 바뀔 수 있는 의존성이 명확할 때다. 서비스가 정상 동작하려면 꼭 필요한 객체라면 생성자에서 받는다.
04Q4. 생성자가 하나뿐이어도 @Autowired를 붙여야 하나?↘

아니다. Spring은 후보 생성자가 하나면 그 생성자를 사용한다. 여러 생성자 가운데 선택이 필요한 경우에는 사용할 생성자를 명시한다. Lombok이 만든 단일 생성자도 이 원리는 같다.

  • 꼬리질문: 필드에 @RequiredArgsConstructor만 붙여도 되나?
  • 답: 아니다. 애노테이션은 클래스에 붙여 생성자를 만들고, 주입 대상 필드에는 private final을 쓴다.
05Q5. @Service 클래스라면 new로 만들어도 Spring 빈인가?↘

아니다. @Service는 스캔될 때 등록 후보라는 표시다. 직접 new한 객체는 컨테이너 생성물이 아니므로 의존 객체 자동 주입이나 프록시 기반 부가 기능을 기대하면 안 된다.

  • 꼬리질문: 그럼 단위 테스트에서는 Spring을 꼭 띄워야 하나?
  • 답: 아니다. 생성자에 테스트 대역을 넣으면 순수 Java 객체로 테스트할 수 있다. Spring 구성 자체를 확인하는 테스트는 별도로 컨테이너를 시작한다.
06Q6. 생성자 주입을 사용하면 테스트가 자동으로 외부 DB 없이 동작하나?↘

자동으로 DB가 가짜가 되는 것은 아니다. 테스트가 OrderService 생성자에 가짜 저장소와 결제 대역을 직접 전달해야 한다. 주입 방식이 교체 가능성을 열어 주고 대역 선택은 테스트가 한다.

  • 꼬리질문: 실제 저장소 구현을 단위 테스트에 넣으면?
  • 답: DB 연결 설정과 데이터 상태가 필요해져 테스트가 통합 테스트 성격을 띤다. 서비스 로직만 확인하려면 저장소 대역을 둔다.
07Q7. Spring 빈은 하나만 만들어지나?↘

기본 범위인 싱글턴에서는 빈 정의마다 컨테이너 하나 안에 인스턴스 하나를 둔다. 별도 설정으로 다른 범위를 쓸 수 있으므로 모든 빈이 무조건 하나라고 말하면 틀리다. 싱글턴 서비스 필드는 여러 호출이 공유하므로 요청별 값을 저장하지 않는다.

  • 꼬리질문: 컨테이너가 두 개면 같은 싱글턴 빈을 공유하나?
  • 답: 아니다. 기본 싱글턴 범위는 컨테이너 기준이다. 컨테이너마다 인스턴스가 따로 만들어질 수 있다.
08Q8. 컴포넌트 표시를 붙였는데 빈을 찾지 못한다면 어디부터 볼까?↘

구현 클래스가 실제로 있는지, @Component 계열 등록 표시가 있는지, 애플리케이션 클래스의 스캔 패키지 하위인지 확인한다. 의존하는 타입과 구현 타입도 일치하는지 살핀다. 구현이 둘이면 반대로 선택 모호성 오류가 날 수 있다.

  • 꼬리질문: @SpringBootApplication은 스캔을 어디까지 하나?
  • 답: 선언한 애플리케이션 클래스가 속한 패키지를 기준으로 하위 패키지를 검색한다. 그래서 보통 패키지 구조의 최상위에 애플리케이션 클래스를 둔다.
