#W11. 트랜잭션은 왜 서비스 계층에 거나

3줄 요약 — 서비스 메서드는 보통 한 번의 업무 요청이 보장해야 할 데이터 불변식을 모으는 곳이라, 트랜잭션 경계를 두기 적합하다. Controller에 두면 HTTP 처리 구조에, Repository에만 두면 저장소 호출 단위에 경계가 묶여 여러 저장 작업의 부분 커밋을 막기 어렵다. 기본값은 업무 유스케이스의 외부 진입 메서드에 @Transactional을 두고, 느린 외부 호출과 오래 걸리는 작업은 트랜잭션 밖으로 분리하는 것이다.

#1. 질문

재고 부족으로 주문 요청이 실패했는데 주문 행은 남았다. Repository 두 곳에 각각 @Transactional을 붙였는데 왜 전체가 되돌아가지 않았을까?

또 다른 Controller는 주문·재고·외부 조회를 모두 조율한다. HTTP 한 요청이 업무 한 건이라는 생각은 자연스럽지만, 웹·배치·메시지 소비자 모두에게 같은 DB 일관성을 제공할 경계는 어디일까?

#2. 짧은 답

  • 서비스 계층의 메서드는 보통 주문 생성처럼 하나의 업무 유스케이스를 나타낸다.
  • 이 유스케이스가 변경하는 여러 테이블·Repository 작업을 한 DB 트랜잭션으로 묶으면 부분 커밋을 막는다.
  • Controller는 HTTP 프로토콜 경계, Repository는 데이터 접근 경계다. 둘 다 업무 전체 경계와 일치한다고 보장할 수 없다.
  • 기본 추천: 유스케이스의 public 진입 메서드에 @Transactional을 둔다. 읽기 전용 조회는 필요에 따라 readOnly = true로 구분한다.
  • 트랜잭션 안에서 외부 API를 호출하면 느린 응답 중에도 트랜잭션과 사용 중인 DB 연결을 오래 유지할 수 있다.
  • 외부 호출은 가능한 한 분리하고, DB 변경은 짧게 묶는다. DB 커밋과 외부 시스템 처리를 함께 보장해야 하면 커밋 후 이벤트, Outbox, Saga 등 별도 전달 전략이 필요하다.
  • @Transactional은 프록시를 통한 호출에 적용된다. 같은 객체 안에서 자기 메서드를 부르면 기본 proxy 모드에서는 새 경계가 만들어지지 않는다.

#3. 왜 그런가 — 원리

#업무 경계와 코드 계층

트랜잭션은 SQL 한 문장의 장식이 아니라 여러 데이터 변경을 하나의 업무 결과로 보이게 하는 경계다. Fowler의 Unit of Work는 업무 트랜잭션 동안 변경된 객체를 모아 DB에 반영하고 동시성 문제를 조정한다[3]. 주문은 남았는데 재고는 그대로라면 SQL은 성공했어도 업무 상태는 잘못된 것이다.

서비스/유스케이스는 보통 여러 Repository와 규칙을 조율하므로 어떤 변경이 함께 커밋되어야 하는지 판단할 수 있다. Controller는 HTTP를 해석하고 결과를 응답으로 바꾸며, Repository는 데이터 접근을 캡슐화한다.

주문 기능을 배치나 메시지 소비자에서도 호출한다면 Controller의 경계는 재사용되지 않지만 유스케이스 경계는 공유된다. 여기서 서비스 계층은 Service라는 클래스명이 아니라 한 업무 작업을 소유하는 애플리케이션 서비스, command handler 등을 포함한다.

#Spring에서 실제로 일어나는 일

@Transactional은 트랜잭션 시작 문장이 아니라 런타임 인프라가 읽는 메타데이터다. 설정에서 관리가 활성화되고 TransactionManager가 있어야 한다. 기본 proxy 모드에서는 외부 호출이 프록시를 지나갈 때 조언이 적용된다[1].

sequenceDiagram
    participant C as "Controller 또는 호출자"
    participant P as "Spring 프록시"
    participant M as "TransactionManager"

    participant R as "여러 Repository"

    P->>M: "시작 또는 기존 트랜잭션 참여"
    P->>S: "대상 메서드 실행"
    S->>R: "주문 저장과 재고 차감"
    R-->>S: "결과 또는 예외"
    S-->>P: "반환"
    P->>M: "커밋 또는 롤백"
    P-->>C: "결과 반환"

호출자는 프록시를 부르고, 프록시는 선언된 전파 규칙을 TransactionManager에 전달한다. 기본 PROPAGATION_REQUIRED는 이미 트랜잭션이 있으면 참여하고 없으면 시작한다[1]. 따라서 Repository 호출마다 새 트랜잭션이 항상 생기는 것은 아니다.

JDBC 접근에서 DataSourceUtils/JdbcTemplate은 현재 트랜잭션에 동기화된 연결을 재사용하고 정리한다[4]. 연결 풀의 자원은 한정돼 있으므로, 연결을 획득한 트랜잭션 안에서 느린 작업을 기다리면 다른 요청이 쓸 자원이 줄 수 있다. 단, 지연 연결 획득 등 구현 차이가 있어 진입 즉시 물리 연결을 빌린다고 단정하면 안 된다.

메서드가 정상 반환하면 프록시가 커밋한다. 기본 rollback 대상은 RuntimeException과 Error이며 checked Exception은 아니다[1]. 설정을 바꾸거나 명시적 rollback 규칙을 둘 수 있다.

rollback 예외가 경계까지 전파되면 앞서 저장한 주문도 재고 차감과 함께 롤백된다. 다만 이 원자성은 해당 TransactionManager가 관리하는 자원에 한정된다. 별도 DB, 메시지 브로커, 결제사 HTTP를 애노테이션 하나로 묶을 수는 없다.

#Controller보다 서비스인가

트랜잭션은 대체로 HTTP 요청 전체보다는 좁고 Repository 한 메서드보다는 넓어야 한다. Controller는 웹 프로토콜에 결합돼 배치·메시지 호출이 경계를 공유하지 않는다. Controller의 트랜잭션은 프록시가 감싼 핸들러 메서드 실행에 적용된다.

MVC의 응답 직렬화·뷰 렌더링은 일반적으로 메서드 반환 뒤이므로 트랜잭션에 자동 포함되지 않는다. 메서드 안의 외부 HTTP 대기나 업무 조율은 포함될 수 있다.

OSIV는 영속성 컨텍스트의 요청 수명에 관한 별도 기능이다. 웹 수명주기에 경계가 끌려간다는 문제는 닮았지만 OSIV와 DB 트랜잭션은 같은 것이 아니다.

#Repository만으로는 왜 부족한가

상위 경계 없이 Repository A와 B가 각각 트랜잭션을 끝내면 A 커밋 → B 실패가 된다. 나중의 실패는 끝난 A를 되돌리지 않는다. 주문과 재고가 함께 바뀌어야 한다면 서비스 진입점이 바깥 트랜잭션을 소유하고, 기본 REQUIRED 참여로 두 저장 호출을 묶어야 한다.

#외부 호출은 다른 자원이다

DB 트랜잭션은 결제 HTTP를 취소하지 않는다. 결제 성공 뒤 DB 저장 실패, 또는 DB 커밋 뒤 이메일 실패는 애노테이션 위치만 바꿔 해결되지 않는다. 외부 조회처럼 부작용이 없는 작업은 가능하면 DB 경계 밖에서 처리한다.

이메일·색인처럼 커밋 후 할 일은 @TransactionalEventListener의 기본 AFTER_COMMIT 단계로 처리할 수 있다[2]. 이것은 커밋 후 실행 시점일 뿐 내구성 있는 메시지 저장·재전달은 아니다. 필수 전달이면 Outbox, 여러 서비스에 걸친 상태 전이에는 Saga 등을 검토한다.

#4. 선택지 비교

선택지 동작 장점 단점 언제 쓰나 국내 실무에서 흔한가
Controller 핸들러 메서드를 프록시로 감싼다. 작은 단일 요청에서 위치가 가깝다. 업무 경계가 HTTP에 결합되고 내부 외부호출이 시간을 늘린다. 기본으로 권하지 않으며 작은 API에 임시 적용할 때. 채택률 통계는 확인하지 못했다. 업무 경계가 맞는지 리뷰한다.
Repository별 저장소 메서드마다 시작하거나 기존 트랜잭션에 참여한다. 한 저장 작업 단독 호출도 보호한다. 상위 경계가 없으면 여러 호출 사이 부분 커밋이 남는다. 독립적으로 완결되는 단일 저장 작업. 프레임워크 구성에서 흔히 보지만 국내 빈도는 미확인.
서비스/유스케이스 여러 저장소 호출을 한 업무 진입 메서드로 묶는다. 웹·배치·메시지 진입이 같은 DB 규칙을 공유한다. 외부 호출까지 넣으면 자원 점유가 길고 프록시 규칙을 지켜야 한다. 함께 성공/실패할 DB 변경이 있는 대부분의 동기 유스케이스. Spring 서비스 앱의 기본 권장 패턴. 국내 정량 근거는 없음.
TransactionTemplate 콜백 블록에만 명시적으로 트랜잭션을 연다. 경계를 좁게 표시하고 전후 작업을 분리한다. 코드가 Spring API에 결합되고 호출이 흩어지면 복잡해진다. 선언형보다 구간이 좁거나 분할이 명확할 때. 국내 선택 비중은 미확인. Spring은 명령형 흐름에 권장[6].

기본 판단은 “함께 커밋할 DB 변경을 소유하는 유스케이스인가?”다. 그렇다면 서비스 진입 메서드가 기본이다. 일부 구간만 원자성이 필요하면 유스케이스를 분리하거나 템플릿을 쓴다. 외부 API까지 원자적으로 묶어야 하는 문제는 트랜잭션 위치만 바꿔 해결되지 않는다.

#5. 코드로 보기

아래 예제는 주문 기록과 재고 차감을 네 방식으로 배치한다. Spring Boot 4.1.1 / Spring Framework 7.0.9 API와 Java 25 기준이며 실행 검증은 하지 않았다. 컨텍스트와 orders, inventory 테이블이 필요한 구조 예제이므로 모두 **(미실행)**이다.

공통 타입과 저장소는 다음과 같다. 재고 UPDATE는 수량이 충분할 때만 성공하며, 갱신 행이 없으면 unchecked 예외를 던진다.

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Repository;
import org.springframework.transaction.annotation.Transactional;

record PlaceOrder(long productId, int quantity) {}

@Repository
class OrderRepository {
    private final JdbcTemplate jdbc;

    OrderRepository(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Transactional
    public void insert(PlaceOrder command) {
        jdbc.update("insert into orders(product_id, quantity) values (?, ?)",
                command.productId(), command.quantity());
    }
}

@Repository
class InventoryRepository {
    private final JdbcTemplate jdbc;

    InventoryRepository(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Transactional
    public void decrease(PlaceOrder command) {
        int changed = jdbc.update(
                "update inventory set quantity = quantity - ? " +
                        "where product_id = ? and quantity >= ?",
                command.quantity(), command.productId(), command.quantity());
        if (changed != 1) {
            throw new IllegalStateException("재고가 부족하거나 상품이 없습니다");
        }
    }
}

선택지 A — Controller 경계 (미실행)

import org.springframework.http.HttpStatus;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.ResponseStatus;
import org.springframework.web.bind.annotation.RestController;

@RestController
class OrderController {
    private final OrderRepository orders;
    private final InventoryRepository inventory;

    OrderController(OrderRepository orders, InventoryRepository inventory) {
        this.orders = orders;
        this.inventory = inventory;
    }

    @PostMapping("/orders")
    @ResponseStatus(HttpStatus.CREATED)
    @Transactional
    public void place(@RequestBody PlaceOrder command) {
        orders.insert(command);
        inventory.decrease(command);
    }
}

위 코드는 두 저장 호출을 묶기는 한다. 하지만 HTTP 핸들러가 업무 원자성 경계까지 소유한다. 같은 주문 기능을 배치가 직접 두 Repository에 호출하면 이 경계는 적용되지 않는다. Controller 내부에 외부 가격 조회를 추가하면 응답을 기다리는 동안 트랜잭션 시간이 길어진다.

선택지 B — Repository 각각의 경계 (미실행)

공통 저장소 코드에 붙은 @Transactional만 사용하고 아래처럼 유스케이스에는 경계를 두지 않는 구성이 B다. 저장소별 호출이 독립 커밋될 수 있다.

import org.springframework.transaction.annotation.Transactional;
import org.springframework.stereotype.Service;

@Service
class OrderUseCase {
    private final OrderRepository orders;
    private final InventoryRepository inventory;

    OrderUseCase(OrderRepository orders, InventoryRepository inventory) {
        this.orders = orders;
        this.inventory = inventory;
    }

    public void place(PlaceOrder command) {
        orders.insert(command);       // 첫 Repository 트랜잭션이 끝날 수 있음
        inventory.decrease(command); // 재고 실패는 앞선 주문 커밋을 되돌리지 못함
    }
}

// 위 OrderRepository와 InventoryRepository만 각각 트랜잭션을 갖는다.

이 선택은 공통 Repository 코드에 주석으로 보인 것처럼 두 Repository 클래스의 메서드에 각각 적용하는 구성이다. 첫 저장이 커밋된 뒤 두 번째 메서드가 “재고 부족”을 던지면 주문은 남는다. 이미 끝난 트랜잭션을 이후 예외로 되돌릴 수는 없다. 반면 서비스의 상위 트랜잭션 안에서 호출되면 Repository의 REQUIRED는 그 트랜잭션에 참여한다.

선택지 C — 서비스/유스케이스 경계와 커밋 후 이벤트 (미실행)

import org.springframework.context.ApplicationEventPublisher;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.transaction.event.TransactionalEventListener;
import org.springframework.stereotype.Component;

record OrderPlaced(long productId, int quantity) {}

@Service
class OrderUseCase {
    private final OrderRepository orders;
    private final InventoryRepository inventory;
    private final ApplicationEventPublisher events;

    OrderUseCase(OrderRepository orders,
                 InventoryRepository inventory,
                 ApplicationEventPublisher events) {
        this.orders = orders;
        this.inventory = inventory;
        this.events = events;
    }

    @Transactional
    public void place(PlaceOrder command) {
        orders.insert(command);
        inventory.decrease(command);
        events.publishEvent(new OrderPlaced(command.productId(), command.quantity()));
    }
}

@Component
class OrderNotificationListener {
    @TransactionalEventListener
    public void afterCommit(OrderPlaced event) {
        // 기본 단계 AFTER_COMMIT에서 알림 등 후속 작업 실행
    }
}

서비스 메서드의 저장 둘 중 하나라도 rollback 예외로 실패하면 이벤트의 기본 AFTER_COMMIT 리스너는 성공 커밋을 전제로 실행되지 않는다[2]. 이 애노테이션 자체는 비동기 실행을 뜻하지 않는다.

프로세스 내 리스너 호출이며, 외부 알림이 실패했을 때 주문 커밋을 취소할 수도 없다. 알림을 나중에 재전달해야 할 정도로 신뢰성이 중요하면 Outbox처럼 이벤트 정보를 DB 커밋과 함께 저장한 뒤 별도 발행자가 보내는 구조를 고려한다.

선택지 D — 외부 조회 뒤 DB 구간만 TransactionTemplate (미실행)

import org.springframework.stereotype.Service;
import org.springframework.transaction.PlatformTransactionManager;
import org.springframework.transaction.support.TransactionTemplate;

interface RiskClient {
    boolean isAllowed(PlaceOrder command);
}

@Service
class CheckedOrderUseCase {
    private final RiskClient riskClient;
    private final OrderRepository orders;
    private final InventoryRepository inventory;
    private final TransactionTemplate transactions;

    CheckedOrderUseCase(RiskClient riskClient,
                        OrderRepository orders,
                        InventoryRepository inventory,
                        PlatformTransactionManager transactionManager) {
        this.riskClient = riskClient;
        this.orders = orders;
        this.inventory = inventory;
        this.transactions = new TransactionTemplate(transactionManager);
    }

    public void place(PlaceOrder command) {
        if (!riskClient.isAllowed(command)) {
            throw new IllegalArgumentException("주문할 수 없습니다");
        }
        transactions.executeWithoutResult(status -> {
            orders.insert(command);
            inventory.decrease(command);
        });
    }
}

여기서 외부 위험도 확인은 부작용이 없는 조회라고 가정했다. 승인·결제처럼 되돌릴 수 없는 외부 동작을 먼저 확정하면 DB가 실패했을 때 보상 흐름이 필요하다.

Spring 공식 문서도 명령형 코드에서 TransactionTemplate, 반응형 코드에서 TransactionalOperator를 프로그램 방식의 선택지로 권한다[6]. TransactionTemplate은 경계를 줄여 주지만 네트워크와 DB를 한 분산 트랜잭션으로 바꾸지는 않는다.

#6. 실무에서는 실제로

신규 서비스: 유스케이스를 정하고 주문·재고·포인트처럼 같이 바뀔 DB 상태를 한 public 메서드의 @Transactional 경계로 묶는다. Controller는 HTTP 처리, Repository는 DB 접근을 맡는다.

조회만 하는 메서드는 팀 규칙에 따라 readOnly=true를 쓸 수 있다. 기본은 read-write이며 read-only는 DB가 항상 쓰기를 거부하는 보안 장벽이 아니라 매니저/ORM이 활용하는 힌트다[1].

레거시: 애노테이션을 한꺼번에 옮기지 않는다. 상위 경계 없는 다중 Repository 흐름을 찾아 부분 실패를 재현하고, 그 유스케이스에 경계를 추가한다. REQUIRED로 기존 저장소 트랜잭션이 참여하는지, 외부 호출이 포함되는지 확인한다.

SI·금융: 조직의 공통 계층과 실제 TransactionManager·리소스 구성을 먼저 확인한다. 서로 다른 DB·브로커까지 자동 원자적이라고 가정하지 않는다.

스타트업·성장 단계: 단순한 선언형 경계를 기본으로 두고 활성 연결 수, 대기, 잠금, rollback, 외부 호출 지연을 함께 관측한다. 풀 고갈 시 크기만 키우지 말고 트랜잭션 안에서 기다리는 작업부터 찾는다. 대량 배치는 전체를 오래 잠그기보다 청크 단위 커밋을 검토하되, 재시작 지점과 멱등성을 설계한다.

외부 시스템이 있는 주문: 부작용 없는 조회는 먼저, DB 변경은 짧은 한 트랜잭션에 둔다. 커밋 뒤 알림은 AFTER_COMMIT을 쓸 수 있지만 프로세스 장애 복구가 필요하면 Outbox를 검토한다. 결제·배송처럼 여러 서비스가 상태를 갖는 업무는 멱등성과 보상 흐름을 모델링한다.

#7. 흔한 오해와 실수

  1. “Controller 트랜잭션은 응답 전송 전체를 감싼다” → 대개 메서드 호출만 감싼다. → 대처: HTTP 응답 시점이 아니라 함께 커밋할 업무 상태로 경계를 정한다.
  2. “Repository가 각각 트랜잭션이면 업무 전체도 원자적이다” → 첫 호출 뒤 커밋되면 다음 실패가 되돌리지 못한다. → 대처: 다중 저장 규칙은 상위 유스케이스에 둔다.
  3. “같은 클래스의 @Transactional 메서드를 호출하면 새 설정이 적용된다” → 기본 proxy 모드에서 자기 호출은 프록시를 우회한다. private 메서드도 진입점이 아니다. → 대처: 외부에서 호출되는 경계 메서드나 별도 빈으로 분리한다. AspectJ는 특별한 이유가 있을 때 검토한다[1].
  4. “모든 예외가 자동 롤백된다” → 기본은 RuntimeException·Error; checked 예외는 rollback 대상이 아니다. 예외를 잡고 정상 반환해도 커밋될 수 있다. → 대처: 도메인 예외와 rollbackFor 규칙을 확인한다[1].
  5. “readOnly=true는 DB 쓰기를 차단한다” → 동작은 기술별로 다르고 보안 장벽이 아니다. → 대처: 힌트로 사용하고 권한은 DB 권한과 설계로 통제한다[1].
  6. “오래 걸리는 메서드 전체를 감싸면 안전하다” → 외부 대기 동안 연결·잠금이 오래 유지될 수 있고 API는 롤백되지 않는다. → 대처: 안전하게 분리할 작업과 실패 보상 규칙을 먼저 설계한다[4].
  7. “서비스 트랜잭션은 DB·브로커·HTTP까지 묶는다” → 설정한 매니저가 관리하는 자원에 한정된다. → 대처: 매니저와 실제 자원을 확인하고 분산 작업은 Outbox·Saga 등으로 다룬다.
  8. “커밋 후 이벤트는 유실되지 않는다” → @TransactionalEventListener는 시점만 제공하고 내구성 있는 저장은 하지 않는다[2]. → 대처: best-effort면 모니터링하고 필수 전달이면 재발행 가능한 기록을 둔다.

#8. 자가점검 Q&A (면접 대비)

#Q1. Repository가 아니라 서비스에 두는 이유는?

업무 규칙은 여러 저장 작업에 걸칠 수 있다. 서비스 유스케이스가 함께 커밋할 변경을 조율하므로 전체 실패를 한 경계로 다룬다. Repository별 경계만 있으면 중간 커밋이 남을 수 있다.

꼬리질문: Repository의 애노테이션은 모두 없애나? 답: 아니다. 상위 경계가 있으면 기본 REQUIRED로 참여한다. 단독 호출 때 필요한지도 보고 결정한다.

#Q2. Controller 트랜잭션의 문제는?

경계가 웹 진입에 결합되어 배치·메시지 호출에 재사용되지 않는다. 메서드 안에서 외부 호출을 기다리면 트랜잭션 시간이 길어진다. 응답 직렬화가 자동으로 포함되는 것은 아니다.

꼬리질문: 반환 후 JSON 직렬화 중 DB 접근은 포함되나? 답: 일반적으로 아니다. 프록시가 Controller 메서드 반환 시 완료한다. OSIV 수명은 별도로 본다.

#Q3. 두 Repository가 각각 트랜잭션이어도 부분 실패가 나는 이유는?

상위 트랜잭션이 없으면 첫 호출이 커밋된 뒤 두 번째 호출이 시작할 수 있다. 두 번째 예외가 앞선 완료된 커밋을 되돌리지는 못한다. 주문·재고 같은 데이터 불변식은 더 바깥 경계가 필요하다.

꼬리질문: 서비스에 붙이면 어떻게 달라지나? 답: 프록시가 먼저 시작하고 Repository 호출은 REQUIRED로 참여한다. rollback 예외가 전파되면 같은 결과로 롤백된다.

#Q4. 자기 호출에서 왜 @Transactional이 적용되지 않을 수 있나?

기본 proxy 모드에서 this.otherMethod()는 같은 객체 내부 호출이라 프록시를 거치지 않는다. 내부 메서드의 새 설정이 진입 경계로 적용되지 않는다. private 메서드도 외부 프록시 진입점으로 쓸 수 없다[1].

꼬리질문: 보통 해결은? 답: 유스케이스 경계를 외부 호출 가능한 별도 빈으로 나눈다. AspectJ는 자기 호출 적용이 꼭 필요할 때만 고려한다.

#Q5. 외부 API를 트랜잭션 안에서 부르면 왜 위험한가?

네트워크 대기 동안 트랜잭션 수명과 연결·잠금 사용 시간이 늘 수 있다. DB rollback은 이미 성공한 API를 취소하지 않는다. 두 자원 사이의 순서와 보상 규칙은 별도 문제다.

꼬리질문: 항상 먼저 외부 API를 호출하나? 답: 부작용 없는 조회는 가능하다. 결제·예약 확정은 멱등성·취소·보상이나 Saga 흐름을 함께 설계한다.

#Q6. AFTER_COMMIT 이벤트가 보장하는 범위는?

트랜잭션 커밋 뒤 리스너를 실행하는 시점이다. 기본 단계가 AFTER_COMMIT이며 이벤트의 영속 저장·재전달까지 보장하지는 않는다[2]. 리스너 실패가 이미 끝난 DB 커밋을 되돌리지 못한다.

꼬리질문: 필수 전달이면? 답: Outbox처럼 이벤트 기록을 DB 트랜잭션과 함께 저장해 재발행 가능하게 한다.

#Q7. readOnly=true와 기본 트랜잭션의 차이는?

기본 전파는 REQUIRED, 기본은 read-write다[1]. readOnly=true는 매니저/ORM에 의도를 전달하는 설정으로 모든 DB의 쓰기 차단을 보장하지 않는다. 조회 의도와 실제 권한 통제는 구분한다.

꼬리질문: 모든 조회에 필수인가? 답: 아니다. 팀 규칙과 기술별 효과를 확인한다. 읽기 전용 경계에 쓰기가 섞이지 않는지 확인하는 편이 우선이다.
