#P — 실무 따라 하기 — 당장 개발할 때 필요한 것

문서 한 줄 요약
P01. Spring vs Spring Boot — 무엇이 다르고 프로젝트는 어떻게 시작하나 Spring Framework는 DI·웹·트랜잭션 같은 애플리케이션 기반 기능을 제공한다.
P02. MVC 패턴과 계층형 구조 — Controller·Service·Repository MVC는 HTTP 요청과 응답을 다루는 표현 계층의 방식이다.
P03. 애노테이션이란 — 그리고 실무에서 매일 쓰는 애노테이션 총정리 애노테이션은 컴파일러·빌드 도구·Spring 같은 프레임워크가 읽는 선언형 메타데이터다.
P04. 객체 생성 — 생성자·정적 팩토리·Builder 패턴·생성자 주입 생성자는 객체가 반드시 지켜야 할 상태를 처음부터 완성한다.
P05. jar·war란 무엇인가 — 빌드 결과물과 실행 JAR/WAR는 클래스와 리소스를 ZIP 기반으로 묶는 배포 파일이다.
P06. 첫 CRUD API 만들기 — 처음부터 끝까지 따라 하기 - HTTP로 게시글 CRUD를 DB에 연결한다.
P07. Spring Boot로 개발할 때 꼭 알아야 할 것들 — 개발 습관과 에러 해결 실행 설정은 application.yml에 모으고 환경 차이는 프로파일·환경 변수로 나눈다.
P08. Maven·Gradle 실무 — 빌드 파일 읽고, 의존성 넣고, 에러 고치기 빌드 도구는 의존성을 해결하고 소스 컴파일·테스트·패키징을 한 흐름으로 반복한다.
P09. Java 문법 기초 — 클래스·필드·메서드·생성자를 선언하고 호출하기 클래스는 상태(필드)와 동작(메서드)을 한 이름 아래 선언하고, 객체는 그 클래스로부터 만들어진다.
P10. 자료구조 실무 사용법 — 배열·List·Set·Map·Queue·Deque·PriorityQueue 기본값은 ArrayList·HashSet·HashMap·ArrayDeque다.
P11. 빈 등록과 의존성 주입 따라 하기 — @Component부터 private final + @RequiredArgsConstructor까지 Spring Bean은 컨테이너에 등록되어 생성과 의존성 연결을 맡기는 객체다.
P12. Spring 처음 — 왜 new 대신 빈으로 받나 (IoC·DI 입문) - 서비스가 의존 객체를 직접 new 하면 구현이 고정되어 교체와 단위 테스트가 번거롭다.
P13. Git 실무 — 충돌 해결·되돌리기·브랜치 작업 Git은 작업 디렉터리·스테이징·저장소를 구분한다.
P14. Docker·docker compose로 로컬 개발 환경 만들기 Docker는 프로세스와 실행 파일을 격리하고, 이미지는 그 프로세스를 만들기 위한 불변 템플릿이다.
P15. IntelliJ IDEA 실무 — 프로젝트 열기부터 디버깅·리팩토링까지 Gradle 프로젝트는 build.gradle.kts와 Wrapper를 기준으로 열고, Project SDK와 Gradle JVM을 먼저 맞춘다.
P16. JSON·Jackson 실무 — 요청/응답 직렬화에서 막히는 것들 JSON은 문자열 문법이고 Jackson은 Java 객체와 그 문자열 사이를 변환하는 라이브러리다.
P17. 파일 업로드·다운로드와 외부 스토리지 multipart는 파일 바이트와 폼 필드를 한 HTTP 요청에 담는 형식이고, Spring Boot는 이를 MultipartFile로 바인딩한다.
P18. 동시성 문제 실전 — 재고 차감·좌석 예약을 안전하게 재고·좌석의 정답은 애플리케이션 변수의 값이 아니라 DB가 원자적으로 보장해야 한다.
P19. MySQL 연결과 JPA 설정 — 의존성부터 연결 에러까지 spring-boot-starter-data-jpa와 mysql-connector-j만 올바르게 넣으면 Boot가 DataSource·Hikari·Hibernate를 자동 구성한다.
P20. JPA 엔티티·연관관계 매핑 따라 하기 엔티티는 자바 객체와 테이블 사이의 상태·식별자·관계를 선언한다.
P21. QueryDSL 설정과 동적 쿼리 실무 QueryDSL은 JPQL 문자열 대신 생성된 Q 타입과 fluent API로 조건을 조립하는 도구다.
P22. 데이터소스 여러 개 쓰기와 읽기 복제본 라우팅 여러 DB는 DataSource·EntityManagerFactory·트랜잭션 매니저의 경계를 명시해야 한다.
P23. Redis 연결과 사용 실무 Redis는 키-값 저장소이면서 String·Hash·List·Set·Sorted Set의 원자적 연산을 제공한다.
P24. Kafka 연결과 사용 실무 Kafka는 토픽 파티션에 레코드를 append하고 컨슈머 그룹이 offset을 관리한다.
P25. 외부 API 연동 실무 — RestClient·HTTP Interface 외부 API 호출은 RestClient를 기본값으로 두고, 리액티브 흐름이면 WebClient를 선택한다.
P26. 메일 발송 실무 — JavaMailSender와 로컬 테스트 Spring Boot는 spring-boot-starter-mail과 spring.mail.* 설정으로 JavaMailSender를 자동 구성한다.
P27. 애노테이션은 누가·언제 실행하나 — 시점별 동작 지도 애노테이션은 표시와 메타데이터일 뿐, 그 자체로 코드를 실행하지 않는다.
P28. Spring Boot가 기본으로 만드는 빈들 — 무엇이, 왜, 어떻게 확인·교체하나 - 스타터를 추가하면 클래스패스와 설정 조건에 맞는 자동 구성이 기본 빈을 등록한다.
P29. static 완전 정리 — 클래스 변수·정적 메서드·상수, 그리고 Spring에서의 static static 멤버는 객체마다 복사되지 않고, 해당 클래스를 정의한 클래스 로더의 클래스에 속한다.
P30. 스케줄링 실무 — @Scheduled부터 서버 여러 대·Quartz·CronJob까지 만료·정산·리포트·정리 작업은 요청이 없어도 정해진 시간에 실행되어야 한다.
P31. Stream 실무 패턴 모음 — for문과 나란히, 언제 무엇을 Stream은 데이터 변환·선별·집계를 파이프라인으로 읽기 좋게 쓴다.

#W — 왜·비교 — "왜 이렇게 하나"에 답하는 문서

문서 한 줄 요약
W01. API 하나 만들 때 실제 작업 순서 — DB부터? 컨트롤러부터? API 개발은 DB나 컨트롤러 중 하나를 먼저 만드는 경주가 아니다. 먼저 사용자 요구와 HTTP 계약을 합의하고, 데이터 제약을 설계한 뒤 한 기능을 저장소부터 응답까지 작은 단위로 연결한다.
W02. 왜 Controller·Service·Repository로 나누나 — 안 나누면 생기는 일 Controller·Service·Repository는 관습적으로 파일을 세 개 만드는 규칙이 아니라, 서로 다른 변경 이유와 실행 경계를 분리하는 방법이다.
W03. DB 접근 방식 총비교 — JDBC부터 JPA·MyBatis·QueryDSL·jOOQ까지 JDBC는 SQL 실행의 기반이고, 각 도구는 SQL 작성·결과 매핑·반복 CRUD 가운데 다른 불편을 줄인다.
W04. MyBatis XML 쿼리 실무 — mapper·동적 SQL·#{}와 ${} SQL 값은 #{}로 바인딩하고, 문법 조각은 검증된 값만 ${}로 치환한다.
W05. JPA vs MyBatis — 언제 무엇을, 섞어 쓰는 전략 JPA는 객체와 도메인 상태를 다루고, MyBatis는 SQL과 결과 매핑을 다룬다.
W06. 디버깅은 왜 서버에선 브레이크포인트·로그로, 프론트에선 console.log로 하나 서버 코드는 내 컴퓨터 밖의 JVM에서 여러 사용자의 요청을 함께 처리한다. 브라우저 코드는 개발자 도구가 붙어 있는 내 탭에서 실행되므로 즉시 멈춰 값을 볼 수 있다.
W07. 왜 System.out.println 대신 로거(SLF4J)를 쓰나 서버에서 로그는 문자열을 화면에 찍는 일이 아니라, 운영 중 켜고 끄고 분류해 수집할 사건을 남기는 일이다.
W08. 예외는 어디서 잡나 — 계층별 처리와 전역 핸들러 예외는 실제로 복구하거나 더 적절한 의미로 바꿀 책임이 있는 곳에서 잡는다.
W09. DTO는 왜 쓰나 — 엔티티를 그대로 반환하면 생기는 일 DTO는 DB 객체를 꾸미는 보일러플레이트가 아니라 외부에 공개할 데이터 계약이다.
W10. 검증은 어디서 하나 — 프론트·서버·DB, 왜 둘 다 하나 프론트 검증은 사용자가 빨리 고칠 수 있게 돕고, 서버 검증은 위조된 요청을 포함한 모든 입력을 신뢰 경계에서 걸러낸다.
W11. 트랜잭션은 왜 서비스 계층에 거나 서비스 메서드는 보통 한 번의 업무 요청이 보장해야 할 데이터 불변식을 모으는 곳이라, 트랜잭션 경계를 두기 적합하다.
W12. 인터페이스는 왜 만드나 — DI·테스트, 그리고 과잉 추상화 인터페이스는 Spring DI를 켜기 위한 문법이 아니라, 호출자와 구현 사이에 교체 가능한 계약을 둔다.
W13. 프론트와 백엔드의 경계 — 무엇을 서버에서만 해야 하나 브라우저 코드와 요청은 사용자가 바꿀 수 있으므로, 화면의 결과를 서버가 사실로 믿으면 안 된다.
W14. 동기 vs 비동기, 블로킹 vs 논블로킹 — 백엔드에서 언제 동기/비동기는 결과를 누가 어떻게 이어 받는지, 블로킹/논블로킹은 호출한 스레드가 기다리는지를 가리킨다.
W15. 페이징 — OFFSET vs 커서(키셋), 무엇을 언제 얕고 번호 이동·전체 건수가 필요한 목록은 OFFSET과 Page가 단순하다.
W16. ID 생성 전략 — AUTO_INCREMENT vs UUID vs ULID·Snowflake 기본 단일 DB CRUD라면 내부 PK는 BIGINT AUTO_INCREMENT가 가장 단순하고 인덱스도 작다.
W17. 캐시는 어디에 — 브라우저·CDN·서버 로컬·Redis·DB 캐시는 요청이 자주 읽히고 원본 계산이 비싸며, 정해진 시간 동안 오래된 값을 허용할 때 둔다.
W18. REST vs GraphQL vs gRPC — 선택 기준 세 방식은 서로 다른 계층의 문제를 푼다. REST는 HTTP 자원과 표준 의미를, GraphQL은 클라이언트가 필요한 필드를 조합하는 질의 계약을, gRPC는 스키마로 생성하는 원격 메서드 계약을
W19. Lombok을 쓸까 말까 — 편리함과 함정 Lombok은 컴파일 시 반복 코드를 만들어 주므로 런타임 성능 기능이나 프레임워크 마법은 아니다.
W20. 시간·타임존은 왜 매번 문제인가 시간 문제의 대부분은 “언제 발생했나”와 “어느 지역 시계로 몇 시였나”를 같은 값으로 취급하면서 시작한다.
W21. null 처리 전략 — Optional·JSpecify·DB NULL null은 값이 비어 있다는 정보이면서, 호출자가 예상하지 못한 결함일 수도 있다. 그래서 경계마다 뜻을 정하고 타입과 제약으로 드러낸다.
W22. 로컬에선 되는데 서버에선 왜 안 되나 — 환경 차이 점검 로컬과 운영은 같은 코드라도 설정·런타임·OS·네트워크·데이터·자원 조건이 다르면 다른 프로그램처럼 동작한다.
W23. 캐시와 인메모리 — 무엇이고, 왜 빠르고, 왜 쓰나 캐시는 느린 원본 데이터의 사본을 더 가까운 곳에 두어, 반복 조회의 지연과 원본 부하를 줄이는 기법이다.
W24. DB는 왜 쓰나 — 파일이나 메모리에 저장하면 안 되나 회원·주문을 한 서버 메모리에만 두면 프로세스 재시작 순간 사라지고, 파일에 바로 쓰면 동시 요청과 부분 실패를 직접 해결해야 한다.
W25. 스프링은 왜 멀티스레드인가 — 요청마다 스레드, 공유되는 싱글턴 빈 Spring MVC의 동기 요청은 보통 Tomcat 작업 스레드 하나가 컨트롤러부터 응답까지 맡는다.
W26. 네이밍 컨벤션 — camelCase부터 Controller·Impl까지, 왜 그렇게 짓나 이름은 실행 규칙이라기보다 사람이 의도를 읽고 도구가 대상을 찾게 하는 약속이다.

#V — 테스트 실전

문서 한 줄 요약
V01. 무엇을 어떻게 테스트하나 — 대상 고르기부터 테스트 하나의 구조까지 테스트는 코드가 아니라 변경 위험과 외부 계약을 검증한다.
V02. 계층별 테스트 따라 하기 — Controller·Service·Repository·통합 Controller는 HTTP 계약, Service는 규칙, Repository는 SQL 결과를 검증한다.
V03. mock 실전 — 무엇을 가짜로 바꾸고 무엇은 실제로 두나 - 외부 시스템과 비결정적 입력은 대체하고, 검증하려는 도메인 로직은 실제로 실행한다.

R07. 백업과 복원 — DB와 서버에서 각각 무엇을, 어떻게 지키나 - 백업은 파일을 만드는 일이 아니라 정해진 RPO·RTO 안에 검증된 상태로 돌아오는 절차다.

S16. Actuator·관측성 (메트릭·트레이싱·로깅) - Actuator는 운영 엔드포인트를 제공하지만, 사용 가능(access) 과 외부 노출(exposure) 은 별개다. 필요한 엔드포인트만 인증·네트워크 경계 안에 노출한다.
S17. Spring Boot 애플리케이션 성능 - 성능 튜닝은 숫자를 크게 올리는 일이 아니라 포화 지점을 찾아 제한을 맞추는 일이다.
S18. Spring Boot 테스트 테스트 범위에 맞는 컨텍스트만 띄워라: 기본은 단위 테스트, MVC/JPA는 슬라이스, 설정·빈 조립까지 검증할 때만 @SpringBootTest다.
S19. 패키징·컨테이너화·배포 실행 JAR는 배포 가능한 단위이고, 계층은 변경 범위를 작게 만드는 장치다.
S20. Spring Cloud·MSA 패턴 MSA는 배포·확장의 경계를 분리하는 대신 네트워크 지연, 부분 실패, 데이터 일관성, 운영 복잡성을 서비스 간 경계로 끌어온다.
S21. Spring Boot 3→4·Framework 7 변화와 마이그레이션 Boot 4는 단순한 버전 교체가 아니라 Framework 7·Jakarta EE 11·Jackson 3·재편된 모듈 경계를 함께 올리는 메이저 업그레이드다.
S22. 아키텍처 스타일과 DDD 기초 — 코드를 어떻게 나눌까 레이어드의 핵심 문제는 레이어 수가 아니라 비즈니스 규칙이 Service와 ORM 모델에 흩어지고 의존성 방향이 뒤엉키는 데 있다.
S23. OpenAPI·Swagger UI — API 계약을 문서로 확인하기 구현한 요청·응답 계약을 OpenAPI 문서와 Swagger UI에서 확인하고 유지한다.
