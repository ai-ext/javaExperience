011. 왜 알아야 하나열기 ↓

/actuator/env를 인증 없이 공개하면 설정 정보가 노출된다. 반대로 Prometheus registry만 추가하고 scrape endpoint를 공개하지 않아 지표가 비는 일도 있다. Actuator는 endpoint access와 전송 경로 exposure를 함께 설정해야 안전하게 동작한다.

Kubernetes liveness에 DB 검사를 넣으면 DB 장애가 Pod 재시작 폭주로 번질 수 있고, readiness에 모든 health indicator를 넣으면 전체 인스턴스가 트래픽에서 빠질 수 있다. 생존 여부와 트래픽 수용 가능성을 구분해야 한다.

request ID·사용자 ID·원본 URL을 메트릭 태그로 만들면 값 조합마다 시계열과 Meter가 생긴다. 고유값을 메트릭으로 모으지 말고 route template과 제한된 상태 값으로 집계하고, 개별 요청 정보는 로그·trace에 둔다.

013.1 Endpoint 접근과 노출↘
Endpoint bean → access 허용? → HTTP/JMX exposure에 포함? → 보안 필터·네트워크 허용? → 응답

세 조건은 독립적이다. 기본 HTTP/JMX 노출은 health이며, Prometheus endpoint를 쓰려면 레지스트리 의존성·access·exposure를 모두 갖춰야 한다. exclude는 include보다 우선한다. /env, /configprops, /quartz 값은 기본 마스킹된다. show-values=always는 피하고 필요하면 when-authorized와 운영 역할을 사용한다.

023.2 Health와 Kubernetes↘

Health endpoint는 HealthContributorRegistry의 상태를 합친다. HealthIndicator는 단일 상태를, CompositeHealthContributor는 하위 상태 묶음을 제공한다. management.endpoint.health.group.<name>.include/exclude로 그룹을 만들면 /actuator/health/{name}에서 확인한다.

Boot probe 지원은 liveness/readiness 그룹으로 애플리케이션 availability를 노출한다. 시작 중에는 liveness가 BROKEN, readiness가 REFUSING_TRAFFIC일 수 있고, 초기화가 끝나면 CORRECT와 ACCEPTING_TRAFFIC가 된다. 종료 때 readiness가 먼저 트래픽을 거부한다.

liveness에는 DB·Redis 같은 외부 검사를 넣지 않는다. 외부 장애를 재시작으로 고치려 하면 재시작 폭주와 연쇄 장애가 난다. readiness에는 필수 외부 의존성만 서비스 정책에 맞게 넣는다. 관리 포트만 검사하면 실제 요청 포트 장애를 놓칠 수 있으므로 management.endpoint.health.probes.add-additional-paths=true로 메인 포트의 /livez, /readyz를 고려한다.

033.3 Meter와 cardinality↘

Micrometer는 측정 코드를 MeterRegistry에 등록하고 클래스패스의 registry가 backend로 전달한다. Boot는 지원 registry를 자동 구성하고 composite로 묶을 수 있다. Meter는 이름과 tag 조합으로 식별된다.

  • Counter: 증가하는 이벤트 수. 주문 접수 횟수에 사용.
  • Gauge: 큐 길이 같은 순간값. 대상 객체를 bean 필드로 유지해 GC되지 않게 한다.
  • Timer: 호출 수와 누적 시간·분포를 기록해 latency 측정에 적합.
  • DistributionSummary: 바이트 수 등 시간 외 값의 분포. LongTaskTimer: 아직 끝나지 않은 작업.

uri=/users/123처럼 값이 매번 바뀌면 시계열이 증가한다. /users/{id}로 정규화하고 userId·requestId·timestamp는 tag에서 뺀다. 태그 값 후보가 각각 5·10·100개면 조합이 최대 5,000개다. Micrometer의 HighCardinalityTagsDetector는 같은 이름의 meter 수를 세어 경고하는 진단기이며 동적 metric 이름이나 실제 수집을 차단하지 않는다.

latency percentile을 인스턴스별로 계산해 평균내면 전체 서비스의 percentile이 되지 않는다. 여러 인스턴스 집계가 필요하면 histogram/SLO bucket을 검토한다. Prometheus 연동은 micrometer-registry-prometheus와 /actuator/prometheus exposure가 필요하며, endpoint는 기본 노출에 포함되지 않는다.

043.4 Observation, trace, MDC↘

ObservationRegistry는 Observation을 시작·종료하고 handler가 이를 메트릭이나 span으로 변환한다. Boot는 registry를 자동 구성한다. 저카디널리티 tag는 메트릭과 trace에, 고카디널리티 값은 trace에만 두는 것이 기본 원칙이다.

Observation → low-cardinality tags → Meter
            → context + high-cardinality tags → Span → trace backend
            → 현재 trace 문맥 → 로그의 traceId/spanId

Boot 기본 sampling probability는 0.1이며 management.tracing.sampling.probability로 조정한다. 샘플링되지 않은 요청도 메트릭·로그에는 남을 수 있다. 원격 호출 trace 전파에는 Boot가 구성한 RestClient.Builder, RestTemplateBuilder, WebClient.Builder를 사용한다. 직접 만든 client는 전파가 빠질 수 있다.

Reactor에서 ThreadLocal은 자동 복원되지 않는다. spring.reactor.context-propagation=auto, Boot @Async executor의 spring.task.execution.propagate-context=true를 검토한다. 직접 구성한 executor에는 ContextPropagatingTaskDecorator를 등록한다.

MDC도 실행 흐름이 바뀔 때 자동 전파된다고 가정하지 말고 MDC.putCloseable로 현재 scope를 정리한다.

01예제 1: Actuator, Prometheus, OTLP 노출 경계↘

Gradle 의존성 예시:

// build.gradle.kts (Spring Boot 4.1.1 의존성 관리 사용)
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-actuator")
    implementation("org.springframework.boot:spring-boot-starter-opentelemetry")
    runtimeOnly("io.micrometer:micrometer-registry-prometheus")
}

운영용 application.yaml 예시. 포트 접근은 사내 모니터링 네트워크와 앱 보안 설정으로 제한한다.

management:
  endpoints:
    access:
      default: none
    web:
      exposure:
        include: "health,info,prometheus"
  endpoint:
    health:
      access: read-only
      probes:
        enabled: true
        add-additional-paths: true
      show-details: when-authorized
      roles: OPS
      group:
        liveness:
          include: livenessState
        readiness:
          include: readinessState,db # DB가 이 서비스의 필수 준비 조건일 때만 포함
    info:
      access: read-only
    prometheus:
      access: read-only
  metrics:
    tags:
      application: ${spring.application.name}
      environment: ${APP_ENV:local}
  tracing:
    sampling:
      probability: 0.1
  opentelemetry:
    tracing:
      export:
        otlp:
          endpoint: ${OTEL_EXPORTER_OTLP_ENDPOINT}

logging:
  structured:
    format:
      console: ecs

management.endpoints.access.default=none을 설정했으므로 노출 목록에 넣은 endpoint도 개별 read access를 열어야 한다. 이 예제는 세 endpoint만 read-only로 허용한다. 앱에 DB health contributor가 없다면 readiness include에서 db를 제거한다.

운영 역할 인증과 실제 네트워크 제한은 앱 배포 환경에 맞춰 더한다. (미실행: Spring Boot 애플리케이션 설정 예시)

02예제 2: Counter와 생명주기가 있는 Gauge↘

OrderMetrics.java — 고정된 metric name에 누적 주문 수와 현재 처리 중 주문 수를 기록한다.

import java.util.concurrent.atomic.AtomicInteger;

import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.Gauge;
import io.micrometer.core.instrument.MeterRegistry;
import org.springframework.stereotype.Component;

@Component
public class OrderMetrics {
    private final Counter accepted;
    private final AtomicInteger inFlight = new AtomicInteger();

    public OrderMetrics(MeterRegistry registry) {
        this.accepted = Counter.builder("orders.accepted")
                .description("Accepted order count")
                .register(registry);
        Gauge.builder("orders.inflight", this.inFlight, AtomicInteger::get)
                .description("Orders currently being processed")
                .register(registry);
    }

    public void orderAccepted() {
        accepted.increment();
    }

    public void processingStarted() {
        inFlight.incrementAndGet();
    }

    public void processingFinished() {
        inFlight.decrementAndGet();
    }
}

Gauge의 대상인 inFlight가 bean 필드라 registry가 값을 읽을 때 사라지지 않는다. 실제 서비스에서는 완료·실패 경로 모두 processingFinished()가 호출되도록 try/finally나 작업 수명주기에 연결한다. (미실행: Boot context 필요)

03예제 3: 업무 동작을 Observation으로 감싸기↘

CheckoutObservation.java — region은 제한된 종류라 metric tag에 두고, 요청 식별자는 trace에만 둔다.

import io.micrometer.observation.Observation;
import io.micrometer.observation.ObservationRegistry;
import org.springframework.stereotype.Component;

@Component
public class CheckoutObservation {
    private final ObservationRegistry registry;

    public CheckoutObservation(ObservationRegistry registry) {
        this.registry = registry;
    }

    public void reserve(String region, String requestId, Runnable businessOperation) {
        Observation.createNotStarted("checkout.reserve", registry)
                .lowCardinalityKeyValue("region", region)
                .highCardinalityKeyValue("request.id", requestId)
                .observe(businessOperation);
    }
}

requestId는 예시를 위해 trace에만 붙였다. 개인정보나 비밀값을 trace attribute로 보내도 된다는 뜻은 아니다. 업무 동작의 예외는 Observation 종료 동작에 반영되므로 호출자가 예외 정책을 소유한다. (미실행: Boot context 및 관측 handler 필요)

04예제 4: 구조화 로그와 MDC 정리↘

OrderAuditLogger.java — ECS 형식은 위 YAML에서 켜고, SLF4J fluent key-value와 MDC를 사용한다.

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;
import org.springframework.stereotype.Component;

@Component
public class OrderAuditLogger {
    private static final Logger log = LoggerFactory.getLogger(OrderAuditLogger.class);

    public void accepted(String orderId) {
        try (MDC.MDCCloseable ignored = MDC.putCloseable("event", "order.accepted")) {
            log.atInfo()
                    .addKeyValue("orderId", orderId)
                    .log("Order accepted");
        }
    }
}

Boot의 ECS 출력은 MDC의 key-value를 JSON 필드로 포함한다. orderId처럼 값 종류가 큰 필드는 로그에서는 요청을 좁히는 데 쓸 수 있지만, 메트릭 태그로 재사용하지 않는다. MDC scope는 현재 실행 흐름에서 닫힌다. 별도 스레드나 Reactor로 넘길 때는 문맥 전파 설정을 추가로 확인한다. (미실행: Boot logging 설정 및 SLF4J 2 런타임 필요)

066. 실무 가이드열기 ↓

기본값 추천: health와 필요한 scrape endpoint만 read-only로 노출하고, 관리 포트·네트워크 정책·인증으로 보호한다. 전체 endpoint 공개는 기본값으로 두지 않는다.

  • if 상태 확인이 목적이면 then health를 열고 상세 정보는 when-authorized로 둔다.
  • if Prometheus를 붙이면 then registry 의존성, endpoint access/exposure, scrape path를 모두 맞추고 수집망을 제한한다.
  • if Kubernetes liveness를 구성하면 then 내부 liveness 상태만 확인한다. 외부 의존성은 필요할 때 readiness에서 판단한다.
  • if 지표를 추가하면 then Counter/Timer/Gauge를 용도에 맞게 선택하고 제한된 값만 tag에 넣는다. percentile 집계가 필요하면 histogram/SLO를 검토한다.
  • if 한 요청을 여러 신호에서 연결하려면 then Observation과 trace correlation을 쓰고, request ID는 메트릭 tag에서 제외한다.
  • if async 실행 뒤에 traceId가 없으면 then Reactor·TaskExecutor 문맥 전파와 직접 만든 executor의 decorator를 확인한다.
  • if 로그 수집 형식이 JSON이면 then ECS·GELF·Logstash JSON 중 파이프라인에 맞는 것을 쓴다. logfmt는 Boot 내장 형식이라 단정하지 말고 StructuredLogFormatter 구현을 검토한다.
  • 배포 파이프라인과 이미지 운용은 이 문서 범위가 아니다 → S19 참조.

088. 자가점검 Q&A (면접 대비)Q1. 기본 health 노출은 모든 Actuator endpoint가 공개됐다는 뜻인가? · Q2. DB 장애 때 liveness와 readiness 중 무엇을 실패시킬까? · Q3. request ID를 메트릭 tag로 넣으면 왜 위험한가? · Q4. Timer와 Counter를 어떻게 구분하는가? 인스턴스별 p95 평균은 전체 p95인가?열기 ↓
01Q1. 기본 health 노출은 모든 Actuator endpoint가 공개됐다는 뜻인가?↘

아니다. Boot 4.1은 access와 HTTP/JMX exposure를 따로 설정한다. 기본 exposure는 health뿐이며 다른 endpoint는 별도로 공개해야 한다.

꼬리질문: access 기본값을 none으로 바꾼 경우 health exposure만으로 충분한가? 답: 아니다. health access도 다시 허용해야 한다.

02Q2. DB 장애 때 liveness와 readiness 중 무엇을 실패시킬까?↘

보통 readiness만 고려한다. liveness 실패는 Pod 재시작으로 이어지므로 DB 장애를 앱 재시작으로 해결하려 해서는 안 된다. readiness도 모든 Pod를 동시에 제외할 위험을 검토한다.

꼬리질문: DB가 모든 Pod에서 공유된다면? 답: 전체 트래픽 차단과 fallback·부분 기능 저하 중 서비스 정책에 맞는 선택을 한다.

03Q3. request ID를 메트릭 tag로 넣으면 왜 위험한가?↘

태그 조합마다 Meter와 시계열이 생긴다. 요청마다 ID가 달라지면 메트릭 수가 요청량을 따라 늘어 비용과 메모리가 압박받는다. 개별 요청 값은 로그·trace에 둔다.

꼬리질문: /users/123 경로는? 답: /users/{id}처럼 정규화한다.

04Q4. Timer와 Counter를 어떻게 구분하는가? 인스턴스별 p95 평균은 전체 p95인가?↘

Counter는 누적 이벤트, Timer는 작업 수와 시간 분포를 기록한다. 여러 인스턴스의 p95 평균은 전체 분포의 p95가 아니다. 집계 가능한 histogram/SLO bucket을 검토한다.

꼬리질문: Gauge를 쓸 때 주의점은? 답: Gauge 대상 객체의 생명주기를 유지해야 한다.

05Q5. Observation은 로그·메트릭·trace를 같은 저장소에 넣는 API인가?↘

아니다. 관측 구간을 정의하고 handler가 메트릭과 span 등으로 변환한다. 저카디널리티 tag는 두 신호에 쓸 수 있고 고카디널리티 값은 trace에만 둔다. 로그는 별도 형식과 correlation으로 연결한다.

꼬리질문: 모든 요청 span이 남는가? 답: 아니다. 기본 sampling probability가 0.1이다.

06Q6. 직접 생성한 RestClient에도 trace propagation이 자동 적용되는가?↘

Boot가 구성한 RestClient.Builder, RestTemplateBuilder, WebClient.Builder를 써야 자동 전파를 기대할 수 있다. 직접 만든 client는 전파 설정이 빠질 수 있다.

꼬리질문: async 로그에 traceId가 없다면? 답: client builder, Reactor/TaskExecutor 전파, MDC 형식과 정리 범위를 확인한다.

07Q7. ECS JSON과 logfmt는 어떻게 선택하는가?↘

Boot structured logging은 ECS·GELF·Logstash JSON을 제공하고 MDC 및 SLF4J key-value를 JSON 필드로 출력할 수 있다. logfmt는 내장 형식이라고 가정하지 말고 필요하면 StructuredLogFormatter로 지원한다.

꼬리질문: MDC를 put하고 정리하지 않으면? 답: 재사용 스레드에 값이 남을 수 있으므로 putCloseable 같은 scope를 쓴다.
