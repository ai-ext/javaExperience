캐시는 DB의 대체물이 아니라 만료와 무효화 규칙이 있는 파생 데이터다. 여러 애플리케이션 인스턴스가 같은 캐시를 봐야 하면 Redis, 한 인스턴스의 제한된 메모리 최적화라면 Caffeine을 고른다. DB 스키마 변경은 구버전·신버전 코드가 함께 떠 있는 배포 구간을 견디도록 expand → migrate → contract 순서로 나눈다.

011. 왜 알아야 하나열기 ↓

@Cacheable 이후 사용자가 고친 가격을 다른 서버가 오래 보여 줄 수 있다. Caffeine은 인스턴스끼리 복제되지 않고, Redis도 쓰기 무효화가 빠지면 stale하다. 인기 키가 함께 만료되면 DB에 스탬피드가 난다.

구버전 서버가 old_name을 읽는 동안 컬럼을 삭제하면 요청이 실패한다. 새 컬럼을 채우기 전에 읽으면 값이 비어 보인다. 따라서 스키마 변경은 롤링 배포 중 구·신 코드의 호환성을 고려해야 한다.

Spring Cache는 저장소만 추상화한다. 키·TTL·무효화·다중 인스턴스 정책을 정하지 않은 @Cacheable은 장애 원인을 숨기는 층이 된다.

적합한 용도 단일 인스턴스, 짧은 로컬 계산 결과, 각 인스턴스에서 독립해도 되는 값 다중 인스턴스에서 공유할 조회 결과, 공통 캐시 상태
대표 함정 서버 A에서 삭제해도 서버 B 값은 남음 단일 장애점·네트워크 문제, 직렬화 호환성, 잘못된 무효화

Caffeine은 크기·무게 기반 축출과 접근/기록 기준 만료를 제공한다. Spring Boot가 두 라이브러리를 모두 발견했다고 해서 자동으로 Caffeine을 L1, Redis를 L2로 묶어 주는 것은 아니다. Boot의 기본 provider 탐색 순서에서는 Redis가 Caffeine보다 먼저 선택되므로, 다중 계층이 필요하면 직접 계층 동작과 무효화를 구성해야 한다.

Spring Data Redis의 RedisTemplate은 Redis 명령과 연결·직렬화를 감싸는 중심 API이며 설정 뒤 여러 인스턴스에서 재사용할 수 있다. 기본 Java 직렬화에 결합하지 말고 값 형식과 버전 호환성을 명시한다.

033. 내부 동작·원리메서드 캐시 호출 흐름 · Cache-aside와 write-through · 만료와 스탬피드 · 무중단 스키마 변경 흐름2개 코드 · 열기 ↓
01메서드 캐시 호출 흐름↘
sequenceDiagram
    participant C as 호출자
    participant P as Spring 캐시 프록시
    participant M as CacheManager
    participant K as Cache (Caffeine/Redis)
    participant T as 대상 메서드·DB
    C->>P: 메서드 호출
    P->>P: cache 이름, key/condition 계산
    P->>M: 이름으로 Cache 선택
    M->>K: key 조회
    alt hit
        K-->>P: 저장된 값
        P-->>C: 대상 메서드 생략 후 반환
    else miss
        P->>T: 실제 메서드 실행
        T-->>P: 결과
        P->>K: 결과 저장 (unless 조건 통과 시)
        P-->>C: 결과 반환
    end

프록시 적용 제약 → S02 참조.

Spring Cache 추상화는 메서드 호출을 가로채 결과를 저장·반환하고 실제 저장소는 CacheManager가 결정한다. 기본 키 생성은 인자가 없으면 SimpleKey.EMPTY, 하나면 해당 인자, 여러 개면 인자 묶음이다.

도메인 키로 쓰기 적합하지 않은 인자가 섞이면 key 식으로 필요한 값만 골라야 한다. 같은 캐시를 여러 메서드가 공유해도 키 공간이 자동 분리되지 않으므로, cacheNames와 키 설계가 데이터 경계를 만든다.

@Cacheable은 miss에서 메서드를 실행한 결과를 저장한다. condition은 실행 전 캐시 적용 여부를 정하고, unless는 실행 후 결과를 보고 저장을 취소할 수 있다. @CachePut은 메서드를 매번 실행하면서 결과를 캐시에 넣고, @CacheEvict는 캐시를 지운다. 세 애노테이션을 같은 메서드에 섞으면 실행·저장 순서를 이해하기 어려우므로 쓰기와 읽기 책임을 분리한다.

02Cache-aside와 write-through↘

Cache-aside는 miss 때 DB를 조회해 결과를 채운다. 필요한 값만 적재하지만 첫 miss는 두 저장소를 모두 왕복한다. 모든 쓰기 경로에서 관련 키를 무효화해야 하며, 외부 배치도 포함한다.

Write-through는 DB 쓰기 직후 캐시도 갱신한다. 두 저장소가 원자적으로 커밋된다고 가정하지 말고 커밋 후 무효화, 짧은 TTL, 재시도 가능한 outbox로 불일치를 복구한다.

03만료와 스탬피드↘

TTL은 최신성 보장이 아니라 오래된 값의 잔류 시간을 제한하는 안전망이다. 데이터별 허용 stale 시간에 맞추고 쓰기 시 무효화한다. TTL 분산이나 stale 값을 내보내며 한 작업만 갱신하는 방식은 스탬피드를 줄인다.

@Cacheable(sync = true)는 같은 키의 동시 적재 동기화를 Cache 구현체에 요청한다. 공통 분산 락은 아니다. Redis 기본 writer는 lock-free이고, 잠금 writer도 캐시 단위 잠금과 추가 왕복이 든다. 다중 노드 단일 재계산은 lease와 실패 시 stale 제공까지 따로 설계한다.

04무중단 스키마 변경 흐름↘
1. Expand: 새 컬럼/테이블을 추가하되 구 코드가 계속 동작하게 둔다
2. Deploy: 새 코드가 구·신 구조를 함께 읽고, 필요한 경우 양쪽에 쓴다
3. Migrate: 기존 행을 작은 재시도 가능 배치로 backfill하고 검증한다
4. Switch: 읽기 기준을 새 구조로 바꾸고 구버전 인스턴스가 모두 빠졌는지 확인한다
5. Contract: 별도 배포에서 구 컬럼/코드 제거, 인덱스·제약 조건을 정리한다

배포 중에는 구버전과 신버전 프로세스가 함께 실행될 수 있다. 따라서 새 컬럼 추가는 구 코드가 무시할 수 있도록 하고, 새 코드 전환은 구버전이 종료된 뒤 진행한다. 대량 backfill을 DDL과 같은 긴 트랜잭션으로 묶지 않고 작은 단위로 처리하면 잠금 지속 시간과 롤백 부담을 줄일 수 있다. 컬럼 삭제처럼 되돌리기 어려운 작업은 호환 구간이 끝난 뒤 별도 단계에 둔다.

044. 코드로 확인예제 1: 조회 메서드를 Cache-aside로 만들기 (미실행) · 예제 2: Redis 캐시별 TTL과 키 접두어 (미실행) · 예제 3: Flyway 기반 Expand/contract DDL4개 코드 · 열기 ↓

아래 Spring 예제는 Boot 4.1 / Framework 7 API 기준이다. 이 작업 환경에서 애플리케이션으로 실행하지 않았다. (미실행)

01예제 1: 조회 메서드를 Cache-aside로 만들기 (미실행)↘
import org.springframework.cache.annotation.Cacheable;
import org.springframework.stereotype.Service;

record ProductView(long id, String name, long price) {}

interface ProductReader {
    ProductView findById(long id);
}

@Service
class ProductQueryService {
    private final ProductReader reader;

    ProductQueryService(ProductReader reader) {
        this.reader = reader;
    }

    @Cacheable(cacheNames = "productDetail", key = "#id",
            unless = "#result == null", sync = true)
    ProductView find(long id) {
        return reader.findById(id);
    }
}

id가 키가 되며 null 결과는 캐시하지 않는다. sync=true는 같은 키의 동시 계산을 Cache 구현체에 요청하지만, 이를 여러 JVM에서 통하는 락으로 해석하면 안 된다. ProductReader에는 실제 저장소 빈을 연결해야 한다.

02예제 2: Redis 캐시별 TTL과 키 접두어 (미실행)↘
import java.time.Duration;
import java.util.Map;
import org.springframework.cache.CacheManager;
import org.springframework.cache.annotation.EnableCaching;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.cache.RedisCacheConfiguration;
import org.springframework.data.redis.cache.RedisCacheManager;
import org.springframework.data.redis.connection.RedisConnectionFactory;

@Configuration(proxyBeanMethods = false)
@EnableCaching
class CacheConfiguration {
    @Bean
    CacheManager cacheManager(RedisConnectionFactory connectionFactory) {
        RedisCacheConfiguration common = RedisCacheConfiguration.defaultCacheConfig()
                .entryTtl(Duration.ofMinutes(5))
                .disableCachingNullValues()
                .computePrefixWith(name -> "catalog:v1::" + name + "::");

        return RedisCacheManager.builder(connectionFactory)
                .cacheDefaults(common)
                .transactionAware()
                .withInitialCacheConfigurations(Map.of(
                        "productDetail", common.entryTtl(Duration.ofMinutes(2)),
                        "categoryTree", common.entryTtl(Duration.ofMinutes(10))))
                .build();
    }
}

기본 CacheManager는 트랜잭션 비인식이므로 필요한 TTL과 커밋 정책을 명시한다. 접두어 버전은 값 구조 변경 시 새 키 공간으로 전환하는 데 쓴다.

03예제 3: Flyway 기반 Expand/contract DDL↘

PostgreSQL 예시다. 파일은 Flyway 버전 migration으로 각각 저장하고, 이미 영구 환경에 적용한 파일을 수정하지 않는다.

-- V20261003_01__expand_customer_display_name.sql
ALTER TABLE customer ADD COLUMN display_name varchar(120);

이 배포에서 기존 코드는 display_name을 몰라도 동작해야 한다. 다음 단계에서 새 코드를 배포해 신규 쓰기와 backfill을 수행하고, 데이터 검증 후 읽기를 새 컬럼으로 전환한다.

-- V20261003_02__contract_customer_legacy_name.sql
ALTER TABLE customer DROP COLUMN legacy_name;

두 번째 파일은 새 코드만 남고 legacy_name 참조가 없음을 확인한 뒤, 별도 배포에서 실행한다. 운영 DB에 따라 DDL 잠금·인덱스 작성 방식이 다르므로 큰 테이블은 해당 DB의 online DDL 제약과 실행 시간을 확인한다.

055. 버전별 변화 — 왜 바뀌었나열기 ↓
  • Spring Framework 3.1: 메서드 결과 캐시 추상화를 도입했다. 캐시 제품마다 다른 API를 서비스 코드에 직접 넣으면 교체·테스트 때 코드가 결합되므로 Cache / CacheManager와 선언형 애노테이션으로 경계를 만들었다. 근거: 현재 Cache Abstraction 문서.
  • Spring Framework 4.0: 여러 파라미터의 기본 키 생성이 해시 코드만 보던 방식에서 모든 인자를 묶는 SimpleKey 방식으로 바뀌었다. 서로 다른 인자 조합이 같은 해시를 가져 잘못된 값을 공유할 수 있었기 때문이다. 복합 키가 필요한 메서드는 그래도 key를 명시하는 편이 읽기 쉽다. 근거: 애노테이션 캐시 문서.
  • Spring Framework 4.1: JCache(JSR-107) 애노테이션 지원 및 캐시 설정 확장이 추가됐다. 기존 Spring 애노테이션만으로 표준 캐시 애노테이션 기반 라이브러리와 연동하기 어려웠던 점을 보완했다. Spring Cache와 JCache 애노테이션을 한 코드에 혼용하면 동작 추적이 복잡해지므로 한 체계를 선택한다. 근거: Cache Abstraction 문서.
  • Spring Boot 기준선 (2026-09-28): Boot 4.1.1은 Framework 7.0.9를 관리하며 Caffeine 3.2.4도 관리 좌표에 포함한다. Boot 캐시 자동 구성은 @EnableCaching을 전제로 하고 provider 탐색 순서를 둔다. 의존성만 보고 특정 provider를 추정하지 말고 spring.cache.type 또는 CacheManager Bean으로 확정한다. 근거: 관리 의존성 좌표, Boot Caching.
  • Spring Data Redis 기본 동작: 관리 버전/현재 메이저는 (미확인). Redis cache writer 기본값은 lock-free와 KEYS 전체 삭제이며, 큰 keyspace에서는 지원 드라이버·모드에 따라 SCAN 배치를 검토한다. 근거: Redis Cache 문서.
  • Flyway 버전 migration: 적용된 파일은 체크섬으로 변경을 감지하므로 이미 영구 환경에 적용한 migration은 고치지 않고 새 버전으로 정정한다. 이전 SQL을 바꾸어 이력을 숨기면 환경별 스키마 결과를 재현하기 어렵기 때문이다. Boot 4.1.1 관리 Flyway는 12.4.0이다. Liquibase 현재 문서 페이지에는 5.2.1 Secure가 표시되지만 Boot 4.1.1의 관리 버전은 이 조사에서 확인하지 못했다. 근거: Flyway Versioned Migrations, Liquibase Changelog, Boot 관리 의존성 좌표.
066. 실무 가이드열기 ↓
  • 기본값 추천: 여러 인스턴스가 같은 값을 읽는 서비스라면 Cache-aside + Redis + 데이터별 명시 TTL + 쓰기 커밋 후 키 무효화를 기본으로 시작한다. TTL은 무효화 누락의 상한을 줄이고, Redis는 인스턴스별 로컬 캐시 불일치를 피한다. 단, 강한 일관성이 필요한 값이나 DB 조회가 충분히 싼 경로는 캐시하지 않는다.
  • If 조회 결과를 공유해야 하면 Redis, 한 JVM 안에서만 재사용하면 충분하면 Caffeine을 쓴다. 어느 쪽이든 최대 크기·만료 정책과 실패 시 DB 보호 한계를 정한다.
  • If 결과가 사용자·테넌트·언어·권한에 따라 바뀌면 그 차원을 키에 넣거나 해당 데이터를 캐시하지 않는다. 키 누락은 성능 문제가 아니라 다른 사용자 데이터 노출이다.
  • If 일반 조회 결과를 캐시하면 cache-aside와 커밋 후 무효화로 시작한다. write-through는 모든 쓰기 경로와 실패 복구를 관리할 수 있을 때 선택한다.
  • If 만료 때 DB 부하가 치솟으면 TTL 분산, 동일 키 적재 합치기, stale 응답, 요청 제한을 조합한다. sync=true를 다중 노드 락으로 보지 않는다.
  • If Boot 자동 구성을 쓰면 @EnableCaching과 실제 CacheManager를 확인한다. Redis가 Caffeine보다 먼저 탐색되므로 의존성만으로 선택을 추정하지 않는다.
  • If 운영 스키마를 변경하면 Flyway 또는 Liquibase 중 하나를 정본으로 선택한다. Hibernate ddl-auto=update와 초기 SQL 스크립트가 운영 migration까지 동시에 책임지게 두지 않는다. Boot는 임베디드 DB이고 migration 도구가 없을 때 create-drop, 그 외에는 기본 none으로 초기화한다.
  • If 새 필드·테이블을 도입하면 additive 확장, backfill, 읽기 전환, 제거를 나눈다. 큰 테이블은 DB별 DDL 잠금과 online 변경 지원을 확인한다.
  • If Flyway 버전 migration이 운영에 적용되면 파일을 고치지 말고 새 migration으로 앞으로 수정한다. Liquibase는 changeset/changelog에 조건과 환경 구분을 표현할 수 있다. 팀의 SQL 검토 방식, DB 종류, 변경 분기 요구에 맞춰 택한다.
077. 함정·안티패턴열기 ↓
  1. 다중 서버에서 로컬 캐시만 사용: 서버마다 같은 키의 값이 다름 → Caffeine은 JVM 내부에만 존재 → 공유가 필요하면 Redis를 쓰고, 로컬 계층도 둔다면 무효화 이벤트/짧은 TTL을 설계한다.
  2. 조회 키에서 필터 인자 누락: 특정 조건의 결과가 다른 요청에 반환됨 → 기본 인자 조합이 실제 결과를 구분하지 못함 → key에 결과를 바꾸는 모든 입력을 포함하고 테넌트 경계를 점검한다.
  3. 쓰기 후 캐시를 남겨 둠: 수정 성공 응답 뒤 조회는 이전 값 → DB와 캐시는 별도 상태이고 TTL이 남아 있음 → 커밋 뒤 @CacheEvict/갱신을 하고 TTL을 안전망으로 둔다.
  4. 모든 키에 같은 짧은 TTL 사용: 정각처럼 특정 시점에 DB QPS가 급증 → 동시에 적재한 값이 함께 만료 → TTL을 분산하고 hot key 적재 합치기·stale 제공을 검토한다.
  5. sync=true를 분산 락으로 오해: 여러 노드가 각각 DB를 조회하거나 락 대기 중 지연이 커짐 → 이 속성은 Cache 구현체에 같은 키 적재 동기화를 요청할 뿐이며 Redis 기본 writer도 lock-free → 구현체 지원을 검증하고 필요하면 별도 분산 조정을 설계한다.
  6. Redis 전체 캐시를 무심코 비움: Redis CPU/지연이 치솟음 → 기본 clear 전략의 KEYS가 큰 keyspace를 훑음 → cache prefix/네임스페이스를 설계하고 지원 드라이버·모드에서 SCAN 배치 전략을 검토한다.
  7. 서로 다른 도구가 스키마를 동시에 관리: 로컬과 운영의 테이블 정의가 달라짐 → ddl-auto, schema.sql, Flyway/Liquibase의 실행 책임이 중복 → 운영 정본은 migration 한 가지로 고정한다.
  8. 적용된 migration 수정 또는 컬럼 즉시 삭제: 환경마다 checksum 오류·배포 중 SQL 실패 → 이력 불변성과 구버전 프로세스 호환성을 깨뜨림 → 새 버전으로 수정하고 expand/contract 단계를 분리한다.
088. 자가점검 Q&A (면접 대비)Q1. Spring Cache가 Redis를 제공하는가? · Q2. Cache-aside에서 DB 쓰기와 캐시 무효화 순서는? · Q3. Caffeine과 Redis 선택 기준은 무엇인가? · Q4. 캐시 스탬피드가 왜 발생하며 어떻게 막는가?열기 ↓
01Q1. Spring Cache가 Redis를 제공하는가?↘

아니다. Spring Cache는 애노테이션과 Cache/CacheManager 계약이다. Boot나 애플리케이션이 어떤 provider를 연결할지 결정하며 Redis를 쓰려면 Spring Data Redis 구현과 연결 설정이 필요하다. 같은 @Cacheable 코드라도 실제 저장소와 공유 범위는 달라진다.

꼬리질문: 로컬과 Redis를 동시에 쓰면 자동 L1/L2인가? 답: 아니다. 계층 조회·쓰기·무효화 순서를 직접 구성해야 한다.

02Q2. Cache-aside에서 DB 쓰기와 캐시 무효화 순서는?↘

DB 커밋 뒤 캐시를 제거한다. 커밋 전에 캐시를 다시 채우면 이전 값이 남을 수 있다. 두 시스템의 원자 커밋은 없으므로 이벤트/outbox와 TTL로 복구한다.

꼬리질문: DB 배치 작업도 있다면? 답: 같은 무효화 작업을 배치 경로에도 연결한다.

03Q3. Caffeine과 Redis 선택 기준은 무엇인가?↘

Caffeine은 JVM별 메모리 캐시라 네트워크 왕복이 없고 크기·만료 제한이 쉽지만 서버끼리 값을 공유하지 않는다. Redis는 공유가 필요할 때 적합하지만 네트워크·직렬화·운영 비용이 생긴다. 조회 결과의 공유 필요성과 허용 가능한 불일치를 기준으로 정한다.

꼬리질문: 두 제품 의존성이 모두 있으면? 답: Boot 기본 provider 탐색 순서에서는 Redis가 Caffeine보다 먼저다. 자동 L1/L2 구성은 아니므로 실제 CacheManager를 확인한다.

04Q4. 캐시 스탬피드가 왜 발생하며 어떻게 막는가?↘

같은 키가 없거나 동시에 만료되면 각 요청이 각자 원본 DB를 다시 조회해 부하가 증폭된다. 동일 키 계산 합치기, TTL 분산, 잠금, stale 응답, 보호용 동시성 제한을 조합한다. sync=true는 구현체 동작에 의존하므로 분산 락으로 간주하지 않는다.

꼬리질문: 모든 요청이 오래 기다려도 하나만 계산하면 충분한가? 답: 아니다. 락 대기 시간·실패·만료를 함께 정하고, 필요하면 오래된 값을 반환하거나 빠른 실패로 DB를 보호한다.

05Q5. Flyway와 Liquibase는 어떻게 고르는가?↘

둘 다 버전 이력에 따라 DB 변경을 적용한다. Flyway는 버전이 붙은 SQL로 실행 순서를 명확히 관리하기 좋고, Liquibase는 changelog, DB 중립 change type, contexts/labels 등 선언·조건 기능이 유용하다. 팀의 SQL 숙련도, DB 이식성, 변경 분기 요구로 선택한다.

꼬리질문: 두 도구를 같이 써도 되는가? 답: 특별한 분리 사유가 없다면 한 DB의 스키마 정본은 하나만 둬야 이력과 실행 순서가 명확하다.

06Q6. 무중단 컬럼 변경에서 왜 추가와 삭제를 나누는가?↘

롤링 배포 중 구버전과 신버전 코드가 동시에 요청을 받을 수 있다. 먼저 nullable 컬럼을 추가하면 구버전은 계속 작동하고, 신버전 전환과 데이터 채우기를 끝낸 다음 구 컬럼을 지울 수 있다. 삭제는 이전 코드가 완전히 빠진 뒤 별도 배포로 수행한다.

꼬리질문: backfill을 한 트랜잭션으로 해도 되는가? 답: 대규모 테이블이면 잠금과 롤백이 커지므로 진행 기록과 재시도가 가능한 작은 배치로 나눈다.
