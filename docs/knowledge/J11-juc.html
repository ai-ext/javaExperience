java.util.concurrent는 스레드 수명과 작업 큐, 공유 상태의 원자성, 대기·신호를 목적에 맞게 나눠 제공한다. 풀의 크기만 정하고 큐와 거절을 방치하면 과부하가 큐 지연·메모리 고갈·무한 대기로 바뀐다. Java 25에서는 CompletableFuture의 기본 비동기 실행 규칙과 ForkJoinPool의 스케줄링 기능도 달라졌다.

011. 왜 알아야 하나열기 ↓

newFixedThreadPool()에 작업을 계속 넣으면 고정 스레드 수와 달리 기본 무한 큐는 계속 자란다. 처리량을 넘는 유입은 큐 지연과 메모리 고갈로 나타난다. 포화 때 DiscardPolicy가 submit() 작업을 버리면 호출자가 가진 Future.get()은 끝나지 않을 수도 있다.

CompletableFuture.supplyAsync()가 블로킹 HTTP 호출을 하면 비동기 체인만으로 격리되지 않는다. 특히 Java 25는 실행기 미지정 async 단계의 기본 동작도 바뀌었다. 이 문서는 풀·완료 단계·잠금·원자 변수·동시 컬렉션·동기화 도구를 다룬다. Virtual Threads·Structured Concurrency는 J12, Spring @Async는 S15 참조.

01ThreadPoolExecutor: 큐가 스레드 증가를 결정한다↘

execute는 제출 때마다 최대 크기까지 스레드를 늘리지 않는다. 작업자 수가 코어보다 작으면 새 작업자를 만들고, 그렇지 않으면 큐 삽입을 시도한다. 큐가 거부한 뒤에야 최대 크기까지 늘리고, 그마저 불가능할 때 거절 정책을 적용한다.

worker < core?  ─예→ 새 worker가 실행
       아니오 ↓
  queue.offer 성공? ─예→ 큐에서 대기
       아니오 ↓
worker < max? ─예→ worker 추가 / 아니오→ reject

무한 LinkedBlockingQueue는 코어 스레드가 바쁜 동안 계속 쌓이므로 maximumPoolSize가 사실상 작동하지 않고, 장기 과부하가 메모리 고갈과 긴 대기로 바뀐다. ArrayBlockingQueue는 백로그 크기를 제한하고, SynchronousQueue는 저장하지 않고 작업자에게 넘긴다. AbortPolicy는 예외로 실패를 알리고, CallerRunsPolicy는 풀 종료 전 제출 스레드가 작업해 입력을 늦춘다.

후자는 요청 스레드 지연이나 잠금 내 실행을 만들 수 있다. DiscardPolicy/DiscardOldestPolicy는 버려진 작업의 Future를 영원히 미완료로 둘 수 있어 완료를 기다리는 업무에는 피한다.

shutdown()은 새 작업을 거부하고 제출된 작업을 끝낸 뒤 종료한다. shutdownNow()는 대기 작업을 반환하고 실행 중 작업에는 interrupt를 요청할 뿐, 강제 종료하지 않는다. 종료 대기와 interrupt 협력을 작업 코드까지 설계한다.

02Future와 CompletableFuture: 실행 위치와 실패 흐름↘

Future.get()은 블로킹하고, 작업 실패를 ExecutionException으로 전달한다. cancel(true)도 interrupt 요청이지 코드 강제 종료가 아니다. CompletableFuture의 비-async 단계는 선행 완료 스레드 또는 완료 메서드의 호출자에서 실행될 수 있다. *Async에 실행기를 주지 않으면 Java 25에서는 common pool을 사용한다.

supplyAsync → thenApply(값 변환) → thenCompose(비동기 결과 평탄화)
      └─ 실패 → exceptionally(복구) / handle(변환) / whenComplete(관찰)

thenApply 함수가 다른 Future를 반환하면 중첩되므로 비동기 다음 단계에는 thenCompose를 쓴다. exceptionally는 실패를 값으로 복구하고, handle은 성공·실패 양쪽을 새 값으로 바꾸며, whenComplete는 결과를 관찰한다.

join()은 unchecked CompletionException, get()은 ExecutionException과 InterruptedException을 노출한다. allOf()는 완료 장벽이며 결과 컬렉션은 반환하지 않는다.

03잠금, CAS, 고경합 카운터↘

synchronized는 모니터 진입·탈출로 잠금을 자동 반납한다. ReentrantLock은 tryLock, 시간 제한·인터럽트 대기, 여러 Condition이 필요할 때 쓰되 unlock()을 finally에서 보장한다. 공정 모드는 대기 순서를 고려하지만 처리량을 낮출 수 있고, 무인자 tryLock()은 공정 설정에서도 대기자를 앞지를 수 있다.

ReadWriteLock은 읽기 공유·쓰기 배타 방식이다. ReentrantReadWriteLock은 쓰기 잠금에서 읽기로 내려갈 수 있지만 읽기에서 쓰기로 승격할 수 없다. StampedLock은 낙관 stamp로 읽은 값을 먼저 복사한 뒤 validate()하고, 실패하면 읽기 잠금으로 재조회한다. 재진입 불가이므로 보호된 코드에서 같은 잠금을 다시 요구하면 멈출 수 있다.

CAS는 “현재 값이 예상값과 같을 때 교체”를 원자적으로 한다. 재시도 경합과 ABA(A→B→A로 돌아와 비교가 통과하는 현상)를 고려한다. 여러 원자 변수로 나눈 상태 전체가 원자적인 것은 아니다. LongAdder는 고경합 업데이트를 여러 셀로 분산하지만 sum()은 단일 시점의 원자 스냅샷이 아니다. 통계에는 적합하고 잔액 검사·고유 번호 같은 제어에는 부적합하다.

04ConcurrentHashMap, 큐와 조정 도구↘

Java 8 이후 ConcurrentHashMap은 segment 대신 power-of-two bin 테이블을 사용한다. 빈 bin 삽입에는 CAS를 쓰고 충돌 bin은 선두 노드 중심으로 갱신한다. 조회는 테이블 전체 잠금을 요구하지 않는다.

긴 충돌 bin은 트리화하고, resize 중 MOVED forwarding node를 두어 작업자들이 bin 이동에 참여할 수 있다. 따라서 동시 갱신 중 size()·순회는 전체 원자 스냅샷이 아니다.

computeIfAbsent/merge는 키 단위 복합 갱신을 원자화하지만 매핑 함수에 느린 I/O나 같은 맵의 재귀 갱신을 넣지 않는다. null 키·값은 허용되지 않는다.

BlockingQueue.put/take는 가득 참·비어 있음에서 기다리고, offer/poll은 즉시 또는 제한 시간 내 결과를 준다. 큐 삽입 전 생산자의 동작은 다른 스레드의 해당 원소 접근 이후와 happens-before 관계를 가진다.

도구 맞는 용도 조심할 점
CountDownLatch(n) n회 완료 후 여러 대기자 해제 일회성. 작업 실패에도 finally에서 count 감소
Semaphore(n) 제한된 자원의 동시 점유 수 소유권 없음. permit 회수 누수를 finally로 방지
CyclicBarrier(n) 고정 참여자의 반복 단계 합류 중단·시간 초과 시 barrier가 깨져 다른 참여자도 예외
05ForkJoinPool: 작업 분할과 work-stealing↘

작업자가 재귀 분할 작업을 처리하고, 한가하면 다른 작업자의 일을 훔친다. RecursiveTask/RecursiveAction으로 큰 CPU 계산을 나누는 데 맞는다. blocking I/O나 긴 잠금 대기는 작업자를 소진해 병렬 진행을 막으므로 별도 실행기 또는 ManagedBlocker를 고려한다.

Java 25에서 ForkJoinPool은 ScheduledExecutorService를 구현하고 submitWithTimeout을 제공한다. 이는 취소가 많은 timeout 예약의 처리 효율을 겨냥한 변화다. 예약 API가 있다는 이유로 blocking 업무까지 같은 풀에 섞지는 않는다.

044. 코드로 확인예제 1 — 제한된 큐, 최대 작업자, 거절 · 예제 2 — thenCompose와 예외 복구4개 코드 · 열기 ↓

아래 순수 Java 코드는 JDK 21로 실제 실행했다. 마지막 출력은 스레드 스케줄링과 무관하도록 latch로 작업 상태를 고정했다.

01예제 1 — 제한된 큐, 최대 작업자, 거절↘
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.TimeUnit;

public class PoolDemo {
    public static void main(String[] args) throws InterruptedException {
        CountDownLatch started = new CountDownLatch(2);
        CountDownLatch release = new CountDownLatch(1);
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                1, 2, 10, TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(1),
                new ThreadPoolExecutor.AbortPolicy());
        Runnable task = () -> {
            started.countDown();
            try {
                release.await();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        };
        pool.execute(task); // core thread
        pool.execute(task); // queue
        pool.execute(task); // queue full: grow to maximum
        started.await();
        try {
            pool.execute(task); // saturated: rejected
        } catch (java.util.concurrent.RejectedExecutionException e) {
            System.out.println("rejected=" + e.getClass().getSimpleName());
        }
        System.out.printf("pool=%d active=%d queued=%d%n",
                pool.getPoolSize(), pool.getActiveCount(), pool.getQueue().size());
        release.countDown();
        pool.shutdown();
        pool.awaitTermination(5, TimeUnit.SECONDS);
    }
}

실제 출력:

rejected=RejectedExecutionException
pool=2 active=2 queued=1
02예제 2 — thenCompose와 예외 복구↘
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.CompletionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class FutureDemo {
    public static void main(String[] args) {
        try (ExecutorService io = Executors.newSingleThreadExecutor()) {
            CompletableFuture<Integer> total = CompletableFuture
                    .supplyAsync(() -> "21", io)
                    .thenApply(Integer::parseInt)
                    .thenCompose(n -> CompletableFuture.supplyAsync(() -> n * 2, io));
            System.out.println("total=" + total.join());
            CompletableFuture<Integer> failed = CompletableFuture.supplyAsync(() -> {
                throw new IllegalStateException("remote failure");
            }, io);
            int recovered = failed.exceptionally(ex -> {
                Throwable cause = ex instanceof CompletionException ? ex.getCause() : ex;
                System.out.println("cause=" + cause.getClass().getSimpleName());
                return -1;
            }).join();
            System.out.println("recovered=" + recovered);
        }
    }
}

실제 출력:

total=42
cause=IllegalStateException
recovered=-1

버전 변화와 이전 한계 근거
Java 5 Executor, Future, 큐, 잠금, latch·semaphore의 표준 계약을 제공했다. 직접 스레드와 wait/notify만으로 작업 수명·결과·가시성을 재사용하기 어려웠다. Java SE 25 API의 관련 클래스는 Since: 1.5.
Java 7 ForkJoinPool이 재귀 분할과 work-stealing을 제공했다. 일반 풀에는 이 계산 모델이 없었다. ForkJoinPool, Since 1.7.
Java 8 LongAdder, 캐시용 ConcurrentHashMap 연산, ForkJoinPool 개선이 추가됐다. 단일 CAS 카운터 경합과 복수 호출로 쪼갠 키 갱신 문제를 다뤘다. JEP 155.
Java 9 CompletableFuture 개선과 Flow는 JEP 266, 형식 안전한 저수준 원자 접근은 VarHandle JEP 193으로 들어왔다. JEP 266, JEP 193.
Java 25 ForkJoinPool의 예약 API와 submitWithTimeout, CompletableFuture async 기본 실행을 common pool로 통일했다. 이전에는 parallelism<2일 때 새 스레드 fallback이 있었다. JDK-8362881. 취소가 많은 timeout 처리 성능을 위한 변화다.
066. 실무 가이드열기 ↓
  • 풀 기본값은 **유한 ArrayBlockingQueue + AbortPolicy를 지정한 ThreadPoolExecutor**다. 큐 대기, 거절 수, 활성·완료 작업을 보고 크기를 조정한다.
  • 결과 대기에는 timeout 있는 Future; 여러 단계를 조합할 때는 CompletableFuture와 명시 실행기를 쓴다. I/O 실행기는 common pool의 계산 작업과 분리한다.
  • 여러 필드의 불변식은 우선 하나의 synchronized/ReentrantLock으로 묶는다. timeout 획득, 인터럽트 대기, 복수 Condition이 필요할 때 Lock을 고른다.
  • 읽기 잠금 계열은 측정 뒤 도입한다. 낙관 읽기의 재검증을 감당할 수 있을 때만 StampedLock을 쓴다.
  • 정확한 원자값은 AtomicLong, 경합 큰 통계는 LongAdder. 키 단위 갱신은 ConcurrentHashMap.compute/merge로 원자화한다.
  • 자원 동시 점유를 제한하면 Semaphore permit을 finally에서 반납한다. 반복적 CPU 분할은 ForkJoinPool; blocking I/O는 전용 실행기로 분리한다.
  • 실행기 종료 때 shutdown·awaitTermination을 호출하고, 인터럽트에 협력하도록 작업을 작성한다.
077. 함정·안티패턴열기 ↓
  1. 힙이 차고 지연이 누적됨 → 무한 큐에 처리량보다 많은 작업이 쌓임 → 유한 큐, 거절·역압력, 큐 대기 경보를 둔다.
  2. Future.get()이 영원히 대기 → discard 정책이 제출 작업을 버림 → 기본은 AbortPolicy; 거절과 timeout을 호출자에게 전달한다.
  3. CF 단계가 요청 스레드를 점유 → 비-async 함수가 완료 스레드에서 블로킹 → I/O와 계산 단계를 다른 실행기로 분리한다.
  4. 비동기 체인에서 실패가 숨음 → 실패 뒤 성공 전용 단계는 실행되지 않음 → 경계에서 exceptionally/handle하고 cause를 기록한다.
  5. 락 이후 전체 처리가 정지 → unlock 누락 또는 StampedLock 재진입 오해 → finally로 해제하고 중복 획득 호출을 제거한다.
  6. 조건부 카운터 결과가 틀림 → LongAdder.sum()을 제어 값으로 사용하거나 여러 atomic 값을 하나의 불변식으로 취급 → 단일 잠금 또는 CAS 상태로 보호한다.
  7. 맵에 중복 생성·지연 → get/put 분리 또는 느린 I/O를 computeIfAbsent에 넣음 → 원자 키 API와 짧은 매핑 함수를 쓴다.
  8. ForkJoin 계산도 멈춤 → 작업자가 블로킹 I/O를 기다림 → blocking 경로를 분리하거나 ManagedBlocker를 쓴다.
088. 자가점검 Q&A (면접 대비)Q1. maximumPoolSize를 늘렸는데 worker 수가 그대로인 이유는? · Q2. thenApply는 비동기인가? thenApplyAsync는 새 스레드를 만드는가? · Q3. thenApply 대신 thenCompose가 필요한 경우는? · Q4. Future.cancel(true)면 작업이 즉시 종료되는가?열기 ↓
01Q1. maximumPoolSize를 늘렸는데 worker 수가 그대로인 이유는?↘

코어가 찬 뒤 executor는 먼저 큐에 삽입한다. 큐가 받아 주면 최대 worker까지 늘리지 않는다.

꼬리질문: 포화 시 작업을 거절하려면? → 유한 큐와 명시 거절 정책을 조합한다.

02Q2. thenApply는 비동기인가? thenApplyAsync는 새 스레드를 만드는가?↘

thenApply는 완료 스레드에서 실행될 수 있다. thenApplyAsync도 명시 실행기가 없으면 Java 25 common pool을 쓸 뿐 새 스레드를 보장하지 않는다.

꼬리질문: blocking HTTP는 어디서 실행할까? → 전용 I/O 실행기를 지정한다.

03Q3. thenApply 대신 thenCompose가 필요한 경우는?↘

함수가 비동기 결과를 반환할 때다. thenApply면 중첩 Future가 되고 thenCompose는 한 단계로 평탄화한다.

꼬리질문: 독립 단계 둘을 묶으려면? → thenCombine; 완료만 모으면 allOf를 쓴다.

04Q4. Future.cancel(true)면 작업이 즉시 종료되는가?↘

아니다. 실행 스레드에 interrupt를 요청하고, 코드는 이에 협력해야 한다.

꼬리질문: CompletableFuture.cancel은? → 완료 상태를 취소로 만들지만 실제 계산을 강제 중단하지 않는다.

05Q5. LongAdder가 AtomicLong보다 나은가?↘

경합이 큰 통계 업데이트에는 유리하지만 sum()은 원자 스냅샷이 아니다. 잔액·순번 등 제어 값에는 적절하지 않다.

꼬리질문: 여러 필드 상태의 원자성은? → 각 원자 변수만으로는 보장되지 않아 잠금이나 단일 CAS 상태가 필요하다.

06Q6. ConcurrentHashMap의 containsKey 후 put은 원자적인가?↘

아니다. 두 호출 사이에 다른 스레드가 갱신할 수 있다. putIfAbsent나 computeIfAbsent를 쓴다.

꼬리질문: 동시 갱신 중 size()는 전체 스냅샷인가? → 아니다. 전체 맵을 잠그지 않는 관찰값이다.

07Q7. 읽기 잠금에서 쓰기 잠금으로 승격할 수 있나?↘

ReentrantReadWriteLock은 승격을 지원하지 않아 여러 reader가 쓰기 잠금을 기다리면 교착할 수 있다.

꼬리질문: 쓰기에서 읽기로 내려가려면? → 읽기 잠금을 추가 획득한 다음 쓰기 잠금을 놓는다.

08Q8. latch·semaphore·barrier 중 자원 풀 제한에 쓸 것은?↘

Semaphore다. permit 수가 동시 점유 수를 제한한다. latch는 일회성 완료, barrier는 정해진 참여자의 반복 합류다.

꼬리질문: permit 반납은 어디서? → 예외에도 누수되지 않도록 finally에서 release()한다.

09Q9. ForkJoinPool의 work-stealing은 blocking I/O 정체도 해결하나?↘

아니다. 분할 계산을 나누는 방식이며, 작업자 모두가 대기하면 진행이 느려진다.

꼬리질문: 피할 수 없는 blocking이면? → ManagedBlocker 또는 별도 실행기를 사용한다.
