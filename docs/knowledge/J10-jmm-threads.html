J10. 스레드와 Java Memory Model

#J10. 스레드와 Java Memory Model

스레드 간 공유 상태는 우연한 타이밍이 아니라 동기화 규칙으로 전달해야 한다. JMM은 “메모리를 즉시 비운다”는 구현 설명이 아니라 허용되는 실행 결과를 정의한다. 기본기는 잠금으로 불변식을 보호하고, volatile은 한 변수의 가시성과 순서를 전달하는 데 쓴다.

011. 왜 알아야 하나열기 ↓

운영 서버에서 종료 플래그를 일반 boolean으로 두면, 한 스레드가 true로 바꿔도 다른 스레드는 루프를 계속 돌 수 있다. JIT는 반복 읽기를 제거할 수 있고 sleep은 가시성을 보장하지 않는다. volatile 없는 이중 검사 락은 객체 완성 전에 참조를 공개할 수 있다.

데이터 레이스는 동작을 불확정하게 만든다. count++ 갱신 누락, 객체 필드의 기본값 관측, wait() 뒤 거짓 조건에서 진행하는 오류가 대표적이다. 서로 다른 순서로 잠금을 얻다가 멈추면 데드락이다.

022. 핵심 개념스레드 상태열기 ↓
용어 뜻 실무에서 확인할 점
스레드(thread) 독립된 실행 흐름. Thread 객체와 실행을 나타내며 **start()**가 새 실행을 시작한다. run() 직접 호출은 새 스레드를 만들지 않고 현재 흐름에서 메서드를 실행한다.
공유 변수 여러 스레드에서 접근 가능한 인스턴스 필드, 정적 필드, 배열 원소. 지역 변수와 매개변수는 보통 스레드별 실행 프레임에 있으므로 공유 변수 자체가 아니다. 다만 지역 변수가 공유 객체를 가리킬 수 있다.
데이터 레이스 같은 변수에 대한 충돌 접근(적어도 하나는 쓰기)이 happens-before로 정렬되지 않은 상태. 경쟁 쓰기가 있으면 소스 코드의 순서만으로 관측값을 추론하지 않는다.
모니터(monitor) 모든 Java 객체에 연관된 상호 배제 잠금과 대기 집합. synchronized가 획득·해제한다. 인스턴스 동기화 메서드는 this, 정적 동기화 메서드는 해당 Class 객체를 잠근다. 재진입 가능하다.
happens-before(HB) 한 동작이 다른 동작보다 먼저이며 그 효과가 후속 동작에 보이도록 보장하는 부분순서. “물리적으로 그 시각에 먼저 실행”이라는 뜻은 아니다. 구현은 HB 제약을 지키는 한 재배치할 수 있다.
안전한 공개(safe publication) 완성된 객체 참조를 동기화 규칙을 통해 다른 스레드에 전달하는 것. 생성자 완료만으로 일반 필드 전체가 자동 공개되지는 않는다.
원자성·가시성·순서 원자성은 쪼개지지 않는 단위, 가시성은 다른 스레드가 쓴 값을 읽는 것, 순서는 관측 가능한 순서를 제한하는 것. volatile은 단순 **count++**를 원자적으로 만들지 않는다.
01스레드 상태↘

Thread.State는 JVM의 여섯 상태이며 OS 상태와 일대일 대응하지 않는다. **getState()**는 순간적인 진단값이지 동기화 수단이 아니다.

상태 들어가는 대표 상황 여기서 헷갈리기 쉬운 점
NEW 생성 후 start() 전 시작된 적이 없는 상태다.
RUNNABLE JVM 안에서 실행 중이거나 실행 가능한 상태 실제 CPU에서 실행 중이라는 뜻만은 아니다. OS 자원을 기다릴 수도 있다.
BLOCKED synchronized 모니터를 얻거나 wait() 후 재획득 대기 Object.wait() 호출로 조건을 기다리는 상태는 보통 WAITING이다.
WAITING 무기한 wait(), 무기한 join(), LockSupport.park() 특정 스레드/행동의 진행을 기다린다.
TIMED_WAITING 시간 제한 wait, join, sleep, parkNanos 등 시간이 만료되어도 즉시 실행된다는 뜻은 아니며 스케줄러가 다시 실행해야 한다.
TERMINATED **run()**이 정상 또는 예외로 끝남 종료한 Thread 객체를 다시 시작할 수 없다.

wait와 sleep은 서로 바꿔 쓸 수 없다. wait는 해당 모니터를 보유한 상태에서만 부를 수 있고 그 객체의 모니터를 놓고 대기한다. sleep은 모니터를 놓지 않으며 조건 변화와도 연결되지 않는다. 어느 쪽도 그 자체로 공유 메모리 가시성을 제공하지 않는다.

033. 내부 동작·원리실행 흐름과 상태 · 모니터와 wait/notify · JMM: 허용 결과를 정하는 규칙 · volatile, 불변 객체와 안전한 공개3개 코드 · 열기 ↓
01실행 흐름과 상태↘

**start()**는 호출 스레드에서 대상 **run()**을 실행하는 메서드 호출이 아니다. 새 스레드의 첫 동작은 start() 호출보다 happens-before다. 다른 스레드가 **join()**에서 정상 반환하면 종료한 스레드의 동작은 그 반환보다 happens-before다.

Thread 객체 생성 ──> NEW ──start()──> RUNNABLE
                                     │
                         모니터 획득 대기 ──> BLOCKED
                         wait/join 대기 ─────> WAITING
                         제한 시간 대기 ─────> TIMED_WAITING
                                     │
                              run() 종료
                                     ▼
                                TERMINATED

RUNNABLE은 실행 대기와 JVM에서 실행 중인 경우를 모두 포함한다. BLOCKED는 모니터 획득 대기, WAITING은 다른 사건 대기다. notify로 대기 집합에서 빠져도 통지자가 모니터를 반납한 뒤에야 잠금을 재획득한다.

02모니터와 wait/notify↘

**synchronized (lock) { ... }**는 lock의 모니터 잠금을 얻은 뒤 블록에 들어간다. 정상 종료, return, 예외 종료 등 블록을 벗어날 때 해당 획득에 대응하는 잠금 하나를 자동으로 해제한다. 같은 스레드는 같은 모니터를 여러 번 획득할 수 있다. 따라서 재진입 횟수만큼 해제해야 다른 스레드가 들어온다.

**wait()**은 모니터를 보유한 상태에서만 부를 수 있다. 대기 집합에 들어가면서 그 모니터의 재진입 횟수만큼 잠금을 풀고, 통지·인터럽트·타임아웃·spurious wakeup으로 깨어난 뒤 같은 횟수만큼 재획득해야 반환하거나 InterruptedException을 던진다.

**notify()**는 대기자 하나를 임의로 선택하고 **notifyAll()**은 모두 깨운다. 깨어난 스레드는 통지자가 모니터를 놓은 뒤 잠금을 다시 얻어야 한다. 따라서 조건은 잠금 안의 반복문에서 확인한다.

생산자: synchronized(lock) { 상태 변경; lock.notifyAll(); }
소비자: synchronized(lock) {
          while (!조건) lock.wait();
          상태 사용;
        }

같은 모니터가 조건 검사와 wait() 사이의 경합을 막는다. 재획득 전 조건이 바뀔 수 있고 spurious wakeup도 허용되므로 if가 아니라 while로 검사한다. 서로 다른 조건의 대기자가 섞여 **notify()**가 잘못된 대기자만 깨우면 진행이 멎을 수 있다.

03JMM: 허용 결과를 정하는 규칙↘

JMM은 컴파일러가 메모리를 비우는 절차가 아니라 읽기가 어떤 쓰기를 관측할 수 있는지 정한다. 한 스레드의 의미를 보존하는 한 컴파일러와 CPU는 JMM이 허용하는 범위에서 동작을 재배치할 수 있다. 데이터 레이스가 있으면 소스 코드 순서가 다른 스레드의 관측 순서를 보장하지 않는다.

핵심 연결은 다음과 같다.

Thread A: 공유 데이터 쓰기 ── program order ──> release 동작
                                                  │ synchronizes-with
                                                  ▼
Thread B: acquire 동작 ────── program order ──> 공유 데이터 읽기
                            전체 연결이 HB

주요 synchronizes-with 규칙:

  • 모니터 **unlock(m)**은 동기화 순서에서 뒤따르는 같은 모니터의 **lock(m)**과 연결된다.
  • volatile 변수 v에 대한 쓰기는 동기화 순서에서 뒤따르는 v 읽기와 연결된다. 다른 변수에 대한 volatile 쓰기/읽기는 이 직접 규칙의 짝이 아니다.
  • Thread.start() 호출은 새 스레드의 첫 동작보다 먼저다. 종료를 관측한 join() 정상 반환은 종료 스레드의 동작보다 뒤다.
  • 객체의 기본값 쓰기는 프로그램의 다른 동작보다 먼저다. 이는 명시적으로 대입한 값이나 생성자의 일반 필드 쓰기를 안전하게 공개한다는 뜻은 아니다.
  • **wait()**와 **join()**에도 명세상 잠금·해제 동작이 있다.

HB는 같은 스레드의 프로그램 순서, 위의 동기화 연결, 추이성으로 만들어진다. 데이터 레이스는 동일 변수에 대한 충돌 접근 사이에 HB 경로가 없을 때 성립한다. 올바르게 동기화된 프로그램은 모든 실행에서 순차 일관성처럼 관측된다. 이는 프로그램이 업무상 정답을 낸다는 보장은 아니며, 단지 동기화되지 않은 재배치 결과를 피할 수 있게 한다.

원자성·가시성·순서는 별개다. int 단일 접근은 원자적이어도 **count++**는 읽기-계산-쓰기라 갱신을 잃을 수 있다. JLS는 비volatile long/double을 두 32비트 접근으로 나누는 구현을 허용(원자 처리를 강하게 권고)하지만 volatile 접근은 원자적이다. 여러 변수의 불변식은 별도 보호가 필요하다.

04volatile, 불변 객체와 안전한 공개↘

volatile 읽기는 동기화 순서에서 앞선 같은 변수의 쓰기를 관측하는 acquire 동작이고, 쓰기는 release 동작이다. 따라서 쓰기 전에 같은 스레드에서 수행한 일반 필드 쓰기는 뒤에서 volatile 값을 읽은 스레드에 보인다.

전형적인 종료 플래그나 단일 작성자가 설정하는 상태 전달에 유용하다. 그러나 **volatile count; count++**의 세 단계는 원자화되지 않고, volatile 두 필드가 하나의 일관된 스냅샷을 보장하지 않는다.

final 필드는 생성자가 끝날 때 초기화된 값에 특별한 보장을 준다. 생성 중 this를 공개하지 않았다면 데이터 레이스로 전달된 참조에서도 올바른 final 값을 본다. 일반 필드까지 공개되는 것은 아니다. final 참조가 가리키는 가변 객체도 자동으로 불변이 되지 않는다.

가변 상태는 잠금, volatile 참조, 클래스 초기화 등 HB가 생기는 경로로 공개한다. 생성 완료와 타 스레드의 안전한 관측은 별개다.

05데드락·라이브락·기아↘
  • 데드락: 잠금 획득 대기가 고리를 이루어 누구도 다음 단계로 가지 못한다. JLS는 감지나 예방을 보장하지 않는다.
  • 라이브락: 스레드가 계속 상태를 바꾸고 양보하지만 서로의 반응으로 같은 작업을 반복해 완료하지 못한다. 잠금을 피한 재시도 정책도 설계가 나쁘면 발생한다.
  • 기아(starvation): 특정 스레드가 잠금이나 CPU를 오래 얻지 못한다. synchronized 모니터는 공정한 대기 순서를 약속하지 않으며, 우선순위도 진행 보장으로 쓰지 않는다.

데드락의 전형은 A가 x를 잡고 y를 기다리는 동안 B가 y를 잡고 x를 기다리는 순환이다. 공유 잠금의 획득 순서를 일관되게 정하면 이 순환을 차단할 수 있다.

044. 코드로 확인예제 1 — volatile로 데이터 게시 · 예제 2 — 조건 변수와 wait/notifyAll · 예제 3 — 올바른 이중 검사 락6개 코드 · 열기 ↓

세 예제는 Corretto JDK 21에서 실행했다. **Thread.onSpinWait()**는 힌트일 뿐 가시성 보장은 volatile이 제공한다.

01예제 1 — volatile로 데이터 게시↘
public class VolatileVisibilityDemo {
    private static int payload;
    private static volatile boolean ready;

    public static void main(String[] args) throws InterruptedException {
        Thread reader = new Thread(() -> {
            while (!ready) {
                Thread.onSpinWait();
            }
            System.out.println("payload=" + payload);
        });
        Thread writer = new Thread(() -> {
            payload = 42;
            ready = true;
        });
        reader.start();
        writer.start();
        reader.join();
        writer.join();
    }
}

payload = 42가 ready = true보다 프로그램 순서상 앞서고, ready를 읽어 루프에서 빠져나온 읽기는 volatile 쓰기와 동기화된다. 그 결과 payload 쓰기도 읽기보다 happens-before다.

payload=42
02예제 2 — 조건 변수와 wait/notifyAll↘
public class WaitNotifyDemo {
    private static final Object monitor = new Object();
    private static boolean ready;
    private static int value;

    public static void main(String[] args) throws InterruptedException {
        Thread waiter = new Thread(() -> {
            synchronized (monitor) {
                while (!ready) {
                    try {
                        monitor.wait();
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                        return;
                    }
                }
                System.out.println("received=" + value);
            }
        });
        waiter.start();

        long deadline = System.nanoTime() + 5_000_000_000L;
        while (waiter.getState() != Thread.State.WAITING
                && System.nanoTime() < deadline) {
            Thread.yield();
        }
        if (waiter.getState() != Thread.State.WAITING) {
            throw new IllegalStateException("waiter did not enter WAITING");
        }
        System.out.println("state=" + waiter.getState());

        synchronized (monitor) {
            value = 42;
            ready = true;
            monitor.notifyAll();
        }
        waiter.join();
    }
}

상태 확인 반복은 예제에서 WAITING 경로를 보이기 위한 장치다. 운영 동기화는 **getState()**가 아니라 ready를 보호하는 모니터가 담당한다. 인터럽트 시 상태를 복원하고 반환한다.

state=WAITING
received=42
03예제 3 — 올바른 이중 검사 락↘
public class DclDemo {
    private static final class SafeLazy {
        private static volatile SafeLazy instance;
        private final int initializedValue;

        private SafeLazy() {
            initializedValue = 42;
        }

        static SafeLazy getInstance() {
            SafeLazy result = instance;
            if (result == null) {
                synchronized (SafeLazy.class) {
                    result = instance;
                    if (result == null) {
                        result = new SafeLazy();
                        instance = result;
                    }
                }
            }
            return result;
        }
    }

    public static void main(String[] args) {
        SafeLazy first = SafeLazy.getInstance();
        SafeLazy second = SafeLazy.getInstance();
        System.out.println("same=" + (first == second)
                + ", initializedValue=" + second.initializedValue);
    }
}

바깥 검사는 초기화가 끝난 뒤 매번 클래스 모니터에 진입하지 않게 한다. 내부 재검사는 두 호출이 동시에 첫 검사를 통과한 경우 중복 생성을 막는다. instance를 volatile로 선언해 생성 완료 후 참조 게시에 release/acquire 순서를 부여한다.

same=true, initializedValue=42
055. 버전별 변화 — 왜 바뀌었나열기 ↓
  • Java 5 / JSR 133 (2004 최종 승인): 이전 JMM은 의도치 않은 결과와 불명확한 동기화 관용구를 허용해 구현 최적화와 프로그래머 추론을 모두 어렵게 했다. 이를 고치기 위해 JLS 17의 스레드·잠금·volatile·데이터 레이스 의미를 크게 다시 규정했고 volatile, final, 안전한 재정렬의 근거가 현재의 모델로 정리됐다. JSR 133 상세
  • JDK 15 / JEP 374: 무경쟁 synchronized를 줄이려던 biased locking은 경합 시 회수 비용과 VM 복잡성에 비해 최근 앱에서 이득이 줄어 기본 비활성화되고 관련 옵션이 deprecated 됐다. 이는 JLS 잠금 의미 변경이 아니라 HotSpot 최적화 이력이다. JEP 374
  • JDK 24 / JEP 491: virtual thread가 synchronized에서 블로킹될 때 carrier를 붙잡던 구현 한계가 확장성을 제한해, 거의 모든 pinning 사례를 제거하도록 HotSpot이 바뀌었다. 모니터의 언어 의미를 대체하지 않으며 virtual thread 상세는 J12 참조. JEP 491
066. 실무 가이드열기 ↓
  • 여러 필드가 함께 만족해야 하는 불변식이면 하나의 private final Object lock과 synchronized로 읽기·쓰기를 보호하라. 잠금 범위가 데이터 규칙을 드러내고, 한 필드만 volatile로 표시하는 식의 부분 보호를 피한다.
  • 단일 상태 플래그를 한 스레드가 쓰고 여러 스레드가 읽으면 volatile boolean을 사용하라. 플래그를 읽어 true가 된 뒤 관련 데이터를 읽는 설계라면 데이터 쓰기를 먼저 하고 volatile 플래그를 마지막에 써라.
  • 증가·감소나 read-modify-write가 필요하면 volatile을 원자 연산으로 간주하지 마라. 이 문서 범위에서는 synchronized로 묶는다. 고수준 원자 변수·락 등 동시성 도구는 → J11 참조.
  • 객체가 변경 불가능하고 모든 필드를 생성자에서 완성하면 final 필드를 사용하고 생성 중 this 공개를 금지하라. 이로써 초기화 안전성을 얻되 이후 가변 상태까지 보호됐다고 착각하지 않는다.
  • 지연 초기화가 목적이면 먼저 정적 초기화를 고려하라. 클래스 초기화가 완료된 정적 필드는 안전하게 게시된다(JLS §12.4.2). lazy가 꼭 필요하면 volatile DCL이나 holder 패턴을 쓰고 bare DCL은 피한다.
  • 모니터 대기 조건을 구현하면 상태와 wait/notify를 동일한 모니터로 보호하고, **while (!조건) wait()**를 사용하라. 여러 종류의 대기 조건이나 복잡한 큐잉을 손수 만들기 시작하면 → J11을 검토한다.
  • 스레드 상태를 관측하면 **getState()**는 순간적인 진단값으로만 쓴다. 완료 여부를 판정하려면 **join()**처럼 명세된 동기화 지점을 사용한다.
  • 여러 잠금을 써야 하면 모든 코드가 같은 전역 순서를 따르게 하라. 잠금 순환을 만들지 않고 코드 리뷰에서 순서가 확인되어야 한다.

기본값 추천: 변경 가능한 공유 데이터의 일관성이 목적이면 private final 모니터 하나에 접근을 모으고 synchronized로 보호한다. volatile은 독립 상태 전달에 한정해 고른다.

077. 함정·안티패턴열기 ↓
  1. 일반 boolean 종료 플래그 — 증상: 종료 요청 뒤 무한 루프가 이어진다 → 원인: 읽기와 쓰기 사이 HB가 없고 컴파일러가 읽기를 재사용할 수 있다 → 대처: volatile 또는 같은 모니터로 읽기·쓰기를 동기화한다. **sleep()**은 해결책이 아니다.
  2. if로 감싼 wait() — 증상: 조건이 거짓인데 큐를 비우거나 예외가 난다 → 원인: spurious wakeup, 경쟁자 선점, 다른 조건의 대기자가 같은 **notifyAll()**로 깨어날 수 있다 → 대처: 잠금 안에서 **while (!조건) wait()**로 재검사한다.
  3. 조건 대입과 통지를 서로 다른 잠금으로 보호 — 증상: 대기자가 영원히 잠들거나 공유 데이터가 오래된 값으로 보인다 → 원인: 조건 검사/대기 진입 사이의 경합 또는 HB 경로 누락 → 대처: 조건 상태, 검사, 대입, wait/notify를 동일 모니터로 보호한다.
  4. 맨몸 DCL — 증상: instance != null인데 내부 필드가 기본값으로 관측될 수 있다 → 원인: 참조 읽기와 생성 완료의 publication ordering을 보장하지 않는다 → 대처: 인스턴스 참조를 volatile로 선언하고 잠금 안에서 두 번째 null 검사를 한다. 아니면 클래스 초기화를 쓴다.
  5. volatile count++ — 증상: 동시에 증가시켰는데 최종 값이 예상보다 작다 → 원인: volatile은 각 읽기·쓰기 가시성과 순서를 보장하지만 증가 전체를 단일 원자 동작으로 만들지 않는다 → 대처: 복합 불변식을 잠금으로 묶는다. 원자 변수 계열은 → J11 참조.
  6. notify()로 대기자 하나만 깨우기 — 증상: 처리 가능한 조건이 있는데 시스템이 멈춘 듯 보인다 → 원인: 어떤 대기자를 선택할지 보장되지 않아 선택된 스레드가 자기 조건을 충족하지 않을 수 있다 → 대처: 조건이 여럿이면 notifyAll() 후 각 스레드가 자기 조건을 반복 검사하거나 조건별 구조를 쓴다.
  7. 모니터를 풀지 않는 sleep() — 증상: 잠든 스레드가 공유 잠금을 계속 쥐어 다른 스레드가 진행하지 못한다 → 원인: **sleep()**은 모니터를 해제하지 않는다 → 대처: 임계 구역을 짧게 유지하고 조건 대기에는 올바른 wait() 패턴을 쓴다.
  8. 공개 객체 생성자에서 this 유출 — 증상: 다른 스레드가 생성자 완료 전에 필드나 콜백을 관측한다 → 원인: 생성 도중 참조가 공유 위치에 저장되거나 다른 스레드에 전달됐다 → 대처: 생성 중 등록·시작을 피하고 객체 완성 후 안전한 채널로 공개한다. final 보장은 조기 유출을 정당화하지 않는다.
088. 자가점검 Q&A (면접 대비)열기 ↓
Q2. happens-before는 실제 CPU 실행 순서와 같은가?


아니다. HB는 가시성과 관측 가능한 순서를 제한하는 명세상의 부분순서다.

구현은 HB에 위배되는 결과가 생기지 않는 한 명령을 재배치할 수 있다.
따라서 “먼저 쓴 필드가 먼저 보인다”가 아니라 어떤 동기화 연결이 있는지 추적한다.

꼬리질문: 같은 락의 unlock/lock은 어떤 역할인가? release-acquire 연결을 만들고 unlock 이전의 동작을 후속 lock 뒤의 동작에 공개한다.

Q3. volatile과 synchronized를 비교하면?


같은 volatile 변수의 쓰기와 읽기는 가시성과 순서를 연결하지만 상호 배제하지 않는다.
synchronized는 모니터 하나에 한 번에 한 스레드만 들어가게 하고 잠금 해제로 HB를 만든다.

여러 필드의 불변식이나 read-modify-write는 잠금으로 묶고, 독립 플래그는 volatile을 고려한다.
꼬리질문: **volatile int n; n++**이 안전한가?

아니다. 읽기와 쓰기 사이에 다른 스레드가 끼어들 수 있다.

Q4. wait() 직후 조건을 다시 검사해야 하는 이유는?


spurious wakeup이 허용되고, 통지 후 잠금을 다시 얻기 전에 다른 스레드가 조건을 바꿀 수 있다.
**notify()**는 대기자 중 임의 하나를 깨울 뿐 조건이 참임을 보장하지 않는다.

따라서 모니터 안에서 **while (!조건) wait()**로 조건이 만족될 때까지 재평가한다.
꼬리질문: notify() 호출 즉시 대기자가 잠금을 얻나?

아니다. 통지자는 모니터를 놓아야 대기자가 재획득한다.

Q5. 두 스레드가 count++를 하는데 왜 값이 빠질 수 있나?


증가는 현재 값을 읽고 더한 뒤 새 값을 쓰는 복합 동작이라 두 스레드가 같은 옛 값을 읽을 수 있다.
volatile은 개별 변수 접근의 가시성·순서를 보장할 뿐 이 묶음을 원자화하지 않는다.

임계 구역으로 전체 동작을 잠그거나 J11의 원자적 동시성 도구를 고른다.
꼬리질문: 일반 32비트 int 읽기 자체가 찢어지나? JLS는 int 접근을 원자적으로 다루지만, 원자적 접근이 복합 증가를 뜻하지 않는다.

Q6. DCL에서 volatile이 필요한 이유는?


참조가 null이 아니라고 관측한 것과 생성자에서 수행한 필드 초기화를 관측하는 것은 별개의 문제다.
volatile 참조 쓰기와 뒤이은 같은 참조의 읽기가 HB를 만들어 인스턴스 게시 순서를 보장한다.

모니터 안의 두 번째 null 검사는 동시에 들어온 초기화자가 둘이 되는 것을 막는다.
꼬리질문: lazy가 필요 없다면 더 단순한 선택은? 정적 필드의 클래스 초기화 또는 holder 패턴이다.

Q7. final 필드가 있으면 객체를 아무렇게나 공개해도 되나?


생성자가 완료되고 this가 생성 중 유출되지 않았다면 final 필드의 초기화 값에 특별한 가시성 보장이 있다.
일반 필드까지 같은 보장을 받는 것은 아니며, final 참조가 가리키는 가변 객체도 자동으로 thread-safe하지 않다.

나머지 상태에는 안전한 공개와 후속 변경을 위한 동기화가 필요하다.
꼬리질문: final 참조가 가리키는 리스트는 불변인가?

아니다. 참조 재할당이 금지될 뿐 리스트 원소 변경은 가능하다.
