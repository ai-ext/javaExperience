013.1 쉘과 파일↘

무엇이 일어나나: Bash는 명령을 나누고 변수·따옴표를 처리한 뒤 builtin 또는 실행 파일을 실행한다. cd는 현재 쉘의 작업 위치를 바꾸므로 builtin이다. PATH는 실행 파일 검색 경로이며 command -v java로 실제 선택된 프로그램을 본다.

>는 stdout을 덮어쓰고 >>는 추가한다. 2>는 stderr를 분리하며 2>&1은 stderr를 stdout의 현재 대상으로 연결한다.

리다이렉션은 왼쪽에서 오른쪽으로 적용되므로 순서를 바꾸면 결과가 달라진다. 파이프 |는 기본적으로 stdout만 다음 명령의 stdin에 보낸다.

누가/도구: 개발자와 쉘, pwd, ls, cat, less, grep, find.

입력과 산출물: 경로·명령·환경이 입력이고, 출력·종료 상태·프로세스가 결과다. /etc는 설정, /var/log는 텍스트 로그가 흔한 위치, /opt는 추가 앱, /home은 사용자 홈으로 쓰인다. 리눅스 로그가 꼭 파일로만 저장되는 것은 아니다.

실패하면: command not found는 설치 또는 PATH, Permission denied는 파일 권한이나 상위 디렉터리 통과 권한을 본다. cat은 짧은 파일, less는 긴 파일에 쓰고, grep -n ERROR file이나 find /opt/orders -name '*.jar'처럼 검색 경로를 좁힌다.

cp는 복사, mv는 이동·이름 변경이다. rm은 휴지통 없이 지우므로 대상과 pwd를 확인하고 rm -i부터 쓴다.

023.2 권한·프로세스·네트워크↘

무엇이 일어나나: rwx는 소유자·그룹·기타별 권한이다. 파일 x는 실행, 디렉터리 x는 경로 탐색을 뜻한다. chmod 640은 소유자 rw·그룹 r, chown은 소유권 변경이다.

sudo는 필요한 명령에만 쓴다. ps·top은 프로세스 관찰, kill은 기본 SIGTERM 종료 요청이다. SIGKILL은 정리 기회 없는 강제 종료다.

포트는 프로세스가 연 소켓에서 확인한다. ss -lntp가 기본 선택이고 netstat -lntp는 구형 환경에서 볼 수 있다. lsof -i :8080은 파일을 연 프로세스와 포트를 연결한다.

curl은 HTTP 응답, nc -vz host 8080은 TCP 연결 가능성을 확인한다. ping은 ICMP만 확인하므로 TCP 포트 테스트가 아니다.

누가/도구: 운영자, chmod, chown, sudo, ps, top, kill, ss, lsof, curl, ping, nc.

입력과 산출물: 소유자·모드·PID·주소를 입력으로 삼아 접근 여부·프로세스·소켓 상태를 확인한다.

실패하면: ls -l로 서비스 계정과 파일 권한을 비교한다. 프로세스·포트 부재는 각각 서비스 상태와 로그·바인딩 설정을 본다. chmod -R 777은 피한다.

033.3 SSH에서 서비스 기동까지↘

무엇이 일어나나: SSH는 원격 로그인을 암호화하며 host key 확인과 사용자 인증을 거친다. 공개키는 서버 계정에 등록하고 개인키는 클라이언트에 보관한다. scp는 파일 복사, rsync는 차이를 비교해 동기화한다.

systemd는 unit의 사용자·작업 디렉터리·실행 명령으로 서비스를 만들고 프로세스 종료를 감시한다. Type=exec는 실행 파일을 실제로 시작했는지 확인한다. Spring Boot의 stdout/stderr는 systemd가 수집해 journal에서 볼 수 있다.

sequenceDiagram
    actor O as "운영자"
    participant C as "systemctl"
    participant S as "systemd 관리자"
    participant J as "JVM과 Spring Boot"
    participant L as "systemd journal"
    O->>C: start orders.service
    C->>S: unit 시작 요청
    S->>S: unit과 사용자·경로 확인
    S->>J: fork 후 execve로 Java 실행
    J-->>S: 실행 성공과 프로세스 상태
    J->>L: stdout과 stderr 출력
    O->>C: status orders.service
    S-->>O: active 또는 failed와 최근 로그

누가/도구: 운영자, SSH, scp/rsync, systemctl, JVM, journalctl.

입력과 산출물: jar·unit·환경 설정을 넣으면 프로세스·포트·로그가 생긴다. systemctl status orders, journalctl -u orders -b -n 100, ss -lntp, 로컬 curl 순으로 본다. daemon-reload는 unit 정의를 다시 읽고, restart는 앱을 재시작하며, enable은 부팅 자동 시작을 등록한다.

실패하면: SSH Permission denied (publickey)는 계정·키 등록·지정키를, timeout은 호스트·포트 경로를 확인한다. systemctl start 성공은 HTTP 준비 완료가 아니다. 서비스가 failed면 journal을 보고, 프로세스는 있으나 포트가 없으면 시작 로그와 바인딩 설정을 확인한다.

043.4 장애를 계층적으로 좁히기↘

무엇이 일어나나: 먼저 관리자 상태, 이어 프로세스·소켓·HTTP·로그를 확인한다. df -h는 파일시스템 공간, du -sh 경로는 디렉터리 점유량이다. free -h에서는 단순 free보다 available을 본다. 값 차이는 열린 채 삭제된 파일이나 다른 마운트에서 생길 수 있다.

누가/도구: 당직자, systemctl, ps, ss, curl, journalctl, df, du, free.

입력과 산출물: 실패 증상과 시각에서 시작해 원인 후보와 조치 결과로 좁힌다.

flowchart LR
    A["요청 실패 제보"] --> B["systemctl status"]
    B -->|failed| C["journalctl로 시작 오류 확인"]
    B -->|active| D["ps로 PID 확인"]
    D --> E["ss로 리스닝 포트 확인"]
    E -->|포트 없음| F["설정·바인딩·기동 로그 점검"]
    E -->|포트 있음| G["curl로 HTTP 응답 확인"]
    G -->|로컬도 실패| H["앱 경로·설정 확인"]
    G -->|로컬 성공| I["호스트 밖 경로 확인"]
    C --> J["수정 후 재검증"]
    F --> J
    H --> J
    I --> J

실패하면: journalctl -u orders -b -n 200 또는 grep 'ERROR'와 시간 문자열로 로그를 좁힌다. 시간대를 기록하고 재시작 전 상태를 남긴다.

044. 직접 해보기실습 A — 파일·환경·권한 · 실습 B — 프로세스·소켓·용량 · 실습 C — 로그·패키지·컨테이너 · 실습 D — SSH와 Spring Boot systemd 서비스6개 코드 · 열기 ↓

아래 실습은 Linux VM이나 개발 컨테이너에서 한다. 운영 서비스는 중지·삭제하지 않는다. systemd 관리자 권한이 없으면 unit 실습 대신 로컬 프로세스를 관찰한다.

01실습 A — 파일·환경·권한↘
pwd
cat /etc/os-release
printf 'JAVA_HOME=%s\n' "$JAVA_HOME"
command -v java
printf 'error\n' > /tmp/d12-a
printf 'warning\n' >> /tmp/d12-a
cp /tmp/d12-a /tmp/d12-copy
mv /tmp/d12-copy /tmp/d12-renamed
grep -nE 'error|warning' /tmp/d12-a
find /tmp -maxdepth 1 -name 'd12-*' -ls
rm -i /tmp/d12-renamed

>는 덮어쓰고 >>는 추가한다. 짧은 파일은 cat, 긴 파일은 less. 삭제 전 경로를 확인한다. export는 변수를 자식에 전달하고 PATH와 JAVA_HOME은 역할이 다르다.

02실습 B — 프로세스·소켓·용량↘
chmod 640 /tmp/d12-a
ls -l /tmp/d12-a
sleep 300 &
pid=$!
ps -p "$pid" -o pid,ppid,stat,cmd
top
kill -TERM "$pid"
ss -lntp
lsof -i :8080
df -h
du -sh /tmp
free -h

htop은 선택 도구다. SIGTERM 뒤 ps로 확인한다. netstat도 가능하지만 ss를 우선 쓴다. curl은 HTTP, nc는 TCP, ping은 ICMP를 확인한다.

03실습 C — 로그·패키지·컨테이너↘
journalctl -b -n 30 --no-pager
journalctl -u orders -b -p warning --since "1 hour ago" --no-pager
grep -n 'ERROR' app.log
tail -f app.log
docker logs --tail 100 --follow api
docker exec -it api sh

tail -f는 Ctrl-C로 끝낸다. journal과 파일 로그는 별개다. Debian/Ubuntu는 apt, RHEL 계열은 dnf를 쓰며 yum은 호환 명령일 수 있다. 컨테이너에는 쉘·진단 도구가 없거나 내부 변경이 재생성 후 사라질 수 있다.

04실습 D — SSH와 Spring Boot systemd 서비스↘

SSH 키를 받은 후 형식에 맞춰 접속하고, 전송 전에는 rsync --dry-run으로 대상을 확인한다.

ssh -i ~/.ssh/id_ed25519 deploy@example-host
scp build/libs/app.jar deploy@example-host:/tmp/app.jar
rsync -av --dry-run build/libs/ deploy@example-host:/tmp/build-libs/

사전 조건은 Boot 4.1.x / Java 25 / Gradle 빌드로 만든 실행 jar와 서버 Java 런타임이다. 프로젝트에서는 보통 ./gradlew bootJar로 jar를 만든다. 관리자에게 전용 사용자 orders와 /opt/orders를 준비하도록 하고, jar를 해당 계정이 읽을 수 있게 배치한다. 아래 unit은 서버 경로에 맞게 수정한다.

/etc/systemd/system/orders.service:

[Unit]
Description=Orders Spring Boot application
After=network.target

[Service]
Type=exec
User=orders
Group=orders
WorkingDirectory=/opt/orders
EnvironmentFile=-/etc/orders/orders.env
ExecStart=/usr/lib/jvm/java-25-openjdk/bin/java -jar /opt/orders/app.jar
Restart=on-failure
RestartSec=5
SuccessExitStatus=143
TimeoutStopSec=45

[Install]
WantedBy=multi-user.target

Java 경로는 배포판에 따라 다르므로 readlink -f "$(command -v java)"로 확인해 ExecStart를 바꾼다. 환경 파일은 KEY=value 형식으로 제한하며 쉘 명령을 실행하는 파일로 취급하지 않는다. unit 편집 후 정의를 읽고 기동 상태·로그·포트를 확인한다.

sudo systemctl daemon-reload
sudo systemctl start orders.service
sudo systemctl status orders.service --no-pager
sudo journalctl -u orders.service -b -n 100 --no-pager
sudo systemctl enable orders.service
ss -lntp
curl -i http://127.0.0.1:8080/

부팅 자동 등록과 즉시 시작은 sudo systemctl enable --now orders.service다. unit 변경은 daemon-reload 후 restart해야 프로세스에 반영된다. graceful shutdown이 필요하면 Spring 설정과 TimeoutStopSec를 맞춘다. 이 systemd 예제는 권한이 필요한 환경이라 미실행이다.

055. 자주 하는 오해와 실수열기 ↓
  1. 프롬프트가 $면 일반 사용자다 → 꾸밀 수 있는 표시일 뿐이다. id, hostname, pwd로 확인한다.
  2. chmod 777이면 해결이다 → 모두에게 쓰기를 열어 위험하다. 소유자·그룹을 확인해 최소 권한만 준다.
  3. kill을 실행하면 끝났다 → 기본은 정리 가능한 SIGTERM 요청이다. ps로 종료를 확인하고 SIGKILL은 마지막에 쓴다.
  4. systemctl start 성공이면 API가 응답한다 → 프로세스 시작과 포트·HTTP 준비는 별개다. 상태, 소켓, 로컬 curl 순으로 본다.
  5. ping이 되면 TCP 포트도 열린 것이다 → ping은 ICMP다. nc -vz나 HTTP 요청으로 목표 포트를 확인한다.
  6. 모든 로그는 /var/log 텍스트 파일이다 → systemd journal에만 있을 수 있다. journalctl -u 서비스명도 확인한다.
  7. df와 du가 다르면 오류다 → 파일시스템과 디렉터리라는 측정 범위가 다르다. 열린 채 삭제된 파일도 확인한다.
  8. SSH 접속 또는 컨테이너 쉘 진입이 곧 배포 성공이다 → 실행 계정·unit·포트·HTTP를 따로 확인하고 컨테이너 상태와 호스트 상태를 구분한다.

077. 자가점검 Q&A (면접 대비)열기 ↓
Q1. 터미널과 쉘은 어떻게 다른가?


터미널은 문자 입출력 창이고 쉘은 입력을 해석해 명령을 실행한다.
한 터미널에서 여러 쉘을 사용할 수 있다.
따라서 프롬프트만 보고 원격인지 로컬인지 단정하지 않는다.
꼬리질문: cd가 builtin인 이유는? 현재 쉘의 경로를 바꿔야 하므로 자식 프로그램으로는 충분하지 않다.

Q2. >와 |의 차이는?


>는 출력을 파일에 연결하고 |는 앞 명령의 stdout을 뒤 명령의 stdin으로 보낸다.
stderr는 자동으로 파이프에 합쳐지지 않는다.

로그를 볼 때 두 스트림이 어디로 연결되는지 확인한다.
꼬리질문: 2>&1은? stderr를 stdout의 현재 대상으로 연결하며 순서에 따라 결과가 달라진다.

Q3. chmod 640과 디렉터리 x의 의미는?


소유자는 rw, 그룹은 r, 기타는 권한이 없다.
디렉터리 x는 경로를 통과하는 권한이다.
필요한 사용자에게만 읽기·쓰기·탐색 권한을 연다.
꼬리질문: 로그 접근 실패 시 첫 조치는? ls -l과 id로 소유권과 서비스 계정을 대조한다.

Q4. SIGTERM과 SIGKILL은?


TERM은 정리할 기회를 주는 종료 요청이다.
KILL은 처리할 수 없는 강제 종료라 마지막 수단이다.
서비스 관리자는 종료 결과를 확인한 뒤 재시작할 수 있다.
꼬리질문: TERM이 보낸 뒤 무엇을 하나? ps나 systemctl status로 종료 여부를 관찰한다.

Q5. daemon-reload, restart, enable은?


앞은 unit 정의 재읽기, restart는 프로세스 재시작, enable은 부팅 자동 시작 등록이다.
각 동작은 서로 대체하지 않는다.

설정 재읽기와 실제 프로세스 반영 단계를 구분한다.
꼬리질문: 지금 시작하면서 자동 등록하려면? systemctl enable --now orders.service를 쓴다.

Q6. 프로세스가 있는데 요청이 실패하면?


ss -lntp로 리스닝을 확인하고 서버 안에서 curl을 해 본다.
로컬 응답과 외부 응답 차이로 앱과 외부 경로를 나눈다.
리스닝 소켓 하나만으로 전체 요청 경로를 증명할 수 없다.
꼬리질문: ping은 포트를 확인하나? 아니다. ICMP만 확인하므로 nc나 HTTP 요청이 필요하다.

Q7. df와 du가 다르면?


df는 파일시스템 공간, du는 선택한 디렉터리 점유량을 나타낸다.
열린 채 삭제된 파일이나 다른 마운트가 차이를 만들 수 있다.
따라서 삭제 직후 파일시스템 여유가 늘지 않을 수 있다.
꼬리질문: 로그 삭제 후 공간이 그대로면? df로 포화 마운트를 찾고 열린 파일과 journal을 조사한다.

Q8. SSH 성공은 서비스 정상의 증거인가?


SSH는 원격 계정 인증과 세션만 확인한다. 앱의 권한·unit·포트·HTTP는 별도 점검한다.
접속 계층과 애플리케이션 계층을 따로 진단한다.
꼬리질문: unit이 즉시 failed면? systemctl status와 journalctl -u orders -b에서 실행 경로와 오류를 본다.
