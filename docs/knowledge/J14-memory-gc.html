J14. 메모리 구조와 GC

#J14. 메모리 구조와 GC

Java 메모리는 JVM 명세의 실행 영역과 HotSpot의 실제 메모리 배치가 다르다. GC는 도달 가능한 객체를 보존하며, collector별로 처리량·지연시간·CPU와 메모리 사용의 균형이 다르다. 운영 기본값은 G1과 GC 로그이며, 먼저 로그에서 할당·회수·생존량을 읽고 병목에 맞춰 collector를 바꾼다.

011. 왜 알아야 하나열기 ↓

-Xmx를 크게 했는데도 프로세스가 컨테이너 메모리 제한을 넘거나, OutOfMemoryError: Direct buffer memory가 나는 사례가 있다. 이때 힙만 보면 원인을 놓친다.

클래스 메타데이터, JIT 코드, 스레드 스택, direct buffer payload도 프로세스 메모리를 쓴다. 반대로 GC overhead limit exceeded나 잦은 Full GC에서 무조건 -Xmx를 올리면, 객체를 계속 붙잡는 캐시·리스너 누수는 그대로 둔 채 장애 시점만 늦출 수 있다.

GC 로그의 before -> after를 보면 단기 할당과 장기 생존 객체 증가를 구분할 수 있다. G1의 pause target은 보증이 아니며, ZGC·Shenandoah도 CPU와 메모리 여유가 부족하면 할당이 정체되거나 처리량이 떨어진다.

022. 핵심 개념용어 정리 · 헷갈리는 메모리 쌍 · 객체 레이아웃과 compact object headers · 세대별 가설열기 ↓

JVM stack 스레드별 메서드 프레임, 지역 변수 슬롯과 operand stack 참조는 프레임에, 참조 대상은 보통 힙에 있다.
Method area 클래스별 런타임 구조와 런타임 상수 풀을 위한 추상 공유 영역 물리 배치와 GC 방식은 명세하지 않는다.
Metaspace HotSpot의 클래스 메타데이터용 native 메모리 PermGen과 다르며 힙 밖에서도 OS 메모리를 쓴다.

Direct memory direct buffer 내용 등 힙 밖에 둘 수 있는 데이터 ByteBuffer wrapper까지 힙 밖이라는 뜻은 아니다.
GC root 스레드 상태·정적 참조·JNI 핸들 등 도달성 탐색의 출발점 루트에서 도달 가능한 객체는 보존한다.
Young / Old 세대형 collector가 최근 할당과 장기 생존 객체를 나누는 논리 영역 collector마다 세대 구조가 같지는 않다.
Region G1 힙의 동일 크기 단위. Eden·Survivor·Old·Humongous 역할을 맡는다. 고정 주소의 세대 경계와 다르다.
Remembered set 다른 region에서 특정 region으로 들어오는 참조 기록 전체 힙을 매번 훑지 않도록 돕는다.
Stop-the-world (STW) 애플리케이션 스레드를 멈추는 작업 구간 concurrent GC도 일부 STW 단계가 있다.

JVM 명세는 heap·stack·method area의 동작 계약을 정하지만 물리 배치, 객체 헤더 크기, GC 알고리즘은 고정하지 않는다.[1]

02헷갈리는 메모리 쌍↘
구분 한쪽 다른 쪽
명세 vs 구현 method area는 추상 영역 Metaspace는 HotSpot 구현이며 Java 8에 PermGen이 제거됐다.[2]
힙 vs 프로세스 Java heap은 객체 회수 대상 RSS에는 Metaspace, code cache, stack, direct/native 영역도 포함
스택 참조 vs 객체 참조 값은 프레임에 놓일 수 있음 그 대상 객체는 보통 힙에서 관리
heap vs direct buffer allocate()는 heap buffer allocateDirect()는 내용이 힙 밖일 수 있어 native I/O 복사를 줄인다. 비용도 다르다.[3]
GC 회수 vs 자원 해제 도달 불가능 객체는 회수 후보 GC가 파일·소켓 등 외부 자원을 즉시 닫지는 않는다.
03객체 레이아웃과 compact object headers↘

HotSpot 객체는 헤더·필드·정렬 padding으로 구성되고 배열에는 길이 정보도 필요하다. 헤더는 동기화 상태와 클래스 식별 등 런타임 정보를 연결한다. 참조 압축, 필드 배치, 빌드와 옵션에 따라 크기는 달라지며 Java 규격은 이를 정의하지 않는다.

JEP 519는 compact object headers를 JDK 25에서 실험 기능에서 제품 기능으로 승격했다. JDK 24에는 -XX:+UnlockExperimentalVMOptions -XX:+UseCompactObjectHeaders가 필요했지만, JDK 25에서는 -XX:+UseCompactObjectHeaders로 켤 수 있다. 기본 레이아웃 변경은 아니므로 서비스에서 힙과 처리량을 측정한다.[4]

04세대별 가설↘

대부분 객체는 생성 후 오래 살지 않는다는 가설을 활용한다. young 영역을 자주 모으고, 생존 객체는 승격(promote)한다. Old에서 young을 가리키는 참조는 remembered set/card table로 기록해 young 수집 때 누락하지 않는다.

이는 가정이지 보장이 아니다. 캐시·세션·큐의 생존 객체가 많으면 old 회수 비용이 커진다. 세대형 ZGC와 Shenandoah도 세대를 나누지만 정책과 barrier는 각 collector가 구현한다.

033. 내부 동작·원리JVM 메모리의 큰 그림 · GC가 객체를 살려 두거나 회수하는 과정 · G1: region 단위 수집과 pause 목표 · ZGC와 Shenandoah: 낮은 지연시간을 위한 동시 작업4개 코드 · 열기 ↓
01JVM 메모리의 큰 그림↘
프로세스 주소 공간 (JVM 명세의 영역 + HotSpot 구현 영역)
├─ Java heap (공유) ─ 객체/배열, GC 수집 대상
│  └─ G1이면 region들로 구성; 세대형 ZGC/Shenandoah는 자체 세대 관리
├─ Metaspace (HotSpot native) ─ 클래스 메타데이터
├─ Code cache (HotSpot native) ─ JIT 컴파일 코드
├─ Direct/native memory ─ direct buffer 내용, JNI·라이브러리 할당 등
└─ 각 Java 스레드
   ├─ JVM stack ─ 메서드 호출별 frame / local variables / operand stack
   ├─ pc register
   └─ 필요 시 native method stack

JVMS에서 heap과 method area는 공유 영역이고 pc register·JVM stack·native method stack은 스레드별이다. 메서드 호출마다 frame이 생기며 지역 변수와 operand stack을 가진다.[1] JEP 122에서 HotSpot은 PermGen을 없애며 클래스 메타데이터를 native로, interned String과 static 변수를 heap으로 이동했다.[2]

02GC가 객체를 살려 두거나 회수하는 과정↘
  1. 할당: 공간을 확보한다. 흔한 빠른 경로는 스레드별 버퍼에서 포인터를 전진시키는 방식이며, 부족하면 수집을 유발한다.
  2. 도달성 추적: 구현이 정한 루트(스레드 상태, 정적·JNI 참조 등)에서 따라갈 수 있는 객체를 보존한다. 나머지는 회수 후보가 된다.
  3. 이동·갱신: 복사형 수집기는 생존 객체를 옮기고 참조를 갱신한다. Concurrent 수집기는 barrier로 애플리케이션 동시 접근을 추적한다.
  4. 외부 자원: 객체 회수가 native buffer·소켓을 즉시 닫지는 않는다. 명시적 close와 라이브러리 수명 관리를 우선한다.
03G1: region 단위 수집과 pause 목표↘

G1은 region 기반 mostly concurrent collector이며 Java 25 대부분의 하드웨어·OS 조합에서 기본이다.[5][6] Young/old는 고정 주소 범위가 아니라 region 역할이다. 큰 객체는 Humongous region을 차지할 수 있고, remembered set은 다른 region에서 들어오는 참조를 찾는다.

Young-only 수집 반복
  Eden region 할당 → STW young GC → 생존 객체를 Survivor/Old로 복사
        │ old 점유·정책 임계치 도달
        ▼
Concurrent marking 시작 → 애플리케이션과 동시 추적
        ▼
Remark / Cleanup 등 짧은 STW 단계로 추적 결과 확정
        ▼
Mixed GC: young + 회수 가치가 높은 일부 old region을 collection set에 포함
        └─ 회수 가치와 예상 작업량을 보고 다음 mixed 수집 집합을 선택

G1은 목표 pause에 맞춰 collection set을 조절하지만 초과하거나 evacuation 실패로 Full GC에 빠질 수 있다. -XX:MaxGCPauseMillis는 절대 상한/SLA가 아니다. 낮춘 목표는 수집 빈도를 늘리고 처리량을 희생할 수 있다. Mixed는 일부 회수 가치가 높은 old region을 젊은 영역과 함께 수집한다. pause, old 회수량, 직후 점유율, allocation rate를 같이 본다.[6]

04ZGC와 Shenandoah: 낮은 지연시간을 위한 동시 작업↘

ZGC는 대부분의 비용 큰 작업을 앱과 동시 수행한다. Oracle Java 25 가이드는 앱 스레드 정지 1ms 미만을 설계 목표로 들지만 SLA 보증은 아니다. 동시 작업도 CPU와 bandwidth를 쓰므로 live set 위에 headroom이 필요하다.[7]

Generational ZGC는 JDK 21에 도입됐고 young 수집으로 allocation stall과 GC overhead를 낮추려 한다.[8] JDK 23에서 기본이 됐으며 JDK 24에 non-generational 모드와 ZGenerational 옵션이 제거됐다. Java 25는 -XX:+UseZGC만으로 세대형을 사용한다.[7][9]

Shenandoah도 동시 작업으로 pause를 줄인다. JEP 521은 JDK 25에 generational 모드를 product feature로 포함했지만 기본은 single-generation이다. 지원 빌드에서 -XX:ShenandoahGCMode=generational로 선택한다.[10]

05Serial과 Parallel↘

Serial은 단일 GC 스레드와 낮은 동기화 비용으로 작은 데이터셋에 적합할 수 있다. Parallel은 여러 GC 스레드로 처리량을 우선하며 STW pause를 감수한다. G1은 pause 목표와 처리량 사이 균형을 노린다.[5]

06GC 로그 읽기↘

JDK 9에서 통합 JVM 로깅이 도입되고 GC 로그도 통합됐다.[11][12] -Xlog:gc는 gc info 로그를, -Xlog:gc*는 더 상세한 로그를 선택한다. 상세 로그에는 파일 회전을 설정한다.

[0.101s][info][gc] GC(0) Pause Young (Allocation Failure) 5M->2M(15M) 1.596ms
[0.187s][info][gc] GC(7) Pause Full (Allocation Failure) 12M->6M(15M) 4.065ms

숫자는 uptime, GC(n)은 이벤트, Young/Full은 종류다. 5M->2M(15M)은 수집 전→후 사용량(용량), 마지막은 pause다. Allocation Failure는 할당 공간 부족으로 수집을 시작한 원인이지 Java 예외가 아니다. 수집 후에도 사용량이 높거나 계속 증가하면 live set·누수·한도를 조사한다. 형식과 수치는 collector/JDK마다 다를 수 있다.

대표 운영 옵션은 다음과 같다.

-Xlog:gc*:file=/var/log/myapp/gc.log:time,uptime,level,tags:filecount=5,filesize=20M

gc*는 상세도를 높인다. 파일 크기·개수는 디스크 예산에 맞추고, 필요 구간에서 태그/레벨을 추가한다. 레거시 PrintGCDetails 대신 unified logging 문법을 사용한다.[11][12]

044. 코드로 확인예제 1: heap buffer와 direct buffer 구분 · 예제 2: 작은 힙에서 allocation GC 로그 관찰5개 코드 · 열기 ↓
01예제 1: heap buffer와 direct buffer 구분↘

ByteBuffer.allocateDirect의 내용은 일반 GC 힙 밖에 놓일 수 있다. wrapper와 데이터의 위치를 혼동하지 말고 isDirect()로 어떤 버퍼를 만든 것인지 확인한다.[3]

import java.nio.ByteBuffer;

public class DirectBufferDemo {
    public static void main(String[] args) {
        ByteBuffer heap = ByteBuffer.allocate(16);
        ByteBuffer direct = ByteBuffer.allocateDirect(16);
        System.out.printf("heap: direct=%s capacity=%d%n", heap.isDirect(), heap.capacity());
        System.out.printf("direct: direct=%s capacity=%d%n", direct.isDirect(), direct.capacity());
    }
}

JDK 21에서 실행한 실제 출력:

heap: direct=false capacity=16
direct: direct=true capacity=16
02예제 2: 작은 힙에서 allocation GC 로그 관찰↘

매 반복마다 256 KiB 배열을 할당하고 12개만 계속 참조한다. 대부분은 다음 young 수집에서 회수 후보가 되며 일부는 참조가 남는다. 테스트용으로 Serial GC와 16 MiB 힙을 고정해 이벤트를 보기 쉽게 했다. 운영 설정 권장값이 아니다.

public class GcLogDemo {
    public static void main(String[] args) {
        byte[][] survivors = new byte[12][];
        long checksum = 0;
        for (int i = 0; i < 400; i++) {
            byte[] block = new byte[256 * 1024];
            block[0] = (byte) i;
            survivors[i % survivors.length] = block;
            checksum += block[0] & 0xff;
        }
        System.out.printf("rounds=400 liveSlots=%d checksum=%d%n", survivors.length, checksum);
    }
}

다음 명령으로 실행했다. stdout 결과와 GC 파일을 나눠 로그가 프로그램 출력 중간에 섞이지 않게 했다.

java \
  -Xms16m -Xmx16m -XX:+UseSerialGC \
  -Xlog:gc=info:file=_scratch/J14/gc.log _scratch/J14/GcLogDemo.java

JDK 21의 실제 프로그램 출력 및 실제 GC 로그 앞부분:

rounds=400 liveSlots=12 checksum=42936
[0.003s][info][gc] Using Serial
[0.101s][info][gc] GC(0) Pause Young (Allocation Failure) 5M->2M(15M) 1.596ms
[0.145s][info][gc] GC(1) Pause Young (Allocation Failure) 6M->3M(15M) 2.011ms
[0.165s][info][gc] GC(2) Pause Young (Allocation Failure) 8M->4M(15M) 1.459ms

관측한 전체 로그 파일은 43줄이었다. 실제 시간·용량·이벤트 수는 JDK 배포판과 실행 환경에서 달라질 수 있다. 명령행의 -Xlog:gc/-Xlog:gc=info가 legacy PrintGC와 유사한 info 수준 GC 메시지를 출력한다.[12]

055. 버전별 변화 — 왜 바뀌었나열기 ↓
버전 변화 이전 방식의 한계와 변화 이유
Java 8 HotSpot PermGen 제거, 클래스 메타데이터를 native 메모리로 이동(JEP 122) PermGen 크기를 미리 튜닝해야 했고 HotSpot/JRockit 간 사용 경험이 달라 이를 단순화하려 했다. static 변수·interned String은 heap으로 옮겨졌다.[2]
Java 9 통합 JVM 로깅 도입(JEP 158), GC 로그를 통합 체계로 재구현(JEP 271) 컴포넌트별 로그 옵션과 형식이 흩어져 있어 태그·레벨·출력 대상을 공통 옵션으로 선택하도록 바꿨다.[11][12]
Java 21 Generational ZGC 도입(JEP 439) 비세대형 ZGC는 젊고 짧게 사는 객체를 별도로 자주 모으지 못했다. young/old를 나눠 단기 객체 수집 비용과 할당 stall 위험을 낮추려 했다.[8]
Java 23 ZGC의 기본 모드를 generational로 변경(JEP 474) 두 모드를 모두 유지하면 개발/유지 비용이 늘고 세대형이 대다수 사용 사례에 더 적합하다는 판단으로 기본 선택을 바꿨다.[9]
Java 24 non-generational ZGC 및 ZGenerational 옵션 제거. Compact Object Headers는 실험 기능으로 도입(JEP 450) 두 ZGC 모드를 계속 지원할 필요를 줄이고, 객체 헤더 개선은 안정성을 검증하기 위해 먼저 실험 기능으로 배포했다. ZGC 변경은 Java 25 가이드에서 확인할 수 있다.[7]
Java 25 Compact Object Headers를 product feature로 승격(JEP 519). Generational Shenandoah도 product feature로 승격(JEP 521) JDK 24 이후 테스트·안정성 검증을 거친 기능에서 실험 플래그 요구를 없앴다. Shenandoah의 기본 모드는 여전히 single-generation이다.[4][10]

Java 25는 이 자료의 기준 버전이다. Java 25에서 G1은 대부분의 하드웨어·OS 조합의 기본이고, ZGC는 generational 모드가 기본이다.[6][7]

066. 실무 가이드열기 ↓

기본값 추천: 별도 근거가 없는 Spring/Java 서버는 JVM 기본 collector인 G1로 시작하고, 시작 때부터 회전 가능한 -Xlog:gc 로그를 남겨라. 낮은 tail latency가 무조건 필요한 게 아니라면 먼저 G1의 allocation rate, pause 분포, GC 후 생존량으로 병목을 분리한다. G1은 Java 25 대부분의 환경에서 기본 collector이고 기본 튜닝을 거의 요구하지 않도록 설계됐다.[5][6]

  • if 서비스의 목표가 일반적인 API 응답시간과 처리량 균형이면 then G1을 유지한다. pause goal은 수집 집합 크기 조정 힌트로 사용하고, 목표값만 낮춰 latency를 보장하려 하지 않는다.
  • if batch 처리량이 pause보다 중요하면 then Parallel GC를 후보로 삼는다. STW pause와 CPU 점유를 받아들인다.[5]
  • if 힙/CPU가 작고 긴 pause가 허용되면 then Serial GC도 측정한다.[5]
  • if p99/p999 pause가 핵심 SLO인데 G1이 목표를 반복해서 넘으면 then ZGC와 지원되는 Shenandoah를 같은 부하로 비교하고 CPU·allocation stall·headroom을 측정한다.[7][10]
  • if ZGC를 선택하면 then Java 25에서는 -XX:+UseZGC로 시작한다. 세대형이 기본이며 live set과 수집 중 할당을 위한 여유가 필요하다.[7][9]
  • if Shenandoah의 세대형 모드가 필요하면 then JDK 빌드에서 지원되는지 확인하고 -XX:+UseShenandoahGC -XX:ShenandoahGCMode=generational을 시험한다. Java 25에서 이 모드는 product 기능이지만 기본은 아니다.[10]
  • if GC 직후 힙 점유가 계속 커지면 then 힙 증설 전 cache, queue, listener, ThreadLocal, classloader의 생존 경로를 찾는다.
  • if OutOfMemoryError가 heap 메시지가 아니면 then 그 영역에 맞는 OS/JVM 지표를 함께 본다. -Xmx만 올려 Metaspace·direct memory·스레드 스택 문제를 해결하려 들지 않는다.[1][3][13]
  • if 처음 GC 로그를 켜면 then -Xlog:gc로 시작하고 필요할 때만 gc*로 넓혀 file rotation을 둔다.[11][12]

컨테이너 메모리 플래그(MaxRAMPercentage)는 J16 참조. 프로파일링 도구는 J15 참조.

077. 함정·안티패턴열기 ↓
  1. 힙만 보고 한도를 올림 — 컨테이너 OOM-kill → native 메모리를 놓침 → RSS, heap, Metaspace, direct buffer, 스레드 수를 함께 본다.
  2. GC 로그 최대치만 비교 — 회수 후 생존 추세를 놓침 → before -> after, pause, 간격, 직후 점유율을 읽는다.
  3. System.gc()로 운영 문제 해결 — 참조 중 객체는 회수 못하고 Full GC 비용을 낼 수 있음 → 생존 경로와 자원 수명을 해결한다.
  4. G1 pause target을 상한으로 취급 — 최악값 보장이 아님 → p99/p999와 초과 원인을 관측한다.
  5. 생존량이 높은데 collector만 교체 — 큰 live set은 회수 불가 → heap dump/할당 프로파일링으로 보존 경로를 찾는다(J15 참조).
  6. direct buffer를 힙으로 계산 — 힙 여유에도 native OOM → direct buffer와 라이브러리 pool을 별도 관측하고 자원 수명을 관리한다.[3]
  7. Metaspace를 PermGen처럼 취급 — PermSize 계열 조정은 무효 → classloader 누수·재배포·동적 프록시 증가를 본다.[2]
  8. 스택 문제를 힙 OOM으로 오진 — 깊은 재귀는 StackOverflowError, 스레드 폭증은 native thread 실패 가능 → 오류와 thread 수, OS 한도를 분류한다.[1][13]
  9. GC 로그를 무제한 상세도로 켬 — I/O·디스크 고갈 → 필요한 태그만 켜고 회전 크기를 제한한다.[11][12]
  10. compact header를 켜고 객체 크기를 단정 — 크기는 VM/옵션에 종속 → 기본 변경이 아님을 기록하고 배포 조합을 계측한다.[4]
088. 자가점검 Q&A (면접 대비)Q1. JVMS의 method area와 HotSpot Metaspace는 같은 개념인가? · Q2. 힙이 충분한데 OOM이 발생할 수 있는가? · Q3. Young GC 뒤 사용량이 다시 높은 값으로 올라오면 무엇을 의심하는가? · Q4. G1의 mixed GC는 Full GC와 어떻게 다른가?열기 ↓
01Q1. JVMS의 method area와 HotSpot Metaspace는 같은 개념인가?↘

답: 아니다. method area는 클래스 구조와 런타임 상수 풀을 위한 추상 영역이다. Metaspace는 HotSpot의 native 클래스 메타데이터 구현이다. 명세는 물리 배치나 GC 방식을 강제하지 않는다.[1][2]

꼬리질문: static 필드는 모두 Metaspace에 있는가? 답: 아니다. static 변수와 interned String은 heap으로, 클래스 메타데이터는 native로 이동했다.[2]

02Q2. 힙이 충분한데 OOM이 발생할 수 있는가?↘

답: 가능하다. direct buffer·Metaspace·스레드 스택·code cache·JNI 할당은 -Xmx와 별도다. 프로세스 한도는 이 영역을 모두 포함한다. 오류 메시지와 heap 외 지표를 확인한다.[1][3][13]

꼬리질문: direct buffer에는 Java 객체가 없는가? 답: wrapper 객체는 있고, 내용이 힙 밖에 놓일 수 있다.[3]

03Q3. Young GC 뒤 사용량이 다시 높은 값으로 올라오면 무엇을 의심하는가?↘

답: 생존 객체와 순간 할당률을 구분하고, old 점유율이 계속 오르면 cache·queue·세션의 보존 경로를 찾는다. 로그 한 줄만으로 누수를 단정하지 않는다.

꼬리질문: 왜 객체를 지우지 않는가? 답: GC root에서 참조 경로가 남아 있어 접근 가능하기 때문이다.

04Q4. G1의 mixed GC는 Full GC와 어떻게 다른가?↘

답: Mixed는 young과 일부 old region을 수집하고 전체 old를 한 번에 처리하지 않는다. Full GC는 공간 압박이나 evacuation 실패 뒤 전체 힙을 처리할 수 있다. 발생 여부와 생존량을 함께 본다.[6]

꼬리질문: remembered set은 왜 필요한가? 답: 대상 region 외부 참조를 찾으려고 전체 힙을 재검색하지 않도록 한다.[6]

05Q5. Generational ZGC는 언제 도입됐고 Java 25에서 어떻게 켜는가?↘

답: JDK 21에 도입됐고 JDK 23에서 기본이 됐다. Java 24에 non-generational 모드와 ZGenerational이 제거됐다. Java 25에서는 -XX:+UseZGC를 쓴다.[7][8][9]

꼬리질문: ZGC 힙을 작게 줘도 되는가? 답: live set과 수집 중 할당 여유가 필요하고 동시 수집은 CPU를 쓴다.[7]

06Q6. G1의 MaxGCPauseMillis를 10ms로 지정하면 pause가 10ms를 넘지 않는가?↘

답: 아니다. pause goal은 수집 집합 조정 목표라 초과할 수 있다. 낮추면 수집 빈도나 처리량이 불리해질 수 있으므로 부하에서 검증한다.[6]

꼬리질문: 왜 지정하는가? 답: 처리량과 pause 균형에서 수집 집합 조정에 운영 의도를 반영한다.

07Q7. Java 25의 Shenandoah generational mode가 기본인가?↘

답: 아니다. JEP 521은 세대형을 product로 승격했지만 기본은 single-generation이다. 지원 여부를 확인하고 ShenandoahGCMode=generational을 지정한다.[10]

꼬리질문: product feature란 무슨 뜻인가? 답: experimental unlock 없이 쓸 수 있지만 collector 빌드 지원은 확인해야 한다.[10]

08Q8. -Xlog:gc와 -Xlog:gc* 중 무엇으로 시작하는가?↘

답: -Xlog:gc로 이벤트와 pause를 보고 필요할 때 gc*로 넓힌다. 파일 회전과 보존량을 설정한다. JDK 9 이후 unified logging 문법은 -Xlog다.[11][12]

꼬리질문: Allocation Failure는 Java OutOfMemoryError인가? 답: 아니다. 수집을 시작한 원인이고 회수 후 정상 실행할 수 있다.
