레거시 테스트는 기존 동작을 먼저 기록해 안전한 변경 경계를 만든다. 버그 수정은 수정 코드보다 재현 테스트를 먼저 작성해 실패를 확인한다. CI는 테스트 결과와 실패 보고서를 남기고, 커버리지는 품질 점수가 아니라 빠진 경로를 찾는 지도다.

#1. 한 줄로 말하면

레거시에 테스트를 붙인다는 것은 명세가 충분하지 않은 코드의 현재 관찰 가능한 동작을 테스트로 고정하고, 그 보호막 안에서 요구된 변경을 진행하는 일이다. 버그 수정은 고장 조건을 입력으로 만든 테스트가 먼저 실패하는 것을 확인한 뒤 코드를 고쳐 같은 테스트를 통과시키는 순서로 한다. CI와 커버리지는 이 피드백을 팀 전체가 반복 가능하게 만드는 장치다.

#2. 당장 알아야 할 것

  1. 명세가 없으면 현재 동작을 기록한다. 특성 테스트와 골든 마스터는 레거시 동작을 드러내는 도구다. 기록된 동작이 요구사항이라는 뜻은 아니며, 날짜·UUID 같은 값은 정규화하고 결과 변경은 사람이 검토한다.
  2. 버그는 수정 전에 재현한다. 최소 입력과 사전조건으로 외부에서 관찰 가능한 오류를 단언한다. 먼저 테스트가 실패해야 재현이 성립하고, 수정 후 같은 테스트가 통과해야 회귀 방지 장치가 된다.
  3. 테스트 seam은 외부 효과 경계에 둔다. 결제·시계·파일·전역 상태를 작은 어댑터로 분리해 대체 가능하게 한다. 테스트를 위해 전 계층을 추상화하지 않는다.
  4. 가장 좁은 신뢰 가능한 범위를 고른다. 계산은 단위 테스트, HTTP 계약은 MVC 슬라이스, 쿼리는 실제 DB 테스트, 전체 연결은 통합 테스트로 검증한다.
  5. 결과를 단언한다. 테스트 이름과 기대값에서 실패 조건이 보여야 한다. 내부 호출 검증은 외부 호출 횟수 자체가 계약일 때만 둔다.
  6. 느림과 flaky는 원인을 고친다. 공유 데이터·시간·비동기 대기·외부 서비스·자원 정리를 점검한다. 재실행은 진단용이며 상시 재시도는 실패 신호를 숨긴다.
  7. CI는 실패 산출물을 보관한다. Gradle HTML/XML 테스트 보고서를 실패 시에도 artifact로 남긴다. Testcontainers를 쓰면 runner의 Docker 가용성을 확인한다.
  8. 커버리지 숫자는 누락 경로를 찾는 데 쓴다. JaCoCo는 바이트코드 명령과 분기를 세지만 assertion의 타당성을 측정하지 않는다. 전체 레거시에 임의의 문턱을 걸기보다 기준선을 기록하고 변경 코드의 위험 경로를 늘린다. 테스트 fixture 중복은 공통 기본값만 정리하고 시나리오 의미를 숨기지 않는다.

예제 기준은 Spring Boot 4.1.1이 관리하는 JUnit Jupiter 6.0.3이다. starter-test를 사용해 버전을 별도로 고정하지 않는다. 기본 추천은 작은 단위 테스트를 기본으로 두고, 변경 위험이 DB·HTTP 경계에 걸칠 때 해당 슬라이스나 통합 테스트를 추가하는 것이다.

#3. 따라 하기

아래 단계는 연습 프로젝트의 실제 구조를 기준으로 한다. Boot 4.1.1·Gradle 9.8 프로젝트이고, 현재 starter의 Java toolchain은 21로 설정되어 있다. 예제 문법은 Java 25에서도 그대로 동작한다. 로컬 기준 경로는 저장소 루트의 practice/starter다.

#1단계: 현재 동작과 테스트 경계 확인

cd practice/starter
rg --files src/main src/test

실제 파일은 ProductServiceUnitTest.java, ProductControllerTest.java, ProductRepositoryTest.java, ProductApiIntegrationTest.java, ProductMySqlIntegrationTest.java다. ProductServiceUnitTest는 Repository를 mock으로 대체하고 서비스를 직접 생성해 매핑·예외·페이징 위임을 확인한다. 리팩터링 전 현재 응답·예외·경계값을 요구사항과 대조한다.

현재 동작이 잘못됐다면 그 동작을 정답으로 고정하지 말고 의도된 결과를 회귀 테스트에 둔다. 확인 방법: rg 결과에서 계층별 테스트 파일과 대상 메서드가 있는지 확인한다.

#2단계: 버그 조건을 테스트로 먼저 재현

저장소 테스트는 실제 MySQL Testcontainers와 연습 스키마를 사용한다. ProductRepositoryTest가 이미 확인하는 핵심 회귀 조건은 삭제 시각이 있는 상품 ID 80을 조회 결과에서 제외하는 것이다. 이를 깨뜨리는 쿼리 변경이 PR에 들어왔다고 가정하고 아래 테스트부터 실행한다. 쿼리가 잘못되어 삭제 상품을 포함하면 assertion이 실패한다.

package com.example.practice.product;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.data.jpa.test.autoconfigure.DataJpaTest;
import org.springframework.boot.jdbc.test.autoconfigure.AutoConfigureTestDatabase;
import org.springframework.boot.testcontainers.service.connection.ServiceConnection;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;
import org.testcontainers.mysql.MySQLContainer;

import static org.assertj.core.api.Assertions.assertThat;

@Testcontainers
@DataJpaTest(properties = {
        "spring.sql.init.mode=always",
        "spring.sql.init.schema-locations=file:../schema/schema.sql,file:../schema/seed.sql"
})
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
class ProductRepositoryTest {
    @Container
    @ServiceConnection
    static final MySQLContainer mysql = new MySQLContainer("mysql:8.4")
            .withDatabaseName("ds_practice")
            .withUsername("practice")
            .withPassword("practice");

    @Autowired
    ProductRepository productRepository;

    @Test
    void derivedFinderExcludesSoftDeletedProduct() {
        assertThat(productRepository.findByIdAndDeletedAtIsNull(1L)).isPresent();
        assertThat(productRepository.findByIdAndDeletedAtIsNull(80L)).isEmpty();
    }

    @Test
    void derivedPageQueryUsesMysqlCount() {
        var page = productRepository.findAllByDeletedAtIsNull(
                org.springframework.data.domain.PageRequest.of(0, 10));
        assertThat(page.getContent()).hasSize(10);
        assertThat(page.getTotalElements()).isEqualTo(79);
        assertThat(page.getTotalPages()).isEqualTo(8);
    }
}

이 코드도 미실행이다. 현재 저장소에는 같은 테스트 클래스가 이미 있고, 실제 클래스는 PageRequest와 Page import를 별도로 둔다. 파일을 새로 만들 때는 중복 클래스를 만들지 말고 기존 메서드에 실패 조건을 추가한다.

Boot 4에서 DataJpaTest는 org.springframework.boot.data.jpa.test.autoconfigure 패키지다. 이 슬라이스의 기본 DB 치환 동작은 Testcontainers를 쓰는 경우 @AutoConfigureTestDatabase(replace = NONE)으로 분명히 바꾼다.

테스트를 먼저 추가하고 재현할 때 확인할 명령은 다음과 같다.

./gradlew test --tests 'com.example.practice.product.ProductRepositoryTest.derivedFinderExcludesSoftDeletedProduct'
./gradlew test --tests 'com.example.practice.product.ProductRepositoryTest'
./gradlew test

첫 명령은 좁은 회귀 케이스, 둘째는 관련 저장소 테스트, 마지막은 필수 전체 테스트다. 잘못된 쿼리 상태에서는 첫 테스트가 실패하고 수정한 뒤에는 통과하는지 확인한다. 오류 메시지에서 첫 실패 테스트와 SQL을 보고 범위를 좁힌다. schema 경로는 starter 디렉터리 기준 ../schema/이므로 다른 작업 디렉터리에서 실행하면 파일을 못 찾을 수 있다.

#3단계: HTTP 계약은 MVC 슬라이스로 고정

ProductController는 /api/products/{id} 응답을 서비스로 위임하고, GlobalExceptionHandler는 ProductNotFoundException을 404 ProblemDetail로 바꾼다. 서비스는 mock으로 대체하고 실제 MVC 변환·예외 응답을 검증한다. 아래는 현재 ProductControllerTest의 핵심 형태이며 미실행이다.

package com.example.practice.product;

import com.example.practice.common.GlobalExceptionHandler;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest;
import org.springframework.context.annotation.Import;
import org.springframework.test.context.bean.override.mockito.MockitoBean;
import org.springframework.test.web.servlet.MockMvc;

import static org.mockito.BDDMockito.given;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@WebMvcTest(ProductController.class)
@Import(GlobalExceptionHandler.class)
class ProductControllerRegressionTest {
    @Autowired
    MockMvc mockMvc;

    @MockitoBean
    ProductService productService;

    @Test
    void missingProductIsReturnedAsProblemDetail() throws Exception {
        given(productService.getById(999L))
                .willThrow(new ProductNotFoundException(999L));

        mockMvc.perform(get("/api/products/999"))
                .andExpect(status().isNotFound())
                .andExpect(jsonPath("$.title").value("Product not found"))
                .andExpect(jsonPath("$.detail").value("Product 999 was not found"));
    }
}

새 파일로 추가한다면 이름에 맞춰 클래스도 ProductControllerRegressionTest로 둔다. 현재 저장소는 같은 API 단언을 ProductControllerTest와 ProductControllerSliceTest에 이미 가지고 있다. Boot 4의 WebMvcTest와 AutoConfigureMockMvc 패키지는 org.springframework.boot.webmvc.test.autoconfigure다.

Boot 3 import를 복사하지 않는다. 확인 방법: ./gradlew test --tests 'com.example.practice.product.ProductControllerTest' 실행 후 404와 ProblemDetail 필드를 확인한다. 실제 DB까지 필요한 경우에만 @SpringBootTest와 Testcontainers를 쓴다.

#4단계: CI에서 실행하고 실패 보고서 보관

저장소 루트의 .github/workflows/test.yml에 둘 수 있는 예시다. starter의 Gradle toolchain이 현재 Java 21이므로 같은 버전으로 맞췄다. toolchain을 25로 올릴 때는 CI의 java-version도 함께 맞춘다.

name: test
on:
  pull_request:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: gradle
      - name: Run tests
        working-directory: practice/starter
        run: ./gradlew test --no-daemon
      - name: Keep test reports
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: gradle-test-reports
          if-no-files-found: ignore
          path: |
            practice/starter/build/reports/tests/test/
            practice/starter/build/test-results/test/

workflow 예시는 미실행이다. 확인 방법: PR에서 job 성공 여부를 보고 실패 시 artifact의 index.html과 TEST-*.xml을 연다. MySQL Testcontainers가 포함되므로 runner에 Docker가 동작해야 한다. 실패 결과가 없으면 로컬에서 재현되지 않는 오류를 분류하기 어렵다.

#5단계: 커버리지 보고서를 추가

Gradle Kotlin DSL의 JaCoCo 최소 설정 예시다. JaCoCo plugin은 jacocoTestReport를 만들고 기본 HTML 위치는 build/reports/jacoco/test/html이다. 보고서 생성 태스크는 테스트를 자동 선행하지 않으므로 연결을 명시한다.

plugins {
    jacoco
}

tasks.test {
    finalizedBy(tasks.jacocoTestReport)
}

tasks.jacocoTestReport {
    dependsOn(tasks.test)
    reports {
        html.required.set(true)
        xml.required.set(true)
    }
}

설정 예시는 미실행이다. 확인 방법: ./gradlew test jacocoTestReport 후 build/reports/jacoco/test/html/index.html과 XML 파일 생성 여부를 확인한다. CI 업로드 경로에도 JaCoCo HTML/XML 디렉터리를 추가한다. 전체 라인 비율보다 빠진 분기와 assertion을 살핀다.

#4. 치트시트

이름 용도 예시 주의
특성 테스트 기존 동작 기록 ProductServiceUnitTest 현재 동작이 요구사항은 아님
회귀 테스트 버그 재현 삭제 상품 ID 80 단언 수정 전에 실패 확인
단위 테스트 계산·매핑 서비스 + mock Repository 실제 SQL은 검증하지 않음
MVC 슬라이스 라우팅·JSON·상태 @WebMvcTest 서비스 대역, DB 미연결
JPA 슬라이스 매핑·쿼리 @DataJpaTest + MySQL 기본 DB 치환 확인
통합 테스트 전체 연결 @SpringBootTest + MockMvc 작은 규칙엔 과함
테스트 명령 범위별 실행 ./gradlew test --tests '패키지.클래스' CI 전체 suite도 실행
리포트 실패 분석 build/reports/tests/test/index.html CI artifact 보관
커버리지 누락 경로 찾기 ./gradlew test jacocoTestReport 정확성 점수가 아님

Maven 대응: ./mvnw test. JaCoCo는 설정된 경우 ./mvnw verify 또는 jacoco:report를 사용한다. lifecycle과 출력 경로는 플러그인 설정에 따른다.

#5. 자주 나는 에러와 해결

  1. Boot 3 테스트 패키지 import를 찾지 못함 → Boot 4에서 패키지가 이동했다. 해결: WebMvcTest·AutoConfigureMockMvc는 org.springframework.boot.webmvc.test.autoconfigure, DataJpaTest는 org.springframework.boot.data.jpa.test.autoconfigure에서 가져온다.
  2. Testcontainers가 embedded DB를 쓰거나 연결에 실패 → @DataJpaTest 기본 DB 치환 또는 Docker 문제다. 해결: @AutoConfigureTestDatabase(replace = NONE), Docker 상태와 컨테이너 로그를 확인한다.
  3. schema.sql을 못 찾음 → 상대 경로 기준이 다르다. 해결: practice/starter에서 실행하고 CI working-directory도 맞춘다.
  4. 실행마다 다른 테스트가 실패 → 공유 상태·시간·비동기·순서·자원 정리 문제다. 해결: 테스트별 초기 상태를 만들고 sleep 대신 완료 조건을 기다린다.
  5. 테스트는 초록인데 버그가 남음 → mock 상호작용만 검증하거나 결과 assertion이 없다. 해결: 사용자에게 보이는 결과를 단언하고 위험한 DB 경계는 실제 DB로 검증한다.
  6. JaCoCo 보고서가 없거나 레거시 PR이 커버리지 문턱에 막힘 → report 연결·artifact 설정이 빠졌거나 기준선을 무시했다. 해결: test 후 리포트를 생성해 실패해도 보관하고, 기존 비율을 기준선으로 관리한다.

#6. 한 단계 더

  • 특성 테스트의 관찰 결과와 합의된 요구사항을 구분하고, 회귀 테스트는 최소 입력과 외부에서 확인 가능한 결과를 고정한다.
  • mock 경계가 넓어지면 실제 쿼리·직렬화·배선 오류를 놓친다. 단위·슬라이스·통합 테스트를 위험에 맞게 섞는다.
  • Gradle 병렬 포크는 테스트 격리를 확인한 뒤 maxParallelForks를 조정한다. 공유 DB·파일·포트·컨테이너 lifecycle과 CI 자원 사용량을 확인하고, flaky quarantine에는 원인·담당자·만료일을 둔다.
  • 리뷰 체크: 테스트가 수정 전 실패했는가, 사용자 결과를 단언하는가, 외부 의존성과 공유 상태를 격리했는가, CI에서 결과를 읽을 수 있는가.
  • 테스트 없는 PR에는 이렇게 요청한다. “이 변경의 실패 조건과 기대 결과를 고정하는 테스트 하나를 추가해 주실 수 있나요? 어려운 이유가 있으면 PR에 남기고 대체 검증을 합의하죠.”
  • 팀 규칙 예: 변경한 동작은 회귀 테스트를 갖고, PR CI는 전체 필수 suite를 실행하며, sleep과 무기한 retry를 금하고, 격리한 flaky에는 담당자와 만료일을 둔다.

JUnit·Mockito·AssertJ와 TDD 기초는 → J19, Spring 테스트는 → S18, CI/CD는 → D08, 디버깅은 → D05 참조.

#7. 자가점검 Q&A (면접 대비)

Q1. 특성 테스트는 요구사항 테스트와 무엇이 다른가?
특성 테스트는 불명확한 기존 동작을 기록한다.
그 결과가 올바른 규칙인지는 별도 검토한다.
동작 변경은 합의된 요구를 새 기대값으로 기록한다.
꼬리질문: 기존 동작이 틀렸다면?
답: 올바른 결과를 기대하는 실패 테스트를 만들고 의도된 변경을 남긴다.

Q2. 왜 버그 수정 전에 테스트를 실패시켜야 하나?
실패해야 입력이 결함을 재현한다는 증거가 된다.
수정 후 같은 테스트가 통과하면 회귀 방지가 된다.
처음부터 통과하면 조건이나 assertion이 약한지 점검한다.
꼬리질문: 재현 테스트가 수정 전부터 통과한다면?
답: 입력과 단언을 좁혀 실제 결함 경로를 잡는다.

Q3. 단위·슬라이스·통합 테스트는 어떻게 나누나?
계산은 단위, HTTP 계약은 MVC, SQL은 DB 슬라이스로 검증한다.
전체 애플리케이션 배선은 통합 테스트에 둔다.
가장 좁고 신뢰할 수 있는 층을 기본으로 선택한다.
꼬리질문: mock 단위 테스트가 SQL 버그를 잡나?
답: 아니다. 실제 쿼리를 실행하는 DB 테스트가 필요하다.

Q4. 테스트를 위해 인터페이스를 얼마나 추가하나?
외부 효과와 불안정한 환경 경계부터 작은 seam으로 분리한다.
업무 로직 전체를 테스트 전용 추상화로 감싸지 않는다.
실제 동작을 검증할 수 있는 좁은 대체 지점만 둔다.
꼬리질문: Mockito 호출 검증은 언제 쓰나?
답: 호출 횟수나 순서 자체가 외부 계약일 때만 쓴다.

Q5. flaky 테스트를 재시도로 처리해도 되나?
재실행은 간헐성을 확인하는 진단용이다.
상시 재시도는 CI 신뢰도를 떨어뜨리고 회귀를 숨긴다.
격리·시간·비동기·자원 정리의 원인을 고친다.
꼬리질문: 당장 고치기 어렵다면?
답: 이유·담당자·기한을 남기고 만료 시 제거한다.

Q6. JaCoCo 라인 커버리지 90%면 충분한가?
실행한 줄의 비율이지 결과 assertion의 타당성은 측정하지 않는다.
분기·경계값·실패 기대값을 함께 확인해야 한다.
전체 비율보다 위험한 경로에 테스트가 있는지 본다.
꼬리질문: branch 커버리지는 품질 점수인가?
답: 아니다. 빠진 분기를 찾는 보조 지표로 사용한다.
