#E7. JPA로 수정·삭제하기 — 변경 감지·삭제·대량 수정

개념 레슨 · 45분

이게 뭐냐예시따라 해 보기일부러 틀려 보기확인 문제더 깊이다음

#이게 뭐냐

E2에서는 UPDATE tag SET name = '연습태그2' WHERE name = '연습태그'를 손으로 썼다. E3·E6에서 본 저장소에는 save·find…·delete…는 있는데 update 메서드가 없다. JPA에서 고치는 법은 이렇다.

트랜잭션 안에서 읽어 온 엔티티의 값을 바꾸면, 트랜잭션이 끝날 때(커밋) Hibernate가 UPDATE를 보낸다.

이걸 변경 감지(dirty checking)라고 한다. 순서는 이렇다.

  1. findById로 읽으면 Hibernate는 객체를 돌려주면서, 그 객체와 읽었을 때 값의 사본을 같이 들고 있다. 이렇게 들고 있는 곳을 영속성 컨텍스트라고 한다. 트랜잭션 하나에 하나씩 생긴다.
  2. 코드가 post.changeTitle("새 제목")으로 필드 값을 바꾼다. 이때는 아무 SQL도 안 나간다.
  3. 트랜잭션이 커밋되기 직전에 Hibernate가 들고 있던 객체를 사본과 하나하나 비교한다. 달라진 객체가 있으면 UPDATE를 보낸다(이걸 flush라고 한다).

그래서 save()를 부르지 않아도 된다. 대신 트랜잭션이 있어야 한다. 트랜잭션은 서비스 메서드에 @Transactional을 붙여 만든다. 메서드가 시작될 때 트랜잭션이 열리고, 정상으로 끝나면 커밋된다. 자세한 규칙(롤백, 어디에 거나)은 G3에서 배운다. 오늘은 "있을 때와 없을 때 SQL이 어떻게 다른가"만 본다.

#고치고 지우는 네 가지 길

길 코드 나가는 SQL 쓰는 때
변경 감지 읽고 → 값 바꾸기 커밋 때 UPDATE … WHERE id = ? 한 줄 글 하나 고치기(제목, 상태)
삭제 delete(엔티티) · deleteById(id) SELECT 먼저, 커밋 때 DELETE 진짜로 행을 지울 때
soft delete 읽고 → deletedAt에 지금 시각 변경 감지와 같은 UPDATE 지운 척만 할 때(게시판은 보통 이쪽)
벌크 수정 @Modifying @Query("update …") UPDATE … WHERE 조건 한 번에 여러 행 조건에 맞는 행을 한꺼번에

#예시

진짜 post 테이블을 고치면 다른 실습이 깨진다. practice DB에 연습용 복사본 lesson_post(글 10개)와 lesson_board를 만들어 거기서 한다. 만드는 SQL은 따라 해 보기 1단계에 있다. 엔티티는 이렇다.

@Entity
@Table(name = "lesson_post")   // 연습용 복사본 — 진짜 post는 건드리지 않는다
public class LessonPost {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "board_id", nullable = false)
    private Long boardId;

    @Column(name = "author_id", nullable = false)
    private Long authorId;

    @Column(nullable = false)
    private String title;

    @Column(nullable = false)
    private String content;

    @Enumerated(EnumType.STRING)          // DB에 'PUBLISHED' 같은 이름으로 저장
    @Column(nullable = false)
    private PostStatus status;

    @Column(name = "view_count")
    private int viewCount;

    @CreationTimestamp                    // INSERT 때 한 번 채운다
    @Column(name = "created_at", nullable = false, updatable = false)
    private LocalDateTime createdAt;

    @UpdateTimestamp                      // INSERT·UPDATE 때마다 새로 채운다
    @Column(name = "updated_at", nullable = false)
    private LocalDateTime updatedAt;

    @Column(name = "deleted_at")
    private LocalDateTime deletedAt;      // null이면 살아 있는 글

    protected LessonPost() {}

    public LessonPost(Long boardId, Long authorId, String title, String content) {
        this.boardId = boardId;
        this.authorId = authorId;
        this.title = title;
        this.content = content;
        this.status = PostStatus.DRAFT;
    }

    // 의도가 보이는 메서드 — setter 대신
    public void changeTitle(String title) {
        if (title == null || title.isBlank()) {
            throw new IllegalArgumentException("제목은 비울 수 없다");
        }
        this.title = title;
    }

    public void softDelete(LocalDateTime now) {
        this.deletedAt = now;
    }

    public Long getId() { return id; }
    public String getTitle() { return title; }
    public PostStatus getStatus() { return status; }
    public int getViewCount() { return viewCount; }
    public LocalDateTime getCreatedAt() { return createdAt; }
    public LocalDateTime getUpdatedAt() { return updatedAt; }
    public LocalDateTime getDeletedAt() { return deletedAt; }
}
public enum PostStatus { PUBLISHED, DRAFT, HIDDEN }

setTitle 대신 changeTitle을 둔 이유가 있다. 값이 바뀌는 곳이 이 메서드 하나라서, "빈 제목 금지" 같은 규칙을 여기 한 번만 쓰면 된다. 서비스 코드를 읽을 때도 post.changeTitle(…)이 "제목을 바꾼다"는 업무로 읽힌다. setDeletedAt(now) 대신 softDelete(now)도 같다.

서비스는 @Transactional이 있는 것과 없는 것을 나란히 둔다.

@Service
public class LessonPostService {

    private final LessonPostRepository posts;

    public LessonPostService(LessonPostRepository posts) {
        this.posts = posts;
    }

    private LessonPost getPost(Long id) {
        return posts.findById(id)
                .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND, "글이 없습니다: " + id));
    }

    @Transactional
    public LessonPost changeTitle(Long id, String title) {
        LessonPost post = getPost(id);
        post.changeTitle(title);
        System.out.println("   changeTitle 메서드 끝 — save는 안 불렀다");
        return post;
    }

    // @Transactional 없음
    public LessonPost changeTitleNoTx(Long id, String title) {
        LessonPost post = getPost(id);
        post.changeTitle(title);
        System.out.println("   changeTitleNoTx 메서드 끝");
        return post;
    }

    // @Transactional 없이 save를 부른다
    public LessonPost changeTitleNoTxSave(Long id, String title) {
        LessonPost post = getPost(id);
        post.changeTitle(title);
        LessonPost saved = posts.save(post);
        System.out.println("   save가 돌려준 객체가 같은 객체인가? " + (saved == post));
        return saved;
    }

    @Transactional(readOnly = true)
    public void changeTitleReadOnly(Long id, String title) {
        LessonPost post = getPost(id);
        post.changeTitle(title);
        System.out.println("   readOnly 메서드 끝");
    }

    @Transactional
    public void softDelete(Long id) {
        LessonPost post = getPost(id);
        post.softDelete(LocalDateTime.now());
    }

    @Transactional
    public void delete(Long id) {
        LessonPost post = getPost(id);
        posts.delete(post);
        System.out.println("   delete 호출 끝");
    }
}

아래 로그는 따라 해 보기에서 실제로 나온 것이다. 읽기 쉽게 줄였다. SQL:은 Hibernate가 보낸 SQL, bind:는 ?에 들어간 값, TX:는 트랜잭션 관리자(JpaTransactionManager)의 로그에서 시작·참여·커밋 줄만 남긴 것이다. lesson_post의 SELECT 목록은 열 10개가 늘 같아서 lp1_0.id,…,lp1_0.view_count로 줄였다.

#① 변경 감지 — save 없이 UPDATE

TX: Creating new transaction with name [org.example.e7.LessonPostService.changeTitle]: PROPAGATION_REQUIRED,ISOLATION_DEFAULT
TX: Participating in existing transaction
SQL: select lp1_0.id,…,lp1_0.view_count from lesson_post lp1_0 where lp1_0.id=?
   changeTitle 메서드 끝 — save는 안 불렀다
TX: Committing JPA transaction
SQL: update lesson_post set author_id=?,board_id=?,content=?,deleted_at=?,status=?,title=?,updated_at=?,view_count=? where id=?
bind: (6:VARCHAR) <- [제목을 고쳤다]
bind: (7:TIMESTAMP) <- [2026-10-10T15:38:50.956617]
bind: (9:BIGINT) <- [1]
  • changeTitle 메서드에 들어갈 때 트랜잭션이 새로 열렸다. 안에서 부른 findById는 새로 열지 않고 참여했다(Participating in existing transaction).
  • UPDATE는 "메서드 끝" 다음, 커밋할 때 나갔다. 값을 바꾼 줄(post.changeTitle)에서는 SQL이 없었다.
  • 제목만 바꿨는데 UPDATE에 열이 8개다. Hibernate는 기본으로 바뀐 칸만이 아니라 모든 칸을 다시 쓴다. created_at만 빠졌는데, updatable = false라서다.
  • updated_at(7번)에는 @UpdateTimestamp가 지금 시각을 넣었다.

② 같은 값으로 다시 바꾸면 select 한 줄 뒤 커밋만 하고 UPDATE가 없었다. 사본과 비교해 달라진 게 없으니 보낼 것도 없다.

#③ @Transactional이 없으면 — 아무 일도 없다

TX: Creating new transaction with name [org.springframework.data.jpa.repository.support.SimpleJpaRepository.findById]: PROPAGATION_REQUIRED,ISOLATION_DEFAULT,readOnly
SQL: select lp1_0.id,…,lp1_0.view_count from lesson_post lp1_0 where lp1_0.id=?
TX: Committing JPA transaction
   changeTitleNoTx 메서드 끝
…
③ DB 제목: [공지] 커뮤니티 이용 규칙 안내

서비스에 트랜잭션이 없으니, findById가 자기 몫의 작은 트랜잭션(SimpleJpaRepository.findById … readOnly)을 열고 읽자마자 커밋했다. 그 순간 영속성 컨텍스트도 닫혔다. 그 뒤에 바꾼 제목은 아무도 비교해 주지 않는다. UPDATE가 없고, 에러도 없다. DB 제목은 그대로다.

API로 부르면 더 헷갈린다. 응답에는 고친 제목이 나온다. 메모리의 객체는 바뀌었기 때문이다(따라 해 보기 4).

#④ @Transactional 없이 save를 부르면

SQL: select lp1_0.id,…,lp1_0.view_count from lesson_post lp1_0 where lp1_0.id=?        ← findById
TX: Creating new transaction with name [org.springframework.data.jpa.repository.support.SimpleJpaRepository.save]: PROPAGATION_REQUIRED,ISOLATION_DEFAULT
SQL: select lp1_0.id,…,lp1_0.view_count from lesson_post lp1_0 where lp1_0.id=?        ← save 안에서 또 읽는다
TX: Committing JPA transaction
SQL: update lesson_post set author_id=?,board_id=?,content=?,deleted_at=?,status=?,title=?,updated_at=?,view_count=? where id=?
   save가 돌려준 객체가 같은 객체인가? false

이번엔 저장됐다. 그런데 같은 행을 두 번 읽었다. save는 id가 있는 객체를 받으면 "이미 있는 행"으로 보고 병합(merge)한다. 새 트랜잭션에서 DB 행을 다시 읽어 새 객체를 만들고, 내 객체의 값을 거기에 복사한 다음, 커밋 때 변경 감지로 UPDATE한다. 그래서 돌려준 객체는 내가 넘긴 객체와 다른 객체다(false). save 뒤에는 돌려받은 객체를 써야 한다.

정리하면, 서비스에 @Transactional을 걸고 값만 바꾸는 쪽(①)이 SQL도 적고 코드도 짧다. save는 새 객체를 처음 넣을 때(id가 null) 부른다.

#⑤ @Transactional(readOnly = true)에서 바꾸면

TX: Creating new transaction with name [org.example.e7.LessonPostService.changeTitleReadOnly]: PROPAGATION_REQUIRED,ISOLATION_DEFAULT,readOnly
SQL: select lp1_0.id,…,lp1_0.view_count from lesson_post lp1_0 where lp1_0.id=?
   readOnly 메서드 끝
TX: Committing JPA transaction
…
⑤ DB 제목: 첫 코드리뷰 받은 날

커밋은 했는데 UPDATE가 없다. 읽기 전용 트랜잭션에서는 Hibernate가 변경 감지를 건너뛴다. 조회용 서비스 메서드에 readOnly = true를 붙이면 쓸데없는 비교를 안 해서 좋지만, 그 안에서 값을 바꿔도 저장되지 않는다는 뜻이기도 하다.

#⑥ 작성·수정 시각 자동 입력

SQL: insert into lesson_post (author_id,board_id,content,created_at,deleted_at,status,title,updated_at,view_count) values (?,?,?,?,?,?,?,?,?)
bind: (4:TIMESTAMP) <- [2026-10-10T15:38:51.058482]       ← created_at
bind: (6:ENUM) <- [DRAFT]
bind: (8:TIMESTAMP) <- [2026-10-10T15:38:51.058504]       ← updated_at
⑥ 저장 직후 객체: createdAt 2026-10-10T15:38:51.058482 / updatedAt 2026-10-10T15:38:51.058504
…(changeTitle로 제목 수정)
SQL: update lesson_post set author_id=?,board_id=?,content=?,deleted_at=?,status=?,title=?,updated_at=?,view_count=? where id=?
bind: (7:TIMESTAMP) <- [2026-10-10T15:38:51.076943]       ← updated_at만 새 값
⑥ DB에서 다시 읽음: createdAt 2026-10-10T15:38:51 / updatedAt 2026-10-10T15:38:51
  • @CreationTimestamp·@UpdateTimestamp(Hibernate 기능)는 서버(JVM)의 지금 시각을 넣는다. 두 필드를 따로 채워서 처음 넣을 때도 마이크로초가 조금 다르다.
  • enum은 @Enumerated(EnumType.STRING) 덕분에 'DRAFT'라는 이름으로 들어갔다.
  • 다시 읽으니 소수점 아래가 사라졌다. 열이 datetime(초까지)이라서 MySQL이 반올림해 저장한다. 다른 실행에서는 15:24:55.648308이 15:24:56으로 저장됐다. 저장 직후 객체에 든 값과 DB 값이 다를 수 있다는 점만 기억한다.

같은 일을 Spring Data의 Auditing으로도 할 수 있다. 실무 코드에서 자주 보는 쪽이다.

@Entity
@Table(name = "lesson_post")
@EntityListeners(AuditingEntityListener.class)   // 저장·수정 직전에 Spring Data가 끼어들게 한다
public class AuditedPost {
    // …id, boardId, authorId, title, content는 같다

    @CreatedDate
    @Column(name = "created_at", nullable = false, updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    @Column(name = "updated_at", nullable = false)
    private LocalDateTime updatedAt;
}
@Configuration
@EnableJpaAuditing      // 이게 있어야 동작한다
public class AuditingConfig {}
Hibernate @CreationTimestamp·@UpdateTimestamp Spring Data @CreatedDate·@LastModifiedDate
필요한 설정 어노테이션만 @EntityListeners(AuditingEntityListener.class) + @EnableJpaAuditing
처음 넣을 때 두 값이 마이크로초 단위로 조금 다르다 두 값이 똑같다(…41.793438과 …41.793438)
더 할 수 있는 것 시각만 @CreatedBy·@LastModifiedBy로 "누가"도 기록(로그인 정보와 연결)

Auditing에 필요한 spring-aspects 라이브러리는 spring-boot-starter-data-jpa가 이미 데려온다(./gradlew dependencies로 확인). 따로 추가하지 않는다. @EnableJpaAuditing을 빼면 어떻게 되는지는 일부러 틀려 보기 4에 있다.

#⑦~⑨ 삭제 — 지우기 전에 먼저 읽는다

⑦ delete(엔티티)                         ← 서비스 @Transactional 안에서 findById → delete
SQL: select lp1_0.id,…,lp1_0.view_count from lesson_post lp1_0 where lp1_0.id=?
   delete 호출 끝
TX: Committing JPA transaction
SQL: delete from lesson_post where id=?
⑧ deleteById(10)
TX: Creating new transaction with name [org.springframework.data.jpa.repository.support.SimpleJpaRepository.deleteById]: …
SQL: select lp1_0.id,…,lp1_0.view_count from lesson_post lp1_0 where lp1_0.id=?
TX: Committing JPA transaction
SQL: delete from lesson_post where id=?
⑨ deleteById(9999) — 없는 번호
SQL: select lp1_0.id,…,lp1_0.view_count from lesson_post lp1_0 where lp1_0.id=?
TX: Committing JPA transaction
⑨ 예외 없이 지나감
  • delete도 UPDATE처럼 커밋 때 나간다(⑦에서 "호출 끝" 뒤).
  • deleteById(10)은 이름만 보면 DELETE 한 줄일 것 같은데, SELECT 먼저다. Spring Data는 id로 엔티티를 먼저 찾고, 찾은 엔티티를 지운다.
  • 없는 번호(9999)면 SELECT만 하고 조용히 끝난다. 예외가 없다. "없는 글을 지우려 하면 404"가 필요하면 ⑦처럼 서비스에서 findById(…).orElseThrow(…)로 먼저 확인한다.

이름 규칙 삭제도 같다. long deleteByBoardId(Long boardId)를 트랜잭션 안에서 불렀더니 select … where lp1_0.board_id=?로 2행을 읽은 뒤, 커밋 때 delete from lesson_post where id=?가 행마다 한 번씩 나갔다. 1000행이면 DELETE가 1000번이다.

#⑩ soft delete — 지운 척, 그리고 거르기

SQL: update lesson_post set author_id=?,board_id=?,content=?,deleted_at=?,status=?,title=?,updated_at=?,view_count=? where id=?
bind: (4:TIMESTAMP) <- [2026-10-10T15:38:51.123729]       ← deleted_at
⑩ findById(9): Optional[이직 준비 근황]
SQL: select lp1_0.id,…,lp1_0.view_count from lesson_post lp1_0 where lp1_0.id=? and lp1_0.deleted_at is null
⑩ findByIdAndDeletedAtIsNull(9): Optional.empty

soft delete는 JPA 기능이 아니라 우리가 정한 규칙이다. softDelete(now)로 deletedAt을 채우면 ①과 같은 변경 감지 UPDATE가 나간다. 행은 남는다.

그래서 findById는 지운 글을 그대로 찾는다. 지운 글을 거르려면 조회마다 deleted_at is null 조건이 있어야 한다. E6의 이름 규칙(findByIdAndDeletedAtIsNull)으로 만들었다. 상세·목록·수정·좋아요처럼 글을 찾는 모든 길에서 이 조건을 빠뜨리지 않는 게 3-2의 핵심이다.

findByIdAndDeletedAtIsNull 앞에는 TX: 줄이 없다. findById·save·deleteById 같은 물려받은 메서드에는 기본 트랜잭션이 붙어 있고, 내가 이름 규칙이나 @Query로 직접 선언한 메서드에는 없다. 읽기는 그래도 되지만, 지우기·고치기는 트랜잭션이 없으면 실패한다(일부러 틀려 보기 3).

#⑪~⑭ 벌크 수정 — @Modifying

"게시판 2의 글 조회수를 전부 +1"을 변경 감지로 하면 글마다 읽고 UPDATE가 한 줄씩 나간다. UPDATE 한 번으로 끝내려면 저장소에 직접 쓴다.

public interface LessonPostRepository extends JpaRepository<LessonPost, Long> {

    // soft delete 된 글은 못 찾는 조회
    Optional<LessonPost> findByIdAndDeletedAtIsNull(Long id);

    long deleteByBoardId(Long boardId);

    // 벌크 UPDATE — 조건에 맞는 행을 SQL 한 번에 고친다
    @Modifying
    @Query("update LessonPost p set p.viewCount = p.viewCount + 1 where p.boardId = :boardId")
    int increaseViews(@Param("boardId") Long boardId);

    @Modifying(clearAutomatically = true)
    @Query("update LessonPost p set p.viewCount = p.viewCount + 1 where p.boardId = :boardId")
    int increaseViewsAndClear(@Param("boardId") Long boardId);

    @Modifying(flushAutomatically = true, clearAutomatically = true)
    @Query("update LessonPost p set p.viewCount = p.viewCount + 1 where p.boardId = :boardId")
    int increaseViewsFlushAndClear(@Param("boardId") Long boardId);
}

@Modifying은 "이 @Query는 조회가 아니라 고치는 쿼리"라는 표시다. 돌려주는 int는 바뀐 행 수다. 그런데 벌크 UPDATE는 영속성 컨텍스트를 거치지 않고 DB에 바로 간다. 그래서 들고 있던 객체와 DB가 어긋난다. 트랜잭션 안에서 글 5(게시판 2)를 먼저 읽고 벌크를 돌렸다.

⑪ 벌크 UPDATE
SQL: select lp1_0.id,…,lp1_0.view_count from lesson_post lp1_0 where lp1_0.id=?
   벌크 전 view_count 36
SQL: update lesson_post lp1_0 set view_count=(lp1_0.view_count+1) where lp1_0.board_id=?
   벌크로 바꾼 행 1
   들고 있던 객체 36 / 다시 findById 36
⑪ 트랜잭션이 끝난 뒤 다시 읽기: 37

DB는 37인데 같은 트랜잭션 안에서는 36이다. 다시 findById를 해도 36이고 SQL도 안 나갔다. 한 트랜잭션 안에서 이미 읽은 엔티티는 영속성 컨텍스트에 있는 것을 돌려주기 때문이다(E4에서 같은 회원을 다시 안 읽던 것과 같다).

⑫ 벌크 UPDATE + clearAutomatically
   벌크 전 view_count 37
SQL: update lesson_post lp1_0 set view_count=(lp1_0.view_count+1) where lp1_0.board_id=?
   벌크로 바꾼 행 1
SQL: select lp1_0.id,…,lp1_0.view_count from lesson_post lp1_0 where lp1_0.id=?
   들고 있던 객체 37 / 다시 findById 38

clearAutomatically = true는 벌크 직후 영속성 컨텍스트를 비운다. 그래서 다시 findById하면 DB를 새로 읽어 38이 나온다. 이미 손에 든 객체(post)는 여전히 37이다. 벌크 뒤에는 다시 읽어서 쓴다.

비우기에는 대가가 있다. 아직 UPDATE로 안 보낸 변경도 같이 버려질 수 있다.

⑬ 게시판 이름을 고친 뒤 clearAutomatically 벌크
SQL: select lb1_0.id,lb1_0.name from lesson_board lb1_0 where lb1_0.id=?
SQL: update lesson_post lp1_0 set view_count=(lp1_0.view_count+1) where lp1_0.board_id=?
TX: Committing JPA transaction
⑬ DB 게시판 이름: 개발
⑭ 같은 일 + flushAutomatically
SQL: select lb1_0.id,lb1_0.name from lesson_board lb1_0 where lb1_0.id=?
SQL: update lesson_board set name=? where id=?
SQL: update lesson_post lp1_0 set view_count=(lp1_0.view_count+1) where lp1_0.board_id=?
⑭ DB 게시판 이름: 개발(바꿈)

⑬에서 게시판 이름을 개발(바꿈)으로 바꿨는데 update lesson_board가 끝내 나가지 않았다. 벌크가 컨텍스트를 비우면서 바뀐 게시판 객체도 같이 버렸다. ⑭처럼 flushAutomatically = true를 더하면 벌크 전에 밀린 변경을 먼저 보내고(update lesson_board) 나서 비운다.

따로 해 본 실험에서, 같은 lesson_post의 제목을 고친 뒤 clearAutomatically 벌크를 돌렸을 때는 Hibernate가 제목 UPDATE를 벌크 앞에 먼저 보내서 잃지 않았다. 벌크와 같은 테이블의 변경은 먼저 보냈고, 다른 테이블(lesson_board)의 변경은 보내지 않은 채 버렸다. 어느 쪽인지 따지기보다 clearAutomatically를 켤 때는 flushAutomatically도 같이 켠다.

public class LessonPostController {

        this.posts = posts;

            return new PostResponse(p.getId(), p.getTitle(), p.getStatus().name(), String.valueOf(p.getUpdatedAt()));
        }
    }

    @PatchMapping("/e7/posts/{id}")
    public PostResponse changeTitle(@PathVariable Long id, @RequestBody TitleRequest req) {
        return PostResponse.from(service.changeTitle(id, req.title()));
    }

    @PatchMapping("/e7/posts/{id}/no-tx")
    public PostResponse changeTitleNoTx(@PathVariable Long id, @RequestBody TitleRequest req) {
        return PostResponse.from(service.changeTitleNoTx(id, req.title()));
    }

    // 나쁜 예: 인자 없는 orElseThrow()
    @GetMapping("/e7/posts/{id}/bad")

        return PostResponse.from(posts.findById(id).orElseThrow());
    }

    @DeleteMapping("/e7/posts/{id}")
    public void delete(@PathVariable Long id) {
        service.softDelete(id);
    }
}

#일부러 틀려 보기

메시지는 Spring Boot 4.1.1 · Spring Data JPA 4.1.1 · Hibernate 7.4.5에서 재현한 원문이다. 할 때마다 1단계 sqlp 줄로 테이블을 새로 만든다.

1. @Enumerated(EnumType.STRING)을 지운다 — 기본값은 ORDINAL(순번)이다.

WARN  o.h.orm.jdbc.error : Value 'PUBLISHED' is outside of valid range for type java.lang.Byte
org.springframework.dao.DataIntegrityViolationException: Could not extract column [7] from JDBC ResultSet [Value 'PUBLISHED' is outside of valid range for type java.lang.Byte] [n/a]; SQL [n/a]

findById(1L)부터 터진다. @Enumerated가 없으면 Hibernate는 enum을 순번(PUBLISHED=0, DRAFT=1, HIDDEN=2)으로 읽고 쓴다. 열에 든 'PUBLISHED' 글자를 숫자로 읽으려다 실패했다. 새 글을 저장하면 binding parameter (6:TINYINT) <- [DRAFT]로 숫자 1을 넣으려다 Check constraint 'lesson_post_chk_2' is violated.로 막힌다. 이 테이블은 CHECK 제약 덕분에 바로 터졌다.

정말 무서운 건 숫자 열에 처음부터 순번으로 저장해 온 경우다. 터지지 않고 값이 조용히 바뀐다. 작은 테이블로 확인했다.

sqlp "CREATE TABLE lesson_ticket (id bigint NOT NULL AUTO_INCREMENT PRIMARY KEY, status tinyint NOT NULL)"
public enum TicketStatus { OPEN, CLOSED }

@Entity
@Table(name = "lesson_ticket")
public class LessonTicket {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Enumerated(EnumType.ORDINAL)   // 순번(0, 1, 2…)으로 저장
    private TicketStatus status;

    protected LessonTicket() {}
    public LessonTicket(TicketStatus status) { this.status = status; }
    public Long getId() { return id; }
    public TicketStatus getStatus() { return status; }
}

1 save(new LessonTicket(TicketStatus.CLOSED)) insert into lesson_ticket (status) values (?), DB에는 status = 1
2 enum 맨 앞에 상태 하나 추가: { WAITING, OPEN, CLOSED } 코드만 바꿨다. DB는 그대로 1
3 서버를 다시 켜고 findAll() 티켓 1: OPEN — 닫힌 티켓이 열렸다

순번 1의 뜻이 CLOSED에서 OPEN으로 바뀌었다. 에러도 경고도 없다. 그래서 상태 enum에는 늘 @Enumerated(EnumType.STRING)을 적는다. 문자열은 enum의 이름을 바꿀 때만 DB 값도 같이 고치면 된다. 다 보면 sqlp "DROP TABLE lesson_ticket".

2. @Modifying을 빼먹는다 — @Query("update …")만 남기고 트랜잭션 안에서 부른다.

org.springframework.dao.InvalidDataAccessApiUsageException: Query executed via 'getResultList()' or 'getSingleResult()' must be a 'select' query [update LessonPost p set p.viewCount = p.viewCount + 1 where p.boardId = :boardId]

@Modifying이 없으면 Spring Data는 조회 쿼리로 보고 결과 목록을 받으려 한다. Hibernate가 "그 방법은 select만 된다"고 거절했다. 서버는 뜨고, 부를 때 터진다.

3. 트랜잭션 없이 벌크·이름 규칙 삭제를 부른다 — 서비스나 TransactionTemplate 없이 posts.increaseViews(2L), posts.deleteByBoardId(4L)

org.springframework.dao.InvalidDataAccessApiUsageException: No active transaction for update or delete query
org.springframework.dao.InvalidDataAccessApiUsageException: No EntityManager with actual transaction available for current thread - cannot reliably process 'remove' call

⑩에서 본 대로 직접 선언한 메서드에는 기본 트랜잭션이 없다. @Modifying도 트랜잭션을 만들어 주지 않는다. deleteByBoardId는 select까지는 나갔다가 지우는 단계에서 막혔다. 고치기·지우기는 @Transactional이 붙은 서비스 메서드 안에서 부른다.

4. @EnableJpaAuditing을 빼먹는다 — 예시의 AuditedPost(나머지 필드는 LessonPost와 같고, 저장소는 JpaRepository<AuditedPost, Long>)로 새 글을 저장했더니 이렇게 나왔다.

org.springframework.dao.DataIntegrityViolationException: not-null property references a null or transient value for entity org.example.e7.AuditedPost.createdAt

@CreatedDate는 표시일 뿐이고, 값을 채우는 일은 @EnableJpaAuditing이 켜 준다. 아무도 안 채운 createdAt이 null이라 nullable = false를 본 Hibernate가 INSERT 전에 막았다. 컴파일도 기동도 멀쩡해서 저장할 때 처음 알게 된다.

#확인 문제

1. 아래 서비스 메서드는 save를 부르지 않는다. 제목이 DB에 저장되나? 저장된다면 UPDATE는 어느 시점에 나가나?

@Transactional
public void rename(Long id, String title) {
    LessonPost post = posts.findById(id).orElseThrow();
    post.changeTitle(title);
    System.out.println("끝");
}
정답

저장된다. findById로 읽은 엔티티는 트랜잭션이 끝날 때까지 영속성 컨텍스트가 들고 있고, 커밋 직전에 읽었을 때의 사본과 비교해 달라진 것을 UPDATE로 보낸다. 그래서 UPDATE는 끝이 찍힌 다음, 커밋할 때 나간다(①의 로그 순서). 같은 값으로 바꿨다면 UPDATE는 아예 나가지 않는다(②).

2. 위 메서드에서 @Transactional을 지우고 PATCH로 불렀다. 응답 JSON의 제목과 DB의 제목은 각각 어떻게 되나? 왜 그런가?

정답

응답에는 새 제목, DB에는 옛 제목이다. 트랜잭션이 없으니 findById가 자기 트랜잭션을 열고 읽자마자 커밋하면서 영속성 컨텍스트도 닫힌다. 그 뒤 바꾼 값은 메모리의 객체에만 있고 비교해서 UPDATE를 보낼 주체가 없다. 에러도 없어서 응답만 보면 성공처럼 보인다. 수정 API는 DB를 다시 읽어 확인해야 한다.

3. posts.deleteById(9999L)(없는 번호)를 부르면 SQL이 몇 번 나가고, 무슨 일이 일어나나? "없는 글 삭제 → 404"를 만들려면?

정답

select … where lp1_0.id=? 한 번만 나가고 끝난다. 예외 없이 조용히 지나간다. deleteById는 먼저 찾고, 찾았을 때만 지운다(있으면 SELECT 후 DELETE). 404가 필요하면 서비스에서 findById(id).orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND, …))로 먼저 확인하고 delete(엔티티)(또는 soft delete)를 한다.

4. 한 트랜잭션 안에서 글 5(조회수 36)를 읽은 뒤 @Modifying 벌크로 조회수를 +1 했다. 같은 트랜잭션에서 posts.findById(5L)을 다시 부르면 조회수는? clearAutomatically = true면?

정답

36이다. SQL도 나가지 않는다. 벌크 UPDATE는 영속성 컨텍스트를 거치지 않고 DB만 바꾸고, findById는 이미 들고 있는 엔티티를 돌려준다. clearAutomatically = true면 벌크 직후 컨텍스트를 비우므로 findById가 SELECT를 다시 보내 37을 읽는다. 단 비우면 아직 안 보낸 다른 테이블의 변경이 버려질 수 있어(⑬) 필요하면 flushAutomatically = true도 켠다.

5. @Enumerated(EnumType.ORDINAL)로 CLOSED(순번 1)를 저장한 뒤, enum 맨 앞에 WAITING을 추가했다. 그 행을 다시 읽으면? 그래서 무엇을 쓰나?

정답

OPEN 으로 읽힌다. DB에는 숫자 1만 있는데, 새 enum { WAITING, OPEN, CLOSED }에서 1번은 OPEN이다. 에러도 없이 데이터의 뜻이 바뀐다. 그래서 @Enumerated(EnumType.STRING)으로 이름을 저장한다. @Enumerated를 아예 안 적어도 기본값이 ORDINAL이니 반드시 적는다.
