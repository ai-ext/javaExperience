#T-025. 글 수정이 서로 덮어쓴다 — 낙관적 락과 409

난이도 고급 · 유형 기존 API 변경 · DB community · 예상 90분

#티켓

요청자 모바일 앱 팀 · 배경 "PC에서 고친 내용이 사라졌어요" 문의. PC와 휴대폰에 같은 글 수정 화면을 열어 두고 PC에서 저장한 뒤, 휴대폰에서 예전 내용 그대로 저장하면 PC에서 고친 내용이 조용히 덮인다.

  • 글 상세 응답에 버전을 내려 주세요. 수정 화면은 연 시점의 버전을 수정 요청에 함께 보냅니다.
  • 보낸 버전이 지금 버전과 다르면(그사이 누가 먼저 고쳤으면) 저장하지 말고 409로 알려 주세요. 응답에 지금 버전이 있어야 앱이 "새로 불러오기"를 띄울 수 있습니다.
  • 글을 열기만 하는 것(조회수 증가)이나 좋아요·댓글은 버전을 바꾸면 안 됩니다 — 수정 화면을 연 채로 누가 글을 읽었다고 저장이 막히면 안 된다.
  • 구버전 앱은 버전을 보내지 않습니다. 버전이 없는 수정 요청은 지금처럼 받습니다.
  • 완료 조건: 같은 버전으로 두 번 저장하면 첫 번째만 반영되고 두 번째는 409, 그사이 동시 조회가 몇 번 있어도 결과는 같다.

DB 시작 상태: community 처음 상태(이 저장소 루트에서 docker compose down -v && docker compose up -d — community·practice·project 세 DB를 모두 지우고 docker/mysql/init/의 처음 상태로 다시 만든다(project는 빈 DB, CloudBeaver 작업 공간도 초기화). 남길 데이터가 있으면 먼저 ./docker/mysql/dump.sh로 세 DB를 docker/mysql/backup/<시각>/에 SQL 파일로 떠 둔다. CloudBeaver에 저장한 SQL 스크립트·바꾼 설정은 이 백업에 들어가지 않으니 따로 복사해 둔다 — 미리 만든 연결 세 개는 다시 들어간다). 기준 코드로 앱을 켜면 Flyway가 V2~V6을 적용한다 — 다음 마이그레이션 번호는 V7. 이스프링(tok-lee)의 글 18(자유글 07)을 쓴다.

#만들 것

항목 내용
마이그레이션 V7__<설명>.sql — post에 버전 컬럼(기존 글은 0부터). 운영 중 테이블이라 테이블 복사가 일어나지 않는 방식으로
상세 응답 GET /api/posts/{id}, PATCH 응답에 version(숫자)
수정 요청 PATCH /api/posts/{id} 본문에 version(선택). 지금 버전과 다르면 409 Problem Details + currentVersion(지금 버전). 같으면 저장하고 버전 +1
버전 없는 요청 지금처럼 저장(구버전 앱 호환) — 저장되면 버전은 오른다
버전을 바꾸지 않는 것 조회수 증가, 좋아요·댓글 수 변경
그대로인 것 404 → 403 순서, 부분 수정 규칙, 다른 응답 필드

BASE=http://localhost:8080; J='Content-Type: application/json'; H='Authorization: Bearer tok-lee'

seq 10 | xargs -P 10 -I{} curl -s -o /dev/null -w '%{http_code}\n' "$BASE/api/posts/18" | sort | uniq -c   # 요청 V — 동시에 10번 열기
curl -s -X PATCH "$BASE/api/posts/18" -H "$H" -H "$J" -d '{"title":"[T-025] PC에서 고침","version":V0}'          # 요청 B — 200, version V0+1
curl -s -X PATCH "$BASE/api/posts/18" -H "$H" -H "$J" -d '{"title":"[T-025] 휴대폰에서 고침","version":V0}'      # 요청 X — 409, currentVersion V0+1
curl -s "$BASE/api/posts/18"                                       # 요청 G — 제목은 PC에서 고친 것
curl -s -X PATCH "$BASE/api/posts/18" -H "$H" -H "$J" -d '{"title":"자유글 07"}'                                 # 요청 O — 버전 없이(구버전 앱), 제목 되돌리기

T1
(선택) 테스트
받은 버전으로 두 번 PATCH → 두 번째 409(currentVersion), 그사이 GET은 버전을 바꾸지 않는다




R1
버전 비교 두 겹
요청의 version을 서비스에서 비교(409 + 지금 버전)하는 것과, @Version이 커밋 때 UPDATE … WHERE version = ?로 잡는 것이 각각 어떤 경쟁을 막는지(비교와 커밋 사이에 끼어든 수정 → ObjectOptimisticLockingFailureException도 409로) 말할 수 있다




R2
버전을 올리는 것·안 올리는 것
조회수를 엔티티 변경 감지로 올리면 버전도 오른다 — 그래서 원자적 벌크 UPDATE로 바꿨다(벌크 JPQL은 VERSIONED 없이는 버전을 안 건드린다). 좋아요·댓글 수가 이미 벌크 UPDATE라서 영향이 없다는 것도 확인했다




R3
낙관적 vs 비관적
글 수정에 SELECT … FOR UPDATE(비관적 락)가 맞지 않는 이유(사람이 화면을 몇 분 열어 둔다), If-Match·ETag 헤더로 같은 계약을 표현하는 방법과 비교할 수 있다

#힌트 (막힐 때만)



힌트 1 — 마이그레이션과 엔티티


ALTER TABLE post ADD COLUMN version BIGINT NOT NULL DEFAULT 0, ALGORITHM = INSTANT; — 맨 뒤에 기본값과 함께 붙이는 컬럼 추가는 테이블을 다시 쓰지 않는다(안 되는 경우면 ALGORITHM을 적어 두었으니 에러가 난다). 엔티티에 @Version Long version, 상세 응답 DTO에 version, 수정 요청 DTO에 Long version.






힌트 2 — 버전이 저절로 오른다면


@Version을 붙이자마자 글을 열 때마다 버전이 오르고 동시에 열면 500(낙관적 락 충돌)이 난다면, 상세 조회가 조회수를 엔티티 필드로 올리고(변경 감지) 있기 때문이다. 글 저장소에 @Modifying @Query("UPDATE Post p SET p.viewCount = p.viewCount + 1 WHERE p.id = :id")를 두고, 응답의 조회수는 다시 읽는다. 엔티티의 조회수 증가 메서드는 지운다.
