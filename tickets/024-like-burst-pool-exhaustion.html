#T-024. 좋아요가 몰리면 30초씩 멈춘다 — 커넥션 풀 고갈

난이도 고급 · 유형 버그 · DB community · 예상 90분

#티켓

요청자 운영·SRE · 배경 이벤트 글 두 개가 동시에 화제가 되자 API 전체가 30초 동안 응답하지 않다가 500을 쏟아냈다. 그 시간 DB CPU는 한가했고, 앱 로그에는 HikariPool-1 - Connection is not available, request timed out after 30000ms (total=10, active=10, idle=0, waiting=…). 누군가 "풀을 50으로 늘리자"고 했다.

  • 좋아요가 동시에 몰려도 요청이 멈추지 않게 고쳐 주세요. 풀 크기를 늘리는 것은 해결로 치지 않습니다(왜 안 되는지도 설명).
  • 좋아요·댓글 알림은 계속 만들어져야 합니다. 좋아요가 롤백되면 알림을 만들지 않는 규칙, 알림 저장이 실패해도 좋아요는 성공하는 규칙도 그대로입니다.
  • 완료 조건: 회원 20명이 글 두 개에 동시에 좋아요(서로 다른 40건)를 눌러도 모두 몇 초 안에 200, 두 글의 좋아요 수가 각각 20, 잠시 뒤 알림이 40개 생긴다.

DB 시작 상태: community 처음 상태(bash scripts/java-db.sh --reset). 기준 코드로 앱을 켜면 Flyway가 V2V6을 적용한다. 박디비(회원 4)의 글 15·17(자유글 04·06, 처음 좋아요 0)에 동시성 회원 tok-c01tok-c20이 좋아요를 누른다. 커넥션 풀은 Spring Boot 기본(HikariCP 최대 10개)이다.

#지금 코드

고급 티켓이라 실마리는 없다. 직접 확인의 xargs -P 40 줄로 재현하고, 멈춘 30초 동안 jcmd <pid> Thread.print(또는 IntelliJ 디버거의 스레드 덤프)로 요청 스레드들이 어디서 기다리는지 본다.

브라우저의 버튼 확인은 같은 서버로 동시에 6개 정도만 보낸다(HTTP/1.1 연결 수 제한). 6개로는 풀 10개가 바닥나지 않아 기준 코드에서도 통과할 수 있다 — 재현은 터미널(xargs -P 40)로 한다.

#직접 확인

BASE=http://localhost:8080
pairs() { for p in 15 17; do for i in $(seq -w 1 20); do echo "tok-c$i $p"; done; done; }

pairs | xargs -P 40 -L1 sh -c 'curl -s -o /dev/null -X DELETE "'$BASE'/api/posts/$1/like" -H "Authorization: Bearer $0"'   # 요청 R — 다시 돌릴 수 있게 먼저 취소
time (pairs | xargs -P 40 -L1 sh -c 'curl -s -o /dev/null -w "%{http_code}\n" -X PUT "'$BASE'/api/posts/$1/like" -H "Authorization: Bearer $0"' | sort | uniq -c)   # 요청 P
curl -s "$BASE/api/posts/15"; curl -s "$BASE/api/posts/17"     # 요청 B1·B2 — likeCount 20

버튼으로 확인 — 아래 실행 칸이 위 요청을 그대로 보내고 채점 기준의 C 항목을 대조한다. 먼저 40건을 모두 취소하고 다시 누르므로 몇 번을 눌러도 같은 결과다(위 안내처럼 브라우저에서는 기준 코드도 통과할 수 있다).

T1
(선택) 테스트
스레드 40개로 좋아요(회원 20 × 글 2)를 동시에 부르고 10초 안에 모두 끝나는지 + 알림 40개(별도 스레드면 잠깐 기다렸다가). 고치기 전 코드에서는 실패해야 한다




R1
원인
AFTER_COMMIT 리스너는 요청 스레드에서, 커넥션 반납 전에 돈다. 거기서 REQUIRES_NEW가 커넥션을 하나 더 빌리므로 요청 하나가 두 개를 쥔다. 풀 크기만큼의 요청이 동시에 그 지점에 오면 서로 반납을 기다리는 교착(풀 데드락)이 된다 — 스레드 덤프로 보여 줄 수 있다




R2
풀을 늘리면?
풀 크기 N이면 N개 동시에서 또 멈춘다(문제를 옮길 뿐). 요청당 필요한 커넥션 수의 최댓값을 1로 만드는 것이 해결이다




R3
고친 방법과 대가
예: 리스너를 크기가 정해진 별도 스레드 풀로(@Async) — 큐가 넘칠 때 정책(CallerRunsPolicy가 왜 위험한지), 서버 종료 때 큐에 남은 알림. 다른 길: 같은 트랜잭션에서 알림을 쓰기(BEFORE_COMMIT·직접 호출 — 알림 실패가 좋아요를 롤백), 아웃박스 테이블(같은 트랜잭션에 기록 + 나중에 발송). 각각 무엇을 얻고 잃는지 말할 수 있다

#힌트 (막힐 때만)



힌트 1 — 어디서 기다리나


멈춘 동안의 스레드 덤프에서 http-nio-…-exec-N 스레드 대부분이 HikariPool.getConnection에서 TIMED_WAITING이다. 그중 정확히 10개(풀 크기)는 아래쪽에 NotificationEventListener.onPostLiked → TransactionSynchronizationUtils.invokeAfterCompletion → AbstractPlatformTransactionManager.processCommit이 있고, 위쪽에 handleExistingTransaction(바깥 트랜잭션이 아직 살아 있다)이 있다. 커밋은 끝났지만 아직 processCommit 안 — 첫 커넥션을 정리(반납)하는 코드는 그 뒤에 있다. 나머지 스레드는 첫 커넥션을 기다린다.






힌트 2 — 고치기


@EnableAsync + 알림 전용 ThreadPoolTaskExecutor(코어·최대 2, 큐 수천, 넘치면 로그만 남기고 버리기)를 빈으로 만들고, 리스너 두 메서드에 @Async("그 빈 이름")을 @TransactionalEventListener와 함께 단다. 요청 스레드는 커밋 직후 커넥션을 반납하고, 알림은 스레드 수만큼만 커넥션을 쓴다.
