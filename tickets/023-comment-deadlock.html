#T-023. 같은 글에 댓글이 몰리면 500 — 교착 상태

난이도 고급 · 유형 버그 · DB community · 예상 75분

#티켓

요청자 운영 · 배경 라이브 방송 공지 글에 댓글이 한꺼번에 달리자 "댓글 등록 실패"가 쏟아졌다. 서버 로그에는 Deadlock found when trying to get lock; try restarting transaction이 수십 줄. 좋아요는 같은 시간에 몰려도 멀쩡했다.

  • 같은 글에 여러 회원이 동시에 댓글을 달아도 모두 저장되게 고쳐 주세요(재시도해 달라고 사용자에게 떠넘기지 않는다).
  • 글의 댓글 수(commentCount)는 실제 댓글 수와 같아야 합니다.
  • 원인을 로그와 DB 잠금 정보로 설명해 주세요 — "동시에 와서"가 아니라 어떤 잠금 두 개가 서로를 기다렸는지.
  • 완료 조건: 서로 다른 회원 8명이 같은 글에 동시에 댓글을 달면 8개 모두 201, 댓글 수가 정확히 8 오른다.

DB 시작 상태: community 처음 상태(이 저장소 루트에서 docker compose down -v && docker compose up -d — community·practice·project 세 DB를 모두 지우고 docker/mysql/init/의 처음 상태로 다시 만든다(project는 빈 DB, CloudBeaver 작업 공간도 초기화). 남길 데이터가 있으면 먼저 ./docker/mysql/dump.sh로 세 DB를 docker/mysql/backup/<시각>/에 SQL 파일로 떠 둔다. CloudBeaver에 저장한 SQL 스크립트·바꾼 설정은 이 백업에 들어가지 않으니 따로 복사해 둔다 — 미리 만든 연결 세 개는 다시 들어간다). 기준 코드로 앱을 켜면 Flyway가 V2V6을 적용한다. 글 14(자유 게시판, 이스프링의 공개 글)에 동시성 회원 tok-c01tok-c08이 댓글을 단다.

#채점 기준


C = HTTP(필수), D = DB(필수, SELECT만), T = 테스트(선택), R = 코드 리뷰(피드백)

확인 방법
기대





C1
요청 P
8개 모두 201




C2
요청 P
8개 응답의 댓글 id가 모두 다르다 — 실제로 8개가 저장됐다




C3
요청 A·B
B의 commentCount = A의 commentCount + 8




D1
SELECT p.comment_count, (SELECT COUNT(*) FROM comment c WHERE c.post_id = p.id AND c.deleted_at IS NULL) AS real_count FROM post p WHERE p.id = 14
두 값이 같다




D2
(재현 때) SHOW ENGINE INNODB STATUS — LATEST DETECTED DEADLOCK
두 트랜잭션이 모두 post 행 14에 lock mode S를 쥐고 lock_mode X를 기다린다(SELECT가 아니지만 읽기 전용 확인이라 허용)




T1
(선택) 동시성 테스트
스레드 8개로 같은 글에 댓글 작성 → 예외 0, comment_count = 실제 행 수. 고치기 전 코드에서는 실패해야 한다




R1
원인
INSERT의 외래키 확인이 부모 행(글 14)에 공유 잠금(S)을 걸고, 같은 트랜잭션의 UPDATE post가 배타 잠금(X)으로 올리려다 서로의 S에 막힌다(S→X 승격 교착). SELECT를 하지 않았는데 잠금이 생기는 이유를 말할 수 있다




R2
고친 방법
잠금 순서를 바꿨다 — 글 행의 X를 먼저 잡고(UPDATE 먼저, 또는 SELECT … FOR UPDATE) 그다음 INSERT. "교착 상태면 재시도"(좋아요 서비스 방식)와 비교해 무엇이 다른지(재시도는 증상을 흡수, 순서는 고리를 없앤다), 둘을 함께 쓰는 경우를 말할 수 있다




R3
대가
같은 글의 댓글 작성이 한 줄로 선다(처리량 상한). 다른 글끼리는 막지 않는다. 좋아요 작성(같은 S→X 모양)과 댓글 작성이 동시에 오면 무엇이 일어날 수 있는지

#힌트 (막힐 때만)



힌트 1 — 잠금 읽기


재현 직후 docker compose exec -T mysql mysql -uroot -proot -e "SHOW ENGINE INNODB STATUS\G" | sed -n '/LATEST DETECTED DEADLOCK/,/WE ROLL BACK/p'. 두 트랜잭션 모두 HOLDS THE LOCK(S): … index PRIMARY of table community.post … lock mode S locks rec but not gap이고 WAITING FOR THIS LOCK … lock_mode X다. S는 누가 걸었을까 — 같은 트랜잭션에서 방금 실행한 insert into comment를 본다.






힌트 2 — 고치기


댓글 서비스의 작성 메서드에서 postRepository.incrementCommentCount(postId)를 commentRepository.save(...) 앞으로 옮긴다(comment는 IDENTITY라 save가 바로 INSERT를 보낸다). UPDATE가 먼저 X를 잡으면 뒤의 INSERT 외래키 확인은 이미 쥔 잠금으로 통과하고, 같은 글의 다른 요청은 UPDATE에서 줄을 선다.
