#T-021. 글에 "마지막 댓글 시각" — 컬럼 추가와 다른 테이블에서 백필

난이도 중급 · 유형 스키마 변경 · DB practice · 예상 90분

#티켓

요청자 기획 · 배경 질문 게시판에서 "답이 달린 지 오래된 질문"을 골라 보여 주고, 목록 카드에 "마지막 댓글 3일 전"을 붙이려 한다. 지금은 글마다 댓글 목록을 불러 가장 최근 것을 찾아야 한다.

  • 글에 마지막 댓글 시각을 저장해 상세와 목록 응답에 내려 주세요. 기준은 삭제되지 않은 댓글(답글 포함) 중 가장 최근 작성 시각, 그런 댓글이 없으면 null입니다.
  • 기존 글에도 값이 채워져 있어야 합니다(백필). 운영 DB이므로 Flyway 마이그레이션으로 합니다.
  • 댓글이 달리거나 지워질 때 값이 맞게 바뀌어야 합니다 — 가장 최근 댓글이 지워지면 그 전 댓글 시각으로 돌아갑니다.
  • 완료 조건: 마이그레이션 직후와 댓글 작성·삭제 뒤 어느 시점에 봐도 모든 글의 값이 "살아 있는 댓글의 최댓값"과 같다.

DB 시작 상태: practice 처음 상태(이 저장소 루트에서 docker compose down -v && docker compose up -d — community·practice·project 세 DB를 모두 지우고 docker/mysql/init/의 처음 상태로 다시 만든다(project는 빈 DB, CloudBeaver 작업 공간도 초기화). 남길 데이터가 있으면 먼저 ./docker/mysql/dump.sh로 세 DB를 docker/mysql/backup/<시각>/에 SQL 파일로 떠 둔다. CloudBeaver에 저장한 SQL 스크립트·바꾼 설정은 이 백업에 들어가지 않으니 따로 복사해 둔다 — 미리 만든 연결 세 개는 다시 들어간다). 기준 코드를 practice 프로파일로 켜면 Flyway가 V2~V6을 적용한다 — 다음 마이그레이션 번호는 V7. 댓글 351개 중 25개가 삭제돼 있고, 글 29처럼 댓글이 지워진 것뿐인 글이 5개, 글 100처럼 가장 최근 댓글만 지워진 글도 있다. 글 138은 댓글이 없다.

#지금 코드

  • 이미 "컬럼 추가 → 기존 행 채우기 → 제약"을 한 마이그레이션이 하나 있다. 그때는 같은 행의 값으로 채웠다. 이번에는 다른 테이블(댓글)을 모아서 채워야 한다.
  • 댓글 작성·삭제가 글의 댓글 수(comment_count)를 어떻게 함께 바꾸는지 본다. 같은 트랜잭션, 같은 방식으로 새 값도 바꾼다.
  • 글 응답 DTO가 여러 개다. 이번에 넣을 곳은 상세와 목록(검색 포함)이다.

#만들 것

항목 내용
마이그레이션 V7__<설명>.sql — post.last_commented_at DATETIME NULL 추가 + 기존 글 백필(삭제 안 된 댓글의 MAX(created_at), 없으면 NULL). NULL은 "댓글 없음"이라는 뜻이라 NOT NULL로 바꾸지 않는다

D1
SELECT COUNT(*) FROM post p WHERE NOT (p.last_commented_at <=> (SELECT MAX(c.created_at) FROM comment c WHERE c.post_id = p.id AND c.deleted_at IS NULL))
0 — 모든 글이 "살아 있는 댓글의 최댓값"과 같다(<=>는 NULL끼리도 같다고 본다). 버튼 확인을 몇 번 돌린 뒤에도 0




D2

46 — 댓글 없는 41개 + 지워진 댓글뿐인 5개(지운 댓글까지 센 백필이면 41)




D3
SELECT column_name, is_nullable, data_type FROM information_schema.columns WHERE table_schema = DATABASE() AND table_name = 'post' AND column_name = 'last_commented_at'
last_commented_at YES datetime

R1
백필 SQL
글마다 상관 서브쿼리를 도는 대신 UPDATE post p JOIN (SELECT post_id, MAX(created_at) … GROUP BY post_id) c ON …처럼 집계 한 번으로 채웠다(또는 둘을 비교해 말할 수 있다). 수백만 행이면 id 범위로 나눠 돌리는 이유도 안다




R2
쓰기 경로
댓글 저장·삭제와 같은 트랜잭션에서, 읽고 계산해 엔티티에 넣지 않고 조건부 UPDATE(더 최근일 때만)·재계산 UPDATE로 바꿨다 — 동시에 댓글 두 개가 달려도 값이 뒤로 가지 않는다




R3
비정규화 대가
이 값은 comment_count처럼 어긋날 수 있는 비정규화 값이다. 어긋날 수 있는 경로(직접 DB 수정, 나중에 생길 댓글 복구 기능 등)와 맞추는 방법(정합성 배치에 포함 등)을 말할 수 있다

#힌트 (막힐 때만)



힌트 1 — 마이그레이션


ALTER TABLE post ADD COLUMN last_commented_at DATETIME NULL;
UPDATE post p
  JOIN (SELECT post_id, MAX(created_at) AS m FROM comment WHERE deleted_at IS NULL GROUP BY post_id) c
    ON c.post_id = p.id
   SET p.last_commented_at = c.m;


WHERE deleted_at IS NULL을 빼면 D2가 41이 되고 C2(글 29·100)가 틀린다.






힌트 2 — 댓글 작성·삭제


글 저장소에 @Modifying 쿼리 두 개: 작성은 UPDATE Post p SET p.lastCommentedAt = :at WHERE p.id = :id AND (p.lastCommentedAt IS NULL OR p.lastCommentedAt < :at), 삭제는 UPDATE Post p SET p.lastCommentedAt = (SELECT MAX(c.createdAt) FROM Comment c WHERE c.post.id = :id AND c.deletedAt IS NULL) WHERE p.id = :id. 댓글 서비스에서 comment_count를 바꾸는 바로 옆에서 부른다. 삭제 쪽은 soft delete가 DB에 먼저 반영돼야 하니(변경 감지는 커밋 때) 그 전에 flush하거나 순서를 맞춘다.
