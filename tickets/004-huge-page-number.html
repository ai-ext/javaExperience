#T-004. 아주 큰 페이지 번호에 엉뚱한 글·500

난이도 쉬움 · 유형 버그 · DB community · 예상 25분

#티켓

요청자 운영(모니터링 알림) · 배경 새벽에 크롤러가 page=2147483647로 목록을 긁으면서 500이 수십 건 났다. 확인해 보니 page=429496730&size=10은 500도 안 나고 첫 페이지 근처의 글을 돌려준다(빈 목록이어야 하는데).

  • 게시판 글 목록과 조합 검색 두 API 모두 해당됩니다.
  • 팀 결정: 페이지 번호는 0~1000만 받는다(그 뒤를 보는 사람은 없다 — 더 보려면 검색 조건을 좁힌다). 넘으면 size 범위를 벗어났을 때처럼 400.
  • 완료 조건: 어떤 page 값에도 500이나 "다른 페이지의 글"이 나오지 않는다. 정상 페이지 동작은 그대로.

DB 시작 상태: community 처음 상태(이 저장소 루트에서 docker compose down -v && docker compose up -d — community·practice·project 세 DB를 모두 지우고 docker/mysql/init/의 처음 상태로 다시 만든다(project는 빈 DB, CloudBeaver 작업 공간도 초기화). 남길 데이터가 있으면 먼저 ./docker/mysql/dump.sh로 세 DB를 docker/mysql/backup/<시각>/에 SQL 파일로 떠 둔다. CloudBeaver에 저장한 SQL 스크립트·바꾼 설정은 이 백업에 들어가지 않으니 따로 복사해 둔다 — 미리 만든 연결 세 개는 다시 들어간다). 기준 코드로 앱을 켜면 Flyway가 V2~V6을 적용한다. 자유 게시판(free)에서 비로그인이 볼 수 있는 글은 13개다.

#지금 코드

  • 먼저 재현한다: 아래 요청 A·B를 기준 코드에 보내고, 500이 날 때 서버 로그의 예외 메시지를 읽는다.
  • 목록·검색이 함께 쓰는 쿼리 조립기가 OFFSET(몇 번째 행부터)을 어떻게 넘기는지 본다. page × size가 어떤 타입으로 계산되고 어떤 타입으로 바뀌는지가 핵심이다.
  • size 상한은 이미 걸려 있다. 같은 방식으로 page에도 걸 수 있다.

원인

R2
고친 곳
입력 경계(컨트롤러 파라미터 검증)에서 막았다. 두 API에 같은 상한을 쓰도록 한 곳에 상수로 두면 더 좋다

#힌트 (막힐 때만)



힌트 1 — 숫자 계산


PageRequest.getOffset()은 long이다(429496730 × 10 = 4294967300). 그걸 (int)로 바꾸면 2³²(4294967296)를 뺀 4가 된다. page=2147483647(size 10)이면 음수가 되어 Hibernate가 예외를 던진다.






힌트 2 — 고치기


size에 이미 붙어 있는 @Max(50)처럼 page에 @Max(1000)을 붙인다(두 컨트롤러). 숫자는 상수 하나로 둔다. 쿼리 쪽 (int)는 Math.toIntExact(...)로 바꾸면 넘칠 때 조용히 틀리지 않고 예외로 드러난다.
