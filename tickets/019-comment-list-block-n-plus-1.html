#T-019. 댓글 목록 N+1 — 로그인하면 쿼리가 댓글 수만큼

난이도 중급 · 유형 성능 · DB practice · 예상 60분

#티켓

요청자 DBA · 배경 인기 글의 댓글 목록 API가 슬로우 쿼리는 아닌데 DB 초당 쿼리 수 1위다. 앱 로그를 보니 로그인한 사람이 댓글 목록을 한 번 열면 member_block을 조회하는 짧은 쿼리가 댓글 수의 두 배쯤 나간다. 비로그인은 2개뿐이다.

  • 댓글 목록 API의 쿼리 수를 댓글 수와 상관없이 일정하게 줄여 주세요. 응답(누가 보이고 누가 숨는지, 순서, 모양)은 한 글자도 바뀌면 안 됩니다.
  • 쿼리 수가 다시 늘지 않게 테스트로 고정해 주세요. 이번 티켓은 그 테스트(T1)까지가 완료 조건입니다.
  • 완료 조건: 로그인 사용자가 댓글 8개짜리 글의 목록을 열 때 SQL 문장이 지금 20개 → 6개 이하, 댓글이 늘어도 그대로. 차단 규칙 결과는 지금과 같다.

DB 시작 상태: practice 처음 상태(이 저장소 루트에서 docker compose down -v && docker compose up -d — community·practice·project 세 DB를 모두 지우고 docker/mysql/init/의 처음 상태로 다시 만든다(project는 빈 DB, CloudBeaver 작업 공간도 초기화). 남길 데이터가 있으면 먼저 ./docker/mysql/dump.sh로 세 DB를 docker/mysql/backup/<시각>/에 SQL 파일로 떠 둔다. CloudBeaver에 저장한 SQL 스크립트·바꾼 설정은 이 백업에 들어가지 않으니 따로 복사해 둔다 — 미리 만든 연결 세 개는 다시 들어간다). 기준 코드를 practice 프로파일로 켜면(./gradlew bootRun --args='--spring.profiles.active=practice') Flyway가 V2~V6을 적용한다. 글 97(작성자 회원 4)에 댓글 8개(최상위 6·답글 2)가 있다. 회원 7은 회원 2를, 14는 3을 차단했고 10↔11은 서로 차단했다. 토큰은 tok-p07처럼 tok-p + 회원 번호 두 자리.

#지금 코드

  • 먼저 잰다: 앱 로그(org.hibernate.SQL)에서 tok-p07로 글 97의 댓글 목록을 한 번 열 때 찍히는 SQL을 센다. 같은 모양의 짧은 쿼리가 반복되는 곳을 찾는다.
  • "여러 건을 한꺼번에 판정할 때"를 위한 메서드가 이미 준비돼 있다. 북마크 목록이 그것을 어떻게 쓰는지 본다.
  • SQL 수를 세는 테스트도 이미 하나 있다(목록 API용). 같은 방법을 쓴다.

#채점 기준


C = HTTP(필수), D = DB(필수, SELECT만), T = 테스트(이 티켓은 필수), R = 코드 리뷰(피드백)

확인 방법
기대





C1
요청 A
비로그인: 최상위 6개 + 답글 2개 그대로




C2
요청 B
회원 7: 회원 2의 댓글 172만 빠진다




C3
요청 C
회원 10: 회원 11의 답글 253만 빠진다(답글 단위 판정)




C4
요청 D
회원 14: 회원 3의 최상위 221이 답글째 빠진다




D1
SELECT CASE WHEN blocker_id = 7 THEN blocked_id ELSE blocker_id END AS other FROM member_block WHERE blocker_id = 7 OR blocked_id = 7
2 한 행 — 고친 코드가 요청당 한 번 보내는 바로 그 조회. 이 결과만으로 C2를 판정할 수 있다




D2
SELECT id, member_id, parent_id FROM comment WHERE post_id = 97 AND deleted_at IS NULL ORDER BY created_at, id
8행 — C1과 같고, 작성자 2·11·3이 C2~C4에서 빠진 그 댓글들이다




T1
쿼리 수 테스트(필수)
Statistics.getPrepareStatementCount()로 로그인 상태 댓글 목록의 SQL 수를 센다: 6 이하, 그리고 그 글에 댓글을 몇 개 더 단 뒤에도 늘지 않는다. 기준 코드에서는 실패해야 한다(먼저 돌려 본다)




R1
원인
차단 판정이 댓글·답글마다 exists 2번(양방향)이었다는 것을 로그 줄 수로 보여 줄 수 있다. 댓글은 fetch join으로 한 번에 읽었는데도 N+1이 생길 수 있다는 점(연관 로딩이 아니라 "반복문 안의 조회")




R2
고친 방법
이미 있는 "차단 관계 id 한꺼번에" 메서드를 재사용하고, 판정은 Set.contains로 했다. 차단 규칙(양방향, 최상위째 제외, 답글 단위 제외)을 새로 쓰지 않았다




R3
측정
고치기 전후 숫자(20 → 6 이하)를 직접 쟀고, 테스트가 그 숫자를 지킨다. 실제 시간이 아니라 문장 수로 고정하는 이유를 말할 수 있다

#힌트 (막힐 때만)



힌트 1 — 고칠 곳


댓글 서비스의 목록 메서드가 최상위·답글을 돌면서 blockPolicy.isBlockedEitherWay(viewerId, 작성자 id)를 부른다. 그 전에 Set<Long> blocked = viewer == null ? Set.of() : blockPolicy.blockRelatedIds(viewerId)를 한 번 읽고, 반복문 안에서는 blocked.contains(작성자 id)만 본다.






힌트 2 — 테스트


기존 목록 SQL 수 테스트처럼 @SpringBootTest @AutoConfigureMockMvc에서 Statistics를 clear() → 요청 → getPrepareStatementCount(). 테스트 DB는 시나리오용 데이터라 글 11(댓글 6개)과 tok-kimjava(한차단에게 차단당함)로 잰다. "댓글이 늘어도 늘지 않는다"는 테스트 메서드에 @Transactional을 붙이고 MockMvc로 댓글을 몇 개 더 단 뒤 다시 잰다(끝나면 되돌려진다). 이때 요청들이 한 트랜잭션·한 영속성 컨텍스트를 공유해서 두 번째 측정은 글·토큰 조회가 1차 캐시로 빠져 오히려 줄 수 있다 — 그래서 같다가 아니라 늘지 않는다(≤)로 단언한다.
