#T-002. 글 상세에 '수정됨' 표시

난이도 쉬움 · 유형 기존 API 변경 · DB community · 예상 25분

#티켓

요청자 기획 · 배경 댓글로 "글 내용이 바뀌었는데 몰랐다"는 문의가 왔다. 다른 커뮤니티처럼 수정된 글에는 작성 시각 옆에 "(수정됨)"과 마지막 수정 시각을 보여 주고 싶다.

  • 글 상세 응답에 마지막 수정 시각과 "수정된 적 있음" 여부를 넣어 주세요. 글 수정 API의 응답도 상세와 같은 모양이라 같이 바뀌어야 합니다.
  • 조회수·좋아요가 늘어난 건 "수정"이 아닙니다.
  • 완료 조건: 기존 필드는 그대로 두고 두 필드만 추가된다.

DB 시작 상태: community 처음 상태(bash scripts/java-db.sh --reset). 기준 코드로 앱을 켜면 Flyway가 V2~V6을 적용한다. 글 2는 한 번도 고친 적 없는 글, 글 6(이스프링의 팔로워 공개 글)은 작성 뒤에 고친 글이다.

#지금 코드

  • 글 상세 조회와 글 수정은 같은 응답 DTO를 쓰지만, DTO를 만드는 곳이 두 군데다(조회 쪽 서비스와 수정 쪽 컨트롤러). 둘 다 찾는다.
  • 테이블에는 이미 마지막 수정 시각 컬럼이 있고, 엔티티도 그 값을 갖고 있다. 어느 동작이 그 값을 바꾸고 어느 동작은 안 바꾸는지 엔티티 메서드를 읽어 본다.

#화면 시나리오

글 상세 — 수정됨 표시

상세 응답의 edited로 '(수정됨)'을 붙이고, updatedAt을 툴팁으로 보여 준다.

제목 고치기 → 수정됨
  1. 사용자

    작성자가 제목을 고치고 [수정 저장]을 누른다

  2. HTTP 요청

    PATCH /api/posts/3

    headers
    Authorization: Bearer tok-park · Content-Type: application/json
    body
    {"title": "인덱스는 언제 타나요? (수정)"}
  3. 서버

    수정 서비스가 updated_at을 지금으로 바꾼다 — 응답 DTO도 상세와 같은 모양이라 edited가 true로 온다

  4. DB

    sql
    UPDATE post SET title = ?, updated_at = ? WHERE id = 3
  5. HTTP 응답

    status
    200
    body
    { "id": 3, "title": "인덱스는 언제 타나요? (수정)", ..., "updatedAt": "2026-10-09T17:30:00", "edited": true }
  6. 화면

    작성 시각 옆에 '(수정됨)'이 붙는다

#만들 것

GET /api/posts/{id}(상세)와 PATCH /api/posts/{id}(수정) 응답에 두 필드를 더한다. 나머지 필드·상태 코드·권한 규칙은 그대로다.

필드 타입 값
updatedAt ISO-8601 문자열 글의 마지막 수정 시각(post.updated_at)
edited 불리언 updatedAt이 createdAt보다 늦으면 true, 같으면 false
  • 조회(조회수 +1)·좋아요·댓글 수 변화는 updated_at을 바꾸지 않으므로 edited도 바뀌지 않는다.
  • DB 변화 없음(스키마 그대로). 수정 API가 원래 updated_at을 바꾸던 동작도 그대로다.

#직접 확인

BASE=http://localhost:8080

# 요청 A — 한 번도 고친 적 없는 글
curl -s "$BASE/api/posts/2"

# 요청 B — 고친 적 있는 글(팔로워 공개라 작성자 토큰으로)
curl -s "$BASE/api/posts/6" -H 'Authorization: Bearer tok-lee'

# 요청 C — 글 3의 제목을 작성자가 고친다
curl -s -X PATCH "$BASE/api/posts/3" -H 'Authorization: Bearer tok-park' -H 'Content-Type: application/json' \
  -d '{"title":"인덱스는 언제 타나요? (수정)"}'

# 요청 D — 고친 글 3을 다시 본다
curl -s "$BASE/api/posts/3"

#채점 기준


C = HTTP(필수), D = DB(필수, SELECT만), R = 코드 리뷰(피드백)

요청 D
edited: true, updatedAt이 createdAt(2026-09-18T14:30:00)과 다르다(DB에 수정 시각이 저장됐다). 기존 필드(조회수·좋아요 수·댓글 수·작성자)는 그대로 있다




D1
SELECT id, created_at, updated_at, updated_at > created_at AS edited FROM post WHERE id IN (2, 3, 6) ORDER BY id
글 2 0, 글 3 1(요청 C 이후), 글 6 1 — 응답의 edited와 같다




R1
계산 위치
"수정됨" 판정이 한 곳(엔티티 메서드 등)에 있다. DTO를 만드는 두 곳에서 각자 비교식을 쓰지 않는다




R2
두 DTO 생성 지점
상세·수정 응답을 만드는 코드가 두 군데라는 걸 찾았다. 하나만 고쳐서 수정 응답에 필드가 빠지지 않는다(C3)




R3
시각 비교
LocalDateTime은 isAfter로 비교한다. ==나 문자열 비교를 쓰지 않는다

#힌트 (막힐 때만)



힌트 1 — 어디를 고치나


상세 응답 record에 LocalDateTime updatedAt, boolean edited를 추가하면 컴파일 에러가 나는 곳이 바로 고칠 곳이다(생성자 호출이 두 군데). 테스트 코드에서 같은 record를 만들고 있으면 거기도 맞춘다.






힌트 2 — 판정


엔티티에 public boolean isEdited() { return updatedAt.isAfter(createdAt); }를 두고 두 곳에서 부른다.
