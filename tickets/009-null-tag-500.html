#T-009. 태그에 null이 섞이면 500

난이도 쉬움 · 유형 버그 · DB community · 예상 20분

#티켓

요청자 운영(에러 알림) · 배경 글 작성 API에서 500이 간헐적으로 난다. 프론트 로그를 보니 태그 입력칸을 하나 추가했다가 비워 두면 "tags": ["spring", null]처럼 null이 섞여 간다.

  • 프론트도 고치겠지만, 서버는 어떤 입력에도 500을 내면 안 됩니다. 잘못된 입력이니 다른 검증 오류처럼 400과 errors(어느 필드가 왜)를 돌려주세요.
  • 완료 조건: null이 섞인 작성 요청은 400이고 글은 저장되지 않는다. 정상 요청·태그 없는 요청은 그대로 201.

DB 시작 상태: community 처음 상태(이 저장소 루트에서 docker compose down -v && docker compose up -d — community·practice·project 세 DB를 모두 지우고 docker/mysql/init/의 처음 상태로 다시 만든다(project는 빈 DB, CloudBeaver 작업 공간도 초기화). 남길 데이터가 있으면 먼저 ./docker/mysql/dump.sh로 세 DB를 docker/mysql/backup/<시각>/에 SQL 파일로 떠 둔다. CloudBeaver에 저장한 SQL 스크립트·바꾼 설정은 이 백업에 들어가지 않으니 따로 복사해 둔다 — 미리 만든 연결 세 개는 다시 들어간다). 기준 코드로 앱을 켜면 Flyway가 V2~V6을 적용한다.

#지금 코드

  • 먼저 재현한다: 아래 요청 A를 기준 코드에 보내고 서버 로그의 예외를 끝까지(맨 아래 Caused by) 읽는다. 어느 계층에서 터지는지가 단서다.
  • 작성 요청의 태그 목록에는 원소마다 길이 검증이 걸려 있다. 그 검증이 null을 어떻게 다루는지 본다.
  • 같은 태그를 받는 수정 API는 null을 이미 400으로 막는다 — 두 API가 다르게 검증하는 이유를 찾는다.

#힌트 (막힐 때만)



힌트 1 — 로그


원인은 NullPointerException이고, 스택의 첫 우리 코드는 글 서비스의 태그 중복 제거 메서드다(List.copyOf는 null 원소를 받지 않는다). 요청 검증을 통과했기 때문에 서비스까지 간 것이다. 서비스 쪽을 null에 안전하게 바꿔도 이번엔 null 이름의 태그를 저장하려다 또 터진다 — 입구에서 막는 게 맞다.






힌트 2 — 한 줄


요청 record의 List<@Size(min = 1, max = 30, …) String> tags에서 원소 쪽에 @NotNull(message = "태그 이름은 1~30자여야 합니다.")을 더한다. 실패하면 이미 있는 전역 핸들러가 errors: [{"field": "tags[0]", …}]로 400을 만든다.
