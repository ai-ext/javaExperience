#T-027. 뒤쪽 페이지가 느리고 글이 겹친다 — 커서 페이징, 옛 앱 호환

난이도 고급 · 유형 성능 · DB practice · 예상 90분

#티켓

요청자 모바일 앱 팀·DBA · 배경 앱이 게시판을 무한 스크롤로 바꾸면서 page=0,1,2…를 계속 늘려 부른다. DBA: "개발 게시판 목록 쿼리가 뒤로 갈수록 읽는 행이 늘어난다, 운영 글 수면 수백 페이지째에서 수십만 행을 읽고 버린다." 앱 팀: "스크롤 중에 새 글이 올라오면 방금 본 글이 다음 묶음에 또 나온다."

  • 게시판 글 목록을 커서로도 받을 수 있게 해 주세요. 응답에 다음 묶음용 커서(nextCursor)를 주고, 앱은 그 값을 그대로 다시 보냅니다(앱은 커서를 열어 보지 않는다).
  • 커서로 받는 다음 묶음은 그사이 새 글이 올라와도 겹치거나 빠지지 않아야 합니다.
  • 커서 요청에서는 전체 건수를 세지 마세요(무한 스크롤은 전체 쪽수를 안 쓴다) — 그 필드들은 null.
  • 옛 앱이 남아 있습니다. page 번호 방식은 그대로 동작해야 하고, 응답 모양은 필드가 늘어나기만 해야 합니다(첫 페이지는 page로 받고 그다음부터 커서로 넘어갈 수 있게, page 응답에도 nextCursor).
  • 완료 조건: 첫 묶음 → 새 글 등록 → 커서로 다음 묶음을 받으면, 새 글이 올라오기 전의 2페이지와 정확히 같다. 깨진 커서는 400.

DB 시작 상태: practice 처음 상태(bash scripts/java-db.sh --reset). 기준 코드를 practice 프로파일로 켠다. 개발 게시판(dev)에 비로그인으로 볼 수 있는 글이 50개 있다. 새 글은 코딩하는고양이(tok-p02)가 쓰고 마지막에 지운다.

#만들 것

항목 내용
요청 GET /api/boards/{slug}/posts?size=&cursor= — cursor가 있으면 커서 방식(page는 무시), 없으면 지금의 page 방식
응답(공통) 지금 필드 + nextCursor(문자열, 다음이 없으면 null)
커서 방식 응답 items·size·hasNext·nextCursor. 전체 건수를 세지 않으므로 page·totalElements·totalPages는 null
순서·경계 지금 목록과 같은 순서(발행 시각 최신 → id 큰 순). 같은 시각의 글도 겹치거나 빠지지 않는다
오류 깨진 커서 400, 없는 게시판 404(지금과 같다)
그대로인 것 page 방식의 결과·필드, 볼 수 있는 글 규칙(로그인·팔로우·차단), 목록 SQL 수

D1
EXPLAIN ANALYZE SELECT id FROM post WHERE board_id = 2 AND deleted_at IS NULL AND status = 'PUBLISHED' AND visibility = 'PUBLIC' ORDER BY published_at DESC, id DESC LIMIT 5 OFFSET 45
10페이지째(오프셋) — 게시판의 인덱스 항목을 전부 읽어(처음 상태 62행, 버튼 확인 한 번마다 지운 글이 1행씩 는다) 거른 50행 중 45행을 버리고 5행을 쓴다(Index lookup … rows=62, Filter … rows=50, Limit/Offset: 5/45)




D2
EXPLAIN ANALYZE SELECT id FROM post WHERE board_id = 2 AND deleted_at IS NULL AND status = 'PUBLISHED' AND visibility = 'PUBLIC' AND (published_at < '2026-07-12 08:12:05' OR (published_at = '2026-07-12 08:12:05' AND id < 18)) ORDER BY published_at DESC, id DESC LIMIT 5
같은 위치(45번째 글 18 뒤)를 커서로 — Index range scan on post using ix_post_board_published … rows=5, 읽은 행 5




T1
(선택) 테스트
커서로 받은 묶음 = page=1 결과, 커서 요청의 SQL 문장 수에 COUNT가 없다(통계로 센다), 깨진 커서 400




R1
왜 빠른가·왜 안 겹치나
오프셋은 버릴 행까지 읽는다(깊을수록 선형), 키셋은 정렬 키 위치부터 인덱스를 읽다가 멈춘다. 정렬 키에 **유일한 마지막 키(id)**가 있어야 같은 시각의 글이 겹치거나 빠지지 않는다. (board_id, published_at, id) 인덱스 순서와 조건 모양이 맞아야 range scan이 된다




R2
호환
기존 필드를 바꾸지 않고 늘리기만 했다(옛 앱은 nextCursor를 무시). 커서 응답에서 null이 되는 필드를 옛 방식에선 그대로 채운다. 커서를 불투명한 문자열로 둔 이유(정렬 키를 바꿔도 클라이언트가 안 바뀐다)




R3
대가
커서는 "임의의 N페이지로 점프"가 안 된다, 정렬 기준을 바꾸면(좋아요순 등) 커서 키도 바뀐다, 커서에 든 값은 위조될 수 있다(조건으로만 쓰고 권한 판단에 쓰지 않는다)

#힌트 (막힐 때만)



힌트 1 — 이미 있는 것


"내가 좋아요한 글"과 "내 북마크"가 이미 (시각, id) 커서를 쓴다 — 커서를 감싸고 푸는 클래스(깨지면 400)를 그대로 쓴다. 게시판 목록 쿼리를 조립하는 저장소에 "같은 조건 + 커서 뒤" 메서드를 하나 더 만든다: publishedAt < at OR (publishedAt = at AND id < id), 같은 정렬, setMaxResults(size + 1) — 하나 더 읽어서 다음이 있는지 안다. COUNT 쿼리는 부르지 않는다.






힌트 2 — 응답 모양


목록 응답 record의 page·totalElements·totalPages를 int·long에서 Integer·Long으로 바꿔야 null을 담을 수 있다. 이 record는 조합 검색도 쓰므로 검색 응답에도 nextCursor 자리가 생긴다(이번 범위에선 null이어도 된다).
