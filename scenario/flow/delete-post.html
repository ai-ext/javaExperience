구현할 일

글을 삭제한 뒤 기존 링크로 돌아가도 보이지 않아야 합니다. DB 행과 태그·좋아요·댓글은 보존합니다.

  1. findById로 글을 찾고 canView 실패를 먼저 404로 처리합니다.
  2. 인증 회원이 작성자 또는 ADMIN인지 검사하고 그 외는 PostForbiddenException을 던집니다.
  3. post.delete(LocalDateTime.now())를 호출해 deletedAt과 updatedAt을 함께 변경합니다.
  4. repository.delete나 연관 삭제를 호출하지 않습니다. Controller의 빈 204 응답을 확인합니다.
  5. 삭제 후 같은 id의 상세·PATCH·DELETE 404와 목록 제외를 확인합니다.

시작 패키지의 실제 코드 · 이번 메서드 본문만 구현

실행 준비 확인 · 처음 시작과 이어서 학습

이미 앞 과제를 구현했다면 같은 프로젝트·서버·DB에서 이어갑니다. 이번에는 delete 메서드 본문만 구현하고, 다음 ZIP을 덮어쓰거나 새 폴더에서 DB를 다시 만들지 않습니다. DB와 Compose는 처음 준비한 한 폴더에서 계속 관리합니다.

아래는 snapshot으로 만든 별도 교육용 패키지의 설정입니다. 저장소 루트의 학생용 src/main/resources/application.yml과 다를 수 있습니다. 준비물은 JDK 21·Docker 런타임·터미널이며, 명령은 압축을 푼 프로젝트 루트에서 실행합니다. 각 명령 블록의 글자를 선택해 복사할 수 있습니다.

실제 요청을 보내는 학습 화면 열기

이미 HTTP 주소로 이 화면을 열었다면 그대로 사용하세요. file://로 열었을 때만, 학습 HTML이 있는 javaExperience 저장소 루트에서 아래 명령을 실행하세요. ZIP을 푼 starter 폴더와는 다릅니다.

python3 -m http.server 3000 --bind 127.0.0.1

현재 학습 화면 열기. 문서 서버는 학습 HTML을 제공하고, 요청을 받는 백엔드 앱 http://localhost:8080과 다릅니다. 앱·DB는 아래 안내대로 별도 starter 폴더에서 실행합니다. 이 안내는 서버를 자동 실행하거나 연결 완료를 판정하지 않습니다.

  1. 새로 시작하거나 중간 합류할 때만 · ZIP과 IDE

    이 과제의 시작 ZIP 받기를 별도의 새 학습 폴더에 풀고 IntelliJ에서 Gradle 프로젝트로 엽니다. 기존 학생 코드 위에 풀지 않습니다. JDK 출력이 21인지 직접 확인합니다.

    java -version
chmod +x gradlew

    명령은 macOS/Linux 기준입니다. Windows에서는 chmod 없이 ./gradlew 대신 gradlew.bat를 씁니다. 자세한 준비 방법은 ZIP의 README-LEARNING.md에 있습니다.

  2. DB가 처음인 경우만 · 처음 준비한 DB 폴더에서

    이미 이 학습용 community DB가 실행 중이면 그대로 사용하고 Compose를 다시 올리지 않습니다. 처음 준비할 때만 Docker 런타임에서 실행합니다.

    DB_PORT=13308 docker compose up -d mysql
docker compose ps mysql

    출력에서 mysql이 healthy인지 직접 확인합니다. 준비되지 않으면 같은 폴더의 docker compose logs mysql로 원인을 확인합니다. 기본 접속은 localhost:13308의 community DB, 계정은 community / community입니다. 기존 DB 데이터는 보존합니다.

  3. 컴파일한 뒤 서버 실행

    ./gradlew compileJava
./gradlew bootRun

    bootRun 터미널은 켜 둡니다. 기본 서버 주소는 http://localhost:8080입니다. 코드 수정 후에는 자동 반영되지 않습니다. 실행 중인 bootRun 터미널에서 Ctrl+C로 앱만 종료하고, 같은 프로젝트 폴더에서 ./gradlew bootRun을 다시 실행합니다. DB·Compose·작성 응답 id는 유지하며, 서버 주소도 그대로 사용합니다. DB 포트를 바꿨다면 앱의 datasource URL도 같은 포트로 지정하는 방법을 ZIP의 README에서 확인하세요.

  4. 다른 터미널에서 연결 확인 · 연습 토큰 준비

    curl -i http://localhost:8080/api/start/ping

    직접 받은 본문이 pong인지 확인합니다. ping은 서버 연결 확인이며 CRUD 메서드 구현 통과를 뜻하지 않습니다. 쓰기 요청의 공개 fixture 토큰 예시는 tok-kimjava이며, community DB의 김자바 회원으로 dev 게시판에 작성할 때 사용합니다. DB 접속 계정과 다릅니다.

    Authorization: Bearer tok-kimjava

    토큰은 요청 폼에 직접 입력하고, 구현을 마친 뒤 전송 버튼으로 요청하세요. 이 안내는 명령·토큰을 자동 실행하거나 입력하지 않습니다. 아직 미구현인 메서드의 실패는 서버 준비 완료나 기능 완성을 증명하지 않습니다.

이번 메서드와 이미 제공된 기반
  • Controller의 경로·HTTP 상태·DTO 변환
  • 요청·응답 DTO, 인증 토큰 확인, 예외 처리
  • PostAccessPolicy와 목록 JPQL의 가시성 조건
  • Repository, Entity의 상태 변경 메서드, 태그·검증 helper
  • MySQL 스키마·연습 fixture·실행 설정
  • 완성된 앞 과제: 게시글 작성 → 게시글 상세 조회 → 게시글 목록 조회 → 게시글 부분 수정

src/main/java/org/example/post/PostService.java의 delete(...) 메서드 본문 한 개를 구현합니다.

계속 학습할 때는 같은 프로젝트·서버·DB에서 다음 메서드만 구현합니다. ZIP은 중간 합류용 새 폴더 초기화 선택지입니다. 기존 사용자 코드 위에 전체 덮어쓰지 마세요. 현재 및 이후 기능은 미구현이므로 이후 API의 미구현 오류는 이번 과제의 실패가 아닙니다.

패키지 컴파일 검사는 서버·DB의 실제 실행을 증명하지 않습니다. 이 화면에서 JDK·DB·서버의 실행 여부를 자동 판정하지 않습니다.

HTTP 204 · 본문 없음

  • 응답 본문 빈 문자열
  • 같은 id GET/PATCH/DELETE는 404
  • 목록에서 capturedId 제외
  • canView 통과한 작성자/ADMIN만 삭제 가능
응답 필드와 실패 조건
    • 401: 인증 없음·오류
    • 403: 비활성 회원 또는 볼 수 있으나 작성자/ADMIN 아님
    • 404: 없는 글·이미 삭제·볼 수 없는 글
    • 연관 행이 원래 0개라면 보존 검증이 충분하지 않습니다. 제공된 삭제 통합 테스트는 일회용 DB에 연결을 넣고 확인합니다.
    • 삭제는 status=HIDDEN 변경과 다릅니다. status는 유지됩니다.

    이 폼의 id는 양의 정수만 허용합니다. 숫자가 아닌 경로의 400을 확인하려면 정상 id로 curl을 복사한 뒤, API 클라이언트에서 경로의 id만 abc로 바꿔 별도로 실행하세요. 복사만으로 요청하지 않습니다.

    직접 DB 확인 · 응답과 별도

    별도 DB 클라이언트에서 새 autocommit SELECT로 관찰합니다. 열린 REPEATABLE READ 트랜잭션은 이전 스냅샷을 볼 수 있습니다.

    DELETE 전·후 · 행과 두 시각

    행은 남고 deleted_at·updated_at에 같은 now가 저장됩니다. 나머지 값은 요청 전에 기록한 값과 같습니다.

    SELECT id, board_id, author_id, title, content, status, visibility,
       view_count, like_count, comment_count,
       created_at, updated_at, published_at, deleted_at
FROM post
WHERE id = :capturedId;

    DELETE 전·후 · 연관 행 수

    삭제 전에 세 수를 기록하고 삭제 후 같은지 비교합니다. 같은 수만으로 행 id·모든 내용의 보존까지 입증하지는 않습니다. 코드에 repository.delete나 연관 삭제 호출이 없는지도 확인합니다. 원래 0개인 관계만으로는 검증이 충분하지 않습니다.

    SELECT
  (SELECT COUNT(*) FROM post_tag WHERE post_id = :capturedId) AS tag_links,
  (SELECT COUNT(*) FROM post_like WHERE post_id = :capturedId) AS likes,
  (SELECT COUNT(*) FROM comment WHERE post_id = :capturedId) AS comments;

    DELETE 전·후 · 태그 원본

    삭제 전에 기록한 tag id·이름이 후에도 남는지 비교합니다. 실제 tag 원본과 글의 post_tag 연결을 별도로 봅니다.

    SELECT id, name
FROM tag
ORDER BY id;

    응답과 DB의 시각은 정밀도를 확인한 뒤 비교하세요. 응답에 소수초가 있고 DB 열이 초 단위라면 문자열 전체가 다를 수 있습니다. 같은 글 id의 값과 실제 열 정밀도를 확인하세요.

    시각 열의 정밀도 확인 SQL

    DATETIME_PRECISION은 소수초 자릿수입니다. 특정 값이 나온다고 가정하지 말고 사용하는 DB에서 확인하세요. 변경되면 안 되는 시각은 같은 DB 열의 요청 전후 값을 비교합니다. 정밀도 차이를 이유로 실제 값 변경을 통과 처리하지 않습니다.

    SELECT COLUMN_NAME, DATETIME_PRECISION
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'post'
  AND DATA_TYPE IN ('datetime', 'timestamp');
SELECT @@session.sql_mode;

    :capturedId는 위 id로 바꿉니다. 목록의 :boardSlug는 따옴표를 포함한 게시판 값(예: 'dev'), :viewerId는 토큰 회원 id 또는 NULL, :size와 :offset은 숫자로 직접 바꿉니다. 위 SQL은 검산용 예시이며 실제 Hibernate 로그가 아닙니다. 이 화면은 DB 쿼리를 실행하거나 저장을 자동 판정하지 않습니다.

    함께 비교할 유지 값 id, title, content, status, visibility, created_at, published_at, view_count, like_count, comment_count, post_tag, tag, post_like, comment

    참고 정답 · delete 메서드

    공통 3-2 snapshot의 파일별 blob과 완성 패키지가 기준입니다. 먼저 직접 구현한 뒤 비교하세요.

    @Transactional
public void delete(Long id, AuthenticatedMember loginMember) {
    Post post = postRepository.findById(id)
            .orElseThrow(PostNotFoundException::new);

    // 404(볼 수 없음·이미 삭제됨) → 403(작성자도 운영자도 아님) 순서
    if (!accessPolicy.canView(loginMember, post)) {
        throw new PostNotFoundException();
    }
    boolean isAuthor = post.getAuthor().getId().equals(loginMember.id());
    boolean isAdmin = ADMIN_ROLE.equals(loginMember.role());
    if (!isAuthor && !isAdmin) {
        throw new PostForbiddenException();
    }

    post.delete(LocalDateTime.now());
}
