#상황

1-3까지 저장한 글을 DB에서 열어 보면 이렇다(1-3 정답 코드로 저장한 행).

id  board_id  author_id  title          status     visibility  published_at  view_count  like_count  comment_count
22  2         2          [채점] 태그 저장  PUBLISHED  PUBLIC      NULL          0           0           0

status·카운트는 엔티티에 없는데 값이 있다. 테이블 기본값(DEFAULT 'PUBLISHED', DEFAULT '0')이 채웠다. published_at은 기본값이 NULL이라 비어 있다. 2장의 게시판 목록은 published_at 최신순으로 정렬하므로, 이 글들은 최신 글인데도 목록 맨 뒤로 밀린다.

엔티티가 테이블의 일부만 알고 있어서 생긴 일이다. 이 단계에서 post 테이블의 컬럼을 하나도 빠짐없이 엔티티에 맞춘다.

  • 모든 컬럼을 매핑하고, 값은 DB 기본값에 맡기지 않고 서버가 정한다(status, published_at, 카운트).
  • author_id를 숫자 필드에서 Member 연관관계로 바꾸고, 응답에 작성자(author)를 싣는다. 로그인은 아직 없으니 작성자는 여전히 김자바(회원 id 2) 고정이다(1-6에서 토큰으로 바꾼다).
  • ddl-auto: validate가 무엇을 잡고 무엇을 못 잡는지, SQL 로그로 실제로 들어간 값을 확인하는 법을 익힌다.

#ddl-auto: validate가 잡는 것과 못 잡는 것

validate는 서버를 켤 때 엔티티가 가리키는 테이블·컬럼이 있는지, 타입이 맞는지만 본다. 아래는 이 단계 정답 코드를 하나씩 바꿔 Spring Boot 4.1.1 · Hibernate 7.4.5에서 재현한 결과다.

엔티티를 이렇게 틀리면 validate가 언제 드러나나
테이블 이름(@Table(name = "posts")) 잡는다 — missing table [posts] 서버를 켤 때
컬럼 이름(@Column(name = "view_cnt")) 잡는다 — missing column [view_cnt] in table [post] 서버를 켤 때
타입(view_count를 String으로) 잡는다 — wrong column type encountered in column [view_count] 서버를 켤 때
NOT NULL인데 기본값 없는 컬럼(updated_at)을 엔티티에서 뺐다 못 잡는다(서버가 뜬다) 저장 요청 때 500 — Field 'updated_at' doesn't have a default value
@Column(nullable = false)를 뺐다(title) 못 잡는다 — 서버가 그대로 뜬다 아무 일도 없다. NULL이 들어가면 그때 DB가 거절한다
CHECK 제약에 없는 값(status에 "OPEN") 못 잡는다 — 값은 서버를 켤 때 알 수 없다 저장 요청 때 500 — Check constraint 'ck_post_status' is violated.

validate는 "엔티티가 아는 것"이 테이블에 있는지를 본다. 엔티티가 모르는 컬럼은 비교하지 않는다. 그래서 1-3까지 status·published_at이 없어도 서버가 떴다. 테이블과 정확히 맞추는 일은 결국 CREATE TABLE과 엔티티를 사람이 대조하는 일이다(위 대조표).

ddl-auto 값의 차이

값 서버를 켤 때 하는 일 이 실습에서
none 아무것도 안 한다. MySQL이면 이 값이 기본이다(줄을 지웠더니 엔티티와 테이블이 달라도 서버가 떴다). 틀린 엔티티가 요청 때에야 500으로 드러난다.
validate 엔티티와 테이블을 비교만 한다. 다르면 서버가 안 뜬다. 실습 레포 기본값. 테이블은 그대로 두고 엔티티를 맞추게 만든다.
update 엔티티에 있는데 테이블에 없는 컬럼·테이블을 추가한다(지우지는 않는다). 쓰지 않는다. 오타 난 컬럼이 조용히 새로 생겨 버린다.
create 켤 때마다 테이블을 지우고 새로 만든다. 쓰면 안 된다. community DB의 시드 데이터(글 21개·회원·게시판)가 사라진다.
create-drop create + 끌 때 또 지운다. 쓰면 안 된다. 위와 같다.

시드가 날아갔다면 javaExperience 레포 루트에서 docker compose down -v && docker compose up -d으로 처음 상태로 되돌린다.

#기본값은 언제 들어가나

DB 기본값(DEFAULT …)은 INSERT의 컬럼 목록에 그 컬럼이 없을 때만 쓰인다. 컬럼을 적고 NULL을 넣으면 "NULL을 넣으라"는 뜻이라 기본값이 쓰이지 않는다.

  • 1-3까지는 엔티티에 status가 없었다 → INSERT 컬럼 목록에 status가 없다 → 기본값 'PUBLISHED'가 들어갔다.
  • visibility는 엔티티에 있다 → Hibernate는 매핑한 컬럼을 항상 INSERT에 적는다 → 요청에서 빠지면 NULL을 넣는다 → NOT NULL이라 거절(Column 'visibility' cannot be null). 관찰 O1이 이것이다.
  • updated_at은 NOT NULL인데 기본값이 없다 → 엔티티에서 빼면 컬럼 목록에서 빠지고, 채울 값이 없어 거절(Field 'updated_at' doesn't have a default value, 아래 "일부러 망가뜨리기" 4번).

그래서 이 실습은 기본값을 서버(엔티티 생성자·서비스)가 정한다. 테이블 기본값은 SQL로 직접 넣을 때를 위한 안전망으로 남겨 둔다. 서버가 정하면 응답과 DB가 어긋날 일이 없고, 코드만 보고도 어떤 값이 들어가는지 알 수 있다.

#SQL 로그 읽기

실습 레포 application.yml의 이 설정 덕분에, Hibernate가 보낸 SQL과 ? 자리에 들어간 값이 로그에 찍힌다.

spring:
  jpa:
    open-in-view: false
    properties:
      hibernate:
        format_sql: true

logging:
  level:
    org.hibernate.SQL: debug
    org.hibernate.orm.jdbc.bind: trace
키 뜻
jpa.open-in-view: false DB 연결을 트랜잭션(서비스 메서드)이 끝나면 바로 돌려준다. 그래서 컨트롤러에서 지연 로딩을 건드리면 에러가 난다(아래 "일부러 망가뜨리기" 6번).
properties.hibernate.format_sql 로그에 찍히는 SQL을 여러 줄로 보기 좋게.
logging.level.org.hibernate.SQL: debug 실행되는 SQL을 로그에 찍는다.
logging.level.org.hibernate.orm.jdbc.bind: trace SQL의 ? 자리에 들어간 값을 찍는다. 1-6부터는 토큰 같은 비밀값도 찍히므로 끈다.

#데이터 넣는 두 가지

post 테이블에 행 하나를 넣는 방법은 크게 둘이다. JPA가 SQL을 만들어 넣게 하거나, 내가 SQL을 직접 쓰거나. 이 실습의 API는 JPA로 만든다. SQL로 넣어 보면 JPA가 대신 해 주는 일과, 테이블 정의(NOT NULL·기본값)가 하는 일이 보인다.

CloudBeaver(http://localhost:8978)라면 community (Java 시나리오) 연결 → SQL 편집기에 INSERT … 문만 붙여 넣고 실행한다.

SQL로 넣어 보면 JPA가 대신 해 주던 일이 다 내 몫이다.

  • NOT NULL이고 기본값 없는 컬럼(created_at·updated_at 등)을 내가 빠짐없이 채워야 한다. 위 INSERT에 없는 view_count 같은 건 테이블 기본값(DEFAULT '0')이 채운다.
  • boardSlug → board_id(dev → 2) 같은 변환을 내가 직접 해야 한다.
  • 태그를 붙이려면 tag에 있는지 먼저 보고, post_tag에 (post_id, tag_id)를 따로 INSERT해야 한다. 이미 있는 태그 이름을 또 INSERT하면 Duplicate entry로 거절된다(tag.name이 UNIQUE). → 에러 도감: 중복 키
  • 앱의 규칙(작성자 고정, 상태 PUBLISHED)을 거치지 않는다. 시험 데이터 넣기에는 편하지만, API의 동작을 확인하는 방법은 아니다.

#JdbcTemplate로 한 줄 넣기 — 그 중간

앱 코드 안에서 SQL을 직접 쓰고 싶을 때는 JdbcTemplate을 쓴다. data-jpa 스타터에 이미 들어 있어서 의존성을 더 넣지 않아도 생성자로 받을 수 있다.

package org.example.tag;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Component;

import java.time.LocalDateTime;

@Component
public class JdbcInsertExample {

    private final JdbcTemplate jdbcTemplate;

    public JdbcInsertExample(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
    }

    public int insertTag(String name) {
        // ? 자리에 값이 순서대로 들어간다(문자열을 이어 붙이지 않는다 — SQL 주입 방지)
        return jdbcTemplate.update(
                "INSERT INTO tag (name, created_at) VALUES (?, ?)",
                name, LocalDateTime.now());
    }
}

재현해 보니 update(...)는 넣은 행 수 1을 돌려줬다. 같은 이름으로 한 번 더 부르면 DuplicateKeyException: … Duplicate entry 'jdbc태그' for key 'tag.uk_tag_name'이 났다.

SQL은 누가 쓰나 Hibernate가 만든다 내가 쓴다(앱 코드 안) 내가 쓴다(앱 밖)
결과를 객체로 엔티티로 자동 내가 매핑(RowMapper) 표로 보기만
언제 쓰나 이 실습의 기본. 객체 단위 저장·수정 통계·대량 처리처럼 SQL이 더 분명할 때 데이터 확인, 시험 데이터 넣기

#일부러 망가뜨리기

다 만들어 통과한 뒤 하나씩 망가뜨려 보고 되돌린다. 메시지는 Spring Boot 4.1.1 · Hibernate 7.4.5에서 이 단계 정답 코드로 재현한 원문이다(경로·시각은 줄였다).

1. 테이블 이름을 틀린다 — @Table(name = "post") → "posts"

Caused by: org.hibernate.tool.schema.spi.SchemaManagementException: Schema validation: missing table [posts]

ddl-auto: validate라서 서버가 안 뜬다. none이었다면 서버는 뜨고, 저장 요청 때 Table 'community.posts' doesn't exist로 500이 난다. 고치는 법 — 엔티티를 테이블 이름에 맞춘다. → 에러 도감: 테이블 없음

2. 컬럼 이름을 틀린다 — @Column(name = "view_count") → "view_cnt"

Caused by: org.hibernate.tool.schema.spi.SchemaManagementException: Schema validation: missing column [view_cnt] in table [post]

[컬럼] in table [테이블]이 어디가 틀렸는지 알려 준다. 참고로 @Column(name=…)을 아예 안 적으면 Boot가 viewCount → view_count로 바꿔 찾아서 통과한다(재현 확인). → 에러 도감: 컬럼 이름 불일치

3. 타입을 틀린다 — private Integer viewCount; → private String viewCount;

Caused by: org.hibernate.tool.schema.spi.SchemaManagementException: Schema validation: wrong column type encountered in column [view_count] in table [post]; found [int (Types#INTEGER)], but expecting [varchar(255) (Types#VARCHAR)]

found가 테이블, expecting이 엔티티 쪽이다. 고치는 법 — 테이블 타입에 맞는 Java 타입(int → Integer)으로.

4. NOT NULL 컬럼을 엔티티에서 뺀다 — updatedAt 필드와 그 매핑을 지운다(같이 title의 nullable = false도 지워 봤다).

  • 서버는 정상으로 뜬다. validate는 엔티티에 없는 컬럼도, nullable도 비교하지 않는다.

  • 저장 요청이 500이다.

    WARN … org.hibernate.orm.jdbc.error : HHH000247: ErrorCode: 1364, SQLState: HY000
WARN … org.hibernate.orm.jdbc.error : Field 'updated_at' doesn't have a default value

  • 고치는 법 — CREATE TABLE에서 NOT NULL인데 DEFAULT가 없는 컬럼은 엔티티에 반드시 매핑하고 서버가 값을 넣는다.

5. CHECK에 없는 상태 값을 넣는다 — 서비스의 "PUBLISHED"를 "OPEN"으로

WARN … org.hibernate.orm.jdbc.error : HHH000247: ErrorCode: 3819, SQLState: HY000
WARN … org.hibernate.orm.jdbc.error : Check constraint 'ck_post_status' is violated.

status는 DRAFT·PUBLISHED·HIDDEN만 받는다(ck_post_status). 서버는 뜨고 저장 때 500이다. 고치는 법 — 테이블의 CHECK를 보고 허용된 값만 쓴다. 값이 정해진 컬럼은 enum + @Enumerated(EnumType.STRING)으로 두면 오타를 컴파일러가 잡는다.

6. 서비스의 @Transactional을 지운다 → 서버는 뜨지만 저장 요청이 500이다.

org.hibernate.LazyInitializationException: Could not initialize proxy [org.example.member.Member#2] - no session
	…
	at org.example.member.Member$HibernateProxy.getNickname(Unknown Source) ~[main/:na]
	at org.example.post.PostService.create(PostService.java:56) ~[main/:na]

getReferenceById(2L)로 받은 작성자는 아직 DB에서 안 읽은 대리 객체(proxy)다. 닉네임을 처음 읽을 때 DB에 가야 하는데, 트랜잭션이 없으니 연결(세션)이 이미 닫혀 있다. @Transactional은 두고 서비스의 "미리 읽어 두기" 두 줄(saved.getAuthor().getNickname(); 등)만 지워도 같은 에러가 컨트롤러(PostController.toResponse)에서 난다. 고치는 법 — 서비스 메서드에 @Transactional을 붙이고, 응답에 필요한 값은 그 안에서 읽어 둔다. → 에러 도감: 지연 로딩 — no session

7. 엔티티의 기본 생성자를 지운다 — Tag에서 protected Tag() {}를 지운다.

org.hibernate.InstantiationException: No default constructor for entity 'org.example.tag.Tag'
	…
	at org.example.post.PostService.create(PostService.java:48) ~[main/:na]

서버는 뜬다. 이미 있는 태그(spring)를 findByName으로 읽어 올 때 500이 난다. JPA는 DB 행을 객체로 만들 때 인자 없는 생성자로 빈 객체부터 만들기 때문이다. 같은 줄을 Post에서 지우면 이 단계의 저장은 201로 성공한다. 글을 읽어 오는 2장에서 터진다. 고치는 법 — 엔티티마다 protected 기본 생성자를 둔다. → 에러 도감: 엔티티 기본 생성자 없음

#구현 가이드

화면 시나리오의 서버·DB 흐름을 이 단계에서 바뀐 파일에 연결한다. 먼저 만들 것의 계약대로 직접 작성하고, 필요한 역할만 펼쳐 파일 전문과 비교한다.

이 단계의 처리 흐름:

  • PostService(@Transactional): 게시판을 찾고, 작성자 2(김자바)를 붙이고, status=PUBLISHED·published_at=지금·카운트 0으로 엔티티를 만든다
  • 13개 컬럼이 모두 들어간다 — 기본값에 맡기는 컬럼이 없다
  • 응답에 쓸 닉네임을 트랜잭션 안에서 읽어 둔다
  • Column 'visibility' cannot be null — 테이블 기본값 'PUBLIC'이 있어도, NULL을 직접 넣으면 기본값은 쓰이지 않는다
Controller — HTTP 연결

PostController.java. 매핑과 메서드의 입력·응답을 위 만들 것의 HTTP 계약과 대조한다.

DTO — 요청·응답 필드

AuthorResponse.java, PostResponse.java. 필드 이름·타입·검증·응답 형태를 위 만들 것과 대조한다.

Service — 처리 순서

PostService.java. 위 서버 처리 순서가 어디에서 검증·조회·상태 변경으로 이어지는지 따라간다. 트랜잭션 경계는 아래 코드의 @Transactional 위치에서 확인한다.

JPA / Repository — DB 조건

MemberRepository.java, PostRepository.java. 쿼리·파생 메서드의 조건을 화면 시나리오의 DB 단계 및 직접 확인 SQL과 대조한다.

Entity — 테이블·상태

Member.java, Post.java. 실제 테이블의 컬럼·외래키와 엔티티 매핑을 대조한다.

MyBatis — 모든 컬럼과 작성자 응답을 SQL로 맞추기

아래 MyBatis 대체 구현 코드의 10개 파일을 이 단계 전체 소스에 적용한다. PostService가 Mapper로 게시판과 회원 2의 id·nickname을 조회한다. JPA의 지연 로딩 대신 필요한 회원 값을 AuthorWriteRow에 먼저 읽고, 서비스가 AuthorResponse를 만들어 컨트롤러에 돌려준다. 이 단계에는 1-5의 게시판 쓰기 권한·입력 검증 규칙을 앞당겨 적용하지 않는다.

PostCreationMapper.xml의 insertPost에는 post의 13개 컬럼을 모두 적는다. status='PUBLISHED', 세 카운트 0, published_at·created_at·updated_at에 같은 #{now}, deleted_at=NULL을 대조한다. 요청에서 visibility를 빼면 #{visibility}가 NULL로 바인딩되어 DB의 DEFAULT 'PUBLIC'이 적용되지 않고 O1은 500이다. JPA와 MyBatis 모두 D1~D3에서 저장 행·태그·중복 방지를 확인한다. 태그·글·연결 행은 서비스의 @Transactional 안에서 저장한다.

import java.time.LocalDateTime;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Set;


// 글 만들기 규칙. HTTP(ResponseEntity, 헤더 등)는 알지 않는다.
@Service
public class PostService {


// 로그인 기능이 없는 동안 작성자를 고정한다 — 1-6에서 토큰 기반으로 바꾼다
private static final long FIXED_AUTHOR_ID = 2L;

private final PostRepository postRepository;
private final BoardRepository boardRepository;
private final MemberRepository memberRepository;
private final TagRepository tagRepository;

public PostService(PostRepository postRepository, BoardRepository boardRepository,
                    MemberRepository memberRepository, TagRepository tagRepository) {
    this.postRepository = postRepository;
    this.boardRepository = boardRepository;
    this.memberRepository = memberRepository;
    this.tagRepository = tagRepository;
}

@Transactional
public Post create(PostCreateRequest request) {
    Board board = boardRepository.findBySlug(request.boardSlug())
            .orElseThrow(() -&gt; new IllegalArgumentException(&quot;게시판을 찾을 수 없습니다: &quot; + request.boardSlug()));
    Member author = memberRepository.getReferenceById(FIXED_AUTHOR_ID);

    LocalDateTime now = LocalDateTime.now();
    Post post = new Post(board, author, request.title(), request.content(),
            &quot;PUBLISHED&quot;, request.visibility(), now);

    for (String tagName : distinctTagNames(request.tags())) {
        Tag tag = tagRepository.findByName(tagName)
                .orElseGet(() -&gt; tagRepository.save(new Tag(tagName, now)));
        post.addTag(tag);
    }

    Post saved = postRepository.save(post);
    // 트랜잭션(영속성 컨텍스트) 안에서 지연 로딩 연관을 미리 읽어 둔다.
    // open-in-view: false라서 컨트롤러가 트랜잭션 밖에서 건드리면 LazyInitializationException이 난다.
    saved.getAuthor().getNickname();
    saved.getTags().forEach(Tag::getName);
    return saved;
}

private List&lt;String&gt; distinctTagNames(List&lt;String&gt; tags) {
    if (tags == null) {
        return List.of();
    }
    Set&lt;String&gt; seen = new LinkedHashSet&lt;&gt;(tags);
    return List.copyOf(seen);
}


}

Service / 규칙 — src/main/java/org/example/post/PostService.java
package org.example.post;


import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import java.time.LocalDateTime;
import java.util.LinkedHashMap;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Map;


// 모든 post 컬럼을 명시하고, 응답용 작성자 정보를 트랜잭션 안에서 읽는다.
@Service
public class PostService {
    private static final long FIXED_AUTHOR_ID = 2L;
    private final PostCreationMapper mapper;


public PostService(PostCreationMapper mapper) {
    this.mapper = mapper;
}

@Transactional
public PostResponse create(PostCreateRequest request) {
    BoardWriteRow board = mapper.findBoardBySlug(request.boardSlug());
    if (board == null) {
        throw new IllegalArgumentException(&quot;게시판을 찾을 수 없습니다: &quot; + request.boardSlug());
    }
    AuthorWriteRow author = mapper.findAuthorById(FIXED_AUTHOR_ID);
    if (author == null) {
        throw new IllegalStateException(&quot;작성자를 찾을 수 없습니다: &quot; + FIXED_AUTHOR_ID);
    }
    PostInsert post = new PostInsert();
    post.boardId = board.id;
    post.authorId = author.id;
    post.title = request.title();
    post.content = request.content();
    post.visibility = request.visibility();
    post.now = LocalDateTime.now();
    mapper.insertPost(post);

    Map&lt;Long, String&gt; storedTags = new LinkedHashMap&lt;&gt;();
    for (String tagName : new LinkedHashSet&lt;&gt;(request.tags() == null ? List.&lt;String&gt;of() : request.tags())) {
        mapper.insertTagIfAbsent(tagName, post.now);
        TagWriteRow tag = mapper.findTagByName(tagName);
        if (!storedTags.containsKey(tag.id)) {
            mapper.linkTag(post.id, tag.id);
            storedTags.put(tag.id, tag.name);
        }
    }
    return new PostResponse(post.id, board.slug, post.title, post.content,
            List.copyOf(storedTags.values()), post.visibility,
            new AuthorResponse(author.id, author.nickname), post.now);
}


}

#힌트 (막힐 때만)



힌트 1 — 엔티티 맞추기


SHOW CREATE TABLE post의 컬럼을 위에서부터 하나씩 필드로 옮긴다. 이름이 snake_case면 @Column(name = "view_count"). text 컬럼은 @Column(columnDefinition = "text"). 서버가 안 뜨면 로그에서 Schema validation:이 들어간 줄을 찾는다(Hibernate 7 표기 — 하이픈 없음) — 어떤 컬럼이 안 맞는지 알려 준다.






힌트 2 — 작성자


Member 엔티티(member 테이블)와 MemberRepository를 만들고, 서비스에서 memberRepository.getReferenceById(2L)로 작성자를 붙인다. getReferenceById는 SELECT 없이 id만 든 대리 객체를 준다. 응답에 닉네임이 필요하니 서비스(트랜잭션) 안에서 getNickname()을 한 번 불러 둔다.






힌트 3 — 기본값


엔티티 생성자에서 this.status = "PUBLISHED"(또는 서비스에서 넘기기), this.viewCount = 0 …, this.publishedAt = now처럼 정한다. 같은 now로 created_at·updated_at·published_at을 채우면 세 시각이 같다.
