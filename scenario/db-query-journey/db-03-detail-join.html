DB-03 · 직접 SQL 확인

필수 두 행과 선택 두 관계를 붙여 읽으세요.

145와 viewer 7은 practice seed의 연습값입니다. 내 DB에서 직접 실행해 확인합니다.

practice DB · 읽기 전용실제 실행 전
SELECT p.id, p.title, p.content,
       b.slug AS boardSlug, m.id AS authorId,
       m.nickname AS authorNickname,
       (pl.id IS NOT NULL) AS likedByMe,
       (bm.id IS NOT NULL) AS bookmarkedByMe
FROM post p
JOIN board b ON b.id = p.board_id
JOIN member m ON m.id = p.author_id
LEFT JOIN post_like pl
  ON pl.post_id = p.id AND pl.member_id = 7
LEFT JOIN bookmark bm
  ON bm.post_id = p.id AND bm.member_id = 7
WHERE p.id = 145;

practice seed 기준 · 실행 전 기대 행id 145 · dev · 밤샘개발자likedByMe 1 · bookmarkedByMe 0
내 DB의 실제 결과아직 실행 전SQL을 실행해 한 행인지 대조하세요.

JOIN과 LEFT JOIN을 나누는 기준

post.board_id, post.author_id는 NOT NULL이며 각각 board.id, member.id를 참조합니다. 이 학습 데이터에서는 게시글의 게시판과 작성자가 항상 존재하므로 일반 JOIN을 씁니다.

반면 한 사용자가 모든 글에 좋아요·북마크를 누르지는 않습니다. 두 관계를 일반 JOIN하면 매칭 행이 없는 글은 결과에서 사라집니다. LEFT JOIN은 글 행은 살려 두고 연결 쪽 열만 NULL로 둡니다. pl.id IS NOT NULL 같은 존재 여부를 Boolean으로 바꿉니다.

중요: 선택 테이블의 viewer 조건은 ON에 둡니다. 이를 WHERE pl.member_id = :viewerId로 옮기면 NULL 행이 제거되어 사실상 INNER JOIN처럼 작동합니다.

#먼저 API 계약을 SQL로 번역하기

M1은 GET /api/posts/{id} 응답에 본문과 likedByMe, bookmarkedByMe를 포함하고, 접근 가능 여부를 확인한 뒤 응답하도록 요구합니다. 아래 SQL은 응답에 필요한 테이블 관계를 연습하는 읽기 쿼리입니다. 이 저장소의 해당 미션 API는 학습자가 구현할 대상이므로, 이 페이지는 실제 서버 응답이나 실행 결과를 가장하지 않습니다.

여기서는 seed 글 145와 viewer 7을 쿼리 예로 사용합니다. 먼저 직접 빈칸을 채워 보세요.

  1. 글 제목과 본문은 어떤 테이블에서 읽나요?
  2. 게시판 slug와 작성자 닉네임을 붙일 때 필요한 두 JOIN 조건은 무엇인가요?
  3. 좋아요·북마크 행이 없을 때도 글을 반환하려면 어떤 JOIN을 골라야 하나요?
  4. viewerId 조건을 선택 관계의 ON과 최종 WHERE 중 어디에 두어야 하나요?
  5. 이 SQL의 결과를 바로 HTTP 응답으로 보내도 될까요? M1의 접근 정책 확인은 어디에 있어야 할까요?
기준 SQL 펼치기 — 필수 관계 + 선택 관계 
SELECT
    p.id,
    p.title,
    p.content,
    b.slug AS boardSlug,
    m.id AS authorId,
    m.nickname AS authorNickname,
    (pl.id IS NOT NULL) AS likedByMe,
    (bm.id IS NOT NULL) AS bookmarkedByMe
FROM post p
JOIN board b
    ON b.id = p.board_id
JOIN member m
    ON m.id = p.author_id
LEFT JOIN post_like pl
    ON pl.post_id = p.id
   AND pl.member_id = 7
LEFT JOIN bookmark bm
    ON bm.post_id = p.id
   AND bm.member_id = 7
WHERE p.id = 145;

7과 145는 SQL 학습용 실제 seed 값입니다. 애플리케이션 코드에서는 리터럴을 문자열로 이어 붙이지 말고 바인딩 파라미터를 사용합니다. 비로그인 요청은 viewer가 없으므로 두 선택 관계가 매칭되지 않아 두 Boolean이 false가 됩니다.

#실제 데이터로 결과 확인

CloudBeaver에서 practice (학습용) 연결을 선택하고 위 쿼리를 실행합니다. 기대 행은 정확히 한 행입니다.

id title boardSlug authorNickname likedByMe bookmarkedByMe
145 스프링 트랜잭션 전파 삽질기 dev 밤샘개발자 1 0

MySQL의 Boolean 표현은 이 SELECT에서 1/0으로 나타납니다. 실제 dump에서 viewer 7의 좋아요 행은 있고 북마크 행은 없기 때문입니다. UI/API 층에서는 이 값을 각각 JSON true/false로 표현할 수 있습니다. 실행 결과가 한 행보다 많거나 0행이면 각 JOIN 키, viewer 조건, seed DB 선택을 점검하세요.

#권한 판정은 쿼리 결과 뒤에 이어진다

이 JOIN 쿼리는 상세 화면 데이터를 만드는 경로를 보여 줍니다. 접근 권한을 이 SQL이 대신 판정한다고 해석하면 안 됩니다. M1의 핵심은 단건 상세가 Java의 PostAccessPolicy로 접근 가능 여부를 판정하고, 목록 쿼리는 SQL 조건으로 거르는 점입니다. 상세 구현에서는 조회한 Post에 정책을 적용하고 허용된 경우에만 DTO를 반환합니다. 거부된 글의 데이터를 HTTP 응답에 섞지 않습니다.

기억할 기준
게시판·작성자처럼 응답을 성립시키는 필수 관계는 JOIN. 내 좋아요·북마크처럼 행이 없어도 글을 보여야 하는 관계는 LEFT JOIN. “지금 이 글을 볼 수 있나?”는 M1의 접근 정책에서 별도로 판단합니다.
