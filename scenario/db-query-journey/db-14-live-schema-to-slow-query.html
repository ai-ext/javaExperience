#1. 격리된 데이터베이스에 접속

저장소 루트에서 disposable fixture를 시작합니다. 이미 실행 중인 컨테이너의 데이터는 up이 보존합니다.

tools/db-perf-fixture.sh up
tools/db-perf-fixture.sh status

CloudBeaver 또는 DBeaver에서 MySQL 연결을 만들거나 기존 연결을 복제합니다. DBeaver Desktop은 호스트 OS에서 실행되므로 127.0.0.1에 접속합니다. CloudBeaver는 컨테이너 안에서 실행되므로 그 컨테이너의 127.0.0.1은 CloudBeaver 자신입니다. Mac Docker Desktop에서는 host.docker.internal을 사용합니다.

기준 확인: 확장 fixture는 board, member, post, post_like, tag, post_tag, comment를 포함합니다. SQL로 실제 테이블·열·인덱스·FK를 확인하고, 보이지 않는 요소가 있으면 생성 스크립트 버전과 연결 대상을 먼저 점검하세요. 확장 schema가 들어오기 전 fixture에서는 이 문서의 게시판 목록 쿼리를 실행할 수 없습니다.

#2. 스키마를 직접 조사

먼저 데이터베이스에서 확인되는 테이블을 기록하고, API 요구사항에 필요한 테이블의 정의를 읽습니다. SHOW CREATE TABLE 결과에는 열 정의, 기본키, 인덱스, FK가 함께 나옵니다.

SHOW CREATE TABLE board;
SHOW CREATE TABLE member;
SHOW CREATE TABLE post;
SHOW CREATE TABLE post_like;
SHOW CREATE TABLE tag;
SHOW CREATE TABLE post_tag;
SHOW CREATE TABLE `comment`;

특정 테이블이 없다는 오류가 나면 중단하고 SHOW TABLES로 실제 fixture 범위를 확인하세요. 전체 열과 인덱스를 결과 그리드로 빠르게 훑으려면 다음 쿼리를 씁니다.

SELECT table_name, ordinal_position, column_name, column_type, is_nullable,
       column_key, extra
FROM information_schema.columns
WHERE table_schema = DATABASE()
ORDER BY table_name, ordinal_position;

SELECT table_name, index_name, non_unique, seq_in_index, column_name,
       collation, cardinality
FROM information_schema.statistics
WHERE table_schema = DATABASE()
ORDER BY table_name, index_name, seq_in_index;

FK는 자식 열에서 부모 열로 연결해 읽습니다. FK가 없으면 결과에 관계가 안 나타날 수 있습니다. 그런 경우 스키마의 실제 키와 앱 계약을 확인하고, 이름만 비슷하다고 관계를 단정하지 마세요.

SELECT table_name AS child_table, column_name AS child_column,
       referenced_table_name AS parent_table,
       referenced_column_name AS parent_column,
       constraint_name
FROM information_schema.key_column_usage
WHERE table_schema = DATABASE()
  AND referenced_table_name IS NOT NULL
ORDER BY table_name, constraint_name, ordinal_position;

#3. API 요구사항을 쿼리 조건으로 바꾸기

이 연습의 고정 계약은 board-03의 발행된 게시글 목록입니다. PUBLISHED이고 삭제되지 않은 글에서 응답에 필요한 글 ID·제목·작성자 닉네임·작성 시각을 가져오고 최신 글부터 최대 20개를 반환한다고 가정합니다. visibility에 따른 공개 범위 판정은 이 쿼리의 범위 밖입니다. 실제 DB 스키마에서 해당 필드와 관계를 찾아 체크하세요.

요구사항 SQL 설계 질문 이 실습의 설계
게시판 범위 slug를 어디서 찾고 게시글과 어떻게 연결하는가? board.slug = 'board-03' → post.board_id
발행 상태 어떤 값이 발행되고 삭제되지 않은 상태인가? post.status = 'PUBLISHED', deleted_at IS NULL
응답 필드 어떤 관계를 거쳐 작성자 닉네임을 얻는가? 게시글 → 작성 회원
정렬 같은 시각의 순서도 고정하는가? created_at DESC, id DESC
페이지 크기 다음 페이지 확인을 위해 여분 행이 필요한가? 여기서는 첫 20행 확인, LIMIT 20
인덱스 후보 게시판·상태 필터 뒤 정렬 키가 어떤 순서인가? (board_id, status, deleted_at, created_at, id) 후보

앞의 스키마 조사에서 이름·타입·관계를 확인한 뒤 아래 쿼리를 실행하세요. 이 열 이름은 확장 fixture 계약에 맞춘 예시입니다. 실제 SHOW CREATE TABLE과 다르면 문서의 가정을 DB에 억지로 맞추지 말고, 확인한 이름을 사용해 쿼리를 고칩니다.

-- 먼저 board-03의 실제 ID를 찾는다. 결과를 아래 쿼리의 board_id에 사용.
SELECT id, slug, name FROM board WHERE slug = 'board-03';

-- API 응답 요구를 관계로 풀어 쓴 쿼리
SELECT p.id AS post_id, p.title, m.nickname AS author_nickname,
       p.created_at
FROM board AS b
JOIN post AS p ON p.board_id = b.id
JOIN member AS m ON m.id = p.author_id
WHERE b.slug = 'board-03'
  AND p.status = 'PUBLISHED'
  AND p.deleted_at IS NULL
ORDER BY p.created_at DESC, p.id DESC
LIMIT 20;

#WHERE · JOIN · ORDER BY를 고른 이유

  • WHERE b.slug = 'board-03': URL에 들어온 slug로 대상 게시판을 찾습니다.
  • JOIN post: 게시판에 속한 게시글을 연결합니다. 상태와 삭제 조건을 함께 적용합니다.
  • JOIN member: 응답에 작성자 닉네임이 필요해 게시글 작성 회원을 연결합니다.
  • ORDER BY p.created_at DESC, p.id DESC: 최신순이며 시각이 같은 행도 안정적으로 순서가 정해집니다. 인덱스 후보의 뒤쪽 열 순서와 연결됩니다.
  • LIMIT 20: 결과를 20개로 자릅니다. 커서 기반 API라면 마지막 (created_at, id)에서 다음 페이지 조건을 추가하고, 더 있는지 확인하려면 보통 size + 1행을 조회합니다. 이 1차 실험은 페이지 계약을 단순하게 고정합니다.

#4. 실제 fixture 쿼리를 실행하고 기준선을 기록

먼저 관계 쿼리를 실행해 응답 후보 열과 정렬 순서를 확인합니다. 인덱스 전후 비교에서는 게시판 ID를 조사 결과로 바꿔 동일한 쿼리를 씁니다. 아래는 그중 실행 계획이 집중되는 게시글 조회입니다. JOIN 응답 쿼리도 별도로 실행해 인덱스 추가 전후 결과를 대조하세요. EXPLAIN ANALYZE는 뒤의 SELECT를 실제 실행합니다.

-- 먼저 실제 행과 정렬 순서를 확인
SELECT id, title, author_id, created_at
FROM post
WHERE board_id = 3
  AND status = 'PUBLISHED'
  AND deleted_at IS NULL
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- 옵티마이저의 추정 계획
EXPLAIN
SELECT id, title, author_id, created_at
FROM post
WHERE board_id = 3
  AND status = 'PUBLISHED'
  AND deleted_at IS NULL
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- SELECT를 실제로 실행하며 iterator의 행·반복·시간을 관찰
EXPLAIN ANALYZE
SELECT id, title, author_id, created_at
FROM post
WHERE board_id = 3
  AND status = 'PUBLISHED'
  AND deleted_at IS NULL
ORDER BY created_at DESC, id DESC
LIMIT 20;

결과 행의 (id, title, author_id, created_at)와 순서를 파일이나 메모에 저장합니다. 실행 계획의 선택 key, 추정 rows, 정렬 처리 표시와 EXPLAIN ANALYZE의 actual rows·loops·actual time도 직접 기록하세요. 실행 전 측정값은 이 문서에 미리 정답으로 쓰지 않습니다.

계획 카드에는 실행 전 기대값을 채워 넣지 않습니다. MySQL이 실제로 반환한 key, 정렬 단계, 추정·실제 행 수와 시간을 기록하고, 인덱스 후 결과 행 ID 순서가 같은지 확인하세요.

직접 실행한 뒤 펼치기 · 로컬 MySQL 8.4 비교 예시

기본 50만 좋아요 fixture에서 board_id=3의 게시글 조회를 한 번씩 실행한 관찰입니다. 인덱스 전에는 ix_post_board로 1,000행을 읽고 정렬했으며, 인덱스 후에는 ix_post_board_status_deleted_created를 역방향으로 읽어 20행을 반환했습니다. 첫 5개 게시글 ID는 두 경우 모두 19983, 19963, 19943, 19923, 19903이었습니다.

이때 EXPLAIN ANALYZE의 한 번 측정 시간은 약 12.4ms와 0.44ms였습니다. 실행 환경·캐시에 따라 달라지는 값이므로 여러분의 완료 기준은 같은 결과 + 직접 관찰한 계획의 변화입니다.

#5. 인덱스를 추가하고 같은 결과인지 확인

먼저 앞에서 확인한 board-03의 실제 ID와 SHOW INDEX FROM post 결과를 확인합니다. 인덱스 이름이 이미 있으면 중복 생성하지 마세요. 후보 인덱스의 앞 열은 동등 조건, 뒤 열은 최신순 정렬 조건을 반영합니다. 보드 ID는 예시에서 3이며 실제 조회 값으로 바꿉니다.

SHOW INDEX FROM post;

CREATE INDEX ix_post_board_status_deleted_created
    ON post (board_id, status, deleted_at, created_at, id);

ANALYZE TABLE post;

ANALYZE TABLE은 옵티마이저 통계를 갱신합니다. 쿼리 실행을 분석하는 EXPLAIN ANALYZE와 다른 명령입니다. 생성한 정의가 맞는지 확인한 다음, 앞 절의 SELECT·EXPLAIN·EXPLAIN ANALYZE를 그대로 다시 실행하세요.

SELECT index_name, seq_in_index, column_name
FROM information_schema.statistics
WHERE table_schema = DATABASE()
  AND table_name = 'post'
ORDER BY index_name, seq_in_index;

결과의 행과 순서가 기준선과 완전히 같아야 합니다. 계획이나 시간이 더 좋아졌다고 단정하려면 관측 근거가 있어야 합니다. MySQL이 새 인덱스를 선택하지 않을 수 있고, 작은 fixture에서는 시간 차이가 없거나 측정 순서에 따라 달라질 수 있습니다. EXPLAIN은 추정 계획이고 EXPLAIN ANALYZE의 시간도 해당 환경에서 SELECT를 실행한 한 번의 관측값입니다.

#6. 인덱스를 제거해 원래 상태 복원

실험 결과를 기록한 뒤 새 인덱스만 제거합니다. 데이터 자체는 수정하지 않았으므로 제거 뒤 조회 행과 순서도 동일해야 합니다.

DROP INDEX ix_post_board_status_deleted_created ON post;
ANALYZE TABLE post;

SHOW INDEX FROM post;

SELECT id, title, author_id, created_at
FROM post
WHERE board_id = 3
  AND status = 'PUBLISHED'
  AND deleted_at IS NULL
ORDER BY created_at DESC, id DESC
LIMIT 20;

원래 인덱스 집합이 복원됐는지 확인합니다. fixture 전체를 초기화해야 한다면 이 격리 DB에 한해 tools/db-perf-fixture.sh reset을 사용할 수 있습니다. 실습을 끝내고 컨테이너를 삭제하려면 tools/db-perf-fixture.sh down을 실행합니다.

  • 게시판 범위, 상태·삭제 조건, 필요한 JOIN, 전체 정렬 키와 LIMIT의 이유를 설명할 수 있다.
  • 인덱스 전후 계획과 실제 행·시간을 직접 기록했다. 숫자를 추정하거나 복사하지 않았다.
  • 인덱스 전·후·제거 후 목록 쿼리의 결과 튜플과 순서가 동일함을 확인했다.
  • 실험 인덱스를 DROP하고 초기 인덱스 집합을 확인했다.
