#DB-02. 목록 SQL에 조건·정렬·커서 붙이기 — 기초

DB-01에서 고른 같은 목록 API를 이어갑니다. 이번에는 어떤 행부터 다음 페이지인지 SQL 조건으로 표현합니다.

GET/api/boards/dev/posts?size=2&cursor={마지막 발행시각,id}practice seed · 비로그인 · PUBLISHED / 미삭제 / PUBLIC

① 첫 페이지

정렬 키 두 개를 함께 고정합니다.

published_at DESCid DESC

id는 발행 시각이 같은 행의 순서를 고정합니다.

② 실제 행 순서

첫 네 행은 시드에서 확인한 순서입니다.

ID발행 시각
14510-03 10:10:08
14410-02 21:57:53
14310-02 08:42:47
14009-26 13:03:17

날짜는 시드의 DATETIME 값을 그대로 표시합니다.

③ 커서 만들기

페이지에서 실제로 반환한 마지막 행 144의 두 값을 가져옵니다.

cursorPublishedAt = 2026-10-02 21:57:53
cursorId = 144

불투명한 문자열로 인코딩해도 서버는 이 두 값을 복원합니다.

④ 다음 페이지 조건

정렬이 내림차순이므로 커서보다 뒤에 있는 행은 더 작은 튜플입니다.

published_at < cursorTime
OR (published_at = cursorTime AND id < cursorId)

결과는 143, 140 순서로 이어지고 앞 페이지 행은 반복되지 않습니다.

1페이지를 반환하면 마지막 행 144의 (published_at, id)를 다음 요청의 커서로 보냅니다.

#먼저 SQL을 직접 확장하기

DB-01의 조건은 유지하고, cursor가 비어 있지 않을 때만 마지막 행보다 뒤인 조건을 추가합니다. published_at은 발행된 글에서 NULL이 아니며, 순서가 같은 행은 id로 정합니다.

SELECT p.id, p.title, p.published_at
FROM board b
JOIN post p ON p.board_id = b.id
WHERE b.slug = 'dev'
  AND p.status = 'PUBLISHED'
  AND p.deleted_at IS NULL
  AND p.visibility = 'PUBLIC'
  AND (
      p.published_at < '2026-10-02 21:57:53'
      OR (p.published_at = '2026-10-02 21:57:53' AND p.id < 144)
  )
ORDER BY p.published_at DESC, p.id DESC
LIMIT 3;

이 예시는 size=2에 다음 행이 있는지 확인할 한 행을 더해 LIMIT 3으로 읽습니다. 세 번째 행은 hasNext 판정에 쓰고 응답에는 넣지 않습니다. 응답의 마지막 행은 140이므로 다음 커서는 140의 키여야 합니다. 실제 구현에서 페이지 크기는 요청값에 맞춰 제한하고 SQL 바인딩 파라미터를 사용하세요.

커서 조건을 왜 두 열로 비교하나요?

`published_at`만 조건으로 쓰면 같은 시각의 행 일부를 건너뛰거나 반복할 수 있습니다. 정렬에 사용한 모든 열을 커서에도 담아야 정렬 순서와 다음 페이지 경계가 일치합니다.

두 열이 모두 DESC이므로 비교는 `<`입니다. 정렬 방향이 섞이면 각 열의 방향에 따라 조건을 풀어 써야 합니다. MySQL row constructor 비교도 가능하지만, 학습과 이식성을 위해 동등 조건을 명시한 형태부터 사용합니다.

#같은 데이터에서 offset과 비교하기

OFFSET 2 LIMIT 2도 현재 시드에서는 143, 140을 반환합니다. 하지만 첫 페이지를 읽은 사이 새 글이 맨 앞에 추가되면 offset 2는 이전 마지막 글 144를 다시 포함할 수 있습니다. 커서는 마지막으로 본 정렬 키 뒤부터 찾으므로 앞에 추가된 행이 다음 페이지를 밀어내지 않습니다.

방식 다음 페이지 기준 앞쪽에 새 글 삽입 큰 페이지 번호
offset 앞에서 몇 행 건너뛸지 행 위치가 밀려 중복·누락 가능 건너뛸 행을 따라가야 함
cursor 마지막 행의 정렬 키 이미 본 경계 뒤를 계속 조회 앞 행 수를 세지 않음

연습: 첫 페이지 크기를 2로 두고 실제 SQL을 실행하세요. 다음 요청의 커서를 145가 아닌 144에서 가져오는 이유를 말하고, ORDER BY p.published_at DESC에서 id를 빼면 결과가 왜 불안정해지는지 설명해 보세요.
