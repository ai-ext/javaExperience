#지금 보는 계약

GET /api/boards/dev/posts?size=20&cursor=는 M1의 비로그인 첫 페이지 계약입니다. 응답에는 id, title, authorNickname, likeCount, commentCount, tags[], publishedAt이 있고 content는 없습니다. PUBLISHED, 미삭제, PUBLIC 글을 publishedAt DESC, id DESC로 정렬합니다. 시드에서 확인한 첫 5개 ID는 145, 144, 143, 140, 138입니다.

상태 표시: M1은 요구사항과 기대값이 정해진 미션입니다. 현재 저장소 루트 앱은 /hello만 구현되어 있고 이 목록 API는 아직 없습니다. 아래 코드는 L12–L14 복원 실습에서 사용하는 스키마·도메인 경로를 바탕으로 한 구현 조각입니다. 현재 루트 앱에 붙여 넣으면 바로 컴파일되는 완성 기능이라고 주장하지 않습니다.

공통 SQL의 핵심은 다음과 같습니다. 태그까지 한 번에 JOIN하면 게시글 한 건이 태그 개수만큼 늘어나므로, 페이지의 글을 먼저 고르고 post_tag와 tag는 페이지의 ID를 모아 별도 일괄 조회합니다.

SELECT p.id, p.title, m.nickname AS author_nickname,
       p.like_count, p.comment_count, p.published_at
FROM board b
JOIN post p ON p.board_id = b.id
JOIN member m ON m.id = p.author_id
WHERE b.slug = 'dev'
  AND p.status = 'PUBLISHED'
  AND p.deleted_at IS NULL
  AND p.visibility = 'PUBLIC'
ORDER BY p.published_at DESC, p.id DESC
LIMIT 20;

#방식별 코드는 필요할 때 펼치기

각 예시는 같은 WHERE와 순서를 표현합니다. 결과 DTO와 태그 일괄 조회는 공통 단계입니다. 코드 조각은 쿼리 차이를 비교하기 위한 것이며, 클래스 전체·프로젝트 설정은 각 링크의 실행 가능한 실습본에서 확인합니다.

① 파생 메서드 — 조건과 정렬이 단순할 때

Repository · PostListRepository.java

List<Post> findTop20ByBoard_SlugAndStatusAndDeletedAtIsNullAndVisibilityOrderByPublishedAtDescIdDesc(
        String boardSlug, String status, String visibility);

Service는 "dev", "PUBLISHED", "PUBLIC"을 넘깁니다. Board_Slug는 Post.board.slug 경로이고 IsNull은 deletedAt IS NULL 조건입니다. Spring Data가 이름을 분석해 쿼리를 만듭니다.

한계: 이 이름만으로 응답의 authorNickname, 저장 카운트, tags[]를 원하는 모양의 한 DTO로 투영하지는 않습니다. 엔티티를 받은 뒤 작성자를 읽으면 지연 로딩 SQL이 추가될 수 있습니다. Fetch 전략을 확인하고, 페이지의 태그는 별도 일괄 조회하세요. Top20은 고정 상한이라 요청 size와 커서 페이지를 그대로 표현할 수 없습니다. 연습에서는 첫 페이지 20개만 비교합니다.

② JPQL @Query — Java 엔티티 경로와 DTO 프로젝션

DTO · PostListRow.java

public record PostListRow(Long id, String title, String authorNickname,
                          Integer likeCount, Integer commentCount, LocalDateTime publishedAt) {}

Repository · PostListRepository.java

@Query("""
    select new org.example.post.PostListRow(
        p.id, p.title, m.nickname, p.likeCount, p.commentCount, p.publishedAt)
    from Post p join p.board b join p.author m
    where b.slug = :slug

JPQL은 post, board_id 같은 SQL 이름 대신 Post, p.board, p.deletedAt 같은 엔티티와 Java 속성을 씁니다. DB-01 첫 페이지에서는 PageRequest.of(0, 20)을 전달할 수 있습니다. Page가 필요하면 전체 개수용 count query가 추가될 수 있으므로 SQL 로그로 호출 수를 확인합니다. 실제 API의 opaque cursor 계약은 offset Pageable로 대체할 수 없습니다.

tags[]는 생성자 프로젝션에 억지로 collection JOIN하지 않습니다. pageRows.map(PostListRow::id)로 ID를 모아 WHERE pt.post_id IN (:ids) 형태의 두 번째 조회를 하고 DTO에 붙입니다.

③ JPQL의 명시적 @Query와 native SQL — ORM 언어와 DB 언어 구분

위 ②의 @Query가 JPQL입니다. 어노테이션이 붙어 있어도 SQL이 아니라 JPQL이라는 점이 포인트입니다. 같은 Repository에 네이티브 SQL을 선언하면 테이블과 실제 열 이름을 직접 씁니다.

    WHERE b.slug = :slug AND p.status = 'PUBLISHED'
      AND p.deleted_at IS NULL AND p.visibility = 'PUBLIC'
    ORDER BY p.published_at DESC, p.id DESC
    LIMIT 20
    """, nativeQuery = true)
List<PostListProjection> firstPageNative(@Param("slug") String slug);

PostListProjection은 getId(), getTitle(), getAuthorNickname() 등 alias에 대응하는 getter를 둔 interface projection입니다. native 결과 매핑은 alias와 provider 동작을 통합 테스트로 확인하세요. 복합 DTO나 DB별 타입을 매핑할 땐 @SqlResultSetMapping 또는 명시적인 JDBC 매핑이 더 분명할 수 있습니다. 태그 일괄 조회는 동일하게 별도 수행합니다.

JPQL은 엔티티 모델 중심이고, native SQL은 MySQL 문법·실행계획을 세밀하게 다룰 수 있습니다. native SQL을 택해도 바인딩 파라미터를 쓰고, 사용자 입력을 문자열로 이어 붙이지 않습니다.

④ MyBatis XML — SQL을 그대로 읽고 수정하기

Mapper · PostListMapper.java

List<PostListRow> findFirstPage(@Param("slug") String slug);

Mapper XML · PostListMapper.xml

<select id="findFirstPage" resultType="org.example.post.PostListRow">
  SELECT p.id, p.title, m.nickname AS authorNickname,
         p.like_count AS likeCount, p.comment_count AS commentCount,
         p.published_at AS publishedAt
  FROM board b
  JOIN post p ON p.board_id = b.id
  JOIN member m ON m.id = p.author_id
  WHERE b.slug = #{slug}
    AND p.status = 'PUBLISHED'
    AND p.deleted_at IS NULL
    AND p.visibility = 'PUBLIC'
  ORDER BY p.published_at DESC, p.id DESC
  LIMIT 20
</select>

#{slug}은 값 바인딩입니다. ${slug}로 바꾸면 값이 SQL 텍스트에 삽입되므로 사용자 입력에 사용하지 않습니다. 프로젝트의 기존 L13 XML은 resultType과 underscore-to-camel 설정을 사용하는 예가 있습니다. 이 예시의 별칭은 DTO Java 이름과 맞춘 것입니다. tags[]는 두 번째 Mapper 메서드에서 페이지 ID들을 <foreach>로 바인딩해 일괄 조회합니다.

MyBatis는 SQL 생성기를 숨기지 않습니다. XML을 열면 실제 SELECT와 JOIN을 읽을 수 있지만, 조건·정렬·페이지 제한의 일관성을 직접 유지해야 합니다.

⑤ QueryDSL — 조건을 Java 코드로 조립하기

Repository · PostListRepositoryCustomImpl.java의 핵심

QPost p = QPost.post;
BooleanBuilder where = new BooleanBuilder()
        .and(p.board.slug.eq("dev"))
        .and(p.status.eq("PUBLISHED"))
        .and(p.deletedAt.isNull())
        .and(p.visibility.eq("PUBLIC"));

List<PostListRow> rows = query
        .select(Projections.constructor(PostListRow.class,
                p.id, p.title, p.author.nickname,
                p.likeCount, p.commentCount, p.publishedAt))
        .from(p)
        .where(where)
        .orderBy(p.publishedAt.desc(), p.id.desc())
        .limit(20)
        .fetch();

실제 L14 실습은 OpenFeign QueryDSL 7.7과 annotation processor로 QPost를 생성합니다. 이 의존성과 생성 설정은 현재 루트 build.gradle이 아니라 L14 복원 코드에 있습니다. 필터가 선택값일 때만 where.and(...)를 추가하면 동적 검색에 유리합니다. 단순 고정 조회에는 파생 메서드가 더 짧을 수 있습니다. 여기서도 태그는 페이지 ID로 모아 별도 조회합니다.

#실제 실행 SQL은 어디서 보나요?

  1. L12/L13/L14 중 사용할 실습 overlay를 복원하고 해당 프로필로 앱을 켭니다. 기본 루트 앱에는 MyBatis와 QueryDSL 의존성이 없습니다.
  2. 요청 버튼 또는 Postman 예시로 동일한 첫 페이지 요청을 보냅니다. M1 API 구현이 없는 체크아웃에서는 각 쿼리 함수를 테스트에서 같은 파라미터로 호출하세요.
  3. JPA 파생 메서드·JPQL·QueryDSL은 Hibernate SQL 로그에서 SQL 형태를 봅니다. 로그의 ?만으로는 바인딩 값이 보이지 않을 수 있어 바인드 파라미터 로그를 별도로 켭니다. MyBatis는 Mapper namespace/statement와 함께 SQL을 확인합니다.
  4. 결과를 MySQL에서 확인하려면 CloudBeaver의 practice (학습용) 연결에서 SQL을 실행합니다. 요청이 DB에 실제 보낸 SQL과 직접 입력한 SQL이 같은지 WHERE·ORDER BY·LIMIT·JOIN을 대조합니다.
  5. 성능을 주장하기 전에는 같은 데이터와 파라미터로 EXPLAIN을 실행합니다. EXPLAIN은 실행계획을 설명하며 SELECT 결과 행을 반환하는 명령이 아닙니다. 실행계획과 실제 반환 결과를 따로 기록합니다.

실제 JDBC 실행문과 바인딩 값을 로그로 남기는 설정은 개발 DB에서만 짧게 사용하세요. 민감한 요청값이 로그에 남을 수 있고, SQL 로그의 출력만으로 실제 소요 시간이나 인덱스 효율을 결론 내릴 수 없습니다.
