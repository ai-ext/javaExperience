좋아요 행 · lpost_likel.post_id
→ p.id = l.post_id →
게시글 행 · ppostp.id

이 관계만으로 좋아요 한 행이 여러 게시글 행으로 불어나지 않습니다. 태그처럼 한 글에 여러 연결 행이 있는 경우는 뒤 장면에서 별도로 봅니다.

JOIN은 게시글 행을 붙입니다.

좋아요 행에 게시글을 연결하고 같은 공개 조건으로 거릅니다.

post_like l→ JOIN →post p→PUBLISHED · PUBLIC · 미삭제
원문 M3 JOIN SELECT읽기 전용 · practice DB에서 직접 실행
SELECT l.id AS like_id, l.post_id, l.created_at AS liked_at
FROM post_like AS l
JOIN post AS p ON p.id = l.post_id
WHERE l.member_id = 12
  AND p.status = 'PUBLISHED'
  AND p.deleted_at IS NULL
  AND p.visibility = 'PUBLIC'
ORDER BY l.created_at DESC, l.id DESC
LIMIT 21;

WHERE l.member_id = 12

JOIN은 글과 태그 연결 행을 붙입니다.

board → post → post_tag → tag 순서로 spring 조건의 글 ID를 읽습니다.

원문 태그 JOIN SELECT읽기 전용 · practice DB에서 직접 실행
-- JOIN: 태그 관계를 결과 집합에 붙여 필터
SELECT p.id
FROM board AS b
JOIN post AS p ON p.board_id = b.id
JOIN post_tag AS pt ON pt.post_id = p.id
JOIN tag AS t ON t.id = pt.tag_id
WHERE b.slug = 'dev'

  AND p.status = 'PUBLISHED'
  AND p.deleted_at IS NULL
  AND p.visibility = 'PUBLIC'
ORDER BY p.published_at DESC, p.id DESC;

EXISTS는 spring 태그의 존재만 묻습니다.

바깥 글 p마다 같은 태그가 있는지 post_tag와 tag로 질문합니다.

바깥 조회board b → post pdev · 공개 · 발행 · 미삭제
→ pt.post_id = p.id →
EXISTS 내부post_tag pt → tag tt.name = spring
원문 태그 EXISTS SELECT읽기 전용 · practice DB에서 직접 실행
-- EXISTS: 태그 행이 있는지 질문. 결과 행에 태그를 붙이지 않음
SELECT p.id
FROM board AS b
JOIN post AS p ON p.board_id = b.id
WHERE b.slug = 'dev'
  AND p.status = 'PUBLISHED'
  AND p.deleted_at IS NULL
  AND p.visibility = 'PUBLIC'
  AND EXISTS (
      SELECT 1
      FROM post_tag AS pt
      JOIN tag AS t ON t.id = pt.tag_id
      WHERE pt.post_id = p.id
        AND t.name = 'spring'
  )
ORDER BY p.published_at DESC, p.id DESC;

#비교 전 API와 데이터 범위 정하기

GET /api/me/likes는 좋아요한 시각의 내림차순으로 정렬하고, 지금 볼 수 없는 글을 제외합니다(M3). 실행 계획 비교에서는 먼저 같은 입력 회원, 같은 응답 열, 같은 권한 조건, 같은 정렬·LIMIT을 사용하세요. 아래는 읽기 전용 SQL 모양을 익히는 예시입니다. M3의 전체 권한 규칙(R1 중 팔로워·차단·운영자 예외 포함)을 완성한 서비스 SQL이라고 주장하지 않습니다. 전체 R1을 적용할 때 두 쿼리의 필터가 반드시 같은지 확인해야 합니다.

practice 연결은 시드 규모가 작아 JOIN과 EXISTS의 계획이 같거나 차이가 거의 없을 수 있습니다. 계획 차이가 보이지 않아도 쿼리가 잘못됐다는 뜻은 아닙니다. 데이터량이 계획 선택을 바꾸는 경험은 DB-10 격리 성능 실습에서 합니다.

#좋아요 목록: JOIN으로 게시글 조건 붙이기

아래는 로그인 회원의 좋아요에서 공개 게시글만 남기는 조건 예시입니다. 12는 실습 회원 예시 값입니다. 완전한 M3/R1 쿼리는 팔로워 공개·차단·작성자 규칙을 추가로 반영해야 합니다.

SELECT l.id AS like_id, l.post_id, l.created_at AS liked_at
FROM post_like AS l
JOIN post AS p ON p.id = l.post_id
WHERE l.member_id = 12
  AND p.status = 'PUBLISHED'
  AND p.deleted_at IS NULL
  AND p.visibility = 'PUBLIC'
ORDER BY l.created_at DESC, l.id DESC
LIMIT 21;

이 실습에서 JOIN은 좋아요 행에 해당 게시글 상태를 붙입니다. post_like.post_id는 게시글 하나를 가리키므로 이 관계만으로 좋아요 행이 늘어나지 않습니다. 목록 응답에서 작성자나 태그를 붙이는 JOIN은 별도 관계이며, 태그처럼 한 게시글에 여러 행이 있으면 결과가 늘어날 수 있습니다.

같은 조건을 “해당 게시글이 존재하는가?”로 적으면 다음과 같습니다. 두 쿼리의 like_id, post_id, liked_at과 순서를 대조하고 각 쿼리 앞에 EXPLAIN을 붙여 계획도 비교하세요.

SELECT l.id AS like_id, l.post_id, l.created_at AS liked_at
FROM post_like AS l
WHERE l.member_id = 12
  AND EXISTS (
      SELECT 1
      FROM post AS p
      WHERE p.id = l.post_id
        AND p.status = 'PUBLISHED'
        AND p.deleted_at IS NULL
        AND p.visibility = 'PUBLIC'
  )
ORDER BY l.created_at DESC, l.id DESC
LIMIT 21;

여기서 EXISTS는 게시글의 표시 필드를 붙이지 않고, 공개 조건을 만족하는 게시글이 있는 좋아요만 남깁니다. 다만 실제 M3는 전체 R1을 적용해야 하므로 이 단순 공개 조건 두 쿼리의 동일성만으로 실제 API 권한 구현을 완료했다고 볼 수 없습니다.

#태그 필터: JOIN과 EXISTS 결과 비교

M1 응답은 글의 tags[]를 포함합니다. 다음은 그 응답을 확장해 “태그가 spring인 글만 반환”하는 쿼리 설계 연습입니다. 기존 M1 API가 tag query parameter를 제공한다고 가정하지 않습니다. 두 쿼리는 게시글 ID를 반환하며 동일한 boardSlug, 상태·삭제·가시성 조건을 추가해 비교할 수 있습니다.

-- JOIN: 태그 관계를 결과 집합에 붙여 필터
SELECT p.id
FROM board AS b
JOIN post AS p ON p.board_id = b.id
JOIN post_tag AS pt ON pt.post_id = p.id
JOIN tag AS t ON t.id = pt.tag_id
WHERE b.slug = 'dev'
  AND t.name = 'spring'
  AND p.status = 'PUBLISHED'
  AND p.deleted_at IS NULL
  AND p.visibility = 'PUBLIC'
ORDER BY p.published_at DESC, p.id DESC;
-- EXISTS: 태그 행이 있는지 질문. 결과 행에 태그를 붙이지 않음
SELECT p.id
FROM board AS b
JOIN post AS p ON p.board_id = b.id
WHERE b.slug = 'dev'
  AND p.status = 'PUBLISHED'
  AND p.deleted_at IS NULL
  AND p.visibility = 'PUBLIC'
  AND EXISTS (
      SELECT 1
      FROM post_tag AS pt
      JOIN tag AS t ON t.id = pt.tag_id
      WHERE pt.post_id = p.id
        AND t.name = 'spring'
  )
ORDER BY p.published_at DESC, p.id DESC;

tag.name은 UNIQUE이고 (post_id, tag_id)는 post_tag의 복합 기본 키입니다. 따라서 이 필터에서는 태그 하나당 게시글이 두 번씩 매칭되지는 않습니다. 여러 태그를 한꺼번에 JOIN하거나 집계하는 쿼리라면 결과 행 수를 확인하고, 필터 목적이면 EXISTS가 중복을 만들지 않는다는 점도 비교하세요.

#EXPLAIN을 직접 실행하고 기록하기

먼저 좋아요 JOIN/EXISTS 쌍과 태그 JOIN/EXISTS 쌍 각각의 결과 ID를 비교해 의미가 같은지 확인합니다. 그다음 네 SELECT에 EXPLAIN FORMAT=TREE 또는 EXPLAIN을 붙여 추정 계획을 읽습니다. 대표로 아래 태그 EXISTS 쿼리에 EXPLAIN ANALYZE도 실행해 실제 계획을 확인합니다. MySQL 8.4의 EXPLAIN ANALYZE는 SELECT를 실제 실행하면서 행·loop·시간을 보여 줍니다. 결과 숫자는 seed·통계·버전에 따라 달라지므로 이 문서에는 정답 수치를 적지 않습니다.

EXPLAIN FORMAT=TREE
SELECT p.id
FROM board AS b
JOIN post AS p ON p.board_id = b.id
WHERE b.slug = 'dev'
  AND p.status = 'PUBLISHED'
  AND p.deleted_at IS NULL
  AND p.visibility = 'PUBLIC'
  AND EXISTS (
      SELECT 1
      FROM post_tag AS pt
      JOIN tag AS t ON t.id = pt.tag_id
      WHERE pt.post_id = p.id AND t.name = 'spring'
  )
ORDER BY p.published_at DESC, p.id DESC;

EXPLAIN ANALYZE
SELECT p.id
FROM board AS b
JOIN post AS p ON p.board_id = b.id
WHERE b.slug = 'dev'
  AND p.status = 'PUBLISHED'
  AND p.deleted_at IS NULL
  AND p.visibility = 'PUBLIC'
  AND EXISTS (
      SELECT 1
      FROM post_tag AS pt
      JOIN tag AS t ON t.id = pt.tag_id
      WHERE pt.post_id = p.id AND t.name = 'spring'
  )
ORDER BY p.published_at DESC, p.id DESC;

CloudBeaver의 practice (학습용) 연결에서 읽기 쿼리로 실행합니다. 기본 seed의 테이블·인덱스는 바꾸지 않습니다. EXPLAIN ANALYZE도 실제 SELECT를 수행하므로 변경 쿼리에 붙이지 마세요.

관찰 항목 실행 계획에서 찾을 것
접근 경로 어떤 테이블이 먼저 읽히고 key 또는 index lookup이 무엇인지
추정과 실제 추정 rows와 actual rows가 크게 다른 구간이 있는지
반복 loops가 어느 연산에서 커지는지
정렬·임시 결과 sort, temporary table 같은 추가 작업이 있는지
결과 정확성 JOIN과 EXISTS의 ID·순서가 같은지, 중복이 생겼는지
계획이 다르지 않을 때 다음에 할 일
MySQL 옵티마이저는 JOIN과 서브쿼리를 내부적으로 비슷한 계획으로 바꿀 수 있습니다. 문법 모양만 보고 어느 쪽이 빠르다고 결론내리지 말고, 같은 스키마와 데이터에서 결과 정확성·계획·실행을 비교합니다. 표본이 작으면 의미 있는 차이가 나오지 않을 수 있습니다. 그때는 값을 기록하고 DB-10의 격리 fixture로 이동합니다. fixture는 이 API의 모든 JOIN과 권한 조건을 재현하지 않으므로, 결과는 “좋아요 목록용 정렬 인덱스”에만 적용합니다.
