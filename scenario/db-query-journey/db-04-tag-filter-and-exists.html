DB-04 · JOIN과 DISTINCT

글 열만 고르고 DISTINCT로 중복을 줄이세요.

태그 이름을 필터에 쓰되 결과 열에는 넣지 않습니다.

JOIN + DISTINCT · 원문 SQLcommunity practice DB · 읽기 전용
SELECT DISTINCT
    p.id,
    p.title,
    p.published_at
FROM post AS p
JOIN post_tag AS pt
    ON pt.post_id = p.id
JOIN tag AS t
    ON t.id = pt.tag_id
WHERE t.name IN ('spring', 'jpa')
  AND p.status = 'PUBLISHED'
  AND p.deleted_at IS NULL
ORDER BY p.published_at DESC, p.id DESC;

01-community.sql seed · 실행 전 기대post id 2글 열만 선택했을 때 post 2는 한 번
내 DB의 실제 결과아직 실행 전위 SQL을 실행해 직접 대조하세요.

DISTINCT는 선택한 열 전체를 비교합니다. 태그 이름까지 결과 열에 넣는 경우는 다음 비교 장면에서 확인합니다.

EXISTS · 원문 SQLcommunity practice DB · 읽기 전용
SELECT
    p.id,
    p.title,
    p.published_at
FROM post AS p
WHERE p.status = 'PUBLISHED'
  AND p.deleted_at IS NULL
  AND EXISTS (
      SELECT 1
      FROM post_tag AS pt
      JOIN tag AS t
        ON t.id = pt.tag_id
      WHERE pt.post_id = p.id
        AND t.name IN ('spring', 'jpa')
  )
ORDER BY p.published_at DESC, p.id DESC;

③ EXISTS로 글을 고르면

“이 글에 조건을 만족하는 태그가 하나라도 있나?”만 검사합니다.

id 2 · JPA 연관관계 매핑 정리

첫 판단: 태그 이름도 결과로 내보내고 싶어 태그별 행이 필요하면 JOIN이 맞습니다. 글 목록만 필요하고 조건에 맞는 태그가 있는지만 알면 EXISTS가 자연스럽습니다.
태그 조건에 맞는 글 목록 만들기 — JOIN과 DISTINCT

아래 JOIN은 실제 seed의 post 2에서 두 행을 반환합니다. `DISTINCT`는 결과의 글 열이 같은 행을 한 번으로 줄입니다.

SELECT DISTINCT
    p.id,
    p.title,
    p.published_at
FROM post AS p
JOIN post_tag AS pt
    ON pt.post_id = p.id
JOIN tag AS t
    ON t.id = pt.tag_id
WHERE t.name IN ('spring', 'jpa')
  AND p.status = 'PUBLISHED'
  AND p.deleted_at IS NULL
ORDER BY p.published_at DESC, p.id DESC;

DISTINCT는 결과 열 전체를 비교합니다. SELECT에 태그 이름까지 추가하면 spring 행과 jpa 행은 서로 다른 결과이므로 둘 다 남습니다. “글만 한 번씩”이 계약이라면 태그 이름을 함께 투영하지 않거나 EXISTS를 고릅니다.

목록의 각 글을 한 번만 검사하기 — EXISTS 
SELECT
    p.id,
    p.title,
    p.published_at
FROM post AS p
WHERE p.status = 'PUBLISHED'
  AND p.deleted_at IS NULL
  AND EXISTS (
      SELECT 1
      FROM post_tag AS pt
      JOIN tag AS t
        ON t.id = pt.tag_id
      WHERE pt.post_id = p.id
        AND t.name IN ('spring', 'jpa')
  )
ORDER BY p.published_at DESC, p.id DESC;

바깥 쿼리의 기준은 `post`이므로 글 한 행은 한 번만 반환됩니다. 안쪽 쿼리는 조건 태그의 존재 여부만 확인합니다. 글마다 태그를 붙여 응답해야 한다면 별도의 태그 로딩·집계를 설계하세요.

언제 JOIN, EXISTS, DISTINCT를 고를까?
필요한 결과시작 선택점검할 점
글과 각 태그를 한 행씩JOIN글이 태그 수만큼 반복되는 것이 맞는 응답인지
조건에 맞는 태그가 있는 글EXISTS존재 검사 결과가 글 행을 늘리지 않음
JOIN 결과에서 글 열을 중복 제거DISTINCT투영 열을 추가하면 중복 판정도 달라짐

이 선택은 “빠른 SQL 문법”을 고르는 문제가 아닙니다. 먼저 응답에서 한 행이 무엇을 뜻하는지 정하고, 그 행 단위에 맞는 관계 표현을 택합니다. 실제 속도 차이는 데이터 분포와 실행 계획을 DB-12에서 확인합니다.

#API 계약으로 연결하기

태그를 이용한 글 목록 API를 만든다면, 먼저 결과 한 행이 “게시글 1개”인지 “게시글-태그 쌍 1개”인지 정합니다. GET /api/boards/{slug}/posts 응답처럼 글 한 건을 한 번만 반환하면서 태그 배열을 포함하려면, 글 필터와 태그 응답 로딩을 구분하고 페이지 경계가 깨지지 않는지 확인해야 합니다. M1은 태그가 포함된 목록 응답과 태그 조회 N+1 점검을 요구합니다.

학습 순서:

  1. post_tag에서 실제로 글 하나에 연결된 태그 행 수를 확인합니다.
  2. JOIN 결과에서 p.id가 중복되는 이유를 설명합니다.
  3. 같은 조건을 EXISTS로 바꾸고 글 ID가 한 번씩 나오는지 확인합니다.
  4. 응답 DTO가 태그 배열을 요구할 때 목록 페이지 조회와 태그 적재 전략을 따로 설계합니다.
