DB-11 · 보이는 상태

숨기기 전의 계획을 먼저 기록합니다.

VISIBLE이라고 반드시 이 인덱스가 선택되는 것은 아닙니다.

원문 동일 SELECT의 EXPLAIN읽기 전용 · 직접 실행
EXPLAIN

FROM post_like AS l

LIMIT 11;

이 실습 SQL은 FORCE INDEX가 없는 핵심 fixture SELECT입니다.

DB-11 · 잠시 숨김

인덱스를 지우지 않고 옵티마이저에서 숨깁니다.

보조 인덱스만 INVISIBLE로 전환합니다. 다음 화면에서 같은 SELECT로 비교하세요.

VISIBLE→INVISIBLE
원문 ALTER INDEX INVISIBLE전용 fixture 스키마 변경
ALTER TABLE post_like

인덱스 자체는 남습니다. 기본 옵티마이저 선택 대상에서 제외됩니다. Primary key에는 적용하지 않습니다. 실험 후 반드시 VISIBLE로 복원하세요.

DB-11 · 같은 SELECT

숨긴 뒤 계획이 어떻게 달라졌나요?

DB-10의 같은 회원·정렬·LIMIT을 유지하고 key·rows·Extra를 나란히 기록합니다.

INVISIBLE 뒤에도 같은 EXPLAIN읽기 전용 · 직접 실행
EXPLAIN
SELECT l.id, l.post_id, l.created_at
FROM post_like AS l
WHERE l.member_id = 12
ORDER BY l.created_at DESC, l.id DESC
LIMIT 11;

계획 변화는 직접 확인해야 합니다. 9-2 전체 API는 FORCE INDEX 경로이므로 이 상태로 호출해 비교하지 않습니다.

DB-11 · 마지막 선택

실습용 인덱스를 유지할까요, 제거할까요?

유지하면 VISIBLE 상태를 확인하고, 제거한다면 전용 인덱스만 지웁니다.

원문 DROP INDEX + 통계 갱신전용 fixture 스키마 변경
DROP INDEX ix_post_like_member_created ON post_like;
ANALYZE TABLE post_like;

기본 FK·UNIQUE 인덱스는 지우지 않습니다. ANALYZE TABLE은 통계 갱신입니다.

원문 전체 · 대상·가시성·복원·삭제 SQL 펼치기

이번 시나리오: DB-10에서 설계한 ix_post_like_member_created가 보이는 상태와 숨긴 상태에서 실행 계획에 어떤 차이를 만드는지 격리 fixture에서 확인한다. 마지막에는 가시성을 되돌리고, 필요하면 이 실습용 인덱스를 제거한다. 기본 practice DB는 사용하지 않는다.

#1. 현재 DB와 인덱스 확인

MySQL 8.4의 127.0.0.1:13319에 연결해 javaexperience_perf DB인지 먼저 확인한다. post_like의 인덱스 목록을 보고 ix_post_like_member_created가 이미 존재하는지, 보이는지 확인한다. DB-10을 마쳤다면 이미 존재할 수 있다. tools/db-perf-fixture.sh up은 실행 중인 컨테이너를 새로 만들지 않는다.

SELECT DATABASE();
SHOW INDEX FROM post_like;

#2. 없다면 전용 인덱스 만들기

DB-10에서 인덱스를 만들지 않은 경우에만 다음 문장을 실행한다. 같은 이름이 이미 있으면 다시 만들지 않는다. 이 변경은 전용 fixture의 post_like에만 적용한다.

CREATE INDEX ix_post_like_member_created
    ON post_like (member_id, created_at, id);
ANALYZE TABLE post_like;

ANALYZE TABLE은 테이블 통계를 갱신한다. 읽기 SELECT를 실제 실행하는 EXPLAIN ANALYZE와 다르다.

#3. 현재 보이는 인덱스의 계획 기록

같은 회원 12, 최신순, LIMIT 11을 계속 사용한다. 먼저 SHOW INDEX의 상태와 다음 EXPLAIN의 key, rows, Extra를 기록한다. 인덱스가 보인다고 무조건 선택되는 것은 아니다.

EXPLAIN
SELECT l.id, l.post_id, l.created_at
FROM post_like AS l
WHERE l.member_id = 12
ORDER BY l.created_at DESC, l.id DESC
LIMIT 11;

#4. 옵티마이저에서 잠시 숨기기

MySQL 8.4의 보조 인덱스 ix_post_like_member_created를 INVISIBLE로 바꾼다. 인덱스 자체는 유지되지만 기본적으로 옵티마이저의 선택 대상에서 빠진다. Primary key에는 이 실습을 적용하지 않는다.

ALTER TABLE post_like
    ALTER INDEX ix_post_like_member_created INVISIBLE;

이 상태에서 SHOW INDEX FROM post_like;와 같은 EXPLAIN을 다시 실행해 현재 key·rows·Extra를 적는다. 계획이 달라지는지는 직접 관찰해야 한다. 9-2의 전체 API 실습은 FORCE INDEX를 사용하므로 그 API를 INVISIBLE 상태에서 호출해 비교하지 않는다. 이 DB-11 실습은 FORCE INDEX 없는 전용 fixture 쿼리다.

#5. 반드시 가시성 복원

비교가 끝나면 다음 SQL을 실행하고 SHOW INDEX 및 EXPLAIN으로 복원 여부를 확인한다. 페이지를 떠나기 전에 이 상태를 점검한다.

ALTER TABLE post_like
    ALTER INDEX ix_post_like_member_created VISIBLE;

#6. 실습용 인덱스를 제거하려면

원래 fixture 인덱스 집합으로 돌릴 때만 다음 SQL을 실행한다. VISIBLE로 복원한 뒤 이 전용 인덱스를 제거한다. 기본 FK·UNIQUE 인덱스는 지우지 않는다. 다시 비교하려면 2단계부터 생성한다.

DROP INDEX ix_post_like_member_created ON post_like;
ANALYZE TABLE post_like;

마지막으로 SHOW INDEX FROM post_like;와 같은 EXPLAIN을 실행해 현재 상태를 기록한다. DROP INDEX는 전용 fixture에서도 스키마 변경이다. 정말 제거할 때만 복사해 실행한다.

#완료 기준

  • 연결 DB와 인덱스 존재·가시성을 확인했다.
  • VISIBLE → INVISIBLE → VISIBLE 각 상태의 계획을 같은 SELECT로 기록했다.
  • ANALYZE TABLE과 EXPLAIN ANALYZE의 차이를 설명할 수 있다.
  • 인덱스를 숨긴 채 실습을 끝내지 않았고, 제거를 선택했다면 전용 인덱스만 지웠다.
