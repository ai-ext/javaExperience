DB-05 · 무엇을 세었나

JOIN 직후 COUNT는 원본 행을 중복해서 셉니다.

각 like는 댓글 셋과, 각 comment는 좋아요 둘과 만납니다.

원시 JOIN 뒤 잘못된 집계 · 합성 예시COUNT(pl.id) = 6COUNT(c.id) = 6
원본 관계의 실제 개수 · 합성 예시좋아요 = 2댓글 = 3

같은 값이 여러 JOIN 행에 반복되므로 SUM도 커질 수 있습니다. COUNT(DISTINCT ...)는 개수 보정일 뿐 모든 가중 합계를 고치지 않습니다.

원문의 잘못된 쿼리 구조 보기
-- 설명용 구조: 실제 인기 점수 쿼리로 쓰면 안 됩니다.
SELECT
    p.id,
    COUNT(pl.id) AS like_count,
    COUNT(c.id) AS comment_count
FROM post AS p
LEFT JOIN post_like AS pl
    ON pl.post_id = p.id
LEFT JOIN comment AS c
    ON c.post_id = p.id
   AND c.deleted_at IS NULL
GROUP BY p.id;

합성 CTE · 실행 가능한 SELECT합성 CTE · 읽기 전용
WITH sample_likes AS (
    SELECT 41 AS like_id, 'synthetic' AS post_key
    UNION ALL SELECT 42, 'synthetic'
), sample_comments AS (
    SELECT 71 AS comment_id, 'synthetic' AS post_key
    UNION ALL SELECT 72, 'synthetic'
    UNION ALL SELECT 73, 'synthetic'
)
SELECT l.like_id, c.comment_id
FROM sample_likes AS l
JOIN sample_comments AS c ON c.post_key = l.post_key
ORDER BY l.like_id, c.comment_id;

좋아요와 댓글을 각각 post_id별로 집계하면 두 원본 관계가 서로 곱해지지 않습니다.

WITH like_counts AS (
    SELECT post_id, COUNT(*) AS like_count
    FROM post_like
    GROUP BY post_id

    SELECT post_id, COUNT(*) AS comment_count
    FROM comment

    GROUP BY post_id

    ON cc.post_id = p.id

DB-05 · M6 인기글 응용

기간 필터는 좋아요·댓글 집계 안에 각각 넣습니다.

M6의 인기 점수는 최근 기간의 좋아요×3과 삭제되지 않은 댓글을 더합니다.

post_like.created_at[since, now)기간 안 좋아요
comment.created_at[since, now)deleted_at IS NULL
scorelikes_in_period × 3 + comments_in_period동점: published_at DESC → id DESC
M6 원문 SQL 뼈대원문 집계 SQL
WITH like_counts AS (
    SELECT pl.post_id, COUNT(*) AS likes_in_period
    FROM post_like AS pl
    WHERE pl.created_at >= :since
      AND pl.created_at < :now
    GROUP BY pl.post_id
), comment_counts AS (
    SELECT c.post_id, COUNT(*) AS comments_in_period
    FROM comment AS c
    WHERE c.deleted_at IS NULL
      AND c.created_at >= :since
      AND c.created_at < :now
    GROUP BY c.post_id
)
SELECT
    p.id,
    (COALESCE(lc.likes_in_period, 0) * 3
       + COALESCE(cc.comments_in_period, 0)) AS score
FROM post AS p
LEFT JOIN like_counts AS lc ON lc.post_id = p.id
LEFT JOIN comment_counts AS cc ON cc.post_id = p.id
WHERE p.status = 'PUBLISHED'
  AND p.visibility = 'PUBLIC'
  AND p.deleted_at IS NULL
ORDER BY score DESC, p.published_at DESC, p.id DESC
LIMIT 10;

구현할 API 계약GET /api/posts/popular?days=7비로그인 공개 글 · 상위 10개
내 서버/DB의 실제 결과아직 실행 전:since, :now는 구현에서 바인딩합니다.

원문의 이름 있는 파라미터는 SQL 클라이언트에 그대로 붙여 실행할 리터럴이 아닙니다. 서버 구현 또는 실습 환경에서 값을 바인딩하세요.

DB-05 · 실무 디버깅

집계가 이상할 때 한 행의 뜻부터 확인하세요.

내 SQL과 DB 결과를 단계별로 기록하며 원인을 좁힙니다.

  1. 각 원본 관계의 행 수를 따로 센다.
  2. JOIN을 하나씩 추가하며 결과 행 수를 본다.
  3. 현재 결과의 한 행이 무엇인지 말로 적는다.
  4. 각 1:N 관계를 먼저 집계한 뒤 붙인다.

COUNT(DISTINCT ...)는 개수만 보정할 수 있습니다. 임의의 SUM·가중치 점수를 자동으로 바로잡지 않습니다.

② COUNT와 SUM이 틀어짐

COUNT(pl.id) = 6 · 기대 2

#합성 2×3을 직접 SELECT로 확인하기

아래 CTE는 실제 post_like·comment 행을 읽거나 수정하지 않습니다. 좋아요 ID 41·42와 댓글 ID 71·72·73을 쿼리 안에서만 만든 설명용 합성 데이터입니다. community DB의 SQL 편집기에서 읽기 전용으로 실행하고, 반환된 (like_id, comment_id) 여섯 쌍을 위 그림과 대조하세요. 특정 게시글의 실제 집계 결과로 사용하지 않습니다.

WITH sample_likes AS (
    SELECT 41 AS like_id, 'synthetic' AS post_key
    UNION ALL SELECT 42, 'synthetic'
), sample_comments AS (
    SELECT 71 AS comment_id, 'synthetic' AS post_key
    UNION ALL SELECT 72, 'synthetic'
    UNION ALL SELECT 73, 'synthetic'
)
SELECT l.like_id, c.comment_id
FROM sample_likes AS l
JOIN sample_comments AS c ON c.post_key = l.post_key
ORDER BY l.like_id, c.comment_id;

두 관계의 행 수는 각각 2와 3인데 JOIN 결과는 6행입니다. 이 쿼리를 실행해 보지 않았다면 여섯 쌍은 기대값일 뿐 실제 관찰 결과가 아닙니다.

잘못된 쿼리 — 두 1:N 관계를 바로 연결 
-- 설명용 구조: 실제 인기 점수 쿼리로 쓰면 안 됩니다.
SELECT
    p.id,
    COUNT(pl.id) AS like_count,
    COUNT(c.id) AS comment_count
FROM post AS p
LEFT JOIN post_like AS pl
    ON pl.post_id = p.id
LEFT JOIN comment AS c
    ON c.post_id = p.id
   AND c.deleted_at IS NULL
GROUP BY p.id;

글 한 개에 좋아요 2개와 살아 있는 댓글 3개가 있으면 집계 입력은 6행입니다. 삭제 댓글 조건은 이 예시에서 제외했지만 곱셈 문제를 해결하지는 않습니다. `COUNT(DISTINCT pl.id)`로 개수를 보정할 수는 있어도, 다른 수치의 SUM·가중치 합산까지 자동으로 고쳐 주지는 않습니다.

안전한 기본형 — 관계마다 먼저 집계한 뒤 JOIN 
WITH like_counts AS (
    SELECT post_id, COUNT(*) AS like_count
    FROM post_like
    GROUP BY post_id
), comment_counts AS (
    SELECT post_id, COUNT(*) AS comment_count
    FROM comment
    WHERE deleted_at IS NULL
    GROUP BY post_id
)
SELECT
    p.id,
    COALESCE(lc.like_count, 0) AS like_count,
    COALESCE(cc.comment_count, 0) AS comment_count
FROM post AS p
LEFT JOIN like_counts AS lc
    ON lc.post_id = p.id
LEFT JOIN comment_counts AS cc
    ON cc.post_id = p.id
WHERE p.status = 'PUBLISHED'
  AND p.deleted_at IS NULL;

각 CTE는 `post_id`마다 최대 한 행입니다. 따라서 게시글에 붙일 때 한쪽 집계가 다른 쪽 원시 행 수만큼 반복되지 않습니다. 실제 API에서는 board, visibility, 기간, 커서 등 응답 계약 조건을 추가하고 `COALESCE`로 관계가 없는 글의 0을 만듭니다.

M6 인기글 — 기간 필터를 각 집계 안에 넣기

M6 점수는 기간 안 좋아요 수 × 3 + 기간 안 살아 있는 댓글 수입니다. 시간 조건이 각각의 원본 테이블에 적용되도록 별도로 집계합니다. 아래는 M6 계약을 옮기는 연습용 뼈대이며, 실제 서버 구현 또는 seed 결과를 주장하지 않습니다.

WITH like_counts AS (
    SELECT pl.post_id, COUNT(*) AS likes_in_period
    FROM post_like AS pl
    WHERE pl.created_at >= :since
      AND pl.created_at < :now
    GROUP BY pl.post_id
), comment_counts AS (
    SELECT c.post_id, COUNT(*) AS comments_in_period
    FROM comment AS c
    WHERE c.deleted_at IS NULL
      AND c.created_at >= :since
      AND c.created_at < :now
    GROUP BY c.post_id
)
SELECT
    p.id,
    (COALESCE(lc.likes_in_period, 0) * 3
       + COALESCE(cc.comments_in_period, 0)) AS score
FROM post AS p
LEFT JOIN like_counts AS lc ON lc.post_id = p.id
LEFT JOIN comment_counts AS cc ON cc.post_id = p.id
WHERE p.status = 'PUBLISHED'
  AND p.visibility = 'PUBLIC'
  AND p.deleted_at IS NULL
ORDER BY score DESC, p.published_at DESC, p.id DESC
LIMIT 10;

계약상 인기글은 비로그인 공개 범위로 접근 가능한 글만 대상으로 합니다. 더 복잡한 접근 정책이 추가되면 같은 필터를 적용해야 합니다. 기간은 `[지금 − days, 지금)`이므로 시작 시각은 포함하고 끝 시각은 제외합니다.

M9 활동 요약도 같은 함정이 있다

회원별 게시글·댓글·받은 좋아요·누른 좋아요 수를 동시에 원시 JOIN하면 서로 독립적인 1:N 관계끼리 행이 곱해집니다. 각각을 `member_id` 또는 기준 회원 키로 먼저 집계한 뒤 회원 테이블에 LEFT JOIN하면 활동이 없는 회원도 0으로 표현할 수 있습니다.

게시글 집계 → 회원당 1행댓글 집계 → 회원당 1행좋아요 집계 → 회원당 1행마지막에 member와 결합

#디버깅할 때 순서

  1. 각 테이블의 원본 행 수를 게시글별로 따로 세어 기대값을 적습니다.
  2. 조인을 하나씩 추가할 때 결과 행 수를 확인합니다.
  3. 한 게시글이 여러 행이면 현재 결과의 한 행이 무엇을 뜻하는지 말로 적습니다.
  4. 여러 1:N 관계를 집계한다면 각 관계를 먼저 그룹화하고, 집계 결과를 붙입니다.
  5. COUNT(DISTINCT ...)는 필요한 경우의 보정입니다. 서로 다른 SUM·가중치 점수가 왜곡되는 구조를 대신 설명해 주지 않습니다.
