SELECT p.id, p.title, m.nickname AS authorNickname,
       p.like_count AS likeCount,
       p.comment_count AS commentCount,
       p.published_at AS publishedAt
FROM board b
JOIN post p ON p.board_id = b.id
JOIN member m ON m.id = p.author_id
WHERE b.slug = 'dev'
  AND p.status = 'PUBLISHED'
  AND p.deleted_at IS NULL
  AND p.visibility = 'PUBLIC'
ORDER BY p.published_at DESC, p.id DESC

#이번 요청에서 정할 것

GET /api/boards/dev/posts?size=20&cursor=는 목록 첫 페이지입니다. 지금은 쿼리 파라미터가 어떤 열을 바꾸는지부터 구분합니다.

계약·응답 스키마에서 찾을 열 SQL에서 할 일
경로의 slug=dev board.slug board와 post를 board.id = post.board_id로 연결
id, title post.id, post.title 목록 SELECT에 포함
authorNickname member.nickname post.author_id = member.id로 연결
likeCount, commentCount post.like_count, post.comment_count 저장된 요약 열을 읽는다. 이번 단계에서 다시 COUNT하지 않는다
tags[] tag.name post_tag를 거쳐 현재 페이지 글의 태그를 한 번에 읽는다
publishedAt post.published_at 내림차순 정렬에 사용하고 응답에도 포함
목록 규칙 post.status, post.deleted_at, post.visibility 비로그인 기준 PUBLISHED, 미삭제, PUBLIC 행만 남긴다
size=20, 빈 cursor 요청 파라미터 첫 페이지는 커서 조건 없이 정렬 후 20개를 읽는다. 커서 인코딩·다음 페이지는 DB-02에서 다룬다

#조건과 정렬을 먼저 말로 만들기

  • WHERE: 게시판 slug가 dev이고, status = 'PUBLISHED', deleted_at IS NULL, 비로그인에게 공개되는 visibility = 'PUBLIC'.
  • ORDER BY: published_at DESC, 같은 시각이면 id DESC. 두 번째 기준이 없으면 동률 행 순서는 고정되지 않습니다.
  • 본문: content는 목록 응답에 없으므로 이 SELECT에 넣지 않습니다.
  • 태그: 한 게시글에 여러 태그가 붙을 수 있습니다. 메인 SELECT에 바로 JOIN하면 글 한 행이 태그 수만큼 반복될 수 있으므로, 이번 초안은 현재 페이지 글을 먼저 고른 뒤 태그를 별도 일괄 조회합니다.

기준 SQL 보기 — 게시글 목록과 태그 일괄 조회

목록 첫 페이지용 SQL입니다. 커서가 비어 있으므로 커서 비교 조건은 아직 없습니다.

SELECT
    p.id,
    p.title,
    m.nickname AS authorNickname,
    p.like_count AS likeCount,
    p.comment_count AS commentCount,
    p.published_at AS publishedAt
FROM board b
JOIN post p ON p.board_id = b.id
JOIN member m ON m.id = p.author_id
WHERE b.slug = 'dev'
  AND p.status = 'PUBLISHED'
  AND p.deleted_at IS NULL
  AND p.visibility = 'PUBLIC'
ORDER BY p.published_at DESC, p.id DESC
LIMIT 20;

목록 쿼리에서 나온 post.id 20개를 모아 아래처럼 태그를 조회합니다. 실제 실행 때는 IN 안에 방금 조회한 페이지의 ID를 넣으세요.

SELECT pt.post_id, t.name
FROM post_tag pt
JOIN tag t ON t.id = pt.tag_id
WHERE pt.post_id IN (145, 144, 143, 140, 138)
ORDER BY pt.post_id, t.name;

예시는 첫 다섯 ID로 관계를 확인하기 위한 것입니다. 실제 페이지 크기가 20이면 두 번째 쿼리에는 첫 쿼리에서 나온 최대 20개의 ID를 넣습니다. 이 방식은 태그 N+1을 피하는 한 가지 방법이며, 실제 M1 구현은 SQL 로그로 조회 횟수를 확인합니다.

#DBeaver에서 실제 행 확인

docker compose up -d로 DB가 준비된 뒤 CloudBeaver의 practice (학습용) 연결을 선택합니다. 아래 쿼리는 읽기 전용입니다. 실행한 결과와 화면의 API 필드를 한 줄씩 대조하세요.

SELECT
    p.id,
    p.title,
    m.nickname AS authorNickname,
    p.like_count AS likeCount,
    p.comment_count AS commentCount,
    p.published_at AS publishedAt
FROM board b
JOIN post p ON p.board_id = b.id
JOIN member m ON m.id = p.author_id
WHERE b.slug = 'dev'
  AND p.status = 'PUBLISHED'
  AND p.deleted_at IS NULL
  AND p.visibility = 'PUBLIC'
ORDER BY p.published_at DESC, p.id DESC
LIMIT 20;

M1의 비로그인 정답 확인값은 필터에 맞는 전체 글 50개이고, 첫 페이지 첫 다섯 ID는 145, 144, 143, 140, 138입니다. 한 번의 목록 SQL은 size=20에 맞춰 최대 20행만 반환합니다. 첫 행 145는 seed에서 제목 스프링 트랜잭션 전파 삽질기, 작성자 밤샘개발자, 좋아요 20, 댓글 1, 발행 시각 2026-10-03 10:10:08입니다. 태그는 두 번째 SQL에서 java로 확인됩니다. 이 값은 docker/mysql/init/02-practice.sql의 seed에서 대조했습니다. 현재 실행 중인 DB가 seed 이후 변경됐다면 DBeaver 결과를 기준으로 원인을 확인하세요.

시안은 텍스트 없는 레이아웃 참고 이미지입니다. 실제 API 경로·테이블·열·결과값은 위 계약과 seed를 기준으로 표시했습니다.
