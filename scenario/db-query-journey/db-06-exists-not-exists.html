DB-06 · 기준 쿼리

NOT EXISTS로 회원 12의 북마크 없는 좋아요를 찾으세요.

같은 회원·글의 북마크가 없을 때만 바깥 좋아요 행이 남습니다.

원문 NOT EXISTS SQLpractice DB · 읽기 전용
SELECT pl.post_id
FROM post_like AS pl
WHERE pl.member_id = 12
  AND NOT EXISTS (
      SELECT 1
      FROM bookmark AS b
      WHERE b.member_id = pl.member_id
        AND b.post_id = pl.post_id
  )
ORDER BY pl.created_at DESC, pl.id DESC;

pl.member_id와 pl.post_id는 현재 바깥 행의 값입니다. 정렬은 pl.created_at DESC, pl.id DESC입니다.

DB-06 · 현재 스키마의 NOT IN

NOT IN도 현재 스키마에서는 같은 제외 결과여야 합니다.

실제 bookmark.post_id와 member_id는 모두 NOT NULL입니다.

SELECT pl.post_id
FROM post_like AS pl
WHERE pl.member_id = 12
  AND pl.post_id NOT IN (
      SELECT b.post_id
      FROM bookmark AS b

NOT EXISTS와 같은 회원 12·같은 정렬을 사용합니다. 실제 ID와 순서는 마지막 대조 장면에서 확인하세요.

② 바깥 행 하나씩 질문하기

post_like에서 회원 12의 글을 한 행씩 꺼냅니다.

좋아요 행의 post_id→같은 member_id와 post_id의 bookmark가 있나?

있으면 제외, 없으면 결과에 남김. 그래서 예시 결과는 101입니다. 이 질문을 SQL로 표현하는 방법이 NOT EXISTS입니다.

먼저 완성할 SQL

SELECT pl.post_id
FROM post_like AS pl
WHERE pl.member_id = 12
  AND NOT EXISTS (
      SELECT 1
      FROM bookmark AS b
      WHERE b.member_id = pl.member_id
        AND b.post_id = pl.post_id
  )
ORDER BY pl.created_at DESC, pl.id DESC;

여기서 pl.member_id, pl.post_id는 바깥 쿼리의 현재 행을 안쪽 쿼리에 전달합니다. 안쪽 쿼리는 그 글의 북마크 행이 있는지만 검사합니다. 실제 API 구현에서는 SELECT와 ORDER BY가 응답 계약에 맞는지 먼저 정하고, 이 SQL 조각은 필터 조건에 넣습니다.

직접 해보기
회원 번호를 12로 고정해 쿼리를 실행하고 결과 ID를 기록하세요. 그다음 아래 EXISTS와 NOT IN 버전으로 바꾸어 ID와 순서를 비교합니다. 예상 결과 숫자는 이 문서에서 만들지 않습니다. 본인이 사용하는 practice seed에서 확인하세요.
EXISTS는 반대로 “북마크도 한 글”을 찾는다 
SELECT pl.post_id
FROM post_like AS pl
WHERE pl.member_id = 12
  AND EXISTS (
      SELECT 1
      FROM bookmark AS b
      WHERE b.member_id = pl.member_id
        AND b.post_id = pl.post_id
  )
ORDER BY pl.created_at DESC, pl.id DESC;

EXISTS는 안쪽 쿼리가 한 행이라도 찾으면 TRUE입니다. 위 결과는 “좋아요와 북마크 둘 다 한 글”이고, 앞의 NOT EXISTS 결과와 서로 반대 관계입니다. SELECT 1은 존재 여부만 확인하고 실제 열 값은 사용하지 않는다는 표시입니다.

같은 제외 조건을 NOT IN으로 표현하면? 
SELECT pl.post_id
FROM post_like AS pl
WHERE pl.member_id = 12
  AND pl.post_id NOT IN (
      SELECT b.post_id
      FROM bookmark AS b
      WHERE b.member_id = 12
  )
ORDER BY pl.created_at DESC, pl.id DESC;

IN은 안쪽 조회가 만든 값 목록에 바깥 값이 포함되는지 확인합니다. 이 예제의 bookmark.post_id는 NOT NULL이고, 안쪽 조건의 member_id도 실제 스키마에서 NOT NULL입니다. 따라서 현재 테이블 제약에서는 위 NOT IN 결과가 NOT EXISTS와 일치해야 합니다.

NOT EXISTS는 각 좋아요 행과 같은 키의 북마크 행이 실제로 있는지 검사하므로, 비교 대상 목록에 무관한 NULL이 포함되어 결과 전체가 미정이 되는 문제를 피합니다. 다만 올바른 키와 NULL 허용 여부를 먼저 확인해야 합니다. 이 프로젝트의 `bookmark.post_id`에는 NOT NULL 제약이 있어 실제 미션에서는 해당 NULL 함정이 재현되지 않습니다.

EXISTS와 JOIN은 언제 같은 결과가 되나요? 
SELECT pl.post_id
FROM post_like AS pl
LEFT JOIN bookmark AS b
  ON b.member_id = pl.member_id
 AND b.post_id = pl.post_id
WHERE pl.member_id = 12
  AND b.id IS NULL
ORDER BY pl.created_at DESC, pl.id DESC;

LEFT JOIN으로 짝이 없는 행을 찾는 방식도 가능합니다. 다만 북마크 조건을 `WHERE`가 아니라 `ON`에 두어야 합니다. 이 관계는 `(member_id, post_id)` UNIQUE KEY로 중복을 막으므로 이 예제의 JOIN은 좋아요 한 행을 북마크 여러 행으로 늘리지 않습니다. `EXISTS`는 “관련 행이 있는가?”라는 의도를 직접 표현해 읽기 쉽습니다. 결과 순서는 API의 정렬 계약에 맞춰 비교하세요.

JPA·MyBatis로 옮길 때 찾아볼 위치
  • MyBatis: Mapper XML의 `SELECT` 조건에 `NOT EXISTS`를 작성하고 `memberId`를 파라미터로 바인딩합니다.
  • JPA: JPQL의 `NOT EXISTS` 상관 서브쿼리 또는 native query를 선택합니다. 생성 SQL과 결과 순서를 확인합니다.
  • Service: 로그인 회원 ID와 페이지·정렬 계약을 Repository/Mapper에 전달합니다. SQL 조건을 Service에서 문자열로 조립하지 않습니다.

이번 페이지는 SQL 읽기·작성 연습입니다. 독립적인 API를 새로 만들거나 실제 서버 요청을 보내지 않습니다. 같은 SQL을 JPA·MyBatis·QueryDSL로 옮기는 단계는 DB-07에서 이어집니다.
