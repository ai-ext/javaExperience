이번에 할 일

access/refresh 수명·다중 기기·폐기·회전·장애 정책을 정하고 만료 경계와 재사용·경쟁을 실제 요청과 자동 테스트로 확인하세요.

시작 조건

  • 기존 로그인·내 정보 API와 서로 다른 기기용 테스트 토큰을 준비합니다.
  • 토큰 원문은 화면 입력에만 쓰고 로그·기록·브라우저 저장소에 넣지 않습니다.
  • refresh를 도입하지 않으면 재로그인 대안·잔여 위험을 분명히 적습니다.

사용자 시나리오

  1. 시작
    같은 회원이 두 기기에 로그인한 상태에서 한 기기가 로그아웃하거나 회원이 정지됩니다.
    행동
    만료 직전/경계/직후, 로그아웃한 토큰 재사용, 정지 회원, 갱신 경쟁 또는 재로그인 대안을 실행합니다.
    결과
    정한 정책에 따라 실제 API가401/403을 구분하며 유효한 다른 기기의 처리 범위도 일치합니다.
    이후
    인증 저장소 장애와 구/신 서명키 전환도 확인합니다. 환경 부족이면 전체 합격을 보류하고 재검증 조건을 남깁니다.

데이터와 이유

토큰 수명·폐기 식별 정보
원문 토큰을 보관하지 않고 효력과 폐기 범위를 판정합니다.
서명키 유예·시계 오차·장애 정책
교체 중 허용과 실패 시 거절/허용의 경계를 고정합니다.

업무 정책

  • fail-open/closed의 보안·가용성 비용을 비교합니다.
  • 최소 구현·만료·로그아웃 재사용·정지·회전 경쟁 또는 재로그인 검증은 필수입니다.
  • 저장소 장애·키 교체 확인 불가를 필수 항목 제외로 바꾸지 않습니다.

입력과 출력

  • 직접 정한 수명·시계 오차·이전키 유예·폐기 반영 지연, 토큰 두 세트, 정지 회원, 장애 조건

성공 기준

  • 정한 정책에 따라 실제 API가401/403을 구분하며 유효한 다른 기기의 처리 범위도 일치합니다.

실패와 데이터 보존

  • 폐기·만료·정지 토큰 또는 refresh 재사용 → 명세의401/403과 재로그인 요구를 응답합니다. · 유지: 폐기한 기기의 효력이 다른 사용자에게 전이되지 않습니다.
  • 인증 저장소 장애 → 선택한fail-open/closed 결과를 관찰합니다. · 유지: 장애를 정상 인증 성공으로 자동 취급하지 않습니다.

입력 사례

  • 같은 대상의 전후 비교

개발 과제

  • access/refresh 수명·다중 기기·폐기·회전·장애 정책을 정하고 만료 경계와 재사용·경쟁을 실제 요청과 자동 테스트로 확인하세요.

완료 확인

  • access/refresh 수명·로그아웃·다중 기기·회원 정지·탈취 의심·refresh rotation/reuse 탐지·서명키 교체 정책을 표로 정한다. refresh 미도입이면 재로그인 대안과 잔여 위험을 명시한다.
  • 인증 저장소 장애에서 fail-open/closed의 보안·가용성 비용, 허용 시계 오차·이전 키 유예·폐기 반영 지연을 결정한다.
  • 만료 경계·로그아웃 후 재사용·정지 회원·회전 경쟁 또는 재로그인 대안을 테스트하고 계약상 401/403을 대조한다.
  • 인증 저장소 장애·서명키 구/신 교체의 허용/거절을 검증하거나 환경 부족을 확인 불가로 남긴다. 토큰 원문은 출력하지 않는다.
  • 최소 구현과 만료·로그아웃 재사용·정지 회원·회전 경쟁 또는 재로그인 대안 검증은 필수다. 인증 저장소 장애·구/신 서명키 검증이 확인 불가이면 전체 합격은 보류하고 수행 환경·재검증 명령·해소 조건을 남긴다. 미도입 refresh는 재로그인 대안 검증으로 충족하지만 필수 실패를 제외로 바꾸지 않는다.
