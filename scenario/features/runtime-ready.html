서버·DB를 켜고 실행 환경 나누기

Java 서버와 MySQL을 로컬에서 재현 가능하게 띄우고, 실행 환경별 설정과 기본 동작을 구분합니다.

이번에 할 일

주어진 board 시작 자료로 서버·DB 실행 기반을 마련하고 health 상태를 확인하세요. DB·프로파일·비밀값·요청 처리를 따로 관찰해 실행이 된 이유를 기록합니다.

시작 조건

  • board-server의 `build.gradle`, `compose.yaml`, `src/main/resources/application*.yml`을 기준으로 실행한다. Java 21과 Spring Boot 4.1, MySQL 8.4를 사용한다.
  • `data-local.sql`은 local profile에서만 실행되는 예시 seed다. 실제 비밀값은 파일에 넣지 않고 환경 변수로 전달한다.

사용자 시나리오

  1. 시작
    새 board 실행 환경이다. D00 값 전달 예제와 D01 local MySQL 연결 설정을 준비한다.
    행동
    `docker compose up -d` 뒤 `./gradlew bootRun --args="--spring.profiles.active=local"`로 기동하고 `GET /actuator/health`를 호출한다. D00의 primitive 변경, 객체 필드 변경, 매개변수 재할당 테스트도 실행한다.
    결과
    MySQL 연결 로그가 확인되고 health는 HTTP 200, JSON `status=UP`이다. D00 테스트는 primitive 호출자 값 유지, 객체 필드 변경 반영, 새 객체 재할당은 호출자 값 유지로 끝난다.
    이후
    local 설정의 datasource가 MySQL 8.4를 가리키는지와 `SERVER_PORT=8081` 지정 시 `http://localhost:8081/actuator/health`가 200인지 확인한다. prod의 `DB_PASSWORD` 미설정 기동은 실패하고 `/actuator/env`는 노출되지 않는 것을 별도로 확인한다.

회원 객체를 담은 List<Post> 실습값

애플리케이션 health가 DB 연결 구성과 분리될 수 있으므로 컨테이너와 실제 연결 로그를 각각 확인한다.

health 응답과 요청 ID 로그
서버 기동·HTTP 상태·요청별 로그 상관관계를 각각 확인한다.

업무 정책

  • 과정 시작 자료의 compose.yaml을 사용하고 이 단계에서는 Flyway를 도입하지 않습니다.
  • 비밀값을 파일이나 학습 기록에 실제 값으로 저장하지 말고 환경 변수 자리표시자로 둡니다.
  • D00의 값 전달 테스트는 primitive 값 복사와 객체 참조 복사를 구분합니다.
  • 원문 완료 기준: 값 전달 테스트 3개: 메서드 안에서 `int`를 바꾸면 호출한 쪽은 그대로, 객체 필드를 바꾸면 호출한 쪽도 바뀜, 매개변수에 새 객체를 대입하면 호출한 쪽은 그대로
  • 원문 완료 기준: `./gradlew bootRun`으로 기동 (D01 ③에서 datasource를 `local` 프로파일로 옮긴 뒤로는 `./gradlew bootRun --args='--spring.profiles.active=local'`로 띄운다)
  • 원문 완료 기준: `GET /actuator/health` → 200, 본문의 `status`가 `UP` (Boot 4는 `groups`도 함께 준다)
  • 원문 완료 기준: `docker compose up -d` 뒤 기동 로그에 `HikariPool-1 - Start completed`
  • 원문 완료 기준: `GET /actuator/health` → 200
  • 원문 완료 기준: `test` 프로파일 설정이 있다: YAML의 `---`·`on-profile: test` 문서 또는 `application-test.properties`의 같은 키·값을 인정한다
  • 원문 완료 기준: `--spring.profiles.active=local` 기동 로그에 `The following 1 profile is active: "local"`
  • 원문 완료 기준: `SERVER_PORT=8081`로 실행하면 설정 파일의 `server.port`보다 환경 변수가 이긴다: `GET http://localhost:8081/actuator/health` → 200
  • 원문 완료 기준: prod 프로파일은 `DB_PASSWORD` 환경 변수 없이 기동하면 실패한다
  • 원문 완료 기준: `GET /actuator/env` → 404 (HTTP로는 `health`만 노출)
  • 원문 완료 기준: `BoardPropertiesTest` 통과: `board.forbidden-words.*` 값이 객체로 바인딩된다
  • 원문 완료 기준: 필수 값을 비우면 `@Validated` 때문에 기동이 실패한다
  • 원문 완료 기준: 정상 값으로 기동하면 `GET /actuator/health` → 200

입력과 출력

  • Java 21, Boot 4.1, Web·Actuator·Validation·Lombok 의존성만 선택한다.
  • 시작 자료의 compose.yaml, datasource URL, local profile을 사용한다. prod 비밀값은 placeholder로 두고 환경 변수로 받는다.
  • health 요청은 GET /actuator/health이며 기본 port와 SERVER_PORT=8081 사례를 각각 기록한다.

성공 기준

  • `docker compose up -d` 뒤 MySQL이 healthy이고 기동 로그에 HikariPool 시작 완료가 남는다.
  • `GET /actuator/health` → 200, `status=UP`; `SERVER_PORT=8081`이면 8081 포트 health도 200이다.
  • D00 값 전달 세 테스트 결과가 각각 호출자 primitive 불변, 공유 객체 필드 반영, 매개변수 재할당 비반영이다.
  • prod에서 `DB_PASSWORD` 없는 기동은 실패하며 `GET /actuator/env`는 404다.

실패와 데이터 보존

  • MySQL 컨테이너가 중지됐거나 datasource URL/자격 설정이 맞지 않음 → Hikari 연결 실패가 기록되고 앱 또는 DB 연결 확인이 실패한다. health 200만으로 DB 준비 완료를 선언하지 않는다. · 유지: 실패한 기동을 정상 완료로 표시하지 않고 datasource 설정이나 container 상태를 바꾸기 전에 원인을 기록한다.
  • prod profile에서 DB_PASSWORD가 주어지지 않음 → 설정 검증 때문에 기동이 실패한다. · 유지: 실제 비밀값을 application.yml이나 결과 로그에 저장하지 않는다.

입력 사례

  • local 기동
  • prod 비밀값 누락

개발 과제

  • D00의 매개변수 전달 결과를 세 경우로 나누어 테스트한다.
  • MySQL 기동, datasource 연결, health 요청을 각각 실행해 어느 계층이 확인됐는지 기록한다.
  • local/prod 설정에서 키의 출처와 환경 변수 우선순위를 대조한다.

완료 확인

  • Java 21·Boot 4.1 구성과 네 의존성을 확인했다.
  • MySQL 8.4 연결 로그와 health 200/status UP을 확인했고 8081 환경 변수 override도 확인했다.
  • D00의 세 값 전달 테스트와 prod 비밀값 누락 기동 실패, actuator 비노출 결과를 각각 기록했다.
