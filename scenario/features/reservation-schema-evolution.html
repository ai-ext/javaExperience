이전 앱도 읽고 쓰는 nullable 메모 추가하기

이전 앱이 실행 중인 상태에서 예약 운영 메모를 보관할 수 있게 확장합니다.

이번에 할 일

nullable 열을 추가하고 구앱/구DB·구앱/확장DB·신앱/확장DB의 읽기·쓰기를 확인하세요. 열린 트랜잭션 때문에 DDL이 기다리는 상황도 별도로 관찰하세요.

시작 조건

  • 앱의 구·신 고정 이미지와 전용 실험 DB, 변경 전 백업·행 수를 준비합니다.
  • 오늘은 nullable 추가와 호환까지만 하며 아직 NOT NULL을 강제하지 않습니다.

사용자 시나리오

  1. 시작
    구앱이 메모 없는 예약을 쓰는 동안 nullable 메모 열을 확장합니다.
    행동
    호환 행렬의 세 조합을 실행하고 두 DB 연결에서 열린 트랜잭션과 DDL 대기를 관찰합니다.
    결과
    기존 데이터·요청이 유지되고 새 앱은 메모를 보관합니다. 금지 조합과 중단 기준이 분명합니다.
    이후
    DDL 대기·timeout·중단 결과와 실제 시간을 남기며 실측 없이 무중단이라고 선언하지 않습니다.

데이터와 이유

기존 예약과 nullable 운영 메모
구앱의 쓰기를 당장 깨뜨리지 않고 새 정보를 받습니다.
호환 행렬과 백업 시점
어느 앱·DB 조합으로 되돌릴 수 있는지 판정합니다.

업무 정책

  • 순서는 expand→신앱 쓰기 전환→구앱 종료→null 재유입 차단→최종 백필→제약 강화입니다.
  • 신앱/구DB 지원 여부는 별도 결정합니다.
  • metadata lock 진단은 disposable DB에서만 합니다.

입력과 출력

  • 메모 없음/있음의 예약, 구·신 이미지, 확장 전후 스키마, 열린 트랜잭션 두 연결

성공 기준

  • 기존 데이터·요청이 유지되고 새 앱은 메모를 보관합니다. 금지 조합과 중단 기준이 분명합니다.

실패와 데이터 보존

  • DDL이 대기하거나 timeout → 미리 정한 기준에서 중단하고 담당 행동을 기록합니다. · 유지: 기존 예약과 실행 중인 쓰기를 임의로 지우지 않습니다.

입력 사례

  • 구앱/구DB·구앱/확장DB·신앱/확장DB의 읽기/쓰기 smoke를 실행한다. 신앱/구DB 지원 여부와 금지 조합도 명시한다.

  • 변경 전 백업 경로·행 수·중단 기준·앱/DB 담당 행동을 runbook에 적는다. 대기 시간 실측 없이 무중단이라고 선언하지 않는다.

  • 원인 서술: ALTER는 무엇을 기다렸고, 그 앞의 무엇이 락을 쥐고 있었으며, 왜 ALTER 뒤의 쿼리까지 멈췄는가
  • 재현 테스트: 첫 주문이 느린 알림을 기다리는 동안 별도 연결로 ALTER(`lock_wait_timeout`을 짧게)를 걸고, 그 뒤의 다른 주문이 곧바로 반영되는지 보는 테스트(결함 상태에서 실패 → 수정 후 통과). 끝나면 추가한 컬럼을 지운다.

  • 백필 중단 또는 구앱의 null 재유입 → 체크포인트로 재개하고 최종 완료 판정을 보류합니다. · 유지: 기존 메모를 덮어쓰거나 다른 구간을 중복 변경하지 않습니다.

    
입력 사례

개발 과제
  • PK 구간과 체크포인트로 백필을 절반에서 멈췄다 재개한 뒤, 모든 구앱·worker 종료와 쓰기 전환을 확인하고 최종 백필·제약 강화를 하세요.

    
완료 확인
  • PK 구간·batch 크기·체크포인트·진행률·재시도 정책을 정하고 대상의 절반에서 중단한다.
  • 재시작·동일 구간 재실행 후 중복 변경 0을 대사한다. 구앱 쓰기로 null이 재유입되는 것을 관찰한다. 이 예비 백필의 미처리 0은 contract 진입 허가가 아니며 쓰기 전환 후 최종 백필을 다시 한다.
  • 전체 순서 expand → 신앱 쓰기 전환 → 구앱 종료 → null 재유입 차단 확인 → 최종 백필 → 제약 강화를 따른다. 신앱 쓰기 전환과 모든 구앱/구 worker 종료를 확인한 뒤 null을 만드는 요청을 신앱이 거부하는지 검사한다. 그 뒤 최종 백필·미처리 0 대사·제약 강화를 실행한다.
  • 강화 후 신앱 테스트와 호환 행렬을 갱신한다. 앱 롤백이 불가능해지는 경계·대신 forward fix/복원 조건을 적는다.
