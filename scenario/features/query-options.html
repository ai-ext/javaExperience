이번에 할 일

20개 목록의 author/tag SQL 증가를 측정하고 member3/dev 결과와 member4 빈 결과를 확인한다.

시작 조건

  • free board 목록 20개와 author/tag 관계를 가진 scenario fixture를 사용한다.
  • member3 이스프링은 post2(dev), member4는 존재하지만 dev 글이 없고 post6 followers/post8 deleted를 확인한다.

사용자 시나리오

  1. 시작
    GET /api/boards/free/posts?size=20 전후 SQL과 item ids를 기록한다.
    행동
    20개 목록 query를 대조한 뒤 GET /api/members/3/posts?board=dev 및 member4 같은 route를 호출한다.
    결과
    N+1 query 수는 측정 후 감소하되 JSON은 유지한다. member3 결과에 post2, member4는 200 [].
    이후
    post6/post8의 공개 결과 제외와 JPQL/query projection을 확인한다.

데이터와 이유

free board 20 posts and author/tag relations
N+1 before/after 측정.
member3 post2 title/author/board
검색 projection과 필터 확인.
member4 empty results, post6/post8
empty result와 visibility exclusions 검증.

업무 정책

  • 2-4 preserves response shape and logs SQL count for 20 items.
  • 2-5 requires member+board existence; missing ->404, existing with no public match ->200 [].
  • filter: author, board, PUBLISHED, PUBLIC, not deleted; SQL uses columns, JPQL uses entity fields.

입력과 출력

  • GET /api/boards/free/posts?size=20.
  • GET /api/members/3/posts?board=dev and member4 equivalent.

성공 기준

  • 20-item response fields/order preserved; before/after query counts are measured.
  • member3 gets id2 JPA 연관관계 매핑 정리; member4 gets 200 [].

실패와 데이터 보존

  • member/board missing → 404. · 유지: posts unchanged.
  • member4/board dev exist but no matching row → 200 empty list. · 유지: database unchanged.
  • post6 or deleted post8 appears in anonymous results → visibility assertion fails. · 유지: query read-only.

입력 사례

  • N+1 measurement
  • member3 dev posts
  • existing member empty

개발 과제

  • Capture SQL logs and result IDs at page size 20.
  • Compare direct SQL and JPQL query filters.
  • Check missing entity versus empty result and public filters.

완료 확인

  • N+1 query count measured; response shape retained.
  • 404 missing member/board differs from 200 empty.
  • public/deleted conditions checked.

  • L16. interface와 impl — 같은 API를 JPA·JDBC 두 구현으로 읽기 ↗ · database-lab
    프로젝트 · community
    필수 여부 · 선택
    원문 요구사항
    • **계약:** `PostSummaryReader` 인터페이스에 `Optional<PostSummary> findPublic(long id)` 한 메서드를 만든다. `PostSummary`는 `id`, `title` 두 값만 담는 불변 DTO다. `PostSummaryService`는 이 인터페이스만 생성자로 받고, 결과가 없으면 404로 바꾼다. Controller는 `GET /api/labs/post-summaries/{id}`만 연결한다. `id<=0`은 400으로 처리한다.
    • **JPA 구현:** `JpaPostSummaryReader implements PostSummaryReader`. 기존 `PostRepository` 또는 JPA 쿼리에서 id와 `deletedAt=null`, `status=PUBLISHED`, `visibility=PUBLIC`을 확인한다. `Post` Entity를 HTTP로 직접 내보내지 않는다. 이미 DB에 읽은 Entity 값에서 DTO로 변환한다.
    • **JDBC 구현:** `JdbcPostSummaryReader implements PostSummaryReader`. 필요하면 프로젝트에 `spring-boot-starter-jdbc`를 추가한다. `JdbcTemplate`의 바인딩 파라미터로 아래 SQL을 실행하고 DTO로 매핑한다. ID를 SQL 문자열에 이어 붙이지 않는다.
    • **Spring 빈 선택:** `app.post-summary.reader=jpa`를 기본값, `jdbc`를 다른 값으로 둔다. 각 구현체를 조건부로 등록해 **한 번에 하나만** `PostSummaryReader` 빈이 생기게 한다. 예를 들면 `@ConditionalOnProperty(name="app.post-summary.reader", havingValue="jpa", matchIfMissing=true)`와 `havingValue="jdbc"`를 쓸 수 있다. Service와 Controller 코드는 설정을 바꿀 때 수정하지 않는다.
    • **실패를 보고 복구:** 잠시 두 조건을 모두 없애 두 구현을 동시에 빈으로 등록한다. 주입 후보가 둘이라 애플리케이션 시작이 실패하는 것을 관찰한다. 예외에 나오는 두 구현체 이름을 찾은 뒤 조건을 다시 넣는다. 빈을 하나도 등록하지 않은 경우도 서비스 생성에 실패한다는 것을 설명한다. 실패 실험은 서버를 구동해 확인한 뒤 원래 설정으로 복구한다.
