7장 Controller slice, service unit, real MySQL integration test가 보장하는 경계를 각각 확인한다.

이번에 할 일

PostControllerTest, LikeServiceTest, PostFlowIntegrationTest 전용 명령을 실행하고 각 테스트의 mock/real dependency와 assertion을 기록한다.

시작 조건

  • community-board test configuration과 Testcontainers의 MySQL 사용 여부를 확인한다.
  • 테스트 class 이름과 package를 원문에서 그대로 사용한다.

사용자 시나리오

  1. 시작
    컨트롤러만 테스트, 서비스 규칙 테스트, 전체 요청 flow 테스트를 각각 분류한다.
    행동
    각 source에 선언된 `./gradlew test --tests ...` 명령을 따로 실행한다.
    결과
    Controller: POST 정상201+Location, blank title400, no token401, absent post404. Service: own post no save, new like once+1, existing like/no unlike no-op, access policy404. Integration: 실제 DB로 글→상세→좋아요→댓글→삭제.
    이후
    integration DB free list id가 21..12,9,5,4인지 확인하고 container 로그를 보존한다.

데이터와 이유

PostControllerTest MockMvc status/header/problem body
HTTP contract 검증을 확인.
LikeServiceTest repository calls/count
순수 서비스 정책과 side effect 횟수 검증.
PostFlowIntegrationTest generated post id and final DB rows
실제 SQL·commit·인증 흐름 검증.
free board seed ids 21..12,9,5,4
visibility/list fixture contract 확인.

업무 정책

  • PostControllerTest는 @WebMvcTest(PostController.class), controller/validation/advice 실물, PostService/token mock, DB container 없이 실행.
  • LikeServiceTest는 Spring context와 DB 없는 pure unit; policy spy는 요구된 테스트에 한해 사용.
  • PostFlowIntegrationTest는 @SpringBootTest + @AutoConfigureMockMvc + real MySQL Testcontainers, service/repository mock 금지. 생성 id를 다음 요청에 이어 쓰고 request commit을 관찰한다.

입력과 출력

  • ./gradlew test --tests org.example.post.PostControllerTest
  • ./gradlew test --tests org.example.like.LikeServiceTest
  • ./gradlew test --tests org.example.post.PostFlowIntegrationTest

성공 기준

  • Controller has 4+ contract tests: 201+Location+author, 400 title error, 401+WWW-Authenticate, 404.
  • Like unit has 5+ cases: self-like no save; new save once and count+1; existing unlike no-op; absent unlike no-op; actual access policy 404.
  • Integration runs real MySQL and verifies create201/detail200/like/comment201/delete204 plus free seed order.

실패와 데이터 보존

  • Controller slice starts Hikari/Testcontainers or claims a mock service performed real SQL → test boundary is misrepresented. · 유지: test environment and database remain unchanged.
  • blank title test invokes create service, or 401 misses WWW-Authenticate → contract assertion fails. · 유지: no database write occurs in slice.
  • integration test reuses hard-coded post id instead of response id or mocks repository → flow does not prove persistent linkage. · 유지: existing fixture preserved.

입력 사례

  • Controller contract
  • Like policy unit
  • Real flow

개발 과제

  • 각 테스트의 annotation, mock target, dependency startup log를 캡처한다.
  • status 외 Location, JSON fields, interaction count, final DB state assertion을 확인한다.
  • 통합은 실제 id를 다음 요청에 전달하고 commit 후 결과를 읽는다.

완료 확인

  • 세 테스트의 가짜/실제 경계를 설명했다.
  • HTTP contract·service rule·database integration assertions를 각각 확인했다.
  • Testcontainers와 seed ordering 증거를 기록했다.

    필수 여부 · 필수

    원문 요구사항

    • 서비스는 `@MockitoBean`으로 가짜로 바꾸고, 각 테스트에서 돌려줄 값을 정한다(`given(...).willReturn(...)`).
    • 1-6의 토큰 확인 부품(인터셉터·ArgumentResolver 등)이 리포지토리를 쓴다면 그 리포지토리도 `@MockitoBean`으로 바꾸고 "토큰 → 회원"을 정해 준다.
    • 그 부품이 `Clock` 같은 **설정 빈**(`@Configuration`)을 주입받는다면 `@WebMvcTest`는 일반 `@Configuration`을 읽지 않으므로 `@Import(ClockConfig.class)`처럼 직접 가져온다.
    • 서비스가 엔티티를 돌려주고 컨트롤러가 DTO로 바꾸는 구조(1-3)라면, 테스트에서 id·게시판이 채워진 엔티티를 mock으로 꾸며야 한다. 서비스가 응답 DTO(또는 결과 객체)를 돌려주면 슬라이스 테스트가 훨씬 쉬워진다 — 구조를 고를 때의 트레이드오프다.
    • DB 없이 돌아야 한다. 이 테스트만 돌리면 Testcontainers MySQL이 뜨지 않는다.
