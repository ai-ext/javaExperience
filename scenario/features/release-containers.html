이번에 할 일

고정 태그·별도 포트·전용 DB 볼륨으로 기동한 뒤 느린 요청 중 SIGTERM을 보내 정상 종료와 강제 종료를 비교하세요.

시작 조건

  • 내 프로젝트의 예약 생성·조회와 기존 로그인이 동작합니다.
  • 격리 포트·DB·환경변수 이름·health 명령을 runbook에 적고 비밀값은 넣지 않습니다.

사용자 시나리오

  1. 시작
    이미지 A가 별도 DB에 예약을 저장했고 느린 요청 하나가 진행 중입니다.
    행동
    종료 신호 뒤 신규 요청·기존 요청·프로세스 종료를 관찰하고 동일 이미지를 다시 기동합니다.
    결과
    health·로그인·예약 smoke가 실제로 동작하고 종료 시 완료/실패한 요청을 식별할 수 있습니다.
    이후
    재기동 후 기존 예약과 새 데이터가 유지되고 종료 제한 시간과 이전 이미지 복귀 명령이 기록됩니다.

데이터와 이유

이미지 ID·설정 이름
같은 실행물을 다시 올릴 수 있게 합니다.
진행 요청 id·종료 시각
신규 수용 중단과 기존 요청 결과를 구분합니다.

업무 정책

  • 공개 클라우드 배포는 필요하지 않습니다.
  • 실험용 앱 PID·컨테이너만 종료합니다.
  • 실측하지 않은 정상 종료 시간과 가용성을 보장으로 쓰지 않습니다.

입력과 출력

  • 고정 이미지 태그·격리 포트·DB볼륨·가짜 요청id·SIGTERM·종료 상한

성공 기준

  • health·로그인·예약 smoke가 실제로 동작하고 종료 시 완료/실패한 요청을 식별할 수 있습니다.

실패와 데이터 보존

  • 제한 시간 안에 끝나지 않은 요청 → 남은 요청과 강제 종료의 영향을 별도로 기록합니다. · 유지: 원본 DB·다른 개발 서버·사용자의 컨테이너를 종료하지 않습니다.

입력 사례

  • 같은 대상의 전후 비교

개발 과제

완료 확인

  • 컨테이너에서 health·예약 생성/조회·기존 로그인 smoke를 실행하고 이미지 ID·설정·출력을 남긴다. 공개 클라우드 배포는 요구하지 않는다.
  • 느린 요청 중 SIGTERM을 보내 신규 요청 수용 중단·기존 요청 완료·종료 제한 시간을 측정한다. 강제 종료와 차이를 기록한다.
