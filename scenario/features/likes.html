반복·동시 요청에서도 좋아요 수 일치시키기

과정 D05 likes 관계의 PUT/DELETE 멱등 동작을 spec-board의 204 빈 body 계약으로 확인한다.

이번에 할 일

같은 member/post를 PUT 두 번, DELETE 두 번 보내고 post_like 행 수와 like_count 변화가 한번만 생기는지 확인한다.

시작 조건

  • spec-board board:like-put/like-delete recipe가 사용하는 PUT/DELETE route를 선택한다.
  • 테스트 post와 Kim member id를 준비하고 좋아요 전 post_like row 수·like_count를 읽는다.

사용자 시나리오

  1. 시작
    post 3, Kim→post 3 관계 없음; 기존 like_count L.
    행동
    PUT /api/posts/3/like 두 번, DELETE 두 번을 순서대로 호출한다.
    결과
    각 board API contract는 204 empty body; 첫 PUT만 관계 생성/카운트 +1, 두 번째는 동일; 첫 DELETE만 제거/카운트 -1, 두 번째 동일.
    이후
    응답 body가 비어 있다는 점과 DB row/count를 구별해 측정한다.

데이터와 이유

post_like(post_id=3,member_id=Kim)
멱등 요청에서 relation row가 최대 1개인지 확인.
post.like_count의 시작값 L
처음 PUT/DELETE의 변화만 계산하고 고정 절대값을 가정하지 않음.
204 empty response
본문 JSON이 없는 성공을 community/project 응답으로 착각하지 않음.

업무 정책

  • board D05 likes API recipe의 URI와 성공 status 204/empty body를 그대로 쓴다. 200 JSON 응답이 아니다.
  • PUT은 liked=true 상태를 만든다. DELETE는 liked=false 상태를 만든다. 같은 verb 반복은 상태를 다시 toggle하지 않는다.
  • 본문에서 member id나 likeCount를 받지 않고 token member를 쓴다. 자기 글 좋아요 및 visibility/접근 조건은 source rule에 따른다.

입력과 출력

  • PUT /api/posts/3/like, 동일 PUT 재요청.
  • DELETE /api/posts/3/like, 동일 DELETE 재요청.
  • 멤버별 토큰 누락 및 없는 post id.

성공 기준

  • 각 정상 PUT/DELETE → 204 No Content.
  • 첫 PUT 뒤 relation 1개와 like_count L+1; 두 번째 뒤 그대로.
  • 첫 DELETE 뒤 row 0개와 L; 두 번째 뒤 그대로.

실패와 데이터 보존

  • token 없음 → 401. · 유지: relation row·like_count 그대로.
  • post 없음/삭제/비공개 접근 불가 → recipe contract에 명시된 404. · 유지: 관계와 count unchanged.
  • 내 글을 좋아요 → 해당 course 원문/API validation status를 확인한다. · 유지: row나 count가 생성되지 않는다.

입력 사례

  • 중복 PUT
  • 중복 DELETE

개발 과제

  • board recipes의 exact project/status/bodyMode를 확인한다.
  • 요청마다 relation count와 count column을 다시 읽는다.
  • status 204에 JSON body를 기대하지 않고 측정한다.

완료 확인

  • PUT/DELETE 재전송 후 관계와 집계가 멱등이다.
  • 204 no-content 계약을 별도 기록했다.
  • 401/404 실패 후 DB가 보존됐다.

선택한 API 계약

반복·동시 요청에서도 좋아요 수 일치시키기

    
    

    
community 4-0~4-2의 좋아요 생성·취소·동시성 경합을 실제 relation 수와 like_count로 검증한다.

    
이번에 할 일
김자바가 박디비 글 3을 먼저 취소하고 PUT/DELETE idempotency를 반복한다. 동시성 fixture에서는 20명·동일 회원 경합도 테스트한다.

    
시작 조건
  • tok-kimjava와 public post 3 또는 자신의 테스트 글, post_like 및 like_count 시작값을 기록한다.
  • 4-2 동시성 테스트는 글16 실제 seed 초기값 0, 회원 7~26 및 tok-c01~tok-c20을 쓴다. 설명 timeline의 5는 별도 예시값이다.

    
사용자 시나리오
  1. 시작
    post 3에서 Kim relation을 DELETE로 제거해 baseline을 기록한다.
    행동
    PUT /api/posts/3/like 두 번 후 DELETE 두 번; 별도 LikeConcurrencyTest에서 20명 동시 PUT 및 같은 회원 5회 PUT.
    결과
    일반 4-1은 각 PUT/DELETE 200 JSON {postId,liked,likeCount}; 반복 요청은 상태/count 유지. 4-2 20명 요청 모두 200이며 row=20,count=20; 같은 회원 동시 5회 row=1.
    이후
    DB count와 select count(*) from post_like를 일치 확인하고 같은 글 request에서 500/중복 key가 없는지 log 확인.

    
데이터와 이유
post 3 Kim relation 및 like_count baseline L
첫/반복 PUT/DELETE의 변화량 분리.
post 16 동시성 fixture와 회원7~26
서로 다른 20명의 정합성 기준.
post_like rows 및 UNIQUE(post_id,member_id)
중복과 갱신손실 예방을 확인.
4-2 설명값 5→6→7
lost-update 원리 그림 예시이며 seed 실제 count=0과 구별.

    
업무 정책
  • community 4-1 PUT은 like 상태, DELETE는 unlike 상태를 멱등하게 만든다. 각 응답은 200 JSON {postId,liked,likeCount}. toggle로 구현하지 않는다.
  • post_like row 수와 post.like_count는 항상 같아야 한다. 원자 DB update는 INSERT/DELETE 실제 영향 행이 1일 때만 count를 바꾼다.
  • 자기 글·없는 글·권한/인증 실패 status는 source recipe를 사용한다. 경합의 unique violation을 transaction에서 삼켜 500으로 끝내지 않는다.
  • 20명 동시 요청과 같은 회원 5회 요청은 서로 다른 동시성 케이스로 실행한다.

    
입력과 출력
  • 일반: Kim token, post 3; 먼저 DELETE baseline reset, then PUT×2, DELETE×2.
  • 경합: post16, 회원 7..26/tok-c01..tok-c20 동시 PUT 20개.
  • 같은 member: 동일 post에 concurrent PUT 5개.

    
성공 기준
  • community PUT/DELETE 200 response의 liked=true/false와 likeCount가 변경 뒤 수치다.
  • 서로 다른 20명 concurrent PUT 모두 200; post_like 20행, like_count 20 증가(시작 0).
  • 같은 회원 5 simultaneous PUT 모두 정상 처리, 관계 row 1개.

    
실패와 데이터 보존
  • 회원 없이 PUT/DELETE → 401. · 유지: relation/count unchanged.
  • 없는 id/자기 글/비공개 글 등 원문 실패 사례 → 각 source recipe 상태(400/401/403/404)를 확인한다. · 유지: row 수와 like_count 관계가 요청 전 상태.
  • 동일 회원 동시 INSERT가 중복키로 충돌 → 원문 기준 이미 좋아요 상태로 정상 응답해야 하며 500이 아니다. · 유지: 중복행 없이 count가 실제 row 수와 일치.

    
입력 사례
  • 멱등 PUT/DELETE
  • 서로 다른 20명 동시
  • 같은 회원 5회 경합

    
개발 과제
  • 4-1 state-reset부터 실행하고 일반 요청과 동시성 테스트를 구분한다.
  • thread barrier 결과, 각 HTTP status, final SQL count를 기록한다.
  • race 설명의 시작 5와 post16 실습 초기 0을 별개라고 표시한다.

    
완료 확인
  • PUT/DELETE 반복이 toggle이 아니라 멱등 상태 설정임을 확인했다.
  • 두 동시성 케이스의 HTTP status/관계행수/count가 일치한다.
  • 500이나 lost update 재현/수정 여부를 테스트 결과로 남겼다.

반복·동시 요청에서도 좋아요 수 일치시키기

    
    

    
spec-board 10-10 토글 v1과 10-11 멱등 v2를 분리해 상태 변화·버전 호환을 검증한다.

    
이번에 할 일
post 29 v1 POST를 두 번 보내 toggle 변화와 10-11 v2 PUT/DELETE 재요청의 멱등 차이를 비교한다.

    
시작 조건
  • project-v1 posts schema post_likes와 count를 확인하고 본인 소유가 아닌 visible post 29/40을 사용한다.
  • 10-10 v1 POST /api/v1/posts/{postId}/like, 10-11 v2 PUT/DELETE /api/v2/posts/{postId}/like는 별개 contract다.

    
사용자 시나리오
  1. 시작
    post29 count=0, Kim relation 없음.
    행동
    v1 POST 두 번, 별도 post40에서 v2 PUT 두 번 후 DELETE 두 번.
    결과
    v1 POST 200 wrapper에서 첫 liked=true,count1, 둘째 false,count0; v2 PUT 반복 모두 200 liked=true,count1, DELETE 반복 모두 200 liked=false,count0.
    이후
    동시 v2 PUT 10개도 모두 200이고 final count=1, old v1 route 의미는 계속 toggle로 둔다.

    
데이터와 이유
post_likes(post_id,user_id) pair
복합 기본키로 한 회원·글 관계를 중복 방지.
posts.like_count
DB atomic delta 후 응답 count를 재조회.
v1/v2 endpoint version
기존 앱 토글 계약을 보존하면서 새 API 의미 차이를 확인.

    
업무 정책
  • 10-10 v1은 POST /api/v1/posts/{id}/like toggle 그대로 둔다. 두 번 호출하면 liked true→false로 전환된다.
  • 10-11 v2는 PUT으로 liked=true, DELETE로 false를 idempotently 설정한다. 같은 회원 동시 PUT 10회 모두 200, count 한 번 증가.
  • count delta는 DB에서 원자 update, 관계 변경과 같은 transaction에서 처리한다. 해당 viewer가 글을 볼 수 없으면 404, token 없음 401.

    
입력과 출력
  • v1 post29: POST twice, token Kim; inspect data.liked/likeCount.
  • v2 post40: PUT twice, DELETE twice.
  • Concurrent v2: 같은 회원·post에 PUT 10회.

    
성공 기준
  • v1 첫 POST {liked:true,likeCount:1}; 두 번째 {liked:false,likeCount:0}, both 200.
  • v2 PUT repeated → both 200, liked=true,count=1. DELETE repeated → both 200, liked=false,count=0.
  • 동시 v2 PUT 10회 모두 200, 한 row와 count1.

    
실패와 데이터 보존
  • token 없음 → 401 ApiResponse error. · 유지: post_likes/count 유지.
  • post 없음·삭제·남의 private → 404. · 유지: like relation/count unchanged.
  • 동시 요청이 unique conflict/deadlock으로 종결 → 재시도 정책 뒤 API success 200을 확인; 처리 안 된 500은 실패. · 유지: final count가 relation row와 같아야 한다.

    
입력 사례
  • v1 toggle 유지
  • v2 idempotent PUT
  • v2 concurrent PUT

    
개발 과제
  • 같은 초기 상태를 만들기 위해 먼저 v1/v2 각각의 reset contract를 실행한다.
  • 응답 body wrapper의 data 값을 확인하고 DB like_count를 새로 읽는다.
  • 동시 요청에서는 server log의 deadlock retry와 최종 row/count를 함께 기록한다.

    
완료 확인
  • v1 toggle와 v2 PUT/DELETE의 의미 차이를 확인했다.
  • 같은 요청 재전송 및 10회 동시 요청의 idempotency를 확인했다.
  • 세션/route version을 바꾸지 않고 기존 v1 호환을 보존했다.
