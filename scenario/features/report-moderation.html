신고 접수와 관리자 목록 연결하기

회원 신고를 저장하고 관리자에게 신고 목록을 제공해 검토 대상을 찾게 합니다.

이번에 할 일

같은 회원의 같은 글 중복 신고를 막고 신고 등록 뒤 ADMIN 목록에 나타나는지 USER와 ADMIN 권한을 비교하세요.

시작 조건

  • ACTIVE 게시글 P-101, USER 회원 A/B, ADMIN token을 준비한다. A는 P-101을 아직 신고하지 않았다.
  • D10 ReportServiceTest의 같은 회원·같은 글 duplicate 규칙과 실제 source recipe를 연결한다.

사용자 시나리오

  1. 시작
    ACTIVE P-101에 USER A/B가 있고 기존 신고는 0건이다.
    행동
    A가 POST /api/posts/101/reports를 보낸다. A로 같은 요청을 다시 보내고 B로 한 번 신고한다. ADMIN과 USER token으로 GET /api/admin/reports를 각각 호출한다.
    결과
    A 첫 신고 201, A 중복 신고 409 `/errors/duplicate`, B 신고 201이다. ADMIN 목록은 200이고 USER 목록은 403이다.
    이후
    DB report는 회원·글 조합별 한 건만 존재하고 관리 목록은 신고 2건을 표시한다. 실패한 duplicate나 USER 권한 요청으로 report 상태가 더 생기지 않는다.

데이터와 이유

report(post_id, reporter_member_id)
신고 대상과 신고자를 외래키로 묶고 동일 조합 중복을 제약한다.
report reason/status/created_at
관리자가 신고를 분류·처리하고 시간순으로 검토하는 데 필요한 사건 정보를 보존한다.
ADMIN/USER security principal
관리자 목록의 200/403을 JWT 역할에 따라 분리한다.
CursorPage<ReportResponse>
관리 목록에서 items와 nextCursor를 읽고 다건 신고를 다음 페이지로 연결한다.

업무 정책

  • 같은 회원이 같은 글을 다시 신고하면 409이며 존재하지 않는 대상은 정상 신고로 저장하지 않습니다.
  • GET /api/admin/reports는 ADMIN 200, USER 403입니다. 인증 없음과 권한 부족도 별도로 확인합니다.
  • 데이터베이스의 대상 참조와 UNIQUE 불변식을 설계 메모와 실행 증거로 남깁니다.
  • 원문 완료 기준: `ReportServiceTest` 통과: 같은 회원이 같은 글을 다시 신고하면 `/errors/duplicate` 예외
  • 원문 완료 기준: 설계 메모: 만든 테이블·키·제약·인덱스와 각각의 이유, 고려했다 버린 대안 1개를 기록한다.
  • 원문 완료 기준: DB 불변식 확인: 같은 회원·같은 글 신고의 두 번째 INSERT와 존재하지 않는 대상 참조를 거부한다. 실행 SQL·결과를 기록하고 DB와 트랜잭션·권한·앱이 맡는 책임을 구분한다.
  • 원문 완료 기준: `POST /api/posts/{postId}/reports` → 201, 다시 → 409
  • 원문 완료 기준: ADMIN 토큰으로 `GET /api/admin/reports` → 200, USER 토큰 → 403
  • 원문 완료 기준: `POST /api/admin/posts/{postId}/hide` → 200, 이후 `GET /api/posts/{postId}` → 404, 연결한 신고는 `RESOLVED`, 인기글에서도 바로 빠진다

입력과 출력

  • USER A: POST /api/posts/101/reports JSON은 recipe의 reason sample을 사용하고 유효 token을 포함한다. 기대 첫 201; 같은 회원/글 중복 409.
  • USER B는 같은 post에 신고해도 별도 reporter라면 201이다.
  • GET /api/admin/reports: ADMIN Bearer → 200 `{items,nextCursor}`; USER Bearer → 403 `/errors/forbidden`; token 없음은 401.

성공 기준

  • P-101 신고 0건에서 USER A 첫 POST → 201; 같은 A+post 재요청 → 409 `/errors/duplicate`; USER B 신고 → 201. report row는 조합당 1개다.
  • ADMIN GET /api/admin/reports → 200 CursorPage `{items,nextCursor}`의 목록에 A/B 두 건; USER GET → 403.
  • 없는 post 신고는 404이며 report row가 생성되지 않는다.

실패와 데이터 보존

  • USER A가 같은 P-101에 두 번째 신고 → 409 `/errors/duplicate`. · 유지: A/P-101 조합 row는 한 건이고 created report count는 증가하지 않는다.
  • USER token으로 GET /api/admin/reports → 403 `/errors/forbidden`; token 누락은 401. · 유지: 신고 목록·상태가 바뀌지 않고 응답은 관리자 데이터를 공개하지 않는다.
  • 존재하지 않는 postId 신고 → 404 not found. · 유지: report row나 없는 post FK가 남지 않는다.

입력 사례

  • 같은 글에 회원별 신고
  • 관리자 목록 권한

개발 과제

  • report table의 post/member FK와 UNIQUE(post_id,reporter_id)를 설계하고 직접 중복 INSERT를 거부한다.
  • 동일 회원 duplicate와 다른 회원 신고를 각각 실행하고 관리자 경로에 역할 보안을 적용한다.
  • HTTP 결과·report row·관리 목록 cursor를 함께 확인한다.

완료 확인

  • A의 최초 신고 201, 같은 조합 409, B의 신고 201을 확인했다.
  • ADMIN 목록 200에 두 신고가 있고 USER 403/무 token 401임을 확인했다.
  • 외래키·UNIQUE 제약 및 잘못된 postId 404 뒤 무저장 근거를 남겼다.
