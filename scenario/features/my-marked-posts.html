좋아요·북마크 조건으로 내 목록 이어 보기

community 4-3 좋아요 목록과 6-5 좋아요/북마크 조건 목록을 목적·페이지 방식별로 구분한다.

이번에 할 일

박디비의 좋아요 8개에서 볼 수 없는 post6/post8 제외·cursor 이어읽기를 확인하고 별도 Kim 조건 조합에서는 OR/단일/교집합 목록을 검사한다.

시작 조건

  • 4-3 seed에서 박디비는 8개 liked; post6 FOLLOWERS(박디비 비팔로워), post8 deleted.
  • 6-5는 Kim의 좋아요/북마크 relation과 공개 글 [표시실습] 둘 다를 별도로 준비한다.

사용자 시나리오

  1. 시작
    박디비 /api/me/likes initial result의 item ids와 nextCursor를 기록한다.
    행동
    size=3 첫 페이지 다음 nextCursor를 그대로 전달하고 bogus cursor도 요청한다. 별도 /api/me/posts에서 liked/bookmarked query 조합을 비교한다.
    결과
    likes 목록은 지금 볼 수 있는 글만 cursor 최신 likedAt/id 순으로 반환. 6-5의 liked=true&bookmarked=true는 두 relation 모두 있는 공개글만 page=0,size=20에서 반환.
    이후
    6-5의 조건 생략/false=OR, liked only, bookmarked only 결과 집합을 확인하고 empty result totalElements 0을 비교한다.

데이터와 이유

박디비의 post_like 8관계 중 post6/post8
볼 수 없는 좋아요 글은 4-3 목록에서 제외됨을 검증.
like.created_at/id cursor
timestamp 동점에서도 중복/누락 없는 keyset 순서.
Kim liked/bookmarked relation 집합
6-5 조건 조합의 OR와 intersection 의미.
PUBLISHED/PUBLIC/deleted/block 상태
6-5는 가시 글만; 6-3 bookmark list의 unavailable 보존과 구별.

업무 정책

  • GET /api/me/likes는 인증 필수 401, size 기본 10 범위 1..100, likedAt desc/id desc cursor. invalid base64/time/relation cursor는 400. 지금 볼 수 없는 글은 목록에서 제외한다.
  • GET /api/me/posts는 인증 필수. liked/bookmarked 둘 다 생략/false이면 OR, 하나 true이면 해당 relation, 둘 다 true면 AND. 대상은 PUBLISHED/PUBLIC/미삭제이며 2-3 block condition 적용.
  • 6-5는 offset page 0-based default, size default20/range1..100, 결과 items[]/totalElements. 범위 안 넘는 valid page는 빈 배열. 6-3처럼 unavailable bookmark placeholder를 유지하지 않는다.

입력과 출력

  • GET /api/me/likes?size=3; then ?size=3&cursor=<nextCursor>; ?cursor=bogus.
  • GET /api/me/posts?liked=true&page=0&size=20.
  • 김자바 token: 조건 생략, liked=true, bookmarked=true, both=true 조합.

성공 기준

  • 4-3 first and next cursor pages are 200; nextCursor returned 그대로 이어짐; 6번과 8번은 visible result에서 제외.
  • 6-5 both=true는 [표시실습] 둘 다 1개만 포함; items[].liked/bookmarked 둘 다 true.
  • 조건 생략/false 결과는 union, true/true는 intersection, empty는 items=[]/totalElements=0.

실패와 데이터 보존

  • GET /api/me/likes without token → 401. · 유지: like/bookmark relations unchanged.
  • cursor=bogus 또는 size=0/101 → 400. · 유지: 관계·글·카운터 변화 없음.
  • liked=빈 문자열/truex 등 invalid boolean, size 범위 밖 → 400. · 유지: 목록 조건/데이터 불변.

입력 사례

  • 박디비 좋아요 첫 cursor
  • 다음 cursor
  • 표시된 글 교집합

개발 과제

  • likes의 cursor 페이지와 marked-posts offset 조건 API를 혼동 없이 별도 호출한다.
  • 응답 item postId 집합과 like/bookmark relation을 SQL로 교차 검증한다.
  • blocked/deleted item이 어느 목록에서 빠지는지 4-3 vs 6-3 vs 6-5 차이를 적는다.

완료 확인

  • 8 likes 중 제한 대상 2개 처리와 cursor 연속성을 확인했다.
  • 6-5의 OR/각 단일조건/AND 결과를 비교했다.
  • 인증/invalid cursor/size 실패에서 데이터가 보존됐다.

선택한 API 계약

GET/api/me/likes?size=3200

C1: HTTP 상태 200이어야 합니다. C1: JSON 경로 $.items[*].postId equals [14,12,11]이어야 합니다. C1: JSON 경로 $.nextCursor exists true이어야 합니다. C1: JSON 경로 $.nextCursor notEquals null이어야 합니다.
