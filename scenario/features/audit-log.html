민감한 작업의 감사 이력 보관하기

관리자 변경 작업을 나중에 추적할 수 있도록 수정·삭제되지 않는 감사 이력으로 보관하고 관리자 조회를 제공합니다.

이번에 할 일

감사 로그 스키마와 보존 원칙을 정하고 숨김 작업에서 action 기록이 한 건 남는지 확인하세요. USER 조회는 권한 거부를 검증합니다.

시작 조건

  • ADMIN token과 ACTIVE 글 P-101 및 관리 대상 데이터가 필요하다. 감사 entity/테이블은 D10 설계 요구와 spec-v2 §6-8에 맞춘다.
  • AuditLogRepositoryTest에서 저장·cursor query만 허용하고 update/delete가 없는 계약을 확인한다.

사용자 시나리오

  1. 시작
    P-101 ACTIVE이고 감사 로그에 해당 작업 기록이 없다. DB는 감사 대상 글이 나중에 상태 변경/삭제되어도 audit row를 보존하도록 준비한다.
    행동
    ADMIN으로 POST /api/admin/posts/101/hide를 한 번 실행한다. 이어 GET /api/admin/audit-logs를 재조회하고 USER token으로 같은 목록을 요청한다.
    결과
    hide는 200. 관리자 audit query는 200이며 `action=HIDE_POST` row가 정확히 한 건 있다. USER audit 조회는 403이다.
    이후
    대상 글 상태가 후속 수정되거나 숨김 후 상세에서 404가 되어도 audit row와 actor/action/target/time은 남는다. 저장소 API에 수정·삭제 경로가 없는 것을 테스트한다.

데이터와 이유

audit actor·action·target·timestamp
누가 어떤 대상을 언제 변경했는지 최소 운영 추적 사실을 유지한다.
HIDE_POST audit row
관리 hide 요청과 감사 이벤트 사이의 업무 연결을 확인한다.
cursor 조회 결과
관리자가 큰 감사 이력을 페이지 단위로 조회하게 한다.
USER/ADMIN 권한 principal
감사 정보가 관리자에게만 노출되는지 USER 요청과 ADMIN 요청의 status를 비교한다.

업무 정책

  • 감사 저장소는 저장과 커서 조회만 제공하고 감사 기록의 update/delete는 금지합니다. 대상 상태가 나중에 바뀌어도 기록은 남습니다.
  • 숨김 성공 뒤 action=HIDE_POST 기록 한 건을 확인합니다. USER 토큰의 GET /api/admin/audit-logs는 403입니다.
  • 감사 대상의 민감정보를 필요 이상으로 복사하지 않고 원문 비밀값을 저장하지 않습니다.
  • 원문 완료 기준: `AuditLogRepositoryTest` 통과: 저장과 커서 조회만 있고 수정·삭제 메서드가 없다
  • 원문 완료 기준: 설계 메모: 만든 테이블·키·제약·인덱스와 각각의 이유, 고려했다 버린 대안 1개를 기록한다.
  • 원문 완료 기준: DB 불변식 확인: 감사 기록 수정·삭제를 저장소·권한 정책으로 막고 대상 변경 뒤에도 기록이 남음을 테스트한다. 실행 SQL·결과를 기록하고 DB와 트랜잭션·권한·앱이 맡는 책임을 구분한다.
  • 원문 완료 기준: `POST /api/admin/posts/{postId}/hide` 뒤 `GET /api/admin/audit-logs` → 200, `action` = `HIDE_POST` 1건
  • 원문 완료 기준: USER 토큰으로 `GET /api/admin/audit-logs` → 403

입력과 출력

  • ADMIN Bearer로 POST /api/admin/posts/101/hide; 기대 200.
  • ADMIN Bearer GET /api/admin/audit-logs → 200 cursor page; action=HIDE_POST 1건.
  • USER Bearer 같은 GET → 403; 인증 없음은 401. 저장소에는 append/save와 cursor read만 둔다.

성공 기준

  • hide 요청 → 200; 직후 GET /api/admin/audit-logs → 200에서 `action=HIDE_POST` 1건과 대상 post 101을 확인한다.
  • USER GET /api/admin/audit-logs → 403; 로그 저장소는 save 및 cursor read만 제공하고 update/delete 메서드가 없다.
  • P-101의 후속 상태가 바뀌어도 감사 row는 삭제/수정되지 않고 보존된다.

실패와 데이터 보존

  • USER가 GET /api/admin/audit-logs를 요청 → 403. · 유지: audit data를 응답하지 않고 저장 이력도 변경하지 않는다.
  • hide 성공인데 HIDE_POST audit row가 없거나 2건 생성 → 업무 조치와 감사 기록 원자성/중복 처리 기준 실패다. · 유지: 정확히 한 건의 변경 기록만 남고 실패 transaction이면 action row도 남지 않는다.
  • 저장소에서 기존 감사 row UPDATE/DELETE 시도 → append-only 정책으로 거부한다. · 유지: 이미 저장된 actor/action/target/timestamp를 보존한다.

입력 사례

  • 숨김 감사 한 건 조회
  • USER 접근과 대상 변경 후 보존

개발 과제

  • audit 테이블의 참조·action·actor·시각·불변 보존 전략과 인덱스를 설계한다.
  • 감사 annotation/aspect와 admin 조회를 연결하되 비밀값이나 불필요한 payload 전체를 저장하지 않는다.
  • hide 200 후 audit row 1건, USER403, update/delete 부재를 API·repository test로 고정한다.

완료 확인

  • AuditLogRepositoryTest에서 save와 cursor 조회만 있고 수정·삭제 메서드가 없음을 확인했다.
  • hide 200 뒤 HIDE_POST 1건, USER 403, 대상 상태 변경 뒤에도 기록 보존을 확인했다.
  • 테이블 key/index와 DB·애플리케이션의 보존 책임 및 버린 대안을 기록했다.

    필수 여부 · 선택
    원문 요구사항
    • `Proxy.newProxyInstance(type.getClassLoader(), new Class<?>[] {type}, handler)`로 `type` 인터페이스의 프록시를 만들고, 인터페이스 메서드 호출을 `target`에 넘긴다.
    • `@Timed`가 붙은 메서드만 `new Timing(메서드 이름, 걸린 시간)`을 `log`에 남긴다. 대상이 예외를 던져도 남긴다.
    • `@Timed`는 인터페이스 메서드(`bulkIssueCoupon`)에 붙어 있을 수도, 구현 클래스 메서드(`FakeAdminActions.hidePost`)에 붙어 있을 수도 있다. 둘 다 찾는다.
    • 대상이 던진 예외는 포장하지 않고 그대로 던진다.
    • `equals`·`hashCode`·`toString`도 프록시로 들어온다. 이 셋은 `target`에 넘기지 않고 프록시 자신을 기준으로 답한다: `equals`는 같은 프록시일 때만 true(`self == args[0]`), `hashCode`는 `System.identityHashCode(self)`, `toString`은 `target.toString()`을 부르지 않는 문자열(예: 프록시 identity + `target` 클래스 이름). 기록하지 않는다.
    • `InvocationHandler.invoke`가 받는 `Method`는 **인터페이스의** 메서드다. 구현 클래스에 붙인 `@Timed`는 거기서 보이지 않는다. `targetClass.getMethod(이름, 매개변수 타입)`으로 구현 메서드를 찾아 확인한다. 예외가 하나 있다: 프록시에 부른 `equals`·`hashCode`·`toString`은 선언 클래스가 `Object`인 `Method`로 들어온다(`method.getDeclaringClass() == Object.class`). 이것까지 `target`에 넘기면 `proxy.equals(proxy)`가 `target.equals(proxy)`로 바뀌어 false가 된다 — 자기 자신과 같지 않은 객체가 생긴다.
    • `method.invoke(target, args)`는 대상이 던진 예외를 `InvocationTargetException`으로 감싼다. 그대로 두면 호출한 쪽은 `UndeclaredThrowableException`을 받는다. `e.getCause()`를 꺼내 던진다.
    • `Timed가_붙은_메서드만_기록된다`
    • `프록시를_거쳐도_인자와_반환값은_그대로_전달된다`
    • `여러_번_부르면_부른_순서대로_기록된다`
    • `인터페이스_메서드에_붙은_Timed도_기록된다`
    • `대상이_던진_예외는_포장되지_않고_그대로_나오며_실패한_호출도_기록된다`
    • `같은_객체_안에서_this로_부르면_프록시를_거치지_않아_기록되지_않는다`
    • `리텐션이_CLASS인_어노테이션은_실행_중에_보이지_않아_기록되지_않는다`
    • `equals_hashCode_toString은_Object_메서드라_target에_넘기지_않고_프록시_자신을_기준으로_답한다`
    • `프록시가_받는_Method는_인터페이스_메서드라_구현_클래스의_어노테이션은_따로_찾아야_한다`
