허용량 초과 쓰기는 저장 없이 거절하기

정해진 시간 창의 허용량을 넘긴 글쓰기 요청은 429로 거절되고 저장되지 않는다.

이번에 할 일

회원/기준 시각에 따른 요청 횟수 산정과 초과 실패를 구현한다.

시작 조건

  • 시나리오 DB(`community`) — 앱을 기본 프로파일로 띄운다. 이 단계는 실제로 흐르는 1분을 센다(practice의 고정 시계로는 1분이 지나지 않는다).
  • community 시간 흐르는 환경에서 동일 회원 요청을 실행한다. practice 고정 시계 예외는 15-3 원문과 연결한다.

사용자 시나리오

  1. 시작
    한 회원의 쓰기 요청을 같은 시간 구간에 반복합니다. 다른 회원도 별도로 요청합니다.
    행동
    원본에 정한 허용량 경계 직전·경계·초과 요청과 실패 입력을 보냅니다.
    결과
    허용 요청만 저장되고 초과 요청은 429로 거절됩니다. 회원별 사용량을 서로 섞지 않습니다.
    이후
    정확한 시간 구간·허용량·실패 요청 차감 규칙은 아래 업무 정책을 따르며 고정 Clock 실습의 예외를 실운영 정책으로 확대하지 않습니다.

데이터와 이유

member별 요청 시각과 POST 결과
원문에서 정한 제한 창·횟수·429 경계를 재현한다.
post 생성 행과 시도 카운터
초과 응답에서 글이 생기지 않았는지와 실패 시도 집계를 분리한다.

업무 정책

  • 새 글 등록과 복사 생성에 같은 회원별 60초 창을 적용합니다. 지우지 않은 최근 글 5개까지 허용하고 6번째부터 429입니다.
  • 입력 검증과 금칙어 검사를 통과한 뒤 셉니다. 400 실패 요청은 생성 횟수에 포함하지 않습니다. 읽기·다른 회원·댓글은 영향받지 않습니다.
  • Retry-After는 창 안의 가장 오래된 글이 60초를 넘길 때까지 올림한 남은 초이며 1~60입니다. 본문 retryAfterSeconds와 맞추고 CORS exposedHeaders에 Retry-After를 노출합니다.
  • created_at과 판정 시각은 같은 초 단위의 지금을 사용합니다. 15-3의 Clock 적용 뒤에도 같은 Clock을 쓰며 practice 고정 Clock의 우회 예외를 보존합니다.

성공 기준
