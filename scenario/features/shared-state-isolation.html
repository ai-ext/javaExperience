같은 값을 다시 읽었을 때 JPA 캐시 때문인지 DB 스냅샷 때문인지 구분합니다.

이번에 할 일

두 연결 A/B의 읽기→변경·commit→재읽기를 RC와 RR에서 비교하고 EntityManager 재조회·clear·새 트랜잭션을 나누세요.

시작 조건

  • 두 DB 연결과 같은 글 id·초기 값을 준비합니다.
  • RC/RR 실제 세션 설정과 일반 SELECT·잠금 읽기를 구분합니다.

사용자 시나리오

  1. 시작
    A가 제목 A를 읽은 뒤 B가 B로 바꾸고 commit합니다.
    행동
    A의 일반 SELECT, 동일 EntityManager 재조회, clear 뒤 조회, 새 트랜잭션을 조건별로 실행합니다.
    결과
    SQL 발행 유무와 실제 값을 조건마다 기록하고 캐시와 DB 격리의 원인을 분리합니다.
    이후
    RC/RR·일반/잠금 읽기·같은/새 트랜잭션의 결과를 한 값으로 뭉뚱그리지 않습니다.

데이터와 이유

세션 격리와 연결 id
어느 DB 스냅샷인지 확인합니다.
EntityManager와 SQL 로그
캐시 재사용과 DB 재조회 여부를 구분합니다.

업무 정책

  • clear는 새 트랜잭션 시작이 아닙니다.
  • 동시 실행의 순서는 테스트 신호로 고정합니다.

입력과 출력

  • 글 id, A/B 두 연결, RC/RR 두 격리 설정, 변경 전후 제목

성공 기준

  • SQL 발행 유무와 실제 값을 조건마다 기록하고 캐시와 DB 격리의 원인을 분리합니다.

실패와 데이터 보존

  • B가 아직 commit하지 않음 → 미확정 변경을 확정값으로 읽었다고 기록하지 않습니다. · 유지: 타 연결의 미완료 변경과 테스트 순서를 섞지 않습니다.

입력 사례

개발 과제

완료 확인

  • 같은 EntityManager의 재조회·clear 뒤 조회·새 트랜잭션 결과를 구분하고 SQL 발행 여부와 실제 값을 남긴다.

글 하나를 지워도 다른 글의 태그 보존하기

여러 글이 공유한 태그를 한 글의 삭제 때문에 함께 잃지 않게 합니다.

이번에 할 일

두 글이 같은 태그를 쓰는 상태에서 한 글을 삭제하고 남은 글·태그·연결을 재확인하세요.

시작 조건

  • 글 A/B와 공유 태그 spring, 각 연결을 격리 DB에 만듭니다.
  • 실제 삭제 정책이 soft delete인지 관계 제거인지 구분합니다.

사용자 시나리오

  1. 시작
    글 A와 B가 spring을 함께 쓰고 있습니다.
    행동
    글 A 삭제 요청을 보내고 새 연결에서 B의 태그와 원본 태그 행을 조회합니다.
    결과
    삭제 대상 A의 정책만 적용되고 B의 spring 연결과 공유 원본이 유지됩니다.
    이후
    공유 원본의 수명과 글별 연결의 수명을 나누고 유지할 불변식 두 개를 기록합니다.

데이터와 이유

글별 태그 연결
어느 글이 태그를 사용하는지 구별합니다.
공유 태그 원본
다른 글이 계속 쓸 수 있게 유지합니다.

업무 정책

  • 연결 삭제안과 원본 삭제안의 참조 무결성을 비교합니다.
  • 원본을 함께 지우는 cascade가 남은 글에 미치는 영향을 실제 실패로 확인합니다.

입력과 출력

  • 공유 태그를 가진 두 실제 글 id, 삭제할 글 id

성공 기준

  • 삭제 대상 A의 정책만 적용되고 B의 spring 연결과 공유 원본이 유지됩니다.

실패와 데이터 보존

  • 공유 태그까지 삭제하려 함 → FK 오류나 다른 글의 연결 손상을 재현하고 안전한 안으로 수정합니다. · 유지: 삭제하지 않은 글 B와 태그가 남아야 합니다.

입력 사례

  • 같은 대상의 전후 비교

개발 과제

  • 두 글이 같은 태그를 쓰는 상태에서 한 글을 삭제하고 남은 글·태그·연결을 재확인하세요.

완료 확인

  • 두 게시글이 한 태그를 공유하는 fixture에서 게시글 하나 삭제 후 다른 글의 태그·연결·원본 행을 확인한다.
  • 연결만 삭제하는 안과 원본 삭제안의 참조 무결성을 비교하고 반드시 유지할 불변식 2개를 남긴다.
