느린 결제에도 중복 없이 충전 접수하기

외부 PG 응답 지연·거절·연결 실패를 구분하면서 충전 요청 중복과 이중 승인을 막습니다.

이번에 할 일

요청을 먼저 기록하고 PG 호출을 DB 트랜잭션 밖에서 수행하세요. 같은 멱등 키 재요청, 거절, 응답 시간 초과, 결과 확인을 나눠 기록합니다.

시작 조건

  • USER JWT와 충전 요청이 필요하다. 외부 PG는 WireMock, 지연 주입은 Toxiproxy로 검증한다. 실제 PG secret/credentials는 사용하지 않는다.
  • Idempotency-Key는 8~64자의 영문·숫자·하이픈이며 충전 amount는 1,000~1,000,000의 1,000 단위다.

사용자 시나리오

  1. 시작
    시험 회원 balance=2,000인 격리 fixture, 아직 없는 charge key `charge-0001`, 정상 WireMock PG를 준비한다.
    행동
    POST /api/me/points/charges에 amount=1,000과 key charge-0001을 보낸다. 별도 사례는 amount=1,500, PG 4초 지연, PG 4xx 거절, 연결 거부로 각각 실행한다. timeout 뒤 같은 key를 재전송하고 GET /api/me/points 및 저장된 orderId 상태를 확인한다.
    결과
    PG가 DONE을 반환하면 HTTP 201, PENDING이면 HTTP 202와 UNKNOWN 응답이며 DONE 처리 뒤 balance 2,000→3,000/CHARGE 원장 +1,000이다. amount 1,500은 400. 응답 timeout은 3초에 504 `/errors/pg-timeout`, 상태 UNKNOWN, balance 2,000 유지다. PG 거절/명확한 연결 실패는 502 `/errors/pg-declined`, FAILED다.
    이후
    요청 저장 transaction, PG HTTP 대기, 결과 확정 transaction을 로그/DB에서 구분한다. timeout key 재전송은 PG 승인 요청을 새로 보내지 않고 기존 UNKNOWN을 돌려주며 잔액은 증가하지 않는다.

데이터와 이유

charge request와 Idempotency-Key
동일 회원의 재전송이 기존 pg_payment를 찾아 외부 승인을 새로 만들지 않는 기준이다.
서버 생성 orderId와 pg_payment.status
콜백·조회 재조정이 요청을 추적할 식별값과 UNKNOWN/FAILED/DONE 상태를 보존한다.
PG 호출 시각·예외 원인
connect/response/pool timeout을 분리해 재시도 가능한 오류와 결과 불명을 구분한다.
point_balance와 CHARGE ledger
DONE 후 1회 적립 여부를 요청 전후 잔액과 원장으로 대사한다.

업무 정책

  • 충전 amount는 1,000~1,000,000의 1,000 단위입니다. Idempotency-Key는 8~64자의 영문·숫자·하이픈입니다.
  • PG 호출을 트랜잭션 밖에 둡니다. 요청 기록 → 외부 호출 → 결과 상태·포인트 반영을 구분해 설명합니다.
  • 연결 실패와 5xx만 같은 키로 최대 2회 재시도하며 backoff는 200ms·400ms입니다. 4xx는 재시도하지 않습니다. 응답 timeout은 승인됐을 수 있어 UNKNOWN으로 남기고 재시도하지 않습니다.
  • 거절은 502 /errors/pg-declined, timeout 또는 5xx 재시도 소진은 504 /errors/pg-timeout이며 잔액은 UNKNOWN 상태에서 늘지 않습니다. B10은 D13의 선택 연습 티켓입니다. 수행 여부를 필수 과제로 승격하지 않고 원문 등급을 유지합니다.
  • 원문 완료 기준: `PgClientTest` 통과: WireMock 4초 지연 → 3초에 응답 타임아웃 예외, 닫힌 포트 → 즉시 연결 실패(연결 거부), 응답 없는 주소 → 1초에 연결 타임아웃 예외, 풀 대기 2초 초과 → 예외
  • 원문 완료 기준: `PgPaymentRepositoryTest` 통과: 같은 충전 멱등 키의 중복 저장을 거부하고 서버가 만든 orderId가 재조회된다
  • 원문 완료 기준: 설계 메모: 만든 테이블·키·제약·인덱스와 각각의 이유, 고려했다 버린 대안 1개를 기록한다.
  • 원문 완료 기준: DB 불변식 확인: 충전 키·orderId·값이 있는 paymentKey 중복을 각각 거부하며 승인 전 식별 값 없음은 허용한다. 실행 SQL·결과를 기록하고 DB와 트랜잭션·권한·앱이 맡는 책임을 구분한다.
  • 원문 완료 기준: `POST /api/me/points/charges` + `Idempotency-Key` → 201, 잔액 증가
  • 원문 완료 기준: WireMock 4초 지연 → 504 `/errors/pg-timeout`, `pg_payment.status` = `UNKNOWN`, 잔액 그대로
  • 원문 완료 기준: WireMock 거절 → 502 `/errors/pg-declined`, PG가 5xx만 돌려주면 결과 불명이라 504 `/errors/pg-timeout`, `pg_payment.status` = `UNKNOWN`
  • 원문 완료 기준: `amount` = 1500 → 400
  • 원문 완료 기준: 트랜잭션 경계: 요청 기록·외부 호출·결과 반영의 경계를 나눈 이유를 적는다. 실패 시 이미 저장한 요청 상태와 잔액 중 무엇을 유지하거나 취소하는지 로그·DB 값으로 설명한다.
  • 원문 완료 기준: `PgClientRetryTest` 통과: 연결 실패와 5xx만 같은 `Idempotency-Key`로 최대 2회 재시도(백오프 200ms·400ms), 거절(4xx)은 재시도하지 않는다
  • 원문 완료 기준: 응답 타임아웃 건은 재시도 대신 `UNKNOWN`으로 남는다. 5xx로 재시도를 다 써도 `UNKNOWN`과 504다
  • 원문 완료 기준: `pg_payment`에서 같은 충전 요청에 승인 2건을 확인
  • 원문 완료 기준: 재현 테스트 통과: WireMock 첫 응답이 늦어도 PG 승인 1건, 포인트 1회
  • 원문 완료 기준: 원인 서술: 누가 왜 다시 보냈고, PG는 왜 두 번째 요청을 별개의 결제로 받았는가
  • 원문 완료 기준: 재현 테스트: 첫 승인 응답이 늦는 PG 모의로 충전 한 번을 보낸 뒤, 결과 불명 건을 재처리(`ChargeService.reconcile`)로 확정해도 PG 승인 1건·충전 원장 1건·잔액 1회분인지 보는 테스트(결함 상태에서 실패 → 수정 후 통과). 예: `src/test/java/com/example/board/payment/ChargeIdempotencyTest.java`

입력과 출력

  • POST /api/me/points/charges JSON `{"amount":1000}`, header `Idempotency-Key: charge-0001`, USER Bearer token.
  • amount=1500은 400 validation. 4초 WireMock 지연은 응답 timeout 3초, 닫힌 포트는 즉시 connection refused, 무응답 주소 연결 timeout 1초, pool 대기는 2초다.
  • 재조회는 GET /api/me/points → 200 `{balance}`와 같은 orderId의 pg_payment status를 사용한다.

성공 기준

  • POST /api/me/points/charges + amount 1,000: PG DONE이면 HTTP 201, PENDING이면 HTTP 202/UNKNOWN; 승인 DONE이면 잔액 2,000→3,000 및 CHARGE 이력 +1,000 1건.
  • amount=1,500 → 400 validation. PG 4xx/연결 불가 → 502 `/errors/pg-declined`; PG가 5xx를 돌려줘 2회(200ms·400ms) 재시도 모두 소진 또는 응답 timeout → 504 `/errors/pg-timeout`, 상태 UNKNOWN.
  • 응답 timeout은 승인 여부가 불명확하므로 잔액을 늘리지 않는다. 같은 key 재요청은 최초 저장 상태를 응답하고 PG 호출을 반복하지 않는다. GET /api/me/points로 전후 balance를 확인한다.

실패와 데이터 보존

  • amount=1,500 또는 key 누락/형식 위반 → 400 `/errors/validation`. · 유지: pg_payment 승인 상태, balance, CHARGE ledger가 바뀌지 않는다.
  • PG가 4초 응답 지연을 주고 클라이언트 response timeout 3초가 먼저 끝남 → 504 `/errors/pg-timeout`, pg_payment UNKNOWN. · 유지: balance와 CHARGE ledger는 증가하지 않는다. 같은 key 재전송은 PG를 다시 호출하지 않는다.
  • PG 명시적 4xx 거절 또는 연결 실패 → 502 `/errors/pg-declined`, status FAILED. · 유지: 포인트 잔액·충전 원장 증가 없음.
  • PG가 5xx를 반환해 동일 key로 최대 2회 재시도한 뒤 모두 소진 → 504 `/errors/pg-timeout`, status UNKNOWN. · 유지: PG 결과를 단정하지 않고 잔액을 적립하지 않는다.

입력 사례

  • 정상 1,000점 충전
  • 응답 timeout 뒤 동일 키 재요청
  • 1,500원 검증 실패

개발 과제

  • pg_payment key/orderId/paymentKey UNIQUE 및 UNKNOWN 상태 추적을 설계하고 test에서 중복 저장을 막는다.
  • 요청 기록 transaction → PG 호출(트랜잭션 밖) → 결과 확정 transaction의 순서를 만든다.
  • WireMock으로 4초 응답 지연, 4xx, 5xx, 닫힌 포트, 무응답 주소, pool 대기를 주입해 재시도 여부와 상태를 표로 남긴다.

완료 확인

  • PgClientTest의 response 3초, connection 1초, pool wait 2초 조건을 각각 확인했다.
  • key/orderId 중복 저장 방지와 1,000 단위 amount 검증, 정상 201/202, 502 FAILED, 504 UNKNOWN 결과를 기록했다.
  • timeout 뒤 잔액 불변·같은 key PG 재호출 없음·GET balance 및 orderId 상태 대사를 끝냈다. B10은 D13의 선택 연습으로 남겼다.

PG 콜백을 HMAC 서명으로 확인해 UNKNOWN 충전 결과를 확정하고 중복 콜백에서도 포인트를 한 번만 적립합니다.

    
이번에 할 일
요청 본문 원문 바이트의 서명을 검증한 뒤 orderId와 paymentKey에 맞는 충전 상태만 전이시키세요. 정상 재전송과 변조·미등록 주문을 확인합니다.

    
시작 조건
  • UNKNOWN인 pg_payment의 실제 orderId·요청 amount와 BOARD_PG_SECRET 설정이 필요하다. secret은 로그·파일·수업 답안에 출력하지 않는다.
  • 콜백 body 원문 byte array와 동일 바이트로 계산한 X-PG-Signature를 준비한다. B13은 D14 선택 Security 후보다.

    
사용자 시나리오
  1. 시작
    balance 2,000, 충전 1,000인 pg_payment가 timeout 뒤 UNKNOWN이며 서버가 만든 orderId가 `ord-test-1`이다. callback body bytes와 대응 HMAC signature를 준비한다.
    행동
    POST /api/pg/callbacks에 같은 원문 바이트·signature를 보낸다. 동일 callback을 다시 보내고, body 한 바이트 변경/서명 불일치와 없는 orderId를 각각 요청한다. 각 응답 뒤 GET /api/me/points를 재조회한다.
    결과
    유효 callback은 200, UNKNOWN→DONE, balance 2,000→3,000 및 CHARGE ledger 1건이다. 같은 paymentKey 재전송도 200이나 balance/ledger는 그대로다. 잘못된 서명은 401 `/errors/invalid-signature`, 없는 orderId는 404다.
    이후
    상태 전이·잔액 UPDATE·ledger INSERT가 함께 확정됐는지 보고 같은 paymentKey가 이미 처리된 뒤 재전송으로 추가 적립이 없음을 확인한다.

    
데이터와 이유
raw callback body bytes
공백·필드 순서 등 원문 차이를 보존해 PG와 동일한 HMAC 입력을 만든다.
X-PG-Signature와 secret key
서명된 발신자 검증에만 쓰고 secret 자체를 데이터나 로그로 저장하지 않는다.
orderId/paymentKey/status/amount
콜백을 기존 충전 row에 연결하고 요청 금액과 결과 상태가 일치하는지 확인한다.
balance와 CHARGE ledger
첫 DONE 전이와 반복 callback 뒤 적립 횟수가 각각 1, 1인지 검증한다.

    
업무 정책
  • HMAC-SHA256 서명은 파싱·재직렬화한 JSON 문자열이 아니라 수신한 raw bytes로 계산하고 constant-time 비교합니다.
  • 올바른 서명은 200이며 UNKNOWN→DONE 전이에서 포인트를 1회 적립합니다. 같은 paymentKey 콜백 재전송은 200이어도 잔액을 다시 올리지 않습니다.
  • 서명 불일치는 401 /errors/invalid-signature, 없는 orderId는 404입니다. 비밀키 원문은 요청 예시·로그에 넣지 않습니다.
  • 콜백은 공개 경로로 설정하되 서명 확인을 생략하지 않습니다. B13은 기존 지원 티켓 등급을 그대로 둡니다. B13은 D14의 선택 Security 후보 티켓입니다.
  • 원문 완료 기준: 서명이 맞는 `POST /api/pg/callbacks` → 200, `UNKNOWN` 충전이 `DONE`이 되고 포인트 1회 적립
  • 원문 완료 기준: 같은 `paymentKey` 콜백 재전송 → 200, 잔액 그대로
  • 원문 완료 기준: 서명 틀림 → 401 `/errors/invalid-signature`
  • 원문 완료 기준: 없는 `orderId` → 404
  • 원문 완료 기준: 트랜잭션 경계: 콜백의 결제 상태 전이·잔액·이력 반영을 어디까지 묶는지와 ChargeService의 어느 로직을 재사용하는지, 그 이유를 적는다. 실패 시 취소 범위와 같은 콜백 재전송 결과를 기록한다.
  • 원문 완료 기준: Toxiproxy 차단 실험에서는 ConnectException 외에 NoHttpResponseException·Connection reset·Broken pipe와 TIMEOUT이 나올 수 있음을 실패 원인 체인으로 기록한다. 명확한 연결 거부와 응답 중단을 분리하고, 결과 불명은 조회·콜백으로 확인한다.
  • 원문 완료 기준: Security debug 로그에서 콜백 요청의 401이 어디서 만들어지는지 찾아 근거로 남긴다
  • 원문 완료 기준: 서명이 맞는 `POST /api/pg/callbacks` → 200, 서명 틀림 → 401 `/errors/invalid-signature`
  • 원문 완료 기준: 원인 서술: 콜백이 어디서, 왜 막히는가(서명 검증까지 가는가?)
  • 원문 완료 기준: 재현 테스트: 토큰 없이 서명이 맞는 콜백 → 200·충전 확정, 서명이 틀리거나 없는 콜백 → 401 `/errors/invalid-signature`를 보는 테스트(결함 상태에서 실패 → 수정 후 통과)
  • 원문 완료 기준: 수정 diff

    
입력과 출력
  • POST /api/pg/callbacks raw JSON bytes의 fields: orderId=`ord-test-1`, paymentKey=`pay-test-1`, status=`DONE`, amount=1000; header `X-PG-Signature`는 같은 원문 bytes의 HMAC-SHA256 hex.
  • 유효 signature 비교는 constant-time 비교를 사용한다. JSON 파싱 후 재직렬화한 문자열을 서명 입력으로 쓰지 않는다.
  • 재조회: GET /api/me/points → 200 `{balance}` 및 격리 DB의 pg_payment/point_ledger 상태.

    
성공 기준
  • 유효한 raw bytes 서명 POST /api/pg/callbacks → 200, `ord-test-1` UNKNOWN→DONE, balance 2,000→3,000, CHARGE 이력 1건.
  • 같은 paymentKey callback 재전송 → 200, balance=3,000 및 CHARGE 이력=1건 유지.
  • signature 불일치 → 401 `/errors/invalid-signature`; 없는 orderId → 404. 올바른 서명인데 amount 불일치면 400 validation이다.

    
실패와 데이터 보존
  • X-PG-Signature가 raw bytes HMAC과 일치하지 않음 → 401 `/errors/invalid-signature`. · 유지: pg_payment 상태 UNKNOWN, balance 2,000, ledger 변화 없음.
  • 서명은 유효하나 orderId가 저장된 충전 요청과 일치하지 않음 → 404 `/errors/not-found`. · 유지: 알려진 충전 row와 회원 잔액은 바뀌지 않는다.
  • paymentKey 길이 0 또는 65, amount≤0/저장 금액 불일치, status가 DONE/FAILED 외 값 → 400 `/errors/validation`. · 유지: UNKNOWN 상태를 확정하지 않고 잔액/원장을 변경하지 않는다.

    
입력 사례
  • raw-byte signature 정상 callback
  • 동일 paymentKey 재전송
  • 서명 위조

    
개발 과제
  • `@RequestBody byte[]` 원문 byte에 HMAC-SHA256을 계산하고 MessageDigest.isEqual로 서명을 확인한다.
  • orderId/paymentKey를 저장된 충전 기록과 비교하고 UNKNOWN→DONE 전이·원장 적립을 원자적으로 처리한다.
  • valid/invalid signature, 반복 paymentKey, 없는 orderId, amount mismatch의 HTTP·DB 결과를 기록한다.

    
완료 확인
  • 유효 서명 callback 200 뒤 UNKNOWN→DONE, balance 증가 1,000, ledger 1건을 확인했다.
  • 같은 paymentKey 재전송 200 뒤 잔액/ledger 불변, 잘못된 서명 401, 미등록 orderId 404를 확인했다.
  • body parse/re-serialize가 아니라 raw bytes가 HMAC 입력임을 테스트 근거로 남겼다. B13은 선택 Security 후보 티켓이다.

    원문 요구사항
    • 서명이 맞는 `POST /api/pg/callbacks` → 200, `UNKNOWN` 충전이 `DONE`이 되고 포인트 1회 적립
    • 같은 `paymentKey` 콜백 재전송 → 200, 잔액 그대로
    • 서명 틀림 → 401 `/errors/invalid-signature`
    • 없는 `orderId` → 404
    • 트랜잭션 경계: 콜백의 결제 상태 전이·잔액·이력 반영을 어디까지 묶는지와 ChargeService의 어느 로직을 재사용하는지, 그 이유를 적는다. 실패 시 취소 범위와 같은 콜백 재전송 결과를 기록한다.
    • Toxiproxy 차단 실험에서는 ConnectException 외에 NoHttpResponseException·Connection reset·Broken pipe와 TIMEOUT이 나올 수 있음을 실패 원인 체인으로 기록한다. 명확한 연결 거부와 응답 중단을 분리하고, 결과 불명은 조회·콜백으로 확인한다.
    원문 질문 힌트
    • 이 순서는 DB → 쿼리 → 서비스 → 컨트롤러 순으로: 이미 만든 층은 재사용하고 오늘 담당 파일만 연결한다.
    • 서명은 `javax.crypto.Mac`(`HmacSHA256`)으로 계산하고 비교는 `MessageDigest.isEqual`로 한다. 원문 바이트는 `@RequestBody byte[]`로 받는다.
    • 콜백 경로는 공개 범위 규칙에 넣되, 같은 `paymentKey`가 다시 와도 포인트가 한 번만 적립되는지 상태 전이 조건으로 확인한다.
