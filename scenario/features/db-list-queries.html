목록·태그·커서를 같은 글 집합으로 맞추기

게시판 목록의 응답 필드를 실제 열과 연결하고, 태그를 붙여도 페이지 글 수와 순서가 유지되게 합니다.

이번에 할 일

dev의 공개·발행·미삭제 글을 발행 시각과id 내림차순으로 읽고, 태그 조건과 같은 시각의 커서를 추가하세요.

시작 조건

  • community 또는 원문이 지정한 practice 연결의 실제 스키마를 확인합니다.
  • DB-01 기준 응답은 id/title/authorNickname/likeCount/commentCount/tags/publishedAt이며 content는 제외합니다.
  • 제시한ID는 원문 seed 기대값이며 현재 사용자DB에 반드시 존재한다고 가정하지 않습니다.

사용자 시나리오

  1. 시작
    게시판 dev에 같은 발행 시각의 글과 태그가 여러 개 붙은 글, 태그 없는 글이 있습니다.
    행동
    목록 페이지를 먼저 고르고 그 페이지id로 태그를 일괄 조회합니다. size2이면3행을 읽어 다음 목록 유무를 판단합니다.
    결과
    글은 태그 수만큼 중복되지 않고 공개·상태 조건과 정렬이 맞습니다. 마지막 응답 행의 시각/id가 다음 커서가 됩니다.
    이후
    빈 커서와 다음 커서의 id·순서·태그 집합을 비교하고 같은 시각의 글이 누락·중복되지 않음을 확인합니다.

데이터와 이유

게시판slug·글 상태·공개 범위
반환하면 안 되는 글을 제외합니다.
발행 시각과id
동일 시각 글도 고정 순서로 이어 읽습니다.
페이지별 태그 연결
글 수를 늘리지 않고 태그 배열을 만듭니다.

업무 정책

  • 비로그인 예시는PUBLISHED·deleted_at NULL·PUBLIC 조건입니다.
  • size+1번째 행은 hasNext용이고 응답/다음커서의 기준행이 아닙니다.
  • 태그 JOIN·EXISTS·DISTINCT의 의미를 같은 글 집합으로 비교합니다.

입력과 출력

  • boardSlug=dev, size=2, 빈 커서와 실제 마지막 응답행의 시각/id, 태그 이름

성공 기준

  • 글은 태그 수만큼 중복되지 않고 공개·상태 조건과 정렬이 맞습니다. 마지막 응답 행의 시각/id가 다음 커서가 됩니다.

실패와 데이터 보존

  • 같은 시각 또는 여러 태그가 있는 글 → 정렬키와 페이지 경계가 누락/중복 없이 유지돼야 합니다. · 유지: SQL 비교는 읽기 전용이며 seed를 수정하지 않습니다.

입력 사례

  • 같은 대상의 전후 비교

개발 과제

  • dev의 공개·발행·미삭제 글을 발행 시각과id 내림차순으로 읽고, 태그 조건과 같은 시각의 커서를 추가하세요.

완료 확인

  • 빈 커서와 다음 커서의 id·순서·태그 집합을 비교하고 같은 시각의 글이 누락·중복되지 않음을 확인합니다.
