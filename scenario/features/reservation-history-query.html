집계·커서·빈 결과가 맞는 조회 만들기

운영자와 회원이 예약 상태와 지급 이력을 정확하게 읽고, 실제 데이터 분포에서 조회 비용을 비교하게 합니다.

이번에 할 일

운영자별 예약·회원별 지급·실패 건수 중 조회 계약 하나를 정하고 두 접근 방식의 결과와 인덱스 전후 비용을 비교하세요.

시작 조건

  • 앞서 선택한 물리 모델을 쓰며 같은 시각·대상 없는 예약·성공/실패 혼합 fixture를 준비합니다.
  • 별도 DB에 최소 200행 균등 분포와 한 예약에 90%가 몰린 편향 분포를 생성하고 seed를 저장합니다.

사용자 시나리오

  1. 시작
    예약 한 개에 여러 대상과 지급 이력이 있고 같은 시각의 항목 및 빈 예약이 섞여 있습니다.
    행동
    직접 쓴 목록·집계 SQL을 MyBatis와 JdbcClient 또는 JPQL에 연결하고 같은 필터·DTO로 실행합니다.
    결과
    대상 수와 성공·실패 수가 JOIN 곱셈으로 불어나지 않으며 빈 예약과 동일 시각 커서도 빠지지 않습니다.
    이후
    두 분포에서 EXPLAIN 추정·EXPLAIN ANALYZE 실측·INSERT 비용을 별도로 남기고 인덱스를 선택합니다.

데이터와 이유

목록 필터·정렬·동률 키
다음 묶음에서 중복과 누락을 막습니다.
예약별 대상·성공·실패 집계
원본 행 수와 응답 그룹 수를 구분합니다.

업무 정책

  • QueryDSL은 선택이며 채택하면 비교 상대 하나를 대체합니다.
  • Q타입 생성·컴파일·SQL·count 비용을 따로 기록합니다.
  • 읽기 속도만으로 채택하지 않고 쓰기·공간·변경 비용을 비교합니다.

입력과 출력

  • 선택한 조회 계약과 실제 물리 이름, 동일 필터·커서·정렬 키, 두 분포의 seed·행 수

성공 기준

  • 대상 수와 성공·실패 수가 JOIN 곱셈으로 불어나지 않으며 빈 예약과 동일 시각 커서도 빠지지 않습니다.

실패와 데이터 보존

  • 같은 시각·빈 예약·일대다 JOIN이 겹침 → 잘못된 집계·중복·누락을 기대값과 대조합니다. · 유지: 조회가 예약·지급 데이터를 바꾸면 안 됩니다.

입력 사례

  • 같은 대상의 전후 비교

개발 과제

  • 운영자별 예약·회원별 지급·실패 건수 중 조회 계약 하나를 정하고 두 접근 방식의 결과와 인덱스 전후 비용을 비교하세요.

완료 확인

  • 운영자별 예약 상태·회원별 지급 이력·실패 건수 중 하나의 조회 계약을 정하고 JOIN 다중성·동일 시각 커서·빈 결과를 테스트한다.
  • 같은 조회 한 건을 MyBatis와 JdbcClient 또는 JPQL로 비교한다. QueryDSL은 선택이며 도입한다면 빌드·Q타입 생성 비용을 별도 기록한다.
  • 예약별 대상·성공·실패 건수 조회를 선집계 JOIN 또는 상관 서브쿼리로 만든다. 행 곱셈·NULL·빈 예약·동일 시각 커서를 반례로 검증한다.
  • QueryDSL을 선택하면 기존 비교 상대 하나를 QueryDSL JPA로 대체해 같은 필터·DTO·집계 결과를 비교한다. Q타입 생성·컴파일·SQL·count 비용을 남긴다. 윈도 함수는 MySQL SQL/MyBatis 선택 과제로 둔다.
  • 최소 200행의 균등 분포와 한 예약에 90%가 몰린 편향 분포를 별도 DB에 생성한다. 행 수·seed·실행 명령을 남긴다.
  • 인덱스 전후 EXPLAIN 추정과 EXPLAIN ANALYZE 실측·동일 INSERT 부하를 기록한다. 읽기 개선만으로 채택하지 않고 쓰기·공간·변경 비용으로 선택한다.

명령을 자동 실행하지 않습니다. 직접 실행한 뒤 결과를 기록하세요.

  1. ./gradlew test --tests "*ReservationQuery*"
