정상 행은 지급하고 잘못된 행은 구분하기

관리자 Excel 업로드를 행 단위로 처리해 가능한 회원은 지급하고 오류 행은 건너뛴 결과를 구분합니다.

이번에 할 일

1,000행 이하의 .xlsx에서 memberId를 읽어 행별로 쿠폰을 지급하세요. 일부 중복·없는 회원이 있어도 나머지 행은 계속 처리되고 결과 수가 합산되게 합니다.

시작 조건

  • ADMIN token, 쿠폰 id=1, 기존 회원 A/B와 없는 memberId를 포함한 .xlsx를 준비한다. 헤더 다음 첫 열은 memberId다.
  • 업로드 계약은 .xlsx 최대 5MB·최대 1,000행이다. 한 행씩 지급해 정상 행과 skipped 행을 분리한다.

사용자 시나리오

  1. 시작
    ADMIN이 쿠폰 1을 지급한다. workbook 3개 data row: member A(미보유), member A(이미 보유), 없는 memberId 99999999. 지급 전 발급 수와 audit BULK_ISSUE_COUPON을 기록한다.
    행동
    정상 파일을 POST /api/admin/coupons/1/bulk-issue multipart로 보낸다. 이어 같은 token으로 6MB 파일을 보내고 USER token으로 정상 파일을 시도한다.
    결과
    정상 업로드는 200 `{issued:1, skipped:[중복 행, 없는 회원 행]}`이며 valid row는 지급된다. 6MB 파일은 400, USER는 403이다. 정상 업로드당 감사 action BULK_ISSUE_COUPON 1건이다.
    이후
    issued 수와 신규 member_coupon row는 +1, skipped의 두 회원은 추가 row가 없다. 같은 파일을 다시 올리면 중복 행들은 skip되고 기존 회원의 중복 지급이 없어야 한다.

데이터와 이유

XLSX 첫 열 memberId
각 workbook row를 회원 식별자로 읽어 어떤 회원 지급을 시도하는지 결정한다.
issued/skipped row result
부분 성공에서 지급 건수와 중복/없는 회원의 구체 사유를 클라이언트에 돌려준다.
member_coupon UNIQUE와 coupon issued_quantity
파일 재업로드와 동시 지급에서도 같은 회원 한 장·총량 이내를 지킨다.
BULK_ISSUE_COUPON audit row
관리자 대량 조치가 한 번 수행됐음을 단일 운영 기록으로 추적한다.

업무 정책

  • 파일은 최대 5MB, 최대 1,000행이며 .xlsx여야 합니다. 6MB는 400, USER는 403입니다.
  • 없는 회원과 이미 쿠폰을 보유한 행은 skipped[]에 담고 나머지는 지급해 HTTP 200 {issued, skipped[]}로 응답합니다.
  • 전체 파일을 하나의 트랜잭션으로 처리하지 않습니다. 행마다 짧은 발급 경계로 부분 성공을 보존합니다. 감사 로그에 BULK_ISSUE_COUPON 1건을 확인합니다.
  • 원문 완료 기준: `POST /api/admin/coupons/{couponId}/bulk-issue` (`.xlsx` 1,000행) → 200 `{issued, skipped[]}`
  • 원문 완료 기준: 없는 회원·이미 보유한 행은 `skipped[]`에 들어가고 나머지는 지급된다
  • 원문 완료 기준: 6MB 파일 → 400, USER 토큰 → 403
  • 원문 완료 기준: `GET /api/admin/audit-logs`에 `BULK_ISSUE_COUPON` 1건

입력과 출력

  • ADMIN POST /api/admin/coupons/1/bulk-issue multipart file `.xlsx`, 첫 column `memberId`, rows≤1,000, file≤5MB.
  • 성공 fixture: A 신규, A 중복, 99999999 미존재. 예상 HTTP 200, issued=1, skipped에는 중복 및 없는 회원 row가 구분됨.
  • 6MB file → 400 `/errors/validation`; USER token → 403; audit GET으로 `BULK_ISSUE_COUPON` count 확인.

성공 기준

  • 3 data row 업로드 → 200 `{issued:1, skipped:[row 3 duplicate, row 4 member-not-found]}` 형태의 실제 row 번호/reason. API response 기준을 대조한다.
  • 정상 행 member_coupon과 issued_quantity만 +1. 없는 회원/중복 행은 추가 발급되지 않는다.
  • 6MB, .xlsx 외 형식, 1,000행 초과 파일은 400; USER는 403; 정상 실행 후 audit GET에서 `BULK_ISSUE_COUPON` 1건.

실패와 데이터 보존

  • 파일 크기 6MB, 확장자 .xlsx 아님 또는 row 1,001개 → 400 `/errors/validation`. · 유지: 행 지급이 시작되지 않고 issued_quantity/member_coupon/audit가 늘지 않는다.
  • USER token으로 대량 지급 요청 → 403. · 유지: 쿠폰 수량·회원 보유·audit row 불변.
  • 회원 A 중복/없는 ID를 포함한 일부 행 → 전체 요청은 200 partial success; 각 잘못된 행은 skipped[]에 row/value/reason으로 들어가고 valid row는 issued된다. · 유지: 오류 행은 지급되지 않고 유효한 행의 성공 결과도 rollback되지 않는다.

입력 사례

  • 유효·중복·없는 회원 혼합 업로드
  • 거절된 업로드 보존

개발 과제

  • 첫 열 memberId parser와 최대 파일/row 검증을 하고 row별 독립 발급 transaction을 구성한다.
  • 없는 회원과 이미 보유 행을 skipped reason으로 기록하면서 다음 행 처리를 계속한다.
  • 반복 업로드·6MB·USER·audit 기록을 검증하고 합계 issued+skipped가 입력 data row 수와 맞는지 확인한다.

완료 확인

  • 3행 혼합 예시에서 200/issued 1/skipped 2 및 신규 row 1을 확인했다.
  • 최대 5MB·1,000행 경계, 6MB 400, USER 403을 확인했다.
  • 정상 업로드당 audit action 1건이며 반복 업로드가 중복 지급하지 않음을 확인했다.
