선택·변경·취소와 종류별 수 일치시키기

회원마다 글에 반응 종류 하나만 유지하며 변경·취소 후 종류별 수가 실제 행과 일치한다.

이번에 할 일

반응 PUT/DELETE 및 종류 변경과 집계를 구현한다.

시작 조건

  • 14장은 시나리오 DB(`community`)로 한다 — 앱을 기본 프로파일로 띄운다(13장과 같다). 이 장의 마이그레이션 번호는 **V50~V59**다(11~13장의 V20~V49 다음).
  • community DB에서 로그인 회원과 존재하는 글을 준비한다.

사용자 시나리오

  1. 시작
    김자바가 글 하나에 아직 공감을 선택하지 않았습니다.
    행동
    허용된 공감 하나를 선택하고 다른 공감으로 바꾼 뒤 취소·반복 요청을 보냅니다.
    결과
    한 회원/글에는 최대 하나의 공감만 남고 종류별 집계는 이동/취소에 맞게 변합니다.
    이후
    허용하지 않은 종류·권한·대상 오류에서는 기존 선택과 모든 종류별 집계를 보존합니다.

데이터와 이유

post_reaction(member_id, post_id, type)
한 회원-글 관계에 현재 선택한 종류 하나만 있는지 본다.
post별 reaction type 집계
변경/취소 전후 실제 행 수와 응답 집계가 맞는지 확인한다.

업무 정책

  • 허용 kind는 THUMBS_UP, HEART, LAUGH, SAD 네 가지 대문자 enum이다. 다른 값/소문자/공백/누락/JSON 타입 오류는 400.
  • UNIQUE(post_id,member_id) 행 하나를 유지한다. 같은 kind PUT은 멱등, 다른 kind PUT은 행을 재생성하지 않고 kind/updated_at만 바꾸며 DELETE는 안 눌렀어도 200.
  • counts는 네 종류를 모두 포함(없으면 0), total은 실제 행 수 합계, 비로그인 GET의 myReaction은 null이다.

성공 기준

  • 반복 PUT/DELETE는 멱등이며 한 회원-글 관계에서 한 종류만.

실패와 데이터 보존

  • PUT /api/posts/13/reaction 입력이 원문 실패 check 조건에 해당 → HTTP 400 — 원문 check의 실패 응답 · 유지: 해당 member/post reaction 종류와 종류별 count를 실패 전 그대로 보존한다.
  • PUT /api/posts/13/reaction · [교육용 fixture · legacy:14-1:E6] 잘못된 입력 — 없는 종류 ANGRY → HTTP 400 (E6); $.errors[*].field contains "kind" · 유지: 회원-글 reaction kind와 kind별 count는 실패 전과 같다.

입력 사례

개발 과제

  • 저장 중복 방지와 종류 변경을 하나의 관계 행 상태로 모델링하고 count를 그 행에서 집계한다.
