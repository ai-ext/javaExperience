파일은 저장소에 두고 DB에는 소유자·글 연결과 메타데이터를 둔다.

이번에 할 일

이미지 업로드와 글 등록의 imageIds 연결을 구현한다.

시작 조건

  • 시나리오 DB(`community`). 이번 단계 마이그레이션은 `V20`이다.
  • community V20, uploads 설정 폴더, MultipartFile 요청을 사용하고 실제 1×1 GIF 파일을 준비한다.

사용자 시나리오

  1. 시작
    김자바가 실제 GIF 이미지를 선택했습니다. 글에는 아직 연결하지 않았습니다.
    행동
    파일을 업로드하고 반환한 실제 이미지 id를 새 글의 imageIds에 넣습니다.
    결과
    정상 파일은 201로 저장되고 본인 소유의 미연결 이미지만 글에 연결됩니다.
    이후
    확장자만 png인 텍스트는 415로 거절합니다. 다른 회원 이미지나 이미 연결된 이미지는 새 글에 가져올 수 없습니다.

데이터와 이유

post_image.uploader_id, post_id
업로더 소유와 업로드 후 글 연결 전후를 구분한다.
stored_name, original_name, content_type, size_bytes
서버 저장 식별자와 사용자 파일 메타데이터, 검사된 실제 형식을 비교한다.

업무 정책

  • 1MB 초과 거절; 파일 앞 바이트 signature로 형식을 검증; 클라이언트 파일명·Content-Type을 신뢰하지 않는다. 이미지 7은 로그인 업로더 본인 소유이고 아직 미연결이어야 연결한다.

성공 기준

  • 업로드 id와 주소로 미리보기를 표시하고 글 저장 후 상세 이미지 순서를 확인.

실패와 데이터 보존

  • POST /api/images 입력이 원문 실패 check 조건에 해당 → HTTP 400 — 원문 check의 실패 응답 · 유지: 기존 파일·post_image row·post 연결을 요청 직전 그대로 보존하고 거절 파일을 새 저장하지 않는다.
  • POST /api/images · [교육용 fixture · legacy:11-2:I2] I2 이름만 .png인 텍스트 → HTTP 415 (I2) · 유지: 기존 파일·post_image row·post 연결은 그대로며 실패 파일은 새 저장하지 않는다.
  • POST /api/images · [교육용 fixture · legacy:11-2:I3] I3 토큰 없이 올리기 → HTTP 401 (I3) · 유지: 기존 파일·post_image row·post 연결은 그대로며 실패 파일은 새 저장하지 않는다.

개발 과제

  • 서버 측 형식 판정, 안전한 저장 이름, 업로더 소유 검증, 글과 연결 트랜잭션을 구성한다.

POST/api/images201

C1: HTTP 상태 201이어야 합니다. C1: JSON 경로 $.id type "number"이어야 합니다. C1: JSON 경로 $.fileName matches "^[0-9a-f]{32}\\.gif$"이어야 합니다. C1: JSON 경로 $.url equals "/api/images/{{I0.body.fileName}}"이어야 합니다.
