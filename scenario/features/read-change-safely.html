코드 진입점부터 Security filter, Controller, Service, Repository까지 실제 요청 경로와 현재 동작을 확인합니다.

이번에 할 일

board 서버 구조·설정·프로파일을 읽어 요청 흐름 지도를 만들고 characterization test로 글·회원 응답의 현재 필드를 고정하세요. 보안 문제는 수정 전 재현 증거를 구분합니다.

시작 조건

  • D11-1/D11-2 원문이 정한 읽기 순서와 재현 스크립트를 따른다. board-server 실제 package, SecurityFilterChain, controllers/services/repositories, application profile을 확인한다.
  • 현재 user implementation의 characterization test는 수정 전에 실행한다. 민감한 actuator response 값과 실제 비밀번호는 캡처하지 않는다.

사용자 시나리오

  1. 시작
    수정 전 board user server다. USER 회원 GET /api/members/me의 현재 필드를 먼저 저장하고 prod profile에서 인증 없이 /actuator/env가 노출되는지 확인할 준비를 한다.
    행동
    Application entry→SecurityFilterChain→Controller→Service→Repository 순으로 요청 지도와 읽은 순서를 그린다. PostServiceCharacterizationTest/MemberApiCharacterizationTest를 실행하고 B14 repro 및 B11 repro 출력을 확인한다.
    결과
    지도는 로그인/글 API 요청 흐름을 한 장으로 보여 준다. 현행 characterization은 글 create/update/delete 알림 호출을 고정하고 내 정보 응답의 passwordHash 노출을 B08 증거로 기록한다. B14 재현은 prod 무인증 GET /actuator/env → 200, B11은 propertySources에서 설정값 제공 출처를 찾는다.
    이후
    아직 코드는 고치지 않는다. `passwordHash` 노출, actuator 공개, expiresIn 설정 출처의 현재 상태와 테스트 기대값을 수정 전 기준으로 보존하고 secret 값은 마스킹한다.

업무 정책

  • 수정 전에 현재 동작을 테스트로 고정하고 기존 결과를 추정으로 바꾸지 않습니다.
  • prod에서 token 없는 GET /actuator/env가 200이 되는 B14, expiresIn 출처가 다른 B11을 증거에 따라 관찰합니다. 비밀값 자체는 복사하지 않습니다.
  • 지원 티켓은 각 원문의 필수·연습·선택 범위를 유지하고 테스트 범위를 임의 확장하지 않습니다.
  • 원문 완료 기준: 패키지·요청 흐름 지도 1장과 읽은 순서 기록
  • 원문 완료 기준: B14 재현: prod 프로파일에서 토큰 없이 `GET /actuator/env` → 200
  • 원문 완료 기준: B11 재현: `bash tickets/B11/repro.sh` 출력의 `/actuator/env` 출처 목록(`propertySources`)에서 prod에서 바뀌지 않는 키의 값을 준 출처를 찾는다
  • 원문 완료 기준: `PostServiceCharacterizationTest` 통과: 글 작성·수정·삭제의 현재 동작(알림 호출 포함)을 고정
  • 원문 완료 기준: `MemberApiCharacterizationTest` 통과: 지금의 `GET /api/members/me` 응답 필드를 그대로 고정 (`passwordHash`가 보이는 것이 B08의 증거)

입력과 출력

  • 지도 대상은 board-server의 실제 Application, SecurityFilterChain, member/post controller-service-repository다.
  • `PostServiceCharacterizationTest`, `MemberApiCharacterizationTest`; prod 재현 `bash tickets/B14/repro.sh`, 설정 추적 `bash tickets/B11/repro.sh`.
  • 현재 상태로 prod `GET /actuator/env`(token 없음) → 200이 B14 문제 재현이다. 이 관찰은 수정 전 기준이며 완료 기대값은 아니다.

성공 기준

  • 요청 지도에 entry→filter chain→controller→service→repository를 실제 클래스/파일 경로와 함께 적고 읽은 순서를 기록한다.
  • 수정 전 PostServiceCharacterizationTest와 MemberApiCharacterizationTest가 현재 동작을 고정하며, 내 정보 JSON에 passwordHash가 보이는 것을 B08 증거로 남긴다.
  • B14의 prod token 없는 GET /actuator/env → 200 재현, B11 출력의 propertySources에서 설정 출처를 찾되 비밀 값은 복사하지 않는다.

실패와 데이터 보존

  • 수정 전 characterization test 없이 응답 DTO/서비스를 먼저 변경 → 현재 행동과 수정으로 생긴 행동 변화의 비교 기준이 없다. · 유지: 수정 전 원본 동작이라고 추측해 쓰지 말고 원문 테스트와 실제 응답을 먼저 기록한다.
  • /actuator/env 결과를 캡처하면서 property secret 원문을 문서에 복사 → 보안 정보가 학습 산출물로 유출된다. · 유지: value를 마스킹하고 source/origin metadata만 남긴다.

입력 사례

  • B08 수정 전 응답 고정
  • prod 설정 출처 확인

개발 과제

  • 실제 source tree를 따라 계층별 entry point를 그리고 파일/호출 관계를 적는다.
  • characterization test가 무엇을 고정하는지와 현재 response JSON field를 보존한다.
  • B11/B14 문제의 재현·원인 후보·property source를 수정 전 증거로만 기록한다.

완료 확인

  • 요청 지도 한 장과 실제 코드 읽은 순서를 제출했다.
  • 글 CRUD/알림 현재 동작과 member response 현재 field set을 characterization test로 고정했다.
  • B14 200 재현 및 B11 propertySources 출처를 비밀값 없이 남겼고 어느 티켓도 아직 수정 완료로 표시하지 않았다.
