기준선·추가·백필·이름 변경 순서 지키기

9-1 기준선, 9-3 excerpt backfill, 9-5 bookmark memo에서 note로 expand/contract를 연결해 기존 row를 보존한다.

이번에 할 일

기존 DB와 빈 Testcontainers DB의 migration history를 비교하고, post excerpt 및 bookmark 메모가 각 schema/data migration을 거쳐 보존되는지 확인한다.

시작 조건

  • scenario DB에는 기존 schema와 rows가 있고 Flyway history는 없음을 확인한다. 별도 Testcontainers DB는 비어 있다.
  • 9-3에서는 본문 101자 글, 9-5에서는 기존 memo 값·null·다른 대소문자·old-version update fixture를 기록한다.

사용자 시나리오

  1. 시작
    각 DB의 schema, Flyway version, post/content/excerpt와 bookmark/memo 값을 기록한다.
    행동
    9-1 기존 schema baseline 및 빈 DB migrate를 비교하고, 이후 9-3 excerpt backfill, 9-5 note 확장·복사·dual-write·불일치 보정·구버전 code 제거 뒤 column 축소를 검토한다.
    결과
    기존 DB는 baseline version만 기록하고 기존 DDL을 다시 실행하지 않는다. 빈 test DB는 V1 schema 다음 test-only seed를 적용한다. excerpt는 본문 첫 100자; note는 최신 memo 값을 복사한다.
    이후
    app read/write 전환 단계와 migration history를 기록하고 old code가 memo를 참조하는 동안 최종 drop을 하지 않는다.

데이터와 이유

flyway_schema_history version/checksum
기존·빈 DB별 migration 적용을 추적한다.
post.content/excerpt 101자 경계 row
기존 데이터 backfill 값과 길이 변환을 검증한다.
bookmark.memo/note: text/null/case-only/old-writer update
dual-write/reconcile의 변경 감지 범위를 확인한다.
기존 DB, blank Testcontainers DB, test-only seed
각 환경의 V1 적용 경로를 구분한다.

업무 정책

  • 기존 populated DB에는 baseline-on-migrate version 1: V1 DDL을 실행하지 않고 history만 만든다. 빈 DB는 V1 schema와 test-only V1_1 seed를 순서대로 실행한다. JPA ddl-auto=validate 유지.
  • 적용된 migration file은 수정하지 않고 새로운 version migration만 추가한다. existing user data를 dump reset으로 교체하지 않는다.
  • 9-3 excerpt는 기존 content 앞 100자에서 backfill하고 column constraint는 data가 채워진 다음 적용한다. create/update content rule에 맞춰 excerpt를 동기화하고 PATCH null은 그대로 둔다.
  • 9-5 V5는 nullable note 추가·memo 복사; rolling stage에서는 새 code가 memo/note 둘 다 쓰되 읽기는 memo. 모든 old node가 사라진 뒤 memo/note byte mismatch를 다시 맞추고 note read, 이후 memo mapping 제거, 최종 drop 순서를 지킨다. 운영 multi-node에서는 reconcile과 drop을 별도 배포로 나눈다.

입력과 출력

  • 기존 schema + rows, history 없음; blank MySQL Testcontainers.
  • post content 101 characters 및 기존 row; PATCH content null/empty.
  • bookmark memo text, null, old writer로 바뀐 값, 대소문자 차이 값.

성공 기준

  • 기존 DB version1 baseline 기록, V1 DDL 재실행 없음. 빈 DB V1 후 test-only seed.
  • excerpt 기존 값은 content first 100 characters; 101 char yields exactly 100.
  • note는 현재 memo와 일치하고 null·case-only·old-writer 변경도 최종 reconcile에서 반영된다. memo drop은 모든 old reader/writer 제거 뒤다.

실패와 데이터 보존

  • 기존 populated DB에 V1 DDL 실행 또는 applied migration checksum 변경 → Flyway validate/startup fails. · 유지: 기존 business rows 보존; DB reset하지 않는다.
  • excerpt NOT NULL 적용 전에 backfill 누락 → null audit 또는 migration fail. · 유지: 다음 schema/app version 전개를 중단한다.
  • memo를 읽고 쓰는 old server가 남았는데 V6 drop → old app SQL fails. · 유지: memo 컬럼 유지하고 호환 release gate를 기다린다.
  • note IS NULL만으로 stale memo 찾기 → old writer update/case/null 이후 note stale 값이 남을 수 있다. · 유지: source memo를 current value로 보존한다.

입력 사례

  • Existing database baseline
  • Excerpt 101자 backfill
  • Memo old writer reconciliation

개발 과제

  • migration 적용 전후 history version, row count, null count를 저장한다.
  • 101자 post와 memo null/case/update row를 실제 SQL query로 다시 읽는다.
  • old/new app의 read/write 지원을 release 단계별 표로 작성한다.

완료 확인

  • existing/empty/test DB baseline 차이를 확인했다.
  • excerpt backfill와 101자 경계를 검증했다.
  • V5 expand, dual-write, mismatch repair, read switch, old code removal, drop 순서를 문서화했다.

선택한 API 계약

GET/api/boards/dev/posts?size=3200

C1: HTTP 상태 200이어야 합니다. C1: JSON 경로 $.items[0].excerpt matches "^[\\s\\S]{0,100}$"이어야 합니다. C1: JSON 경로 $.items[1].excerpt matches "^[\\s\\S]{0,100}$"이어야 합니다. C1: JSON 경로 $.items[2].excerpt matches "^[\\s\\S]{0,100}$"이어야 합니다.
