정상·예외·취소 뒤 요청 문맥 정리하기

재사용하는 작업 스레드에서 앞사람의 사용자 번호와 요청 ID가 다음 사람에게 보이지 않게 합니다.

이번에 할 일

A 요청이 예외로 끝난 뒤 같은 스레드의 B 요청을 처리하고, 필터와 작업 스레드의 문맥 생성·전달·정리를 고치세요.

시작 조건

  • 내 프로젝트의 요청 ID 필터와 SecurityContext 사용 위치를 확인합니다.
  • 격리 테스트에서 스레드 한 개를 재사용하고 A와 B를 서로 다른 사용자·요청 ID로 만듭니다.

사용자 시나리오

  1. 시작
    한 작업 스레드에서 A의 문맥을 설정했고 A는 처리 중 예외가 납니다. B의 사용자와 요청 ID는 다릅니다.
    행동
    A→예외→B 순서와 별도 작업 스레드 전달, 취소 순서를 실행합니다.
    결과
    B에서는 B의 문맥만 보이고, 문맥을 전달하지 않은 별도 스레드에 A 값이 자동으로 나타나지 않습니다.
    이후
    작업 완료·예외·취소 뒤 문맥이 비어 있고 요청 ID 로그를 섞지 않습니다.

데이터와 이유

사용자·요청 ID
어느 요청의 로그와 작업인지 구별합니다. 토큰 원문과 개인정보는 기록하지 않습니다.
작업 종료 상태
정상·예외·취소 각각에서 정리가 실행됐는지 구별합니다.

업무 정책

  • ThreadLocal의 스레드별 저장과 작업 간 재사용을 구분합니다.
  • 부모 스레드 값이 자동 전파된다고 가정하지 않습니다.
  • 진단 로그에는 식별용 가짜 값만 씁니다.

입력과 출력

  • A/B 사용자 값, 요청 ID, 정상·예외·취소 세 종료 방식, 단일 재사용 worker

성공 기준

  • B에서는 B의 문맥만 보이고, 문맥을 전달하지 않은 별도 스레드에 A 값이 자동으로 나타나지 않습니다.

실패와 데이터 보존

  • A가 예외로 종료 → B가 A 값을 읽으면 실패입니다. 정리 전 실패를 남기고 수정 후 다시 실행합니다. · 유지: B의 인증·응답·로그에 A의 값이 남지 않아야 합니다.

입력 사례

  • 같은 대상의 전후 비교

개발 과제

  • A 요청이 예외로 끝난 뒤 같은 스레드의 B 요청을 처리하고, 필터와 작업 스레드의 문맥 생성·전달·정리를 고치세요.

완료 확인

  • `GET /actuator/health` → 200, 응답 헤더에 `X-Request-Id`
  • 같은 요청의 로그 줄마다 같은 요청 ID가 찍힌다 (기본 INFO에서는 헬스 요청이 로그 줄을 남기지 않으므로 `--args='--spring.profiles.active=local --logging.level.org.springframework.web.servlet.DispatcherServlet=DEBUG'`로 띄워 요청 안 로그 줄을 만든다)
  • 동시에 보낸 3건의 로그를 요청 ID로 나눠 볼 수 있다 (위와 같이 `DispatcherServlet` DEBUG로 띄운 기동 로그에서)
  • 동시 50요청 부하로 다른 회원 요청의 결과가 섞이는 것을 재현
  • `ForbiddenWordCheckerConcurrencyTest` 통과: 고친 뒤 동시 요청에서도 결과가 섞이지 않는다
  • 한 스레드 풀에서 A→예외→B 순서로 사용자·요청 ID를 관찰한다. finally 정리 전 실패와 정리 후 통과를 남긴다.
  • 부모 스레드의 ThreadLocal 값이 다른 작업 스레드로 자동 전달된다고 가정하지 않고 실제 값을 비교한다.
  • 내 프로젝트의 요청 ID 필터·SecurityContext 사용 위치를 읽고 생성·사용·정리 시점을 연결한다.
  • 작업 스레드로 필요한 문맥을 명시 전달하고 완료·예외·취소 뒤 개인정보와 문맥이 남지 않는 테스트를 남긴다.
  • 원인 서술: 동시 요청에서만 검사 결과가 달라지는 원인과 그 근거(재현 결과)
  • 재현 테스트: 검사기 하나를 여러 스레드가 함께 쓰게 해 결과가 섞이는지 세는 테스트(결함 상태에서 반복 실행해도 매번 실패 → 수정 후 통과). 예: `src/test/java/com/example/board/common/ForbiddenWordCheckerConcurrencyTest.java`
