결제가 느려도 글 목록은 계속 응답하기

결제가 느릴 때도 글 목록은 1.5초 안에 응답하게 하세요. 같은 시점의 메트릭·스레드 덤프로 원인을 설명하고, 목록과 충전의 정상 결과를 함께 확인합니다.

1 · 이번에 할 일

Toxiproxy로 PG 응답을 늦추고 충전 요청 중 actuator 메트릭·스레드 덤프를 수집하세요. PG 대기 중에도 목록이 정해진 응답시간 안에 끝나도록 경계를 고칩니다.

2 · 시작 조건

  • B01은 D12 필수 ticket이다. Hikari pool max=10, connection timeout=2초인 현재 설정값을 먼저 기록한다.
  • Toxiproxy로 PG response delay를 걸고 concurrent 충전과 GET /api/posts를 발생시킬 격리 DB/회원 fixture를 준비한다.

3 · 세부 요구사항

입력과 출력
  • 동시 points charge 요청은 WireMock PG response를 지연시킨다. GET /api/posts를 지연 주입이 살아 있는 같은 구간에서 보낸다.
  • 수정 전 관찰 설정: Hikari max pool 10, connection timeout 2초. 성공 기준: 목록 HTTP 200, 1.5초 이내.
  • `/actuator/metrics` Hikari active/pending과 thread dump, request ID·시간을 같은 evidence 묶음에 저장한다.
성공 기준
  • 충전 요청들이 PG 응답을 기다리는 동안에도 GET /api/posts → 200, 1.5초 이내; PostListDuringSlowPgTest 통과.
  • 수정 전 thread dump의 PG wait와 Hikari active=10/pending 적체를 연결하고, 수정 뒤 대기 thread/connection hold가 사라졌음을 기록한다.
  • PG 호출은 transaction/DB connection을 잡지 않는 경계에서 일어난다. B01 mandatory ticket의 재현·원인·수정 test를 제출한다.
개발 과제
  • 충전 서비스 transaction 시작/종료와 PgClient HTTP 호출의 실제 stack 경계를 찾는다.
  • 같은 주입 구간에서 Hikari metrics/thread dump/GET timing을 수정 전후 비교한다.
  • PostListDuringSlowPgTest를 고치고 request ID 기준 evidence를 남긴다.

데이터와 이유

Hikari maximumPoolSize=10/active/pending
충전 요청이 점유한 connection 수와 대기 요청을 글 목록 지연과 연결한다.
PG response delay 및 충전 thread stack
대기 stack이 PG network response를 기다리는지 확인한다.
GET /api/posts status·elapsed time
동일 지연 주입 구간에서 목록이 HTTP 200/1.5초 이내로 끝나는지 합격 기준을 준다.
connection timeout 2초
목록 실패가 pool 대기 만료에서 발생하는지 로그와 elapsed time으로 판별한다.

4 · 사용자 시나리오

시작 상태
pool 10개가 비어 있고 글 목록 endpoint는 정상이다. 여러 충전이 PG 응답을 기다리는 동안 pool active/pending과 요청 thread를 동시에 관찰할 수 있게 한다.
요청
Toxiproxy로 PG를 지연시키고 충전 요청을 몰아 actuator metrics와 thread dump를 수집한다. 그동안 GET /api/posts를 호출하고 수정 전후 응답시간과 Hikari connection 사용을 비교한다.
응답
수정 전에는 PG HTTP를 `@Transactional` 안에서 기다려 pool 10개가 차고 목록 요청이 connection timeout 2초를 기다릴 수 있다. 수정 후 charging 중 GET /api/posts → 200, 1.5초 이내다.
이후 상태
thread dump에서 PG wait와 Hikari metrics active=max/pending>0을 같은 시각으로 연결한다. 해결은 PG 대기를 DB transaction 밖으로 옮기는 것이며 pool size만 키우지 않는다.

느린 목록 쿼리를 slow log에서 찾고 EXPLAIN ANALYZE의 실제 읽은 행과 반환 행으로 병목을 검증합니다.

    
1 · 이번에 할 일
목록 요청의 SQL을 slow query log에서 찾고 전후 실행 계획을 비교하세요. 실제 사용 인덱스·행 수·Extra를 근거로 수정 여부를 설명합니다.
2 · 시작 조건
  • B02는 D12 필수 ticket이다. `GET /api/posts`가 실제 query를 만들고 충분한 격리 데이터가 있는 상태를 준비한다.
  • slow log 실험 전 local DB setting과 원래 `long_query_time` 값을 기록해 종료 뒤 복원한다. 기본값은 10초다.
3 · 세부 요구사항
입력과 출력
  • `GET /api/posts` 실제 목록 query를 B02 repro data로 발생시킨다.
  • MySQL 기본 long_query_time 10초를 기록한 뒤 로컬 실험 임계값을 낮춰 slow log를 수집한다.
  • EXPLAIN ANALYZE 결과에서 actual rows 읽은 수/반환 수, 선택 key, rows, Extra를 복사하고 실험 setting을 복원한다.
성공 기준
  • slow log에서 GET /api/posts 목록 SQL을 식별한다.
  • EXPLAIN ANALYZE 실제 실행의 read rows, returned rows, key/rows/Extra를 수정 전후 표에 기록하고 source에 맞는 인덱스 수정 뒤 PostListExplainTest 통과.
  • 수치 성능 향상을 측정하지 않았으면 속도 향상 claim은 하지 않는다. long_query_time local 설정 복원 기록을 남긴다.
개발 과제
  • 동일 GET list 요청으로 slow log 대상 SQL을 특정한다.
  • query predicate/order와 composite index 선행 열을 비교하고 EXPLAIN ANALYZE 실제 수치를 저장한다.
  • index 수정 후 동일 데이터/쿼리로 다시 측정하고 local setting을 원복한다.

GET /api/posts list query

EXPLAIN ANALYZE actual rows read/returned
추정 계획만 보지 않고 실행이 실제로 읽고 돌려준 행 수를 비교한다.
key/rows/Extra

조건결과유지할 상태

복합 index 컬럼 순서를 query 조건과 대조하지 않음선택 key/rows/Extra가 기대와 다를 수 있다.source 조건을 맞춰 재실행하고 실험 DB 밖의 schema를 임의 파괴하지 않는다.
  • slow log의 long_query_time 기본값은 10초이므로 실험에 사용할 로컬 관찰 설정과 복원을 기록합니다.
  • EXPLAIN ANALYZE는 실제 실행 결과와 함께 해석하고 측정하지 않은 속도 개선 수치를 쓰지 않습니다.
  • 복합 인덱스는 왼쪽 컬럼부터 활용되므로 조건·정렬과 key/rows/Extra를 비교합니다. B02 ticket 상태는 원문대로 유지합니다. B02는 D12 필수 티켓입니다.
