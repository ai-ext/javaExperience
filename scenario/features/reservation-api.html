운영자가 예약을 접수하고 같은 예약의 대상·시각·상태를 다시 확인하게 합니다.

이번에 할 일

D23에서 설계한 예약 생성 POST와 상세 GET 계약을 확정해 실제 서버에 구현하세요. 이 기능은 지급을 실행하지 않습니다.

시작 조건

  • 내 예약 모델·최소 6행 fixture와 운영자/일반 회원 인증을 준비합니다.
  • 아래 계약 등록에서 내 서버의 실제 경로·필드·상태를 입력하고, 생성·상세 계약을 따로 저장합니다.

사용자 시나리오

  1. 시작
    운영자가 쿠폰·고정 대상 회원 집합·미래 지급 시각으로 예약을 요청합니다.
    행동
    정상 생성 요청을 보내고 반환 위치나 응답에서 얻은 실제 id를 상세 요청에 직접 이어 넣습니다.
    결과
    생성 201, 같은 예약 상세 200이며 예약과 대상이 DB에 남고 아직 실제 지급 행은 생기지 않습니다.
    이후
    잘못된 입력400·미인증401·권한없음403·없는예약404를 각각 호출하고 실패 전후 DB를 대조합니다.

데이터와 이유

예약 id·쿠폰·고정 대상·미래 시각
승인한 의도를 다시 읽고 나중에 같은 대상에게 지급합니다.
현재 예약 상태
접수와 실제 지급 완료를 구분합니다.

업무 정책

  • 원본에는 고정 URI와 필드 이름이 없습니다. D23에서 정한 계약을 사용합니다.
  • 생성201과 상세200은 원본 필수 계약입니다.
  • 지급 실행은 뒤의 작업 기능에서 구현합니다.

입력과 출력

  • 확정한 생성 JSON·미래 시각·회원 id 집합·운영자 인증, 생성 후 상세 경로의 실제 예약 id

성공 기준

  • 생성 201, 같은 예약 상세 200이며 예약과 대상이 DB에 남고 아직 실제 지급 행은 생기지 않습니다.

실패와 데이터 보존

  • 입력 오류·미인증·일반 회원·없는 예약 → 각각400·401·403·404와 확정 오류 본문을 확인합니다. · 유지: 실패한 생성의 예약·대상이 일부만 남지 않아야 합니다.

입력 사례

  • 같은 대상의 전후 비교

개발 과제

완료 확인

  • D23에서 직접 정한 POST 예약 생성·GET 예약 상세 계약을 명세에 확정하고 DTO→서비스→저장소를 연결한다. 물리 경로는 내 패키지로 바꾼다.
