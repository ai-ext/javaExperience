커뮤니티 실행과 요청 오류 확인하기

0장 여덟 단계를 하나의 실행 흐름으로 묶어 route·path/query/header/body, DTO·Java type, annotation, stack trace, Gradle/YAML, Lombok, response JSON을 확인한다.

이번에 할 일

원문에 있는 /api/start routes를 실제 요청하고 각 입력 위치와 응답 필드를 확인한다. 정확한 200/400/404/415 case를 recipe별로 비교한다.

시작 조건

  • community-board 서버와 원문 compose MySQL을 실행한다. 0-6 GET config 결과로 app 설정이 반영됐는지 본다.
  • legacy:0-1..0-8 recipe를 선택해 id·path·request body를 원문 그대로 보낸다.

사용자 시나리오

  1. 시작
    서버 기동 후 GET /api/start/hello?name=김자바 및 GET /api/start/ping을 호출한다. 구성 단계를 따라 profile/echo/member/config/summary 요청을 준비한다.
    행동
    legacy recipe 0-1..0-8의 정상과 실패 요청을 실행하며 0-3은 path=7, query=spring, header X-Client, JSON body를 각각 바꿔 본다.
    결과
    hello 김자바/익명은 200과 nameLength 3/2; ping=200 pong text; 존재하지 않는 pong=404; echo/profile 성공은 200; 누락 query 400, text/plain 415, 잘못된 age/name 400; member1=200, member3=404; config/summary 200.
    이후
    각 응답과 server log를 실행한 단계별로 연결하고 DB row가 바뀌지 않는 GET 요청과 profile POST의 변화 여부를 구분한다.

데이터와 이유

query `name=김자바`와 생략 기본값
0-1 response name/message/nameLength 비교.
path 7, query spring, X-Client javaExperience, body title/tags/extra
0-3에서 요청의 네 입력 위치가 독립된 JSON field로 수신되는지 확인.
profile name/age: 김자바20, 이프론15
0-4/0-7의 age 숫자 type, adult true/false, Bean Validation 비교.
member id 1/3
0-5의 존재 성공과 404 실패를 확인.
application config appName/maxItems와 summary fields
0-6/0-8 YAML/configuration 및 response DTO 결과 확인.
stacktrace 첫 원인과 요청 route
0-5 오류에서 로그를 따라 실제 원인 위치 확인.

업무 정책

  • @GetMapping/@PostMapping 같은 annotation이 어떤 method+path를 맡는지 실제 handler와 대조한다.
  • 0-3 path/query/header/body는 각각 path=7, q=spring, X-Client=javaExperience, body={title:첫 요청,tags:[java,spring],extra:덤}; DTO mapping은 extra를 보존/제거하는 source case 차이를 관찰한다.
  • JSON 숫자 age=20/15는 숫자로 보내고 "스무살" 문자열은 400. request DTO validation 실패는 저장 전 응답으로 처리한다.
  • Gradle 의존성·YAML application 설정은 실제 프로젝트 파일에서 확인한다. Lombok annotation 사용이 생성하는 DTO getter/constructor와 Java type/method signature를 컴파일 결과와 연결한다.
  • 404는 등록하지 않은 route/없는 resource를 구분한다. 0-2 `/api/start/pong`은 원문 recipe의 404이며 임의 경로를 만들지 않는다.

입력과 출력

  • GET /api/start/hello?name=김자바; GET /api/start/hello.
  • GET /api/start/ping; GET /api/start/pong.
  • POST /api/start/echo/7?q=spring with X-Client=javaExperience, body {title:"첫 요청",tags:["java","spring"],extra:"덤"}; missing q -> /echo/7; text/plain content type.
  • POST /api/start/profile body {name:"김자바",age:20}, {name:"이프론",age:15}, invalid age "스무살"; Lombok checks {name:" ", missing age, age151}.
  • GET /api/start/members/1 and /3; GET /api/start/config; GET /api/start/summary.

성공 기준

  • GET /api/start/hello?name=김자바 → 200 {name:김자바,message:김자바님, 반가워요,nameLength:3}; no name → 200 익명/nameLength2.
  • GET /api/start/ping → 200 `pong`; POST echo A/B →200 with path/query/header/body mapping according to recipe.
  • POST profile age20 →200 adult=true; age15 →200 adult=false. GET member1/config/summary→200 with recipe fields.

실패와 데이터 보존

  • GET /api/start/pong (the exact missing route from 0-2 source) → 404 and JSON path identifies /api/start/pong. · 유지: server data unchanged.
  • POST /api/start/echo/7 without required q → 400. · 유지: no data write.
  • POST echo with Content-Type text/plain → 415. · 유지: no data write.
  • POST /api/start/profile sends age as "스무살", name blank, age missing or age151 → 400. · 유지: request rejected at validation/binding boundary; no profile write is expected.
  • GET /api/start/members/3 → 404. · 유지: existing member data unchanged.

입력 사례

  • hello name value
  • request four places
  • annotation route missing
  • wrong JSON number type
  • existing member not found

개발 과제

  • 0-2의 ping/pong recipe로 annotation 매핑 성공·실패를 비교한다.
  • 0-3의 path/query/header/body 각 source field와 DTO를 한 항목씩 대조한다.
  • 0-4 record/DTO validation과 0-7 Lombok DTO case의 정상·400을 비교한다.
  • 0-5에서 response 404와 server stack trace 첫 원인 위치를 확인한다.
  • 0-6 Gradle/YAML 설정과 config response 값을 실제 설정파일에서 찾고 0-8 Java type/method/summary DTO와 연결한다.

완료 확인

  • 0-1..0-8 모든 recipe source에 있는 정상/실패 입력과 status를 확인했다.
  • 요청 네 위치, DTO/Java 타입, annotation, Lombok/설정/stack trace가 응답에 미치는 차이를 설명한다.
  • 성공 및 실패 요청 뒤 DB 변화 유무를 실제로 구분했다.

선택한 API 계약

GET/api/start/hello?name=김자바200

C1: HTTP 상태 200이어야 합니다. C1: JSON 경로 $.name equals "김자바"이어야 합니다. C1: JSON 경로 $.message equals "김자바님, 반가워요"이어야 합니다. C1: JSON 경로 $.nameLength equals 3이어야 합니다. C1: 응답 헤더 Content-Type {"contains":"application/json"}이어야 합니다.

project-v1 · 명세 프로젝트 · 1단계
별도 명세 프로젝트와 DB 준비하기

    
    

    
spec-board 전용 DB·Flyway·공통 응답을 실행 확인해 커뮤니티 과정과 다른 project 설정 경계를 세운다.

    
이번에 할 일
별도 application 설정을 확인하고 GET /api/v1/health 및 없는 route의 status와 ApiResponse envelope를 대조한다.

    
시작 조건
  • legacy 10장 spec-board용 project DB를 사용한다. community-board DB·application.yml과 합치지 않는다.
  • 10-1/10-2의 실제 health 경로·Flyway 설정·오류 envelope를 확인한다.

    
사용자 시나리오
  1. 시작
    앱 시작 전 datasource DB명과 flyway_schema_history version을 기록한다.
    행동
    spec-board를 띄우고 GET /api/v1/health와 원문 없는 경로 GET /api/v1/no-such-path를 요청한다.
    결과
    health 성공은 {status,message,data}; route 실패는 {status,message,code,errors,data:null} 형식으로 구분된다.
    이후
    서버 재기동 후 같은 health와 schema version을 다시 확인한다.

    
데이터와 이유
spec-board datasource와 project schema
다른 project의 연결을 잘못 검사하지 않도록 한다.
Flyway migration version
재기동 때 적용된 스키마와 데이터 호환을 추적한다.
ApiResponse / ErrorCode 응답 필드
HTTP 상태와 envelope의 의미를 함께 확인한다.

    
업무 정책
  • 10장 success/error는 ApiResponse wrapper다. course spec-v2의 ProblemDetail 계약을 섞지 않는다.
  • 실패는 controller 개별 try/catch 대신 전역 advice가 공통 에러 틀로 바꾸는지 확인한다.
  • spec-board 전용 DB만 사용한다. migration SQL을 적용한 뒤 schema version을 보존한다.

    
입력과 출력
  • GET /api/v1/health.
  • GET /api/v1/no-such-path.
  • 비교로 Flyway history와 project datasource명을 읽는다.

    
성공 기준
  • health 정상 요청은 project API contract의 200 응답과 wrapper를 반환한다.
  • 기동 완료와 Flyway 적용 version을 기록할 수 있다.

    
실패와 데이터 보존
  • GET /api/v1/no-such-path (10-2 exact source route) → HTTP 실패와 공통 code/errors/data=null을 반환한다. · 유지: 회원·게시글 row 변화 없음.
  • project datasource 연결 실패 → 기동/health가 실패하고 로그에 DB 연결 원인이 드러난다. · 유지: community DB 데이터·schema는 그대로다.

    
입력 사례
  • 명세 프로젝트 health
  • 없는 경로 오류

    
개발 과제
  • 실제 application profile의 datasource와 Flyway locations를 적는다.
  • 성공·실패 JSON을 필드 단위로 비교한다.
  • 재기동 뒤 schema version과 health가 같은지 기록한다.

    
완료 확인
  • spec-board DB 분리와 migration version을 확인했다.
  • 공통 success/error 응답 모양과 실제 HTTP status를 기록했다.
  • community-board의 계약을 섞지 않았다.
