이번에 할 일

내 격리 앱에서 세 조건을 한 번에 하나씩 재현하고 같은 시각의 CPU·덤프·Hikari·GC/heap을 모아 설정 하나의 변경 전후를 비교하세요.

시작 조건

  • D38 처리율·체류 시간과 작은 전용 앱을 준비합니다.
  • WireMock/Toxiproxy 지연과 제한 힙을 사용하며 전체 기계 메모리를 소진하지 않습니다.

사용자 시나리오

  1. 시작
    CPU 계산 증가·PG 응답 대기·객체 보유 증가 중 하나만 주입한 앱이 느려집니다.
    행동
    각 조건의 CPU·스레드 덤프·풀 pending·GC/heap 추이를 같은 시간대에 기록하고 배제한 가설을 적습니다.
    결과
    CPU 사용·대기 위치·메모리 보유 증거로 원인을 구분하고 요청 스레드/DB 풀/queue/timeout의 순서를 정합니다.
    이후
    풀 증가안과 유입 제한/작업 분리안을 비교하고 설정 하나만 바꾸어 다시 측정해 회복·잔여 작업·누수 여부를 확인합니다.

데이터와 이유

동시 처리량 가설과 실측
처리율·체류 시간을 운영 설정과 연결합니다.
덤프·GC·풀 지표
원인이 서로 다른 포화 조건을 구분합니다.

업무 정책

  • OOM 유발은 선택입니다.
  • 용량 가설과 실제 측정을 구분합니다.
  • 대기열·거부·timeout 상한과 복구를 함께 확인합니다.

입력과 출력

  • 격리 앱 PID·CPU/대기/보유 조건별 값·제한 힙·timeout·queue·측정 시간 구간

성공 기준

  • CPU 사용·대기 위치·메모리 보유 증거로 원인을 구분하고 요청 스레드/DB 풀/queue/timeout의 순서를 정합니다.

실패와 데이터 보존

  • 자원 상한 또는 응답 대기 상한에 도달함 → 정한 거부/timeout으로 종료하고 완료·미완료 작업을 구분합니다. · 유지: 다른 프로세스와 기계 전체 메모리를 실험 대상으로 삼지 않습니다.
