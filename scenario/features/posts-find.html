글·태그·검색 조건을 같은 목록에 적용하기

과정 D06의 MyBatis 최신순 목록·태그/키워드 검색·cursor 경계를 결과 id와 실행 쿼리로 확인한다.

이번에 할 일

21건 fixture를 size=20 cursor 방식으로 읽고 다음 cursor가 마지막 1건을 가리키는지, 태그 조건이 결과에만 적용되는지 확인한다.

시작 조건

  • course D06에서 만든 MyBatis mapper/query와 PostListResponse 계약을 사용한다.
  • 실습용 데이터가 21건이며 모두 테스트 fixture임을 확인한다.

사용자 시나리오

  1. 시작
    21개 글을 최신순 id 내림차순으로 준비한다.
    행동
    GET /api/posts?size=20 후 실제 nextCursor를 그대로 넣어 두 번째 호출; 추가로 ?tag=spring.
    결과
    첫 응답 20건과 nextCursor, 다음 응답 1건과 nextCursor=null; tag=spring은 해당 tag 글만 반환.
    이후
    size=51, keyword=a, sort=title 요청을 각각 보낸다.

데이터와 이유

정렬된 21개 post id와 ACTIVE status
20+1 경계와 최신순 순서를 비교.
tag spring과 keyword title
동적 where에서 지정 predicate만 결과를 좁히는지 확인.
nextCursor 문자열
서버 반환값 그대로 재사용해 keyset 연속성을 확인.

업무 정책

  • 최신순 커서 경계는 마지막 id보다 작은 id를 읽는다. cursor는 클라이언트에서 파싱하지 않고 그대로 전달한다.
  • keyword/tag가 없으면 조건이 SQL에서 빠진다. 빈 IN 목록으로 IN ()을 만들지 않는다.
  • 목록 DTO items+nextCursor이며 D06에서 명시한 cursor를 page/offset으로 바꾸지 않는다.

입력과 출력

  • GET /api/posts?size=20.
  • GET /api/posts?size=20&cursor=<첫 응답 nextCursor>.
  • GET /api/posts?tag=spring; GET /api/posts?size=51; GET /api/posts?keyword=a; GET /api/posts?sort=title.

성공 기준

  • 21건에서 첫 응답 20개+nextCursor, 두 번째 1개+nextCursor=null.
  • 태그 선택 시 그 태그가 연결된 글만 반환한다.

실패와 데이터 보존

  • size=51 → 400 validation error. · 유지: 게시글·태그 row와 조회 순서는 변하지 않는다.
  • keyword=a 또는 sort=title → 400 validation error. · 유지: 읽기 전용이므로 DB 불변.

입력 사례

  • cursor 첫 묶음
  • 마지막 묶음
  • 태그 필터

개발 과제

  • source API recipe로 연속 두 요청을 보내고 응답 id를 합친다.
  • 합친 id가 중복·누락 없는지 DB 정렬 결과와 대조한다.
  • MyBatis SQL에서 미지정 filter가 조건에서 빠지는지 log로 확인한다.

완료 확인

  • 21건 경계 결과가 20+1로 이어졌다.
  • cursor를 변형하지 않고 사용했고 id 집합에 중복이 없다.
  • invalid size/keyword/sort 요청이 400이고 DB는 읽기 전과 동일하다.

    원문 요구사항
    • `CursorPage.of(fetched, size)`: 저장소는 size+1건을 읽어 온다. size보다 많으면 앞의 size건만 담고 **마지막 항목의 id**를 `nextCursor`로, 아니면 전부 담고 `nextCursor`는 null.
    • `map(mapper)`: 항목만 바꾸고 커서는 그대로(엔티티 쪽 → DTO 쪽).
    • 최신순은 id 내림차순, 인기순은 좋아요 내림차순 → 같으면 id 내림차순(커서가 한 줄로 정해지게).
    • `pageAfter(rows, cursor, order, size)`: order로 정렬했을 때 cursor 바로 다음부터 size건. cursor가 null이면 처음부터, cursor 자신은 담지 않는다.
    • `한_건_더_읽어_왔으면_size만큼_자르고_마지막_id를_다음_커서로_준다`
    • `size_이하로_읽어_왔으면_마지막_쪽이라_다음_커서가_null이다`
    • `map은_항목만_바꾸고_커서는_그대로_둔다`
    • `T_extends_HasId라서_글이든_댓글이든_같은_메서드로_쪽을_만든다`
    • `최신순은_id_내림차순이다`
    • `인기순은_좋아요_내림차순이고_같으면_id_내림차순이다`
    • `커서_다음부터_size건을_정렬_순서대로_돌려준다`
    • `super_와일드카드_덕분에_HasId_비교기를_댓글_목록에도_쓴다`
    • `함정_long_id의_차이를_int로_자르는_비교기는_큰_id에서_순서가_뒤집힌다` (`LeakyComparators`가 먼저 틀린다)

community board 목록의 offset page·size·board slug·visibility 정책을 정렬 id와 page metadata로 검증한다.

    
이번에 할 일
free 게시판 14개 샘플에서 size=5의 첫·마지막 페이지를 읽고 잘못된 범위와 없는 board 응답을 확인한다.

    
시작 조건
  • legacy 2-2 fixture의 free 게시판 글이 최신순 14개이며 자유글 10~01 형태다.
  • page는 0부터, 기본 size 10, 허용 size 1~50이다.

    
사용자 시나리오
  1. 시작
    free 게시판 전체 14글; id/order를 기록한다.
    행동
    GET /api/boards/free/posts?page=0&size=5, 이어 page=2&size=5를 보낸다.
    결과
    첫 응답 item title 자유글 10/09/08/07/06, totalElements=14,totalPages=3,hasNext=true; page2는 남은 마지막 묶음.
    이후
    size=51, page=-1, /boards/nope/posts와 protected visibility 조합을 요청한다.

    
데이터와 이유
free 게시판의 14개 정렬 글
offset 경계와 total count를 대조.
page/size/totalElements/totalPages/hasNext
응답 메타데이터와 실제 result page 수가 맞는지 확인.
PUBLISHED·PUBLIC·FOLLOWERS·PRIVATE 상태
현재 viewer의 공개/관계 정책에 따른 목록 포함 여부 검증.

    
업무 정책
  • legacy 2-2 page는 0부터, 기본 0, size 기본 10; 1..50만 허용한다.
  • community board 목록은 미삭제 공개 가능 글과 요청자 정책을 적용하고 DRAFT/HIDDEN을 일반 목록에 포함하지 않는다.
  • offset pagination을 project-v1 cursor 계약과 교환해 쓰지 않는다.

    
입력과 출력
  • page0: GET /api/boards/free/posts?page=0&size=5.
  • last: GET /api/boards/free/posts?page=2&size=5.
  • failure: size=51, page=-1, /api/boards/nope/posts.

  • page0 200, 자유글 10→06 순서, totalElements 14,totalPages 3,hasNext true.

  • page 경계를 이어 읽을 때 겹침/누락을 확인했다.

spec-board 글 목록의 sort·offset/cursor·tag/q 필터를 계약별로 실행해 데이터와 cursor 경계를 검증한다.

    
이번에 할 일
tag=mybatis 최신순 size=2 결과를 page 또는 cursor로 이어 보고 popular 정렬, invalid 조합을 따로 확인한다.

    
시작 조건
  • 10-7 spec-board의 PUBLIC/PRIVATE fixture 및 tag mybatis 데이터 확인.
  • spec-board token을 사용할 때만 내 PRIVATE가 추가되는지 구분한다.

    
사용자 시나리오
  1. 시작
    PUBLIC mybatis 글과 PRIVATE 소유 글이 존재하고 최신순 id가 기록됨.
    행동
    GET /api/v1/posts?tag=mybatis&size=2 후 응답 cursor를 그대로 넘겨 다음 page를 요청한다.
    결과
    200, tag 대상만 반환; 익명에는 PUBLIC만, login 시 자신의 PRIVATE 포함. 최신순 cursor가 이어진다.
    이후
    sort=popular+cursor, page와 cursor 동시, size=51, sort=title을 전송한다.

    
데이터와 이유
PUBLIC/PRIVATE 게시글과 author id
익명과 로그인 viewer의 노출 집합을 비교.
tag mybatis 및 q 제목 검색
필터 대상 집합과 결합 결과를 확인.
cursor와 page metadata
offset page 방식과 keyset 방식의 요청 모드를 분리.

    
업무 정책
  • size 1..50 기본 20. sort latest/popular만 허용, 기본 latest; q는 제목검색.
  • cursor parameter가 존재하면 cursor mode이며 빈 값은 첫 page. cursor는 최신순에서만 가능하고 page+cursor 동시 금지.
  • popular는 likes 내림차순, tie는 id 내림차순. PUBLIC만 공개, 로그인 시 자신의 PRIVATE도 포함.

    
입력과 출력
  • GET /api/v1/posts?tag=mybatis&size=2; 다음 요청에 nextCursor 그대로 전달.
  • GET /api/v1/posts?sort=popular&size=3.
  • 실패: ?size=51, ?sort=title, ?sort=popular&cursor=, ?page=1&cursor=, ?size=abc.

    
성공 기준
  • tag=mybatis 요청은 그 tag 글만 반환하고 200.
  • latest page/cursor는 id 내림차순, popular는 likeCount 내림차순 후 id 내림차순.
  • 응답 page/cursor metadata가 선택 모드와 일치한다.

    
실패와 데이터 보존
  • size 51·숫자 아님 또는 sort=title → 400 VALIDATION_FAILED와 field=size/sort. · 유지: 게시글·tag·like 관계 불변.
  • popular+cursor, page+cursor 동시 → 400 errors field cursor 또는 page. · 유지: 조회 조건 및 데이터 불변.

    
입력 사례
  • 태그 첫 cursor page
  • 다음 cursor page
  • popular와 cursor 충돌

    
개발 과제
  • spec-board recipe의 page/cursor 각각을 project-v1 서버에서 실행한다.
  • 익명 및 Kim token으로 response ids를 비교해 PRIVATE 포함 규칙을 본다.
  • invalid query field와 status를 errors에서 확인한다.

    
완료 확인
  • latest/popular 정렬과 tie-break를 확인했다.
  • page/cursor 제한과 태그/제목 필터의 실제 응답을 기록했다.
  • 익명/인증 공개 집합 차이를 확인했다.
