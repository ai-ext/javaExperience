글·태그·검색 조건을 같은 목록에 적용하기

과정 D06의 MyBatis 최신순 목록·태그/키워드 검색·cursor 경계를 결과 id와 실행 쿼리로 확인한다.

1 · 이번에 할 일

21건 fixture를 size=20 cursor 방식으로 읽고 다음 cursor가 마지막 1건을 가리키는지, 태그 조건이 결과에만 적용되는지 확인한다.

2 · 시작 조건

  • course D06에서 만든 MyBatis mapper/query와 PostListResponse 계약을 사용한다.
  • 실습용 데이터가 21건이며 모두 테스트 fixture임을 확인한다.

3 · 세부 요구사항

입력과 출력
  • GET /api/posts?size=20.
  • GET /api/posts?size=20&cursor=<첫 응답 nextCursor>.
  • GET /api/posts?tag=spring; GET /api/posts?size=51; GET /api/posts?keyword=a; GET /api/posts?sort=title.
성공 기준
  • 21건에서 첫 응답 20개+nextCursor, 두 번째 1개+nextCursor=null.
  • 태그 선택 시 그 태그가 연결된 글만 반환한다.
개발 과제
  • source API recipe로 연속 두 요청을 보내고 응답 id를 합친다.
  • 합친 id가 중복·누락 없는지 DB 정렬 결과와 대조한다.
  • MyBatis SQL에서 미지정 filter가 조건에서 빠지는지 log로 확인한다.

데이터와 이유

정렬된 21개 post id와 ACTIVE status
20+1 경계와 최신순 순서를 비교.
tag spring과 keyword title
동적 where에서 지정 predicate만 결과를 좁히는지 확인.
nextCursor 문자열
서버 반환값 그대로 재사용해 keyset 연속성을 확인.

업무 정책

조건결과유지할 상태
size=51400 validation error.게시글·태그 row와 조회 순서는 변하지 않는다.
keyword=a 또는 sort=title400 validation error.읽기 전용이므로 DB 불변.
  • 최신순 커서 경계는 마지막 id보다 작은 id를 읽는다. cursor는 클라이언트에서 파싱하지 않고 그대로 전달한다.
  • keyword/tag가 없으면 조건이 SQL에서 빠진다. 빈 IN 목록으로 IN ()을 만들지 않는다.
  • 목록 DTO items+nextCursor이며 D06에서 명시한 cursor를 page/offset으로 바꾸지 않는다.

    필수 여부 · 선택
    원문 요구사항
    • `CursorPage.of(fetched, size)`: 저장소는 size+1건을 읽어 온다. size보다 많으면 앞의 size건만 담고 **마지막 항목의 id**를 `nextCursor`로, 아니면 전부 담고 `nextCursor`는 null.
    • `map(mapper)`: 항목만 바꾸고 커서는 그대로(엔티티 쪽 → DTO 쪽).
    • 최신순은 id 내림차순, 인기순은 좋아요 내림차순 → 같으면 id 내림차순(커서가 한 줄로 정해지게).
    • `pageAfter(rows, cursor, order, size)`: order로 정렬했을 때 cursor 바로 다음부터 size건. cursor가 null이면 처음부터, cursor 자신은 담지 않는다.
    • `한_건_더_읽어_왔으면_size만큼_자르고_마지막_id를_다음_커서로_준다`
    • `size_이하로_읽어_왔으면_마지막_쪽이라_다음_커서가_null이다`
    • `map은_항목만_바꾸고_커서는_그대로_둔다`
    • `T_extends_HasId라서_글이든_댓글이든_같은_메서드로_쪽을_만든다`
    • `최신순은_id_내림차순이다`
    • `인기순은_좋아요_내림차순이고_같으면_id_내림차순이다`
