회원 가입부터 내 정보까지 연결하기

spec-board 회원가입·JWT 로그인·내 정보 요청으로 회원 정규화와 인증 주체가 이어지는지 확인한다.

이번에 할 일

가입한 email을 정규화해 중복 차단하고 BCrypt hash를 저장한 뒤 실제 id와 token으로 내 정보를 조회한다.

시작 조건

  • project DB에 check-10-3@example.com 계정이 없어야 한다.
  • 가입 길이 경계: password 8~64자와 UTF-8 72 bytes 이하, nickname 2~20자.

사용자 시나리오

  1. 시작
    user row에 check-10-3@example.com 없음; 현재 row 수 n.
    행동
    POST /api/v1/users에 email=" Check-10-3@Example.COM ", password="password1234", nickname=" 채점용 "을 전송하고 response id로 login/me 수행.
    결과
    가입 201과 Location /api/v1/users/{id}; email은 check-10-3@example.com으로 정규화. login 200, me 200에서 같은 id/email/nickname.
    이후
    중복 email은 409, password 7자와 한글 25자(75 bytes)는 400, 없는 email/틀린 password는 동일 401.

데이터와 이유

users.email, password_hash, nickname
정규화·중복 여부·hash 저장·응답 제외 여부를 확인.
회원 id와 임시 accessToken
가입에서 인증 조회까지 같은 회원이 유지되는지 검증; token은 저장하지 않음.
8/7자 password, 한글24/25자 password, nickname1/2자
문자 수와 UTF-8 byte 경계의 오류를 재현.

업무 정책

  • email은 trim 후 lowercase(Locale.ROOT)하여 검사·저장한다. nickname은 앞뒤 공백 제거 후 2~20자다.
  • password는 BCrypt로 hash만 저장하며 8~64자와 72 UTF-8 byte 조건을 모두 만족해야 한다. 한글 24자 허용, 25자 거절.
  • 없는 이메일과 틀린 password는 동일한 401 문구여야 한다.

입력과 출력

  • 정상 body: {email:" Check-10-3@Example.COM ",password:"password1234",nickname:" 채점용 "}.
  • 정상 경계: password 8자, 64자, 한글 24자; nickname 2자, 20자.
  • 실패: 중복 email, password 7자/65자/한글25자, nickname 1자/21자, email 배열 JSON.

성공 기준

  • POST /api/v1/users → 201, Location 포함, data {id,email,nickname}; 비밀번호/hash 미포함.
  • POST /api/v1/auth/login → 200 accessToken/expiresIn; GET /api/v1/users/me → 200 같은 id.

실패와 데이터 보존

  • 정규화 뒤 이미 존재하는 email로 가입 → 409 DUPLICATE. · 유지: user row 수 n 유지, 기존 password_hash/nickname 불변.
  • password가 7자 또는 한글 25자, nickname 경계 밖 → 400 VALIDATION_FAILED와 해당 errors[].field. · 유지: DB에 회원이 추가되지 않고 BCrypt encode를 호출하지 않는다.
  • 이메일 없음과 틀린 비밀번호 로그인 → 양쪽 모두 401 같은 문구. · 유지: token/user row가 생성되지 않는다.
  • token 없이 /api/v1/users/me → 401. · 유지: 회원 데이터 변화 없음.

입력 사례

  • 정규화 가입
  • 중복
  • BCrypt byte 경계

개발 과제

  • 가입 후 Location/id를 기록해 로그인과 내 정보 요청에 재사용한다.
  • DB는 email과 hash의 존재만 확인하고 hash/token 값은 출력 자료에 복사하지 않는다.
  • 오류 응답의 field·code·status와 row count를 같이 대조한다.

완료 확인

  • 가입·login·me에서 id가 이어지고 secret은 응답에 없다.
  • email 중복·byte 경계·nickname 실패가 DB row를 추가하지 않았다.
  • 존재/비밀번호 오류의 401 문구가 동일하다.
