이번에 할 일

시작 조건

  • 내 사본·DB/Redis·장애 주입 스크립트의 정확한 대상을 확인합니다.
  • 기존 정상 요청과 실패 시 중단 기준을 기록합니다.

사용자 시나리오

  1. 시작
    정상 목록에 응답하던 사본에 제공된 캐시 장애 조건을 주입합니다.
    행동
    실패/지연·서버 로그·대기 지점을 확인하고 대응한 뒤 같은 요청을 다시 실행합니다.
    결과
    기존 정상 요청이 복구되고 저장/조회 데이터가 유지됩니다.
    이후
    영향·주입·완화·복구 시각과 근거·재발 방지 담당/기한/검증을 기록합니다.

데이터와 이유

장애 타임라인
어떤 대응이 언제 영향을 줄였는지 구분합니다.
정상 기준과 복구 응답
프로세스 재시작만으로 복구됐다고 오해하지 않습니다.

업무 정책

  • 공개된 주입 훈련과 원인을 모르는 진단을 구분합니다.
  • 다른 개발자의 프로세스나 DB를 주입 대상으로 쓰지 않습니다.

입력과 출력

  • 훈련 스크립트·사본 주소·정상 요청·중단 기준·관찰 시각

성공 기준

  • 기존 정상 요청이 복구되고 저장/조회 데이터가 유지됩니다.

실패와 데이터 보존

  • 완화 후에도 응답/데이터가 일치하지 않음 → 복구 완료로 기록하지 않고 추가 영향과 다음 확인 사항을 명시합니다. · 유지: 기존 정상 데이터와 실패 증거를 보존합니다.

입력 사례

개발 과제

완료 확인

  • 모의 장애 훈련 필수 / B16 수정 기준은 선택 시 적용
  • 지연 3초와 연결 끊김을 한 번씩 주입한 `injections.log`와 복구 결과를 남긴다
  • 로그·메트릭·스레드 덤프(`evidence-*/`)와 `probe-*.log`로 장애를 알아차린 시각과 원인을 지목한 시각을 기록한다
  • B16을 고친 서버: 주입 중에도 `POST /api/posts` → 201, `GET /api/posts/popular` → 200, 둘 다 1초 이내 (`probe-*.log`와 `injections.log`의 같은 주입 구간을 보여 준다)
  • 회고 문서: 타임라인, 원인(스레드 덤프·로그 근거), 조치, 재발 방지. 주입 중 응답 코드·시간은 `probe-*.log`에서 옮긴다
