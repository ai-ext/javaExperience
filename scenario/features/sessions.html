로그인·내 정보·로그아웃을 같은 세션으로 확인하기

Servlet HttpSession과 JSESSIONID 쿠키로 CSRF 준비·로그인·내 정보·로그아웃을 이어 보고, JWT 인증과 다른 관찰값을 분리한다.

이번에 할 일

POST /api/v1/session/login 성공 전후 session id 회전, GET /api/v1/session/me의 회원 id N, POST /api/v1/session/logout의 204 및 같은 옛 쿠키의 401을 확인한다. 준비 경로는 POST /api/v1/auth/login, GET /api/v1/session/csrf이며 세션 로그아웃 뒤 JWT는 GET /api/v1/users/me에서 별도로 검증한다.

시작 조건

  • L15 README 실행 절차로 회원 session-lab@example.com을 가입하고 실제 id N을 기록한다. 10-4에서 발급받은 JWT와 쿠키 jar는 서로 다른 인증 재료다.
  • GET /api/v1/session/csrf가 만든 익명 세션을 session-before.jar에 저장하고 반환 CSRF token을 로컬 변수로만 사용한다.

사용자 시나리오

  1. 시작
    가입 응답에서 얻은 회원 id N, JWT와 익명 session-before.jar를 준비한다.
    행동
    동일 jar와 X-CSRF-Token으로 POST /api/v1/session/login 후 새 jar로 GET /api/v1/session/me, POST /api/v1/session/logout, 다시 GET /api/v1/session/me를 호출한다.
    결과
    로그인은 200이고 session id가 회전한다. /me는 200과 N의 회원 정보를 반환하고 logout은 204, 옛 쿠키의 /me는 401이다.
    이후
    쿠키 없는 /me의 401, CSRF 누락 로그인·로그아웃 403, 세션 로그아웃 뒤 JWT /api/v1/users/me 유효성을 각각 기록한다.

데이터와 이유

회원 N과 users row
가입 응답에서 얻은 실제 id로 로그인·세션 /me의 DB 조회가 같은 회원을 가리키는지 확인한다.
JSESSIONID와 CSRF token
쿠키 jar를 통한 세션 복원 및 CSRF 검증을 확인한다. id와 token은 로컬에서만 비교·사용한다.
10-4 JWT
세션 로그아웃이 Bearer JWT의 인증 상태를 지우지 않는다는 별도 경계를 확인한다.

업무 정책

  • GET /api/v1/session/csrf는 익명 세션과 예측하기 어려운 CSRF token을 만들고 쿠키에는 session id만 둔다.
  • POST /api/v1/session/login은 기존 익명 세션에서 X-CSRF-Token을 먼저 확인한다. 불일치는 403이며 비밀번호 검증은 시작하지 않는다. 성공 시 changeSessionId()로 회전하고 userId=N을 저장한다.
  • GET /api/v1/session/me는 getSession(false)로 새 세션을 만들지 않는다. userId가 없거나 DB 회원을 조회할 수 없으면 401이다.
  • POST /api/v1/session/logout은 CSRF 확인 뒤 session.invalidate()하며 204를 반환한다. CSRF 실패는 403이고 세션을 유지한다. 세션 로그아웃은 이미 발급된 JWT를 무효화하지 않는다.
  • 비밀번호는 로그인에서 가입 길이 규칙을 재검사하지 않고 공백 여부만 확인한다. 없는 이메일과 틀린 비밀번호는 같은 401 문구다. 쿠키는 HttpOnly·SameSite=Lax, HTTPS 배포 시 Secure 차이를 관찰한다.

입력과 출력

  • 가입 계정 email=session-lab@example.com 및 가입 때 설정한 password.
  • CSRF token은 X-CSRF-Token header로만 보내고 URL·로그·저장소에 넣지 않는다.
  • session-before.jar와 session-after.jar를 분리해 로그인 전/후 JSESSIONID의 실제 값을 로컬에서만 비교한다.

성공 기준

  • POST /api/v1/session/login은 200이며 로그인 전후 session id가 다르고 응답에는 password/hash가 없다.
  • GET /api/v1/session/me는 200으로 id N, email, nickname을 반환한다.
  • POST /api/v1/session/logout은 204이고 같은 이전 쿠키의 /me는 401이다. 익명 쿠키 없는 /me도 401이다.
  • 세션 로그아웃 이후에도 10-4 JWT는 만료 전 POST 준비 흐름과 무관하게 GET /api/v1/users/me에서 별도 검증할 때 유효할 수 있다.

실패와 데이터 보존

  • 로그인 또는 로그아웃에서 X-CSRF-Token이 없거나 세션 값과 다름 → 403이며 비밀번호 확인이나 session.invalidate가 일어나지 않는다. · 유지: 기존 세션 인증 상태와 회원 row가 그대로다.
  • 없는 이메일 또는 틀린 비밀번호로 로그인 → 둘 다 같은 401 문구이며 회원 존재를 구분하지 않는다. · 유지: 세션 userId가 설정되지 않고 session id가 인증 세션으로 회전하지 않는다.
  • 다른 cookie jar 또는 쿠키 없이 GET /api/v1/session/me → 401이며 새 세션을 만들지 않는다. · 유지: 원래 jar의 로그인은 유지된다.
  • 로그아웃 뒤 오래된 쿠키로 /me 재요청 또는 실습 timeout 뒤 /me → 401이다. · 유지: userId를 복구하지 않고 별도 만료 로직으로 상태를 만들지 않는다.

입력 사례

  • L15 정상 쿠키 흐름
  • CSRF 거절
  • JWT와 세션 분리

개발 과제

  • L15 README의 curl 흐름을 두 cookie jar로 실행하고 실제 id N·session id·응답을 적는다.
  • Set-Cookie가 매번 온다고 가정하지 말고 -b/-c jar의 JSESSIONID를 로컬에서 비교한다.
  • 틀린 비밀번호/CSRF/다른 jar/logout 이후를 각각 실행하고 응답 상태와 세션 상태를 관찰한다.
  • 짧은 실습 timeout은 설정을 읽고 유휴 만료 결과를 기다려 확인한다. 특정 초를 결과처럼 쓰지 않는다.

완료 확인

  • 로그인 성공 시 세션 id 회전과 /me의 N이 확인됐다.
  • CSRF 실패·다른 쿠키·로그아웃·유휴 만료의 403/401과 상태 보존을 확인했다.
  • 세션 인증과 Bearer JWT 결과를 분리해 기록했다.
