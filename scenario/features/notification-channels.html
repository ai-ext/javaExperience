채널을 늘려도 기존 알림 계약 지키기

알림 전달 채널을 늘리면서 게시글·댓글 도메인의 기존 알림 계약과 의존 방향을 보존합니다.

이번에 할 일

B04 문제를 재현하고 인터페이스 구현 선택이 알림 생산자 API에 퍼지지 않게 구성하세요. ArchUnit 규칙과 characterization test로 구조·기존 동작을 검증합니다.

시작 조건

  • D11-4의 B04는 필수 티켓이다. 현재 글 create/update/delete 알림 호출을 PostServiceCharacterizationTest로 고정한다.
  • 알림 provider/channel은 board 프로젝트 내부 경계로 다룬다. 신규 HTTP endpoint나 다른 프로젝트의 dispatch API를 만들지 않는다.

사용자 시나리오

  1. 시작
    글 작성 요청이 현재 알림 구현체에 직접 의존해 ArchitectureTest가 실패하도록 구성된 B04 재현 상태다. POST /api/posts는 USER token에서 201이어야 한다.
    행동
    ArchitectureTest의 최초 실패와 B04 원인을 기록한다. 알림 채널 구현/선택을 별도 경계에 둔 뒤 ArchitectureTest와 PostServiceCharacterizationTest를 재실행하고 POST /api/posts를 확인한다.
    결과
    수정 전 ArchitectureTest 실패; 수정 후 ArchitectureTest 및 PostServiceCharacterizationTest 통과. 기존 POST /api/posts는 201 및 Location 계약을 유지하며 알림 채널 추가는 post/comment API 코드 변경을 요구하지 않는다.
    이후
    동일 글 create/update/delete 관찰에서 기존 알림 호출 수·순서가 유지되고 신규 channel은 별도 구현 경계에서 선택되는지 확인한다.

  • D11-4는 ArchitectureTest가 먼저 실패하는 것을 확인한 뒤 B04 수정 후 ArchitectureTest와 PostServiceCharacterizationTest를 통과시킵니다.

  • 원문 완료 기준: 고치기 전에 지금 동작을 고정하는 특성화 테스트(`PostServiceCharacterizationTest`: 글 작성·수정·삭제와 댓글의 알림 행, 금칙어 400). 고친 뒤에도 그대로 통과해야 한다.
  • 원문 완료 기준: `ArchitectureTest`(ArchUnit 규칙 1개로 이번 원인의 재발 막기)가 고치기 전에 실패 → 고친 뒤 통과
  • 원문 완료 기준: 수정 diff
  • 원문 완료 기준: **계약:** `PostSummaryReader` 인터페이스에 `Optional<PostSummary> findPublic(long id)` 한 메서드를 만든다. `PostSummary`는 `id`, `title` 두 값만 담는 불변 DTO다. `PostSummaryService`는 이 인터페이스만 생성자로 받고, 결과가 없으면 404로 바꾼다. Controller는 `GET /api/labs/post-summaries/{id}`만 연결한다. `id<=0`은 400으로 처리한다.
  • 원문 완료 기준: **JPA 구현:** `JpaPostSummaryReader implements PostSummaryReader`. 기존 `PostRepository` 또는 JPA 쿼리에서 id와 `deletedAt=null`, `status=PUBLISHED`, `visibility=PUBLIC`을 확인한다. `Post` Entity를 HTTP로 직접 내보내지 않는다. 이미 DB에 읽은 Entity 값에서 DTO로 변환한다.
  • 원문 완료 기준: **JDBC 구현:** `JdbcPostSummaryReader implements PostSummaryReader`. 필요하면 프로젝트에 `spring-boot-starter-jdbc`를 추가한다. `JdbcTemplate`의 바인딩 파라미터로 아래 SQL을 실행하고 DTO로 매핑한다. ID를 SQL 문자열에 이어 붙이지 않는다.
  • 원문 완료 기준: **Spring 빈 선택:** `app.post-summary.reader=jpa`를 기본값, `jdbc`를 다른 값으로 둔다. 각 구현체를 조건부로 등록해 **한 번에 하나만** `PostSummaryReader` 빈이 생기게 한다. 예를 들면 `@ConditionalOnProperty(name="app.post-summary.reader", havingValue="jpa", matchIfMissing=true)`와 `havingValue="jdbc"`를 쓸 수 있다. Service와 Controller 코드는 설정을 바꿀 때 수정하지 않는다.
  • 원문 완료 기준: **실패를 보고 복구:** 잠시 두 조건을 모두 없애 두 구현을 동시에 빈으로 등록한다. 주입 후보가 둘이라 애플리케이션 시작이 실패하는 것을 관찰한다. 예외에 나오는 두 구현체 이름을 찾은 뒤 조건을 다시 넣는다. 빈을 하나도 등록하지 않은 경우도 서비스 생성에 실패한다는 것을 설명한다. 실패 실험은 서버를 구동해 확인한 뒤 원래 설정으로 복구한다.

입력과 출력

  • 기존 API 확인: USER POST /api/posts 정상은 201 + Location, 잘못된 요청은 400, token 없이는 401. 채널 전용 API는 원문/recipe에 없으므로 만들지 않는다.
  • `ArchitectureTest`는 먼저 실패해야 하고 B04 수정 뒤 `ArchitectureTest`와 `PostServiceCharacterizationTest`가 모두 통과한다.
  • 알림 채널 추가 후 글·댓글 API 처리 파일이 변경 대상에 포함되지 않았는지 확인한다.

성공 기준

  • 수정 전 ArchitectureTest의 B04 의존 규칙 실패를 재현하고 원인을 특정한다.
  • 수정 후 ArchitectureTest 및 PostServiceCharacterizationTest 통과; USER POST /api/posts → 201/Location과 기존 create/update/delete 알림 호출 동작 유지.
  • 새 channel 선택/전달 endpoint를 추가하지 않는다. B04는 D11 필수 티켓이다.

실패와 데이터 보존

  • 알림 channel 변경으로 PostController/PostService의 기존 동작이 바뀌거나 characterization 호출이 달라짐 → PostServiceCharacterizationTest 실패 또는 POST /api/posts의 HTTP 201/Location 계약 위반이다. · 유지: 기존 글 CRUD 응답·알림 발행 semantics를 유지한다.
  • 수정 전 ArchitectureTest가 통과해 B04 결함을 재현하지 못함 → 결함을 만든 의존 관계나 규칙 적용 대상을 다시 확인한다. · 유지: 재현 없이 새 구현을 완료 처리하지 않는다.
