이번에 할 일

회원·공통 에러 저장 기반을 정하고 닉네임 정규화와 비밀번호 해시를 적용해 가입 흐름을 연결하세요. 중복과 유효성 실패가 계정 일부를 남기지 않는지 확인합니다.

시작 조건

  • D02의 ErrorCode/ProblemDetail 기반, 회원 테이블과 닉네임 정규화 규칙을 준비한다.
  • 가입 요청은 새 email/nickname으로 시작하고, 동일 email 재시도는 첫 성공 뒤 수행한다.

사용자 시나리오

  1. 시작
    회원 테이블에 `learner@example.test` 계정이 없다. 요청 nickname에는 앞뒤 공백과 대문자를 넣고 password는 8자 이상으로 준비한다.
    행동
    `POST /api/auth/signup` 정상 요청을 보내고 같은 email로 한 번 더 요청한다. 별도 요청에서 password를 7자로 줄인다.
    결과
    첫 요청은 HTTP 201이며 정규화된 nickname과 BCrypt password hash가 저장된다. 같은 email 재요청은 409 `/errors/duplicate`; 7자 password는 400 `/errors/validation`, `errors[0].field=password`다.
    이후
    DB에서 해당 email row가 한 건이고 password_hash가 입력 원문이 아닌 BCrypt 형식인지 확인한다. 중복·검증 실패 뒤 row 수는 계속 한 건이다.

데이터와 이유

email과 nickname
email과 정규화된 nickname 각각의 UNIQUE 조건을 가입 중복 검증과 연결한다.
password 원문과 password_hash
BCrypt 저장 여부를 확인하며 원문은 DB·응답·로그에 남기지 않는다.
nickname 정규화 결과
앞뒤 공백 제거·소문자화가 저장 전에 적용되는지 비교한다.
ErrorCode 및 ProblemDetail
중복·필드 검증 실패를 안정적인 409/400 계약으로 표현한다.

입력과 출력

  • POST /api/auth/signup JSON: email=`learner@example.test`, nickname=` Learner `, password는 8자 이상 문자열.
  • 동일 email 재요청은 409 `/errors/duplicate`; password를 7자로 보낸 별도 요청은 400 `/errors/validation`이며 errors[0].field는 password다.
  • 회원 엔티티는 USER 역할과 생성·수정 시각을 보관한다. 요청 DTO와 저장 Entity를 구분한다.

성공 기준

  • 첫 `POST /api/auth/signup` → 201. nickname은 앞뒤 공백 제거 및 소문자화 후 저장된다.
  • email 중복 요청 → 409 `/errors/duplicate`; password 7자 요청 → 400 `/errors/validation`, `errors[0].field=password`.
  • 회원 row는 성공 1건만 남고 password_hash는 BCrypt hash이며 평문 password와 passwordHash 응답 노출은 없다.

실패와 데이터 보존

  • 동일 email 또는 정규화한 nickname이 이미 존재함 → 409 `/errors/duplicate`. · 유지: 첫 가입 row가 한 건 유지되고 두 번째 회원 row가 생기지 않는다.
  • password가 7자임 → 400 `/errors/validation`, errors[0].field=password. · 유지: 새 회원 row/hash가 추가되지 않는다.
  • 요청 필수값 누락 또는 email 형식 위반 → 400 validation 응답으로 거부한다. · 유지: 회원 row와 닉네임 데이터가 바뀌지 않는다.

입력 사례

  • 가입 후 정규화 확인
  • 중복 및 짧은 비밀번호

개발 과제

  • 회원 email·정규화 nickname UNIQUE와 역할·시각 필드를 설계하고 DB 직접 INSERT 중복도 거부되는지 확인한다.
  • 닉네임 정규화, BCrypt encode, DTO 검증, ProblemDetail 매핑을 연결한다.
  • 성공·중복·검증 실패 요청 전후 회원 row와 hash를 비교한다.

완료 확인

  • 신규 가입 201과 정규화 nickname, USER 역할을 확인했다.
  • 같은 email 409 및 password 7자 400/password 필드를 재현했다.
  • DB에서 중복이 거부되고 비밀번호 hash만 보관되며 실패 요청으로 row가 늘지 않는 근거를 남겼다.

저장된 회원 자격을 확인해 Bearer JWT를 발급하고, 발급된 주체로 내 정보를 조회합니다.

    
이번에 할 일
로그인 실패 사유가 계정 존재 여부를 노출하지 않게 하고, 토큰으로 인증된 회원 정보만 돌려주는 요청 흐름을 만드세요.

    
시작 조건
  • 앞 단계에서 가입한 `learner@example.test`와 저장된 BCrypt hash를 사용한다.
  • BOARD_JWT_SECRET은 환경 변수에서 공급하며 token을 로그·학습 기록에 복사하지 않는다.

    
사용자 시나리오
  1. 시작
    가입 회원 learner@example.test가 있고 password hash가 저장돼 있다.
    행동
    올바른 password로 POST /api/auth/login 후 반환된 Bearer token으로 GET /api/members/me를 호출한다. 이어서 틀린 password와 없는 email을 각각 로그인시킨다.
    결과
    정상 로그인은 200 `{accessToken, tokenType:"Bearer", expiresIn}`이고 tokenType은 Bearer다. 내 정보는 200 `{id,email,nickname,role,createdAt}`이며 passwordHash가 없다. 두 종류의 잘못된 자격은 같은 401 `/errors/unauthorized`다.
    이후
    정상 응답 token을 보안 입력란에만 사용한다. GET /api/members/me에 token을 빼거나 만료 token을 넣으면 401이며 비밀값이 body·로그에 저장되지 않는다.

    
데이터와 이유
email lookup key
요청 email이 어떤 회원 row와 비교되는지 확인하고 등록되지 않은 계정의 실패 응답도 동일하게 만든다.
BCrypt password hash
평문 비교 대신 저장 hash에 대한 password 검증이 성공/실패를 결정한다.
accessToken·tokenType·expiresIn
클라이언트가 인증 헤더를 만들기 위해 필요한 필드와 만료 정보를 검증한다.
인증 회원의 MemberResponse
JWT 주체에서 회원을 찾고 passwordHash를 응답 DTO에서 제외한다.

    
업무 정책
  • 없는 email과 틀린 password는 모두 401 /errors/unauthorized로 같은 응답 계약을 사용합니다.
  • JWT 서명 키는 BOARD_JWT_SECRET 환경 변수에서 읽습니다. 토큰·비밀번호를 기록 파일에 저장하지 않습니다.
  • 내 정보에는 passwordHash를 노출하지 않습니다.
  • 원문 완료 기준: `POST /api/auth/login` → 200 `{accessToken, tokenType: "Bearer", expiresIn}`
  • 원문 완료 기준: 틀린 비밀번호와 없는 이메일 → 둘 다 같은 401 `/errors/unauthorized`
  • 원문 완료 기준: USER 토큰으로 `GET /api/members/me` → 200 `{id, email, nickname, role, createdAt}`, `passwordHash` 없음
  • 원문 완료 기준: 토큰 없음·만료 토큰 → 401
  • 원문 완료 기준: USER 토큰으로 `GET /api/admin/reports` → 403 `/errors/forbidden` (컨트롤러는 D10에 만들지만 규칙은 지금 막는다)

    
입력과 출력
  • POST /api/auth/login JSON의 email/password; 성공 시 응답의 accessToken을 Bearer token으로 사용한다.
  • GET /api/members/me는 Authorization: Bearer <실제 accessToken>이며 token은 예시 파일에 붙여 넣지 않는다.
  • 잘못된 password와 존재하지 않는 email은 같은 401 `/errors/unauthorized` 응답이어야 한다.

    
성공 기준
  • `POST /api/auth/login` → 200 `{accessToken, tokenType:"Bearer", expiresIn}`.
  • Bearer token의 `GET /api/members/me` → 200 `{id,email,nickname,role,createdAt}`; passwordHash 필드는 없다.
  • token 미포함·만료 token은 401; 틀린 password와 없는 email은 둘 다 401 `/errors/unauthorized`로 동일하다.

    
실패와 데이터 보존
  • password가 맞지 않거나 email에 해당하는 회원이 없음 → 양쪽 모두 401 `/errors/unauthorized`의 같은 공개 오류 형식을 반환한다. · 유지: accessToken이 발급되지 않고 회원 데이터·password hash도 변경되지 않는다.
  • token 없이 또는 만료된 token으로 GET /api/members/me → 401 `/errors/unauthorized`. · 유지: 요청자 임의 ID의 회원 정보나 passwordHash를 반환하지 않는다.

    
입력 사례
  • 로그인해 내 정보 확인
  • 실패 사유 감추기

    
개발 과제
  • password hash 검증과 JWT 생성·검증을 환경 변수 서명 키에 연결한다.
  • 인증 subject에서 내 회원 ID를 얻어 응답 DTO에 필요한 다섯 필드만 매핑한다.
  • 정상/틀린 password/없는 email/누락·만료 token의 상태와 응답 필드를 비교한다.

    
완료 확인
  • 정상 login 200 필드와 만료 초, Bearer token의 내 정보 200 필드 및 passwordHash 부재를 확인했다.
  • 틀린 password와 없는 email의 공개 401 형식이 같고 token이 발급되지 않는 것을 확인했다.
  • token을 저장하지 않고 BOARD_JWT_SECRET이 환경 변수에서 읽힌다는 설정 근거를 남겼다.
