실행계획과 데이터 분포로 인덱스 비교하기

9-2 내 좋아요 cursor query의 실제 인덱스 사용·추정 rows·실제 rows·정렬 단계를 격리 DB에서 비교한다.

이번에 할 일

post_like 회원별 목록 query를 기존 member_id index와 migration index 상태에서 EXPLAIN/EXPLAIN ANALYZE하고 결과 순서를 보존한다.

시작 조건

  • 4-3 seed에서 member_id 인덱스만 있는지 SHOW INDEX로 기록한다.
  • 이 실험은 disposable practice DB에서 실행하며 schema.sql 원본 index를 영구 변경하지 않는다.

사용자 시나리오

  1. 시작
    member12의 likes query `WHERE member_id=12 ORDER BY created_at DESC,id DESC LIMIT 6`; 기존 index와 rows를 기록한다.
    행동
    EXPLAIN과 EXPLAIN ANALYZE를 실행하고 V2 ix_post_like_member_created 및 ANALYZE TABLE 후 같은 plan/query를 재확인한다.
    결과
    actual API GET /api/me/likes?size=6의 IDs/순서는 전후 동일. key/rows/Extra와 actual rows/loops/time을 각 실행 결과 그대로 기록한다.
    이후
    기존 foreign key index는 삭제하지 않는다. `Using filesort` 또는 작은 seed latency만으로 대량 속도 개선을 단정하지 않는다.

데이터와 이유

post_like(member_id,created_at,id)
회원 조건과 cursor 정렬 키의 복합 인덱스 후보.
member12 likes rows and six result IDs
계획 변경 후 user result ordering이 동일한지 확인.
EXPLAIN key/rows/Extra estimates
optimizer plan estimate 기록.
EXPLAIN ANALYZE actual rows/loops/time
실제 실행 관찰값과 추정값을 분리.
SHOW INDEX before/after
기존 FK index 보존 및 새 index 존재 확인.

업무 정책

  • 같은 select/join/order/limit와 같은 data state를 비교한다. `EXPLAIN rows`는 estimate이지 duration이 아니다.
  • EXPLAIN ANALYZE는 읽기 SELECT를 실행해 actual iterator rows/loops/time을 보여준다. 결과 데이터와 API 응답은 별도 확인한다.
  • ANALYZE TABLE은 optimizer statistics refresh이며 EXPLAIN ANALYZE와 다른 조작이다.
  • 새 compound index migration에 `ANALYZE TABLE post_like`; FK index는 이번 단계에서 제거하지 않는다. 쿼리 결과는 동일해야 한다.
  • 운영 큰 데이터 결과를 추정하거나 속도 수치를 만들어 쓰지 않는다.

입력과 출력

  • EXPLAIN SELECT l.id,l.post_id,l.created_at FROM post_like l WHERE l.member_id=12 ORDER BY l.created_at DESC,l.id DESC LIMIT 5.
  • EXPLAIN ANALYZE same SELECT.
  • V2 after index + ANALYZE TABLE; repeat.
  • API GET /api/me/likes?size=6.

성공 기준

  • Index key/rows/Extra pre/post values are transcribed.
  • EXPLAIN ANALYZE actual rows/loops/time kept separate from estimates.
  • Same API response id order before and after index.
  • 실제 route GET /api/me/likes?size=5는 200이며 seed postId 순서 [145,143,140,139,142]를 반환한다. EXPLAIN query는 size+1 처리용 limit을 포함할 수 있으므로 SQL과 API page size를 별도 기록한다.

실패와 데이터 보존

  • EXPLAIN ANALYZE reads a different query, page, user or data snapshot → comparison is invalid. · 유지: do not claim performance change.
  • new index changes returned IDs/order → result regression. · 유지: restore disposable experiment index and preserve schema.sql.
  • old foreign key index deleted to simplify plan → out of task scope. · 유지: recreate original FK index before recording final state.

입력 사례

  • Before index plan
  • After V2 candidate
  • No speed claim from small seed
  • API 응답과 plan 결과 보존

개발 과제

  • Same database snapshot and SQL before/after.
  • Copy plan columns key/rows/Extra and ANALYZE actual fields into notes.
  • Compare six IDs and cursor order before/after.
  • legacy:9-2:A의 정확한 GET /api/me/likes?size=5 응답 id와 EXPLAIN의 query limit을 구분한다.

완료 확인

  • EXPLAIN estimate and ANALYZE actual metrics are distinguished.
  • Index presence and preserved FK index checked.
  • Results unchanged and no unsupported performance claim made.
  • API 200의 실제 seed id 순서가 인덱스 전후 유지됨을 확인했다.

선택한 API 계약

GET/api/me/likes?size=5200

C1: HTTP 상태 200이어야 합니다. C1: JSON 경로 $.items[*].postId equals [145,143,140,139,142]이어야 합니다.
