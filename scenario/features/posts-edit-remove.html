전체 교체와 부분 변경으로 내 글 수정하기

board 과정의 PUT 전체 교체와 PATCH 일부 수정 계약을 적용해 작성자·태그·기본값을 확인한다.

이번에 할 일

자기 글 title A→B 수정, PUT 전체 본문 교체, PATCH title만 변경을 비교한다. 과정 board D05-2에 포함된 DELETE까지 실행해 soft delete 204와 후속 상세 404를 확인한다.

시작 조건

  • spec-board recipe board:post-replace:normal, board:post-patch:normal을 사용하고 실제 postId를 받는다.
  • Kim 소유 글과 Park 소유 글을 분리한다.

사용자 시나리오

  1. 시작
    post title A, content C, tags=[java]이며 Kim 소유.
    행동
    PUT /api/posts/{postId}에 title B/content D/tags=[spring] 전송; 뒤에 PATCH {title:E}.
    결과
    각 요청 200. PUT은 전체 필드를 반영하고 PATCH는 E로 title만 변경, content D와 tags[spring] 유지.
    이후
    PUT에서 tags를 생략한 별도 요청은 tags=[]로 교체되는지 확인하고 실패 body/권한에서 row 불변을 확인.

데이터와 이유

Kim post의 title/content/tags
PUT 교체와 PATCH 보존 필드를 분리한다.
Park owner id와 Kim token
작성자 불일치 403에서 타인 row가 유지되는지 확인한다.
post_tag의 java/spring 관계
PUT tag replacement 뒤 연결 row와 공유 tag 보존을 확인한다.

업무 정책

  • PUT /api/posts/{postId}는 title/content 필수, tags 생략은 빈 목록, visibility는 기본 PUBLIC이며 author/board 변경 필드는 받지 않는다.
  • PATCH는 전달한 non-null 필드만 수정하며 boardSlug·authorId를 임의로 받지 않는다.
  • 대상 존재 및 작성자 권한은 source 규칙으로 판정한다. DB 실패는 부분 필드 변경을 남기지 않는다.
  • course D05-2 source unit에는 DELETE /api/posts/{postId}도 포함한다. 작성자는 204, 후속 GET은 404이며 soft delete다. title/body 수정 stage에 함께 매핑된 이 source endpoint도 이 board variant에서 확인한다.

입력과 출력

  • PUT body title=B,content=D,tags=[spring]; PATCH body {title:E}.
  • 비정상 body PATCH {title:F,tags:["", "valid"]}; Park token; id 999999.
  • board exact recipe: DELETE /api/posts/{postId}; 성공 뒤 GET 같은 id.

성공 기준

  • PUT recipe: 200 상세 응답, title=B/content=D/tags=[spring].
  • PATCH recipe: 200, title=E/content=D/tags=[spring].
  • PUT tags 생략 시 빈 배열로 기존 tag가 제거되는 계약 확인.
  • board D05-2 DELETE /api/posts/{postId} → 204; 후속 GET → 404.

실패와 데이터 보존

  • PATCH의 tag 검증이 실패 → 400 validation 오류. · 유지: 요청 전 title/content/tags 모두 유지.
  • Park token이 Kim 글을 수정 → 403. · 유지: Kim post와 java/spring 연결 모두 유지.
  • postId 999999 또는 token 누락 → 404 또는 401. · 유지: 대상 목록과 다른 글 모두 변화 없음.
  • Park token deletes Kim post or id missing → 403 또는 404 source contract. · 유지: post state and tag associations remain unchanged.

입력 사례

  • PUT 뒤 PATCH
  • PATCH 뒤쪽 필드 검증 실패
  • 다른 작성자 token
  • Course board soft delete

개발 과제

  • normal recipe와 source error cases를 호출하고 actual id를 사용한다.
  • GET 상세와 post_tag query를 수정 전/후 비교한다.
  • validation 실패 후 DB 값을 새 연결에서 읽어 rollback을 확인한다.
  • D05-2 board delete recipe도 수행해 PUT/PATCH와 별개 status 및 상세 후속 결과를 기록한다.

완료 확인

  • PUT 기본값과 PATCH 누락 필드 보존이 분리 확인됐다.
  • Kim/Park 권한 오류와 없는 id가 기대 status를 냈다.
  • 실패 후 title/content/tags DB 값이 그대로였다.
  • course source가 포함한 DELETE 204·GET 404를 board variant에서 확인했다.
