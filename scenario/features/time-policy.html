서버가 실행되는 시각에 따라 달라지는 쿠폰·출석 판정을 같은 조건으로 재현합니다.

이번에 할 일

만료 직전·경계·직후를 고정 Clock으로 실행하고 두 정책의 결과와 도입 비용을 비교하세요.

시작 조건

  • 현재 쿠폰 유효 기간·사용 가능 조건을 원본 계약에서 확인합니다.
  • 현재 정책의 만료 비교가 경계 시각을 포함하는지 먼저 명세에 적고, 임의로 바꾸지 않습니다.

사용자 시나리오

  1. 시작
    같은 회원·쿠폰·장바구니를 준비하고 기준 시각만 만료 직전·경계·직후로 바꿉니다.
    행동
    고정 Clock으로 세 시각을 판정하고, 동일 입력에 정책 두 안을 적용합니다.
    결과
    시각을 바꿀 때만 유효 여부가 명세대로 달라지고, 정책별 금액 차이를 실제 값으로 설명합니다.
    이후
    서버 시간대와 사용자 표시 시각이 달라도 같은 만료 순간을 가리키며 자정 전후 출석 포인트 중복이 없어야 합니다.

데이터와 이유

기준 시각·시간대
테스트 재현과 사용자 표시를 구분합니다.
쿠폰 만료·출석 업무 키
유효 여부와 하루 한 번의 범위를 판정합니다.

업무 정책

  • board 기본 할인은 10%입니다. 다른 정책 비교를 기본 정책 변경으로 자동 채택하지 않습니다.
  • 테스트에서 실제 시스템 시각에 기대지 않습니다.
  • 인터페이스 분리안과 조건문 유지안의 비용을 함께 적습니다.

입력과 출력

  • 동일 쿠폰·회원·구매 입력, 고정 Clock의 세 시각, 자정 직전·직후의 출석 요청

성공 기준

  • 시각을 바꿀 때만 유효 여부가 명세대로 달라지고, 정책별 금액 차이를 실제 값으로 설명합니다.

실패와 데이터 보존

  • 시각이 경계에 걸림 → 미리 적은 포함·제외 규칙과 다른 판정은 실패입니다. · 유지: 시간대 표시 차이로 추가 적립이나 이미 만료된 쿠폰 사용이 생기면 안 됩니다.

입력 사례

  • 같은 대상의 전후 비교

개발 과제

    • `TokenIssuer`: TTL이 null이거나 0 이하면 `IllegalArgumentException`. 만료 시각 = 발급 시각 + TTL. **지금이 만료 시각과 같거나 지났으면 만료**다(JWT `exp`와 같다). 남은 시간은 이미 지났으면 `Duration.ZERO`(음수를 내주지 않는다).
    • `MidnightTtl.untilNextKstMidnight`: 시계의 zone과 상관없이 KST로 다음 자정까지 센다. KST 23:59:59이면 1초, KST 00:00:00 정각이면 24시간이다.
    • `발급_시각은_주입한_시계에서_읽고_만료_시각은_발급_시각에_TTL을_더한다`
    • `만료_시각_1초_전에는_유효하고_만료_시각_정각부터는_만료다`
    • `남은_시간은_만료까지의_Duration이고_이미_지났으면_0이다`
    • `TTL이_null이거나_0이거나_음수이면_거절한다`
    • `KST_자정_1초_전이면_다음_자정까지_1초가_남는다`
    • `KST_자정_정각이면_새_날이_시작됐으므로_24시간이_남는다`
    • `UTC_자정은_KST_오전_9시라_KST_자정까지_15시간이_남는다`
    • `시계의_zone이_무엇이든_같은_순간이면_같은_TTL이다` (UTC·뉴욕·서울 시계)
