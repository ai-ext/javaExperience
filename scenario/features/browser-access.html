실제 요청과 사전 요청을 함께 허용하기

허용된 브라우저 출처의 실제 요청과 preflight를 함께 처리하고 차단 원인을 네트워크 증거로 구분합니다.

이번에 할 일

기존 출처·새 출처·허용 목록 밖 출처를 비교해 OPTIONS preflight와 실제 POST가 의도한 범위만 통과하도록 설정하고 재현 기록을 남기세요.

시작 조건

  • local board 서버와 별도 브라우저 출처를 사용한다. D03 허용 출처 `http://localhost:3000`과 B12의 `http://127.0.0.1:8765`를 구분한다.
  • 실제 POST는 이미 발급한 USER Bearer token과 유효한 JSON body를 사용한다. OPTIONS preflight는 브라우저가 보낼 Authorization/Content-Type 헤더를 요청한다.

사용자 시나리오

  1. 시작
    허용 출처 `http://localhost:3000`, 추가하려는 출처 `http://127.0.0.1:8765`, 비허용 출처 `http://evil.example`의 세 브라우저 탭을 준비한다. 게시글 생성 전 상태를 기록한다.
    행동
    각 출처에서 OPTIONS /api/posts 또는 /api/auth/login에 Origin, Access-Control-Request-Method: POST, Access-Control-Request-Headers: authorization,content-type를 넣는다. 허용된 출처에서는 이어 실제 POST를 보낸다.
    결과
    원문 계약상 localhost:3000 preflight는 200과 `Access-Control-Allow-Origin: http://localhost:3000`; evil.example은 403이다. B12의 새 출처는 설정 후 OPTIONS 200과 허용 origin 헤더를 받고 실제 POST까지 브라우저에서 완료한다.
    이후
    Network 탭의 OPTIONS와 POST 상태·응답 헤더를 각각 기록한다. 허용된 POST만 글을 201로 만들고 비허용 출처 거부는 글 수를 바꾸지 않는다.

데이터와 이유

Origin 출처 세 개
기존 허용·추가 허용·차단 대상을 나란히 비교해 단일 출처 성공만으로 CORS 정책을 과개방하지 않게 한다.
Access-Control-Request-Method/Headers
브라우저 preflight가 실제 POST와 Authorization·Content-Type 전송을 요청했는지 확인한다.
Access-Control-Allow-Origin·상태
OPTIONS 응답이 허용 출처만 정확히 반영하는지 관찰한다.
게시글 생성 수
preflight 차단과 실제 POST 성공을 데이터 변경으로 구별한다.

업무 정책

  • CORS는 브라우저의 교차 출처 응답 읽기 정책이며 인증이나 API 권한 검사를 대체하지 않습니다.
  • 허용 출처 목록에 없는 Origin을 무조건 반사해 허용하지 않습니다. 새 출처와 목록 밖 출처를 각각 비교합니다.
  • B12는 선택 지원 티켓입니다. 기존 mandatory/practice/optional 구분을 유지하고 재현·수정 기록을 티켓 제출물로 남깁니다. B12는 D14의 선택 Security 후보 티켓이며 선택하지 않은 경우 별도 티켓 완료를 표시하지 않습니다.
  • 원문 완료 기준: `OPTIONS /api/auth/login` + `Origin: http://localhost:3000` → 200, `Access-Control-Allow-Origin: http://localhost:3000`
  • 원문 완료 기준: `Origin: http://evil.example` → 403
  • 원문 완료 기준: 브라우저(`http://127.0.0.1:8765`)에서 `POST /api/auth/login` → 200
  • 원문 완료 기준: 개발자 도구 Network 탭에서 실패한 요청과 그 상태 코드·응답 헤더를 근거로 남긴다(서버 에러 로그 없음)
  • 원문 완료 기준: `OPTIONS /api/posts` + `Origin: http://127.0.0.1:8765` → 200, `Access-Control-Allow-Origin` 포함
  • 원문 완료 기준: 원인 서술: 기존 출처와 새 출처의 결과가 왜 다른가, 그리고 그렇게 판단한 관찰 근거(Network 탭·응답 헤더·서버 설정)
  • 원문 완료 기준: 재현 테스트: 새·기존·목록에 없는 출처로 preflight(`OPTIONS` + `Origin` + `Access-Control-Request-Method`/`-Headers`)를 보내 상태 코드와 허용 헤더를 단언하는 테스트(결함 상태에서 실패 → 수정 후 통과)
  • 원문 완료 기준: 수정 diff

입력과 출력

  • OPTIONS 요청에 `Origin`, `Access-Control-Request-Method: POST`, `Access-Control-Request-Headers: authorization,content-type`를 보낸다.
  • 허용 출처 사례: `http://localhost:3000`; B12 추가 출처: `http://127.0.0.1:8765`; 차단 사례: `http://evil.example`.
  • 실제 POST는 Authorization Bearer token과 `{"title":"CORS 확인","content":"허용된 출처 요청","tags":[]}`를 사용한다.

성공 기준

  • 허용 localhost:3000의 OPTIONS /api/auth/login → 200, `Access-Control-Allow-Origin: http://localhost:3000`.
  • 비허용 Origin `http://evil.example` → 403; B12 추가 허용 Origin은 OPTIONS /api/posts → 200 및 allow-origin 포함.
  • 브라우저에서 허용 Origin의 POST /api/posts → 201. 기존/추가/비허용 출처별 Network 요청과 게시글 생성 여부를 구분한다.

실패와 데이터 보존

  • Origin이 `http://evil.example`이고 OPTIONS preflight를 보냄 → 403으로 거부하며 응답에 그 Origin을 반사해 허용하지 않는다. · 유지: 실제 POST가 이어지지 않고 새 게시글이 생성되지 않는다.
  • 허용 Origin preflight는 성공했으나 실제 POST 인증 token이 없음 → CORS 허용과 별개로 API는 401이다. · 유지: 게시글은 생성되지 않는다.

입력 사례

  • 허용 출처의 브라우저 생성
  • 목록 밖 출처 차단

개발 과제

  • Security가 사용하는 CorsConfigurationSource와 실제 허용 origin 목록의 단일 기준을 찾는다.
  • 세 Origin에 대해 OPTIONS 상태와 허용 헤더를 비교하고 기존/추가 출처를 명세 목록에만 추가한다.
  • 브라우저에서 OPTIONS 성공과 실제 API 401/201을 따로 관찰해 인증과 CORS를 구분한다.

완료 확인

  • localhost:3000의 200 및 evil.example의 403을 확인했다.
  • B12 추가 출처의 preflight 200/allow-origin과 브라우저 POST 201을 Network 증거로 남겼다.
  • CORS 실패 요청에서 게시글이 생성되지 않고 token 없는 실제 POST는 401인 것을 분리해 기록했다.
