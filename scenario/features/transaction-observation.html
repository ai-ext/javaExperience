같은 행의 flush·commit·rollback 비교하기

Java 객체를 바꾼 것, SQL을 보낸 것, 다른 연결에서도 저장이 보이는 것을 나누어 확인합니다.

이번에 할 일

동일한 글 한 행으로 commit 경로와 flush 후 rollback 경로를 각각 실행하고 시간표를 남기세요.

시작 조건

  • 현재 글 id와 초기 값을 새 DB 연결에서 기록합니다.
  • 실험을 독립 트랜잭션으로 나누고 비교용 DB 클라이언트의 자동 커밋 상태를 확인합니다.

사용자 시나리오

  1. 시작
    글 제목을 A에서 B로 바꿉니다. Java 객체·트랜잭션 내부 조회·외부 연결은 서로 다른 관찰자입니다.
    행동
    변경 전→객체 변경→flush→commit 또는 rollback→종료 후 새 연결 SELECT 순서로 값을 기록합니다.
    결과
    commit 경로에서만 종료 후 새 연결의 값이 B가 되고 rollback 경로의 DB는 A를 유지합니다.
    이후
    객체에 B가 남아 있어도 rollback한 DB에 저장됐다고 판단하지 않으며 실제 SQL 시점을 기록합니다.

데이터와 이유

행 id와 초기·변경 값
각 관찰자가 같은 데이터를 보고 있는지 확인합니다.
연결·트랜잭션·SQL 시각
flush와 다른 연결의 가시성을 구별합니다.

업무 정책

  • flush는 commit이 아닙니다.
  • 테스트를 감싼 트랜잭션과 프록시 경유 여부를 기록합니다.
  • 이전 D05/D07 증거를 재사용해도 새 경계 한 개를 실행합니다.

입력과 출력

  • 같은 행 id, 초기 제목 A와 변경 제목 B, commit·rollback 두 종료 방식

성공 기준

  • commit 경로에서만 종료 후 새 연결의 값이 B가 되고 rollback 경로의 DB는 A를 유지합니다.

실패와 데이터 보존

  • flush 뒤 예외로 rollback → 외부 새 연결에서는 원래 값 A가 보여야 합니다. · 유지: 기존 행·태그 연결이 부분 변경으로 남지 않아야 합니다.

입력 사례

  • 같은 대상의 전후 비교

개발 과제

  • 동일한 글 한 행으로 commit 경로와 flush 후 rollback 경로를 각각 실행하고 시간표를 남기세요.

완료 확인

  • 같은 행의 객체 값·변경 감지 전후 SQL·트랜잭션 안 조회·별도 연결 조회 값을 시간표로 남긴다.
  • flush 뒤 rollback 경로와 commit 경로를 각각 실행하고 종료 후 새 연결의 값을 확인한다. flush를 commit으로 설명하지 않는다.
  • 기존 D05·D07 관찰을 재사용했다면 조건·실행일·증거를 링크하고 새 경계 한 개를 추가한다.
  • 객체 값이 남아 있어도 DB에 저장됐다고 주장하지 않으며 프록시 호출/테스트 트랜잭션의 관찰 제한을 명시한다.
