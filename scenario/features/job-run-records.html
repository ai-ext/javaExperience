실패·재실행을 실행 이력으로 구분하기

각 배치 실행은 기준일·trigger·status·처리량·오류를 기록하고 FAILED 기준일만 재시도한다.

이번에 할 일

job_run 이력 조회, 실패 기준 재시도, 성공 상태 기록을 구현한다.

시작 조건

  • 학습용 DB(`practice`) — 앱을 `practice` 프로파일로 띄운다.
  • practice V65 시드와 job_run API를 사용; weekly-ranking은 기준일 2026-09-21 실패.

사용자 시나리오

  1. 시작
    배치 실행 중 한 기준일의 마지막 실행이 FAILED로 기록됐습니다.
    행동
    운영자가 실행 이력을 조회하고 해당 실패 기준일만 재시도합니다.
    결과
    새 실행은 RETRY로 구분되고 멱등한 대상 배치의 성공/실패와 오류 요약이 이력에 남습니다.
    이후
    성공한 날짜를 임의 재시도하지 않고 실패 재시도도 기존 이력과 다른 날짜 스냅샷을 덮어쓰지 않습니다.

데이터와 이유

job_run(job_name,run_date,trigger_type,status,processed,error)
기준일별 마지막 실행과 재시도 행 상태를 비교한다.
weekly-ranking run_date=2026-09-21
원문 시드의 실패 job과 retry 기준일이다.

업무 정책

  • job_name/run_date별 실행을 RUNNING/SUCCESS/FAILED로 기록하고 trigger_type은 SCHEDULED/MANUAL/RETRY를 구분합니다. started_at/finished_at은 실제 벽시계, run_date는 업무 기준일입니다.
  • 실패 이유는 예외 이름+메시지 최대 500자입니다. 예약 발행 reference_at은 원래 기준 시각을 보관해 재시도에도 같은 값을 사용합니다.
  • 해당 업무/기준일의 마지막 실행이 FAILED일 때만 재시도합니다. 성공한 날짜와 예전 실패 이력은 그대로 보존하고 새 RETRY 실행을 추가합니다. 대상 배치의 멱등성도 검증합니다.
