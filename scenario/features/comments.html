댓글 작성·목록·삭제 연결하기

course D05의 댓글 관계 테이블과 작성·목록·삭제 API를 연결해 글별 댓글의 안정적 순서를 확인한다.

이번에 할 일

글 3에 댓글을 작성하고 목록·삭제를 실행해 생성한 commentId와 postId 관계를 검증한다.

시작 조건

  • spec-board course recipe를 선택한다. 글과 회원 id는 실제 API 응답/fixture에서 확인한다.
  • 요구된 DB 설계는 직접 선택하되 comment가 없는 글과 여러 댓글이 있는 글을 준비한다.

사용자 시나리오

  1. 시작
    게시글 3에는 댓글이 없고, 인증된 회원 Kim이 로그인했다.
    행동
    POST /api/posts/3/comments에 content="첫 댓글 A" 작성, GET 목록, commentId를 DELETE.
    결과
    POST 201; GET 200에서 새 댓글과 author가 보이고 DELETE 204 이후 목록에서 사라진다.
    이후
    없는 post 999999/invalid token으로 작성 시도하고 comment row가 생성되지 않는지 확인.

데이터와 이유

comments.post_id/author_id/parent_id/content
글·회원·부모 관계와 응답 DTO의 일치 확인.
글 3 및 댓글이 없는 글
빈 목록과 댓글 작성 후 목록을 비교.
commentId Location
응답으로 얻은 자원 id로 삭제 대상을 지정.

업무 정책

  • course D05-3/4가 정한 안정적 댓글 순서와 relationship은 유지한다.
  • 작성은 토큰 주체 author를 사용한다. 댓글 없는 응답은 빈 배열 []이며 만들어낸 placeholder를 추가하지 않는다.
  • 삭제는 course API recipe의 DELETE /api/comments/{commentId} contract를 따른다.

입력과 출력

  • POST /api/posts/3/comments JSON {content:"첫 댓글 A"}.
  • GET /api/posts/3/comments.
  • DELETE /api/comments/{actual comment id}.
  • 실패: 잘못된 content, postId 999999, token 없음.

성공 기준

  • POST 201 및 실제 commentId Location/응답.
  • GET 200에서 내용·작성자·순서가 저장 상태와 일치.
  • DELETE 204 뒤 같은 댓글이 삭제 정책대로 목록에서 빠진다.

실패와 데이터 보존

  • 본문이 비었거나 규칙 밖 → 400 validation. · 유지: 댓글 row 수와 대상 글 상태 유지.
  • 없는 게시글에 comment 작성 → 404. · 유지: comment row 추가 없음.
  • 토큰 없이 작성/삭제 → 401. · 유지: 기존 comment와 작성자 불변.

입력 사례

  • 댓글 작성 후 조회
  • 없는 글 작성
  • 댓글 삭제

개발 과제

  • board 댓글 recipe를 project spec-board에서 요청하고 실제 id를 캡처한다.
  • GET 응답 순서를 생성 시각·DB row와 비교한다.
  • 실패 요청 전후 댓글 수를 읽는다.

완료 확인

  • 작성201·목록200·삭제204가 course recipe와 일치한다.
  • 빈 목록 및 post/member FK 정책을 확인했다.
  • 실패 후 댓글 데이터가 보존됐다.

댓글 작성·목록·삭제 연결하기

    
    

    
community 5-0~5-3 댓글 작성·1단계 답글·목록 트리·삭제의 단계별 정책을 연결한다.

    
이번에 할 일
post 11의 top-level comment와 한 단계 reply를 작성하고 차단·삭제 규칙에 맞는 tree를 조회한 뒤 본인/타인의 삭제를 검사한다.

    
시작 조건
  • 원문 seed: post 11, top comments id 1 박디비 및 id 3 한차단; id2/id5 replies, id4/id6 deleted.
  • 김자바 tok-kimjava, 박디비 tok-park, 한차단 fixture의 block 관계를 확인한다.

    
사용자 시나리오
  1. 시작
    GET /api/posts/11/comments의 source fixture 결과와 김자바 viewer의 block 관계를 기록한다.
    행동
    김자바가 post 11에 content="[채점] 댓글 A" 작성 후 parentId=1 답글을 남기고 GET 목록을 호출한다.
    결과
    POST 정상은 201; 5-3 목록은 시간순 top-level + replies tree. 삭제된 top-level은 보이는 reply가 있으면 placeholder로 남고 차단된 작성자의 댓글 및 해당 top subtree는 빠진다.
    이후
    parentId=2(이미 답글) 요청은 400, 없는 부모/글은 404, 잘못된 body·비인증은 source recipe의 400/401; comment 상태는 기존값 유지.

    
데이터와 이유
post 11 top comment id1 박디비 / id3 한차단
원문 응답의 top-level 순서와 viewer block filter를 비교.
id2/id5 reply 및 id4/id6 deleted comment
reply nesting·삭제 placeholder·숨김 답글 정책 검증.
김자바/박디비/한차단의 작성자·차단 관계
조회 필터 및 delete owner check.
parent_id·deleted_at·edited flag
트리 조립과 soft-delete/수정표시 결과 보관.

    
업무 정책
  • 5-2는 답글의 답글을 허용하지 않는다. parentId가 이미 reply이면 400, 없거나 다른 글의 부모면 404로 구분한다.
  • 5-3 목록은 top-level 시간순, replies는 부모 아래에 둔다. 삭제 top-level은 author=null/content="삭제된 댓글입니다"/deleted=true로 남길 수 있고 visible reply가 없으면 제거한다. 삭제/차단 reply는 DTO에 만들지 않는다.
  • viewer와 block 관계인 회원 댓글은 제외한다. top-level이 차단되면 그 아래 reply도 제외한다.
  • 댓글 작성/삭제는 원문에서 요구한 post/comment lock 순서 및 transaction을 지키며 삭제된 글에 새 reply를 만들지 않는다.

    
입력과 출력
  • POST /api/posts/11/comments {content:"[채점] 댓글 A"}; 답글 {content:"답글 A",parentId:1}.
  • 잘못된 nested reply {content:"답글의 답글",parentId:2}.
  • GET /api/posts/11/comments as anonymous/Kim.
  • DELETE own comment; then delete Park/other user comment with Kim token.

    
성공 기준
  • POST 정상 댓글/답글 → 201.
  • GET 공개 글 댓글 → 200; 5-3 tree DTO는 chronological, replies nested.
  • 작성자 삭제 → source 5-3의 soft-delete/응답 contract; public tree는 삭제 marker로 표시.

    
실패와 데이터 보존
  • parentId=2가 이미 답글 → 400. · 유지: 댓글 수와 parent tree 유지.
  • parent id가 없거나 다른 post 소속, post id 없음/삭제/차단된 글 → 404. · 유지: 새 comment row 없음.
  • 토큰 없음 또는 잘못된 request JSON/content → 401 또는 400. · 유지: 기존 comment row와 post comment_count 유지.
  • 김자바가 박디비 댓글 삭제 → 403. · 유지: comment.deleted_at과 comment_count 그대로.

    
입력 사례
  • post 11 top-level 댓글과 reply
  • reply의 reply 금지
  • 차단 viewer tree

    
개발 과제
  • POST case의 status/body/parent id를 확인하고 top/reply를 각각 재조회한다.
  • 익명과 김자바 응답의 comment id 집합을 비교한다.
  • soft delete 후 API tree와 comment_count 및 deleted_at을 대조한다.

    
완료 확인
  • top-level/reply parent 제약과 다른 post parent 거절을 확인했다.
  • 삭제·차단 댓글이 원문 tree 표시 규칙을 따른다.
  • 401/400/403/404 이후 기존 댓글·comment_count가 바뀌지 않았다.

댓글을 수정하고 수정됨 표시하기

    
    

    
12-1 댓글 수정과 edited 표시를 연결하고 실제 내용 변경 시점과 본문 동일 요청을 구별한다.

    
이번에 할 일
작성자가 content A→B 수정 후 같은 내용 재전송, 댓글 목록 edited field, 1000/1001 경계 및 타인·없는 댓글 오류를 검사한다.

    
시작 조건
  • comment 11 등 수정 가능한 top/reply를 준비하고 본인/타인 token을 구분한다.
  • V30 migration으로 edited_at이 추가됐는지 기록한다. 기존 댓글 edited_at은 null이다.

    
사용자 시나리오
  1. 시작
    comment 11 content="원문 A", edited_at=null.
    행동
    PATCH /api/comments/11 {content:"수정 본문 B"}; 이어 같은 B, 마지막 1001자 content를 보낸다.
    결과
    변경 요청 200 edited=true/editedAt 존재; 동일 내용 200 edited=false/editedAt 기존 값 유지; 1001자는 400.
    이후
    GET /api/posts/{postId}/comments에서 최상위/답글 edited 표시를 확인한다. 삭제 placeholder는 edited=false.

    
데이터와 이유
comment.content 및 edited_at
실제 내용 변경과 단순 재전송을 구분.
작성자 id와 viewer token
수정 가능한 주체인지 판정.
V30 migration history
기존 row의 edited_at null 초기상태 보존 확인.

    
업무 정책
  • PATCH /api/comments/{id}; content trim 전후 규칙은 5-1과 같고 1~1000자, 1001자는 400.
  • 없는/삭제/볼 수 없는 글의 comment는 404가 403보다 먼저다. 다른 작성자 댓글은 403, token 없음은 401.
  • 내용이 같은 요청은 edited=false로 기존 timestamp를 바꾸지 않는다. 목록의 삭제 placeholder edited=false, 나머지 필드는 유지.

    
입력과 출력
  • 정상 body {content:"수정 본문 B"}; 동일 body 재요청.
  • 경계 content 정확히 1000자와 1001자.
  • 실패: {content:123}, 빈 body, other author token, id 999999.

    
성공 기준
  • 본문 실제 변경 PATCH → 200, edited=true와 editedAt.
  • 같은 내용 PATCH → 200, edited=false; edited_at unchanged.
  • GET tree의 해당 top/reply edited 값이 true, 삭제 marker는 false.

    
실패와 데이터 보존
  • content 1001자·공백만·숫자/array JSON → 400 errors.content 또는 malformed JSON 400. · 유지: content 및 edited_at 모두 기존 값 유지.
  • 다른 회원이 수정 가능한 댓글 수정 → 403. · 유지: comment content와 edited_at 불변.
  • 없음/삭제/볼 수 없는 글의 댓글 또는 token 없음 → 404 또는 401. · 유지: comment와 timestamp 그대로.

    
입력 사례
  • 내용 변경
  • 같은 내용 재전송
  • 경계 밖 길이

    
개발 과제
  • 수정 전후 GET tree와 DB edited_at을 함께 읽는다.
  • 수정 전/같은 값/다른 값 요청을 분리한다.
  • migration version과 기존 null row, 삭제 placeholder의 edited를 확인한다.

    
완료 확인
  • 변경/동일/실패에서 content·edited_at 값을 기록했다.
  • 1000/1001자 및 JSON 타입 검증을 실행했다.
  • 404-before-403과 list edited field를 확인했다.

댓글 작성·목록·삭제 연결하기

    
    

    
spec-board 10-9 댓글 API의 wrapper·답글 트리·soft delete 및 접근 판정 순서를 검증한다.

    
이번에 할 일
post 28에 top-level [채점] 첫 댓글을 만들고 reply를 확인한 뒤 parent reply 42 등록 실패와 본인 soft delete를 실행한다.

    
시작 조건
  • 10-6에 따라 접근 가능한 공개 post 28, spec-board JWT 회원 이스프링 id2를 준비한다.
  • 10-9 route: POST/GET /api/v1/posts/{postId}/comments, DELETE /api/v1/comments/{commentId}.

    
사용자 시나리오
  1. 시작
    post 28 공개, comment id41 top-level과 id42 reply를 별도 생성/캡처한다.
    행동
    POST top-level content="[채점] 첫 댓글" 후 GET 목록, parentId=42로 nested reply 시도, id41을 소유자 삭제.
    결과
    작성 201 Location /api/v1/comments/{id}; 목록 200 트리; parent가 reply인 요청 400; 삭제 200 ApiResponse.data=null.
    이후
    삭제 후 목록에서 id41 자리에는 "삭제된 댓글입니다"가 있고 김자바 reply는 남는다. 다른 회원 delete는 403, 삭제된 comment는 404.

    
데이터와 이유
comments(post_id=28,author_id=2,parent_id,content)
요청·트리·소프트삭제가 DB row로 이어지는지 확인.
comment 41 top-level / comment 42 reply
parent validation과 deleted-parent placeholder를 구체적으로 검증.
ApiResponse wrapper
10장 201/200/400 body envelope를 process-course raw JSON과 분리.

    
업무 정책
  • 댓글 content는 trim 뒤 1~500자. parentId는 같은 글의 top-level 댓글만 허용하고 reply-of-reply는 400.
  • 없는/삭제된/남의 비공개 post는 404. 댓글 삭제는 404(없음/이미 삭제/글 접근불가)를 403(남의 댓글)보다 먼저 확인한다.
  • 삭제는 deleted_at soft marker이며 답글을 cascade delete하지 않는다. 10장 DELETE 성공은 200 data:null이다.

    
입력과 출력
  • POST /api/v1/posts/28/comments {content:"[채점] 첫 댓글"}.
  • reply {content:"답글 A",parentId:<top comment id>}; failure parentId=42.
  • GET list; DELETE /api/v1/comments/{own id}.

    
성공 기준
  • 작성 201 + Location + data comment fields.
  • GET 200 data는 detail과 같은 tree array.
  • own delete 200 {status:200,message:"OK",data:null}; 삭제 부모의 placeholder 아래 valid reply 유지.

    
실패와 데이터 보존
  • parentId=42가 reply → 400 validation/common envelope. · 유지: comment row·parent-child 관계 변화 없음.
  • 글 없음·삭제·비공개, 댓글 없음/이미 삭제 → 404, 남의 댓글이면 403. · 유지: 삭제 marker와 comment data unchanged.
  • token 없음 → 401. · 유지: comment row 및 comment_count 불변.

    
입력 사례
  • 10장 top-level 작성
  • reply의 reply 실패
  • top-level 삭제 후 tree

    
개발 과제
  • spec-board recipes를 실행하고 status·ApiResponse body·Location을 함께 적는다.
  • 삭제된 부모/답글 tree를 재조회한다.
  • 404/403 순서를 보이기 위해 없는/지운/볼 수 없는 글과 타인 comment를 각각 준비한다.

    
완료 확인
  • 작성201·목록200·삭제200 wrapper를 확인했다.
  • parent reply 400 및 404-before-403 정책을 확인했다.
