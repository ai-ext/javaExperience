캐시 장애에도 목록을 반환하고 변경 후 갱신하기

Redis 캐시가 정상일 때 빠른 인기글 응답을 제공하고 Redis 장애·글 변경 뒤에도 응답과 결과를 유지합니다.

이번에 할 일

인기글 GET 결과의 TTL과 SQL 호출을 관찰하고 Redis 지연·중단 시 DB 폴백, 글 상태 변경 후 커밋 시점에 맞춘 캐시 무효화를 구현하세요.

시작 조건

  • Redis와 MySQL을 실행하고 ACTIVE 글·좋아요가 있는 fixture를 준비한다. Redis command timeout=500ms, 인기글 TTL=60s를 설정한다.
  • B15/B16은 D14의 선택 Redis 후보 티켓이다. D09의 cache fallback/eviction 작업과 ticket 완료를 섞지 않는다.

사용자 시나리오

  1. 시작
    ACTIVE 인기글 P-101이 DB에 있고 캐시는 비어 있다. Redis는 먼저 정상, 다음은 3초 지연, 마지막은 중지 상태로 바꿔 관찰한다.
    행동
    GET /api/posts/popular를 요청하고 60초 안에 다시 요청해 SQL 로그와 Redis TTL을 확인한다. Redis 지연/중지 중에도 GET을 보내고 POST /api/posts, 글 삭제 또는 관리자 숨김을 성공시킨 뒤 인기글을 재조회한다.
    결과
    첫 GET은 200과 DB 결과, cache TTL은 60 이하; 60초 내 hit에는 목록 SQL이 없다. Redis 3초 지연은 500ms timeout 뒤 DB 폴백으로 GET 200이며 Redis 중지 중 글 작성도 POST 201이다. 커밋 뒤 삭제/숨김된 P-101은 다음 GET의 목록에서 빠진다.
    이후
    DB 글 status와 cache key 삭제 시각을 transaction commit과 로그로 대조한다. rollback된 글 변경은 cache를 미리 지우지 않으며 인기글 응답 계약을 유지한다.

데이터와 이유

ACTIVE 글/좋아요를 포함한 인기 목록
빈 결과만으로 목록 쿼리·캐시 hit·장애 폴백 내용을 확인할 수 없어 실제 P-101 fixture를 둔다.
Redis popular key와 TTL
최초 적재와 60초 이내 재요청의 캐시 hit 여부를 TTL/SQL 로그로 확인한다.
Redis 명령 timeout 500ms
3초 지연이 요청 thread를 500ms보다 오래 붙잡지 않는 경계를 관찰한다.
글 status·commit event·cache eviction
DB 변경이 확정된 뒤에만 캐시를 지워 stale 데이터 재적재를 막는다.

업무 정책

  • 인기글 TTL은 60초, Redis 명령 timeout은 500ms입니다. 캐시 hit이면 60초 안에 다시 조회할 때 목록 SQL이 없어야 합니다.
  • Redis 3초 지연/중단에도 GET /api/posts/popular는 200으로 DB 결과를 반환하고, Redis 중단에도 POST /api/posts는 201이어야 합니다.
  • 글 삭제 응답은 204이며 커밋 뒤 캐시가 갱신되어 숨김·삭제 글은 직후 인기글에서 빠집니다. 롤백된 트랜잭션은 캐시를 지우지 않습니다.
  • B15와 B16은 D14의 연습용 지원 티켓입니다. 티켓 제출물은 각 원문의 등급·체크리스트에 따릅니다. B15·B16은 D14에서 선택하는 Redis 후보 티켓입니다.

입력과 출력

  • GET /api/posts/popular 정상 query는 board recipe의 기본값을 사용하고 200 응답의 items를 확인한다.
  • Redis 정상/3초 지연/중지 세 상태를 분리한다. local compose Redis를 중지한 경우에도 POST /api/posts 요청을 수행한다.
  • 커밋 완료 후 P-101을 삭제(DELETE → 204)하거나 숨김(POST /api/admin/posts/{postId}/hide → 200)하고 GET popular를 재조회한다.

성공 기준

  • GET /api/posts/popular → 200. 최초 miss에서 DB 목록을 읽고 Redis TTL ≤60초; 60초 이내 두 번째 GET에는 목록 SQL이 추가되지 않는다.
  • Redis 3초 지연 시 명령 timeout 500ms 뒤 DB 폴백 GET → 200. Redis 중지 시 POST /api/posts → 201.
  • DELETE /api/posts/{postId} → 204 또는 관리자 hide → 200 후 commit이 끝난 다음 GET popular 200에서 해당 글 제외. rollback transaction이면 cache eviction 없음. B15/B16은 선택 후보 티켓이다.

실패와 데이터 보존

  • Redis가 3초 지연되거나 중지돼 cache read/write가 실패 → GET /api/posts/popular는 DB 폴백으로 200이어야 한다. · 유지: cache 장애를 이유로 글 내용을 500으로 실패시키지 않고 DB의 ACTIVE 목록을 반환한다.
  • hide/delete transaction이 rollback됨 → 변경 이벤트의 AFTER_COMMIT 처리는 실행되지 않는다. · 유지: DB의 기존 ACTIVE status와 이전 cache 값이 유지되어 숨김·삭제가 완료됐다고 표시하지 않는다.
  • 글 변경 commit 전에 cache를 삭제하고 동시 GET이 old row를 다시 적재 → 숨긴 글이 최대 TTL 60초 동안 재노출되는 순서 오류다. · 유지: 이를 정상 완료로 인정하지 않고 transaction commit 후 eviction되도록 고친다.

입력 사례

  • 캐시 hit 확인
  • Redis 장애 fallback과 hide

개발 과제

  • TTL 60초와 command timeout 500ms를 설정하고 최초 miss/hit에서 실제 SQL 및 Redis TTL을 측정한다.
  • cache 오류를 DB read fallback으로 변환하고 글 변경 이벤트를 transaction AFTER_COMMIT에 연결한다.
  • Redis 지연·중지, 정상 캐시, rollback, commit 직후 조회를 각각 재현하고 B15/B16 선택 여부를 기록한다.

완료 확인

  • 첫/재호출 popular 200, 60초 TTL·SQL hit, Redis 지연/중지 시 GET 200 및 POST 201을 확인했다.
  • 삭제 204/hide 200 후 commit된 글은 목록에서 빠지고 rollback 시 cache가 유지되는 순서를 검증했다.
  • B15/B16은 선택 ticket 후보로 유지하고 실제 수행한 경우에만 재현 로그를 붙였다.

만료 순간 동시에 들어온 인기글 조회가 DB 재적재를 한 번만 수행하도록 캐시 stampede를 막습니다.

    
이번에 할 일
TTL 만료 직후 다수의 동시 요청을 재현하고 인기글 응답 계약을 유지하면서 DB 목록 조회가 한 번만 일어나는지 테스트하세요.

    
시작 조건
  • GET /api/posts/popular의 정상 200 응답과 60초 cache TTL이 구현돼 있어야 한다. DB에 ACTIVE 인기글이 여러 건 있는 fixture를 준비한다.
  • E01 고도화는 필수. B15 처리 여부는 선택이다. TTL 만료 순간 동시 호출을 제어할 barrier와 SQL count 관찰을 준비한다.

    
사용자 시나리오
  1. 시작
    Redis popular key의 TTL을 0으로 만들어 만료시킨다. DB popular 조회 결과와 cache 결과 계약은 기존 GET /api/posts/popular를 기준으로 한다.
    행동
    100개 요청 thread를 barrier로 동시에 시작해 GET /api/posts/popular를 호출한다. DB 목록 SELECT 횟수와 각 HTTP 응답의 status/body shape를 수집한다.
    결과
    100개 응답 모두 HTTP 200, 기존 response 형식을 유지하고 cache 재적재를 위한 DB 목록 query는 총 1회다.
    이후
    새 key TTL은 최대 60초로 설정되고 곧바로 GET을 다시 해 cache hit 응답이 같은 목록인지 확인한다. B15를 선택했다면 hide commit 직후 제거도 별도 증거로 둔다.

    
데이터와 이유
만료된 popular cache key
경합 시작 시 모든 thread가 cache miss를 보도록 만료 상태를 고정한다.
100개 동시 GET과 barrier
순차 호출이 아니라 stampede가 발생할 수 있는 실제 동시 시점을 재현한다.
DB 목록 query count
single-flight가 성공해 재적재 쿼리를 단 한 번만 실행했는지 수량으로 판정한다.
100개의 status/body shape
경합 제어가 응답 계약이나 반환 목록을 바꾸지 않았음을 비교한다.

  • TTL 만료 순간 100개 요청에서도 DB 목록 쿼리는 1회여야 합니다. 응답 형식은 기존 GET /api/posts/popular 계약과 같습니다.
  • 단일 JVM 동기화와 여러 인스턴스 분산 조정의 적용 범위를 구분해 선택 근거를 기록합니다. source에 구체 구현이 고정돼 있지 않으므로 알고리즘을 정답처럼 강제하지 않습니다.
  • E01 고도화는 원문 요구에 따라 필수입니다. B15 처리는 선택입니다. 기존 티켓의 상태 구분을 유지합니다.

  • 원문 완료 기준: 순서는 시간(`sleep`)에 맡기지 말고 멈출 자리를 만들어 고정한다. 모든 대기에 상한을 둔다.

입력과 출력
  • 실제 API는 GET /api/posts/popular, body 없음이며 기존 query/response 계약을 변경하지 않는다.
  • TTL 만료 후 100개 동시 요청을 barrier로 동시에 발사한다. 별도 seed 상태와 전체 DB query count를 관찰한다.
  • E01 제출물은 설계 메모·재현 테스트·수정 diff 모두 필요하다. B15는 선택 ticket이다.

    
성공 기준
  • 100개 GET /api/posts/popular이 모두 200이고 response field/정렬이 기존 recipe와 같다.
  • 만료 순간 DB 목록 SELECT는 1회이며 재적재 뒤 key TTL ≤60초; 다음 GET은 캐시 hit다.
  • E01 설계 메모·테스트·diff를 제출한다. B15를 선택하지 않았으면 B15 ticket 완료를 표시하지 않는다.

    
실패와 데이터 보존
  • TTL 만료 때 100개 GET이 각자 cache miss를 보고 DB를 조회 → DB 목록 query count가 100 또는 1보다 큰 수로 측정되어 E01 기준 실패다. · 유지: 응답 형식을 바꾸거나 stale/partial 목록을 반환해 쿼리 수만 줄인 것으로 처리하지 않는다.
  • 동시 요청 하나라도 500/비정상 JSON/다른 response field를 반환 → 기존 GET /api/posts/popular 계약을 지키지 못한 실패다. · 유지: 이미 정상 사용자에게 제공하는 response schema와 목록 의미를 보존한다.

    
입력 사례
  • TTL 만료 경합 100건
  • 재생성 직후 재조회

    
개발 과제
  • single-flight/JVM lock 또는 source-compatible coordination 방법을 선택하고 instance 수 한계를 설계 메모에 적는다.
  • 100 worker barrier 테스트와 DB query counter를 설정해 cache miss 경합을 계량한다.
  • response contract, TTL, E01 제출물, 선택 B15 수행 여부를 각각 기록한다.

    
완료 확인
  • TTL 만료 순간 100건 동시 GET에서 100개 200과 DB query 정확히 1회를 확인했다.
  • 재생성 TTL ≤60초와 후속 cache hit, 기존 response 형식 보존을 확인했다.
  • E01 필수 산출물을 작성했고 B15는 실행 여부와 무관하게 선택 등급을 유지했다.

    • `findByEmail`의 반환 타입을 `Optional<Member>`로 바꾼다. 그러면 호출부가 컴파일 에러로 바뀐다. 이 에러가 "없는 경우를 처리하지 않은 곳" 목록이다.
    • 호출부를 `findByEmail(email).map(…).orElse(…)`로 고친다. `isPresent()` + `get()`은 null 검사를 이름만 바꾼 것이므로 쓰지 않는다.
    • 특성화(값이 있는 경우. 바꾸기 전에도 통과하고, 바꾼 뒤에도 그대로 통과해야 한다)
    • `특성화_내역이_있는_회원은_닉네임과_합계를_보여_준다`
    • `특성화_없는_회원이면_회원_없음이다`
    • `특성화_합계는_적립과_사용을_더한_값이다`
    • 호출부(지금은 NPE로 실패한다)
    • `내역이_없는_회원도_NPE_없이_0P를_보여_준다`
    • `없는_회원이나_내역이_없는_회원의_합계는_NPE_없이_0이다`
    • 저장소(지금은 실패한다)
    • `findByEmail의_반환_타입은_Optional_Member다`
    • `findByEmail은_있으면_값이_든_Optional_없으면_빈_Optional이다`
    • `findHistories는_내역이_없으면_null이_아니라_빈_목록이다`
