같은 트랜잭션의 JPA 쓰기와 SQL 읽기 비교하기

10-12 JPA write와 MyBatis read가 같은 transaction/connection에서 flush 전후에 언제 보이는지 실제 SQL과 응답으로 확인한다.

이번에 할 일

POST/PUT 뒤 MyBatis listItem이 새 값을 반환하는지, flush 없는 경로는 이전 값이 보이는지, rollback/별도 connection은 다른 시점인지 구분한다.

시작 조건

  • 10-7 listItem fields를 확인하고 project-v1 post39 또는 실제 capture id를 사용한다.
  • 같은 transaction에서 JPA와 MyBatis가 함께 실행되도록 실습 설정을 확인한다.

사용자 시나리오

  1. 시작
    post39 title old, tags [check,flush], visibility PUBLIC 상태와 SQL log 기록.
    행동
    PUT /api/v1/posts/39 title="[채점] 10-12 수정 후", tags=[after], visibility=PRIVATE; flush 있는 실행과 flush 생략 실행을 비교한다.
    결과
    flush 뒤 same transaction MyBatis listItem은 수정 title/tags/visibility를 읽는다. flush 생략 대조 경로는 mapper read에서 old title/tags가 나타날 수 있다. API 200 response body detail/listItem이 같은 값인지 확인.
    이후
    flush는 commit이 아니다. 외부 DB client는 commit 전 값을 못 보고 rollback 뒤에는 row 이전값으로 남는다.

데이터와 이유

post39 title/tags/visibility old and new values
JPA entity, MyBatis listItem, DB observation 비교.
SQL log ordering UPDATE then SELECT
flush가 mapper read 전에 변경을 DB로 보냈는지 확인.
transaction identity/connection and commit/rollback markers
same transaction visibility와 외부 connection 분리.
listItem fields id/title/visibility/viewCount/likeCount/author/tags/createdAt
GET list item과 POST/PUT response shape equality.

업무 정책

  • 10-12는 JPA write → explicit flush → MyBatis card query in same transaction. Flush sends pending SQL but does not commit.
  • POST and PUT response `data.listItem` must match GET /api/v1/posts list item shape.
  • Invalid title/tags is validated before persist/flush, returns 400 ApiResponse and writes nothing.
  • Same transaction connection can observe flushed write; another DB client cannot observe before commit; rollback undoes DB update.

입력과 출력

  • PUT /api/v1/posts/39 title="[채점] 10-12 수정 후", tags=["after"], visibility="PRIVATE".
  • Control request without flush on disposable test code: expected mapper old title/tags `check`,`flush`; JPA response detail new values.
  • Invalid title blank or tags beyond 5 / blank tag; rollback observation.

성공 기준

  • flush path 200; detail/listItem title [채점] 10-12 수정 후, tags [after], visibility PRIVATE.
  • flush SQL UPDATE precedes MyBatis SELECT; same transaction sees new values.
  • API response `listItem` matches list item fields.

실패와 데이터 보존

  • flush omitted before MyBatis read → mapper listItem may return prior title/tags while JPA detail shows new values. · 유지: no commit yet; later flush behavior is recorded separately.
  • validation fails before flush → 400 VALIDATION_FAILED. · 유지: post39 old title/tags/visibility and SQL update count unchanged.
  • transaction rollback after flush → rollback completes without commit. · 유지: external fresh connection after rollback reads old title/tags.

입력 사례

  • Flush before read
  • Read before flush control
  • Rollback after flush

개발 과제

  • Capture Hibernate and MyBatis SQL log timestamps/order.
  • Compare JPA response detail with listItem; query DB from same and separate connection at stated moments.
  • Record persist, flush, commit, rollback as separate events.

완료 확인

  • Same transaction mapper sees flushed write.
  • Flush not mislabeled commit; external connection and rollback observations are recorded.
  • POST/PUT response listItem contract and invalid-input no-write confirmed.
