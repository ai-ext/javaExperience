#10-3. 회원 가입 — BCrypt 해시와 이메일 중복 409

#상황

명세서의 첫 API다.

API 요청 성공 실패
POST /api/v1/users 가입 {email, password(8~64자, UTF-8 72바이트 이하), nickname(2~20자)} 201 {id, email, nickname} 400, 409

처음으로 입력을 받아 DB에 쓰는 API다. 네 가지를 지킨다.

  1. 비밀번호는 원문으로 저장하지 않는다. DB가 새도 원래 비밀번호를 알 수 없게 BCrypt 해시만 저장한다. 로그인(10-4)은 해시끼리 비교한다.
  2. 같은 이메일로 두 번 가입하지 못한다 → 409 DUPLICATE. Kim@Example.com과 kim@example.com은 같은 주소로 본다. 받은 이메일은 앞뒤 공백을 떼고 소문자로 바꿔 저장한다.
  3. 입력이 틀리면 10-2의 400 틀로 답한다 → 필드별 errors.
  4. 비밀번호는 글자 수와 바이트 수를 둘 다 본다. 8~64자이면서 UTF-8로 72바이트 이하. BCrypt는 72바이트를 넘는 입력을 해시하지 못하고 예외를 던진다. 글자 수만 보면 한글 25자(75바이트)가 검증을 통과해 500이 된다. 넘으면 400 VALIDATION_FAILED(field: password)로 막는다. 왜 72바이트인지는 F4에 있다.

엔티티·저장소·서비스·컨트롤러를 한 번에 만든다. 계층을 나누는 이유는 E1, JPA가 무엇인지는 E3에 있다.

#만들 것

항목 내용
의존성 spring-security-crypto 하나만 추가한다(Spring Security 전체가 아니다 — 로그인 필터·기본 로그인 페이지가 딸려 오지 않는다)
메서드·경로 POST /api/v1/users
요청 email: 필수, 이메일 형식, 255자 이하 · password: 필수, 864자 그리고 UTF-8 72바이트 이하(한글 24자까지) · nickname: 필수, 220자(앞뒤 공백 제거 후). 이메일은 앞뒤 공백 제거 + 소문자로 다듬은 뒤 검사·저장
저장 users에 password_hash = BCrypt 해시
성공 201, 헤더 Location: /api/v1/users/{id}, data = {id, email, nickname} — 비밀번호·해시는 싣지 않는다
실패 입력 규칙 위반 400 VALIDATION_FAILED(필드별 errors) · 깨진 JSON 400 BAD_JSON · 이메일 중복 409 DUPLICATE

필드 규칙 — 다듬은 뒤 검사한다. 잘못된 입력은 저장 전에 막고 500이 나면 안 된다

필드 필수 null·빈 값 길이·범위 형식 기본값 틀렸을 때
email 필수 안 됨 — 없음·null·""·공백만 거절 앞뒤 공백 제거·소문자 뒤 255자 이하 이메일 형식 없음 400 VALIDATION_FAILED, errors에 email · 이미 있으면 409 DUPLICATE
password 필수 null·"" 거절(공백은 다듬지 않는다 — 아래 관찰 O1) 8~64자(8자·64자 성공, 7자·65자 거절) 그리고 UTF-8 72바이트 이하(한글 24자 성공, 25자 거절) 문자열 없음 400, errors에 password
nickname 필수 안 됨 — 없음·null·""·공백만 거절 앞뒤 공백 제거 뒤 2~20자(2자·20자 성공, 1자·21자 거절) 문자열 없음 400, errors에 nickname
본문 전체 필수 — — JSON, 각 값은 문자열 — JSON이 아니거나 문자열 자리에 배열이면 400 BAD_JSON

#User — 엔티티

src/main/java/org/example/board/user/User.java

package org.example.board.user;

import java.time.LocalDateTime;
import java.time.temporal.ChronoUnit;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String email;

    @Column(name = "password_hash", nullable = false)
    private String passwordHash;

    @Column(nullable = false, length = 20)
    private String nickname;

    @Column(name = "created_at", nullable = false)
    private LocalDateTime createdAt;

    // JPA가 DB 행을 객체로 만들 때 쓰는 기본 생성자 — 우리 코드는 아래 생성자만 쓴다
    protected User() {
    }

    public User(String email, String passwordHash, String nickname) {
        this.email = email;
        this.passwordHash = passwordHash;
        this.nickname = nickname;
        this.createdAt = LocalDateTime.now().truncatedTo(ChronoUnit.SECONDS);
    }

    public Long getId() {
        return id;
    }

    public String getEmail() {
        return email;
    }

    public String getPasswordHash() {
        return passwordHash;
    }

    public String getNickname() {
        return nickname;
    }
}
코드 설명
@Entity · @Table(name = "users") 이 클래스 = users 테이블의 한 행. 클래스 이름과 테이블 이름이 달라 @Table로 적었다
@Id @GeneratedValue(strategy = GenerationType.IDENTITY) 기본 키. 값은 DB의 AUTO_INCREMENT가 정한다. 그래서 save 하는 순간 INSERT가 나가고 id가 채워진다
@Column(name = "password_hash", nullable = false) 필드 이름(passwordHash)과 컬럼 이름이 달라 적었다
protected User() { } JPA가 DB 행을 객체로 만들 때 쓰는 빈 생성자. 우리 코드는 못 쓰게 protected로 둔다
LocalDateTime.now().truncatedTo(ChronoUnit.SECONDS) 컬럼이 초 단위(DATETIME)라 초 아래를 버린다
setter 없음 만든 뒤 바꿀 일이 없는 값은 setter를 만들지 않는다

ddl-auto: validate라 이 클래스가 테이블과 다르면(컬럼 이름 오타 등) 앱이 뜨지 않는다. 그 에러가 오히려 안전장치다.

#MaxBytes — 바이트 수를 보는 검증 어노테이션

@Size는 글자 수만 센다. BCrypt의 한계는 바이트(72)다. UTF-8에서 영문·숫자는 1바이트, 한글은 3바이트라 한글 25자는 25글자지만 75바이트다. 그래서 바이트를 세는 검증을 하나 만든다.

서비스에서 if로 검사하지 않고 어노테이션으로 만드는 이유: 그러면 다른 입력 오류와 함께 @Valid 단계에서 errors(field: password)로 나온다. 서비스에서 던지는 ApiException에는 필드를 실을 자리가 없어 10-2의 공통 코드까지 고쳐야 한다.

src/main/java/org/example/board/user/MaxBytes.java

package org.example.board.user;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;
import java.nio.charset.StandardCharsets;

import jakarta.validation.Constraint;
import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;
import jakarta.validation.Payload;

// 글자 수가 아니라 UTF-8 바이트 수로 길이를 막는다 — BCrypt는 72바이트를 넘는 입력을 encode하지 못한다(F4)
@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = MaxBytes.Validator.class)
public @interface MaxBytes {

    int value();

    String message();

    // 아래 두 줄은 Bean Validation 규칙상 모든 검증 어노테이션에 있어야 한다
    Class<?>[] groups() default {};

    Class<? extends Payload>[] payload() default {};

    // 실제 검사 — true면 통과
    class Validator implements ConstraintValidator<MaxBytes, String> {

        private int max;

        @Override
        public void initialize(MaxBytes annotation) {
            this.max = annotation.value();
        }

        @Override
        public boolean isValid(String value, ConstraintValidatorContext context) {
            // null은 @NotNull 몫이라 여기서는 통과시킨다
            return value == null || value.getBytes(StandardCharsets.UTF_8).length <= max;
        }
    }
}
코드 설명
public @interface MaxBytes 어노테이션을 직접 만든다. @MaxBytes(value = 72, message = "…")처럼 쓴다
@Target(ElementType.FIELD) · @Retention(RetentionPolicy.RUNTIME) 필드(record의 각 항목)에 붙이고, 실행 중에도 남아 있어야 검증기가 읽는다
@Constraint(validatedBy = MaxBytes.Validator.class) "이 어노테이션은 이 클래스가 검사한다"를 검증 엔진에 알린다
groups() · payload() 쓰지 않지만 빠지면 앱은 뜨는데 가입 요청마다 500이다(로그: HV000074: ... does not contain a groups parameter). 그대로 따라 적는다
value.getBytes(StandardCharsets.UTF_8).length <= max 문자열을 UTF-8 바이트 배열로 바꿔 길이를 잰다. "가".getBytes(UTF_8).length는 3
value == null || … null은 통과 — 비어 있음은 @NotNull이 따로 잡는다(@Email과 같은 약속)

#SignupRequest — 요청 + 검증 + 다듬기

src/main/java/org/example/board/user/SignupRequest.java

package org.example.board.user;

import java.util.Locale;

import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Size;

public record SignupRequest(
        @NotBlank(message = "이메일은 필수입니다.")
        @Email(message = "이메일 형식이 아닙니다.")
        @Size(max = 255, message = "이메일은 255자 이하여야 합니다.")
        String email,

        @NotNull(message = "비밀번호는 필수입니다.")
        @Size(min = 8, max = 64, message = "비밀번호는 8자 이상 64자 이하여야 합니다.")
        @MaxBytes(value = 72, message = "비밀번호는 72바이트 이하여야 합니다(한글은 한 글자에 3바이트).")
        String password,

        @NotBlank(message = "닉네임은 필수입니다.")
        @Size(min = 2, max = 20, message = "닉네임은 2자 이상 20자 이하여야 합니다.")
        String nickname) {

    // 검증 전에 다듬는다 — 이메일은 앞뒤 공백을 떼고 소문자로(같은 주소를 두 번 가입하지 못하게), 닉네임은 앞뒤 공백만
    public SignupRequest {
        email = email == null ? null : email.strip().toLowerCase(Locale.ROOT);
        nickname = nickname == null ? null : nickname.strip();
    }
}
코드 설명
@NotBlank(message = "…") null·빈 문자열·공백만인 문자열을 막는다. message가 그대로 errors[].reason이 된다
@Email 이메일 형식 검사. null은 통과시키므로(다른 애노테이션 몫) @NotBlank와 같이 쓴다
@NotNull + @Size(min = 8, max = 64) 비밀번호는 공백도 글자로 인정해 @NotBlank 대신 @NotNull을 썼다
@MaxBytes(value = 72, …) 위에서 만든 바이트 검사. @Size와 둘 다 붙인다 — 한글 65자면 password 오류가 두 개 나온다
public SignupRequest { … } record의 압축 생성자. JSON → 객체로 바뀔 때 실행되고, @Valid 검사는 그다음이다. 그래서 다듬은 값으로 검사한다
email.strip().toLowerCase(Locale.ROOT) strip()은 앞뒤 공백 제거, Locale.ROOT는 실행하는 컴퓨터의 언어 설정에 따라 대소문자 변환이 달라지지 않게 고정한다

@Service
public class UserService {

    private final PasswordEncoder passwordEncoder;

        this.userRepository = userRepository;
        this.passwordEncoder = passwordEncoder;
    }

    @Transactional
    public UserResponse signup(SignupRequest request) {
        if (userRepository.existsByEmail(request.email())) {
            throw new ApiException(ErrorCode.DUPLICATE, "이미 가입된 이메일입니다.");
        }
        User user = new User(request.email(), passwordEncoder.encode(request.password()), request.nickname());
        try {
            userRepository.save(user);
        } catch (DataIntegrityViolationException e) {
            // 확인과 저장 사이에 같은 이메일이 먼저 들어간 경우 — DB의 UNIQUE가 마지막 방어선이다
            throw new ApiException(ErrorCode.DUPLICATE, "이미 가입된 이메일입니다.");
        }
        return UserResponse.from(user);
    }
}

@Transactional 메서드 전체를 DB 트랜잭션 하나로 묶는다. 중간에 예외가 나면 쓴 것을 되돌린다(G3)

passwordEncoder.encode(request.password()) 원문 → $2a$10$... 해시. 같은 원문도 매번 다른 해시가 나온다(솔트)

#구현 가이드

화면 시나리오의 서버·DB 흐름을 이 단계에서 바뀐 파일에 연결한다. 먼저 만들 것의 계약대로 직접 작성하고, 필요한 역할만 펼쳐 파일 전문과 비교한다.

이 단계의 처리 흐름:

  • @Valid가 길이·형식을 검사 → UserService가 이메일 중복을 확인 → passwordEncoder.encode로 해시
  • 요청 record가 이메일을 다듬는다(공백 제거·소문자) → 이미 있어 ApiException(DUPLICATE)
  • @Valid 실패 → MethodArgumentNotValidException → 전역 처리기가 필드별 errors로
  • @Valid — @Size(8~64자)는 통과, @MaxBytes(72)가 UTF-8 75바이트라 실패. encode까지 가지 않는다

MyBatis / Mapper — 같은 가입을 SQL로 구현하기

선택 경로에서는 UserRepository와 JPA 엔티티를 빼고 UserMapper와 SQL XML을 넣는다. UserController·SignupRequest·UserResponse의 HTTP 계약과 검증은 그대로 쓴다. 아래 MyBatis 대체 구현 코드 접기에는 기본 10-3 스냅샷에 적용할 설정·POJO·Service·Mapper 전문이 있다.

<select id="existsByEmail" resultType="boolean">
    SELECT EXISTS(SELECT 1 FROM users WHERE email = #{email})
</select>
<insert id="insert" parameterType="org.example.board.user.User"
        useGeneratedKeys="true" keyProperty="id">

    VALUES (#{email}, #{passwordHash}, #{nickname}, #{createdAt})

#{email}은 문자열을 SQL에 이어 붙이지 않고 바인딩한다. INSERT가 만든 id는 useGeneratedKeys로 User.id에 채워져 Location과 응답 DTO에 쓰인다. Service에서는 먼저 existsByEmail로 확인하고, 그 사이 같은 이메일이 들어오면 DB의 UNIQUE 위반을 DuplicateKeyException으로 받아 409 DUPLICATE로 바꾼다. @Transactional과 BCrypt 해시는 JPA 경로와 동일하다.

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;
import java.nio.charset.StandardCharsets;


import jakarta.validation.Constraint;
import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;
import jakarta.validation.Payload;


// 글자 수가 아니라 UTF-8 바이트 수로 길이를 막는다 — BCrypt는 72바이트를 넘는 입력을 encode하지 못한다(F4)
@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = MaxBytes.Validator.class)
public @interface MaxBytes {


int value();

String message();

// 아래 두 줄은 Bean Validation 규칙상 모든 검증 어노테이션에 있어야 한다
Class&lt;?&gt;[] groups() default {};

Class&lt;? extends Payload&gt;[] payload() default {};

// 실제 검사 — true면 통과
class Validator implements ConstraintValidator&lt;MaxBytes, String&gt; {

    private int max;

    @Override
    public void initialize(MaxBytes annotation) {
        this.max = annotation.value();
    }

    @Override
    public boolean isValid(String value, ConstraintValidatorContext context) {
        // null은 @NotNull 몫이라 여기서는 통과시킨다
        return value == null || value.getBytes(StandardCharsets.UTF_8).length &lt;= max;
    }
}

package org.example.board.user;


import org.example.board.common.ApiException;
import org.example.board.common.ErrorCode;
import org.springframework.dao.DuplicateKeyException;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;


@Service
public class UserService {


private final UserMapper userMapper;
private final PasswordEncoder passwordEncoder;

public UserService(UserMapper userMapper, PasswordEncoder passwordEncoder) {
    this.userMapper = userMapper;
    this.passwordEncoder = passwordEncoder;
}

@Transactional
public UserResponse signup(SignupRequest request) {
    if (userMapper.existsByEmail(request.email())) {
        throw new ApiException(ErrorCode.DUPLICATE, &quot;이미 가입된 이메일입니다.&quot;);
    }
    User user = new User(request.email(), passwordEncoder.encode(request.password()), request.nickname());
    try {
        userMapper.insert(user);
    } catch (DuplicateKeyException e) {
        // 확인과 저장 사이에 같은 이메일이 먼저 들어간 경우 — DB의 UNIQUE가 마지막 방어선이다
        throw new ApiException(ErrorCode.DUPLICATE, &quot;이미 가입된 이메일입니다.&quot;);
    }
    return UserResponse.from(user);
}


}

#힌트 (막힐 때만)



힌트 1 — 앱이 Schema-validation 에러로 뜨지 않는다


Schema-validation: missing column [...]이나 wrong column type이면 엔티티의 @Column(name = ...)이 V1의 컬럼 이름과 다르다. users 테이블은 password_hash·created_at처럼 밑줄 이름이다.






힌트 2 — 대문자 이메일이 409가 아니라 201이다


이메일을 다듬지 않고 그대로 저장했다. record에 압축 생성자 public SignupRequest { email = ...; }를 두고 strip()·toLowerCase(Locale.ROOT)를 한다. 서비스에서 해도 되지만 그러면 @Email 검사는 다듬기 전 값으로 한다.






힌트 3 — errors에 필드가 하나만 나온다


검증은 모든 필드를 한꺼번에 본다. 하나만 나오면 처리기가 getFieldError()(첫 번째 하나)를 썼다. getFieldErrors()(목록)를 쓴다.
