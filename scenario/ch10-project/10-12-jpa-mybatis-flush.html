"글을 쓰거나 고친 뒤에 목록을 다시 불러오기 싫어요. 응답에 목록 카드 한 줄을 같이 주시면 목록에 바로 끼울게요. 목록 API랑 모양이 똑같아야 해요."

바뀐 API 추가되는 것
POST /api/v1/posts, PUT /api/v1/posts/{postId} 응답 data.listItem — 10-7 목록의 항목과 같은 모양(id, title, visibility, viewCount, likeCount, author, tags, createdAt)

이 단계는 그 카드 한 줄을 MyBatis로 읽는다(10-7을 MyBatis로 짰다면 목록과 같은 쿼리 조각을 그대로 쓰니 모양이 저절로 같다). 그러면 한 서비스 메서드 안에서 이렇게 된다.

  1. JPA로 쓴다(엔티티 저장·변경).
  2. 같은 트랜잭션에서 MyBatis로 방금 그 글을 읽는다.

여기에 함정이 있다. JPA는 바뀐 내용을 바로 DB에 보내지 않는다. 모아 두었다가 커밋 직전이나 필요할 때 한꺼번에 보낸다(flush). MyBatis는 JPA 밖에 있어서, JPA가 아직 안 보낸 변경을 모른다. 이 단계에서는 "언제 보이고 언제 안 보이는지"를 직접 재현하고, 확실히 보이게 만든다.

#MyBatis 넣기

10-7을 JPA로만 짰다면 MyBatis가 아직 없다. 이 단계에서 처음 넣는다(10-7 선택 칸을 했다면 이미 있으니 건너뛴다).

build.gradle의 dependencies에 한 줄 — MyBatis는 Boot BOM에 없어서 버전을 직접 적는다(4.1.x가 Boot 4.1용).

implementation 'org.mybatis.spring.boot:mybatis-spring-boot-starter:4.1.0'

application.yml에 둔다.

mybatis:
  mapper-locations: classpath:mapper/*.xml
  configuration:
    map-underscore-to-camel-case: true   # 컬럼 view_count → 필드 viewCount

매퍼는 인터페이스(post/PostQueryMapper.java, @Mapper)와 XML(src/main/resources/mapper/PostQueryMapper.xml) 한 쌍이다. XML의 namespace가 인터페이스의 전체 이름과 같아야 하고, <select id>가 메서드 이름이다(자세히는 E5 MyBatis 첫걸음).

@Mapper
public interface PostQueryMapper {
    PostListRow findListRowById(@Param("id") Long id);
    List<PostTagRow> findTagsByPostIds(@Param("postIds") List<Long> postIds);
}

결과 한 줄은 컬럼이 평평한(author_id, author_nickname) 클래스 PostListRow로 받고, 목록 항목 record로 옮길 때 author{id, nickname}으로 묶는다. MyBatis는 setter가 없어도 필드에 값을 넣는다. 태그 한 쌍은 10-7의 PostTagRow record를 그대로 쓴다.

03◇무엇을 만들까설계 포인트 — 직접 재현한 것아래는 정답 코드에서 postRepository.flush() 를 빼거나 순서를 바꿔 SQL 로그( org.hibernate.SQL ·MyBatis 매퍼 DEBUG)로 확인한…5개 코드 · 열기 ↓
① 작성 — 글은 보이는데 태그가 비어 있다② 수정 — 통째로 옛 값③ flush하면 왜 보이나 — 같은 커넥션

아래는 정답 코드에서 postRepository.flush()를 빼거나 순서를 바꿔 SQL 로그(org.hibernate.SQL·MyBatis 매퍼 DEBUG)로 확인한 결과다(Boot 4.1.1, Hibernate 7.4, MyBatis 3.5.19).

#① 작성 — 글은 보이는데 태그가 비어 있다

flush 없이 작성하면 응답이 이렇다.

data.tags            ['check', 'flush']
data.listItem.title  [채점] 10-12 flush 없이      ← 글은 보인다
data.listItem.tags   []                           ← 태그는 안 보인다

SQL 로그 순서는 다음과 같다.

insert into posts (author_id,content,created_at,...) values (...)    ← save() 순간 바로 나감
==>  Preparing: SELECT p.id, p.title, ... (MyBatis 목록 한 줄)
==>  Preparing: SELECT pt.post_id, t.name ... (MyBatis 태그)
insert into post_tags (post_id,tag_id) values (?,?)                  ← 커밋 직전 flush 때
insert into post_tags (post_id,tag_id) values (?,?)
  • 글 행이 보이는 이유: id가 IDENTITY(AUTO_INCREMENT)라 JPA는 id를 알려고 save 순간 INSERT를 보낸다. 다른 변경처럼 미뤄 둘 수 없다.
  • 태그가 안 보이는 이유: post_tags(연결 테이블) INSERT는 미뤄 두었다가 flush 때 나간다.
  • "작성 직후 MyBatis로 읽어 봤더니 되더라"는 우연히 IDENTITY라서다. 연관된 행은 여전히 늦다.

#② 수정 — 통째로 옛 값

flush 없이 수정하면 이렇다.

data.title           [채점] 10-12 수정 후
data.listItem.title  [채점] 10-12 flush 없이     ← 옛 제목
data.listItem.tags   ['check', 'flush']          ← 옛 태그
==>  Preparing: SELECT p.id, p.title, ... (MyBatis)
update posts set title=? where id=?                               ← MyBatis 조회 뒤에야 나감
delete from post_tags where post_id=? and tag_id=?
insert into post_tags (post_id,tag_id) values (?,?)
select count(*) from post_likes where post_id = ? and user_id = ?   ← (좋아요 여부 네이티브 쿼리)

변경 감지는 엔티티의 값만 바꿔 두고, UPDATE는 flush 때 만든다. 로그를 보면 UPDATE가 JPA 네이티브 쿼리(countLike) 바로 앞에서 나갔다. Hibernate는 자기가 실행하는 쿼리 앞에서는 결과가 틀리지 않게 알아서 flush한다(auto flush). MyBatis 쿼리는 Hibernate가 모르는 쿼리라 그 앞에서는 flush하지 않는다.

함정이 하나 더 있다. MyBatis 조회를 우연히 countLike 뒤에 두면 flush 없이도 맞게 나온다. 순서를 바꾸는 순간 깨지는 코드다. 필요한 곳에 flush()를 직접 적는다.

#③ flush하면 왜 보이나 — 같은 커넥션

flush()는 SQL을 DB로 보낼 뿐 커밋하지 않는다. 커밋 전의 변경은 원래 다른 커넥션에서 안 보인다. 그런데도 MyBatis가 새 값을 읽는다는 것은 MyBatis가 JPA와 같은 트랜잭션·같은 커넥션을 쓰고 있다는 뜻이다.

@Transactional(JPA 트랜잭션 관리자)이 연 커넥션을 MyBatis-Spring이 그대로 받아 쓴다. 그래서 둘을 섞으려면 반드시 같은 @Transactional 메서드 안에서 부른다.

#④ 그래도 옛 값 — MyBatis 1차 캐시

수정 메서드 앞부분에서 같은 MyBatis 쿼리로 "수정 전 카드"를 한 번 읽고, 변경 → flush → 다시 읽어 보았다.

data.title           [채점] 10-12 수정 후
data.listItem.title  [채점] 10-12 캐시 실험     ← flush했는데도 옛 값
data.listItem.tags   ['check']

MyBatis는 한 트랜잭션 안에서 같은 쿼리·같은 파라미터의 결과를 기억해 두고(1차 캐시) DB에 다시 묻지 않는다. JPA의 flush는 MyBatis 캐시를 비우지 않는다. 그 쿼리에 flushCache="true"를 주자 새 값이 나왔다(실측). 한 트랜잭션에서 같은 MyBatis 조회를 두 번 할 일이 있으면 이 점을 기억한다.

조건 MyBatis가 보나
JPA save + IDENTITY id — 그 글 행 보인다(INSERT가 즉시)
연관 행(post_tags), 변경 감지 UPDATE — flush 전 안 보인다
flush 뒤, 같은 트랜잭션 보인다
JPA 쿼리(JPQL·네이티브)가 사이에 실행된 뒤 보인다(auto flush) — 우연에 기대지 말 것
같은 MyBatis 쿼리를 앞에서 이미 읽었음 flush해도 옛 값(1차 캐시)

package org.example.board.post;

import java.util.List;
import java.util.Map;
import java.util.stream.Collectors;

import org.example.board.common.ApiException;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Slice;
import org.springframework.data.domain.Sort;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

// 게시글 목록·검색 — JPA(JPQL + Pageable). 작성·수정 응답의 카드 한 줄(listItem)만 MyBatis(10-12)
@Service
public class PostQueryService {

    // 정렬은 사용자가 보낸 문자열을 Sort에 넣지 않고 정해 둔 두 가지 중에서 고른다
    private static final Sort LATEST = Sort.by(Sort.Order.desc("id"));
    private static final Sort POPULAR = Sort.by(Sort.Order.desc("likeCount"), Sort.Order.desc("id"));

    private final PostQueryRepository postQueryRepository;
    private final PostQueryMapper postQueryMapper;

    public PostQueryService(PostQueryRepository postQueryRepository, PostQueryMapper postQueryMapper) {
        this.postQueryRepository = postQueryRepository;
        this.postQueryMapper = postQueryMapper;
    }

    @Transactional(readOnly = true)
    public Object list(PostListQuery query, Long loginUserId) {
        if (query.cursorMode()) {
            return cursorList(query, loginUserId);
        }
        int page = query.page() == null ? 0 : query.page();
        Sort sort = "popular".equals(query.sort()) ? POPULAR : LATEST;
        Page<Post> result = postQueryRepository.findVisible(loginUserId, query.tag(), query.q(),
                PageRequest.of(page, query.size(), sort));
        // Spring의 Page를 그대로 내보내지 않고 명세의 모양으로 옮긴다
        return new PageResponse<>(withTags(result.getContent()), page, query.size(), result.getTotalElements(),
                result.hasNext());
    }

    // 같은 트랜잭션 안에서 부르면 JPA가 flush한 것까지 보인다(호출하는 쪽이 먼저 flush해야 한다)
    public PostListItemResponse listItem(Long postId) {
        PostListRow row = postQueryMapper.findListRowById(postId);
        List<String> tags = postQueryMapper.findTagsByPostIds(List.of(postId)).stream().map(PostTagRow::name).toList();
        return PostListItemResponse.of(row, tags);
    }

    private CursorResponse<PostListItemResponse> cursorList(PostListQuery query, Long loginUserId) {
        // 인기순은 좋아요가 바뀌면 순서가 흔들려 커서가 글을 빠뜨리거나 두 번 준다 — 최신순만 허락한다
        if ("popular".equals(query.sort())) {
            throw ApiException.invalid("cursor", "커서 페이징은 최신순(latest)에서만 쓸 수 있습니다.");
        }
        if (query.page() != null) {
            throw ApiException.invalid("page", "page와 cursor는 함께 쓸 수 없습니다.");
        }
        Long cursorId = parseCursor(query.cursor());
        // 커서는 항상 첫 "페이지"(0)만 읽는다 — 어디서부터인지는 id < cursorId가 정한다(keyset)
        Slice<Post> slice = postQueryRepository.findVisibleBefore(loginUserId, query.tag(), query.q(), cursorId,
                PageRequest.of(0, query.size(), LATEST));
        List<Post> posts = slice.getContent();
        String next = slice.hasNext() ? String.valueOf(posts.get(posts.size() - 1).getId()) : null;
        return new CursorResponse<>(withTags(posts), next);
    }

    private Long parseCursor(String cursor) {
        if (cursor.isBlank()) {
            return null;
        }
        try {
            return Long.valueOf(cursor);
        } catch (NumberFormatException e) {
            throw ApiException.invalid("cursor", "커서 값이 올바르지 않습니다.");
        }
    }

    // 글과 태그를 JOIN한 채 페이징하지 않는다(행이 태그 수만큼 불어난다) — 이번 페이지 글들의 태그를 IN 한 번으로
    private List<PostListItemResponse> withTags(List<Post> posts) {
        if (posts.isEmpty()) {
            return List.of();
        }
        Map<Long, List<String>> tagsByPost = postQueryRepository.findTagsByPostIds(posts.stream().map(Post::getId).toList())
                .stream()
                .collect(Collectors.groupingBy(PostTagRow::postId, Collectors.mapping(PostTagRow::name, Collectors.toList())));
        return posts.stream()
                .map(p -> PostListItemResponse.of(p, tagsByPost.getOrDefault(p.getId(), List.of())))
                .toList();
    }
}

package org.example.board.post;

import java.util.LinkedHashSet;
import java.util.List;
import java.util.Set;

import jakarta.persistence.EntityManager;

import org.example.board.comment.CommentRepository;
import org.example.board.comment.CommentTree;
import org.example.board.common.ApiException;
import org.example.board.common.ErrorCode;
import org.example.board.user.User;
import org.example.board.user.UserRepository;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

// 게시글 쓰기 — JPA
@Service
public class PostService {

    private final PostRepository postRepository;
    private final TagRepository tagRepository;
    private final UserRepository userRepository;
    private final CommentRepository commentRepository;
    private final EntityManager entityManager;
    private final PostQueryService postQueryService;

    public PostService(PostRepository postRepository, TagRepository tagRepository, UserRepository userRepository,
                       CommentRepository commentRepository, PostQueryService postQueryService, EntityManager entityManager) {
        this.postRepository = postRepository;
        this.tagRepository = tagRepository;
        this.userRepository = userRepository;
        this.commentRepository = commentRepository;
        this.entityManager = entityManager;
        this.postQueryService = postQueryService;
    }

    @Transactional
    public PostDetailResponse create(Long userId, PostRequest request) {
        User author = userRepository.findById(userId)
                .orElseThrow(() -> new ApiException(ErrorCode.UNAUTHORIZED));
        Post post = new Post(author, request.title(), request.content(),
                Visibility.valueOf(request.visibility()), findOrCreateTags(request.tags()));
        postRepository.save(post);
        // posts 행은 save 때 이미 INSERT됐지만(IDENTITY) post_tags는 flush 때 들어간다.
        // MyBatis는 JPA가 아직 DB에 안 보낸 변경을 모른다 — 읽기 전에 flush
        postRepository.flush();
        return PostDetailResponse.of(post, post.getViewCount(), false, List.of())
                .withListItem(postQueryService.listItem(post.getId()));
    }

    // 상세: 보이는 글인지 확인 → 조회수 +1 → 좋아요 여부·댓글 트리와 함께
    @Transactional
    public PostDetailResponse detail(Long postId, Long loginUserId) {
        Post post = postRepository.findDetailById(postId)
                .orElseThrow(() -> new ApiException(ErrorCode.NOT_FOUND, "게시글을 찾을 수 없습니다."));
        boolean isAuthor = post.getAuthor().getId().equals(loginUserId);
        if (post.getVisibility() == Visibility.PRIVATE && !isAuthor) {
            // 남의 비공개 글은 "있지만 못 본다"(403)가 아니라 "없다"(404) — 있다는 사실도 흘리지 않는다
            throw new ApiException(ErrorCode.NOT_FOUND, "게시글을 찾을 수 없습니다.");
        }
        postRepository.increaseViewCount(postId);
        boolean liked = loginUserId != null && postRepository.countLike(postId, loginUserId) > 0;
        return PostDetailResponse.of(post, post.getViewCount() + 1, liked,
                CommentTree.build(commentRepository.findAllWithAuthorByPostId(postId)));
    }

    // 수정: 없음·남의 비공개 → 404, 남의 글 → 403
    @Transactional
    public PostDetailResponse update(Long userId, Long postId, PostRequest request) {
        Post post = findWritable(userId, postId, "작성자만 수정할 수 있습니다.");
        post.replace(request.title(), request.content(), Visibility.valueOf(request.visibility()),
                findOrCreateTags(request.tags()));
        // 변경 감지(dirty checking)한 UPDATE·태그 교체는 아직 JPA 안에만 있다 — MyBatis로 읽기 전에 DB로 보낸다
        postRepository.flush();
        PostListItemResponse listItem = postQueryService.listItem(postId);
        boolean liked = postRepository.countLike(postId, userId) > 0;
        return PostDetailResponse.of(post, post.getViewCount(), liked,
                CommentTree.build(commentRepository.findAllWithAuthorByPostId(postId))).withListItem(listItem);
    }

    @Transactional
    public void delete(Long userId, Long postId) {
        findWritable(userId, postId, "작성자만 삭제할 수 있습니다.").delete();
    }

    private Post findWritable(Long userId, Long postId, String forbiddenMessage) {
        // 삭제와 수정의 경합에서 먼저 행을 잠근다. 선행 삭제가 끝났다면 404로 종료한다.
        if (entityManager.createNativeQuery("select id from posts where id = :id and deleted_at is null for update")
                .setParameter("id", postId).getResultList().isEmpty()) {
            throw new ApiException(ErrorCode.NOT_FOUND, "게시글을 찾을 수 없습니다.");
        }
        Post post = postRepository.findDetailById(postId)
                .orElseThrow(() -> new ApiException(ErrorCode.NOT_FOUND, "게시글을 찾을 수 없습니다."));
        boolean isAuthor = post.getAuthor().getId().equals(userId);
        if (post.getVisibility() == Visibility.PRIVATE && !isAuthor) {
            throw new ApiException(ErrorCode.NOT_FOUND, "게시글을 찾을 수 없습니다.");
        }
        if (!isAuthor) {
            throw new ApiException(ErrorCode.FORBIDDEN, forbiddenMessage);
        }
        return post;
    }

    // 이름으로 찾고, 없으면 새로 만든다(tags.name은 UNIQUE)
    private Set<Tag> findOrCreateTags(List<String> names) {
        Set<Tag> tags = new LinkedHashSet<>();
        for (String name : names) {
            tags.add(tagRepository.findByName(name).orElseGet(() -> tagRepository.save(new Tag(name))));
        }
        return tags;
    }
}

태그는 SELECT pt.post_id, t.name FROM post_tags pt JOIN tags t ON t.id = pt.tag_id WHERE pt.post_id IN <foreach …>#{id}</foreach> ORDER BY t.name. 목록 서비스에 listItem(Long postId)를 두고, 행 하나와 그 글의 태그로 항목 하나를 만든다.


태그도 MyBatis로 읽어야 한다 — JPA 쿼리로 읽으면 그 앞에서 Hibernate가 auto flush해 버려 아래 ①을 재현할 수 없다.

JpaRepository에 flush()가 있다. EntityManager를 주입받아 em.flush()를 불러도 같다.






힌트 3 — 응답에 listItem 붙이기


상세 응답 record에 @JsonInclude(JsonInclude.Include.NON_NULL) PostListItemResponse listItem 필드를 더하고, 상세(GET)에서는 null로 둔다. 그러면 GET 응답에는 키가 없고, 10-5·10-8의 확인도 그대로 통과한다.

  • 쓰는 메서드는 쓰기만 하고 id만 돌려준다. 읽기는 커밋 뒤 따로 한다(컨트롤러에서 서비스 두 번 호출 — 둘째 호출은 새 트랜잭션).
    •
