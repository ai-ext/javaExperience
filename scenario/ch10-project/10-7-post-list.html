#10-7. 목록 — 최신·인기·페이지·커서·태그·검색, JPA(JPQL·Pageable)

#상황

API 규칙 성공 실패
GET /api/v1/posts?sort=latest|popular&page=&size= · ?cursor=&size= · &tag=&q= PUBLIC만(로그인하면 내 PRIVATE도). size 1~50, 기본 20. q는 제목 검색. 인기순 = 좋아요 수 내림차순 → 같으면 id 내림차순, 최신순 = id 내림차순. 커서는 최신순만 200 페이지 또는 커서 400(size 범위·잘못된 sort·인기순+커서)

목록 API는 조건이 많다. 정렬 둘, 페이지 방식 둘, 태그·검색어는 있을 수도 없을 수도 있고, 로그인 여부에 따라 보이는 글도 달라진다. 이 단계는 10-5·10-6과 같은 JPA로 만든다. 조건은 JPQL @Query 하나에 쓰고, 페이지·정렬은 Spring Data의 Pageable에 맡긴다. 같은 목록을 SQL을 직접 쓰는 MyBatis 동적 SQL로 짜 보는 것은 맨 아래 선택 칸이다. 채점(check)은 같아서 어느 쪽으로 짜도 통과한다.

명세서가 정한 응답은 두 모양이다.

{ "items": [ … ], "page": 0, "size": 20, "totalElements": 57, "hasNext": true }
{ "items": [ … ], "nextCursor": "17" }

페이지와 커서는 무엇이 다른가. 페이지 방식(page=3)은 "앞에서 60개 건너뛰고 20개"다. 그 사이 새 글이 생기면 경계가 밀려 같은 글을 두 번 보거나 하나를 놓친다. 커서 방식은 "마지막으로 본 글(id 17)보다 오래된 것부터 20개"라 새 글이 생겨도 밀리지 않는다. 무한 스크롤에 쓴다. 그런데 인기순에서는 커서가 깨진다. 좋아요 수가 바뀌면 순서 자체가 바뀌어서 "이 글 다음"이 의미를 잃는다. 그래서 명세서는 인기순 + 커서를 400으로 막았다.

#설계 포인트

  • 정렬은 사용자가 보낸 문자열로 만들지 않는다. Sort.by(query.sort())는 아무 속성 이름이나 받는다 — 엔티티 필드 이름이 그대로 바깥 입력이 되고, 없는 이름이면 Spring Data가 PropertyReferenceException을 던진다. JPQL에 "order by " + sort로 이어 붙이면 SQL 주입과 같은 문제가 된다(JPQL 주입). 정해 둔 Sort 둘 중에서 고른다: 최신순 Sort.by(desc("id")), 인기순 Sort.by(desc("likeCount"), desc("id")). 값은 항상 :tag처럼 바인딩으로 넣는다.
  • 있을 수도 없을 수도 있는 조건은 (:tag is null or ...)로. JPQL은 문자열 하나라 조건을 붙였다 뗐다 할 수 없다. 값이 null이면 앞쪽이 참이 되어 그 조건이 빠진 것과 같다. 조건이 더 늘어나 이 모양이 버거워지면 Specification·Querydsl을 쓰거나, SQL을 직접 쓰는 MyBatis로 간다(아래 선택 칸).
  • 같은 조건을 두 번 쓰지 않는다. 반환 타입이 Page면 Spring Data가 같은 JPQL에서 select count(*) 쿼리를 만들어 totalElements를 채운다. 커서 쿼리는 조건 문자열 상수(VISIBLE) 뒤에 and (:cursorId is null or p.id < :cursorId)만 이어 붙인다. 실측: 첫 페이지 결과가 size보다 적으면 개수가 이미 확정이라 count 쿼리를 생략한다.
  • "다음이 있나"는 하나 더 읽어서. 커서는 반환 타입을 Slice로 하고 PageRequest.of(0, size, 최신순)을 넘긴다. Spring Data가 size + 1개를 읽어 남으면 hasNext()가 참이다. 개수 쿼리는 없다. 어디서부터인지는 페이지 번호가 아니라 id < :cursorId가 정한다(keyset).
  • 작성자는 같은 쿼리에서, 태그는 따로 한 번에. @EntityGraph(attributePaths = "author")로 작성자를 JOIN해 함께 읽는다(글마다 작성자를 따로 읽으면 N+1). 태그는 컬렉션이라 join fetch p.tags와 페이징을 같이 쓰면 행이 태그 수만큼 불어나 LIMIT가 글 단위로 걸리지 않는다. 목록은 글만 페이징하고, 그 페이지 글 id들의 태그를 where p.id in :postIds 한 번으로 읽어 자바에서 붙인다.
  • Spring의 Page를 그대로 응답하지 않는다. Page를 JSON으로 내보내면 content·pageable·totalPages… 명세에 없는 모양이 나가고 Spring 버전에 따라 바뀐다. 명세의 {items, page, size, totalElements, hasNext} record로 옮긴다.
  • 쿼리 파라미터 묶음은 record 하나로. @Valid @ModelAttribute PostListQuery query로 받으면 @Min·@Max·@Pattern이 그대로 동작하고, 실패는 @RequestBody와 같은 MethodArgumentNotValidException으로 온다(10-2 처리기가 그대로 받는다). size=abc처럼 변환 실패도 같은 예외로 오는데, 기본 문구가 영어 내부 메시지라 fieldError.isBindingFailure()면 "형식이 올바르지 않습니다."로 바꾼다.
  • 두 값을 함께 봐야 하는 규칙(인기순 + 커서)은 애노테이션으로 걸기 어렵다. 서비스에서 확인하고, 필드 오류를 담은 400 예외를 던진다(ApiException에 errors를 실을 수 있게 넓힌다).

package org.example.board.common;


import java.util.List;


import org.example.board.common.ApiResponse.FieldErrorItem;


// 서비스가 "이 요청은 이 코드로 실패"를 알릴 때 던진다 — 전역 처리기가 공통 틀로 바꾼다
public class ApiException extends RuntimeException {


private final ErrorCode code;
private final List&lt;FieldErrorItem&gt; errors;

public ApiException(ErrorCode code) {
    this(code, code.defaultMessage());
}

public ApiException(ErrorCode code, String message) {
    this(code, message, List.of());
}

private ApiException(ErrorCode code, String message, List&lt;FieldErrorItem&gt; errors) {
    super(message);
    this.code = code;
    this.errors = errors;
}

// 애노테이션으로 못 거는 규칙(여러 값을 함께 봐야 하는 것)을 서비스에서 400으로
public static ApiException invalid(String field, String reason) {
    return new ApiException(ErrorCode.VALIDATION_FAILED, ErrorCode.VALIDATION_FAILED.defaultMessage(),
            List.of(new FieldErrorItem(field, reason)));
}

public ErrorCode code() {
    return code;
}

public List&lt;FieldErrorItem&gt; errors() {
    return errors;
}


}

package org.example.board.common;


import java.util.Comparator;
import java.util.List;


import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.http.HttpHeaders;
import org.springframework.http.ResponseEntity;
import org.springframework.http.converter.HttpMessageNotReadableException;
import org.springframework.web.HttpRequestMethodNotSupportedException;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.MissingServletRequestParameterException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.method.annotation.MethodArgumentTypeMismatchException;
import org.springframework.web.servlet.resource.NoResourceFoundException;


import org.example.board.common.ApiResponse.FieldErrorItem;


// 컨트롤러 밖으로 나온 예외를 한곳에서 공통 응답 틀로 바꾼다
@RestControllerAdvice
public class GlobalExceptionHandler {


private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

// 서비스가 던진 실패(401·403·404·409 …)
@ExceptionHandler(ApiException.class)
public ResponseEntity&lt;ApiResponse&lt;Void&gt;&gt; handleApi(ApiException e) {
    return fail(e.code(), e.getMessage(), e.errors());
}

// @Valid 검증 실패 — 필드별 이유를 errors에 담는다
@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity&lt;ApiResponse&lt;Void&gt;&gt; handleInvalid(MethodArgumentNotValidException e) {
    List&lt;FieldErrorItem&gt; errors = e.getBindingResult().getFieldErrors().stream()
            .map(fe -&gt; new FieldErrorItem(fe.getField(),
                    // ?size=abc 같은 변환 실패는 기본 문구가 영어 내부 메시지라 바꾼다
                    fe.isBindingFailure() ? &quot;형식이 올바르지 않습니다.&quot; : fe.getDefaultMessage()))
            .sorted(Comparator.comparing(FieldErrorItem::field))
            .toList();
    return fail(ErrorCode.VALIDATION_FAILED, ErrorCode.VALIDATION_FAILED.defaultMessage(), errors);
}

// 쿼리·경로 값의 타입이 틀림(?page=abc, /posts/abc)
@ExceptionHandler(MethodArgumentTypeMismatchException.class)
public ResponseEntity&lt;ApiResponse&lt;Void&gt;&gt; handleTypeMismatch(MethodArgumentTypeMismatchException e) {
    return fail(ErrorCode.VALIDATION_FAILED, ErrorCode.VALIDATION_FAILED.defaultMessage(),
            List.of(new FieldErrorItem(e.getName(), &quot;형식이 올바르지 않습니다.&quot;)));
}

// 필수 쿼리 파라미터 없음
@ExceptionHandler(MissingServletRequestParameterException.class)
public ResponseEntity&lt;ApiResponse&lt;Void&gt;&gt; handleMissingParam(MissingServletRequestParameterException e) {
    return fail(ErrorCode.VALIDATION_FAILED, ErrorCode.VALIDATION_FAILED.defaultMessage(),

private CursorResponse&lt;PostListItemResponse&gt; cursorList(PostListQuery query, Long loginUserId) {

    }
    Long cursorId = parseCursor(query.cursor());
    // 커서는 항상 첫 &quot;페이지&quot;(0)만 읽는다 — 어디서부터인지는 id &lt; cursorId가 정한다(keyset)

    return new CursorResponse&lt;&gt;(withTags(posts), next);
}

private Long parseCursor(String cursor) {

    try {

    }
}

힌트 1 — 목록 전용 리포지토리와 JPQL


쓰기용 PostRepository와 나눠 읽기 전용 인터페이스를 하나 둔다. Repository<Post, Long>을 상속하면 save·delete 같은 쓰기 메서드가 딸려 오지 않는다. 조건은 문자열 상수 하나로 두고 두 쿼리가 이어 붙여 쓴다.


public interface PostQueryRepository extends Repository<Post, Long> {

    String VISIBLE = """
            p.deletedAt is null
            and (p.visibility = org.example.board.post.Visibility.PUBLIC or p.author.id = :loginUserId)
            and (:tag is null or exists (select 1 from Post p2 join p2.tags t where p2.id = p.id and t.name = :tag))
            and (:q is null or p.title like concat('%', :q, '%'))
            """;

    @EntityGraph(attributePaths = "author")
    @Query("select p from Post p where " + VISIBLE)
    Page<Post> findVisible(Long loginUserId, String tag, String q, Pageable pageable);
}


JPQL은 테이블·컬럼이 아니라 엔티티·필드 이름(Post, p.deletedAt)으로 쓴다. 비로그인이면 loginUserId가 null이라 p.author.id = null은 참이 아니고, 공개 글만 남는다.






힌트 2 — 페이지: Pageable과 Sort


Sort sort = "popular".equals(query.sort())
        ? Sort.by(Sort.Order.desc("likeCount"), Sort.Order.desc("id"))
        : Sort.by(Sort.Order.desc("id"));
Page<Post> result = postQueryRepository.findVisible(userId, query.tag(), query.q(),
        PageRequest.of(page, query.size(), sort));
// result.getContent() · result.getTotalElements() · result.hasNext() → 명세의 응답 record로


Sort에 넣는 이름도 엔티티 필드 이름(likeCount)이다. JPQL에 order by를 직접 쓰지 않아도 Spring Data가 Pageable의 정렬을 붙인다.






힌트 3 — 커서: Slice와 id < :cursorId


@EntityGraph(attributePaths = "author")
@Query("select p from Post p where " + VISIBLE + " and (:cursorId is null or p.id < :cursorId)")
Slice<Post> findVisibleBefore(Long loginUserId, String tag, String q, Long cursorId, Pageable pageable);


커서 처음(cursor= 빈 값)은 cursorId를 null로 넘긴다. 항상 PageRequest.of(0, size, 최신순) — 몇 번째 페이지인지는 커서가 정하므로 페이지 번호는 늘 0이다. slice.hasNext()가 참이면 마지막 글의 id를 문자열로 nextCursor에 담는다.






힌트 4 — 태그를 IN 한 번으로


@Query("select new org.example.board.post.PostTagRow(p.id, t.name) from Post p join p.tags t where p.id in :postIds order by t.name")
List<PostTagRow> findTagsByPostIds(List<Long> postIds);


PostTagRow는 record PostTagRow(Long postId, String name). select new는 결과를 엔티티가 아닌 record로 바로 받는다(전체 이름을 쓴다). Collectors.groupingBy(PostTagRow::postId, mapping(PostTagRow::name, toList()))로 글 id별로 묶는다. 페이지가 비었으면 이 쿼리를 부르지 않는다(in ()).

페이지와 커서의 data 모양이 달라서 서비스가 Object(또는 두 record의 공통 인터페이스)를 돌려주게 한다. 실무에서는 두 API로 나누기도 한다(/posts와 /posts/feed). 이 명세서는 한 주소로 정했다.





#선택 — 같은 목록을 MyBatis로 짜 보기


JPA로 끝냈다면 여기는 건너뛰어도 된다. 조건이 많은 조회를 SQL로 직접 쓰는 방식을 익히고 싶을 때, 같은 API를 MyBatis 동적 SQL로 다시 짠다. 아래 MyBatis 대체 구현 코드 접기에 Mapper·XML·Service·DTO·설정의 파일 전문이 있다. 격리된 project DB에서 이 대체 구현을 컴파일하고 위 실행 칸 C1~C9를 모두 통과시켰다. 먼저 E5 MyBatis 첫걸음을 읽고, XML 문법은 W04 MyBatis XML 실무, 둘을 어떻게 나눠 쓰는지는 W05를 본다.


의존성 추가 — MyBatis는 이때 처음 넣는다(10-12를 할 때도 같다). Boot BOM에 없어서 버전을 직접 적는다(4.1.x가 Boot 4.1용).


implementation 'org.mybatis.spring.boot:mybatis-spring-boot-starter:4.1.0'


mybatis:
  mapper-locations: classpath:mapper/*.xml
  configuration:
    map-underscore-to-camel-case: true   # 컬럼 view_count → 필드 viewCount


동적 SQL 요점


    

  • 값이 있을 때만 조건을 붙인다: <if test="cond.tag != null">AND EXISTS (...)</if>. JPQL의 ? is null or와 달리 값이 없으면 SQL에서 그 줄이 아예 빠진다. <where>가 맨 앞 AND를 정리한다.
    • 

  • 정렬은 ORDER BY ${sort}로 끼우지 않는다(쿼리 파라미터가 SQL에 그대로 붙어 SQL 주입). <choose><when test="cond.sort == 'popular'">ORDER BY p.like_count DESC, p.id DESC</when><otherwise>ORDER BY p.id DESC</otherwise></choose>로 정해 둔 조각에서 고른다. 값은 항상 #{}.
    • 

  • 목록과 COUNT(*)의 WHERE가 같아야 totalElements가 맞는다. <sql id="visibleWhere">로 한 번 쓰고 <include refid="visibleWhere"/>로 두 곳에서 쓴다. 개수 쿼리는 Spring Data처럼 알아서 만들어 주지 않는다.
    • 

  • 커서는 LIMIT #{limit}에 size + 1을 넘겨 남으면 다음이 있다고 본다. XML 안에서 <는 &lt;로 쓴다(p.id &lt; #{cursorId}).
    • 

  • 태그는 <foreach collection="postIds" item="id" open="(" separator="," close=")">#{id}</foreach>로 IN 한 번.
    •
