#10-5. 게시글 작성 — JPA, 검증 규칙·태그·작성자는 토큰 주인

#상황

명세서의 게시글 작성 줄을 그대로 옮긴다.

API 규칙 성공 실패
POST /api/v1/posts 토큰 필수. title 5100자(앞뒤 공백 제거 후), content 없어도 됨(최대 10000자), tags 05개(각 1~20자, 소문자로, 중복 제거), visibility 기본 PUBLIC. 작성자 = 토큰 주인 201 + Location, data = 상세 400, 401

규칙 칸에 "다듬기"가 섞여 있다. 공백 제거, 소문자, 중복 제거, 기본값이다. 다듬은 다음에 검사한다는 순서가 중요하다. " abc "는 7글자지만 다듬으면 3글자라 400이다. ["Java", "java"]는 태그 두 개가 아니라 하나다.

쓰기는 JPA로 한다. 처음으로 엔티티끼리의 연관관계를 쓴다. 글 → 작성자는 다대일(@ManyToOne), 글 ↔ 태그는 다대다(@ManyToMany, 연결 테이블 post_tags)다.

#설계 포인트

  • 작성자는 토큰에서. 요청 본문으로 작성자를 받으면 남의 이름으로 글을 쓸 수 있다. 요청 record에 authorId 필드를 아예 만들지 않으면, JSON에 그 키가 와도 Jackson이 버린다.
  • 다듬기는 record 압축 생성자에서. JSON → record 변환 때 압축 생성자가 먼저 돌고, @Valid는 그 결과를 검사한다(10-3의 이메일과 같다). 서비스에서 다듬으면 검사는 다듬기 전 값으로 하게 된다.
  • 목록 원소 검증. List<@Size(min = 1, max = 20) String> tags처럼 타입 인자에 애노테이션을 붙이면 원소마다 검사한다. 실패 필드 이름은 tags[1]이 된다. @Size(max = 5)를 목록 자체에 붙이면 개수를 본다.
  • LAZY. 글을 읽을 때 작성자까지 매번 읽지 않게 기본을 지연 로딩으로 둔다. 필요할 때 한 번에 가져오는 법은 10-6에서 다룬다.
  • @Enumerated(EnumType.STRING). 기본값(ORDINAL)은 enum의 순번(0, 1)을 저장한다. 테이블은 ENUM('PUBLIC','PRIVATE') 문자열이라 반드시 STRING이다.
  • 같은 이름 태그를 동시에 처음 만들면? 두 요청이 동시에 "없다"를 보고 둘 다 INSERT하면 UNIQUE 위반으로 한쪽이 500이 난다. 이 단계에서는 넘어가지만, 실무에서는 생긴다(티켓 T-018에서 다룬다).

화면 시나리오의 서버·DB 흐름을 이 단계에서 바뀐 파일에 연결한다. 먼저 만들 것의 계약대로 직접 작성하고, 필요한 역할만 펼쳐 파일 전문과 비교한다.

이 단계의 처리 흐름:

  • 인터셉터 → userId=1. PostRequest 압축 생성자가 다듬는다: 제목 strip, 태그 [api, check], 공개 범위 PUBLIC. 그다음 @Valid

Controller — HTTP 연결

PostController.java. 매핑과 메서드의 입력·응답을 위 만들 것의 HTTP 계약과 대조한다. 이번 단계 매핑: @PostMapping("/api/v1/posts"). 변경된 메서드: create.

@PostMapping("/api/v1/posts")
public ResponseEntity<ApiResponse<PostResponse>> create(
        @LoginUser Long userId, @Valid @RequestBody PostCreateRequest request) {
    PostResponse created = postService.create(userId, request);
    return ResponseEntity.created(URI.create("/api/v1/posts/" + created.id()))
            .body(ApiResponse.created(created));
}

작성자 id는 JSON이 아니라 @LoginUser에서 온다. 인증 인터셉터가 먼저 실행되므로 토큰이 없는 요청은 본문이 깨져 있어도 401이다.

DTO — 요청·응답 필드

AuthorResponse.java, PostCreateRequest.java, PostResponse.java. 필드 이름·타입·검증·응답 형태를 위 만들 것과 대조한다. 변경된 메서드: from.

public PostCreateRequest {
    title = title == null ? null : title.strip();
    tags = tags == null ? List.of() : tags.stream()
            .map(t -> Objects.requireNonNullElse(t, "").strip().toLowerCase(Locale.ROOT))
            .distinct().toList();
    visibility = visibility == null ? "PUBLIC" : visibility;
}

이 압축 생성자가 다듬은 뒤 @Valid가 제목 5100자, 태그 05개·원소 1~20자, 본문 10000자, 공개 범위를 검사한다. PostResponse.from은 작성자 DTO와 이름순 태그를 만들며 해시를 내보내지 않는다. 어노테이션과 응답 필드 전문은 아래 DTO 접기에서 확인한다.

Service — 처리 순서

PostService.java. 위 서버 처리 순서가 어디에서 검증·조회·상태 변경으로 이어지는지 따라간다. 변경된 메서드: create. 트랜잭션 경계는 아래 코드의 @Transactional 위치에서 확인한다.

@Transactional
public PostResponse create(Long userId, PostCreateRequest request) {
    User author = userRepository.findById(userId)
            .orElseThrow(() -> new ApiException(ErrorCode.UNAUTHORIZED));
    Post post = new Post(author, request.title(), request.content(),
            Visibility.valueOf(request.visibility()), findOrCreateTags(request.tags()));
    postRepository.save(post);
    return PostResponse.from(post);
}

작성자 조회, 태그 조회·생성, 글과 연결 테이블 저장이 한 트랜잭션에 들어간다.

Post.java, Tag.java. 실제 테이블의 컬럼·외래키와 엔티티 매핑을 대조한다.

MyBatis / Mapper — 글·태그·연결 행을 직접 저장하기

선택 경로에서는 JPA Repository와 엔티티 매핑 대신 PostMapper SQL을 쓴다. Controller와 요청·응답 DTO는 그대로 두고, Service의 한 @Transactional 안에서 작성자 조회 → 태그 조회/생성 → 글 INSERT → post_tags INSERT를 수행한다. 글과 새 태그의 id는 useGeneratedKeys로 받아 다음 INSERT에 쓴다.

    if (author == null) throw new ApiException(ErrorCode.UNAUTHORIZED);
    Set&lt;Tag&gt; tags = findOrCreateTags(request.tags());
    Post post = new Post(author, request.title(), request.content(),
            Visibility.valueOf(request.visibility()), tags);
    postMapper.insertPost(post);
    for (Tag tag : tags) postMapper.linkTag(post.getId(), tag.getId());

}

        if (tag == null) {
            tag = new Tag(name);
            postMapper.insertTag(tag);
        }
        tags.add(tag);
    }
    return tags;

힌트 3 — 요청 record에서 다듬기


public PostRequest {
    title = title == null ? null : title.strip();
    tags = tags == null ? List.of() : tags.stream()
            .map(t -> Objects.requireNonNullElse(t, "").strip().toLowerCase(Locale.ROOT))
            .distinct()
            .toList();
    visibility = visibility == null ? "PUBLIC" : visibility;
}


visibility를 String + @Pattern(regexp = "PUBLIC|PRIVATE")로 받으면 틀린 값이 errors의 visibility 필드로 나온다. enum 타입으로 바로 받으면 "SECRET"은 JSON 변환 단계에서 실패해 BAD_JSON이 된다.
