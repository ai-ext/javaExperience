EchoController.java 한 파일에 두 방식을 만듭니다

먼저 Map, 그다음 DTO로 같은 본문을 받습니다.

만들 위치src/main/java/org/example/start/EchoController.java
첫 메서드POST /api/start/echo/{id}

본문을 Map으로 받습니다.

두 번째 메서드POST /api/start/echo/{id}/dto

본문을 EchoBody record로 받습니다.

EchoBody와 EchoResponse는 모두 EchoController 안에 선언합니다. 별도 Java 파일을 만들지 않습니다.

원문 EchoController.java 전체직접 작성할 한 파일
package org.example.start;

import java.util.List;
import java.util.Map;

import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestHeader;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class EchoController {

    // 본문 DTO — JSON의 title·tags만 받는다(모르는 필드는 버린다)
    public record EchoBody(String title, List<String> tags) {
    }

    // 응답 — 어느 자리에서 온 값인지 이름에 적었다
    public record EchoResponse(Long fromPath, String fromQuery, String fromHeader, Object fromBody) {
    }

    // 본문을 Map으로 — 들어온 JSON을 키·값 그대로 받는다
    @PostMapping("/api/start/echo/{id}")
    public EchoResponse echo(@PathVariable Long id,
                             @RequestParam String q,
                             @RequestHeader("X-Client") String client,
                             @RequestBody Map<String, Object> body) {
        return new EchoResponse(id, q, client, body);
    }

    // 본문을 DTO로 — 정한 필드만 받는다
    @PostMapping("/api/start/echo/{id}/dto")
    public EchoResponse echoDto(@PathVariable Long id,
                                @RequestParam String q,
                                @RequestHeader("X-Client") String client,
                                @RequestBody EchoBody body) {
        return new EchoResponse(id, q, client, body);
    }
}

0-3 · 경로 id04 / 21

경로의 7은 Long id로 들어갑니다

Spring이 경로 글자를 Long 값으로 바꿉니다.

① · 경로/api/start/echo/7→@PathVariable Long id→fromPath: 7

@PostMapping("/api/start/echo/{id}")의 {id}와 매개변수 이름 id를 맞추세요.

0-3 · 쿼리 q05 / 21

쿼리 q=spring은 String q로 들어갑니다

주소의 물음표 뒤 값은 요청 매개변수입니다.

② · 쿼리?q=spring→@RequestParam String q→fromQuery: "spring"

@RequestParam은 기본적으로 필수입니다. q를 뺐을 때의 400은 뒤에서 실험합니다.

0-3 · 헤더 X-Client06 / 21

X-Client 헤더는 String client로 들어갑니다

하이픈이 있는 헤더 이름은 어노테이션 괄호에 정확히 적습니다.

③ · 헤더X-Client: javaExperience→@RequestHeader("X-Client") String client→fromHeader: "javaExperience"

헤더 이름 X-Client는 Java 변수 이름으로 쓸 수 없어 client에 연결합니다.

네 값이 EchoResponse의 네 키가 됩니다

이번 실험에서 Object는 Map과 DTO를 한 응답 모양으로 비교하기 위한 선택입니다.

EchoController 안의 응답 record
public record EchoResponse(Long fromPath, String fromQuery, String fromHeader, Object fromBody) {}
Controller 반환
return new EchoResponse(id, q, client, body);
① · 경로id = 7L→Long fromPath→fromPath: 7
② · 쿼리q = "spring"→String fromQuery→fromQuery: "spring"

0-3 · 본문 DTO10 / 21

EchoBody는 같은 파일 안의 record입니다

DTO는 title과 tags만 선언합니다.

EchoController.java 내부
public record EchoBody(String title, List<String> tags) {}
DTO가 받는 값title = "첫 요청"tags = ["java", "spring"]
DTO에 없는 키extra = "덤"

이 실습의 DTO 역직렬화 결과에는 포함되지 않습니다.

List<String>은 문자열 목록입니다. EchoBody는 별도 파일이 아닙니다.

0-3 · Map·DTO 비교13 / 21

Map과 DTO의 extra를 나란히 비교합니다

같은 입력이어도 Java에서 받는 타입에 따라 남는 키가 다릅니다.

Map<String, Object>extra 유지

body.get("title")은 Object를 돌려줍니다. titel 오타도 컴파일은 됩니다.

EchoBody recordextra 무시

body.title()은 String입니다. 메서드 이름 오타는 컴파일에서 걸립니다.

실무 API에서는 입력 모양을 DTO로 정하는 편이 일반적입니다.

0-3 · 본문은 한 번14 / 21

본문은 한 번 읽는 한 덩어리입니다

정상 A·B를 본 뒤 echoDto에 두 번째 @RequestBody를 추가해 보세요.

첫 번째 본문 매개변수@RequestBody EchoBody body

본문을 읽습니다.

두 번째로 추가한 매개변수@RequestBody Map<String,Object> raw

읽을 본문이 남지 않습니다.

예상 결과 · 요청 BHTTP 400Required request body is missing

컴파일은 통과하고 요청 시점에 실패합니다.

실험 뒤 두 번째 @RequestBody를 지우세요. 여러 값은 DTO 하나에 담습니다.

0-3 · CORS 사전 요청20 / 21

브라우저는 X-Client 허용을 먼저 묻습니다

이 실험에서는 서버의 400·415가 아니라 브라우저가 본 POST를 막습니다.

먼저 OPTIONS 사전 요청Access-Control-Request-Headers: content-type,x-client

브라우저가 보낼 헤더를 허락받으려 합니다.

X-Client 허용을 지우면Access-Control-Allow-Headers에 x-client 없음

브라우저가 이후 POST를 보내지 않습니다.

CorsConfig의 allowedHeaders에서 X-Client를 잠깐 지우고 관찰하세요. Postman은 CORS를 적용하지 않습니다. 끝나면 허용을 복원하세요.

요청 한 통에는 값이 실리는 자리가 네 곳 있다. 경로(/echo/7), 쿼리(?q=spring), 헤더(X-Client: javaExperience), 본문(JSON)이다. 서버는 이 네 자리를 각각 다른 어노테이션으로 받는다. 이걸 짝지어 두지 않으면 "@PathVariable이 뭐였더라", "@RequestBody를 두 개 놓으면 왜 안 되지"에서 계속 막힌다.

이 단계에서는 **받은 것을 그대로 돌려주는 API(echo)**를 만든다. 응답의 키 이름에 fromPath처럼 어느 자리에서 왔는지를 적어 두었다. 그래서 버튼을 누르면 내가 보낸 값이 서버의 어느 매개변수로 들어갔는지 바로 보인다. 본문을 Map으로 받는 방법과 DTO로 받는 방법도 나란히 비교한다.

package org.example.start;

import java.util.List;
import java.util.Map;

import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestHeader;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class EchoController {

    // 본문 DTO — JSON의 title·tags만 받는다(모르는 필드는 버린다)
    public record EchoBody(String title, List<String> tags) {
    }

    // 응답 — 어느 자리에서 온 값인지 이름에 적었다
    public record EchoResponse(Long fromPath, String fromQuery, String fromHeader, Object fromBody) {
    }

    // 본문을 Map으로 — 들어온 JSON을 키·값 그대로 받는다
    @PostMapping("/api/start/echo/{id}")
    public EchoResponse echo(@PathVariable Long id,
                             @RequestParam String q,
                             @RequestHeader("X-Client") String client,
                             @RequestBody Map<String, Object> body) {
        return new EchoResponse(id, q, client, body);
    }

    // 본문을 DTO로 — 정한 필드만 받는다
    @PostMapping("/api/start/echo/{id}/dto")
    public EchoResponse echoDto(@PathVariable Long id,
                                @RequestParam String q,
                                @RequestHeader("X-Client") String client,
                                @RequestBody EchoBody body) {
        return new EchoResponse(id, q, client, body);
    }
}

#요청 글과 한 줄씩 맞춰 보기

아래 직접 확인의 요청 A가 서버에 도착한 모양이다. HTTP 클라이언트가 자동으로 붙이는 Host·User-Agent 같은 머리글은 빼고 주요 줄만 옮겼다.

POST /api/start/echo/7?q=spring       ← @PostMapping · ① 경로의 7 · ② 쿼리 q
Content-Type: application/json        ← "본문은 JSON이에요" — 없거나 다르면 415
X-Client: javaExperience              ← ③ 헤더 → @RequestHeader("X-Client")

{"title":"첫 요청","tags":["java","spring"],"extra":"덤"}   ← ④ 본문 → @RequestBody
자리 HTTP 요청에서 Spring에서 없으면
① 경로 URL 안 /echo/7 @PathVariable Long id + 경로의 {id} 다른 주소라 404
② 쿼리 ?q=spring @RequestParam String q 400(필수일 때)
③ 헤더 -H 'X-Client: javaExperience' @RequestHeader("X-Client") String client 400(필수일 때)
④ 본문 -d '{...}' + -H 'Content-Type: application/json' @RequestBody 타입 이름 — 하나만 400(본문 없음), 415(형식 다름)

#본문은 왜 @RequestBody 하나뿐인가

경로·쿼리·헤더는 요청 맨 앞(주소·머리글)에 있어서 몇 번이든 꺼내 읽을 수 있다. 본문은 요청 끝에 붙은 한 덩어리 흐름(스트림)이다. 서버는 그것을 처음부터 끝까지 한 번 읽는다. 첫 번째 @RequestBody가 다 읽고 나면 두 번째 @RequestBody가 읽을 것이 남아 있지 않다. 그래서 400이 난다(아래 망가뜨리기 ①).

본문에서 여러 값을 받고 싶으면 그 값들을 다 담는 객체 하나를 만든다.

#Map으로 받기 vs DTO로 받기

Map<String, Object> DTO(record EchoBody)
모르는 키(extra) 그대로 담긴다 버려진다
값 꺼내기 body.get("title") → Object라 (String)으로 바꿔야 한다. 오타 body.get("titel")도 컴파일된다(결과는 null) body.title() → 이미 String. 오타는 컴파일 에러
타입이 틀린 값("tags": 3) 그대로 담긴다 400(변환 실패)
어디에 쓰나 이 echo처럼 "뭐가 오는지 그대로 보기" 보통의 API 전부 — 받을 모양을 코드로 못 박는다

실무 API에서는 DTO로 받는다. 1-1의 채점 기준에도 "Map이 아니라 전용 클래스로 받는다"가 있다.

Postman에서 Content-Type: application/json을 지정하지 않고 폼 본문을 선택하면 application/x-www-form-urlencoded(HTML 폼 형식)로 보낼 수 있다.


WARN ... .w.s.m.s.DefaultHandlerExceptionResolver : Resolved [org.springframework.web.HttpMediaTypeNotSupportedException: Content-Type 'application/x-www-form-urlencoded;charset=UTF-8' is not supported]


브라우저에서 본문을 문자열로만 보내고 Content-Type을 적지 않으면 브라우저가 text/plain;charset=UTF-8을 붙인다. 그때는 Content-Type 'text/plain;charset=UTF-8' is not supported(요청 D와 같다)가 나온다. 응답 헤더 Accept: application/json, application/*+json이 서버가 받는 형식이다.


#③ 쿼리 q를 빼고 보낸다 → 400 (요청 C)


WARN ... Resolved [org.springframework.web.bind.MissingServletRequestParameterException: Required request parameter 'q' for method parameter type String is not present]


#④ 헤더 X-Client를 빼고 보낸다 → 400


WARN ... Resolved [org.springframework.web.bind.MissingRequestHeaderException: Required request header 'X-Client' for method parameter type String is not present]


없어도 되는 값이면 @RequestParam(required = false), @RequestHeader(value = "X-Client", required = false)로 쓴다. 그러면 값이 없을 때 null이 들어온다.


#⑤ 경로에 숫자 대신 글자 → 400


POST /api/start/echo/abc?q=spring


WARN ... Resolved [org.springframework.web.method.annotation.MethodArgumentTypeMismatchException: Method parameter 'id': Failed to convert value of type 'java.lang.String' to required type 'java.lang.Long'; For input string: "abc"]


경로·쿼리·헤더는 원래 전부 글자다. Long·int로 선언하면 Spring이 대신 바꿔 준다. 바꿀 수 없는 글자가 오면 메서드에 들어가기 전에 400이 난다.


#⑥ 닫는 괄호가 없는 JSON → 400


본문을 {"title": "깨짐"으로 보낸다.


WARN ... Resolved [org.springframework.http.converter.HttpMessageNotReadableException: JSON parse error: Unexpected end-of-input: expected close marker for Object (start marker at [Source: REDACTED (`StreamReadFeature.INCLUDE_SOURCE_IN_LOCATION` disabled); byte offset: #UNKNOWN])]


Source: REDACTED는 Jackson 3가 보안상 본문 내용을 로그에 싣지 않는다는 표시다. 무엇을 보냈는지는 실행 패널의 요청 본문에서 확인한다.


#⑦ CORS 설정에서 X-Client를 뺀다 → 브라우저 요청은 실패


CorsConfig의 .allowedHeaders(...)에서 "X-Client"를 지우고 다시 띄운다. 실행 패널의 브라우저 요청은 "CORS로 막혔어요"로 실패한다. preflight 헤더는 브라우저가 관리하므로 아래 Postman 절차로 OPTIONS 응답을 직접 살펴본다.



Postman 설정 · OPTIONS preflight


    

  • URL: 상단 API 서버 주소 + /api/start/echo/7?q=spring
    • 

  • Method: OPTIONS
    • 

  • Headers: Origin: http://localhost:3000, Access-Control-Request-Method: POST, Access-Control-Request-Headers: content-type,x-client
    • 

  • Postman에서는 CORS 검사를 하지 않으므로 서버가 돌려준 헤더를 직접 비교한다.
    • 






HTTP/1.1 200
Access-Control-Allow-Origin: http://localhost:3000
Access-Control-Allow-Methods: GET,POST,PUT,PATCH,DELETE,OPTIONS
Access-Control-Allow-Headers: content-type


(실측은 Origin: http://localhost:3020으로 했다. 출처 값만 다르다.) x-client를 허락해 달라고 물었는데 Allow-Headers에 content-type만 돌아왔다. 그래서 브라우저가 본 요청을 보내지 않는다. 서버 로그에는 아무것도 남지 않는다. 막은 쪽이 서버가 아니라 브라우저이기 때문이다.
