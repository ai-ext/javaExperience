# 말하기 카드

리뷰어가 그날 묻는 질문이다. "문제 상황 → 원인 → 선택 → 결과" 순서로 답한다. **답에 들어가야 할 것**의 세 줄이 모두 나오면 통과다. **근거**는 `~/research/java-onboarding/`의 문서 번호와 절, 또는 `course/spec-v2.md`의 절이다.

## D01 프로젝트 뼈대

### TC-D01-1
**질문** `application.yml`의 `server.port`를 바꿨는데 서버가 예전 포트로 뜹니다. 어디부터 확인하나요?
**답에 들어가야 할 것**
- 커맨드라인 인자와 OS 환경 변수는 `application.yml`보다 우선하므로, 같은 키가 그쪽에 있으면 yml 수정은 반영되지 않는다
- 활성 프로파일의 설정(`application-local.yml` 또는 `on-profile` 문서)이 기본 문서의 같은 키를 덮어쓴다
- 값은 키 단위로 덮어써지므로 추측하지 않고, 로컬에서 연 `/actuator/env`의 출처 목록이나 기동 로그로 어느 출처가 이겼는지 확인한다
**근거** 06 §15

### TC-D01-2
**질문** prod 서버가 로컬 DB 주소로 떠 있었습니다. 원인으로 무엇을 의심하나요?
**답에 들어가야 할 것**
- 활성 프로파일을 지정하지 않으면 `default` 프로파일로 기동해 prod 문서가 적용되지 않는다
- 프로파일 전용 문서(`on-profile` 문서, `application-prod.yml`) 안에서는 `spring.profiles.active`를 지정할 수 없으므로, 활성화는 실행 인자나 환경 변수로 한다
- 기동 로그에 찍히는 활성 프로파일 줄로 어떤 프로파일이 켜졌는지 먼저 확인한다
**근거** 06 §15

### TC-D01-3
**질문** DB 비밀번호를 `application.yml`에 적어 커밋했습니다. 무엇이 문제고 어떻게 바꾸나요?
**답에 들어가야 할 것**
- 파일에서 지워도 git 이력에 평문이 남으므로, 이미 커밋된 비밀번호는 노출된 것으로 보고 교체한다
- Spring Boot에는 내장 프로퍼티 암호화가 없어서 yml에는 `${DB_PASSWORD}` 같은 자리표시자만 둔다
- 실제 값은 환경 변수(또는 `configtree:`로 마운트한 파일)로 주입한다. PG 비밀키도 같은 방식이다
**근거** 06 §15, spec-v2 §7

### TC-D01-4
**질문** 동시 요청 세 건의 로그가 섞여서 한 사용자 요청만 골라낼 수 없었습니다. 요청 ID 필터를 어떻게 만들었나요?
**답에 들어가야 할 것**
- 서블릿 필터가 요청 시작에서 요청 ID를 `MDC.put`하고, 로그 패턴에 그 키를 넣어 모든 줄에 찍는다
- `finally`에서 MDC를 지운다. 톰캣 스레드는 재사용되므로 지우지 않으면 다음 요청 로그에 이전 ID가 남을 수 있다
- MDC는 스레드 단위라 `@Async`나 별도 스레드풀로 넘어가면 전파되지 않으므로 `TaskDecorator`로 복사한다
**근거** 06 §8

### TC-D01-5
**질문** 헬스 체크(liveness)에 DB 연결 확인을 넣자는 제안을 받았습니다. 어떻게 답하나요?
**답에 들어가야 할 것**
- liveness에 DB 같은 외부 시스템을 넣으면 DB가 잠깐 끊겼을 때 모든 인스턴스가 재시작돼 장애가 커진다
- 외부 의존 상태는 readiness에서 다룰지 판단한다. 넣으면 그 시스템 장애 때 인스턴스가 트래픽에서 빠진다
- Boot는 기본으로 HTTP에 `health`만 노출하고, 명세도 `/actuator/health` 외의 actuator는 공개하지 않는다
**근거** 10 §1, spec-v2 §3

## D02 공통 기반

### TC-D02-1
**질문** 금칙어 목록을 DB에서 읽어 메모리에 올리는 코드를 `@PostConstruct`가 아니라 `ApplicationReadyEvent`에 둔 이유는?
**답에 들어가야 할 것**
- `@PostConstruct`는 빈을 만드는 도중(싱글톤 생성 락 안)에 실행되므로, 여기서 DB 적재 같은 무거운 일을 하면 그만큼 기동이 늦어진다
- `@PostConstruct` 안에서 같은 클래스의 `@Transactional` 메서드를 불러도 프록시를 거치지 않아 트랜잭션이 걸리지 않는다
- `ApplicationReadyEvent`는 컨텍스트 refresh와 runner 실행이 끝난 뒤 발행되므로 기동 후 적재는 여기나 `ApplicationRunner`에 둔다
**근거** 06 §14

### TC-D02-2
**질문** 금칙어 검사기에 마지막 검사 결과를 담는 필드 `lastMatched`를 두자는 코드가 올라왔습니다. 리뷰에서 뭐라고 하나요?
**답에 들어가야 할 것**
- Spring 빈의 기본 스코프는 singleton이라 모든 요청 스레드가 같은 인스턴스를 공유한다
- 요청마다 바뀌는 값을 인스턴스 필드에 쓰면 동시 요청끼리 덮어써 다른 사용자의 값이 섞인다
- 요청별 값은 지역 변수·인자·반환값으로 다루고, 필드에는 `final` 의존성과 불변 설정만 둔다
**근거** 06 §1

### TC-D02-3
**질문** 닉네임 정규화 함수는 static 유틸로, 금칙어 검사기는 빈으로 만들었습니다. 무엇을 기준으로 나눴나요?
**답에 들어가야 할 것**
- 입력만 받아 결과를 돌려주고 외부 자원이 없는 순수 함수는 static 유틸로 둔다
- DB·설정·다른 빈에 의존하거나 트랜잭션·AOP가 필요한 것은 빈으로 만들어 주입받는다
- 빈은 생성자 주입으로 테스트 대역을 넣을 수 있지만, static 호출은 대역으로 바꾸기 어렵다
**근거** 06 §1

### TC-D02-4
**질문** 전역 예외 처리기에서 `IllegalArgumentException`을 전부 400으로 바꾸자는 제안이 있습니다. 어떻게 답하나요?
**답에 들어가야 할 것**
- `IllegalArgumentException`은 서버 버그에서도 나므로, 일괄 400으로 바꾸면 서버 결함이 클라이언트 잘못으로 보이고 5xx 지표에서 사라진다
- 클라이언트 잘못이 명백한 경우만 도메인 예외로 정의해 4xx로 매핑하고, 예상하지 못한 예외는 500으로 둔다
- 모든 에러는 ProblemDetail(`application/problem+json`)로 내고, 클라이언트는 `type`으로 분기한다
**근거** 06 §10, spec-v2 §2

### TC-D02-5
**질문** 여러 클래스에서 `@Value`로 읽던 금칙어 설정을 `@ConfigurationProperties` 하나로 묶었습니다. 무엇이 좋아졌나요?
**답에 들어가야 할 것**
- 관련 설정이 한 타입에 모이고, `@Validated`를 붙이면 잘못된 값이 기동 시점에 실패한다
- relaxed binding으로 kebab-case, camelCase, 환경 변수 표기를 모두 받는다
- `@Value`는 relaxed binding이 제한적이라, 키를 정규형(kebab-case)으로 쓰지 않으면 다른 표기의 값을 못 찾을 수 있다
**근거** 06 §14

## D03 회원·인증

### TC-D03-1
**질문** permitAll 규칙을 관리자 규칙보다 앞에 두면 어떤 일이 생기나요?
**답에 들어가야 할 것**
- 인가 규칙은 위에서부터 첫 번째로 매치된 것만 적용된다
- 넓은 패턴이 앞에 있으면 뒤의 관리자 규칙은 평가되지 않는다
- 테스트로 관리자 경로에 USER 토큰을 보내 403을 확인한다
**근거** 06 §6

### TC-D03-2
**질문** 프론트(`http://localhost:3000`)에서만 로그인 요청이 막히고 curl로는 성공합니다. 왜 그런가요?
**답에 들어가야 할 것**
- 브라우저는 다른 출처로 JSON 본문이나 `Authorization` 헤더를 보낼 때 먼저 `OPTIONS` preflight를 보내고, curl은 CORS를 검사하지 않는다
- preflight에는 인증 정보가 없으므로 CORS 처리가 인증보다 먼저 돼야 한다. 그렇지 않으면 401·403으로 막히고 브라우저에는 CORS 에러로만 보인다
- `http.cors(...)`로 Security 체인에 CORS를 붙이고, 허용 출처는 명세의 두 곳만 둔다
**근거** 06 §6, spec-v2 §3

### TC-D03-3
**질문** 토큰 없이 `GET /api/members/me`를 부르면 401, USER 토큰으로 `GET /api/admin/reports`를 부르면 403입니다. 두 응답을 어디서 만들었나요?
**답에 들어가야 할 것**
- 401(인증 없음·만료)은 `AuthenticationEntryPoint`가, 403(인증됐지만 권한 없음)은 `AccessDeniedHandler`가 만든다
- URL 인가 단계의 401·403은 필터 체인에서 처리돼 `@RestControllerAdvice`까지 오지 않으므로, 두 핸들러에서 직접 응답을 쓴다
- 두 응답도 다른 에러와 같은 ProblemDetail 형식으로 낸다
**근거** spec-v2 §2, 06 §6

### TC-D03-4
**질문** 로그인 실패 때 "없는 이메일"과 "틀린 비밀번호"를 구분해 알려 주면 안 되는 이유는?
**답에 들어가야 할 것**
- 구분해 알려 주면 응답만으로 가입된 이메일을 알아낼 수 있다
- 명세대로 두 경우 모두 같은 401 `/errors/unauthorized`로 응답한다
- 비밀번호는 BCrypt 해시로 저장하고 `PasswordEncoder.matches`로 비교한다. 해시에 솔트가 들어 있어 같은 비밀번호도 매번 다른 해시가 나온다
**근거** spec-v2 §5-1

### TC-D03-5
**질문** JWT 필터는 토큰이 없을 때 401을 바로 내지 않고 다음 필터로 넘깁니다. 왜 그렇게 했나요?
**답에 들어가야 할 것**
- 공개 경로(가입·로그인·공개 GET)도 같은 필터를 지나므로, 토큰이 없다고 막으면 공개 API까지 막힌다
- 필터는 토큰이 유효할 때만 `SecurityContextHolder`에 인증을 올리고, 막을지는 인가 규칙(`authorizeHttpRequests`)이 정한다
- 토큰이 없거나 잘못된 요청이 보호 경로에 오면 진입점(`AuthenticationEntryPoint`)이 401을 낸다
**근거** 06 §6, 05 §3-3

## D04 게시글 쓰기 (JPA)

### TC-D04-1
**질문** `PostStatus` enum 맨 앞에 `DRAFT`를 추가했더니 기존 글의 상태가 전부 바뀌어 보입니다. 원인과 예방은?
**답에 들어가야 할 것**
- `@Enumerated`의 기본값은 `ORDINAL`이라 enum의 순서 번호가 저장된다
- 중간에 상수를 끼우면 기존 숫자가 다른 상수를 가리켜 데이터가 조용히 바뀐다
- `@Enumerated(EnumType.STRING)`으로 이름을 저장한다. 대신 상수 이름을 바꿀 때는 데이터 이전을 함께 한다
**근거** spec-v2 §6

### TC-D04-2
**질문** `Post` 엔티티에 `@Setter`와 `@AllArgsConstructor`를 두지 않고 `protected` 기본 생성자와 정적 팩토리를 쓴 이유는?
**답에 들어가야 할 것**
- JPA는 기본 생성자(public 또는 protected)가 필요하다. `protected`로 두면 다른 코드가 빈 엔티티를 `new`로 만들지 못한다
- 정적 팩토리(`Post.create(...)`)에서 필수값과 규칙을 검사해 잘못된 상태의 엔티티가 생기지 않게 한다
- setter 대신 의미 있는 메서드(`edit`, `delete`)로만 상태를 바꾸면 변경 규칙이 한곳에 모인다
**근거** 06 §4

### TC-D04-3
**질문** 구현이 하나뿐인데 `PostService` 인터페이스와 `PostServiceImpl`을 두었습니다. 왜 두었고, 어디부터 과잉인가요?
**답에 들어가야 할 것**
- Spring은 CGLIB 클래스 프록시로 인터페이스 없이도 `@Transactional`을 적용하므로, AOP 때문에 인터페이스가 필요하지는 않다
- 인터페이스가 값을 하는 곳은 구현이 둘 이상이거나 바뀔 것이 분명한 경계다. 외부 연동이나 테스트용 Fake가 그 예다
- 쌍을 팀 관례로 둔다면 그 이유(구현 은닉, 인터페이스 기준 테스트)를 말할 수 있어야 하고, 근거 없이 모든 클래스에 쌍을 만들면 과잉이다
**근거** 06 §12

### TC-D04-4
**질문** 제목이 공백 문자만 있는 글이 저장됐습니다. 검증을 어디에 어떻게 두었나요?
**답에 들어가야 할 것**
- 요청 DTO에 Bean Validation(`@NotBlank`, `@Size(max = 100)`)을 붙이고 컨트롤러 파라미터에 `@Valid`를 둔다
- `@NotEmpty`나 `@NotNull`은 공백만 있는 문자열을 통과시키므로, 명세의 "공백만 불가"는 `@NotBlank`로 표현한다
- 검증 실패(`MethodArgumentNotValidException`)는 400 ProblemDetail로 바꾸고 `errors[]`에 `{field, reason}`을 담는다
**근거** spec-v2 §5-2

## D05 조회·수정·삭제 (JPA)

### TC-D05-1
**질문** 글 수정 서비스에서 `save()`를 부르지 않았는데 UPDATE가 나갑니다. 왜 그런가요?
**답에 들어가야 할 것**
- 트랜잭션 안에서 조회한 엔티티는 영속성 컨텍스트가 관리하며, 조회 시점의 상태를 따로 가지고 있다
- flush 시점(커밋 직전, 또는 관련 테이블을 읽는 JPQL 실행 직전)에 그 상태와 비교해 바뀐 필드를 UPDATE로 보낸다
- 그래서 변경은 `@Transactional` 서비스 메서드 안에서 엔티티 메서드로 하고, SQL 로그로 UPDATE가 나가는 시점을 확인한다
**근거** 05 §3-4, 06 §16

### TC-D05-2
**질문** 댓글 목록 API에서 댓글 20개의 작성자 닉네임을 보여 주는데 SQL이 21번 나갑니다. 원인과 해결은?
**답에 들어가야 할 것**
- 댓글을 한 번 조회한 뒤, 지연 로딩인 `member`를 댓글마다 접근하면서 작성자마다 회원 조회가 한 번씩 더 나간다(N+1)
- `join fetch`(또는 `@EntityGraph`)로 작성자를 함께 가져오거나, 필요한 컬럼만 DTO로 조회한다
- SQL 로그나 Hibernate 통계로 쿼리 수를 세고, 그 수를 테스트로 고정한다
**근거** 05 §3-4, 06 §16

### TC-D05-3
**질문** 남의 글을 수정하려는 요청과 삭제된 글을 수정하려는 요청에 각각 무엇을 돌려주고, 어떤 순서로 검사하나요?
**답에 들어가야 할 것**
- 대상이 없거나 삭제·숨김 상태면 404 `/errors/not-found`다
- 대상은 있지만 요청자가 작성자가 아니면 403 `/errors/forbidden`이다
- 존재 여부를 먼저 보고 그다음 작성자를 검사하며, 작성자는 요청 본문이 아니라 토큰의 회원 ID와 글의 `member_id`로 비교한다
**근거** spec-v2 §5-2, 05 §3-3

### TC-D05-4
**질문** 좋아요 `PUT`을 두 번 보내도 204이고 수는 한 번만 오릅니다. 동시에 두 번 와도 그런가요? 어떻게 보장했나요?
**답에 들어가야 할 것**
- `post_like`의 UNIQUE(`post_id`, `member_id`)가 DB에서 중복 행을 막는다
- 동시 요청 중 하나가 중복 키 예외를 받으면 이미 눌린 상태로 보고 204를 돌려준다
- `like_count`는 읽고 더해서 저장하지 않고, 새 행이 실제로 들어갔을 때만 `like_count = like_count + 1` UPDATE로 올린다
**근거** spec-v2 §5-2, 07 #12

### TC-D05-5
**질문** 글 삭제를 행 삭제 대신 `status = DELETED`로 바꾸는 소프트 삭제로 했습니다. 이유와 대가는?
**답에 들어가야 할 것**
- 신고(`report`)와 감사 로그가 글을 가리키므로, 행을 남겨야 나중에 추적할 수 있다
- 대가는 모든 조회에 상태 조건을 빠뜨리지 않아야 한다는 것이다. 하나라도 빠지면 삭제된 글이 노출된다
- 목록 인덱스를 (`status`, `id`)로 둔 것도 모든 목록 조회에 이 상태 조건이 붙기 때문이다
**근거** spec-v2 §6

## D06 목록·검색 (MyBatis)

### TC-D06-1
**질문** 정렬 키를 요청 파라미터로 받아 `ORDER BY ${sort}`로 넣는 코드가 있습니다. 무엇이 문제고 어떻게 바꾸나요?
**답에 들어가야 할 것**
- `${}`는 값을 SQL 문자열에 그대로 끼워 넣으므로 SQL 인젝션이 가능하다
- `#{}`는 PreparedStatement 파라미터로 바인딩돼 안전하지만, 값으로만 들어가므로 컬럼명이나 `ORDER BY` 대상에는 쓸 수 없다
- 정렬은 허용 목록(명세상 `latest`만)으로 받고, 서버가 고정된 SQL 조각을 고른다
**근거** 06 §16, spec-v2 §5-3

### TC-D06-2
**질문** 글 목록(`WHERE status = 'ACTIVE' ... ORDER BY id DESC LIMIT 20`)이 데이터가 늘자 느려졌습니다. 인덱스를 어떻게 정하고 확인했나요?
**답에 들어가야 할 것**
- 동등 조건 컬럼을 앞에, 정렬 컬럼을 뒤에 둔 (`status`, `id`) 인덱스면 인덱스가 정렬을 제공해 filesort 없이 LIMIT만큼 읽고 멈춘다
- EXPLAIN의 `type`, `key`, `rows`, `Extra`(Using filesort 여부)를 인덱스 전후로 비교하고, `EXPLAIN ANALYZE`로 실제 읽은 행 수를 본다
- 커서 페이징은 `id < 마지막 id`로 이어 읽어, offset처럼 앞쪽 행을 읽고 버리지 않는다
**근거** 07 §2, 07 §5

### TC-D06-3
**질문** 같은 트랜잭션에서 JPA로 글 제목을 고친 직후 MyBatis로 목록을 읽었더니 옛 제목이 나왔습니다. 왜 그런가요?
**답에 들어가야 할 것**
- JPA의 변경은 flush 전까지 영속성 컨텍스트에만 있고 DB에는 아직 UPDATE가 나가지 않았다
- Hibernate의 자동 flush는 JPQL 실행 전에 일어나며, MyBatis가 JDBC로 직접 보내는 SQL은 Hibernate가 모르므로 flush를 일으키지 않는다
- MyBatis 조회 전에 명시적으로 flush하고, 두 도구가 같은 트랜잭션(같은 커넥션)에 참여하는지 실험으로 확인한다
**근거** 06 §16

### TC-D06-4
**질문** MyBatis 목록에서 글마다 태그를 `<collection select="...">`로 가져왔더니 쿼리가 글 수만큼 늘었습니다. 어떻게 고치나요?
**답에 들어가야 할 것**
- 중첩 select는 부모 행마다 쿼리를 따로 실행하므로 글 20개면 태그 쿼리가 20번 나간다
- JOIN 한 번으로 가져와 `resultMap`의 중첩 결과로 묶고, `<id>`를 선언해 같은 글의 행을 합친다
- 다만 1:N JOIN에 LIMIT을 걸면 글이 아니라 행 기준으로 잘리므로, 글 ID를 먼저 커서로 뽑고 태그는 `IN`으로 따로 가져온다
**근거** 06 §16

## D07 포인트·쿠폰 상점

### TC-D07-1
**질문** 같은 회원의 구매 두 건이 동시에 들어왔는데 포인트가 한 번만 차감됐습니다. 원인과 수정은?
**답에 들어가야 할 것**
- 두 트랜잭션이 같은 잔액을 읽고 각자 계산해 쓰면, 나중 쓰기가 앞 쓰기를 덮어쓴다(갱신 손실)
- `UPDATE member SET point_balance = point_balance - ? WHERE id = ? AND point_balance >= ?`로 DB가 원자적으로 계산하게 하고, 바뀐 행이 0이면 409 `/errors/insufficient-points`로 처리한다
- 같은 트랜잭션에서 `point_ledger`에 이력을 쌓아 잔액과 이력의 합이 항상 맞게 한다
**근거** 05 §3-6, spec-v2 §6

### TC-D07-2
**질문** 쿠폰 발급 버튼을 연타하면 한 회원이 두 장을 받을 수 있나요? 어떻게 막았나요?
**답에 들어가야 할 것**
- "이미 받았는지 조회 후 INSERT"는 두 요청이 동시에 조회를 통과하면 둘 다 INSERT한다
- `member_coupon`의 UNIQUE(`coupon_id`, `member_id`)로 DB가 두 번째 INSERT를 거부하게 하고, 중복 키 예외를 409 `/errors/duplicate`로 바꾼다
- 중복 키 오류가 난 INSERT는 기존 행에 공유 락을 걸기 때문에 동시 INSERT가 많으면 데드락이 날 수 있어, 예외 처리를 함께 설계한다
**근거** 07 #13, spec-v2 §5-4

### TC-D07-3
**질문** 구매 중 데드락으로 실패한 요청을 재시도합니다. 재시도 코드를 `@Transactional` 메서드 안에 두면 안 되는 이유는?
**답에 들어가야 할 것**
- 데드락이 나면 InnoDB가 한쪽 트랜잭션 전체를 롤백한다
- 같은 트랜잭션·영속성 컨텍스트 안에서 다시 시도하면 이미 롤백된 작업을 이어 가게 되므로, 재시도는 바깥에서 새 트랜잭션으로 한다
- 여러 행을 잠글 때는 순서(예: id 오름차순)를 통일해 데드락 자체를 줄이고, 재시도에는 횟수 상한을 둔다
**근거** 07 §6, 07 #3

### TC-D07-4
**질문** 구매 요청이 네트워크 문제로 다시 전송되면 두 번 구매되나요? `Idempotency-Key`를 어떻게 처리했나요?
**답에 들어가야 할 것**
- 클라이언트는 같은 구매를 재시도할 때 같은 `Idempotency-Key`를 보낸다
- `shop_order`의 UNIQUE(`member_id`, `idempotency_key`)로 두 번째 주문 생성을 막고, 같은 키·같은 본문이면 처음 응답을 그대로 돌려준다
- 같은 키에 다른 본문이 오면 422로 거부한다
**근거** spec-v2 §5-4, 05 §3-2

## D08 포인트 충전 (외부 PG 모의)

### TC-D08-1
**질문** PG 클라이언트에 연결 1s, 응답 3s, 커넥션 풀 대기 2s를 따로 두었습니다. 셋은 각각 무엇을 막나요?
**답에 들어가야 할 것**
- 연결 타임아웃은 TCP 연결을 맺는 시간, 응답 타임아웃은 요청 후 응답을 기다리는 시간, 풀 대기 타임아웃은 클라이언트 풀에서 빈 커넥션을 얻는 시간이다
- 셋 중 하나라도 비어 있으면 그 구간에서 요청 스레드가 오래(클라이언트에 따라 무한히) 묶일 수 있다
- 값은 명세 운영 값을 쓰고, WireMock·Toxiproxy로 지연을 주입해 각 타임아웃이 어떤 예외로 나는지 직접 확인한다
**근거** 10 §8, spec-v2 §8

### TC-D08-2
**질문** 포인트 충전 흐름을 트랜잭션 몇 개로 나눴나요? 왜 그렇게 나눴나요?
**답에 들어가야 할 것**
- `pg_payment`를 `REQUESTED`로 저장하는 짧은 트랜잭션 → 트랜잭션 밖에서 PG 호출 → 결과로 상태를 바꾸고 포인트를 적립하는 짧은 트랜잭션, 세 단계다
- 요청 기록을 먼저 커밋해 두어야 PG 호출 중 서버가 죽어도 무엇을 보냈는지 남는다
- PG를 기다리는 동안 DB 커넥션을 쥐지 않으므로, PG가 느려도 Hikari 풀(10)이 고갈되지 않는다
**근거** 10 §8, spec-v2 §8

### TC-D08-3
**질문** PG 응답이 3초를 넘겨 타임아웃이 났습니다. 사용자에게 "충전 실패"라고 보여 주면 왜 안 되나요?
**답에 들어가야 할 것**
- 타임아웃은 실패가 아니라 결과 불명이다. PG는 승인을 끝냈을 수 있다
- `pg_payment`를 `UNKNOWN`으로 남기고 504 `/errors/pg-timeout`을 돌려준다
- 상태는 `orderId`가 담긴 PG 콜백이나 `GET /pg/v1/payments?orderId=` 조회(재처리 워커)로 확정한다. 같은 `Idempotency-Key`로 승인을 다시 요청해도 PG는 처음 결과를 돌려준다
**근거** 10 §8, spec-v2 §5-5, spec-v2 §7

### TC-D08-4
**질문** PG 호출이 실패하면 무조건 세 번 재시도하게 했다가 리뷰에서 지적을 받았습니다. 무엇을 재시도하고 무엇을 하지 않나요?
**답에 들어가야 할 것**
- 연결 실패·타임아웃·5xx는 재시도 후보지만, 400·401 같은 4xx는 같은 요청이 같은 실패를 내므로 재시도하지 않는다
- 결제 같은 POST는 같은 멱등 키로 재시도할 때만 이중 승인이 생기지 않는다
- 재시도 간격은 지수 백오프와 지터로 늘리고, 전체 시간이 상위 요청의 시간 예산을 넘지 않게 횟수를 제한한다
**근거** 10 §8, 10 §5

### TC-D08-5
**질문** PG 콜백 경로는 인증 없이 공개했습니다. 그러면 아무나 "결제 완료"를 보내 포인트를 받을 수 있지 않나요?
**답에 들어가야 할 것**
- 공개 경로라도 서버가 본문 원문 바이트를 같은 비밀키로 HMAC-SHA256해 `X-PG-Signature`와 상수 시간으로 비교하고, 다르면 401을 낸다
- 서명은 파싱 전 원문으로 계산한다. JSON을 파싱해 다시 직렬화하면 공백이나 필드 순서가 바뀌어 바이트가 달라질 수 있다
- 같은 `paymentKey` 콜백이 여러 번 와도 한 번만 적립하고, `amount`가 저장된 충전 금액과 다르면 거부한다
**근거** spec-v2 §5-5, spec-v2 §7

## D09 Redis

### TC-D09-1
**질문** 인기글 캐시(TTL 60초)가 만료되는 순간마다 DB 쿼리가 몰립니다. 왜 그렇고 어떻게 막나요?
**답에 들어가야 할 것**
- 키가 만료된 순간 들어온 요청이 모두 캐시 미스를 보고 동시에 DB를 조회한다(스탬피드)
- 짧은 TTL의 락 키(`SET NX`)를 잡은 요청 하나만 다시 계산하게 하거나, 만료 전에 미리 갱신한다
- `@Cacheable(sync = true)`는 기본적으로 한 인스턴스(JVM) 안의 요청만 합치므로, 인스턴스가 여럿이면 이것만으로는 막지 못한다
**근거** 10 §3

### TC-D09-2
**질문** Redis가 느려지거나 죽으면 인기글 조회가 어떻게 동작하도록 만들었나요?
**답에 들어가야 할 것**
- Redis 명령 타임아웃을 500ms로 둬서 Redis 지연이 요청 스레드를 오래 잡지 않게 한다
- 캐시 조회 실패는 경고 로그를 남기고 DB 조회로 폴백한다
- Spring Cache를 쓰면 `CacheErrorHandler`를 등록해 조회 오류를 캐시 미스로 처리한다. 기본 처리기는 예외를 그대로 던진다
**근거** spec-v2 §8, 10 §3

### TC-D09-3
**질문** 선착순 쿠폰 잔여 수량을 Redis `DECR`로 관리합니다. Redis 값과 DB의 `issued_quantity`가 다르면 무엇을 믿나요?
**답에 들어가야 할 것**
- 남은 수량 확인과 감소를 원자적으로 묶어(Lua 스크립트 등) 0 아래로 내려가지 않게 한다. `DECR` 뒤 음수면 `INCR`로 되돌리는 방식은 초과 요청과 DB 실패 되돌리기가 겹치면 수량이 어긋날 수 있다
- 발급의 최종 기준은 DB(`member_coupon` UNIQUE, `issued_quantity` <= `total_quantity`)이고, Redis는 DB 앞에서 요청을 거르는 장치다
- Redis에서 차감한 뒤 DB 저장이 실패하면 Redis 수량을 되돌리거나 DB 기준으로 다시 맞추는 절차가 있어야 한다
**근거** 10 §4, spec-v2 §6

### TC-D09-4
**질문** 관리자가 글을 숨기면 인기글 캐시를 지웁니다. 지우는 시점을 트랜잭션 커밋 뒤로 둔 이유는?
**답에 들어가야 할 것**
- 커밋 전에 지우면 그 사이 들어온 조회가 아직 커밋되지 않은, 숨기기 전 값을 DB에서 읽어 캐시에 다시 넣는다
- 그러면 TTL(60초)이 끝날 때까지 숨긴 글이 인기글에 보인다
- 그래서 `@TransactionalEventListener(phase = AFTER_COMMIT)`이나 `TransactionSynchronization`의 `afterCommit`에서 지운다
**근거** 08 #7, spec-v2 §8

### TC-D09-5
**질문** 로그인 시도 제한(10분에 5회)을 서버 메모리가 아니라 Redis에 둔 이유와 구현은?
**답에 들어가야 할 것**
- 메모리 카운터는 인스턴스마다 따로 세므로 인스턴스가 여럿이면 제한이 인스턴스 수만큼 느슨해진다
- 계정별 키를 `INCR`하고 첫 증가 때 600초 만료를 건다. 두 명령 사이에 실패하면 만료 없는 키가 남아 계정이 계속 막힐 수 있으므로 Lua 스크립트로 묶는다
- 5회를 넘으면 429 `/errors/too-many-attempts`로 응답한다
**근거** 10 §4, spec-v2 §5-1

## D10 관리자 · AOP · 테스트

### TC-D10-1
**질문** `AdminService`의 한 메서드가 같은 클래스의 `@PreAuthorize("hasRole('ADMIN')")` 메서드를 부르는데, USER도 통과합니다. 왜 그런가요?
**답에 들어가야 할 것**
- `@PreAuthorize`, `@Transactional`, 감사 로그 AOP는 프록시로 들어온 호출에만 적용되고, `this`로 부른 내부 호출은 프록시를 거치지 않는다
- `@PreAuthorize`는 `@EnableMethodSecurity`를 켜야 동작하므로, 붙였는데 아무도 막지 않으면 이것부터 확인한다
- 보호할 메서드는 바깥에서 직접 부르는 진입점에 두거나 별도 빈으로 빼고, URL 규칙(`/api/admin/**`는 ADMIN)을 첫 방어선으로 함께 둔다
**근거** 06 §7, 06 §6

### TC-D10-2
**질문** 서비스 테스트에 `@Transactional`을 붙였더니 통과했는데, 운영에서는 `LazyInitializationException`이 났습니다. 왜 그런가요?
**답에 들어가야 할 것**
- 테스트의 `@Transactional`은 테스트 메서드 전체를 한 트랜잭션으로 감싸고 끝에 롤백한다
- 그래서 서비스에 `@Transactional`이 빠져 있어도 테스트에서는 영속성 컨텍스트가 열려 있어 지연 로딩과 변경 감지가 동작한다
- 서비스 동작을 검증하는 통합 테스트는 테스트 트랜잭션 없이 돌리고, 데이터는 테스트가 끝난 뒤 직접 정리한다
**근거** 06 §11

### TC-D10-3
**질문** 감사 로그를 서비스 코드에 직접 쓰지 않고 AOP로 뺐습니다. 감사 로그가 남지 않는 경우는 언제인가요?
**답에 들어가야 할 것**
- 대상 메서드가 같은 클래스 안에서 호출되거나 `private`·`final`이면 프록시가 가로채지 못해 남지 않는다
- 감사 로그를 업무 트랜잭션 안에서 쓰면 업무가 롤백될 때 로그도 함께 사라진다. 실패한 시도까지 남기려면 별도 빈의 `REQUIRES_NEW` 트랜잭션으로 쓴다
- 기록할 값(`actor_id`, `action`, `target_type`, `target_id`)은 메서드 인자와 `SecurityContext`에서 얻는다
**근거** 06 §7, 05 §3-1, spec-v2 §6

### TC-D10-4
**질문** 1,000행 엑셀로 쿠폰을 대량 지급하다 한 행이 실패하면 어떻게 되나요?
**답에 들어가야 할 것**
- 명세는 부분 성공이다. 없는 회원이나 이미 보유한 행은 건너뛰고 `{issued, skipped[]}`로 알린다
- 한 트랜잭션에서 행마다 중복 키 예외를 잡고 계속해도 JPA에서는 그 트랜잭션을 살려 쓸 수 없어(rollback-only 표시 또는 flush 시점 실패) 전체가 롤백된다
- 그래서 보유 여부를 미리 조회해 건너뛰고, 경합으로 들어오는 중복은 UNIQUE가 막게 한다. 같은 파일을 다시 올려도 중복 지급되지 않는다
**근거** spec-v2 §5-6, 06 §7

### TC-D10-5
**질문** "신고 목록은 ADMIN만" 규칙을 어떤 테스트로 고정했나요?
**답에 들어가야 할 것**
- 토큰 없음(401), USER(403), ADMIN(200) 세 경우를 모두 보낸다. 성공 한 경우만 보면 규칙이 열려 있어도 통과한다
- 테스트 컨텍스트에 실제 `SecurityFilterChain`과 JWT 필터가 올라와 있는지 확인한다. 보안 설정이 빠진 테스트는 아무것도 검증하지 않는다
- `@WithMockUser`는 `SecurityContext`를 직접 채우므로 JWT 파싱 경로는 검증되지 않는다. JWT 필터는 실제 토큰으로 따로 확인한다
**근거** 06 §6, 06 §11

## D12 티켓 처리 1

### TC-D12-1
**질문** (B01) "PG가 느린 날 글 목록까지 멈춘다." 상관없어 보이는 두 기능이 왜 같이 멈췄나요?
**답에 들어가야 할 것**
- 충전 서비스가 `@Transactional` 안에서 PG를 호출해, PG가 느린 동안 DB 커넥션을 쥔 채 기다렸다
- 동시 충전 요청이 Hikari 풀(10개)을 모두 쥐자, 같은 풀을 쓰는 글 목록도 `connection-timeout`(2초)까지 기다리다 실패했다
- Hikari 메트릭(active가 최대에 붙고 pending이 쌓임)과 스레드 덤프로 확인하고, PG 호출을 트랜잭션 밖으로 뺀다. 풀을 키우는 것은 해법이 아니다
**근거** 07 #4, 10 §9, spec-v2 §8

### TC-D12-2
**질문** (B02) "글 목록이 어느 날부터 느리다." 어떻게 원인 쿼리를 찾고 무엇을 고쳤나요?
**답에 들어가야 할 것**
- slow query log로 후보를 찾는다. `long_query_time` 기본값이 10초라 낮춰야 잡힌다
- `EXPLAIN ANALYZE`로 읽은 행 수와 실제 돌려준 행 수를 비교해 풀스캔이나 인덱스 비효율을 확인한다. 데이터가 적을 때는 풀스캔도 빨라 보여 드러나지 않았다
- 복합 인덱스는 왼쪽 컬럼부터만 쓰이므로 조건·정렬에 맞게 순서를 고치고, 고친 뒤 EXPLAIN의 `key`, `rows`, `Extra`로 확인한다
**근거** 07 #7, 07 §2

### TC-D12-3
**질문** (B03) "예외를 잡았는데도 구매가 롤백된다 / 안 된다." 두 증상의 원인은 각각 무엇이었나요?
**답에 들어가야 할 것**
- 다른 빈의 `@Transactional`(REQUIRED) 메서드에서 런타임 예외가 나면 트랜잭션에 rollback-only가 표시되고, 바깥에서 잡아도 커밋 때 `UnexpectedRollbackException`으로 전체가 롤백된다
- 같은 클래스 안에서 `this`로 부른 메서드의 `@Transactional`(예: `REQUIRES_NEW`)은 프록시를 거치지 않아 적용되지 않는다
- 체크 예외는 기본적으로 롤백하지 않으므로, 체크 예외로 실패를 알리는 코드는 롤백되지 않는다. `rollbackFor`를 지정하거나 런타임 예외로 바꾼다
**근거** 06 §7, 08 #16

### TC-D12-4
**질문** (B05) "부하 때만 다른 사람 값이 섞인다." 왜 부하 때만 나타났나요?
**답에 들어가야 할 것**
- 싱글톤 빈의 인스턴스 필드에 요청별 값을 저장해, 동시 요청이 서로의 값을 덮어썼다
- 요청이 하나씩 올 때는 덮어쓸 상대가 없어 단위 테스트나 수동 확인으로는 재현되지 않았다
- 여러 스레드로 동시에 호출하는 재현 테스트(`ExecutorService`, `CountDownLatch`)로 섞임을 먼저 보이고, 값을 지역 변수·인자로 옮긴 뒤 같은 테스트가 통과하는지 확인한다
**근거** 06 §1

## D13 티켓 처리 2

### TC-D13-1
**질문** (B06) "컬럼 하나 추가했더니 상점 전체가 멈췄다." ALTER 한 줄이 왜 서비스를 멈췄나요?
**답에 들어가야 할 것**
- 커밋하지 않은 긴 트랜잭션이 그 테이블의 메타데이터 락(MDL)을 쥐고 있어, ALTER가 MDL을 얻지 못하고 기다렸다
- 대기 중인 ALTER 뒤로 같은 테이블의 일반 쿼리까지 줄줄이 막혀 상점 전체가 멈췄다
- `SHOW PROCESSLIST`의 `Waiting for table metadata lock`과 `information_schema.innodb_trx`로 오래된 트랜잭션을 찾고, DDL 세션에는 짧은 `lock_wait_timeout`을 걸어 무한 대기를 막는다
**근거** 07 #1

### TC-D13-2
**질문** (B07) "쿠폰 동시 사용에서 가끔 실패한다." 실패 원인이 무엇이었나요?
**답에 들어가야 할 것**
- REPEATABLE READ에서 `SELECT ... FOR UPDATE`로 없는 행을 확인하면, 결과가 없어도 그 구간에 gap lock이 걸린다
- gap lock끼리는 충돌하지 않아 두 트랜잭션이 같은 구간을 잡을 수 있고, 이어서 각자 INSERT하면 insert intention lock이 서로의 gap lock을 기다려 데드락이 된다
- `SHOW ENGINE INNODB STATUS`의 `LATEST DETECTED DEADLOCK`에서 두 트랜잭션의 락을 읽고, 중복 확인용 `FOR UPDATE`를 빼고 UNIQUE 제약과 중복 키 처리로 바꾼다
**근거** 07 #2

### TC-D13-3
**질문** (B09) "자정 전후 출석 포인트가 두 번 쌓인다." 원인과 재현 방법은?
**답에 들어가야 할 것**
- "오늘"을 서버 기본 시간대로 구하는 코드와 KST로 구하는 코드가 섞여 있었다. 서버가 UTC면 두 날짜의 경계가 9시간 어긋나 같은 출석을 다른 날로 판단했다
- `LocalDate.now()`처럼 시간대를 생략하면 JVM 기본 시간대를 쓰므로, 업무 기준 시간대(`Asia/Seoul`)를 명시한다
- `Clock`을 주입해 23:59:59와 00:00:00을 고정한 재현 테스트를 쓰고, (회원, 날짜) UNIQUE로 DB에서도 두 번째 적립을 막는다
**근거** 08 #10

### TC-D13-4
**질문** (B10) "포인트 충전이 가끔 두 번 된다." 원인이 무엇이었나요?
**답에 들어가야 할 것**
- PG 호출이 타임아웃 난 뒤 재시도가 새 승인 요청으로 나갔고, PG는 첫 요청도 이미 처리했다
- 재요청에 같은 멱등 키가 없어서 PG와 우리 DB가 모두 새 결제로 처리했다
- PG 호출에 같은 `Idempotency-Key`를 다시 보내고 `pg_payment.idempotency_key` UNIQUE로 막은 뒤, WireMock 지연과 연계 로그로 "요청 2번, 승인 1번"을 테스트로 고정한다
**근거** 10 §8, 10 §10

## D14 고도화와 모의 장애 훈련

### TC-D14-1
**질문** (B12) "새 프론트 도메인에서만 호출이 실패한다." 서버 로그에 에러가 없는데 무엇을 봤나요?

### TC-D14-3
**질문** (B15) "숨긴 글이 인기글에 1분간 계속 보인다." 캐시를 지웠는데도 왜 보였나요?
**답에 들어가야 할 것**

- 그 값이 TTL(60초) 동안 남았다. 캐시 삭제·캐시 적재·커밋 시각을 로그로 찍어 순서를 증명하고, 삭제를 커밋 후(`AFTER_COMMIT`)로 옮긴다
**근거** 08 #7, spec-v2 §8

### TC-D14-4
**질문** (B16) "Redis 점검 시간에 글쓰기까지 멈췄다." 캐시 서버 점검이 왜 글쓰기를 막았나요?

- 스레드 덤프에서 Redis 응답을 기다리는 요청 스레드를 확인하고, 타임아웃을 500ms로 두며 캐시 실패는 로그만 남기고 진행한다
**근거** 10 §3, spec-v2 §8

- 원인을 짐작이 아니라 재현 테스트·로그·메트릭 같은 근거와 함께 말한다
- 고른 해법과 버린 대안, 고친 뒤 무엇(테스트, 수치)으로 확인했는지 말한다
**근거** 05 §4, 06 §9

### TC-D15-2
**질문** 처음 진단이 틀렸던 티켓이 있었나요? 무엇에 속았고, 무엇으로 바로잡았나요?
**답에 들어가야 할 것**
- 처음 세운 가설과 그 가설을 믿게 만든 단서를 말한다
- 가설을 버리게 한 관찰(재현 결과, 로그, 메트릭, 스레드 덤프)을 말한다
- 같은 증상을 다시 보면 먼저 확인할 것을 순서대로 말한다
**근거** 06 §9, 08 #8, 08 #9

### TC-D15-3
**질문** 1단계에서 직접 만든 코드에 2단계 티켓과 같은 결함이 있었나요? 그때는 왜 놓쳤나요?
**답에 들어가야 할 것**
- 해당 코드 위치와 같은 원인의 티켓 번호를 댄다
- 놓친 이유를 말한다(예: 테스트가 동시 요청이나 경계 시각을 다루지 않았다)
- 같은 실수를 막을 장치(재현 테스트, ArchUnit 규칙, 리뷰 체크 항목)를 말한다
**근거** 06 §17

### TC-D15-4
**질문** 모의 장애 훈련에서 장애를 알아차리고 원인을 지목하기까지 무엇을 봤나요? 회고 문서에는 무엇을 남겼나요?
**답에 들어가야 할 것**
- 처음 알아차린 신호(에러율, 응답 시간, Hikari pending 등)와 그 시각을 말한다
- 원인을 좁힌 순서(메트릭 → 요청 ID로 로그 → 스레드 덤프 등)를 말한다
- 사람 탓이 아니라 구조의 원인을 적고, 재발 방지 조치마다 확인 방법을 남겼다
**근거** 13 §4, 10 §1

### TC-D15-5
**질문** 지금 다시 만든다면 바꿀 설계 결정 하나는 무엇인가요? 바꾸는 데 드는 비용은?
**답에 들어가야 할 것**
- 당시 결정과 그때의 근거를 말한다
- 생각을 바꾸게 한 관찰(티켓, 측정 결과)을 말한다
- 바꿀 때의 영향 범위와 옮겨 가는 방법(하위 호환, 데이터 이전)을 말한다
**근거** 05 §4, 05 §3-12
