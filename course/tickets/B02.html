#힌트

1. slow log에서 쿼리를 찾되, rows_examined를 믿지 않는다

SET GLOBAL long_query_time = 0.01; SET GLOBAL slow_query_log = ON; SET GLOBAL log_output = 'TABLE'; 뒤에 mysql.slow_log를 본다. 목록 쿼리는 FROM (SELECT ... FROM post WHERE status = 'ACTIVE' ORDER BY id DESC LIMIT ?) p 모양이다. 이 쿼리의 rows_examined는 43으로 작게 찍힌다(performance_schema 요약도 같다). 파생 테이블(괄호 안 SELECT)이 읽은 행은 여기에 잡히지 않는다. 그래서 EXPLAIN ANALYZE로 내려간다. 같은 쿼리인데 첫 쪽(30ms대)과 다음 쪽(1ms 안쪽)의 시간이 크게 다르다는 것이 단서다.

2. EXPLAIN ANALYZE에서 "읽은 행"과 "남긴 행"을 비교한다

안쪽 SELECT를 EXPLAIN ANALYZE로 본다. 각 노드의 (actual ... rows=N loops=L)이 실제로 처리한 행 수다. Filter: (post.status = 'ACTIVE') ... rows=21 아래 접근 노드가 rows=200042라면 20만 행을 읽고 21행만 남긴 것이다. key가 무엇인지, 원래 이 쿼리를 위해 만든 인덱스가 왜 쓰이지 않는지 SHOW INDEX FROM post와 함께 본다.

3. "어느 날부터"와 "첫 쪽만"을 설명할 근거를 모은다

SELECT status, COUNT(*) FROM post GROUP BY status와, 최근 id 구간의 status 분포(WHERE id > (SELECT MAX(id) - 10000 FROM post))를 본다. PK를 거꾸로 훑으며 거르는 방식은 최근 글이 ACTIVE로 촘촘하면 21건 근처에서 멈추고, 최근 글이 숨김으로 쏠리면 그만큼 더 읽는다. 테스트는 실행 시간이 아니라 이 "읽은 행 수"로 단언한다. 로컬에서 시간은 너무 작아 흔들린다.

#원인과 정답

펼치기

원인. 목록 쿼리 안쪽은 WHERE status = 'ACTIVE' ORDER BY id DESC LIMIT 21이다. schema.sql의 목록용 인덱스가 idx_post_id_status (id, status)로 잡혀 있다. 복합 인덱스는 앞 컬럼부터 쓰이므로 status = ? 등호 조건으로 범위를 좁히지 못한다. 순서도 PRIMARY(id)와 같아 옵티마이저는 이 인덱스를 쓰지 않는다. 결국 PK를 최신 글부터 거꾸로 훑으며 status를 한 행씩 거른다. 평소에는 최근 글 절반이 ACTIVE라 42행쯤 읽고 멈춰서 티가 안 났다. "어느 날"은 스팸 계정 정리로 최근 글 수십만 건이 HIDDEN이 된 날이다. 그 뒤로 첫 쪽은 숨김 글을 모두 지나야 ACTIVE 21건을 채운다. 다음 쪽은 커서(id < ?)가 숨김 구간 아래(오래된 글 구간)에서 시작하므로 다시 빠르다. 서버를 키워도 읽는 행 수는 그대로다.

측정(분포 고정, MySQL 8.4).

데이터 인덱스 접근 경로(post) 읽은 행 남긴 행
오래된 2만(ACTIVE 1만) + 최근 HIDDEN 2만 (id, status) 결함 Index scan on post using PRIMARY (reverse) + Filter 20,041 21
같음 (status, id) 정답 Index lookup on post using idx_post_status_id (status='ACTIVE') (reverse) 21 21
오래된 20만 + 최근 HIDDEN 20만 (repro.sh) (id, status) 결함 같음(약 31~37ms, Handler_read_prev 200,041) 200,042 21
같음 (status, id) 정답 Index lookup (reverse) (약 0.03ms) 21 21
확인 테스트 fixture(오래된 4천 + HIDDEN 4천) (id, status) 결함 PRIMARY (reverse) 4,042 21
같음 (status, id) 정답 Index lookup (reverse) 21 21

커서 페이지(id < 15000, 오래된 구간)는 세 인덱스 모두 PRIMARY range scan으로 42행을 읽어 차이가 없다. 그래서 "첫 쪽만" 느리다. 인덱스가 아예 없을 때도 결함 인덱스와 같은 계획(20,041행)이 나온다. 즉 (id, status)는 공간과 쓰기 비용만 먹는 죽은 인덱스다.

정답 수정. 인덱스를 (status, id)로 바꾼다. 등호 조건 컬럼이 앞, 정렬·범위 컬럼(id)이 뒤다. 이 인덱스는 status='ACTIVE' 구간을 id 역순 그대로 읽으므로 21행에서 멈추고 filesort도 없다. PostListExplainTest를 "최근 글이 숨김으로 쏠린 분포 + EXPLAIN ANALYZE 읽은 행 수"로 다시 쓴다. (tickets/B02/answer/fix.patch) 운영 DB에는 ALTER TABLE post DROP INDEX idx_post_id_status, ADD INDEX idx_post_status_id (status, id), ALGORITHM=INPLACE, LOCK=NONE처럼 온라인 DDL로 반영한다(B06의 MDL 대기도 함께 생각할 것).

로컬에서 확인할 때. schema.sql은 CREATE TABLE IF NOT EXISTS라서, 이미 만들어진 로컬 DB에는 schema.sql을 고쳐도 인덱스가 바뀌지 않는다. 로컬에서 수정 결과를 보려면 ALTER TABLE로 인덱스를 바꾸거나 MySQL 컨테이너 볼륨을 지우고 다시 띄운다.

확인 테스트. tickets/B02/answer/B02ConfirmTest.java

  • 최근_글이_대부분_숨김이어도_목록_첫_쪽이_읽는_post_행은_100개_이하다 — 실제 매퍼 SQL의 EXPLAIN ANALYZE에서 post 접근 노드의 실제 행 수(결함 4,042 → 수정 21). 인덱스 이름은 보지 않는다.
  • 목록_첫_쪽과_다음_쪽은_최신_ACTIVE_글_순서_그대로다 — 인덱스를 바꿔도 응답(첫 쪽 + 다음 쪽 40건)이 같다.

1단계 정답 서버는? board-server/src/main/resources/schema.sql은 idx_post_status_id (status, id)이고, board-server/src/test/java/com/example/board/post/PostListExplainTest.java가 EXPLAIN의 key와 컬럼 순서를 고정했다. 이 서버에서는 그 테스트가 지워져 있다. 다만 그 테스트의 데이터는 ACTIVE가 촘촘해서(50%) 행 수 차이는 드러나지 않았다. 분포를 고정해야 결함이 보인다는 것이 이 티켓의 교훈이다.

더 찾아볼 것. keyword·tag 조건이 붙은 목록은 인덱스와 상관없이 많이 읽는다(LIKE '%..%'). 같은 방법으로 읽은 행 수를 재 보고 전문 검색이 필요한지 판단해 본다.
