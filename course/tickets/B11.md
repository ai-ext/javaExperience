# B11. prod에서 설정값이 안 바뀐다

> 같은 날: D11 ①·③ · 선택(인수인계 리뷰 과제) · 진단 도구: `/actuator/env/{키}`의 `propertySources`, 로그인 응답 `expiresIn`

## 받은 티켓

> 보안 점검 지적으로 운영 로그인 토큰 만료를 1시간에서 30분으로 줄이기로 했고, `application-prod.yml`에 `expires-in-seconds: 1800`을 넣어 어제 배포했습니다.
> 그런데 운영에서 로그인해 보면 `expiresIn`이 여전히 7200입니다. 1800도 3600도 아니고 7200이라 더 이상합니다.
> 배포가 덜 된 건지 확인했는데 jar는 새 것이 맞습니다. — 운영팀

## 환경과 재현

1. `messy-server`에서 `docker compose up -d`
2. `bash tickets/B11/repro.sh` (bootJar로 만든 jar를 8088 포트에 띄우고, 끝나면 그 프로세스만 내린다. 포트가 이미 쓰이면 시작하지 않는다)
   - 운영 서버가 읽는 환경 변수 파일 `deploy/board.env`를 그대로 읽고, 접속 정보·비밀값만 로컬 값으로 바꿔 `prod` 프로파일로 띄운다.
   - 로그인 응답의 `expiresIn`과 `/actuator/env/board.jwt.expires-in-seconds`를 찍는다.
   - 기대 증상: `expiresIn`이 7200이다. `/actuator/env`가 보여 주는 이 키의 출처 목록에서 맨 위(이긴 값)가 `application-prod.yml`이 아니다.

## 제출물

- 원인 서술: 7200은 어디서 왔고, 왜 `application-prod.yml`의 1800을 이겼는가
- 재현 테스트: 운영과 같은 환경 변수로 설정을 합쳤을 때 실제로 쓰이는 값이 1800인지 보는 테스트(결함 상태에서 실패 → 수정 후 통과)
- 수정 diff

## 힌트

<details>
<summary>1. 값을 추측하지 말고 Environment에 묻는다</summary>

yml을 눈으로 읽어서는 이긴 값을 알 수 없다. `/actuator/env/board.jwt.expires-in-seconds`는 그 키를 가진 출처를 우선순위 순서로 모두 보여 주고,
`property.source`가 실제로 이긴 출처다. 출처 이름(`systemEnvironment`, `Config resource 'class path resource [application-prod.yml]'` 등)과 `origin`을 본다.
</details>

<details>
<summary>2. 같은 키에 값을 줄 수 있는 곳을 모두 찾는다</summary>

뒤에 오는 것이 이긴다: jar 안 `application.yml` → jar 안 `application-{profile}.yml` → … → **OS 환경 변수** → Java 시스템 프로퍼티 → 커맨드라인 인자.
환경 변수는 느슨한 바인딩(relaxed binding)으로 키에 붙는다. 점을 밑줄로 바꾸고 대문자로 쓴 `BOARD_JWT_EXPIRES_IN_SECONDS`는 `board.jwt.expires-in-seconds`와 같은 키다.
리포에서 `7200`과 `EXPIRES`를 찾아본다(`grep -rn`). 소스 밖 파일도 본다.
</details>

<details>
<summary>3. 테스트로 고정하기</summary>

`SpringApplicationBuilder`로 빈 없는 작은 설정 클래스를 `prod` 프로파일로 띄우되, `StandardEnvironment`의 `systemEnvironment` 출처를
`deploy/board.env` 내용으로 바꿔 끼운다(`SystemEnvironmentPropertySource`). 그 뒤 `Binder.get(env).bind("board.jwt.expires-in-seconds", Long.class)`로 이긴 값을 단언한다.
</details>

## 원인과 정답

<details>
<summary>펼치기</summary>

**원인.** 운영 서버 환경 변수 파일 `deploy/board.env`에 6월에 넣은 `BOARD_JWT_EXPIRES_IN_SECONDS=7200`("로그인 유지" 임시 연장)이 남아 있다.
OS 환경 변수는 어떤 `application*.yml`보다 우선순위가 높으므로, `application-prod.yml`에 1800을 넣어도 환경 변수 7200이 이긴다.
"프로파일 전용 yml이 마지막에 덮는다"는 착각이 원인이다. yml끼리는 맞지만 환경 변수·시스템 프로퍼티·커맨드라인 인자는 그보다 위다.
yml만 고치면 몇 번을 배포해도 그대로다(로드맵 함정).

**정답 수정.** 환경 변수 파일에서 그 줄을 지우고, 운영 동작값은 `application-prod.yml` 한 곳에만 둔다는 규칙을 파일 머리에 적는다.
환경 변수에는 서버마다 다른 접속 정보만 둔다. 같은 키를 두 곳에 두지 않는 것이 핵심이다. (`tickets/B11/answer/fix.patch`)
고친 뒤 `/actuator/env/board.jwt.expires-in-seconds`의 이긴 출처가 `application-prod.yml`이고, 로그인 응답 `expiresIn`이 1800인지 확인한다.

**확인 테스트.** `tickets/B11/answer/B11ConfirmTest.java` — `운영_배포_환경_변수로_띄우면_토큰_만료는_1800초다`, `환경_변수가_없는_로컬은_기본값_3600초다`

**1단계 정답 서버는?** `board-server/src/main/resources/application-prod.yml`은 비밀값·접속 정보를 기본값 없는 자리표시자(`${DB_URL}` 등)로만 두고,
동작값은 `application.yml`에 둔다. 정답 서버도 같은 `@ConfigurationProperties("board")` 바인딩을 쓰므로 환경 변수는 여전히 어떤 키든 덮어쓸 수 있다.
차이는 배포 구성에 있다. 정답 서버의 운영 구성에서 환경 변수로 넣는 것은 자리표시자가 가리키는 이름(`DB_URL`, `BOARD_JWT_SECRET` 등)뿐이고 동작값 키를 넣는 환경 변수는 없어서, 같은 키가 두 출처에 겹치지 않는다. 자리표시자가 덮어쓰기를 막아 주는 것은 아니다. 누가 `BOARD_JWT_EXPIRES_IN_SECONDS`를 넣으면 정답 서버에서도 그 값이 이긴다.
</details>
