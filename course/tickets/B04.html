#힌트

1. 먼저 동작을 고정한다(특성화 테스트)

리팩터링 전에 지금 나오는 알림 행을 그대로 적는다. 글을 쓰고, 남이 댓글을 달고, 글을 지운 뒤 SELECT member_id, channel, type, title, body, ref_id FROM notification을 본다. "옳다고 생각하는 값"이 아니라 지금 나오는 값을 적는다. 푸시 본문이 40자에서 잘리는 규칙, 메일 제목 머리말·꼬리말까지 고정해야 리팩터링 중 실수가 잡힌다.

2. KAKAO가 어디서 거절되는지 찾는다

PostServiceImpl에서 switch (channel)을 찾는다. 글 작성, 글 삭제, 댓글 알림(notifyCommentAdded)에 같은 모양이 세 번 있고, 셋 다 default에서 예외를 던진다. 채널마다 다른 것(제목·본문 모양)과 알림 종류마다 다른 것(어느 채널로 보내나)을 나눠 본다. 채널은 구현 하나로, 종류별 채널 목록은 표 하나로 모으면 분기가 사라진다.

3. 기동 실패 경로를 따라간다

CommentService는 댓글 알림 때문에 PostServiceImpl을, PostServiceImpl은 삭제 알림 대상(댓글 단 사람) 때문에 CommentService를 필드로 받는다. Spring Boot는 기본으로 순환 참조를 막는다(spring.main.allow-circular-references=false). 그래서 누군가 한쪽에 @Lazy를 붙여 프록시로 기동만 되게 했다. 생성자 주입으로 바꾸면 순환이 기동 실패로 바로 드러난다. 알림을 별도 서비스로 빼고, 댓글 단 사람 조회는 CommentRepository로 직접 하면 순환이 끊긴다. 설정으로 순환을 허용하는 것은 수정이 아니다.

#원인과 구현 예시

펼치기

원인.

  • 알림 기능을 붙일 때 채널(IN_APP·PUSH·EMAIL)별 저장 코드를 글 서비스 안에 switch로 직접 썼고, 글 삭제·댓글 알림에서 그것을 복사했다.
  • 셋 다 default -> throw new IllegalStateException("알 수 없는 알림 채널")이다. 그래서 enum에 값 하나를 더하면 글 작성·글 삭제·댓글 작성 세 API가 함께 500이 된다.
  • 금칙어 검사도 작성·PUT·PATCH에 복사돼 있다.
  • 댓글 알림을 "규칙이 같다"는 이유로 PostServiceImpl에 두고 CommentService가 그것을 필드로 받는다. PostServiceImpl도 CommentService를 필드로 받는다. 이 순환을 @Lazy로 덮어 기동만 되게 했다.

구현 예시 수정. (tickets/B04/answer/fix.patch)

  • notification 패키지에 NotificationSender(채널 하나 = 구현 하나: InApp·Push·Email)와 NotificationService를 둔다. NotificationService는 List<NotificationSender>를 받아 종류에 맞는 채널로 보낸다.
  • 종류별 채널 목록은 NotificationType이 갖는다. 채널을 더할 때는 새 NotificationSender 구현과 NotificationType 표만 고친다.
  • PostServiceImpl·CommentService는 생성자 주입으로 NotificationService만 부른다. 댓글 단 사람 조회는 CommentRepository.findCommenterIds로 직접 해서 순환을 끊는다.
  • 금칙어 검사는 rejectForbiddenWords 하나로 모은다.
  • 댓글 작성은 댓글 쓴 회원과 글쓴이의 회원 행을 id 순서로 먼저 잠그는 원래 순서를 그대로 둔다. 글쓴이에게 가는 알림 INSERT가 글쓴이 회원 행에 FK 공유 잠금을 걸기 때문에, 이 순서를 빼면 서로의 글에 동시에 댓글을 다는 두 요청이 교착한다(CommentLockOrderTest).
  • build.gradle에 ArchUnit(archunit-junit5)을 더하고 ArchitectureTest에 NO_CLASSES_SHOULD_USE_FIELD_INJECTION 규칙 하나를 둔다.

확인 테스트. tickets/B04/answer/B04ConfirmTest.java

  • 동작 보존:
    • 글을_쓰면_작성자에게_알림함과_푸시로_등록_알림이_간다
    • 남의_글에_댓글을_달면_글쓴이에게_세_채널로_가고_내_글에_단_댓글은_알리지_않는다
    • 글을_지우면_댓글을_단_다른_회원에게만_알림함과_메일로_간다
    • 제목이나_본문에_금칙어가_있으면_작성_수정_모두_400이다
    • 이 네 개는 결함 상태에서도 통과해야 한다. 리팩터링이 동작을 바꾸지 않았다는 증거다.
  • 구조:
    • 애플리케이션_빈에_필드_주입이_없다(@Autowired·@Inject·@Resource·@Lazy 필드)
    • 애플리케이션_빈_사이_의존에_순환이_없다(생성자·필드 타입으로 빈 그래프를 그려 순환을 찾는다)
    • 결함 상태에서는 이 둘이 실패한다.
  • 채널 추가(클래스 이름·파일 수는 보지 않고 컴파일된 main 클래스의 바이트코드로 판정한다):
    • 글_댓글_API를_처리하는_빈은_개별_알림_채널을_모른다 — POST /api/posts·POST /api/posts/{id}/comments·DELETE /api/posts/{id}를 처리하는 컨트롤러와 그 컨트롤러가 받는 빈이 NotificationChannel을 참조하지 않는다. 채널을 더할 때 글·댓글 쪽을 고칠 일이 없다는 뜻이다.
    • 알림_채널별로_갈라지는_분기는_한_곳을_넘지_않는다 — 채널 switch나 채널 값 여럿과의 비교가 있는 메서드가 앱 전체에 한 곳 이하다(종류별 채널 표 같은 정적 초기화는 세지 않는다).
    • 필드 주입·순환만 고치고 switch 세 개를 그대로 둔 수정은 이 둘에 걸린다. 채널 enum에 동작을 넣는 방식, 채널을 고르는 switch를 알림 서비스 한 곳에 두는 방식은 통과한다.

1단계 구현 예시 서버는? board-server/src/main/java/com/example/board/post/PostServiceImpl.java는 생성자 주입만 쓰고, 글 서비스가 다른 서비스를 필드로 받지 않는다. 알림 기능은 1단계에 없었다. 2단계에서 "남이 붙인 기능"으로 들어온 것이다.

더 찾아볼 것. 푸시·메일 대기열 행을 실제로 보내는 배치가 없다. 보낸 행 표시(sent_at)와 재시도는 어떻게 둘지 설계해 본다.
