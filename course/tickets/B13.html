#받은 티켓

결제사에서 연락이 왔습니다. 저희 서버로 보내는 결제 완료 통지가 지난 배포 이후 전부 401로 거절된다고 합니다. 그 사이 승인 응답을 못 받고 "결과 불명"으로 남은 충전 건들이 확정되지 않아 고객 문의가 들어오고 있습니다. 결제사 쪽 서명 키는 바뀐 게 없다고 합니다. — 결제 담당

#힌트

1. 같은 401이라도 누가 만든 401인지 본다▸

응답 본문의 type이 /errors/unauthorized면 Security 진입점(ProblemDetailSecurityHandler)이 만든 것이고, /errors/invalid-signature면 컨트롤러의 서명 검증이 만든 것이다. 서명이 맞든 틀리든 같은 /errors/unauthorized라면 요청은 컨트롤러에 닿지도 못했다. 서명 키를 의심할 이유가 없다.

2. Security TRACE 로그 읽기▸

TRACE 로그에서 POST /api/pg/callbacks가 필터를 하나씩 지나는 줄(Invoking ... (n/m))을 따라간다. AuthorizationFilter에서 어떤 인가 관리자(AuthenticatedAuthorizationManager 등)로 판정했는지 본다. 그 관리자가 어느 규칙에서 왔는지 SecurityConfig의 규칙을 위에서부터 짚어 본다.

3. 테스트에서 이 문제가 안 보였던 이유▸

PgCallbackApiTest·PgCallbackOrderingTest 클래스에 붙은 애노테이션을 본다. 테스트가 늘 인증된 사용자로 요청하면 인가 규칙의 실수를 잡을 수 없다. 확인 테스트는 인증 없이(PG 서버처럼) 보내야 한다. pg_payment에 UNKNOWN 행을 하나 넣고 서명한 콜백을 보낸 뒤 상태와 잔액을 본다.

#원인과 구현 예시

펼치기▸

원인. SecurityConfig에 "회원 전용 쓰기 API" 규칙 requestMatchers(HttpMethod.POST, "/api/**").authenticated()가 추가됐는데, 콜백 공개 규칙 requestMatchers(HttpMethod.POST, "/api/pg/callbacks").permitAll()보다 위에 있다. 인가 규칙은 위에서부터 처음 매치된 것 하나만 적용되므로 POST /api/pg/callbacks는 넓은 쓰기 규칙에 먼저 걸려 토큰을 요구받고, 아래의 permitAll은 영원히 매치되지 않는다. PG 서버는 JWT가 없으니 모든 콜백이 401이다. 서명 검증(PgCallbackController)까지 가지 못하므로 서명이 맞든 틀리든 같은 401이다. 테스트가 이를 놓친 것은 콜백 테스트 클래스에 @WithMockUser가 붙어 모든 요청이 이미 인증된 상태였기 때문이다.

구현 예시 수정. 콜백 permitAll 규칙을 넓은 쓰기 규칙보다 위로 올리고, 콜백 테스트의 @WithMockUser를 지워 PG처럼 인증 없이 보내게 한다. 콜백 경로를 공개하는 것은 서명 검증이 있어서 안전하다. 경로를 permitAll로 여는 김에 서명 검증까지 빼거나 우회하면 누구나 충전을 확정할 수 있는 구멍이 된다(로드맵 함정). (tickets/B13/answer/fix.patch)

확인 테스트. tickets/B13/answer/B13ConfirmTest.java — 토큰_없이_서명이_맞는_콜백은_200이고_충전이_확정된다, 서명이_틀리면_401_invalid_signature이고_상태는_그대로다, 서명이_없어도_401_invalid_signature다

1단계 구현 예시 서버는? board-server/src/main/java/com/example/board/config/SecurityConfig.java는 구체적인 공개 규칙만 나열하고 마지막에 anyRequest().authenticated() 하나로 닫는다. 넓은 /api/** 규칙이 중간에 없으니 콜백 permitAll이 가려지지 않는다. PgCallbackApiTest는 인증 헤더 없이 서명만으로 통과하는지 확인했다.
