#받은 티켓

PG사 정산 담당자가 연락해 왔습니다. 어제 저녁(PG 응답이 느렸던 시간) 같은 회원의 같은 금액 충전이 몇 초 간격으로 두 번씩 승인된 건이 여러 개라고 합니다. 회원 쪽 화면에서도 7,000포인트를 한 번 충전했는데 잔액은 14,000이 됐다는 문의가 있습니다. 앱은 충전 버튼을 한 번만 보내도록 막혀 있다고 합니다. — 정산팀

▷ 실습실행하고 관찰

#환경과 재현

  1. messy-server에서
    • 1단계(승인 요청이 두 번 간다): WireMock을 "첫 승인 요청은 승인하되 5초 뒤에 답하는" 상태 있는 PG로 바꾸고 충전을 한 번 보낸다. 기대 증상: PG가 받은 승인 요청이 2건, pg_payment에 행이 2개(UNKNOWN 1, DONE 1). 이 시점 잔액은 아직 7000이다.
    • 2단계(정산하면 두 번 쌓인다): PG가 하듯 UNKNOWN 행의 orderId로 서명을 붙인 결제 완료 콜백(DONE)을 보낸다. 기대 증상: 잔액 14000, 충전 원장 2건. 이 서버는 토큰 없는 콜백이 401로 막히는 다른 증상(B13)이 있어 스크립트는 회원 토큰을 붙여 보낸다(서명 검증·반영은 그대로 거친다).

#힌트

1. 연계 로그와 PG 요청 기록을 맞춰 본다▸

SELECT order_id, idempotency_key, status, requested_at FROM pg_payment WHERE member_id = ? ORDER BY id로 같은 충전 시각 근처의 행을 본다. 클라이언트가 보낸 키가 아닌 행이 있는가? WireMock의 POST /__admin/requests/find로 PG가 받은 Idempotency-Key 헤더 목록을 보고 연계 로그의 키와 짝지어 본다.

2. "응답 타임아웃"이 무엇을 뜻하는지 다시 본다▸

PgException.Kind.TIMEOUT의 주석과 PgRetryPolicy의 재시도 대상을 읽는다. 응답 타임아웃은 "요청은 보냈고 PG는 승인했을 수 있다"이다. 그런데도 다시 보내는 코드가 어디 있는가? ChargeService.charge가 무엇을 잡아서 무엇으로 다시 부르는지 본다.

3. 상태 있는 PG 모의로 고정한다▸

WireMock 시나리오(scenarioName, requiredScenarioState, newScenarioState)로 "첫 요청은 4초 지연(승인), 다음부터는 즉시 승인"을 만든다(PgContainers.stub(...), priority 1). 결과 불명 행은 PgContainers.stubLookupDone(orderId, amount) 뒤 chargeService.reconcile(orderId)로 확정한다. 콜백 HTTP 경로는 이 서버에서 다른 문제가 있을 수 있어 쓰지 않는다. 판정은 PG가 받은 서로 다른 키 수, 충전 원장 건수, 잔액을 따로 본다. HTTP 요청 수는 고정하지 않는다(같은 키로 다시 보내는 것은 PG가 같은 결과를 돌려주므로 괜찮다).

#원인과 구현 예시

펼치기▸

원인. ChargeService.charge가 "PG가 잠깐 느린 경우가 많다"며 PG_TIMEOUT이면 한 번 더 시도하는데, 같은 키로 다시 보내면 처음 기록(UNKNOWN)을 돌려주는 504만 나오니 재시도용 키를 새로 만든다(UUID.randomUUID()). 새 키 = 새 pg_payment 행 = 새 orderId라 PG에는 별개의 결제 요청이다. 첫 요청은 PG가 이미 승인했고 응답만 늦었으므로 PG 승인은 2건이 된다. 두 번째는 바로 DONE으로 적립되고, 첫 번째(UNKNOWN)는 PG 콜백이 오거나 재처리(ChargeService.reconcile, PG 조회)로 DONE을 확인하는 순간 또 적립된다. 행마다 "한 번만 적립"(조건부 상태 전이)은 지켜지지만 행이 둘이라 적립도 둘이다. 클라이언트가 같은 키로 다시 보낸 경우에도 이 재시도가 새 키를 만든다. 재시도 횟수를 줄여도 키를 새로 만드는 한 줄어들 뿐 없어지지 않는다.

구현 예시 수정. 응답 타임아웃은 다시 보내지 않는다. 결과 불명(UNKNOWN)으로 남기고 504로 답한 뒤, 콜백·재처리(reconcile)가 같은 orderId로 확정한다(tickets/B10/answer/fix.patch). 꼭 다시 보내야 한다면 같은 Idempotency-Key(같은 orderId)로 보내 PG가 처음 결과를 돌려주게 한다. 클라이언트의 재요청도 같은 키면 서버가 처음 기록을 돌려준다.

확인 테스트. tickets/B10/answer/B10ConfirmTest.java — 승인_응답이_늦게_와도_PG_승인은_한_건이고_포인트는_한_번_쌓인다 이 서버에는 reconcile을 주기적으로 부르는 워커가 아직 없어, 확인 테스트가 결과 불명 건마다 직접 부른다(운영이라면 워커나 PG 콜백이 그 역할을 한다).

1단계 구현 예시 서버는? board-server/src/main/java/com/example/board/payment/PgRetryPolicy.java는 연결 실패와 5xx만 재시도하고(응답 타임아웃은 결과 불명), PgClient.approve는 재시도해도 같은 키를 보낸다. ChargeService는 한 요청에 pg_payment 한 행만 만든다. PgTimeoutTest가 "504이고 UNKNOWN이며 재시도하지 않는다"를 확인했는데, 이 서버에서는 그 단언들이 지워지거나 약해져 있다.
