#모의 장애 훈련: Redis 장애 대응과 회고

같은 날: D14 ⑥ · 모두 한다 · 서버: B16(Redis 타임아웃·폴백)을 고쳤으면 고친 서버, 고치지 않았으면 지금 서버 그대로 · 도구: messy-server/drills/, 스레드 덤프, 서버 로그

이 연습을 쓰는 날: D14 ⑥ · 고도화와 모의 장애 훈련

훈련의 목표는 장애를 알아차리고, 증거를 남기고, 원인을 지목하고, 회고로 정리하는 것이다. B16을 고친 서버라면 "고쳤다"를 장애 상황에서 다시 증명하는 것까지 한다. 장애를 넣는 쪽과 대응하는 쪽을 나누면 좋다(혼자라면 start.sh가 주입 시각을 숨겨 준다). 증상이 보이자마자 재시작하지 않는다. 재시작하면 스레드 덤프 같은 증거가 사라져 원인을 지목할 수 없다.

#준비

  1. messy-server에서 docker compose up -d
    • 서버는 Toxiproxy(16380)를 거쳐 Redis에 붙는다(compose.yaml, toxiproxy.json의 redis 프록시). redis-cli로 Redis에 바로 붙을 때는 16381(또는 docker compose exec redis redis-cli).
  2. 서버를 띄우고 로그를 파일로도 남긴다: mkdir -p /tmp/board-drill && ./gradlew bootRun --args='--spring.profiles.active=local' 2>&1 | tee /tmp/board-drill/server.log
  3. 다른 터미널에서 bash drills/probe.sh — 1초마다 글쓰기·인기글을 부르고 코드·시간을 찍는다. 1초를 넘기거나 코드가 다르면 !!.
    • probe는 장애를 넣기 전에 켜 둔다. 처음에 로그인해 토큰을 받는데, B16을 고치지 않은 서버는 Redis가 끊긴 동안 로그인이 500이라 probe가 시작하지 못하고 멈춘다(이유를 알려 준다). 그때는 recover.sh로 복구한 뒤 다시 켠다.

#스크립트

스크립트 하는 일
drills/start.sh 10~90초 뒤 무작위 시각에 장애를 한 번 넣는다(기본 지연 3초, FAULT=down이면 연결 끊김). 시각은 알려 주지 않는다
drills/inject.sh latency [ms] / down / status 바로 주입한다(지연 기본 3000ms / 프록시 닫기 / 상태 보기)
drills/probe.sh 사용자 흉내 요청과 응답 시간 기록(/tmp/board-drill/probe-*.log)
drills/evidence.sh 복구 전에 증거를 남긴다: 스레드 덤프 3장(2초 간격), 헬스, Toxiproxy 상태. Redis를 기다리는 요청 스레드를 추려 보여 준다
drills/recover.sh 장애를 걷고 프록시를 다시 연다. 주입·복구 기록(실제 주입 시각)을 보여 준다

기록은 모두 /tmp/board-drill/(DRILL_OUT으로 바꿀 수 있다)에 남는다.

#진행

  1. bash drills/start.sh → probe.sh 출력과 서버 로그를 지켜본다.
  2. 이상을 알아차린 순간의 시각을 적는다(무엇을 보고 알았는가: !!, 경고 로그 Redis … 실패, 5초 동안 Redis 없이 처리한다, 지표).
  3. bash drills/evidence.sh로 증거부터 남긴다. 스레드 덤프에서 요청 스레드가 어디서 기다리는지 본다.
  4. 원인을 지목한 시각과 근거를 적는다. 조치(복구)는 그다음이다: bash drills/recover.sh.
  5. 합격 기준
    • 모두: 알아차린 시각, 증거(evidence-*/), 원인을 지목한 시각과 근거, 회고 문서가 있고 회고의 시각이 probe-*.log·injections.log·서버 로그와 맞는다.
    • B16을 고친 서버는 더해서: 주입 중에도 probe.sh의 글쓰기가 201, 인기글이 200이고 둘 다 1초 안이다. 경고 로그는 남되 요청은 실패하지 않는다.
    • B16을 고치지 않은 서버라면 여기서 글쓰기가 수 초씩 걸리거나(지연) 인기글이 500이다(끊김). 그것이 이번 장애의 증상이다. 회고의 원인 칸은 스레드 덤프·로그로 왜 그렇게 됐는지 지목한다. 실패 자체는 불합격이 아니다.
  6. 지연과 끊김을 한 번씩 해 본다(FAULT=down bash drills/start.sh). 두 번째 주입 전에 recover.sh로 복구하고 probe가 정상으로 돌아온 것을 본다.

#더 해 보기

  • 지연 시간을 400ms·1000ms·5000ms로 바꿔 가며 응답 시간이 어떻게 변하는지 표로 남긴다(B16을 고쳤다면 명령 타임아웃 500ms와, 고치지 않았다면 Lettuce 기본 60초와 비교).
  • drills/inject.sh latency 3000을 넣은 채 로그인을 해 본다. 로그인 시도 제한(fail-open)은 Redis 없이도 통과하는가.
  • 인기글 캐시를 비운 상태(docker compose exec redis redis-cli DEL popular:posts)에서 지연을 넣고, 캐시 재적재가 DB에 몰리는지 본다(D14 ⑤ 고도화와 연결).
