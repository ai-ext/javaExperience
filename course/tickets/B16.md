# B16. Redis 점검 시간에 글쓰기까지 멈췄다

> 같은 날: D14 ④ (⑥ 모의 장애 훈련으로 이어짐) · 선택(Redis) · 진단 도구: 스레드 덤프(`jcmd <pid> Thread.print`), 응답 시간 측정, 서버 경고 로그

## 받은 티켓

> 어젯밤 Redis 점검(장애 조치 리허설) 20분 동안 글쓰기가 1분 넘게 돌다 실패했고, 인기글 화면은 500이 섞여 나왔습니다.
> Redis는 캐시라서 점검 중에도 서비스는 된다고 들었는데요. APM에서 글 저장 API가 `@Transactional` 메서드 근처에서 오래 걸린 것으로 보여서 DB 쪽 락을 먼저 의심하고 있습니다.
> 다음 달 점검 전까지 원인 파악 부탁드립니다. — 운영팀

## 환경과 재현

1. `messy-server`에서 `docker compose up -d`
2. `./gradlew bootRun --args='--spring.profiles.active=local'`
3. `bash tickets/B16/repro.sh` — Redis 컨테이너를 일시 정지한다(연결은 살아 있는데 응답이 없다)
   - 기대 증상: `POST /api/posts`와 `GET /api/posts/popular`가 15초 안에 끝나지 않는다.
4. `bash tickets/B16/repro.sh stop` — Redis 컨테이너를 내린다(연결 끊김)
   - 기대 증상: 글쓰기는 201이지만 `GET /api/posts/popular`가 500이다.
5. 멈춘 동안 다른 터미널에서 `jcmd $(pgrep -f BoardApplication) Thread.print`로 스레드 덤프를 뜬다.

## 제출물

- 원인 서술: 요청 스레드가 무엇을 기다렸고, 왜 캐시 장애가 글쓰기·인기글 실패가 됐는가. "응답 지연"과 "연결 끊김"이 각각 어떻게 번졌는지 나눠서
- 재현 테스트: Toxiproxy로 Redis 응답을 3초 늦춘 경우와 연결을 끊은 경우 각각, 글쓰기 201·인기글 200이 1초 안인지 보는 테스트(결함 상태에서 실패 → 수정 후 통과)
- 수정 diff

## 힌트

<details>
<summary>1. 스레드 덤프에서 기다리는 곳을 찾는다</summary>

`http-nio-8080-exec-*` 스레드 가운데 `TIMED_WAITING`/`WAITING`인 것의 스택을 위에서 아래로 읽는다.
`io.lettuce.core.LettuceFutures.awaitOrCancel` → `StringRedisTemplate`… → `ActivityRankingService`/`PopularPostService` 순서라면 DB가 아니라 Redis 응답을 기다리는 중이다.
스택 아래쪽에 `TransactionSynchronizationUtils.invokeAfterCompletion`이 있으면 커밋이 끝난 뒤 리스너(`@TransactionalEventListener(AFTER_COMMIT)`)에서 기다리는 것이다. APM에서 트랜잭션 메서드가 "길어 보인" 이유도 여기서 나온다.
</details>

<details>
<summary>2. 얼마나 기다리는가</summary>

`application.yml`의 `spring.data.redis.*`를 spec-v2 8절의 운영 값과 비교한다. 명령 타임아웃을 주지 않으면 Lettuce 기본값(60초)을 쓴다.
글 하나 쓸 때 Redis를 몇 번 부르는지도 세어 본다(커밋 뒤 랭킹 가산, 인기글 캐시 삭제).
</details>

<details>
<summary>3. 실패는 어디까지 올라가는가</summary>

`RedisGuard`가 무엇을 잡고 무엇을 올리는지 본다. 끊긴 연결에 명령을 보내면 Lettuce가 `Currently not connected`로 거절하고,
Spring은 이를 `RedisSystemException`으로 바꾼다. 응답이 늦어 타임아웃이 나면 `QueryTimeoutException`이다. 둘 다 `RedisConnectionFailureException`이 아니다.
</details>

<details>
<summary>4. 테스트로 고정하기</summary>

`@SpringBootTest(properties = "test.redis.route=proxy")`로 Toxiproxy를 거쳐 Redis에 붙는 컨텍스트를 만든다. 장애를 넣기 전에 정상 상태로 한 번씩 불러 기동 비용을 측정에서 뺀다.
지연은 `RedisContainers.proxy().toxics().latency(…, DOWNSTREAM, 3000)`, 끊김은 `RedisContainers.proxy().disable()`. 끝나면 `RedisContainers.healProxy()`로 되돌리고 재연결을 기다린다.
두 시나리오는 컨텍스트를 따로 둔다(앞 시나리오가 남긴 폴백 상태가 다음 측정에 섞이지 않게).
</details>

## 원인과 정답

<details>
<summary>펼치기</summary>

**원인.** 두 가지가 겹쳤다.
① `application.yml`에서 Redis 명령 타임아웃(`spring.data.redis.timeout`)을 지웠다("큰 명령이 중간에 끊기면 안 되므로 기본값"). Lettuce 기본값은 60초다.
Redis가 응답하지 않으면 글쓰기 커밋 뒤의 랭킹 가산·인기글 캐시 삭제가 각각 그만큼 요청 스레드를 붙잡고, 인기글 조회도 캐시 조회·저장에서 같은 시간을 기다린다.
② `RedisGuard`가 `RedisConnectionFailureException`(처음부터 붙지 못함)만 잡고 나머지는 올린다. 끊긴 연결의 명령 거절(`RedisSystemException`)과 명령 타임아웃(`QueryTimeoutException`)은 폴백되지 않아 인기글 조회가 500이 된다.
기존 테스트는 "Redis 없이 기동"(처음부터 연결 거부)만 남아 있어 둘 다 보지 못했다. DB 락은 오진이다. 글은 이미 커밋됐고(커넥션도 커밋 직후 풀에 돌아간다), 커밋 뒤 동기화 콜백에서 Redis를 기다린 것이다.

**정답 수정.** 명령 타임아웃 500ms를 되살리고(spec-v2 8절), `RedisGuard`는 `DataAccessException` 전체를 Redis 장애로 보고 폴백한다.
한 번 실패하면 5초 동안 Redis를 건너뛰는 기존 동작 덕분에 글 하나에 Redis 호출이 두 번이어도 타임아웃은 한 번만 기다린다.
타임아웃만 고치면 인기글 500과 "500ms × 호출 수"가 남고, 예외만 고치면 지연 장애에서 60초를 그대로 기다린다. 둘 다 고쳐야 한다. (`tickets/B16/answer/fix.patch`)

**확인 테스트.** `tickets/B16/answer/B16ConfirmTest.java` — `Redis_응답이_3초씩_늦으면`·`Redis_연결이_끊기면` 각각 `장애_중에도_글쓰기_201과_그_뒤_인기글_200이_각각_1초_안이다`, `장애_뒤_첫_요청인_인기글도_1초_안에_DB_결과로_200이다`

**1단계 정답 서버는?** `board-server/src/main/resources/application.yml`이 `timeout: 500ms`·`connect-timeout: 500ms`를 두고,
`board-server/src/main/java/com/example/board/config/RedisGuard.java`가 `DataAccessException`을 잡아 폴백한 뒤 5초간 건너뛴다.
`PopularPostFallbackTest`의 "Redis가 느리면" 테스트들이 지연 3초에서도 1초 안을 확인했는데, 이 서버에서는 지워져 있다.
</details>
