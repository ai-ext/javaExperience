#힌트

1. 요청 ID로 로그를 줄 세운다

로그 줄마다 [요청ID]가 찍힌다. 숨김 요청의 ID로 인기글 캐시 삭제·Committing JPA transaction을 찾고, 그 사이에 다른 요청 ID의 인기글 캐시 적재가 끼어 있는지 본다. 끼어 있다면 그 요청은 커밋 전 DB(아직 ACTIVE)를 읽어 캐시에 다시 넣은 것이다.

2. 캐시를 지우는 곳이 몇 군데인지 본다

글 작성·수정·삭제는 PostChangedEvent → PostCacheEvictListener(@TransactionalEventListener(AFTER_COMMIT))로 지운다. 숨김은 어떻게 지우는지 AdminService.hidePost를 본다. 트랜잭션 안에서 바로 지우면 "지운 시점"과 "새 값이 보이는 시점(커밋)" 사이에 틈이 생긴다.

3. 틈을 테스트로 벌린다

별도 Connection으로 SELECT id FROM post WHERE id = ? FOR UPDATE를 잡은 채, 다른 스레드에서 숨김 요청을 보낸다. 숨김 요청은 커밋 전에 그 행 잠금에서 멈춘다. 멈췄는지는 SQL 문장 모양(update post …)이 아니라 잠금 대기로 본다. performance_schema.data_lock_waits·data_locks에서 "잠근 연결(CONNECTION_ID())의 post 행을 기다리는 트랜잭션"을 센다. 이 표는 PROCESS 권한이 있어야 보여서 테스트에서는 컨테이너 root(MySQLContainer의 JDBC URL·비밀번호)로 읽는다. 그러면 숨김 쪽이 UPDATE에서 기다리든 SELECT … FOR UPDATE에서 기다리든 같다. 기다리는 반복문에는 마감 시간을 두고, 숨김 요청이 먼저 끝나 버렸는지(isDone())도 함께 본다. 끝나 버렸다면 그 응답·예외를 실패 메시지에 담는다. 그 사이에 인기글을 읽고, 잠금을 푼 뒤 다시 읽어 숨긴 글이 없는지 단언한다. 끝낼 때 스레드를 interrupt하지 않는다(진행 중인 Redis 명령이 실패해 다음 테스트까지 캐시가 꺼진다).

#원인과 정답

펼치기

원인. AdminService.hidePost가 "신고로 숨긴 글은 바로 내려야 한다"며 이벤트를 거치지 않고 트랜잭션 안에서 popularPostService.evict()를 직접 부른다. 순서는 이렇다.

  1. 숨김 요청이 캐시를 지운다(커밋 전).
  2. 다른 요청이 인기글을 부른다. 캐시가 비어 DB를 읽는데, 숨김은 아직 커밋 전이라 그 글이 ACTIVE로 보인다. 이 옛 값을 60초 TTL로 다시 적재한다.
  3. 숨김이 커밋된다. 그 뒤로 캐시를 지우는 사람이 없어 TTL 동안 숨긴 글이 보인다.

트래픽이 많을수록 2번이 끼어들 확률이 커진다("가끔, 바쁜 시간대에"). 롤백될 때도 캐시를 이미 지워 버린다(쓸데없는 DB 부하). TTL을 줄이면 증상 시간만 줄 뿐 순서 문제는 남는다.

정답 수정. 숨김도 다른 글 변경처럼 PostChangedEvent를 발행한다. 그러면 기존 PostCacheEvictListener가 커밋 뒤에 지운다. 커밋 전에 끼어든 재적재가 있어도 커밋 뒤 삭제가 그것을 지운다. 롤백되면 리스너가 돌지 않아 캐시는 그대로다. (tickets/B15/answer/fix.patch — AdminService 수정과 HidePostCacheRaceTest 추가) 같은 효과의 다른 수정도 맞다. 예를 들어 TransactionSynchronization.afterCommit에서 지우는 방식이다. 커밋 전·후에 두 번 지우는 방식("지연 이중 삭제")은 롤백 때 캐시를 잃는다. 확인 테스트의 롤백 검사에 걸린다.

확인 테스트. tickets/B15/answer/B15ConfirmTest.java

  • 숨김이_커밋되기_전에_다른_요청이_인기글을_읽어도_커밋_뒤_조회에는_숨긴_글이_없다 — 글 행 잠금으로 숨김 커밋을 멈추고(멈춘 것은 잠금 대기 표로 확인, 상한 10초), 그 사이 인기글 조회 → 잠금 해제 → 숨긴 글 없음
  • 숨김이_롤백되면_인기글_캐시는_그대로_남는다 — 바깥 트랜잭션에서 hidePost 뒤 롤백 → 캐시 값 그대로

1단계 정답 서버는? board-server/src/main/java/com/example/board/admin/AdminService.java는 숨김에서 PostChangedEvent를 발행한다. board-server/src/main/java/com/example/board/post/PostCacheEvictListener.java(AFTER_COMMIT)와 PostCacheEvictListenerTest가 커밋 뒤 삭제·롤백 보존을 고정했다. 이 서버에서는 리스너 테스트가 남아 있어도 숨김 경로가 리스너를 타지 않아 걸리지 않는다.

남는 틈. 커밋 뒤에 지워도, 숨김 커밋 전에 DB를 읽기 시작한 적재 요청이 삭제 뒤에 옛 목록을 저장하면 같은 증상이 남는다(DB 조회 → 숨김 커밋·캐시 삭제 → 늦은 저장). 이 틈은 적재 쪽을 고치는 고도화 E01에서 막는다(무효화 세대 번호 + Lua 비교 저장, 정답 서버 answer-fix(D09-3)과 같은 방식).

함께 볼 것. 같은 인기글 코드의 고도화 E01(스탬피드·적재 중 무효화)과 fix.patch가 함께 적용된다(tools/tickets/verify.sh --all-fixes B15 E01).
