# E01. 고도화: 인기글 캐시 재적재를 한 요청만 하도록 (스탬피드 방지)

> 같은 날: D14 ⑤ · 고도화(필수 1건) · 진단 도구: DB 쿼리 실행 횟수(performance_schema 다이제스트), 서버 로그의 "인기글 캐시 적재" 줄 수

## 받은 요청

> 이벤트 배너로 메인 트래픽이 몰리는 날, 인기글 캐시가 만료되는 1분마다 DB CPU가 잠깐씩 튑니다. 캐시가 있는데 왜 DB를 그렇게 많이 읽는지 봐 주세요.
> 응답 형식은 앱이 이미 쓰고 있으니 바꾸면 안 됩니다. — 플랫폼팀

## 환경과 재현

1. `messy-server`에서 `docker compose up -d`
2. `./gradlew bootRun --args='--spring.profiles.active=local'`
3. `bash tickets/E01/repro.sh` (`N=200`처럼 동시 수를 바꿀 수 있다)
   - Redis의 `popular:posts`를 지워 TTL이 막 끝난 순간을 만들고, `GET /api/posts/popular`를 동시에 100개 보낸다. 전후로 performance_schema에서 인기글 쿼리 실행 횟수를 센다.
   - 기대 증상: DB 인기글 쿼리가 100번 가까이 실행되고, 서버 로그에 `인기글 캐시 적재`가 그만큼 찍힌다.

## 제출물

- 설계 메모: 무엇을 한 요청만 하게 할지, 기다리는 요청은 얼마나 기다리고 그 뒤에는 어떻게 할지, 서버가 여러 대면 어떻게 달라지는지
- 테스트: 캐시가 빈 순간 동시 100요청에 DB 목록 쿼리 1회(예: `src/test/java/com/example/board/post/PopularPostStampedeTest.java`, `MyBatisQueryCounter`로 센다). 응답 형식이 그대로인지도 본다.
- 수정 diff

## 힌트

<details>
<summary>1. 캐시가 빈 순간 무슨 일이 일어나는지 센다</summary>

`PopularPostService.getPopular`는 캐시가 없으면 바로 `mapper.findPopular`를 부르고 캐시에 쓴다. 동시에 들어온 요청은 모두 "캐시 없음"을 보고 각자 DB를 읽는다.
`MyBatisQueryCounter.attach(sqlSessionFactory)`를 붙이고 스레드 100개를 `CountDownLatch`로 한꺼번에 출발시켜 `count("findPopular")`를 본다.
</details>

<details>
<summary>2. 한 요청만 읽고 나머지는 그 결과를 받는다(single-flight)</summary>

JVM 안에서는 `ReentrantLock`이나 "진행 중인 적재"를 담은 `CompletableFuture` 하나로 충분하다.
락을 쓰면 락을 얻은 뒤 캐시를 한 번 더 본다. 앞 요청이 이미 채웠을 수 있다. 다시 보지 않으면 줄 선 요청이 차례로 모두 DB를 읽는다.
</details>

<details>
<summary>3. 기다림에 상한을 둔다</summary>

적재하는 요청이 Redis 지연(명령 타임아웃 500ms)이나 DB 지연에 걸리면, 상한 없는 `lock()`·`get()` 앞에서 모든 요청이 함께 멈춘다.
`tryLock(시간)`이나 `future.get(시간)`으로 상한을 두고, 넘으면 DB에서 바로 읽어 응답한다(캐시는 적재하는 요청에 맡긴다).
상한은 응답 예산(인기글 1초)과 Redis 타임아웃을 함께 보고 정한다.
</details>

## 원인과 정답

<details>
<summary>펼치기</summary>

**원인.** 캐시 미스 때 재적재를 막는 장치가 없다. 주석은 "캐시가 비는 건 60초에 한 번이고 가볍다"고 하지만, 비는 그 순간 들어온 요청 수만큼 DB 조회가 겹친다.
확인 테스트 기준으로 동시 100요청에 `findPopular`가 97번 실행됐다. 무효화(글 변경 커밋)마다도 같은 일이 생긴다.

**정답 수정(예).** (`tickets/E01/answer/fix.patch`)
- `PopularPostService`에 진행 중인 적재를 담는 `AtomicReference<CompletableFuture<List<PopularPost>>>`를 둔다.
- 캐시가 비면 자리를 차지한 한 요청만 캐시를 한 번 더 보고, DB를 읽어 캐시에 쓴 뒤 결과를 `complete`한다.
- 나머지 요청은 `get(1초)`로 그 결과를 받는다. 1초가 넘거나 적재가 실패하면 DB에서 바로 읽는다. 끝나면 자리를 비운다.
- Redis 장애 때는 캐시 읽기·쓰기가 `RedisGuard`로 건너뛰어진다. 그때도 동시 요청은 한 번의 DB 조회를 함께 받는다.
- `PopularPostStampedeTest`를 추가했다.

다른 정답도 된다. 상한을 둔 `ReentrantLock.tryLock` + 락 안 재확인, 또는 서버가 여러 대이고 DB 부하가 문제라면 Redis `SET NX PX` 락 + 짧은 대기 + 폴백이다.
서버 대수만큼 DB 조회가 남는 JVM 락으로 충분한지, Redis 락이 Redis 장애 때 함께 사라지는 것을 감수할지가 판단 지점이다.

**확인 테스트.** `tickets/E01/answer/E01ConfirmTest.java` — `캐시가_빈_순간_동시_100요청에도_DB_목록_쿼리는_1번이고_응답은_평소와_같다`
- 100요청 모두 200이고 `findPopular` 1회다.
- 각 응답 본문이 캐시를 지운 뒤 DB에서 바로 읽은 응답과 같다.

**1단계 정답 서버는?** `board-server/src/main/java/com/example/board/post/PopularPostService.java`는 `ReentrantLock` + 락 안 재확인으로 막았다. `PopularPostCacheTest`의 동시 20요청 테스트가 고정했다.
이 서버에서는 락과 그 테스트가 빠져 있다. 정답 서버의 `lock()`에는 기다림 상한이 없다. 고도화에서는 상한까지 둔다.

**함께 볼 것.** B15(숨긴 글이 인기글에 남음)와 같은 파일 주변을 고친다. 두 fix.patch는 함께 적용된다(`tools/tickets/verify.sh --all-fixes B15 E01`).
</details>
