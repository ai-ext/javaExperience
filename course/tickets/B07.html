#받은 티켓

오늘 10시 선착순 쿠폰(1,000장) 오픈 때 "받기를 눌렀더니 오류가 났다"는 문의가 수십 건 들어왔습니다. 다시 누르면 대부분 받아집니다. 쿠폰은 10시 5분까지 남아 있었으니 수량이 모자란 것은 아닙니다. 오픈 직후 몇 초 동안만 그렇고, 평소에 한 명씩 받을 때는 한 번도 재현되지 않습니다. — CS팀

#환경과 재현

  1. messy-server에서 docker compose up -d
  2. ./gradlew bootRun --args='--spring.profiles.active=local'
  3. bash tickets/B07/repro.sh (기본 20명, N=30으로 바꿀 수 있다)
    • 수량이 인원만큼인 쿠폰을 새로 만들고 회원 N명이 동시에 발급을 누른다.
    • 기대 증상: 일부가 500. 서버 로그에 Deadlock found when trying to get lock; try restarting transaction(MySQL 1213), SHOW ENGINE INNODB STATUS의 LATEST DETECTED DEADLOCK에 member_coupon 두 트랜잭션이 보인다.

#제출물

  • 원인 서술: 데드락의 두 트랜잭션이 각각 무엇을 쥐고 무엇을 기다렸는가(락 종류·인덱스까지)
  • 재현 테스트: 수량이 충분한 쿠폰을 여러 회원이 동시에 받을 때 모두 201이고, 수량이 모자라면 나머지는 정해진 409(/errors/coupon-exhausted)인지 보는 테스트(결함 상태에서 실패 → 수정 후 통과). 예: src/test/java/com/example/board/coupon/CouponUseDeadlockTest.java

#힌트

1. 500의 정체부터 확인한다

서버 로그에서 500 요청의 원인 예외를 찾는다. CannotAcquireLockException/DeadlockLoserDataAccessException과 SQL 상태 40001, 오류 코드 1213이면 데드락이다. 락 대기 시간 초과(1205)와도 다르다. UNIQUE 위반(1062 Duplicate entry)이면 이미 409로 바뀌므로 500이 되지 않는다. 둘을 구분한다.

2. 데드락 기록을 읽는다

재현 직후 root로 SHOW ENGINE INNODB STATUS\G를 보고 LATEST DETECTED DEADLOCK의 (1)(2) 트랜잭션에서 HOLDS THE LOCK(S)와 WAITING FOR THIS LOCK TO BE GRANTED를 짝지어 본다. 두 트랜잭션이 기다리는 것이 서로 다르다. 한쪽은 member_coupon의 uk_member_coupon_coupon_member 인덱스에 락(lock_mode X, 새 쿠폰이면 supremum)을 쥔 채 coupon 행 락(update coupon ...)을 기다리고, 다른 쪽은 그 coupon 행 락을 쥔 채 같은 인덱스 자리에 insert intention 락을 기다린다. 각 쪽이 쥔 락은 어떤 SQL이 걸었는가? 특히 member_coupon에 아직 아무것도 쓰지 않은 쪽이 왜 그 인덱스에 락을 쥐고 있는가?

3. 조회와 잠금 범위를 확인한다

REPEATABLE READ에서 결과가 없는 SELECT ... FOR UPDATE는 그 키가 들어갈 자리(갭)를 잠근다. 갭 락끼리는 서로 막지 않아 여러 트랜잭션이 같은 갭을 함께 쥘 수 있다. 그런데 그 갭에 INSERT하려면 삽입 의도 락이 필요하고, 그것은 남이 쥔 갭 락에 막힌다. 새 쿠폰의 발급 키(쿠폰 id, 회원 id)는 모두 같은 갭에 들어간다.

#원인과 정답

펼치기

원인. CouponService.issueInDb가 "연타 방지"를 위해 MemberCouponRepository.findByCouponIdAndMemberIdForUpdate(SELECT ... FOR UPDATE)로 아직 없는 발급 행을 잠그고 확인한 뒤 increaseIssued(쿠폰 행 UPDATE)와 member_coupon INSERT를 한다. 동시 요청 A·B가 모두 같은 갭에 갭 락을 잡고, A가 쿠폰 행 락을 얻은 뒤 INSERT하려 하면 B의 갭 락에 막히고, B는 A가 쥔 쿠폰 행 락을 기다린다. InnoDB가 순환 대기를 보고 한쪽을 롤백(1213)하고, 그 요청은 500이 된다. 평소 한 명씩 받을 때는 갭을 나눠 가질 상대가 없어 재현되지 않는다. KINTO의 결제 중복 확인 FOR UPDATE 데드락과 같은 구조다.

정답 수정. 이미 받았는지는 잠그지 않고 확인하고(existsByCouponIdAndMemberId), 동시에 둘 다 통과한 경우는 UNIQUE(coupon_id, member_id) 위반을 잡아 409로 바꾼다. 쓰지 않게 된 잠금 조회 메서드는 지운다(tickets/B07/answer/fix.patch). 총량은 원래대로 조건부 UPDATE(issued_quantity < total_quantity)가 지킨다. 데드락 재시도를 덧붙이는 것은 원인을 남겨 두는 땜질이고, 넣더라도 트랜잭션 밖에서 해야 한다.

확인 테스트. tickets/B07/answer/B07ConfirmTest.java — 수량_20장을_20명이_동시에_받으면_모두_201이다, 수량_10장을_20명이_동시에_받으면_10명은_201_나머지는_409다 201·409가 아닌 응답은 원인 예외의 SQL 오류 코드로 나눠 "데드락(1213/40001)이 아닌 실패"와 "데드락으로 실패한 요청"을 따로 단언하고, 회차마다 MySQL의 1213 발생 수(performance_schema.events_errors_summary_global_by_error, root로 조회) 증가분을 메시지에 남긴다. 409는 본문 type이 /errors/coupon-exhausted인지까지 본다.

1단계 정답 서버는? board-server/src/main/java/com/example/board/coupon/CouponService.java는 잠금 조회 없이 exists 확인 → 조건부 UPDATE → INSERT 순서이고, 최종 방어선은 schema.sql의 uk_member_coupon_coupon_member다. CouponIssueApiTest·CouponIssueConcurrencyTest의 동시 발급 테스트가 이것을 확인했는데, 이 서버에서는 그 테스트들의 단언이 "총량을 넘지 않는다"만 보도록 약해져 있다(500이 섞여도 통과한다).
