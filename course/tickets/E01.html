#받은 요청

이벤트 배너로 메인 트래픽이 몰리는 날, 인기글 캐시가 만료되는 1분마다 DB CPU가 잠깐씩 튑니다. 캐시가 있는데 왜 DB를 그렇게 많이 읽는지 봐 주세요. 응답 형식은 앱이 이미 쓰고 있으니 바꾸면 안 됩니다. — 플랫폼팀

#진행 순서와 선행 자료

연결 개념과 선택 티켓 확인

먼저 J07의 공유 상태·동시 요청, J12의 책임별 메서드 읽기, J14의 값 없음과 빈 결과, D09의 캐시 조회·쓰기 계약을 확인한다. B15·B16은 관련 증상과 현재 수정 여부를 확인할 자료이며, 선택하지 않은 티켓을 먼저 해결해야 하는 것은 아니다.

동시 적재: 캐시가 빈 순간 동시 100요청의 정상 응답 형식을 유지하면서 DB 목록 쿼리가 1회인지 확인한다.

#힌트

1. 캐시가 빈 순간 무슨 일이 일어나는지 센다▸

PopularPostService.getPopular는 캐시가 없으면 바로 mapper.findPopular를 부르고 캐시에 쓴다. 동시에 들어온 요청은 모두 "캐시 없음"을 보고 각자 DB를 읽는다. MyBatisQueryCounter.attach(sqlSessionFactory)를 붙이고 스레드 100개를 CountDownLatch로 한꺼번에 출발시켜 count("findPopular")를 본다.

2. 한 요청만 읽고 나머지는 그 결과를 받는다(single-flight)▸

JVM 안에서는 ReentrantLock이나 "진행 중인 적재"를 담은 CompletableFuture 하나로 충분하다. 락을 쓰면 락을 얻은 뒤 캐시를 한 번 더 본다. 앞 요청이 이미 채웠을 수 있다. 다시 보지 않으면 줄 선 요청이 차례로 모두 DB를 읽는다.

3. 기다림에 상한을 둔다▸

적재하는 요청이 Redis 지연(명령 타임아웃: B16을 고쳤으면 500ms, 고치지 않았으면 Lettuce 기본 60초)이나 DB 지연에 걸리면, 상한 없는 lock()·get() 앞에서 모든 요청이 함께 멈춘다. tryLock(시간)이나 future.get(시간)으로 상한을 두고, 넘으면 DB에서 바로 읽어 응답한다(캐시는 적재하는 요청에 맡긴다). 상한은 응답 예산(인기글 1초)과 Redis 타임아웃을 함께 보고 정한다. 첫 적재가 예외로 끝나면 기다리던 요청에 그 예외를 그대로 넘기지 않는다.

4. 적재하는 동안 글이 바뀌면▸

적재 요청이 DB를 읽은 뒤 캐시에 쓰기 전에, 다른 요청이 글을 지우고 커밋한 뒤 캐시를 지웠다고 해 보자. 적재 요청은 지금 무엇을 캐시에 쓰는가? 테스트로는 MyBatis Interceptor를 이미 뜬 SqlSessionFactory에 붙여 findPopular의 DB 조회 직후 CountDownLatch로 멈추게 하면 이 순서를 매번 만들 수 있다. "내가 읽기 시작한 뒤에 무효화가 있었는지"를 저장하는 순간에 알아야 한다. 서버가 여러 대이면 그 표시는 JVM 밖(Redis)에 있어야 한다. 함께 받는 쪽도 본다. 무효화 뒤에 온 요청이 무효화 전에 시작한 적재의 결과를 받아 가면 안 된다.

#원인과 구현 예시

펼치기▸

원인. 캐시 미스 때 재적재를 막는 장치가 없다. 주석은 "캐시가 비는 건 60초에 한 번이고 가볍다"고 하지만, 비는 그 순간 들어온 요청 수만큼 DB 조회가 겹친다. 첫 적재를 멈춰 둔 확인 테스트에서는 그사이 들어온 요청이 저마다 DB를 읽어 findPopular가 1번이 아니라 십수 번 실행됐다(커넥션 풀 크기에 따라 다르다). 무효화(글 변경 커밋)마다도 같은 일이 생긴다.

적재 중 무효화. 무효화(커밋 뒤 캐시 삭제)는 DEL 하나뿐이고 적재는 무조건 SET이다. DB 조회 → 글 숨김·삭제 커밋과 캐시 삭제 → 늦은 SET 순서가 되면 옛 목록이 TTL 동안 다시 보인다. B15를 고쳐 커밋 뒤에 지워도 이 틈은 남는다. single-flight를 더하면 한 가지가 더 생긴다. 무효화 뒤에 온 요청이 무효화 전에 시작한 적재에 합류하면, 삭제 응답 뒤인데도 옛 목록을 받는다.

구현 예시 수정(예). (tickets/E01/answer/fix.patch)

  • 무효화 세대 번호 popular:posts:gen(만료 없음)을 둔다. 무효화는 Lua 한 번으로 "세대 +1, 캐시 삭제", 적재는 DB를 읽기 전에 본 세대가 그대로일 때만 Lua 한 번으로 저장한다. 세대를 못 읽으면(Redis 장애) 저장하지 않는다. 구현 예시 서버 answer-fix(D09-3)(커밋 eab20ce5)과 같은 방식이다.
  • 진행 중인 적재를 세대별로 하나씩 담는 ConcurrentHashMap<세대, CompletableFuture<List<PopularPost>>>를 둔다. 같은 세대의 요청만 결과를 함께 받는다. 무효화 뒤에 온 요청은 새 세대라 따로 읽는다.
  • 자리를 차지한 한 요청만 캐시를 한 번 더 보고, DB를 읽어 (세대가 같으면) 캐시에 쓴 뒤 결과를 complete한다. 끝나면 자리를 비운다.
  • 나머지 요청은 get(1초)로 그 결과를 받는다. 1초가 넘거나 적재가 실패하면 DB에서 바로 읽는다.
  • RedisGuard가 처리하는 연결 실패는 캐시 읽기·쓰기를 건너뛰어 DB로 진행한다. B16 수정 전에는 명령 타임아웃(기본 60초)·명령 거절이 그대로 전파되므로 E01만으로 장애 폴백을 보장하지 않는다. B16을 고치면 이 예외도 폴백한다. single-flight의 공유 범위는 같은 세대이며, 대기 상한을 넘긴 요청은 별도로 DB를 읽을 수 있다.
  • PopularPostStampedeTest를 추가했다.

다른 구현 예시도 된다. 상한을 둔 ReentrantLock.tryLock + 락 안 재확인, 또는 서버가 여러 대이고 DB 부하가 문제라면 Redis SET NX PX 락 + 짧은 대기 + 폴백이다. 어느 쪽이든 늦은 저장을 막는 장치(세대 비교 저장 등)는 따로 있어야 한다. JVM 락으로 적재와 무효화를 묶으면 서버 한 대 안에서만 막히고 다른 서버의 무효화는 못 막는다. 서버 대수만큼 DB 조회가 남는 JVM 락으로 충분한지, Redis 락이 Redis 장애 때 함께 사라지는 것을 감수할지가 판단 지점이다.

확인 테스트. tickets/E01/answer/E01ConfirmTest.java — 첫 적재의 findPopular DB 조회 직후를 MyBatis 인터셉터로 멈춰 순서를 고정한다(시간에 맡기지 않는다). 구현 방식은 보지 않고 쿼리 수·응답·캐시만 본다.
