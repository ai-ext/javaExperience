# B12. 새 프론트 도메인에서만 호출이 실패한다

> 같은 날: D14 ① · 선택 후보(Security) · 진단 도구: 브라우저 개발자 도구(Network·Console), `curl -X OPTIONS`

## 받은 티켓

> 새 프론트(`http://127.0.0.1:8765`)를 붙였는데 로그인 버튼부터 아무 반응이 없습니다. 기존 웹(`localhost:3000`)은 멀쩡합니다.
> 지난주에 서버 담당자분이 새 도메인을 CORS 설정에 추가했다고 들었고, 서버 에러 로그에도 아무것도 안 남아서 프론트 쪽 문제로 보고 있습니다.
> 서버 쪽에서 한 번만 더 봐 주실 수 있을까요? — 프론트 개발자

## 환경과 재현

1. `messy-server`에서 `docker compose up -d`
2. `./gradlew bootRun --args='--spring.profiles.active=local'`
3. `bash tickets/B12/repro.sh` — curl로 브라우저의 preflight를 흉내 낸다
   - 기대 증상: `localhost:3000`의 preflight는 200 + `Access-Control-Allow-Origin`. `127.0.0.1:8765`의 preflight는 403 `Invalid CORS request`, 허용 헤더 없음. 서버 로그는 조용하다.
4. 브라우저로 보기: `bash tickets/B12/repro.sh browser` 후 `http://127.0.0.1:8765/`를 열고 개발자 도구를 켠 채 버튼을 누른다.
   Network 탭에서 실패한 `OPTIONS` 요청을, Console에서 CORS 오류 문구를 확인한다.

## 제출물

- 원인 서술: 기존 출처와 새 출처의 결과가 왜 다른가, 그리고 그렇게 판단한 관찰 근거(Network 탭·응답 헤더·서버 설정)
- 재현 테스트: 새·기존·목록에 없는 출처로 preflight(`OPTIONS` + `Origin` + `Access-Control-Request-Method`/`-Headers`)를 보내 상태 코드와 허용 헤더를 단언하는 테스트(결함 상태에서 실패 → 수정 후 통과)
- 수정 diff

## 힌트

<details>
<summary>1. 브라우저는 무엇을 먼저 보내는가</summary>

`Authorization`이나 `Content-Type: application/json`이 붙은 교차 출처 요청은 본 요청 전에 `OPTIONS` preflight를 먼저 보낸다.
preflight가 200과 `Access-Control-Allow-Origin`을 받지 못하면 브라우저는 본 요청을 아예 보내지 않는다. 그래서 컨트롤러 로그도, 에러 로그도 없다.
Network 탭에서 `OPTIONS` 줄의 상태 코드와 응답 헤더를 본다. 403이고 본문이 `Invalid CORS request`면 서버의 CORS 처리기가 출처를 거절한 것이다.
</details>

<details>
<summary>2. preflight를 누가 처리하는가</summary>

요청은 Security 필터 체인을 먼저 지나고, 그 뒤에 DispatcherServlet(컨트롤러)에 닿는다. `SecurityConfig`의 `.cors(...)`는 필터 체인 안에 `CorsFilter`를 넣는데,
이 필터는 `CorsConfigurationSource` 빈의 설정을 쓴다. 출처가 그 목록에 없으면 여기서 403으로 끝난다.
`WebMvcConfigurer.addCorsMappings`는 DispatcherServlet 단계의 설정이라 그보다 뒤에 있다.
새 출처 설정이 코드 어디에 들어갔는지, 그리고 preflight가 그 설정까지 도달하는지 따져 본다.
</details>

<details>
<summary>3. 테스트로 고정하기</summary>

MockMvc의 `options("/api/posts").header("Origin", …).header("Access-Control-Request-Method", "POST").header("Access-Control-Request-Headers", "authorization,content-type")`로
새 출처·기존 출처·목록에 없는 출처(`http://evil.example`)를 각각 보내고, 상태 코드와 `Access-Control-Allow-Origin`·`-Methods`·`-Headers`를 본다.
새 출처로 토큰을 붙인 실제 `POST /api/posts`에도 허용 출처 헤더가 붙는지 함께 본다.
</details>

## 원인과 정답

<details>
<summary>펼치기</summary>

**원인.** 새 출처 `http://127.0.0.1:8765`가 `CorsConfig.addCorsMappings`(Spring MVC의 CORS 매핑)에만 들어가 있고,
Security가 쓰는 `corsConfigurationSource()` 빈의 허용 목록에는 `localhost:3000`만 있다.
preflight는 Security 필터 체인 안의 `CorsFilter`가 먼저 처리하므로, 새 출처는 여기서 403으로 거절되고 MVC 매핑까지 오지 못한다.
설정 파일에는 새 도메인이 "있으니" 서버 쪽은 맞다고 믿기 쉽다(받은 티켓의 오진). 같은 API를 curl로 부르면 멀쩡해 보이는 것도 헷갈림을 키운다. curl은 preflight를 보내지 않고 `Origin`도 붙이지 않아 CORS 검사를 받지 않는다.

**정답 수정.** 허용 출처를 Security가 쓰는 `CorsConfigurationSource` 한 곳에 모은다(spec-v2 3절의 두 출처). MVC 쪽 중복 매핑은 지운다.
CORS 설정이 두 곳에 있으면 다음 사람도 또 엉뚱한 곳에 추가한다. 와일드카드(`*`)나 `allowedOriginPatterns("*")`로 여는 것은 오답이다. (`tickets/B12/answer/fix.patch`)

**확인 테스트.** `tickets/B12/answer/B12ConfirmTest.java` — 새 출처 preflight 200·허용 헤더, 새 출처 로그인 preflight 200, 기존 출처 200, 목록에 없는 출처 거절, 새 출처 실제 글쓰기 201·허용 출처 헤더

**1단계 정답 서버는?** `board-server/src/main/java/com/example/board/config/CorsConfig.java`의 `CorsConfigurationSource` 빈 하나에 두 출처를 두고,
`SecurityConfig`의 `.cors(Customizer.withDefaults())`가 그 빈을 인증 필터 앞에서 쓴다. `SecurityRulesTest`가 두 출처의 preflight를 확인했는데, 이 서버에서는 기존 출처만 본다.
</details>
