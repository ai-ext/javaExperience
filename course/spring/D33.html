#오늘의 SQL

내 프로젝트의 disposable 실습 DB를 쓴다. D23에서 정한 예약·대상·지급 상태의 물리 이름과 필터로 아래 예시를 반드시 매핑한다. 예시의 member_coupon은 1단계 비교 모델이며 새 예약 테이블의 구현 예시가 아니다. practice·원본 서버 DB는 수정하지 않는다.

  1. 승인 시 고정한 예약 대상에서 지급되지 않은 식별 집합을 찾는다.

    확인할 성질 예약 ID를 고정해 대상 밖 회원과 다른 예약의 지급을 제외한다. 미지급 행의 FAILED/PENDING, attempts, next_retry_at을 함께 남기고 합의된 대기와 누락을 구분한다.

  2. 재시작 전후 중복 지급이 없는지 대사한다.

    확인할 성질 내 물리 테이블·키·필터로 옮긴 SQL, 관찰 시각, 실제 출력과 기대 성질의 일치 여부를 남긴다. 예시는 실행 결과가 아니다.

구현 예시 SQL · 직접 작성한 뒤 비교하기

아래는 비교용 SQL이다. 예약·대상·작업 모델은 내가 정한 물리 이름과 필터로 옮긴다. board-server의 설계 기준이다. 2단계에서는 같은 계열의 기존 스키마를 관찰한다. 내 물리 이름·키·정렬이 다르면 매핑해 비교한다. 아래 SQL은 실제 실행 결과가 아니며 예시 서버가 모든 불변식을 보장한다는 뜻도 아니다. 오류가 예상되는 문장은 하나씩 실행하고 실패 뒤 ROLLBACK을 별도로 보낸다.

#TC-D33-1

질문 어느 장애 지점이 가장 위험했나요?

답에 들어가야 할 것
  • beforeCommit은 미확정 상태이고 afterCommit은 DB 확정 뒤 응답 전일 수 있다.
  • 각 marker에서 실제 JVM을 종료하고 별도 연결로 확인한 행을 제시한다.
  • 재실행 중복/누락 위험이 큰 경계와 선택한 회복 대안의 비용을 설명한다.

#TC-D33-2

질문 재시작해도 누락이 없음을 어떻게 증명하나요?

답에 들어가야 할 것
  • 중단 전 대상 식별 집합을 기준 시점과 함께 보존한다.
  • 재시작·재처리 후 성공/실패/대기 집합을 서로 대사한다.
  • 중복·누락 0 또는 실제 차이·checkpoint와 commit 결과를 증거로 제시한다.

#TC-D33-3

질문 영구 실패는 언제 자동 재시도를 멈추나요?

답에 들어가야 할 것
  • 일시 실패와 입력 오류 등 영구 실패를 구분하는 기준을 말한다.
  • 재시도 횟수·backoff·최대 대기·격리/수동 처리 종료 조건을 정한다.
  • 영구 실패 fixture의 실제 시도 수·상태·운영자 후속 행동을 제시한다.
