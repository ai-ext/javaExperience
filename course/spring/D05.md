**만들 파일** (내 프로젝트 · 경로는 구현 예시 기준)

- **기존 수정**: `src/main/java/com/example/board/post/PostServiceImpl.java` · `src/main/java/com/example/board/post/PostController.java` · `src/main/java/com/example/board/post/PostRepository.java` · `src/main/java/com/example/board/common/GlobalExceptionHandler.java`

**겪을 것** 응답 DTO를 만들며 지연 로딩 연관(작성자·태그)을 건드리면 쿼리가 추가로 나가므로 SQL 로그로 쿼리 수를 센다. 선택 관찰: 주입 EM 프록시·실제 컨텍스트와 readOnly의 층별 동작을 각각 기록한다. 오늘은 선택 실험 중 하나만 골라도 되며 필수 채점에는 추가하지 않는다.

**완료 조건**

- 토큰 없이 `GET /api/posts/{postId}` → 200
- 없는 글 → 404 `/errors/not-found`
- `postId` = 0 → 400 `/errors/validation`

**명세** [`GET /api/posts/{postId}`](../spec-v2.md#4-엔드포인트)

<details class="step-hint" data-step="D05-1">
<summary>막히면</summary>

- 이 순서는 DB → 쿼리 → 서비스 → 컨트롤러 순으로: 기존 테이블과 제약을 확인한다 → 필요한 저장·조회 조건을 저장소에서 먼저 확인한다 → 업무 검증과 트랜잭션 경계를 연결한다 → DTO와 응답 계약을 연결해 호출로 확인한다. 앞서 만든 층은 재사용하고 이 순서에서 바꾸는 부분만 진행한다.
- `@PathVariable`의 `@Positive`는 Spring 6.1부터 내장 메서드 검증이 처리한다. 컨트롤러 클래스에 `@Validated`를 붙이지 않는다(붙이면 AOP 검증으로 바뀌어 `ConstraintViolationException`이 난다). 내장 검증이 던지는 `HandlerMethodValidationException`을 전역 처리기에서 400으로 바꾼다.
- `spring.jpa.show-sql` 또는 `logging.level.org.hibernate.SQL=DEBUG`로 조회 한 번에 SQL이 몇 번 나가는지 센다.

</details>

<details class="step-observations" data-step="D05-1">
<summary>선택 관찰 실험 · 필요한 실험을 골라 하세요</summary>

- 선택 관찰 A(10분, C09): 테스트 메서드의 자동 @Transactional과 OSIV를 끈 독립 fixture에서 같은 singleton의 @PersistenceContext 참조를 두 개의 순차 TransactionTemplate 실행에 사용한다. 각 tx 안에서 EntityManagerProxy.getTargetEntityManager()로 얻은 실제 EM 참조, 같은 ID의 find 결과 두 개와 contains를 기록한다. 같은 tx의 두 find는 같은 관리 객체, 두 tx의 실제 EM·관리 객체는 서로 다른지 참조 비교한다. System.identityHashCode 로그만으로 동일성을 확정하지 않는다. 주입 프록시가 같아도 컨텍스트는 tx별로 바뀐다. 실제 EM을 worker 사이에 공유하지 않는다.
- 선택 관찰 B(10분, C14): 현재 @Transactional의 완전한 import를 확인한다. jakarta.transaction.Transactional에는 readOnly 속성이 없으므로 org.springframework.transaction.annotation.Transactional을 사용하는 독립 테스트에서 ① 조회 후 관리 객체 변경 ② 신규 persist+flush(IDENTITY 포함) ③ 같은 tx에 참여하는 JdbcTemplate UPDATE ④ 바깥 read-write tx에 REQUIRED readOnly 메서드가 참여하는 경우를 하나씩 실행한다. 테스트 밖 새 tx로 행을 초기화하고, 별도 빈을 통해 호출한다. 매번 실제 tx의 readOnly 플래그·Hibernate flush mode·JDBC connection.isReadOnly·SQL·예외·쓰기 직후 같은 연결의 값·종료 후 새 연결의 값을 기록한다. 실험 쓰기는 rollback하고 데이터 확인은 별도 연결로 한다. 조회 최적화 힌트와 DB/driver의 쓰기 거절은 다른 층이며 readOnly를 쓰기 금지나 권한 검사로 취급하지 않는다. REQUIRED 참여가 기존 tx의 속성을 자동 변경한다고 가정하지 않는다. 환경별 실제 관측을 쓰고 특정 DML 성공/거절을 보편 결과로 적지 않는다.

</details>

```java
/** 호출하는 쪽에서 member·postTags가 이미 로딩돼 있어야 한다(fetch join). */
public record PostDetailResponse(Long id, Long authorId, String authorNickname, String title, String content,
        List<String> tags, int likeCount, OffsetDateTime createdAt, OffsetDateTime updatedAt) {

    private static final ZoneId KST = ZoneId.of("Asia/Seoul");

    public static PostDetailResponse from(Post post) {
        List<String> tags = post.getPostTags().stream().map(pt -> pt.getTag().getName()).toList();
        return new PostDetailResponse(post.getId(), post.getMember().getId(), post.getMember().getNickname(),
                post.getTitle(), post.getContent(), tags, post.getLikeCount(),
                post.getCreatedAt().atZone(KST).toOffsetDateTime(), post.getUpdatedAt().atZone(KST).toOffsetDateTime());
    }
}
```

```java
@SpringBootTest
@Import(TestcontainersConfig.class)
@ActiveProfiles("test")
@AutoConfigureMockMvc
public abstract class ApiTestSupport {

    @Autowired
    protected MockMvc mockMvc;

    @Autowired
    protected MemberRepository memberRepository;

    @Autowired
    protected JwtProvider jwtProvider;

    @Autowired
    protected JdbcTemplate jdbc;

    @Autowired
    protected EntityManagerFactory emf;

    protected Member newMember(Role role) {
        return memberRepository.saveAndFlush(Member.create(UUID.randomUUID() + "@t.com", "hash",
                "m" + UUID.randomUUID().toString().replace("-", "").substring(0, 10), role));
    }

    protected String bearer(Member member) {
        return "Bearer " + jwtProvider.issue(member.getId(), member.getRole());
    }

    protected Statistics statistics() {
        return emf.unwrap(SessionFactory.class).getStatistics();
    }

    protected Long newPost(Member author) {
        jdbc.update("INSERT INTO post (member_id, title, content, status, like_count, created_at, updated_at)"
                + " VALUES (?, '제목', '내용', 'ACTIVE', 0, NOW(6), NOW(6))", author.getId());
        return jdbc.queryForObject("SELECT MAX(id) FROM post WHERE member_id = ?", Long.class, author.getId());
    }
}
```

<details class="step-observations" data-step="D05-2">
<summary>꼭 할 관찰 · 증거를 완료 조건과 함께 제출하세요</summary>

- 꼭 할 관찰: flush 후 rollback(10분, C11·C16): 커밋된 제목 old를 가진 독립 글을 준비한다. A tx에서 find → 제목을 local로 변경 → 명시 flush 순으로 Java 값·SQL·A 연결의 JDBC SELECT·별도 autocommit B의 일반 SELECT 값을 기록한다. 기대: Java/A는 local, commit 전 B는 old다(READ COMMITTED 또는 REPEATABLE READ의 비잠금 읽기). A를 rollback한 뒤 B의 새 조회는 old, 기존 Java 객체는 local일 수 있다. commit 변형은 새 fixture로 반복해 B의 새 조회가 local인지 본다. SQL 발행과 확정을 구분하고 열린 B의 snapshot은 새 조회와 구별한다. 관련 JPQL/무관 JPQL 앞 AUTO flush 비교는 추가 선택이며 이 결과를 모든 native SQL에 일반화하지 않는다.
- 꼭 할 관찰: 공유 태그 수명(10분, I12·C17·C18): 새 회원 A/B의 글 두 개가 같은 새 태그를 순차 사용하게 한다. 기준은 공유 태그 1건·글별 연결 2건이다. A 글의 태그만 빈 목록으로 교체하면 공유 태그 1건·연결 1행, B 글은 계속 조회 가능해야 한다. 이어 A 글 soft delete 전후도 비교하고 연결 보존 정책과 공유 태그 수명을 구분한다. 독립 fixture에서 글·새 태그·연결을 만든 직후 RuntimeException으로 rollback시켜 관련 저장 영역이 원래 행 수로 돌아오는지 새 tx로 확인한다. FK/cascade REMOVE/orphanRemoval 설정을 읽고 연결 소유권과 공유 태그 삭제를 같은 뜻으로 두지 않는다. 서비스 수정은 이 관찰 과제의 필수 조건이 아니다.

```java
package com.example.board.comment;

import java.nio.charset.StandardCharsets;
import java.util.Base64;
import java.util.List;

import org.springframework.data.domain.PageRequest;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import com.example.board.common.BusinessException;
import com.example.board.common.ErrorCode;
import com.example.board.member.MemberRepository;
import com.example.board.member.Role;
import com.example.board.post.PostRepository;
import com.example.board.post.PostStatus;

@Service
public class CommentService {

    private final CommentRepository commentRepository;
    private final PostRepository postRepository;
    private final MemberRepository memberRepository;

    public CommentService(CommentRepository commentRepository, PostRepository postRepository,
            MemberRepository memberRepository) {
        this.commentRepository = commentRepository;
        this.postRepository = postRepository;
        this.memberRepository = memberRepository;
    }

    @Transactional
    public CommentResponse create(Long postId, Long memberId, String content) {
        requireActivePost(postId);
        Comment saved = commentRepository.save(Comment.create(postRepository.getReferenceById(postId),
                memberRepository.getReferenceById(memberId), content));
        // 응답에 작성자 닉네임이 필요해서 member를 실제로 읽는다(작성 1건이라 N+1이 아니다)
        return CommentResponse.from(saved);
    }

    @Transactional(readOnly = true)
    public CommentPage list(Long postId, String cursor, int size) {
        long afterId = decode(cursor);
        requireActivePost(postId);
        List<Comment> rows = commentRepository.findPage(postId, afterId, PageRequest.of(0, size + 1));
        boolean hasNext = rows.size() > size;
        List<Comment> page = hasNext ? rows.subList(0, size) : rows;
        String next = hasNext ? encode(page.get(page.size() - 1).getId()) : null;
        return new CommentPage(page.stream().map(CommentResponse::from).toList(), next);
    }

    /** 대상 없음(404)을 작성자 검사(403)보다 먼저 한다. */
    @Transactional
    public void delete(Long commentId, Long memberId, Role role) {
        Comment comment = commentRepository.findByIdAndDeletedFalse(commentId)
                .orElseThrow(() -> new BusinessException(ErrorCode.NOT_FOUND, "댓글을 찾을 수 없습니다."));
        if (role != Role.ADMIN && !comment.isWrittenBy(memberId)) {
            throw new BusinessException(ErrorCode.FORBIDDEN, "작성자만 삭제할 수 있습니다.");
        }
        comment.delete();
    }

    private void requireActivePost(Long postId) {
        if (!postRepository.existsByIdAndStatus(postId, PostStatus.ACTIVE)) {
            throw new BusinessException(ErrorCode.NOT_FOUND, "글을 찾을 수 없습니다.");
        }
    }

    private static String encode(Long id) {
        return Base64.getUrlEncoder().withoutPadding().encodeToString(id.toString().getBytes(StandardCharsets.UTF_8));
    }

    private static long decode(String cursor) {
        if (cursor == null || cursor.isEmpty()) {
            return 0L;
        }
        try {
            return Long.parseLong(new String(Base64.getUrlDecoder().decode(cursor), StandardCharsets.UTF_8));
        } catch (IllegalArgumentException e) {
            throw new BusinessException(ErrorCode.VALIDATION, "cursor가 올바르지 않습니다.");
        }
    }
}
```

- 트랜잭션 경계: 좋아요 관계와 저장한 카운터(선택 설계)를 어디까지 함께 바꾸는지, 중복 경합을 어느 경계에서 처리하는지와 그 이유를 적는다. 실패 시 rollback 범위와 재요청 뒤 좋아요 수를 테스트 결과로 설명한다.

```java
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.stereotype.Service;
import org.springframework.transaction.support.TransactionTemplate;

import com.example.board.common.BusinessException;
import com.example.board.common.ErrorCode;
import com.example.board.member.MemberRepository;

/** 이 클래스에는 @Transactional을 두지 않는다. 트랜잭션 경계를 안쪽(TransactionTemplate)에 두고 중복 예외를 바깥에서 잡기 위해서다. */
@Service
public class PostLikeService {

    private final PostRepository postRepository;
    private final PostLikeRepository postLikeRepository;
    private final MemberRepository memberRepository;
    private final TransactionTemplate tx;

    public PostLikeService(PostRepository postRepository, PostLikeRepository postLikeRepository,
            MemberRepository memberRepository, TransactionTemplate tx) {
        this.postRepository = postRepository;
        this.postLikeRepository = postLikeRepository;
        this.memberRepository = memberRepository;
        this.tx = tx;
    }

    /** 이미 눌렀으면 아무 일도 하지 않는다(멱등). */
    public void like(Long postId, Long memberId) {
        try {
            tx.executeWithoutResult(s -> {
                // 글 행을 먼저 잠그고(+1) 그 뒤에 좋아요 행을 넣는다. 중복이면 INSERT 예외로 +1도 함께 롤백된다.
                if (postRepository.increaseLikeCount(postId) == 0) {
                    throw new BusinessException(ErrorCode.NOT_FOUND, "글을 찾을 수 없습니다.");
                }
                postLikeRepository.saveAndFlush(PostLike.create(postRepository.getReferenceById(postId),
                        memberRepository.getReferenceById(memberId)));
            });
        } catch (DataIntegrityViolationException duplicate) {
            // UNIQUE(post_id, member_id) 위반 = 이미 누른 상태. 트랜잭션은 이미 롤백됐으므로 여기서 삼켜도 안전하다.
        }
    }

    /** 누른 적이 없으면 아무 일도 하지 않는다(멱등). */
    public void unlike(Long postId, Long memberId) {
        tx.executeWithoutResult(s -> {
            postRepository.lockActiveId(postId)
                    .orElseThrow(() -> new BusinessException(ErrorCode.NOT_FOUND, "글을 찾을 수 없습니다."));
            // 지운 행이 있을 때만 줄인다. 같은 쌍의 동시 취소 중 한 건만 지우므로 카운트가 두 번 줄지 않는다.
            if (postLikeRepository.deleteByPostAndMember(postId, memberId) > 0) {
                postRepository.decreaseLikeCount(postId);
            }
        });
    }
}
```

```java
            for (Future<Integer> f : futures) {

            return result;
```

## 말하기 카드

하루가 끝나면 질문에 "문제 상황 → 원인 → 선택 → 결과" 순서로 소리 내어 답한 뒤, 접힌 "답에 들어가야 할 것"과 비교한다. 세 줄이 모두 나오면 통과다.

### TC-D05-1

**질문** 글 수정 서비스에서 `save()`를 부르지 않았는데 UPDATE가 나갑니다. 왜 그런가요?

<details class="card-answer" data-card="TC-D05-1">
<summary>답에 들어가야 할 것</summary>

- 트랜잭션 안에서 조회한 엔티티는 영속성 컨텍스트가 관리하며, 조회 시점의 상태를 따로 가지고 있다
- flush에서 그 상태와 비교해 UPDATE SQL을 발행한다. 명시적 flush, commit 전 또는 AUTO 모드에서 결과에 영향을 받는 JPQL 실행 전에 일어날 수 있고, flush 후에도 rollback할 수 있다
- 변경은 `@Transactional` 안에서 하고 SQL 로그로 flush를 확인한다. commit은 변경을 확정한다. 별도 연결의 새 조회로 확정 결과를 확인하되, 기존 REPEATABLE READ 스냅샷은 이전 값을 볼 수 있다

</details>

### TC-D05-2

**질문** 댓글 목록 API에서 댓글 20개의 작성자 닉네임을 보여 주는데 SQL이 21번 나갑니다. 원인과 해결은?

<details class="card-answer" data-card="TC-D05-2">
<summary>답에 들어가야 할 것</summary>

- 댓글을 한 번 조회한 뒤, 지연 로딩인 `member`를 댓글마다 접근하면서 작성자마다 회원 조회가 한 번씩 더 나간다(N+1)
- `join fetch`(또는 `@EntityGraph`)로 작성자를 함께 가져오거나, 필요한 컬럼만 DTO로 조회한다
- SQL 로그나 Hibernate 통계로 쿼리 수를 세고, 그 수를 테스트로 고정한다

</details>

### TC-D05-3

**질문** 남의 글을 수정하려는 요청과 삭제된 글을 수정하려는 요청에 각각 무엇을 돌려주고, 어떤 순서로 검사하나요?

<details class="card-answer" data-card="TC-D05-3">
<summary>답에 들어가야 할 것</summary>

- 대상이 없거나 삭제·숨김 상태면 404 `/errors/not-found`다
- 대상은 있지만 요청자가 작성자가 아니면 403 `/errors/forbidden`이다
- 존재 여부를 먼저 보고 그다음 작성자를 검사하며, 작성자는 요청 본문이 아니라 토큰의 회원 ID와 글의 `member_id`로 비교한다

**근거** spec-v2 §5-2

</details>

### TC-D05-4

**질문** 좋아요 `PUT`을 두 번 보내도 204이고 수는 한 번만 오릅니다. 동시에 두 번 와도 그런가요? 어떻게 보장했나요?

<details class="card-answer" data-card="TC-D05-4">
<summary>답에 들어가야 할 것</summary>

- 한 회원·한 글의 좋아요 중복을 DB에서 거부하도록 설계하고 실제 중복 INSERT 결과로 확인한다
- 동시 요청 중 하나가 중복 키 예외를 받으면 이미 눌린 상태로 보고 204를 돌려준다
- 좋아요 수를 저장한다면 읽고 더해 덮어쓰지 않고 DB의 현재 값에서 원자적으로 갱신한다. +1 UPDATE와 INSERT를 한 트랜잭션에 두고(글 행을 먼저 잠가 교착을 피한다) 중복이면 트랜잭션째 롤백해 +1도 취소한다

**근거** spec-v2 §5-2

</details>

### TC-D05-5

**질문** 글 삭제를 행 삭제 대신 공개 상태를 `DELETED`로 바꾸는 소프트 삭제로 했습니다. 이유와 대가는? 공개 상태 필터와 최신순·커서 조회를 위해 설계한 인덱스의 이유도 설명해 보세요.

<details class="card-answer" data-card="TC-D05-5">
<summary>답에 들어가야 할 것</summary>

- 신고 기록와 감사 로그가 글을 가리키므로, 행을 남겨야 나중에 추적할 수 있다
- 대가는 모든 조회에 상태 조건을 빠뜨리지 않아야 한다는 것이다. 하나라도 빠지면 삭제된 글이 노출된다
- 공개 상태 필터와 최신순·커서 조회 패턴을 바탕으로 내가 만든 인덱스의 이유를 설명한다

**근거** spec-v2 §6

</details>

## AI 채점 프롬프트

오늘 순서를 다 만들었으면 서버를 띄운 채로 아래 프롬프트를 복사해 Codex 또는 Claude Code에 붙여 넣는다. 에이전트가 완료 조건·함정·말하기 카드로 채점표를 준다. 코드는 고치지 않는다.

**꼭 할 관찰**의 관찰 증거도 함께 채점받는다. 미제출은 해당 완료 조건 실패다. 선택 관찰은 제외한다.

```text
[javaExperience 일자 채점] D05. 조회·수정·삭제 (JPA)
레포 경로: 내 프로젝트 루트(이 프롬프트를 붙여 넣은 에이전트를 연 폴더)
서버 주소: http://localhost:8080

너는 Java·Spring 온보딩 과정 v2로 백엔드를 배우는 사람의 리뷰어다. 학습자는 빈 프로젝트에서 명세서 v2의 서버를 하루씩 만들고 있고, 오늘은 D05다.
설정 형식 채점: application.yml과 application.properties를 모두 인정한다. application-local·prod·test 등 프로파일별 파일도 두 형식을 인정한다. 파일 확장자나 YAML의 --- 구조만으로 실패 처리하지 말고 같은 키·값, 활성 프로파일, 자리표시자, 실행 결과를 확인한다. 2. 아래 "채점 기준"이 통과/실패의 유일한 기준이다. 기준에 없는 것으로 실패 처리하지 말고, 다른 날의 기준은 보지 마라.
3. [C] 항목: HTTP 요청은 서버 주소로 직접 보내 상태 코드·응답 헤더·본문을 기대값과 비교한다. 테스트 이름이 적힌 항목은 레포 루트에서 `./gradlew test --tests '<테스트 클래스 이름>'`으로 실행해 통과 여부를 본다(테스트 코드도 고치지 마라). 로그 항목은 기동 로그에서 찾거나 학습자에게 해당 줄을 붙여 달라고 한다. DB 확인이 필요하면 `docker compose exec -T mysql mysql -uboard -pboard board -e "<SELECT 문>"`으로 조회만 한다.

  - [C2-3] PATCH 본문 {} → 400
  - [C2-4] DELETE /api/posts/{postId} → 204, 이후 GET → 404
  - [C2-5] 다른 회원 토큰으로 PUT → 403 /errors/forbidden, 삭제된 글에 PUT → 404
  - [C2-6] [꼭 할 관찰] flush 후 rollback의 Java 값·SQL·같은 연결·별도 연결 값을 기록해 제출한다.
  - [C2-7] [꼭 할 관찰] 공유 태그 수명: 연결 해제·soft delete·rollback 전후의 공유 태그·연결 사실 수를 기록해 제출한다.
  - [R2] 함정을 피했는지 코드로 확인: save()를 부르지 않아도 변경 감지로 flush 때 UPDATE SQL이 발행된다. commit은 변경을 확정하며 flush 뒤에도 rollback할 수 있다. SQL 로그와 별도 연결의 commit 후 새 조회를 구분해 확인한다. 꼭 할 관찰: flush 후 rollback의 값·SQL·연결별 관찰과 공유 태그의 연결 해제·실패 원복을 모두 기록한다. 두 관찰의 증거를 완료 조건으로 채점받는다.
③ 댓글 엔티티와 글별 목록 조회 설계 — 데이터 요구사항 §6-4을 만족하도록 테이블을 직접 설계·생성

말하기 카드
- [TC-D05-1] 글 수정 서비스에서 save()를 부르지 않았는데 UPDATE가 나갑니다. 왜 그런가요?
    · 트랜잭션 안에서 조회한 엔티티는 영속성 컨텍스트가 관리하며, 조회 시점의 상태를 따로 가지고 있다
    · flush에서 그 상태와 비교해 UPDATE SQL을 발행한다. 명시적 flush, commit 전 또는 AUTO 모드에서 결과에 영향을 받는 JPQL 실행 전에 일어날 수 있고, flush 후에도 rollback할 수 있다
    · 변경은 @Transactional 안에서 하고 SQL 로그로 flush를 확인한다. commit은 변경을 확정한다. 별도 연결의 새 조회로 확정 결과를 확인하되, 기존 REPEATABLE READ 스냅샷은 이전 값을 볼 수 있다
- [TC-D05-2] 댓글 목록 API에서 댓글 20개의 작성자 닉네임을 보여 주는데 SQL이 21번 나갑니다. 원인과 해결은?
    · 댓글을 한 번 조회한 뒤, 지연 로딩인 member를 댓글마다 접근하면서 작성자마다 회원 조회가 한 번씩 더 나간다(N+1)
    · join fetch(또는 @EntityGraph)로 작성자를 함께 가져오거나, 필요한 컬럼만 DTO로 조회한다
    · SQL 로그나 Hibernate 통계로 쿼리 수를 세고, 그 수를 테스트로 고정한다
- [TC-D05-3] 남의 글을 수정하려는 요청과 삭제된 글을 수정하려는 요청에 각각 무엇을 돌려주고, 어떤 순서로 검사하나요?
    · 대상이 없거나 삭제·숨김 상태면 404 /errors/not-found다
    · 대상은 있지만 요청자가 작성자가 아니면 403 /errors/forbidden이다
    · 존재 여부를 먼저 보고 그다음 작성자를 검사하며, 작성자는 요청 본문이 아니라 토큰의 회원 ID와 글의 member_id로 비교한다
- [TC-D05-4] 좋아요 PUT을 두 번 보내도 204이고 수는 한 번만 오릅니다. 동시에 두 번 와도 그런가요? 어떻게 보장했나요?
    · 한 회원·한 글의 좋아요 중복을 DB에서 거부하도록 설계하고 실제 중복 INSERT 결과로 확인한다
    · 동시 요청 중 하나가 중복 키 예외를 받으면 이미 눌린 상태로 보고 204를 돌려준다
    · 좋아요 수를 저장한다면 읽고 더해 덮어쓰지 않고 DB의 현재 값에서 원자적으로 갱신한다. +1 UPDATE와 INSERT를 한 트랜잭션에 두고(글 행을 먼저 잠가 교착을 피한다) 중복이면 트랜잭션째 롤백해 +1도 취소한다
- [TC-D05-5] 글 삭제를 행 삭제 대신 공개 상태를 DELETED로 바꾸는 소프트 삭제로 했습니다. 이유와 대가는? 공개 상태 필터와 최신순·커서 조회를 위해 설계한 인덱스의 이유도 설명해 보세요.
    · 신고 기록와 감사 로그가 글을 가리키므로, 행을 남겨야 나중에 추적할 수 있다
    · 대가는 모든 조회에 상태 조건을 빠뜨리지 않아야 한다는 것이다. 하나라도 빠지면 삭제된 글이 노출된다
    · 공개 상태 필터와 최신순·커서 조회 패턴을 바탕으로 내가 만든 인덱스의 이유를 설명한다

리뷰 초점
- 삭제된 글이 상세·수정·댓글 작성에서 모두 404로 막히는지
- 좋아요 수를 엔티티 필드에 읽어 더해 저장하지 않는지(동시 요청에서 갱신이 사라진다)
```
