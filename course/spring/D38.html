#오늘의 SQL

내 프로젝트의 disposable 실습 DB를 쓴다. D23에서 정한 예약·대상·지급 상태의 물리 이름과 필터로 아래 예시를 반드시 매핑한다. 예시의 member_coupon은 1단계 비교 모델이며 새 예약 테이블의 구현 예시가 아니다. practice·원본 서버 DB는 수정하지 않는다.

  1. 실험 구간 전후 statement 누적값 차이를 기록한다.

    확인할 성질 내 물리 테이블·키·필터로 옮긴 SQL, 관찰 시각, 실제 출력과 기대 성질의 일치 여부를 남긴다. 예시는 실행 결과가 아니다.

  2. 부하 후 중복 지급 불변식을 대사한다.

#말하기 카드

하루가 끝나면 질문에 "문제 상황 → 원인 → 선택 → 결과" 순서로 소리 내어 답한 뒤, 접힌 "답에 들어가야 할 것"과 비교한다. 세 줄이 모두 나오면 통과다.

#TC-D38-1

질문 단일 앱의 락이 두 앱에서 충분했나요?

답에 들어가야 할 것
  • 단일 앱 락은 다른 JVM의 요청/캐시 재적재를 막지 못한다.
  • 한 앱/두 앱에서 같은 요청으로 재적재·오래된 값·중복 지급을 비교한다.
  • 실제 수치·공유 경계 대안의 비용과 단일 JVM 테스트 한계를 제시한다.

#TC-D38-2

질문 어떤 지표가 병목 가설을 지지하나요?

답에 들어가야 할 것
  • 병목 가설과 이를 지지/반박할 지표를 먼저 정한다.
  • 처리량·오류율·p50/p95/p99·DB pending·CPU/메모리를 같은 구간에서 기록한다.
  • 반복 조건·실제 상관관계와 원인을 확정하지 못한 항목을 말한다.

#TC-D38-3

질문 개선 수치를 어떤 범위까지만 주장하나요?

답에 들어가야 할 것
  • 변경 하나·동일 데이터/유입/측정 구간·반복 횟수를 명시한다.
  • 전후 실측과 변동·다음 병목·정합성 회귀를 함께 제시한다.
  • 운영 적정값으로 일반화하지 못하는 범위와 추가 검증 비용을 말한다.
