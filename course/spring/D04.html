import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.EnumType;
import jakarta.persistence.Enumerated;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;

import com.example.board.common.BaseEntity;
import com.example.board.member.Member;

import lombok.AccessLevel;
import lombok.Getter;
import lombok.NoArgsConstructor;

@Getter
@Entity
@Table(name = "post")
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Post extends BaseEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "member_id", nullable = false)
    private Member member;

    @Column(nullable = false, length = 100)
    private String title;

    @Column(nullable = false, length = 5000)
    private String content;

    // ORDINAL이면 enum 중간에 값을 끼울 때 기존 행의 의미가 바뀐다
    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 10)
    private PostStatus status;

    @Column(name = "like_count", nullable = false)
    private int likeCount;

    private Post(Member member, String title, String content) {
        this.member = member;
        this.title = title;
        this.content = content;
        this.status = PostStatus.ACTIVE;
    }

    public static Post create(Member member, String title, String content) {
        return new Post(member, title, content);
    }
}

            post.addTag(tagRepository.findByName(name).orElseGet(() -> tagRepository.save(Tag.create(name))));
        }
        return postRepository.save(post).getId();
    }

하루가 끝나면 질문에 "문제 상황 → 원인 → 선택 → 결과" 순서로 소리 내어 답한 뒤, 접힌 "답에 들어가야 할 것"과 비교한다. 세 줄이 모두 나오면 통과다.

#TC-D04-1

질문 PostStatus enum 맨 앞에 DRAFT를 추가했더니 기존 글의 상태가 전부 바뀌어 보입니다. 원인과 예방은?

답에 들어가야 할 것
  • @Enumerated의 기본값은 ORDINAL이라 enum의 순서 번호가 저장된다
  • 중간에 상수를 끼우면 기존 숫자가 다른 상수를 가리켜 데이터가 조용히 바뀐다
  • @Enumerated(EnumType.STRING)으로 이름을 저장한다. 대신 상수 이름을 바꿀 때는 데이터 이전을 함께 한다

근거 spec-v2 §6

#TC-D04-2

질문 Post 엔티티에 @Setter와 @AllArgsConstructor를 두지 않고 protected 기본 생성자와 정적 팩토리를 쓴 이유는?

답에 들어가야 할 것
  • JPA는 기본 생성자(public 또는 protected)가 필요하다. protected로 두면 다른 코드가 빈 엔티티를 new로 만들지 못한다
  • 정적 팩토리(Post.create(...))에서 필수값과 규칙을 검사해 잘못된 상태의 엔티티가 생기지 않게 한다
  • setter 대신 의미 있는 메서드(edit, delete)로만 상태를 바꾸면 변경 규칙이 한곳에 모인다

#TC-D04-3

질문 구현이 하나뿐인데 PostService 인터페이스와 PostServiceImpl을 두었습니다. 왜 두었고, 어디부터 과잉인가요?

답에 들어가야 할 것
  • Spring은 CGLIB 클래스 프록시로 인터페이스 없이도 @Transactional을 적용하므로, AOP 때문에 인터페이스가 필요하지는 않다
  • 인터페이스가 값을 하는 곳은 구현이 둘 이상이거나 바뀔 것이 분명한 경계다. 외부 연동이나 테스트용 Fake가 그 예다
  • 쌍을 팀 관례로 둔다면 그 이유(구현 은닉, 인터페이스 기준 테스트)를 말할 수 있어야 하고, 근거 없이 모든 클래스에 쌍을 만들면 과잉이다

#TC-D04-4

질문 제목이 공백 문자만 있는 글이 저장됐습니다. 검증을 어디에 어떻게 두었나요?

답에 들어가야 할 것
  • 요청 DTO에 Bean Validation(@NotBlank, @Size(max = 100))을 붙이고 컨트롤러 파라미터에 @Valid를 둔다
  • @NotEmpty나 @NotNull은 공백만 있는 문자열을 통과시키므로, 명세의 "공백만 불가"는 @NotBlank로 표현한다
  • 검증 실패(MethodArgumentNotValidException)는 400 ProblemDetail로 바꾸고 errors[]에 {field, reason}을 담는다

근거 spec-v2 §5-2

#AI 채점 프롬프트

오늘 순서를 다 만들었으면 서버를 띄운 채로 아래 프롬프트를 복사해 Codex 또는 Claude Code에 붙여 넣는다. 에이전트가 완료 조건·함정·말하기 카드로 채점표를 준다. 코드는 고치지 않는다.

채점 프롬프트 내용 확인
[javaExperience 일자 채점] D04. 게시글 쓰기 (JPA)
레포 경로: 내 프로젝트 루트(이 프롬프트를 붙여 넣은 에이전트를 연 폴더)
서버 주소: http://localhost:8080

너는 Java·Spring 온보딩 과정 v2로 백엔드를 배우는 사람의 리뷰어다. 학습자는 빈 프로젝트에서 명세서 v2의 서버를 하루씩 만들고 있고, 오늘은 D04다.
설정 형식 채점: application.yml과 application.properties를 모두 인정한다. application-local·prod·test 등 프로파일별 파일도 두 형식을 인정한다. 파일 확장자나 YAML의 --- 구조만으로 실패 처리하지 말고 같은 키·값, 활성 프로파일, 자리표시자, 실행 결과를 확인한다. ApplicationYmlTest·ProfileConfigTest·LocalProfileSeedTest처럼 YAML 원문을 읽는 예시는 properties의 동등한 키·값·프로파일 로딩 검사로 대체할 수 있다.
지킬 것: 코드는 절대 수정하지 마라. DB는 조회만 한다(SELECT·SHOW·EXPLAIN). 서버를 대신 띄우거나 끄지 마라. 구현 예시 코드를 통째로 주지 말고 방향과 힌트로 알려 줘라.

1. 서버 주소의 `GET /actuator/health`로 응답 가능 여부를 확인해라. 꺼져 있으면 `./gradlew bootRun --args='--spring.profiles.active=local'`(또는 `SPRING_PROFILES_ACTIVE=local ./gradlew bootRun`)으로 띄우라고만 알려 주고 멈춰라. D01 ③부터 DB 설정이 `local` 프로파일에 있어 프로파일 없이는 기동에 실패한다.
설계 채점: 테이블·컬럼·키·제약·인덱스 이름은 학습자의 설계를 따른다. board-server의 이름·분할과 다르다는 이유로 실패 처리하지 마라. 설계 메모와 DB 불변식 확인은 제출 SQL·거부 결과·테스트를 읽고 판단한다. 채점자가 INSERT·UPDATE·DELETE로 재현하지 말고 증거가 없으면 확인 불가로 적어라. API 필드·상태·오류 계약은 유지한다.
2. 아래 "채점 기준"이 통과/실패의 유일한 기준이다. 기준에 없는 것으로 실패 처리하지 말고, 다른 날의 기준은 보지 마라.
3. [C] 항목: HTTP 요청은 서버 주소로 직접 보내 상태 코드·응답 헤더·본문을 기대값과 비교한다. 테스트 이름이 적힌 항목은 레포 루트에서 `./gradlew test --tests '<테스트 클래스 이름>'`으로 실행해 통과 여부를 본다(테스트 코드도 고치지 마라). 로그 항목은 기동 로그에서 찾거나 학습자에게 해당 줄을 붙여 달라고 한다. DB 확인이 필요하면 `docker compose exec -T mysql mysql -uboard -pboard board -e "<SELECT 문>"`으로 조회만 한다.
4. [R] 항목: 관련 코드를 찾아 읽고 그 함정을 피했는지 판단해라. 지적할 때는 `파일:줄`을 붙여라.
5. 말하기 카드: 학습자에게 카드 질문마다 답을 말하거나 적어 달라고 해라. "답에 들어가야 할 것"(· 표시) 세 줄이 모두 나오면 통과다. 빠진 줄은 정답 문장을 먼저 말하지 말고 되묻는 질문으로 끌어내라.
6. 리뷰 초점은 채점표에 넣지 말고 ②·③에 적어라.

채점 기준
① 글 엔티티와 상태 매핑, 목록 조회 계획 — 데이터 요구사항 §6-3을 만족하도록 테이블을 직접 설계·생성
  - [C1-1] PostRepositoryTest 통과: 저장한 글의 공개 상태를 다시 읽으면 ACTIVE다(물리 열 이름·표현은 내 설계).
  - [C1-2] 설계 메모: 만든 테이블·키·제약·인덱스와 각각의 이유, 고려했다 버린 대안 1개를 기록한다.
  - [C1-3] DB 불변식 확인: 존재하지 않는 작성자의 글 저장이 거부되고 공개 상태·시각이 보존된다. 실행 SQL·결과를 기록하고 DB와 트랜잭션·권한·앱이 맡는 책임을 구분한다.

② 공유 태그와 글별 태그 관계 매핑 — 데이터 요구사항 §6-3을 만족하도록 테이블을 직접 설계·생성
  - [C2-1] TagRepositoryTest 통과: 같은 이름의 태그는 새로 만들지 않고 재사용한다
  - [C2-2] 설계 메모: 만든 테이블·키·제약·인덱스와 각각의 이유, 고려했다 버린 대안 1개를 기록한다.
  - [C2-3] DB 불변식 확인: 같은 이름의 태그·같은 글의 같은 태그 중복 및 존재하지 않는 대상의 연결을 거부한다. 실행 SQL·결과를 기록하고 DB와 트랜잭션·권한·앱이 맡는 책임을 구분한다.
  - [R2] 함정을 피했는지 코드로 확인: 엔티티에 @Setter·@AllArgsConstructor를 열어 두면 아무 곳에서나 상태가 바뀌므로 protected 기본 생성자와 정적 팩토리만 둔다. 선택 관찰: 두 글의 태그 1행·연결 2행을 확인하고 수명 실험은 D05 ②로 이어 간다. 오늘은 선택 실험 중 하나만 골라도 되며 필수 채점에는 추가하지 않는다.
③ 글 작성 요청·응답 DTO와 검증 규칙
  - [C3-1] PostCreateRequestTest 통과: 공백만 있는 제목, 태그 6개, 21자 태그를 거절한다
  - [R3] 함정을 피했는지 코드로 확인: @NotEmpty는 공백만 있는 제목을 통과시키므로 @NotBlank를 쓴다.
④ PostService 인터페이스와 PostServiceImpl (작성자는 로그인 회원)
  - [C4-1] PostServiceImplTest 통과: 중복 태그는 한 번만 저장한다
  - [R4] 함정을 피했는지 코드로 확인: 인터페이스를 두면 그 이유(팀 관례·교체·테스트 대역)를 말할 수 있어야 한다. 근거 없이 모든 클래스에 인터페이스·구현 쌍을 두면 과잉이다.
⑤ 글 작성 API와 검증 오류 errors[] 응답 (검증 예외 처리는 D02에 만든 GlobalExceptionHandler가 이미 맡는다)

  - [C5-2] 토큰 없음 → 401
  - [C5-3] 제목이 공백만 → 400 /errors/validation, errors[]에 {field: "title"}
  - [R5] 함정을 피했는지 코드로 확인: 컨트롤러 매개변수에 @Valid를 빠뜨리면 DTO에 검증 애노테이션이 있어도 아무 검사 없이 저장된다.

    · @NotEmpty나 @NotNull은 공백만 있는 문자열을 통과시키므로, 명세의 "공백만 불가"는 @NotBlank로 표현한다
