#이 날 데이터 넣기

  • D23 스키마를 복제한 별도 실험 DB에서 균등 200행 이상과 한 예약에 90%가 몰린 편향 200행 이상을 별도로 생성한다.
  • 생성 SQL·seed·정렬·실제 행 수를 저장하고 각 실험 전 기준 상태로 되돌린다. practice·공유 DB에 적재하지 않는다.
  • 실행 경로: 내 프로젝트의 src/test/java/D24FixtureTest.java에서 D23 스키마용 fixture loader를 작성한다. seed=24·예약 10개·회원 200개를 먼저 만들고 균등은 예약별 20행, 편향은 첫 예약 180행·나머지 9개에 20행을 분산한다. 생성 순번과 실제 FK 매핑을 저장하고 부모·대상 행 수를 단언한다. 실행은 ./gradlew test --tests D24FixtureTest이며 loader와 실행 로그를 함께 제출한다.
  • 조회 두 구현을 같은 fixture에서 실행해 결과 집합·정렬을 먼저 대조한다. baseline.sql·with-index.sql에 동일한 SELECT와 동일 200행 INSERT를 저장하고 별도실험DB의 D24_PORT·D24_USER·D24_DB를 지정하고 mysql --host=127.0.0.1 --port="$D24_PORT" --user="$D24_USER" --password --database="$D24_DB" < baseline.sql로 실행한다. 각 실행 전 같은 dump로 복원하고 warm-up 1회·측정 3회·실행 순서를 기록한다. EXPLAIN ANALYZE 출력과 information_schema.TABLES의 DATA_LENGTH/INDEX_LENGTH는 추정 공간이며 실측 지연과 구분한다.

#오늘의 SQL

내 프로젝트의 disposable 실습 DB를 쓴다. D23에서 정한 예약·대상·지급 상태의 물리 이름과 필터로 아래 예시를 반드시 매핑한다. 예시의 member_coupon은 1단계 비교 모델이며 새 예약 테이블의 구현 예시가 아니다. practice·원본 서버 DB는 수정하지 않는다.

  1. 동일 issued_at이 20건을 넘는 데이터에서 첫 페이지와 다음 페이지의 경계를 검사한다.

    확인할 성질 첫 20건과 다음 페이지의 (issued_at,id) 교집합이 0이고 두 페이지 합집합이 상위 40건과 같다. 25건의 동일 시각 fixture에서는 20+5를 확인한다. 예약 필터가 있으면 두 쿼리에 모두 적용한다.

  2. 선택 조회의 실제 계획을 인덱스 전후 비교한다.

    확인할 성질 내 물리 테이블·키·필터로 옮긴 SQL, 관찰 시각, 실제 출력과 기대 성질의 일치 여부를 남긴다. 예시는 실행 결과가 아니다.

  3. 예약별 대상·성공·실패를 선집계해 행 곱셈 없이 조회한다.

    확인할 성질 예약 1의 대상 5·성공 2·실패 1, 예약 2의 대상 1·성공 0·실패 0을 확인한다. 대상 없는 예약도 0으로 나타내고 실제 조회 API의 필터·정렬과 대조한다.

#TC-D24-2

질문 JOIN 때문에 지급 건수가 부풀지 않나요?

답에 들어가야 할 것
  • 일대다 JOIN의 행 증폭과 지급 건수의 업무 집계 단위를 구분한다.

질문 어떤 분포에서 인덱스 선택을 바꾸겠나요?
