#오늘의 SQL

내 프로젝트의 disposable 실습 DB를 쓴다. D23에서 정한 예약·대상·지급 상태의 물리 이름과 필터로 아래 예시를 반드시 매핑한다. 예시의 member_coupon은 1단계 비교 모델이며 새 예약 테이블의 정답이 아니다. practice·원본 서버 DB는 수정하지 않는다.

  1. 새 요구의 영향 대상을 SQL로 직접 산정한다.

    확인할 성질 내 물리 테이블·키·필터로 옮긴 SQL, 관찰 시각, 실제 출력과 기대 성질의 일치 여부를 남긴다. 예시는 실행 결과가 아니다.

  2. 데이터 이행의 범위·상태 분포를 확인한다.

    확인할 성질 내 물리 테이블·키·필터로 옮긴 SQL, 관찰 시각, 실제 출력과 기대 성질의 일치 여부를 남긴다. 예시는 실행 결과가 아니다.

구현 예시 SQL · 직접 작성한 뒤 비교하기

아래는 비교용 SQL이다. 예약·대상·작업 모델은 내가 정한 물리 이름과 필터로 옮긴다. board-server의 설계 기준이다. 2단계에서는 같은 계열의 기존 스키마를 관찰한다. 내 물리 이름·키·정렬이 다르면 매핑해 비교한다. 아래 SQL은 실제 실행 결과가 아니며 예시 서버가 모든 불변식을 보장한다는 뜻도 아니다. 오류가 예상되는 문장은 하나씩 실행하고 실패 뒤 ROLLBACK을 별도로 보낸다.

문항 1 구현 예시

SELECT coupon_id,COUNT(*) FROM member_coupon GROUP BY coupon_id;

문항 2 구현 예시

SELECT MIN(id),MAX(id),COUNT(*) FROM member_coupon;

#AI 채점 프롬프트

채점 프롬프트 내용 확인
[javaExperience 확장 과정 채점] D35. 새 업무 선택과 일정 산정 회의
작업 위치: 학습자가 제출한 내 프로젝트 또는 messy-server 사본. 먼저 실제 경로·DB·기준 상태·처리한 A/B와 도움받은 범위를 확인한다. 원본 서버 코드를 수정하지 마라.
설정 형식 채점: application.yml과 application.properties를 모두 인정한다. application-local·prod·test 등 프로파일별 파일도 두 형식을 인정한다. 파일 확장자나 YAML의 --- 구조만으로 실패 처리하지 말고 같은 키·값, 활성 프로파일, 자리표시자, 실행 결과를 확인한다. ApplicationYmlTest·ProfileConfigTest·LocalProfileSeedTest처럼 YAML 원문을 읽는 예시는 properties의 동등한 키·값·프로파일 로딩 검사로 대체할 수 있다.
지킬 것: 파일은 수정하지 마라. 예상값과 실측, 사실과 가정, 실행과 미실행을 구분한다. 체크만으로 통과시키지 마라. 새 요구는 일자 원본의 완료 조건과 학습자 합의 명세를 대조한다. 물리 이름·설계가 예시와 달라도 불변식·계약을 충족하면 인정한다.

각 C 항목은 실제 테스트·SQL·로그·문서 경로와 줄을 근거로 통과/실패/확인 불가로 판정한다. 티켓 A/B는 원인 서술·수정 전 RED·수정 후 GREEN·반례·diff를 확인하고 미선택 티켓을 실패로 채점하지 마라. 미수행 대신 정한 새 조건은 조건과 새 실패 증거를 요구한다. 이미 새 조건도 통과하면 통과 사실을 인정하고 정상 코드를 약화하지 마라. 해당 일자의 요구 합의 단계(D16~D18은 D16, D36은 D35)로 돌아가 담당자/훈련 진행자와 미충족 새 계약을 합의하도록 하며, 미합의·미실행은 확인 불가로 남긴다. 기존 2단계 제외 규칙을 3단계 필수 A/B에 자동 적용하지 마라.
회의가 있으면 M1~M5 각각 0(없음)/1(부분)/2(근거·합의까지)로 채점한다. 각 항목 1점 이상 및 총 8/10 이상이어야 회의 통과다. 한 항목 0점이면 총점과 무관하게 재훈련한다. 먼저 발언을 받고 반론을 하나 제시한 뒤 수정 발언을 기록한다. 외운 답 선공개는 금지한다.
