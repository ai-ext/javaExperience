i 가이드읽고 이해하기막히면▸
  • 이 순서는 DB → 쿼리 → 서비스 → 컨트롤러 순으로: 기존 테이블과 제약을 확인한다 → 필요한 저장·조회 조건을 저장소에서 먼저 확인한다 → 업무 검증과 트랜잭션 경계를 연결한다 → DTO와 응답 계약을 연결해 호출로 확인한다. 앞서 만든 층은 재사용하고 이 순서에서 바꾸는 부분만 진행한다.
  • spring-boot-starter-data-redis와 spring.data.redis.timeout, StringRedisTemplate의 opsForValue().set(key, value, Duration)을 찾아본다.
  • docker compose exec redis redis-cli 안에서 KEYS *와 TTL <키>로 캐시가 들어갔는지 본다.
▷ 실습실행하고 관찰선택 관찰 실험 · 필요한 실험을 골라 하세요▸
  • 선택 관찰(15분, C27): J09의 선택 DecimalAmount 실험 뒤 학습자 서버 테스트의 같은 JDBC 연결에만 임시 테이블을 만든다(CREATE TEMPORARY TABLE precision_probe(amount DECIMAL(5,2), happened_at DATETIME(6))). 기존 상점의 정수 금액 계약은 바꾸지 않는다. Clock.fixed의 2026-10-22T14:59:59.123456789Z를 Asia/Seoul의 LocalDateTime으로 바꾸고 나노초를 MICROS까지 명시적으로 절삭한다. 정규화한 금액을 PreparedStatement.setBigDecimal, 시각을 setObject로 넣고 getBigDecimal/getObject(LocalDateTime.class)로 다시 읽는다. 1.0→1.00, 1.005→1.01, 999.994→999.99를 금액 compareTo=0 및 scale=2로, 시각은 마이크로초 정밀도로 비교하고 같은 KST 약속으로 Instant를 복원한다. 999.995는 반올림 뒤 범위 초과로 Java에서 거절되는지 본다. DB에 원본 소수 셋째 자리·1000.00을 직접 넣는 대조군도 별도로 실행해 @@sql_mode, SHOW WARNINGS/예외와 재조회값을 기록한다. DB의 반올림·절삭·거절을 Java 정책과 같다고 전제하지 않는다. DATETIME에는 zone이 저장되지 않으므로 UTC/서울 표시와 저장값을 구분한다. 끝에 같은 연결을 닫고 임시 테이블을 정리한다. 실제 DB 왕복 통과는 순수 Java 테스트 통과와 별개다.

#오늘의 SQL

원래 seed DB에서 D08까지 넣은 상태를 쓴다. bulk 실험 DB와 구분한다. 변경을 멈추고 SQL·실제 결과와 캐시 관찰 시각을 저장한다.

더미 SQL·붙여 넣는 순서를 먼저 확인한다.

  1. 인기글 캐시 응답의 식별·좋아요 수를 같은 시점의 DB 상위 목록과 대조한다.

    확인할 성질 seed D08까지 기준 공개 글 상위 20건을 같은 정렬·페이지 조건의 캐시 응답과 대조한다. 변경을 멈추고 캐시 생성·DB 조회 시각과 TTL을 적는다. SQL이 Redis를 직접 읽는다고 가정하지 않는다.

  2. 활동 적립만 회원별 집계해 랭킹 원천을 만든다.

    확인할 성질 seed D08까지 기준 20명 모두 활동 점수 1,000점이다. 회원 20은 댓글 적립, 나머지는 글 적립이며 충전·지출은 포함되지 않는다.

구현 예시 SQL · 직접 작성한 뒤 비교하기

board-server의 설계 기준이다. 2단계에서는 같은 계열의 기존 스키마를 관찰한다. 내 물리 이름·키·정렬이 다르면 매핑해 비교한다. 아래 SQL은 실제 실행 결과가 아니며 예시 서버가 모든 불변식을 보장한다는 뜻도 아니다. 오류가 예상되는 문장은 하나씩 실행하고 실패 뒤 ROLLBACK을 별도로 보낸다.

02 · 소리 내어 설명하기

#말하기 카드

하루가 끝나면 질문에 "문제 상황 → 원인 → 선택 → 결과" 순서로 소리 내어 답한 뒤, 접힌 "답에 들어가야 할 것"과 비교한다. 세 줄이 모두 나오면 통과다.

#TC-D09-1

질문 인기글 캐시(TTL 60초)가 만료되는 순간마다 DB 쿼리가 몰립니다. 왜 그렇고 어떻게 막나요?

답에 들어가야 할 것
  • 키가 만료된 순간 들어온 요청이 모두 캐시 미스를 보고 동시에 DB를 조회한다(스탬피드)
  • 한 요청만 다시 계산하고 나머지는 그 결과를 기다리게 한다(single-flight). 방법은 인스턴스 안의 JVM 락(ReentrantLock, @Cacheable(sync = true))이나 분산 락(SET NX), 만료 전 선갱신이 있다
  • 무엇을 골랐고 왜인지 말한다. JVM 락이면 서버 대수만큼 DB 조회가 남는 한계가 있고(구현 예시는 이 정도면 충분하고 Redis 장애 때 락까지 잃지 않아 JVM 락을 골랐다), 분산 락이면 Redis 장애 때 락도 함께 잃는다

#TC-D09-2

질문 Redis가 느려지거나 죽으면 인기글 조회가 어떻게 동작하도록 만들었나요?

답에 들어가야 할 것
  • Redis 명령 타임아웃을 500ms로 둬서 Redis 지연이 요청 스레드를 오래 잡지 않게 한다
  • 캐시 조회 실패는 경고 로그를 남기고 DB 조회로 폴백한다
  • 캐시 호출을 직접 감쌌다면 예외를 잡아 폴백한다(구현 예시 RedisGuard). Spring Cache를 쓴다면 CacheErrorHandler를 등록해 조회 오류를 캐시 미스로 처리한다(기본 처리기는 예외를 그대로 던진다)

근거 spec-v2 §8

#TC-D09-3

질문 선착순 쿠폰 잔여 수량을 Redis DECR로 관리합니다. Redis 값과 DB의 issued_quantity가 다르면 무엇을 믿나요?

답에 들어가야 할 것
  • 남은 수량 확인과 감소를 원자적으로 묶어(Lua 스크립트 등) 0 아래로 내려가지 않게 한다. DECR 뒤 음수면 INCR로 되돌리는 방식은 초과 요청과 DB 실패 되돌리기가 겹치면 수량이 어긋날 수 있다
  • 발급의 최종 기준은 DB(member_coupon UNIQUE, issued_quantity <= total_quantity)이고, Redis는 DB 앞에서 요청을 거르는 장치다
  • Redis에서 차감한 뒤 DB 저장이 실패하면 Redis 수량을 되돌리거나 DB 기준으로 다시 맞추는 절차가 있어야 한다

근거 spec-v2 §6

#TC-D09-4

질문 관리자가 글을 숨기면 인기글 캐시를 지웁니다. 지우는 시점을 트랜잭션 커밋 뒤로 둔 이유는?

답에 들어가야 할 것
  • 커밋 전에 지우면 그 사이 들어온 조회가 아직 커밋되지 않은, 숨기기 전 값을 DB에서 읽어 캐시에 다시 넣는다
  • 그러면 TTL(60초)이 끝날 때까지 숨긴 글이 인기글에 보인다
  • 그래서 @TransactionalEventListener(phase = AFTER_COMMIT)이나 TransactionSynchronization의 afterCommit에서 지운다

근거 spec-v2 §8

#TC-D09-5

질문 로그인 시도 제한(10분에 5회)을 서버 메모리가 아니라 Redis에 둔 이유와 구현은?

답에 들어가야 할 것
  • 메모리 카운터는 인스턴스마다 따로 세므로 인스턴스가 여럿이면 제한이 인스턴스 수만큼 느슨해진다
  • 계정별 키를 INCR하고 첫 증가 때 600초 만료를 건다. 두 명령 사이에 실패하면 만료 없는 키가 남아 계정이 계속 막힐 수 있으므로 Lua 스크립트로 묶는다
  • 5회를 넘으면 429 /errors/too-many-attempts로 응답한다

근거 spec-v2 §5-1
