#오늘의 SQL

내 프로젝트의 disposable 실습 DB를 쓴다. D23에서 정한 예약·대상·지급 상태의 물리 이름과 필터로 아래 예시를 반드시 매핑한다. 예시의 member_coupon은 1단계 비교 모델이며 새 예약 테이블의 구현 예시가 아니다. practice·원본 서버 DB는 수정하지 않는다.

  1. 정확 전체 건수의 조회 계획을 측정한다.

    확인할 성질 내 물리 테이블·키·필터로 옮긴 SQL, 관찰 시각, 실제 출력과 기대 성질의 일치 여부를 남긴다. 예시는 실행 결과가 아니다.

  2. 목록 조회 비용과 전체 건수 비용을 분리한다.

    확인할 성질 내 물리 테이블·키·필터로 옮긴 SQL, 관찰 시각, 실제 출력과 기대 성질의 일치 여부를 남긴다. 예시는 실행 결과가 아니다.

  3. HAVING 뒤의 결과 그룹 수를 목록과 같은 조건으로 센다.

    확인할 성질 COUNT(*) 원본 행 수와 결과 그룹 수를 구분하고 API total의 의미를 합의한다. 목록·count SQL의 실행 계획과 실행 시간을 따로 기록한다.

구현 예시 SQL · 직접 작성한 뒤 비교하기

아래는 비교용 SQL이다. 예약·대상·작업 모델은 내가 정한 물리 이름과 필터로 옮긴다. board-server의 설계 기준이다. 2단계에서는 같은 계열의 기존 스키마를 관찰한다. 내 물리 이름·키·정렬이 다르면 매핑해 비교한다. 아래 SQL은 실제 실행 결과가 아니며 예시 서버가 모든 불변식을 보장한다는 뜻도 아니다. 오류가 예상되는 문장은 하나씩 실행하고 실패 뒤 ROLLBACK을 별도로 보낸다.

문항 1 구현 예시

EXPLAIN ANALYZE SELECT COUNT(*) FROM member_coupon WHERE member_id=1;

문항 2 구현 예시

EXPLAIN ANALYZE SELECT id FROM member_coupon WHERE member_id=1 ORDER BY id DESC LIMIT 20;

문항 3 구현 예시

SELECT campaign_id,COUNT(*) AS failed_count FROM target WHERE state='FAILED' GROUP BY campaign_id HAVING COUNT(*)>=1 ORDER BY campaign_id LIMIT 20;
SELECT COUNT(*) AS total_groups FROM (SELECT campaign_id FROM target WHERE state='FAILED' GROUP BY campaign_id HAVING COUNT(*)>=1) grouped;

질문 전체 건수 요청에 어떤 비용과 대안을 제시했나요?

#TC-D30-2

질문 예약 접수와 지급 성공을 어떻게 구분해 합의했나요?

답에 들어가야 할 것
  • 예약 접수는 미래 작업 수락이고 지급 성공은 항목별 확정 사실이다.
  • 접수 응답·상세 상태·부분 실패와 재시도의 외부 계약을 합의한다.
  • 정상/실패 JSON fixture·상태 코드·책임 경계 증거를 제시한다.

#TC-D30-3

질문 구앱을 못 바꾼다는 반론에 무엇을 수정했나요?

답에 들어가야 할 것
  • 구앱이 처리하는 필드·enum·상태 코드 계약을 말한다.
  • 새 필드 선택화/버전 분리 등 대안의 이행 비용을 비교한다.
  • 반론 전후 합의·구클라이언트 fixture 재검증·보류/담당을 기록한다.
