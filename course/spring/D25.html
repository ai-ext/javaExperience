01 · 직접 풀기

#오늘의 SQL

내 프로젝트의 disposable 실습 DB를 쓴다. D23에서 정한 예약·대상·지급 상태의 물리 이름과 필터로 아래 예시를 반드시 매핑한다. 예시의 member_coupon은 1단계 비교 모델이며 새 예약 테이블의 정답이 아니다. practice·원본 서버 DB는 수정하지 않는다.

  1. 동일 생성 키 요청 뒤 예약 수와 고정 대상 수·식별 집합을 검증한다.

    확인할 성질 같은 키의 동시 요청에서도 예약 1건과 합의한 대상 ID 집합 1개가 유지된다. 생성 키별 중복 예약과 예약별 중복 대상은 별도로 검사하고 API 응답의 예약 ID와 대조한다.

  2. API 응답에서 고른 조회 SQL의 계획을 확인한다.

    확인할 성질 내 물리 테이블·키·필터로 옮긴 SQL, 관찰 시각, 실제 출력과 기대 성질의 일치 여부를 남긴다. 예시는 실행 결과가 아니다.

구현 예시 SQL · 직접 작성한 뒤 비교하기

아래는 비교용 SQL이다. 예약·대상·작업 모델은 내가 정한 물리 이름과 필터로 옮긴다. board-server의 설계 기준이다. 2단계에서는 같은 계열의 기존 스키마를 관찰한다. 내 물리 이름·키·정렬이 다르면 매핑해 비교한다. 아래 SQL은 실제 실행 결과가 아니며 예시 서버가 모든 불변식을 보장한다는 뜻도 아니다. 오류가 예상되는 문장은 하나씩 실행하고 실패 뒤 ROLLBACK을 별도로 보낸다.

문항 1 구현 예시

SELECT creation_key,COUNT(*) AS reservations FROM campaign GROUP BY creation_key HAVING COUNT(*)<>1;
SELECT c.id,c.creation_key,COUNT(t.id) AS targets,COUNT(DISTINCT t.member_id) AS distinct_members,GROUP_CONCAT(t.member_id ORDER BY t.member_id) AS member_ids FROM campaign c LEFT JOIN target t ON t.campaign_id=c.id GROUP BY c.id,c.creation_key ORDER BY c.id;

문항 2 구현 예시

EXPLAIN SELECT id FROM member_coupon WHERE member_id=1 ORDER BY id DESC LIMIT 20;
