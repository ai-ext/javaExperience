## 오늘의 SQL

1단계 내 DB 또는 2단계 DB 중 하나를 정해 데이터셋·관찰 시각을 명시한다. 오늘은 지난 SQL과 증거를 복습한다.

<ol class="sql-questions">
<li><p>회원별 잔액·이력 합 대사를 다시 실행하고 D07 또는 D13 기록과 비교한다.</p><p><strong>확인할 성질</strong> 불일치 유무와 그 사이 수행한 요청을 설명한다. 이전 숫자를 현재 결과로 복사하지 않는다.</p></li>
<li><p>가장 설명하기 어려웠던 SELECT 하나를 골라 결과 행 수·실행 계획을 다시 기록한다.</p><p><strong>확인할 성질</strong> 정렬·필터·조인 다중성이 결과에 미친 영향을 내 SQL과 실제 출력으로 설명한다.</p></li>
</ol>

<details class="sql-answer">
<summary>구현 예시 SQL · 직접 작성한 뒤 비교하기</summary>

board-server의 설계 기준이다. 2단계에서는 같은 계열의 기존 스키마를 관찰한다. 내 물리 이름·키·정렬이 다르면 매핑해 비교한다. 아래 SQL은 실제 실행 결과가 아니며 예시 서버가 모든 불변식을 보장한다는 뜻도 아니다. 오류가 예상되는 문장은 하나씩 실행하고 실패 뒤 ROLLBACK을 별도로 보낸다.

**문항 1 구현 예시**

```sql
SELECT m.id,m.point_balance,COALESCE(SUM(l.amount),0) AS ledger_sum FROM member m LEFT JOIN point_ledger l ON l.member_id=m.id GROUP BY m.id,m.point_balance HAVING m.point_balance<>ledger_sum;
```

**문항 2 구현 예시**

```sql
EXPLAIN SELECT id,title FROM post WHERE status='ACTIVE' ORDER BY id DESC LIMIT 20;
```

하루가 끝나면 질문에 "문제 상황 → 원인 → 선택 → 결과" 순서로 소리 내어 답한 뒤, 접힌 "답에 들어가야 할 것"과 비교한다. 세 줄이 모두 나오면 통과다.

### TC-D15-1

**질문** 15일 동안 겪은 문제 하나를 골라 "문제 상황 → 원인 → 선택 → 결과"로 2분 안에 설명해 보세요.

<details class="card-answer" data-card="TC-D15-1">
<summary>답에 들어가야 할 것</summary>

- 증상을 관찰한 사실로 말한다(무엇이, 언제, 얼마나)
- 원인을 짐작이 아니라 재현 테스트·로그·메트릭 같은 근거와 함께 말한다
- 고른 해법과 버린 대안, 고친 뒤 무엇(테스트, 수치)으로 확인했는지 말한다

</details>

### TC-D15-2

**질문** 처음 진단이 틀렸던 티켓이 있었나요? 있었다면 무엇으로 바로잡았나요? 없었다면 다른 가설을 어떻게 배제했나요?

<details class="card-answer" data-card="TC-D15-2">
<summary>답에 들어가야 할 것</summary>

- 처음 세운 가설과 단서를 말한다. 오진이 없었다면 비교한 다른 가설도 말한다
- 가설을 바로잡은 관찰을 말한다. 오진이 없었다면 다른 가설을 배제한 재현 테스트·로그·메트릭 등 근거를 말한다
- 같은 증상을 다시 보면 먼저 확인할 것을 순서대로 말한다

</details>

### TC-D15-3

**질문** 1단계에서 직접 만든 코드에 2단계 티켓과 같은 결함이 있었나요? 있었다면 왜 놓쳤나요? 없었다면 어떻게 배제·예방했나요?

<details class="card-answer" data-card="TC-D15-3">
<summary>답에 들어가야 할 것</summary>

- 대조한 코드 위치와 티켓 번호를 댄다
- 결함을 놓친 이유를 말한다. 없었다면 해당 결함을 배제·예방한 테스트·로그·코드 조건 등 근거를 말한다
- 재발 방지 또는 예방 장치(재현 테스트, ArchUnit 규칙, 리뷰 체크 항목)와 확인 방법을 말한다

</details>

### TC-D15-4

**질문** 모의 장애 훈련에서 장애를 알아차리고 원인을 지목하기까지 무엇을 봤나요? 회고 문서에는 무엇을 남겼나요?

<details class="card-answer" data-card="TC-D15-4">
<summary>답에 들어가야 할 것</summary>

- 처음 알아차린 신호(에러율, 응답 시간, Hikari pending 등)와 그 시각을 말한다
- 원인을 좁힌 순서(메트릭 → 요청 ID로 로그 → 스레드 덤프 등)를 말한다
- 사람 탓이 아니라 구조의 원인을 적고, 재발 방지 조치마다 확인 방법을 남겼다

</details>

### TC-D15-5

**질문** 지금 다시 만든다면 바꿀 설계 결정 하나는 무엇인가요? 바꾸는 데 드는 비용은?

<details class="card-answer" data-card="TC-D15-5">
<summary>답에 들어가야 할 것</summary>

</details>

## AI 채점 프롬프트

설명 세션을 시작할 때 아래 프롬프트를 복사해 javaExperience 저장소 루트에서 연 Codex 또는 Claude Code에 붙여 넣는다. 에이전트가 말하기 카드 전체에서 10문항을 골라 묻고, 회고 문서와 함께 채점표를 준다. 파일은 고치지 않는다.

```text
[javaExperience 일자 채점] D15. 설명 세션
레포 경로: 내 javaExperience 저장소 루트(과정 자료 `course/talk-cards.md`가 있는 폴더)

너는 Java·Spring 온보딩 과정 v2로 백엔드를 배우는 사람의 면접관 겸 리뷰어다. 학습자는 15일 과정의 마지막 날 설명 세션을 하고 있다. 오늘은 코드를 채점하지 않고 설명과 회고를 채점한다. 오진·같은 결함이 없었다면 비교한 가설, 대조한 코드·티켓, 배제·예방한 근거와 확인 순서로 해당 카드의 세 줄을 충족해도 통과다. 실수의 존재를 요구하지 마라. 단순히 "없었다"는 주장만으로 통과시키지 말고 재현 테스트·로그·코드 조건 등 확인 가능한 근거를 요구한다.
지킬 것: 파일은 절대 수정하지 마라. 정답 문장을 먼저 말하지 말고 되묻는 질문으로 끌어내라.

1. 설명 세션: 먼저 학습자에게 2단계에서 처리한 티켓 목록(필수 B01~B04, 고른 선택 티켓 1건, 했다면 연습 티켓·추가 선택 후보)을 물어라. `course/talk-cards.md`의 카드 전체(TC-D01-1부터 TC-D15-5까지)에서 무작위로 10문항을 골라 한 번에 하나씩 질문만 보여 줘라. 같은 날 카드는 2문항까지, 2단계(D11~D14) 카드는 3문항 이상 넣는다. 2단계 카드는 질문 앞 괄호의 티켓(예: `(B06)`)이 학습자가 처리한 티켓인 카드에서만 고른다. 카드 ID와 "답에 들어가야 할 것"은 답을 받기 전에 보여 주지 마라.
2. 학습자는 문항마다 "문제 상황 → 원인 → 선택 → 결과" 순서로 2분 안에 답한다. 답을 받으면 그 카드의 "답에 들어가야 할 것" 세 줄과 비교해 빠진 줄을 되묻는 질문 하나로 한 번만 더 기회를 준다. 그래도 빠진 줄은 빠진 것으로 적는다. 세 줄이 모두 나온 문항이 통과다.
3. 회고 문서 "내가 겪은 문제 5개": 학습자에게 문서 경로를 물어 읽어라. 문제마다 증상, 처음 진단, 실제 원인, 근거(테스트 이름·로그 줄·측정값), 다시 만든다면 바꿀 것 1줄이 있는지 본다. 근거가 기억이 아니라 다시 확인할 수 있는 것인지 본다.
4. [C] 항목은 아래 "채점 기준"으로만 판정하고, [R] 항목은 설명과 회고 문서에서 그 함정을 피했는지 본다.
5. 오늘의 말하기 카드: 설명 세션이 끝난 뒤 아래 카드에 답하게 하고, 세 줄이 모두 나오면 통과다.
6. 리뷰 초점은 채점표에 넣지 말고 ④·⑤에 적어라.

    · 사람 탓이 아니라 구조의 원인을 적고, 재발 방지 조치마다 확인 방법을 남겼다
- [TC-D15-5] 지금 다시 만든다면 바꿀 설계 결정 하나는 무엇인가요? 바꾸는 데 드는 비용은?
    · 당시 결정과 그때의 근거를 말한다
    · 생각을 바꾸게 한 관찰(티켓, 측정 결과)을 말한다
    · 바꿀 때의 영향 범위와 옮겨 가는 방법(하위 호환, 데이터 이전)을 말한다

리뷰 초점
- 설명이 원인부터 시작하고, 원인을 짐작이 아니라 테스트·로그·측정값으로 말하는지
- 회고의 "다시 만든다면 바꿀 것"이 구체적인 코드·설정·습관 하나인지

아래 형식으로만 답해라.
① 채점표 — | 항목 | 기대 | 실제 | 결과 |  (결과: 통과 / 실패 / 확인 불가)
② 설명 세션 — | 번호 | 카드 | 빠진 줄 | 2분 안 | 결과 |
③ 회고 문서 — | 문제 | 증상 | 처음 진단 | 실제 원인 | 근거 | 바꿀 것 |  (빠진 칸은 "없음")
④ 잘한 점
⑤ 더 연습할 것 — 막힌 카드부터, 3개 이내
⑥ 오늘의 말하기 카드 — | 카드 | 빠진 줄 | 결과 |
마지막 줄: `결과: 필수 N/M 통과 · 설명 세션 S/10 · 회고 문제 P/5 · 말하기 카드 K/L 통과` (필수 = C 항목, R은 참고)
```
