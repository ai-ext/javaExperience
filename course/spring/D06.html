#오늘의 SQL

seed.sql의 D02~D05 블록 뒤 bulk.sql 전체를 한 번 실행한 별도 실험 DB를 쓴다. 이름이 다르면 INSERT·UPDATE·조회 이름을 바꾼다. D04·D05의 seed 전용 DB와 구분해 SQL·실제 결과를 저장한다.

더미 SQL·붙여 넣는 순서를 먼저 확인한다.

  1. 지정 태그가 붙은 공개 글을 EXISTS와 JOIN 두 방식으로 조회한다.

    확인할 성질 seed D05+bulk 기준 spring 태그 공개 글은 16,080건이다. EXISTS·JOIN의 글 식별 집합·순서가 같고 중복 행이 없다.

  2. 위 두 SQL의 실행 계획을 비교한다.

    확인할 성질 seed D05+bulk의 16,080건 결과 동등성을 먼저 확인하고 접근 경로·행 수·중복 제거 단계를 기록한다. 보편적으로 빠른 문법이라고 단정하지 않는다.

  3. 선택 필터를 바꿔 같은 글 ID 집합을 비교한다. MyBatis의 조건 생성과 값 바인딩은 애플리케이션 테스트에서 확인한다.

    확인할 성질 keyword만, tag만, 둘 다, 필터 없음에서 공개 글의 식별 집합·정렬을 확인한다. 공백과 빈 목록의 계약은 D06 ③의 API 테스트로 확인한다.

#TC-D06-1

질문 정렬 키를 요청 파라미터로 받아 ORDER BY ${sort}로 넣는 코드가 있습니다. 무엇이 문제고 어떻게 바꾸나요?

답에 들어가야 할 것
  • ${}는 값을 SQL 문자열에 그대로 끼워 넣으므로 SQL 인젝션이 가능하다
  • #{}는 PreparedStatement 파라미터로 바인딩돼 안전하지만, 값으로만 들어가므로 컬럼명이나 ORDER BY 대상에는 쓸 수 없다
  • 정렬은 허용 목록(명세상 latest만)으로 받고, 서버가 고정된 SQL 조각을 고른다
  • null·공백·빈 목록을 구분하고 조건 조합별 ID·순서가 같은지 확인한다

근거 spec-v2 §5-3

#TC-D06-2

질문 공개 글 최신순 커서 목록이 데이터가 늘자 느려졌습니다. 인덱스를 어떻게 정하고 확인했나요?

답에 들어가야 할 것
  • 내 필터·정렬·커서·데이터 분포를 보고 만든 인덱스의 열 순서와 선택 이유, 버린 대안 1개를 설명한다. 특정 실행 계획을 측정 전에 보장하지 않는다
  • EXPLAIN의 type, key, rows, Extra(Using filesort 여부)를 인덱스 전후로 비교하고, EXPLAIN ANALYZE로 실제 읽은 행 수를 본다
  • 커서 페이징은 내가 정한 안정적 정렬의 마지막 위치 뒤부터 이어 읽어, offset처럼 앞쪽 행을 읽고 버리지 않는다

#TC-D06-3

질문 같은 트랜잭션에서 JPA로 글 제목을 고친 직후 MyBatis로 목록을 읽었더니 옛 제목이 나왔습니다. 왜 그런가요?

답에 들어가야 할 것
  • JPA의 변경은 flush 전까지 영속성 컨텍스트에만 있고 DB에는 아직 UPDATE가 나가지 않았다
  • Hibernate의 자동 flush는 JPQL 실행 전에 일어나며, MyBatis가 JDBC로 직접 보내는 SQL은 Hibernate가 모르므로 flush를 일으키지 않는다
  • MyBatis 조회 전에 명시적으로 flush하고, 두 도구가 같은 트랜잭션(같은 커넥션)에 참여하는지 실험으로 확인한다

#TC-D06-4

질문 MyBatis 목록에서 글마다 태그를 <collection select="...">로 가져왔더니 쿼리가 글 수만큼 늘었습니다. 어떻게 고치나요?

답에 들어가야 할 것
  • 중첩 select는 부모 행마다 쿼리를 따로 실행하므로 글 20개면 태그 쿼리가 20번 나간다
  • JOIN 한 번으로 가져와 resultMap의 중첩 결과로 묶고, <id>를 선언해 같은 글의 행을 합친다
  • 다만 1:N JOIN 결과에 LIMIT을 걸면 글이 아니라 행 기준으로 잘리므로, 글에만 LIMIT을 거는 파생 테이블로 먼저 자르고 바깥에서 태그를 JOIN한다(글 ID 목록을 뽑은 뒤 IN으로 두 번 조회하는 것도 대안)
