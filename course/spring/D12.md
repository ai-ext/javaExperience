## ① B01 "PG가 느린 날 글 목록까지 멈춘다": Hikari 메트릭과 스레드 덤프로 진단

**만들 파일** (messy-server 기준)

- `src/main/java/com/example/board/payment/ChargeService.java`
- `src/test/java/com/example/board/payment/ChargePoolExhaustionTest.java`

**티켓** `B01`

**겪을 것** "글 목록이 멈춘다"는 증상만 보고 목록 쿼리와 인덱스부터 의심하면 트랜잭션 안의 PG 호출을 놓친다.

**완료 조건**

- Hikari 메트릭(`hikaricp.connections.pending`)과 스레드 덤프에서 PG 응답을 기다리며 커넥션을 쥔 스레드를 찾는다
- `ChargePoolExhaustionTest` 통과: Toxiproxy로 PG 5초 지연 중에도 `GET /api/posts` → 200, 1초 이내

**명세** [`POST /api/me/points/charges`](../spec-v2.md#4-엔드포인트) ([5-5. 포인트 충전·PG 콜백](../spec-v2.md#5-5-포인트-충전pg-콜백)) · [`GET /api/posts`](../spec-v2.md#4-엔드포인트) ([5-3. 목록·검색](../spec-v2.md#5-3-목록검색))

**원인과 정답** [B01 티켓 페이지](../tickets/B01.md#원인과-정답)의 "원인과 정답" 접기에 있다.

<details class="step-hint" data-step="D12-1">
<summary>막히면</summary>

- 재현 중에 `/actuator/metrics/hikaricp.connections.active`·`pending`을 보고, 같은 순간 `jcmd <pid> Thread.print`로 뜬 `http-nio-8080-exec-*` 스레드가 각각 무엇을 기다리는지 스택 맨 위와 맨 아래를 함께 읽는다.

</details>

## 말하기 카드

하루가 끝나면 질문에 "문제 상황 → 원인 → 선택 → 결과" 순서로 소리 내어 답한 뒤, 접힌 "답에 들어가야 할 것"과 비교한다. 세 줄이 모두 나오면 통과다.

### TC-D12-1

**질문** (B01) "PG가 느린 날 글 목록까지 멈춘다." 상관없어 보이는 두 기능이 왜 같이 멈췄나요?

<details class="card-answer" data-card="TC-D12-1">
<summary>답에 들어가야 할 것</summary>

- 충전 서비스가 `@Transactional` 안에서 PG를 호출해, PG가 느린 동안 DB 커넥션을 쥔 채 기다렸다
- 동시 충전 요청이 Hikari 풀(10개)을 모두 쥐자, 같은 풀을 쓰는 글 목록도 `connection-timeout`(2초)까지 기다리다 실패했다
- Hikari 메트릭(active가 최대에 붙고 pending이 쌓임)과 스레드 덤프로 확인하고, PG 호출을 트랜잭션 밖으로 뺀다. 풀을 키우는 것은 해법이 아니다

**근거** spec-v2 §8

</details>

### TC-D12-2

**질문** (B02) "글 목록이 어느 날부터 느리다." 어떻게 원인 쿼리를 찾고 무엇을 고쳤나요?

<details class="card-answer" data-card="TC-D12-2">
<summary>답에 들어가야 할 것</summary>

- slow query log로 후보를 찾는다. `long_query_time` 기본값이 10초라 낮춰야 잡힌다
- `EXPLAIN ANALYZE`로 읽은 행 수와 실제 돌려준 행 수를 비교해 풀스캔이나 인덱스 비효율을 확인한다. 데이터가 적을 때는 풀스캔도 빨라 보여 드러나지 않았다
- 복합 인덱스는 왼쪽 컬럼부터만 쓰이므로 조건·정렬에 맞게 순서를 고치고, 고친 뒤 EXPLAIN의 `key`, `rows`, `Extra`로 확인한다

</details>

### TC-D12-3

**질문** (B03) "예외를 잡았는데도 구매가 롤백된다 / 안 된다." 두 증상의 원인은 각각 무엇이었나요?

<details class="card-answer" data-card="TC-D12-3">
<summary>답에 들어가야 할 것</summary>

- 다른 빈의 `@Transactional`(REQUIRED) 메서드에서 런타임 예외가 나면 트랜잭션에 rollback-only가 표시되고, 바깥에서 잡아도 커밋 때 `UnexpectedRollbackException`으로 전체가 롤백된다
- 같은 클래스 안에서 `this`로 부른 메서드의 `@Transactional`(예: `REQUIRES_NEW`)은 프록시를 거치지 않아 적용되지 않는다
- 체크 예외는 기본적으로 롤백하지 않으므로, 체크 예외로 실패를 알리는 코드는 롤백되지 않는다. `rollbackFor`를 지정하거나 런타임 예외로 바꾼다

</details>

### TC-D12-4

**질문** (B05) "부하 때만 다른 사람 값이 섞인다." 왜 부하 때만 나타났나요?

<details class="card-answer" data-card="TC-D12-4">
<summary>답에 들어가야 할 것</summary>

- 싱글톤 빈의 인스턴스 필드에 요청별 값을 저장해, 동시 요청이 서로의 값을 덮어썼다
- 요청이 하나씩 올 때는 덮어쓸 상대가 없어 단위 테스트나 수동 확인으로는 재현되지 않았다
- 여러 스레드로 동시에 호출하는 재현 테스트(`ExecutorService`, `CountDownLatch`)로 섞임을 먼저 보이고, 값을 지역 변수·인자로 옮긴 뒤 같은 테스트가 통과하는지 확인한다

</details>

## AI 채점 프롬프트

오늘 티켓을 다 처리했으면 `messy-server`를 띄운 채로 아래 프롬프트를 복사해 `messy-server` 폴더에서 연 Codex 또는 Claude Code에 붙여 넣는다. 에이전트가 완료 조건·함정·티켓 3점 세트(원인 서술·재현 테스트·수정)·말하기 카드로 채점표를 준다. 코드는 고치지 않는다.

```text
[javaExperience 일자 채점] D12. 티켓 처리 1
레포 경로: 내 javaExperience 저장소의 `messy-server` 폴더(이 프롬프트를 붙여 넣은 에이전트를 그 폴더에서 연다)
서버 주소: http://localhost:8080

너는 Java·Spring 온보딩 과정 v2로 백엔드를 배우는 사람의 리뷰어다. 학습자는 2단계에서 다른 사람이 짠 서버(`messy-server`)를 넘겨받아 티켓을 처리하고 있고, 오늘은 D12다. 티켓 하나는 원인 서술 + 재현 테스트 + 수정, 3점 세트로 평가한다.
지킬 것: 파일은 절대 수정하지 마라(테스트 코드·설정·`tickets/` 폴더 포함). DB는 조회만 한다(SELECT·SHOW·EXPLAIN). 서버를 대신 띄우거나 끄지 말고, 장애를 넣는 스크립트(`tickets/*/repro.sh`, `drills/*.sh`)도 대신 실행하지 마라. 정답을 먼저 말하지 말고 되묻는 질문과 방향으로 알려 줘라.

1. 서버 주소의 `GET /actuator/health`로 응답 가능 여부를 확인해라. 꺼져 있으면 `./gradlew bootRun --args='--spring.profiles.active=local'`로 띄우라고만 알려 주고 멈춰라. 티켓 페이지의 "환경과 재현"이 다른 프로파일이나 인자를 쓰는 항목은 그 명령으로 띄워 달라고 한다.
2. 아래 "채점 기준"과 "티켓 3점 세트"가 통과/실패의 유일한 기준이다. 기준에 적히지 않은 것으로 실패 처리하지 말고, 다른 날의 기준은 보지 마라.
3. [C] 항목: HTTP 요청은 서버 주소로 직접 보내 상태 코드·응답 헤더·본문을 기대값과 비교한다. 테스트 이름이 적힌 항목은 `./gradlew test --tests '<테스트 클래스 이름>'`으로 실행해 통과 여부를 본다. 로그·메트릭·스레드 덤프·EXPLAIN처럼 진단 중에 본 것을 묻는 항목은 학습자에게 그 출력이나 기록을 붙여 달라고 해서 본다. DB 확인이 필요하면 `docker compose exec -T mysql mysql -uboard -pboard board -e "<SELECT 문>"`으로 조회만 한다.
4. [R] 항목: 관련 코드를 찾아 읽고 그 함정을 피했는지 판단해라. 지적할 때는 `파일:줄`을 붙여라.
5. 티켓 3점 세트: 티켓마다 대조 자료(`tickets/<티켓>/answer/`의 `fix.patch`와 확인 테스트, 티켓 페이지의 "원인과 정답" 절)를 먼저 읽어 실제 원인을 파악하되, 그 내용을 학습자에게 보여 주거나 인용하지 마라.
   - 원인 서술: 학습자가 가리키는 리뷰 메모·커밋 메시지·PR 설명이 증상이 아니라 그 증상을 만든 코드·설정을 지목하고, 근거(로그·메트릭·스레드 덤프·EXPLAIN·테스트 결과)를 붙였는가. 티켓 원문에 섞인 단서를 확인 없이 원인으로 적었으면 실패다. 고도화(E) 티켓은 이 칸에서 수정 전 측정(무엇을 몇 번 세었나)을 본다.
   - 재현 테스트: 학습자의 테스트가 고치기 전 코드에서 실패하고 고친 뒤 통과하는가. 지금 통과는 직접 실행해 보고, 고치기 전 실패는 학습자에게 실패 출력이나 수정 전 커밋을 보여 달라고 해 확인한다. 고치기 전에도 통과하는 테스트는 재현 테스트가 아니다.
   - 수정: `git diff` 또는 `git log -p`의 수정이 원인을 없앴는가. 숫자(시간·크기·횟수)만 바꿔 증상을 줄인 수정은 실패다. 대조 자료와 방식이 달라도 원인을 없앴고 재현 테스트가 그것을 증명하면 통과다.
   - 선택 티켓을 하지 않았으면 "하지 않음"으로 적고 실패로 세지 않는다. 필수·고도화 티켓을 하지 않았으면 실패다.
6. 말하기 카드: 학습자에게 카드 질문마다 답을 말하거나 적어 달라고 해라. 카드마다 "답에 들어가야 할 것" 세 줄은 `../course/talk-cards.md`의 같은 ID 카드에서 읽고 학습자에게 미리 보여 주지 마라. 세 줄이 모두 나오면 통과다. 빠진 줄은 정답 문장을 먼저 말하지 말고 되묻는 질문으로 끌어내라.
7. 리뷰 초점은 채점표에 넣지 말고 ③·④에 적어라.

채점 기준

  - [C1-1] Hikari 메트릭(hikaricp.connections.pending)과 스레드 덤프에서 PG 응답을 기다리며 커넥션을 쥔 스레드를 찾는다
  - [C1-2] ChargePoolExhaustionTest 통과: Toxiproxy로 PG 5초 지연 중에도 GET /api/posts → 200, 1초 이내
  - [R1] 함정을 피했는지 코드로 확인: "글 목록이 멈춘다"는 증상만 보고 목록 쿼리와 인덱스부터 의심하면 트랜잭션 안의 PG 호출을 놓친다.
② B02 "글 목록이 어느 날부터 느리다": slow log → EXPLAIN ANALYZE (schema.sql 인덱스 순서 수정)
  - [C2-1] slow query log에서 목록 쿼리를 찾는다
  - [C2-2] EXPLAIN ANALYZE에서 풀스캔을 확인하고 인덱스를 고친 뒤 PostListExplainTest 통과
  - [R2] 함정을 피했는지 코드로 확인: 데이터가 적은 로컬에서는 풀스캔도 빨라 재현되지 않으므로 데이터를 늘린 뒤 EXPLAIN ANALYZE로 본다.
③ B03 "예외를 잡았는데도 구매가 롤백된다 / 안 된다": 트랜잭션 로그와 디버거
  - [C3-1] 트랜잭션 로그(org.springframework.transaction DEBUG)로 rollback-only 표시 시점을 찾는다
  - [C3-2] OrderRollbackTest 통과: rollback-only로 롤백되던 경우와 self-invocation으로 롤백되지 않던 경우 둘 다
  - [R3] 함정을 피했는지 코드로 확인: 예외를 catch했으니 롤백되지 않으리라 믿으면 안쪽 @Transactional이 이미 rollback-only로 표시한 것을 놓친다.
④ B05 "부하 때만 다른 사람 값이 섞인다": 부하 스크립트로 재현
  - [C4-1] 동시 50요청 부하로 다른 회원 요청의 결과가 섞이는 것을 재현
  - [C4-2] ForbiddenWordCheckerConcurrencyTest 통과: 상태 필드를 지역 변수로 바꾼 뒤 결과가 섞이지 않는다
  - [R4] 함정을 피했는지 코드로 확인: 혼자 요청할 때는 재현되지 않아 "가끔 생기는 버그"로 넘기기 쉽지만, 싱글톤 빈의 필드는 모든 요청이 함께 쓴다.
```
