#인수인계 시작

  1. 1단계 앱 종료: 실행 중인 터미널에서 Ctrl+C(IDE라면 Stop). 1단계 프로젝트 루트에서 docker compose down으로 의존 서비스도 멈춘다. 데이터 삭제 옵션은 붙이지 않는다.
  2. 작업 대상 전환: 저장소 루트에서 cd messy-server. 이제 코드·명령의 기준은 messy-server/다. 1단계 내 프로젝트와 구분한다.
  3. 서버의 compose·DB 기동: 아래 명령을 messy-server/에서 실행한다. compose.yaml과 local 설정의 MySQL은 localhost:13311/board다(1단계는 13310). Redis·PG도 이 compose를 쓴다.
  1. 최초 기동 확인: 별도 터미널에서 curl -i http://localhost:8080/actuator/health → 200과 UP. 실패하면 기동 로그를 먼저 기록한다.
  2. 기준 테스트: 별도 터미널의 messy-server/에서 ./gradlew test를 실행한다(Docker 필요, 테스트는 별도 컨테이너 사용). 수정 전 성공·실패 개수와 실패 테스트·로그를 저장한다. 이 기록과 수정 후 결과를 비교한다.
  3. 이번 주 규칙 확인: 2단계 티켓 규칙을 읽고 필수 B01~B04·선택 1건·E01·훈련을 구분한다.

오늘 티켓의 장애 흐름

2단계는 요청 하나 대신 장애가 번지는 길을 따라갑니다. 티켓 페이지의 흐름은 증상 쪽만 먼저 보여 주고, 원인 쪽은 접혀 있습니다.

  • B11prod에서 설정값이 안 바뀐다증상 단계 3개 · 원인 단계는 티켓 페이지에서 펼침
  • B14운영에서 /actuator/env가 인증 없이 열린다증상 단계 3개 · 원인 단계는 티켓 페이지에서 펼침
  • B04알림 채널 하나 추가하는데 세 군데가 깨진다증상 단계 4개 · 원인 단계는 티켓 페이지에서 펼침
  • B08회원 API 응답에 비밀번호 해시가 보인다증상 단계 4개 · 원인 단계는 티켓 페이지에서 펼침

2단계 티켓 규칙 필수는 B01·B02·B03·B04 4건이다. 선택 1건은 D11을 시작할 때 Security 후보(B12·B13·B14)나 Redis 후보(B15·B16)에서 골라 끝까지 처리한다. 고도화 E01과 D14 ⑥ 모의 장애 훈련은 모두 한다. 연습 티켓은 나머지 7건(B05·B06·B07·B08·B09·B10·B11)이다. 연습 티켓과 고르지 않은 선택 후보는 했으면 채점 프롬프트에 알려 채점받고, 하지 않았으면 채점에서 빠진다. 필수·고른 선택·E01·훈련을 하지 않으면 그 항목은 실패다.

오늘 필수는 ④ B04다. ①·③의 B14는 Security 후보, B08·B11은 연습 티켓이다. 선택 1건을 B14로 고르면 오늘 ③에서 끝낸다. ③의 리뷰 메모는 모두 쓴다.

#오늘의 SQL

messy-server DB(13311)의 실제 스키마와 티켓 재현 자료를 쓴다. 1단계 seed.sql·bulk.sql은 적재하지 않는다. 읽기 전용 진단 SQL·관찰 시각·실제 결과만 남긴다. 관찰 결과가 0행이어도 원인이나 정상 여부를 단정하지 않는다. 예시 SQL은 기존 서버 설계 기준이다.

  1. 현재 DB의 테이블·열·제약 목록을 조사해 코드의 저장 경로와 짝짓는다.

    확인할 성질 실제 존재하는 이름과 관찰 시각을 지도에 기록한다. 예상 설계로 실제 결과를 대신하지 않는다.

  2. 관찰할 요청 하나를 정하고 전후 관련 데이터 건수를 비교한다.

    확인할 성질 읽은 경로와 건수 변화만 기록한다. 업무 요청은 해당 티켓 절차대로 학습자가 실행한다.

구현 예시 SQL · 직접 작성한 뒤 비교하기

board-server의 설계 기준이다. 2단계에서는 같은 계열의 기존 스키마를 관찰한다. 내 물리 이름·키·정렬이 다르면 매핑해 비교한다. 아래 SQL은 실제 실행 결과가 아니며 예시 서버가 모든 불변식을 보장한다는 뜻도 아니다. 오류가 예상되는 문장은 하나씩 실행하고 실패 뒤 ROLLBACK을 별도로 보낸다.

#TC-D11-1

질문 (B04) "알림 채널 하나 추가하는데 세 군데가 깨진다." 원인이 무엇이었나요?

답에 들어가야 할 것
  • 알림 채널(IN_APP·PUSH·EMAIL)별 저장 코드가 글 작성·글 삭제·댓글 작성 세 곳에 switch로 복사돼 있고 셋 다 default에서 예외를 던져, 채널 하나를 더하면 세 API가 함께 500이 됐다
  • 댓글 알림 때문에 PostServiceImpl과 CommentService가 서로를 필드로 받는 순환이 있었다. 현재 Boot는 순환 참조를 기본으로 막는데, 이 순환을 @Lazy로 덮어 기동만 되게 해 두었다
  • 고치기 전에 현재 동작을 특성화 테스트로 고정하고, 채널 하나 = 구현 하나(NotificationSender)로 모아 글·댓글 서비스는 생성자 주입으로 알림 서비스만 부르게 바꾼 뒤, 필드 주입 금지 ArchUnit 규칙으로 재발을 막는다

#TC-D11-2

질문 (B08) "회원 API 응답에 비밀번호 해시가 보인다." 원인과 재발 방지는?

답에 들어가야 할 것
  • 회원 엔티티를 그대로 JSON으로 응답해 passwordHash 필드까지 직렬화됐다
  • 엔티티를 직접 응답하면 엔티티 필드 추가가 곧 API 변경이 되고, 지연 로딩 연관이 있으면 직렬화 중 예외나 순환이 날 수 있다
  • 응답 DTO(id, email, nickname, role, createdAt)로 바꾸고, 응답에 비밀번호 필드가 없음을 단언하는 테스트를 둔다

근거 spec-v2 §5-1

#TC-D11-3

질문 (B11) "prod에서 설정값이 안 바뀐다." yml을 고쳤는데 왜 그대로였나요?

답에 들어가야 할 것
  • 커맨드라인 인자와 환경 변수가 설정 파일보다 우선하므로, prod에 같은 키의 환경 변수가 있으면 yml 수정은 반영되지 않는다
  • jar 밖의 application-prod.yml(또는 application-prod.properties)은 jar 안 파일보다 우선하므로, 서버에 남아 있는 외부 파일도 후보다
  • 인증 뒤의 /actuator/env/{키}에서 propertySources로 그 키를 어느 출처가 주는지 확인한 다음 그 출처를 고친다

#TC-D11-4

질문 (B14) "운영에서 /actuator/env가 인증 없이 열린다." 원인이 무엇이었나요?

답에 들어가야 할 것
  • 넓은 permitAll 규칙(EndpointRequest.toAnyEndpoint())이 env 관리자 규칙보다 앞에 있어, 첫 매치 규칙 때문에 env가 공개로 끝나고 뒤의 제한은 평가되지 않았다
  • prod 설정이 env를 노출하면서 show-values: always로 값 가림까지 꺼, 공개된 env에 비밀값이 평문으로 실렸다. SecurityFilterChain을 직접 정의하면 actuator 보안은 이 규칙이 전부다
  • health만 공개하고 나머지 노출 엔드포인트는 ADMIN으로 둔 뒤(좁은 규칙 먼저), show-values는 기본(never)으로 되돌리고, 토큰 없음 401·일반 회원 403·관리자 200을 테스트로 고정한다
