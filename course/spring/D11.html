2단계 티켓 규칙 필수는 B01·B02·B03·B04 4건이다. 선택 1건은 D11을 시작할 때 Security 후보(B12·B13·B14)나 Redis 후보(B15·B16)에서 골라 끝까지 처리한다. 고도화 E01과 D14 ⑥ 모의 장애 훈련은 모두 한다. 연습 티켓은 나머지 7건(B05·B06·B07·B08·B09·B10·B11)이다. 연습 티켓과 고르지 않은 선택 후보는 했으면 채점 프롬프트에 알려 채점받고, 하지 않았으면 채점에서 빠진다. 필수·고른 선택·E01·훈련을 하지 않으면 그 항목은 실패다.

오늘 필수는 ④ B04다. ①·③의 B14는 Security 후보, B08·B11은 연습 티켓이다. 선택 1건을 B14로 고르면 오늘 ③에서 끝낸다. ③의 리뷰 메모는 모두 쓴다.

#오늘의 SQL

messy-server DB(13311)의 실제 스키마와 티켓 재현 자료를 쓴다. 1단계 seed.sql·bulk.sql은 적재하지 않는다. 읽기 전용 진단 SQL·관찰 시각·실제 결과만 남긴다. 관찰 결과가 0행이어도 원인이나 정상 여부를 단정하지 않는다. 예시 SQL은 기존 서버 설계 기준이다.

  1. 현재 DB의 테이블·열·제약 목록을 조사해 코드의 저장 경로와 짝짓는다.

    확인할 성질 실제 존재하는 이름과 관찰 시각을 지도에 기록한다. 예상 설계로 실제 결과를 대신하지 않는다.

  2. 관찰할 요청 하나를 정하고 전후 관련 데이터 건수를 비교한다.

    확인할 성질 읽은 경로와 건수 변화만 기록한다. 업무 요청은 해당 티켓 절차대로 학습자가 실행한다.

구현 예시 SQL · 직접 작성한 뒤 비교하기

board-server의 설계 기준이다. 2단계에서는 같은 계열의 기존 스키마를 관찰한다. 내 물리 이름·키·정렬이 다르면 매핑해 비교한다. 아래 SQL은 실제 실행 결과가 아니며 예시 서버가 모든 불변식을 보장한다는 뜻도 아니다. 오류가 예상되는 문장은 하나씩 실행하고 실패 뒤 ROLLBACK을 별도로 보낸다.

문항 1 구현 예시

SELECT table_name,column_name,column_type FROM information_schema.columns WHERE table_schema=DATABASE() ORDER BY table_name,ordinal_position;
SELECT table_name,constraint_name,constraint_type FROM information_schema.table_constraints WHERE table_schema=DATABASE();

문항 2 구현 예시

SELECT COUNT(*) FROM post;
SELECT COUNT(*) FROM notification;

#TC-D11-1

질문 (B04) "알림 채널 하나 추가하는데 세 군데가 깨진다." 원인이 무엇이었나요?

답에 들어가야 할 것
  • 알림 채널(IN_APP·PUSH·EMAIL)별 저장 코드가 글 작성·글 삭제·댓글 작성 세 곳에 switch로 복사돼 있고 셋 다 default에서 예외를 던져, 채널 하나를 더하면 세 API가 함께 500이 됐다
  • 댓글 알림 때문에 PostServiceImpl과 CommentService가 서로를 필드로 받는 순환이 있었다. 현재 Boot는 순환 참조를 기본으로 막는데, 이 순환을 @Lazy로 덮어 기동만 되게 해 두었다
  • 고치기 전에 현재 동작을 특성화 테스트로 고정하고, 채널 하나 = 구현 하나(NotificationSender)로 모아 글·댓글 서비스는 생성자 주입으로 알림 서비스만 부르게 바꾼 뒤, 필드 주입 금지 ArchUnit 규칙으로 재발을 막는다

#TC-D11-2

질문 (B08) "회원 API 응답에 비밀번호 해시가 보인다." 원인과 재발 방지는?

답에 들어가야 할 것
  • 회원 엔티티를 그대로 JSON으로 응답해 passwordHash 필드까지 직렬화됐다
  • 엔티티를 직접 응답하면 엔티티 필드 추가가 곧 API 변경이 되고, 지연 로딩 연관이 있으면 직렬화 중 예외나 순환이 날 수 있다
  • 응답 DTO(id, email, nickname, role, createdAt)로 바꾸고, 응답에 비밀번호 필드가 없음을 단언하는 테스트를 둔다

#TC-D11-3

질문 (B11) "prod에서 설정값이 안 바뀐다." yml을 고쳤는데 왜 그대로였나요?

답에 들어가야 할 것
  • 커맨드라인 인자와 환경 변수가 설정 파일보다 우선하므로, prod에 같은 키의 환경 변수가 있으면 yml 수정은 반영되지 않는다
  • jar 밖의 application-prod.yml(또는 application-prod.properties)은 jar 안 파일보다 우선하므로, 서버에 남아 있는 외부 파일도 후보다
  • 인증 뒤의 /actuator/env/{키}에서 propertySources로 그 키를 어느 출처가 주는지 확인한 다음 그 출처를 고친다

#TC-D11-4

질문 (B14) "운영에서 /actuator/env가 인증 없이 열린다." 원인이 무엇이었나요?

답에 들어가야 할 것
  • 넓은 permitAll 규칙(EndpointRequest.toAnyEndpoint())이 env 관리자 규칙보다 앞에 있어, 첫 매치 규칙 때문에 env가 공개로 끝나고 뒤의 제한은 평가되지 않았다
  • prod 설정이 env를 노출하면서 show-values: always로 값 가림까지 꺼, 공개된 env에 비밀값이 평문으로 실렸다. SecurityFilterChain을 직접 정의하면 actuator 보안은 이 규칙이 전부다
  • health만 공개하고 나머지 노출 엔드포인트는 ADMIN으로 둔 뒤(좁은 규칙 먼저), show-values는 기본(never)으로 되돌리고, 토큰 없음 401·일반 회원 403·관리자 200을 테스트로 고정한다

#AI 채점 프롬프트

오늘 티켓을 다 처리했으면 messy-server를 띄운 채로 아래 프롬프트를 복사해 messy-server 폴더에서 연 Codex 또는 Claude Code에 붙여 넣는다. 에이전트가 완료 조건·함정·티켓 3점 세트(원인 서술·재현 테스트·수정)·말하기 카드로 채점표를 준다. 코드는 고치지 않는다.

채점 프롬프트 내용 확인
[javaExperience 일자 채점] D11. 인수인계
레포 경로: 내 javaExperience 저장소의 `messy-server` 폴더(이 프롬프트를 붙여 넣은 에이전트를 그 폴더에서 연다)
서버 주소: http://localhost:8080

너는 Java·Spring 온보딩 과정 v2로 백엔드를 배우는 사람의 리뷰어다. 학습자는 2단계에서 다른 사람이 짠 서버(`messy-server`)를 넘겨받아 티켓을 처리하고 있고, 오늘은 D11다. 티켓 하나는 원인 서술 + 재현 테스트 + 수정, 3점 세트로 평가한다.
0. 채점을 시작하기 전에 학습자에게 두 가지를 묻고 답 첫 줄에 적어라. (1) 2단계에서 고른 선택 티켓 1건: Security 후보(B12·B13·B14)나 Redis 후보(B15·B16) 중 하나다. (2) 그 밖에 오늘 처리한 티켓(연습 티켓 B05~B11이나 고르지 않은 선택 후보, 없으면 "없음"). 꼭 채점하는 대상은 `B01~B04(필수) + 학습자가 고른 선택 티켓 1건 + E01 + 모의 장애 훈련`이다. 필수 티켓 B01·B02·B03·B04 4건과 D14의 고도화 E01, 모의 장애 훈련은 모두가 한다. (2)의 티켓은 했다고 답한 것만 채점한다.
설정 형식 채점: application.yml과 application.properties를 모두 인정한다. application-local·prod·test 등 프로파일별 파일도 두 형식을 인정한다. 파일 확장자나 YAML의 --- 구조만으로 실패 처리하지 말고 같은 키·값, 활성 프로파일, 자리표시자, 실행 결과를 확인한다. ApplicationYmlTest·ProfileConfigTest·LocalProfileSeedTest처럼 YAML 원문을 읽는 예시는 properties의 동등한 키·값·프로파일 로딩 검사로 대체할 수 있다.
지킬 것: 파일은 절대 수정하지 마라(테스트 코드·설정·`tickets/` 폴더 포함). DB는 조회만 한다(SELECT·SHOW·EXPLAIN). 서버를 대신 띄우거나 끄지 말고, 장애를 넣는 스크립트(`tickets/*/repro.sh`, `drills/*.sh`)도 대신 실행하지 마라. 정답을 먼저 말하지 말고 되묻는 질문과 방향으로 알려 줘라.

1. 서버 주소의 `GET /actuator/health`로 응답 가능 여부를 확인해라. 꺼져 있으면 `./gradlew bootRun --args='--spring.profiles.active=local'`로 띄우라고만 알려 주고 멈춰라. 티켓 페이지의 "환경과 재현"이 다른 프로파일이나 인자를 쓰는 항목은 그 명령으로 띄워 달라고 한다.
2. 아래 "채점 기준"과 "티켓 3점 세트"가 통과/실패의 유일한 기준이다. 기준에 적히지 않은 것으로 실패 처리하지 말고, 다른 날의 기준은 보지 마라.
   - "제외"는 C 항목 괄호에 `선택`이나 `연습`이 붙은 티켓(이 날 제외할 수 있는 티켓: B11·B14·B08)이 0번의 (1)·(2) 어디에도 없을 때만 쓴다. 그 항목은 "제외"로 적고 필수 분모와 실패 수에서 모두 뺀다. 훈련의 B16 표시 항목도 이 규칙을 따른다. 괄호에 `필수`(B01~B04)나 `고도화`(E01)가 붙은 항목과 괄호에 티켓이 적히지 않은 항목(모의 장애 훈련 포함)은 학습자가 무엇을 골랐든 제외하지 않고 분모에 넣는다.
   - "(기록으로 확인)" 항목은 지금 서버·지금 코드로 판정하지 않는다. 고치기 전의 증상·진단 과정이거나, 네 권한 밖의 조건(다른 프로파일로 띄운 서버, 장애 주입, DDL 실행)에서 본 결과다. 항목에 적힌 기록(예: 고친 뒤 실행한 재현 스크립트 출력)을, 적힌 것이 따로 없으면 학습자가 보관한 재현 스크립트 출력·실패한 테스트 로그·수정 전 커밋(`git show <커밋>`)·기록 문서를 붙여 달라고 해서 확인한다. 표시가 붙지 않은 C 항목은 고친 뒤의 조건이므로 지금 서버와 지금 테스트로 확인한다. 같은 요청에 수정 전 결과와 수정 후 결과가 둘 다 기준에 있는 것은 이 구분 때문이다.
3. 표시가 붙지 않은 [C] 항목: HTTP 요청은 서버 주소로 직접 보내 상태 코드·응답 헤더·본문을 기대값과 비교한다. 테스트 이름이 적힌 항목은 `./gradlew test --tests '<테스트 클래스 이름>'`으로 실행해 통과 여부를 본다. 로그·메트릭·스레드 덤프·EXPLAIN처럼 진단 중에 본 것을 묻는 항목은 학습자에게 그 출력이나 기록을 붙여 달라고 해서 본다. DB 확인이 필요하면 `docker compose exec -T mysql mysql -uboard -pboard board -e "<SELECT 문>"`으로 조회만 한다.
4. [R] 항목: 그 순서의 티켓이 모두 "제외"면 R도 "제외"로 적는다. 나머지는 관련 코드를 찾아 읽고 그 함정을 피했는지 판단해라. 지적할 때는 `파일:줄`을 붙여라.
5. 티켓 3점 세트: 티켓마다 대조 자료(`tickets/<티켓>/answer/`의 `fix.patch`와 확인 테스트, 티켓 페이지의 "원인과 정답" 절)를 먼저 읽어 실제 원인을 파악하되, 그 내용을 학습자에게 보여 주거나 인용하지 마라.
   - 원인 서술: 학습자가 가리키는 리뷰 메모·커밋 메시지·PR 설명이 증상이 아니라 그 증상을 만든 코드·설정을 지목하고, 근거(로그·메트릭·스레드 덤프·EXPLAIN·테스트 결과)를 붙였는가. 티켓 원문에 섞인 단서를 확인 없이 원인으로 적었으면 실패다. 고도화(E) 티켓은 이 칸에서 수정 전 측정(무엇을 몇 번 세었나)을 본다.
   - 재현 테스트: 학습자의 테스트가 고치기 전 코드에서 실패하고 고친 뒤 통과하는가. 지금 통과는 직접 실행해 보고, 고치기 전 실패는 학습자에게 실패 출력이나 수정 전 커밋을 보여 달라고 해 확인한다. 고치기 전에도 통과하는 테스트는 재현 테스트가 아니다.
   - 수정: `git diff` 또는 `git log -p`의 수정이 원인을 없앴는가. 숫자(시간·크기·횟수)만 바꿔 증상을 줄인 수정은 실패다. 대조 자료와 방식이 달라도 원인을 없앴고 재현 테스트가 그것을 증명하면 통과다.
   - 0번의 (1)·(2)에 포함되지 않은 선택·연습 티켓만 "제외"로 적고 세지 않는다. 필수 티켓 B01~B04, 고른 선택 티켓, E01을 하지 않았으면 제외가 아니라 실패다.
6. 말하기 카드: 학습자에게 카드 질문마다 답을 말하거나 적어 달라고 해라. 질문 앞 괄호의 티켓(예: `(B06)`)이 2번 규칙으로 "제외"인 티켓이면 그 카드도 "제외"로 적고 K/L에서 뺀다. 대상 카드가 하나도 없으면 "대상 없음(0/0)"으로 적는다. 카드마다 "답에 들어가야 할 것" 세 줄은 `../course/talk-cards.md`의 같은 ID 카드에서 읽고 학습자에게 미리 보여 주지 마라. 세 줄이 모두 나오면 통과다. 빠진 줄은 정답 문장을 먼저 말하지 말고 되묻는 질문으로 끌어내라.
7. 리뷰 초점은 채점표에 넣지 말고 ③·④에 적어라.

채점 기준
① 코드 읽기: 진입점 → 필터 체인 → 컨트롤러 → 서비스 → 저장소 지도 그리기, 설정·보안 규칙 점검
  - [C1-1] (기록으로 확인) 패키지·요청 흐름 지도 1장과 읽은 순서 기록
  - [C1-2] (B14 선택 · 기록으로 확인) B14 재현: prod 프로파일에서 토큰 없이 GET /actuator/env → 200
  - [C1-3] (B11 연습 · 기록으로 확인) B11 재현: bash tickets/B11/repro.sh 출력의 /actuator/env 출처 목록(propertySources)에서 prod에서 바뀌지 않는 키의 값을 준 출처를 찾는다
  - [R1] 함정을 피했는지 코드로 확인: yml 파일만 읽고 값을 추측하면 실제로 쓰이는 값과 그 값을 준 곳을 놓친다.
② 특성화 테스트로 지금 동작 고정하기
  - [C2-1] (B04 필수) PostServiceCharacterizationTest 통과: 글 작성·수정·삭제의 현재 동작(알림 호출 포함)을 고정
  - [C2-2] (B08 연습 · 기록으로 확인) MemberApiCharacterizationTest 통과: 지금의 GET /api/members/me 응답 필드를 그대로 고정 (passwordHash가 보이는 것이 B08의 증거)
  - [R2] 함정을 피했는지 코드로 확인: 특성화 테스트에 "옳은 동작"을 적으면 고치기 전부터 실패해 동작을 고정하지 못하므로 지금 나오는 값을 그대로 적는다.
③ 구조·컨벤션 리뷰 메모 쓰기, B08·B11(연습)·B14(Security 후보) 고치기
  - [C3-1] (기록으로 확인) 리뷰 메모: 구조·컨벤션 지적 5개 이상, 오늘 처리한 티켓에 원인 서술 + 재현 테스트 + 수정 기록
  - [C3-2] (B08 연습) GET /api/members/me → 200, 응답에 passwordHash 없음 (특성화 테스트를 새 기대값으로 갱신)
  - [C3-3] (B14 선택 · 기록으로 확인) prod 프로파일에서 토큰 없이 GET /actuator/env → 401 (고친 뒤 bash tickets/B14/repro.sh 출력을 남긴다)
  - [C3-4] (B11 연습 · 기록으로 확인) prod에서 고친 설정값이 반영된다: 고친 뒤 bash tickets/B11/repro.sh 출력에서 로그인 expiresIn이 1800이고 /actuator/env에 그 값을 준 출처가 나온다
  - [R3] 함정을 피했는지 코드로 확인: B11을 yml 수정만으로 끝내면 prod에서 여전히 반영되지 않을 수 있으므로, 고친 뒤 /actuator/env로 그 키의 실제 값과 출처를 다시 확인한다.
④ B04 "알림 채널 하나 추가하는데 세 군데가 깨진다": ArchUnit 규칙 1개로 이번에 찾은 구조 문제의 재발 막기

  - [C4-2] (B04 필수) B04를 고친 뒤 ArchitectureTest·PostServiceCharacterizationTest 통과
  - [C4-3] (B04 필수) 알림 채널을 하나 더해도 글·댓글 API 처리 코드는 고치지 않는다
  - [R4] 함정을 피했는지 코드로 확인: 구조를 바꾸는 도중 기동이 실패하면 되돌리고 싶어지지만, 그 실패 메시지가 이번 구조 문제의 증거다.

리뷰 초점
- 리뷰 메모의 지적이 `파일:줄`과 함께 "그래서 어떤 사고가 나는가"까지 말하는지
- 특성화 테스트가 고치기 전 동작을 그대로 적었고, 기대값을 바꾼 곳마다 이유가 커밋이나 메모에 남아 있는지

아래 형식으로만 답해라.
① 채점표 — | 항목 | 기대 | 실제 | 결과 |  (결과: 통과 / 실패 / 확인 불가 / 제외)
② 티켓 3점 세트 — | 티켓 | 원인 서술 | 재현 테스트 | 수정 |  (칸마다 통과 / 실패 / 제외, 실패는 이유 한 줄)
③ 잘한 점
④ 부족한 점과 이유 — 실패한 C 항목과 3점 세트부터
⑤ 내일 전에 고칠 것 — 중요한 것부터, 3개 이내
⑥ 말하기 카드 — | 카드 | 빠진 줄 | 결과 |  (결과: 통과 / 실패 / 제외)
마지막 줄: `결과: 고른 티켓 <목록> · 필수 N/M 통과 · 티켓 3점 세트 T/U 완성 · 말하기 카드 K/L 통과` (필수 = 제외하지 않은 C 항목, R은 참고, 3점 세트·말하기 카드도 "제외"인 티켓만 빼고 센다)

프롬프트를 복사한 뒤 에이전트에서 실행하고 채점표를 확인하세요. 복사와 구현 체크는 채점 완료가 아닙니다.
