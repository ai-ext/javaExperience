#오늘의 SQL

내 프로젝트의 disposable 실습 DB를 쓴다. D23에서 정한 예약·대상·지급 상태의 물리 이름과 필터로 아래 예시를 반드시 매핑한다. 예시의 member_coupon은 1단계 비교 모델이며 새 예약 테이블의 구현 예시가 아니다. practice·원본 서버 DB는 수정하지 않는다.

  1. 복구 후 고정 대상 대비 지급 중복·누락·상태 불일치를 대사한다.

    확인할 성질 예약별 전체=성공+실패+대기를 확인한다. 중복 0, SUCCESS 미지급 0, 지급됐지만 SUCCESS가 아닌 행 0을 각각 확인한다. FAILED/PENDING 미지급은 누락으로 숨기지 말고 후속 처리 상태로 남긴다.

  2. 복구 전후 항목의 재시도·대기·영구 실패 상태를 확인한다.

    확인할 성질 FAILED/PENDING 행의 attempts·next_retry_at과 합의된 영구 실패 표시를 기록하고 전후 식별 집합을 비교한다. DB 세션 목록을 작업 상태로 대체하지 않는다.

구현 예시 SQL · 직접 작성한 뒤 비교하기

아래는 비교용 SQL이다. 예약·대상·작업 모델은 내가 정한 물리 이름과 필터로 옮긴다. board-server의 설계 기준이다. 2단계에서는 같은 계열의 기존 스키마를 관찰한다. 내 물리 이름·키·정렬이 다르면 매핑해 비교한다. 아래 SQL은 실제 실행 결과가 아니며 예시 서버가 모든 불변식을 보장한다는 뜻도 아니다. 오류가 예상되는 문장은 하나씩 실행하고 실패 뒤 ROLLBACK을 별도로 보낸다.

#TC-D45-1

질문 원인을 모르는 상태에서 무엇부터 결정했나요?

답에 들어가야 할 것
  • 새 장애의 초기 영향·사실·가정·미확인을 구분한다.
  • 최소 증거 확보와 완화 우선순위·담당·다음 보고 시각을 결정한다.
  • 초기 진단 뒤 선택한 가설/Java 반증·실제 타임라인과 받은 도움을 제시한다.

#TC-D45-2

질문 복구와 원인 확정을 각각 무엇으로 확인했나요?

답에 들어가야 할 것
  • 복구는 요청 정상화·데이터 대사·정상 구간 유지로 확인한다.
  • 원인 확정은 주입 기록/재현/반증으로 가설과 대조하며 복구와 다른 시점일 수 있다.
  • 실제 복구·원인 증거·미확인 항목과 비공개 주입자 부재 한계를 제시한다.

#TC-D45-3

질문 무엇을 혼자 할 수 있고 무엇은 재평가가 필요한가요?

답에 들어가야 할 것
  • D15/D42 설명·회고 5개·네 회의·D44/D45 독립 결과를 연결한다.
  • 혼자 가능한 범위와 도움 필요/실패/미실행을 역량별로 나눈다.
  • 연차 보증 대신 약점별 다음 실험·완료 조건·재평가 시점을 확정한다.
