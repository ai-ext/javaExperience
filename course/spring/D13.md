## 오늘의 SQL

messy-server DB(13311)의 실제 스키마와 티켓 재현 자료를 쓴다. 1단계 seed.sql·bulk.sql은 적재하지 않는다. 읽기 전용 진단 SQL·관찰 시각·실제 결과만 남긴다. 관찰 결과가 0행이어도 원인이나 정상 여부를 단정하지 않는다. 예시 SQL은 기존 서버 설계 기준이다.

<ol class="sql-questions">
<li><p>재현 중 DB의 대기 관계와 최근 엔진 진단 기록을 조회한다.</p><p><strong>확인할 성질</strong> 관찰한 식별 값·시각·출력을 그대로 저장한다. 행이 없으면 그 사실을 적고 원인으로 단정하지 않는다.</p></li>
<li><p>주문 요청별 데이터 건수와 회원별 잔액·이력 합을 대조한다.</p><p><strong>확인할 성질</strong> 중복 또는 차이의 유무를 SQL 결과로 남긴다. 결과를 맞추려고 데이터를 수정하지 않는다.</p></li>
</ol>

<details class="sql-answer">
<summary>구현 예시 SQL · 직접 작성한 뒤 비교하기</summary>

board-server의 설계 기준이다. 2단계에서는 같은 계열의 기존 스키마를 관찰한다. 내 물리 이름·키·정렬이 다르면 매핑해 비교한다. 아래 SQL은 실제 실행 결과가 아니며 예시 서버가 모든 불변식을 보장한다는 뜻도 아니다. 오류가 예상되는 문장은 하나씩 실행하고 실패 뒤 ROLLBACK을 별도로 보낸다.

**문항 1 구현 예시**

```sql
SELECT * FROM performance_schema.data_lock_waits;
SHOW ENGINE INNODB STATUS;
```

**문항 2 구현 예시**

```sql
SELECT member_id,idempotency_key,COUNT(*) FROM shop_order GROUP BY member_id,idempotency_key HAVING COUNT(*)>1;
SELECT m.id,m.point_balance,COALESCE(SUM(l.amount),0) AS ledger_sum FROM member m LEFT JOIN point_ledger l ON l.member_id=m.id GROUP BY m.id,m.point_balance HAVING m.point_balance<>ledger_sum;
```

</details>

### TC-D13-1

**질문** (D13 ⑤ · B06) "컬럼 하나 추가했더니 상점 전체가 멈췄다." ALTER 한 줄이 왜 서비스를 멈췄나요?

<details class="card-answer" data-card="TC-D13-1">
<summary>답에 들어가야 할 것</summary>

- 커밋하지 않은 긴 트랜잭션이 그 테이블의 메타데이터 락(MDL)을 쥐고 있어, ALTER가 MDL을 얻지 못하고 기다렸다
- 대기 중인 ALTER 뒤로 같은 테이블의 일반 쿼리까지 줄줄이 막혀 상점 전체가 멈췄다
- `SHOW PROCESSLIST`의 `Waiting for table metadata lock`과 `information_schema.innodb_trx`로 오래된 트랜잭션을 찾고, DDL 세션에는 짧은 `lock_wait_timeout`을 걸어 무한 대기를 막는다

</details>

### TC-D13-2

**질문** (D13 ② · B07) "선착순 쿠폰을 동시에 받을 때 가끔 실패한다." 실패 원인이 무엇이었나요?

<details class="card-answer" data-card="TC-D13-2">
<summary>답에 들어가야 할 것</summary>

- REPEATABLE READ에서 `SELECT ... FOR UPDATE`로 없는 행을 확인하면, 결과가 없어도 그 구간에 gap lock이 걸린다
- gap lock끼리는 충돌하지 않아 두 트랜잭션이 같은 구간을 잡는다. A는 쿠폰 행 락을 쥔 채 발급 행 INSERT(insert intention)가 B의 gap lock에 막히고, B는 A가 쥔 쿠폰 행 락을 기다려 순환 대기(데드락)가 된다
- `SHOW ENGINE INNODB STATUS`의 `LATEST DETECTED DEADLOCK`에서 두 트랜잭션의 락을 읽고, 중복 확인용 `FOR UPDATE`를 빼고 UNIQUE 제약과 중복 키 처리로 바꾼다

</details>

### TC-D13-3

**질문** (D13 ③ · B09) "자정 전후 출석 포인트가 두 번 쌓인다." 원인과 재현 방법은?

<details class="card-answer" data-card="TC-D13-3">
<summary>답에 들어가야 할 것</summary>

- 출석 날짜를 `LocalDate.now(clock)`으로 구했는데 주입된 시계가 `Clock.systemUTC()`라 날짜가 UTC 기준으로 잘렸다. KST 08:59:59와 09:00:00(UTC 자정)이 다른 날이 되어 같은 KST 날짜에 두 번 적립됐다
- 반대로 KST 23:59:59와 다음 날 00:00:00은 UTC로 같은 날이라 다음 날 첫 출석이 거절됐다. (회원, 날짜) UNIQUE는 같은 날짜 값의 중복만 막으므로 날짜 값 자체가 틀린 것은 막지 못한다
- 업무 기준 시간대를 코드에 명시하고(`LocalDate.ofInstant(clock.instant(), ZoneId.of("Asia/Seoul"))`), 영역은 UTC 그대로 시각만 바꾸는 가변 시계로 KST 08:59:59/09:00:00과 23:59:59/00:00:00을 고정한 테스트를 쓴다

</details>

### TC-D13-4

**질문** (D13 ④ · B10) "포인트 충전이 가끔 두 번 된다." 원인이 무엇이었나요?

<details class="card-answer" data-card="TC-D13-4">
<summary>답에 들어가야 할 것</summary>

- PG 응답 타임아웃 뒤 재시도가 새 멱등 키(`UUID.randomUUID()`)로 새 승인 요청을 보냈고, PG는 응답만 늦었을 뿐 첫 요청도 이미 승인했다
- 새 키 = 새 `pg_payment` 행이라 행마다 "한 번만 적립"은 지켜져도 두 행이 각각 적립됐다. `idempotency_key` UNIQUE는 같은 키만 막으므로 새로 만든 키는 막지 못한다
- 응답 타임아웃은 다시 보내지 않고 결과 불명(UNKNOWN)으로 남겨 콜백·재처리(`reconcile`)로 확정한다(다시 보내야 하면 같은 키로). WireMock 시나리오로 첫 응답만 늦춰 "PG가 받은 서로 다른 키 1개, 충전 원장 1건"을 테스트로 고정한다

</details>

(2)의 티켓은 했다고 답한 것만 채점한다.

1. 서버 주소의 `GET /actuator/health`로 응답 가능 여부를 확인해라. 꺼져 있으면 `./gradlew bootRun --args='--spring.profiles.active=local'`로 띄우라고만 알려 주고 멈춰라. 티켓 페이지의 "환경과 재현"이 다른 프로파일이나 인자를 쓰는 항목은 그 명령으로 띄워 달라고 한다.
2. 아래 "채점 기준"과 "티켓 3점 세트"가 통과/실패의 유일한 기준이다. 기준에 적히지 않은 것으로 실패 처리하지 말고, 다른 날의 기준은 보지 마라.

3. 표시가 붙지 않은 [C] 항목: HTTP 요청은 서버 주소로 직접 보내 상태 코드·응답 헤더·본문을 기대값과 비교한다. 테스트 이름이 적힌 항목은 `./gradlew test --tests '<테스트 클래스 이름>'`으로 실행해 통과 여부를 본다. 로그·메트릭·스레드 덤프·EXPLAIN처럼 진단 중에 본 것을 묻는 항목은 학습자에게 그 출력이나 기록을 붙여 달라고 해서 본다. DB 확인이 필요하면 `docker compose exec -T mysql mysql -uboard -pboard board -e "<SELECT 문>"`으로 조회만 한다.

   - 원인 서술: 학습자가 가리키는 리뷰 메모·커밋 메시지·PR 설명이 증상이 아니라 그 증상을 만든 코드·설정을 지목하고, 근거(로그·메트릭·스레드 덤프·EXPLAIN·테스트 결과)를 붙였는가. 티켓 원문에 섞인 단서를 확인 없이 원인으로 적었으면 실패다. 고도화(E) 티켓은 이 칸에서 수정 전 측정(무엇을 몇 번 세었나)을 본다.
   - 재현 테스트: 학습자의 테스트가 고치기 전 코드에서 실패하고 고친 뒤 통과하는가. 지금 통과는 직접 실행해 보고, 고치기 전 실패는 학습자에게 실패 출력이나 수정 전 커밋을 보여 달라고 해 확인한다. 고치기 전에도 통과하는 테스트는 재현 테스트가 아니다.
   - 수정: `git diff` 또는 `git log -p`의 수정이 원인을 없앴는가. 숫자(시간·크기·횟수)만 바꿔 증상을 줄인 수정은 실패다. 대조 자료와 방식이 달라도 원인을 없앴고 재현 테스트가 그것을 증명하면 통과다.
   - 0번의 (1)·(2)에 포함되지 않은 선택·연습 티켓만 "제외"로 적고 세지 않는다. 필수 티켓 B01~B04, 고른 선택 티켓, E01을 하지 않았으면 제외가 아니라 실패다.

③ 잘한 점
④ 부족한 점과 이유 — 실패한 C 항목과 3점 세트부터
⑤ 내일 전에 고칠 것 — 중요한 것부터, 3개 이내
⑥ 말하기 카드 — | 카드 | 빠진 줄 | 결과 |  (결과: 통과 / 실패 / 제외)
마지막 줄: `결과: 고른 티켓 <목록> · 필수 N/M 통과 · 티켓 3점 세트 T/U 완성 · 말하기 카드 K/L 통과` (필수 = 제외하지 않은 C 항목, R은 참고, 3점 세트·말하기 카드도 "제외"인 티켓만 빼고 센다)
