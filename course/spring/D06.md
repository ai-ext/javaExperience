**새 파일** `src/main/java/com/example/board/common/CursorPage.java`

```java
package com.example.board.common;

import java.nio.charset.StandardCharsets;
import java.util.Base64;
import java.util.List;

/** 커서 방식 목록 응답. 마지막 쪽이면 nextCursor는 null이다. */
public record CursorPage<T>(List<T> items, String nextCursor) {

    /** 커서는 마지막 항목의 id를 Base64URL로 감싼 불투명 문자열이다. */
    public static String encode(long id) {
        return Base64.getUrlEncoder().withoutPadding().encodeToString(Long.toString(id).getBytes(StandardCharsets.UTF_8));
    }

    /** 첫 쪽(null·빈 값)이면 null. 서버가 준 적 없는 값은 VALIDATION 예외다. */
    public static Long decode(String cursor) {
        if (cursor == null || cursor.isEmpty()) {
            return null;
        }
        try {
            long id = Long.parseLong(new String(Base64.getUrlDecoder().decode(cursor), StandardCharsets.UTF_8));
            if (id > 0) {
                return id;
            }
        } catch (IllegalArgumentException e) {
            // 아래에서 같은 예외로 처리한다
        }
        throw new BusinessException(ErrorCode.VALIDATION, "cursor가 올바르지 않습니다.");
    }
}
```

**새 파일** `src/main/java/com/example/board/post/PostQueryService.java`

```java
package com.example.board.post;

import java.util.List;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import com.example.board.common.CursorPage;

@Service
public class PostQueryService {

    private final PostQueryMapper mapper;

    public PostQueryService(PostQueryMapper mapper) {
        this.mapper = mapper;
    }

    @Transactional(readOnly = true)
    public CursorPage<PostSummary> search(PostSearchCondition condition, String cursor, int size) {
        Long afterId = CursorPage.decode(cursor);
        PostSearchCondition safe = new PostSearchCondition(escapeLike(condition.keyword()), condition.tag());
        // 한 건 더 읽어 다음 쪽이 있는지만 판단한다
        List<PostSummary> rows = mapper.search(safe, afterId, size + 1);
        boolean hasNext = rows.size() > size;
        List<PostSummary> page = hasNext ? rows.subList(0, size) : rows;
        String next = hasNext ? CursorPage.encode(page.get(page.size() - 1).getId()) : null;
        return new CursorPage<>(page, next);
    }
```

### TC-D06-1

**질문** 정렬 키를 요청 파라미터로 받아 `ORDER BY ${sort}`로 넣는 코드가 있습니다. 무엇이 문제고 어떻게 바꾸나요?

<details class="card-answer" data-card="TC-D06-1">
<summary>답에 들어가야 할 것</summary>

- `${}`는 값을 SQL 문자열에 그대로 끼워 넣으므로 SQL 인젝션이 가능하다
- `#{}`는 PreparedStatement 파라미터로 바인딩돼 안전하지만, 값으로만 들어가므로 컬럼명이나 `ORDER BY` 대상에는 쓸 수 없다
- 정렬은 허용 목록(명세상 `latest`만)으로 받고, 서버가 고정된 SQL 조각을 고른다

**근거** spec-v2 §5-3

### TC-D06-2

**질문** 공개 글 최신순 커서 목록이 데이터가 늘자 느려졌습니다. 인덱스를 어떻게 정하고 확인했나요?

<details class="card-answer" data-card="TC-D06-2">
<summary>답에 들어가야 할 것</summary>

- 내 필터·정렬·커서·데이터 분포를 보고 만든 인덱스의 열 순서와 선택 이유, 버린 대안 1개를 설명한다. 특정 실행 계획을 측정 전에 보장하지 않는다
- EXPLAIN의 `type`, `key`, `rows`, `Extra`(Using filesort 여부)를 인덱스 전후로 비교하고, `EXPLAIN ANALYZE`로 실제 읽은 행 수를 본다
- 커서 페이징은 내가 정한 안정적 정렬의 마지막 위치 뒤부터 이어 읽어, offset처럼 앞쪽 행을 읽고 버리지 않는다

</details>

### TC-D06-3

**질문** 같은 트랜잭션에서 JPA로 글 제목을 고친 직후 MyBatis로 목록을 읽었더니 옛 제목이 나왔습니다. 왜 그런가요?

<details class="card-answer" data-card="TC-D06-3">
<summary>답에 들어가야 할 것</summary>

- JPA의 변경은 flush 전까지 영속성 컨텍스트에만 있고 DB에는 아직 UPDATE가 나가지 않았다
- Hibernate의 자동 flush는 JPQL 실행 전에 일어나며, MyBatis가 JDBC로 직접 보내는 SQL은 Hibernate가 모르므로 flush를 일으키지 않는다
- MyBatis 조회 전에 명시적으로 flush하고, 두 도구가 같은 트랜잭션(같은 커넥션)에 참여하는지 실험으로 확인한다

</details>

### TC-D06-4

**질문** MyBatis 목록에서 글마다 태그를 `<collection select="...">`로 가져왔더니 쿼리가 글 수만큼 늘었습니다. 어떻게 고치나요?

<details class="card-answer" data-card="TC-D06-4">
<summary>답에 들어가야 할 것</summary>

- 중첩 select는 부모 행마다 쿼리를 따로 실행하므로 글 20개면 태그 쿼리가 20번 나간다
- JOIN 한 번으로 가져와 `resultMap`의 중첩 결과로 묶고, `<id>`를 선언해 같은 글의 행을 합친다
- 다만 1:N JOIN 결과에 LIMIT을 걸면 글이 아니라 행 기준으로 잘리므로, 글에만 LIMIT을 거는 파생 테이블로 먼저 자르고 바깥에서 태그를 JOIN한다(글 ID 목록을 뽑은 뒤 `IN`으로 두 번 조회하는 것도 대안)

</details>

```text
설계 채점: 테이블·컬럼·키·제약·인덱스 이름은 학습자의 설계를 따른다. board-server의 이름·분할과 다르다는 이유로 실패 처리하지 마라. 설계 메모와 DB 불변식 확인은 제출 SQL·거부 결과·테스트를 읽고 판단한다. 채점자가 INSERT·UPDATE·DELETE로 재현하지 말고 증거가 없으면 확인 불가로 적어라. API 필드·상태·오류 계약은 유지한다.
2. 아래 "채점 기준"이 통과/실패의 유일한 기준이다. 기준에 없는 것으로 실패 처리하지 말고, 다른 날의 기준은 보지 마라.
3. [C] 항목: HTTP 요청은 서버 주소로 직접 보내 상태 코드·응답 헤더·본문을 기대값과 비교한다. 테스트 이름이 적힌 항목은 레포 루트에서 `./gradlew test --tests '<테스트 클래스 이름>'`으로 실행해 통과 여부를 본다(테스트 코드도 고치지 마라). 로그 항목은 기동 로그에서 찾거나 학습자에게 해당 줄을 붙여 달라고 한다. DB 확인이 필요하면 `docker compose exec -T mysql mysql -uboard -pboard board -e "<SELECT 문>"`으로 조회만 한다.
4. [R] 항목: 관련 코드를 찾아 읽고 그 함정을 피했는지 판단해라. 지적할 때는 `파일:줄`을 붙여라.
5. 말하기 카드: 학습자에게 카드 질문마다 답을 말하거나 적어 달라고 해라. "답에 들어가야 할 것"(· 표시) 세 줄이 모두 나오면 통과다. 빠진 줄은 정답 문장을 먼저 말하지 말고 되묻는 질문으로 끌어내라.
6. 리뷰 초점은 채점표에 넣지 말고 ②·③에 적어라.

말하기 카드
- [TC-D06-1] 정렬 키를 요청 파라미터로 받아 ORDER BY ${sort}로 넣는 코드가 있습니다. 무엇이 문제고 어떻게 바꾸나요?
    · ${}는 값을 SQL 문자열에 그대로 끼워 넣으므로 SQL 인젝션이 가능하다
    · #{}는 PreparedStatement 파라미터로 바인딩돼 안전하지만, 값으로만 들어가므로 컬럼명이나 ORDER BY 대상에는 쓸 수 없다
    · 정렬은 허용 목록(명세상 latest만)으로 받고, 서버가 고정된 SQL 조각을 고른다
- [TC-D06-2] 공개 글 최신순 커서 목록이 데이터가 늘자 느려졌습니다. 인덱스를 어떻게 정하고 확인했나요?
    · 내 필터·정렬·커서·데이터 분포를 보고 만든 인덱스의 열 순서와 선택 이유, 버린 대안 1개를 설명한다. 특정 실행 계획을 측정 전에 보장하지 않는다
    · EXPLAIN의 type, key, rows, Extra(Using filesort 여부)를 인덱스 전후로 비교하고, EXPLAIN ANALYZE로 실제 읽은 행 수를 본다
    · 커서 페이징은 내가 정한 안정적 정렬의 마지막 위치 뒤부터 이어 읽어, offset처럼 앞쪽 행을 읽고 버리지 않는다
- [TC-D06-3] 같은 트랜잭션에서 JPA로 글 제목을 고친 직후 MyBatis로 목록을 읽었더니 옛 제목이 나왔습니다. 왜 그런가요?
    · JPA의 변경은 flush 전까지 영속성 컨텍스트에만 있고 DB에는 아직 UPDATE가 나가지 않았다
    · Hibernate의 자동 flush는 JPQL 실행 전에 일어나며, MyBatis가 JDBC로 직접 보내는 SQL은 Hibernate가 모르므로 flush를 일으키지 않는다
    · MyBatis 조회 전에 명시적으로 flush하고, 두 도구가 같은 트랜잭션(같은 커넥션)에 참여하는지 실험으로 확인한다
- [TC-D06-4] MyBatis 목록에서 글마다 태그를 <collection select="...">로 가져왔더니 쿼리가 글 수만큼 늘었습니다. 어떻게 고치나요?
    · 중첩 select는 부모 행마다 쿼리를 따로 실행하므로 글 20개면 태그 쿼리가 20번 나간다
    · JOIN 한 번으로 가져와 resultMap의 중첩 결과로 묶고, <id>를 선언해 같은 글의 행을 합친다
    · 다만 1:N JOIN 결과에 LIMIT을 걸면 글이 아니라 행 기준으로 잘리므로, 글에만 LIMIT을 거는 파생 테이블로 먼저 자르고 바깥에서 태그를 JOIN한다(글 ID 목록을 뽑은 뒤 IN으로 두 번 조회하는 것도 대안)

리뷰 초점
- 매퍼 XML에 `${}`로 사용자 입력이 들어가는 곳이 없는지
- 쓰기는 JPA, 목록·검색 읽기는 MyBatis로 경계가 지켜지는지
```
