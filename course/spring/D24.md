## 이 날 데이터 넣기

- D23 스키마를 복제한 별도 실험 DB에서 균등 200행 이상과 한 예약에 90%가 몰린 편향 200행 이상을 별도로 생성한다.
- 생성 SQL·seed·정렬·실제 행 수를 저장하고 각 실험 전 기준 상태로 되돌린다. practice·공유 DB에 적재하지 않는다.
- 실행 경로: 내 프로젝트의 src/test/java/D24FixtureTest.java에서 D23 스키마용 fixture loader를 작성한다. seed=24·예약 10개·회원 200개를 먼저 만들고 균등은 예약별 20행, 편향은 첫 예약 180행·나머지 9개에 20행을 분산한다. 생성 순번과 실제 FK 매핑을 저장하고 부모·대상 행 수를 단언한다. 실행은 ./gradlew test --tests D24FixtureTest이며 loader와 실행 로그를 함께 제출한다.
- 조회 두 구현을 같은 fixture에서 실행해 결과 집합·정렬을 먼저 대조한다. baseline.sql·with-index.sql에 동일한 SELECT와 동일 200행 INSERT를 저장하고 별도실험DB의 D24_PORT·D24_USER·D24_DB를 지정하고 mysql --host=127.0.0.1 --port="$D24_PORT" --user="$D24_USER" --password --database="$D24_DB" < baseline.sql로 실행한다. 각 실행 전 같은 dump로 복원하고 warm-up 1회·측정 3회·실행 순서를 기록한다. EXPLAIN ANALYZE 출력과 information_schema.TABLES의 DATA_LENGTH/INDEX_LENGTH는 추정 공간이며 실측 지연과 구분한다.

## 오늘의 SQL

<details class="sql-answer">
<summary>구현 예시 SQL · 직접 작성한 뒤 비교하기</summary>

아래는 비교용 SQL이다. 예약·대상·작업 모델은 내가 정한 물리 이름과 필터로 옮긴다. board-server의 설계 기준이다. 2단계에서는 같은 계열의 기존 스키마를 관찰한다. 내 물리 이름·키·정렬이 다르면 매핑해 비교한다. 아래 SQL은 실제 실행 결과가 아니며 예시 서버가 모든 불변식을 보장한다는 뜻도 아니다. 오류가 예상되는 문장은 하나씩 실행하고 실패 뒤 ROLLBACK을 별도로 보낸다.

**문항 1 구현 예시**

```sql
SELECT id,issued_at FROM member_coupon ORDER BY issued_at DESC,id DESC LIMIT 20;
```

**문항 2 구현 예시**

```sql
EXPLAIN ANALYZE SELECT id FROM member_coupon WHERE member_id=1 ORDER BY id DESC LIMIT 20;
```

</details>

### TC-D24-2

**질문** JOIN 때문에 지급 건수가 부풀지 않나요?

<details class="card-answer" data-card="TC-D24-2">
<summary>답에 들어가야 할 것</summary>

- 일대다 JOIN의 행 증폭과 지급 건수의 업무 집계 단위를 구분한다.
- 중복 대상·여러 지급 상태 fixture에서 식별 집합과 합계를 검증한다.
- 집계 위치/중복 제거 대안의 비용과 실제 SQL 출력을 제시한다.

</details>

### TC-D24-3

**질문** 어떤 분포에서 인덱스 선택을 바꾸겠나요?

<details class="card-answer" data-card="TC-D24-3">
<summary>답에 들어가야 할 것</summary>

- 선택도·편향·데이터 크기가 다른 두 분포를 말한다.
- 동일 요청의 실행 계획·실측 지연·읽은 행 수를 제시한다.
- 인덱스 쓰기/공간 비용을 포함한 변경 임계값과 일반화 한계를 말한다.

</details>

- 인덱스 전후 EXPLAIN 추정과 EXPLAIN ANALYZE 실측·동일 INSERT 부하를 기록한다. 읽기 개선만으로 채택하지 않고 쓰기·공간·변경 비용으로 선택한다.
- 실행하지 않은 항목은 확인 불가이며 예상값·추정·실측을 구분한다.

오늘은 별도 회의 역할극 없이 완료 조건·SQL·카드를 검증한다.

각 C 항목은 실제 테스트·SQL·로그·문서 경로와 줄을 근거로 통과/실패/확인 불가로 판정한다. 티켓 A/B는 원인 서술·수정 전 RED·수정 후 GREEN·반례·diff를 확인하고 미선택 티켓을 실패로 채점하지 마라. 미수행 대신 정한 새 조건은 조건과 새 실패 증거를 요구한다. 이미 새 조건도 통과하면 통과 사실을 인정하고 정상 코드를 약화하지 마라. 해당 일자의 요구 합의 단계(D16~D18은 D16, D36은 D35)로 돌아가 담당자/훈련 진행자와 미충족 새 계약을 합의하도록 하며, 미합의·미실행은 확인 불가로 남긴다. 기존 2단계 제외 규칙을 3단계 필수 A/B에 자동 적용하지 마라.
회의가 있으면 M1~M5 각각 0(없음)/1(부분)/2(근거·합의까지)로 채점한다. 각 항목 1점 이상 및 총 8/10 이상이어야 회의 통과다. 한 항목 0점이면 총점과 무관하게 재훈련한다. 먼저 발언을 받고 반론을 하나 제시한 뒤 수정 발언을 기록한다. 외운 답 선공개는 금지한다.
독립 수행이면 해법/힌트를 주지 말고 도움 횟수와 범위를 기록한다. 스스로 주입해 원인을 알고 있으면 비공개 장애 진단은 확인 불가다. 설명만으로 구현·진단을 통과시키지 마라.

출력: ① | C 항목 | 기대 | 실제 근거 | 결과 | ② SQL·불변식 ③ | 카드 | 빠진 줄 | 결과 | ④ 회의 점수·반론·바뀐 결정 ⑤ 도움·미실행·남은 약점
마지막 줄: 필수 N/M 통과 · SQL S/T · 카드 K/L · 회의(해당 시) Q/10 · 독립 수행(해당 시) 통과/실패/확인 불가. 연차 도달을 보증하지 않는다.
