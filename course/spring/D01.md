## ② Colima에서 MySQL 8.4를 띄우고 JPA 연결하기 (`compose.yaml`은 출발 자료의 파일 사용, `build.gradle`에 JPA·MySQL 의존성 추가, 스키마는 `src/main/resources/schema.sql`로 관리하고 Flyway는 쓰지 않는다, 테스트 DB는 Testcontainers `TestcontainersConfig`)

**이 순서에서 만들 층** DB · 테스트

<details class="step-hint" data-step="D01-2">

## ③ 프로파일을 local·prod로 나누고 비밀값은 자리표시자로만 두기 (datasource는 `application.yml`에서 `application-local.yml`로 옮긴다)

**이 순서에서 만들 층** 해당 없음 · 공통 설정·지원 코드

**만들 파일** (내 프로젝트 · 경로는 구현 예시 기준)

- `src/main/resources/application-local.yml`
- `src/main/resources/application-prod.yml`
- `src/main/java/com/example/board/config/ProdSecretsCheck.java`

**겪을 것** DB 비밀번호를 yml에 적어 커밋하면 파일에서 지워도 git 이력에 남으므로 yml에는 `${DB_PASSWORD}` 자리표시자만 둔다.

**완료 조건**

- `--spring.profiles.active=local` 기동 로그에 `The following 1 profile is active: "local"`
- `SERVER_PORT=8081`로 실행하면 yml의 `server.port`보다 환경 변수가 이긴다: `GET http://localhost:8081/actuator/health` → 200
- prod 프로파일은 `DB_PASSWORD` 환경 변수 없이 기동하면 실패한다
- `GET /actuator/env` → 404 (HTTP로는 `health`만 노출)

**명세** [`GET /actuator/health`](../spec-v2.md#4-엔드포인트)

<details class="step-hint" data-step="D01-3">
<summary>막히면</summary>

- Spring Boot 문서의 "Externalized Configuration" 우선순위 표에서 환경 변수와 `application.yml`의 순서를 확인한다.

```java
package com.example.board.common;

import java.io.IOException;
import java.util.UUID;
import java.util.regex.Pattern;

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;

import org.slf4j.MDC;
import org.springframework.core.Ordered;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class RequestIdFilter extends OncePerRequestFilter {

    public static final String HEADER = "X-Request-Id";
    public static final String MDC_KEY = "requestId";

    // 클라이언트가 보낸 값이 로그 줄을 깨지 않도록 안전한 문자만 받는다
    private static final Pattern SAFE = Pattern.compile("^[A-Za-z0-9_-]{1,64}$");

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain chain)
            throws ServletException, IOException {
        String id = request.getHeader(HEADER);
        if (id == null || !SAFE.matcher(id).matches()) {
            id = UUID.randomUUID().toString();
        }
        MDC.put(MDC_KEY, id);
        response.setHeader(HEADER, id);
        try {
            chain.doFilter(request, response);
        } finally {
            // 톰캣은 스레드를 재사용하므로 지우지 않으면 다음 요청 로그에 이전 ID가 남는다
            MDC.remove(MDC_KEY);
        }
    }
}
```

<summary>구현 예시 SQL · 직접 작성한 뒤 비교하기</summary>

**문항 2 구현 예시**

```sql
SHOW TABLES;
SELECT table_name, column_name, column_type, is_nullable FROM information_schema.columns WHERE table_schema = DATABASE() ORDER BY table_name, ordinal_position;

## 말하기 카드

하루가 끝나면 질문에 "문제 상황 → 원인 → 선택 → 결과" 순서로 소리 내어 답한 뒤, 접힌 "답에 들어가야 할 것"과 비교한다. 세 줄이 모두 나오면 통과다.

### TC-D01-1

**질문** `application.yml`의 `server.port`를 바꿨는데 서버가 예전 포트로 뜹니다. 어디부터 확인하나요?

<details class="card-answer" data-card="TC-D01-1">
<summary>답에 들어가야 할 것</summary>

- 커맨드라인 인자와 OS 환경 변수는 `application.yml`보다 우선하므로, 같은 키가 그쪽에 있으면 yml 수정은 반영되지 않는다
- 활성 프로파일의 설정(`application-local.yml` 또는 `on-profile` 문서)이 기본 문서의 같은 키를 덮어쓴다
- 값은 키 단위로 덮어써지므로 추측하지 않고, 로컬에서 연 `/actuator/env`의 출처 목록이나 기동 로그로 어느 출처가 이겼는지 확인한다

</details>

### TC-D01-2

**질문** prod 서버가 로컬 DB 주소로 떠 있었습니다. 원인으로 무엇을 의심하나요?

<details class="card-answer" data-card="TC-D01-2">
<summary>답에 들어가야 할 것</summary>

- 활성 프로파일을 지정하지 않으면 `default` 프로파일로 기동해 prod 문서가 적용되지 않는다
- 프로파일 전용 문서(`on-profile` 문서, `application-prod.yml`) 안에서는 `spring.profiles.active`를 지정할 수 없으므로, 활성화는 실행 인자나 환경 변수로 한다
- 기동 로그에 찍히는 활성 프로파일 줄로 어떤 프로파일이 켜졌는지 먼저 확인한다

</details>

### TC-D01-3

**질문** DB 비밀번호를 `application.yml`에 적어 커밋했습니다. 무엇이 문제고 어떻게 바꾸나요?

<details class="card-answer" data-card="TC-D01-3">
<summary>답에 들어가야 할 것</summary>

- 파일에서 지워도 git 이력에 평문이 남으므로, 이미 커밋된 비밀번호는 노출된 것으로 보고 교체한다
- Spring Boot에는 내장 프로퍼티 암호화가 없어서 yml에는 `${DB_PASSWORD}` 같은 자리표시자만 둔다
- 실제 값은 환경 변수(또는 `configtree:`로 마운트한 파일)로 주입한다. PG 비밀키도 같은 방식이다

**근거** spec-v2 §7

</details>

### TC-D01-4

**질문** 동시 요청 세 건의 로그가 섞여서 한 사용자 요청만 골라낼 수 없었습니다. 요청 ID 필터를 어떻게 만들었나요?

<details class="card-answer" data-card="TC-D01-4">
<summary>답에 들어가야 할 것</summary>

- 서블릿 필터가 요청 시작에서 요청 ID를 `MDC.put`하고, 로그 패턴에 그 키를 넣어 모든 줄에 찍는다
- `finally`에서 MDC를 지운다. 톰캣 스레드는 재사용되므로 지우지 않으면 다음 요청 로그에 이전 ID가 남을 수 있다
- MDC는 스레드 단위라 `@Async`나 별도 스레드풀로 넘어가면 전파되지 않으므로 `TaskDecorator`로 복사한다

</details>

### TC-D01-5

**질문** 헬스 체크(liveness)에 DB 연결 확인을 넣자는 제안을 받았습니다. 어떻게 답하나요?

<details class="card-answer" data-card="TC-D01-5">
<summary>답에 들어가야 할 것</summary>

- liveness에 DB 같은 외부 시스템을 넣으면 DB가 잠깐 끊겼을 때 모든 인스턴스가 재시작돼 장애가 커진다
- 외부 의존 상태는 readiness에서 다룰지 판단한다. 넣으면 그 시스템 장애 때 인스턴스가 트래픽에서 빠진다
- Boot는 기본으로 HTTP에 `health`만 노출하고, 명세도 `/actuator/health` 외의 actuator는 공개하지 않는다

**근거** spec-v2 §3

</details>

말하기 카드
- [TC-D01-1] application.yml의 server.port를 바꿨는데 서버가 예전 포트로 뜹니다. 어디부터 확인하나요?
    · 커맨드라인 인자와 OS 환경 변수는 application.yml보다 우선하므로, 같은 키가 그쪽에 있으면 yml 수정은 반영되지 않는다

    · 값은 키 단위로 덮어써지므로 추측하지 않고, 로컬에서 연 /actuator/env의 출처 목록이나 기동 로그로 어느 출처가 이겼는지 확인한다
- [TC-D01-2] prod 서버가 로컬 DB 주소로 떠 있었습니다. 원인으로 무엇을 의심하나요?
    · 활성 프로파일을 지정하지 않으면 default 프로파일로 기동해 prod 문서가 적용되지 않는다
    · 프로파일 전용 문서(on-profile 문서, application-prod.yml) 안에서는 spring.profiles.active를 지정할 수 없으므로, 활성화는 실행 인자나 환경 변수로 한다
    · 기동 로그에 찍히는 활성 프로파일 줄로 어떤 프로파일이 켜졌는지 먼저 확인한다
- [TC-D01-3] DB 비밀번호를 application.yml에 적어 커밋했습니다. 무엇이 문제고 어떻게 바꾸나요?
    · 파일에서 지워도 git 이력에 평문이 남으므로, 이미 커밋된 비밀번호는 노출된 것으로 보고 교체한다
    · Spring Boot에는 내장 프로퍼티 암호화가 없어서 yml에는 ${DB_PASSWORD} 같은 자리표시자만 둔다
    · 실제 값은 환경 변수(또는 configtree:로 마운트한 파일)로 주입한다. PG 비밀키도 같은 방식이다
- [TC-D01-4] 동시 요청 세 건의 로그가 섞여서 한 사용자 요청만 골라낼 수 없었습니다. 요청 ID 필터를 어떻게 만들었나요?
    · 서블릿 필터가 요청 시작에서 요청 ID를 MDC.put하고, 로그 패턴에 그 키를 넣어 모든 줄에 찍는다
    · finally에서 MDC를 지운다. 톰캣 스레드는 재사용되므로 지우지 않으면 다음 요청 로그에 이전 ID가 남을 수 있다
    · MDC는 스레드 단위라 @Async나 별도 스레드풀로 넘어가면 전파되지 않으므로 TaskDecorator로 복사한다
- [TC-D01-5] 헬스 체크(liveness)에 DB 연결 확인을 넣자는 제안을 받았습니다. 어떻게 답하나요?
    · liveness에 DB 같은 외부 시스템을 넣으면 DB가 잠깐 끊겼을 때 모든 인스턴스가 재시작돼 장애가 커진다
    · 외부 의존 상태는 readiness에서 다룰지 판단한다. 넣으면 그 시스템 장애 때 인스턴스가 트래픽에서 빠진다
    · Boot는 기본으로 HTTP에 health만 노출하고, 명세도 /actuator/health 외의 actuator는 공개하지 않는다

리뷰 초점
- `application.yml`·`application-prod.yml`과 git 이력에 실제 비밀번호 문자열이 없는지
- 패키지가 `common`·`config`처럼 역할별 도메인형으로 시작하는지(`controller`·`service` 계층형 패키지로 시작하지 않았는지)

아래 형식으로만 답해라.
① 채점표 — | 항목 | 기대 | 실제 | 결과 |  (결과: 통과 / 실패 / 확인 불가)
② 잘한 점
③ 부족한 점과 이유 — 실패한 C 항목부터
④ 내일 전에 고칠 것 — 우선순위순, 3개 이내
⑤ 말하기 카드 — | 카드 | 빠진 줄 | 결과 |
마지막 줄: `결과: 필수 N/M 통과 · 말하기 카드 K/L 통과` (필수 = C 항목, R은 참고)
```
