# D14. 고도화와 모의 장애 훈련

> 2단계 · 어수선한 서버 넘겨받기 · 오늘의 Java [J14](../java/J14.md) · 순서 6개 · 말하기 카드 4장

**2단계 티켓 규칙** 필수는 B01·B02·B03·B04 4건이다. 선택 1건은 D11을 시작할 때 Security 후보(B12·B13·B14)나 Redis 후보(B15·B16)에서 골라 끝까지 처리한다. 고도화 E01과 D14 ⑥ 모의 장애 훈련은 모두 한다. 연습 티켓은 나머지 7건(B05·B06·B07·B08·B09·B10·B11)이다. 연습 티켓과 고르지 않은 선택 후보는 했으면 채점 프롬프트에 알려 채점받고, 하지 않았으면 채점에서 빠진다. 필수·고른 선택·E01·훈련을 하지 않으면 그 항목은 실패다.

**오늘** ①·② B12·B13은 Security 후보, ③·④ B15·B16은 Redis 후보다. 고른 선택 티켓이 여기 있으면 그것부터 한다. ⑤ 고도화 E01과 ⑥ 모의 장애 훈련은 모두 한다. 훈련은 B16을 고쳤으면 고친 서버로, 고치지 않았으면 지금 서버로 하며 합격 기준이 다르다([모의 장애 훈련](../tickets/drill.md)).

## 오늘의 SQL

messy-server DB(13311)의 실제 스키마와 티켓 재현 자료를 쓴다. 1단계 CSV는 적재하지 않는다. 읽기 전용 진단 SQL·관찰 시각·실제 결과만 남긴다. 관찰 결과가 0행이어도 원인이나 정상 여부를 단정하지 않는다. 예시 SQL은 기존 서버 설계 기준이다.

<ol class="sql-questions">
<li><p>관찰 시각별로 공개 글의 DB 목록을 조회해 API에서 받은 식별 집합과 대조한다.</p><p><strong>확인할 성질</strong> 쿼리·API 응답·양쪽 시각을 같이 남긴다. 차이가 있어도 해법을 추측해 결론으로 쓰지 않는다.</p></li>
<li><p>요청 관찰 구간 전후 DB 문장 실행 횟수 누적값을 읽고 차이를 계산한다.</p><p><strong>확인할 성질</strong> 같은 digest의 누적값 차이와 구간을 기록한다. 다른 요청도 함께 섞일 수 있으므로 전체 증가량을 한 요청의 값으로 단정하지 않는다.</p></li>
</ol>

<details class="sql-answer">
<summary>구현 예시 SQL · 직접 작성한 뒤 비교하기</summary>

board-server의 설계 기준이다. 2단계에서는 같은 계열의 기존 스키마를 관찰한다. 내 물리 이름·키·정렬이 다르면 매핑해 비교한다. 아래 SQL은 실제 실행 결과가 아니며 예시 서버가 모든 불변식을 보장한다는 뜻도 아니다. 오류가 예상되는 문장은 하나씩 실행하고 실패 뒤 ROLLBACK을 별도로 보낸다.

**문항 1 구현 예시**


## 말하기 카드

하루가 끝나면 질문에 "문제 상황 → 원인 → 선택 → 결과" 순서로 소리 내어 답한 뒤, 접힌 "답에 들어가야 할 것"과 비교한다. 세 줄이 모두 나오면 통과다.

### TC-D14-1

**질문** (B12) "새 프론트 도메인에서만 호출이 실패한다." 서버 로그에 에러가 없는데 무엇을 봤나요?

<details class="card-answer" data-card="TC-D14-1">
<summary>답에 들어가야 할 것</summary>

- 새 출처가 CORS 허용 목록에 없으면 preflight가 거부되고, 브라우저는 실제 요청을 서버로 보내지 않는다
- 새 출처가 MVC `addCorsMappings`에만 있고 Security가 쓰는 `CorsConfigurationSource`에는 없어, 필터 체인 안의 `CorsFilter`가 preflight를 403(`Invalid CORS request`)으로 끝내 MVC 매핑까지 오지 못했다
- 브라우저 개발자 도구 Network 탭에서 `OPTIONS` 요청의 상태 코드와 `Access-Control-Allow-Origin` 응답 헤더를 먼저 확인하고, 허용 출처는 Security가 쓰는 `CorsConfigurationSource` 한 곳에 명세의 출처 목록대로 모은다(와일드카드로 열지 않는다)

**근거** spec-v2 §3

</details>

### TC-D14-2

**질문** (B13) "PG 결제 완료 콜백이 전부 401." 원인과 수정은?

<details class="card-answer" data-card="TC-D14-2">
<summary>답에 들어가야 할 것</summary>

- PG 콜백에는 JWT가 없는데 `/api/pg/callbacks`가 인증 필요 규칙에 걸려 진입점이 401을 냈다
- Security 로그(`logging.level.org.springframework.security=TRACE`)로 어느 필터·규칙에서 막혔는지 확인한다. 규칙 판정(`Checking authorization`) 줄은 TRACE에서 보인다
- 콜백 경로를 넓은 규칙보다 앞에서 `permitAll`로 열고, 인증 대신 `X-PG-Signature` 서명 검증으로 보호한다

**근거** spec-v2 §7

</details>

### TC-D14-3

**질문** (B15) "숨긴 글이 인기글에 1분간 계속 보인다." 캐시를 지웠는데도 왜 보였나요?

<details class="card-answer" data-card="TC-D14-3">
<summary>답에 들어가야 할 것</summary>

- 숨김 트랜잭션이 커밋되기 전에 캐시를 지웠다
- 그 사이 들어온 인기글 조회가 캐시 미스를 보고, 아직 커밋 전이라 숨기기 전 값을 DB에서 읽어 캐시에 다시 넣었다
- 그 값이 TTL(60초) 동안 남았다. 캐시 삭제·캐시 적재·커밋 시각을 로그로 찍어 순서를 증명하고, 삭제를 커밋 후(`AFTER_COMMIT`)로 옮긴다

**근거** spec-v2 §8

</details>

### TC-D14-4

**질문** (B16) "Redis 점검 시간에 글쓰기까지 멈췄다." 캐시 서버 점검이 왜 글쓰기를 막았나요?

<details class="card-answer" data-card="TC-D14-4">
<summary>답에 들어가야 할 것</summary>

- Redis 명령 타임아웃을 설정하지 않아, 요청 스레드가 Lettuce 기본값(60초)까지 Redis 응답을 기다렸다
- 폴백(`RedisGuard`)이 연결 실패(`RedisConnectionFailureException`)만 잡아, 끊긴 연결의 명령 거절·명령 타임아웃 예외가 인기글 조회까지 올라가 500이 됐다
- 스레드 덤프에서 Redis 응답을 기다리는 요청 스레드를 확인하고, 타임아웃을 500ms로 두며 캐시 실패는 로그만 남기고 진행한다

**근거** spec-v2 §8

</details>

## AI 채점 프롬프트

오늘 티켓을 다 처리했으면 `messy-server`를 띄운 채로 아래 프롬프트를 복사해 `messy-server` 폴더에서 연 Codex 또는 Claude Code에 붙여 넣는다. 에이전트가 완료 조건·함정·티켓 3점 세트(원인 서술·재현 테스트·수정)·말하기 카드로 채점표를 준다. 코드는 고치지 않는다.

```text
[javaExperience 일자 채점] D14. 고도화와 모의 장애 훈련
레포 경로: 내 javaExperience 저장소의 `messy-server` 폴더(이 프롬프트를 붙여 넣은 에이전트를 그 폴더에서 연다)
서버 주소: http://localhost:8080

너는 Java·Spring 온보딩 과정 v2로 백엔드를 배우는 사람의 리뷰어다. 학습자는 2단계에서 다른 사람이 짠 서버(`messy-server`)를 넘겨받아 티켓을 처리하고 있고, 오늘은 D14다. 티켓 하나는 원인 서술 + 재현 테스트 + 수정, 3점 세트로 평가한다.
0. 채점을 시작하기 전에 학습자에게 두 가지를 묻고 답 첫 줄에 적어라. (1) 2단계에서 고른 선택 티켓 1건: Security 후보(B12·B13·B14)나 Redis 후보(B15·B16) 중 하나다. (2) 그 밖에 오늘 처리한 티켓(연습 티켓 B05~B11이나 고르지 않은 선택 후보, 없으면 "없음"). 꼭 채점하는 대상은 `B01~B04(필수) + 학습자가 고른 선택 티켓 1건 + E01 + 모의 장애 훈련`이다. 필수 티켓 B01·B02·B03·B04 4건과 D14의 고도화 E01, 모의 장애 훈련은 모두가 한다. (2)의 티켓은 했다고 답한 것만 채점한다.
지킬 것: 파일은 절대 수정하지 마라(테스트 코드·설정·`tickets/` 폴더 포함). DB는 조회만 한다(SELECT·SHOW·EXPLAIN). 서버를 대신 띄우거나 끄지 말고, 장애를 넣는 스크립트(`tickets/*/repro.sh`, `drills/*.sh`)도 대신 실행하지 마라. 정답을 먼저 말하지 말고 되묻는 질문과 방향으로 알려 줘라.

1. 서버 주소의 `GET /actuator/health`로 응답 가능 여부를 확인해라. 꺼져 있으면 `./gradlew bootRun --args='--spring.profiles.active=local'`로 띄우라고만 알려 주고 멈춰라. 티켓 페이지의 "환경과 재현"이 다른 프로파일이나 인자를 쓰는 항목은 그 명령으로 띄워 달라고 한다.
2. 아래 "채점 기준"과 "티켓 3점 세트"가 통과/실패의 유일한 기준이다. 기준에 적히지 않은 것으로 실패 처리하지 말고, 다른 날의 기준은 보지 마라.
   - "제외"는 C 항목 괄호에 `선택`이나 `연습`이 붙은 티켓(이 날 제외할 수 있는 티켓: B12·B13·B15·B16)이 0번의 (1)·(2) 어디에도 없을 때만 쓴다. 그 항목은 "제외"로 적고 필수 분모와 실패 수에서 모두 뺀다. 훈련의 B16 표시 항목도 이 규칙을 따른다. 괄호에 `필수`(B01~B04)나 `고도화`(E01)가 붙은 항목과 괄호에 티켓이 적히지 않은 항목(모의 장애 훈련 포함)은 학습자가 무엇을 골랐든 제외하지 않고 분모에 넣는다.
   - "(기록으로 확인)" 항목은 지금 서버·지금 코드로 판정하지 않는다. 고치기 전의 증상·진단 과정이거나, 네 권한 밖의 조건(다른 프로파일로 띄운 서버, 장애 주입, DDL 실행)에서 본 결과다. 항목에 적힌 기록(예: 고친 뒤 실행한 재현 스크립트 출력)을, 적힌 것이 따로 없으면 학습자가 보관한 재현 스크립트 출력·실패한 테스트 로그·수정 전 커밋(`git show <커밋>`)·기록 문서를 붙여 달라고 해서 확인한다. 표시가 붙지 않은 C 항목은 고친 뒤의 조건이므로 지금 서버와 지금 테스트로 확인한다. 같은 요청에 수정 전 결과와 수정 후 결과가 둘 다 기준에 있는 것은 이 구분 때문이다.
3. 표시가 붙지 않은 [C] 항목: HTTP 요청은 서버 주소로 직접 보내 상태 코드·응답 헤더·본문을 기대값과 비교한다. 테스트 이름이 적힌 항목은 `./gradlew test --tests '<테스트 클래스 이름>'`으로 실행해 통과 여부를 본다. 로그·메트릭·스레드 덤프·EXPLAIN처럼 진단 중에 본 것을 묻는 항목은 학습자에게 그 출력이나 기록을 붙여 달라고 해서 본다. DB 확인이 필요하면 `docker compose exec -T mysql mysql -uboard -pboard board -e "<SELECT 문>"`으로 조회만 한다.
4. [R] 항목: 그 순서의 티켓이 모두 "제외"면 R도 "제외"로 적는다. 나머지는 관련 코드를 찾아 읽고 그 함정을 피했는지 판단해라. 지적할 때는 `파일:줄`을 붙여라.
5. 티켓 3점 세트: 티켓마다 대조 자료(`tickets/<티켓>/answer/`의 `fix.patch`와 확인 테스트, 티켓 페이지의 "원인과 정답" 절)를 먼저 읽어 실제 원인을 파악하되, 그 내용을 학습자에게 보여 주거나 인용하지 마라.
   - 원인 서술: 학습자가 가리키는 리뷰 메모·커밋 메시지·PR 설명이 증상이 아니라 그 증상을 만든 코드·설정을 지목하고, 근거(로그·메트릭·스레드 덤프·EXPLAIN·테스트 결과)를 붙였는가. 티켓 원문에 섞인 단서를 확인 없이 원인으로 적었으면 실패다. 고도화(E) 티켓은 이 칸에서 수정 전 측정(무엇을 몇 번 세었나)을 본다.
   - 재현 테스트: 학습자의 테스트가 고치기 전 코드에서 실패하고 고친 뒤 통과하는가. 지금 통과는 직접 실행해 보고, 고치기 전 실패는 학습자에게 실패 출력이나 수정 전 커밋을 보여 달라고 해 확인한다. 고치기 전에도 통과하는 테스트는 재현 테스트가 아니다.
   - 수정: `git diff` 또는 `git log -p`의 수정이 원인을 없앴는가. 숫자(시간·크기·횟수)만 바꿔 증상을 줄인 수정은 실패다. 대조 자료와 방식이 달라도 원인을 없앴고 재현 테스트가 그것을 증명하면 통과다.
   - 0번의 (1)·(2)에 포함되지 않은 선택·연습 티켓만 "제외"로 적고 세지 않는다. 필수 티켓 B01~B04, 고른 선택 티켓, E01을 하지 않았으면 제외가 아니라 실패다.
6. 말하기 카드: 학습자에게 카드 질문마다 답을 말하거나 적어 달라고 해라. 질문 앞 괄호의 티켓(예: `(B06)`)이 2번 규칙으로 "제외"인 티켓이면 그 카드도 "제외"로 적고 K/L에서 뺀다. 대상 카드가 하나도 없으면 "대상 없음(0/0)"으로 적는다. 카드마다 "답에 들어가야 할 것" 세 줄은 `../course/talk-cards.md`의 같은 ID 카드에서 읽고 학습자에게 미리 보여 주지 마라. 세 줄이 모두 나오면 통과다. 빠진 줄은 정답 문장을 먼저 말하지 말고 되묻는 질문으로 끌어내라.
7. 리뷰 초점은 채점표에 넣지 말고 ③·④에 적어라.

  - [R5] 함정을 피했는지 코드로 확인: 재적재를 락으로 막으면서 락 대기에 상한을 두지 않으면 Redis가 느릴 때 모든 요청이 락 앞에서 멈춘다.
⑥ 모의 장애 훈련: 장애 주입 스크립트 → 대응 → 회고 문서
  - [C6-1] (기록으로 확인) 지연 3초와 연결 끊김을 한 번씩 주입한 injections.log와 복구 결과를 남긴다
  - [C6-2] (기록으로 확인) 로그·메트릭·스레드 덤프(evidence-*/)와 probe-*.log로 장애를 알아차린 시각과 원인을 지목한 시각을 기록한다
  - [C6-3] (B16 선택 · 기록으로 확인) B16을 고친 서버: 주입 중에도 POST /api/posts → 201, GET /api/posts/popular → 200, 둘 다 1초 이내 (probe-*.log와 injections.log의 같은 주입 구간을 보여 준다)
  - [C6-4] (기록으로 확인) 회고 문서: 타임라인, 원인(스레드 덤프·로그 근거), 조치, 재발 방지. 주입 중 응답 코드·시간은 probe-*.log에서 옮긴다
  - [R6] 함정을 피했는지 코드로 확인: 증상이 보이자마자 재시작부터 하면 스레드 덤프 같은 증거가 사라져 원인을 지목할 수 없다.
```
