#오늘의 SQL

messy-server DB(13311)의 실제 스키마와 티켓 재현 자료를 쓴다. 1단계 seed.sql·bulk.sql은 적재하지 않는다. 읽기 전용 진단 SQL·관찰 시각·실제 결과만 남긴다. 관찰 결과가 0행이어도 원인이나 정상 여부를 단정하지 않는다. 예시 SQL은 기존 서버 설계 기준이다.

  1. 재현 중 DB의 대기 관계와 최근 엔진 진단 기록을 조회한다.

    확인할 성질 관찰한 식별 값·시각·출력을 그대로 저장한다. 행이 없으면 그 사실을 적고 원인으로 단정하지 않는다.

  2. 주문 요청별 데이터 건수와 회원별 잔액·이력 합을 대조한다.

    확인할 성질 중복 또는 차이의 유무를 SQL 결과로 남긴다. 결과를 맞추려고 데이터를 수정하지 않는다.

구현 예시 SQL · 직접 작성한 뒤 비교하기

board-server의 설계 기준이다. 2단계에서는 같은 계열의 기존 스키마를 관찰한다. 내 물리 이름·키·정렬이 다르면 매핑해 비교한다. 아래 SQL은 실제 실행 결과가 아니며 예시 서버가 모든 불변식을 보장한다는 뜻도 아니다. 오류가 예상되는 문장은 하나씩 실행하고 실패 뒤 ROLLBACK을 별도로 보낸다.

#말하기 카드

하루가 끝나면 질문에 "문제 상황 → 원인 → 선택 → 결과" 순서로 소리 내어 답한 뒤, 접힌 "답에 들어가야 할 것"과 비교한다. 세 줄이 모두 나오면 통과다.

⑤ 과제 · B06를 설명하는 카드

#TC-D13-1

질문 (D13 ⑤ · B06) "컬럼 하나 추가했더니 상점 전체가 멈췄다." ALTER 한 줄이 왜 서비스를 멈췄나요?

답에 들어가야 할 것
  • 커밋하지 않은 긴 트랜잭션이 그 테이블의 메타데이터 락(MDL)을 쥐고 있어, ALTER가 MDL을 얻지 못하고 기다렸다
  • 대기 중인 ALTER 뒤로 같은 테이블의 일반 쿼리까지 줄줄이 막혀 상점 전체가 멈췄다
  • SHOW PROCESSLIST의 Waiting for table metadata lock과 information_schema.innodb_trx로 오래된 트랜잭션을 찾고, DDL 세션에는 짧은 lock_wait_timeout을 걸어 무한 대기를 막는다

② 과제 · B07를 설명하는 카드

#TC-D13-2

질문 (D13 ② · B07) "선착순 쿠폰을 동시에 받을 때 가끔 실패한다." 실패 원인이 무엇이었나요?

답에 들어가야 할 것
  • REPEATABLE READ에서 SELECT ... FOR UPDATE로 없는 행을 확인하면, 결과가 없어도 그 구간에 gap lock이 걸린다
  • gap lock끼리는 충돌하지 않아 두 트랜잭션이 같은 구간을 잡는다. A는 쿠폰 행 락을 쥔 채 발급 행 INSERT(insert intention)가 B의 gap lock에 막히고, B는 A가 쥔 쿠폰 행 락을 기다려 순환 대기(데드락)가 된다
  • SHOW ENGINE INNODB STATUS의 LATEST DETECTED DEADLOCK에서 두 트랜잭션의 락을 읽고, 중복 확인용 FOR UPDATE를 빼고 UNIQUE 제약과 중복 키 처리로 바꾼다

③ 과제 · B09를 설명하는 카드

#TC-D13-3

질문 (D13 ③ · B09) "자정 전후 출석 포인트가 두 번 쌓인다." 원인과 재현 방법은?

답에 들어가야 할 것
  • 출석 날짜를 LocalDate.now(clock)으로 구했는데 주입된 시계가 Clock.systemUTC()라 날짜가 UTC 기준으로 잘렸다. KST 08:59:59와 09:00:00(UTC 자정)이 다른 날이 되어 같은 KST 날짜에 두 번 적립됐다
  • 반대로 KST 23:59:59와 다음 날 00:00:00은 UTC로 같은 날이라 다음 날 첫 출석이 거절됐다. (회원, 날짜) UNIQUE는 같은 날짜 값의 중복만 막으므로 날짜 값 자체가 틀린 것은 막지 못한다
  • 업무 기준 시간대를 코드에 명시하고(LocalDate.ofInstant(clock.instant(), ZoneId.of("Asia/Seoul"))), 영역은 UTC 그대로 시각만 바꾸는 가변 시계로 KST 08:59:59/09:00:00과 23:59:59/00:00:00을 고정한 테스트를 쓴다

④ 과제 · B10를 설명하는 카드

#TC-D13-4

질문 (D13 ④ · B10) "포인트 충전이 가끔 두 번 된다." 원인이 무엇이었나요?

답에 들어가야 할 것
  • PG 응답 타임아웃 뒤 재시도가 새 멱등 키(UUID.randomUUID())로 새 승인 요청을 보냈고, PG는 응답만 늦었을 뿐 첫 요청도 이미 승인했다
  • 새 키 = 새 pg_payment 행이라 행마다 "한 번만 적립"은 지켜져도 두 행이 각각 적립됐다. idempotency_key UNIQUE는 같은 키만 막으므로 새로 만든 키는 막지 못한다
  • 응답 타임아웃은 다시 보내지 않고 결과 불명(UNKNOWN)으로 남겨 콜백·재처리(reconcile)로 확정한다(다시 보내야 하면 같은 키로). WireMock 시나리오로 첫 응답만 늦춰 "PG가 받은 서로 다른 키 1개, 충전 원장 1건"을 테스트로 고정한다
