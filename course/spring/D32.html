#오늘의 SQL

내 프로젝트의 disposable 실습 DB를 쓴다. D23에서 정한 예약·대상·지급 상태의 물리 이름과 필터로 아래 예시를 반드시 매핑한다. 예시의 member_coupon은 1단계 비교 모델이며 새 예약 테이블의 구현 예시가 아니다. practice·원본 서버 DB는 수정하지 않는다.

  1. 예약별 고정 대상의 성공·실패·대기 수를 대사한다.

    확인할 성질 전체=성공+실패+대기가 예약마다 성립하고, 상태별 건수와 실제 지급 건수를 나누어 기록한다. 성공 2·실패 1·대기 2 fixture를 확인한다.

  2. 성공 항목과 실제 지급을 양방향으로 대사하고 중복 지급을 찾는다.

    확인할 성질 SUCCESS인데 지급이 없거나 지급은 있는데 고정 대상의 SUCCESS가 아닌 행은 모두 조사한다. 실패·대기는 합의된 미지급 상태로 남겨 재처리 시각과 시도 횟수를 별도 확인한다.

구현 예시 SQL · 직접 작성한 뒤 비교하기

아래는 비교용 SQL이다. 예약·대상·작업 모델은 내가 정한 물리 이름과 필터로 옮긴다. board-server의 설계 기준이다. 2단계에서는 같은 계열의 기존 스키마를 관찰한다. 내 물리 이름·키·정렬이 다르면 매핑해 비교한다. 아래 SQL은 실제 실행 결과가 아니며 예시 서버가 모든 불변식을 보장한다는 뜻도 아니다. 오류가 예상되는 문장은 하나씩 실행하고 실패 뒤 ROLLBACK을 별도로 보낸다.

문항 1 구현 예시

SELECT c.id AS campaign_id,COUNT(t.id) AS total,COALESCE(SUM(t.state='SUCCESS'),0) AS success,COALESCE(SUM(t.state='FAILED'),0) AS failed,COALESCE(SUM(t.state='PENDING'),0) AS pending FROM campaign c LEFT JOIN target t ON t.campaign_id=c.id GROUP BY c.id ORDER BY c.id;

문항 2 구현 예시

SELECT t.campaign_id,t.member_id,t.state,i.id AS issuance_id FROM target t LEFT JOIN issuance i ON i.campaign_id=t.campaign_id AND i.member_id=t.member_id WHERE t.state='SUCCESS' AND i.id IS NULL UNION ALL SELECT i.campaign_id,i.member_id,COALESCE(t.state,'NO_TARGET'),i.id FROM issuance i LEFT JOIN target t ON t.campaign_id=i.campaign_id AND t.member_id=i.member_id WHERE t.id IS NULL OR t.state<>'SUCCESS';
SELECT campaign_id,member_id,COUNT(*) FROM issuance GROUP BY campaign_id,member_id HAVING COUNT(*)>1;

#TC-D32-2

질문 체크포인트보다 지급 행이 먼저 남으면?

답에 들어가야 할 것
  • 지급 행 commit 뒤 checkpoint가 남지 않으면 재시작이 같은 구간을 다시 읽을 수 있다.
  • 같은 트랜잭션 경계 또는 업무 키 중복 방지 대안을 비교한다.
  • 당일 한 chunk의 지급 commit·checkpoint 전후 결과를 제시한다. 실제 중단·재시작과 누락/중복 실증은 D33에서 평가한다.

#TC-D32-3

질문 외부 발송에 정확히 한 번을 약속할 수 있나요?

답에 들어가야 할 것
  • DB commit과 외부 발송은 하나의 원자 트랜잭션이 아닐 수 있다.
  • 응답 유실·재시도 중복에 대한 멱등 키/발송 기록/보상 대안 비용을 말한다.
  • 외부 발송 선택 시 실패 경계의 실제 실험을 제시한다. 미선택 시 실패 경계·대안 설명으로 충족하며 정확히 한 번이라고 보장하지 못하는 범위를 말한다.

리뷰 초점
- 중복 실행 키·작업 소유권·재시도 횟수/시각·영구 실패·취소 시점을 설계한다. 외부 발송을 붙이면 정확히 한 번을 약속하지 않고 수신 측 멱등키를 정한다.
- 지급 행과 항목 완료의 commit 경계를 정해 중복 요청에도 1인 1매를 보장한다. 오늘은 단일 프로세스 한 chunk까지만 한다.
- 실행하지 않은 항목은 확인 불가이며 예상값·추정·실측을 구분한다.

오늘은 별도 회의 역할극 없이 완료 조건·SQL·카드를 검증한다.

각 C 항목은 실제 테스트·SQL·로그·문서 경로와 줄을 근거로 통과/실패/확인 불가로 판정한다. 티켓 A/B는 원인 서술·수정 전 RED·수정 후 GREEN·반례·diff를 확인하고 미선택 티켓을 실패로 채점하지 마라. 미수행 대신 정한 새 조건은 조건과 새 실패 증거를 요구한다. 이미 새 조건도 통과하면 통과 사실을 인정하고 정상 코드를 약화하지 마라. 해당 일자의 요구 합의 단계(D16~D18은 D16, D36은 D35)로 돌아가 담당자/훈련 진행자와 미충족 새 계약을 합의하도록 하며, 미합의·미실행은 확인 불가로 남긴다. 기존 2단계 제외 규칙을 3단계 필수 A/B에 자동 적용하지 마라.
회의가 있으면 M1~M5 각각 0(없음)/1(부분)/2(근거·합의까지)로 채점한다. 각 항목 1점 이상 및 총 8/10 이상이어야 회의 통과다. 한 항목 0점이면 총점과 무관하게 재훈련한다. 먼저 발언을 받고 반론을 하나 제시한 뒤 수정 발언을 기록한다. 외운 답 선공개는 금지한다.
독립 수행이면 해법/힌트를 주지 말고 도움 횟수와 범위를 기록한다. 스스로 주입해 원인을 알고 있으면 비공개 장애 진단은 확인 불가다. 설명만으로 구현·진단을 통과시키지 마라.
