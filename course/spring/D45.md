## 오늘의 SQL

내 프로젝트의 disposable 실습 DB를 쓴다. D23에서 정한 예약·대상·지급 상태의 물리 이름과 필터로 아래 예시를 반드시 매핑한다. 예시의 member_coupon은 1단계 비교 모델이며 새 예약 테이블의 정답이 아니다. practice·원본 서버 DB는 수정하지 않는다.

<ol class="sql-questions">
<li><p>복구 후 고정 대상 대비 지급 중복·누락·상태 불일치를 대사한다.</p><p><strong>확인할 성질</strong> 예약별 전체=성공+실패+대기를 확인한다. 중복 0, SUCCESS 미지급 0, 지급됐지만 SUCCESS가 아닌 행 0을 각각 확인한다. FAILED/PENDING 미지급은 누락으로 숨기지 말고 후속 처리 상태로 남긴다.</p></li>
<li><p>복구 전후 항목의 재시도·대기·영구 실패 상태를 확인한다.</p><p><strong>확인할 성질</strong> FAILED/PENDING 행의 attempts·next_retry_at과 합의된 영구 실패 표시를 기록하고 전후 식별 집합을 비교한다. DB 세션 목록을 작업 상태로 대체하지 않는다.</p></li>
</ol>

<details class="sql-answer">
<summary>구현 예시 SQL · 직접 작성한 뒤 비교하기</summary>

아래는 비교용 SQL이다. 예약·대상·작업 모델은 내가 정한 물리 이름과 필터로 옮긴다. board-server의 설계 기준이다. 2단계에서는 같은 계열의 기존 스키마를 관찰한다. 내 물리 이름·키·정렬이 다르면 매핑해 비교한다. 아래 SQL은 실제 실행 결과가 아니며 예시 서버가 모든 불변식을 보장한다는 뜻도 아니다. 오류가 예상되는 문장은 하나씩 실행하고 실패 뒤 ROLLBACK을 별도로 보낸다.

**문항 1 구현 예시**

```sql
SELECT c.id,COUNT(t.id) AS total,COALESCE(SUM(t.state='SUCCESS'),0) AS success,COALESCE(SUM(t.state='FAILED'),0) AS failed,COALESCE(SUM(t.state='PENDING'),0) AS pending FROM campaign c LEFT JOIN target t ON t.campaign_id=c.id GROUP BY c.id;
SELECT campaign_id,member_id,COUNT(*) FROM issuance GROUP BY campaign_id,member_id HAVING COUNT(*)>1;
SELECT t.campaign_id,t.member_id,t.state,i.id AS issuance_id FROM target t LEFT JOIN issuance i ON i.campaign_id=t.campaign_id AND i.member_id=t.member_id WHERE (t.state='SUCCESS' AND i.id IS NULL) OR (t.state<>'SUCCESS' AND i.id IS NOT NULL) UNION ALL SELECT i.campaign_id,i.member_id,'NO_TARGET',i.id FROM issuance i LEFT JOIN target t ON t.campaign_id=i.campaign_id AND t.member_id=i.member_id WHERE t.id IS NULL;
```

**문항 2 구현 예시**

```sql
SELECT t.campaign_id,t.member_id,t.state,t.attempts,t.next_retry_at,i.id AS issuance_id FROM target t LEFT JOIN issuance i ON i.campaign_id=t.campaign_id AND i.member_id=t.member_id WHERE t.state IN ('FAILED','PENDING') ORDER BY t.campaign_id,t.member_id;
```

- 실행하지 않은 항목은 확인 불가이며 예상값·추정·실측을 구분한다.

독립 수행 평가: 해법·힌트를 먼저 제공하지 않는다. 도움 횟수와 범위·시간·미실행을 기록하고 역량별 판정한다.

각 C 항목은 실제 테스트·SQL·로그·문서 경로와 줄을 근거로 통과/실패/확인 불가로 판정한다. 티켓 A/B는 원인 서술·수정 전 RED·수정 후 GREEN·반례·diff를 확인하고 미선택 티켓을 실패로 채점하지 마라. 미수행 대신 정한 새 조건은 조건과 새 실패 증거를 요구한다. 이미 새 조건도 통과하면 통과 사실을 인정하고 정상 코드를 약화하지 마라. 해당 일자의 요구 합의 단계(D16~D18은 D16, D36은 D35)로 돌아가 담당자/훈련 진행자와 미충족 새 계약을 합의하도록 하며, 미합의·미실행은 확인 불가로 남긴다. 기존 2단계 제외 규칙을 3단계 필수 A/B에 자동 적용하지 마라.
회의가 있으면 M1~M5 각각 0(없음)/1(부분)/2(근거·합의까지)로 채점한다. 각 항목 1점 이상 및 총 8/10 이상이어야 회의 통과다. 한 항목 0점이면 총점과 무관하게 재훈련한다. 먼저 발언을 받고 반론을 하나 제시한 뒤 수정 발언을 기록한다. 외운 답 선공개는 금지한다.
독립 수행이면 해법/힌트를 주지 말고 도움 횟수와 범위를 기록한다. 스스로 주입해 원인을 알고 있으면 비공개 장애 진단은 확인 불가다. 설명만으로 구현·진단을 통과시키지 마라.
