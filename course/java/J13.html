옮기는 순서(한 단계마다 특성화_ 테스트 4개가 초록인지 본다):

  1. RatePolicy를 채운다. supports는 "RATE".equals(coupon.type())이고, discount는 RATE 분기의 몸통이다.

  4. discount의 if-else를 "목록에서 supports가 참인 첫 정책에 맡기고, 없으면 0"으로 바꾼다.

#상황

쿠폰 종류가 늘면 할인 계산 메서드에 if-else가 하나씩 붙는다. 계산 규칙을 객체로 나누면 규칙마다 따로 테스트하고 바꿔 끼울 수 있다. D13 티켓과 실제 서버의 구현 비교는 티켓을 마친 뒤 아래 접기에서 읽는다. 오늘은 Spring 없이 종류별 if-else로 된 할인 계산을 DiscountPolicy 구현 클래스로 옮긴다. 할인액은 한 원도 바뀌면 안 된다. J11·J12처럼 특성화 테스트가 이것을 지킨다.

i 가이드읽고 이해하기

#빠른 연상

if-else 사슬 전략(DiscountPolicy 구현)
종류별 규칙이 사는 곳 한 메서드 안의 분기 종류마다 클래스 하나(RatePolicy …)
종류를 하나 더하면 계산 메서드를 열어 else if를 끼운다 구현 클래스를 하나 더하고 목록에 넣는다. 계산기는 그대로다
한 종류만 테스트 계산기 전체를 거쳐야 한다 new RatePolicy().discount(…)를 바로 부른다
계산기가 하는 일 모든 규칙을 안다 "이 쿠폰을 맡는 정책"을 찾아 맡긴다
JS로 치면 if (type === 'RATE') … const policies = { RATE: rateFn, … }

흔한 착각: "전략 패턴을 쓰면 조건문이 사라진다". 조건은 없어지지 않는다. 어느 정책이 맡을지 고르는 곳 한 군데로 모일 뿐이다(여기서는 각 정책의 supports와 standardPolicies()). 바뀌는 것은 규칙이 흩어져 있던 곳이다. 분기 몸통이 클래스로 갈라져 서로 섞이지 않는다.

#기본기 반복

가진 쿠폰 목록을 stream으로 돌며 이 주문에서 쓸 수 있는(할인액이 0보다 큰) 쿠폰 중 할인액이 가장 큰 것을 고른다. 없을 수 있으므로 Optional<Coupon>을 돌려준다.

filter로 거른 뒤 가장 큰 쿠폰을 고른다. "같으면 앞의 쿠폰"은 업무 규칙이므로 코드에 직접 적는다. Stream.max는 같은 값일 때 어느 원소를 남길지 약속하지 않는다(지금 구현이 어떻게 동작하든 계약이 아니다). reduce((best, next) -> 뒤가 더 클 때만 next, 아니면 best)처럼 "더 클 때만 바꾼다"를 써 두면 같을 때 앞의 쿠폰이 남는다.

#타입 한 컷

record: 불변 데이터 운반 객체, compact 생성자 검증. DTO와 값 객체.

레거시 DTO 클래스(LegacyCouponCodeDto) record CouponCode
값 넣기 기본 생성자 + setValue 생성자 한 번(바꾸려면 새로 만든다)
규칙 검사 없음. 아무 값이나 담긴다 compact 생성자에서. 통과하지 못하면 객체가 안 생긴다
정규화(공백·대소문자) 쓰는 쪽마다 따로 compact 생성자에서 매개변수를 다시 대입
equals·hashCode 없음(주소 비교). Set에 같은 코드가 둘 구성 요소 값으로 자동
어울리는 자리 프레임워크가 setter로 채우는 옛 DTO 요청·응답 DTO, 값 객체

함정: compact 생성자 안에서는 this.value = …를 쓸 수 없다(컴파일 에러). 대신 매개변수 value에 다시 대입하면 생성자 끝에서 그 값이 필드에 담긴다. 그리고 record의 불변은 얕다. 구성 요소가 List면 compact 생성자에서 List.copyOf로 복사해야 한다(J01의 방어적 복사).

과제: CouponCode의 compact 생성자를 채운다. 앞뒤 공백을 지우고 대문자로 바꾼 뒤(toUpperCase(Locale.ROOT) — 인자 없는 toUpperCase()는 서버 기본 로케일을 따라 터키어 로케일에서 "i"를 "İ"로 바꾼다), 영문 대문자·숫자만 6~12자인지 검사한다. 아니면(null 포함) IllegalArgumentException을 던진다.

#구현 예시

펼치기▸

왜 이렇게 쓰나:

  1. 계산기가 정책 목록을 생성자로 받으면 테스트나 다른 화면에서 다른 목록을 끼울 수 있다. Spring에서는 이 목록을 List<DiscountPolicy> 생성자 주입으로 받는다(구현 빈이 모두 들어온다).
  2. 정책 하나에 한 종류의 규칙과 그 상수(MAX_DISCOUNT)가 같이 산다. 정률 규칙을 고칠 때 정액 코드를 건드릴 일이 없다.
  3. 값 객체는 들어오는 순간 정규화·검사를 끝낸다. 그러면 CouponCode를 받은 쪽은 다시 검사하지 않아도 된다. equals가 값 기준이라 Set·Map 키로도 바로 쓴다.
