# J08. 예외·try-with-resources·람다로 만드는 재시도 함수

> 같은 날: D08 · 소요 30~60분 · 실행 `./gradlew :java-track:test --tests 'J08*'`

## 상황

D08은 외부 PG를 붙여 포인트 충전을 만드는 날이다. D08 ④ "재시도와 백오프"에서 `PgRetryPolicy`가 연결 실패만 200ms·400ms 간격으로 다시 보내고, 거절은 다시 보내지 않는다. D08 ① `PgClient`는 HTTP 라이브러리 예외를 원인을 담은 `PgException`으로 바꾼다.
오늘은 Spring 없이 같은 재시도 함수 `retry(Supplier<T>, int)`를 직접 만든다. 람다로 호출을 넘기려면 체크 예외를 언체크 예외로 바꿔야 하고, 연결은 try-with-resources로 반드시 닫고, 바꿀 때 원인을 버리면 장애 때 무엇이 실패했는지 알 수 없다는 것까지 테스트로 확인한다.

## 빠른 연상

| | 체크 예외 (`IOException`, `InterruptedException`) | 언체크 예외 (`RuntimeException` 하위) | TS로 치면 |
|---|---|---|---|
| 컴파일러가 처리를 강제하나 | 강제한다. `catch` 하거나 `throws`로 선언해야 컴파일된다 | 강제하지 않는다 | TS는 둘 다 강제하지 않는다 |
| 람다(`Supplier.get()`) 안에서 던질 수 있나 | 없다. `get()`에 `throws`가 없다 | 있다 | 콜백 안 `throw` |
| 언제 쓰나 | 호출한 쪽이 복구할 수 있는 외부 실패 | 프로그래밍 오류, 또는 체크 예외를 감싸 올릴 때 | |

```
retry(call, 3)
 ├─ 1회 call.get() ── PgUnreachableException ── 200ms 기다림 (Sleeper)
 ├─ 2회 call.get() ── PgUnreachableException ── 400ms 기다림
 └─ 3회 call.get() ── PgUnreachableException ── 기다리지 않고 그대로 던짐
          └─ PgDeclinedException(거절)이면 몇 번째든 바로 던짐
```

흔한 착각: "체크 예외를 언체크로 바꾸면 정보가 사라진다". 원인을 생성자 두 번째 인자로 넘기면(`new PgUnreachableException(msg, e)`) 원래 예외가 `getCause()`와 스택 트레이스의 `Caused by:`로 그대로 남는다. 정보가 사라지는 경우는 원인을 넘기지 않을 때다.

`retry` 규칙:

- `maxAttempts`는 첫 시도를 포함한 전체 시도 횟수다. 1보다 작으면 한 번도 부르지 않고 `IllegalArgumentException`을 던진다.
- `PgUnreachableException`(연결 실패)만 다시 시도한다. 다른 예외(`PgDeclinedException` 등)는 그대로 던진다.
- 다시 시도하기 전에 200ms부터 두 배씩(200ms, 400ms, 800ms …) 기다린다. 마지막 시도 뒤에는 기다리지 않는다.
- 끝까지 실패하면 마지막 예외를 **그대로** 던진다(새 예외로 감싸지 않는다).
- 기다리는 일은 생성자로 받은 `Sleeper`가 한다. 테스트는 기다리지 않고 시간만 적어 두는 람다(`sleeps::add`)를 넘긴다. `Thread.sleep`을 직접 부르지 않는다.
- `Sleeper`가 `InterruptedException`을 던지면 인터럽트 표시를 되살리고(`Thread.currentThread().interrupt()`), 더 시도하지 않고 마지막 예외를 던진다.

뼈대 발췌:

```java
@FunctionalInterface
public interface Sleeper {                         // 주어진 코드
    void sleep(Duration duration) throws InterruptedException;
}

public class Retrier {

    public static final Duration FIRST_BACKOFF = Duration.ofMillis(200);

    // TODO: 주입받은 Sleeper를 담을 필드를 선언하세요(다시 대입할 일이 없다)

    public Retrier(Sleeper sleeper) {
        throw new UnsupportedOperationException("J08: Retrier 생성자 — 받은 Sleeper를 필드에 담으세요");
    }

    /** call을 최대 maxAttempts번 부른다. 성공하면 그 값을 돌려준다. */
    public <T> T retry(Supplier<T> call, int maxAttempts) {
        throw new UnsupportedOperationException("J08: Retrier.retry — 연결 실패만 백오프를 두고 다시 부르세요");
    }
}

public final class PgCall {
    /** 채널을 열어 보내고 반드시 닫는다. IOException은 원인으로 담아 PgUnreachableException으로 바꾼다. */
    public static String sendOnce(Supplier<PgChannel> opener, String body) {
        throw new UnsupportedOperationException("J08: PgCall.sendOnce — try-with-resources로 보내고, IOException은 원인을 담아 바꾸세요");
    }
}
```

`PgChannel`은 `AutoCloseable`이고 `send`가 체크 예외 `IOException`을 던진다. `Supplier.get()`은 체크 예외를 던질 수 없으므로, `retrier.retry(() -> channel.send(body), 3)`처럼 바로 넘기면 컴파일되지 않는다. `sendOnce`가 바꿔 주면 `retrier.retry(() -> PgCall.sendOnce(opener, body), 3)`이 된다.

통과시킬 테스트(주제 과제) — `J08RetryTest`:

- `첫_시도에_성공하면_한_번만_부르고_기다리지_않는다`
- `연결_실패_뒤_성공하면_그_값을_돌려주고_200ms_400ms를_기다린다`
- `끝까지_실패하면_마지막_예외를_그대로_던지고_마지막_시도_뒤에는_기다리지_않는다` (4회 시도, 200·400·800ms)
- `거절은_다시_보내지_않고_기다리지도_않는다`
- `시도_횟수가_1보다_작으면_한_번도_부르지_않고_거절한다` (0, -1)
- `기다리다_인터럽트되면_인터럽트_표시를_되살리고_마지막_예외를_던진다`
- `보내고_나면_채널이_닫힌다`

## 타입 한 컷

`String` 불변, `+` 결합과 `StringBuilder`, `String.format` — 외부 API URL 조립과 로그 메시지.

| | `+` / `+=` | `StringBuilder` | `String.format` |
|---|---|---|---|
| 결과 | 매번 새 `String` | 한 버퍼에 이어 붙이고 마지막에 `toString()` | 틀(`%s`, `%d`)에 값을 채운 새 `String` |
| 어울리는 곳 | 한 줄짜리 짧은 결합 | 반복문으로 개수가 정해지지 않은 조각 붙이기(쿼리 파라미터) | 모양이 정해진 메시지(로그 한 줄) |
| 반복문 안에서 | 조각마다 새 문자열을 만든다 | 버퍼 하나를 늘려 간다 | - |

함정: `String`은 불변이라 `url.concat("?a=1")`, `url.replace(…)`, `url.toUpperCase()`는 **새 문자열을 돌려줄 뿐** `url`을 바꾸지 않는다. 결과를 받지 않으면(`url = url.concat(…)`) 아무 일도 일어나지 않는다. 그리고 쿼리 값에 `&`·공백이 섞이면 파라미터가 갈라지므로 `URLEncoder.encode(값, UTF_8)`로 인코딩한다.

과제: `PgMessages.queryUrl(baseUrl, params)`는 `StringBuilder`로 `?키=값&키=값`을 params 순서대로 붙이고(비어 있으면 baseUrl 그대로), `approvalLog`는 `String.format`으로 `PG 승인 orderId=CHG-1 amount=10000 elapsedMs=120`을 만든다.

확인 테스트 — `J08TypeCutTest`:

- `쿼리_파라미터를_넣은_순서대로_이어_붙인다`
- `파라미터가_없으면_물음표_없이_기본_URL만_돌려준다`
- `값에_섞인_특수문자는_인코딩해_파라미터가_갈라지지_않게_한다`
- `로그_메시지는_String_format으로_자리를_채운다`
- `함정_String은_불변이라_concat_결과를_받지_않으면_그대로다`

## 실무 습관

예외 원인 연결과 삼키기. 주어진 `LeakyPgCall`은 컴파일도 되고 평소에는 잘 돈다. 장애가 나야 문제가 드러난다.

1. `sendSwallowing` — 빈 `catch`. PG에 연결하지 못했는데 `null`을 돌려준다. 호출한 쪽은 "응답이 비었다"와 "실패했다"를 구분하지 못하고, 로그에도 아무것도 남지 않는다.
2. `sendWithoutCause` — `new PgUnreachableException("PG 호출 실패")`처럼 원인 없이 새 예외를 던진다. 실패한 것은 알지만 연결 거부인지 리셋인지 알 수 없다. 스택 트레이스에 `Caused by:`가 없다.

과제: `PgCall.sendOnce`에서 `IOException`을 바꿀 때 `new PgUnreachableException(msg, e)`로 원인을 넘긴다.

테스트 — `J08HabitTest` (각 테스트가 `LeakyPgCall`이 무엇을 숨기는지 먼저 보여 준다):

- `빈_catch는_실패를_null로_숨기고_PgCall은_예외로_드러낸다`
- `원인_없이_새_예외를_던지면_원래_IOException이_사라진다_PgCall은_원인으로_남긴다`
- `원인을_이어_두면_스택_트레이스에_Caused_by로_원래_예외가_찍힌다`

```java
// Retrier
private final Sleeper sleeper;

public Retrier(Sleeper sleeper) {
    this.sleeper = sleeper;
}

public <T> T retry(Supplier<T> call, int maxAttempts) {
    if (maxAttempts < 1) {
        throw new IllegalArgumentException("maxAttempts는 1 이상이어야 합니다: " + maxAttempts);
    }
    Duration backoff = FIRST_BACKOFF;
    for (int attempt = 1; ; attempt++) {
        try {
            return call.get();
        } catch (PgUnreachableException e) {
            // 재시도 대상만 잡는다. 거절 같은 다른 예외는 catch에 걸리지 않고 그대로 나간다
            if (attempt >= maxAttempts) {
                throw e;
            }
            pause(backoff, e);
            backoff = backoff.multipliedBy(2);
        }
    }
}

private void pause(Duration backoff, PgUnreachableException last) {
    try {
        sleeper.sleep(backoff);
    } catch (InterruptedException interrupted) {
        // 잡는 순간 인터럽트 표시가 지워진다. 되살려야 스레드를 멈추려던 쪽이 신호를 잃지 않는다
        Thread.currentThread().interrupt();
        throw last;
    }
}
```

// PgCall
public static String sendOnce(Supplier<PgChannel> opener, String body) {
    // 괄호 안에서 연 자원은 블록을 어떻게 빠져나가든 close된다. close 예외는 원래 예외의 suppressed로 붙는다
    try (PgChannel channel = opener.get()) {
        return channel.send(body);
    } catch (IOException e) {
        // 두 번째 인자로 원인을 넘긴다. 빼면 로그에서 "왜" 실패했는지가 사라진다
        throw new PgUnreachableException("PG 호출 실패: " + e.getMessage(), e);
    }
}

```java
// ChargeValidator
public static long validateAndSum(List<ChargeRequest> requests) {
    List<ChargeFailure> failures = new ArrayList<>();
    long total = 0;
    for (int i = 0; i < requests.size(); i++) {
        String reason = reasonOf(requests.get(i));
        if (reason != null) {
            failures.add(new ChargeFailure(i, reason));
        } else {
            total += requests.get(i).amount();
        }
    }
    if (!failures.isEmpty()) {
        throw new ChargeValidationException(failures);
    }
    return total;
}

/** 통과하면 null, 실패하면 첫 번째로 어긴 규칙의 사유. */
private static String reasonOf(ChargeRequest request) {
    if (request.idempotencyKey() == null || request.idempotencyKey().isBlank()) {
        return "멱등 키가 없습니다";
    }
    int amount = request.amount();
    if (amount < MIN_AMOUNT || amount > MAX_AMOUNT) {
        return "금액은 1,000~1,000,000원이어야 합니다: " + amount;
    }
    if (amount % AMOUNT_UNIT != 0) {
        return "금액은 1,000원 단위여야 합니다: " + amount;
    }
    return null;
}
```

```java
// PgMessages
public static String queryUrl(String baseUrl, Map<String, String> params) {
    // String은 불변이라 반복문에서 +=를 쓰면 매번 새 문자열을 만든다. 한 버퍼에 이어 붙인다
    StringBuilder url = new StringBuilder(baseUrl);
    char separator = '?';
    for (Map.Entry<String, String> param : params.entrySet()) {
        url.append(separator)
                .append(param.getKey())
                .append('=')
                .append(URLEncoder.encode(param.getValue(), StandardCharsets.UTF_8));
        separator = '&';
    }
    return url.toString();
}

public static String approvalLog(String orderId, int amount, long elapsedMillis) {
    return String.format("PG 승인 orderId=%s amount=%d elapsedMs=%d", orderId, amount, elapsedMillis);
}
```

왜 이렇게 쓰나:

1. `catch (PgUnreachableException e)`처럼 재시도할 예외만 잡으면 "무엇을 다시 보내는가"가 catch 한 줄에 드러난다. 거절이나 버그 예외는 잡히지 않고 그대로 나간다. `Exception`을 통째로 잡고 다시 고르는 것보다 실수할 곳이 적다.
2. 기다리는 일을 `Sleeper`로 주입받으면 테스트는 실제로 기다리지 않고 "몇 ms를 몇 번 기다렸나"만 정확히 확인한다. 실제로 기다리는 테스트는 느리고, 걸린 시간을 범위로만 단언할 수 있다. `InterruptedException`을 잡으면 인터럽트 표시가 지워지므로 되살려 둔다.
3. 체크 예외를 언체크로 바꾸는 곳은 람다 경계 한 곳(`sendOnce`)에 모으고, 바꿀 때 반드시 원인을 넘긴다. try-with-resources는 close 실패를 버리지 않고 원래 예외의 `getSuppressed()`에 붙이므로, 원인 연결과 함께 쓰면 장애 로그 한 덩어리에 전부 남는다.
