틈(betweenReadAndWrite): 지갑은 생성자로 Runnable 하나를 받아 읽은 뒤 쓰기 전에 한 번 부른다. 테스트는 여기에 "두 스레드가 모두 잔액을 읽을 때까지 기다리기"를 넣는다. 그래서 LeakyPointWallet은 매번 둘이 같은 0을 읽고 손실이 난다. 고친 지갑도 이 틈을 반드시 거쳐야 한다.

  • synchronized 지갑 테스트는 기다림이 제때 끝났는지(시간 초과인지)를 기록한다. 먼저 들어온 스레드는 잠금을 쥔 채 기다리다 시간 초과, 뒤 스레드는 잠금이 풀린 뒤 바로 통과 — 이 모양이 "한 번에 한 스레드"의 증거다.
  • CAS 지갑 테스트는 첫 읽기 두 번만 CyclicBarrier에서 서로를 기다리게 한다. 둘 다 같은 0을 읽었으니 compareAndSet(0, 10)은 한쪽만 성공하고, 실패한 쪽은 다시 읽어 틈을 한 번 더 지난다. 그래서 틈은 정확히 3번 불린다(2번이면 재시도하지 않은 것이다).

규칙:

  • SynchronizedPointWallet.earn: 읽기 → betweenReadAndWrite.run() → 쓰기. 메서드에 synchronized를 붙인다. balance()도 같은 잠금으로 읽는다.
  • AtomicPointWallet.earn: get() → betweenReadAndWrite.run() → compareAndSet(읽은 값, 읽은 값 + amount). 실패하면 get()부터 다시.
  • MemberPoints: 회원별 잔액을 ConcurrentHashMap에 담는다. 더할 때는 merge 한 번으로.
  • CouponIssuer.issue: 처음 받는 회원이면 true. contains로 확인하고 add하지 말고, add의 반환값을 쓴다.

이전 (LeakyPointWallet) synchronized AtomicInteger
방법 읽고 → 더해서 쓰기 한 번에 한 스레드만 메서드 안에 들어온다(잠금) 읽은 값이 그대로일 때만 바꾼다(compareAndSet), 실패하면 다시 읽는다
기다림 없다(대신 손실) 다른 스레드는 입구에서 기다린다 기다리지 않고 다시 시도한다
DB로 치면 SELECT 후 UPDATE … SET balance = 읽은값+10 SELECT … FOR UPDATE(비관적 잠금) UPDATE … WHERE balance = 읽은값(낙관적 갱신)
board-server가 쓴 방법 한 문장 UPDATE … SET balance = balance + ?

JS는 한 스레드에서 돌아서 balance += 10 사이에 다른 코드가 끼지 않는다. Java 서버는 요청마다 다른 스레드가 같은 객체(싱글톤 빈)를 동시에 쓴다.

흔한 착각: "balance += 10은 한 줄이니 한 번에 일어난다". 컴파일되면 읽기·더하기·쓰기 세 단계다. 그 사이에 다른 스레드가 끼어들 수 있다. 테스트에서 잘 안 터지는 것은 틈이 아주 짧기 때문이다. 그래서 오늘은 틈을 일부러 벌려 매번 터지게 한다.

#타입 한 컷

boolean vs Boolean, is 접두어와 JSON 직렬화 — 응답 필드 이름이 바뀌는 문제.

boolean Boolean
값 true·false true·false·null
쓰는 곳 응답의 상태 값(언제나 정해짐) 요청·설정에서 "보내지 않음"을 구분할 때
Lombok @Getter (필드 used) isUsed() getUsed()
Lombok @Getter (필드 isExpired) isExpired() (접두어를 겹치지 않는다) getIsExpired()

JSON 라이브러리(Jackson)는 필드가 아니라 getter 이름으로 응답 이름을 정한다. isExpired()는 expired, getIsExpired()는 isExpired로 나간다.

필드 선언 Lombok이 만든 getter 응답 JSON 이름
boolean used isUsed() used
boolean isExpired isExpired() expired (필드 이름과 다르다)
boolean issued isIssued() issued ("is" 다음이 소문자라 접두어가 아니다)
Boolean isExpired getIsExpired() isExpired
Boolean autoRenew getAutoRenew() autoRenew

함정 두 가지:

  1. boolean isExpired로 이름 지으면 응답에는 expired로 나간다. 프런트엔드가 response.isExpired를 읽으면 undefined다.
  2. 나중에 null을 담으려고 타입만 Boolean으로 바꾸면 getter가 getIsExpired()가 되어 응답 이름이 isExpired로 바뀐다. 코드 한 글자 안 바꾼 클라이언트가 깨진다.

그래서 boolean 필드는 is를 붙이지 않고 expired처럼 짓는다. record는 구성 요소 이름이 그대로 응답 이름이 된다(Jackson 2.18·3.1에서 record R(boolean isUsed) → "isUsed" 확인).

이 모듈에는 Jackson이 없어서, 같은 이름 규칙을 쓰는 JDK의 java.beans.Introspector로 확인한다. 위 표의 getter 모양에서는 Jackson(2.18·3.1)과 Introspector의 결과가 같다. 다만 Boolean을 돌려주는 isX()를 손으로 쓰면 Jackson은 x로 내보내고 Introspector는 프로퍼티로 보지 않는다. 라이브러리마다 다르니 그런 getter는 만들지 않는다.

약어도 하나 본다. boolean isURL의 getter는 isURL()이고, "is"를 뗀 URL은 앞 두 글자가 모두 대문자라 첫 글자를 소문자로 바꾸지 않는다(Introspector.decapitalize 규칙). 응답 이름은 uRL이 아니라 URL이다.

기본 과제: 관찰. 주어진 delombok 코드(LombokCouponResponse·WrapperExpiredResponse·AcronymFlagResponse)를 Introspector로 읽어 위 표가 맞는지 확인한다. 이 테스트들은 처음부터 통과한다 — 읽고 왜 그런지 설명할 수 있으면 된다.

선택 과제: JsonNames.jsonName(Field)로 이름 규칙을 직접 구현한다. 기본형 boolean이고 이름이 "is" + 대문자로 시작하면 "is"를 떼고 decapitalize 규칙(앞 두 글자가 모두 대문자면 그대로, 아니면 첫 글자만 소문자)을 적용한다. 아니면 필드 이름 그대로다. jsonNames(Class)는 인스턴스 필드마다 모은다. getDeclaredFields()는 선언 순서를 보장하지 않으므로 순서는 정하지 않는다(테스트도 순서 없이 비교한다). 여기서 다루는 getter 모양에 한한 규칙이다(Lombok이 xIndex 같은 이름에 만드는 getter까지 다루지 않는다).

#실무 습관

Map 함정 두 가지.

함정 터지는 모양 고치는 법
Collectors.toMap(키, 값)에 같은 키가 두 번 나옴 IllegalStateException: Duplicate key 자바초보 세 번째 인자로 합치는 함수 (first, later) -> first
HashMap을 돌면 순서가 섞임 넣은 순서도 키 순서도 약속하지 않는다. 데이터가 바뀌면 순서도 바뀐다 넣은 순서: LinkedHashMap, 키 순서: TreeMap

toMap(키, 값)은 어떤 Map을 돌려줄지 약속하지 않는다(API 문서에 종류·순서·가변 여부 보장이 없다. 지금 JDK는 HashMap을 준다). 순서가 필요하면 네 번째 인자로 LinkedHashMap::new처럼 원하는 Map을 직접 넘긴다.

과제: NicknameIndex를 채운다. 닉네임 중복 검사가 생기기 전의 옛 데이터라 같은 닉네임이 섞여 있다. 먼저 나온 회원의 id를 남기고, 닉네임이 처음 나온 순서를 지킨다. sortedById는 id 오름차순으로 도는 Map을 돌려준다.

#구현 예시

펼치기▸

틈이 없다면 balance.addAndGet(amount) 한 줄이 같은 결과를 원자적으로 낸다. 오늘은 틈을 거쳐야 해서 되풀이를 직접 썼다.

왜 이렇게 쓰나:

  1. 여러 스레드가 함께 쓰는 값은 "읽고 → 계산하고 → 쓰기"가 끊기지 않게 한다. 잠그거나(synchronized), 읽은 값이 그대로일 때만 바꾸거나(compareAndSet), 그 일을 한 번에 해 주는 API(merge, Set.add)를 쓴다. DB에서는 같은 일을 한 문장 UPDATE … SET x = x + ?와 UNIQUE 제약이 한다.
  2. 응답 DTO의 boolean 필드는 is를 붙이지 않고 짓는다. getter 이름이 응답 이름을 정하므로, 필드 이름이나 타입(boolean ↔ Boolean)만 바꿔도 API가 바뀔 수 있다.
  3. toMap에는 중복 키를 어떻게 합칠지와 어떤 Map에 담을지를 적어 둔다. 순서가 의미 있는 결과를 HashMap에 담지 않는다.
