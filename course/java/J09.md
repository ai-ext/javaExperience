# J09. Clock 주입과 Duration — TTL과 KST 자정 경계

> 같은 날: D09 · 소요 30~60분 · 실행 `./gradlew :java-track:test --tests 'J09*'`

## 상황

D09는 Redis를 붙이는 날이다. D09 ① 인기글 캐시는 TTL 60초, D09 ⑥ 로그인 시도 제한은 "10분 5회"라서 시간이 지나면 키가 사라진다. D03 ④ `JwtProvider`는 만료 토큰을 테스트하려고 `Clock`을 주입받는다. 그리고 D13 ③에서는 "자정 전후 출석 포인트가 두 번 쌓인다"를 `Clock`을 고정한 테스트로 재현한다.
오늘은 Spring 없이 시간을 다룬다. "지금"을 `Instant.now()`로 직접 읽지 않고 주입받은 `Clock`에서 읽으면, 테스트가 `Clock.fixed`로 만료 시각 1초 전과 KST 자정 정각을 정확히 만들 수 있다.

## 빠른 연상

| | 서버 코드 | 테스트 | TS로 치면 |
|---|---|---|---|
| 지금 읽기 | `clock.instant()` | `Clock.fixed(Instant.parse("2026-10-22T14:59:59Z"), ZoneOffset.UTC)` | `Date.now()` 대신 `now()` 함수를 주입 |
| 시간 흐름 | 진짜로 흐른다 | "지금"만 다른 시계를 하나 더 만든다 | `jest.useFakeTimers()` + `setSystemTime` |
| 길이 | `Duration.ofSeconds(60)` | `Duration.between(a, b)` | 밀리초 `number` |

```
UTC  ... 14:59:59 | 15:00:00 ...          (같은 10월 22일)
KST  ... 23:59:59 | 00:00:00 (10월 23일)
                  ↑ KST 자정 = UTC 15:00
```

흔한 착각: "`LocalDate.now(clock)`이면 시계를 주입했으니 안전하다". `LocalDate.now(clock)`는 **시계의 zone**으로 날짜를 자른다. 운영 서버 시계가 UTC면 KST 00:00~08:59 사이의 출석이 전날로 잡힌다. 날짜를 자를 때는 KST를 직접 지정한다(`clock.instant().atZone(KST)`). 그래서 오늘 테스트의 시계는 모두 일부러 UTC로 두고, 테스트하는 동안 JVM 기본 시간대도 `America/New_York`으로 바꿔 둔다(`@BeforeEach`에서 바꾸고 `@AfterEach`에서 되돌린다). 개발 PC의 기본 시간대가 KST라서 `ZoneId.systemDefault()`나 시계의 zone에 기대는 코드가 우연히 맞는 것을 잡아내려는 것이다.

## 타입 한 컷

`LocalDate`·`LocalDateTime`·`Instant`·`ZonedDateTime`의 차이 — 출석 자정 경계, 토큰 만료.

| | 담는 것 | 시간대 | 어울리는 곳 |
|---|---|---|---|
| `Instant` | 타임라인 위의 한 점(UTC 기준 초·나노초) | 없음. 어디서 봐도 같은 순간 | 토큰 만료, TTL 계산, "몇 초 남았나" |
| `ZonedDateTime` | 날짜·시각 + zone(`Asia/Seoul`) | 있음 | "KST로 오늘 자정은 언제인가" 같은 달력 계산 |
| `LocalDateTime` | 날짜·시각(벽시계 숫자) | **없음** | DB `DATETIME`(KST로 저장한다는 약속이 따로 있어야 의미가 있다) |
| `LocalDate` | 날짜만 | 없음 | 출석 날짜, "하루 한 번" |

함정: 같은 `Instant`라도 어느 zone으로 보느냐에 따라 `LocalDate`가 달라진다. `LocalDate.now(utcClock)`는 KST 00:30을 **전날**로 본다. 반대로 `LocalDateTime`에는 zone이 없으므로 `Instant`로 되돌릴 때는 "이 값은 KST다"를 직접 붙여야 한다(`atZone(KST)`).

과제: `KstTime`을 채운다. `today(clock)`은 시계 zone을 무시하고 KST 날짜를, `toOffsetString`은 응답용 `2026-10-22T09:30:00+09:00`(초가 0이어도 초까지)을 만든다.

확인 테스트 — `J09TypeCutTest`:

- `today는_시계의_zone이_아니라_KST_날짜를_돌려준다`
- `함정_UTC_시계로_LocalDate_now를_부르면_KST_자정_직후가_어제가_된다`
- `같은_Instant도_어느_zone으로_보느냐에_따라_LocalDateTime이_다르다`
- `LocalDateTime에는_시간대가_없어_KST라는_zone을_붙여야_Instant로_되돌아간다`
- `응답에는_KST_오프셋을_붙인_ISO_문자열로_내보낸다`

## 선택 관찰: 금액과 시각의 저장 정밀도 (10분)

시간대와 정밀도는 서로 다른 경계다. Clock을 고정해도 DB가 나노초를 모두 저장한다는 뜻은 아니다. D08에서 금액을 다뤘으므로, 오늘은 **선택**으로 문자열 금액 → Java 정책 → DB 재조회 경계를 확인한다. 오늘 시간이 없으면 J14의 선택 BigDecimal 과제 뒤에 돌아온다. 기존 19개 필수 테스트와 30~60분 분량에는 넣지 않는다.

채울 파일은 `java-track/src/main/java/com/example/javatrack/j09/DecimalAmount.java`다. 이 작은 실험은 부호를 허용하는 `DECIMAL(5,2)`를 사용한다. 기존 상점의 정수 포인트·원화 API 계약을 바꾸는 과제가 아니다.

| 입력·관찰 | 이 실험의 계약 |
|---|---|
| `forStorage("1.005")`, `forStorage("-1.005")` | 문자열로 만들고 scale 2, HALF_UP → `1.01`, `-1.01` |
| `forStorage("1.0")` | 저장 표현은 `1.00`. `equals(1.0)`은 false, `compareTo(1.0)`은 0 |
| `999.994`, `999.995` | 반올림 **뒤** 범위 검사: `999.99` 허용, `1000.00`은 IllegalArgumentException |
| `exact("1.230")`, `exact("1.231")` | scale 2로 손실 없이 표현. 앞은 허용, 뒤는 ArithmeticException |
| `new BigDecimal(0.1)`과 문자열 `"0.1"` | 이진 부동소수점에서 넘어온 값과 정확한 십진수의 차이 비교 |

```bash
./gradlew :java-track:optionalTest --tests 'J09DecimalAmountTest'
```

`J09DecimalAmountTest` 5개를 통과시킨다. 기존 `check`는 선택 과제까지 정답 통과·뼈대 의도 실패를 검사한다. DB 없이 실행하는 이 테스트는 **실제 MySQL 왕복을 증명하지 않는다**.

DB까지 확인하려면 [D09 ① 힌트](../spring/D09.md)의 선택 관찰로 이어 간다. 같은 연결의 임시 `DECIMAL(5,2)`·`DATETIME(6)` 테이블에서 금액을 `setBigDecimal/getBigDecimal`로 왕복하고, `Clock.fixed`의 같은 순간을 UTC/서울로 표시한다. 나노초는 마이크로초로 명시적으로 줄인 뒤 비교한다. 제출 표는 `입력 → Java 값/scale → JDBC 바인딩 → DB 재조회 → 값·정밀도 비교`다. 실제 쿼리 결과와 실행하지 않은 예상값을 구분한다.

```java
// TokenIssuer
private final Clock clock;
private final Duration ttl;

public TokenIssuer(Clock clock, Duration ttl) {
    if (ttl == null || ttl.isZero() || ttl.isNegative()) {
        throw new IllegalArgumentException("TTL은 0보다 커야 합니다: " + ttl);
    }
    this.clock = clock;
    this.ttl = ttl;
}

public Token issue(Long memberId) {
    Instant now = clock.instant();
    return new Token(memberId, now, now.plus(ttl));
}

public boolean isExpired(Token token) {
    // "지금이 만료 시각 전인가"의 반대. isAfter로 쓰면 만료 시각 정각을 유효로 잘못 본다
    return !clock.instant().isBefore(token.expiresAt());
}

public Duration remaining(Token token) {
    Duration left = Duration.between(clock.instant(), token.expiresAt());
    return left.isNegative() ? Duration.ZERO : left;
}
```

```java
// MidnightTtl
public static Duration untilNextKstMidnight(Clock clock) {
    // 시계의 zone을 쓰지 않고 순간(Instant)만 꺼내 KST로 본다
    ZonedDateTime now = clock.instant().atZone(KST);
    ZonedDateTime nextMidnight = now.toLocalDate().plusDays(1).atStartOfDay(KST);
    return Duration.between(now, nextMidnight);
}
```

```java
// AttendanceBook
public static List<Attendance> firstPerKstDay(List<Attendance> records) {
    // 먼저 시각 순으로 정렬해 두면 "처음 본 것"이 곧 "가장 이른 것"이다
    List<Attendance> sorted = new ArrayList<>(records);
    sorted.sort(Comparator.comparing(Attendance::checkedAt));

    Map<String, Attendance> firstByMemberAndDay = new LinkedHashMap<>();
    for (Attendance attendance : sorted) {
        LocalDate kstDate = attendance.checkedAt().atZone(KST).toLocalDate();
        firstByMemberAndDay.putIfAbsent(attendance.memberId() + "@" + kstDate, attendance);
    }
    return new ArrayList<>(firstByMemberAndDay.values());
}
```

```java
// KstTime
public static LocalDate today(Clock clock) {
    // LocalDate.now(clock)는 시계의 zone으로 자른다. zone을 KST로 바꾼 시계를 넘긴다
    return LocalDate.now(clock.withZone(KST));
}

public static LocalDateTime toKstLocalDateTime(Instant instant) {
    return LocalDateTime.ofInstant(instant, KST);
}

public static Instant fromKstLocalDateTime(LocalDateTime kstDateTime) {
    return kstDateTime.atZone(KST).toInstant();
}

public static String toOffsetString(Instant instant) {
    // OffsetDateTime.toString()은 초가 0이면 "09:30+09:00"처럼 초를 뺀다. 형식을 고정하려고 포매터를 쓴다
    return instant.atZone(KST).toOffsetDateTime().format(DateTimeFormatter.ISO_OFFSET_DATE_TIME);
}
```

선택 금액 실험 정답:

```java
package com.example.javatrack.j09;

import java.math.BigDecimal;
import java.math.RoundingMode;

/** 선택: DECIMAL(5,2)에 넣기 전 명시적으로 적용하는 실험용 정책. */
public final class DecimalAmount {
    private static final BigDecimal MAX = new BigDecimal("999.99");

    private DecimalAmount() {
    }

    public static BigDecimal forStorage(String text) {
        return withinRange(new BigDecimal(text).setScale(2, RoundingMode.HALF_UP));
    }

    public static BigDecimal exact(String text) {
        return withinRange(new BigDecimal(text).setScale(2, RoundingMode.UNNECESSARY));
    }

    private static BigDecimal withinRange(BigDecimal amount) {
        // 반올림 때문에 정수 자릿수가 늘어날 수 있으므로 정규화 뒤 검사한다.
        if (amount.abs().compareTo(MAX) > 0) {
            throw new IllegalArgumentException("DECIMAL(5,2) 범위 초과: " + amount);
        }
        return amount;
    }
}
```

왜 이렇게 쓰나:

1. "지금"을 한 곳(`Clock`)에서만 읽으면 테스트가 경계 시각(만료 1초 전, 자정 정각)을 정확히 만들 수 있다. `Instant.now()`가 코드 곳곳에 흩어져 있으면 자정 경계 버그는 자정에 테스트를 돌려야만 보인다.
2. 만료와 TTL은 시간대와 상관없는 `Instant`·`Duration`으로 계산하고, "오늘"이 필요한 곳에서만 KST `ZonedDateTime`으로 바꾼다. 날짜를 자르는 zone은 시계나 서버 설정에 맡기지 않고 `KST` 상수로 못 박는다.
3. 경계는 "같거나 지나면 만료"처럼 한쪽을 포함하는 규칙으로 정하고, 테스트로 정각 케이스를 고정한다. `isAfter`와 `!isBefore`는 정각에서만 다르게 동작한다.
