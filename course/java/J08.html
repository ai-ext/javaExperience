retry 규칙:

  • maxAttempts는 첫 시도를 포함한 전체 시도 횟수다. 1보다 작으면 한 번도 부르지 않고 IllegalArgumentException을 던진다.
  • PgUnreachableException(연결 실패)만 다시 시도한다. 다른 예외(PgDeclinedException 등)는 그대로 던진다.
  • 다시 시도하기 전에 200ms부터 두 배씩(200ms, 400ms, 800ms …) 기다린다. 마지막 시도 뒤에는 기다리지 않는다.
  • 끝까지 실패하면 마지막 예외를 그대로 던진다(새 예외로 감싸지 않는다).
  • 기다리는 일은 생성자로 받은 Sleeper가 한다. 테스트는 기다리지 않고 시간만 적어 두는 람다(sleeps::add)를 넘긴다. Thread.sleep을 직접 부르지 않는다.
  • Sleeper가 InterruptedException을 던지면 인터럽트 표시를 되살리고(Thread.currentThread().interrupt()), 더 시도하지 않고 마지막 예외를 던진다.

뼈대 발췌:

뼈대 코드·실행 원문 펼치기▸

PgChannel은 AutoCloseable이고 send가 체크 예외 IOException을 던진다. Supplier.get()은 체크 예외를 던질 수 없으므로, retrier.retry(() -> channel.send(body), 3)처럼 바로 넘기면 컴파일되지 않는다. sendOnce가 바꿔 주면 retrier.retry(() -> PgCall.sendOnce(opener, body), 3)이 된다.

#상황

D08은 외부 PG를 붙여 포인트 충전을 만드는 날이다. D08 ④ "재시도와 백오프"에서 PgRetryPolicy가 연결 실패만 200ms·400ms 간격으로 다시 보내고, 거절은 다시 보내지 않는다. D08 ① PgClient는 HTTP 라이브러리 예외를 원인을 담은 PgException으로 바꾼다. 오늘은 Spring 없이 같은 재시도 함수 retry(Supplier<T>, int)를 직접 만든다. 람다로 호출을 넘기려면 체크 예외를 언체크 예외로 바꿔야 하고, 연결은 try-with-resources로 반드시 닫고, 바꿀 때 원인을 버리면 장애 때 무엇이 실패했는지 알 수 없다는 것까지 테스트로 확인한다.

#빠른 연상

체크 예외 (IOException, InterruptedException) 언체크 예외 (RuntimeException 하위) TS로 치면
컴파일러가 처리를 강제하나 강제한다. catch 하거나 throws로 선언해야 컴파일된다 강제하지 않는다 TS는 둘 다 강제하지 않는다
람다(Supplier.get()) 안에서 던질 수 있나 없다. get()에 throws가 없다 있다 콜백 안 throw
언제 쓰나 호출한 쪽이 복구할 수 있는 외부 실패 프로그래밍 오류, 또는 체크 예외를 감싸 올릴 때

흔한 착각: "체크 예외를 언체크로 바꾸면 정보가 사라진다". 원인을 생성자 두 번째 인자로 넘기면(new PgUnreachableException(msg, e)) 원래 예외가 getCause()와 스택 트레이스의 Caused by:로 그대로 남는다. 정보가 사라지는 경우는 원인을 넘기지 않을 때다.

#실무 습관

예외 원인 연결과 삼키기. 주어진 LeakyPgCall은 컴파일도 되고 평소에는 잘 돈다. 장애가 나야 문제가 드러난다.

  1. sendSwallowing — 빈 catch. PG에 연결하지 못했는데 null을 돌려준다. 호출한 쪽은 "응답이 비었다"와 "실패했다"를 구분하지 못하고, 로그에도 아무것도 남지 않는다.
  2. sendWithoutCause — new PgUnreachableException("PG 호출 실패")처럼 원인 없이 새 예외를 던진다. 실패한 것은 알지만 연결 거부인지 리셋인지 알 수 없다. 스택 트레이스에 Caused by:가 없다.

과제: PgCall.sendOnce에서 IOException을 바꿀 때 new PgUnreachableException(msg, e)로 원인을 넘긴다.

테스트 — J08HabitTest (각 테스트가 LeakyPgCall이 무엇을 숨기는지 먼저 보여 준다):

확인할 테스트 이름 3개
  • 빈_catch는_실패를_null로_숨기고_PgCall은_예외로_드러낸다
  • 원인_없이_새_예외를_던지면_원래_IOException이_사라진다_PgCall은_원인으로_남긴다
  • 원인을_이어_두면_스택_트레이스에_Caused_by로_원래_예외가_찍힌다

#구현 예시

펼치기▸

왜 이렇게 쓰나:

  1. catch (PgUnreachableException e)처럼 재시도할 예외만 잡으면 "무엇을 다시 보내는가"가 catch 한 줄에 드러난다. 거절이나 버그 예외는 잡히지 않고 그대로 나간다. Exception을 통째로 잡고 다시 고르는 것보다 실수할 곳이 적다.
  2. 기다리는 일을 Sleeper로 주입받으면 테스트는 실제로 기다리지 않고 "몇 ms를 몇 번 기다렸나"만 정확히 확인한다. 실제로 기다리는 테스트는 느리고, 걸린 시간을 범위로만 단언할 수 있다. InterruptedException을 잡으면 인터럽트 표시가 지워지므로 되살려 둔다.
  3. 체크 예외를 언체크로 바꾸는 곳은 람다 경계 한 곳(sendOnce)에 모으고, 바꿀 때 반드시 원인을 넘긴다. try-with-resources는 close 실패를 버리지 않고 원래 예외의 getSuppressed()에 붙이므로, 원인 연결과 함께 쓰면 장애 로그 한 덩어리에 전부 남는다.
