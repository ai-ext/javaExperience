# J04. 인터페이스와 구현, 선언 타입과 실제 타입

> 같은 날: D04 · 소요 30~60분 · 실행 `./gradlew :java-track:test --tests 'J04*'`

## 상황

D04는 게시글 쓰기를 만드는 날이다. ④ `PostService` 인터페이스와 `PostServiceImpl` 구현을 나누고, 컨트롤러는 `PostService` 타입으로만 서비스를 받는다. ① `Post.isWrittenBy(Long memberId)`로 작성자를 판정하고, ③ 태그는 최대 5개로 제한한다.
오늘은 Spring 없이 `DiscountPolicy policy = new RateDiscountPolicy(10)`처럼 선언 타입과 실제 타입이 다른 변수를 만들고, 어떤 메서드가 불리는지 테스트로 확인한다. 추상 클래스로 "할인 상한"을 한 곳에서 강제하는 방법도 인터페이스와 비교한다.

## 빠른 연상

```
DiscountPolicy policy = new RateDiscountPolicy(10);
└─ 선언 타입 ─┘          └──── 실제 타입 ────┘
   무엇을 부를 수 있나       실제로 무엇이 실행되나
```

| | 인터페이스 `DiscountPolicy` | 추상 클래스 `CappedDiscountPolicy` | TS로 치면 |
|---|---|---|---|
| 필드(상태) | 못 가진다(상수만) | 가진다(`maxDiscount`) | `interface` / `abstract class` |
| 생성자 | 없다 | 있다. 자식이 `super(...)`로 부른다 | 같다 |
| 구현 메서드 | `default`·`static`·`private` 메서드(Java 9부터 `private`도). 그 밖의 메서드는 몸통 없는 추상 메서드 | 일반·`final` 메서드 | |
| 여러 개 붙이기 | 클래스 하나가 여러 인터페이스를 구현 | 클래스는 하나만 상속 | 같다 |
| 쓰는 곳 | 바꿔 끼울 약속(정책, 서비스 경계) | 자식이 바꾸면 안 되는 공통 흐름 | |

| 메서드 고르기 | 언제 정하나 | 무엇을 보나 |
|---|---|---|
| 오버라이딩(같은 시그니처를 자식이 다시 씀) | 실행할 때 | **실제 객체**의 타입 |
| 오버로딩(이름만 같고 매개변수 타입이 다름) | 컴파일할 때 | **변수의 선언 타입** |

흔한 착각: "`DiscountPolicy`로 선언했으니 인터페이스의 메서드가 불린다". `discount`는 인터페이스에서 몸통 없는 추상 메서드다. 실행되는 것은 언제나 실제 객체(`RateDiscountPolicy`)의 `discount`다. 반대로 오버로딩된 메서드에 넘길 때는 선언 타입이 고르는 기준이라 `describe(policy)`가 `describe(DiscountPolicy)` 쪽으로 간다.

규칙:

- 정률: 가격의 `ratePercent`%를 깎고 원 단위 아래는 버린다(정수 나눗셈). 할인율은 0~100. 이름은 `"정률 10%"`. 3천만 원 × 100처럼 곱한 값이 `int` 최댓값(약 21억)을 넘어도 맞아야 한다 — 곱하기를 `long`으로 한다.
- 정액: `amount`원을 깎되 가격보다 많이 깎지 않는다. 음수 거절. 이름은 `"정액 3000원"`.
- 상한 정률: 상한은 부모 `CappedDiscountPolicy`의 `final discount`가 적용한다. 자식은 상한 전 할인액(`rawDiscount`)만 채운다(여기서 넘쳐 음수가 되면 상한이 소용없다). 이름은 `"정률 10% (최대 3000원)"`.
- `bestPrice`: 정책마다 `apply`한 가격 중 가장 작은 값. 정책이 없으면 가격 그대로.

주어진 인터페이스와 추상 클래스:

```java
public interface DiscountPolicy {

    int discount(int price);

    String name();

    /** 할인한 뒤의 가격. default 메서드라 구현 클래스가 쓰지 않아도 있다. 안에서 부르는 discount는 실제 객체의 것이다. */
    default int apply(int price) {
        return price - discount(price);
    }
}

public abstract class CappedDiscountPolicy implements DiscountPolicy {

    private final int maxDiscount;

    protected CappedDiscountPolicy(int maxDiscount) { … 음수 거절 … }

    /** final이라 자식이 덮어쓸 수 없다. 상한은 언제나 적용된다. */
    @Override
    public final int discount(int price) {
        return Math.min(rawDiscount(price), maxDiscount);
    }

    /** 상한을 적용하기 전의 할인액. */
    protected abstract int rawDiscount(int price);
}
```

## 타입 한 컷

`==` vs `equals` — 래퍼 타입(`Long`·`Integer`)끼리 `==`는 값이 아니라 **같은 객체인지**를 본다.

| | `long a == long b` | `Long a == Long b` | `Long a.equals(Long b)` |
|---|---|---|---|
| 비교하는 것 | 값 | 참조(같은 객체인가) | 값 |
| `100L`과 `100L`(오토박싱) | true | true (캐시된 같은 객체임이 **보장**된다) | true |
| `128L`과 `128L`(오토박싱) | true | **보장되지 않는다** (지금 JDK는 보통 false) | true |
| `new Long(128)` 두 개 | - | **false** (서로 다른 객체) | true |

오토박싱은 `Long.valueOf`·`Integer.valueOf`를 쓴다. 이 메서드는 -128~127 범위를 미리 만들어 둔 같은 객체로 돌려준다고 API가 약속한다. 그 밖의 값은 캐시할 수도, 안 할 수도 있다(약속이 없다). 그래서 작은 수는 `==`도 맞아 보이고, 큰 수는 맞을지 틀릴지 모른다. 어느 쪽이든 `==`에 기대는 코드는 틀린 코드다.

함정: 주어진 `LeakyAuthorCheck.isWrittenBy(Long, Long)`는 `writerId == memberId`로 비교한다. 개발 DB처럼 id가 작을 때는 통과하다가, 운영에서 id가 커지면 "작성자인데 403"이 날 수 있다. 테스트는 "같은 값, 다른 객체"를 확실히 만들려고 `new Long(128)`을 쓴다(없어질 예정인 생성자라 테스트에서만 쓴다).

과제: `AuthorCheck.isWrittenBy`를 `equals`로 채운다. 두 id 중 하나라도 null이면 false다.

확인 테스트 — `J04TypeCutTest`:

- `Integer와_Long_오토박싱은_마이너스128부터_127까지_같은_객체임이_보장된다` (관찰. 처음부터 통과한다)
- `함정_작은_id는_캐시된_같은_객체라_참조_비교도_맞아_보인다`
- `함정_캐시_범위_밖은_같은_객체라는_보장이_없다_다른_객체면_참조_비교가_틀린다`
- `다른_id거나_null이면_false다`

```java
// RateDiscountPolicy
private final int ratePercent;

public RateDiscountPolicy(int ratePercent) {
    if (ratePercent < 0 || ratePercent > 100) {
        throw new IllegalArgumentException("할인율은 0~100이어야 합니다: " + ratePercent);
    }
    this.ratePercent = ratePercent;
}

@Override
public int discount(int price) {
    // 곱하기를 먼저 해야 한다. 999원 10%를 price / 100 * rate로 하면 99가 아니라 90이 된다.
    // 곱하기는 long으로 한다. int끼리 곱하면 3천만 원 × 100에서 int 범위를 넘어 음수가 된다.
    // 결과는 price 이하라 int로 돌려도 넘치지 않는다
    return (int) ((long) price * ratePercent / 100);
}

@Override
public String name() {
    return "정률 " + ratePercent + "%";
}
```

```java
public FixedDiscountPolicy(int amount) {

        throw new IllegalArgumentException("할인액은 0 이상이어야 합니다: " + amount);

    this.amount = amount;
}

@Override

}

@Override
```

```java
// CappedRateDiscountPolicy
private final int ratePercent;

public CappedRateDiscountPolicy(int ratePercent, int maxDiscount) {
    // 부모 생성자가 먼저 돌아 maxDiscount를 검사하고 담는다
    super(maxDiscount);
    if (ratePercent < 0 || ratePercent > 100) {
        throw new IllegalArgumentException("할인율은 0~100이어야 합니다: " + ratePercent);
    }
    this.ratePercent = ratePercent;
}

@Override
protected int rawDiscount(int price) {
    // 상한은 부모가 나중에 적용한다. 그 전에 넘쳐 음수가 되면 상한이 소용없으므로 long으로 곱한다
    return (int) ((long) price * ratePercent / 100);
}

@Override
public String name() {
    // 부모의 private 필드는 못 보지만 public 메서드 maxDiscount()로 읽는다
    return "정률 " + ratePercent + "% (최대 " + maxDiscount() + "원)";
}
```

```java
// DiscountSelector
public static int bestPrice(int price, List<DiscountPolicy> policies) {
    int best = price;
    for (DiscountPolicy policy : policies) {
        // 선언 타입은 DiscountPolicy지만 실행되는 discount는 실제 객체(정률·정액·상한)의 것이다
        best = Math.min(best, policy.apply(price));
    }
    return best;
}
```

```java
// AuthorCheck
public static boolean isWrittenBy(Long writerId, Long memberId) {

    return writerId != null && writerId.equals(memberId);
```

왜 이렇게 쓰나:

1. 쓰는 쪽(`DiscountSelector`)은 `DiscountPolicy`만 안다. 정책이 하나 늘어도 고칠 곳은 새 구현 클래스 하나다. 실행되는 메서드는 실제 객체가 정하기 때문이다.
2. 모든 자식이 지켜야 하는 규칙(상한)은 추상 클래스의 `final` 메서드에 두고, 자식은 달라지는 계산만 채운다. 상태도 공통 흐름도 없는 약속이면 인터페이스로 충분하다.
3. id처럼 래퍼 타입인 값은 언제나 `equals`로 비교한다. `==`가 맞는다고 보장되는 것은 -128~127뿐이다. 금액 계산은 곱한 값이 `int`를 넘지 않는지도 함께 본다.

## 오늘 Spring에서 다시 만나는 곳

- D04 ① `board-server/src/main/java/com/example/board/post/Post.java` — `isWrittenBy(Long memberId)`가 `member.getId().equals(memberId)`로 비교한다. `==`였다면 id 128부터 작성자 판정이 틀린다.
- D04 ① `board-server/src/main/java/com/example/board/post/PostRepository.java` — `interface PostRepository extends JpaRepository<Post, Long>`. 구현 클래스는 Spring Data가 실행할 때 만든다. 쓰는 쪽은 인터페이스 타입만 안다.
- D04 ③ `board-server/src/main/java/com/example/board/post/PostCreateRequest.java` — `@Size(max = 5) List<@NotBlank @Size(max = 20) String> tags`. 오늘 `TagCleaner`는 거르고 자르지만, 요청 DTO는 규칙을 어기면 400으로 거절한다.
- D04 ④ `board-server/src/main/java/com/example/board/post/PostService.java` — 서비스 경계의 인터페이스. 컨트롤러는 `PostService` 타입으로 받는다(선언 타입 `PostService`, 실제 타입 `PostServiceImpl`).
- D04 ④ `board-server/src/main/java/com/example/board/post/PostServiceImpl.java` — `implements PostService`, 메서드마다 `@Override`. `List.copyOf(new LinkedHashSet<>(request.tags()))`로 입력 순서를 지키며 중복 태그를 없앤다(오늘 `TagCleaner`와 같은 방법). 이날 함정은 "구현이 하나뿐인 곳마다 인터페이스를 만들면 과잉"이다.
- D05 ③ `board-server/src/main/java/com/example/board/comment/Comment.java` — 댓글도 `isWrittenBy(Long memberId)`를 `equals`로 비교한다.
- D07 ⑥ `board-server/src/main/java/com/example/board/shop/OrderService.java` — 쿠폰 할인이 `total - total * COUPON_DISCOUNT_PERCENT / 100`이다. 곱하기를 먼저 하고 나누는 오늘의 정률 계산과 같다. board-server는 할인 방식이 하나뿐이라 `DiscountPolicy` 같은 인터페이스를 두지 않았다.
