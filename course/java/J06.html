#상황

D06은 목록·검색을 MyBatis로 만드는 날이다. ③ 커서 페이징을 위해 CursorPage<T>를 만들고, 한 건 더 읽어 와서 다음 쪽이 있는지 판단한다. 같은 CursorPage를 D07에서 포인트 이력에도 그대로 쓴다. 오늘은 Spring 없이 어떤 행이든 담는 제네릭 CursorPage<T>와, 커서 목록의 정렬 기준(최신순·인기순)을 Comparator로 만든다. 단건 조회에서 자주 쓰는 Optional의 orElse·orElseGet 차이도 직접 터뜨려 본다.

#빠른 연상

문법 읽는 법 쓰는 곳 TS로 치면
class CursorPage<T> 만들 때 T가 정해지는 클래스 CursorPage<PostRow> class CursorPage<T>
static <T> T first(List<T> list) 이 메서드만의 T. 부를 때 인자로 정해진다 CursorPage.of(rows, 20) function first<T>(list: T[])
<T extends HasId> T는 HasId의 하위 타입이어야 한다 → t.id()를 부를 수 있다 of(...) <T extends HasId>
List<? extends HasId> HasId의 어떤 하위 타입 목록. 꺼내 읽기만 한다 List<PostRow>도 List<CommentRow>도 받는다 readonly HasId[]
Comparator<? super T> T나 T의 상위 타입을 비교하는 것. T를 넣어 비교만 한다 Comparator<HasId>로 PostRow를 정렬 (TS는 이 구분이 느슨하다)

외우는 말: 꺼내 쓰면(생산자) extends, 넣어 쓰면(소비자) super.

흔한 착각: "PostRow가 HasId의 하위 타입이니 List<PostRow>도 List<HasId>의 하위 타입이다". 아니다. List<HasId>에는 CommentRow를 add할 수 있는데 List<PostRow>에는 안 되기 때문이다. 그래서 List<HasId> 매개변수에는 List<PostRow>를 넘길 수 없고, 읽기만 할 때 List<? extends HasId>로 받는다.

규칙:

  • CursorPage.of(fetched, size): 저장소는 size+1건을 읽어 온다. size보다 많으면 앞의 size건만 담고 마지막 항목의 id를 nextCursor로, 아니면 전부 담고 nextCursor는 null.
  • map(mapper): 항목만 바꾸고 커서는 그대로(엔티티 쪽 → DTO 쪽).
  • 최신순은 id 내림차순, 인기순은 좋아요 내림차순 → 같으면 id 내림차순(커서가 한 줄로 정해지게).
  • pageAfter(rows, cursor, order, size): order로 정렬했을 때 cursor 바로 다음부터 size건. cursor가 null이면 처음부터, cursor 자신은 담지 않는다.

#타입 한 컷

Optional — 단건 조회의 "있을 수도, 없을 수도".

orElse(x) orElseGet(() -> x) orElseThrow(() -> e)
받는 것 이미 계산된 값 값을 만드는 방법(함수) 예외를 만드는 방법(함수)
값이 있을 때 인자 그래도 먼저 계산된다 실행하지 않는다 실행하지 않는다
쓰는 곳 상수·이미 있는 값(orElse("")) 만드는 데 비용·부수 효과가 있는 기본값 없으면 404
자리 Optional을 쓰나 이유
반환 타입 쓴다 "없을 수 있음"을 호출하는 쪽에 강제한다
매개변수 쓰지 않는다 부르는 쪽이 null을 넘기면 막을 수 없다. 그냥 null 가능한 타입으로 받는다
필드 쓰지 않는다 직렬화되지 않고(Serializable이 아니다), 필드 자체가 null일 수 있다

함정: repository.findById(id).orElse(factory.create())는 쿠폰이 있어도 create()를 실행한다. Java는 메서드를 부르기 전에 인자를 먼저 계산하기 때문이다. create()가 DB 저장이면 쓸데없는 행이 쌓인다(주어진 LeakyCouponLookup).

과제: CouponLookup을 채운다. 기본 쿠폰은 없을 때만 만들고(orElseGet), 없으면 404 예외(orElseThrow), 검색어는 String으로 받아 Optional<String>으로 돌려준다.

확인 테스트 — J06TypeCutTest:

  • 함정_orElse는_값이_있어도_인자를_먼저_실행한다_orElseGet은_없을_때만_실행한다
  • 없으면_orElseGet이_그때_기본_쿠폰을_만든다
  • orElseThrow로_없는_쿠폰을_404_예외로_바꾼다
  • 함정_Optional_매개변수에는_null이_들어올_수_있다_Optional은_반환_타입에만_쓴다 (LeakyPostSearch가 먼저 터진다)
  • 함정_Optional_필드는_그_자체가_null일_수_있고_직렬화도_되지_않는다 (관찰. 테스트 안의 작은 클래스로 확인한다. 처음부터 통과한다)

// CursorPage
public static <T extends HasId> CursorPage<T> of(List<? extends T> fetched, int size) {
    boolean hasNext = fetched.size() > size;
    // List<? extends T>에서 꺼낸 값은 T로 읽을 수 있다. copyOf가 List<T>로 담아 준다
    List<T> items = List.copyOf(hasNext ? fetched.subList(0, size) : fetched);
    Long nextCursor = hasNext ? items.get(items.size() - 1).id() : null;
    return new CursorPage<>(items, nextCursor);
}

public <R> CursorPage<R> map(Function<? super T, ? extends R> mapper) {
    // 이 메서드만의 타입 매개변수 R은 부를 때 mapper의 반환 타입으로 정해진다
    List<R> mapped = items.stream().<R>map(mapper).toList();
    return new CursorPage<>(mapped, nextCursor);
}
// CursorOrders
public static Comparator<HasId> byIdDesc() {
    // 빼기로 비교하지 않는다. comparingLong은 Long.compare를 써서 넘치지 않는다
    return Comparator.comparingLong(HasId::id).reversed();
}

public static Comparator<PostRow> popular() {
    // thenComparing은 Comparator<? super PostRow>를 받으므로 Comparator<HasId>를 그대로 넘길 수 있다
    return Comparator.comparingInt(PostRow::likeCount).reversed()
            .thenComparing(byIdDesc());
}

public static <T> List<T> pageAfter(List<T> rows, T cursor, Comparator<? super T> order, int size) {
    return rows.stream()
            .sorted(order)
            // 정렬 기준에서 cursor보다 뒤(compare > 0)인 것만 남긴다. 같은 행(compare == 0)은 빠진다
            .filter(row -> cursor == null || order.compare(row, cursor) > 0)
            .limit(size)
            .toList();
}
// TagRanking
public static List<TagCount> rank(List<List<String>> tagsOfPosts) {
    Map<String, Long> counts = tagsOfPosts.stream()
            .flatMap(List::stream)
            .collect(Collectors.groupingBy(Function.identity(), Collectors.counting()));
    return counts.entrySet().stream()
            .map(entry -> new TagCount(entry.getKey(), entry.getValue()))
            // 첫 기준을 뒤집은 뒤 thenComparing을 붙인다. 순서를 바꾸면 이름까지 뒤집힌다
            .sorted(Comparator.comparingLong(TagCount::count).reversed()
                    .thenComparing(TagCount::tag))
            .toList();
}
// CouponLookup
public Coupon findOrDefault(long id) {
    // orElseGet은 "만드는 방법"을 받는다. 값이 없을 때만 그 방법을 실행한다
    return repository.findById(id).orElseGet(factory::create);
}

public Coupon getOrThrow(long id) {
    return repository.findById(id).orElseThrow(() -> new NotFoundException("쿠폰", id));
}

public static Optional<String> normalizeKeyword(String keyword) {
    return Optional.ofNullable(keyword)
            .map(String::strip)
            .filter(stripped -> !stripped.isEmpty());
}

왜 이렇게 쓰나:

  1. 커서 페이징의 "한 건 더 읽고 잘라서 마지막 id를 커서로" 규칙은 행 종류와 상관없다. 그래서 CursorPage<T> 하나에 두고, 필요한 능력(id())만 T extends HasId로 요구한다. 읽기만 하는 인자는 ? extends, 비교기처럼 값을 넣어 쓰는 인자는 ? super로 받아 더 많은 타입을 받아 준다.
  2. 커서 정렬은 동점이 없게 마지막에 id를 붙인다(thenComparing(byIdDesc())). 좋아요가 같은 글이 여럿이면 "커서 다음"이 하나로 정해지지 않기 때문이다. 비교는 빼기가 아니라 comparingLong(Long.compare)으로 한다.
  3. 기본값을 만드는 데 비용이나 부수 효과가 있으면 orElseGet, 없으면 예외로 바꿀 때는 orElseThrow를 쓴다. Optional은 반환 타입에만 쓰고 매개변수는 null 가능한 일반 타입으로 받는다.
