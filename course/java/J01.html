#빠른 연상

일반 클래스 Member record MemberProfile TS로 치면
필드 직접 선언, private으로 숨김 괄호 안 구성 요소가 곧 private final 필드 class의 private 필드 / readonly 객체
생성자 직접 작성, 여기서 값 검사 자동 생성. 검사는 compact 생성자 MemberProfile { … }에 constructor
getter 직접 작성 getEmail() 자동 생성 email() 프로퍼티 접근
equals 안 만들면 **같은 객체인지(주소)**만 비교 모든 필드 값으로 비교 === / 값 비교 함수
값 바꾸기 메서드로 허용할 수 있음 못 바꾼다(새로 만든다) Readonly<T>

흔한 착각: "final List<String> tags면 태그 목록이 안 바뀐다". final은 다른 리스트를 대입하지 못하게 할 뿐이다. 리스트 안에 add하는 것은 막지 않는다. 그리고 getter가 그 리스트를 그대로 내주면 밖에서도 add할 수 있다. J00에서 본 "참조가 복사된다"가 엔티티에서 터지는 모양이다.

#타입 한 컷

int vs Integer — 요청 DTO에서 "값 없음"과 "0"을 구분해야 하는 이유.

int (기본형) Integer (래퍼)
null을 담을 수 있나 없다 있다
필드 기본값 0 null
요청에 값이 없을 때 0이 들어가 "안 보냄"과 "0을 보냄"을 구분 못 한다 null이 들어가 "안 보냄"을 알 수 있다
제네릭에 쓰기 List<int> 불가 List<Integer>

함정: Integer가 null인데 int로 받으면(int size = request.size();) 언박싱하는 순간 NullPointerException이 난다. 그래서 null을 먼저 처리한 메서드(sizeOrDefault)로 꺼낸다.

과제: PostListRequest(Integer size)를 채운다. size를 보내지 않으면(null) 기본값 20을 쓰고, 보냈다면 1~50만 받는다. 0은 "값 없음"이 아니라 잘못된 값이다.

확인 테스트 — J01TypeCutTest:

확인할 테스트 이름 5개
  • 대입하지_않은_필드는_int면_0이고_Integer면_null이다 (관찰. 테스트 안의 작은 클래스로 필드 기본값을 직접 본다. 처음부터 통과한다)
  • size를_보내지_않으면_null로_받고_기본값_20을_쓴다
  • 보낸_size가_범위_안이면_그대로_쓴다 (1, 20, 50)
  • size_0은_값_없음이_아니라_잘못된_값이라_거절한다 (0, -1, 51)
  • 함정_null인_Integer를_int로_꺼내면_NPE가_난다

#실무 습관

서로 독립인 두 참조 사고

독립 사례참조 관계실행해 비교할 것
A · getter 노출외부 변수 → 같은 리스트 ← 객체 필드외부 add 전후 태그 값
B · 불변 입력List.of() → 같은 리스트 ← 객체 필드객체의 addTag 실행 결과

A와 B는 시간 순서가 아니다. 입력 리스트 복사·외부에 내주는 리스트를 각각 바꾼 뒤 기존 테스트로 확인한다.

불변 컬렉션과 방어적 복사. 주어진 LeakyPost는 받은 리스트를 그대로 필드에 담고, getter로 그대로 내준다. 그래서 두 가지 사고가 난다.

  1. 독립 사례 A

    외부 변수→같은 리스트←LeakyPost.tags

    getter로 받은 리스트에 밖에서 add하면 글의 태그가 바뀐다(addTag를 거치지 않는다).
  2. 독립 사례 B

    List.of()→같은 불변 리스트←LeakyPost.tags

    생성자에 List.of()를 넘기면 그 불변 리스트를 그대로 쓰게 되어, 나중에 addTag가 UnsupportedOperationException으로 터진다.

과제: Post를 채워 두 사고를 막는다. 받은 리스트는 내 리스트로 복사해 담고, getter는 밖에서 고칠 수 없는 리스트를 내준다.

테스트 — J01HabitTest (각 테스트가 LeakyPost가 어떻게 터지는지 먼저 보여 준다):

확인할 테스트 이름 4개
  • getter가_내부_리스트를_내주면_밖에서_글이_바뀐다_Post는_막는다
  • 생성자에_넘긴_리스트를_밖에서_바꿔도_글의_태그는_그대로다
  • List_of를_넘겨도_addTag가_된다
  • 태그는_addTag로만_바뀐다
✓ 확인끝났는지 판단

#구현 예시

펼치기▸

왜 이렇게 쓰나:

  1. 검사를 생성자와 changeNickname에 모아 두면 "만들어진 Member는 언제나 규칙을 지킨다"가 보장된다. 필드가 private이라 이 길을 우회할 방법이 없다.
  2. 요청 값은 "안 보냄"이 의미를 가지므로 Integer로 받고, 꺼내는 곳은 null을 처리한 메서드 하나로 모은다. 기본형으로 받으면 0과 구분할 수 없다.
  3. 리스트 필드는 들어올 때 복사하고(new ArrayList<>(tags)) 나갈 때 읽기 전용으로 내준다(Collections.unmodifiableList). 그래야 태그가 addTag 한 곳에서만 바뀐다. 호출할 때마다 그 시점의 복사본을 내주고 싶으면 List.copyOf(tags)를 쓴다.
