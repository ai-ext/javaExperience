#상황

D05는 조회·수정·삭제를 만드는 날이다. ① 글 상세 조회에서 엔티티를 응답 DTO로 바꾸고, 없는 글은 Optional의 orElseThrow로 404를 낸다. ④ 댓글 목록은 엔티티 목록을 stream().map(CommentResponse::from).toList()로 바꿔 내보낸다. 먼저 Spring 없이 엔티티 목록을 for와 stream으로 각각 DTO 목록으로 바꾼다. 두 결과를 비교한 뒤 다음 과제로 이동한다.

#빠른 연상

for 반복문 stream JS로 치면
List<PostResponse> result = new ArrayList<>(); posts.stream() posts
if (post.getStatus() == ACTIVE) .filter(post -> post.getStatus() == ACTIVE) .filter(...)
result.add(PostResponse.from(post)) .map(PostResponse::from) .map(...)
return result; .toList() (배열이 바로 나옴)
찾으면 return, 없으면 null .findFirst() → Optional<T> .find() → T | undefined

흔한 착각: "for를 stream으로 바꾸면 원래 리스트가 바뀐다". stream은 원본을 건드리지 않고 새 리스트를 만든다. 반대로 원본에서 지워야 할 때는 for 안에서 remove하지 말고 removeIf를 쓴다. .toList()가 돌려준 리스트는 고칠 수 없다(J01의 List.of와 같다).

#타입 한 컷

제네릭에는 왜 래퍼만 쓰나(List<int> 불가), 그리고 합계는 기본형 stream으로.

Stream<Integer> IntStream LongStream
담는 것 Integer 객체 int 값 long 값
만드는 법 list.stream() .mapToInt(Post::getLikeCount) .mapToLong(Post::getLikeCount)
sum() 없다(reduce로) 있다, int로 돌려줌 있다, long으로 돌려줌
넘침 - 21억을 넘으면 조용히 음수 넉넉하다

제네릭(List<T>, Map<K, V>)의 T에는 객체만 들어간다. 그래서 List<int>는 만들 수 없고 List<Integer>로 담는다(컴파일 오류라 테스트로 확인하지 않고 설명으로 다룬다). 숫자를 많이 다룰 때는 박싱이 없는 IntStream·LongStream으로 바꿔 계산한다.

함정: List<Integer>의 remove는 두 개다. remove(int index)는 위치로, remove(Object o)는 값으로 지운다. counts.remove(0)은 값 0이 아니라 0번 자리를 지운다.

과제: LikeSums.totalLikes(넘치지 않게 long으로)와 LikeSums.removeValue(값으로 지우기)를 채운다.

확인 테스트 — J05TypeCutTest:

확인할 테스트 이름 3개
  • 좋아요_합계는_mapToLong으로_구한다
  • 함정_int로_더하면_21억을_넘을_때_음수가_된다
  • 함정_List_Integer의_remove에_int를_넘기면_값이_아니라_위치를_지운다

#실무 습관

Map 실무 API. get으로 꺼내 고친 뒤 put하는 코드는 처음 보는 키에서 NPE가 난다(get이 null을 돌려준다).

하고 싶은 일 터지는 코드 실무 API
없으면 기본값으로 읽기 map.get(k) → null map.getOrDefault(k, List.of())
없으면 만들고 거기에 담기 map.get(k).add(v) → NPE map.computeIfAbsent(k, key -> new ArrayList<>()).add(v)
세기·더하기 map.put(k, map.get(k) + 1) → NPE map.merge(k, 1, Integer::sum)

과제: TagIndex를 채운다. add는 태그별 글 id 목록에 더하고, postIdsOf는 목록의 고칠 수 없는 복사본(List.copyOf)을, 없는 태그면 빈 리스트를, countTags는 태그별 등장 횟수를 돌려준다. 내부 리스트를 그대로 내주면 받은 쪽의 clear() 한 번에 색인이 비워진다(J01에서 막은 내부 리스트 노출과 같은 함정).

테스트 — J05HabitTest:

확인할 테스트 이름 5개
  • 함정_처음_보는_키를_get으로_꺼내_add하면_NPE다_computeIfAbsent는_리스트를_만든다
  • computeIfAbsent는_있는_키에는_새로_만들지_않고_이어_붙인다
  • 없는_태그를_찾으면_getOrDefault로_빈_리스트를_돌려준다
  • 돌려준_목록을_고쳐도_색인_안의_목록은_바뀌지_않는다
  • 함정_get에_1을_더해_넣으면_처음_보는_키에서_NPE다_merge는_없으면_1로_넣는다

#구현 예시

펼치기▸

왜 이렇게 쓰나:

  1. 엔티티 → DTO 변환은 DTO의 static 팩토리(from) 한 곳에 두고, 목록은 map(PostResponse::from)으로 바꾼다. 어떤 값을 내보내는지가 한 곳에 모인다.
  2. "없을 수도 있는 하나"는 Optional로 돌려준다. 받는 쪽이 orElseThrow로 404를 내거나 isEmpty로 갈라야 해서 null을 잊고 지나칠 수 없다.
  3. 숫자를 모을 때는 기본형 stream(mapToLong)으로, Map에 모을 때는 computeIfAbsent·merge로 쓴다. get으로 꺼내 고치는 코드는 처음 보는 키에서 터진다.
