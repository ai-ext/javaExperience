# J07. Map·Set과 스레드: 잔액 갱신 손실 재현하고 고치기

> 같은 날: D07 · 소요 30~60분 · 실행 `./gradlew :java-track:test --tests 'J07*'`

## 상황

D07은 포인트·쿠폰 상점을 만드는 날이다. ① 포인트를 적립할 때 "잔액을 읽어 더한 뒤 저장"하면 동시 적립에서 갱신이 사라지므로 `UPDATE … SET point_balance = point_balance + ?`로 바꾼다. ④ 쿠폰 발급 버튼을 연타하면 "이미 받았나" 조회가 두 요청 모두 통과한다.
오늘은 DB 없이 같은 사고를 순수 Java로 재현한다. 두 스레드가 같은 잔액을 읽게 만들어 적립 하나가 사라지는 것을 확실히 보고, `synchronized`와 `AtomicInteger`로 고친다. 여러 스레드가 함께 쓰는 `Map`·`Set`도 같은 원리로 고른다.

## 빠른 연상

```
스레드 A: 잔액 읽기(0) ─────────────── 0+10 쓰기 → 10
스레드 B:        잔액 읽기(0) ── 0+10 쓰기 → 10        결과 10 (20이어야 한다)
```

| | 이전 (`LeakyPointWallet`) | `synchronized` | `AtomicInteger` |
|---|---|---|---|
| 방법 | 읽고 → 더해서 쓰기 | 한 번에 한 스레드만 메서드 안에 들어온다(잠금) | 읽은 값이 **그대로일 때만** 바꾼다(`compareAndSet`), 실패하면 다시 읽는다 |
| 기다림 | 없다(대신 손실) | 다른 스레드는 입구에서 기다린다 | 기다리지 않고 다시 시도한다 |
| DB로 치면 | `SELECT` 후 `UPDATE … SET balance = 읽은값+10` | `SELECT … FOR UPDATE`(비관적 잠금) | `UPDATE … WHERE balance = 읽은값`(낙관적 갱신) |
| board-server가 쓴 방법 | | | 한 문장 `UPDATE … SET balance = balance + ?` |

JS는 한 스레드에서 돌아서 `balance += 10` 사이에 다른 코드가 끼지 않는다. Java 서버는 요청마다 다른 스레드가 같은 객체(싱글톤 빈)를 동시에 쓴다.

흔한 착각: "`balance += 10`은 한 줄이니 한 번에 일어난다". 컴파일되면 읽기·더하기·쓰기 세 단계다. 그 사이에 다른 스레드가 끼어들 수 있다. 테스트에서 잘 안 터지는 것은 틈이 아주 짧기 때문이다. 그래서 오늘은 틈을 일부러 벌려 매번 터지게 한다.

틈(`betweenReadAndWrite`): 지갑은 생성자로 `Runnable` 하나를 받아 **읽은 뒤 쓰기 전에** 한 번 부른다. 테스트는 여기에 `CountDownLatch`를 넣어 "두 스레드가 모두 잔액을 읽을 때까지 기다리기"를 시킨다. 그래서 `LeakyPointWallet`은 매번 둘이 같은 0을 읽고 손실이 난다. 고친 지갑도 이 틈을 반드시 거쳐야 한다(테스트가 불린 횟수를 센다).

규칙:

- `SynchronizedPointWallet.earn`: 읽기 → `betweenReadAndWrite.run()` → 쓰기. 메서드에 `synchronized`를 붙인다. `balance()`도 같은 잠금으로 읽는다.
- `AtomicPointWallet.earn`: `get()` → `betweenReadAndWrite.run()` → `compareAndSet(읽은 값, 읽은 값 + amount)`. 실패하면 `get()`부터 다시.
- `MemberPoints`: 회원별 잔액을 `ConcurrentHashMap`에 담는다. 더할 때는 `merge` 한 번으로.
- `CouponIssuer.issue`: 처음 받는 회원이면 true. `contains`로 확인하고 `add`하지 말고, `add`의 반환값을 쓴다.

## 타입 한 컷

`boolean` vs `Boolean`, `is` 접두어와 JSON 직렬화 — 응답 필드 이름이 바뀌는 문제.

| | `boolean` | `Boolean` |
|---|---|---|
| 값 | true·false | true·false·**null** |
| 쓰는 곳 | 응답의 상태 값(언제나 정해짐) | 요청·설정에서 "보내지 않음"을 구분할 때 |
| Lombok `@Getter` (필드 `used`) | `isUsed()` | `getUsed()` |
| Lombok `@Getter` (필드 `isExpired`) | `isExpired()` (접두어를 겹치지 않는다) | `getIsExpired()` |

JSON 라이브러리(Jackson)는 필드가 아니라 **getter 이름**으로 응답 이름을 정한다. `isExpired()`는 `expired`, `getIsExpired()`는 `isExpired`로 나간다.

| 필드 선언 | Lombok이 만든 getter | 응답 JSON 이름 |
|---|---|---|
| `boolean used` | `isUsed()` | `used` |
| `boolean isExpired` | `isExpired()` | **`expired`** (필드 이름과 다르다) |
| `boolean issued` | `isIssued()` | `issued` ("is" 다음이 소문자라 접두어가 아니다) |
| `Boolean isExpired` | `getIsExpired()` | **`isExpired`** |
| `Boolean autoRenew` | `getAutoRenew()` | `autoRenew` |

함정 두 가지:

1. `boolean isExpired`로 이름 지으면 응답에는 `expired`로 나간다. 프런트엔드가 `response.isExpired`를 읽으면 `undefined`다.
2. 나중에 null을 담으려고 타입만 `Boolean`으로 바꾸면 getter가 `getIsExpired()`가 되어 응답 이름이 `isExpired`로 바뀐다. 코드 한 글자 안 바꾼 클라이언트가 깨진다.

그래서 boolean 필드는 `is`를 붙이지 않고 `expired`처럼 짓는다. record는 구성 요소 이름이 그대로 응답 이름이 된다(Jackson 2.18·3.1에서 `record R(boolean isUsed)` → `"isUsed"` 확인).

이 모듈에는 Jackson이 없어서, 같은 이름 규칙을 쓰는 JDK의 `java.beans.Introspector`로 확인한다. 위 표의 getter 모양에서는 Jackson(2.18·3.1)과 Introspector의 결과가 같다. 다만 `Boolean`을 돌려주는 `isX()`를 손으로 쓰면 Jackson은 `x`로 내보내고 Introspector는 프로퍼티로 보지 않는다. 라이브러리마다 다르니 그런 getter는 만들지 않는다.

과제: `JsonNames.jsonName(Field)`를 채운다. 기본형 `boolean`이고 이름이 "is" + 대문자로 시작하면 "is"를 떼고 첫 글자를 소문자로, 아니면 필드 이름 그대로다. `jsonNames(Class)`는 인스턴스 필드마다 선언 순서대로 모은다.

확인 테스트 — `J07TypeCutTest`:

- `getter_이름_규칙대로_필드마다_응답_이름을_구한다` (`Introspector`가 찾은 이름과 같은지도 본다)
- `함정_boolean_필드를_isExpired로_지으면_응답_필드는_expired가_된다`
- `함정_null을_담으려고_Boolean으로만_바꿔도_getIsExpired가_되어_응답_이름이_isExpired로_바뀐다`
- `is_다음이_소문자면_접두어가_아니라_issued는_그대로다`

## 실무 습관

Map 함정 두 가지.

| 함정 | 터지는 모양 | 고치는 법 |
|---|---|---|
| `Collectors.toMap(키, 값)`에 같은 키가 두 번 나옴 | `IllegalStateException: Duplicate key 자바초보` | 세 번째 인자로 합치는 함수 `(first, later) -> first` |
| `HashMap`을 돌면 순서가 섞임 | 넣은 순서도 키 순서도 약속하지 않는다. 데이터가 바뀌면 순서도 바뀐다 | 넣은 순서: `LinkedHashMap`, 키 순서: `TreeMap` |

`toMap`의 기본 결과는 `HashMap`이다. 순서가 필요하면 네 번째 인자로 `LinkedHashMap::new`를 넘긴다.

과제: `NicknameIndex`를 채운다. 닉네임 중복 검사가 생기기 전의 옛 데이터라 같은 닉네임이 섞여 있다. 먼저 나온 회원의 id를 남기고, 닉네임이 처음 나온 순서를 지킨다. `sortedById`는 id 오름차순으로 도는 `Map`을 돌려준다.

테스트 — `J07HabitTest`:

- `함정_toMap은_같은_키가_두_번_나오면_IllegalStateException이다`
- `같은_닉네임이면_먼저_나온_회원의_id를_남긴다`
- `결과를_돌면_닉네임이_처음_나온_순서대로_나온다`
- `id_오름차순으로_도는_Map을_돌려준다`

```java
// AtomicPointWallet
private final AtomicInteger balance = new AtomicInteger(0);

public AtomicPointWallet(Runnable betweenReadAndWrite) {
    this.betweenReadAndWrite = betweenReadAndWrite;
}

public void earn(int amount) {
    while (true) {
        int current = balance.get();
        betweenReadAndWrite.run();
        // 지금 값이 아직 current일 때만 바꾼다. 그 사이 누가 바꿨으면 false → 새 값을 다시 읽는다
        if (balance.compareAndSet(current, current + amount)) {
            return;
        }
    }
}

public int balance() {
    return balance.get();
}
```

틈이 없다면 `balance.addAndGet(amount)` 한 줄이 같은 결과를 원자적으로 낸다. 오늘은 틈을 거쳐야 해서 되풀이를 직접 썼다.

```java
// MemberPoints
public void earn(long memberId, long amount) {
    // ConcurrentHashMap.merge는 "읽고 합쳐서 쓰기"를 그 키에 대해 한 번에(원자적으로) 한다.
    // get으로 읽고 put으로 쓰면 그 사이에 다른 스레드가 끼어 LeakyPointWallet과 같은 손실이 난다
    balances.merge(memberId, amount, Long::sum);
}

public long balanceOf(long memberId) {
    return balances.getOrDefault(memberId, 0L);
}

// CouponIssuer
public boolean issue(long memberId) {
    // contains로 확인한 뒤 add하면 두 요청이 둘 다 "없음"을 본다. add는 넣었으면 true, 이미 있었으면 false
    return issuedMemberIds.add(memberId);
}

public int issuedCount() {
    return issuedMemberIds.size();
}
```

```java
// PointBasics
public static Map<Long, List<PointEntry>> groupByMember(List<PointEntry> entries) {
    Map<Long, List<PointEntry>> byMember = new HashMap<>();
    for (PointEntry entry : entries) {
        byMember.computeIfAbsent(entry.memberId(), id -> new ArrayList<>()).add(entry);
    }
    return byMember;
}

public static Map<Long, Long> balances(Map<Long, List<PointEntry>> entriesByMember) {
    Map<Long, Long> balances = new HashMap<>();
    for (Map.Entry<Long, List<PointEntry>> member : entriesByMember.entrySet()) {
        long sum = 0;
        for (PointEntry entry : member.getValue()) {
            sum += entry.amount();
        }
        balances.put(member.getKey(), sum);
    }
    return balances;
}
```

```java
// JsonNames
public static String jsonName(Field field) {
    String name = field.getName();
    // boolean.class는 기본형, Boolean.class는 래퍼. 래퍼 필드의 getter는 getIsHidden()이라 이름이 그대로 남는다
    boolean primitiveBoolean = field.getType() == boolean.class;
    if (primitiveBoolean && name.length() > 2 && name.startsWith("is") && Character.isUpperCase(name.charAt(2))) {
        return Character.toLowerCase(name.charAt(2)) + name.substring(3);
    }
    return name;
}

public static List<String> jsonNames(Class<?> type) {
    List<String> names = new ArrayList<>();
    for (Field field : type.getDeclaredFields()) {
        if (!Modifier.isStatic(field.getModifiers())) {
            names.add(jsonName(field));
        }
    }
    return names;
}
```

```java
// NicknameIndex
public static Map<String, Long> firstIdByNickname(List<MemberRow> rows) {
    return rows.stream().collect(Collectors.toMap(
            MemberRow::nickname,
            MemberRow::id,
            // 같은 키가 또 나오면 어느 값을 남길지 정한다. 이 인자가 없으면 IllegalStateException
            (first, later) -> first,
            // 기본은 HashMap이라 순서가 섞인다. 넣은 순서를 지키는 Map을 만들게 한다
            LinkedHashMap::new));
}

public static Map<Long, Long> sortedById(Map<Long, Long> balances) {
    // TreeMap은 키를 정렬해 담는다
    return new TreeMap<>(balances);
}
```

왜 이렇게 쓰나:

1. 여러 스레드가 함께 쓰는 값은 "읽고 → 계산하고 → 쓰기"가 끊기지 않게 한다. 잠그거나(`synchronized`), 읽은 값이 그대로일 때만 바꾸거나(`compareAndSet`), 그 일을 한 번에 해 주는 API(`merge`, `Set.add`)를 쓴다. DB에서는 같은 일을 한 문장 `UPDATE … SET x = x + ?`와 UNIQUE 제약이 한다.
2. 응답 DTO의 boolean 필드는 `is`를 붙이지 않고 짓는다. getter 이름이 응답 이름을 정하므로, 필드 이름이나 타입(`boolean` ↔ `Boolean`)만 바꿔도 API가 바뀔 수 있다.
3. `toMap`에는 중복 키를 어떻게 합칠지와 어떤 `Map`에 담을지를 적어 둔다. 순서가 의미 있는 결과를 `HashMap`에 담지 않는다.

- D03 ① `board-server/src/main/java/com/example/board/config/ProblemDetailSecurityHandler.java` — 401·403 응답 본문을 `new LinkedHashMap<>()`에 담는다. JSON 필드가 넣은 순서(`type`, `title`, `status`…)대로 나간다.
- D05 ② `board-server/src/main/java/com/example/board/post/PostPatchRequest.java` — `@AssertTrue public boolean isAnyFieldPresent()`. `is`로 시작하는 boolean 메서드라 JavaBeans getter 규칙에 맞는다. Bean Validation은 메서드 검증 애노테이션을 getter에 붙였을 때 프로퍼티로 보고 검사한다(`checkAnyField()`처럼 getter 규칙에 맞지 않는 이름이면 빈 검증 대상이 아니다).
- D07 ① `board-server/src/main/java/com/example/board/point/PointService.java` — `earn`이 `memberRepository.addBalance(memberId, amount)`(한 문장 `UPDATE … SET pointBalance = pointBalance + :amount`)로 더한다. 오늘 `LeakyPointWallet`의 "읽고 더해 쓰기"를 DB가 한 번에 하게 바꾼 것이다.
- D07 ③ `board-server/src/main/java/com/example/board/coupon/CouponRepository.java` — 발급 수량을 `issued_quantity < total_quantity`일 때만 올리고 영향 행 수로 판정한다. `compareAndSet`처럼 "조건이 맞을 때만 바꾸고, 바뀌었는지로 판단"한다.
- D07 ④ `board-server/src/main/java/com/example/board/coupon/CouponService.java` — 1인 1매를 UNIQUE(`coupon_id`, `member_id`) 위반으로 막고 409로 바꾼다. 오늘 `Set.add`가 false를 돌려주는 것과 같은 판단을 DB 제약이 한다.
- D09 ⑤ `board-server/src/main/java/com/example/board/point/ActivityRankingService.java` — `Collectors.toMap(Member::getId, Member::getNickname)`. 키가 회원 id라 중복이 없으므로 합치는 함수 없이 쓴다. 키가 닉네임이었다면 오늘의 함정에 걸린다.
