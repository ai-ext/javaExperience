# J01. 클래스·생성자·record와 참조 복사

> 같은 날: D01 · 소요 30~60분 · 실행 `./gradlew :java-track:test --tests 'J01*'`

## 상황

D01은 프로젝트 뼈대를 세우는 날이다(헬스 체크, DB 연결, 프로파일, 요청 ID 필터). D01 ④ `RequestIdFilter`부터 `public static final` 상수와 `private` 필드가 나오고, D03에서는 `Member` 엔티티와 가입 요청 record를 만든다.
오늘은 Spring 없이 `Member`를 직접 만들어 본다. 생성자에서 잘못된 값을 거절하는 클래스, 값으로 비교되는 record, 그리고 객체를 메서드에 넘기면 참조가 복사된다는 사실이 엔티티의 리스트 필드에서 어떤 사고로 이어지는지 확인한다.

## 빠른 연상

| | 일반 클래스 `Member` | `record MemberProfile` | TS로 치면 |
|---|---|---|---|
| 필드 | 직접 선언, `private`으로 숨김 | 괄호 안 구성 요소가 곧 `private final` 필드 | `class`의 `private` 필드 / `readonly` 객체 |
| 생성자 | 직접 작성, 여기서 값 검사 | 자동 생성. 검사는 compact 생성자 `MemberProfile { … }`에 | `constructor` |
| getter | 직접 작성 `getEmail()` | 자동 생성 `email()` | 프로퍼티 접근 |
| `equals` | 안 만들면 **같은 객체인지(주소)**만 비교 | **모든 필드 값**으로 비교 | `===` / 값 비교 함수 |
| 값 바꾸기 | 메서드로 허용할 수 있음 | 못 바꾼다(새로 만든다) | `Readonly<T>` |

흔한 착각: "`final List<String> tags`면 태그 목록이 안 바뀐다". `final`은 **다른 리스트를 대입하지 못하게** 할 뿐이다. 리스트 안에 `add`하는 것은 막지 않는다. 그리고 getter가 그 리스트를 그대로 내주면 밖에서도 `add`할 수 있다. J00에서 본 "참조가 복사된다"가 엔티티에서 터지는 모양이다.

## 타입 한 컷

`int` vs `Integer` — 요청 DTO에서 "값 없음"과 "0"을 구분해야 하는 이유.

| | `int` (기본형) | `Integer` (래퍼) |
|---|---|---|
| null을 담을 수 있나 | 없다 | 있다 |
| 필드 기본값 | `0` | `null` |
| 요청에 값이 없을 때 | `0`이 들어가 "안 보냄"과 "0을 보냄"을 구분 못 한다 | `null`이 들어가 "안 보냄"을 알 수 있다 |
| 제네릭에 쓰기 | `List<int>` 불가 | `List<Integer>` |

함정: `Integer`가 null인데 `int`로 받으면(`int size = request.size();`) 언박싱하는 순간 `NullPointerException`이 난다. 그래서 null을 먼저 처리한 메서드(`sizeOrDefault`)로 꺼낸다.

과제: `PostListRequest(Integer size)`를 채운다. size를 보내지 않으면(null) 기본값 20을 쓰고, 보냈다면 1~50만 받는다. 0은 "값 없음"이 아니라 잘못된 값이다.

확인 테스트 — `J01TypeCutTest`:

- `대입하지_않은_필드는_int면_0이고_Integer면_null이다` (관찰. 테스트 안의 작은 클래스로 필드 기본값을 직접 본다. 처음부터 통과한다)
- `size를_보내지_않으면_null로_받고_기본값_20을_쓴다`
- `보낸_size가_범위_안이면_그대로_쓴다` (1, 20, 50)
- `size_0은_값_없음이_아니라_잘못된_값이라_거절한다` (0, -1, 51)
- `함정_null인_Integer를_int로_꺼내면_NPE가_난다`

## 실무 습관

불변 컬렉션과 방어적 복사. 주어진 `LeakyPost`는 받은 리스트를 그대로 필드에 담고, getter로 그대로 내준다. 그래서 두 가지 사고가 난다.

1. getter로 받은 리스트에 밖에서 `add`하면 글의 태그가 바뀐다(`addTag`를 거치지 않는다).
2. 생성자에 `List.of()`를 넘기면 그 불변 리스트를 그대로 쓰게 되어, 나중에 `addTag`가 `UnsupportedOperationException`으로 터진다.

과제: `Post`를 채워 두 사고를 막는다. 받은 리스트는 내 리스트로 복사해 담고, getter는 밖에서 고칠 수 없는 리스트를 내준다.

테스트 — `J01HabitTest` (각 테스트가 `LeakyPost`가 어떻게 터지는지 먼저 보여 준다):

- `getter가_내부_리스트를_내주면_밖에서_글이_바뀐다_Post는_막는다`
- `생성자에_넘긴_리스트를_밖에서_바꿔도_글의_태그는_그대로다`
- `List_of를_넘겨도_addTag가_된다`
- `태그는_addTag로만_바뀐다`

```java
// Member
private final String email;
private String nickname;

public Member(String email, String nickname) {
    if (email == null || !email.contains("@") || email.length() > EMAIL_MAX_LENGTH) {
        throw new IllegalArgumentException("이메일 형식이 아닙니다: " + email);
    }
    this.email = email;
    this.nickname = validNickname(nickname);
}

public void changeNickname(String newNickname) {
    // 검사를 먼저 하고 통과한 값만 대입하므로, 예외가 나면 원래 닉네임이 그대로 남는다
    this.nickname = validNickname(newNickname);
}

public MemberProfile toProfile() {
    return new MemberProfile(email, nickname);
}

private static String validNickname(String nickname) {
    if (nickname == null || nickname.length() < NICKNAME_MIN_LENGTH || nickname.length() > NICKNAME_MAX_LENGTH) {
        throw new IllegalArgumentException("닉네임은 2~20자여야 합니다: " + nickname);
    }
    return nickname;
}
```

```java
// MemberStats
public static int countValidNicknames(List<MemberRow> rows) {
    int count = 0;
    for (MemberRow row : rows) {
        String nickname = row.nickname();
        // null 검사를 먼저 해야 length()에서 NPE가 나지 않는다
        if (nickname != null
                && nickname.length() >= Member.NICKNAME_MIN_LENGTH
                && nickname.length() <= Member.NICKNAME_MAX_LENGTH) {
            count++;
        }
    }
    return count;
}
```

```java
// PostListRequest
public PostListRequest {
    // null(보내지 않음)을 먼저 걸러야 size < 1 비교에서 언박싱 NPE가 나지 않는다
    if (size != null && (size < 1 || size > MAX_SIZE)) {
        throw new IllegalArgumentException("size는 1~50이어야 합니다: " + size);
    }
}

public int sizeOrDefault() {
    return size == null ? DEFAULT_SIZE : size;
}
```

```java
// Post
private final String title;
private final List<String> tags;

public Post(String title, List<String> tags) {
    this.title = title;
    // 방어적 복사: 받은 리스트와 연결을 끊는다. 받은 것이 List.of()여도 내 리스트는 add할 수 있다
    this.tags = new ArrayList<>(tags);
}

public List<String> getTags() {
    // 읽기 전용 뷰를 내준다. 밖에서 add하면 UnsupportedOperationException
    return Collections.unmodifiableList(tags);
}

public void addTag(String tag) {
    tags.add(tag);
}
```

왜 이렇게 쓰나:

1. 검사를 생성자와 `changeNickname`에 모아 두면 "만들어진 `Member`는 언제나 규칙을 지킨다"가 보장된다. 필드가 `private`이라 이 길을 우회할 방법이 없다.
2. 요청 값은 "안 보냄"이 의미를 가지므로 `Integer`로 받고, 꺼내는 곳은 null을 처리한 메서드 하나로 모은다. 기본형으로 받으면 0과 구분할 수 없다.
3. 리스트 필드는 들어올 때 복사하고(`new ArrayList<>(tags)`) 나갈 때 읽기 전용으로 내준다(`Collections.unmodifiableList`). 그래야 태그가 `addTag` 한 곳에서만 바뀐다. 호출할 때마다 그 시점의 복사본을 내주고 싶으면 `List.copyOf(tags)`를 쓴다.

## 오늘 Spring에서 다시 만나는 곳

- D01 ④ `board-server/src/main/java/com/example/board/common/RequestIdFilter.java` — 밖에서 쓰는 헤더 이름은 `public static final String HEADER`, 안에서만 쓰는 정규식은 `private static final Pattern SAFE`. 접근제어자로 공개 범위를 나눈다.
- D03 ② `board-server/src/main/java/com/example/board/member/Member.java` — 필드는 모두 `private`이고, 생성자는 `private`으로 숨긴 뒤 `Member.create(…)`로만 만든다.
- D03 ③ `board-server/src/main/java/com/example/board/member/SignupRequest.java` — 가입 요청이 record다. 닉네임 2~20자 규칙은 이 DTO의 `@Pattern`이 검사한다(오늘은 같은 규칙을 생성자에서 직접 검사했다).
- D03 ⑤ `board-server/src/main/java/com/example/board/member/MemberResponse.java` — 응답 DTO도 record다. 엔티티를 그대로 내보내지 않고 필요한 값만 복사해 담는다(`toProfile`과 같은 생각).
- D04 ① `board-server/src/main/java/com/example/board/post/Post.java` — 클래스에 붙은 `@Getter`가 `getPostTags()`로 내부 `ArrayList`를 그대로 내준다. 지금 호출부는 읽기만 하지만, 밖에서 `add`하면 `addTag`를 거치지 않고 엔티티가 바뀐다(`LeakyPost`와 같은 모양).
- D06 ④ `board-server/src/main/java/com/example/board/post/PostListRequest.java` — `@Min(1) @Max(50) Integer size`로 받는다. 기본값 20과 1~50 범위는 오늘과 같지만, 여기서는 compact 생성자가 `size == null`을 20으로 바꿔 담는다(오늘 만든 것은 null을 그대로 두고 `sizeOrDefault`에서 처리해 언박싱 함정을 볼 수 있게 했다). 어느 쪽이든 `Integer`라서 "안 보냄"과 "0"을 구분할 수 있다.
