# J13. 리팩터링 ③: 쿠폰 종류별 if-else를 DiscountPolicy 전략으로

> 같은 날: D13 · 소요 30~60분 · 실행 `./gradlew :java-track:test --tests 'J13*'`

## 상황

D13은 쿠폰 동시 사용(B07)과 충전 재시도(B10)를 고치는 날이다. 지금 서버(board-server·messy-server 둘 다)의 쿠폰 할인은 `OrderService`의 "10% 한 가지"뿐이다. 하지만 쿠폰 종류가 늘면 계산 메서드에 `if-else`가 하나씩 붙는다. D13 ④의 `PgClient`는 재시도 규칙을 메서드 안의 조건문으로 두지 않는다. `PgRetryPolicy` 객체로 받는다. 규칙을 객체로 빼 두면 바꿔 끼울 수 있다.
오늘은 Spring 없이 종류별 if-else로 된 할인 계산을 `DiscountPolicy` 구현 클래스로 옮긴다. 할인액은 한 원도 바뀌면 안 된다. J11·J12처럼 특성화 테스트가 이것을 지킨다.

## 빠른 연상

| | if-else 사슬 | 전략(`DiscountPolicy` 구현) |
|---|---|---|
| 종류별 규칙이 사는 곳 | 한 메서드 안의 분기 | 종류마다 클래스 하나(`RatePolicy` …) |
| 종류를 하나 더하면 | 계산 메서드를 열어 `else if`를 끼운다 | 구현 클래스를 하나 더하고 목록에 넣는다. 계산기는 그대로다 |
| 한 종류만 테스트 | 계산기 전체를 거쳐야 한다 | `new RatePolicy().discount(…)`를 바로 부른다 |
| 계산기가 하는 일 | 모든 규칙을 안다 | "이 쿠폰을 맡는 정책"을 찾아 맡긴다 |
| JS로 치면 | `if (type === 'RATE') …` | `const policies = { RATE: rateFn, … }` |

흔한 착각: "전략 패턴을 쓰면 조건문이 사라진다". 조건은 없어지지 않는다. **어느 정책이 맡을지 고르는 곳 한 군데로 모일 뿐이다**(여기서는 각 정책의 `supports`와 `standardPolicies()`). 바뀌는 것은 규칙이 흩어져 있던 곳이다. 분기 몸통이 클래스로 갈라져 서로 섞이지 않는다.

## 기본기 반복

가진 쿠폰 목록을 stream으로 돌며 이 주문에서 쓸 수 있는(할인액이 0보다 큰) 쿠폰 중 할인액이 가장 큰 것을 고른다. 없을 수 있으므로 `Optional<Coupon>`을 돌려준다.

```java
/** 가진 쿠폰 중 이 주문에서 할인액이 가장 큰 쿠폰. 할인액이 0인 쿠폰은 고르지 않는다. 같으면 앞의 쿠폰. */
public Optional<Coupon> bestCoupon(List<Coupon> coupons, Order order)
```

`filter`로 거른 뒤 가장 큰 쿠폰을 고른다. "같으면 앞의 쿠폰"은 업무 규칙이므로 코드에 직접 적는다. `Stream.max`는 같은 값일 때 어느 원소를 남길지 약속하지 않는다(지금 구현이 어떻게 동작하든 계약이 아니다). `reduce((best, next) -> 뒤가 더 클 때만 next, 아니면 best)`처럼 "더 클 때만 바꾼다"를 써 두면 같을 때 앞의 쿠폰이 남는다.

테스트 — `J13BasicsTest`:

- `할인액이_가장_큰_쿠폰을_고른다`
- `할인액이_0인_쿠폰만_있으면_빈_Optional이다`
- `빈_목록이면_빈_Optional이다`
- `할인액이_같으면_앞의_쿠폰을_고른다`

## 타입 한 컷

`record`: 불변 데이터 운반 객체, compact 생성자 검증. DTO와 값 객체.

| | 레거시 DTO 클래스(`LegacyCouponCodeDto`) | `record CouponCode` |
|---|---|---|
| 값 넣기 | 기본 생성자 + `setValue` | 생성자 한 번(바꾸려면 새로 만든다) |
| 규칙 검사 | 없음. 아무 값이나 담긴다 | compact 생성자에서. 통과하지 못하면 객체가 안 생긴다 |
| 정규화(공백·대소문자) | 쓰는 쪽마다 따로 | compact 생성자에서 매개변수를 다시 대입 |
| `equals`·`hashCode` | 없음(주소 비교). `Set`에 같은 코드가 둘 | 구성 요소 값으로 자동 |
| 어울리는 자리 | 프레임워크가 setter로 채우는 옛 DTO | 요청·응답 DTO, 값 객체 |

함정: compact 생성자 안에서는 `this.value = …`를 쓸 수 없다(컴파일 에러). 대신 **매개변수 `value`에 다시 대입**하면 생성자 끝에서 그 값이 필드에 담긴다. 그리고 record의 불변은 얕다. 구성 요소가 `List`면 compact 생성자에서 `List.copyOf`로 복사해야 한다(J01의 방어적 복사).

과제: `CouponCode`의 compact 생성자를 채운다. 앞뒤 공백을 지우고 대문자로 바꾼 뒤(`toUpperCase(Locale.ROOT)` — 인자 없는 `toUpperCase()`는 서버 기본 로케일을 따라 터키어 로케일에서 `"i"`를 `"İ"`로 바꾼다), 영문 대문자·숫자만 6~12자인지 검사한다. 아니면(null 포함) `IllegalArgumentException`을 던진다.

확인 테스트 — `J13TypeCutTest`:

- `앞뒤_공백과_대소문자를_정규화해_담는다`
- `정규화는_서버_기본_로케일과_상관없이_같다` (테스트 안에서 기본 로케일을 `tr-TR`로 바꿨다가 되돌린다)
- `규칙에_맞지_않으면_만들_수_없다` (null, 빈 문자열, 공백만, 4자, 13자, `-` 포함, 한글)
- `경계_6자와_12자는_받아들인다`
- `정규화한_값이_같으면_equals로_같고_Set에_하나만_남는다`
- `함정_레거시_DTO는_규칙을_어긴_값도_담기고_같은_코드도_다른_객체다`

```java
// RatePolicy (FixedAmountPolicy·FirstOrderPolicy도 같은 모양)
public class RatePolicy implements DiscountPolicy {

    private static final int MAX_DISCOUNT = 5000;

    @Override
    public boolean supports(Coupon coupon) {
        return "RATE".equals(coupon.type());
    }

    @Override
    public int discount(Coupon coupon, Order order) {
        int raw = order.totalPrice() * coupon.value() / 100;
        // 10원 단위 버림
        return Math.min(raw / 10 * 10, MAX_DISCOUNT);
    }
}
```

```java
// DiscountCalculator
private final List<DiscountPolicy> policies;

public DiscountCalculator() {
    this(standardPolicies());
}

public DiscountCalculator(List<DiscountPolicy> policies) {
    this.policies = List.copyOf(policies);
}

public static List<DiscountPolicy> standardPolicies() {
    // 쿠폰 종류를 더할 때 고치는 곳은 여기 한 줄과 새 구현 클래스뿐이다
    return List.of(new FixedAmountPolicy(), new RatePolicy(), new FirstOrderPolicy());
}

public int discount(Coupon coupon, Order order) {
    if (coupon == null) {
        return 0;
    }
    return policies.stream()
            .filter(policy -> policy.supports(coupon))
            .findFirst()
            .map(policy -> policy.discount(coupon, order))
            .orElse(0);
}

public Optional<Coupon> bestCoupon(List<Coupon> coupons, Order order) {
    // 동률 규칙(앞의 쿠폰)을 코드에 적는다. Stream.max는 같은 값일 때 어느 쪽을 남길지 약속하지 않는다.
    // 뒤 쿠폰이 "더 클 때만" 바꾸므로 같으면 앞의 쿠폰이 남는다
    return coupons.stream()
            .filter(coupon -> discount(coupon, order) > 0)
            .reduce((best, next) -> discount(next, order) > discount(best, order) ? next : best);
}
```

```java
// CouponCode
public CouponCode {
    if (value == null) {
        throw new IllegalArgumentException("쿠폰 코드가 없습니다");
    }
    // this.value = …는 쓸 수 없다. 매개변수에 대입하면 compact 생성자 끝에서 그 값이 필드에 담긴다
    // 인자 없는 toUpperCase()는 서버 기본 로케일을 쓴다. 터키어 로케일이면 "i"가 "İ"가 되므로 Locale.ROOT로 고정한다
    value = value.strip().toUpperCase(Locale.ROOT);
    if (value.length() < MIN_LENGTH || value.length() > MAX_LENGTH || !isUpperAlphanumeric(value)) {
        throw new IllegalArgumentException("쿠폰 코드는 영문·숫자 6~12자여야 합니다: " + value);
    }
}
```

왜 이렇게 쓰나:

1. 계산기가 정책 목록을 **생성자로 받으면** 테스트나 다른 화면에서 다른 목록을 끼울 수 있다. Spring에서는 이 목록을 `List<DiscountPolicy>` 생성자 주입으로 받는다(구현 빈이 모두 들어온다).
2. 정책 하나에 한 종류의 규칙과 그 상수(`MAX_DISCOUNT`)가 같이 산다. 정률 규칙을 고칠 때 정액 코드를 건드릴 일이 없다.
3. 값 객체는 들어오는 순간 정규화·검사를 끝낸다. 그러면 `CouponCode`를 받은 쪽은 다시 검사하지 않아도 된다. `equals`가 값 기준이라 `Set`·`Map` 키로도 바로 쓴다.

## 오늘 Spring에서 다시 만나는 곳

2단계(D11~D14)에서 진단하고 고치는 곳은 넘겨받은 `messy-server`다. `board-server`의 같은 이름 파일은 고친 뒤의 모습(정답 모양)이라 내용이 다르다. 아래는 어느 쪽을 보는지 경로에 적었다.

- D07 ⑥ (참고) `board-server/src/main/java/com/example/board/shop/OrderService.java` — 쿠폰 할인이 `COUPON_DISCOUNT_PERCENT = 10` 한 가지 규칙으로 `place` 안에 들어 있다(`messy-server`의 같은 파일도 같다). 쿠폰 종류가 늘면 이 줄이 오늘의 if-else가 될 자리다. 그때 `List<DiscountPolicy>`를 주입받아 맡기면 된다.
- D13 ② `messy-server/src/main/java/com/example/board/coupon/CouponService.java` — 쿠폰 발급. 고친 뒤 모습은 `board-server`의 같은 파일이다. B07을 고칠 때 할인 규칙 같은 다른 관심사가 이 서비스에 섞여 있지 않아야 고칠 곳만 따로 볼 수 있다.
- D08 ①④ (참고) `board-server/src/main/java/com/example/board/payment/PgClient.java` — 재시도 규칙을 메서드 안에 조건문으로 두지 않고 생성자로 받은 `PgRetryPolicy`에 맡긴다. `new PgRetryPolicy(maxAttempts)`로 시도 횟수가 다른 정책을 만들어 끼울 수 있다(오늘 `DiscountCalculator(List<DiscountPolicy>)`와 같은 생각).
- D13 ④ `board-server/src/main/java/com/example/board/payment/ChargeService.java` (고친 뒤 모습. B10을 고치는 `messy-server`의 같은 파일도 이 switch는 같다) — `apply`가 PG 승인 상태(`DONE`·`FAILED`·`PENDING`)를 switch 식(`case DONE -> …`)으로 가른다. 분기가 한 곳에 모여 있고 enum 상수라 오타가 없다(선택: switch 식).
