# J12. 리팩터링 ②: 긴 메서드를 검증·계산·저장으로 나누기

> 같은 날: D12 · 소요 30~60분 · 실행 `./gradlew :java-track:test --tests 'J12*'`

## 상황

D12에서 고치는 티켓들은 모두 긴 서비스 메서드 안에 원인이 숨어 있다. D12 ①에서는 충전 처리 안에서 PG 호출이 트랜잭션에 묶여 있고, ③에서는 구매 처리 안의 예외 처리와 롤백 경계가 엉켜 있다. 고치려면 먼저 "어디까지가 검증이고 어디부터가 저장인가"가 보이도록 메서드를 나눠야 한다.
오늘은 Spring 없이 76줄짜리 구매 처리 메서드를 검증·계산·저장 세 메서드로 나눈다. 나누기 전후에 동작이 같은지는 J11에서 익힌 특성화 테스트가 지킨다.

## 빠른 연상

| | 나누기 전 `purchase` (76줄) | 나눈 뒤 |
|---|---|---|
| 한눈에 보이는 것 | `if`와 문자열 이어 붙이기가 섞인 한 덩어리 | `validate` → `calculate` → `save` 흐름 4줄 |
| 실패 사유 | `error = error + ", " + …`로 문자열에 누적 | `List<String>`에 `add`하고, 잇기(`String.join`)는 보여 줄 때 한 번 |
| 한 부분만 테스트 | 불가능(항상 전체가 돈다) | `validate`·`calculate`만 따로 불러 본다 |
| 바꿀 때 | 계산식을 고치다 저장 순서를 건드릴 수 있다 | 계산은 `calculate` 한 곳 |
| JS로 치면 | 300줄 `handleSubmit` | `validate(form)`, `toPayload(form)`, `api.save(payload)` |

흔한 착각: "나누면서 조금 더 낫게 고쳐도 된다". 리팩터링은 **동작을 바꾸지 않는** 변경이다. 레거시에는 수량이 11개면 "수량" 사유와 "재고" 사유가 둘 다 나오는 이상한 동작이 있다. 이것도 그대로 둔다. 고치는 것은 특성화 테스트가 지키는 상태에서 따로 한다.

나누는 순서(한 단계마다 `J12PurchaseTest`의 `특성화_` 테스트 4개를 돌려 초록인지 본다):

1. 계산 부분을 `calculate`로 옮기고 `Payment`를 돌려준다. `purchase`는 `Payment`의 값을 쓴다.
2. 저장 부분을 `save`로 옮긴다.
3. 검증 부분을 `validate`로 옮긴다. 이때 사유를 문자열에 이어 붙이지 말고 `List<String>`에 모은다. `purchase`에서 `String.join(", ", errors)`로 잇는다.

세 메서드는 `package-private`이고 `final`이 아니다. 테스트가 하나씩 바꿔 끼워(익명 하위 클래스로 override) `purchase`가 정말 그 메서드를 부르는지 확인하기 때문이다.

## 기본기 반복

나눈 `validate`가 실패 사유를 `List<String>`으로 모아 돌려준다. 첫 실패에서 `return`하지 않고 끝까지 검사한다. 사용자는 한 번에 모든 사유를 봐야 한다. 문제가 없으면 null이 아니라 빈 목록을 돌려준다.

```java
List<String> errors = new ArrayList<>();
if (…) {
    errors.add("수량은 1~10개여야 합니다");
}
…
return errors;
```

테스트 — `J12BasicsTest`:

- `문제가_없으면_빈_목록이다`
- `첫_실패에서_멈추지_않고_사유를_순서대로_모두_모은다`
- `없는_상품이면_재고는_검사하지_않는다`

## 타입 한 컷

`enum` 확장: 필드·생성자·메서드를 가진 enum, 상수별 메서드 구현. 주어진 `LegacyOrderStatus`는 상태를 문자열(`"PAID"`)로 들고 다닌다. 그리고 `label`·`canCancel`·`refundAmount` 메서드마다 같은 if-else를 반복한다.

| | 문자열 코드 + if-else | 필드만 가진 enum | 상수별 몸체를 가진 enum |
|---|---|---|---|
| 오타(`"PIAD"`) | 실행해 봐야 안다 | 컴파일 에러 | 컴파일 에러 |
| 상태별 값(라벨) | if-else | 생성자로 받은 필드 | 생성자로 받은 필드 |
| 상태별 동작(환불액) | if-else | 메서드 안 `switch (this)` | 상수마다 `{ … }` 안에 구현 |
| 상태를 하나 더하면 | if-else를 전부 찾아 고친다 | `switch`를 찾아 고친다 | 메서드를 `abstract`로 두면 구현을 빠뜨린 순간 컴파일 에러 |

함정: 상수에 `{ … }` 몸체를 열면 그 상수는 enum을 상속한 **익명 클래스의 객체**가 된다. 그래서 `OrderStatus.SHIPPING.getClass() == OrderStatus.class`는 `false`다. "어느 enum의 상수인가"는 `getDeclaringClass()`로 묻는다(`EnumMap`·직렬화 라이브러리도 이것을 쓴다). 그리고 `valueOf("paid")`는 대소문자가 달라 `IllegalArgumentException`이다.

과제: `OrderStatus`를 채운다. 규칙은 `LegacyOrderStatus`와 같다. 결제 완료면 전액 환불, 배송 중이면 배송비 3000원을 빼고 환불(0 아래로는 내려가지 않음), 배송 완료와 취소됨은 취소할 수 없고 환불액 0이다.

확인 테스트 — `J12TypeCutTest`:

- `상태마다_라벨을_필드로_가진다`
- `라벨_취소_가능_환불액이_레거시_if_else와_같다` (상태 4개)
- `배송_중_환불은_배송비_3000원을_빼고_0_아래로_내려가지_않는다`
- `함정_상수별_몸체가_있으면_getClass는_enum_타입이_아니다`
- `함정_valueOf는_대소문자까지_같아야_하고_없으면_예외다`

```java
// PurchaseService
private static final int MIN_QUANTITY = 1;
private static final int MAX_QUANTITY = 10;
private static final String COUPON_PREFIX = "SALE";
private static final long COUPON_DISCOUNT_PERCENT = 10;
private static final long COUPON_DISCOUNT_MAX = 5000;
private static final long EARN_PERCENT = 1;

public PurchaseResult purchase(PurchaseRequest request) {
    List<String> errors = validate(request);
    if (!errors.isEmpty()) {
        return new PurchaseResult(false, null, 0, String.join(", ", errors));
    }
    Payment payment = calculate(request);
    long orderId = save(request, payment);
    return new PurchaseResult(true, orderId, payment.paidAmount(), "구매 완료");
}

List<String> validate(PurchaseRequest request) {
    // 첫 실패에서 돌아가지 않고 끝까지 모은다. ", " 잇기는 보여 주는 쪽(purchase)이 한다
    List<String> errors = new ArrayList<>();
    if (request.quantity() < MIN_QUANTITY || request.quantity() > MAX_QUANTITY) {
        errors.add("수량은 1~10개여야 합니다");
    }
    ShopItem item = store.findItem(request.itemCode());
    if (item == null) {
        errors.add("없는 상품입니다");
    } else if (item.stock() < request.quantity()) {
        errors.add("재고가 부족합니다");
    }
    if (request.usePoints() < 0) {
        errors.add("사용 포인트는 0 이상이어야 합니다");
    } else if (request.usePoints() > store.pointsOf(request.memberId())) {
        errors.add("포인트가 부족합니다");
    }
    if (request.couponCode() != null && !request.couponCode().startsWith(COUPON_PREFIX)) {
        errors.add("쓸 수 없는 쿠폰입니다");
    }
    return errors;
}

Payment calculate(PurchaseRequest request) {
    long total = store.findItem(request.itemCode()).price() * request.quantity();
    long discount = request.couponCode() == null
            ? 0
            : Math.min(total * COUPON_DISCOUNT_PERCENT / 100, COUPON_DISCOUNT_MAX);
    // 포인트는 할인 뒤 금액의 절반까지만 쓸 수 있다
    int usedPoints = (int) Math.min(request.usePoints(), (total - discount) / 2);
    return new Payment(total, discount, usedPoints, total - discount - usedPoints);
}

long save(PurchaseRequest request, Payment payment) {
    store.decreaseStock(request.itemCode(), request.quantity());
    if (payment.usedPoints() > 0) {
        store.usePoints(request.memberId(), payment.usedPoints());
    }
    store.addPoints(request.memberId(), (int) (payment.paidAmount() * EARN_PERCENT / 100));
    return store.saveOrder(new PurchaseOrder(request.memberId(), request.itemCode(), request.quantity(),
            payment.totalPrice(), payment.discount(), payment.usedPoints(), payment.paidAmount()));
}
```

```java
// OrderStatus
public enum OrderStatus {

    PAID("결제 완료") {
        @Override
        public boolean canCancel() {
            return true;
        }

        @Override
        public long refundAmount(long paidAmount) {
            return paidAmount;
        }
    },
    SHIPPING("배송 중") {
        @Override
        public boolean canCancel() {
            return true;
        }

        @Override
        public long refundAmount(long paidAmount) {
            return Math.max(0, paidAmount - SHIPPING_FEE);
        }
    },
    DELIVERED("배송 완료") { /* canCancel → false, refundAmount → 0 */ },
    CANCELLED("취소됨") { /* canCancel → false, refundAmount → 0 */ };

    private static final long SHIPPING_FEE = 3000;

    private final String label;

    OrderStatus(String label) {
        this.label = label;
    }

    public String label() {
        return label;
    }

    // 몸체마다 반드시 구현하게 abstract로 둔다. 상태를 하나 더하면서 구현을 빠뜨리면 컴파일 에러가 난다
    public abstract boolean canCancel();

    public abstract long refundAmount(long paidAmount);
}
```

왜 이렇게 쓰나:

1. `purchase`가 흐름만 남으면 "검증에 걸리면 아무것도 저장하지 않는다"가 코드 모양으로 보인다. 저장은 `save` 한 곳에서만 일어난다.
2. 실패 사유는 모으는 일(`List.add`)과 보여 주는 일(`String.join`)을 나눈다. 그러면 나중에 사유를 JSON 배열로 내보내도 `validate`는 그대로다.
3. 나누는 동안 매 단계 특성화 테스트를 돌린다. 한 번에 다 옮기고 나서 돌리면 어느 단계에서 동작이 바뀌었는지 찾기 어렵다.

## 오늘 Spring에서 다시 만나는 곳

2단계(D11~D14)에서 진단하고 고치는 곳은 넘겨받은 `messy-server`다. `board-server`의 같은 이름 파일은 고친 뒤의 모습(정답 모양)이라 내용이 다르다. 아래는 어느 쪽을 보는지 경로에 적었다.

- D12 ① `board-server/src/main/java/com/example/board/payment/ChargeService.java` (고친 뒤 모습) — `charge`가 `start`(결제 행 만들기) → PG 호출 → `apply`(결과 반영)로 나뉘어 있다. 나눠 두었기 때문에 트랜잭션을 DB 단계에만 짧게 걸고, PG를 기다리는 동안에는 커넥션을 쥐지 않을 수 있다. D12 ①에서 진단하는 `messy-server`의 같은 파일은 `start` → PG 호출 → `apply`로 나뉘어 있지만 PG 호출과 `apply`가 한 트랜잭션(`tx.execute`) 안에 있어, PG를 기다리는 동안 커넥션을 쥔다(B01).
- D12 ③ `board-server/src/main/java/com/example/board/shop/OrderService.java` (고친 뒤 모습) — `order` → `placeOnce` → `place`, `findReplay`로 나뉜 구매 처리. 데드락 재시도(`order`)는 트랜잭션 밖, 실제 처리(`place`)는 `TransactionTemplate` 안이라는 경계가 메서드 단위로 보인다. B03에서 보듯 나눈 메서드에 `@Transactional`을 붙이고 같은 클래스 안에서 부르면 프록시를 거치지 않는다(self-invocation, J10에서 본 것). 나눌 때는 트랜잭션 경계가 어디에 걸리는지도 같이 본다. B03을 고치는 `messy-server`의 같은 파일에서는 `order`가 같은 클래스의 `@Transactional placeOnce`를 직접 부른다.
- D12 ③ `messy-server/src/test/java/com/example/board/shop/OrderRollbackTest.java` (**D12 ③에서 작성할 예정** — 아직 없는 파일이다) — 메서드를 나누고 경계를 옮긴 뒤에도 롤백 동작을 테스트로 고정한다.
