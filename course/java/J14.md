# J14. 리팩터링 ④: null 반환을 Optional과 빈 컬렉션으로

> 같은 날: D14 · 소요 30~60분 · 실행 `./gradlew :java-track:test --tests 'J14*'`

## 상황

D14는 장애 훈련 날이다. Redis를 멈추거나 느리게 만든 상태에서도 글쓰기와 인기글이 돌아가야 한다. D14 ④⑤의 `PopularPostService`는 캐시가 없거나 Redis가 죽으면 `readCache()`가 null을 돌려준다. 호출부는 매번 `cached != null`을 확인하고 DB로 간다. 이 검사를 한 곳이라도 빠뜨리면 장애 때만 NPE가 터진다.
오늘은 Spring 없이 null을 돌려주는 조회 메서드를 고친다. 단건 조회는 `Optional`로, 목록 조회는 빈 목록으로 바꾼다. 그리고 호출부에서 터지던 NPE를 없앤다.

## 빠른 연상

| 조회 결과가 없을 때 | null 반환 | `Optional<Member>` | 빈 목록 `List.of()` |
|---|---|---|---|
| 반환 타입만 보고 "없을 수 있다"를 아는가 | 모른다(문서·코드를 읽어야) | 안다 | 목록은 원래 0개일 수 있다 |
| 호출부가 확인을 빠뜨리면 | 꺼내 쓰는 순간 NPE | `map`·`orElse`를 거쳐야만 값이 나온다 | for·stream이 0번 돈다. 문제없다 |
| 쓰는 자리 | (피한다) | 단건 조회의 **반환 타입** | 목록 조회 |
| TS로 치면 | `Member \| null`인데 타입엔 `Member` | `Member \| undefined` + 옵셔널 체이닝 | `[]` |

흔한 착각: "목록도 `Optional<List<…>>`로 감싸면 더 안전하다". 목록의 "없음"은 빈 목록이면 충분하다. 감싸면 호출부가 두 겹을 풀어야 한다. `Optional`은 단건 조회의 반환 타입에만 쓴다. 필드·매개변수에는 쓰지 않는다(J06). 예외는 "캐시에 없음"과 "캐시에 빈 목록이 들어 있음"을 구분해야 할 때다(아래 D14 ④).

레거시(뼈대) 발췌:

```java
// MemberRepository
/** 이메일로 회원을 찾는다. 없으면 null. */
public Member findByEmail(String email) {
    return membersByEmail.get(email);
}

/** 회원의 포인트 내역을 쌓인 순서대로 돌려준다. 내역이 하나도 없으면 null. */
public List<PointHistory> findHistories(long memberId) {
    List<PointHistory> histories = historiesByMember.get(memberId);
    if (histories == null) {
        return null;
    }
    return List.copyOf(histories);
}

// PointReportService
public int totalPoints(String email) {
    Member member = repository.findByEmail(email);                 // 없으면 null
    List<PointHistory> histories = repository.findHistories(member.id()); // ← 없는 회원이면 여기서 NPE
    int total = 0;
    for (PointHistory history : histories) {                       // ← 내역이 없으면 여기서 NPE
        total += history.amount();
    }
    return total;
}
```

고치는 순서:

1. `findHistories`가 null 대신 빈 목록을 돌려주게 한다(`getOrDefault(memberId, List.of())`). 반환 타입이 그대로라 호출부는 고치지 않아도 컴파일된다. `report`의 NPE 하나가 이것만으로 사라진다.
2. `findByEmail`의 반환 타입을 `Optional<Member>`로 바꾼다. 그러면 호출부가 컴파일 에러로 바뀐다. 이 에러가 "없는 경우를 처리하지 않은 곳" 목록이다.
3. 호출부를 `findByEmail(email).map(…).orElse(…)`로 고친다. `isPresent()` + `get()`은 null 검사를 이름만 바꾼 것이므로 쓰지 않는다.

`findByEmail`은 반환 타입이 바뀐다. 그래서 테스트가 이 메서드만 이름으로 찾아(리플렉션) 부른다. 테스트는 바꾸기 전 코드로 컴파일되기 때문에, 직접 부르면 바꾼 뒤 `NoSuchMethodError`가 난다.

통과시킬 테스트(주제 과제) — `J14NullRefactorTest`:

- 특성화(값이 있는 경우. 바꾸기 전에도 통과하고, 바꾼 뒤에도 그대로 통과해야 한다)
  - `특성화_내역이_있는_회원은_닉네임과_합계를_보여_준다`
  - `특성화_없는_회원이면_회원_없음이다`
  - `특성화_합계는_적립과_사용을_더한_값이다`
- 호출부(지금은 NPE로 실패한다)
  - `내역이_없는_회원도_NPE_없이_0P를_보여_준다`
  - `없는_회원이나_내역이_없는_회원의_합계는_NPE_없이_0이다`
- 저장소(지금은 실패한다)

  - `findByEmail은_있으면_값이_든_Optional_없으면_빈_Optional이다`

## 기본기 반복

null이 섞인 회원 목록에서 null을 거르고 닉네임을 정렬해 `String.join`으로 잇는다. 회원 자체가 null인 칸과 닉네임이 null인 회원(옛 데이터)이 섞여 있다.

```java
/** null인 회원과 닉네임이 null인 회원을 거르고, 닉네임을 가나다순으로 정렬해 ", "로 잇는다. 남는 회원이 없으면 빈 문자열. */
public static String joinNicknames(List<Member> members)
```

거르는 순서가 중요하다. 회원 null을 먼저 걸러야 `member.nickname()`에서 NPE가 나지 않는다. `Objects::nonNull`을 쓴다.

테스트 — `J14BasicsTest`:

- `null인_회원과_닉네임을_거르고_정렬해_쉼표로_잇는다`
- `빈_목록이면_빈_문자열이다`
- `모두_걸러지면_빈_문자열이다`
- `한_명이면_쉼표_없이_닉네임만이다`

## 타입 한 컷

(선택) `double` vs `BigDecimal`: 포인트 적립률과 결제 금액.

| | `double` | `BigDecimal` |
|---|---|---|
| `0.1 + 0.2` | `0.30000000000000004` | `0.3` (`new BigDecimal("0.1").add(…)`) |
| 70000원 × 1.13% | `790.99999…` → 버리면 **790** | 정확히 **791** |
| 나눗셈 | 그냥 된다(오차 포함) | 자릿수·반올림 방식을 정해야 한다: `divide(HUNDRED, 0, RoundingMode.DOWN)` |
| 같은 값 비교 | `==`(오차 때문에 위험) | `compareTo(…) == 0`. `equals`는 `1.0`과 `1.00`을 다르다고 본다 |
| 만들기 | - | `new BigDecimal("1.13")` 또는 `BigDecimal.valueOf(1.13)`. `new BigDecimal(1.13)`은 오차까지 담는다 |

함정: 금액 계산을 `double`로 하고 `(long)`로 버리면 가끔 1원(1포인트)이 사라진다. 대부분의 입력에서는 맞기 때문에 테스트 몇 개로는 드러나지 않는다. 그리고 `BigDecimal`을 `equals`로 비교하면 DB에서 읽은 `1500.00`과 계산한 `1500`이 다르다고 나온다.

과제: `PointMath.earnPoints(long price, String ratePercent)`(소수점 아래 버림)와 `PointMath.sameAmount(BigDecimal, BigDecimal)`(값 비교)를 채운다.

선택 과제 테스트 — `J14TypeCutTest` (클래스 전체에 `@Tag("optional")`. 기본 실행 `--tests 'J14*'`에는 들어가지 않고 `./gradlew :java-track:optionalTest --tests 'J14*'`로 돌린다):

- `함정_double로_0_1과_0_2를_더하면_0_3이_아니다`
- `함정_double로_적립률을_곱하면_1포인트가_사라진다`
- `적립_포인트는_소수점_아래를_버린다`
- `함정_BigDecimal_equals는_소수_자릿수까지_비교한다`
- `함정_new_BigDecimal에_double을_넣으면_오차까지_담긴다`

```java
// MemberRepository
public Optional<Member> findByEmail(String email) {
    // "없을 수 있다"를 반환 타입에 적는다. 호출부는 꺼내기 전에 없는 경우를 처리해야 컴파일된다
    return Optional.ofNullable(membersByEmail.get(email));
}

public List<PointHistory> findHistories(long memberId) {
    // 컬렉션은 Optional로 감싸지 않는다. "없음"은 빈 목록이면 충분하고, 호출부의 for·stream이 그대로 돈다
    return List.copyOf(historiesByMember.getOrDefault(memberId, List.of()));
}
```

```java
// PointReportService
public String report(String email) {
    return repository.findByEmail(email)
            .map(member -> member.nickname() + ": " + sum(repository.findHistories(member.id())) + "P")
            .orElse("회원 없음");
}

public int totalPoints(String email) {
    return repository.findByEmail(email)
            .map(member -> sum(repository.findHistories(member.id())))
            .orElse(0);
}

private static int sum(List<PointHistory> histories) {
    // 빈 목록이면 0. null이 오지 않으므로 검사하지 않는다
    return histories.stream().mapToInt(PointHistory::amount).sum();
}
```

```java
// MemberNames
public static String joinNicknames(List<Member> members) {
    // 회원 null을 먼저 걸러야 member.nickname()에서 NPE가 나지 않는다
    List<String> nicknames = members.stream()
            .filter(Objects::nonNull)
            .map(Member::nickname)
            .filter(Objects::nonNull)
            .sorted()
            .toList();
    return String.join(", ", nicknames);
}
```

```java
// PointMath
private static final BigDecimal HUNDRED = BigDecimal.valueOf(100);

public static long earnPoints(long price, String ratePercent) {
    // new BigDecimal("1.13")은 정확히 1.13이다. 나눗셈은 자릿수(0)와 반올림 방식(DOWN = 버림)을 꼭 정한다
    return BigDecimal.valueOf(price)
            .multiply(new BigDecimal(ratePercent))
            .divide(HUNDRED, 0, RoundingMode.DOWN)
            .longValueExact();
}

public static boolean sameAmount(BigDecimal a, BigDecimal b) {
    // equals는 scale까지 비교한다(1.0 ≠ 1.00). 값만 비교하려면 compareTo
    return a.compareTo(b) == 0;
}
```

왜 이렇게 쓰나:

1. 반환 타입을 `Optional`로 바꾸면 "null 검사를 빠뜨린 호출부"가 컴파일 에러로 한꺼번에 드러난다. 장애 때 런타임에 하나씩 발견하는 것보다 싸다.
2. 목록은 빈 목록으로 돌려주면 호출부가 아무것도 고치지 않아도 된다. 레거시 호출부를 고치는 범위가 가장 작은 변경이 이것이라서 먼저 한다.
3. `map(…).orElse(…)`는 "있을 때"와 "없을 때"를 한 식에 둔다. `isPresent()` 뒤 `get()`은 null 검사를 이름만 바꾼 것이라 빠뜨릴 위험이 그대로다.

</details>

## 오늘 Spring에서 다시 만나는 곳

2단계(D11~D14)에서 진단하고 고치는 곳은 넘겨받은 `messy-server`다. `board-server`의 같은 이름 파일은 고친 뒤의 모습(정답 모양)이라 내용이 다르다. 아래는 어느 쪽을 보는지 경로에 적었다.

- D14 ③ `messy-server/src/main/java/com/example/board/admin/AdminService.java` (`board-server`의 같은 파일도 이 부분은 같다) — `hidePost`가 `postRepository.findById(postId).filter(…).orElseThrow(…)`로 "없거나 삭제된 글"을 한 식에서 404로 바꾼다. 선택 매개변수 `reportId`는 null일 수 있어 지역 변수 `Report report = null`로 받는다. 매개변수에 `Optional`을 쓰지 않는 예다.
- D14 ④⑤ `board-server/src/main/java/com/example/board/post/PopularPostService.java` (D14 ⑤ 고도화까지 마친 뒤 모습) — `readCache()`가 "캐시에 없음 또는 Redis 장애"를 null로 돌려주고, `getPopular`가 그 null을 확인한다. 여기서 빈 목록으로 바꾸면 안 된다. 빈 목록은 "인기글 0건이 캐시돼 있음"과 구분되지 않는다. 바꾼다면 `Optional<List<PopularPost>>`가 맞는 드문 자리다.
