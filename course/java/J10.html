#상황

D10은 관리자 기능과 AOP를 붙이는 날이다. D10 ③에서 @Audited 어노테이션을 만들고, D10 ④ AuditLogAspect가 그 어노테이션이 붙은 메서드만 가로채 감사 로그를 남긴다. 같은 날 함정이 두 번 나온다. D10 ②는 같은 클래스 안에서 @PreAuthorize 메서드를 부르면 USER도 통과하는 것이고, D10 ④는 같은 클래스 안 호출이나 private 메서드에 붙인 @Audited가 기록되지 않는 것이다. 오늘은 Spring 없이 그 원리를 직접 만든다. java.lang.reflect.Proxy로 인터페이스를 구현한 가짜 객체를 만들고, 호출마다 리플렉션으로 @Timed가 붙었는지 본 뒤 실행 시간을 기록한다. 그러면 this.xxx() 호출이 왜 프록시를 건너뛰는지가 테스트로 보인다.

#빠른 연상

호출한 쪽 ──▶ [프록시] ──▶ InvocationHandler.invoke(proxy, method, args)
                              │ @Timed? → 시간 재기 시작
                              ├─▶ method.invoke(target, args) ──▶ [target] hideAll()
                              │                                      └─ this.hidePost()  ← 프록시를 거치지 않는다
                              └─ 기록 남기기
Spring AOP (D10) 오늘 만드는 것 TS로 치면
표시 @Audited @Timed 데코레이터 @Timed()
가로채는 것 스프링이 만든 프록시 빈 Proxy.newProxyInstance new Proxy(target, { get… })
진짜 메서드 부르기 joinPoint.proceed() method.invoke(target, args) Reflect.apply
자기 호출 프록시를 거치지 않는다 같다 클로저 안 this는 원본

흔한 착각: "어노테이션을 붙이면 그 메서드가 무언가를 한다". 어노테이션은 표시일 뿐 스스로 아무것도 하지 않는다. 누군가(프록시, 프레임워크)가 실행 중에 리플렉션으로 읽어야 의미가 생긴다. 그래서 @Retention(RUNTIME)이어야 하고, 읽는 쪽을 거치지 않는 호출(this.xxx())에는 효과가 없다.

#만들 것

펼치기

TimedProxy 규칙:

  • Proxy.newProxyInstance(type.getClassLoader(), new Class<?>[] {type}, handler)로 type 인터페이스의 프록시를 만들고, 인터페이스 메서드 호출을 target에 넘긴다.
  • @Timed가 붙은 메서드만 new Timing(메서드 이름, 걸린 시간)을 log에 남긴다. 대상이 예외를 던져도 남긴다.
  • @Timed는 인터페이스 메서드(bulkIssueCoupon)에 붙어 있을 수도, 구현 클래스 메서드(FakeAdminActions.hidePost)에 붙어 있을 수도 있다. 둘 다 찾는다.
  • 대상이 던진 예외는 포장하지 않고 그대로 던진다.
  • equals·hashCode·toString도 프록시로 들어온다. 이 셋은 target에 넘기지 않고 프록시 자신을 기준으로 답한다: equals는 같은 프록시일 때만 true(self == args[0]), hashCode는 System.identityHashCode(self), toString은 target.toString()을 부르지 않는 문자열(예: 프록시 identity + target 클래스 이름). 기록하지 않는다.

뼈대 발췌:

    public static boolean isTimed(Method interfaceMethod, Class<?> targetClass) {
        throw new UnsupportedOperationException("J10: TimedProxy.isTimed — 인터페이스 메서드와 구현 메서드에서 @Timed를 찾으세요");
    }

막히는 곳 두 군데:

  1. InvocationHandler.invoke가 받는 Method는 인터페이스의 메서드다. 구현 클래스에 붙인 @Timed는 거기서 보이지 않는다. targetClass.getMethod(이름, 매개변수 타입)으로 구현 메서드를 찾아 확인한다. 예외가 하나 있다: 프록시에 부른 equals·hashCode·toString은 선언 클래스가 Object인 Method로 들어온다(method.getDeclaringClass() == Object.class). 이것까지 target에 넘기면 proxy.equals(proxy)가 target.equals(proxy)로 바뀌어 false가 된다 — 자기 자신과 같지 않은 객체가 생긴다.
  2. method.invoke(target, args)는 대상이 던진 예외를 InvocationTargetException으로 감싼다. 그대로 두면 호출한 쪽은 UndeclaredThrowableException을 받는다. e.getCause()를 꺼내 던진다.

#기본기 반복

감사 로그 목록에서 action별 건수를 stream으로 세어 고칠 수 없는 Map으로 돌려준다. action이 생기기 전에 쌓인 옛 기록은 action이 null이라 건너뛴다.

/** action별 건수. action이 null이면 건너뛴다. 돌려주는 Map에 put하면 UnsupportedOperationException. */
public static Map<String, Long> countByAction(List<AuditEntry> entries)

함정 두 개: Collectors.groupingBy는 분류 키가 null이면 NullPointerException을 던진다. 그리고 groupingBy는 돌려주는 Map의 종류도, 고칠 수 없는지도 약속하지 않는다(지금 JDK는 가변 HashMap을 준다). 그대로 내주면 밖에서 숫자를 고칠 수 있으니 Map.copyOf로 불변을 직접 만든다.

테스트 — J10BasicsTest:

  • action별_건수를_센다
  • 빈_목록이면_빈_Map을_돌려준다
  • action이_null인_옛_기록은_예외_없이_건너뛴다
  • 돌려준_Map은_고칠_수_없다

#타입 한 컷

final·var·static final 상수 — 설정 상수, 불변 필드.

뜻 다시 대입 어울리는 곳
static final int MAX_ROWS = 1_000 클래스에 하나뿐인 상수 불가 업로드 한도, TTL 같은 설정 상수
static int maxRows 클래스에 하나뿐인 변수 어디서든 가능 거의 없다. 한 곳에서 바꾸면 모든 인스턴스가 바뀐다
private final int rows 객체마다 하나, 생성자에서 한 번만 대입 불가 만든 뒤 바뀌면 안 되는 값(엔티티 id·DTO 필드)
var limits = … 타입을 오른쪽 값에서 추론하는 지역 변수 가능 타입이 길고 오른쪽에서 뻔히 보일 때

함정: static만 붙이고 final을 빼면 "설정"이 전역 변수가 된다. 주어진 LeakyUploadSettings.maxRows를 요청 A가 "이번만" 10으로 줄이면 요청 B도 함께 줄어든다. 그리고 var는 타입을 적지 않을 뿐 final이 아니다. 다시 대입을 막으려면 final var로 쓴다.

과제: UploadLimits(int rows, long fileBytes)를 채운다. 행 수는 1MAX_ROWS, 파일 크기는 1MAX_FILE_BYTES(5MB)만 받고, 값은 private final 필드에 담는다.

확인 테스트 — J10TypeCutTest:

  • 한도_안의_업로드는_받아들인다
  • 한도를_넘으면_거절한다 (0행, 1,001행, 0바이트, 5MB+1)
  • 인스턴스_필드는_모두_private_final이다
  • 함정_final이_없는_static_필드는_한_곳에서_바꾸면_모든_곳이_바뀐다
  • var는_오른쪽_값으로_타입이_정해질_뿐_final은_아니다

// TimedProxy
public static <T> T wrap(Class<T> type, T target, TimingLog log) {
    Object proxy = Proxy.newProxyInstance(type.getClassLoader(), new Class<?>[] {type}, (self, method, args) -> {
        if (method.getDeclaringClass() == Object.class) {
            // equals·hashCode·toString. target에 넘기면 proxy.equals(proxy)가 target.equals(proxy) = false가 된다
            return objectMethod(self, target, method, args);
        }
        if (!isTimed(method, target.getClass())) {
            return invoke(target, method, args);
        }
        long start = System.nanoTime();
        try {
            return invoke(target, method, args);
        } finally {
            // 성공이든 예외든 한 줄 남긴다
            log.add(new Timing(method.getName(), Duration.ofNanos(System.nanoTime() - start)));
        }
    });
    return type.cast(proxy);
}

public static boolean isTimed(Method interfaceMethod, Class<?> targetClass) {
    if (interfaceMethod.isAnnotationPresent(Timed.class)) {
        return true;
    }
    try {
        // 프록시가 받는 Method는 인터페이스 쪽이다. 구현 클래스에 붙은 어노테이션은 구현 메서드를 찾아야 보인다
        Method implementation = targetClass.getMethod(interfaceMethod.getName(), interfaceMethod.getParameterTypes());
        return implementation.isAnnotationPresent(Timed.class);
    } catch (NoSuchMethodException e) {
        return false;
    }
}

/** 프록시 자신의 참조로 답한다. 같은 프록시끼리만 같고, hashCode는 그와 맞는 identityHashCode다. target의 메서드는 부르지 않는다. */
private static Object objectMethod(Object self, Object target, Method method, Object[] args) {
    return switch (method.getName()) {
        case "equals" -> self == args[0];
        case "hashCode" -> System.identityHashCode(self);
        // target + "" 는 target.toString()을 부른다. 클래스 이름만 쓰고 프록시 자신의 identity로 구분한다
        case "toString" -> "TimedProxy@" + Integer.toHexString(System.identityHashCode(self))
                + "(" + target.getClass().getName() + ")";
        default -> throw new IllegalStateException("프록시로 들어올 수 없는 Object 메서드: " + method);
    };
}

private static Object invoke(Object target, Method method, Object[] args) throws Throwable {
    try {
        return method.invoke(target, args);
    } catch (InvocationTargetException e) {
        // 대상이 던진 원래 예외를 꺼내 던진다. 그대로 두면 호출한 쪽은 UndeclaredThrowableException을 받는다
        throw e.getCause();
    }
}
// AuditStats
public static Map<String, Long> countByAction(List<AuditEntry> entries) {
    Map<String, Long> counts = entries.stream()
            .map(AuditEntry::action)
            // groupingBy는 null 키에서 NPE를 던지므로 먼저 거른다
            .filter(Objects::nonNull)
            .collect(Collectors.groupingBy(action -> action, Collectors.counting()));
    // groupingBy는 Map의 종류·불변 여부를 약속하지 않는다(지금 JDK는 가변 HashMap). 복사해 불변으로 내준다
    return Map.copyOf(counts);
}
// UploadLimits
private final int rows;
private final long fileBytes;

public UploadLimits(int rows, long fileBytes) {
    if (rows < 1 || rows > MAX_ROWS) {
        throw new IllegalArgumentException("행 수는 1~" + MAX_ROWS + "이어야 합니다: " + rows);
    }
    if (fileBytes < 1 || fileBytes > MAX_FILE_BYTES) {
        throw new IllegalArgumentException("파일 크기는 1~" + MAX_FILE_BYTES + "바이트여야 합니다: " + fileBytes);
    }
    // final 필드는 생성자에서 딱 한 번 대입한다. 빠뜨리거나 두 번 대입하면 컴파일 오류다
    this.rows = rows;
    this.fileBytes = fileBytes;
}

왜 이렇게 쓰나:

  1. 기록은 finally에서 남긴다. 성공한 호출만 남기면 장애 때 가장 궁금한 "실패한 시도"가 빠진다. D10 AuditLogAspect도 실패를 result=FAILURE로 따로 남긴다.
  2. 프록시는 밖에서 들어오는 호출만 가로챈다. 대상 객체 안의 this는 프록시가 아니라 원본이다. 그래서 어노테이션은 public 메서드에 붙이고 다른 객체에서 부르게 설계한다(같은 클래스 안 호출이 필요하면 메서드를 다른 빈으로 옮긴다).
  3. 설정 한도는 static final 상수로 이름을 붙이고, 객체의 값은 private final로 생성자에서 한 번만 정한다. 바뀔 수 없는 값은 "누가 언제 바꿨나"를 추적할 일이 없다.

#오늘 Spring에서 다시 만나는 곳

  • D10 ② board-server/src/main/java/com/example/board/admin/AdminService.java — hidePost에 @Audited(action = "HIDE_POST", targetType = "POST")와 @Transactional이 함께 붙어 있다. 둘 다 프록시가 처리하므로 다른 빈(컨트롤러)에서 불러야 동작한다. 같은 단계의 함정이 "같은 클래스 안에서 @PreAuthorize 메서드를 부르면 USER도 통과한다"이다.
  • D10 ③ board-server/src/main/java/com/example/board/admin/Audited.java — @Target(METHOD), @Retention(RUNTIME). 주석에 "public 메서드에 붙이고, 다른 빈에서 불러야 한다(같은 클래스 안 this 호출·private 메서드는 기록되지 않는다)"라고 적혀 있다.
  • D10 ④ board-server/src/main/java/com/example/board/admin/AuditLogAspect.java — @Around("@annotation(audited)")가 오늘 만든 InvocationHandler 자리다. joinPoint.proceed()가 method.invoke이고, 실패하면 기록을 남긴 뒤 원래 예외를 다시 던진다(기록 실패는 addSuppressed로 붙인다).
  • D10 ⑤ board-server/src/main/java/com/example/board/admin/CouponBulkIssueService.java — @Audited(action = "BULK_ISSUE_COUPON", targetType = "COUPON"). 감사 로그의 action 값이 오늘 기본기에서 센 키다.
  • D10 ⑤ board-server/src/main/java/com/example/board/admin/ExcelMemberIdReader.java — static final long MAX_BYTES = 5L * 1024 * 1024, static final int MAX_ROWS = 1000. 오늘 UploadLimits의 상수와 같은 한도다.
