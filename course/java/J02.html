#타입 한 컷

long vs Long — 엔티티 id는 왜 Long인가.

long (기본형) Long (래퍼)
저장 전 id 값 0 (기본값) null
"아직 저장 전"을 표현 못 한다. 0이 저장 전인지 0번 글인지 모른다 id == null이면 저장 전
JPA(Spring Data)의 신규 판단 기본형이면 0을 신규로 본다(규칙을 외워야 한다) null이면 신규 → INSERT, 아니면 기존 → 병합
담을 수 있는 곳 필드·지역 변수 필드·지역 변수·제네릭(Map<Long, Post>)

함정: id를 long으로 선언하면(PrimitiveIdPost) 저장 전에도 getId()가 0이다. "아직 저장 전"이라는 상태를 타입이 표현하지 못한다.

#실무 습관

Lombok이 만드는 코드. 이 모듈은 Lombok을 쓰지 않는다. 대신 애노테이션이 만들어 주는 코드를 손으로 써 본다. 이 칸의 과제는 전부 선택 과제다. 기본 완료 조건(--tests 'J02*' 17개)에는 들어가지 않는다. 아래 표와 LeakyCoupon 설명은 D03부터 엔티티를 읽을 때 필요하니 과제를 건너뛰더라도 읽고 간다. 아래 표의 "만들어지는 코드"는 Lombok 1.18.46의 delombok 출력에서 @Generated 같은 표시만 걷어 낸 것이다.

애노테이션 만들어지는 코드 주의
@Getter 필드마다 public 타입 getX() { return this.x; } boolean 필드는 isX(). 필드 이름이 isOpen이면 isIsOpen이 아니라 isOpen(). Boolean(래퍼) 필드는 getX()
@RequiredArgsConstructor final이고 선언에서 초기화하지 않은 필드만 선언 순서대로 받는 public 생성자 private final Set<Long> ids = new HashSet<>();처럼 초기화한 final 필드와 final이 아닌 필드는 받지 않는다(@NonNull을 붙인 비-final 필드는 예외로 받는다)
@Builder (생성자에 붙임) public static XBuilder builder(), 중첩 클래스 XBuilder(매개변수마다 같은 이름의 필드와 this를 돌려주는 메서드, build()) 빌더에서 넣지 않은 값은 오류 없이 null·0이 된다. 검사는 생성자에 둔다
@NoArgsConstructor(access = PROTECTED) protected X() {} JPA가 리플렉션으로 쓰는 빈 생성자. 밖에서 new X()를 막는다
@Setter 필드마다 public void setX(타입 x) 엔티티 규칙을 거치지 않고 아무 곳에서나 값을 바꾼다
@AllArgsConstructor 모든 필드를 받는 public 생성자 id·발급 수량처럼 밖에서 정하면 안 되는 값까지 받는다

주어진 LeakyCoupon은 @Getter @Setter @NoArgsConstructor @AllArgsConstructor를 붙인 쿠폰 엔티티를 delombok한 코드다. new LeakyCoupon(1L, "웰컴 쿠폰", 10, 50)도, setIssuedQuantity(999)도 막지 못해 총량보다 많이 발급된 쿠폰이 생긴다.

과제(선택):

  1. Coupon을 @Getter @NoArgsConstructor(access = PROTECTED) + private 생성자 모양으로 손으로 채운다. 검사는 private 생성자 한 곳에 둔다(이름이 비었거나 총량이 1보다 작으면 IllegalArgumentException). 발급 수량은 issue()로만 바뀐다(소진이면 IllegalStateException). 빌더 테스트 말고는 주어진 같은 패키지 전용 팩토리 Coupon.create(name, totalQuantity)로 쿠폰을 만든다(Lombok에는 없는 메서드다. 빌더를 채우지 않아도 1·2를 풀 수 있게 둔 것이다).
  2. CouponIssueService를 @RequiredArgsConstructor가 만들 모양으로 채운다. 쿠폰은 생성자로 받고, 받은 회원 id 집합은 선언에서 바로 만든다. issue(memberId)는 1인 1매다.
  3. @Builder가 private 생성자에 붙었을 때 만들 코드 — public static CouponBuilder builder()와 중첩 클래스 CouponBuilder — 를 손으로 채운다.

선택 과제 테스트 — J02HabitTest (클래스 전체에 @Tag("optional"). 기본 실행 --tests 'J02*'에는 들어가지 않고 ./gradlew :java-track:optionalTest --tests 'J02*'로 돌린다):

  • Setter와_전체_생성자가_열린_쿠폰은_총량을_넘는_발급_수량을_막지_못한다_Coupon은_막는다
  • 쿠폰은_이름과_총량을_검사해_만들고_발급_수량은_0에서_시작한다
  • Coupon에는_public_생성자와_setter가_없다
  • RequiredArgsConstructor는_선언에서_초기화하지_않은_final_필드만_받는다
  • 한_회원에게는_한_번만_발급한다
  • 선택_빌더는_이름을_붙여_값을_넣고_발급_수량은_0에서_시작한다
  • 선택_빌더에서_총량을_빠뜨리면_0이_들어가_생성자_검사에_걸린다

#구현 예시

펼치기▸

왜 이렇게 쓰나:

  1. 예외마다 ErrorCode를 들려 보내면 받는 쪽은 BusinessException 하나만 잡고 코드로 응답을 고른다. 자식 예외(NotFoundException)는 코드를 생성자에서 정해 두므로 던지는 쪽은 대상과 id만 안다.
  2. Result는 생성자를 숨기고 이름 있는 static 팩토리(success·failure)로만 만든다. "값도 있고 에러 코드도 있는" 잘못된 조합을 만들 길이 없다. 엔티티 id를 Long으로 두는 것도 같은 생각이다. "아직 없음"을 null이라는 값으로 표현할 수 있어야 저장소가 신규와 기존을 가른다.
  3. 엔티티에는 @Setter·@AllArgsConstructor를 열지 않는다. 생성은 검사가 있는 생성자(빌더나 정적 팩토리를 거쳐)로, 변경은 issue() 같은 의도가 드러나는 메서드로만 한다. Lombok을 쓸 때도 이 모양이 나오도록 애노테이션을 고른다.
